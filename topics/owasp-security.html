OWASP (Open Worldwide Application Security Project) یک بنیاد غیرانتفاعی است و Top 10 آن یک سند آگاهی‌بخشی (awareness document) درباره رایج‌ترین و پرخطرترین دسته‌های ریسک در اپلیکیشن‌های وب است؛ استاندارد کامل امنیتی نیست (برای آن OWASP ASVS وجود دارد). هر آیتم یک «دسته» است که چندین CWE را پوشش می‌دهد.

تفاوت Insecure Design با پیاده‌سازی ناامن را بدانید: Insecure Design یعنی کنترل امنیتی لازم اصلاً طراحی نشده (مثلاً هیچ محدودیتی برای تعداد تلاش OTP در نظر گرفته نشده)؛ با کدنویسی بی‌نقص هم رفع نمی‌شود. پیاده‌سازی ناامن یعنی طراحی درست بوده ولی کد باگ دارد. راه مقابله Insecure Design: threat modeling، الگوهای طراحی امن و abuse case در کنار use case.

Broken Access Control و IDOR

Authentication می‌پرسد «تو کی هستی؟»؛ Authorization می‌پرسد «اجازه انجام این کار روی این منبع را داری؟». Broken Access Control یعنی کاربر بتواند خارج از مجوزش عمل کند. رایج‌ترین شکل آن IDOR (Insecure Direct Object Reference) است: سرور شناسه منبع را از کاربر می‌گیرد و بدون بررسی مالکیت، منبع را برمی‌گرداند یا تغییر می‌دهد.

انواع

  • Horizontal privilege escalation: دسترسی به داده کاربر دیگر هم‌سطح (سفارش‌های کاربر دیگر).
  • Vertical privilege escalation: انجام عمل نقش بالاتر (کاربر عادی endpoint ادمین را صدا می‌زند).
  • دستکاری پارامتر یا فیلد مخفی (role=admin، price=0)، force browsing به URLهای پنهان، تکیه بر مخفی‌کردن دکمه در UI، و متدهای HTTP محافظت‌نشده (GET بررسی می‌شود ولی DELETE نه).
<?php
// نادرست: IDOR — هر کاربر لاگین‌کرده هر فاکتوری را می‌بیند
Route::get('/invoices/{id}', function (int $id) {
    return Invoice::findOrFail($id);
})->middleware('auth');

راه مقابله در Laravel

<?php
// app/Policies/InvoicePolicy.php  (با auto-discovery نیازی به ثبت دستی نیست)
final class InvoicePolicy
{
    public function before(User $user, string $ability): ?bool
    {
        return $user->isAdmin() ? true : null; // null یعنی برو سراغ متد اصلی
    }

    public function view(User $user, Invoice $invoice): bool
    {
        return $invoice->user_id === $user->id;
    }

    public function update(User $user, Invoice $invoice): Response
    {
        return $invoice->user_id === $user->id
            ? Response::allow()
            : Response::denyAsNotFound(); // 404 به‌جای 403 تا وجود منبع لو نرود
    }
}

// Controller
public function show(Invoice $invoice)
{
    Gate::authorize('view', $invoice); // در صورت عدم مجوز AuthorizationException → 403
    return new InvoiceResource($invoice);
}

// یا روی route
Route::put('/invoices/{invoice}', [InvoiceController::class, 'update'])
    ->middleware('auth')
    ->can('update', 'invoice');

// یا محدودکردن خود کوئری به داده‌های کاربر (دفاع اضافه)
$invoice = $request->user()->invoices()->findOrFail($id);

// Scoped binding: پست حتماً متعلق به همین کاربر باشد
Route::get('/users/{user}/posts/{post}', fn (User $user, Post $post) => $post)
    ->scopeBindings();

در Blade برای نمایش شرطی از @can('update', $invoice) استفاده کنید، ولی یادتان باشد مخفی‌کردن دکمه کنترل دسترسی نیست؛ بررسی باید همیشه سمت سرور و در هر درخواست انجام شود.

اصول

  • Deny by default: هر چیزی که صریحاً مجاز نشده، ممنوع است.
  • بررسی مجوز در یک مکان متمرکز (Policy) نه پراکنده در کنترلرها.
  • UUID/ULID (HasUuids، HasUlids) حدس‌زدن شناسه را سخت می‌کند و جلوی enumeration را می‌گیرد، ولی جایگزین authorization نیست (security through obscurity).
  • تست خودکار برای سناریوهای منفی: «کاربر B نباید بتواند فاکتور کاربر A را ببیند».
  • در API چندمستأجری (multi-tenant)، global scope روی tenant_id + Policy.

در پاسخ به سوال IDOR حتماً بنویسید که مشکل نبود بررسی مالکیت/مجوز سمت سرور است، نه قابل حدس بودن id. راه‌حل اصلی Policy/Gate یا scope کردن کوئری به کاربر جاری است؛ UUID فقط لایه دفاعی تکمیلی است.

SQL Injection و سایر Injectionها

Injection وقتی رخ می‌دهد که داده غیرقابل‌اعتماد به‌عنوان بخشی از یک دستور یا کوئری به یک مفسر (SQL، shell، LDAP، template engine) فرستاده شود و مفسر نتواند کد را از داده تشخیص دهد.

<?php
// نادرست: concatenation
$email = $request->input('email');
$users = DB::select("SELECT * FROM users WHERE email = '$email'");
// ورودی: ' OR '1'='1  ← همه کاربران برگردانده می‌شوند
// ورودی: '; DROP TABLE users; --  ← اگر درایور چند statement را اجازه دهد

چرا Prepared Statement جلوی آن را می‌گیرد؟

در parameterized query، ساختار کوئری (با placeholder) و مقادیر جداگانه به دیتابیس ارسال می‌شوند؛ دیتابیس ابتدا کوئری را parse می‌کند و سپس مقدار را فقط به‌عنوان داده در آن قرار می‌دهد. هر چه کاربر بفرستد، هرگز بخشی از دستور SQL نمی‌شود. این با «escape کردن» تفاوت بنیادی دارد که به درستی تابع escape و charset وابسته است.

<?php
// درست: Eloquent و Query Builder به‌صورت خودکار از PDO binding استفاده می‌کنند
User::where('email', $request->input('email'))->first();

// درست: raw با placeholder
DB::select('SELECT * FROM users WHERE email = ?', [$email]);
DB::select('SELECT * FROM users WHERE email = :email', ['email' => $email]);
User::whereRaw('LOWER(email) = ?', [strtolower($email)])->get();
Order::selectRaw('SUM(total) as revenue')->whereRaw('created_at >= ?', [$from]);

// نادرست: متدهای raw با رشته الحاق‌شده — binding خودکار وجود ندارد
User::whereRaw("email = '$email'")->get();
DB::statement("UPDATE users SET name = '$name'");
Order::orderByRaw($request->input('sort'));

جاهایی که binding کمک نمی‌کند: نام ستون و جهت مرتب‌سازی

Placeholder فقط برای مقدار است؛ نام جدول، نام ستون، ASC/DESC و کلمات کلیدی را نمی‌توان bind کرد. برای اینها از allowlist استفاده کنید:

<?php
$sortable = ['created_at', 'total', 'status'];
$column = in_array($request->input('sort'), $sortable, true) ? $request->input('sort') : 'created_at';
$direction = $request->input('dir') === 'asc' ? 'asc' : 'desc';

Order::orderBy($column, $direction)->paginate();

// یا با validation
$request->validate(['sort' => ['nullable', Rule::in($sortable)]]);

سایر انواع Injection

  • Command Injection: exec("convert {$file} out.png") با نام فایل a.png; rm -rf /. مقابله: پرهیز از shell، استفاده از کتابخانه، یا escapeshellarg() برای هر آرگومان؛ در Laravel 10+ از Process::run([...]) با آرایه آرگومان استفاده کنید تا shell درگیر نشود.
  • NoSQL Injection: در MongoDB ارسال {"password": {"$ne": null}} به‌جای رشته. مقابله: اعتبارسنجی نوع ('password' => 'string').
  • LDAP / XPath / Header Injection و CRLF Injection در هدرها یا لاگ‌ها.
  • Server-Side Template Injection: کامپایل قالب از ورودی کاربر (مثلاً Blade::render($userInput)) که به اجرای کد می‌رسد.

دفاع چندلایه

  • کاربر دیتابیس اپلیکیشن با حداقل دسترسی (بدون DROP، GRANT، FILE).
  • اعتبارسنجی ورودی با نوع و قالب مشخص (allowlist)، اما به‌عنوان لایه تکمیلی نه جایگزین binding.
  • نمایش‌ندادن خطای SQL به کاربر (APP_DEBUG=false) تا error-based injection سخت شود.
  • WAF به‌عنوان لایه اضافه، نه راه‌حل اصلی.

اشتباه رایج: «چون از Eloquent استفاده می‌کنم، از SQL Injection در امانم». متدهای whereRaw، selectRaw، orderByRaw، havingRaw، DB::raw، DB::statement و DB::unprepared اگر رشته را با ورودی کاربر بسازید، آسیب‌پذیرند. همچنین نام ستون پویا در orderBy و where بدون allowlist.

انواع SQLi که ممکن است بپرسند: In-band (Union-based و Error-based: نتیجه در همان پاسخ)، Blind (Boolean-based و Time-based با SLEEP(): فقط رفتار پاسخ تغییر می‌کند) و Out-of-band (ارسال داده از طریق DNS/HTTP). همچنین Second-order: داده مخرب ذخیره می‌شود و بعداً در کوئری دیگری بدون binding استفاده می‌شود.

Cross-Site Scripting (XSS) و CSP

XSS یعنی تزریق اسکریپت مخرب به صفحه‌ای که مرورگر قربانی آن را از origin سایت معتبر می‌بیند؛ اسکریپت با همان دسترسی‌های سایت اجرا می‌شود: خواندن DOM، ارسال درخواست با کوکی‌های کاربر، سرقت توکن در localStorage، keylogging یا تغییر محتوای صفحه (phishing).

اصل کلیدی: Context-aware output encoding

Escape باید متناسب با context خروجی باشد: بدنه HTML، مقدار attribute (همیشه داخل کوتیشن)، داخل JavaScript، داخل URL و داخل CSS هر کدام encoding متفاوتی دارند. {{ }} فقط برای context بدنه و attribute کوتیشن‌دار HTML طراحی شده است.

  • برای URL کاربر، scheme را validate کنید ('website' => ['url:http,https']).
  • اگر کاربر باید HTML بنویسد (ویرایشگر WYSIWYG)، خروجی را با یک HTML sanitizer مبتنی بر allowlist (مثل HTML Purifier) پاکسازی کنید؛ هرگز با regex.
  • در فرانت‌اند textContent به‌جای innerHTML؛ React و Vue به‌طور پیش‌فرض escape می‌کنند ولی dangerouslySetInnerHTML و v-html همان {!! !!} هستند.
  • کوکی session با HttpOnly تا JS نتواند آن را بخواند (تأثیر XSS را کم می‌کند، رفعش نمی‌کند).
  • پاسخ‌های API با Content-Type: application/json و X-Content-Type-Options: nosniff.

Content Security Policy (CSP)

CSP یک هدر پاسخ است که به مرورگر می‌گوید از چه منابعی اجازه بارگذاری و اجرای اسکریپت، استایل، تصویر و … وجود دارد. یک لایه دفاعی دوم است: حتی اگر XSS تزریق شود، اسکریپت inline یا از دامنه ناشناس اجرا نمی‌شود.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  object-src 'none';
  base-uri 'self';
  frame-ancestors 'none';
  form-action 'self';
  • از 'unsafe-inline' و 'unsafe-eval' در script-src پرهیز کنید؛ به‌جایش nonce تصادفی برای هر پاسخ یا hash. در Laravel، Vite::useCspNonce() nonce را به تگ‌های اسکریپت Vite اضافه می‌کند.
  • ابتدا با Content-Security-Policy-Report-Only و گزارش‌گیری شروع کنید تا سایت نشکند، سپس enforce کنید.
  • frame-ancestors جایگزین مدرن X-Frame-Options برای مقابله با clickjacking است.

ترتیب دفاع در برابر XSS را این‌طور بنویسید: (۱) output encoding متناسب با context (اصلی‌ترین)، (۲) sanitize وقتی HTML لازم است، (۳) validation ورودی، (۴) CSP به‌عنوان defense in depth، (۵) کوکی HttpOnly برای کاهش اثر. و تأکید کنید که encoding باید در زمان خروجی انجام شود نه در زمان ذخیره، چون یک داده ممکن است در چند context استفاده شود.

هدر X-XSS-Protection منسوخ است و مرورگرهای مدرن فیلتر XSS را حذف کرده‌اند؛ آن را راهکار ذکر نکنید. راهکار مدرن CSP است.

CSRF و SameSite

Cross-Site Request Forgery: سایت مهاجم مرورگر قربانیِ لاگین‌کرده را وادار می‌کند درخواستی تغییردهنده وضعیت به سایت هدف بفرستد. چون مرورگر کوکی‌های سایت هدف را خودکار ضمیمه می‌کند، سرور درخواست را معتبر و از طرف کاربر می‌بیند. مهاجم پاسخ را نمی‌بیند؛ هدفش اثر جانبی است (انتقال وجه، تغییر ایمیل).

<!-- روی evil.example — به‌محض باز شدن صفحه ارسال می‌شود -->
<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000000">
</form>
<script>document.getElementById('f').submit()</script>

شرایط لازم برای CSRF

  • احراز هویت مبتنی بر چیزی که مرورگر خودکار می‌فرستد (کوکی، HTTP Basic، گواهی کلاینت).
  • درخواست تغییردهنده وضعیت که پارامترهایش قابل پیش‌بینی است.
  • نبود توکن غیرقابل حدس یا بررسی origin.

پس APIای که فقط با هدر Authorization: Bearer … احراز هویت می‌کند (توکن در کوکی نیست) ذاتاً در برابر CSRF آسیب‌پذیر نیست؛ چون مرورگر این هدر را خودکار اضافه نمی‌کند.

دفاع‌ها

  1. Synchronizer Token: توکن تصادفی مرتبط با session در هر فرم؛ سرور مقایسه می‌کند. سایت مهاجم به‌خاطر Same-Origin Policy نمی‌تواند توکن را بخواند.
  2. SameSite cookie: Strict (کوکی در هیچ درخواست cross-site ارسال نمی‌شود)، Lax (فقط در navigation سطح بالا با متد امن مثل GET ارسال می‌شود؛ POST cross-site بدون کوکی)، None (همیشه، به شرط Secure).
  3. بررسی هدرهای Origin/Referer و هدرهای Fetch Metadata (Sec-Fetch-Site) به‌عنوان لایه تکمیلی.
  4. متدهای امن (GET، HEAD) هرگز نباید وضعیت را تغییر دهند.
  5. برای عملیات حساس: احراز هویت مجدد (رمز فعلی، OTP).

  • middleware ValidateCsrfToken (در نسخه‌های قدیمی VerifyCsrfToken) روی گروه web فعال است و برای POST/PUT/PATCH/DELETE توکن را از فیلد _token یا هدر X-CSRF-TOKEN می‌خواند.
  • Laravel توکن را در کوکی XSRF-TOKEN هم قرار می‌دهد؛ Axios آن را خودکار در هدر X-XSRF-TOKEN برمی‌گرداند (الگوی double submit). Sanctum در حالت SPA بر همین مکانیزم تکیه دارد (/sanctum/csrf-cookie).
  • تنظیم same_site در config/session.php به‌طور پیش‌فرض lax است.
  • route‌های مستثنی‌شده (webhook) باید با روش دیگری احراز شوند، مثلاً امضای HMAC درخواست.

«آیا SameSite=Lax کافی است؟» پاسخ: یک لایه دفاعی قوی است ولی جایگزین کامل توکن نیست؛ چون (۱) GETهایی که اشتباهاً وضعیت را تغییر می‌دهند محافظت نمی‌شوند، (۲) درخواست از subdomain‌های همان site (مثلاً یک زیردامنه آسیب‌پذیر) same-site حساب می‌شود، (۳) مرورگرهای قدیمی پشتیبانی نمی‌کنند. پس توکن + SameSite.

CORS از CSRF محافظت نمی‌کند. CORS فقط تعیین می‌کند اسکریپت cross-origin بتواند پاسخ را بخواند؛ «درخواست‌های ساده» (مثل POST فرم با application/x-www-form-urlencoded) بدون preflight ارسال و روی سرور اجرا می‌شوند.

حملات رایج و مقابله

  • Brute force / Credential stuffing (استفاده از رمزهای لو رفته سایت‌های دیگر): rate limiting بر اساس ترکیب ایمیل + IP، lockout موقت، CAPTCHA پس از چند شکست، MFA.
  • User enumeration: پیام خطای یکسان برای «کاربر وجود ندارد» و «رمز اشتباه» و زمان پاسخ مشابه؛ همچنین در «فراموشی رمز» پیام عمومی «اگر حساب وجود داشته باشد ایمیل ارسال شد».
  • Session fixation: مهاجم یک session id معلوم را به قربانی تحمیل می‌کند و پس از لاگین قربانی، با همان id وارد می‌شود. مقابله: تولید session id جدید پس از لاگین و تغییر سطح دسترسی.
  • Session hijacking: سرقت کوکی با XSS یا شنود. مقابله: HttpOnly، Secure، HTTPS، انقضای مناسب.
  • Password reset ناامن: توکن قابل حدس یا بدون انقضا؛ توکن باید تصادفی، یک‌بارمصرف، با انقضای کوتاه و هش‌شده در DB باشد (Laravel همین کار را می‌کند).

MFA

Multi-Factor Authentication یعنی ترکیب حداقل دو عامل از دسته‌های مختلف: چیزی که می‌دانید (رمز)، چیزی که دارید (گوشی با TOTP، کلید سخت‌افزاری) و چیزی که هستید (بیومتریک). TOTP (مثل Google Authenticator) از SMS امن‌تر است (SMS در برابر SIM swap آسیب‌پذیر است). WebAuthn/Passkey در برابر phishing مقاوم است چون به origin سایت گره خورده. Laravel Fortify پشتیبانی آماده از 2FA مبتنی بر TOTP و recovery code دارد.

سوال «چرا MD5 برای رمز مناسب نیست ولی bcrypt هست؟»: نکته اصلی سرعت است. هش رمز باید عمداً کند باشد (work factor) تا brute force آفلاین پس از نشت دیتابیس گران شود؛ و salt داشته باشد تا rainbow table بی‌اثر شود و دو کاربر با رمز یکسان هش متفاوت داشته باشند. MD5 سریع است و برای این کاربرد طراحی نشده.

اشتباهات و حملات رایج

  • alg: none: کتابخانه‌هایی که توکن بدون امضا را می‌پذیرند. مقابله: الگوریتم مجاز را سمت سرور ثابت کنید و از header توکن نخوانید.
  • Algorithm confusion: سرور RS256 انتظار دارد ولی مهاجم توکن HS256 می‌سازد و کلید عمومی را به‌عنوان secret HMAC استفاده می‌کند. مقابله: allowlist الگوریتم.

  • نبود یا نادیده گرفتن exp، و بررسی‌نکردن iss، aud و nbf.
  • قرار دادن داده حساس در payload (فقط encode شده است).
  • ابطال (revocation): JWT stateless است و تا انقضا معتبر می‌ماند؛ logout یا تغییر رمز آن را باطل نمی‌کند. راه‌حل: عمر کوتاه access token (مثلاً ۵ تا ۱۵ دقیقه) + refresh token چرخشی (rotation) ذخیره‌شده سمت سرور، یا denylist بر اساس jti.
  • ذخیره در localStorage: با هر XSS قابل سرقت است. برای SPA هم‌دامنه، کوکی HttpOnly; Secure; SameSite امن‌تر است (ولی آن‌وقت باید CSRF را مدیریت کنید).
  • اعتماد به headerهای kid، jku یا x5u بدون اعتبارسنجی که به مهاجم اجازه می‌دهد کلید خودش را معرفی کند.

Mass Assignment و Insecure Deserialization

Mass Assignment

وقتی همه فیلدهای ورودی کاربر مستقیماً به مدل نسبت داده می‌شوند، مهاجم می‌تواند فیلدهایی را که در فرم نبوده‌اند (مثل is_admin، balance، role) به درخواست اضافه کند. این یک نوع Broken Access Control در سطح فیلد است (در OWASP API Security Top 10 نسخه 2019 آیتم مستقل Mass Assignment بود و در نسخه 2023 زیر Broken Object Property Level Authorization قرار گرفت).

<?php
// نادرست
$user->update($request->all());       // POST: name=Ali&is_admin=1

final class User extends Model
{
    protected $guarded = [];          // نادرست: همه فیلدها قابل پرشدن
}

// درست: allowlist در مدل
final class User extends Model
{
    protected $fillable = ['name', 'email', 'avatar'];
}

// درست‌تر: فقط داده اعتبارسنجی‌شده
$user->update($request->validated());
// یا صریح
$user->update($request->safe()->only(['name', 'avatar']));

// فیلدهای حساس فقط با کد صریح و پس از بررسی مجوز
Gate::authorize('promote', $user);
$user->forceFill(['is_admin' => true])->save();
  • $fillable (allowlist) از $guarded (denylist) امن‌تر است چون فیلد جدید به‌طور پیش‌فرض محافظت‌شده است.
  • forceFill و Model::unguard() محافظت را دور می‌زنند؛ فقط با داده مورد اعتماد.
  • Model::preventSilentlyDiscardingAttributes() در محیط توسعه باعث می‌شود فیلدهای غیر fillable به‌جای نادیده‌گرفته‌شدن بی‌صدا، exception بدهند و باگ زود دیده شود.
  • سمت خروجی هم مراقب باشید: $hidden یا بهتر، API Resource صریح تا password، توکن‌ها یا فیلدهای داخلی در JSON لو نروند (Excessive Data Exposure).

Insecure Deserialization

unserialize() در PHP می‌تواند اشیای هر کلاسی را بازسازی کند و متدهای جادویی (__wakeup، __destruct، __toString) آنها به‌طور خودکار اجرا می‌شوند. مهاجم با ساختن رشته serialize‌شده از کلاس‌های موجود در پروژه و vendor، یک زنجیره (POP chain / gadget chain) می‌سازد که به خواندن/نوشتن فایل یا اجرای کد از راه دور (RCE) می‌رسد. ابزارهایی مثل PHPGGC زنجیره‌های آماده برای فریم‌ورک‌های رایج دارند.

<?php
// نادرست
$prefs = unserialize($_COOKIE['prefs']);

// درست: فرمت داده‌ای بدون رفتار
$prefs = json_decode($request->cookie('prefs'), true, 512, JSON_THROW_ON_ERROR);

// اگر ناچارید: محدود کردن کلاس‌ها
$data = unserialize($payload, ['allowed_classes' => false]);
  • داده serialize‌شده‌ای که از کلاینت برمی‌گردد را امضا (HMAC) یا رمزنگاری کنید و قبل از deserialize امضا را بررسی کنید.
  • Laravel کوکی‌ها را با APP_KEY رمزنگاری و MAC می‌کند؛ به همین دلیل نشت APP_KEY بحرانی است: مهاجم می‌تواند داده رمزنگاری‌شده و signed URL جعل کند و در ترکیب با deserialization به RCE برسد. اگر نشت کرد: فوراً php artisan key:generate، با در نظر داشتن داده‌های رمزنگاری‌شده موجود (Laravel 11+ از APP_PREVIOUS_KEYS برای چرخش تدریجی پشتیبانی می‌کند).
  • دسته A08 فقط deserialization نیست: یکپارچگی نرم‌افزار هم هست؛ استفاده از CDN بدون Subresource Integrity، pipeline CI/CD بدون کنترل دسترسی، پکیج‌های بدون بررسی و auto-update بدون امضا.

چرا JSON امن‌تر از serialize است؟ چون json_decode فقط داده (آرایه، رشته، عدد) تولید می‌کند و هیچ کلاسی را نمونه‌سازی نمی‌کند، پس هیچ متد جادویی اجرا نمی‌شود. اصل کلی: هرگز داده غیرقابل‌اعتماد را به مکانیزمی که می‌تواند کد یا شیء بسازد ندهید.

SSRF و امنیت آپلود فایل

Server-Side Request Forgery

SSRF وقتی رخ می‌دهد که سرور به درخواست کاربر، به یک URL دلخواه درخواست بفرستد (پیش‌نمایش لینک، import از URL، webhook، دریافت آواتار). مهاجم از سرور به‌عنوان پراکسی برای دسترسی به منابعی استفاده می‌کند که از بیرون در دسترس نیستند:

  • Cloud metadata: http://169.254.169.254/ که در برخی پیکربندی‌ها credential موقت IAM را برمی‌گرداند.
  • سرویس‌های داخلی: http://localhost:6379 (Redis)، پنل‌های ادمین داخلی، Elasticsearch.
  • اسکن شبکه داخلی و پورت‌ها؛ استفاده از schemeهای دیگر (file://، gopher://).
<?php
// نادرست
$image = Http::get($request->input('avatar_url'))->body();

// بهتر
final class SafeUrlFetcher
{
    private const ALLOWED_HOSTS = ['cdn.partner.example', 'images.example.com'];

    public function fetch(string $url): string
    {
        $parts = parse_url($url);
        if (($parts['scheme'] ?? null) !== 'https' || ! in_array($parts['host'] ?? '', self::ALLOWED_HOSTS, true)) {
            throw new UnsafeUrl($url);
        }

        // اگر allowlist ممکن نیست: IP نهایی را resolve و رنج‌های خصوصی را رد کنید
        $ip = gethostbyname($parts['host']);
        if (! filter_var($ip, FILTER_VALIDATE_IP, FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE)) {
            throw new UnsafeUrl($url);
        }

        return Http::timeout(5)
            ->withOptions(['allow_redirects' => false]) // redirect به آدرس داخلی را ببندید
            ->get($url)
            ->throw()
            ->body();
    }
}
  • Allowlist دامنه‌ها بهترین دفاع است؛ denylist به‌راحتی دور زده می‌شود (نمایش‌های مختلف IP مثل 2130706433، IPv6، DNSهایی که به 127.0.0.1 resolve می‌شوند).
  • DNS rebinding: بین بررسی و درخواست، DNS به IP دیگری resolve شود؛ در صورت امکان به همان IP بررسی‌شده متصل شوید.
  • لایه شبکه: egress filtering، اجرای fetcher در شبکه ایزوله، و در AWS استفاده از IMDSv2 که نیاز به توکن session دارد.
  • پاسخ خام سرویس داخلی را به کاربر برنگردانید (جلوگیری از SSRF با خروجی قابل مشاهده).

امنیت آپلود فایل

ریسک‌ها: آپلود web shell (shell.php) و اجرای آن، XSS با فایل HTML یا SVG، path traversal با نام فایل ../../.env، DoS با فایل‌های بسیار بزرگ یا decompression bomb، و فایل‌های polyglot (هم تصویر معتبر و هم کد PHP).

<?php
use Illuminate\Validation\Rules\File;

$request->validate([
    'avatar' => ['required', File::image()->max(2 * 1024)],            // KB
    'doc'    => ['required', File::types(['pdf', 'docx'])->max(10 * 1024)],
]);

// نام تصادفی (hashName) تولید می‌شود؛ هرگز getClientOriginalName را مسیر نکنید
// 'private' = یک disk غیرعمومی تعریف‌شده در config/filesystems.php
$path = $request->file('doc')->store('documents', 'private');

// تحویل از طریق controller با بررسی مجوز
public function download(Document $document)
{
    Gate::authorize('view', $document);
    return Storage::disk('private')->download($document->path, $document->display_name);
}
  • اعتبارسنجی بر اساس محتوا (MIME واقعی)، نه فقط پسوند یا هدر Content-Type که کلاینت می‌فرستد؛ قوانین mimes/image در Laravel MIME را از محتوای فایل حدس می‌زنند.
  • allowlist پسوند و نوع؛ محدودیت اندازه در سه سطح: validation، upload_max_filesize/post_max_size در PHP، و client_max_body_size در Nginx.
  • ذخیره بیرون از document root یا روی object storage؛ اگر روی public است، اجرای PHP در آن مسیر را در وب‌سرور ببندید.
  • پردازش مجدد تصاویر (re-encode/resize) که metadata و payloadهای پنهان را حذف می‌کند.
  • SVG و HTML را به‌عنوان فایل فعال در نظر بگیرید؛ یا ممنوع کنید یا با Content-Disposition: attachment و از دامنه جدا سرو کنید.
  • در صورت نیاز اسکن بدافزار (ClamAV) به‌صورت async در Job.
# جلوگیری از اجرای اسکریپت در مسیر آپلود

HTTPS و TLS

  • TLS سه چیز می‌دهد: محرمانگی (رمزنگاری کانال)، یکپارچگی و احراز هویت سرور (گواهی امضاشده توسط CA). جلوی شنود و MITM را می‌گیرد.
  • فقط TLS 1.2 و 1.3؛ SSLv3، TLS 1.0 و 1.1 غیرفعال. cipher suiteهای مدرن با forward secrecy (ECDHE).
  • HSTS تا مرورگر هرگز با HTTP وصل نشود و حمله SSL stripping بی‌اثر شود.
  • پشت load balancer: $middleware->trustProxies(at: [...]) در Laravel 11 تا X-Forwarded-Proto درست تشخیص داده شود و URLها HTTPS ساخته شوند؛ در صورت نیاز URL::forceScheme('https').
  • در درخواست‌های خروجی هرگز اعتبارسنجی گواهی را خاموش نکنید (Http::withoutVerifying() یا 'verify' => false در production).
  • رمزنگاری at rest هم لازم است: دیسک/دیتابیس رمزشده، بکاپ‌های رمزشده، و رمزنگاری سطح فیلد برای داده‌های خیلی حساس.

پاسخ نمونه برای «تفاوت Encoding، Hashing و Encryption»: Encoding برای سازگاری است و امنیتی نمی‌دهد؛ Hashing یک‌طرفه و برای integrity و ذخیره رمز است (برای رمز باید کند و salted باشد)؛ Encryption دوطرفه با کلید و برای محرمانگی است. سپس یک مثال از هر کدام و یک اشتباه رایج (Base64 به‌عنوان رمزنگاری، یا encrypt کردن رمز عبور).

Misconfiguration، Secrets و وابستگی‌ها

Security Misconfiguration (A05)

  • APP_DEBUG=true در production: صفحه خطای دیباگ stack trace، کوئری‌ها، مسیر فایل‌ها و در مواردی متغیرهای محیطی (کلیدها و رمز دیتابیس) را نشان می‌دهد. همیشه APP_ENV=production و APP_DEBUG=false.
  • .env یا .git قابل دانلود: اگر document root وب‌سرور به جای public/ روی ریشه پروژه باشد، https://site/.env همه secretها را لو می‌دهد. document root باید فقط public/ باشد و دسترسی به فایل‌های نقطه‌دار مسدود شود.
  • ابزارهای توسعه باز: Telescope، Horizon، Debugbar، phpinfo()، phpMyAdmin بدون محافظت. Telescope و Horizon در production با Gate (viewTelescope، viewHorizon) محدود شوند یا نصب نشوند (--dev).
  • رمزهای پیش‌فرض، پورت‌های باز غیرضروری (Redis/MySQL روی اینترنت بدون رمز)، directory listing، نسخه افشاشده سرور (expose_php = Off، server_tokens off;).
  • نبود هدرهای امنیتی، CORS بیش از حد باز، S3 bucket عمومی.
  • XXE: پردازش XML با entity خارجی فعال که به خواندن فایل یا SSRF می‌رسد؛ در libxml نسخه 2.9 به بعد (که PHP 8 از آن استفاده می‌کند) بارگذاری entity خارجی به‌طور پیش‌فرض غیرفعال است و به همین دلیل libxml_disable_entity_loader() در PHP 8 منسوخ شد. هرگز LIBXML_NOENT را روی XML غیرقابل‌اعتماد فعال نکنید.

مدیریت Secretها

  • secret هرگز در کد یا مخزن git نباشد؛ فقط .env.example بدون مقدار واقعی commit شود و .env در .gitignore.
  • تزریق از محیط: متغیرهای محیطی CI/CD، Docker/Kubernetes Secrets، یا Secret Manager (HashiCorp Vault، AWS Secrets Manager) با کنترل دسترسی و audit log.
  • Laravel: php artisan env:encrypt فایل .env.encrypted می‌سازد که می‌توان commit کرد و کلیدش جدا (مثلاً LARAVEL_ENV_ENCRYPTION_KEY) در محیط deploy نگه‌داری می‌شود.
  • Rotation دوره‌ای و فوری پس از نشت؛ secret لو رفته در تاریخچه git با حذف فایل پاک نمی‌شود و باید باطل و عوض شود.
  • اسکن خودکار مخزن (gitleaks، trufflehog، GitHub secret scanning) و pre-commit hook.
  • secretها را لاگ نکنید؛ PHP 8.2 attribute #[\SensitiveParameter] مقدار پارامتر را در stack trace پنهان می‌کند.
  • کلید جدا برای هر محیط (dev/staging/prod) و هر سرویس، با حداقل دسترسی.

وابستگی‌های آسیب‌پذیر (A06)

  • composer audit (از Composer 2.4) پکیج‌های نصب‌شده را با پایگاه advisoryها مقایسه می‌کند؛ در CI اجرا شود تا build در صورت آسیب‌پذیری شکست بخورد. معادل فرانت: npm audit.
  • Dependabot یا Renovate برای PR خودکار به‌روزرسانی.
  • composer.lock را commit کنید و در production composer install (نه update) بزنید تا نسخه‌ها دقیقاً همان تست‌شده‌ها باشند.
  • نسخه PHP، Laravel و سیستم‌عامل را در بازه پشتیبانی امنیتی نگه دارید.
  • حذف پکیج‌های بلااستفاده (کاهش attack surface)؛ دقت به typosquatting و پکیج‌های کم‌اعتبار؛ تهیه SBOM برای شناخت دقیق زنجیره تأمین.

<?php
final class SecurityHeaders
{
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);

        $response->headers->set('X-Content-Type-Options', 'nosniff');
        $response->headers->set('X-Frame-Options', 'DENY');
        $response->headers->set('Referrer-Policy', 'strict-origin-when-cross-origin');
        $response->headers->set('Permissions-Policy', 'camera=(), microphone=(), geolocation=()');

        if ($request->isSecure()) {
            $response->headers->set('Strict-Transport-Security', 'max-age=31536000; includeSubDomains');
        }

        return $response;
    }
}

// bootstrap/app.php
->withMiddleware(fn (Middleware $m) => $m->append(SecurityHeaders::class))

HSTS را ابتدا با max-age کوتاه تست کنید؛ با includeSubDomains اگر زیردامنه‌ای HTTPS نداشته باشد از دسترس خارج می‌شود. preload عملاً برگشت‌ناپذیر است. این هدرها را می‌توان در Nginx هم با add_header … always; تنظیم کرد.

CORS

Same-Origin Policy (SOP) مرورگر اجازه نمی‌دهد اسکریپت یک origin (scheme + host + port) پاسخ درخواست به origin دیگر را بخواند. CORS مکانیزمی است که سرور با آن به‌صورت کنترل‌شده SOP را شل می‌کند و به originهای مشخص اجازه خواندن پاسخ را می‌دهد.

  • برای درخواست‌های غیرساده (متد PUT/DELETE، هدر سفارشی، Content-Type: application/json) مرورگر ابتدا preflight با متد OPTIONS می‌فرستد.
  • CORS یک مکانیزم مرورگر است؛ curl یا سرور مهاجم آن را رعایت نمی‌کنند. پس CORS کنترل دسترسی API نیست؛ authentication و authorization سر جای خودشان لازم‌اند.
<?php
// config/cors.php  (در Laravel 11: php artisan config:publish cors)
return [
    'paths' => ['api/*', 'sanctum/csrf-cookie'],
    'allowed_methods' => ['GET', 'POST', 'PUT', 'DELETE'],
    'allowed_origins' => ['https://app.example.com'],   // نه '*' برای API با credential
    'allowed_headers' => ['Content-Type', 'Authorization', 'X-XSRF-TOKEN'],
    'supports_credentials' => true,
    'max_age' => 600,
];

اشتباهات خطرناک CORS: (۱) بازتاب هر Origin در Access-Control-Allow-Origin همراه با Access-Control-Allow-Credentials: true؛ هر سایتی می‌تواند با کوکی کاربر داده او را بخواند. (۲) اعتماد به Origin: null. (۳) regex ضعیف مثل «شامل example.com» که example.com.evil.net را هم قبول می‌کند. مرورگرها ترکیب * با credentials را رد می‌کنند و همین باعث می‌شود برخی توسعه‌دهندگان به‌اشتباه origin را بازتاب دهند.

تمایز مهم: SOP جلوی خواندن پاسخ را می‌گیرد، نه ارسال درخواست را. به همین دلیل CORS در برابر CSRF محافظت نمی‌کند و CSRF دفاع جداگانه (توکن، SameSite) لازم دارد.

Logging و Monitoring امنیتی

A09 درباره این است که حمله رخ می‌دهد ولی کسی متوجه نمی‌شود یا پس از وقوع، شواهد کافی برای تحلیل وجود ندارد. لاگ بدون monitoring و alert ارزش کمی دارد.

چه چیزی لاگ شود

  • لاگین موفق و ناموفق، lockout، logout
  • تغییر رمز، ایمیل، فعال/غیرفعال کردن MFA، reset رمز
  • خطاهای authorization (403) و validation مشکوک
  • عملیات ادمین و تغییر نقش‌ها و مجوزها
  • تراکنش‌های مالی و عملیات حساس کسب‌وکار
  • خطاهای امضا/توکن نامعتبر، rate limit

چه چیزی لاگ نشود

  • رمز عبور (حتی ناموفق)، OTP، توکن، session id، کلید API
  • شماره کارت کامل، داده‌های حساس شخصی (یا mask شوند)
  • بدنه کامل درخواست‌ها بدون فیلتر
<?php
use Illuminate\Auth\Events\Failed;
use Illuminate\Auth\Events\Lockout;

// Listener برای رویدادهای احراز هویت Laravel
final class LogFailedLogin
{
    public function handle(Failed $event): void
    {
        Log::channel('security')->warning('auth.failed', [
            'email' => $event->credentials['email'] ?? null, // بدون password
            'ip'    => request()->ip(),
            'ua'    => request()->userAgent(),
        ]);
    }
}
  • Structured logging (JSON) با context ثابت: user id، IP، request id (correlation id)، زمان دقیق UTC.
  • جلوگیری از log injection: ورودی کاربر را در متن پیام concat نکنید؛ در context ساختاریافته بگذارید (CRLF می‌تواند خط لاگ جعلی بسازد).
  • لاگ متمرکز (ELK/OpenSearch، Loki، SIEM) خارج از سرور اپلیکیشن، تا مهاجم با نفوذ به سرور نتواند آن را پاک کند؛ کنترل دسترسی و retention مشخص.
  • Alerting روی الگوها: افزایش ناگهانی لاگین ناموفق، 403های پشت‌سرهم از یک کاربر، ورود ادمین از کشور جدید.
  • سیگنال‌های Laravel: Illuminate\Auth\Events\Login، Failed، Lockout، PasswordReset.
  • برنامه Incident Response: چه کسی، چه زمانی، چه اقدامی.

تعادل را در پاسخ نشان دهید: لاگ کافی برای تشخیص و تحلیل (forensics) و non-repudiation، ولی بدون نقض حریم خصوصی و بدون تبدیل لاگ به منبع نشت secret. لاگ بدون alert، تشخیص را به هفته‌ها بعد موکول می‌کند.

endpoint، پورت، پکیج و قابلیت غیرضروری حذف شود.

هیچ درخواستی به صرف بودن در شبکه داخلی مورد اعتماد نیست؛ هر درخواست احراز و مجوزسنجی شود.
Separation of Duties
عملیات حساس به تأیید بیش از یک نقش نیاز داشته باشد.

OWASP Top 10 چیست؟ پنج مورد از آیتم‌های نسخه 2021 را نام برده و هر کدام را با یک مثال و راه مقابله توضیح دهید.

تعریف: OWASP Top 10 یک سند آگاهی‌بخشی از بنیاد OWASP است که ده دسته از مهم‌ترین ریسک‌های امنیتی اپلیکیشن‌های وب را بر اساس داده‌های واقعی و نظرسنجی متخصصان رتبه‌بندی می‌کند. استاندارد کامل نیست (برای آن ASVS وجود دارد) ولی نقطه شروع مشترک تیم‌هاست.

  • A01 Broken Access Control: تغییر /orders/15 به /orders/16 و دیدن سفارش دیگران (IDOR). مقابله: Policy/Gate و scope کردن کوئری به کاربر، deny by default.

  • A03 Injection: whereRaw("email = '$email'") با ورودی ' OR 1=1 --؛ XSS هم اینجاست. مقابله: parameterized query، output encoding.
  • A05 Security Misconfiguration: APP_DEBUG=true در production یا .env قابل دانلود. مقابله: hardening، document root روی public/، چک‌لیست deploy.
  • A10 SSRF: قابلیت «دریافت تصویر از URL» که با http://169.254.169.254/ به metadata ابری دسترسی پیدا می‌کند. مقابله: allowlist، بلاک IPهای داخلی، غیرفعال‌کردن redirect.

SQL Injection چیست و چرا Prepared Statement از آن جلوگیری می‌کند؟ آیا استفاده از Eloquent به‌تنهایی امنیت کامل در برابر SQLi را تضمین می‌کند؟

تعریف: SQLi زمانی رخ می‌دهد که ورودی غیرقابل‌اعتماد با الحاق رشته وارد کوئری شود و دیتابیس نتواند کد را از داده تفکیک کند؛ نتیجه: دور زدن لاگین، خواندن/تغییر/حذف داده، و در مواردی اجرای دستور روی سرور.

چرا Prepared Statement کار می‌کند: ساختار کوئری با placeholder و مقادیر جداگانه به دیتابیس ارسال می‌شوند. دیتابیس ابتدا کوئری را parse و برنامه اجرا را ثابت می‌کند و سپس مقدار را فقط به‌عنوان literal داده قرار می‌دهد؛ پس هیچ ورودی‌ای نمی‌تواند ساختار کوئری را تغییر دهد. این برخلاف escape کردن است که به charset و درستی تابع escape وابسته است.

Eloquent: متدهای عادی (where، find، create) به‌صورت خودکار از PDO binding استفاده می‌کنند، ولی امنیت کامل تضمین نمی‌شود:

  • متدهای raw (whereRaw، selectRaw، orderByRaw، DB::raw، DB::statement، DB::unprepared) اگر رشته با ورودی ساخته شود، آسیب‌پذیرند. راه‌حل: آرگومان bindings، مثل whereRaw('price > ?', [$min]).
  • نام ستون و جهت sort قابل bind نیستند؛ orderBy($request->sort) باید با allowlist کنترل شود.
<?php
$col = in_array($request->sort, ['price', 'created_at'], true) ? $request->sort : 'created_at';
Product::where('category_id', $request->category)->orderBy($col)->get();

دفاع چندلایه: کاربر DB با حداقل دسترسی، خاموش بودن نمایش خطا، validation نوع ورودی، و WAF به‌عنوان لایه اضافه.

انواع XSS را تعریف و مقایسه کنید. تفاوت {{ }} و {!! !!} در Blade چیست و آیا {{ }} همه حالت‌ها را پوشش می‌دهد؟

تعریف: XSS تزریق اسکریپت به صفحه‌ای است که مرورگر قربانی آن را از origin سایت معتبر می‌داند؛ اسکریپت با دسترسی کامل سایت اجرا می‌شود (سرقت توکن، ارسال درخواست از طرف کاربر، تغییر صفحه).

  • Stored: payload در DB ذخیره می‌شود (کامنت، نام کاربری) و به همه نمایش داده می‌شود؛ خطرناک‌ترین چون قربانی‌ها زیادند.
  • Reflected: payload در URL است و سرور آن را بی‌درنگ در پاسخ بازتاب می‌دهد؛ نیاز به فریب کاربر برای کلیک روی لینک.
  • DOM-based: کاملاً سمت کلاینت؛ JS داده را از source ناامن (location.hash) به sink خطرناک (innerHTML، eval) می‌برد و ممکن است اصلاً به سرور نرسد.

Blade: {{ $x }} خروجی را با htmlspecialchars (با ENT_QUOTES و UTF-8) escape می‌کند؛ {!! $x !!} خروجی خام است و فقط برای HTML مورد اعتماد یا sanitize‌شده با کتابخانه allowlist (مثل HTML Purifier) مجاز است.

محدودیت‌های {{ }}:

  • در href، URL با scheme javascript: را متوقف نمی‌کند؛ scheme را validate کنید.
  • داخل <script> context جاوااسکریپت است؛ از @js() یا Js::from() استفاده کنید.
  • در attribute بدون کوتیشن یا داخل event handler (onclick) ناکافی است.
  • DOM XSS در JS فرانت را پوشش نمی‌دهد.

لایه‌های تکمیلی: CSP بدون unsafe-inline (با nonce)، کوکی HttpOnly، validation ورودی. اصل کلیدی: context-aware output encoding در زمان خروجی.

CSRF چیست و چه شرایطی برای وقوع آن لازم است؟ Laravel چگونه از آن جلوگیری می‌کند و نقش SameSite cookie چیست؟

تعریف: حمله‌ای که در آن سایت مهاجم مرورگر کاربرِ لاگین‌کرده را وادار به ارسال درخواست تغییردهنده وضعیت به سایت هدف می‌کند؛ چون مرورگر کوکی‌ها را خودکار ضمیمه می‌کند، سرور درخواست را مشروع می‌پندارد. مهاجم پاسخ را نمی‌بیند؛ هدفش اثر جانبی است.

شرایط: (۱) احراز هویت مبتنی بر credential خودکار مرورگر (کوکی)، (۲) عملیات حساس با پارامترهای قابل پیش‌بینی، (۳) نبود توکن غیرقابل‌حدس. به همین دلیل APIهایی که با هدر Authorization: Bearer کار می‌کنند ذاتاً مستعد CSRF نیستند.

Laravel:

  • middleware ValidateCsrfToken در گروه web برای متدهای POST/PUT/PATCH/DELETE توکن session را با _token فرم (@csrf) یا هدر X-CSRF-TOKEN/X-XSRF-TOKEN مقایسه می‌کند؛ عدم تطابق = خطای 419.
  • کوکی XSRF-TOKEN برای کتابخانه‌هایی مثل Axios که خودکار آن را در هدر برمی‌گردانند.
  • webhookها با validateCsrfTokens(except: [...]) مستثنی و با امضای HMAC احراز می‌شوند.

SameSite: Lax (پیش‌فرض Laravel) کوکی را در درخواست‌های cross-site فقط برای navigation سطح بالا با GET می‌فرستد؛ پس فرم POST مهاجم بدون کوکی می‌رسد. Strict هیچ‌وقت. ولی SameSite جایگزین کامل توکن نیست: GETهای تغییردهنده وضعیت، زیردامنه‌های same-site و مرورگرهای قدیمی. پس توکن + SameSite + GET امن.

نکته: CORS در برابر CSRF محافظت نمی‌کند، چون درخواست ساده بدون preflight اجرا می‌شود.

کد زیر چه مشکل امنیتی دارد و چگونه آن را اصلاح می‌کنید؟ Route::get('/api/orders/{id}', fn ($id) => Order::find($id))->middleware('auth:sanctum');

مشکل اصلی: IDOR (Broken Access Control، A01). کد فقط احراز هویت را بررسی می‌کند، نه مجوز؛ هر کاربر لاگین‌کرده با تغییر id سفارش‌های همه کاربران را می‌بیند. id عددی ترتیبی، enumeration را هم ساده می‌کند.

مشکلات فرعی:

  • برگرداندن مستقیم مدل: همه ستون‌ها (شاید فیلدهای داخلی یا حساس) در JSON سریال می‌شوند (Excessive Data Exposure).
  • find در صورت نبودن، null با کد 200 برمی‌گرداند.
  • نبود rate limit برای جلوگیری از enumeration گسترده.
<?php
// Policy
public function view(User $user, Order $order): Response
{
    return $order->user_id === $user->id
        ? Response::allow()
        : Response::denyAsNotFound();
}

// Route + Controller
Route::middleware(['auth:sanctum', 'throttle:api'])
    ->get('/api/orders/{order}', [OrderController::class, 'show']);

public function show(Order $order): OrderResource
{
    Gate::authorize('view', $order);
    return new OrderResource($order); // فقط فیلدهای مجاز
}

// جایگزین: scope کردن کوئری به کاربر
$order = $request->user()->orders()->findOrFail($id);

تکمیلی: استفاده از ULID/UUID حدس‌زدن را سخت می‌کند ولی جایگزین authorization نیست؛ تست خودکار منفی («کاربر B نباید سفارش A را ببیند») اضافه شود.

رمزهای عبور را چگونه باید ذخیره کرد؟ چرا MD5 و SHA-1 (و حتی SHA-256) مناسب نیستند؟ Salt و Pepper را توضیح دهید.

اصل: رمز عبور باید با یک تابع هش مخصوص رمز که عمداً کند، salted و قابل تنظیم (work factor) است ذخیره شود: Argon2id (توصیه مدرن، memory-hard) یا bcrypt (پیش‌فرض Laravel). هرگز متن ساده یا رمزنگاری برگشت‌پذیر.

چرا MD5/SHA مناسب نیستند:

  • برای سرعت طراحی شده‌اند؛ GPU میلیاردها هش در ثانیه محاسبه می‌کند، پس پس از نشت DB، brute force و dictionary attack آفلاین ارزان است.
  • بدون salt، با rainbow table شکسته می‌شوند و رمزهای یکسان هش یکسان دارند.
  • MD5 و SHA-1 علاوه بر این از نظر collision هم شکسته شده‌اند. SHA-256 برای integrity امن است ولی برای رمز چون سریع است مناسب نیست.

Salt: مقدار تصادفی یکتا برای هر رمز که کنار هش ذخیره می‌شود (مخفی نیست)؛ rainbow table را بی‌اثر می‌کند و حمله را مجبور می‌کند برای هر کاربر جداگانه انجام شود. bcrypt و Argon2 خودکار salt می‌سازند و در خروجی قرار می‌دهند.

Pepper: راز سراسری خارج از دیتابیس (مثلاً در secret manager) که به محاسبه اضافه می‌شود؛ اگر فقط DB نشت کند، هش‌ها قابل حمله نیستند. اختیاری است و چرخش آن دشوار.

<?php
$user->password = Hash::make($request->password);   // یا cast 'hashed'
Hash::check($request->password, $user->password);  // مقایسه امن
Hash::needsRehash($user->password);                // ارتقای cost

تکمیلی: سیاست طول حداقلی، بررسی رمزهای لو رفته (Password::uncompromised())، rate limit و MFA.

Session Fixation و Session Hijacking را توضیح دهید و راه‌های جلوگیری از آنها در Laravel را بنویسید.

Session Fixation: مهاجم یک session id معلوم (که خودش گرفته) را به قربانی تحمیل می‌کند (مثلاً از طریق لینک یا زیردامنه‌ای که کوکی تنظیم می‌کند). اگر سرور پس از لاگین همان id را نگه دارد، مهاجم با آن id به‌عنوان قربانی وارد می‌شود.

مقابله: تولید session id جدید پس از لاگین و هر تغییر سطح دسترسی؛ پذیرفتن session id فقط از کوکی (نه URL).

<?php
if (Auth::attempt($credentials)) {
    $request->session()->regenerate();
    return redirect()->intended('dashboard');
}

// Logout
Auth::logout();
$request->session()->invalidate();
$request->session()->regenerateToken();

Session Hijacking: سرقت session id معتبر از طریق XSS، شنود ترافیک HTTP، malware یا لاگ‌شدن id.

مقابله:

  • کوکی HttpOnly (عدم دسترسی JS)، Secure (فقط HTTPS)، SameSite؛ در config/session.php.
  • HTTPS همه‌جا + HSTS.
  • انقضای بی‌فعالیتی (lifetime) و انقضای مطلق برای عملیات حساس.
  • جلوگیری از XSS (ریشه رایج سرقت).
  • نمایش و امکان قطع sessionهای فعال؛ Auth::logoutOtherDevices($password) پس از تغییر رمز.
  • احراز هویت مجدد برای عملیات حساس (middleware password.confirm).
سایت شما با حمله Credential Stuffing روی صفحه لاگین مواجه شده است. چه اقداماتی انجام می‌دهید؟

تعریف: مهاجم لیست بزرگی از ترکیب ایمیل/رمز لو رفته از سایت‌های دیگر را به‌صورت خودکار امتحان می‌کند، با تکیه بر استفاده مجدد کاربران از رمز. معمولاً از IPهای متعدد (botnet) انجام می‌شود، پس محدودیت فقط بر اساس IP کافی نیست.

اقدامات فوری:

  • Rate limiting چندبعدی: بر اساس ایمیل + IP و همچنین فقط IP و فقط ایمیل (RateLimiter::for('login', …) و throttle:login).
  • CAPTCHA پس از چند تلاش ناموفق یا هنگام ترافیک مشکوک.
  • بررسی لاگ‌ها برای شناسایی حساب‌هایی که لاگین موفق داشته‌اند؛ اجبار به تغییر رمز و قطع sessionهای آنها.
  • مسدودسازی موقت در لایه WAF/CDN برای الگوهای bot.

اقدامات ساختاری:

  • MFA (حداقل برای حساب‌های حساس)؛ مؤثرترین دفاع.
  • رد رمزهای لو رفته هنگام ثبت‌نام و تغییر رمز: Password::min(12)->uncompromised().
  • پیام خطای عمومی و زمان پاسخ یکسان (جلوگیری از user enumeration).
  • اطلاع‌رسانی به کاربر درباره لاگین از دستگاه/مکان جدید.
  • Monitoring و alert روی نرخ Failed events و lockoutها (A09).

نکته: lockout دائمی حساب پس از چند شکست می‌تواند خودش ابزار DoS علیه کاربران شود؛ lockout موقت و تدریجی بهتر است.

مزایا و ریسک‌های امنیتی JWT را بیان کنید. چه اشتباهاتی در پیاده‌سازی JWT رایج است؟

تعریف: JWT توکن خودبسنده با ساختار header.payload.signature (هر بخش Base64URL) است. امضا (HS256 با کلید مشترک یا RS256/ES256 با جفت‌کلید) یکپارچگی و اصالت را تضمین می‌کند؛ payload رمزنگاری نشده است.

مزایا: stateless، بررسی بدون lookup دیتابیس، مناسب سیستم‌های توزیع‌شده، SSO و ارتباط سرویس‌به‌سرویس؛ با امضای نامتقارن، سرویس‌ها فقط کلید عمومی لازم دارند.

اشتباهات رایج:

  • پذیرش alg: none یا اعتماد به alg داخل توکن؛ و algorithm confusion (RS256 ← HS256 با کلید عمومی به‌عنوان secret). الگوریتم باید سمت سرور ثابت باشد.
  • secret ضعیف HS256 قابل brute force آفلاین.
  • نبود exp یا عمر طولانی؛ بررسی‌نکردن iss و aud.
  • داده حساس در payload.
  • ذخیره در localStorage که با XSS سرقت می‌شود.
  • نبود مکانیزم ابطال: logout یا تغییر رمز توکن را باطل نمی‌کند.

راه‌حل‌ها: access token کوتاه‌عمر (چند دقیقه) + refresh token چرخشی ذخیره‌شده سمت سرور با تشخیص استفاده مجدد؛ denylist بر اساس jti در Redis در صورت نیاز؛ کتابخانه معتبر با allowlist الگوریتم؛ کوکی HttpOnly برای SPA هم‌دامنه.

مقایسه: اگر ابطال فوری مهم است و یک سرویس دارید، session یا توکن opaque (مثل Sanctum که هش توکن را در DB نگه می‌دارد) ساده‌تر و امن‌تر است.

Mass Assignment چیست؟ کد User::create($request->all()) چه خطری دارد و تفاوت $fillable و $guarded چیست؟

تعریف: آسیب‌پذیری‌ای که در آن همه فیلدهای ارسالی کاربر به‌صورت دسته‌جمعی به ویژگی‌های مدل نسبت داده می‌شوند؛ مهاجم فیلدهایی را که در فرم نبوده (مثل is_admin، role، balance، email_verified_at) به درخواست اضافه می‌کند و آنها را تغییر می‌دهد. نتیجه: privilege escalation یا دستکاری داده.

خطر کد: $request->all() هر چیزی را که کاربر فرستاده شامل می‌شود. اگر مدل $guarded = [] داشته باشد، درخواست name=Ali&is_admin=1 یک ادمین می‌سازد.

  • $fillable: allowlist؛ فقط فیلدهای نام‌برده mass-assignable هستند. فیلد جدید به‌طور پیش‌فرض محافظت‌شده است؛ امن‌تر.
  • $guarded: denylist؛ همه به جز فیلدهای نام‌برده. اگر ستون حساس جدیدی اضافه شود و فراموش شود، باز است. $guarded = [] یعنی محافظت خاموش.
<?php
// اصلاح
$user = User::create($request->validated());   // فقط فیلدهای قوانین FormRequest

// فیلد حساس: صریح، پس از authorization
Gate::authorize('changeRole', $user);
$user->forceFill(['role' => Role::Editor])->save();

بهترین روش: هر دو لایه: $fillable در مدل + استفاده از validated()/safe()->only(). در توسعه Model::preventSilentlyDiscardingAttributes() را فعال کنید. سمت خروجی هم با API Resource فقط فیلدهای مجاز را برگردانید.

SSRF را تعریف کنید. در یک قابلیت «وارد کردن تصویر از URL» چه ریسک‌هایی وجود دارد و چگونه آن را امن پیاده‌سازی می‌کنید؟

تعریف: Server-Side Request Forgery یعنی مهاجم سرور را وادار کند به URL دلخواه او درخواست بفرستد. سرور در شبکه داخلی و با اعتماد بیشتری نسبت به مهاجم قرار دارد، پس به‌عنوان پراکسی برای رسیدن به منابع داخلی استفاده می‌شود.

ریسک‌ها:

  • دسترسی به metadata ابری (169.254.169.254) و سرقت credential.
  • دسترسی به سرویس‌های داخلی بدون احراز هویت (Redis، Elasticsearch، پنل ادمین روی localhost).
  • اسکن پورت و شبکه داخلی؛ استفاده از schemeهای file:// و gopher://.
  • DoS با URL به فایل‌های بسیار بزرگ یا پاسخ کند.

پیاده‌سازی امن:

  • Allowlist دامنه‌ها در صورت امکان؛ فقط https.
  • در غیر این صورت: resolve کردن DNS و رد IPهای خصوصی، loopback، link-local و رزروشده (هم IPv4 هم IPv6)، و اتصال به همان IP بررسی‌شده (مقابله با DNS rebinding).
  • غیرفعال‌کردن redirect یا بررسی مجدد مقصد هر redirect.
  • timeout کوتاه، محدودیت اندازه پاسخ، بررسی Content-Type و اعتبارسنجی اینکه محتوا واقعاً تصویر است (re-encode).
  • اجرای دانلود در Job روی worker با شبکه ایزوله و egress filtering؛ در AWS استفاده از IMDSv2.
  • برنگرداندن پاسخ یا پیام خطای خام به کاربر.

نکته: denylist رشته‌ای (مثلاً رد «localhost») با نمایش‌های مختلف IP، دامنه‌هایی که به 127.0.0.1 resolve می‌شوند یا redirect به‌راحتی دور زده می‌شود.

برای یک قابلیت آپلود فایل (مدارک هویتی کاربران) چه کنترل‌های امنیتی پیاده می‌کنید؟

تهدیدها: آپلود web shell و اجرای کد، XSS با HTML/SVG، path traversal با نام فایل، DoS با فایل بزرگ، فایل polyglot، و نشت مدارک حساس به افراد غیرمجاز.

کنترل‌ها:

  1. Validation محتوا‌محور با allowlist: File::types(['jpg','png','pdf'])->max(5 * 1024)؛ MIME از محتوا تشخیص داده می‌شود نه از هدر کلاینت.
  2. محدودیت اندازه در validation، upload_max_filesize/post_max_size و client_max_body_size.
  3. نام تصادفی سمت سرور (store() با hashName)؛ نام اصلی فقط به‌عنوان metadata در DB.
  4. ذخیره خارج از document root روی disk خصوصی یا object storage خصوصی؛ عدم امکان اجرای PHP در مسیر آپلود.
  5. تحویل با بررسی مجوز: controller با Gate::authorize و Storage::download، یا temporary signed URL کوتاه‌عمر.
  6. پردازش مجدد تصویر (re-encode) برای حذف payload و metadata (مثل GPS در EXIF).
  7. رمزنگاری at rest برای مدارک هویتی (encryption سمت سرور storage).
  8. اسکن بدافزار به‌صورت async (Job + ClamAV) و قرنطینه تا پایان اسکن.
  9. هدرهای Content-Disposition: attachment و X-Content-Type-Options: nosniff هنگام سرو.
  10. rate limit روی endpoint آپلود و لاگ دسترسی به مدارک (audit).

$path = $request->file('id_card')->store("kyc/{$user->id}", 's3-private');
return Storage::disk('s3-private')->temporaryUrl($path, now()->addMinutes(5));
Encryption، Hashing و Encoding را تعریف و مقایسه کنید. برای هر کدام یک کاربرد درست و یک کاربرد نادرست مثال بزنید.
  • Encoding: تبدیل قالب داده برای انتقال یا سازگاری (Base64، URL encoding، HTML entities)؛ برگشت‌پذیر بدون کلید و هیچ امنیتی نمی‌دهد. درست: Base64 کردن فایل باینری برای JSON. نادرست: Base64 کردن رمز یا شماره کارت و «امن» دانستن آن (payload در JWT هم فقط encode شده است).
  • Hashing: تابع یک‌طرفه که خروجی با طول ثابت تولید می‌کند و تغییر کوچک ورودی آن را کاملاً عوض می‌کند. درست: SHA-256 برای checksum فایل، bcrypt/Argon2id برای رمز، HMAC-SHA256 برای امضای webhook. نادرست: MD5/SHA-1 برای رمز، یا هش بدون salt.
  • Encryption: تبدیل داده به ciphertext با کلید که فقط با کلید برگشت‌پذیر است؛ هدف: محرمانگی. متقارن (AES-256-GCM) یا نامتقارن (RSA/ECC). درست: رمزنگاری کد ملی با cast encrypted یا Crypt::encryptString؛ TLS برای انتقال. نادرست: رمزنگاری رمز عبور (اگر کلید لو برود همه رمزها لو می‌روند)، حالت ECB، کلید hardcode‌شده.

نکته Laravel: Crypt از APP_KEY و AES با MAC استفاده می‌کند تا دستکاری ciphertext تشخیص داده شود؛ ستون‌های encrypted قابل جست‌وجو با WHERE نیستند و چرخش کلید نیاز به برنامه دارد.

هنگام بررسی یک سرور production متوجه می‌شوید APP_DEBUG=true است و فایل https://site.com/.env قابل دانلود است. چه ریسک‌هایی وجود دارد و چه اقداماتی انجام می‌دهید؟

دسته: Security Misconfiguration (A05) با پیامد Information Disclosure.

ریسک‌ها:

  • .env شامل APP_KEY، رمز دیتابیس، کلیدهای API، SMTP و درگاه پرداخت است؛ با APP_KEY مهاجم می‌تواند کوکی و داده رمزنگاری‌شده و signed URL جعل کند و داده‌های encrypted را رمزگشایی کند.
  • صفحه دیباگ stack trace، کوئری SQL، مسیر فایل‌ها، نسخه‌ها و گاهی متغیرهای محیطی را نشان می‌دهد که شناسایی و حملات بعدی را تسهیل می‌کند.

اقدامات فوری (به ترتیب):

  1. APP_DEBUG=false و APP_ENV=production، سپس php artisan config:cache.
  2. اصلاح document root وب‌سرور به public/ و بستن مسیرهای نقطه‌دار.
  3. فرض نشت: چرخش همه secretها: رمز DB، کلیدهای API، APP_KEY (با برنامه برای داده رمزنگاری‌شده؛ APP_PREVIOUS_KEYS)، باطل کردن sessionها.
  4. بررسی access log برای درخواست‌های /.env و فعالیت مشکوک با credentialهای لو رفته؛ در صورت لزوم فرایند incident response.

پیشگیری: چک‌لیست deploy خودکار، اسکن پیکربندی در CI، تست خارجی مسیرهای حساس، مدیریت secret با secret manager و monitoring.

CORS چیست و چه ارتباطی با Same-Origin Policy دارد؟ یک پیکربندی اشتباه CORS و پیامد آن را توضیح دهید.

SOP: سیاست مرورگر که اجازه نمی‌دهد اسکریپت یک origin (scheme + host + port) پاسخ درخواست به origin دیگر را بخواند. SOP از داده‌های کاربر در سایت‌های دیگر محافظت می‌کند.

CORS: مکانیزمی با هدرهای HTTP که سرور با آن به‌طور کنترل‌شده SOP را برای originهای مشخص شل می‌کند (Access-Control-Allow-Origin، -Methods، -Headers، -Credentials). برای درخواست‌های غیرساده، مرورگر ابتدا preflight با OPTIONS می‌فرستد.

پیکربندی اشتباه رایج: سرور مقدار هدر Origin درخواست را بدون بررسی در Access-Control-Allow-Origin بازتاب می‌دهد و Access-Control-Allow-Credentials: true هم دارد. پیامد: هر سایت مخربی که کاربر لاگین‌کرده باز کند، می‌تواند با کوکی کاربر به API درخواست بزند و پاسخ را بخواند (پروفایل، توکن‌ها، داده‌های مالی). موارد مشابه: اعتماد به Origin: null و regex ضعیف دامنه.

<?php
// config/cors.php
'allowed_origins' => ['https://app.example.com'],
'supports_credentials' => true,

نکات کلیدی:

  • CORS کنترل دسترسی سمت سرور نیست؛ ابزارهای غیرمرورگری آن را نادیده می‌گیرند.
  • CORS از CSRF محافظت نمی‌کند؛ SOP جلوی ارسال درخواست ساده را نمی‌گیرد، فقط خواندن پاسخ را.
  • * برای API عمومی بدون credential قابل قبول است.
اصول «Least Privilege» و «Defense in Depth» را تعریف کنید و برای هر کدام مثال‌هایی در یک اپلیکیشن Laravel بزنید.

Least Privilege: هر موجودیت (کاربر، سرویس، پروسه، توکن) فقط حداقل دسترسی لازم برای انجام کارش را، فقط برای مدت لازم، داشته باشد. هدف: محدود کردن دامنه آسیب (blast radius) در صورت نفوذ.

  • کاربر دیتابیس اپ بدون DROP/GRANT؛ کاربر جدا برای migration.
  • PHP-FPM با کاربر غیر root؛ فقط storage و bootstrap/cache قابل نوشتن.
  • توکن‌های Sanctum با ability محدود (['orders:read']) و tokenCan().
  • نقش‌ها و Policyهای ریزدانه به‌جای «ادمین یا هیچ»؛ IAM policy محدود به یک bucket.

Defense in Depth: استفاده از چند لایه کنترل مستقل، تا شکست یا دور زده شدن یک لایه به نفوذ کامل منجر نشود.

  • XSS: output encoding در Blade + CSP + کوکی HttpOnly + validation.
  • SQLi: Eloquent bindings + allowlist ستون‌ها + کاربر DB محدود + خطای عمومی.
  • دسترسی: middleware auth + Policy + scope کوئری به کاربر/tenant + تست خودکار.
  • شبکه: WAF و rate limit + TLS + فایروال که DB و Redis را از اینترنت جدا می‌کند.
  • تشخیص: لاگ امنیتی + alert.

رابطه: این دو مکمل‌اند؛ least privilege اثر نفوذ را کم می‌کند و defense in depth احتمال موفقیت نفوذ را. هر دو بخشی از طراحی امن (پیشگیری از Insecure Design) هستند و همراه با fail securely و secure by default مطرح می‌شوند.

Threat Modeling چیست؟ مدل STRIDE را توضیح دهید و آن را روی یک endpoint «انتقال وجه» اعمال کنید.

Threat Modeling: فرایند ساختاریافته و ترجیحاً در فاز طراحی برای شناسایی تهدیدها و تعیین کنترل‌ها، با چهار سوال: چه می‌سازیم (DFD و trust boundary‌ها)؟ چه چیزی ممکن است خراب شود؟ چه می‌کنیم؟ آیا کافی بود؟ ابزار اصلی مقابله با Insecure Design است و Shift Left را محقق می‌کند.

STRIDE روی POST /transfers:

  • Spoofing (Authentication): استفاده از session دزدیده‌شده ← MFA یا تأیید OTP برای انتقال، کوکی امن.
  • Tampering (Integrity): تغییر مبلغ یا مقصد در مسیر یا دستکاری فیلد مخفی ← TLS، محاسبه و بررسی همه چیز سمت سرور، CSRF token.
  • Repudiation (Non-repudiation): کاربر انتقال را انکار می‌کند ← audit log غیرقابل تغییر با user، IP، زمان و شناسه درخواست.
  • Information Disclosure (Confidentiality): دیدن تراکنش دیگران با IDOR یا خطای دیباگ ← Policy، خطای عمومی، عدم افشای موجودی در پیام خطا.
  • Denial of Service (Availability): هزاران درخواست انتقال ← rate limit، timeout، صف.
  • Elevation of Privilege (Authorization): برداشت از حساب دیگران یا تغییر سقف انتقال با mass assignment ← Policy روی حساب مبدأ، $fillable، least privilege.

تکمیلی برای این endpoint: idempotency key برای جلوگیری از انتقال تکراری، تراکنش دیتابیس با lockForUpdate برای جلوگیری از race condition (برداشت هم‌زمان بیش از موجودی)، و محدودیت‌های کسب‌وکار (سقف روزانه).

  • A02 Cryptographic Failures ← bcrypt/Argon2id، TLS، encrypted
  • A03 Injection (+XSS) ← binding، output encoding
  • A04 Insecure Design ← threat modeling
  • A05 Security Misconfiguration (+XXE) ← APP_DEBUG=false، root=public/
  • A06 Vulnerable Components ← composer audit
  • A07 Auth Failures ← throttle، MFA، regenerate session
  • A08 Integrity Failures (+Deserialization) ← JSON، امضا، SRI
  • A09 Logging Failures ← لاگ + alert

Injection و XSS

  • Prepared statement: کد و داده جدا ارسال می‌شوند.
  • *Raw و DB::statement فقط با ? + آرایه bindings.
  • نام ستون/جهت sort ← allowlist.
  • Command injection ← Process::run([...]) یا escapeshellarg.
  • XSS: Stored، Reflected، DOM.
  • {{ }} = escape؛ {!! !!} = خام؛ @js() برای JS؛ scheme لینک را validate کن.
  • CSP با nonce، بدون unsafe-inline؛ اول Report-Only.

CSRF / CORS

  • CSRF = کوکی خودکار + اثر جانبی؛ Bearer header مصون است.
  • @csrf، X-CSRF-TOKEN، XSRF-TOKEN؛ خطای 419.
  • SameSite: Strict / Lax (پیش‌فرض) / None+Secure.
  • GET نباید وضعیت را تغییر دهد.
  • SOP خواندن پاسخ را می‌بندد نه ارسال را؛ CORS ≠ محافظت CSRF.
  • هرگز Origin بازتابی + credentials.

Auth و Session

  • رمز: Argon2id/bcrypt، salt خودکار، کند؛ MD5/SHA ممنوع.
  • Hash::make، Hash::check، cast hashed، Password::uncompromised().
  • Rate limit: ایمیل+IP؛ پیام خطای عمومی؛ MFA (TOTP > SMS، Passkey ضد phishing).
  • لاگین: session()->regenerate()؛ logout: invalidate() + regenerateToken().
  • کوکی: Secure، HttpOnly، SameSite.
  • hash_equals برای مقایسه توکن؛ random_bytes نه rand.

JWT

  • امضا ≠ رمزنگاری؛ payload قابل خواندن است.
  • alg ثابت سمت سرور (none و confusion)؛ secret قوی.
  • exp کوتاه + refresh token چرخشی؛ iss/aud.
  • ابطال سخت ← denylist jti یا توکن opaque (Sanctum).
  • localStorage در برابر XSS آسیب‌پذیر است.

Mass Assignment / Deserialization

  • $fillable (allowlist) > $guarded؛ هرگز $request->all()؛ از validated() استفاده کن.
  • unserialize روی ورودی ← POP chain/RCE؛ JSON یا allowed_classes => false.
  • نشت APP_KEY = بحرانی؛ چرخش با APP_PREVIOUS_KEYS.

SSRF / Upload

  • SSRF: metadata 169.254.169.254، سرویس‌های داخلی؛ allowlist، resolve + رد IP خصوصی، بدون redirect، egress filter.
  • Upload: MIME محتوا، allowlist، max size، نام تصادفی، خارج از web root، بدون اجرای PHP، دانلود با Policy.

Crypto / TLS

  • Encoding (بدون امنیت) / Hashing (یک‌طرفه) / Encryption (کلید، محرمانگی).
  • HMAC = integrity + authenticity؛ signed URL و webhook.
  • TLS 1.2+، HSTS، هرگز verify=false؛ trustProxies.

Config / Secrets / Deps

  • APP_DEBUG=false، root=public/، بستن .env/.git، Telescope با Gate.
  • secret در git نه؛ env:encrypt یا Vault؛ نشت = چرخش.
  • #[\SensitiveParameter] برای پنهان کردن در stack trace.
  • composer audit در CI، Dependabot، composer.lock commit شود.

Headers

  • HSTS، CSP، X-Frame-Options: DENY / frame-ancestors، nosniff، Referrer-Policy، Permissions-Policy.
  • X-XSS-Protection منسوخ است.

اصول و فرایند

  • CIA، Least Privilege، Defense in Depth، Fail Securely، Secure by Default، Zero Trust.
  • لاگ: لاگین/۴۰۳/تغییرات حساس؛ بدون رمز و توکن؛ لاگ متمرکز + alert.
  • STRIDE: Spoofing↔Authn، Tampering↔Integrity، Repudiation↔Non-repudiation، Info Disclosure↔Confidentiality، DoS↔Availability، EoP↔Authz.
  • SDLC: ASVS ← threat model ← SAST ← DAST/SCA ← pentest ← monitoring.
