Database Design

طراحی پایگاه داده‌ی رابطه‌ای از نیازمندی تا جدول: مدل مفهومی/منطقی/فیزیکی، ER، کلیدها، روابط، نرمال‌سازی تا BCNF با مثال کامل، Constraintها، انتخاب نوع داده، Soft delete، Polymorphic، Audit، ایندکس، مرور SQL و Migrationهای Laravel، همراه با یک case study فروشگاه آنلاین.

گام نیازمندی‌ها: چه سوال‌هایی بپرسیم؟

  • چه موجودیت‌هایی (اسم‌ها) داریم؟ مشتری، سفارش، محصول…
  • چه روابطی (فعل‌ها) بین آن‌هاست؟ «مشتری سفارش می‌دهد».
  • قواعد کسب‌وکار: آیا سفارش بدون مشتری معنا دارد؟ هر محصول چند دسته می‌تواند داشته باشد؟ حذف مشتری با سفارش‌هایش چه می‌کند؟
  • الگوهای دسترسی: پرتکرارترین کوئری‌ها چیست؟ نسبت خواندن به نوشتن؟ حجم داده و رشد؟
  • نیازهای غیرعملکردی: تاریخچه و audit، چندزبانه، چندمستأجره (multi-tenant)، منطقه‌ی زمانی، نگه‌داری داده (retention) و GDPR.

تفاوت سه سطح مدل سوال کلاسیک است. یک جمله‌ی خلاصه: Conceptual = «چه چیزی» (برای کسب‌وکار)، Logical = «چه ساختاری» (جداول و کلیدها، مستقل از محصول)، Physical = «چگونه» (پیاده‌سازی روی MySQL/PostgreSQL با نوع داده و ایندکس).

مدل ER و کاردینالیتی

Entity
شیء یا مفهومی که داده‌اش را نگه می‌داریم (Customer، Order). در مدل منطقی معمولاً یک جدول.
Entity Instance
یک نمونه‌ی مشخص (مشتری شماره‌ی ۴۲) → یک سطر.
Attribute
ویژگی موجودیت (name، email) → ستون.
Composite Attribute
ویژگی قابل تقسیم (address = city + street + zip).
Multi-valued Attribute
ویژگی با چند مقدار (چند شماره تلفن) → در مدل رابطه‌ای جدول جدا.
Derived Attribute
قابل محاسبه از بقیه (age از birth_date، total از آیتم‌ها) → معمولاً ذخیره نمی‌شود مگر برای کارایی.
Weak Entity
موجودیتی که بدون والد شناسایی نمی‌شود (OrderItem بدون Order). کلیدش شامل کلید والد است.
Relationship
ارتباط بین موجودیت‌ها؛ خودش هم می‌تواند attribute داشته باشد (quantity در رابطه‌ی سفارش-محصول).

کاردینالیتی (Cardinality) و مشارکت (Participation)

  • کاردینالیتی: حداکثر تعداد نمونه‌های طرف مقابل: 1:1، 1:N، M:N.
  • مشارکت (Optionality/Modality): حداقل تعداد: اجباری (حداقل یک) یا اختیاری (صفر هم مجاز). در پیاده‌سازی، اجباری بودن معمولاً با NOT NULL روی FK نمایش داده می‌شود.

نماد Crow's Foot

  ──o|──   صفر یا یک (zero or one)

  ──o<──   صفر یا بیشتر (zero or many)

برای پیدا کردن کاردینالیتی، رابطه را از هر دو طرف جمله‌بندی کنید: «یک مشتری چند سفارش می‌تواند داشته باشد؟ (چند)» و «یک سفارش به چند مشتری تعلق دارد؟ (یک)» → 1:N. اگر هر دو طرف «چند» بود → M:N و نیاز به جدول واسط.

کلیدها

Super Key
هر مجموعه از ستون‌ها که سطر را یکتا مشخص کند (ممکن است ستون اضافی داشته باشد).
Candidate Key
Super key کمینه؛ با حذف هر ستون دیگر یکتا نیست. ممکن است چند candidate key داشته باشیم (id، email، national_code).
Primary Key
candidate key انتخاب‌شده برای شناسایی سطر؛ یکتا، NOT NULL، و در حالت ایده‌آل تغییرناپذیر. هر جدول یک PK.
Alternate Key
candidate keyهایی که PK نشده‌اند → با UNIQUE اجبار می‌شوند.
Composite Key
کلید چندستونی، مثل (order_id, product_id) در جدول واسط.
Foreign Key
ستونی که به PK (یا unique key) جدول دیگر اشاره می‌کند و Referential Integrity را تضمین می‌کند.

Natural Key در برابر Surrogate Key

Natural Key

  • مقداری با معنای کسب‌وکاری (کد ملی، ISBN، email، کد کشور ISO).
  • بدون ستون اضافه؛ خوانا.
  • خطر: تغییر می‌کند (ایمیل عوض می‌شود)، فرمتش عوض می‌شود، یا یکتایی‌اش در واقعیت نقض می‌شود؛ و تغییر PK باید در همه‌ی FKها منتشر شود.
  • اغلب طولانی (رشته) → ایندکس‌ها بزرگ‌تر.

Surrogate Key

  • شناسه‌ی مصنوعی بی‌معنا (auto-increment، UUID، ULID).
  • پایدار، کوچک، یکنواخت؛ JOIN سریع.
  • عیب: نیاز به ستون اضافه و همچنان باید natural key را با UNIQUE محافظت کرد، وگرنه رکورد تکراری منطقی خواهیم داشت.

توصیه‌ی رایج: PK را surrogate بگیرید و natural key را UNIQUE کنید. استثنا: جداول lookup کوچک و پایدار (مثل کد ارز IRR، USD) و جداول واسط که composite key طبیعی دارند.

یک الگوی رایج: PK داخلی BIGINT auto-increment برای JOINهای سریع، به‌علاوه‌ی ستون public_id از نوع ULID/UUID یکتا برای استفاده در URL و API. در Laravel، traitهای HasUuids و HasUlids شناسه‌های مرتب زمانی تولید می‌کنند و ستون‌ها با $table->uuid() یا $table->ulid() ساخته می‌شوند.

پنهان کردن ID با UUID جایگزین Authorization نیست. حتی با شناسه‌ی غیرقابل حدس، باید بررسی کنید کاربر اجازه‌ی دسترسی به آن رکورد را دارد (Policy در Laravel).

پیاده‌سازی روابط

یک‌به‌یک (1:1)

FK با UNIQUE در یکی از دو طرف (معمولاً طرف اختیاری/وابسته). کاربرد: جدا کردن ستون‌های کم‌استفاده یا حجیم (پروفایل، تنظیمات)، داده‌ی حساس با دسترسی متفاوت، یا زیرنوع‌ها.

CREATE TABLE user_profiles (
  id         BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL UNIQUE,         -- UNIQUE = یک‌به‌یک
  bio        TEXT,
  avatar_url VARCHAR(500),
  CONSTRAINT fk_profile_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
-- راه دیگر: PK جدول فرزند همان FK باشد (shared primary key)
-- user_profiles(user_id PRIMARY KEY REFERENCES users(id))

یک‌به‌چند (1:N)

FK در طرف «چند». هر سفارش یک customer_id دارد.

CREATE TABLE orders (
  id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  customer_id BIGINT UNSIGNED NOT NULL,                -- NOT NULL = مشارکت اجباری
  status      VARCHAR(20) NOT NULL DEFAULT 'pending',
  created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT,
  INDEX idx_orders_customer_created (customer_id, created_at)
);

چندبه‌چند (M:N)

در مدل رابطه‌ای مستقیماً ممکن نیست؛ با جدول واسط (Junction/Pivot/Associative) به دو رابطه‌ی 1:N شکسته می‌شود. جدول واسط می‌تواند attributeهای خود رابطه را هم نگه دارد.

CREATE TABLE product_tag (
  product_id BIGINT UNSIGNED NOT NULL,
  tag_id     BIGINT UNSIGNED NOT NULL,
  created_at TIMESTAMP NULL,
  PRIMARY KEY (product_id, tag_id),                  -- جلوگیری از تکرار + ایندکس برای product → tags
  INDEX idx_tag_product (tag_id, product_id),        -- برای tag → products
  FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id)     REFERENCES tags(id)     ON DELETE CASCADE
);

وقتی رابطه‌ی M:N خودش داده و رفتار مهمی دارد (مثل enrollments بین دانشجو و درس با نمره و تاریخ، یا order_items با قیمت و تعداد)، آن را یک موجودیت مستقل ببینید: PK surrogate، مدل Eloquent جدا (یا Pivot model سفارشی) و قواعد خودش.

رابطه‌ی خودارجاع (Self-referencing)

-- دسته‌بندی درختی و کارمند/مدیر
CREATE TABLE categories (
  id        BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  parent_id BIGINT UNSIGNED NULL,
  name      VARCHAR(100) NOT NULL,
  FOREIGN KEY (parent_id) REFERENCES categories(id) ON DELETE SET NULL
);

برای درخت عمیق و کوئری «همه‌ی زیرشاخه‌ها» گزینه‌ها: Adjacency list (بالا) + WITH RECURSIVE، Materialized path (path = '1/4/9/')، Nested set، یا Closure table (جدول همه‌ی جفت‌های جد/نواده).

نرمال‌سازی: FD، ناهنجاری‌ها، 1NF تا BCNF

Functional Dependency (FD)

می‌گوییم X → Y (X تعیین‌کننده‌ی Y است) اگر هر دو سطری که در X مقدار یکسان دارند، در Y هم مقدار یکسان داشته باشند. مثال: customer_id → customer_name، (order_id, product_id) → quantity.

Full FD
Y به کل کلید ترکیبی وابسته است و نه به بخشی از آن.
Partial FD
Y فقط به بخشی از کلید ترکیبی وابسته است → نقض 2NF.
Transitive FD
A → B و B → C که B کلید نیست → C به‌طور غیرمستقیم به کلید وابسته است → نقض 3NF.
Determinant
طرف چپ یک FD (X در X → Y).

BCNF با مثال

جدول teaching(student, course, instructor) با قواعد: هر استاد فقط یک درس تدریس می‌کند (instructor → course)، هر دانشجو در هر درس یک استاد دارد ((student, course) → instructor).

  • Candidate keyها: (student, course) و (student, instructor).
  • همه‌ی ستون‌ها جزء یک candidate key هستند (prime attribute)، پس جدول در 3NF است.
  • اما instructor → course و instructor super key نیست → نقض BCNF. ناهنجاری: درس هر استاد در چند سطر تکرار می‌شود.
  • تجزیه: instructor_course(instructor PK, course) و student_instructor(student, instructor, PK(student, instructor)).
  • هزینه: قاعده‌ی (student, course) → instructor (هر دانشجو در یک درس فقط یک استاد) دیگر با یک constraint ساده قابل اجبار نیست (dependency preservation از دست می‌رود). به همین دلیل گاهی در 3NF می‌مانیم.

تفاوت 3NF و BCNF: 3NF اجازه می‌دهد determinant غیرکلید باشد اگر ستون وابسته جزئی از یک candidate key باشد؛ BCNF این استثنا را ندارد. BCNF سخت‌گیرانه‌تر است، اما تجزیه به BCNF همیشه حافظ وابستگی‌ها نیست، در حالی که تجزیه به 3NF همیشه می‌تواند هم lossless و هم dependency-preserving باشد. فرم‌های بالاتر (4NF برای multi-valued dependency، 5NF برای join dependency) در عمل کمتر مطرح‌اند.

تجزیه باید Lossless join باشد: با JOIN جداول حاصل، دقیقاً جدول اصلی (نه سطرهای جعلی اضافه) برگردد. شرط کافی: ستون مشترک بین دو جدول حاصل، کلید یکی از آن‌ها باشد.

Denormalization

Denormalization یعنی افزودن عمدی و کنترل‌شده‌ی افزونگی به یک Schema نرمال برای بهبود کارایی خواندن. ترتیب درست: اول نرمال طراحی کن، بعد با شواهد (اندازه‌گیری) denormalize کن.

چه زمانی توجیه دارد؟

  • کوئری‌های پرتکرار با JOIN/aggregate سنگین که با ایندکس حل نمی‌شوند (داشبورد، لیست محصولات با تعداد نظر).
  • نسبت خواندن به نوشتن بسیار بالا و داده‌ی تکراری کم‌تغییر.
  • گزارش‌گیری و Data Warehouse (Star Schema) که عمداً denormalized است.
  • Snapshot تاریخی که اصلاً denormalization نیست بلکه نیاز کسب‌وکار است (قیمت و آدرس در سفارش).

Constraintها و اکشن‌های FK

Constraintها آخرین خط دفاع از یکپارچگی داده هستند. Validation در برنامه لازم است، اما کافی نیست: چند سرویس، اسکریپت، race condition و باگ همه می‌توانند آن را دور بزنند.

CREATE TABLE products (
  id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  sku         VARCHAR(40)  NOT NULL,
  title       VARCHAR(200) NOT NULL,
  price       DECIMAL(12,2) NOT NULL,
  stock       INT NOT NULL DEFAULT 0,
  category_id BIGINT UNSIGNED NULL,
  CONSTRAINT uq_products_sku   UNIQUE (sku),
  CONSTRAINT ck_products_price CHECK (price >= 0),
  CONSTRAINT ck_products_stock CHECK (stock >= 0),
  CONSTRAINT fk_products_cat   FOREIGN KEY (category_id) REFERENCES categories(id)
      ON DELETE SET NULL ON UPDATE CASCADE
);
NOT NULL
مقدار اجباری. پیش‌فرض را NOT NULL بگیرید و فقط وقتی «ناشناخته/ناموجود» معنای واقعی دارد NULL مجاز کنید.
UNIQUE
یکتایی؛ معمولاً یک ایندکس یکتا می‌سازد. در اغلب DBMSها چند NULL در ستون UNIQUE مجاز است (NULL با NULL برابر نیست).
CHECK
شرط دلخواه روی سطر. در MySQL از 8.0.16 واقعاً اجرا می‌شود (قبل از آن parse و نادیده گرفته می‌شد).
DEFAULT
مقدار پیش‌فرض.
PRIMARY KEY
UNIQUE + NOT NULL؛ در InnoDB ترتیب فیزیکی ذخیره (clustered index) را هم تعیین می‌کند.
FOREIGN KEY
یکپارچگی ارجاعی؛ نمی‌توان به سطر ناموجود اشاره کرد.

CASCADE زنجیره‌ای خطرناک است: حذف یک کاربر می‌تواند ده‌ها هزار سطر را در چند جدول حذف کند، بدون اینکه Eloquent eventها (مثل deleting) اجرا شوند و بدون اینکه فایل‌های مرتبط پاک شوند. برای داده‌ی مالی و تاریخی از RESTRICT و soft delete استفاده کنید.

در PostgreSQL تفاوت RESTRICT و NO ACTION این است که NO ACTION را می‌توان deferrable کرد (بررسی در انتهای تراکنش). در MySQL/InnoDB این دو عملاً یکسان‌اند. همچنین InnoDB روی ستون FK اگر ایندکس نباشد خودش ایندکس می‌سازد، ولی PostgreSQL نه؛ آنجا باید خودتان ایندکس بگذارید.

انتخاب نوع داده

نوع داده‌ی درست هم صحت را تضمین می‌کند (تاریخ نامعتبر ذخیره نمی‌شود) و هم کارایی را (ستون کوچک‌تر = ایندکس کوچک‌تر = صفحه‌های بیشتر در حافظه).

پول: DECIMAL، نه FLOAT

FLOAT/DOUBLE اعداد ممیز شناور دودویی‌اند و مقادیری مثل 0.1 را دقیق نمایش نمی‌دهند؛ جمع هزاران تراکنش خطای گرد کردن انباشته می‌کند.

-- با FLOAT/DOUBLE: مقدار 0.1 دقیق قابل نمایش نیست و 0.1 + 0.2 می‌شود 0.30000000000000004
-- ✅
price DECIMAL(12,2) NOT NULL       -- 12 رقم کل، 2 رقم اعشار
-- یا ذخیره به کوچک‌ترین واحد پول به‌صورت عدد صحیح
amount_minor BIGINT NOT NULL       -- ریال، سنت
  • واحد پول را هم ذخیره کنید (currency CHAR(3)) اگر چندارزی هستید.
  • در PHP هم پول را با float حساب نکنید؛ از عدد صحیح (واحد خرد) یا کتابخانه‌هایی مثل brick/money یا bcmath استفاده کنید. Cast decimal:2 در Eloquent مقدار را به رشته برمی‌گرداند تا دقت حفظ شود.

قاعده‌ی طلایی: زمان را در UTC ذخیره کن و در لایه‌ی نمایش به منطقه‌ی زمانی کاربر تبدیل کن. در Laravel 'timezone' => 'UTC' در config/app.php را نگه دارید و در خروجی با Carbon ->setTimezone('Asia/Tehran') تبدیل کنید. استثنا: رویدادهای آینده‌ای که به «ساعت محلی» وابسته‌اند (جلسه ساعت ۹ صبح تهران) — آنجا زمان محلی + نام time zone را ذخیره کنید، چون قوانین DST/time zone ممکن است عوض شوند.

تاریخ شمسی را به‌عنوان رشته ذخیره نکنید. تاریخ میلادی/UTC ذخیره کنید و در نمایش تبدیل کنید؛ وگرنه مرتب‌سازی، بازه‌گیری و محاسبات تاریخ مشکل‌ساز می‌شود.

رشته‌ها: CHAR، VARCHAR، TEXT

  • CHAR(n): طول ثابت؛ برای کدهای با طول ثابت (کد کشور ISO، کد ارز).
  • VARCHAR(n): طول متغیر با سقف؛ برای اکثر رشته‌ها (نام، ایمیل، عنوان). سقف را بر اساس دامنه‌ی واقعی تعیین کنید (ایمیل حدود ۲۵۵ یا ۳۲۰).
  • TEXT: متن بلند (بدنه‌ی مقاله، توضیحات). در MySQL محدودیت‌هایی دارد: ایندکس کامل روی آن ممکن نیست (فقط prefix index یا FULLTEXT)، و ممکن است خارج از صفحه‌ی اصلی سطر ذخیره شود.
  • در PostgreSQL تفاوت کارایی VARCHAR(n) و TEXT عملاً وجود ندارد؛ سقف طول نقش constraint دارد.
  • Charset را utf8mb4 بگیرید (پشتیبانی کامل از یونیکد و emoji). utf8 قدیمی MySQL (utf8mb3) کاراکترهای ۴ بایتی را ذخیره نمی‌کند.

  • مناسب برای: داده‌ی نیمه‌ساختاریافته و متغیر که کمتر روی آن فیلتر/JOIN می‌شود: تنظیمات کاربر، payload وب‌هوک، ویژگی‌های متغیر محصول، metadata.
  • نامناسب برای: داده‌ای که روی آن JOIN، FK، constraint یا گزارش‌گیری مکرر دارید. اگر مدام WHERE json->'$.x' می‌زنید، احتمالاً باید ستون واقعی باشد.

  • کوچک‌ترین نوع عددی کافی: TINYINT/SMALLINT برای مقادیر کوچک؛ برای PK جداول بزرگ BIGINT UNSIGNED (پر شدن INT در حدود ۲.۱ میلیارد یا ۴.۲ میلیارد unsigned).

  • شماره تلفن، کد ملی، کد پستی: رشته نه عدد (صفر ابتدایی، عدم انجام عملیات ریاضی).
  • IP: در PostgreSQL نوع inet؛ در MySQL VARBINARY(16) یا VARCHAR(45).

Soft delete، Polymorphic و Audit

Soft Delete

به جای حذف فیزیکی، ستون deleted_at مقدار می‌گیرد و کوئری‌ها سطرهای حذف‌شده را نادیده می‌گیرند. در Laravel: $table->softDeletes() + trait SoftDeletes؛ global scope به‌طور خودکار whereNull('deleted_at') اضافه می‌کند.

مزایا

  • بازیابی (undo/سطل زباله).
  • حفظ یکپارچگی ارجاعی با داده‌ی تاریخی (فاکتورهای مشتری حذف‌شده).
  • ردگیری و audit ساده.

معایب

  • UNIQUE می‌شکند: کاربر حذف‌شده با email X مانع ثبت‌نام مجدد با همان email است.
  • FK و CASCADE معنایشان را از دست می‌دهند (دیتابیس از soft delete خبر ندارد).
  • هر کوئری خام/گزارش باید شرط را به یاد داشته باشد؛ JOINها به رکوردهای حذف‌شده می‌رسند.
  • رشد جدول و ایندکس‌ها؛ تضاد با حق حذف داده (GDPR).

راه‌حل‌های UNIQUE:

-- PostgreSQL: partial unique index
CREATE UNIQUE INDEX uq_users_email_active ON users(email) WHERE deleted_at IS NULL;

-- MySQL: ستون تولیدی که برای سطرهای حذف‌شده NULL است (NULLها در UNIQUE تکرارپذیرند)
ALTER TABLE users
  ADD COLUMN email_active VARCHAR(255)
    GENERATED ALWAYS AS (IF(deleted_at IS NULL, email, NULL)) STORED,
  ADD UNIQUE KEY uq_users_email_active (email_active);

جایگزین‌ها: جابه‌جایی رکورد حذف‌شده به جدول archive، یا جدول تاریخچه/رویداد. soft delete را فقط برای موجودیت‌هایی بزنید که واقعاً بازیابی یا ارجاع تاریخی لازم دارند، نه پیش‌فرض همه‌ی جداول.

Polymorphic Associations

یک جدول به چند نوع والد اشاره می‌کند، با دو ستون *_type و *_id. مثال: کامنت روی پست و ویدیو.

<?php
Schema::create('comments', function (Blueprint $table) {
    $table->id();
    $table->morphs('commentable');   // commentable_type + commentable_id + index ترکیبی
    $table->text('body');
    $table->timestamps();
});

// AppServiceProvider::boot — نام کلاس را مستقیم در دیتابیس ذخیره نکنید
Relation::enforceMorphMap([
    'post'  => Post::class,
    'video' => Video::class,
]);

مزایا

  • یک جدول و یک منطق برای همه‌ی انواع؛ افزودن نوع جدید بدون migration.
  • پشتیبانی خوب در Eloquent (morphTo، morphMany، morphToMany).

معایب

  • FK ممکن نیست (ستون id به چند جدول اشاره می‌کند) → خطر رکورد یتیم؛ cascade باید در برنامه انجام شود.
  • JOIN و گزارش‌گیری سخت‌تر.
  • اگر نام کلاس ذخیره شود، با refactor namespace داده می‌شکند (morph map لازم است).

جایگزین‌ها با یکپارچگی کامل: (۱) جدول جدا برای هر نوع (post_comments، video_comments)؛ (۲) چند FK nullable (post_id، video_id) با CHECK که دقیقاً یکی پر باشد؛ (۳) جدول supertype مشترک (commentables) که post و video به آن اشاره کنند.

مبانی طراحی ایندکس

ایندکس (معمولاً B+Tree) ساختاری مرتب روی یک یا چند ستون است که جست‌وجو، مرتب‌سازی و JOIN را از O(n) به حدود O(log n) می‌رساند. در عوض نوشتن را کندتر می‌کند و فضا می‌گیرد.

کجا ایندکس بگذاریم؟

  • ستون‌های پرتکرار در WHERE، JOIN ... ON، ORDER BY و GROUP BY.
  • همه‌ی FKها (برای JOIN و برای بررسی FK هنگام حذف والد).
  • ستون‌هایی با selectivity بالا (مقادیر متمایز زیاد). ایندکس تنها روی ستون boolean معمولاً بی‌فایده است، مگر داده خیلی نامتوازن باشد یا در ایندکس ترکیبی.

ایندکس ترکیبی و قاعده‌ی leftmost prefix

CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at);

-- ✅ استفاده می‌شود
SELECT * FROM orders WHERE user_id = 5;
SELECT * FROM orders WHERE user_id = 5 AND status = 'paid';
SELECT * FROM orders WHERE user_id = 5 AND status = 'paid' ORDER BY created_at DESC;
-- ❌ نه به‌طور مؤثر (ستون اول نیست)
SELECT * FROM orders WHERE status = 'paid';
  • ستون‌های برابری اول، سپس ستون بازه‌ای/مرتب‌سازی. بعد از اولین شرط بازه‌ای، ستون‌های بعدی برای جست‌وجو کمتر مؤثرند.
  • Covering index: اگر همه‌ی ستون‌های مورد نیاز کوئری در ایندکس باشند، جدول اصلاً خوانده نمی‌شود (در EXPLAIN مای‌اسکیوال: Using index).
  • ایندکس روی (a, b) ایندکس جداگانه روی (a) را زائد می‌کند.

چه چیزهایی ایندکس را بی‌اثر می‌کند

  • تابع روی ستون: WHERE YEAR(created_at) = 2026 → بنویسید created_at >= '2026-01-01' AND created_at < '2027-01-01'.
  • LIKE '%abc' (wildcard ابتدایی) → FULLTEXT یا موتور جست‌وجو.
  • تبدیل نوع ضمنی: مقایسه‌ی ستون VARCHAR با عدد.
  • OR روی ستون‌های مختلف (گاهی؛ با UNION یا index merge).
EXPLAIN SELECT * FROM orders WHERE user_id = 5 AND status = 'paid' ORDER BY created_at DESC LIMIT 20;
-- type: ref/range خوب، ALL = full scan؛ key: ایندکس انتخاب‌شده؛ rows: تخمین سطرها؛
-- Extra: "Using filesort" یا "Using temporary" = هشدار

Trade-off ایندکس را همیشه ذکر کنید: هر ایندکس هزینه‌ی INSERT/UPDATE/DELETE و فضا دارد؛ پس بر اساس کوئری‌های واقعی (slow query log، EXPLAIN) ایندکس بگذارید، نه روی همه‌ی ستون‌ها. در InnoDB هر secondary index، PK را هم در خود دارد؛ PK بزرگ (مثل UUID رشته‌ای) همه‌ی ایندکس‌ها را بزرگ می‌کند.

مرور SQL: JOIN، GROUP BY، Subquery

داده‌ی نمونه: customers(id, name) و orders(id, customer_id, total, created_at). مشتری ۳ هیچ سفارشی ندارد و سفارشی با customer_id ناموجود هم فرض کنید.

  INNER JOIN       LEFT JOIN        RIGHT JOIN       FULL OUTER JOIN
   ( A (∩) B )     (AAA(∩) B )      ( A (∩)BBB)      (AAA(∩)BBB)
  فقط مشترک‌ها      همه‌ی A + مطابق‌ها  همه‌ی B + مطابق‌ها  همه‌ی هر دو
-- INNER: فقط مشتریانی که سفارش دارند
SELECT c.name, o.id, o.total
FROM customers c
JOIN orders o ON o.customer_id = c.id;

-- LEFT: همه‌ی مشتریان، حتی بدون سفارش (ستون‌های o برایشان NULL)
SELECT c.name, COUNT(o.id) AS order_count     -- COUNT(o.id) نه COUNT(*)، تا مشتری بدون سفارش 0 شود
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

-- Anti-join: مشتریانی که هیچ سفارشی ندارند
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- CROSS JOIN: ضرب دکارتی (همه‌ی ترکیب‌ها)، مثلاً سایز × رنگ
SELECT s.name, col.name FROM sizes s CROSS JOIN colors col;

-- SELF JOIN: کارمند و مدیرش
SELECT e.name AS employee, m.name AS manager
FROM employees e LEFT JOIN employees m ON m.id = e.manager_id;

شرط روی جدول سمت راست LEFT JOIN را در WHERE بگذارید، LEFT JOIN عملاً به INNER JOIN تبدیل می‌شود (چون سطرهای NULL حذف می‌شوند). اگر می‌خواهید فقط سفارش‌های ۲۰۲۶ را join کنید ولی همه‌ی مشتریان بمانند، شرط را در ON بیاورید: LEFT JOIN orders o ON o.customer_id = c.id AND o.created_at >= '2026-01-01'. همچنین MySQL، FULL OUTER JOIN ندارد و با UNION یک LEFT و یک RIGHT شبیه‌سازی می‌شود.

GROUP BY و HAVING

-- مشتریانی که در 2026 بیش از 5 سفارش و مجموع خرید بالای 1000 داشته‌اند
SELECT customer_id, COUNT(*) AS cnt, SUM(total) AS spent
FROM orders
WHERE created_at >= '2026-01-01'          -- قبل از گروه‌بندی، روی سطرها
GROUP BY customer_id
HAVING COUNT(*) > 5 AND SUM(total) > 1000 -- بعد از گروه‌بندی، روی گروه‌ها
ORDER BY spent DESC;

ترتیب منطقی اجرا: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. به همین دلیل alias تعریف‌شده در SELECT در WHERE قابل استفاده نیست. در حالت ONLY_FULL_GROUP_BY (پیش‌فرض MySQL جدید)، هر ستون غیرتجمعی در SELECT باید در GROUP BY باشد یا به‌طور تابعی به آن وابسته باشد.

Subquery، EXISTS و CTE

-- Scalar subquery
SELECT name, (SELECT MAX(total) FROM orders o WHERE o.customer_id = c.id) AS max_order
FROM customers c;

-- IN
SELECT * FROM products WHERE id IN (SELECT product_id FROM order_items WHERE qty > 10);

-- EXISTS (correlated): معمولاً برای «آیا وجود دارد؟» مناسب است و در اولین مطابقت متوقف می‌شود
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.total > 500);

-- CTE + Window function: آخرین سفارش هر مشتری
WITH ranked AS (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
  FROM orders o
)
SELECT * FROM ranked WHERE rn = 1;

NOT IN با subqueryای که ممکن است NULL برگرداند، هیچ سطری برنمی‌گرداند (چون مقایسه با NULL نتیجه‌ی UNKNOWN دارد). برای anti-join از NOT EXISTS یا LEFT JOIN ... IS NULL استفاده کنید.

Migrationهای Laravel

Migrationها کنترل نسخه‌ی Schema هستند: هر تغییر یک فایل با timestamp، قابل بازبینی در Git و قابل اجرا یکسان روی همه‌ی محیط‌ها.

<?php
use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    public function up(): void
    {
        Schema::create('orders', function (Blueprint $table) {
            $table->id();                                              // BIGINT UNSIGNED AUTO_INCREMENT PK
            $table->ulid('public_id')->unique();
            $table->foreignId('customer_id')->constrained()->restrictOnDelete();
            $table->foreignId('coupon_id')->nullable()->constrained()->nullOnDelete();
            $table->string('status', 20)->default('pending');
            $table->decimal('subtotal', 12, 2);
            $table->decimal('total', 12, 2);
            $table->char('currency', 3)->default('IRR');
            $table->json('shipping_address');                          // snapshot
            $table->timestamp('paid_at')->nullable();
            $table->timestamps();
            $table->softDeletes();

            $table->index(['customer_id', 'created_at']);
            $table->index(['status', 'created_at']);
        });

        Schema::create('order_items', function (Blueprint $table) {
            $table->id();
            $table->foreignId('order_id')->constrained()->cascadeOnDelete();
            $table->foreignId('product_id')->constrained()->restrictOnDelete();
            $table->string('product_name');                            // snapshot
            $table->decimal('unit_price', 12, 2);
            $table->unsignedInteger('quantity');
            $table->unique(['order_id', 'product_id']);
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('order_items');
        Schema::dropIfExists('orders');
    }
};

بهترین روش‌ها

  • Migration اجراشده در production را ویرایش نکنید؛ یک migration جدید بسازید. ویرایش فایل قدیمی روی محیط‌هایی که قبلاً اجرا شده اثری ندارد و Schemaها واگرا می‌شوند.
  • متد down() را بنویسید و تست کنید (یا آگاهانه تصمیم بگیرید که rollback پشتیبانی نمی‌شود).
  • FK و ایندکس را در migration تعریف کنید، نه دستی روی دیتابیس.
  • در Laravel 11 به بعد، هنگام تغییر ستون با ->change() باید همه‌ی modifierهایی که می‌خواهید بمانند (nullable، default، comment…) را دوباره بنویسید؛ وگرنه حذف می‌شوند.
  • Migration داده (تبدیل داده‌ی موجود) را از تغییر Schema جدا کنید و برای جداول بزرگ به‌صورت دسته‌ای (chunkById) یا در job انجام دهید.
  • از مدل‌های Eloquent در migration استفاده نکنید (مدل در آینده تغییر می‌کند و migration قدیمی می‌شکند)؛ از DB::table() استفاده کنید.
  • تعداد زیاد migration را با php artisan schema:dump --prune فشرده کنید.

تغییرات بدون downtime (Expand / Contract)

برای تغییر نام یا نوع ستون در سیستم زنده، به جای یک تغییر شکننده، چند گام:

  1. Expand: ستون جدید را nullable اضافه کن.
  2. کد را deploy کن که در هر دو ستون بنویسد.
  3. داده‌های قدیمی را دسته‌ای منتقل کن (backfill).
  4. کد را deploy کن که از ستون جدید بخواند.
  5. Contract: ستون قدیمی را حذف و در صورت نیاز NOT NULL را اعمال کن.

افزودن ستون NOT NULL بدون default یا ساخت ایندکس روی جدول بسیار بزرگ می‌تواند جدول را قفل کند یا طول بکشد. نسخه‌ی DBMS، الگوریتم ALTER (در MySQL: INSTANT/INPLACE) و ابزارهای online schema change را در نظر بگیرید.

جداول کلیدی و تصمیم‌ها

CREATE TABLE users (
  id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  email       VARCHAR(255) NOT NULL UNIQUE,
  name        VARCHAR(150) NOT NULL,
  password    VARCHAR(255) NOT NULL,
  created_at  TIMESTAMP NULL, updated_at TIMESTAMP NULL
);

CREATE TABLE addresses (
  id        BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  user_id   BIGINT UNSIGNED NOT NULL,
  city      VARCHAR(100) NOT NULL,
  line1     VARCHAR(255) NOT NULL,
  postal_code VARCHAR(10) NOT NULL,
  is_default BOOLEAN NOT NULL DEFAULT FALSE,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE product_variants (
  id         BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  product_id BIGINT UNSIGNED NOT NULL,
  sku        VARCHAR(40) NOT NULL UNIQUE,
  price      DECIMAL(12,2) NOT NULL CHECK (price >= 0),
  stock      INT NOT NULL DEFAULT 0 CHECK (stock >= 0),
  attributes JSON NULL,                         -- {"color":"black","size":"L"}
  FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE CASCADE
);

CREATE TABLE orders (
  id               BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  user_id          BIGINT UNSIGNED NOT NULL,
  coupon_id        BIGINT UNSIGNED NULL,
  status           VARCHAR(20) NOT NULL DEFAULT 'pending',
  subtotal         DECIMAL(12,2) NOT NULL,
  discount         DECIMAL(12,2) NOT NULL DEFAULT 0,
  total            DECIMAL(12,2) NOT NULL,
  shipping_address JSON NOT NULL,              -- snapshot، نه FK به addresses
  created_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id)   REFERENCES users(id)   ON DELETE RESTRICT,
  FOREIGN KEY (coupon_id) REFERENCES coupons(id) ON DELETE SET NULL,
  INDEX idx_orders_user_created (user_id, created_at),
  INDEX idx_orders_status_created (status, created_at)
);

CREATE TABLE order_items (
  id           BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  order_id     BIGINT UNSIGNED NOT NULL,
  variant_id   BIGINT UNSIGNED NOT NULL,
  product_name VARCHAR(200) NOT NULL,          -- snapshot
  unit_price   DECIMAL(12,2) NOT NULL,         -- snapshot قیمت
  quantity     INT UNSIGNED NOT NULL CHECK (quantity > 0),
  UNIQUE (order_id, variant_id),
  FOREIGN KEY (order_id)   REFERENCES orders(id) ON DELETE CASCADE,
  FOREIGN KEY (variant_id) REFERENCES product_variants(id) ON DELETE RESTRICT
);

CREATE TABLE reviews (
  id         BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL,
  product_id BIGINT UNSIGNED NOT NULL,
  rating     TINYINT NOT NULL CHECK (rating BETWEEN 1 AND 5),
  body       TEXT NULL,
  UNIQUE (user_id, product_id),                -- قاعده‌ی «یک نظر برای هر محصول»
  FOREIGN KEY (user_id)    REFERENCES users(id)    ON DELETE CASCADE,
  FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE CASCADE
);

سوالات تشریحی

مدل مفهومی، منطقی و فیزیکی را تعریف و با هم مقایسه کنید.
  • Conceptual (مفهومی): دید سطح بالا و مستقل از تکنولوژی از موجودیت‌ها، روابط اصلی و قواعد کسب‌وکار. مخاطب: ذی‌نفعان غیرفنی. ابزار: ER diagram ساده. مثال: «مشتری سفارش می‌دهد؛ سفارش شامل محصولات است.»
  • Logical (منطقی): تبدیل مدل مفهومی به ساختار رابطه‌ای: جداول، همه‌ی attributeها، PK و FK، کاردینالیتی دقیق، شکستن M:N به جدول واسط و نرمال‌سازی (معمولاً تا 3NF). هنوز مستقل از DBMS خاص.
  • Physical (فیزیکی): پیاده‌سازی روی DBMS مشخص: نوع داده‌ی دقیق (DECIMAL(12,2)، TIMESTAMP)، ایندکس‌ها، constraintها، charset، partitioning، و گاهی denormalization برای کارایی. خروجی: DDL یا Migration.

چرا جدا؟ هر سطح سوال متفاوتی را جواب می‌دهد: «چه چیزی» (درستی نیازمندی)، «چه ساختاری» (صحت و عدم افزونگی)، «چگونه» (کارایی روی پلتفرم). جدا کردن آن‌ها اجازه می‌دهد خطای نیازمندی زود کشف شود و تصمیمات فیزیکی (مثلاً تغییر از MySQL به PostgreSQL) روی مدل منطقی اثر نگذارد.

Natural Key و Surrogate Key را مقایسه کنید. شما برای جدول کاربران کدام را انتخاب می‌کنید و چرا؟

Natural key: شناسه‌ای با معنای واقعی که در دامنه وجود دارد (email، کد ملی، ISBN). Surrogate key: شناسه‌ی مصنوعی بدون معنا که سیستم تولید می‌کند (auto-increment، UUID، ULID).

مقایسه:

  • پایداری: natural key ممکن است تغییر کند (کاربر ایمیلش را عوض می‌کند) و این تغییر باید به همه‌ی FKها منتشر شود؛ surrogate هرگز تغییر نمی‌کند.
  • اندازه و کارایی: surrogate عددی کوچک است و JOIN و ایندکس‌ها را سبک نگه می‌دارد.
  • یکتایی واقعی: natural keyها گاهی در عمل یکتا نیستند یا همیشه موجود نیستند (کاربر خارجی کد ملی ندارد).
  • معنا: natural key خواناست و گاهی JOIN را حذف می‌کند.

انتخاب برای users: PK = BIGINT auto-increment (یا ULID اگر شناسه در URL عمومی است یا تولید توزیع‌شده لازم است)، و email با UNIQUE. یعنی surrogate برای ارجاع، و natural key همچنان با constraint محافظت می‌شود تا کاربر تکراری ساخته نشود.

استثنا: جداول lookup کوچک و پایدار (کد ارز، کد کشور) و جدول واسط که composite natural key دارد.

استفاده از UUID به‌عنوان کلید اصلی چه مزایا و معایبی نسبت به auto-increment دارد؟

مزایای UUID:

  • تولید در برنامه بدون هماهنگی با دیتابیس؛ شناسه قبل از INSERT معلوم است (مفید در سیستم توزیع‌شده، صف‌ها و offline-first).
  • یکتایی سراسری: ادغام داده بین دیتابیس‌ها/شاردها بدون تعارض.
  • غیرقابل حدس و شمارش: تعداد کاربران/سفارش‌ها نشت نمی‌کند و حمله‌ی شمارشی (IDOR) سخت‌تر است.

معایب:

  • اندازه: ۱۶ بایت (یا ۳۶ کاراکتر اگر رشته ذخیره شود) در برابر ۸ بایت؛ در InnoDB همه‌ی secondary indexها PK را هم دارند، پس همه بزرگ‌تر می‌شوند.
  • UUID v4 تصادفی در clustered index باعث درج در مکان‌های تصادفی B-tree، page split، fragmentation و کاهش کارایی cache می‌شود.
  • خوانایی و دیباگ سخت‌تر.

راه‌حل‌های میانه: UUID مرتب زمانی (UUIDv7) یا ULID که تقریباً append-only درج می‌شوند؛ ذخیره به‌صورت BINARY(16) یا نوع بومی uuid در PostgreSQL؛ یا PK عددی داخلی + ستون public_id یکتا برای بیرون. در Laravel، HasUuids/HasUlids شناسه‌ی مرتب تولید می‌کنند.

نکته: UUID جایگزین authorization نیست.

نرمال‌سازی چیست؟ فرم‌های 1NF، 2NF و 3NF را با یک مثال توضیح دهید.

تعریف: فرایند سازمان‌دهی جداول بر اساس وابستگی‌های تابعی برای حذف افزونگی و ناهنجاری‌های درج/به‌روزرسانی/حذف؛ با تجزیه‌ی جداول به جداول کوچک‌تر به‌صورت lossless.

مثال: orders(order_id, date, customer_id, customer_name, products="P1:2,P7:1")

  • 1NF: هر خانه یک مقدار اتمیک، بدون گروه تکرارشونده. ستون products را به سطرها می‌شکنیم: (order_id, product_id, date, customer_id, customer_name, product_name, qty) با کلید (order_id, product_id).
  • 2NF: 1NF + هیچ ستون غیرکلیدی به بخشی از کلید ترکیبی وابسته نباشد. date, customer_* فقط به order_id و product_name فقط به product_id وابسته‌اند. تجزیه: orders(order_id, date, customer_id, customer_name)، products(product_id, product_name)، order_items(order_id, product_id, qty).
  • 3NF: 2NF + بدون وابستگی تعدی (ستون غیرکلیدی به غیرکلیدی). در orders: order_id → customer_id → customer_name. تجزیه: customers(customer_id, customer_name) و orders(order_id, date, customer_id).

نتیجه: نام مشتری و محصول هر کدام فقط در یک جا ثبت می‌شوند؛ تغییر نام در یک سطر انجام می‌شود و حذف یک سفارش اطلاعات محصول را از بین نمی‌برد.

Trade-off: JOIN بیشتر هنگام خواندن؛ در صورت اثبات مشکل کارایی، denormalization کنترل‌شده.

تفاوت 3NF و BCNF چیست؟ مثالی بزنید که جدولی در 3NF باشد ولی در BCNF نباشد.

3NF: برای هر FD غیربدیهی X → A، یا X یک super key است، یا A یک prime attribute (عضو یک candidate key) است. BCNF: برای هر FD غیربدیهی X → A، X حتماً super key است. پس BCNF استثنای «prime attribute» را حذف می‌کند و سخت‌گیرانه‌تر است.

مثال: teaching(student, course, instructor) با قواعد: هر استاد فقط یک درس می‌دهد (instructor → course) و هر دانشجو در هر درس یک استاد دارد (student, course → instructor).

  • Candidate keyها: (student, course) و (student, instructor). همه‌ی ستون‌ها prime هستند ⇒ 3NF برقرار است.
  • ولی instructor → course و instructor super key نیست ⇒ نقض BCNF. ناهنجاری: درسِ هر استاد به ازای هر دانشجو تکرار می‌شود.
  • تجزیه به BCNF: instructors(instructor PK, course) و enrollments(student, instructor).

هزینه: FD student, course → instructor دیگر در یک جدول نیست و با UNIQUE ساده قابل اجبار نیست (dependency preservation از دست می‌رود). تجزیه به 3NF همیشه می‌تواند lossless و dependency-preserving باشد ولی BCNF نه؛ به همین دلیل در عمل 3NF هدف معمول است و BCNF وقتی که هزینه‌اش قابل قبول باشد.

ناهنجاری‌های درج، به‌روزرسانی و حذف را با مثال توضیح دهید و بگویید نرمال‌سازی چگونه آن‌ها را برطرف می‌کند.

جدول enrollments(student_id, course_id, course_title, instructor_phone) با کلید (student_id, course_id):

  • Update anomaly: عنوان و تلفن استاد درس در همه‌ی سطرهای ثبت‌نام آن درس تکرار شده؛ تغییر تلفن نیازمند به‌روزرسانی ده‌ها سطر است و اگر یکی جا بماند، داده متناقض می‌شود.
  • Insert anomaly: درس جدید را تا وقتی دانشجویی ثبت‌نام نکرده نمی‌توان ثبت کرد، چون student_id جزء کلید است و نمی‌تواند NULL باشد.
  • Delete anomaly: اگر آخرین دانشجوی یک درس حذف شود، اطلاعات خود درس (عنوان، استاد) هم از بین می‌رود.

علت ریشه‌ای: دو واقعیت مستقل (اطلاعات درس و ثبت‌نام دانشجو) در یک جدول ترکیب شده‌اند؛ course_id → course_title وابستگی جزئی است (نقض 2NF).

راه‌حل: تجزیه به courses(course_id, course_title, instructor_id)، instructors(instructor_id, phone) و enrollments(student_id, course_id). حالا هر واقعیت یک بار ثبت می‌شود: درس مستقل از دانشجو درج می‌شود، تلفن در یک سطر به‌روز می‌شود و حذف ثبت‌نام اطلاعات درس را حذف نمی‌کند.

Denormalization چیست و در چه شرایطی توجیه دارد؟ ریسک‌های آن را چگونه مدیریت می‌کنید؟

تعریف: افزودن عمدی افزونگی به Schema نرمال (کپی ستون، ستون تجمعی، جدول خلاصه) برای کاهش JOIN و محاسبه در زمان خواندن.

شرایط توجیه:

  • کوئری پرتکرار و کند که با ایندکس و بازنویسی حل نشده و با اندازه‌گیری (EXPLAIN، APM) اثبات شده است.
  • خواندن بسیار بیشتر از نوشتن و داده‌ی تکراری کم‌تغییر.
  • گزارش‌گیری/OLAP (star schema، جداول خلاصه‌ی روزانه).
  • مثال: posts.comments_count برای لیست پست‌ها به جای COUNT روی هر پست؛ orders.total.

تفاوت با snapshot: قیمت در order_items denormalization نیست؛ واقعیت تاریخی متفاوتی است.

مدیریت ریسک:

  • مشخص کردن source of truth.
  • همگام‌سازی در همان تراکنش (increment اتمیک)، با Model Event/Observer، trigger یا job دوره‌ای.
  • به‌روزرسانی اتمیک (SET c = c + 1) به جای read-modify-write برای جلوگیری از race.
  • دستور/job بازسازی (recalculate) برای اصلاح ناسازگاری‌ها و مانیتورینگ آن.
سناریو: مدیر می‌خواهد یک کاربر را حذف کند. کاربر سفارش، آدرس، نظر و توکن‌های ورود دارد. اکشن‌های ON DELETE را برای هر رابطه چگونه انتخاب می‌کنید؟
  • orders → users: RESTRICT. سفارش‌ها داده‌ی مالی و حقوقی‌اند و نباید با حذف کاربر از بین بروند. بنابراین کاربر دارای سفارش اصلاً hard delete نمی‌شود؛ به جای آن soft delete یا ناشناس‌سازی (anonymize: پاک کردن نام/ایمیل/تلفن و نگه‌داشتن سطر) انجام می‌شود که با حریم خصوصی هم سازگار است.
  • addresses → users: CASCADE. آدرس بدون کاربر معنایی ندارد. سفارش‌ها هم وابسته‌ی آدرس نیستند چون snapshot آدرس را دارند.
  • personal_access_tokens / sessions: CASCADE. باید فوراً حذف شوند تا دسترسی قطع شود.
  • reviews → users: بستگی به سیاست کسب‌وکار دارد: CASCADE اگر نظرها باید حذف شوند؛ یا SET NULL (ستون nullable) و نمایش «کاربر حذف‌شده» اگر محتوای نظر برای دیگران ارزشمند است. در حالت دوم، ستون‌های تجمعی مثل امتیاز میانگین محصول دست‌نخورده می‌مانند.

نکات: CASCADE در دیتابیس eventهای Eloquent (deleting) را اجرا نمی‌کند، پس پاک کردن فایل‌ها (آواتار) یا به‌روزرسانی شمارنده‌ها باید در کد انجام شود. حذف کاربر را در یک تراکنش و ترجیحاً در یک Action/Service با log انجام دهید.

کد/Schema زیر چه مشکلاتی دارد؟ CREATE TABLE invoices (id INT, customer VARCHAR(100), amount FLOAT, created VARCHAR(20), tags VARCHAR(255));
  • بدون PRIMARY KEY: id نه PK است نه auto-increment؛ سطر تکراری ممکن است و InnoDB یک کلید پنهان می‌سازد. → id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY.
  • customer VARCHAR: نام مشتری به جای FK؛ تکرار، ناهنجاری به‌روزرسانی و عدم یکپارچگی. → customer_id با FK به customers (و اگر snapshot نام لازم است، جداگانه و آگاهانه).
  • amount FLOAT: خطای گرد کردن در پول. → DECIMAL(12,2) یا عدد صحیح به واحد خرد + currency.
  • created VARCHAR: تاریخ به‌صورت رشته: بدون اعتبارسنجی، مرتب‌سازی و بازه‌گیری غلط یا کند. → created_at TIMESTAMP (UTC).
  • tags VARCHAR با مقادیر جداشده با کاما: نقض 1NF؛ جست‌وجو با LIKE '%x%' (بدون ایندکس)، بدون FK، حذف/تغییر نام تگ سخت. → جدول tags و pivot invoice_tag.
  • همه‌ی ستون‌ها nullable و بدون CHECK (مثلاً amount >= 0).
CREATE TABLE invoices (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  customer_id BIGINT UNSIGNED NOT NULL,
  amount      DECIMAL(12,2) NOT NULL CHECK (amount >= 0),
  currency    CHAR(3) NOT NULL DEFAULT 'IRR',
  created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT,
  INDEX idx_invoices_customer_created (customer_id, created_at)
);
CREATE TABLE invoice_tag (
  invoice_id BIGINT UNSIGNED NOT NULL, tag_id BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (invoice_id, tag_id),
  FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id) REFERENCES tags(id) ON DELETE CASCADE
);
زمان و تاریخ را چگونه در دیتابیس ذخیره می‌کنید تا کاربران در منطقه‌های زمانی مختلف دچار مشکل نشوند؟

اصل: لحظه‌های زمانی (instant) را در UTC ذخیره کن؛ تبدیل به منطقه‌ی زمانی کاربر فقط در لایه‌ی نمایش.

  • نوع داده: در PostgreSQL timestamptz؛ در MySQL TIMESTAMP (که به UTC تبدیل می‌کند و محدود به ۲۰۳۸ است) یا DATETIME با این قرارداد که همیشه UTC نوشته شود.
  • تنظیمات: config/app.php با 'timezone' => 'UTC'، time zone اتصال دیتابیس UTC، و ذخیره‌ی time zone هر کاربر (users.timezone = 'Asia/Tehran').
  • نمایش: $order->created_at->setTimezone($user->timezone)؛ و تبدیل ورودی کاربر از زمان محلی به UTC قبل از ذخیره یا کوئری بازه‌ای.
  • فقط تاریخ (تولد، سررسید): DATE بدون time zone؛ تبدیل آن معنا ندارد.
  • رویداد آینده با ساعت محلی (جلسه ساعت ۹ تهران): زمان محلی + شناسه‌ی time zone (نه offset ثابت مثل +03:30)، چون قوانین time zone ممکن است تغییر کنند.
  • تقویم شمسی: فقط در نمایش؛ ذخیره میلادی/UTC.

اشتباهات رایج: ذخیره‌ی زمان محلی سرور، ترکیب داده‌ی UTC و محلی، گزارش «فروش روزانه» با مرز روز UTC به جای مرز روز تهران (باید بازه را بر اساس time zone گزارش محاسبه کرد).

مزایا و معایب Soft Delete را بیان کنید. اگر ایمیل کاربران UNIQUE باشد و کاربر soft-delete شده بخواهد دوباره ثبت‌نام کند، چه مشکلی پیش می‌آید و راه‌حل چیست؟

Soft delete: علامت‌گذاری سطر به‌عنوان حذف‌شده (deleted_at) به جای حذف فیزیکی؛ در Laravel با trait SoftDeletes و global scope.

مزایا: امکان بازیابی، حفظ ارجاع داده‌ی تاریخی (سفارش‌های کاربر حذف‌شده)، audit.

معایب: شکستن UNIQUE، بی‌اثر شدن FK/CASCADE دیتابیس، خطر فراموش کردن شرط در کوئری‌های خام/گزارش‌ها، رشد جدول، و تعارض با الزامات حذف داده‌ی شخصی.

مشکل ایمیل: سطر حذف‌شده هنوز ایمیل را دارد، پس INSERT جدید با خطای duplicate key رد می‌شود (در حالی که Rule::unique در Laravel ممکن است با withoutTrashed() اجازه دهد و خطا در دیتابیس بروز کند).

راه‌حل‌ها:

  • PostgreSQL: partial unique index CREATE UNIQUE INDEX ... ON users(email) WHERE deleted_at IS NULL.
  • MySQL: ستون generated که برای سطرهای حذف‌شده NULL است و UNIQUE روی آن (NULLها تکرارپذیرند).
  • هنگام soft delete ایمیل را تغییر دهید (email = concat(email, '#deleted#', id)) — ساده ولی داده را دستکاری می‌کند.
  • بازیابی (restore) حساب قبلی به جای ساخت حساب جدید، اگر کسب‌وکار اجازه دهد.
Polymorphic Association چیست؟ مزایا، معایب و جایگزین‌های آن را توضیح دهید.

تعریف: الگویی که در آن یک جدول (مثلاً comments یا images) با جفت ستون commentable_type و commentable_id می‌تواند به سطرهای چند جدول مختلف (posts، videos) اشاره کند. در Laravel: $table->morphs('commentable') و روابط morphTo/morphMany.

مزایا: یک جدول و یک منطق مشترک برای همه‌ی انواع؛ افزودن نوع جدید بدون تغییر Schema؛ پشتیبانی کامل Eloquent (eager loading با with('commentable')).

معایب:

  • نبود Foreign Key: دیتابیس نمی‌تواند یکپارچگی ارجاعی را تضمین کند ⇒ رکوردهای یتیم و نبود CASCADE.
  • JOIN و گزارش‌گیری SQL سخت‌تر (JOIN شرطی بر اساس type).
  • ذخیره‌ی نام کلاس در دیتابیس، کد را به داده گره می‌زند؛ باید Relation::enforceMorphMap استفاده شود.
  • ایندکس ترکیبی (type, id) لازم است.

جایگزین‌ها: (۱) جدول جدا برای هر نوع؛ (۲) چند FK nullable (post_id، video_id) + CHECK «دقیقاً یکی NOT NULL»؛ (۳) جدول supertype مشترک که والدها به آن ارجاع دهند.

جمع‌بندی: برای ویژگی‌های عمومی و کم‌ریسک (کامنت، تگ، فایل پیوست، لاگ فعالیت) polymorphic عملی است؛ برای داده‌ی حیاتی که یکپارچگی می‌خواهد، FK واقعی.

یک رابطه‌ی چندبه‌چند بین دانشجو و درس که نمره و تاریخ ثبت‌نام هم دارد را طراحی کنید و در Laravel پیاده کنید.

M:N با جدول واسط پیاده می‌شود؛ چون رابطه attribute دارد (grade، enrolled_at)، جدول واسط عملاً یک موجودیت به نام enrollments است.

<?php
Schema::create('enrollments', function (Blueprint $table) {
    $table->id();
    $table->foreignId('student_id')->constrained()->cascadeOnDelete();
    $table->foreignId('course_id')->constrained()->restrictOnDelete();
    $table->decimal('grade', 4, 2)->nullable();
    $table->timestamp('enrolled_at');
    $table->unique(['student_id', 'course_id']);   // هر دانشجو یک بار در هر درس
    $table->index('course_id');                    // برای course → students
});

class Student extends Model {
    public function courses() {
        return $this->belongsToMany(Course::class, 'enrollments')
                    ->withPivot('grade', 'enrolled_at')
                    ->using(Enrollment::class);    // Pivot model سفارشی (اختیاری)
    }
}

$student->courses()->updateExistingPivot($courseId, ['grade' => 18.5]);

نکات:

  • UNIQUE ترکیبی از ثبت‌نام تکراری جلوگیری می‌کند (حتی در race condition).
  • ایندکس UNIQUE روی (student_id, course_id) کوئری‌های سمت دانشجو را پوشش می‌دهد؛ برای سمت درس ایندکس جدا لازم است.
  • اگر enrollment رفتار مستقل دارد (وضعیت، پرداخت شهریه)، آن را مدل کامل با روابط belongsTo در نظر بگیرید.
  • CHECK (grade BETWEEN 0 AND 20) قاعده‌ی دامنه را اجبار می‌کند.
سناریو: تیم مالی می‌خواهد بداند قیمت هر محصول در هر تاریخ گذشته چه بوده و چه کسی آن را تغییر داده است. Schema را طراحی کنید.

این یک نیاز temporal/history است: یک جدول تاریخچه با بازه‌ی اعتبار.

CREATE TABLE product_prices (
  id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  product_id  BIGINT UNSIGNED NOT NULL,
  price       DECIMAL(12,2) NOT NULL CHECK (price >= 0),
  valid_from  TIMESTAMP NOT NULL,
  valid_to    TIMESTAMP NULL,                 -- NULL = قیمت فعلی
  changed_by  BIGINT UNSIGNED NOT NULL,
  reason      VARCHAR(255) NULL,
  FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE RESTRICT,
  FOREIGN KEY (changed_by) REFERENCES users(id),
  INDEX idx_prices_product_from (product_id, valid_from)
);

-- قیمت در یک لحظه‌ی مشخص
SELECT price FROM product_prices
WHERE product_id = ? AND valid_from <= ? AND (valid_to IS NULL OR valid_to > ?);
  • تغییر قیمت = در یک تراکنش: بستن سطر فعلی (valid_to = now()) و درج سطر جدید. این از بازه‌های هم‌پوشان جلوگیری می‌کند. (در PostgreSQL می‌توان با exclusion constraint روی بازه‌ها هم‌پوشانی را در سطح دیتابیس منع کرد.)
  • جدول append-only است؛ به‌روزرسانی/حذف سطرهای قدیمی مجاز نیست (مجوز دیتابیس یا policy).
  • برای کارایی، قیمت فعلی را می‌توان در products.price هم نگه داشت (denormalization با source of truth مشخص).
  • سفارش‌ها همچنان unit_price snapshot دارند و به این جدول وابسته نیستند.
  • جایگزین عمومی‌تر: جدول audit با old_values/new_values برای همه‌ی ستون‌ها؛ ولی برای کوئری «قیمت در تاریخ X» جدول history اختصاصی ساده‌تر و سریع‌تر است.
انواع JOIN را با مثال توضیح دهید. تفاوت WHERE و HAVING چیست؟
  • INNER JOIN: فقط سطرهایی که در هر دو جدول مطابق دارند. «سفارش‌ها با نام مشتری».
  • LEFT JOIN: همه‌ی سطرهای جدول چپ و مطابق‌های راست (یا NULL). «همه‌ی مشتریان با تعداد سفارش، حتی صفر» — با COUNT(o.id).
  • RIGHT JOIN: قرینه‌ی LEFT؛ معمولاً با جابه‌جایی جداول به LEFT تبدیل می‌شود.
  • FULL OUTER JOIN: همه‌ی سطرهای هر دو؛ در MySQL با UNION شبیه‌سازی می‌شود.
  • CROSS JOIN: ضرب دکارتی؛ مثلاً ساخت همه‌ی ترکیب‌های سایز × رنگ.
  • SELF JOIN: جدول با خودش؛ کارمند و مدیر.
-- مشتریان بدون سفارش (anti-join)
SELECT c.* FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.id IS NULL;

WHERE در برابر HAVING: WHERE سطرها را قبل از گروه‌بندی فیلتر می‌کند و نمی‌تواند از توابع تجمعی استفاده کند؛ HAVING گروه‌ها را بعد از GROUP BY فیلتر می‌کند و روی COUNT/SUM شرط می‌گذارد.

SELECT customer_id, SUM(total) spent
FROM orders WHERE status = 'paid'
GROUP BY customer_id HAVING SUM(total) > 1000;

نکته‌ی کارایی: هر شرطی که می‌تواند در WHERE باشد را در HAVING نگذارید، چون فیلتر زودتر یعنی سطرهای کمتر برای گروه‌بندی و امکان استفاده از ایندکس. و شرط روی جدول راست LEFT JOIN را در ON بگذارید، نه WHERE.

برای ستون وضعیت سفارش (pending، paid، shipped، cancelled)، ENUM دیتابیس، جدول lookup یا VARCHAR را انتخاب می‌کنید؟ دلیل بیاورید.
  • ENUM: فشرده و خوداعتبارسنج، ولی افزودن/تغییر مقدار نیاز به ALTER TABLE دارد، ترتیب مرتب‌سازی بر اساس ترتیب تعریف است، بین DBMSها قابل حمل نیست و نمی‌توان metadata (برچسب، رنگ، ترتیب) کنارش داشت.
  • جدول lookup + FK: افزودن مقدار با INSERT، metadata قابل نگه‌داری، یکپارچگی با FK؛ هزینه: JOIN یا cache.
  • VARCHAR + CHECK/validation + PHP Enum: خوانا در دیتابیس، منطق در کد متمرکز (enum OrderStatus: string با cast در مدل)، افزودن مقدار با تغییر کد.

انتخاب من: برای وضعیت سفارش، که مجموعه‌ای کوچک است و منطق برنامه (state machine، انتقال مجاز وضعیت‌ها) به آن وابسته است و کاربر ادمین نباید مقدار جدید اضافه کند، VARCHAR(20) + PHP backed enum + cast + در صورت امکان CHECK. ایندکس (status, created_at) برای لیست‌های ادمین.

برای مقادیری که کسب‌وکار پویا مدیریت می‌کند (روش ارسال، دلایل لغو با متن فارسی)، جدول lookup. ENUM دیتابیس را فقط برای مجموعه‌های واقعاً ثابت در نظر بگیرید.

Migration زیر در production مشکل‌ساز است. چرا و چگونه آن را اصلاح می‌کنید؟ 
<?php
// جدول orders با 50 میلیون سطر
Schema::table('orders', function (Blueprint $table) {
    $table->renameColumn('amount', 'total');
    $table->string('tracking_code');            // NOT NULL بدون default
});
foreach (Order::all() as $order) {              // داخل همان migration
    $order->update(['tracking_code' => Str::random(10)]);
}

مشکلات:

  • rename ستون: کد در حال اجرا (نسخه‌ی قبلی در زمان deploy) هنوز amount را می‌خواند ⇒ خطا تا پایان deploy. باید Expand/Contract شود.
  • ستون NOT NULL بدون default روی جدول پر: یا خطا می‌دهد یا مقدار پیش‌فرض ضمنی (رشته‌ی خالی) می‌گیرد و بسته به DBMS/نسخه ممکن است جدول را بازسازی و قفل کند.
  • Order::all(): ۵۰ میلیون مدل در حافظه ⇒ memory exhaustion؛ و ۵۰ میلیون UPDATE تکی.
  • استفاده از مدل Eloquent در migration: با تغییر آینده‌ی مدل (scope، cast، event) migration می‌شکند؛ eventها هم اجرا می‌شوند.
  • ترکیب تغییر Schema و داده در یک migration طولانی.

اصلاح:

  1. Migration ۱: افزودن total و tracking_code به‌صورت nullable().
  2. Deploy کدی که در هر دو ستون amount/total می‌نویسد.
  3. Backfill در یک command/job با DB::table('orders')->whereNull('total')->chunkById(1000, ...).
  4. Deploy کدی که فقط از total می‌خواند.
  5. Migration نهایی: حذف amount و اعمال NOT NULL و UNIQUE روی tracking_code.

خلاصه برای مرور سریع

فرایند

  • Requirements → Conceptual (چه) → Logical (چه ساختاری) → Physical (چگونه، روی DBMS).
  • اسم‌ها = موجودیت، فعل‌ها = رابطه، صفت‌ها = attribute.
  • کاردینالیتی (حداکثر) + مشارکت (حداقل: NOT NULL روی FK).

کلیدها

  • Super ⊇ Candidate (کمینه) → Primary (انتخاب‌شده) + Alternate (UNIQUE).
  • Surrogate PK + natural key با UNIQUE.
  • Auto-inc: کوچک، سریع، قابل حدس. UUIDv4: توزیع‌شده، ولی page split. UUIDv7/ULID: مرتب + توزیع‌شده.
  • UUID ≠ authorization.

روابط

  • 1:1 → FK + UNIQUE.
  • 1:N → FK در طرف چند.
  • M:N → pivot با PK/UNIQUE ترکیبی + ایندکس معکوس.
  • درخت: adjacency + WITH RECURSIVE، materialized path، closure table.

نرمال‌سازی

  • FD: X → Y. Partial (بخشی از کلید) → نقض 2NF. Transitive → نقض 3NF.
  • ناهنجاری‌ها: insert، update، delete.
  • 1NF: اتمیک، بدون گروه تکراری (بدون CSV در ستون).
  • 2NF: وابسته به کل کلید.
  • 3NF: هیچ چیز جز کلید.
  • BCNF: هر determinant یک super key؛ ممکن است dependency preservation را از دست بدهد.
  • تجزیه باید lossless باشد.
  • Snapshot (قیمت/آدرس سفارش) ≠ افزونگی.

Denormalization

  • اول نرمال، بعد با اندازه‌گیری denormalize.
  • شمارنده، کپی ستون، جدول خلاصه، cache.
  • Source of truth + مکانیزم همگام‌سازی + job بازسازی.

Constraint و FK

  • NOT NULL پیش‌فرض؛ UNIQUE؛ CHECK (MySQL 8.0.16+)؛ DEFAULT.
  • RESTRICT: داده‌ی مالی/تاریخی. CASCADE: فرزند بی‌معنا بدون والد. SET NULL: رابطه‌ی اختیاری.
  • CASCADE دیتابیس eventهای Eloquent را اجرا نمی‌کند.
  • همه‌ی FKها ایندکس (PostgreSQL خودکار نمی‌سازد).

نوع داده

  • پول: DECIMAL(p,s) یا BIGINT واحد خرد؛ هرگز FLOAT.
  • زمان: UTC ذخیره، محلی نمایش؛ timestamptz؛ MySQL TIMESTAMP تا ۲۰۳۸.
  • VARCHAR با سقف واقعی؛ TEXT برای متن بلند؛ utf8mb4.
  • تلفن/کد ملی/کد پستی = رشته.
  • ENUM: تغییر سخت؛ lookup: پویا؛ VARCHAR + PHP Enum: منطق در کد.
  • JSON: داده‌ی متغیر کم‌کوئری؛ ایندکس با generated column / GIN.

الگوهای خاص

  • Soft delete: بازیابی و حفظ تاریخچه؛ ولی UNIQUE (partial index / generated column)، FK، فراموشی شرط.
  • Polymorphic: morphs()، بدون FK، enforceMorphMap.
  • Audit: ستون‌های created_by، جدول audit با old/new JSON، history با valid_from/valid_to.

ایندکس

  • WHERE، JOIN، ORDER BY، FKها؛ selectivity بالا.
  • Composite: leftmost prefix؛ برابری اول، بازه آخر.
  • Covering index؛ تابع روی ستون و LIKE '%x' ایندکس را می‌کشد.
  • EXPLAIN: type=ALL بد؛ Using filesort/temporary هشدار.

SQL

  • ترتیب: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
  • LEFT JOIN + شرط WHERE روی جدول راست = INNER.
  • Anti-join: LEFT JOIN ... IS NULL یا NOT EXISTS؛ مراقب NOT IN با NULL.
  • COUNT(col) NULLها را نمی‌شمارد، COUNT(*) می‌شمارد.
  • Window: ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...).

Laravel Migration

  • id()، foreignId()->constrained()->cascadeOnDelete()/nullOnDelete()/restrictOnDelete().
  • decimal('price', 12, 2)، ulid()، json()، softDeletes()، morphs().
  • Migration اجراشده را ویرایش نکن؛ down بنویس؛ Eloquent در migration نه.
  • Laravel 11+: change() همه‌ی modifierها را دوباره می‌خواهد.
  • Expand → migrate data (chunkById) → Contract.
