Eloquent

همه‌چیز درباره ORM لاراول: الگوی Active Record، قراردادهای مدل، CRUD و mass assignment، cast و accessor، انواع رابطه‌ها و eager loading و مسئله N+1، scope و soft delete، رویدادها و observerها، کار با داده‌های حجیم، تراکنش و قفل، صفحه‌بندی، API Resource، factory و نکات کارایی.

Active Record و قراردادهای مدل

Eloquent پیاده‌سازی لاراول از الگوی Active Record است: هر کلاس مدل نماینده یک جدول است، هر نمونه (instance) نماینده یک سطر، و خود شیء هم داده را نگه می‌دارد و هم متدهای ذخیره و بازیابی (save()، delete()، find()) را دارد. یعنی منطق persistence داخل خود مدل است.

در مقابل، الگوی Data Mapper (مثل Doctrine در Symfony) موجودیت‌ها را به‌صورت شیء‌های ساده PHP (POPO) نگه می‌دارد و یک لایه جدا (EntityManager / Repository) مسئول نگاشت آن‌ها به دیتابیس است. موجودیت چیزی از دیتابیس نمی‌داند.

اگر پرسیدند «Eloquent چه الگویی است و ایرادش چیست؟»: Active Record؛ ایراد اصلی نقض Single Responsibility (مدل هم داده/رفتار دامنه است و هم persistence) و گره‌خوردن لایه دامنه به دیتابیس است. راه کاهش اثر: مدل‌های لاغر، منطق تجاری در Service/Action کلاس‌ها، و در صورت نیاز Repository برای جداسازی کوئری‌های پیچیده.

قراردادهای پیش‌فرض (Convention over Configuration)

  • نام جدول: شکل snake_case و جمع نام کلاس؛ Flight → flights، AirTrafficController → air_traffic_controllers. با protected $table عوض می‌شود.
  • کلید اصلی: ستون id، عدد صحیح و auto-increment. با $primaryKey، $keyType و $incrementing تغییر می‌کند. Eloquent از کلید ترکیبی (composite key) پشتیبانی نمی‌کند (برای جدول pivot مشکلی نیست).
  • Timestamps: ستون‌های created_at و updated_at خودکار پر می‌شوند؛ با public $timestamps = false غیرفعال، و با ثابت‌های CREATED_AT/UPDATED_AT تغییر نام می‌دهند. $dateFormat قالب ذخیره را مشخص می‌کند.
  • Connection: پیش‌فرض اتصال تعریف‌شده در config/database.php؛ با protected $connection = 'reporting' عوض می‌شود.
  • مقادیر پیش‌فرض attribute: با protected $attributes = ['status' => 'draft'].
<?php
namespace App\Models;

use Illuminate\Database\Eloquent\Model;

class Flight extends Model
{
    protected $table = 'my_flights';
    protected $primaryKey = 'flight_id';
    protected $connection = 'mysql_reporting';
    public $timestamps = true;

    const CREATED_AT = 'creation_date';
    const UPDATED_AT = 'updated_date';

    protected $attributes = [
        'delayed' => false,
    ];
}

کلیدهای UUID و ULID

برای جلوگیری از قابل‌حدس‌بودن شناسه‌ها (مثلاً در URL) یا تولید شناسه سمت اپلیکیشن پیش از insert، می‌توان از UUID یا ULID استفاده کرد. تریت HasUuids یا HasUlids کلید را هنگام ساخت مدل تولید می‌کند و $incrementing و $keyType را خودش درست تنظیم می‌کند.

<?php
// migration
Schema::create('orders', function (Blueprint $table) {
    $table->ulid('id')->primary();      // یا $table->uuid('id')->primary();
    $table->foreignUlid('user_id')->constrained();
    $table->timestamps();
});

// model
use Illuminate\Database\Eloquent\Concerns\HasUlids;

class Order extends Model
{
    use HasUlids;

    // اگر ستون دیگری هم باید UUID/ULID بگیرد:
    public function uniqueIds(): array
    {
        return ['id', 'tracking_code'];
    }
}

UUID نسخه ۴ کاملاً تصادفی است و چون ترتیب ندارد، درج در ایندکس B-Tree (به‌خصوص کلید clustered در InnoDB) را تکه‌تکه و کند می‌کند. برای همین لاراول از UUIDهای مرتب‌شونده استفاده می‌کند: در Laravel 12 تریت HasUuids به‌صورت پیش‌فرض UUIDv7 (مبتنی بر زمان) تولید می‌کند و برای رفتار قدیمی (ordered UUIDv4) تریت HasVersion4Uuids وجود دارد. ULID هم ذاتاً مرتب بر اساس زمان و ۲۶ کاراکتری است.

Eloquent یا Query Builder یا SQL خام؟

Eloquent

  • رابطه‌ها، cast، accessor، رویدادها، scopeها، soft delete
  • خوانایی بالا و کد دامنه‌محور
  • هزینه: ساخت شیء برای هر سطر (hydration)، مصرف حافظه بیشتر

Query Builder (DB::table)

  • خروجی آرایه‌ای از stdClass؛ سبک‌تر و سریع‌تر
  • مناسب گزارش‌ها، aggregateهای سنگین، عملیات انبوه
  • بدون رویداد مدل، cast، scope سراسری و soft delete خودکار

SQL خام (DB::select، DB::statement، whereRaw، selectRaw) برای قابلیت‌های خاص دیتابیس (window function، CTE پیچیده، hint) لازم است، ولی قابلیت حمل بین دیتابیس‌ها را کم می‌کند و مسئولیت امنیت با شماست.

SQL Injection در متدهای raw

Query Builder تمام مقادیر را با PDO parameter binding ارسال می‌کند، پس where('email', $input) امن است. اما هر متدی که رشته خام SQL می‌گیرد (whereRaw، selectRaw، orderByRaw، havingRaw، DB::raw) اگر ورودی کاربر را مستقیم در رشته قرار دهید آسیب‌پذیر است.

<?php
// ❌ آسیب‌پذیر
User::whereRaw("email = '{$request->email}'")->get();

// ✅ امن: binding
User::whereRaw('email = ?', [$request->email])->get();
User::selectRaw('price * ? as price_with_tax', [1.09])->get();

// ⚠️ نام ستون‌ها bind نمی‌شوند! orderBy روی ورودی کاربر را whitelist کنید
$sort = in_array($request->sort, ['name', 'created_at'], true)
    ? $request->sort
    : 'created_at';
User::orderBy($sort)->get();

PDO فقط «مقدار» را bind می‌کند، نه نام ستون، نام جدول یا جهت مرتب‌سازی. پس orderBy($request->input('sort')) یا select($request->fields) بدون whitelist، خطر injection یا افشای ستون‌های حساس دارد.

درج، به‌روزرسانی و Mass Assignment

درج و به‌روزرسانی

$post = new Post;

$post = Post::create(['title' => 'Hello', 'body' => '...']);

Mass Assignment

Mass assignment یعنی پر کردن چند attribute با یک آرایه (create($data)، fill($data)، update($data)). خطر آن این است که کاربر فیلدی مثل is_admin یا balance را به فرم اضافه کند و چون کد $request->all() را پاس می‌دهد، آن فیلد هم ذخیره شود.

$fillable (whitelist)

  • فقط ستون‌های فهرست‌شده قابل mass assign هستند
  • امن‌تر؛ ستون جدیدی که بعداً اضافه شود خودکار باز نمی‌شود
  • رویکرد پیشنهادی

$guarded (blacklist)

  • همه‌چیز به‌جز ستون‌های فهرست‌شده مجاز است
  • $guarded = [] یعنی همه آزاد — فقط وقتی همیشه $request->validated() پاس می‌دهید
  • ستون حساس جدید را ممکن است فراموش کنید
<?php
class User extends Model
{
    protected $fillable = ['name', 'email', 'password'];
}

// ✅ فقط داده اعتبارسنجی‌شده
User::create($request->validated());

// ❌ خطرناک حتی با $fillable اگر $fillable گسترده باشد
User::create($request->all());

// تخصیص مستقیم از mass assignment عبور می‌کند (عمداً و آگاهانه)
$user->is_admin = true;
$user->save();

// forceFill / forceCreate: نادیده گرفتن guard برای کد مورد اعتماد
$user->forceFill(['email_verified_at' => now()])->save();

Model::unguard() محافظت را برای همه مدل‌ها خاموش می‌کند (معمولاً در seederها استفاده می‌شد). اگر در کد اپلیکیشن فراخوانی شود و reguard() نشود، کل برنامه در برابر mass assignment بی‌دفاع می‌شود. نسخه امن‌تر: Model::unguarded(fn () => ...) که فقط داخل closure اثر دارد.

به‌صورت پیش‌فرض، فیلدهایی که در $fillable نیستند بی‌صدا دور ریخته می‌شوند. با Model::preventSilentlyDiscardingAttributes(! app()->isProduction()) در محیط توسعه به‌جای آن exception گرفته می‌شود و باگ‌های «چرا این فیلد ذخیره نشد؟» زود پیدا می‌شوند.

Attribute Casting، Accessor/Mutator و Serialization

Casting

Cast تبدیل خودکار نوع داده بین دیتابیس و PHP است: هنگام خواندن (مثلاً رشته JSON → آرایه، tinyint → bool، رشته تاریخ → Carbon) و هنگام نوشتن (برعکس). از Laravel 11 روش پیشنهادی متد casts() است (خاصیت $casts هنوز کار می‌کند). مزیت متد: می‌توان در آن از فراخوانی متد استفاده کرد، مثل AsEnumCollection::of(...).

<?php
use App\Enums\OrderStatus;
use Illuminate\Database\Eloquent\Casts\AsCollection;
use Illuminate\Database\Eloquent\Casts\AsEnumCollection;

class Order extends Model
{
    protected function casts(): array
    {
        return [
            'paid_at'      => 'datetime',
            'shipped_on'   => 'immutable_date',
            'total'        => 'decimal:2',
            'is_gift'      => 'boolean',
            'meta'         => 'array',               // JSON ⇄ array
            'items'        => AsCollection::class,   // JSON ⇄ Collection
            'status'       => OrderStatus::class,    // backed enum
            'flags'        => AsEnumCollection::of(OrderFlag::class),
            'card_last4'   => 'encrypted',           // رمز با APP_KEY
            'secret_notes' => 'encrypted:array',
            'pin'          => 'hashed',
        ];
    }
}

enum OrderStatus: string
{
    case Pending = 'pending';
    case Paid    = 'paid';
}

$order->status === OrderStatus::Paid;   // مقایسه نوع‌امن
$order->meta['coupon'] ?? null;

با cast نوع array، تغییر مستقیم یک کلید ($order->meta['x'] = 1) خطای «Indirect modification» می‌دهد چون accessor یک کپی برمی‌گرداند. کل آرایه را دوباره assign کنید یا از AsArrayObject/AsCollection استفاده کنید. همچنین ستون encrypted قابل جستجو با where نیست و با چرخش APP_KEY باید مراقب باشید.

Custom Cast

<?php
use Illuminate\Contracts\Database\Eloquent\CastsAttributes;

class MoneyCast implements CastsAttributes
{
    public function get(Model $model, string $key, mixed $value, array $attributes): Money
    {
        return new Money((int) $value, $attributes['currency'] ?? 'IRR');

    public function set(Model $model, string $key, mixed $value, array $attributes): array
    {
        return [
            $key       => $value->amount,
            'currency' => $value->currency,
        ];
    }
}

Accessor و Mutator

Accessor مقدار را هنگام خواندن تغییر می‌دهد و Mutator هنگام نوشتن. سینتکس مدرن (Laravel 9+): یک متد protected با نام camelCase هم‌نام attribute که Attribute برمی‌گرداند. سینتکس قدیمی getFirstNameAttribute/setFirstNameAttribute هنوز پشتیبانی می‌شود.

<?php
use Illuminate\Database\Eloquent\Casts\Attribute;

class User extends Model
{
    // accessor + mutator برای ستون واقعی first_name
    protected function firstName(): Attribute
    {
        return Attribute::make(
            get: fn (string $value) => ucfirst($value),
            set: fn (string $value) => strtolower(trim($value)),
        );
    }

    // attribute مجازی (ستون ندارد)
    protected function fullName(): Attribute
    {
        return Attribute::make(
            get: fn (mixed $value, array $attributes) =>
                $attributes['first_name'] . ' ' . $attributes['last_name'],
        )->shouldCache();
    }
}

echo $user->full_name;

فرق cast با accessor: cast تبدیل نوع عمومی و دوطرفه است (قابل استفاده مجدد در چند مدل)؛ accessor منطق نمایشی/محاسباتی خاص یک مدل است. accessorها در کوئری SQL قابل استفاده نیستند — where('full_name', ...) کار نمی‌کند چون full_name ستون نیست.

Serialization: hidden، visible، appends

وقتی مدل به آرایه یا JSON تبدیل می‌شود (toArray()، toJson()، یا return مستقیم از کنترلر)، این خاصیت‌ها تعیین می‌کنند چه چیزی خروجی برود:

  • $hidden = ['password', 'remember_token']: هرگز در خروجی نیاید (blacklist).
  • $visible = ['id', 'name']: فقط این‌ها (whitelist).
  • $appends = ['full_name']: accessorهای مجازی به خروجی اضافه شوند (به‌صورت پیش‌فرض اضافه نمی‌شوند).
  • در زمان اجرا: $user->makeVisible('email')، makeHidden، setVisible، append('x').
  • رابطه‌های لودشده هم در خروجی می‌آیند؛ تاریخ‌ها به‌صورت پیش‌فرض با قالب ISO-8601 (UTC) سریالایز می‌شوند (قابل تغییر با serializeDate).

هر accessor داخل $appends در هر سریالایز اجرا می‌شود؛ اگر داخلش به رابطه‌ای دسترسی داشته باشید ($this->orders->sum(...)) روی یک لیست ۱۰۰تایی، N+1 پنهان ساخته‌اید. برای APIهای جدی به‌جای تکیه بر $hidden/$appends از API Resource استفاده کنید تا قرارداد خروجی صریح باشد.

روابط یک‌به‌یک و یک‌به‌چند

رابطه‌ها به‌صورت متد روی مدل تعریف می‌شوند و یک شیء Relation برمی‌گردانند. دو شکل دسترسی وجود دارد: $user->posts() (متد) یک Query Builder برای ادامه کوئری است، و $user->posts (dynamic property) نتیجه را لود و کش می‌کند.

hasOne / belongsTo

<?php
// migration
Schema::create('profiles', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->unique()->constrained()->cascadeOnDelete();
    $table->string('bio')->nullable();
    $table->timestamps();
});

class User extends Model
{
    public function profile(): HasOne
    {
        return $this->hasOne(Profile::class);   // profiles.user_id = users.id
    }
}

class Profile extends Model
{
    public function user(): BelongsTo
    {
        return $this->belongsTo(User::class);   // profiles.user_id → users.id
    }
}

قاعده تشخیص: کلید خارجی در جدول هر مدلی باشد، آن مدل belongsTo دارد؛ طرف مقابل hasOne یا hasMany. نام کلید خارجی پیش‌فرض: snake_case نام مدل والد + _id. امضای کامل: hasOne(Related, foreignKey, localKey) و belongsTo(Related, foreignKey, ownerKey).

Custom Pivot Model

اگر pivot خودش منطق دارد (cast، accessor، رابطه یا رویداد)، یک مدل که از Pivot ارث می‌برد بسازید و با using() معرفی کنید:

<?php
use Illuminate\Database\Eloquent\Relations\Pivot;

class RoleUser extends Pivot
{
    public $incrementing = false;   // اگر ستون id ندارد

    protected function casts(): array
    {
        return ['expires_at' => 'datetime'];
    }

    public function isExpired(): bool
    {
        return $this->expires_at?->isPast() ?? false;
    }
}

// در User
return $this->belongsToMany(Role::class)->using(RoleUser::class)->withPivot('expires_at');

چه زمانی pivot باید به یک مدل کامل تبدیل شود؟ وقتی رابطه خودش یک مفهوم دامنه با هویت و چرخه حیات مستقل است (مثلاً Enrollment بین Student و Course با نمره، وضعیت و پرداخت). در آن صورت به‌جای belongsToMany، دو رابطه hasMany/belongsTo به مدل میانی تعریف کنید.

روابط Through، Polymorphic و One-of-Many

hasOneThrough و hasManyThrough

برای دسترسی به رکوردهای «دو قدم آن‌طرف‌تر» از طریق یک مدل میانی، بدون نوشتن join دستی:

Country ──hasMany──► User ──hasMany──► Post
   └──────────── hasManyThrough(Post, User) ───────────►

Mechanic ──hasOne──► Car ──hasOne──► Owner
   └──────── hasOneThrough(Owner, Car) ────────►
<?php
// countries(id) ← users(id, country_id) ← posts(id, user_id)
class Country extends Model
{
    public function posts(): HasManyThrough
    {
        return $this->hasManyThrough(
            Post::class,   // مقصد
            User::class,   // میانی
            'country_id',  // FK روی users
            'user_id',     // FK روی posts
            'id',          // local key روی countries
            'id'           // local key روی users
        );
    }
}

class Mechanic extends Model
{
    public function carOwner(): HasOneThrough
    {
        return $this->hasOneThrough(Owner::class, Car::class);
    }
}

Through فقط برای زنجیره‌های hasOne/hasMany طراحی شده است؛ برای مسیرهایی که از belongsToMany عبور می‌کنند، معمولاً whereHas تو در تو یا پکیج‌های جانبی لازم است.

رابطه چندریختی یعنی یک مدل می‌تواند به بیش از یک نوع مدل والد تعلق داشته باشد؛ مثلاً Comment هم برای Post و هم برای Video. به‌جای دو ستون FK، دو ستون commentable_id و commentable_type نگه می‌داریم.

Morph Map

به‌صورت پیش‌فرض نام کامل کلاس (App\Models\Post) در ستون _type ذخیره می‌شود. اگر بعداً namespace یا نام کلاس را عوض کنید داده‌ها خراب می‌شوند و جزئیات داخلی کد هم در دیتابیس لو می‌رود. راه‌حل: morph map.

<?php
// AppServiceProvider::boot()
use Illuminate\Database\Eloquent\Relations\Relation;

Relation::enforceMorphMap([
    'post'  => \App\Models\Post::class,
    'video' => \App\Models\Video::class,
]);

معایب polymorphic: امکان تعریف foreign key constraint در دیتابیس وجود ندارد (چون ستون id به چند جدول اشاره می‌کند)، پس یکپارچگی ارجاعی و cascade باید در اپلیکیشن مدیریت شود؛ join و گزارش‌گیری سخت‌تر است. enforceMorphMap علاوه بر نگاشت، اگر مدلی بدون نگاشت ذخیره شود exception می‌دهد.

One-of-Many

گاهی از یک رابطه hasMany فقط «یکی» را می‌خواهیم: آخرین سفارش، قدیمی‌ترین ورود، گران‌ترین خرید. این‌ها به‌صورت یک رابطه hasOne با زیرکوئری بهینه تعریف می‌شوند و قابل eager load هستند:

<?php
class User extends Model
{
    public function latestOrder(): HasOne
    {
        return $this->hasOne(Order::class)->latestOfMany();
    }

    public function oldestOrder(): HasOne
    {
        return $this->hasOne(Order::class)->oldestOfMany();
    }

    public function largestOrder(): HasOne
    {
        return $this->hasOne(Order::class)->ofMany('total', 'max');
    }
}

$users = User::with('latestOrder')->get();   // دو کوئری، نه N+1

Eager Loading و مسئله N+1

Lazy loading یعنی رابطه فقط وقتی به dynamic property دسترسی پیدا می‌کنید لود شود. اگر این کار داخل حلقه باشد، برای هر آیتم یک کوئری جدا اجرا می‌شود: ۱ کوئری برای لیست + N کوئری برای رابطه‌ها = N+1.

<?php
// ❌ N+1: برای ۵۰ پست، ۵۱ کوئری
$posts = Post::latest()->take(50)->get();        // 1 query
foreach ($posts as $post) {
    echo $post->author->name;                      // +1 query per post
}

// ✅ Eager loading: فقط ۲ کوئری
$posts = Post::with('author')->latest()->take(50)->get();

SELECT * FROM users WHERE id = 7      [2]     SELECT * FROM users
SELECT * FROM users WHERE id = 3      [3]       WHERE id IN (7, 3, 9, ...)           [2]
SELECT * FROM users WHERE id = 9      [4]

SELECT * FROM users WHERE id = 12     [51]    ۲ کوئری، مستقل از تعداد پست‌ها
───────────────────────────────

پیشگیری: preventLazyLoading و shouldBeStrict

<?php
// app/Providers/AppServiceProvider.php
use Illuminate\Database\Eloquent\Model;

public function boot(): void
{
    // در توسعه/تست هر lazy load یک LazyLoadingViolationException می‌دهد
    Model::preventLazyLoading(! $this->app->isProduction());

    // یا هر سه محافظ با هم:
    // preventLazyLoading + preventSilentlyDiscardingAttributes + preventAccessingMissingAttributes
    Model::shouldBeStrict(! $this->app->isProduction());

    // در production به‌جای exception فقط لاگ کن
    Model::handleLazyLoadingViolationUsing(function (Model $model, string $relation) {
        logger()->warning('Lazy loading', [get_class($model), $relation]);
    });
}

preventAccessingMissingAttributes یعنی اگر ستونی را select نکرده‌اید (مثلاً select('id')) و به $user->email دسترسی پیدا کنید، به‌جای null بی‌صدا، exception بگیرید. ابزارهای تشخیص N+1 در عمل: Laravel Debugbar، Telescope (بخش Queries)، DB::listen و DB::enableQueryLog()، و در تست‌ها expectsDatabaseQueryCount.

نسخه‌های جدید Laravel 12 قابلیت «automatic eager loading» را هم اضافه کرده‌اند (Model::automaticallyEagerLoadRelationships() یا ->withRelationshipAutoloading() روی Collection) که با اولین دسترسی lazy، رابطه را برای کل collection یکجا لود می‌کند. این جایگزین طراحی درست کوئری نیست ولی شبکه ایمنی خوبی است.

Local / Global Scope و Soft Delete

Local Scope

Scope محلی یک تکه شرط قابل استفاده مجدد است که خوانایی کوئری را بالا می‌برد و شرط‌های تجاری (مثلاً «فعال» یعنی چه) را در یک جا متمرکز می‌کند.

<?php
use Illuminate\Database\Eloquent\Builder;
use Illuminate\Database\Eloquent\Attributes\Scope;

class Post extends Model
{
    // سینتکس کلاسیک (همه نسخه‌ها): پیشوند scope
    public function scopePublished(Builder $query): void
    {
        $query->whereNotNull('published_at')->where('published_at', '<=', now());
    }

    // scope پارامتری
    public function scopeOfType(Builder $query, string $type): void
    {
        $query->where('type', $type);
    }

    // Laravel 12: attribute #[Scope] بدون پیشوند
    #[Scope]
    protected function popular(Builder $query): void
    {
        $query->where('views', '>', 1000);
    }
}

Post::published()->ofType('news')->popular()->get();

Global Scope

Scope سراسری روی همه کوئری‌های مدل اعمال می‌شود؛ نمونه آشنا: خود SoftDeletes، یا multi-tenancy (where tenant_id = ?).

<?php
use Illuminate\Database\Eloquent\Scope;

class TenantScope implements Scope
{
    public function apply(Builder $builder, Model $model): void
    {
        $builder->where($model->getTable() . '.tenant_id', tenant()->id);
    }
}

// ثبت با attribute
#[ScopedBy([TenantScope::class])]
class Invoice extends Model {}

// یا در booted()
protected static function booted(): void
{
    static::addGlobalScope(new TenantScope);
    static::addGlobalScope('active', fn (Builder $b) => $b->where('active', true));
}

// حذف موقت
Invoice::withoutGlobalScope(TenantScope::class)->get();
Invoice::withoutGlobalScope('active')->get();
Invoice::withoutGlobalScopes()->get();

Global scope «جادوی پنهان» است: توسعه‌دهنده‌ای که کوئری را می‌خواند شرط را نمی‌بیند و دیباگ سخت می‌شود. همچنین Query Builder خام (DB::table('invoices')) scopeها را اعمال نمی‌کند؛ در multi-tenancy این می‌تواند نشت داده بین tenantها باشد. نام جدول را در شرط بیاورید تا در joinها ابهام ستون پیش نیاید.

Soft Delete

به‌جای حذف فیزیکی، ستون deleted_at مقدار می‌گیرد و یک global scope رکوردهای حذف‌شده را از همه کوئری‌ها پنهان می‌کند.

<?php
// migration
$table->softDeletes();   // ستون nullable deleted_at

use Illuminate\Database\Eloquent\SoftDeletes;

class Post extends Model
{
    use SoftDeletes;
}

$post->delete();                 // UPDATE posts SET deleted_at = now()
$post->trashed();                // true
Post::withTrashed()->find($id);  // شامل حذف‌شده‌ها
Post::onlyTrashed()->get();      // فقط حذف‌شده‌ها
$post->restore();                // deleted_at = null
$post->forceDelete();            // DELETE واقعی

// روی رابطه هم کار می‌کند
$user->posts()->withTrashed()->get();

مشکل unique index با soft delete: اگر email یکتا باشد و کاربر soft delete شود، سطرش هنوز در جدول است و ثبت‌نام دوباره با همان ایمیل خطای duplicate می‌دهد. ایندکس ترکیبی (email, deleted_at) هم راه‌حل کامل نیست، چون در MySQL و PostgreSQL مقادیر NULL با هم برابر حساب نمی‌شوند و دو کاربر فعال با یک ایمیل مجاز می‌شوند. راه‌حل‌ها: partial index در PostgreSQL (UNIQUE (email) WHERE deleted_at IS NULL)، در MySQL یک generated column که فقط برای سطرهای فعال مقدار دارد و unique روی آن؛ و در اعتبارسنجی Rule::unique('users')->withoutTrashed().

Soft delete روی رابطه‌ها cascade نمی‌شود (foreign key ON DELETE CASCADE فقط با DELETE واقعی فعال می‌شود). اگر پست soft delete شد و کامنت‌هایش هم باید پنهان شوند، باید در رویداد deleting یا observer خودتان آن را مدیریت کنید. همچنین جدول به مرور بزرگ می‌شود؛ با Pruning رکوردهای قدیمی را پاک کنید.

Eloquent در چرخه حیات مدل رویدادهایی dispatch می‌کند. رویدادهای «ـing» قبل از عمل اجرا می‌شوند و اگر listener مقدار false برگرداند عمل لغو می‌شود؛ رویدادهای «ـed» بعد از عمل.

create:   saving → creating → [INSERT] → created → saved
update:   saving → updating → [UPDATE] → updated → saved
delete:   deleting → [DELETE / SET deleted_at] → deleted   (+ trashed در SoftDeletes)
force:    forceDeleting → [DELETE] → forceDeleted
restore:  restoring → [UPDATE deleted_at=NULL] → restored
read:     retrieved        replicate: replicating

اگر save() روی مدلی صدا زده شود که هیچ ستون dirty ندارد، کوئری UPDATE زده نمی‌شود و رویدادهای updating/updated اجرا نمی‌شوند؛ اما saving/saved اجرا می‌شوند.

چه زمانی رویدادهای مدل اجرا نمی‌شوند؟ هر عملیاتی که مستقیماً از Query Builder یک کوئری می‌زند و مدل را hydrate نمی‌کند: Post::where(...)->update([...])، Post::where(...)->delete()، insert()، upsert()، increment روی query builder، DB::table()، و MassPrunable. همچنین saveQuietly()، deleteQuietly()، updateQuietly() و Model::withoutEvents(fn () => ...) عمداً رویداد را خاموش می‌کنند. اگر audit log یا پاک‌کردن کش به observer وابسته است، این مسیرها باید آگاهانه مدیریت شوند.

Observer داخل تراکنش: created قبل از commit اجرا می‌شود؛ اگر در آن job صف کنید یا ایمیل بفرستید و تراکنش rollback شود، کار روی داده ناموجود انجام شده است. راه‌حل: پیاده‌سازی اینترفیس ShouldHandleEventsAfterCommit روی observer (جزئیات afterCommit صف‌ها در صفحه «Laravel Deeper»). منطق سنگین را هم در observer نگذارید؛ observer کنترل‌پذیری کد را کم می‌کند چون جریان اجرا پنهان است.

Eloquent Collection و کار با داده‌های حجیم

خروجی get() و رابطه‌های چندتایی یک Illuminate\Database\Eloquent\Collection است که از Collection پایه ارث می‌برد و متدهای مخصوص مدل هم دارد: find($id)، modelKeys()، load()، loadMissing()، fresh()، makeHidden()، toQuery()، only()/except() بر اساس کلید اصلی.

متد Collection یا متد Query؟

<?php

تراکنش‌ها و قفل‌گذاری (Pessimistic Locking)

تراکنش چند عملیات را به یک واحد اتمیک تبدیل می‌کند: یا همه commit می‌شوند یا هیچ‌کدام. در لاراول ساده‌ترین و امن‌ترین روش DB::transaction با closure است که در صورت exception خودکار rollback و exception را دوباره پرتاب می‌کند.

<?php
use Illuminate\Support\Facades\DB;

$order = DB::transaction(function () use ($cart, $user) {
    $order = $user->orders()->create(['total' => $cart->total()]);
    foreach ($cart->items as $item) {
        $order->items()->create($item->toArray());
    }
    return $order;            // مقدار بازگشتی closure برگردانده می‌شود
}, attempts: 3);              // در صورت deadlock تا ۳ بار کل closure را تکرار کن

// روش دستی (کنترل بیشتر، ولی مسئولیت rollback با شما)
DB::beginTransaction();
try {
    // ...
    DB::commit();
} catch (\Throwable $e) {
    DB::rollBack();
    throw $e;
}

آرگومان دوم DB::transaction تعداد تلاش است و فقط برای deadlock (و خطاهای مشابه همزمانی) دوباره تلاش می‌کند، نه هر exception. چون کل closure دوباره اجرا می‌شود، کارهای غیرتراکنشی (فراخوانی API خارجی، ارسال ایمیل) را داخلش نگذارید یا idempotent کنید. تراکنش‌های تو در تو با savepoint پیاده می‌شوند.

Race Condition و قفل سطری

سناریو: دو درخواست هم‌زمان موجودی کیف پول ۱۰۰ را می‌خوانند، هر دو ۸۰ برداشت می‌کنند و هر دو موفق می‌شوند (lost update). راه‌حل: قفل بدبینانه.

<?php
DB::transaction(function () use ($walletId, $amount) {
    // SELECT ... FOR UPDATE: سطر تا پایان تراکنش برای نوشتن و قفل دیگران بسته است
    $wallet = Wallet::whereKey($walletId)->lockForUpdate()->firstOrFail();

    if ($wallet->balance < $amount) {
        throw new InsufficientFunds();
    }
    $wallet->decrement('balance', $amount);
});

// sharedLock: SELECT ... LOCK IN SHARE MODE / FOR SHARE
// دیگران می‌توانند بخوانند ولی تا commit نمی‌توانند تغییر دهند
$product = Product::whereKey($id)->sharedLock()->first();

Pessimistic (lockForUpdate)

  • قفل در دیتابیس؛ تضمین قطعی
  • مناسب رقابت زیاد روی یک سطر (موجودی، کیف پول)
  • خطر deadlock و کاهش throughput؛ تراکنش را کوتاه نگه دارید
  • بیرون از تراکنش بی‌اثر است

Optimistic (ستون version)

  • UPDATE ... WHERE id = ? AND version = ? و بررسی تعداد سطرهای تغییرکرده
  • بدون قفل؛ مناسب رقابت کم
  • در صورت تعارض باید retry یا خطا به کاربر
  • Eloquent پشتیبانی داخلی ندارد؛ دستی پیاده می‌شود

برای عملیات ساده، اتمیک کردن در خود SQL از قفل ارزان‌تر است: Wallet::whereKey($id)->where('balance', '>=', $amount)->decrement('balance', $amount) و بررسی اینکه خروجی (تعداد سطرهای تأثیرپذیر) برابر ۱ باشد. قفل توزیع‌شده سطح اپلیکیشن (Cache::lock) در صفحه «Laravel Deeper» آمده است.

API Resource

Resource یک لایه تبدیل (transformation layer) بین مدل و JSON خروجی است. مزیت: قرارداد API از ساختار جدول جدا می‌شود، فیلدهای حساس تصادفاً لو نمی‌روند، و شرط‌ها (رابطه لودشده، دسترسی کاربر) صریح‌اند.

php artisan make:resource UserResource
php artisan make:resource UserCollection        # یا --collection
<?php
use Illuminate\Http\Request;
use Illuminate\Http\Resources\Json\JsonResource;

class UserResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id'          => $this->id,
            'name'        => $this->name,
            'email'       => $this->when($request->user()?->isAdmin(), $this->email),
            'posts'       => PostResource::collection($this->whenLoaded('posts')),
            'posts_count' => $this->whenCounted('posts'),
            'created_at'  => $this->created_at->toIso8601String(),
            $this->mergeWhen($this->is_vip, ['tier' => $this->tier]),
        ];
    }
}

// کنترلر
public function index()
{
    $users = User::withCount('posts')->paginate(20);
    return UserResource::collection($users);   // data + links + meta خودکار
}

public function show(User $user)
{
    return new UserResource($user->load('posts'));
}

// متادیتای اضافه
return UserResource::collection($users)->additional(['meta' => ['version' => 'v1']]);

whenLoaded('posts') کلیدی‌ترین ابزار جلوگیری از N+1 در Resource است: فقط اگر رابطه از قبل eager load شده باشد آن را در خروجی می‌گذارد و هرگز کوئری جدید نمی‌زند. نوشتن $this->posts مستقیم داخل Resource در یک collection، همان N+1 است. خروجی به‌صورت پیش‌فرض در کلید data wrap می‌شود (JsonResource::withoutWrapping() برای حذف).

Model Factory، Pruning و Replicate

Factory

Factory برای ساخت داده تستی و seed استفاده می‌شود. مدل باید تریت HasFactory داشته باشد. پایه‌اش متد definition() است و stateها حالت‌های خاص را تعریف می‌کنند.

<?php
// php artisan make:factory PostFactory --model=Post
class PostFactory extends Factory
{
    public function definition(): array
    {
        return [
            'user_id'      => User::factory(),       // رابطه: کاربر جدید می‌سازد
            'title'        => fake()->sentence(),
            'body'         => fake()->paragraphs(3, true),
            'published_at' => null,
        ];
    }

    public function published(): static
    {
        return $this->state(fn (array $attributes) => [
            'published_at' => now(),
        ]);
    }

    public function configure(): static
    {
        return $this->afterCreating(function (Post $post) {
            $post->tags()->attach(Tag::factory()->count(2)->create());
        });
    }
}

// استفاده
$post  = Post::factory()->make();                    // بدون ذخیره
$posts = Post::factory()->count(10)->published()->create();

// has: فرزندان (hasMany)
$user = User::factory()->has(Post::factory()->count(3))->create();
$user = User::factory()->hasPosts(3)->create();       // magic method

// for: والد (belongsTo)
$posts = Post::factory()->count(3)->for(User::factory()->state(['name' => 'Ali']))->create();

// belongsToMany با داده pivot
$user = User::factory()->hasAttached(Role::factory()->count(2), ['expires_at' => now()->addYear()])->create();

// sequence: مقادیر چرخشی
Post::factory()->count(4)->sequence(['status' => 'draft'], ['status' => 'published'])->create();

// recycle: استفاده مجدد از یک نمونه موجود برای همه رابطه‌ها
$tenant = Tenant::factory()->create();
Invoice::factory()->count(5)->recycle($tenant)->create();

در definition() رابطه را به‌صورت User::factory() (نه User::factory()->create()->id) بنویسید؛ در این حالت اگر با for() یا مقدار صریح user_id override شود، کاربر اضافه ساخته نمی‌شود.

Prunable

  • هر رکورد را hydrate و delete() می‌کند
  • رویدادهای deleting/deleted و هوک pruning() اجرا می‌شوند
  • با SoftDeletes، حذف قطعی (forceDelete) انجام می‌دهد
  • کندتر روی حجم بالا

MassPrunable

  • یک DELETE انبوه با کوئری
  • بدون رویداد و بدون pruning()
  • بسیار سریع؛ مناسب لاگ و داده موقت

Replicate

// نسخه ذخیره‌نشده از مدل، بدون کلید اصلی و timestamps

چک‌لیست کارایی Eloquent

  1. N+1 را حذف کنید: with() برای رابطه‌هایی که در حلقه، view یا Resource استفاده می‌شوند؛ preventLazyLoading() در توسعه.
  2. فقط ستون‌های لازم: select(['id', 'title']) و with('author:id,name')؛ ستون‌های TEXT/JSON سنگین را بی‌دلیل نیاورید.
  3. Aggregate در دیتابیس: withCount، withSum، count() روی query به‌جای شمردن Collection.
  4. ایندکس‌گذاری: روی کلیدهای خارجی، ستون‌های where/orderBy، ایندکس ترکیبی متناسب با کوئری (ترتیب ستون‌ها مهم است)، ستون‌های _type/_id در polymorphic (morphs() خودش ایندکس می‌سازد).
  5. exists به‌جای count: برای بررسی وجود، exists() ارزان‌تر از count() > 0 است.
  6. عملیات انبوه: insert/upsert/update روی query به‌جای حلقه save() (آگاه از نبود رویداد).
  7. داده حجیم: chunkById/lazyById به‌جای all().
  8. صفحه‌بندی درست: simplePaginate/cursorPaginate برای جدول‌های بزرگ.
  9. کش: نتایج کوئری‌های پرتکرار و کم‌تغییر را با Cache::remember کش و در observer/رویداد مدل invalidate کنید.
  10. تحلیل: کوئری را با toSql()/toRawSql() یا dd()/dump() روی builder ببینید و در دیتابیس EXPLAIN بگیرید؛ ->explain() هم روی builder وجود دارد.
  11. از accessorهای سنگین در $appends و $with سراسری پرهیز کنید.
  12. whereHas روی جدول‌های بزرگ به زیرکوئری EXISTS تبدیل می‌شود؛ اگر کند بود، join یا whereIn با زیرکوئری را بسنجید.
<?php
// دیدن کوئری‌ها هنگام دیباگ
DB::enableQueryLog();
$posts = Post::with('author')->get();
dump(DB::getQueryLog());

// هشدار برای کوئری‌های کند (AppServiceProvider)
DB::listen(function ($query) {
    if ($query->time > 500) {
        logger()->warning('Slow query', ['sql' => $query->sql, 'ms' => $query->time]);

اگر در آزمون سناریویی مثل «صفحه لیست سفارش‌ها ۳ ثانیه طول می‌کشد» دادند، پاسخ ساختاریافته: (۱) اندازه‌گیری با Telescope/Debugbar و شمارش کوئری‌ها، (۲) رفع N+1 با eager loading، (۳) محدود کردن ستون‌ها و صفحه‌بندی، (۴) EXPLAIN و افزودن ایندکس، (۵) انتقال aggregateها به SQL، (۶) کش و در نهایت denormalization (مثلاً ستون شمارنده).

تعریف: در Active Record هر شیء هم داده یک سطر جدول را نگه می‌دارد و هم مسئول ذخیره و بازیابی خودش است ($user->save()). در Data Mapper موجودیت‌ها شیء ساده‌اند و یک لایه جدا (Mapper/EntityManager) آن‌ها را به دیتابیس نگاشت می‌کند. Eloquent پیاده‌سازی Active Record است؛ Doctrine نمونه Data Mapper.

// Active Record
$user = User::find(1); $user->name = 'Ali'; $user->save();
// Data Mapper
$user = $repo->find(1); $user->rename('Ali'); $em->flush();

پیامدهای Active Record:

  • ✅ توسعه سریع، کد کم، قراردادهای پیش‌فرض، API روان برای رابطه‌ها.
  • ❌ نقض SRP؛ دامنه به ساختار جدول و دیتابیس وابسته است.
  • ❌ تست واحد بدون دیتابیس سخت‌تر است؛ معمولاً تست با RefreshDatabase.
  • ❌ Unit of Work ندارد؛ هر save یک کوئری فوری است و دسته‌بندی تغییرات با خود توسعه‌دهنده است (تراکنش).

جمع‌بندی: برای اکثر اپلیکیشن‌های وب مناسب است؛ در دامنه‌های پیچیده با مدل‌های لاغر، Service/Action کلاس‌ها و در صورت نیاز Repository، معایبش را کنترل می‌کنیم.

مسئله N+1 چیست؟ با یک مثال تعداد کوئری‌ها را نشان دهید و راه‌های تشخیص و رفع آن را در لاراول توضیح دهید.

تعریف: وقتی یک لیست با ۱ کوئری گرفته می‌شود و سپس برای هر آیتم در حلقه، رابطه‌اش به‌صورت lazy با یک کوئری جدا لود می‌شود؛ مجموعاً N+1 کوئری.

$posts = Post::all();                 // 1 query (مثلاً 100 پست)
foreach ($posts as $p) echo $p->author->name;   // +100 query  => 101

$posts = Post::with('author')->get();  // 2 query: posts + users WHERE id IN (...)

تشخیص: Debugbar/Telescope (تعداد و تکرار کوئری‌ها)، DB::enableQueryLog()، DB::listen، و مهم‌تر از همه Model::preventLazyLoading(! app()->isProduction()) که در توسعه exception می‌دهد.

رفع:

  • with() هنگام کوئری، شامل تو در تو (comments.user) و مقید با closure.
  • load()/loadMissing() وقتی مدل‌ها از قبل گرفته شده‌اند.
  • withCount/withSum به‌جای $post->comments->count() در حلقه.
  • در API Resource از whenLoaded استفاده شود.

نکته: eager load بی‌رویه هم هزینه دارد (داده و حافظه اضافه)؛ فقط آنچه استفاده می‌شود لود شود و ستون‌ها محدود شوند.

Mass Assignment چیست و چه خطر امنیتی دارد؟ $fillable و $guarded را مقایسه کنید و بگویید Model::unguard() چه ریسکی دارد.

تعریف: پر کردن چند attribute مدل با یک آرایه در یک فراخوانی: create()، fill()، update().

خطر: اگر ورودی کاربر مستقیم پاس شود (User::create($request->all()))، مهاجم می‌تواند فیلدهایی مثل is_admin=1 یا balance را به درخواست اضافه کند و آن‌ها هم ذخیره شوند (privilege escalation).

  • $fillable = whitelist؛ فقط این ستون‌ها مجازند. امن‌تر، چون ستون جدید به‌طور پیش‌فرض بسته است.
  • $guarded = blacklist؛ همه به‌جز این‌ها. $guarded = [] یعنی همه باز. ریسک فراموش کردن ستون حساس جدید.
protected $fillable = ['name', 'email'];
User::create($request->validated());   // دفاع دولایه: validation + fillable
$user->forceFill(['is_admin' => true])->save();  // فقط در کد مورد اعتماد

unguard: محافظت را به‌صورت سراسری برای همه مدل‌ها در طول اجرای پروسس خاموش می‌کند؛ اگر در کد اپ استفاده و برگردانده نشود (یا در Octane که پروسس ماندگار است) کل برنامه آسیب‌پذیر می‌شود. جایگزین امن: Model::unguarded(fn () => ...) با دامنه محدود، و فقط در seeder.

تکمیلی: preventSilentlyDiscardingAttributes() در توسعه باعث می‌شود فیلدهای غیرمجاز بی‌صدا دور ریخته نشوند و exception بدهند.

تفاوت $user->posts()->count() و $user->posts->count() چیست؟ هر کدام در چه شرایطی انتخاب درست است؟

با پرانتز (posts()) شیء Relation یعنی یک Query Builder برمی‌گردد و count() یک SELECT COUNT(*) در دیتابیس اجرا می‌کند؛ هیچ مدلی ساخته نمی‌شود.

بدون پرانتز (posts) dynamic property است: اگر رابطه لود نشده باشد، همه پست‌ها SELECT و به مدل تبدیل می‌شوند، نتیجه روی مدل کش می‌شود، سپس count() روی Collection در PHP اجرا می‌شود.

  • فقط عدد لازم است → posts()->count() یا برای لیست، withCount('posts') (یک زیرکوئری، بدون N+1).
  • رابطه قبلاً eager load شده یا بعداً خود پست‌ها را هم نمایش می‌دهید → posts->count() کوئری اضافه نمی‌زند و انتخاب بهتری است.
$users = User::withCount('posts')->get();
foreach ($users as $u) echo $u->posts_count;    // بدون کوئری اضافه

همین منطق برای where (SQL در برابر فیلتر حافظه)، exists() در برابر isNotEmpty() و sum صدق می‌کند. اشتباه رایج: Post::all()->where('active', 1) که کل جدول را می‌آورد.

رابطه چندبه‌چند بین User و Role را با migration و مدل پیاده کنید. تفاوت attach، sync، syncWithoutDetaching و toggle را توضیح دهید.

ساختار: جدول pivot role_user (نام مفرد الفبایی) با دو کلید خارجی و کلید اصلی ترکیبی برای جلوگیری از تکرار.

Schema::create('role_user', function (Blueprint $t) {
    $t->foreignId('role_id')->constrained()->cascadeOnDelete();
    $t->foreignId('user_id')->constrained()->cascadeOnDelete();
    $t->timestamps();
    $t->primary(['role_id', 'user_id']);
});
// User
public function roles(): BelongsToMany {
    return $this->belongsToMany(Role::class)->withTimestamps();
}
// Role
public function users(): BelongsToMany {
    return $this->belongsToMany(User::class);
}
  • attach($ids, $pivotData): فقط INSERT؛ وجود قبلی را چک نمی‌کند (بدون کلید یکتا، تکراری می‌سازد و با کلید یکتا خطا می‌دهد).
  • sync($ids): وضعیت نهایی را تعیین می‌کند؛ IDهای غایب detach و جدیدها attach می‌شوند. خروجی: attached/detached/updated. مناسب فرم «انتخاب نقش‌ها».
  • syncWithoutDetaching($ids): اضافه می‌کند اگر نیست، چیزی حذف نمی‌کند؛ attach ایمن در برابر تکرار.
  • toggle($ids): هر ID متصل را جدا و غیرمتصل را وصل می‌کند؛ مناسب like/bookmark.
  • detach / updateExistingPivot: حذف اتصال / به‌روزرسانی ستون‌های pivot.

برای ستون‌های اضافه withPivot()، برای منطق روی pivot using(CustomPivot::class)، و اگر رابطه خودش موجودیت مستقل است، آن را مدل کامل کنید.

رابطه Polymorphic چیست؟ یک سیستم کامنت برای Post و Video طراحی کنید و معایب این رابطه و نقش Morph Map را توضیح دهید.

تعریف: رابطه‌ای که در آن یک مدل می‌تواند به چند نوع مدل والد تعلق داشته باشد. به‌جای چند FK، دو ستون {name}_id و {name}_type ذخیره می‌شود.

// migration: $table->morphs('commentable');
class Comment extends Model {
    public function commentable(): MorphTo { return $this->morphTo(); }
}
class Post extends Model {
    public function comments(): MorphMany {
        return $this->morphMany(Comment::class, 'commentable');
    }
}
// AppServiceProvider::boot
Relation::enforceMorphMap(['post' => Post::class, 'video' => Video::class]);

چرا: جلوگیری از جدول‌های تکراری (post_comments، video_comments) و منطق مشترک.

معایب:

  • عدم امکان foreign key constraint و cascade در دیتابیس؛ یکپارچگی باید در کد (رویداد deleting) حفظ شود.
  • کوئری‌ها و گزارش‌ها (join) پیچیده‌تر؛ ایندکس ترکیبی (type, id) لازم است (morphs می‌سازد).

Morph Map: به‌جای نام کامل کلاس (App\Models\Post) یک alias پایدار ذخیره می‌کند؛ با refactor نام/namespace داده‌ها خراب نمی‌شوند و ساختار داخلی کد افشا نمی‌شود. enforceMorphMap همچنین برای مدل بدون نگاشت exception می‌دهد. انواع دیگر: morphOne، و چندبه‌چند با morphToMany/morphedByMany.

کد زیر چه مشکلی دارد؟ آن را بازنویسی کنید. User::where('active', 0)->chunk(100, fn ($users) => $users->each->update(['active' => 1]));

مشکل: chunk با LIMIT/OFFSET صفحه‌بندی می‌کند. بعد از پردازش صفحه اول، آن ۱۰۰ رکورد دیگر شرط active = 0 را ندارند و مجموعه نتیجه جابه‌جا می‌شود؛ کوئری بعدی با OFFSET 100 از ۱۰۰ رکورد پردازش‌نشده رد می‌شود. نتیجه: حدود نیمی از رکوردها به‌روز نمی‌شوند. همچنین هر update یک کوئری جدا است (۱۰۰ کوئری در هر chunk).

// ✅ اگر منطق یا رویداد مدل لازم است
User::where('active', 0)->chunkById(100, function ($users) {
    foreach ($users as $user) {
        $user->update(['active' => 1]);   // رویدادها اجرا می‌شوند
    }
});

// ✅ اگر رویداد لازم نیست: یک کوئری
User::where('active', 0)->update(['active' => 1]);

// ✅ میانه: chunk امن + update انبوه هر دسته
User::where('active', 0)->chunkById(1000, fn ($users) =>
    User::whereKey($users->modelKeys())->update(['active' => 1])
);

توضیح: chunkById از WHERE id > lastId ORDER BY id استفاده می‌کند؛ به تغییر داده حساس نیست و روی جدول بزرگ از OFFSET سریع‌تر است. برای پیمایش با API Collection، lazyById()؛ و cursor() فقط یک کوئری می‌زند ولی eager loading ندارد.

رویدادهای مدل و Observer را توضیح دهید. در چه شرایطی رویدادهای مدل اجرا نمی‌شوند و این چه خطری برای منطق برنامه دارد؟

تعریف: Eloquent در چرخه حیات مدل رویداد dispatch می‌کند: retrieved، creating/created، updating/updated، saving/saved، deleting/deleted، restoring/restored، forceDeleting/forceDeleted، replicating. رویدادهای «ـing» پیش از عمل‌اند و با return false عمل را لغو می‌کنند. Observer کلاسی است که همه listenerهای یک مدل را یکجا جمع می‌کند.

#[ObservedBy([OrderObserver::class])]
class Order extends Model {}

class OrderObserver implements ShouldHandleEventsAfterCommit {
    public function updated(Order $o): void {
        if ($o->wasChanged('status')) Cache::forget("order:{$o->id}");
    }
}

زمانی که اجرا نمی‌شوند:

  • عملیات انبوه روی query: Order::where(...)->update()، ->delete()، insert، upsert.
  • DB::table() و SQL خام.
  • saveQuietly، deleteQuietly، Model::withoutEvents()، MassPrunable.
  • save() بدون تغییر: updating/updated اجرا نمی‌شود.

خطر: اگر audit log، invalidation کش، همگام‌سازی جستجو (Scout) یا محاسبه فیلد به observer وابسته باشد، یک update انبوه بی‌صدا آن را دور می‌زند و داده ناسازگار می‌شود. راه‌حل: برای این مسیرها منطق را صریح فراخوانی کنید یا منطق حیاتی را در Service لایه بگذارید. همچنین observer داخل تراکنش قبل از commit اجرا می‌شود؛ با ShouldHandleEventsAfterCommit آن را به بعد از commit منتقل کنید.

Soft Delete چگونه کار می‌کند؟ مشکل آن با unique index را توضیح دهید و راه‌حل ارائه کنید.

سازوکار: تریت SoftDeletes و ستون deleted_at. متد delete() به‌جای DELETE، ستون را با زمان فعلی پر می‌کند و یک global scope شرط whereNull('deleted_at') را به همه کوئری‌ها اضافه می‌کند. API: withTrashed()، onlyTrashed()، restore()، forceDelete()، trashed().

مشکل unique: ایندکس یکتای email سطرهای حذف‌شده را هم در نظر می‌گیرد؛ کاربری که حساب حذف‌شده دارد نمی‌تواند با همان ایمیل دوباره ثبت‌نام کند. ایندکس (email, deleted_at) هم کافی نیست، چون NULLها در unique index متمایز حساب می‌شوند و دو رکورد فعال با یک ایمیل مجاز می‌شود.

-- PostgreSQL: partial index
CREATE UNIQUE INDEX users_email_active ON users (email) WHERE deleted_at IS NULL;

-- MySQL: generated column
ALTER TABLE users ADD active_email VARCHAR(255)
  AS (IF(deleted_at IS NULL, email, NULL)) STORED,
  ADD UNIQUE (active_email);
'email' => [Rule::unique('users')->withoutTrashed()],

نکات دیگر: soft delete روی فرزندان cascade نمی‌شود (FK cascade فقط با DELETE واقعی)؛ کوئری‌های DB::table scope را اعمال نمی‌کنند؛ جدول رشد می‌کند و باید Prunable شود؛ و از نظر حریم خصوصی، soft delete «حذف واقعی» داده شخصی نیست.

در یک سیستم کیف پول، دو درخواست برداشت هم‌زمان ممکن است موجودی را منفی کنند. مشکل را تحلیل و با Eloquent راه‌حل ارائه کنید.

تحلیل: یک race condition از نوع lost update / check-then-act: هر دو درخواست موجودی ۱۰۰ را می‌خوانند، هر دو شرط balance >= 80 را برقرار می‌بینند و هر دو کم می‌کنند. بررسی در PHP و نوشتن در دو مرحله جداست و اتمیک نیست.

راه‌حل ۱ — قفل بدبینانه در تراکنش:

DB::transaction(function () use ($id, $amount) {
    $wallet = Wallet::whereKey($id)->lockForUpdate()->firstOrFail();
    if ($wallet->balance < $amount) throw new InsufficientFunds;
    $wallet->decrement('balance', $amount);
    $wallet->transactions()->create(['amount' => -$amount]);
}, attempts: 3);

lockForUpdate یعنی SELECT ... FOR UPDATE؛ درخواست دوم تا commit اولی منتظر می‌ماند و سپس موجودی به‌روز را می‌بیند. بیرون از تراکنش اثری ندارد.

راه‌حل ۲ — UPDATE شرطی اتمیک:

$affected = Wallet::whereKey($id)->where('balance', '>=', $amount)
    ->decrement('balance', $amount);
if ($affected === 0) throw new InsufficientFunds;

مقایسه: قفل تضمین قوی و امکان منطق پیچیده‌تر می‌دهد ولی throughput را کم و ریسک deadlock دارد (پس attempts و تراکنش کوتاه). UPDATE شرطی سریع‌تر است ولی فقط برای منطق ساده. قفل خوش‌بینانه (ستون version) برای رقابت کم مناسب است. علاوه بر این‌ها CHECK constraint (balance >= 0) لایه دفاعی آخر است.

انواع صفحه‌بندی در لاراول (paginate، simplePaginate، cursorPaginate) را مقایسه کنید. برای یک API فید با میلیون‌ها رکورد کدام را انتخاب می‌کنید و چرا؟
  • paginate: دو کوئری، COUNT(*) و LIMIT/OFFSET. تعداد کل و شماره صفحات دارد؛ مناسب پنل ادمین با جدول متوسط.
  • simplePaginate: بدون COUNT؛ یک سطر اضافه می‌گیرد تا بفهمد صفحه بعد هست یا نه. فقط قبلی/بعدی.
  • cursorPaginate: keyset pagination؛ WHERE (id) < ? ORDER BY id DESC LIMIT n با cursor رمزشده در query string.

انتخاب برای فید: cursorPaginate، چون:

  • هزینه OFFSET خطی است (دیتابیس باید سطرهای قبلی را بخواند و دور بریزد)؛ cursor با ایندکس مستقیم seek می‌کند و سرعت در صفحه ۱ و ۱۰۰۰ یکسان است.
  • COUNT روی میلیون‌ها سطر (به‌خصوص InnoDB) گران است.
  • با درج آیتم جدید، offset باعث تکرار/جاافتادن آیتم‌ها می‌شود؛ cursor پایدار است.
return PostResource::collection(
    Post::where('published', true)->orderByDesc('id')->cursorPaginate(20)
);

محدودیت‌ها: پرش به صفحه دلخواه و نمایش تعداد کل ممکن نیست؛ مرتب‌سازی باید روی ستون(های) یکتا و ایندکس‌دار باشد (مثلاً created_at + id) و ستون‌های مرتب‌سازی nullable مشکل‌سازند.

API Resource چیست و چرا بهتر از برگرداندن مستقیم مدل یا استفاده از $hidden است؟ نقش whenLoaded را توضیح دهید.

تعریف: کلاسی (JsonResource) که یک مدل یا collection را به آرایه خروجی API تبدیل می‌کند؛ یک transformation layer بین لایه داده و قرارداد API.

چرا:

  • جداسازی قرارداد از schema: تغییر نام ستون یا refactor جدول، API را نمی‌شکند.
  • امنیت به‌صورت whitelist: با return مستقیم مدل، هر ستون جدید (مثلاً api_token) خودکار لو می‌رود مگر یادتان باشد به $hidden اضافه کنید.
  • منطق شرطی صریح: when()، mergeWhen() بر اساس دسترسی کاربر.
  • یکنواختی: wrap در data، links/meta خودکار برای paginator، نسخه‌بندی (V1/V2).
public function toArray(Request $request): array {
    return [
        'id'       => $this->id,
        'title'    => $this->title,
        'author'   => new UserResource($this->whenLoaded('author')),
        'comments' => $this->whenCounted('comments'),
    ];
}
// کنترلر
return PostResource::collection(Post::with('author')->withCount('comments')->paginate());

whenLoaded: رابطه را فقط اگر از قبل eager load شده باشد در خروجی می‌گذارد و هرگز lazy load نمی‌کند؛ پس Resource خودش منبع N+1 نمی‌شود و کنترلر تصمیم می‌گیرد چه چیزی لود شود. هزینه Resource: یک کلاس اضافه و کمی overhead که در برابر مزایا ناچیز است.

Local Scope و Global Scope را تعریف و مقایسه کنید. یک global scope برای multi-tenancy بنویسید و خطرات آن را بگویید.

Local scope: شرط قابل استفاده مجدد که صریحاً فراخوانی می‌شود (Post::published())؛ با متد scopeXxx یا در Laravel 12 با attribute #[Scope].

Global scope: شرطی که خودکار به همه کوئری‌های مدل اضافه می‌شود؛ کلاسی که Scope را با متد apply() پیاده می‌کند، یا closure در booted(). نمونه داخلی: SoftDeletes.

class TenantScope implements Scope {
    public function apply(Builder $b, Model $m): void {
        $b->where($m->qualifyColumn('tenant_id'), app('tenant')->id);
    }
}
#[ScopedBy([TenantScope::class])]
class Invoice extends Model {
    protected static function booted(): void {
        static::creating(fn ($i) => $i->tenant_id ??= app('tenant')->id);
    }
}
Invoice::withoutGlobalScope(TenantScope::class)->get();   // ادمین کل سیستم

مقایسه: local = صریح، قابل‌دیدن، اختیاری؛ global = پیش‌فرض امن (فراموش کردن شرط ممکن نیست) ولی پنهان.

خطرات global scope:

  • Query Builder خام (DB::table) و SQL خام آن را اعمال نمی‌کنند → نشت داده بین tenantها.
  • دیباگ سخت: شرط در کد کوئری دیده نمی‌شود.
  • در queue job و command، tenant فعلی باید صریحاً تنظیم شود.
  • در joinها بدون qualify کردن نام ستون، ابهام ستون پیش می‌آید.
Attribute Casting، Accessor و Mutator را توضیح دهید. چه زمانی custom cast می‌نویسید و تفاوت روش Laravel 11 با نسخه‌های قبل چیست؟

Cast: تبدیل خودکار و دوطرفه نوع بین دیتابیس و PHP. در Laravel 11+ با متد casts(): array (پیش‌تر خاصیت $casts که هنوز معتبر است). مزیت متد: امکان فراخوانی متد مثل AsEnumCollection::of(Flag::class).

protected function casts(): array {
    return [
        'status'   => OrderStatus::class,  // enum
        'options'  => AsCollection::class,
        'paid_at'  => 'immutable_datetime',
        'token'    => 'encrypted',
        'price'    => MoneyCast::class,    // custom
    ];
}
protected function fullName(): Attribute {
    return Attribute::make(get: fn ($v, $a) => "{$a['first_name']} {$a['last_name']}");
}

Accessor/Mutator: تغییر مقدار هنگام خواندن/نوشتن یا ساخت attribute مجازی. سینتکس مدرن: متد protected camelCase که Attribute::make(get:, set:) برمی‌گرداند؛ سینتکس قدیمی: getXxxAttribute/setXxxAttribute.

Custom cast وقتی: تبدیل در چند مدل تکرار می‌شود، Value Object دارید (Money، Address، Coordinates)، یا یک attribute به چند ستون نگاشت می‌شود. کلاس CastsAttributes با متدهای get و set.

نکات: accessorها در SQL قابل استفاده نیستند؛ attribute مجازی برای JSON باید در $appends بیاید؛ ستون encrypted قابل جستجو نیست؛ تغییر مستقیم کلید آرایه cast شده خطای indirect modification می‌دهد.

تفاوت firstOrCreate، updateOrCreate، createOrFirst و upsert چیست؟ کدام در شرایط هم‌زمانی بالا امن است؟
  • firstOrCreate(attrs, values): SELECT بر اساس attrs؛ اگر نبود INSERT با attrs+values. رویدادها اجرا می‌شوند.
  • updateOrCreate(attrs, values): SELECT؛ اگر بود UPDATE با values، وگرنه INSERT.
  • createOrFirst(attrs, values): ابتدا INSERT؛ اگر خطای unique constraint داد، SELECT. نیاز به unique index دارد.
  • upsert(rows, uniqueBy, update): یک کوئری انبوه (INSERT ... ON DUPLICATE KEY UPDATE یا ON CONFLICT)؛ بدون رویداد مدل؛ نیاز به unique index.

هم‌زمانی: firstOrCreate و updateOrCreate الگوی check-then-act دارند و اتمیک نیستند؛ دو درخواست هم‌زمان هر دو «پیدا نمی‌کنند» و دو INSERT می‌زنند. بدون unique index داده تکراری، و با unique index یکی از درخواست‌ها exception می‌گیرد.

// unique index روی (user_id, date) شرط لازم است
$stat = DailyStat::createOrFirst(['user_id' => $id, 'date' => today()]);

DailyStat::upsert(
    [['user_id' => $id, 'date' => today(), 'visits' => 1]],
    uniqueBy: ['user_id', 'date'],
    update: ['visits' => DB::raw('visits + 1')]
);

جمع‌بندی: امنیت واقعی همیشه از unique constraint دیتابیس می‌آید؛ upsert و createOrFirst بر آن تکیه دارند. برای import انبوه upsert، برای یک رکورد با نیاز به رویداد createOrFirst یا updateOrCreate داخل تراکنش با مدیریت خطای تکراری.

تفاوت whereHas، with با closure و withWhereHas را با مثال توضیح دهید.

هدف: «کاربرانی که پست ویژه دارند، همراه با فقط همان پست‌های ویژه».

// ۱) فقط والدها فیلتر می‌شوند؛ $u->posts همه پست‌ها (و lazy!)
User::whereHas('posts', fn ($q) => $q->where('featured', true))->get();

// ۲) همه کاربران می‌آیند؛ فقط پست‌های لودشده فیلتر می‌شوند
User::with(['posts' => fn ($q) => $q->where('featured', true)])->get();

// ۳) هر دو: کاربرانِ دارای پست ویژه + eager load همان پست‌ها
User::withWhereHas('posts', fn ($q) => $q->where('featured', true))->get();
  • whereHas: زیرکوئری EXISTS روی جدول والد؛ چیزی لود نمی‌کند.
  • with + closure: کوئری دوم WHERE user_id IN (...) AND featured = 1؛ کاربران بدون پست ویژه با collection خالی برمی‌گردند.
  • withWhereHas: ترکیب دو مورد بالا با یک شرط مشترک؛ جلوگیری از تکرار closure.

مرتبط‌ها: has('posts', '>', 5) برای شرط تعداد، doesntHave/whereDoesntHave برای نبود رابطه، whereRelation به‌عنوان میان‌بر، و withCount/withExists برای افزودن ستون محاسباتی بدون لود رکوردها.

برای خروجی گرفتن CSV از ۵ میلیون رکورد سفارش، از کدام روش Eloquent استفاده می‌کنید؟ chunk، chunkById، lazy و cursor را مقایسه کنید.

مشکل: Order::all() یا get() همه ۵ میلیون مدل را در حافظه می‌سازد و با memory exhausted از کار می‌افتد.

  • chunk(n): LIMIT/OFFSET؛ حافظه محدود ولی OFFSET در صفحات عمیق کند و به تغییر داده حساس است.
  • chunkById(n): WHERE id > last؛ سرعت ثابت، امن در برابر تغییر داده.
  • lazy()/lazyById(): همان chunk ولی خروجی LazyCollection؛ API روان (map/filter/each) و پشتیبانی از eager loading در هر chunk.
  • cursor(): یک کوئری و generator؛ فقط یک مدل در لحظه hydrate می‌شود، اما eager loading ندارد و در MySQL با buffered query، نتیجه خام در حافظه PDO انباشته می‌شود.
$out = fopen(storage_path('app/orders.csv'), 'w');
Order::query()
    ->select(['id', 'user_id', 'total', 'created_at'])
    ->with('user:id,email')
    ->lazyById(2000)
    ->each(fn ($o) => fputcsv($out, [$o->id, $o->user->email, $o->total, $o->created_at]));
fclose($out);

انتخاب: lazyById با ستون‌های محدود و eager load. این کار را در یک queued job انجام دهید (نه در درخواست HTTP) و پس از اتمام، لینک دانلود اطلاع داده شود. اگر به منطق مدل نیازی نیست، toBase() یا Query Builder باز هم سبک‌تر است.

تفاوت isDirty، wasChanged و getOriginal چیست؟ در یک observer چگونه فقط هنگام تغییر وضعیت سفارش ایمیل می‌فرستید؟
  • isDirty('attr'): قبل از ذخیره؛ آیا مقدار فعلی با مقدار اصلی (خوانده‌شده از DB) فرق دارد؟ getDirty() لیست کامل.
  • getOriginal('attr'): مقدار اصلی قبل از تغییرات؛ در رویداد updating یا updated مقدار قبلی را می‌دهد.
  • wasChanged('attr'): بعد از ذخیره؛ آیا این ستون در آخرین save تغییر کرد؟ getChanges() لیست کامل.
class OrderObserver
{
    public function updating(Order $order): void
    {
        if ($order->isDirty('status') && $order->getOriginal('status') === OrderStatus::Shipped) {
            // جلوگیری از بازگشت وضعیت
        }
    }

    public function updated(Order $order): void
    {
        if ($order->wasChanged('status')) {
            // notification صف‌شده با afterCommit(): فقط بعد از commit موفق ارسال می‌شود
            $order->user->notify(
                (new OrderStatusChanged($order, from: $order->getOriginal('status')))->afterCommit()
            );
        }
    }
}

نکات: در updated، isDirty هنوز true است چون syncOriginal بعد از رویداد اجرا می‌شود، ولی wasChanged معنای روشن‌تری دارد. اگر وضعیت با Order::where(...)->update() تغییر کند observer اجرا نمی‌شود. ارسال ایمیل باید بعد از commit تراکنش باشد؛ اینجا با afterCommit() روی notification صف‌شده انجام شده است. اگر به‌جای آن کل observer را ShouldHandleEventsAfterCommit کنید، دقت کنید که تا زمان اجرای listener، syncOriginal انجام شده و getOriginal دیگر مقدار قبلی را نمی‌دهد (اما wasChanged هنوز درست است)؛ پس مقدار قبلی را باید در updating نگه دارید.

اگر یک صفحه لیست محصولات در production کند شده باشد، چه مراحلی برای بهینه‌سازی لایه Eloquent طی می‌کنید؟

۱. اندازه‌گیری قبل از تغییر: Telescope یا Debugbar یا لاگ DB::listen برای تعداد کوئری، کوئری‌های تکراری و زمان هر کدام؛ APM در production.

۲. حذف N+1: رابطه‌های استفاده‌شده در view/Resource را با with لود کنید؛ preventLazyLoading در توسعه.

۳. کاهش داده: select ستون‌های لازم، with('category:id,name')، صفحه‌بندی (و برای جدول بزرگ simplePaginate/cursorPaginate).

۴. aggregate در دیتابیس: withCount('reviews')، withAvg('reviews', 'rating') به‌جای محاسبه در حلقه.

۵. ایندکس: با EXPLAIN بررسی کنید؛ ایندکس ترکیبی متناسب با where + order، مثلاً (category_id, is_active, created_at).

$products = Product::query()
    ->select(['id', 'name', 'price', 'category_id'])
    ->with('category:id,name')
    ->withAvg('reviews', 'rating')
    ->where('is_active', true)
    ->latest('id')
    ->simplePaginate(24);

۶. کش: Cache::remember برای داده پرتکرار (مثلاً دسته‌بندی‌ها) با invalidation در observer؛ دقت به کلید کش برای هر صفحه/فیلتر.

۷. denormalization: اگر هنوز کند است، ستون‌های شمارنده/میانگین ذخیره‌شده یا جدول خلاصه که با job به‌روز می‌شود. در نهایت حذف accessorهای سنگین از $appends و $with سراسری.

خلاصه برای مرور سریع

مفاهیم

  • Eloquent = Active Record (مدل = جدول، نمونه = سطر)؛ Doctrine = Data Mapper.
  • قرارداد: جدول جمع snake_case، PK id، created_at/updated_at، FK = model_id.
  • UUID/ULID: HasUuids (L12: UUIDv7)، HasUlids؛ migration: uuid()/ulid().
  • Laravel 11+: protected function casts(): array.

  • find/first → null؛ findOrFail/firstOrFail → 404؛ sole → دقیقاً یکی.
  • value('col')، pluck('name','id')، exists()، firstWhere.
  • raw فقط با binding: whereRaw('x = ?', [$v])؛ نام ستون را whitelist کنید.

  • create (fillable)، update، save، firstOrCreate، firstOrNew، updateOrCreate، createOrFirst.

  • Attribute::make(get:, set:)؛ قدیمی: getXAttribute.
  • $hidden، $visible، $appends، makeVisible.
