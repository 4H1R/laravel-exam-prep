Scripting

اسکریپت‌نویسی برای خودکارسازی کارهای سرور و توسعه: مبانی Bash (متغیر، quoting، شرط، حلقه، تابع، exit code)، مدیریت خطا با set -euo pipefail و trap، redirection و pipe، ابزارهای پردازش متن، cron و scheduler لاراول، نوشتن اسکریپت‌های مقاوم (بکاپ، deploy، health check)، دستورات Artisan و مقایسه با Python و Makefile.

اسکریپت چیست و کی خودکارسازی کنیم

Script برنامه‌ای است که توسط یک interpreter (bash، php، python) اجرا می‌شود و معمولاً برای به هم چسباندن ابزارها و خودکارسازی کارهای تکراری نوشته می‌شود: بکاپ، deploy، پاک‌سازی لاگ، import داده، بررسی سلامت سرویس، آماده‌سازی محیط توسعه. تفاوت اصلی با برنامه‌ی کامپایلی: نیاز به build ندارد، سریع نوشته و تغییر داده می‌شود و معمولاً به محیط اجرا (سیستم‌عامل و دستورات موجود) وابسته است.

چه زمانی خودکارسازی کنیم؟

  • کار تکراری است (روزانه، در هر deploy، روی هر سرور جدید).
  • کار حساس به خطا است و یک قدم فراموش‌شده هزینه دارد (deploy، migration، بکاپ).
  • کار باید در زمان مشخص و بدون حضور انسان اجرا شود (cron).
  • نیاز به مستندسازی اجرایی دارید: اسکریپت خودش دقیق‌ترین مستند «چطور انجامش می‌دهیم» است.
  • قاعده‌ی سرانگشتی: اگر کاری را سومین بار دستی انجام می‌دهید، وقت اسکریپت کردنش است؛ اما هزینه‌ی نوشتن و نگهداری را با زمان صرفه‌جویی‌شده مقایسه کنید.

Shebang و مجوز اجرا

خط اول اسکریپت با #! (shebang) مشخص می‌کند کرنل فایل را با کدام interpreter اجرا کند.

#!/usr/bin/env bash
# env مسیر bash را از PATH پیدا می‌کند؛ قابل‌حمل‌تر از /bin/bash ثابت
set -euo pipefail

echo "Hello from $(hostname)"
chmod +x hello.sh      # افزودن بیت اجرا
./hello.sh             # اجرا با interpreter مشخص‌شده در shebang
bash hello.sh          # اجرا مستقیم با bash (shebang نادیده گرفته می‌شود)
sh hello.sh            # خطرناک: با sh (مثلاً dash در اوبونتو) اجرا می‌شود و قابلیت‌های bash کار نمی‌کنند
  • ./ لازم است چون پوشه‌ی جاری به‌طور پیش‌فرض در PATH نیست (به دلایل امنیتی).
  • در اوبونتو /bin/sh به dash اشاره می‌کند که POSIX خالص است؛ [[ ]]، آرایه‌ها و pipefail (در نسخه‌های قدیمی dash) را ندارد. اگر از امکانات bash استفاده می‌کنید، shebang باید bash باشد.
  • shebangهای دیگر: #!/usr/bin/env php، #!/usr/bin/env python3.

اسکریپتی که روی ویندوز ذخیره شده و خطای /usr/bin/env: 'bash\r': No such file or directory یا bad interpreter می‌دهد، پایان خط CRLF دارد. با dos2unix script.sh یا sed -i 's/\r$//' script.sh اصلاح کنید و در git با .gitattributes (*.sh text eol=lf) جلوی تکرار را بگیرید.

شرط‌ها، case و حلقه‌ها

if و دستور test

در Bash، if روی کد خروج یک دستور تصمیم می‌گیرد: صفر یعنی موفق (true). [ در واقع یک دستور (همان test) است و ] آخرین آرگومان آن؛ به همین دلیل فاصله‌ها اجباری‌اند.

if [[ -f "$config" && -r "$config" ]]; then
    echo "config is readable"
elif [[ -d "$config" ]]; then
    echo "it is a directory"
else
    echo "missing" >&2
fi

# هر دستوری می‌تواند شرط باشد
if grep -q "APP_DEBUG=true" .env; then
    echo "debug is on!" >&2
fi

if ! command -v jq >/dev/null 2>&1; then
    echo "jq is required" >&2; exit 1
fi

[ ] (POSIX test)

  • یک دستور معمولی؛ در همه‌ی شل‌های POSIX (sh، dash) موجود است.
  • متغیرها word splitting و globbing می‌شوند؛ quote اجباری: [ "$a" = "b" ].
  • برای AND/OR: [ … ] && [ … ] (گزینه‌های -a/-o منسوخ‌اند).
  • < و > به عنوان redirection تفسیر می‌شوند.

[[ ]] (کلمه‌ی کلیدی bash)

  • بخشی از syntax شل؛ word splitting و globbing روی متغیرها ندارد (quote همچنان عادت خوبی است).
  • &&، || و ! داخل آن مجاز است.
  • تطبیق الگو: [[ $f == *.log ]].
  • regex: [[ $v =~ ^[0-9]+$ ]] و گروه‌ها در BASH_REMATCH.
  • قابل‌حمل به sh نیست.

توابع، Exit Code و مدیریت خطا

توابع

log() {
    local level="$1"; shift
    printf '%s [%s] %s\n' "$(date '+%F %T')" "$level" "$*" >&2
}

is_port_open() {
    local host="$1" port="$2"
    timeout 3 bash -c "</dev/tcp/${host}/${port}" 2>/dev/null
}

get_release_dir() {
    echo "/var/www/app/releases/$(date +%Y%m%d%H%M%S)"   # «برگرداندن» مقدار با stdout
}

log INFO "starting"
release=$(get_release_dir)
if is_port_open 127.0.0.1 3306; then log INFO "mysql is up"; fi
  • آرگومان‌های تابع با $1، $2 و "$@" خوانده می‌شوند، نه با پرانتز.
  • local متغیر را محلی می‌کند؛ بدون آن همه‌ی متغیرها سراسری هستند و تابع‌ها روی هم اثر می‌گذارند.
  • return N فقط یک کد وضعیت (۰ تا ۲۵۵) برمی‌گرداند؛ داده را با echo و $( ) برگردانید.
  • لاگ و پیام‌ها را به stderr (>&2) بفرستید تا با خروجی داده‌ای که با $( ) گرفته می‌شود قاطی نشوند.

Exit code و عملگرهای && و ||

هر دستور یک exit status برمی‌گرداند: 0 یعنی موفقیت، هر مقدار دیگر (۱ تا ۲۵۵) یعنی خطا. قراردادهای رایج: 1 خطای عمومی، 2 استفاده‌ی نادرست، 126 قابل اجرا نیست، 127 دستور پیدا نشد، 128+N کشته شدن با سیگنال N (مثلاً 130 برای Ctrl+C و 137 برای SIGKILL).

mkdir -p /tmp/work && cd /tmp/work     # دومی فقط اگر اولی موفق بود
cd "$APP_DIR" || exit 1                  # اگر شکست خورد، خارج شو
grep -q ERROR app.log; echo "status: $?" # 0 = پیدا شد، 1 = پیدا نشد، 2 = خطا

# الگوی کوتاه مدیریت خطا
command -v composer >/dev/null || { echo "composer missing" >&2; exit 127; }

a && b || c معادل if/else نیست: اگر a موفق و b ناموفق باشد، c هم اجرا می‌شود. برای منطق شرطی واقعی از if استفاده کنید.

Strict mode: set -euo pipefail

set -e (errexit)
اگر دستوری با کد غیرصفر تمام شد، اسکریپت فوراً خارج شود. استثناها: دستورات داخل شرط if/while، دستورات قبل از آخرین عضو زنجیره‌ی &&/||، و دستوری که با ! منفی شده.
set -u (nounset)
استفاده از متغیر تعریف‌نشده خطاست؛ جلوی اشتباه تایپی و فاجعه‌هایی مثل rm -rf "$DIR/" با DIR خالی را می‌گیرد. برای متغیر اختیاری: ${VAR:-}.
set -o pipefail
کد خروج pipeline برابر کد آخرین دستوری است که شکست خورده (نه فقط آخرین دستور). بدون آن mysqldump … | gzip > f.gz حتی اگر mysqldump شکست بخورد موفق گزارش می‌شود.
set -x
چاپ هر دستور پیش از اجرا؛ برای دیباگ (bash -x script.sh).

local out=$(cmd) کد خروج cmd را با کد خروج local (که همیشه صفر است) می‌پوشاند و set -e عمل نمی‌کند (ShellCheck: SC2155). جدا بنویسید: local out; out=$(cmd).

trap برای تمیزکاری

#!/usr/bin/env bash
set -euo pipefail

tmpdir=$(mktemp -d)
cleanup() {
    rm -rf "$tmpdir"
}
trap cleanup EXIT                                        # در هر نوع خروج (موفق، خطا، exit)
trap 'echo "error on line $LINENO" >&2' ERR             # هنگام خطای یک دستور
trap 'echo "interrupted" >&2; exit 130' INT TERM        # Ctrl+C یا kill

cd "$tmpdir"
curl -fsSLo data.json https://example.com/export
# ... پردازش؛ پوشه‌ی موقت در هر حال پاک می‌شود

در پاسخ به «set -euo pipefail چه می‌کند؟» هر سه گزینه را جدا تعریف کنید، یک مثال برای هر کدام بزنید (به‌خصوص pipefail با mysqldump | gzip) و حتماً به محدودیت‌های set -e اشاره کنید (داخل if، زنجیره‌ی &&، local var=$(...)، ((i++)) با صفر). این نشان می‌دهد ابزار را عمیق می‌شناسید.

ورودی/خروجی، Redirection، Pipe و Here-doc

هر فرایند سه جریان استاندارد دارد: stdin (FD 0)، stdout (FD 1) و stderr (FD 2). جدا بودن stderr باعث می‌شود پیام‌های خطا وارد داده‌ای که به دستور بعدی pipe می‌شود نشوند.

شکلمعنا
cmd > filestdout به فایل (بازنویسی)
cmd >> filestdout به انتهای فایل (append)
cmd 2> err.logstderr به فایل
cmd > out.log 2>&1هر دو به یک فایل (ترتیب مهم است)
cmd &> out.logمعادل کوتاه bash برای مورد قبل
cmd > /dev/null 2>&1دور ریختن همه‌ی خروجی
cmd < filestdin از فایل
cmd1 | cmd2stdout اولی به stdin دومی (هر دو هم‌زمان اجرا می‌شوند)
cmd1 |& cmd2stdout و stderr با هم به pipe (bash)
diff <(cmd1) <(cmd2)process substitution: خروجی دستور به شکل یک فایل
echo "x" >&2نوشتن روی stderr

چرا ترتیب در 2>&1 مهم است؟ redirectionها از چپ به راست پردازش می‌شوند و 2>&1 یعنی «FD 2 را به همان جایی ببر که FD 1 الان اشاره می‌کند». در cmd > file 2>&1 اول stdout به فایل می‌رود و بعد stderr به همان فایل؛ در cmd 2>&1 > file اول stderr به ترمینال (جای فعلی stdout) و بعد فقط stdout به فایل می‌رود، پس خطاها در فایل نیستند.

تله‌های cron

  • محیط حداقلی: cron متغیرهای .bashrc را ندارد و PATH آن محدود است (مثلاً /usr/bin:/bin). از مسیر کامل استفاده کنید یا PATH را بالای crontab تعریف کنید.
  • کاراکتر % در crontab به معنای newline است و باید escape شود: date +\%F.
  • پوشه‌ی جاری home کاربر است؛ cd صریح انجام دهید.
  • خروجی: اگر خروجی redirect نشود، cron سعی می‌کند آن را ایمیل کند؛ لاگ کنید: >> /var/log/job.log 2>&1.

Scheduler لاراول

به جای ده‌ها خط cron، Laravel زمان‌بندی را در کد (نسخه‌دار و قابل review) تعریف می‌کند و فقط یک cron لازم است که هر دقیقه schedule:run را اجرا کند. این دستور بررسی می‌کند کدام تسک‌ها در این دقیقه موعدشان است و آن‌ها را اجرا می‌کند.

* * * * * cd /var/www/app/current && php artisan schedule:run >> /dev/null 2>&1
<?php
// routes/console.php  (Laravel 11+)
use Illuminate\Support\Facades\Schedule;

Schedule::command('reports:daily --email')
    ->dailyAt('02:00')
    ->timezone('Asia/Tehran')
    ->withoutOverlapping()        // اگر اجرای قبلی هنوز در جریان است، اجرا نکن (با cache lock)
    ->onOneServer()               // روی چند سرور فقط یک‌بار (نیاز به cache مشترک مثل Redis)
    ->runInBackground()           // تسک‌های دیگر همان دقیقه را معطل نکند
    ->emailOutputOnFailure('ops@example.com');

Schedule::command('queue:prune-failed --hours=168')->daily();
Schedule::command('sanctum:prune-expired --hours=24')->daily();
Schedule::job(new SyncExchangeRates)->everyFifteenMinutes();
Schedule::exec('/usr/local/bin/db-backup.sh')->dailyAt('03:00');
  • php artisan schedule:list: نمایش تسک‌ها و زمان اجرای بعدی.
  • php artisan schedule:test: اجرای دستی یک تسک برای تست.
  • php artisan schedule:work: در محیط local بدون cron، در foreground هر دقیقه scheduler را اجرا می‌کند.
  • Laravel تسک‌های کمتر از یک دقیقه را هم پشتیبانی می‌کند (مثلاً everyTenSeconds())؛ در این حالت schedule:run تا پایان دقیقه فعال می‌ماند.

چرا scheduler لاراول بهتر از چند خط cron است؟ زمان‌بندی در کد و git (review، تاریخچه، یکسان در همه‌ی محیط‌ها)، امکانات داخلی مثل withoutOverlapping، onOneServer، hookهای onFailure/onSuccess، منطقه‌ی زمانی و شرط‌ها (->when()، ->environments('production'))، و فقط یک ورودی cron برای مدیریت روی سرور.

usage() {
    cat <<EOF
Usage: $(basename "$0") [-e env] [-n] [-h] <target>

  -h       show help

while getopts ":e:nh" opt; do       # : اول = مدیریت خطا توسط خودمان؛ e: = نیاز به مقدار
    case "$opt" in
        e)  ENV="$OPTARG" ;;
        n)  DRY_RUN=1 ;;
        h)  usage; exit 0 ;;
        :)  echo "option -$OPTARG requires a value" >&2; usage; exit 2 ;;
        \?) echo "unknown option -$OPTARG" >&2; usage; exit 2 ;;
    esac
done
shift $(( OPTIND - 1 ))              # حذف گزینه‌ها؛ حالا $1 اولین آرگومان موقعیتی است
TARGET="${1:?target is required}"

۱. بکاپ دیتابیس با چرخش (Rotation)

#!/usr/bin/env bash
# /usr/local/bin/db-backup.sh — بکاپ روزانه‌ی MySQL با نگهداری N روز
set -euo pipefail

DB_NAME="${DB_NAME:-app}"
BACKUP_DIR="${BACKUP_DIR:-/var/backups/mysql}"
RETENTION_DAYS="${RETENTION_DAYS:-7}"
MYSQL_CNF="${MYSQL_CNF:-/root/.my.cnf}"     # [client] user=... password=... (chmod 600)
TIMESTAMP="$(date +%Y%m%d-%H%M%S)"
FILE="${BACKUP_DIR}/${DB_NAME}-${TIMESTAMP}.sql.gz"

log() { printf '%s [%s] %s\n' "$(date '+%F %T')" "$1" "$2"; }

exec 9>/var/lock/db-backup.lock
flock -n 9 || { log ERROR "backup already running"; exit 1; }

cleanup() { [[ -f "${FILE}.part" ]] && rm -f "${FILE}.part"; }
trap cleanup EXIT

mkdir -p "$BACKUP_DIR"
log INFO "starting backup of ${DB_NAME}"

# --single-transaction: snapshot سازگار InnoDB بدون قفل جدول؛ pipefail شکست mysqldump را می‌گیرد
mysqldump --defaults-extra-file="$MYSQL_CNF" \
    --single-transaction --quick --routines --triggers \
    "$DB_NAME" | gzip -c > "${FILE}.part"

gzip -t "${FILE}.part"                 # بررسی سلامت آرشیو
mv "${FILE}.part" "$FILE"              # فقط فایل کامل نام نهایی می‌گیرد
log INFO "backup written: $FILE ($(du -h "$FILE" | cut -f1))"

# چرخش: حذف بکاپ‌های قدیمی‌تر از RETENTION_DAYS
find "$BACKUP_DIR" -name "${DB_NAME}-*.sql.gz" -type f -mtime +"$RETENTION_DAYS" -print -delete

# کپی خارج از سرور (قاعده‌ی 3-2-1)؛ مثلاً با rclone یا aws cli
# rclone copy "$FILE" remote:backups/mysql/
log INFO "done"
  • رمز دیتابیس در فایل .my.cnf با دسترسی 600 است، نه در آرگومان -p که در ps دیده می‌شود.
  • نوشتن در .part و سپس mv اتمیک تضمین می‌کند فایل ناقص هرگز به عنوان بکاپ سالم شناخته نشود.
  • بکاپی که restore آن تست نشده، قابل اتکا نیست؛ تست restore دوره‌ای جزو فرایند است.

#!/usr/bin/env bash
# deploy.sh — ساختار: releases/<ts>، shared/{.env,storage}، current -> releases/<ts>
set -euo pipefail

APP_DIR=/var/www/app
REPO=git@github.com:acme/app.git
BRANCH="${1:-main}"
KEEP=5
RELEASE="$APP_DIR/releases/$(date +%Y%m%d%H%M%S)"
PHP_FPM=php8.3-fpm

log() { echo "==> $*"; }
trap 'echo "deploy FAILED at line $LINENO; current release untouched" >&2' ERR

exec 9>"$APP_DIR/.deploy.lock"
flock -n 9 || { echo "another deploy is running" >&2; exit 1; }

log "cloning $BRANCH"
git clone --depth 1 --branch "$BRANCH" "$REPO" "$RELEASE"

log "linking shared files"
rm -rf "$RELEASE/storage"
ln -s "$APP_DIR/shared/storage" "$RELEASE/storage"
ln -s "$APP_DIR/shared/.env" "$RELEASE/.env"

cd "$RELEASE"
log "installing dependencies"
composer install --no-dev --prefer-dist --no-interaction --optimize-autoloader
npm ci --no-audit --no-fund
npm run build

log "migrating"
php artisan migrate --force

log "caching framework files"
php artisan optimize

log "switching symlink (atomic)"
ln -sfn "$RELEASE" "$APP_DIR/current.tmp"
mv -T "$APP_DIR/current.tmp" "$APP_DIR/current"

log "reloading services"
sudo systemctl reload "$PHP_FPM"        # پاک شدن OPcache
php artisan queue:restart

log "smoke test"
curl -fsS --max-time 10 -o /dev/null https://example.com/up

log "cleaning old releases"
ls -1dt "$APP_DIR"/releases/*/ | tail -n +$(( KEEP + 1 )) | xargs -r rm -rf

log "deployed $RELEASE"

  • ln -sfn به یک نام موقت و سپس mv -T جایگزینی را اتمیک می‌کند (rename در یک فایل‌سیستم اتمیک است).
  • Nginx باید با $realpath_root پیکربندی شده باشد.
  • Migrationها باید با نسخه‌ی قبلی کد سازگار باشند (expand/contract)، چون بین migrate و سوییچ، کد قدیمی هنوز سرویس می‌دهد.
  • Rollback: اشاره دادن current به release قبلی و reload FPM.
  • در اینجا parse کردن ls فقط برای نام‌های کنترل‌شده‌ی timestamp (بدون فاصله) قابل قبول است.

۳. Health check

#!/usr/bin/env bash
# healthcheck.sh — بررسی HTTP، سرویس‌ها، دیسک و صف؛ کد خروج غیرصفر در صورت مشکل
set -uo pipefail          # بدون -e: می‌خواهیم همه‌ی بررسی‌ها اجرا شوند

URL="${URL:-https://example.com/up}"
DISK_LIMIT="${DISK_LIMIT:-85}"
SERVICES=(nginx php8.3-fpm mysql redis-server supervisor)
failures=0

fail() { echo "CRITICAL: $*" >&2; failures=$(( failures + 1 )); }
ok()   { echo "OK: $*"; }

# 1) HTTP
code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 "$URL" || echo "000")
[[ "$code" == "200" ]] && ok "http $code" || fail "http status $code for $URL"

# 2) سرویس‌ها
for svc in "${SERVICES[@]}"; do
    if systemctl is-active --quiet "$svc"; then ok "$svc active"; else fail "$svc is not active"; fi
done

# 3) دیسک
usage=$(df -P / | awk 'NR==2 {gsub("%", "", $5); print $5}')
if (( usage >= DISK_LIMIT )); then fail "disk usage ${usage}%"; else ok "disk ${usage}%"; fi

# 4) طول صف (Redis، صف default در لاراول)
pending=$(redis-cli LLEN queues:default 2>/dev/null || echo -1)
if (( pending < 0 )); then fail "redis unreachable"
elif (( pending > 1000 )); then fail "queue backlog: $pending"
else ok "queue $pending"; fi

if (( failures > 0 )); then
    # ارسال هشدار، مثلاً به webhook
    # curl -fsS -X POST -H 'Content-Type: application/json' \
    #   -d "{\"text\":\"$(hostname): $failures health checks failed\"}" "$ALERT_WEBHOOK"
    exit 1
fi

در این اسکریپت set -e عمداً استفاده نشده، چون هدف اجرای همه‌ی بررسی‌ها و گزارش مجموع خطاهاست. این یک تصمیم آگاهانه است؛ strict mode قانون کورکورانه نیست. نام کلید صف Redis به تنظیمات (مثلاً prefix دیتابیس Redis) بستگی دارد.

دستور سفارشی Artisan

در پروژه‌ی Laravel تقریباً همیشه Artisan command بهتر از اسکریپت PHP خالص است: به container، Eloquent، config، لاگ و صف دسترسی دارد، parse آرگومان‌ها و خروجی رنگی و progress bar آماده است و با scheduler یکپارچه می‌شود.

php artisan make:command PruneInactiveUsers
<?php

namespace App\Console\Commands;

use App\Models\User;
use Illuminate\Console\Command;

class PruneInactiveUsers extends Command
{
    // {days=365}: آرگومان با پیش‌فرض؛ {--dry-run}: سوییچ؛ {--chunk=500}: گزینه با مقدار
    protected $signature = 'users:prune-inactive
                            {days=365 : Inactivity threshold in days}
                            {--dry-run : Only report, do not delete}
                            {--chunk=500 : Batch size}';

    protected $description = 'Soft-delete users who have not logged in for a given number of days';

    public function handle(): int
    {
        $days = (int) $this->argument('days');
        if ($days < 30) {
            $this->error('Threshold must be at least 30 days.');
            return self::INVALID;
        }

        $query = User::where('last_login_at', '<', now()->subDays($days));
        $total = $query->count();

        if ($total === 0) {
            $this->info('Nothing to prune.');
            return self::SUCCESS;
        }

        if ($this->option('dry-run')) {
            $this->warn("[dry-run] {$total} users would be pruned.");
            return self::SUCCESS;
        }

        if ($this->input->isInteractive() && ! $this->confirm("Prune {$total} users?")) {
            return self::FAILURE;
        }

        $bar = $this->output->createProgressBar($total);
        $query->chunkById((int) $this->option('chunk'), function ($users) use ($bar) {
            foreach ($users as $user) {
                $user->delete();
                $bar->advance();
            }
        });
        $bar->finish();
        $this->newLine();

        $this->table(['Pruned', 'Threshold (days)'], [[$total, $days]]);
        return self::SUCCESS;
    }
}

مقایسه با Python و آشنایی با Makefile

Bash یا Python؟

Bash مناسب است وقتی…

  • کار اصلی اجرای دستورات دیگر و چسباندن آن‌ها با pipe است (glue code).
  • اسکریپت کوتاه است (چند ده خط).
  • روی هر سرور لینوکسی بدون نصب چیزی باید اجرا شود.
  • کار با فایل، فرایند، سرویس و پکیج‌های سیستم.

Python بهتر است وقتی…

  • ساختار داده‌ی پیچیده (دیکشنری تو در تو، کلاس) لازم است.
  • کار با JSON، API و HTTP، CSV یا Excel، دیتابیس.
  • مدیریت خطای دقیق (exception)، تست واحد و نگهداری بلندمدت مهم است.
  • اسکریپت از حدود ۱۰۰ خط بیشتر می‌شود یا منطق شرطی زیادی دارد.
  • قابلیت اجرا روی ویندوز و لینوکس لازم است.
#!/usr/bin/env python3
"""Check a list of URLs and report the ones that fail."""
import argparse
import subprocess
import sys
import urllib.request

def check(url: str, timeout: int) -> bool:
    try:
        with urllib.request.urlopen(url, timeout=timeout) as resp:
            return resp.status == 200
    except Exception as exc:  # noqa: BLE001
        print(f"{url}: {exc}", file=sys.stderr)
        return False

def main() -> int:
    parser = argparse.ArgumentParser()
    parser.add_argument("urls", nargs="+")
    parser.add_argument("--timeout", type=int, default=5)
    args = parser.parse_args()

    failed = [u for u in args.urls if not check(u, args.timeout)]
    # اجرای دستور سیستمی به صورت امن: لیست آرگومان، بدون shell
    subprocess.run(["logger", "-t", "urlcheck", f"{len(failed)} failed"], check=False)
    return 1 if failed else 0

if __name__ == "__main__":
    sys.exit(main())

در یک تیم PHP، گزینه‌ی سوم معمولاً Artisan command یا اسکریپت PHP CLI است: همان زبان تیم، دسترسی به کد و مدل‌های پروژه، و بدون نیاز به مهارت جدید.

make ابزار build است که بر اساس وابستگی بین «هدف‌ها» (target) کار می‌کند؛ در پروژه‌های وب بیشتر به عنوان task runner برای یکسان کردن دستورات تیم استفاده می‌شود (make test، make up).

سوالات تشریحی

Shebang چیست و چرا معمولاً #!/usr/bin/env bash را به #!/bin/bash ترجیح می‌دهند؟ تفاوت اجرای ./script.sh، bash script.sh و sh script.sh را توضیح دهید.

تعریف: shebang خط اول فایل است که با #! شروع می‌شود و به کرنل می‌گوید هنگام اجرای مستقیم فایل، آن را به کدام interpreter بدهد. کرنل در execve این خط را می‌خواند و مثلاً /usr/bin/env bash ./script.sh را اجرا می‌کند.

env در برابر مسیر ثابت: /usr/bin/env bash اولین bash موجود در PATH را پیدا می‌کند؛ روی سیستم‌هایی که bash در مسیر دیگری است (مثلاً macOS با bash جدیدتر از Homebrew، یا BSD در /usr/local/bin) هم کار می‌کند. عیب: وابستگی به PATH؛ در اسکریپت‌های حساس امنیتی که با دسترسی بالا اجرا می‌شوند، مسیر مطلق ممکن است ترجیح داده شود.

شیوه‌های اجرا:

  • ./script.sh: نیاز به بیت اجرا (chmod +x)؛ interpreter از shebang تعیین می‌شود. ./ لازم است چون پوشه‌ی جاری در PATH نیست.
  • bash script.sh: بیت اجرا لازم نیست؛ shebang نادیده گرفته می‌شود و حتماً bash اجرا می‌کند.
  • sh script.sh: با /bin/sh اجرا می‌شود که در اوبونتو dash است؛ امکانات bash مثل [[ ]]، آرایه‌ها، {1..5} و $'...' کار نمی‌کنند و خطاهای گیج‌کننده می‌دهد.
  • source script.sh (یا . script.sh): در همان شل جاری اجرا می‌شود؛ متغیرها و cd روی شل فعلی اثر می‌گذارند (برای بارگذاری env).

نکته: اگر اسکریپت روی ویندوز ویرایش شده باشد، CRLF در shebang باعث خطای bad interpreter می‌شود.

قواعد quoting در Bash را توضیح دهید. چرا باید متغیرها را در double quote قرار داد؟ تفاوت "$@" و "$*" چیست؟

سه حالت:

  • بدون quote: پس از expansion، شل نتیجه را بر اساس IFS (فاصله، tab، newline) به چند کلمه می‌شکند (word splitting) و الگوهای *، ? و [ ] را با فایل‌ها جایگزین می‌کند (globbing).
  • Double quote: متغیر، $( ) و $(( )) expand می‌شوند اما نتیجه یک کلمه‌ی واحد می‌ماند و glob نمی‌شود.
  • Single quote: هیچ چیز expand نمی‌شود؛ متن لفظی.

چرا double quote:

file="monthly report.pdf"
rm $file        # تلاش برای حذف "monthly" و "report.pdf"
rm "$file"      # درست

pattern="*"
echo $pattern   # لیست همه‌ی فایل‌های پوشه!
echo "$pattern" # *

بدون quote، داده‌ی کاربر یا نام فایل می‌تواند منطق اسکریپت را تغییر دهد؛ متغیر خالی هم ممکن است کلاً حذف شود و آرگومان‌ها جابه‌جا شوند (مثلاً [ $a = x ] با a خالی خطای syntax می‌دهد). ShellCheck این را SC2086 می‌نامد.

"$@" در برابر "$*":

  • "$@" هر آرگومان را یک کلمه‌ی جدا و دست‌نخورده نگه می‌دارد: "$1" "$2" …. برای پاس دادن آرگومان‌ها به دستور دیگر (wrapper) همیشه این درست است.
  • "$*" همه را با اولین کاراکتر IFS به هم می‌چسباند و یک رشته می‌سازد: "$1 $2 …". برای ساخت پیام لاگ مناسب است.
  • بدون quote هر دو یکسان و هر دو در معرض word splitting هستند.
wrapper() { php artisan "$@"; }
wrapper migrate --path="database/migrations/2026 batch"   # آرگومان دارای فاصله سالم می‌رسد
عبارت set -euo pipefail را تشریح کنید. هر گزینه چه می‌کند و چه محدودیت‌ها یا تله‌هایی دارد؟

این خط «strict mode» غیررسمی Bash است و رفتار پیش‌فرض «ادامه بده حتی اگر خطا رخ داد» را به «fail fast» تبدیل می‌کند.

  • -e (errexit): اگر دستوری کد خروج غیرصفر داشت، اسکریپت خارج می‌شود. بدون آن، شکست composer install نادیده گرفته می‌شود و deploy با کد ناقص ادامه می‌یابد.
  • -u (nounset): ارجاع به متغیر تعریف‌نشده خطاست؛ از اشتباه تایپی و فاجعه‌ی rm -rf "$BUILD_DIR/" با متغیر خالی جلوگیری می‌کند. متغیر اختیاری: ${VAR:-}.
  • -o pipefail: کد خروج pipeline برابر کد آخرین دستور ناموفق است. بدون آن، در mysqldump db | gzip > b.gz شکست mysqldump پنهان می‌ماند چون gzip موفق است و یک بکاپ خالی به عنوان موفق ثبت می‌شود.

محدودیت‌ها و تله‌های -e:

  • در شرط if/while/until، دستورات قبل از آخرین عضو &&/|| و دستورات منفی‌شده با ! فعال نیست.
  • local v=$(cmd) شکست را پنهان می‌کند (کد خروج local صفر است).
  • (( i++ )) وقتی i صفر است کد ۱ برمی‌گرداند و اسکریپت بی‌صدا خارج می‌شود.
  • دستوراتی که «شکست» آن‌ها طبیعی است (grep بدون نتیجه کد ۱ می‌دهد) باید صریحاً مدیریت شوند: grep -q x f || true.
  • در توابعی که در زمینه‌ی شرطی صدا زده می‌شوند، -e درون تابع هم غیرفعال است.

تکمیل: همراه آن trap 'echo "failed at line $LINENO" >&2' ERR برای پیام خطای واضح و trap cleanup EXIT برای تمیزکاری. strict mode جایگزین بررسی صریح خطا در نقاط حساس نیست.

تفاوت [ ] و [[ ]] و (( )) در Bash چیست؟ هر کدام را در چه شرایطی استفاده می‌کنید؟

[ ]: همان دستور test است (یک builtin معمولی، و فایل /usr/bin/[). چون دستور است، آرگومان‌هایش word splitting و globbing می‌شوند؛ پس quote اجباری است و فاصله‌ها لازم‌اند. در همه‌ی شل‌های POSIX کار می‌کند. < و > را شل به عنوان redirection تفسیر می‌کند؛ برای AND از [ a ] && [ b ] استفاده می‌شود.

[[ ]]: کلمه‌ی کلیدی bash (و zsh/ksh) است که شل آن را خودش parse می‌کند:

  • بدون word splitting و globbing روی متغیرها؛ امن‌تر.
  • &&، || و پرانتز درون آن مجاز است.
  • تطبیق الگوی glob: [[ $file == *.sql.gz ]] (سمت راست بدون quote الگوست).
  • regex: [[ $ver =~ ^([0-9]+)\.([0-9]+) ]] و نتیجه در BASH_REMATCH.
  • قابل‌حمل به sh/dash نیست.

(( )): ارزیابی حسابی؛ اگر نتیجه غیرصفر باشد کد خروج ۰ (true) است. متغیرها بدون $ و عملگرهای آشنای < > == &&.

if [ -f "$cfg" ] && [ "$env" = "prod" ]; then …; fi     # POSIX
if [[ -f $cfg && $env == prod* ]]; then …; fi           # bash
if (( disk_usage > 90 && retries < 3 )); then …; fi     # عددی

انتخاب: اسکریپت bash ← [[ ]] برای رشته و فایل، (( )) برای عدد. اسکریپتی که باید با /bin/sh (مثلاً در Docker image مبتنی بر Alpine بدون bash) اجرا شود ← [ ] با quote کامل.

تله: در [ ]، عبارت [ 10 > 9 ] مقایسه نیست؛ خروجی را به فایلی به نام 9 redirect می‌کند. برای عدد از -gt یا (( )) استفاده کنید.

stdin، stdout و stderr را توضیح دهید. تفاوت cmd > file 2>&1 و cmd 2>&1 > file چیست؟ چرا sudo echo text > /etc/file کار نمی‌کند؟

جریان‌های استاندارد: هر فرایند با سه file descriptor شروع می‌شود: 0 = stdin (ورودی)، 1 = stdout (خروجی عادی/داده)، 2 = stderr (خطا و پیام‌های تشخیصی). جدا بودن stderr باعث می‌شود در cmd | next فقط داده به دستور بعد برود و خطاها روی ترمینال یا لاگ دیده شوند.

ترتیب redirection: شل redirectionها را از چپ به راست اعمال می‌کند و 2>&1 یعنی «FD 2 را کپی مقصد فعلی FD 1 کن».

  • cmd > file 2>&1: ابتدا FD1 → file؛ سپس FD2 → همان file. هر دو خروجی در فایل. ✓
  • cmd 2>&1 > file: ابتدا FD2 → مقصد فعلی FD1 (ترمینال)؛ سپس فقط FD1 → file. خطاها همچنان روی ترمینال‌اند.
  • استثنای pipe: در cmd 2>&1 | less، چون pipe قبل از redirectionها برقرار می‌شود، stderr هم وارد pipe می‌شود.

sudo و redirection: در sudo echo text > /etc/file، عمل > توسط شل کاربر فعلی و قبل از اجرای sudo انجام می‌شود؛ فقط echo با دسترسی root اجرا می‌شود و کاربر عادی اجازه‌ی نوشتن در /etc را ندارد (Permission denied).

echo "text" | sudo tee /etc/file > /dev/null        # بازنویسی
echo "text" | sudo tee -a /etc/file > /dev/null     # افزودن
sudo sh -c 'echo text > /etc/file'                  # جایگزین

در cron الگوی استاندارد >> /var/log/job.log 2>&1 است تا هم خروجی و هم خطاها ثبت شوند.

یک دستور (one-liner) بنویسید که ۱۰ آدرس IP با بیشترین درخواست را از فایل access.log در Nginx استخراج کند. هر بخش آن را توضیح دهید و بگویید چگونه فقط درخواست‌های با خطای 5xx را بشمارید. 
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10
  • awk '{print $1}': در فرمت combined، ستون اول (جداکننده فاصله) IP کلاینت است؛ فقط آن چاپ می‌شود.
  • sort: IPهای یکسان کنار هم قرار می‌گیرند؛ لازم است چون uniq فقط تکرارهای مجاور را ادغام می‌کند.
  • uniq -c: هر IP یکتا با تعداد تکرارش ( 523 203.0.113.7).
  • sort -rn: مرتب‌سازی عددی نزولی بر اساس شمارش.
  • head -10: ده مورد اول.

شمارش 5xx: ستون نهم status code است.

awk '$9 ~ /^5/' access.log | wc -l                          # تعداد کل
awk '$9 ~ /^5/ {print $7}' access.log | sort | uniq -c | sort -rn | head   # URLهای مسئول
awk '$9 ~ /^5/ {c[$9]++} END {for (s in c) print s, c[s]}' access.log    # به تفکیک کد

نکات تکمیلی:

  • برای لاگ‌های چرخیده‌ی فشرده: zcat access.log.*.gz | awk ….
  • پشت load balancer یا CDN، ستون اول IP پروکسی است؛ باید real_ip در Nginx تنظیم شده باشد یا از ستون X-Forwarded-For در log_format سفارشی استفاده کرد.
  • اگر log_format سفارشی است، شماره‌ی ستون‌ها را بررسی کنید؛ برای لاگ JSON از jq استفاده می‌شود.
  • روی فایل‌های خیلی بزرگ، یک awk واحد با آرایه‌ی شمارش ({c[$1]++} END {...}) از نظر حافظه و سرعت بهتر از sort کل داده است.
Syntax یک خط crontab را توضیح دهید. Scheduler لاراول چگونه با cron کار می‌کند و چه مزیتی نسبت به تعریف مستقیم کارها در crontab دارد؟

Syntax: پنج فیلد زمانی و سپس دستور: دقیقه (0–59)، ساعت (0–23)، روز ماه (1–31)، ماه (1–12)، روز هفته (0–7، یکشنبه 0 یا 7). * یعنی هر مقدار، */5 هر ۵ واحد، 1-5 بازه، 1,15 لیست.

0 2 * * *     /usr/local/bin/db-backup.sh >> /var/log/backup.log 2>&1   # هر روز 02:00
*/10 * * * *  /usr/local/bin/healthcheck.sh                               # هر 10 دقیقه
30 4 * * 1    /usr/local/bin/weekly-report.sh                             # دوشنبه‌ها 04:30

تله‌های cron: PATH و محیط حداقلی (استفاده از مسیر مطلق)، % باید escape شود، پوشه‌ی جاری home است، خروجی باید لاگ شود، و اجرای هم‌پوشان (راه‌حل: flock).

Scheduler لاراول: فقط یک ورودی cron لازم است:

* * * * * cd /var/www/app/current && php artisan schedule:run >> /dev/null 2>&1

هر دقیقه schedule:run اجرا می‌شود، تعریف‌ها در routes/console.php را بررسی و تسک‌هایی که موعدشان رسیده را اجرا می‌کند. در محیط local به جای cron از schedule:work استفاده می‌شود.

مزایا:

  • زمان‌بندی در کد و git: قابل review، تاریخچه‌دار و یکسان بین سرورها؛ با deploy به‌روز می‌شود.
  • withoutOverlapping() برای جلوگیری از اجرای هم‌زمان، onOneServer() برای محیط چندسروری.
  • runInBackground()، hookهای onSuccess/onFailure، ارسال خروجی، timezone()، environments() و when().
  • دسترسی به کل اپلیکیشن (command، job، closure) و دستور schedule:list برای مشاهده.

نکته: اگر cron اصلی روی سرور تنظیم نشود، هیچ تسکی اجرا نمی‌شود؛ این مورد باید در چک‌لیست deploy باشد.

اسکریپت زیر برای پاک کردن فایل‌های قدیمی نوشته شده است. چه مشکلاتی دارد و نسخه‌ی اصلاح‌شده را بنویسید. cd $LOG_DIR; for f in $(ls *.log); do rm $f; done

مشکلات:

  1. cd بدون بررسی: اگر LOG_DIR خالی یا نادرست باشد، cd شکست می‌خورد (یا با متغیر خالی به home می‌رود) و حلقه در پوشه‌ی اشتباه فایل‌ها را حذف می‌کند.
  2. متغیر بدون quote: $LOG_DIR و $f در معرض word splitting و globbing؛ مسیر یا نام دارای فاصله شکسته می‌شود.
  3. parse کردن ls: نام فایل‌های دارای فاصله یا کاراکتر خاص خراب می‌شوند؛ اگر فایلی نباشد، خطا یا رفتار غیرمنتظره.
  4. شرط سن وجود ندارد: هدف «فایل‌های قدیمی» بوده اما همه را حذف می‌کند.
  5. نبود set -euo pipefail، لاگ، و حالت dry-run برای عملیات مخرب.
  6. نام فایلی که با - شروع شود به عنوان گزینه‌ی rm تفسیر می‌شود.

نسخه‌ی اصلاح‌شده:

#!/usr/bin/env bash
set -euo pipefail

LOG_DIR="${LOG_DIR:?LOG_DIR is required}"
DAYS="${DAYS:-14}"
DRY_RUN="${DRY_RUN:-0}"

[[ -d "$LOG_DIR" ]] || { echo "not a directory: $LOG_DIR" >&2; exit 1; }

if (( DRY_RUN )); then
    find "$LOG_DIR" -maxdepth 1 -type f -name '*.log' -mtime +"$DAYS" -print
else
    find "$LOG_DIR" -maxdepth 1 -type f -name '*.log' -mtime +"$DAYS" -print -delete
fi

چرا بهتر است: find بدون cd و بدون parse کردن خروجی کار می‌کند، نام‌های خاص را درست مدیریت می‌کند، شرط سن (-mtime) و نوع (-type f) دارد؛ ${LOG_DIR:?} جلوی متغیر خالی را می‌گیرد؛ -print لاگ حذف‌ها را می‌دهد و dry-run امکان بررسی قبل از اجرا را فراهم می‌کند. برای لاگ‌ها در عمل logrotate یا channel daily لاراول با days راه‌حل استانداردتری است.

یک اسکریپت بکاپ روزانه‌ی دیتابیس MySQL با نگهداری ۷ روز طراحی کنید. چه نکاتی را برای قابل اتکا بودن آن رعایت می‌کنید؟ 
#!/usr/bin/env bash
set -euo pipefail
DB=app; DIR=/var/backups/mysql; KEEP=7
FILE="$DIR/$DB-$(date +%Y%m%d-%H%M%S).sql.gz"

exec 9>/var/lock/db-backup.lock
flock -n 9 || { echo "already running" >&2; exit 1; }
trap 'rm -f "$FILE.part"' EXIT

mkdir -p "$DIR"
mysqldump --defaults-extra-file=/root/.my.cnf --single-transaction --quick \
    --routines --triggers "$DB" | gzip > "$FILE.part"
gzip -t "$FILE.part" && mv "$FILE.part" "$FILE"
find "$DIR" -name "$DB-*.sql.gz" -mtime +"$KEEP" -delete
# rclone copy "$FILE" offsite:mysql/

و در crontab: 0 2 * * * /usr/local/bin/db-backup.sh >> /var/log/db-backup.log 2>&1

نکات قابل اتکا بودن:

  • pipefail: بدون آن شکست mysqldump پشت موفقیت gzip پنهان می‌ماند.
  • --single-transaction: snapshot سازگار برای InnoDB بدون قفل کردن جدول‌ها؛ --quick برای خواندن ردیف‌به‌ردیف و حافظه‌ی کم.
  • بدون رمز در خط فرمان: فایل .my.cnf با chmod 600؛ رمز در ps دیده نمی‌شود.
  • فایل موقت + mv اتمیک و gzip -t: فایل ناقص هرگز بکاپ معتبر شناخته نمی‌شود.
  • flock: جلوگیری از اجرای هم‌زمان در صورت طولانی شدن.
  • Rotation با find -mtime؛ مراقب الگوی نام تا فایل دیگری حذف نشود.
  • Off-site (قاعده‌ی 3-2-1) و رمزنگاری بکاپ.
  • مانیتورینگ: exit code، لاگ و هشدار در صورت شکست یا کوچک بودن غیرعادی فایل.
  • تست restore دوره‌ای روی محیط جدا؛ بکاپ تست‌نشده قابل اتکا نیست.
  • برای دیتابیس‌های بزرگ: بکاپ فیزیکی (XtraBackup) یا snapshot، و binary log برای point-in-time recovery.
Idempotency در اسکریپت‌ها به چه معناست و چرا مهم است؟ با مثال توضیح دهید که یک اسکریپت آماده‌سازی سرور را چگونه idempotent می‌کنید.

تعریف: اسکریپت idempotent اسکریپتی است که اجرای چندباره‌ی آن همان وضعیت نهایی اجرای یک‌باره را ایجاد کند، بدون خطا یا اثر جانبی تکراری.

اهمیت:

  • اگر اسکریپت وسط کار شکست بخورد، می‌توان با خیال راحت دوباره اجرایش کرد.
  • اجرای مجدد روی سرورهایی که بخشی از آن‌ها از قبل آماده است (drift) امن است.
  • پایه‌ی ابزارهایی مثل Ansible و Terraform و retry در jobها همین مفهوم است.

تکنیک‌ها:

# ساخت پوشه: خطا نمی‌دهد اگر وجود داشته باشد
mkdir -p /var/www/app/shared/storage

# ایجاد کاربر فقط اگر وجود ندارد
id deploy &>/dev/null || sudo adduser --disabled-password --gecos "" deploy

# افزودن خط فقط یک‌بار
grep -qxF 'fs.inotify.max_user_watches=524288' /etc/sysctl.conf \
  || echo 'fs.inotify.max_user_watches=524288' | sudo tee -a /etc/sysctl.conf

# symlink: جایگزینی به جای خطا
ln -sfn /var/www/app/releases/20261107 /var/www/app/current

# نصب پکیج: apt خودش idempotent است
sudo apt-get install -y nginx

# نوشتن کامل فایل config (نه append) با heredoc
sudo tee /etc/supervisor/conf.d/worker.conf >/dev/null <<'EOF'
[program:worker]
command=php /var/www/app/current/artisan queue:work
EOF

ضد الگوها: echo … >> file بدون بررسی (خط تکراری در هر اجرا)، mkdir بدون -p، ln -s روی لینک موجود، migration دستی SQL بدون بررسی وجود ستون، و ارسال ایمیل یا شارژ مالی بدون کلید یکتا.

وقتی چنین اسکریپت‌هایی بزرگ می‌شوند، استفاده از Ansible که ماژول‌های idempotent دارد بهتر است.

چگونه از اجرای هم‌زمان دو نمونه از یک اسکریپت (مثلاً یک cron که ممکن است طولانی شود) جلوگیری می‌کنید؟ مزیت flock نسبت به فایل pid دستی چیست؟ معادل آن در Laravel کدام است؟

مشکل: cron به اجرای قبلی کاری ندارد؛ اگر job هر ۵ دقیقه اجرا شود و یک‌بار ۸ دقیقه طول بکشد، دو نمونه هم‌زمان روی همان داده کار می‌کنند: پردازش تکراری، race condition، بار مضاعف.

راه‌حل با flock:

# داخل اسکریپت
exec 200>/var/lock/sync.lock
flock -n 200 || { echo "already running, skip" >&2; exit 0; }

# یا از بیرون در crontab
*/5 * * * * flock -n /var/lock/sync.lock /usr/local/bin/sync.sh

-n یعنی اگر قفل گرفته شده منتظر نماند؛ -w 30 تا ۳۰ ثانیه صبر می‌کند.

مزیت flock بر pid file:

  • قفل در کرنل و وابسته به file descriptor باز است؛ وقتی فرایند به هر دلیلی (حتی kill -9 یا کرش) تمام شود، قفل خودکار آزاد می‌شود. pid file دستی در این حالت باقی می‌ماند (stale lock) و اجرای بعدی را برای همیشه مسدود می‌کند، مگر منطق پیچیده‌ی بررسی زنده بودن PID بنویسید.
  • بررسی و گرفتن قفل اتمیک است؛ در روش «اگر فایل نیست، بساز» بین بررسی و ساخت race condition وجود دارد.

محدودیت: flock فقط روی یک ماشین کار می‌کند؛ برای چند سرور قفل توزیع‌شده لازم است.

معادل‌های Laravel:

  • Schedule::command(...)->withoutOverlapping(): قفل مبتنی بر cache (با زمان انقضا) برای جلوگیری از هم‌پوشانی.
  • ->onOneServer(): در محیط چندسروری فقط یک سرور اجرا کند (نیاز به cache مشترک مثل Redis).
  • دستور Artisan با Isolatable و گزینه‌ی --isolated.
  • Cache::lock('name', $seconds)->get(fn () => …) برای قفل دلخواه در کد، و middleware WithoutOverlapping برای jobها.
یک دستور سفارشی Artisan برای یک کار دوره‌ای طراحی کنید. signature، آرگومان‌ها و گزینه‌ها، خروجی، کد خروج و زمان‌بندی آن را توضیح دهید. چرا Artisan command را به اسکریپت PHP یا Bash مستقل ترجیح می‌دهید؟

ساخت: php artisan make:command SendWeeklyDigest که کلاسی در app/Console/Commands می‌سازد (در Laravel 11 خودکار ثبت می‌شود).

<?php
protected $signature = 'digest:send
    {segment=all : Which users to target}
    {--dry-run : Do not send, only count}
    {--limit= : Max number of users}';

public function handle(DigestService $digest): int
{
    $users = User::query()->subscribedTo($this->argument('segment'))
        ->when($this->option('limit'), fn ($q, $l) => $q->limit((int) $l));

    if ($this->option('dry-run')) {
        $this->info($users->count() . ' users would receive the digest.');
        return self::SUCCESS;
    }

    $this->withProgressBar($users->lazyById(), fn ($u) => $digest->queueFor($u));
    $this->newLine();
    return self::SUCCESS;
}
  • Signature: {arg} اجباری، {arg?} اختیاری، {arg=default}، {--flag} بولی، {--opt=} با مقدار؛ توضیح با :. خواندن با argument() و option().
  • خروجی: info، warn، error، table، progress bar؛ ورودی تعاملی با confirm/ask (در cron غیرتعاملی است).
  • کد خروج: self::SUCCESS/FAILURE/INVALID تا scheduler، CI و مانیتورینگ شکست را تشخیص دهند.
  • Dependency injection در متد handle.

زمان‌بندی:

<?php
Schedule::command('digest:send')->weeklyOn(1, '08:00')->withoutOverlapping()->onOneServer();

چرا Artisan: دسترسی به container، Eloquent، config، cache، queue و logging پروژه؛ parse آرگومان و help خودکار (php artisan help digest:send)؛ یکپارچگی با scheduler و قفل‌ها؛ قابل تست با $this->artisan(...)->assertExitCode(0)؛ همان زبان و استانداردهای کد تیم. Bash برای کارهای سطح سیستم (بکاپ فایل، deploy، مدیریت سرویس) مناسب‌تر است. بهتر است منطق در یک Service باشد و Command فقط لایه‌ی رابط.

در چه شرایطی برای خودکارسازی به جای Bash از Python (یا PHP) استفاده می‌کنید؟ معیارهای تصمیم‌گیری خود را بنویسید.

Bash در اصل یک «زبان چسب» است: عالی برای اجرای دستورات، اتصال آن‌ها با pipe، کار با فایل و فرایند و سرویس، و همه‌جا (روی هر سرور لینوکس) موجود است. اما ساختار داده، مدیریت خطا و تست در آن ضعیف است.

معیارهای انتخاب Python/PHP:

  • اندازه و پیچیدگی: اگر اسکریپت از حدود ۱۰۰ خط بیشتر شد یا شرط‌ها و حلقه‌های تو در تو دارد.
  • ساختار داده: نیاز به دیکشنری تو در تو، لیست اشیاء، مرتب‌سازی پیچیده؛ آرایه‌های Bash محدودند.
  • فرمت‌های داده: JSON، YAML، CSV، XML، تاریخ و منطقه‌ی زمانی؛ در Bash به jq و ابزارهای خارجی وابسته‌اید.
  • شبکه و API: فراخوانی REST با احراز هویت، صفحه‌بندی و retry.
  • مدیریت خطا: exception و try/except/finally به جای تکیه بر exit code و تله‌های set -e.
  • تست و نگهداری: unit test، type hint، linting و قابلیت خواندن برای تیم.
  • قابلیت‌حمل: اجرا روی ویندوز/macOS/لینوکس.
  • محاسبات اعشاری و منطق کسب‌وکار.

معیارهای ماندن در Bash: اسکریپت کوتاه، عمدتاً فراخوانی دستورات سیستم، محیط حداقلی (مثلاً entrypoint کانتینر)، نیاز به اجرای بدون وابستگی.

PHP در تیم Laravel: اگر کار به داده و منطق پروژه مربوط است (گزارش، import، پاک‌سازی رکوردها)، Artisan command بهترین گزینه است: زبان تیم، دسترسی به مدل‌ها و config، scheduler و تست آماده.

ترکیب: رایج است که Bash نقش orchestrator سطح بالا را داشته باشد (deploy.sh) و کارهای منطقی را به php artisan یا یک اسکریپت Python بسپارد. در Python هم دستورات سیستم را با subprocess.run([...], check=True) و لیست آرگومان (نه shell=True) اجرا کنید تا از command injection جلوگیری شود.

یک اسکریپت deploy ساده برای Laravel با حداقل downtime طراحی کنید. مراحل آن و نقش هر مرحله را توضیح دهید و بگویید rollback چگونه انجام می‌شود.

ایده: ساختار releases + symlink: هر deploy در یک پوشه‌ی جدید (releases/<timestamp>) کامل آماده می‌شود و در انتها symlink current به‌صورت اتمیک به آن اشاره می‌کند. فایل‌های مشترک (.env و storage) در shared/ هستند.

مراحل:

  1. Strict mode و lock: set -euo pipefail و flock تا دو deploy هم‌زمان اجرا نشوند؛ trap ERR برای پیام شکست.
  2. دریافت کد: git clone --depth 1 --branch main در پوشه‌ی release جدید.
  3. لینک shared: ln -s shared/.env و جایگزینی storage با لینک به shared/storage.
  4. وابستگی‌ها: composer install --no-dev --optimize-autoloader --no-interaction و npm ci && npm run build (یا artifact آماده از CI).
  5. Migration: php artisan migrate --force؛ باید با کد قدیمی سازگار باشد (الگوی expand/contract) چون تا سوییچ، کد قبلی سرویس می‌دهد.
  6. کش‌ها: php artisan optimize.
  7. سوییچ اتمیک: ln -sfn $RELEASE current.tmp && mv -T current.tmp current.
  8. Reload: systemctl reload php8.3-fpm (پاک شدن OPcache بدون قطع درخواست‌های جاری) و php artisan queue:restart.
  9. Smoke test: curl -fsS https://example.com/up؛ در صورت شکست، rollback خودکار.
  10. پاک‌سازی: نگه داشتن ۵ release آخر.

چرا downtime کم است: همه‌ی کارهای کند قبل از سوییچ انجام می‌شود و اگر هر مرحله شکست بخورد، current دست‌نخورده می‌ماند. سوییچ یک rename اتمیک است. Nginx باید از $realpath_root استفاده کند.

Rollback: اشاره‌ی current به release قبلی (ls -1dt releases/*/ | sed -n 2p)، reload FPM و queue:restart. migrationها خودکار برنمی‌گردند؛ به همین دلیل migrationهای مخرب (حذف ستون) در deploy بعدی و جدا انجام می‌شوند.

در عمل: ابزارهایی مثل Deployer یا Envoyer همین الگو را پیاده‌سازی می‌کنند؛ برای چند سرور، deploy پشت load balancer به‌صورت rolling.

ابزارهای grep، sed، awk، cut و jq را مقایسه کنید. هر کدام برای چه نوع کاری مناسب‌اند؟ برای هر یک مثالی کاربردی از کار روزمره‌ی یک توسعه‌دهنده‌ی بک‌اند بزنید.
  • grep — پیدا کردن خطوط: فیلتر خطوط بر اساس الگو (regex). سریع‌ترین انتخاب برای «کدام خطوط شامل X هستند». مثال: grep -rn "env(" app/ --include="*.php" برای پیدا کردن استفاده‌ی نادرست از env خارج از config؛ grep -c "production.ERROR" laravel.log.
  • sed — ویرایش جریانی: جایگزینی، حذف یا چاپ بخشی از خطوط؛ مناسب تغییرات مکانیکی در فایل‌های config. مثال: sed -i 's/^APP_DEBUG=.*/APP_DEBUG=false/' .env؛ sed -n '/2026-11-07 10:00/,/2026-11-07 10:05/p' laravel.log برای برش بازه‌ی زمانی لاگ.
  • awk — پردازش ستونی و محاسبه: یک زبان کوچک با متغیر، شرط، آرایه‌ی انجمنی و BEGIN/END؛ مناسب گزارش‌گیری از داده‌ی جدولی. مثال: awk '$9 >= 500 {c[$7]++} END {for (u in c) print c[u], u}' access.log | sort -rn | head برای پرخطاترین URLها.
  • cut — برش ساده‌ی ستون: وقتی جداکننده ثابت و یک‌کاراکتری است؛ ساده‌تر و سریع‌تر از awk اما بدون منطق. مثال: cut -d: -f1 /etc/passwd؛ cut -d, -f2 export.csv. محدودیت: فاصله‌های متوالی را یک جداکننده نمی‌داند (آنجا awk بهتر است).
  • jq — JSON: parse، فیلتر و تبدیل JSON به‌صورت ساختاریافته؛ grep/sed روی JSON شکننده است. مثال: curl -s api/health | jq -r '.checks[] | select(.ok == false) | .name'؛ jq -r '.require | keys[]' composer.json.

قاعده‌ی انتخاب: پیدا کردن ← grep؛ تغییر متن ← sed؛ ستون + شرط + شمارش/جمع ← awk؛ ستون ساده ← cut؛ JSON ← jq. با pipe ترکیب می‌شوند و در کنار sort | uniq -c | sort -rn | head بیشتر نیازهای تحلیل لاگ را پوشش می‌دهند. وقتی منطق پیچیده شد، به Python یا PHP منتقل شوید.

خلاصه برای مرور سریع

پایه

  • #!/usr/bin/env bash + chmod +x + ./script.sh.
  • sh در اوبونتو = dash (بدون [[ ]] و آرایه).
  • CRLF → bad interpreter → dos2unix.
  • set -euo pipefail + trap cleanup EXIT.

متغیر و quoting

  • a=1 بدون فاصله؛ "$a" همیشه.
  • double: expand بدون split؛ single: لفظی.
  • ${v:-d} پیش‌فرض؛ ${v:=d} اختصاص؛ ${v:?} خطا.
  • ${f##*/} basename؛ ${f%/*} dirname؛ ${f%.*} بدون پسوند.
  • "$@" آرگومان‌ها جدا؛ "$*" یک رشته؛ $# تعداد؛ $? کد خروج.

کنترل

  • [[ ]] امن، regex =~، glob ==؛ [ ] POSIX با quote.
  • (( )) عددی؛ -eq -lt -gt در test.
  • -f -d -e -z -n -s -x.
  • while IFS= read -r line; do …; done < file.
  • pipe به while = subshell.
  • local در توابع؛ return فقط کد؛ داده با echo.
  • 0 موفق؛ 127 not found؛ 128+N سیگنال.

تله‌های set -e

  • داخل if، زنجیره‌ی &&/|| غیرفعال.
  • local x=$(cmd) خطا را می‌پوشاند.
  • ((i++)) با i=0 → خروج.
  • grep بدون نتیجه = 1 → || true.

I/O

  • 0 stdin، 1 stdout، 2 stderr.
  • > file 2>&1 (ترتیب مهم)؛ &>؛ >/dev/null.
  • | sudo tee file به جای sudo echo >.
  • <<EOF با expansion؛ <<'EOF' بدون؛ <<< here-string.

متن

  • grep -i -v -c -n -r -o -E -F -l.
  • sed s///g، -n 'Np'، /re/d، -i.
  • awk $1 NF NR -F END؛ {s+=$10} END{print s}.
  • sort | uniq -c | sort -rn | head.
  • find -mtime +7 -delete، -exec … {} +، -print0 | xargs -0.
  • jq -r '.data[] | select(.x=="y") | .id'.
  • Nginx: $1 IP، $7 path، $9 status، $10 bytes.

cron و scheduler

  • دقیقه ساعت روز ماه روزهفته.
  • PATH حداقلی، \%، مسیر مطلق، لاگ، flock.
  • * * * * * cd app && php artisan schedule:run.
  • schedule:work (local)، schedule:list.
  • withoutOverlapping، onOneServer، runInBackground.

اسکریپت مقاوم

  • getopts ":e:nh" + shift $((OPTIND-1)).
  • log به stderr، idempotent (mkdir -p، ln -sfn، grep -q ||).
  • dry-run برای عملیات مخرب.
  • flock -n؛ قفل با مرگ فرایند آزاد می‌شود.
  • رمز در فایل 600 نه آرگومان.
  • نوشتن .part + mv اتمیک.

Artisan و دیگر ابزارها

  • make:command؛ {arg} {arg?} {arg=d} {--flag} {--opt=}.
  • argument()، option()، info/warn/error/table، progress bar.
  • self::SUCCESS / FAILURE / INVALID.
  • Isolatable → --isolated.
  • Python: داده‌ی پیچیده، API، تست، بیش از ~۱۰۰ خط.
  • Makefile: TAB، .PHONY، هر خط shell جدا، $$.
  • ShellCheck: SC2086 quote، SC2164 cd، SC2155 local، SC2045 ls.
