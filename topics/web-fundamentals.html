دسته‌های status code

  • 1xx اطلاعاتی (101 Switching Protocols، 103 Early Hints)
  • 2xx موفق (200، 201، 204)
  • 3xx redirect (301، 302، 304، 307، 308)
  • 4xx خطای client (400، 401، 403، 404، 419 در Laravel برای CSRF منقضی، 422، 429)
  • 5xx خطای سرور (500، 502، 503، 504)

تفاوت ارسال فرم HTML با application/x-www-form-urlencoded (پیش‌فرض، a=1&b=2) و multipart/form-data (لازم برای آپلود فایل، بخش‌ها با boundary جدا می‌شوند) و ارسال JSON با application/json سوال رایجی است. فرم HTML فقط GET و POST را پشتیبانی می‌کند؛ Laravel برای PUT/PATCH/DELETE از method spoofing با فیلد مخفی _method (دستور Blade @method('PUT')) استفاده می‌کند.

Cookie و Session

چون HTTP stateless است، برای «به خاطر سپردن» کاربر بین درخواست‌ها از cookie استفاده می‌کنیم: سرور با Set-Cookie یک جفت نام/مقدار به مرورگر می‌دهد و مرورگر آن را در درخواست‌های بعدی (منطبق با دامنه و مسیر) با هدر Cookie برمی‌گرداند.

Set-Cookie: __Host-session=9f8a7c...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=7200
Attributeمعنانکته
Expires / Max-Ageزمان انقضا (تاریخ مطلق / ثانیه)بدون هر دو ⇐ session cookie که با بستن مرورگر پاک می‌شود. اگر هر دو باشند، Max-Age اولویت دارد. Max-Age=0 یعنی حذف.
Domainدامنه‌هایی که cookie برایشان ارسال می‌شوداگر تنظیم نشود، فقط همان host (host-only). اگر Domain=example.com شود، زیردامنه‌ها هم دریافت می‌کنند (دامنهٔ گسترده‌تر = ریسک بیشتر).
Pathپیشوند مسیرهایی که cookie برایشان ارسال می‌شودمرز امنیتی محسوب نمی‌شود.
Secureفقط روی HTTPS ارسال شودبرای cookieهای حساس الزامی.
HttpOnlyاز طریق JavaScript (document.cookie) قابل دسترسی نیستسرقت session با XSS را دشوار می‌کند (ولی XSS را حل نمی‌کند).
SameSiteکنترل ارسال در درخواست‌های cross-siteStrict: هرگز cross-site؛ Lax: فقط در navigation سطح بالا با متد امن (کلیک روی لینک)؛ None: همیشه — نیازمند Secure. مرورگرهای مبتنی بر Chromium در نبود این attribute رفتار Lax را پیش‌فرض می‌گیرند.

پیشوند __Host- در نام cookie مرورگر را مجبور می‌کند فقط وقتی آن را بپذیرد که Secure باشد، Path=/ داشته باشد و Domain نداشته باشد؛ بنابراین زیردامنهٔ آلوده نمی‌تواند آن را بازنویسی کند.

Session سمت سرور

1. POST /login (credentials)
2. سرور کاربر را احراز می‌کند، session id تصادفی می‌سازد، داده را در store ذخیره می‌کند
     store (file / database / Redis):  9f8a7c → { user_id: 42, cart: [...] }
3. Set-Cookie: laravel_session=9f8a7c (HttpOnly, Secure, SameSite=Lax)
4. درخواست‌های بعدی: Cookie: laravel_session=9f8a7c → lookup در store → کاربر 42
  • در cookie فقط شناسهٔ تصادفی است؛ داده‌ها روی سرور می‌ماند. (Laravel cookieها را رمز می‌کند؛ درایور cookie خود داده را در cookie رمزشده نگه می‌دارد.)
  • در چند سرور، session store باید مشترک باشد (Redis یا دیتابیس) — یا sticky session که توصیه نمی‌شود.
  • Session fixation: پس از login شناسهٔ session را عوض کنید ($request->session()->regenerate()؛ Laravel در سیستم احراز هویتش این کار را انجام می‌دهد). در logout هم session را invalidate کنید.
  • CSRF: چون مرورگر cookie را خودکار می‌فرستد، سایت مخرب می‌تواند درخواست تغییردهنده از طرف کاربر ارسال کند. دفاع: CSRF token (@csrf در Laravel؛ خطای 419 در صورت نبود یا انقضا)، SameSite=Lax/Strict، و عدم انجام تغییر با GET.

Session + Cookie

  • stateful؛ لغو فوری با حذف session
  • HttpOnly ⇒ دور از دسترس JS
  • نیاز به CSRF protection
  • مناسب اپ وب سرور-رندر و SPA first-party

Token در هدر Authorization

  • stateless (JWT) یا lookup (opaque)
  • اگر در localStorage باشد ⇒ در معرض XSS
  • CSRF ندارد (مرورگر خودکار نمی‌فرستد)
  • مناسب موبایل، API شخص ثالث، cross-domain

مبانی HTTP Cache و CORS

HTTP Cache

cache در مرورگر (private) یا در CDN و proxy (shared) پاسخ‌ها را نگه می‌دارد. دو مکانیزم دارد:

  1. Freshness: تا وقتی پاسخ تازه است، بدون تماس با سرور استفاده می‌شود: Cache-Control: max-age=3600.
  2. Validation: بعد از stale شدن، مرورگر درخواست شرطی می‌فرستد (If-None-Match: "etag") و اگر تغییری نبود، 304 Not Modified بدون بدنه می‌گیرد.
نوع محتواسیاست پیشنهادی
فایل static با hash در نام (app.3f9c1.js؛ خروجی Vite)Cache-Control: public, max-age=31536000, immutable — تغییر محتوا = نام جدید (cache busting)
HTML صفحهno-cache (همیشه revalidate) یا max-age کوتاه
پاسخ API شخصیprivate, no-cache یا no-store برای داده حساس
دادهٔ عمومی کم‌تغییرpublic, max-age=60, s-maxage=300

no-cache = «ذخیره کن ولی قبل از استفاده بپرس»؛ no-store = «اصلاً ذخیره نکن». هدر Vary (مثلاً Vary: Accept-Encoding) به cache می‌گوید پاسخ بسته به کدام هدر درخواست متفاوت است.

Same-Origin Policy و CORS

Origin = scheme + host + port. https://app.example.com و https://api.example.com دو origin متفاوت‌اند (اما same-site هستند چون دامنهٔ ثبت‌شدهٔ یکسان دارند — این تمایز برای SameSite cookie مهم است). Same-Origin Policy مرورگر اجازه نمی‌دهد JS یک origin پاسخ درخواست به origin دیگر را بخواند، مگر اینکه سرور مقصد با CORS اجازه دهد.

  • Simple request: متد GET/HEAD/POST، فقط هدرهای ساده و Content-Type یکی از text/plain، application/x-www-form-urlencoded، multipart/form-data. مستقیم ارسال می‌شود و مرورگر فقط هدر Access-Control-Allow-Origin پاسخ را چک می‌کند.
  • Preflight: در غیر این صورت (مثلاً Content-Type: application/json، هدر Authorization، یا متد PUT/DELETE) مرورگر ابتدا یک OPTIONS می‌فرستد تا اجازه بگیرد.
Browser (app.example.com)                         Server (api.example.com)
  │ OPTIONS /orders                                          │
  │ Origin: https://app.example.com                          │
  │ Access-Control-Request-Method: DELETE                    │
  │ Access-Control-Request-Headers: authorization ─────────► │
  │ ◄─────────────── 204  Access-Control-Allow-Origin: https://app.example.com
  │                       Access-Control-Allow-Methods: GET, POST, DELETE
  │                       Access-Control-Allow-Headers: authorization
  │                       Access-Control-Max-Age: 600
  │ DELETE /orders/7  (درخواست اصلی) ──────────────────────► │
  │ ◄─────────────── 204  Access-Control-Allow-Origin: https://app.example.com

CORS را مرورگر اعمال می‌کند؛ از سرور در برابر curl یا اسکریپت محافظت نمی‌کند. همچنین CORS جلوی ارسال simple request را نمی‌گیرد (فقط خواندن پاسخ را مسدود می‌کند)، پس جایگزین CSRF token نیست. Access-Control-Allow-Origin: * همراه با credentials (cookie) مجاز نیست.

Meta و مبانی SEO

  • <title> یکتا و توصیفی برای هر صفحه؛ meta description برای snippet نتایج جستجو.
  • <link rel="canonical"> برای جلوگیری از محتوای تکراری (مثلاً صفحه با پارامترهای مرتب‌سازی مختلف).
  • <meta name="robots" content="noindex"> برای صفحاتی که نباید index شوند؛ robots.txt و sitemap.xml.
  • Open Graph و Twitter Card برای پیش‌نمایش اشتراک‌گذاری؛ hreflang برای نسخه‌های چندزبانه؛ داده‌های ساختاریافته (JSON-LD با schema.org).

  • محتوایی که فقط با JS رندر می‌شود ممکن است دیرتر یا ناقص index شود؛ SSR (مثل Blade یا Inertia SSR) برای صفحات عمومی مزیت دارد.

نکات فرم

  • Input typeها: text، email، password، number، tel، url، search، date، datetime-local، time، range، color، file، checkbox، radio، hidden. type درست کیبورد مناسب موبایل و validation داخلی را فعال می‌کند.
  • Validation داخلی (Constraint Validation): required، min/max، minlength/maxlength، pattern، step؛ در CSS با :invalid و :user-invalid و در JS با checkValidity() و setCustomValidity(). novalidate آن را خاموش می‌کند.
  • اعتبارسنجی سمت client هرگز کافی نیست: با DevTools یا curl دور زده می‌شود؛ همیشه در سرور (Form Request لاراول) validate کنید.
  • name کلید ارسال‌شده به سرور است؛ id برای اتصال label و CSS/JS. فیلد بدون name ارسال نمی‌شود؛ فیلد disabled هم ارسال نمی‌شود (برخلاف readonly). checkbox تیک‌نخورده اصلاً ارسال نمی‌شود.
  • enctype="multipart/form-data" برای آپلود فایل الزامی است. method="GET" داده‌ها را در query string می‌گذارد (برای جستجو مناسب، برای رمز عبور هرگز).
  • autocomplete درست (email، current-password، one-time-code) تجربهٔ کاربری و مدیران رمز را بهبود می‌دهد.
  • <button> داخل form به‌طور پیش‌فرض type="submit" است؛ برای دکمه‌های دیگر type="button" بگذارید.

دسترس‌پذیری (Accessibility، a11y) و ARIA

  • اول HTML معنایی: «قانون اول ARIA»: اگر عنصر بومی HTML با معنا و رفتار مورد نیاز وجود دارد، از آن استفاده کنید نه از <div role="button">. عنصر بومی فوکوس، کیبورد و معنا را رایگان دارد.
  • هر input باید label مرتبط داشته باشد (placeholder جایگزین label نیست).
  • تصاویر معنادار alt توصیفی؛ تصاویر تزئینی alt="" تا screen reader از آن‌ها بگذرد.
  • همهٔ تعامل‌ها با کیبورد قابل انجام باشند؛ ترتیب فوکوس منطقی؛ :focus-visible را حذف نکنید. tabindex="0" عنصر را فوکوس‌پذیر می‌کند، -1 فقط با اسکریپت؛ مقادیر مثبت ضدالگو هستند.
  • کنتراست رنگ کافی (WCAG AA: نسبت ۴٫۵:۱ برای متن معمولی) و عدم اتکای صرف به رنگ برای انتقال معنا.
  • ARIA پرکاربرد:
    • aria-label / aria-labelledby: نام دسترس‌پذیر (مثلاً دکمهٔ آیکونی).
    • aria-describedby: توضیح یا پیام خطای مرتبط با فیلد.
    • aria-expanded، aria-controls: وضعیت منوی کشویی/آکاردئون.
    • aria-live="polite": اعلام تغییرات پویا (نتیجهٔ ذخیره، toast).
    • aria-hidden="true": پنهان کردن از فناوری‌های کمکی (روی عنصر فوکوس‌پذیر نگذارید).
    • aria-invalid="true": فیلد نامعتبر.
<button type="button" aria-label="بستن" aria-controls="menu" aria-expanded="false">
  <svg aria-hidden="true">...</svg>
</button>
<div role="status" aria-live="polite"></div>   <!-- پیام «ذخیره شد» این‌جا درج می‌شود -->

ARIA فقط معنا را برای فناوری‌های کمکی تغییر می‌دهد، نه رفتار را. <div role="button"> همچنان با Enter/Space کار نمی‌کند و فوکوس نمی‌گیرد مگر خودتان tabindex و event handler کیبورد اضافه کنید. «ARIA بد بدتر از نبود ARIA است.»

Cascade، Specificity و Inheritance

وقتی چند قانون CSS برای یک property روی یک عنصر رقابت می‌کنند، Cascade برنده را تعیین می‌کند. ترتیب معیارها (از مهم‌ترین):

  1. Origin و importance: استایل‌های transition؛ !important مرورگر (user-agent)؛ !important کاربر؛ !important نویسنده؛ animationها؛ استایل عادی نویسنده؛ کاربر؛ مرورگر. (برای حالت عادی: نویسنده > کاربر > مرورگر و برای !important برعکس.)
  2. Cascade layers (@layer): استایل بیرون از layerها بر داخل layerها غلبه می‌کند و بین layerها، آخرین تعریف‌شده برنده است (برای !important برعکس).
  3. Specificity selector.
  4. ترتیب ظاهر شدن: در specificity برابر، قانون آخر برنده است.

(استایل inline با style="" را می‌توان بالاترین سطح specificity در نظر گرفت.)

محاسبهٔ Specificity

specificity یک سه‌تایی (A, B, C) است که از چپ مقایسه می‌شود (نه مبنای ده!):

  • A: تعداد ID selectorها (#nav)
  • B: تعداد class (.btn)، attribute ([type="text"]) و pseudo-class (:hover، :nth-child())
  • C: تعداد type selector (div) و pseudo-element (::before)
  • صفر: universal *، combinatorها (>، +، ~، فاصله) و :where().
  • :is()، :not() و :has() خودشان صفرند اما specificity بیشترین آرگومان خود را می‌گیرند.

یک ID همیشه از هر تعداد class قوی‌تر است، چون مقایسه ستون‌به‌ستون انجام می‌شود: (1,0,0) > (0,15,0). specificity فقط وقتی مطرح است که قوانین در یک origin و layer باشند؛ در غیر این صورت معیارهای بالاتر cascade تصمیم می‌گیرند.

برای CSS قابل نگه‌داری: specificity را پایین و یکنواخت نگه دارید (classها، روش BEM یا utility-first مثل Tailwind)، از ID برای استایل و از !important پرهیز کنید، و برای استایل‌های پایه/ریست از :where() یا @layer استفاده کنید تا به‌راحتی override شوند.

Inheritance

  • برخی propertyها به‌طور پیش‌فرض از والد ارث می‌رسند: عمدتاً متنی‌ها مثل color، font-*، line-height، text-align، visibility، direction، cursor.
  • بیشتر propertyهای چیدمان و جعبه ارث نمی‌رسند: margin، padding، border، width، background، display، position.
  • کلمات کلیدی سراسری: inherit (از والد بگیر)، initial (مقدار اولیهٔ مشخصات)، unset (inherit اگر ارثی است، وگرنه initial)، revert (برگشت به استایل مرورگر).
  • مقدار ارث‌رسیده specificity ندارد: هر قانونی که مستقیماً عنصر را هدف بگیرد، حتی *، بر مقدار ارثی غلبه می‌کند.

Flexbox و Grid

Flexbox — یک‌بعدی

  • چیدمان در یک راستا (ردیف یا ستون)
  • content-first: اندازهٔ آیتم‌ها از محتوا
  • مناسب: navbar، ردیف دکمه‌ها، وسط‌چین کردن، توزیع فضا

Grid — دوبعدی

  • ردیف و ستون هم‌زمان
  • layout-first: ابتدا شبکه تعریف می‌شود
  • مناسب: layout کل صفحه، گالری، داشبورد، فرم‌های چندستونه

Flexbox

.toolbar {
  display: flex;
  flex-direction: row;          /* main axis: row | column (+ -reverse) */
  justify-content: space-between; /* چیدمان روی main axis */
  align-items: center;          /* چیدمان روی cross axis */
  flex-wrap: wrap;              /* شکستن به خط بعد */
  gap: 1rem;                    /* فاصله بین آیتم‌ها */
}
.toolbar .search { flex: 1 1 240px; } /* flex-grow flex-shrink flex-basis */
.toolbar .logo   { flex: none; }      /* 0 0 auto: نه بزرگ می‌شود نه کوچک */

/* وسط‌چین کردن کامل */
.center { display: flex; justify-content: center; align-items: center; min-height: 100vh; }
  • Main axis با flex-direction تعیین می‌شود؛ justify-content روی main axis و align-items روی cross axis کار می‌کند. در RTL، row از راست شروع می‌شود.
  • flex-grow: سهم از فضای اضافی؛ flex-shrink: سهم از کوچک شدن؛ flex-basis: اندازهٔ پایه قبل از توزیع. flex: 1 یعنی 1 1 0% (آیتم‌های هم‌اندازه).
  • align-self برای یک آیتم؛ order ترتیب نمایشی را عوض می‌کند (ولی ترتیب DOM و فوکوس کیبورد عوض نمی‌شود — مراقب دسترس‌پذیری باشید).
  • دام رایج: آیتم flex به‌طور پیش‌فرض min-width: auto دارد و از محتوایش کوچک‌تر نمی‌شود (مثلاً متن طولانی بدون شکستن)؛ min-width: 0 مشکل را حل می‌کند.

Media query و Mobile-first

Mobile-first یعنی استایل پایه برای صفحهٔ کوچک نوشته شود و با min-width برای صفحات بزرگ‌تر اضافه شود. مزایا: CSS ساده‌تر برای دستگاه‌های ضعیف‌تر، تمرکز بر محتوای اصلی و پیشرفت تدریجی.

.products { display: grid; grid-template-columns: 1fr; gap: 1rem; }

@media (min-width: 640px)  { .products { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 1024px) { .products { grid-template-columns: repeat(4, 1fr); } }

@media (prefers-color-scheme: dark)   { :root { --bg: #111; --text: #eee; } }
@media (prefers-reduced-motion: reduce) { * { animation: none !important; transition: none !important; } }
@media (hover: hover) { .card:hover { transform: translateY(-2px); } }

/* Container query: بر اساس اندازهٔ والد، نه viewport */
.sidebar { container-type: inline-size; }
@container (min-width: 400px) { .widget { display: flex; } }

بدون <meta name="viewport" content="width=device-width, initial-scale=1"> مرورگر موبایل صفحه را با عرض مجازی بزرگ (حدود ۹۸۰px) رندر و کوچک می‌کند و media queryها طبق انتظار کار نمی‌کنند. responsive = viewport meta + layout سیال (flex/grid، درصد، fr) + media query + تصاویر واکنش‌گرا (srcset، sizes، max-width: 100%).

JavaScript dynamically typed و weakly typed است. هفت نوع primitive (immutable، کپی با مقدار): string، number (float 64 بیتی IEEE 754)، bigint، boolean، undefined، null، symbol؛ و object (شامل آرایه، تابع، Date، Map و …) که با reference منتقل می‌شود.

Coercion و == در برابر ===

  • === (strict equality): بدون تبدیل نوع؛ اگر نوع متفاوت باشد false.
  • == (loose equality): قبل از مقایسه تبدیل نوع ضمنی (coercion) با قواعد پیچیده انجام می‌دهد.
  • objectها در هر دو حالت با reference مقایسه می‌شوند: {} === {} false است.
0 == ''            // true    ('' → 0)

JS: Scope، Closure، this و Prototype

Scope و Closure

JavaScript lexical scope دارد: دسترسی به متغیرها بر اساس محل نوشتن کد تعیین می‌شود نه محل فراخوانی. scopeها: global، module، function، block. جستجوی متغیر از scope داخلی به بیرونی (scope chain) انجام می‌شود.

Closure تابعی است همراه با ارجاع به محیط lexical که در آن تعریف شده؛ یعنی تابع داخلی حتی پس از بازگشت تابع بیرونی، به متغیرهای آن دسترسی دارد (متغیرها زنده می‌مانند، نه کپی‌شان).

function createCounter() {
  let count = 0;                 // private state
  return {
    inc: () => ++count,
    get: () => count,
  };
}
const c = createCounter();
c.inc(); c.inc();
c.get();      // 2  — count از بیرون قابل دسترسی مستقیم نیست (encapsulation)

// کاربردهای دیگر: factory، memoize، debounce، partial application
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}
// سوال کلاسیک
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3 3 3  ← یک i مشترک (function-scoped)؛ callbackها بعد از اتمام حلقه اجرا می‌شوند

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0 1 2  ← let در هر تکرار binding جدید می‌سازد؛ هر closure، i خودش را دارد

closureها متغیرهای محیطشان را زنده نگه می‌دارند؛ اگر event listener یا timerای که به ساختار دادهٔ بزرگ ارجاع دارد پاک نشود، memory leak رخ می‌دهد.

قواعد this

مقدار this در توابع معمولی هنگام فراخوانی تعیین می‌شود، نه تعریف. چهار قاعده به ترتیب اولویت:

  1. new binding: new Foo() ⇐ this شیء تازه ساخته‌شده است.
  2. Explicit binding: fn.call(obj, a)، fn.apply(obj, [a])، fn.bind(obj) (تابع جدید با this ثابت).
  3. Implicit binding: obj.method() ⇐ this === obj (شیء قبل از نقطه).
  4. Default binding: فراخوانی ساده fn() ⇐ در strict mode (و ماژول‌ها و کلاس‌ها) undefined؛ در غیر این صورت global object.

Arrow function اصلاً this خودش را ندارد؛ this را به‌صورت lexical از scope بیرونی می‌گیرد و با call/bind/new تغییر نمی‌کند (با new قابل فراخوانی نیست، arguments و prototype ندارد).

'use strict';
const user = {
  name: 'Ali',

Prototype و class

وراثت در JavaScript prototype-based است: هر شیء یک لینک داخلی به شیء دیگر (prototype) دارد؛ اگر property در خود شیء پیدا نشود، در prototype chain جستجو می‌شود تا null. class در ES2015 syntactic sugar روی همین مکانیزم است (به‌علاوهٔ چند تفاوت مثل اجرای خودکار در strict mode و TDZ).

class Animal {
  #sound;                              // فیلد private واقعی
  static count = 0;
  constructor(name, sound) { this.name = name; this.#sound = sound; Animal.count++; }
  speak() { return `${this.name} says ${this.#sound}`; }  // روی Animal.prototype
}
class Dog extends Animal {
  constructor(name) { super(name, 'woof'); }               // super قبل از this اجباری است
  speak() { return super.speak() + '!'; }
}
const d = new Dog('Rex');
d.speak();                                        // 'Rex says woof!'
Object.getPrototypeOf(d) === Dog.prototype;       // true
Object.getPrototypeOf(Dog.prototype) === Animal.prototype; // true
d.hasOwnProperty('speak');                        // false — از prototype می‌آید
// chain: d → Dog.prototype → Animal.prototype → Object.prototype → null

متدها روی prototype یک‌بار تعریف و بین همهٔ نمونه‌ها به اشتراک گذاشته می‌شوند (صرفه‌جویی حافظه). فیلدهای کلاس (مثل handle = () => {}) روی هر نمونه جداگانه ساخته می‌شوند — مفید برای bind کردن this در callbackها ولی با هزینهٔ حافظه.

JS: Event Loop و برنامه‌نویسی ناهمگام

JavaScript در مرورگر (و Node) روی یک thread اصلی اجرا می‌شود: یک call stack دارد و در هر لحظه فقط یک کار انجام می‌دهد. عملیات کند (شبکه، timer، I/O) به محیط میزبان (Web APIs / libuv) سپرده می‌شوند و callbackهایشان بعداً از طریق صف‌ها اجرا می‌شوند. Event loop این هماهنگی را انجام می‌دهد.

┌─────────────┐     ┌──────────────────────────┐
│ Call Stack  │ ──► │ Web APIs (timer, fetch,   │
└─────▲───────┘     │ DOM events)               │
      │             └───────────┬──────────────┘
      │                         ▼
      │   ┌─────────────────────────────────────────────┐
      │   │ Microtask queue: Promise.then/catch/finally, │  ← اولویت بالا: همه تخلیه می‌شوند
      │   │ await continuation, queueMicrotask,          │
      │   │ MutationObserver                             │
      │   └─────────────────────────────────────────────┘
      │   ┌─────────────────────────────────────────────┐
      └───│ Macrotask (task) queue: setTimeout,          │  ← در هر دور فقط یکی
          │ setInterval, I/O, UI events, MessageChannel  │
          └─────────────────────────────────────────────┘
الگوریتم هر دور:
1) یک task از صف macrotask اجرا کن (اجرای اولیهٔ script هم خودش یک task است)
2) تا خالی شدن کامل، همهٔ microtaskها را اجرا کن (microtaskهای تازه هم در همین دور)
3) در صورت نیاز rendering (requestAnimationFrame، style، layout، paint)
4) تکرار

مثال ترتیب اجرا

console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

queueMicrotask(() => console.log('4'));

(async () => {
  console.log('5');        // بدنهٔ async تا اولین await همگام اجرا می‌شود
  await null;
  console.log('6');        // ادامه به‌صورت microtask
})();

console.log('7');

// خروجی: 1 5 7 3 4 6 2
  1. کد همگام: 1، سپس 5 (بدنهٔ async تا await)، سپس 7.
  2. stack خالی شد ⇐ تخلیهٔ microtaskها به ترتیب ورود: 3 (then)، 4 (queueMicrotask)، 6 (ادامهٔ await).
  3. دور بعد: macrotask مربوط به setTimeout ⇐ 2.

setTimeout(fn, 0) یعنی «حداقل» صفر میلی‌ثانیه، نه «فوراً»؛ همیشه بعد از همهٔ کد همگام و همهٔ microtaskهای موجود اجرا می‌شود. حلقهٔ بی‌پایان microtask (Promiseای که مدام then جدید می‌سازد) rendering و eventها را گرسنه نگه می‌دارد، و کد همگام سنگین (مثلاً حلقهٔ ۲ ثانیه‌ای) صفحه را freeze می‌کند ⇐ کار سنگین را به Web Worker بسپارید یا تکه‌تکه کنید.

Callback ⇐ Promise ⇐ async/await

// 1) Callback — «callback hell» و مدیریت خطای پراکنده
getUser(id, (err, user) => {
  if (err) return handle(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handle(err);
    render(orders);
  });
});

// 2) Promise — شیئی برای نتیجهٔ آینده با وضعیت pending → fulfilled | rejected (فقط یک‌بار settle)
getUser(id)
  .then(user => getOrders(user.id))   // زنجیره‌سازی صاف
  .then(render)
  .catch(handle)                      // یک نقطهٔ مدیریت خطا
  .finally(hideSpinner);

// 3) async/await — sugar روی Promise با ظاهر همگام
async function showOrders(id) {
  try {
    const user = await getUser(id);
    const orders = await getOrders(user.id);
    render(orders);
  } catch (err) {
    handle(err);
  } finally {
    hideSpinner();
  }
}

fetch API

async function createOrder(payload) {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), 8000);

  try {
    const res = await fetch('/api/v1/orders', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json',
        'X-XSRF-TOKEN': getCookie('XSRF-TOKEN'),   // برای Sanctum SPA
      },
      credentials: 'include',      // ارسال cookie در درخواست cross-origin
      body: JSON.stringify(payload),
      signal: controller.signal,
    });

    if (!res.ok) {                 // ⚠ fetch برای 4xx/5xx reject نمی‌شود!
      const problem = await res.json().catch(() => ({}));
      throw new Error(problem.title ?? `HTTP ${res.status}`);
    }
    return await res.json();
  } finally {
    clearTimeout(timeout);
  }
}

fetch فقط در خطای شبکه (یا abort) reject می‌شود؛ پاسخ 404 یا 500 یک Promise موفق با res.ok === false است و باید دستی بررسی شود. بدنه فقط یک‌بار قابل خواندن است (res.json()، res.text()). پیش‌فرض credentials برابر same-origin است.

Reflow و Repaint

  • Reflow (layout): محاسبهٔ دوبارهٔ هندسه؛ با تغییر width، height، margin، font-size، افزودن/حذف عنصر، تغییر اندازهٔ پنجره. پرهزینه، چون ممکن است به فرزندان و همسایه‌ها سرایت کند.
  • Repaint: رسم دوبارهٔ پیکسل‌ها بدون تغییر هندسه؛ مثلاً color، background، visibility.
  • Composite-only: transform و opacity معمولاً فقط در مرحلهٔ composite (روی GPU) اعمال می‌شوند ⇐ بهترین انتخاب برای انیمیشن.
  • Layout thrashing: خواندن و نوشتن متناوب مقادیر layout در حلقه (مثلاً خواندن offsetHeight بعد از تغییر style) مرورگر را به reflow همگام اجباری وادار می‌کند. راه‌حل: اول همهٔ خواندن‌ها، بعد همهٔ نوشتن‌ها (batch)، یا requestAnimationFrame.
// ✗ thrashing: هر دور یک reflow
boxes.forEach(b => { b.style.width = (b.offsetWidth + 10) + 'px'; });
// ✓ batch
const widths = boxes.map(b => b.offsetWidth);                  // همهٔ خواندن‌ها
boxes.forEach((b, i) => { b.style.width = (widths[i] + 10) + 'px'; }); // همهٔ نوشتن‌ها

XSS (Cross-Site Scripting)

XSS یعنی مهاجم بتواند اسکریپت دلخواه خود را در صفحه‌ای که کاربر دیگری می‌بیند اجرا کند؛ در نتیجه به هر چیزی که JS آن صفحه دسترسی دارد (DOM، localStorage، درخواست با cookie کاربر) دست پیدا می‌کند.

  • Stored: payload در دیتابیس ذخیره می‌شود (کامنت، نام کاربری) و به همه نمایش داده می‌شود — خطرناک‌ترین.
  • Reflected: payload در URL است و سرور آن را بدون escape در پاسخ برمی‌گرداند (?q=<script>...).
  • DOM-based: کد سمت client داده را از منبعی مثل location.hash مستقیماً در sink خطرناک (innerHTML، eval) می‌ریزد؛ ممکن است اصلاً به سرور نرسد.
{{-- Blade: escape خودکار با htmlspecialchars ⇒ امن --}}
<p>{{ $comment->body }}</p>

{{-- ✗ بدون escape: فقط برای HTML کاملاً مورد اعتماد یا sanitize شده --}}
<p>{!! $comment->body !!}</p>

{{-- ✓ انتقال داده به JS --}}
<script> const user = @json($user->only('id', 'name')); </script>

دفاع‌ها:

  1. Output encoding متناسب با context (HTML body، attribute، URL، JS) — اصلی‌ترین دفاع؛ موتورهای قالب مثل Blade و فریم‌ورک‌هایی مثل React/Vue به‌طور پیش‌فرض escape می‌کنند.
  2. در JS از textContent به‌جای innerHTML استفاده کنید؛ اگر HTML کاربر لازم است، با کتابخانهٔ sanitizer معتبر (مثل DOMPurify یا HTML Purifier در سرور) پاک‌سازی کنید.
  3. Content-Security-Policy (مثلاً script-src 'self' با nonce و بدون unsafe-inline) به‌عنوان لایهٔ دفاعی دوم.
  4. cookie session با HttpOnly تا سرقت آن دشوار شود.
  5. اعتبارسنجی ورودی (مثلاً فقط URLهای https: در href؛ جلوگیری از javascript:).

تفاوت XSS و CSRF: در XSS کد مهاجم درون سایت قربانی اجرا می‌شود و می‌تواند همه‌چیز را بخواند؛ در CSRF سایت مهاجم مرورگر کاربر را وادار می‌کند درخواستی (با cookie کاربر) به سایت قربانی بفرستد ولی پاسخ را نمی‌تواند بخواند. CSRF token در برابر XSS بی‌اثر است، چون اسکریپت مهاجم می‌تواند token را از صفحه بخواند.

  • Request line: متد، request-target (مسیر و query) و نسخه: GET /products?page=2 HTTP/1.1
  • هدرها: زوج‌های نام/مقدار مثل Host (در 1.1 اجباری)، Accept، Content-Type، Authorization، Cookie؛ سپس یک خط خالی.
  • بدنه (اختیاری): برای POST/PUT/PATCH، با قالبی که Content-Type مشخص می‌کند (JSON، form-urlencoded، multipart).

پاسخ: status line (HTTP/1.1 200 OK)، هدرها (Content-Type، Set-Cookie، Cache-Control، Location) و بدنه.

Stateless: هر درخواست مستقل است و پروتکل هیچ حافظه‌ای از درخواست‌های قبلی ندارد؛ سرور به‌طور ذاتی نمی‌داند دو درخواست از یک کاربرند. این ویژگی scale افقی و سادگی را ممکن می‌کند.

تشخیص کاربر: state را در لایهٔ application با اطلاعاتی که هر درخواست حمل می‌کند بازسازی می‌کنیم:

  • Session + cookie: پس از login، سرور یک session id تصادفی در store (فایل، دیتابیس، Redis) می‌سازد و با Set-Cookie (با HttpOnly، Secure، SameSite) به مرورگر می‌دهد؛ مرورگر آن را در هر درخواست برمی‌گرداند و سرور با lookup کاربر را پیدا می‌کند.
  • Token: client توکن (opaque یا JWT) را در هدر Authorization: Bearer می‌فرستد.

در هر دو حالت، خود HTTP stateless می‌ماند؛ «state» در store سرور یا در توکن حمل می‌شود.

attributeهای HttpOnly، Secure، SameSite، Domain، Path و Max-Age در cookie را توضیح دهید. یک cookie نشست امن را چگونه تنظیم می‌کنید و هر attribute در برابر چه حمله‌ای محافظت می‌کند؟
  • HttpOnly: cookie از طریق document.cookie قابل خواندن نیست ⇐ اگر XSS رخ دهد، مهاجم نمی‌تواند session id را بدزدد و جای دیگری استفاده کند (هرچند همچنان می‌تواند در همان صفحه از طرف کاربر درخواست بزند؛ پس XSS را باید جداگانه رفع کرد).
  • Secure: فقط روی HTTPS ارسال می‌شود ⇐ محافظت در برابر شنود در شبکه (Wi-Fi عمومی، MITM).
  • SameSite: کنترل ارسال در درخواست‌های cross-site ⇐ دفاع در برابر CSRF. Strict هیچ‌وقت؛ Lax فقط در navigation سطح بالا با متد امن (کلیک روی لینک)؛ None همیشه (نیازمند Secure؛ برای embed یا SSO). Chromium در نبود این attribute رفتار Lax را پیش‌فرض می‌گیرد.
  • Domain: اگر تنظیم نشود cookie فقط برای همان host است (امن‌تر)؛ اگر تنظیم شود زیردامنه‌ها هم آن را دریافت می‌کنند و زیردامنهٔ آلوده می‌تواند آن را بخواند یا بازنویسی کند.
  • Path: محدودیت ارسال به مسیرهای مشخص؛ مرز امنیتی قوی نیست.
  • Max-Age/Expires: عمر cookie؛ بدون آن‌ها session cookie است. عمر کوتاه پنجرهٔ سوءاستفاده را کم می‌کند.

تنظیم پیشنهادی:

Set-Cookie: __Host-session=<random-256bit>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=7200

پیشوند __Host- تضمین می‌کند cookie بدون Domain، با Secure و Path=/ تنظیم شده است. علاوه بر این: session id تصادفی و غیرقابل‌حدس، regenerate پس از login (ضد session fixation)، invalidate در logout، و CSRF token برای درخواست‌های تغییردهنده. در Laravel این تنظیمات در config/session.php (secure، http_only، same_site، lifetime) قرار دارند.

CORS و درخواست preflight را توضیح دهید. چرا یک درخواست fetch با Content-Type: application/json قبل از ارسال، یک درخواست OPTIONS می‌فرستد؟

Same-Origin Policy: مرورگر اجازه نمی‌دهد اسکریپت یک origin (scheme + host + port) پاسخ درخواست به origin دیگری را بخواند. این سیاست جلوی آن را می‌گیرد که سایت مخرب با cookieهای کاربر، داده‌های او را از سایت‌های دیگر بخواند.

CORS: مکانیزمی که سرور مقصد با هدرهای پاسخ (Access-Control-Allow-Origin، -Methods، -Headers، -Credentials) اعلام کند کدام originها مجاز به خواندن پاسخ‌اند.

Simple request (بدون preflight): متد GET/HEAD/POST، فقط هدرهای مجاز ساده، و Content-Type یکی از text/plain، application/x-www-form-urlencoded یا multipart/form-data. این‌ها همان درخواست‌هایی هستند که یک فرم HTML معمولی هم از قبل می‌توانست بفرستد، پس CORS آن‌ها را ارسال می‌کند و فقط خواندن پاسخ را کنترل می‌کند.

Preflight: اگر درخواست از این محدوده خارج شود — مثل application/json، هدر Authorization یا متد PUT/DELETE — مرورگر نمی‌تواند فرض کند سرور قدیمی برای چنین درخواست cross-originی آماده است. پس ابتدا OPTIONS با Origin، Access-Control-Request-Method و Access-Control-Request-Headers می‌فرستد؛ فقط اگر سرور با هدرهای مجوز پاسخ دهد، درخواست اصلی ارسال می‌شود. Access-Control-Max-Age نتیجهٔ preflight را برای مدتی cache می‌کند.

نکات مهم:

  • CORS را مرورگر اجرا می‌کند؛ curl و Postman تحت تأثیر نیستند — پس CORS جایگزین احراز هویت نیست.
  • برای ارسال cookie، client باید credentials: 'include' بگذارد و سرور origin دقیق (نه *) و Allow-Credentials: true برگرداند.
  • middleware احراز هویت نباید preflight را 401 کند. در Laravel، HandleCors با config/cors.php این را مدیریت می‌کند.
HTML معنایی (Semantic HTML) چیست و چه مزایایی دارد؟ ساختار معنایی یک صفحهٔ وبلاگ را بنویسید.

تعریف: استفاده از عناصر HTML بر اساس معنای محتوا نه ظاهر آن: <nav> برای ناوبری، <article> برای محتوای مستقل، <button> برای عمل، به‌جای استفاده از <div> و <span> برای همه‌چیز.

مزایا:

  • دسترس‌پذیری: screen readerها landmarkها (main، nav) و headingها را برای پرش سریع استفاده می‌کنند؛ عناصر بومی فوکوس و کیبورد را رایگان دارند.
  • SEO: موتور جستجو محتوای اصلی، عنوان‌ها و ساختار را بهتر می‌فهمد.
  • نگه‌داری و خوانایی: ساختار کد خودتوصیف است.
  • رفتار پیش‌فرض: مثلاً button در form، ارسال را انجام می‌دهد و با Enter/Space فعال می‌شود.

نکات: یک h1 و سلسله‌مراتب heading بدون پرش، alt برای تصاویر، lang و dir روی html، و <title> و meta description یکتا.

اعتبارسنجی فرم در سمت client (HTML5) چگونه انجام می‌شود و چرا کافی نیست؟ دسترس‌پذیری یک فرم را چگونه تضمین می‌کنید؟

Validation داخلی HTML: با type مناسب (email، url، number، tel) و attributeهای required، min/max، minlength/maxlength، pattern و step. مرورگر پیش از submit بررسی و پیام خطا نمایش می‌دهد. در CSS با :invalid/:user-invalid و در JS با Constraint Validation API (checkValidity()، setCustomValidity()، validity) قابل کنترل است.

چرا کافی نیست؟ کد client کاملاً تحت کنترل کاربر است: می‌توان attributeها را در DevTools حذف کرد، novalidate گذاشت یا درخواست را مستقیماً با curl فرستاد. پس validation سمت client فقط برای تجربهٔ کاربری (بازخورد سریع) است و اعتبارسنجی واقعی و امنیتی باید در سرور انجام شود (Form Request در Laravel، با پاسخ 422 یا بازگشت با خطاها).

دسترس‌پذیری فرم:

  • هر فیلد یک <label for="id"> مرتبط داشته باشد؛ placeholder جایگزین label نیست.
  • گروه‌های radio/checkbox در <fieldset> با <legend>.
  • پیام راهنما و خطا با aria-describedby به فیلد وصل شود؛ فیلد نامعتبر aria-invalid="true"؛ خلاصهٔ خطاها در ناحیهٔ role="alert" یا aria-live اعلام شود و فوکوس به اولین فیلد نامعتبر برود.
  • خطا فقط با رنگ قرمز نشان داده نشود؛ متن صریح داشته باشد.
  • همهٔ کنترل‌ها با کیبورد قابل دسترسی و فوکوس قابل‌مشاهده باشد؛ از عناصر بومی (button، select) به‌جای div سفارشی استفاده شود.
  • autocomplete مناسب و type درست برای کیبورد موبایل.
Cascade و Specificity در CSS را توضیح دهید. Specificity هر یک از selectorهای #nav .item a، .menu li.active a:hover و div p را محاسبه کنید و بگویید کدام برنده است.

Cascade: الگوریتمی که وقتی چند declaration برای یک property روی یک عنصر رقابت می‌کنند، برنده را تعیین می‌کند. معیارها به ترتیب: (۱) origin و importance (استایل مرورگر، کاربر، نویسنده؛ و !important که ترتیب را برعکس می‌کند)، (۲) cascade layers (@layer)، (۳) specificity، (۴) ترتیب ظاهر شدن (آخری برنده). استایل inline قوی‌تر از هر selector است.

Specificity: سه‌تایی (A, B, C): A = تعداد ID، B = تعداد class/attribute/pseudo-class، C = تعداد type/pseudo-element. مقایسه ستون‌به‌ستون از چپ است. * و combinatorها و :where() صفرند؛ :is()/:not()/:has() بیشترین آرگومانشان را می‌گیرند.

  • #nav .item a ⇐ یک ID، یک class، یک type ⇐ (1,1,1)
  • .menu li.active a:hover ⇐ classها: .menu، .active، pseudo-class :hover = ۳؛ typeها: li، a = ۲ ⇐ (0,3,2)
  • div p ⇐ (0,0,2)

برنده: #nav .item a، چون در ستون اول (ID) یک دارد و بقیه صفر؛ تعداد classها اهمیتی ندارد. (البته به شرطی که هر سه بر یک عنصر منطبق باشند و در یک origin/layer قرار داشته باشند.)

توصیهٔ عملی: specificity بالا باعث «جنگ specificity» و استفادهٔ بیش از حد از !important می‌شود. از classهای تک‌سطحی (BEM یا utility)، :where() برای استایل‌های پایه و @layer برای مدیریت اولویت کتابخانه‌ها استفاده کنید. همچنین inheritance را با cascade اشتباه نگیرید: مقدار ارث‌رسیده هیچ specificityای ندارد و هر قانون مستقیمی بر آن غلبه می‌کند.

Box model را توضیح دهید و تفاوت content-box و border-box را با محاسبه نشان دهید. تفاوت position‌های relative، absolute، fixed و sticky چیست؟

Box model: هر عنصر یک جعبه است متشکل از content، padding (فاصلهٔ داخلی، با پس‌زمینهٔ عنصر)، border و margin (فاصلهٔ بیرونی، شفاف). marginهای عمودی بلوک‌های مجاور collapse می‌شوند (بزرگ‌ترین می‌ماند).

مثال: width: 300px; padding: 20px; border: 5px solid;

  • content-box (پیش‌فرض): width فقط content ⇐ عرض نهایی = 300 + 2×20 + 2×5 = 350px.
  • border-box: width شامل padding و border ⇐ عرض نهایی = 300px و content = 300 − 40 − 10 = 250px.

به همین دلیل معمولاً *, *::before, *::after { box-sizing: border-box; } سراسری تنظیم می‌شود: ستون‌های ۵۰٪ با padding از والد بیرون نمی‌زنند.

position:

  • relative: در جریان سند می‌ماند و فضای اصلی‌اش حفظ می‌شود؛ top/left آن را نسبت به جای عادی‌اش جابه‌جا می‌کند. کاربرد اصلی: مرجع شدن برای فرزندان absolute.
  • absolute: از جریان خارج می‌شود (فضا نمی‌گیرد) و نسبت به نزدیک‌ترین جد positioned (غیر static) قرار می‌گیرد. کاربرد: badge، dropdown.
  • fixed: از جریان خارج و نسبت به viewport ثابت است و با scroll حرکت نمی‌کند (مگر جدی transform داشته باشد که containing block جدید می‌سازد). کاربرد: هدر ثابت، modal.
  • sticky: مثل relative رفتار می‌کند تا هنگام scroll به آستانه (مثلاً top: 0) برسد، سپس درون scroll container والدش می‌چسبد. کاربرد: هدر جدول. اگر والد overflow: hidden داشته باشد یا ارتفاع کافی نداشته باشد، کار نمی‌کند.
Flexbox و Grid را مقایسه کنید. هر کدام برای چه سناریویی مناسب‌ترند؟ یک گالری محصول واکنش‌گرا را بدون media query پیاده کنید.

Flexbox: سیستم layout یک‌بعدی: آیتم‌ها را در یک محور (ردیف یا ستون) می‌چیند و فضای خالی را بین آن‌ها توزیع می‌کند. Content-first است: اندازهٔ آیتم‌ها از محتوا و flex-grow/shrink/basis تعیین می‌شود. ویژگی‌های کلیدی: flex-direction، justify-content (محور اصلی)، align-items (محور عمود)، flex-wrap، gap.

Grid: سیستم layout دوبعدی: ردیف‌ها و ستون‌ها هم‌زمان کنترل می‌شوند. Layout-first است: ابتدا شبکه (grid-template-columns/rows/areas) تعریف و آیتم‌ها در آن جای‌گذاری می‌شوند. واحد fr، تابع‌های repeat و minmax.

سناریوها:

  • Flex: نوار ناوبری، ردیف دکمه‌ها، وسط‌چین کردن، کارت با footer چسبیده به پایین، چیدمان آیتم‌ها با اندازهٔ نامشخص.
  • Grid: اسکلت کل صفحه (header/sidebar/main/footer)، داشبورد، گالری با ستون‌های هم‌تراز، فرم‌های چندستونه.
  • ترکیب: Grid برای ماکرو-layout و Flex برای اجزای داخلی.

گالری بدون media query:

.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(220px, 1fr));
  gap: 1rem;
}
.gallery img { width: 100%; height: auto; aspect-ratio: 4 / 3; object-fit: cover; }

مرورگر هر تعداد ستون با حداقل عرض ۲۲۰px که جا شود می‌سازد و فضای باقی‌مانده را با 1fr بین آن‌ها تقسیم می‌کند؛ در موبایل یک ستون و در دسکتاپ چند ستون. با auto-fit به‌جای auto-fill، وقتی آیتم‌ها کم‌اند، ستون‌های خالی حذف و آیتم‌ها کش می‌آیند.

تفاوت واحدهای rem، em، %، vh و px چیست؟ رویکرد Mobile-first در طراحی واکنش‌گرا را توضیح دهید.
  • px: واحد مطلق CSS؛ مناسب border و جزئیات دقیق. برای فونت توصیه نمی‌شود چون تنظیم اندازهٔ فونت کاربر در مرورگر را نادیده می‌گیرد.
  • rem: نسبت به font-size عنصر ریشه (html؛ معمولاً ۱۶px). یکنواخت و پیش‌بینی‌پذیر، با تنظیمات دسترس‌پذیری کاربر مقیاس می‌گیرد ⇐ انتخاب اصلی برای فونت و فاصله‌ها.
  • em: نسبت به font-size خود عنصر (و برای خود font-size نسبت به والد). در ساختار تودرتو ضرب می‌شود (۱٫۲em داخل ۱٫۲em = ۱٫۴۴ برابر). مناسب برای padding دکمه که باید با اندازهٔ متن همان دکمه متناسب باشد.
  • %: نسبت به containing block (برای width عرض والد؛ نکته: padding و margin درصدی، حتی عمودی، نسبت به عرض والدند).
  • vw/vh: ۱٪ عرض/ارتفاع viewport. در موبایل 100vh به دلیل نوار آدرس پویا ممکن است بیشتر از فضای قابل‌مشاهده باشد ⇐ 100dvh.

Mobile-first: استایل پایه برای کوچک‌ترین صفحه نوشته می‌شود و سپس با @media (min-width: ...) برای صفحات بزرگ‌تر قابلیت‌ها و ستون‌ها اضافه می‌شوند.

.layout { display: grid; gap: 1rem; }                       /* موبایل: یک ستون */
@media (min-width: 768px) { .layout { grid-template-columns: 240px 1fr; } } /* تبلت به بالا */

چرا؟ دستگاه‌های ضعیف‌تر CSS ساده‌تر را پردازش می‌کنند؛ تیم مجبور می‌شود محتوای اصلی را اولویت‌بندی کند؛ افزودن پیچیدگی آسان‌تر از حذف آن است. پیش‌نیاز: <meta name="viewport" content="width=device-width, initial-scale=1">، layout سیال با flex/grid و تصاویر با max-width: 100% و srcset. امروز container query هم امکان واکنش‌گرایی بر اساس اندازهٔ والد را می‌دهد.

تفاوت == و === در JavaScript چیست؟ خروجی عبارات زیر را با دلیل بنویسید: 0 == ''، null == undefined، null == 0، NaN === NaN، '5' + 3، '5' - 3، [] + {}.

تعریف: === (strict equality) بدون تبدیل نوع مقایسه می‌کند: اگر نوع‌ها متفاوت باشند false. == (loose equality) پیش از مقایسه با قواعد Abstract Equality تبدیل نوع ضمنی (coercion) انجام می‌دهد؛ معمولاً هر دو طرف به عدد تبدیل می‌شوند، و objectها به primitive. objectها در هر دو حالت با reference مقایسه می‌شوند.

  • 0 == '' ⇐ true: رشتهٔ خالی به عدد 0 تبدیل می‌شود.
  • null == undefined ⇐ true: قاعدهٔ ویژه؛ این دو فقط با هم (و با خودشان) loose-equal هستند.
  • null == 0 ⇐ false: در ==، null به عدد تبدیل نمی‌شود (هرچند null >= 0 true است چون مقایسهٔ رابطه‌ای آن را به 0 تبدیل می‌کند — نمونهٔ ناسازگاری).
  • NaN === NaN ⇐ false: طبق IEEE 754، NaN با هیچ چیز حتی خودش برابر نیست؛ از Number.isNaN() یا Object.is() استفاده کنید.
  • '5' + 3 ⇐ '53': عملگر + اگر یک طرف رشته باشد، الحاق رشته انجام می‌دهد.
  • '5' - 3 ⇐ 2: عملگر - فقط عددی است و رشته را به عدد تبدیل می‌کند.
  • [] + {} ⇐ '[object Object]': هر دو به primitive (رشته) تبدیل می‌شوند: '' و '[object Object]'.

نتیجه‌گیری: == حتی transitive نیست (0 == '' و 0 == '0' ولی '' != '0')، پس همیشه از === استفاده کنید؛ تنها استثنای پذیرفته‌شده x == null برای بررسی هم‌زمان null و undefined است. برای مقدار پیش‌فرض از ?? استفاده کنید تا مقادیر falsy معتبر مثل 0 حذف نشوند. TypeScript و ESLint (eqeqeq) این خطاها را زودتر می‌گیرند.

تفاوت var، let و const را از نظر scope، hoisting و TDZ توضیح دهید. خروجی کد زیر چیست و چرا؟ for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));
  • Scope: var function-scoped است (block مثل if/for را نمی‌شناسد)؛ let و const block-scoped.
  • Hoisting: هر سه hoist می‌شوند، یعنی هنگام ورود به scope ثبت می‌شوند؛ اما var با undefined مقداردهی اولیه می‌شود، در حالی که let/const تا رسیدن به خط تعریف مقداردهی نشده می‌مانند.
  • TDZ (Temporal Dead Zone): فاصلهٔ بین شروع block و خط تعریف let/const/class که دسترسی به متغیر در آن ReferenceError می‌دهد. این رفتار باگ استفادهٔ زودهنگام را آشکار می‌کند، برخلاف var که بی‌صدا undefined می‌دهد.
  • دیگر تفاوت‌ها: var اجازهٔ تعریف مجدد دارد و در سطح بالای script روی window property می‌سازد؛ const انتساب مجدد را منع می‌کند ولی محتوای object/array قابل تغییر است.

خروجی کد: 3 3 3.

دلیل: با var فقط یک متغیر i برای کل حلقه وجود دارد. callbackهای setTimeout macrotask هستند و پس از اتمام کامل کد همگام اجرا می‌شوند؛ تا آن زمان حلقه تمام شده و i برابر ۳ است. هر سه closure به همان یک متغیر ارجاع دارند.

رفع:

for (let i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 0 1 2
// let در هر تکرار binding جدید می‌سازد؛ هر closure مقدار خودش را دارد

// روش قدیمی با IIFE

Closure را تعریف کنید و دو کاربرد عملی آن را با کد نشان دهید. چه خطری می‌تواند داشته باشد؟

تعریف: closure ترکیب یک تابع با محیط lexicalی است که در آن تعریف شده. به لطف lexical scope، تابع داخلی حتی پس از بازگشت تابع بیرونی، به متغیرهای آن دسترسی دارد؛ این متغیرها (نه کپی‌شان) زنده می‌مانند.

کاربرد ۱ — داده و state خصوصی (encapsulation):

function createWallet(initial) {
  let balance = initial;                 // از بیرون قابل دسترسی نیست
  return {
    deposit(x) { if (x <= 0) throw new Error('invalid'); balance += x; },
    get balance() { return balance; },
  };
}
const w = createWallet(100);
w.deposit(50);
w.balance;   // 150 — تغییر مستقیم balance ممکن نیست

کاربرد ۲ — توابع مرتبهٔ بالا (debounce، memoize، factory):

function debounce(fn, ms) {
  let timer;                                   // در closure بین فراخوانی‌ها حفظ می‌شود
  return (...args) => { clearTimeout(timer); timer = setTimeout(() => fn(...args), ms); };
}
input.addEventListener('input', debounce(e => search(e.target.value), 300));

function memoize(fn) {
  const cache = new Map();
  return (n) => cache.has(n) ? cache.get(n) : (cache.set(n, fn(n)), cache.get(n));
}

کاربردهای دیگر: callbackها و event handlerها که به متغیرهای بیرونی نیاز دارند، partial application، module pattern پیش از ESM.

خطرها:

  • Memory leak: closure کل محیطی را که ارجاع می‌دهد زنده نگه می‌دارد؛ listener یا interval پاک‌نشده که به آرایهٔ بزرگ یا عنصر DOM حذف‌شده ارجاع دارد، مانع garbage collection می‌شود. راه‌حل: removeEventListener، clearInterval، AbortController برای listenerها.
  • داده‌های کهنه (stale closure): مثل حلقه با var یا در React، closure مقدار قدیمی را نگه می‌دارد.
مقدار this در JavaScript چگونه تعیین می‌شود؟ تفاوت arrow function با تابع معمولی در این زمینه چیست؟ کد زیر چه مشکلی دارد؟ class Timer { constructor(){ this.s = 0; setInterval(function(){ this.s++; }, 1000); } }

قاعدهٔ کلی: در تابع معمولی، this هنگام فراخوانی و بر اساس نحوهٔ فراخوانی تعیین می‌شود. چهار قاعده به ترتیب اولویت:

  1. new: new Fn() ⇐ شیء تازه.
  2. Explicit: call، apply، bind ⇐ شیء داده‌شده.
  3. Implicit: obj.fn() ⇐ obj.
  4. Default: fn() ⇐ undefined در strict mode (کلاس‌ها و ماژول‌ها همیشه strict هستند)؛ در غیر این صورت global object.

همچنین در event listener با تابع معمولی، this برابر currentTarget است.

Arrow function this خودش را ندارد و آن را lexically از scope دربرگیرنده در زمان تعریف می‌گیرد؛ call/apply/bind آن را تغییر نمی‌دهند و با new قابل فراخوانی نیست. بنابراین برای callbackهای داخل متد عالی است ولی برای متد شیء (که به this شیء نیاز دارد) نامناسب.

مشکل کد: callback با function معمولی توسط setInterval به‌صورت ساده (default binding) فراخوانی می‌شود؛ پس this داخل آن نمونهٔ Timer نیست (در مرورگر window، یا undefined در strict mode). نتیجه: this.s نمونه هرگز افزایش نمی‌یابد (یا TypeError).

class Timer {
  s = 0;
  #id;
  start() {
    this.#id = setInterval(() => { this.s++; }, 1000);   // ✓ arrow: this = نمونه
    // یا: setInterval(function () { this.s++; }.bind(this), 1000);
  }
  stop() { clearInterval(this.#id); }                    // جلوگیری از نشت
}

بهبود جانبی: شروع interval در constructor و نداشتن راه توقف، نشت حافظه و منبع ایجاد می‌کند؛ متد stop اضافه شد.

Event loop در JavaScript را شرح دهید و تفاوت microtask و macrotask را بگویید. خروجی کد زیر را با توضیح مرحله‌به‌مرحله بنویسید. 
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve()
  .then(() => console.log('C'))
  .then(() => console.log('D'));
(async () => { console.log('E'); await undefined; console.log('F'); })();
setTimeout(() => Promise.resolve().then(() => console.log('G')), 0);
console.log('H');

مفاهیم: JS یک call stack و یک thread اصلی دارد. عملیات ناهمگام به محیط میزبان سپرده می‌شوند و callbackهایشان در صف قرار می‌گیرند:

  • Macrotask (task): setTimeout، setInterval، رویدادهای UI، I/O، اجرای اولیهٔ script.
  • Microtask: واکنش‌های Promise (then/catch/finally)، ادامهٔ بعد از await، queueMicrotask، MutationObserver.

الگوریتم: یک macrotask اجرا می‌شود ⇐ سپس همهٔ microtaskها تا خالی شدن صف (شامل microtaskهای تازه اضافه‌شده) ⇐ فرصت render ⇐ macrotask بعدی.

اجرای مرحله‌به‌مرحله:

  1. کد همگام: A؛ timer اول ثبت؛ then اول (C) در صف microtask؛ تابع async اجرا و E چاپ، سپس در await متوقف و ادامه‌اش (F) در صف microtask؛ timer دوم ثبت؛ H.
  2. تخلیهٔ microtaskها: C ⇐ resolve شدنش then بعدی (D) را به انتهای صف می‌افزاید؛ F؛ سپس D.
  3. macrotask اول: B.
  4. macrotask دوم: یک Promise.then در صف microtask می‌گذارد که بلافاصله پس از این task اجرا می‌شود: G.

خروجی: A E H C F D B G

پیامد عملی: setTimeout(fn, 0) «فوری» نیست؛ کد همگام طولانی UI را قفل می‌کند (long task)؛ و زنجیرهٔ بی‌پایان microtask می‌تواند rendering را گرسنه نگه دارد. کار CPU-سنگین باید به Web Worker منتقل یا تکه‌تکه شود.

سیر تکامل برنامه‌نویسی ناهمگام از callback به Promise و async/await را توضیح دهید. کد زیر چه مشکلاتی دارد و چگونه اصلاح می‌شود؟ 
async function loadDashboard(ids) {
  const user = await fetch('/api/me').then(r => r.json());
  const stats = await fetch('/api/stats').then(r => r.json());
  ids.forEach(async (id) => {
    await fetch(`/api/widgets/${id}`, { method: 'POST' });
  });
  console.log('done');
}

تکامل:

  • Callback: تابعی که پس از اتمام کار صدا زده می‌شود. مشکلات: تودرتویی (callback hell)، مدیریت خطای پراکنده، inversion of control (اعتماد به اینکه کتابخانه callback را دقیقاً یک‌بار صدا بزند).
  • Promise: شیئی نمایندهٔ نتیجهٔ آینده با وضعیت‌های pending/fulfilled/rejected که فقط یک‌بار settle می‌شود؛ زنجیره‌سازی با then، یک catch برای کل زنجیره، ترکیب با all/allSettled/race/any.
  • async/await: syntactic sugar روی Promise؛ کد ناهمگام با ظاهر همگام و مدیریت خطا با try/catch معمولی. تابع async همیشه Promise برمی‌گرداند.

مشکلات کد:

  1. user و stats مستقل‌اند ولی ترتیبی await شده‌اند ⇐ زمان کل = مجموع زمان‌ها.
  2. fetch برای 4xx/5xx reject نمی‌شود و res.ok بررسی نشده است.
  3. forEach Promise برگشتی callback را نادیده می‌گیرد ⇐ 'done' قبل از اتمام درخواست‌ها چاپ می‌شود و خطاهایشان unhandled rejection می‌شوند.
  4. هیچ مدیریت خطا یا timeoutی وجود ندارد.
async function getJson(url, init) {
  const res = await fetch(url, { ...init, signal: AbortSignal.timeout(8000) });
  if (!res.ok) throw new Error(`HTTP ${res.status} for ${url}`);
  return res.status === 204 ? null : res.json();
}

async function loadDashboard(ids) {
  try {
    const [user, stats] = await Promise.all([getJson('/api/me'), getJson('/api/stats')]);
    const results = await Promise.allSettled(
      ids.map(id => getJson(`/api/widgets/${id}`, { method: 'POST' }))
    );
    const failed = results.filter(r => r.status === 'rejected');
    if (failed.length) console.warn(`${failed.length} widgets failed`);

Event bubbling، capturing و event delegation را توضیح دهید. چرا delegation برای فهرستی با هزاران ردیف که پویا اضافه می‌شوند مناسب است؟

انتشار رویداد سه فاز دارد:

  1. Capturing: از window به سمت پایین تا والد هدف.
  2. Target: روی خود عنصر هدف.
  3. Bubbling: از هدف به سمت بالا تا window.

listenerها به‌طور پیش‌فرض در فاز bubbling اجرا می‌شوند؛ با addEventListener(type, fn, { capture: true }) در فاز capturing. event.target عنصر اصلی رویداد و event.currentTarget عنصری است که listener روی آن ثبت شده. stopPropagation() انتشار را متوقف و preventDefault() رفتار پیش‌فرض را لغو می‌کند (این دو مستقل‌اند).

Event delegation: به‌جای ثبت listener روی تک‌تک فرزندان، یک listener روی والد مشترک ثبت می‌شود و به لطف bubbling، با بررسی event.target تشخیص داده می‌شود کدام فرزند هدف بوده است.

table.addEventListener('click', (e) => {
  const btn = e.target.closest('[data-action]');
  if (!btn || !table.contains(btn)) return;
  const id = btn.closest('tr').dataset.id;
  if (btn.dataset.action === 'delete') removeRow(id);
  if (btn.dataset.action === 'edit') openEditor(id);
});

چرا برای فهرست بزرگ و پویا؟

  • حافظه و کارایی: یک listener به‌جای هزاران؛ زمان راه‌اندازی کمتر.
  • عناصر پویا: ردیف‌هایی که بعداً (مثلاً با AJAX یا infinite scroll) اضافه می‌شوند، بدون ثبت listener جدید کار می‌کنند.
  • عدم نشت: با حذف ردیف‌ها نیازی به پاک کردن listenerهایشان نیست.

محدودیت‌ها: رویدادهایی که bubble نمی‌کنند (focus، blur ⇐ از focusin/focusout استفاده کنید)؛ استفاده از closest() چون target ممکن است فرزند داخلی دکمه (مثلاً آیکون) باشد؛ و اگر کدی در مسیر stopPropagation کند، رویداد به والد نمی‌رسد.

Critical rendering path مرورگر را شرح دهید. reflow و repaint چه تفاوتی دارند و تفاوت async و defer در تگ script چیست؟ برای بهبود سرعت بارگذاری اولیهٔ یک صفحه چه می‌کنید؟

مراحل:

  1. parse HTML ⇐ DOM؛ parse CSS ⇐ CSSOM.
  2. ترکیب آن‌ها ⇐ Render tree (فقط عناصر قابل‌مشاهده؛ display:none حذف می‌شود).
  3. Layout (reflow): محاسبهٔ اندازه و موقعیت هر جعبه.
  4. Paint: رسم پیکسل‌ها (متن، رنگ، تصویر، سایه) در layerها.
  5. Composite: ترکیب layerها (اغلب روی GPU) و نمایش.

CSS render-blocking است و script معمولی parser-blocking.

Reflow در برابر repaint: reflow هندسه را دوباره محاسبه می‌کند (تغییر اندازه، فونت، افزودن عنصر، خواندن offsetHeight پس از نوشتن) و معمولاً repaint هم به دنبال دارد — پرهزینه‌تر. repaint فقط ظاهر را بدون تغییر هندسه دوباره رسم می‌کند (رنگ، background). transform و opacity اغلب فقط composite لازم دارند ⇐ مناسب انیمیشن. از layout thrashing (خواندن/نوشتن متناوب) با batch کردن پرهیز کنید.

async در برابر defer: هر دو اسکریپت را موازی با parse دانلود می‌کنند. async به‌محض دانلود اجرا می‌شود (parse را قطع می‌کند و ترتیب تضمین نمی‌شود) ⇐ اسکریپت‌های مستقل مثل analytics. defer پس از اتمام parse و قبل از DOMContentLoaded، به ترتیب نوشته‌شده اجرا می‌شود ⇐ اسکریپت‌های اصلی اپ. type="module" به‌طور پیش‌فرض مثل defer است.

بهبود بارگذاری اولیه:

  • CSS حیاتی کوچک و inline، بقیه با بارگذاری غیر مسدودکننده؛ JS با defer و code splitting.
  • فشرده‌سازی (Brotli)، minify، cache طولانی با نام hash‌دار (Vite)، CDN، HTTP/2+.
  • تصاویر بهینه (WebP/AVIF، srcset، loading="lazy" برای پایین صفحه، ابعاد مشخص برای جلوگیری از CLS)، preload برای تصویر LCP و فونت.
  • کاهش TTFB در سرور: cache صفحه/داده، OPcache، کوئری بهینه.
  • اندازه‌گیری با Lighthouse و Core Web Vitals (LCP، INP، CLS).
localStorage، sessionStorage، cookie و IndexedDB را مقایسه کنید. یک سناریو: تیم frontend می‌خواهد توکن احراز هویت را در localStorage ذخیره کند؛ نظر شما چیست و XSS چگونه در این تصمیم نقش دارد؟

مقایسه:

  • Cookie: حدود ۴KB؛ با هر درخواست منطبق خودکار به سرور ارسال می‌شود (سربار شبکه)؛ قابل تنظیم با HttpOnly/Secure/SameSite/Expires؛ تنها گزینه‌ای که سرور مستقیماً می‌خواند.
  • localStorage: چند مگابایت برای هر origin، دائمی، API همگام و فقط string، مشترک بین همهٔ tabهای همان origin؛ به سرور ارسال نمی‌شود؛ برای همهٔ اسکریپت‌های صفحه قابل خواندن است.
  • sessionStorage: مثل localStorage ولی محدود به همان tab و تا بسته شدن آن.
  • IndexedDB: پایگاه‌دادهٔ کلید-مقدار تراکنشی، ناهمگام، با ظرفیت بالا و پشتیبانی از object و ایندکس ⇐ داده‌های آفلاین و حجیم (PWA).

تحلیل سناریو: هر داده‌ای در localStorage با XSS قابل سرقت است: یک کتابخانهٔ ثالث آلوده یا یک نقطهٔ escape‌نشده کافی است تا localStorage.getItem('token') به سرور مهاجم ارسال شود و مهاجم تا انقضای توکن، از هر جایی به‌جای کاربر عمل کند.

پیشنهاد:

  • برای SPA first-party روی همان دامنهٔ اصلی: احراز هویت مبتنی بر cookie با HttpOnly; Secure; SameSite=Lax (مثلاً Laravel Sanctum SPA mode) + CSRF token. JS اصلاً به توکن دسترسی ندارد.
  • اگر توکن Bearer ضروری است (cross-domain): access token کوتاه‌عمر در حافظه (متغیر JS) و refresh token در cookie HttpOnly با rotation.
  • در هر حال XSS را ریشه‌ای رفع کنید: escape خروجی (Blade {{ }}، عدم استفاده از {!! !!} و innerHTML با داده کاربر)، CSP سخت‌گیرانه، و بررسی وابستگی‌ها. HttpOnly فقط سرقت توکن را دشوار می‌کند؛ XSS همچنان می‌تواند در همان صفحه از طرف کاربر درخواست بفرستد.
  • trade-off: cookie نیازمند دفاع CSRF است؛ localStorage CSRF ندارد ولی در برابر XSS آسیب‌پذیرتر است. با SameSite و CSRF token، ریسک CSRF به‌خوبی مهار می‌شود، پس معمولاً cookie HttpOnly انتخاب امن‌تری است.

خلاصه برای مرور سریع

HTTP

  • Request: method + target + version، هدرها، خط خالی، body. Response: status line، هدرها، body.
  • Stateless ⇒ state با cookie/session یا token.
  • Form: urlencoded (پیش‌فرض)، multipart (فایل)؛ فقط GET/POST ⇒ @method در Laravel.
  • هدرهای امنیتی: HSTS، CSP، nosniff، frame-ancestors، Referrer-Policy.

Cookie

  • HttpOnly ضد سرقت با XSS · Secure فقط HTTPS · SameSite ضد CSRF (Strict/Lax/None+Secure).
  • بدون Domain = host-only (امن‌تر) · بدون Max-Age/Expires = session cookie.
  • __Host-: Secure + Path=/ + بدون Domain.
  • Session: فقط id در cookie؛ regenerate بعد از login؛ store مشترک (Redis).

Cache و CORS

  • no-cache = revalidate؛ no-store = هرگز؛ immutable برای فایل‌های hash‌دار.
  • ETag + If-None-Match ⇒ 304.
  • Origin = scheme+host+port. CORS را مرورگر اعمال می‌کند.
  • Preflight OPTIONS برای JSON، Authorization، PUT/DELETE.
  • * با credentials ممنوع.

HTML

  • <!DOCTYPE html>، lang، charset، viewport.
  • Semantic: header، nav، main، article، section، aside، footer، figure، time، button در برابر a.
  • SEO: title، description، canonical، robots، OG، JSON-LD، headingها.
  • فرم: label for، fieldset/legend، type مناسب، required/pattern/min؛ disabled ارسال نمی‌شود.
  • Validation client = UX؛ server = امنیت.
  • ARIA: اول HTML بومی؛ aria-label، describedby، expanded، live، hidden؛ alt، کیبورد، کنتراست.

CSS

  • Cascade: origin/importance ← layer ← specificity ← ترتیب.
  • Specificity (ID, class/attr/pseudo-class, type/pseudo-element)؛ :where = 0؛ :is/:not/:has = max آرگومان.
  • ارثی: color، font، line-height، text-align؛ غیرارثی: margin، padding، border، width.
  • border-box: width شامل padding+border.
  • position: relative (مرجع)، absolute (جد positioned)، fixed (viewport)، sticky (آستانه).
  • z-index در stacking context؛ transform/opacity context می‌سازند.
  • Flex = ۱بعدی (justify روی main، align روی cross)؛ Grid = ۲بعدی (fr، repeat، minmax، areas).
  • repeat(auto-fill, minmax(200px, 1fr)) = گالری بدون media query.
  • rem (ریشه)، em (خود/والد)، % (والد)، vw/vh/dvh، ch.
  • Mobile-first: پایه + min-width. Container queries.
  • Custom properties: runtime، ارثی، theming.

JS

  • ۷ primitive + object؛ typeof null === 'object'.
  • === همیشه؛ x == null استثنا؛ ?? در برابر ||.
  • Falsy: false، 0، -0، 0n، ''، null، undefined، NaN.
  • var: function scope، hoist با undefined. let/const: block scope، TDZ.
  • Closure = تابع + محیط lexical؛ state خصوصی، debounce؛ خطر leak.
  • this: new > call/apply/bind > obj.fn() > default (undefined در strict). Arrow: lexical this.
  • class = sugar روی prototype chain؛ #private.

Async

  • Sync ⇒ همهٔ microtaskها ⇒ render ⇒ یک macrotask ⇒ …
  • Microtask: then، await، queueMicrotask. Macrotask: setTimeout، events، I/O.
  • Promise.all (اولین شکست)، allSettled (همه)، race (اولین settle)، any (اولین موفق).
  • مستقل‌ها را موازی (Promise.all)؛ await در forEach کار نمی‌کند.
  • fetch روی 4xx/5xx reject نمی‌شود ⇒ res.ok؛ AbortController برای timeout.

DOM

  • capturing ⇒ target ⇒ bubbling؛ target در برابر currentTarget.
  • stopPropagation ≠ preventDefault.
  • Delegation: یک listener روی والد + closest().
  • textContent امن؛ innerHTML با داده کاربر = XSS.
  • ESM: static، tree shaking، dynamic import، type="module" = defer.

مرورگر

  • DOM + CSSOM ⇒ Render tree ⇒ Layout ⇒ Paint ⇒ Composite.
  • CSS render-blocking؛ script parser-blocking؛ async (مستقل، بی‌ترتیب)، defer (بعد از parse، با ترتیب).
  • Reflow (هندسه) > Repaint (ظاهر) > Composite (transform/opacity).
  • Storage: cookie ~4KB به سرور می‌رود؛ local دائمی؛ session تا بستن tab؛ IndexedDB حجیم و async.
  • Web Vitals: LCP، INP، CLS.
  • XSS: stored/reflected/DOM؛ دفاع: escape متناسب با context، textContent، sanitize، CSP، HttpOnly.
  • XSS ≠ CSRF؛ CSRF token در برابر XSS بی‌اثر است.
