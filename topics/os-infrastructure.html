OS & Infrastructure

مفاهیم پایه‌ی سیستم‌عامل (فرایند، thread، حافظه، فایل‌سیستم، هم‌روندی) و زیرساخت عملی یک بک‌اند Laravel روی لینوکس: دسترسی‌ها، دستورات ضروری، systemd و Supervisor، شبکه و SSH، Nginx و PHP-FPM، TLS، کانتینر و ابر، IaC، دسترس‌پذیری بالا، بکاپ و چک‌لیست استقرار.

کرنل، فضای کاربر و System Call

سیستم‌عامل لایه‌ای است که سخت‌افزار (CPU، حافظه، دیسک، شبکه) را مدیریت و به‌صورت انتزاعی و امن در اختیار برنامه‌ها قرار می‌دهد. هسته‌ی آن Kernel است.

Kernel space

  • کد هسته با بالاترین سطح دسترسی (ring 0) اجرا می‌شود.
  • دسترسی مستقیم به سخت‌افزار، مدیریت حافظه، زمان‌بندی فرایندها، درایورها، فایل‌سیستم و پشته‌ی شبکه.
  • خطا در این فضا می‌تواند کل سیستم را از کار بیندازد (kernel panic).

User space

  • برنامه‌های عادی (Nginx، PHP-FPM، MySQL، bash) با دسترسی محدود اجرا می‌شوند.
  • هر فرایند فضای حافظه‌ی ایزوله‌ی خودش را دارد.
  • برای هر کار سطح پایین باید از کرنل درخواست کنند.

System call رابط کنترل‌شده‌ی برنامه‌ی user space برای درخواست سرویس از کرنل است. CPU با یک دستور ویژه به حالت kernel می‌رود، کرنل کار را انجام می‌دهد و نتیجه را برمی‌گرداند. این جابه‌جایی هزینه دارد؛ به همین دلیل خواندن فایل با بافرهای بزرگ‌تر یا کاهش تعداد syscallها کارایی را بهتر می‌کند.

در خروجی ps یا top ستون STAT/S این حالت‌ها را نشان می‌دهد:

  • R: Running یا Runnable (در صف اجرا).
  • S: Interruptible sleep؛ منتظر رویداد (بیشتر فرایندها).
  • D: Uninterruptible sleep؛ معمولاً منتظر دیسک یا NFS؛ با سیگنال هم متوقف نمی‌شود.

Context switch

Context switch یعنی کرنل اجرای یک فرایند/thread را متوقف کند، وضعیت آن (رجیسترها، program counter، اشاره‌گر stack) را ذخیره و وضعیت دیگری را بارگذاری کند. علت‌ها: تمام شدن time slice، انتظار برای I/O، یا رسیدن کاری با اولویت بالاتر. سربار آن شامل خود ذخیره/بارگذاری و از دست رفتن گرمی cache و TLB است. تعداد بسیار زیاد فرایندهای فعال نسبت به هسته‌ها (مثلاً pm.max_children خیلی بزرگ روی کار CPU-bound) زمان CPU را در context switch هدر می‌دهد.

زمان‌بندی (Scheduling)

  • Preemptive: کرنل می‌تواند اجرای فرایند را در هر زمان قطع کند (لینوکس). Cooperative: کار خودش کنترل را واگذار می‌کند (coroutineها).
  • الگوریتم‌های کلاسیک: FCFS، Shortest Job First، Round Robin با time slice، Priority scheduling.
  • لینوکس سال‌ها از CFS (Completely Fair Scheduler) استفاده می‌کرد که سهم منصفانه‌ای از CPU به هر کار می‌دهد؛ از کرنل 6.6 زمان‌بند پیش‌فرض به EEVDF تغییر کرد که همان ایده‌ی انصاف را با توجه به latency پیاده می‌کند.
  • اولویت در فضای کاربر با nice (از ‎-20 بالاترین تا 19 پایین‌ترین) تنظیم می‌شود: nice -n 10 php artisan report:build یا renice.
  • Load average (در uptime و top): میانگین تعداد فرایندهای در حالت R یا D در ۱، ۵ و ۱۵ دقیقه‌ی اخیر. باید با تعداد هسته‌ها (nproc) مقایسه شود: load برابر ۸ روی ۸ هسته یعنی تقریباً کامل مشغول.

تفاوت process و thread را با سه محور بنویسید: حافظه (ایزوله در برابر مشترک)، هزینه (ایجاد و context switch) و ایزولاسیون خطا. سپس مثال بزنید: PHP-FPM مدل process دارد پس state بین درخواست‌ها مشترک نیست و نیاز به lock داخلی ندارد، اما حافظه‌ی بیشتری مصرف می‌کند.

هم‌روندی، Race Condition، Mutex، Semaphore و Deadlock

Concurrency (هم‌روندی)

ساختار برنامه طوری است که چند کار در یک بازه‌ی زمانی پیشرفت می‌کنند؛ ممکن است با جابه‌جایی سریع روی یک هسته باشد. موضوع آن «مدیریت» چند کار است. مثال: event loop در Nginx یا Node.js.

Parallelism (موازی‌سازی)

چند کار واقعاً در یک لحظه روی چند هسته یا ماشین اجرا می‌شوند. موضوع آن «انجام» هم‌زمان است. مثال: ۸ queue worker روی سرور ۸ هسته‌ای.

جمله‌ی معروف Rob Pike: «Concurrency is about dealing with lots of things at once; parallelism is about doing lots of things at once.»

Race condition

Race condition زمانی رخ می‌دهد که نتیجه‌ی برنامه به ترتیب یا زمان‌بندی اجرای چند کار هم‌زمان روی داده‌ی مشترک بستگی داشته باشد. حتی در PHP که هر درخواست فرایند جداست، داده‌ی مشترک (دیتابیس، Redis، فایل) باعث race می‌شود.

<?php
// Race: دو درخواست هم‌زمان هر دو موجودی 100 را می‌خوانند و هر دو 80 می‌نویسند
$wallet = Wallet::find($id);              // read
if ($wallet->balance >= 20) {             // check
    $wallet->balance -= 20;               // modify
    $wallet->save();                      // write  ← یکی از برداشت‌ها گم می‌شود
}

// راه‌حل ۱: قفل ردیف در تراکنش (pessimistic)
DB::transaction(function () use ($id) {
    $wallet = Wallet::whereKey($id)->lockForUpdate()->first();
    if ($wallet->balance < 20) {
        throw new InsufficientFunds();
    }
    $wallet->decrement('balance', 20);
});

// راه‌حل ۲: عملیات اتمیک با شرط در خود UPDATE
$affected = Wallet::whereKey($id)->where('balance', '>=', 20)->decrement('balance', 20);
// اگر $affected صفر بود یعنی موجودی کافی نبود

// راه‌حل ۳: قفل توزیع‌شده برای بخش بحرانی غیر دیتابیسی
Cache::lock("invoice:{$orderId}", 10)->block(5, function () use ($orderId) {
    // فقط یک فرایند در هر لحظه
});

الگوی کلی خطر، check-then-act یا read-modify-write غیراتمیک است. راه‌حل: اتمیک کردن عملیات، قفل، یا optimistic locking (ستون version و UPDATE ... WHERE version = ?).

ابزارهای همگام‌سازی

Critical section
بخشی از کد که به منبع مشترک دسترسی دارد و نباید هم‌زمان توسط بیش از یک کار اجرا شود.
Mutex
قفل انحصاری (mutual exclusion): در هر لحظه فقط یک صاحب دارد و همان صاحب باید آن را آزاد کند.
Semaphore
شمارنده‌ای که اجازه می‌دهد حداکثر N کار هم‌زمان وارد شوند (عملیات wait/P و signal/V). semaphore با N=1 (binary) شبیه mutex است اما مفهوم «مالکیت» ندارد. مثال: محدود کردن به ۵ اتصال هم‌زمان به یک API.
Spinlock
قفلی که به جای خوابیدن در حلقه منتظر می‌ماند؛ فقط برای انتظارهای بسیار کوتاه (بیشتر در کرنل).
Atomic operation
عملیاتی که تقسیم‌ناپذیر است، مثل INCR در Redis یا UPDATE x = x + 1.

Deadlock و چهار شرط Coffman

Deadlock وضعیتی است که دو یا چند کار هر کدام منتظر منبعی هستند که در اختیار دیگری است و هیچ‌کدام پیش نمی‌روند. Deadlock فقط وقتی ممکن است که هر چهار شرط هم‌زمان برقرار باشند:

  1. Mutual exclusion: منبع در هر لحظه فقط در اختیار یک کار است.
  2. Hold and wait: کار، منبعی را نگه داشته و منتظر منبع دیگری است.
  3. No preemption: نمی‌توان منبع را به زور از صاحبش گرفت.
  4. Circular wait: زنجیره‌ی چرخه‌ای انتظار وجود دارد (A منتظر B، B منتظر A).
  Transaction 1: lock(row A) ─► منتظر lock(row B)
                     ▲                     │
                     │                     ▼
  Transaction 2: منتظر lock(row A) ◄─ lock(row B)

پیشگیری با شکستن یکی از شرط‌ها: گرفتن قفل‌ها با ترتیب ثابت (مثلاً همیشه بر اساس id صعودی؛ شکستن circular wait)، گرفتن همه‌ی قفل‌ها یکجا، timeout روی قفل (innodb_lock_wait_timeout، block(5)) و کوتاه نگه داشتن تراکنش‌ها. InnoDB خودش deadlock را تشخیص می‌دهد و یکی از تراکنش‌ها را rollback می‌کند؛ اپلیکیشن باید آماده‌ی retry باشد (DB::transaction($callback, attempts: 3)).

تفاوت Deadlock و Livelock و Starvation: در deadlock همه متوقف‌اند؛ در livelock کارها مدام وضعیت تغییر می‌دهند (مثلاً پی‌درپی عقب‌نشینی و تلاش مجدد) اما پیشرفتی ندارند؛ در starvation یک کار به دلیل اولویت پایین یا بی‌انصافی زمان‌بند هرگز منبع را به دست نمی‌آورد.

مدیریت حافظه: Virtual Memory، Paging، Swap و OOM

Virtual memory به هر فرایند این توهم را می‌دهد که یک فضای آدرس پیوسته و اختصاصی دارد. آدرس‌های مجازی توسط MMU و با کمک page table (که کرنل برای هر فرایند نگه می‌دارد) به آدرس فیزیکی RAM ترجمه می‌شوند. TLB کش ترجمه‌های اخیر است.

  • Page: حافظه در واحدهای ثابت (معمولاً ۴KB) مدیریت می‌شود.
  • Page fault: وقتی فرایند به صفحه‌ای دسترسی پیدا می‌کند که در RAM نگاشت نشده است. minor: صفحه در حافظه هست ولی نگاشت نشده (مثلاً shared library)؛ major: باید از دیسک (فایل یا swap) خوانده شود که بسیار کند است.
  • مزایا: ایزولاسیون فرایندها، استفاده‌ی مشترک از کتابخانه‌ها، copy-on-write بعد از fork (فرایند فرزند تا وقتی چیزی را تغییر نداده، صفحات والد را به اشتراک می‌گذارد؛ PHP-FPM از این بهره می‌برد)، و امکان استفاده از حافظه‌ی بیشتر از RAM با swap.

Swap

Swap فضایی روی دیسک است که صفحات کم‌استفاده‌ی RAM به آن منتقل می‌شوند. کمی swap به عنوان سپر اطمینان مفید است، اما اگر سرور مدام در حال swap in/out باشد (thrashing) کارایی به‌شدت سقوط می‌کند، چون دیسک چند مرتبه کندتر از RAM است. پارامتر vm.swappiness میزان تمایل کرنل به swap را تعیین می‌کند. در vmstat 1 ستون‌های si/so فعالیت swap را نشان می‌دهند.

OOM Killer

وقتی حافظه (RAM + swap) تمام شود و کرنل نتواند صفحه‌ای آزاد کند، OOM killer بر اساس امتیاز (/proc/<pid>/oom_score، که بیشتر به مصرف حافظه وابسته است) یک فرایند را با SIGKILL می‌کشد؛ اغلب بزرگ‌ترین مصرف‌کننده مثل MySQL. با oom_score_adj می‌توان احتمال کشته شدن یک سرویس را کم یا زیاد کرد.

# آیا OOM killer فرایندی را کشته است؟
sudo dmesg -T | grep -i -E "out of memory|killed process"
sudo journalctl -k | grep -i oom

سناریوی رایج: «MySQL ناگهان ری‌استارت شده و در لاگ خودش خطایی نیست.» پاسخ: بررسی dmesg/journalctl -k برای پیام OOM killer؛ علت معمولاً pm.max_children بیش از حد، queue workerهایی با نشت حافظه یا buffer pool بزرگ‌تر از RAM است. راه‌حل: محاسبه‌ی بودجه‌ی حافظه برای هر سرویس، محدود کردن workerها و مانیتورینگ.

inode

inode ساختاری است که متادیتای یک فایل را نگه می‌دارد: نوع فایل، مالک و گروه، مجوزها، اندازه، زمان‌ها (atime، mtime، ctime)، تعداد hard linkها و اشاره‌گر به بلوک‌های داده. نام فایل در inode نیست؛ نام در «ورودی دایرکتوری» (directory entry) ذخیره می‌شود که نام را به شماره‌ی inode نگاشت می‌کند. ls -i شماره‌ی inode را نشان می‌دهد.

Hard link

  • یک نام دیگر برای همان inode (ln a b).
  • حذف یکی، داده را پاک نمی‌کند؛ داده وقتی پاک می‌شود که شمارنده‌ی link صفر شود و هیچ فرایندی فایل را باز نکرده باشد.
  • نمی‌تواند بین فایل‌سیستم‌ها باشد و برای دایرکتوری مجاز نیست.

Symbolic (soft) link

  • فایلی جدا با inode خودش که حاوی مسیر مقصد است (ln -s target link).
  • می‌تواند به دایرکتوری و فایل‌سیستم دیگر اشاره کند.
  • با حذف مقصد «شکسته» (dangling) می‌شود.
  • کاربرد: php artisan storage:link، پوشه‌ی current در deploy.

دو مشکل کلاسیک «دیسک پر است»: ۱) تمام شدن inodeها با میلیون‌ها فایل کوچک (مثلاً sessionهای فایلی یا کش فایلی)؛ df -h فضای آزاد نشان می‌دهد اما df -i صددرصد است. ۲) فایل حذف‌شده‌ای که هنوز باز است: لاگ بزرگی را با rm پاک کرده‌اید اما فرایند هنوز آن را باز نگه داشته، پس فضا آزاد نمی‌شود. با lsof +L1 پیدا کنید و سرویس را reload کنید، یا از ابتدا به جای rm فایل را truncate کنید (: > file.log).

File Descriptor

File descriptor (FD) یک عدد صحیح است که کرنل هنگام باز کردن فایل، سوکت، pipe یا هر منبع I/O به فرایند می‌دهد و فرایند با آن عملیات read/write انجام می‌دهد. در لینوکس «تقریباً همه‌چیز فایل است» و سوکت‌های شبکه هم FD هستند.

  • سه FD استاندارد: 0 = stdin، 1 = stdout، 2 = stderr.
  • لیست FDهای یک فرایند: ls -l /proc/<PID>/fd یا lsof -p <PID>.
  • هر فرایند سقف تعداد FD دارد (ulimit -n، معمولاً 1024 به‌صورت پیش‌فرض برای shell). سرورهای پراتصال (Nginx، MySQL، Redis، Octane) به سقف بالاتری نیاز دارند؛ در غیر این صورت خطای Too many open files (EMFILE) می‌گیرید.
  • برای سرویس‌های systemd سقف با LimitNOFILE= در unit تنظیم می‌شود؛ برای Nginx هم worker_rlimit_nofile و worker_connections.
  • نشت FD (باز کردن فایل یا اتصال بدون بستن) در پروسه‌های طولانی‌مدت مثل queue worker به این خطا می‌رسد.

chmod -R g+w storage              # بازگشتی
chown deploy:www-data file        # تغییر مالک و گروه

chgrp www-data file
find storage -type d -exec chmod 775 {} +   # فقط دایرکتوری‌ها
find storage -type f -exec chmod 664 {} +   # فقط فایل‌ها

بیت‌های ویژه و umask

setuid (4xxx)
فایل اجرایی با هویت مالک فایل اجرا می‌شود نه کاربر اجراکننده؛ مثال /usr/bin/passwd که باید /etc/shadow را تغییر دهد. ریسک امنیتی بالایی دارد.
setgid (2xxx)
روی فایل اجرایی: اجرا با گروه فایل. روی دایرکتوری: فایل‌های جدید گروه دایرکتوری را به ارث می‌برند؛ برای پوشه‌ی storage مشترک بین کاربر deploy و www-data بسیار مفید است.
sticky bit (1xxx)
روی دایرکتوری: فقط مالک فایل می‌تواند آن را حذف کند، حتی اگر همه حق نوشتن داشته باشند؛ مثل /tmp (مجوز 1777).
umask
ماسکی که بیت‌هایش از مجوز پیش‌فرض فایل‌های جدید حذف می‌شوند. پیش‌فرض فایل 666 و دایرکتوری 777؛ با umask 022 نتیجه 644 و 755؛ با 002 نتیجه 664 و 775 (مناسب کار گروهی).

کاربران و sudo

  • root (UID 0) هیچ محدودیتی ندارد؛ کار روزمره با root یعنی هر اشتباه یا نفوذ، کل سیستم را در اختیار می‌گذارد.
  • کاربر عادی با عضویت در گروه sudo (اوبونتو) می‌تواند دستورات مدیریتی را با sudo اجرا کند؛ هر استفاده لاگ می‌شود.
  • تنظیمات در /etc/sudoers و /etc/sudoers.d/، فقط با visudo ویرایش شود (بررسی syntax). می‌توان به کاربر deploy فقط اجازه‌ی reload سرویس خاص بدون رمز داد:
# /etc/sudoers.d/deploy
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl reload php8.3-fpm, /usr/bin/systemctl reload nginx
sudo adduser deploy
sudo usermod -aG www-data deploy     # -a مهم است؛ بدون آن گروه‌های قبلی حذف می‌شوند
id deploy                            # نمایش UID و گروه‌ها
sudo -u www-data php artisan cache:clear   # اجرای دستور با هویت کاربر وب‌سرور

دسترسی‌های پروژه‌ی Laravel

اصل حداقل دسترسی (least privilege): کاربر وب‌سرور (www-data که PHP-FPM با آن اجرا می‌شود) فقط باید جایی بنویسد که لازم است: storage (لاگ، کش فایل، session، viewهای کامپایل‌شده، آپلودها) و bootstrap/cache (کش config، routes، services، packages).

cd /var/www/app
sudo chown -R deploy:www-data .
sudo find . -type f -exec chmod 644 {} +
sudo find . -type d -exec chmod 755 {} +
sudo chmod -R ug+rwX storage bootstrap/cache        # X بزرگ: x فقط برای دایرکتوری‌ها
sudo find storage bootstrap/cache -type d -exec chmod g+s {} +   # ارث بردن گروه
chmod 640 .env                                      # خواندن فقط برای مالک و گروه www-data

هرگز chmod -R 777 نکنید. یعنی هر کاربر و هر فرایند روی سرور (از جمله یک اسکریپت آلوده‌ی آپلودشده) می‌تواند کد شما را تغییر دهد. همچنین کل پروژه نباید متعلق به www-data و قابل نوشتن برای آن باشد؛ اگر PHP آسیب‌پذیری داشته باشد، مهاجم می‌تواند فایل‌های PHP را بازنویسی کند. خطای رایج دیگر: اجرای php artisan با root که فایل‌های لاگ یا کش را با مالک root می‌سازد و سپس www-data نمی‌تواند در آن‌ها بنویسد (Permission denied در laravel.log).

در پاسخ سوال «دسترسی‌های پوشه‌های Laravel را چگونه تنظیم می‌کنید؟» به این‌ها اشاره کنید: مالک = کاربر deploy، گروه = www-data، فایل‌ها 644 و دایرکتوری‌ها 755، storage و bootstrap/cache قابل نوشتن برای گروه (775/664)، setgid برای ارث گروه، umask 002 برای فرایندهای مشترک، .env با 640، document root فقط پوشه‌ی public، و پرهیز از 777 و اجرای artisan با root.

مدیریت سرویس‌ها: systemd و Supervisor برای Queue Worker

systemd سیستم init و مدیر سرویس در بیشتر توزیع‌های مدرن لینوکس است (PID 1). سرویس‌ها با فایل‌های unit تعریف می‌شوند و systemd وظیفه‌ی شروع در boot، ری‌استارت پس از کرش، مدیریت وابستگی‌ها، محدودیت منابع و جمع‌آوری لاگ (journald) را بر عهده دارد.

Queue worker با systemd

# /etc/systemd/system/laravel-worker@.service
[Unit]
Description=Laravel queue worker %i
After=network.target mysql.service redis-server.service

[Service]
User=www-data
Group=www-data
WorkingDirectory=/var/www/app/current
ExecStart=/usr/bin/php artisan queue:work redis --queue=high,default --sleep=3 --tries=3 --max-time=3600
Restart=always
RestartSec=5
KillSignal=SIGTERM
TimeoutStopSec=120
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload                       # بعد از هر تغییر در unit
sudo systemctl enable --now laravel-worker@{1..4}  # چهار نمونه با template unit
systemctl status laravel-worker@1
journalctl -u 'laravel-worker@*' -f

Queue worker با Supervisor

Supervisor یک process control system مستقل است که در مستندات Laravel برای queue workerها پیشنهاد شده است؛ تعریف چند نمونه با numprocs ساده است.

; /etc/supervisor/conf.d/laravel-worker.conf
[program:laravel-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/app/current/artisan queue:work redis --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=4
redirect_stderr=true
stdout_logfile=/var/www/app/shared/storage/logs/worker.log
stopwaitsecs=3600
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl start "laravel-worker:*"
sudo supervisorctl status
  • stopwaitsecs (یا TimeoutStopSec) باید از طولانی‌ترین job بیشتر باشد تا هنگام stop، job نیمه‌کاره kill نشود.
  • queue:work یک پروسه‌ی طولانی‌مدت است و کد را یک‌بار load می‌کند؛ بعد از هر deploy باید php artisan queue:restart اجرا شود تا workerها پس از job جاری خارج شوند و مدیر سرویس آن‌ها را با کد جدید بالا بیاورد.
  • --max-time و --max-jobs و --memory worker را دوره‌ای بازیافت می‌کنند تا نشت حافظه انباشته نشود.
  • برای Laravel Horizon (صف Redis) به جای چند worker فقط یک پروسه‌ی php artisan horizon تعریف می‌شود و در deploy horizon:terminate اجرا می‌شود.

مفاهیم پایه

  • IP address مشخص‌کننده‌ی میزبان و port (۰ تا ۶۵۵۳۵) مشخص‌کننده‌ی سرویس روی آن است؛ ترکیب پروتکل + IP + port یک socket را مشخص می‌کند.
  • پورت‌های زیر ۱۰۲۴ (privileged) فقط با root قابل bind هستند؛ به همین دلیل master Nginx با root اجرا می‌شود و workerها با کاربر کم‌دسترسی.
  • TCP: اتصال‌گرا، تضمین ترتیب و تحویل (HTTP/1.1، HTTP/2، MySQL، SSH). UDP: بدون اتصال، سبک (DNS، QUIC/HTTP/3).
  • گوش دادن روی 127.0.0.1 یعنی فقط از خود سرور قابل دسترسی است؛ 0.0.0.0 یعنی روی همه‌ی اینترفیس‌ها. MySQL و Redis نباید روی اینترفیس عمومی گوش دهند.
  • DNS نام دامنه را به IP تبدیل می‌کند: رکورد A (IPv4)، AAAA (IPv6)، CNAME (نام مستعار)، MX (ایمیل)، TXT (تأیید دامنه، SPF).

فایروال: ufw و iptables

لینوکس فیلتر بسته‌ها را در کرنل با netfilter انجام می‌دهد؛ iptables (و جانشین مدرنش nftables) رابط سطح پایین آن است و ufw (Uncomplicated Firewall) رابط ساده‌ی اوبونتو روی آن. سیاست درست: همه چیز ورودی بسته، فقط موارد لازم باز.

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH                 # قبل از enable! وگرنه خودتان را بیرون می‌اندازید
sudo ufw allow 80,443/tcp
sudo ufw allow from 10.0.0.5 to any port 3306 proto tcp   # فقط سرور اپ به دیتابیس
sudo ufw limit OpenSSH                 # محدودیت نرخ اتصال برای مقابله با brute-force
sudo ufw enable
sudo ufw status verbose
# معادل تقریبی با iptables
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -p tcp -m multiport --dports 22,80,443 -j ACCEPT
sudo iptables -P INPUT DROP

Docker برای publish کردن پورت‌ها (-p 3306:3306) قوانین iptables خودش را مستقیماً اضافه می‌کند و این قوانین می‌توانند ufw را دور بزنند؛ یعنی ممکن است فکر کنید پورت بسته است در حالی که از اینترنت باز است. پورت‌های داخلی را فقط روی 127.0.0.1 publish کنید (-p 127.0.0.1:3306:3306) یا اصلاً publish نکنید.

SSH: کلید و امن‌سازی

احراز هویت با کلید عمومی/خصوصی: کلید خصوصی نزد شما می‌ماند و کلید عمومی در ~/.ssh/authorized_keys سرور قرار می‌گیرد. سرور با یک challenge ثابت می‌کند که شما کلید خصوصی را دارید، بدون اینکه کلید یا رمزی از شبکه عبور کند. در برابر brute-force رمز عبور مقاوم است.

ssh-keygen -t ed25519 -C "ali@laptop"      # ساخت جفت کلید (با passphrase)
ssh-copy-id deploy@203.0.113.10             # کپی کلید عمومی به سرور
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys   # SSH با دسترسی باز کلید را رد می‌کند
# /etc/ssh/sshd_config (یا فایلی در /etc/ssh/sshd_config.d/)
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AllowUsers deploy ali
MaxAuthTries 3
sudo sshd -t                 # بررسی syntax قبل از اعمال
sudo systemctl reload ssh    # نشست فعلی را باز نگه دارید و از ترمینال دوم تست کنید

Reverse proxy

Reverse proxy سروری است که جلوی سرورهای اپلیکیشن می‌نشیند و درخواست‌های کلاینت را از طرف آن‌ها دریافت و به backend می‌فرستد (در مقابل forward proxy که از طرف کلاینت به اینترنت می‌رود). وظایف: TLS termination، سرو فایل ثابت، فشرده‌سازی، کش، rate limiting، پنهان کردن ساختار داخلی و load balancing.

TLS و گواهی‌های Let's Encrypt

TLS (جانشین SSL) سه چیز فراهم می‌کند: محرمانگی (رمزنگاری ترافیک)، یکپارچگی (تشخیص دستکاری) و احراز هویت سرور (با گواهی امضاشده توسط یک CA مورد اعتماد). HTTPS یعنی HTTP روی TLS.

Handshake به زبان ساده (TLS 1.3)

  1. کلاینت ClientHello می‌فرستد: نسخه‌ها و cipherهای پشتیبانی‌شده، سهم کلید (key share) و نام دامنه (SNI).
  2. سرور ServerHello با سهم کلید خودش، و گواهی به همراه زنجیره‌ی گواهی‌های میانی را می‌فرستد و با کلید خصوصی ثابت می‌کند مالک گواهی است.
  3. کلاینت زنجیره را تا یک root CA مورد اعتماد، نام دامنه و تاریخ انقضا را بررسی می‌کند.
  4. دو طرف با تبادل کلید (ECDHE) یک کلید متقارن مشترک می‌سازند و بقیه‌ی ارتباط با رمزنگاری متقارن (سریع) انجام می‌شود. TLS 1.3 این کار را در یک round-trip انجام می‌دهد.

رمزنگاری نامتقارن (کلید عمومی/خصوصی) فقط برای احراز هویت و توافق کلید است؛ داده‌ی اصلی با رمزنگاری متقارن (مثل AES-GCM یا ChaCha20) رمز می‌شود چون بسیار سریع‌تر است. Forward secrecy به لطف کلیدهای موقت ECDHE یعنی حتی اگر کلید خصوصی سرور بعداً لو برود، ترافیک ضبط‌شده‌ی قبلی قابل رمزگشایی نیست.

  • مجازی‌سازی سخت‌افزار توسط hypervisor (KVM، VMware، Hyper-V)؛ هر VM کرنل و OS کامل خودش را دارد.

  • ایزوله‌سازی در سطح سیستم‌عامل با namespaces (دید جدای PID، شبکه، mount، user) و cgroups (محدودیت CPU و حافظه)؛ کرنل میزبان مشترک است.

Infrastructure as Code (IaC)

IaC یعنی تعریف زیرساخت (سرورها، شبکه، دیتابیس، DNS، پیکربندی) در فایل‌های متنی نسخه‌دار به جای کلیک در پنل یا اجرای دستی دستورات. مزایا: تکرارپذیری (ساخت staging مشابه production)، بازبینی در code review، تاریخچه در git، حذف configuration drift (تفاوت تدریجی سرورها)، و بازسازی سریع در فاجعه.

Terraform (Provisioning)

  • ساخت منابع زیرساخت در ابر (VM، VPC، load balancer، دیتابیس مدیریت‌شده، DNS).
  • Declarative: وضعیت مطلوب را با HCL توصیف می‌کنید؛ Terraform تفاوت با وضعیت فعلی را محاسبه می‌کند.
  • State file نگاشت منابع واقعی را نگه می‌دارد؛ باید به‌صورت remote و با lock ذخیره شود.
  • جریان کار: terraform init ← plan (پیش‌نمایش تغییرات) ← apply.
  • Providerها برای AWS، GCP، Azure، Cloudflare و…

Ansible (Configuration management)

  • پیکربندی سرورهای موجود: نصب بسته‌ها، فایل‌های config، کاربران، سرویس‌ها، deploy.
  • Agentless: از طریق SSH اجرا می‌شود؛ نیازی به نصب agent روی سرور نیست.
  • Playbookهای YAML با taskهایی که از ماژول‌ها استفاده می‌کنند.
  • ماژول‌ها idempotent هستند: اجرای چندباره همان نتیجه را می‌دهد و فقط تغییرات لازم اعمال می‌شود.
# playbook.yml — نمونه‌ی ساده‌ی Ansible
- hosts: web
  become: true
  tasks:
    - name: Install packages
      ansible.builtin.apt:
        name: [nginx, php8.3-fpm, php8.3-mysql, php8.3-redis, supervisor]
        state: present
        update_cache: true

    - name: Deploy nginx site config
      ansible.builtin.template:
        src: templates/app.conf.j2
        dest: /etc/nginx/sites-available/app.conf
      notify: Reload nginx

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

Mutable در برابر Immutable infrastructure: در مدل mutable سرورها در جا به‌روزرسانی می‌شوند (Ansible روی سرور موجود)؛ در مدل immutable برای هر تغییر یک image جدید (Docker image یا AMI) ساخته و سرور/کانتینر قدیمی جایگزین می‌شود. مدل immutable drift ندارد و rollback آن ساده است (برگشت به image قبلی).

High Availability (HA) یعنی سیستم با وجود خرابی اجزای منفرد به کار ادامه دهد. معیار آن درصد uptime است:

  • Redundancy: چند سرور اپ stateless پشت load balancer، چند availability zone.
  • Replication دیتابیس: primary-replica؛ replicaها برای خواندن و failover. Laravel از جداسازی read/write در config دیتابیس و گزینه‌ی sticky پشتیبانی می‌کند.

  • Health check و self-healing: خارج کردن خودکار نمونه‌ی ناسالم و جایگزینی آن.
  • Graceful degradation: اگر سرویس جانبی (مثل توصیه‌گر) از دست رفت، صفحه‌ی اصلی همچنان کار کند؛ timeout و circuit breaker برای وابستگی‌های خارجی.
  • Zero-downtime deploy: rolling update یا blue-green، و migrationهای سازگار با نسخه‌ی قبل (expand/contract).

Backup و Disaster Recovery

RPO
Recovery Point Objective: حداکثر مقدار داده‌ای (بر حسب زمان) که از دست رفتنش قابل قبول است. RPO یک ساعت یعنی بکاپ یا replication حداقل هر ساعت.
RTO
Recovery Time Objective: حداکثر زمان قابل قبول تا بازگشت سرویس پس از فاجعه. RTO پانزده دقیقه یعنی باید فرایند بازیابی خودکار و تمرین‌شده باشد.
Full / Incremental / Differential
کامل؛ فقط تغییرات از آخرین بکاپ (هر نوع)؛ تغییرات از آخرین بکاپ کامل.

  • قاعده‌ی 3-2-1: حداقل ۳ نسخه از داده، روی ۲ نوع رسانه‌ی متفاوت، ۱ نسخه خارج از سایت (مثلاً object storage در region دیگر).
  • Replication بکاپ نیست: یک DELETE اشتباه یا ransomware فوراً روی replica هم اعمال می‌شود. بکاپ نسخه‌دار و ترجیحاً تغییرناپذیر (immutable) لازم است.
  • بکاپی که restore آن تست نشده، بکاپ نیست. بازیابی را دوره‌ای روی محیط جدا تمرین و زمانش را اندازه بگیرید (برای سنجش RTO).
  • چه چیزهایی: دیتابیس، فایل‌های آپلودی (storage/app یا S3)، فایل .env و secrets (در vault امن)، کد زیرساخت. کد اپلیکیشن در git است.
  • بکاپ‌ها را رمزنگاری کنید و دسترسی به آن‌ها را محدود؛ بکاپ نشت‌کرده یعنی نشت کل دیتابیس.
  • برای MySQL با InnoDB از mysqldump --single-transaction برای بکاپ سازگار بدون قفل کردن جدول‌ها استفاده کنید؛ برای دیتابیس‌های بزرگ ابزارهای فیزیکی مثل Percona XtraBackup یا snapshot مدیریت‌شده.

RPO و RTO را با هم اشتباه نگیرید: RPO به گذشته نگاه می‌کند (چقدر داده از دست می‌رود؛ تعیین‌کننده‌ی تناوب بکاپ/replication) و RTO به آینده (چقدر طول می‌کشد سرویس برگردد؛ تعیین‌کننده‌ی میزان خودکارسازی و آماده‌به‌کار بودن زیرساخت). هر چه هر دو کوچک‌تر، هزینه بیشتر.

چک‌لیست استقرار Laravel در Production

سرور و امنیت

  • کاربر غیر root برای deploy، SSH فقط با کلید، PermitRootLogin no، fail2ban، به‌روزرسانی امنیتی خودکار.
  • فایروال: فقط 22 (ترجیحاً محدود به IPهای مشخص)، 80 و 443 باز؛ MySQL و Redis فقط در شبکه‌ی خصوصی یا localhost؛ Redis با رمز.
  • نسخه‌ی پشتیبانی‌شده‌ی PHP و افزونه‌های لازم (php -m)، OPcache فعال، Xdebug غیرفعال.
  • HTTPS با Let's Encrypt و تمدید خودکار، ریدایرکت 80 به 443، HSTS.
  • document root فقط public/؛ دسترسی به dotfileها مسدود.

اپلیکیشن

  • .env: APP_ENV=production، APP_DEBUG=false (در غیر این صورت stack trace و متغیرهای محیطی لو می‌رود)، APP_KEY تنظیم‌شده و ثابت (تغییرش sessionها و داده‌های رمزشده را باطل می‌کند)، APP_URL درست، driverهای cache/session/queue روی Redis.
  • composer install --no-dev --optimize-autoloader --no-interaction
  • npm ci && npm run build (یا ساخت assets در CI)
  • php artisan migrate --force (با بکاپ قبل از migrationهای پرریسک)
  • php artisan optimize (config، routes، views، events)
  • php artisan storage:link
  • دسترسی‌های storage و bootstrap/cache؛ .env با 640.
  • reload PHP-FPM برای پاک شدن OPcache؛ php artisan queue:restart (یا horizon:terminate).

پروسه‌های پس‌زمینه

  • queue workerها زیر Supervisor یا systemd با --max-time و stop timeout مناسب.
  • cron برای schedule:run هر دقیقه.

عملیات

  • لاگ: channel مناسب (مثلاً daily با نگهداری محدود یا ارسال به سرویس متمرکز)، logrotate برای لاگ‌های Nginx.
  • مانیتورینگ و هشدار: uptime (health route /up)، خطاها (Sentry و…)، منابع سرور، طول صف، failed jobs.
  • بکاپ خودکار دیتابیس و فایل‌ها، خارج از سرور، با restore تست‌شده.
  • استراتژی deploy بدون downtime (releases + symlink یا ابزارهایی مثل Deployer/Envoyer) و برنامه‌ی rollback.
  • تست smoke بعد از deploy (صفحه‌ی اصلی، login، یک endpoint کلیدی).

سوالات تشریحی

تفاوت Process، Thread و Coroutine را توضیح دهید. مدل اجرای PHP-FPM و Nginx کدام است و چه پیامدی دارد؟

Process: نمونه‌ی در حال اجرای یک برنامه با فضای آدرس حافظه‌ی ایزوله، PID، FDها و حداقل یک thread. ایجاد و context switch آن پرهزینه است (تعویض page table و TLB)، اما کرش یک فرایند بقیه را خراب نمی‌کند. ارتباط با IPC (pipe، socket).

Thread: واحد اجرا درون فرایند؛ heap و کد و فایل‌ها را با threadهای دیگر به اشتراک می‌گذارد اما stack و رجیسترهای خودش را دارد. سبک‌تر است ولی دسترسی مشترک به حافظه نیاز به همگام‌سازی (mutex) دارد و کرش یک thread کل فرایند را می‌کشد.

Coroutine: واحد اجرای بسیار سبک در user space با زمان‌بندی همکارانه؛ در نقطه‌ی انتظار (مثلاً I/O) کنترل را واگذار می‌کند. بدون ورود به کرنل جابه‌جا می‌شود، پس هزاران یا میلیون‌ها coroutine ممکن است. نمونه: Swoole، Fiberهای PHP 8.1، async/await.

PHP-FPM: مدل multi-process؛ هر worker یک درخواست در هر لحظه. پیامدها:

  • state بین درخواست‌ها مشترک نیست؛ امن و ساده، بدون نیاز به lock درون حافظه.
  • هم‌زمانی محدود به pm.max_children و مصرف حافظه‌ی بیشتر (هر worker ده‌ها مگابایت).
  • داده‌ی مشترک فقط از طریق دیتابیس/Redis؛ race condition آنجا رخ می‌دهد.

Nginx: چند worker process، هر کدام با event loop non-blocking (epoll) که هزاران اتصال را هم‌زمان مدیریت می‌کند؛ به همین دلیل با حافظه‌ی کم تعداد زیادی اتصال (مثلاً keep-alive و کلاینت‌های کند) را نگه می‌دارد و PHP-FPM را از آن‌ها محافظت می‌کند.

Race condition چیست؟ یک مثال واقعی در یک اپلیکیشن Laravel بزنید و حداقل دو راه برای جلوگیری از آن ارائه دهید.

تعریف: وضعیتی که نتیجه‌ی برنامه به ترتیب زمانی اجرای چند کار هم‌زمان روی داده‌ی مشترک وابسته است و ترتیب نامناسب نتیجه‌ی نادرست می‌دهد. الگوی رایج آن read-modify-write یا check-then-act غیراتمیک است.

مثال: فروش آخرین بلیت: دو درخواست هم‌زمان stock = 1 را می‌خوانند، هر دو شرط stock > 0 را برقرار می‌بینند و هر دو سفارش ثبت می‌کنند؛ نتیجه فروش دو بلیت با یک موجودی. حتی با فرایندهای جدای FPM، داده‌ی مشترک دیتابیس باعث این مشکل است.

راه‌حل‌ها:

  1. عملیات اتمیک شرطی: شرط و تغییر در یک دستور SQL. 
    <?php
$ok = Ticket::whereKey($id)->where('stock', '>', 0)->decrement('stock');
if (! $ok) { abort(409, 'Sold out'); }
  2. Pessimistic lock: lockForUpdate() داخل DB::transaction؛ درخواست دوم تا commit اولی منتظر می‌ماند و مقدار به‌روز را می‌خواند.
  3. Optimistic lock: ستون version و UPDATE ... WHERE id = ? AND version = ?؛ اگر ردیفی تغییر نکرد یعنی کس دیگری زودتر نوشته و باید retry کرد. برای رقابت کم مناسب است.
  4. قفل توزیع‌شده: Cache::lock('key', 10) روی Redis برای بخش‌های بحرانی غیر دیتابیسی (مثل فراخوانی API پرداخت یک‌باره).
  5. Unique constraint: برای جلوگیری از رکورد تکراری (مثلاً دوبار ثبت یک پرداخت) محدودیت یکتا در دیتابیس آخرین خط دفاع است.

Trade-off: قفل pessimistic ساده و مطمئن است ولی throughput را کم می‌کند و احتمال deadlock دارد؛ optimistic در رقابت زیاد retry زیادی دارد.

Deadlock را تعریف کنید، چهار شرط لازم برای وقوع آن را بنویسید و بگویید در یک اپلیکیشن مبتنی بر MySQL چگونه از آن جلوگیری یا آن را مدیریت می‌کنید.

تعریف: وضعیتی که مجموعه‌ای از کارها (فرایند، thread یا تراکنش) هر کدام منتظر منبعی هستند که در اختیار دیگری است و هیچ‌کدام نمی‌توانند پیش بروند.

شرایط Coffman (هر چهار شرط لازم است):

  1. Mutual exclusion: منبع انحصاری است.
  2. Hold and wait: نگه داشتن یک منبع و انتظار برای دیگری.
  3. No preemption: منبع را نمی‌توان به زور گرفت.
  4. Circular wait: زنجیره‌ی چرخه‌ای انتظار.

مثال MySQL: تراکنش ۱ ردیف حساب A را قفل می‌کند و سپس B را می‌خواهد؛ تراکنش ۲ هم‌زمان B را قفل کرده و A را می‌خواهد (انتقال پول دوطرفه).

پیشگیری (شکستن یکی از شرط‌ها):

  • ترتیب ثابت قفل‌ها: همیشه ردیف‌ها را به ترتیب id صعودی قفل کنید؛ circular wait حذف می‌شود. 
    <?php
DB::transaction(function () use ($fromId, $toId, $amount) {
    $accounts = Account::whereIn('id', [$fromId, $toId])
        ->orderBy('id')->lockForUpdate()->get()->keyBy('id');
    // ...
}, attempts: 3);
  • تراکنش‌های کوتاه؛ بدون فراخوانی API خارجی داخل تراکنش.
  • ایندکس مناسب تا InnoDB ردیف‌های کمتری را قفل کند (بدون ایندکس، قفل‌ها گسترده‌تر می‌شوند).

مدیریت: InnoDB deadlock را تشخیص می‌دهد و یکی از تراکنش‌ها را rollback می‌کند (خطای 1213)؛ اپلیکیشن باید retry کند (پارامتر attempts در DB::transaction). برای تحلیل از SHOW ENGINE INNODB STATUS (بخش LATEST DETECTED DEADLOCK) استفاده می‌کنم. innodb_lock_wait_timeout هم جلوی انتظار بی‌پایان روی قفل را می‌گیرد.

Virtual memory چیست و چه مزایایی دارد؟ Swap و OOM killer را توضیح دهید. اگر MySQL روی سرور شما به‌طور ناگهانی kill شود چگونه علت را بررسی می‌کنید؟

Virtual memory: هر فرایند یک فضای آدرس مجازی اختصاصی می‌بیند که توسط MMU و page table به حافظه‌ی فیزیکی (در صفحات ۴KB) نگاشت می‌شود.

مزایا:

  • ایزولاسیون: فرایندها حافظه‌ی هم را نمی‌بینند.
  • اشتراک کارآمد: کتابخانه‌های مشترک یک‌بار در RAM؛ copy-on-write پس از fork (که PHP-FPM از آن سود می‌برد).
  • امکان استفاده از فضای بیشتر از RAM با swap و memory-mapped files.

Swap: فضای دیسک برای صفحات کم‌استفاده. کمی swap سپر اطمینان است؛ اما swap مداوم (thrashing) چون دیسک بسیار کندتر از RAM است، کارایی را نابود می‌کند. با vmstat 1 (ستون‌های si/so) بررسی می‌شود.

OOM killer: وقتی RAM و swap تمام شود، کرنل بر اساس oom_score (عمدتاً حجم حافظه) فرایندی را با SIGKILL می‌کشد؛ اغلب MySQL چون بزرگ‌ترین مصرف‌کننده است.

بررسی:

  1. dmesg -T | grep -i "killed process" یا journalctl -k برای پیام OOM و نام فرایند.
  2. free -h و مانیتورینگ تاریخی حافظه برای دیدن الگوی رشد.
  3. بررسی مصرف‌کنندگان: ps aux --sort=-rss | head؛ تعداد workerهای FPM × RSS هر کدام، queue workerها، innodb_buffer_pool_size.

راه‌حل: بودجه‌بندی حافظه (buffer pool + max_children × RSS + سایر سرویس‌ها کمتر از RAM)، کاهش pm.max_children، بازیافت workerها با --max-jobs/--memory، کاهش oom_score_adj برای MySQL، جدا کردن دیتابیس از سرور اپ یا افزایش RAM.

inode چیست؟ تفاوت hard link و symbolic link را بنویسید. سناریو: df -h نشان می‌دهد دیسک ۴۰٪ خالی است اما اپلیکیشن خطای No space left on device می‌دهد. علت چیست؟

inode: ساختار داده‌ای در فایل‌سیستم که متادیتای فایل را نگه می‌دارد: نوع، مالک و گروه، مجوزها، اندازه، زمان‌ها، تعداد hard linkها و اشاره‌گر به بلوک‌های داده. نام فایل در inode نیست؛ در ورودی دایرکتوری ذخیره می‌شود که نام را به شماره‌ی inode وصل می‌کند.

Hard link: نام دیگری برای همان inode؛ همه‌ی نام‌ها هم‌ارزند و داده تا وقتی آخرین link حذف نشده (و فایل باز نیست) باقی می‌ماند. بین فایل‌سیستم‌ها و برای دایرکتوری ممکن نیست.

Symbolic link: فایلی جدا با inode خود که مسیر مقصد را نگه می‌دارد؛ می‌تواند به دایرکتوری یا فایل‌سیستم دیگر اشاره کند و با حذف مقصد شکسته می‌شود. نمونه: public/storage با storage:link یا current در deploy.

سناریو، علت اول: تمام شدن inodeها. هر فایل یک inode می‌گیرد و تعداد inodeها هنگام ساخت فایل‌سیستم ext4 ثابت است. میلیون‌ها فایل کوچک (session فایلی، کش فایلی، فایل‌های موقت) inodeها را تمام می‌کنند در حالی که فضای بلوک باقی است.

df -i                                   # IUse% نزدیک 100%
sudo find /var/www -xdev -type f | cut -d/ -f1-5 | sort | uniq -c | sort -rn | head

راه‌حل: پاک کردن فایل‌های قدیمی (مثلاً sessionها)، انتقال session و cache به Redis، و job پاک‌سازی دوره‌ای.

علت دوم ممکن: اگر df -h پر باشد اما du حجم کمی نشان دهد، فایل حذف‌شده‌ای هنوز توسط یک فرایند باز است (lsof +L1)؛ با reload/restart آن فرایند فضا آزاد می‌شود.

سیستم دسترسی فایل‌ها در لینوکس را توضیح دهید و بگویید دسترسی‌های یک پروژه‌ی Laravel را در production چگونه تنظیم می‌کنید. چرا chmod 777 راه‌حل نیست؟

مدل دسترسی: هر فایل مالک و گروه دارد و برای سه دسته (user، group، others) سه بیت r (4)، w (2) و x (1) تعریف می‌شود. روی دایرکتوری، r یعنی لیست کردن، w یعنی ایجاد/حذف فایل و x یعنی ورود. بیت‌های ویژه: setuid، setgid (روی دایرکتوری: ارث بردن گروه)، sticky. umask بیت‌های حذف‌شده از مجوز پیش‌فرض فایل‌های جدید است.

تنظیم Laravel:

  • مالک کد: کاربر deploy؛ گروه: www-data (کاربر PHP-FPM).
  • فایل‌ها 644، دایرکتوری‌ها 755؛ PHP فقط کد را می‌خواند.
  • storage و bootstrap/cache قابل نوشتن برای گروه: دایرکتوری‌ها 775 و فایل‌ها 664، به همراه chmod g+s روی دایرکتوری‌ها تا فایل‌های جدید گروه www-data را بگیرند.
  • .env با 640.
  • Nginx root فقط روی public/.
  • دستورات artisan را با همان کاربر اجرا کنید (sudo -u www-data یا deploy با umask 002) تا فایل‌هایی با مالک root ساخته نشود.
sudo chown -R deploy:www-data /var/www/app
sudo chmod -R ug+rwX /var/www/app/storage /var/www/app/bootstrap/cache

چرا 777 نه: هر کاربر و هر فرایند روی سرور می‌تواند فایل‌ها را تغییر دهد؛ اگر مهاجم از طریق یک آسیب‌پذیری (مثلاً آپلود فایل) کد اجرا کند، می‌تواند کد اپ را بازنویسی و backdoor بگذارد. 777 علت مشکل (مالکیت اشتباه) را حل نمی‌کند و اصل least privilege را نقض می‌کند.

تفاوت سیگنال‌های SIGTERM، SIGKILL و SIGHUP چیست؟ هنگام deploy، queue workerهای Laravel را چگونه به‌صورت ایمن ری‌استارت می‌کنید؟

تعریف سیگنال: اعلان ناهم‌زمانی که کرنل یا فرایند دیگر به یک فرایند می‌فرستد؛ فرایند می‌تواند برای بیشتر سیگنال‌ها handler تعریف کند.

  • SIGTERM (15): درخواست مؤدبانه‌ی خاتمه و پیش‌فرض kill و systemctl stop. قابل catch؛ فرایند می‌تواند کار جاری را تمام کند، اتصال‌ها را ببندد و تمیزکاری کند.
  • SIGKILL (9): کشتن فوری توسط کرنل؛ قابل catch یا ignore نیست؛ هیچ تمیزکاری انجام نمی‌شود (job نیمه‌کاره، فایل موقت، lock آزادنشده). آخرین راه‌حل.
  • SIGHUP (1): در اصل قطع ترمینال؛ قراردادی برای daemonها به معنای بارگذاری مجدد config بدون قطع سرویس (مثل Nginx).

Restart ایمن workerها:

  1. queue:work پروسه‌ی طولانی‌مدت است و کد قدیمی را در حافظه دارد؛ پس بعد از deploy باید ری‌استارت شود.
  2. php artisan queue:restart یک سیگنال در cache می‌گذارد؛ هر worker پس از اتمام job جاری به‌صورت graceful خارج می‌شود (Horizon: horizon:terminate).
  3. Supervisor/systemd با autorestart=true یا Restart=always worker را با کد جدید بالا می‌آورد.
  4. stopwaitsecs/TimeoutStopSec بیشتر از طولانی‌ترین job، تا مدیر سرویس پس از SIGTERM زودتر از موعد SIGKILL نفرستد. افزونه‌ی pcntl برای مدیریت سیگنال در worker لازم است.

و همچنین jobها idempotent باشند تا اگر در شرایط استثنایی kill شدند، اجرای مجدد آسیبی نزند.

مسیر یک درخواست HTTP از مرورگر تا کد Laravel را روی سروری با Nginx و PHP-FPM شرح دهید. خطاهای 502 و 504 در این معماری معمولاً چه علتی دارند؟

مسیر:

  1. مرورگر با DNS آدرس IP را پیدا و اتصال TCP و TLS handshake با Nginx روی پورت 443 برقرار می‌کند.
  2. Nginx بر اساس server_name بلوک server را انتخاب می‌کند. try_files $uri $uri/ /index.php?$query_string: اگر فایل ثابت در public/ وجود داشت مستقیم سرو می‌شود؛ در غیر این صورت به index.php می‌رود.
  3. بلوک location ~ \.php درخواست را با پروتکل FastCGI از طریق Unix socket (یا TCP) به PHP-FPM می‌فرستد؛ SCRIPT_FILENAME مسیر اسکریپت را مشخص می‌کند.
  4. PHP-FPM master درخواست را به یک worker آزاد می‌دهد (اگر آزاد نباشد، در صف می‌ماند).
  5. worker فایل public/index.php را اجرا می‌کند (با OPcache): autoload، bootstrap اپ، Kernel، middlewareها، router، controller، دیتابیس و Redis، ساخت پاسخ.
  6. پاسخ از FastCGI به Nginx برمی‌گردد و Nginx (با فشرده‌سازی) آن را به کاربر می‌فرستد.

502 Bad Gateway: Nginx نتوانسته پاسخ معتبری از upstream بگیرد: PHP-FPM اجرا نمی‌شود، مسیر سوکت در fastcgi_pass با listen در pool یکی نیست (مثلاً بعد از ارتقای نسخه‌ی PHP)، مجوز سوکت برای www-data نیست، یا worker حین پردازش کرش کرده (segfault). بررسی: systemctl status php8.3-fpm، error log Nginx و لاگ FPM.

504 Gateway Timeout: FPM پاسخ را در زمان fastcgi_read_timeout نداده: کوئری کند، API خارجی بدون timeout، lock دیتابیس یا پر بودن همه‌ی workerها (max_children reached). راه‌حل اصلی رفع کندی یا انتقال کار به صف است، نه صرفاً افزایش timeout.

یک سرور Ubuntu تازه برای اجرای اپلیکیشن Laravel تحویل گرفته‌اید. برای امن‌سازی اولیه‌ی آن (SSH، فایروال، کاربران) چه اقداماتی انجام می‌دهید؟

۱. به‌روزرسانی: apt update && apt upgrade و فعال کردن unattended-upgrades برای patchهای امنیتی.

۲. کاربران: ساخت کاربر غیر root (adduser deploy)، افزودن به گروه sudo فقط در صورت نیاز، و برای کاربر deploy دسترسی sudo محدود (فقط reload سرویس‌های خاص) با visudo.

۳. SSH:

  • کلید ed25519 با ssh-keygen و ssh-copy-id.
  • در sshd_config: PermitRootLogin no، PasswordAuthentication no، AllowUsers deploy.
  • sshd -t و reload، در حالی که نشست فعلی باز است و از ترمینال دوم تست می‌کنم تا قفل بیرون نمانم.
  • fail2ban برای مسدود کردن brute-force.

۴. فایروال (ufw):

ufw default deny incoming
ufw allow OpenSSH
ufw allow 80,443/tcp
ufw enable

MySQL و Redis فقط روی 127.0.0.1 یا شبکه‌ی خصوصی bind شوند؛ Redis با رمز. اگر Docker استفاده می‌شود، مراقب دور زدن ufw توسط پورت‌های publish‌شده هستم.

۵. سرویس‌ها: Nginx با root روی public/، مسدود کردن dotfileها، HTTPS با certbot، HSTS؛ PHP-FPM با کاربر www-data؛ expose_php=Off؛ APP_DEBUG=false.

۶. فایل‌ها: مالکیت deploy:www-data، 644/755، فقط storage و bootstrap/cache قابل نوشتن، .env با 640.

۷. پایش: لاگ‌ها (journald، auth.log)، مانیتورینگ منابع و uptime، بکاپ خارج از سرور.

بهتر است همه‌ی این مراحل با Ansible کدنویسی شوند تا برای سرورهای بعدی تکرارپذیر باشند.

Virtual Machine و Container را از نظر معماری، ایزولاسیون، کارایی و کاربرد مقایسه کنید.

مدل‌های IaaS، PaaS، SaaS و Serverless را تعریف و مقایسه کنید. برای یک استارتاپ با تیم کوچک که اپلیکیشن Laravel دارد کدام را پیشنهاد می‌کنید و چرا؟

تعاریف (بر اساس مرز مسئولیت):

  • IaaS: ارائه‌دهنده سخت‌افزار، شبکه و مجازی‌سازی را می‌دهد؛ شما OS، patch، runtime، وب‌سرور و اپ را مدیریت می‌کنید. نمونه: EC2، Droplet. بیشترین کنترل و بیشترین بار عملیاتی.
  • PaaS: شما فقط کد و config را تحویل می‌دهید؛ پلتفرم OS، runtime، scale و deploy را مدیریت می‌کند. نمونه: Heroku، Elastic Beanstalk.
  • SaaS: نرم‌افزار آماده که فقط استفاده می‌شود (Gmail، Jira). برای بخش‌های جانبی (ایمیل تراکنشی، مانیتورینگ خطا) مناسب است.
  • Serverless/FaaS: کد به‌صورت تابع در پاسخ به رویداد اجرا می‌شود، scale خودکار تا صفر و پرداخت به ازای اجرا (Lambda؛ برای Laravel: Vapor یا Bref). معایب: cold start، محدودیت زمان اجرا، vendor lock-in و محدودیت‌های فایل‌سیستم محلی.

Trade-off کلی: از IaaS به SaaS، کنترل و انعطاف کاهش و سرعت توسعه و سادگی عملیات افزایش می‌یابد؛ هزینه‌ی مستقیم معمولاً در PaaS بیشتر و هزینه‌ی نیروی انسانی کمتر است.

پیشنهاد برای تیم کوچک: PaaS یا یک پلتفرم مدیریت‌شده‌ی مخصوص Laravel روی IaaS (ابزارهایی که سرور را provision و deploy را خودکار می‌کنند)، به همراه سرویس‌های مدیریت‌شده برای دیتابیس (RDS یا معادل) و Redis. دلایل:

  • تیم کوچک باید روی محصول تمرکز کند نه patch سیستم‌عامل و تنظیم بکاپ.
  • بکاپ، failover و به‌روزرسانی دیتابیس توسط ارائه‌دهنده انجام می‌شود.
  • اگر ترافیک بسیار نامنظم است، serverless هم گزینه است، به شرط سازگاری کد (stateless، بدون نوشتن روی دیسک محلی).

با رشد و نیاز به کنترل یا کاهش هزینه، می‌توان با IaC به IaaS یا Kubernetes مهاجرت کرد.

Infrastructure as Code چیست و چه مزایایی دارد؟ نقش Terraform و Ansible را مقایسه کنید.

تعریف: مدیریت و provisioning زیرساخت از طریق فایل‌های تعریف قابل‌خواندن توسط ماشین که در git نگهداری می‌شوند، به جای پیکربندی دستی در کنسول یا SSH.

مزایا:

  • تکرارپذیری: ساخت محیط staging یا region جدید با همان کد؛ parity بین محیط‌ها.
  • نسخه‌گذاری و code review: هر تغییر قابل بازبینی، ردیابی و rollback است.
  • حذف configuration drift و «snowflake server»: سرورهایی که با تغییرات دستی منحصربه‌فرد شده‌اند و کسی نمی‌داند چگونه بازسازی‌شان کند.
  • بازیابی سریع در فاجعه (کاهش RTO) و مستندسازی زنده.
  • خودکارسازی در CI/CD.

Terraform: ابزار provisioning؛ منابع زیرساخت (VM، شبکه، LB، دیتابیس مدیریت‌شده، DNS) را با زبان declarative (HCL) تعریف می‌کند. State file نگاشت به منابع واقعی را نگه می‌دارد؛ terraform plan تفاوت وضعیت مطلوب و فعلی را نشان می‌دهد و apply اعمال می‌کند. چندابری با provider.

Ansible: ابزار configuration management؛ داخل سرورهای موجود بسته نصب، فایل config قرار، سرویس مدیریت و اپ deploy می‌کند. Agentless روی SSH، playbookهای YAML، ماژول‌های idempotent.

ترکیب رایج: Terraform سرورها و شبکه را می‌سازد، Ansible آن‌ها را پیکربندی می‌کند؛ یا در مدل immutable، image با Docker/Packer ساخته و Terraform آن را مستقر می‌کند.

نکات: state فایل Terraform حاوی اطلاعات حساس است و باید remote، رمزنگاری‌شده و با lock نگهداری شود؛ secrets در کد قرار نگیرند.

RPO و RTO را تعریف کنید. یک استراتژی بکاپ و Disaster Recovery برای اپلیکیشن Laravel با دیتابیس MySQL طراحی کنید.

RPO (Recovery Point Objective): حداکثر داده‌ای که از دست دادنش قابل قبول است، بر حسب زمان. RPO پنج دقیقه یعنی در بدترین حالت فقط داده‌ی پنج دقیقه‌ی آخر از دست برود. تناوب بکاپ/replication را تعیین می‌کند.

RTO (Recovery Time Objective): حداکثر زمان قابل قبول قطعی تا بازگشت سرویس. میزان خودکارسازی و آماده بودن زیرساخت جایگزین را تعیین می‌کند.

استراتژی (فرض: RPO پانزده دقیقه، RTO یک ساعت):

  • دیتابیس: بکاپ کامل روزانه (mysqldump --single-transaction یا XtraBackup برای حجم بزرگ) + فعال بودن binary log و آرشیو آن هر چند دقیقه برای point-in-time recovery. یک replica برای failover سریع.
  • فایل‌ها: آپلودها در object storage با versioning، یا sync دوره‌ای storage/app.
  • Config و secrets: .env در secret manager؛ زیرساخت با IaC تا سرور جدید سریع ساخته شود.
  • قاعده‌ی 3-2-1: نسخه‌ی خارج از سایت در region یا ارائه‌دهنده‌ی دیگر، رمزنگاری‌شده، با دسترسی محدود و ترجیحاً immutable (مقاوم در برابر ransomware یا حذف تصادفی).
  • Retention: مثلاً ۷ روزانه، ۴ هفتگی، ۱۲ ماهانه؛ مطابق الزامات قانونی.
  • تست restore: بازیابی ماهانه روی محیط جدا، بررسی یکپارچگی داده و اندازه‌گیری زمان (مقایسه با RTO).
  • Runbook: مستند گام‌به‌گام بازیابی و مسئولان؛ مانیتورینگ و هشدار برای شکست بکاپ.

نکته‌ی کلیدی: replication جایگزین بکاپ نیست؛ DROP TABLE اشتباه فوراً روی replica هم اجرا می‌شود.

سناریو: سرور production کند شده و کاربران از timeout شکایت دارند. با چه دستورات و ترتیبی مشکل را عیب‌یابی می‌کنید؟

رویکرد: از کلی به جزئی؛ اول منبع محدودکننده (CPU، حافظه، دیسک، شبکه، وابستگی خارجی) را پیدا می‌کنم.

  1. تصویر کلی: uptime (مقایسه‌ی load با nproc)، top/htop: کدام فرایند CPU یا RAM را گرفته؟ درصد wa (انتظار I/O) بالاست؟
  2. حافظه: free -h (available)، vmstat 1 (swap si/so)، dmesg -T | grep -i oom.
  3. دیسک: df -h و df -i (پر بودن دیسک باعث شکست نوشتن لاگ و session می‌شود)، iostat -x 1.
  4. سرویس‌ها: systemctl --failed، systemctl status php8.3-fpm nginx mysql، journalctl -u php8.3-fpm --since "30 min ago".
  5. PHP-FPM: لاگ برای max_children reached، slowlog برای stack trace درخواست‌های کند، صفحه‌ی status (listen queue).
  6. شبکه و اتصال‌ها: ss -s و ss -tanp (تعداد اتصال‌ها، TIME_WAIT زیاد، اتصال‌های معلق به سرویس خارجی).
  7. لاگ‌ها: error log Nginx (502/504)، storage/logs/laravel.log؛ مقایسه‌ی زمان شروع مشکل با آخرین deploy.
  8. دیتابیس: SHOW PROCESSLIST (کوئری‌های طولانی، قفل‌ها)، slow query log.
  9. فرایند مشکوک: strace -p PID یا lsof -p PID برای دیدن اینکه worker منتظر چیست.

اقدام: کاهش فوری اثر (rollback deploy اخیر، kill کوئری قفل‌کننده، افزایش موقت منابع، غیرفعال کردن قابلیت سنگین) و سپس رفع ریشه‌ای و postmortem. در ادامه هشدارهای مانیتورینگ را طوری تنظیم می‌کنم که دفعه‌ی بعد قبل از کاربران مطلع شویم.

Load balancer چیست و چه الگوریتم‌هایی دارد؟ برای اینکه یک اپلیکیشن Laravel بتواند پشت load balancer روی چند سرور اجرا شود چه تغییراتی لازم است؟

تعریف: جزئی که ترافیک ورودی را بین چند سرور backend توزیع می‌کند تا ظرفیت (scale افقی) و دسترس‌پذیری بالا برود؛ سرورهای ناسالم با health check از چرخه خارج می‌شوند. نوعی reverse proxy است. L4 در سطح TCP/UDP و L7 در سطح HTTP (مسیریابی بر اساس مسیر، header یا cookie) کار می‌کند.

الگوریتم‌ها: Round robin (نوبتی، با وزن)، Least connections (برای درخواست‌هایی با زمان متغیر)، IP hash (چسبندگی کلاینت به یک سرور)، و در برخی LBها least response time.

تغییرات لازم در Laravel (stateless کردن):

  • Session: driver از file به redis یا database؛ وگرنه کاربر با رفتن به سرور دیگر logout می‌شود (یا نیاز به sticky session که توزیع را ناهموار می‌کند).
  • Cache و lockها: Redis مشترک تا Cache::lock و rate limiting بین سرورها معتبر باشد.
  • فایل‌ها: آپلودها روی دیسک مشترک یا object storage (S3) با Laravel Filesystem.
  • Queue: Redis/SQS/database مشترک؛ workerها روی هر سرور یا سرورهای مجزا.
  • Scheduler: تسک‌ها با onOneServer() تا روی همه‌ی سرورها تکرار نشوند.
  • Trusted proxies: تنظیم trustProxies تا IP واقعی کاربر و HTTPS از X-Forwarded-* تشخیص داده شود.
  • APP_KEY یکسان روی همه‌ی سرورها (برای cookieها و داده‌ی رمزشده) و deploy هم‌زمان نسخه‌ی یکسان.
  • Health check endpoint (/up) و لاگ متمرکز (چون لاگ‌ها روی چند سرور پخش‌اند).

خود load balancer هم نباید SPOF باشد: LB مدیریت‌شده‌ی ابری یا جفت LB با IP شناور.

خلاصه برای مرور سریع

سیستم‌عامل

  • Kernel space: سخت‌افزار و دسترسی کامل؛ User space: ایزوله؛ ارتباط با syscall.
  • Process: حافظه‌ی ایزوله؛ Thread: حافظه‌ی مشترک، stack جدا؛ Coroutine: user space، cooperative.
  • حالت‌ها: New، Ready، Running، Waiting، Terminated؛ ps: R، S، D، T، Z.
  • Zombie: تمام‌شده، wait نشده؛ Orphan: والد مرده → PID 1.
  • Context switch: ذخیره/بارگذاری وضعیت؛ سربار + از دست رفتن cache.
  • Load average را با nproc مقایسه کن.

هم‌روندی

  • Concurrency = مدیریت چند کار؛ Parallelism = اجرای هم‌زمان واقعی.
  • Race: read-modify-write غیراتمیک → UPDATE شرطی، lockForUpdate، optimistic version، Cache::lock.
  • Mutex: یک صاحب؛ Semaphore: N مجوز.
  • Deadlock (Coffman): mutual exclusion، hold & wait، no preemption، circular wait → ترتیب ثابت قفل، تراکنش کوتاه، retry.

حافظه و فایل

  • Virtual memory: page table، MMU، TLB؛ page fault minor/major.
  • Swap مداوم = thrashing؛ vmstat si/so.
  • OOM killer: SIGKILL بر اساس oom_score → dmesg.
  • free: ستون available؛ RSS واقعی، VSZ مجازی.
  • inode: متادیتا بدون نام؛ df -i.
  • Hard link: همان inode؛ Symlink: مسیر.
  • FD: 0 stdin، 1 stdout، 2 stderr؛ ulimit -n، LimitNOFILE.
  • حذف‌شده ولی باز: lsof +L1.

دسترسی

  • r=4، w=2، x=1؛ 755، 644، 640، 600.
  • setuid 4، setgid 2 (دایرکتوری: ارث گروه)، sticky 1 (/tmp).
  • umask 022 → 644/755؛ 002 → 664/775.
  • Laravel: deploy:www-data، storage و bootstrap/cache قابل نوشتن گروه؛ هرگز 777.
  • usermod -aG؛ visudo؛ sudo محدود.

دستورات و سیگنال

  • ps aux، top، free -h، df -h/-i، du -sh، lsof -i :80، ss -tulpn.
  • journalctl -u x -f، systemctl status/reload/enable --now.
  • SIGTERM 15 مؤدبانه؛ SIGKILL 9 غیرقابل catch؛ SIGHUP 1 reload؛ SIGINT 2 Ctrl+C.
  • FPM: USR2 reload؛ Nginx: HUP reload، QUIT graceful.

سرویس‌ها

  • systemd unit: Restart=always، TimeoutStopSec؛ daemon-reload.
  • Supervisor: numprocs، stopwaitsecs > طولانی‌ترین job؛ reread/update.
  • Deploy: queue:restart؛ cron هر دقیقه schedule:run.

شبکه و وب

  • ufw: deny incoming، allow OpenSSH قبل از enable، 80/443.
  • Docker می‌تواند ufw را دور بزند.
  • SSH: ed25519، no root، no password، fail2ban، sshd -t.
  • Nginx → FastCGI → FPM؛ root = public؛ $realpath_root.
  • 502: FPM در دسترس نیست/سوکت؛ 504: FPM کند.
  • LB: round robin، least_conn، ip_hash؛ L4 در برابر L7؛ اپ stateless.
  • TLS: محرمانگی، یکپارچگی، احراز هویت؛ Let's Encrypt با ACME، ۹۰ روز، HTTP-01/DNS-01 (wildcard).

زیرساخت

  • dev / CI / staging (مشابه prod) / production.
  • VM: کرنل جدا، hypervisor؛ Container: namespaces + cgroups، کرنل مشترک.
  • IaaS → PaaS → SaaS: کنترل کمتر، بار عملیاتی کمتر؛ Serverless: cold start، lock-in.
