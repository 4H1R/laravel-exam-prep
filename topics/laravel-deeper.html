Laravel Deeper

سازوکارهای درونی و زیرسیستم‌های پیشرفته Laravel: Service Container و Service Providerها در عمق، درون Facadeها، صف و Job، رویدادها و Broadcasting، Cache و قفل اتمیک، زمان‌بندی، مجوزدهی و احراز هویت API، Pipeline، تست، Octane و نکات استقرار و امنیت.

Service Container در عمق

Service Container قلب Laravel است: یک IoC Container که دو کار اصلی انجام می‌دهد: ثبت (binding) یعنی «وقتی کسی X خواست، این‌طور بسازش» و حل وابستگی (resolving) یعنی ساختن شیء همراه با تمام وابستگی‌هایش. خود شیء Illuminate\Foundation\Application از Illuminate\Container\Container ارث می‌برد؛ پس app() همان کانتینر است. Controllerها، Middlewareها، Jobها، Listenerها، Commandها و Policyها همه از طریق کانتینر ساخته می‌شوند و به همین دلیل type-hint در constructor آن‌ها «خودبه‌خود کار می‌کند».

انواع binding

متدطول عمر نمونهکاربرد معمول
bindهر بار make یک نمونه جدید (transient)سرویس‌های بدون state یا وقتی هر مصرف‌کننده نمونه مستقل لازم دارد
singletonیک نمونه برای کل عمر Application (در PHP-FPM یعنی یک درخواست؛ در Octane و Queue Worker یعنی تا ری‌استارت پروسه)کلاینت‌های پرهزینه، سرویس‌های بدون state وابسته به درخواست
scopedیک نمونه در هر «چرخه» درخواست یا Job؛ Octane و Queue Worker در شروع هر درخواست/Job آن را flush می‌کنندسرویس‌هایی که state مربوط به درخواست جاری دارند (tenant فعلی، کاربر فعلی)
instanceشیئی که خودتان از قبل ساخته‌اید به‌عنوان singleton ثبت می‌شودتست‌ها، اشیای ساخته‌شده بیرون از کانتینر
 
<?php
use App\Contracts\PaymentGateway;
use App\Services\ZarinpalGateway;
use Illuminate\Contracts\Foundation\Application;

// داخل register() یک ServiceProvider
$this->app->bind(ReportBuilder::class, fn (Application $app) => new ReportBuilder($app->make(Exporter::class)));

$this->app->singleton(PaymentGateway::class, function (Application $app) {
    return new ZarinpalGateway(config('services.zarinpal.merchant_id'));
});

$this->app->scoped(TenantContext::class, fn () => new TenantContext());

$this->app->instance(Clock::class, new FrozenClock('2026-11-11 12:45'));

// نسخه‌های شرطی: فقط اگر قبلاً ثبت نشده باشد
$this->app->singletonIf(Exporter::class, CsvExporter::class);

تفاوت singleton و scoped فقط در محیط‌های long-running (Octane، Queue Worker) معنا پیدا می‌کند. در PHP-FPM معمولی هر درخواست پروسه را از صفر boot می‌کند، پس هر دو عملاً یکسان رفتار می‌کنند.

Auto-resolution با Reflection (Autowiring)

اگر برای یک کلاس concrete هیچ bindingی ثبت نشده باشد، کانتینر با Reflection API خود PHP آن را می‌سازد. به همین دلیل اکثر کلاس‌ها اصلاً نیازی به binding ندارند. مراحل متد build():

  1. با ReflectionClass بررسی می‌کند کلاس instantiable است یا نه (interface و abstract نیستند).
  2. constructor را می‌خواند؛ اگر constructor نداشته باشد، مستقیم new می‌کند.
  3. برای هر پارامتر: اگر type آن یک کلاس یا interface باشد، به‌صورت بازگشتی make می‌کند؛ اگر primitive باشد (string، int) و مقدار پیش‌فرض داشته باشد از آن استفاده می‌کند، وگرنه BindingResolutionException می‌دهد.
  4. نتیجه را با newInstanceArgs می‌سازد و resolving callbackها را اجرا می‌کند.
<?php
class InvoiceService
{
    // هیچ binding لازم نیست؛ کانتینر Mailer و InvoiceRepository را خودش می‌سازد
    public function __construct(
        private InvoiceRepository $invoices,
        private Mailer $mailer,
        private int $dueDays = 30, // primitive با مقدار پیش‌فرض: مشکلی نیست
    ) {}
}

// خطای رایج: interface بدون binding
// Target [App\Contracts\PaymentGateway] is not instantiable while building [CheckoutController].

bind کردن interface به implementation

این مهم‌ترین کاربرد کانتینر در معماری تمیز است: کد مصرف‌کننده به abstraction وابسته است (اصل Dependency Inversion) و تصمیم «کدام پیاده‌سازی» در یک جای مرکزی گرفته می‌شود. تعویض درگاه پرداخت یا Mock کردن در تست فقط یک خط تغییر است.

<?php
$this->app->bind(PaymentGateway::class, ZarinpalGateway::class);

// یا با property در ServiceProvider (برای bindingهای ساده)
public array $bindings = [
    PaymentGateway::class => ZarinpalGateway::class,
];
public array $singletons = [
    SmsSender::class => KavenegarSmsSender::class,
];

Contextual Binding

وقتی دو کلاس به یک interface نیاز دارند ولی هرکدام پیاده‌سازی متفاوتی می‌خواهند:

<?php
use Illuminate\Contracts\Filesystem\Filesystem;
use Illuminate\Support\Facades\Storage;

$this->app->when(PhotoController::class)
    ->needs(Filesystem::class)
    ->give(fn () => Storage::disk('local'));

$this->app->when([VideoController::class, UploadController::class])
    ->needs(Filesystem::class)
    ->give(fn () => Storage::disk('s3'));

// تزریق مقدار primitive
$this->app->when(SmsSender::class)
    ->needs('$apiKey')
    ->giveConfig('services.kavenegar.key');

در نسخه‌های اخیر Laravel 11 به بعد، Contextual Attributeها هم اضافه شده‌اند که همین کار را در خود امضای constructor انجام می‌دهند؛ مثل #[Config('app.timezone')] string $tz، #[Storage('s3')] Filesystem $disk و #[CurrentUser] User $user (از فضای نام Illuminate\Container\Attributes).

Tagging، extend و resolving callback

<?php
// Tagging: گروه‌بندی چند binding و resolve یکجا
$this->app->tag([CpuReport::class, MemoryReport::class], 'reports');
$this->app->bind(ReportAggregator::class, fn ($app) => new ReportAggregator($app->tagged('reports')));

// extend: تزئین (Decorator) یک سرویس بعد از ساخته شدن
$this->app->extend(PaymentGateway::class, function (PaymentGateway $gateway, $app) {
    return new LoggingPaymentGateway($gateway, $app->make(LoggerInterface::class));
});

// resolving: هر بار که نوعی resolve شد، روی آن کاری انجام بده
$this->app->resolving(ApiClient::class, function (ApiClient $client, $app) {
    $client->setUserAgent('MyApp/1.0');
});
$this->app->afterResolving(ApiClient::class, fn ($client) => /* ... */ null);

گرفتن نمونه و Method Injection

  • app(Foo::class)، resolve(Foo::class)، $this->app->make(Foo::class) معادل‌اند؛ makeWith(Foo::class, ['id' => 5]) پارامترهای ناقص را تکمیل می‌کند.
  • app()->bound(Foo::class) و app()->has() وجود binding را بررسی می‌کنند.
  • Method injection: علاوه بر constructor، کانتینر پارامترهای متدهایی مثل action کنترلر، handle() در Job و Command، و boot() در Provider را هم تزریق می‌کند. خودتان هم می‌توانید با App::call([$obj, 'method']) یا app()->call(fn (Mailer $m) => ...) از آن استفاده کنید.

صدا زدن app() یا resolve() در وسط منطق کسب‌وکار یعنی الگوی Service Locator: وابستگی‌ها پنهان می‌شوند و تست سخت‌تر می‌شود. تا جایی که می‌شود از constructor injection استفاده کنید.

Service Providerها و توسعه پکیج

Service Provider محل مرکزی bootstrap کردن برنامه است: ثبت bindingها در کانتینر، ثبت event listener، middleware، route، macro، view composer و هر پیکربندی دیگر. خود Laravel هم تمام زیرسیستم‌هایش (Cache، Queue، Mail، Database…) را با Providerها ثبت می‌کند. در Laravel 11 به بعد، Providerهای برنامه در فایل bootstrap/providers.php فهرست می‌شوند (در Laravel ≤10 در آرایه providers فایل config/app.php) و make:provider آن را خودکار به این فایل اضافه می‌کند.

register در برابر boot و چرا این تفکیک وجود دارد

register()

  • فقط و فقط binding در کانتینر.
  • برای همه Providerها اول register اجرا می‌شود و بعد boot.
  • نباید از سرویس دیگری استفاده کنید؛ ممکن است Provider آن هنوز register نشده باشد.
  • mergeConfigFrom پکیج اینجاست.

boot()

  • بعد از register همه Providerها اجرا می‌شود؛ همه سرویس‌ها در دسترس‌اند.
  • ثبت Gate و Policy، RateLimiter::for، Event::listen، macroها، view composer، Model::preventLazyLoading().
  • از method injection پشتیبانی می‌کند: boot(Dispatcher $events).

دلیل این طراحی، ترتیب نامعلوم Providerهاست. Laravel اول نقشه کامل «چه چیزی را چطور بسازم» را کامل می‌کند (فاز register) و بعد اجازه استفاده از سرویس‌ها را می‌دهد (فاز boot). اگر در register مثلاً Route:: یا Auth:: را صدا بزنید، ممکن است سرویس پشت آن هنوز ثبت نشده باشد یا زودتر از موعد و با پیکربندی ناقص ساخته شود.

<?php
namespace App\Providers;

use App\Contracts\PaymentGateway;
use App\Services\ZarinpalGateway;
use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->singleton(PaymentGateway::class, ZarinpalGateway::class);
    }

    public function boot(): void
    {
        RateLimiter::for('api', fn (Request $request) =>
            Limit::perMinute(60)->by($request->user()?->id ?: $request->ip()));
    }
}

Deferred Provider

Providerی که فقط binding ثبت می‌کند را می‌توان deferred کرد تا تنها زمانی load شود که یکی از سرویس‌هایش واقعاً درخواست شود. Laravel فهرست سرویس‌های هر deferred provider را در bootstrap/cache/services.php کش می‌کند و در هر درخواست به‌جای register همه، فقط نقشه را می‌خواند؛ نتیجه، boot سریع‌تر است.

<?php
use Illuminate\Contracts\Support\DeferrableProvider;

class RiakServiceProvider extends ServiceProvider implements DeferrableProvider
{
    public function register(): void
    {
        $this->app->singleton(Connection::class, fn ($app) => new Connection(config('riak')));
    }

    public function provides(): array
    {
        return [Connection::class];
    }
}

Providerی که در boot() کار جانبی دارد (ثبت route، listener، macro) نباید deferred باشد؛ چون ممکن است هرگز load نشود و آن کارها انجام نشوند.

Package Auto-Discovery

پکیج‌ها در composer.json خود، Provider و Facade را اعلام می‌کنند و Laravel بعد از composer install با اسکریپت package:discover آن‌ها را خودکار ثبت می‌کند (نتیجه در bootstrap/cache/packages.php). برنامه می‌تواند با dont-discover در composer.json خودش جلوی کشف یک پکیج را بگیرد.

{
  "extra": {
    "laravel": {
      "providers": ["Acme\\Invoices\\InvoicesServiceProvider"],
      "aliases": { "Invoices": "Acme\\Invoices\\Facades\\Invoices" }
    }
  }
}

مبانی توسعه پکیج

یک پکیج Laravel در اصل یک پکیج Composer با یک Service Provider است. ابزارهای اصلی Provider پکیج:

<?php
class InvoicesServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // config پیش‌فرض پکیج با config برنامه ادغام می‌شود
        $this->mergeConfigFrom(__DIR__.'/../config/invoices.php', 'invoices');
        $this->app->singleton(InvoiceManager::class);
    }

    public function boot(): void
    {
        $this->loadRoutesFrom(__DIR__.'/../routes/web.php');
        $this->loadViewsFrom(__DIR__.'/../resources/views', 'invoices'); // view('invoices::pdf')
        $this->loadMigrationsFrom(__DIR__.'/../database/migrations');
        $this->loadTranslationsFrom(__DIR__.'/../lang', 'invoices');

        $this->publishes([
            __DIR__.'/../config/invoices.php' => config_path('invoices.php'),
        ], 'invoices-config'); // php artisan vendor:publish --tag=invoices-config

        if ($this->app->runningInConsole()) {
            $this->commands([GenerateInvoicesCommand::class]);
        }
    }
}

برای تست پکیج بیرون از یک برنامه کامل، از Orchestra Testbench استفاده می‌شود که یک Application مینیمال برای تست فراهم می‌کند.

درون Facadeها و Contracts

Facade یک کلاس با رابط static است که فراخوانی را به یک شیء واقعی در کانتینر پراکسی می‌کند. پس Cache::get('key') در واقع متد static نیست؛ معادل app('cache')->get('key') است. (مقدمه Facade در صفحه Laravel Basics آمده؛ اینجا سازوکار درونی را می‌بینیم.)

یک فراخوانی Facade قدم به قدم

   │  متد static به نام get در کلاس Facade وجود ندارد
   ▼
Facade::__callStatic('get', ['key'])
   │
   ▼
static::getFacadeRoot()
   │  getFacadeAccessor()  ──►  'cache'
   ▼

   │  اگر در static::$resolvedInstance کش شده بود همان را برگردان
   │  وگرنه  static::$app['cache']   (یعنی $app->make('cache'))
   ▼

<?php
// تعریف یک Facade سفارشی
namespace App\Facades;

use Illuminate\Support\Facades\Facade;

/**
 * @method static bool charge(int $amount, string $token)
 * @see \App\Services\ZarinpalGateway
 */
class Payment extends Facade
{
    protected static function getFacadeAccessor(): string
    {
        return \App\Contracts\PaymentGateway::class; // کلید binding در کانتینر
    }
}

// استفاده
Payment::charge(50000, $token);

docblockهای @method فقط برای IDE و ابزارهای تحلیل ایستا است؛ اجرای واقعی با __callStatic انجام می‌شود.

Real-time Facade

با پیشوند Facades\ در namespace، هر کلاسی بدون تعریف کلاس Facade، رابط Facade پیدا می‌کند. Laravel کلاس Facade را در زمان اجرا تولید و کش می‌کند (در storage/framework/cache).

<?php
use Facades\App\Services\ExchangeRateService;

$rate = ExchangeRateService::usdToIrr();   // پشت صحنه: app(ExchangeRateService::class)->usdToIrr()

// در تست
ExchangeRateService::shouldReceive('usdToIrr')->andReturn(600000);

تست با Facadeها

<?php
use Illuminate\Support\Facades\Cache;
use Illuminate\Support\Facades\Mail;
use Illuminate\Support\Facades\Queue;

Cache::shouldReceive('get')->once()->with('settings')->andReturn(['theme' => 'dark']);

Queue::fake();   // Jobها push نمی‌شوند، فقط ثبت می‌شوند
Mail::fake();
// ... اجرای کد
Queue::assertPushed(ProcessOrder::class, fn ($job) => $job->order->id === 1);
Mail::assertSent(OrderShipped::class);

متدهای shouldReceive، spy، partialMock و expects روی همه Facadeها در دسترس‌اند (Mockery). Facadeهایی مثل Queue، Bus، Event، Mail، Notification، Storage و Http متد fake() اختصاصی دارند که شیء واقعی را با یک Fake قابل assert جایگزین می‌کند.

Contracts

Contracts مجموعه interfaceهای Illuminate\Contracts\* است که سرویس‌های هسته را تعریف می‌کنند؛ مثل Illuminate\Contracts\Cache\Repository، Illuminate\Contracts\Queue\Queue، Illuminate\Contracts\Mail\Mailer، Illuminate\Contracts\Auth\Guard. هر Facade معادل یک Contract دارد. type-hint روی Contract یعنی:

  • loose coupling: کد شما به interface وابسته است نه به پیاده‌سازی Redis یا File.
  • وابستگی صریح در constructor (بر خلاف Facade).
  • برای نویسندگان پکیج بهترین گزینه است؛ چون پکیج به جزئیات فریم‌ورک گره نمی‌خورد.

Contractهای علامت‌گذار (marker) هم داریم که متدی ندارند و فقط رفتار را فعال می‌کنند: ShouldQueue، ShouldBroadcast، ShouldBeUnique، DeferrableProvider.

صف‌ها و Jobها: مبانی

Queue کارهای زمان‌بر یا ناپایدار (ارسال ایمیل و SMS، پردازش تصویر، فراخوانی API خارجی، تولید گزارش) را از چرخه درخواست HTTP بیرون می‌برد تا پاسخ سریع برگردد و کار در پس‌زمینه توسط Worker انجام شود. مزایا: زمان پاسخ کمتر، retry خودکار در خطاهای گذرا، کنترل نرخ و موازی‌سازی، و جداسازی خرابی‌ها.

آناتومی یک Job

<?php
namespace App\Jobs;

use App\Models\Podcast;
use App\Services\AudioProcessor;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;

class ProcessPodcast implements ShouldQueue
{
    use Queueable; // Laravel 11: شامل Dispatchable, InteractsWithQueue, Queueable, SerializesModels

    public int $tries = 3;
    public int $timeout = 120;

    public function __construct(public Podcast $podcast) {}

    // وابستگی‌های handle با method injection از کانتینر می‌آیند
    public function handle(AudioProcessor $processor): void
    {
        $processor->process($this->podcast);
    }
}

در Laravel ≤10 کلاس Job چهار trait جدا داشت: Dispatchable, InteractsWithQueue, Queueable, SerializesModels. در Laravel 11 همه در trait واحد Illuminate\Foundation\Queue\Queueable جمع شده‌اند.

SerializesModels: چه چیزی واقعاً در صف ذخیره می‌شود؟

وقتی یک مدل Eloquent را به Job می‌دهید، کل مدل serialize نمی‌شود؛ فقط کلاس و کلید اصلی (و relationهای load شده) ذخیره می‌شود و Worker هنگام اجرا مدل را دوباره از دیتابیس می‌خواند. نتیجه‌ها:

  • payload کوچک می‌ماند و Job با داده تازه کار می‌کند.
  • اگر مدل تا زمان اجرا حذف شود، ModelNotFoundException رخ می‌دهد. با public bool $deleteWhenMissingModels = true; Job بی‌صدا حذف می‌شود.
  • closure، resource، اتصال PDO و اشیای غیرقابل serialize را در property قرار ندهید.

ProcessPodcast::dispatchSync($podcast);                     // فوراً و همزمان، بدون صف
ProcessPodcast::dispatchAfterResponse($podcast);            // بعد از ارسال پاسخ به کاربر، در همان پروسه
ProcessPodcast::dispatch($podcast)->afterCommit();          // فقط بعد از commit تراکنش جاری

dispatch(function () use ($podcast) {                       // Closure job
    $podcast->publish();
});

مشکل dispatch داخل تراکنش و afterCommit

اگر Job را داخل DB::transaction dispatch کنید، ممکن است Worker قبل از commit آن را بردارد؛ رکورد هنوز در دیتابیس دیده نمی‌شود (ModelNotFound) یا اگر تراکنش rollback شود، Job برای داده‌ای اجرا می‌شود که هرگز وجود نداشته (مثلاً ایمیل تأیید سفارشی که ثبت نشد).

<?php
DB::transaction(function () use ($request) {
    $order = Order::create($request->validated());
    SendOrderConfirmation::dispatch($order)->afterCommit(); // تا commit صبر می‌کند؛ با rollback دور ریخته می‌شود
});

می‌توان در config/queue.php برای یک connection گزینه 'after_commit' => true را فعال کرد تا همه Jobهای آن رفتار afterCommit داشته باشند؛ متد beforeCommit() هم برعکس عمل می‌کند. همین مفهوم برای Event Listenerها، Mail و Notificationهای صف‌شده هم وجود دارد.

قابلیت اطمینان Jobها: retry، timeout، failed، unique

تلاش مجدد و زمان‌بندی آن

$tries
حداکثر دفعات اجرا. پیش‌فرض worker برابر 1 است (--tries). property خود Job بر گزینه worker مقدم است.
$maxExceptions
حداکثر تعداد exception مجاز؛ با آن می‌توان tries زیاد (مثلاً برای release دستی) ولی exception کم داشت.
$backoff / backoff()
فاصله بین تلاش‌ها به ثانیه؛ آرایه مثل [10, 60, 300] یعنی exponential backoff.
retryUntil()
به‌جای تعداد، یک مهلت زمانی برمی‌گرداند؛ تا آن زمان Job هر چند بار لازم باشد تکرار می‌شود.
$timeout
حداکثر ثانیه اجرای یک تلاش؛ worker پروسه فرزند را kill می‌کند (نیازمند افزونه pcntl). با $failOnTimeout = true Job مستقیم fail می‌شود.
retry_after
در config/queue.php؛ اگر Job بعد از این مدت هنوز تمام نشده باشد، connection فرض می‌کند worker مرده و Job را دوباره در دسترس قرار می‌دهد.

قانون طلایی: --timeout باید همیشه چند ثانیه کمتر از retry_after باشد. در غیر این صورت Job هنوز در حال اجراست که کپی دومش توسط worker دیگری برداشته می‌شود و Job دو بار اجرا می‌شود (ایمیل یا شارژ دوباره).

<?php
class SyncInvoiceToAccounting implements ShouldQueue
{
    use Queueable;

    public int $tries = 5;
    public int $maxExceptions = 3;
    public int $timeout = 30;

    public function backoff(): array
    {
        return [10, 60, 300];
    }

    public function handle(AccountingApi $api): void
    {
        if (! $api->isAvailable()) {
            $this->release(120); // دستی به صف برگردان؛ یک tries مصرف می‌شود
            return;
        }
        $api->push($this->invoice);
    }

    public function failed(?\Throwable $e): void
    {
        // بعد از تمام شدن همه تلاش‌ها: اطلاع به تیم، علامت‌گذاری رکورد و ...
        $this->invoice->update(['sync_status' => 'failed']);
    }
}

Unique Jobs

با پیاده‌سازی ShouldBeUnique، اگر نمونه‌ای با همان uniqueId در صف یا در حال اجرا باشد، dispatch جدید نادیده گرفته می‌شود. این کار با قفل Cache انجام می‌شود، پس درایور cache باید از lock پشتیبانی کند (redis، database، memcached، dynamodb، file، array).

<?php
use Illuminate\Contracts\Queue\ShouldBeUnique;

class RecalculateProductStock implements ShouldQueue, ShouldBeUnique
{
    use Queueable;

    public int $uniqueFor = 3600; // قفل حداکثر یک ساعت

    public function __construct(public Product $product) {}

    public function uniqueId(): string
    {
        return (string) $this->product->id;
    }
}

ShouldBeUniqueUntilProcessing قفل را به‌محض شروع پردازش آزاد می‌کند (نه پایان)، تا در حین اجرا بتوان یک نمونه جدید در صف گذاشت.

Job Middleware

منطق‌های تکراری حول اجرای Job (قفل، محدودیت نرخ، throttle خطا) را از handle بیرون می‌کشد. متد middleware() آرایه‌ای از middlewareها برمی‌گرداند:

<?php
use Illuminate\Queue\Middleware\RateLimited;
use Illuminate\Queue\Middleware\ThrottlesExceptions;
use Illuminate\Queue\Middleware\WithoutOverlapping;

public function middleware(): array
{
    return [
        // دو Job برای یک کاربر همزمان اجرا نشوند (قفل cache)
        (new WithoutOverlapping($this->user->id))->releaseAfter(60)->expireAfter(180),

        // از limiter تعریف‌شده با RateLimiter::for('backups', ...) استفاده می‌کند
        new RateLimited('backups'),

        // اگر سرویس خارجی پشت سر هم خطا داد، مدتی دست نگه دار
        (new ThrottlesExceptions(10, 5 * 60))->backoff(5),
    ];
}

ShouldBeUnique

  • در زمان dispatch عمل می‌کند.
  • نسخه تکراری اصلاً وارد صف نمی‌شود.
  • برای جلوگیری از کار اضافه (dedupe).

WithoutOverlapping

  • در زمان اجرا عمل می‌کند.
  • همه Jobها وارد صف می‌شوند ولی همزمان اجرا نمی‌شوند؛ تکراری release می‌شود.
  • برای جلوگیری از race condition روی یک منبع.

Idempotency را جدی بگیرید: چون هر Job ممکن است بیش از یک بار اجرا شود (retry، timeout، crash worker)، طراحی کنید که اجرای دوباره آسیبی نزند؛ مثلاً قبل از شارژ وضعیت را چک کنید، از کلید یکتا (idempotency key) در API پرداخت و از updateOrCreate به‌جای create استفاده کنید.

Chain، Batch، Worker و Horizon

Job Chaining

اجرای ترتیبی چند Job؛ هر Job فقط در صورت موفقیت قبلی اجرا می‌شود و اگر یکی fail شود بقیه زنجیره اجرا نمی‌شوند.

<?php
use Illuminate\Support\Facades\Bus;

Bus::chain([
    new ProcessPodcast($podcast),
    new OptimizePodcast($podcast),
    new ReleasePodcast($podcast),
])->onQueue('media')
  ->catch(function (\Throwable $e) {
      // یکی از Jobهای زنجیره شکست خورد
  })
  ->dispatch();

Job Batching

اجرای موازی گروهی از Jobها با امکان پیگیری پیشرفت و callback در پایان. Jobها باید trait Batchable داشته باشند و جدول job_batches لازم است (make:queue-batches-table).

<?php
use Illuminate\Bus\Batch;

$batch = Bus::batch(
    $rows->chunk(500)->map(fn ($chunk) => new ImportCustomers($chunk))->all()
)->name('Import customers')
 ->allowFailures()                                  // بدون آن، اولین شکست batch را cancelled می‌کند
 ->then(fn (Batch $batch) => /* همه موفق */ null)
 ->catch(fn (Batch $batch, \Throwable $e) => /* اولین شکست */ null)
 ->finally(fn (Batch $batch) => /* در هر حال */ null)
 ->dispatch();

// بعداً
$batch = Bus::findBatch($batchId);
$batch->progress();     // درصد
$batch->failedJobs;

// داخل Job
public function handle(): void
{
    if ($this->batch()->cancelled()) {
        return;
    }
    // ...
}
ChainBatch
اجراترتیبی، یکی بعد از دیگریموازی بین workerها
وابستگیمرحله بعد به نتیجه قبلی وابسته استJobها مستقل‌اند
شکستبقیه زنجیره اجرا نمی‌شوندbatch لغو می‌شود مگر allowFailures
پیگیرینداردprogress، تعداد موفق/ناموفق، جدول job_batches

می‌توان این دو را ترکیب کرد: یک chain داخل batch (آرایه تو در تو) یا یک batch به‌عنوان حلقه‌ای از chain.

queue:work در برابر queue:listen

queue:work

  • پروسه long-running؛ فریم‌ورک یک بار boot می‌شود و در حافظه می‌ماند.
  • بسیار سریع‌تر؛ مخصوص production.
  • تغییرات کد را نمی‌بیند؛ بعد از deploy باید ری‌استارت شود.
  • مراقب نشت حافظه و state ماندگار (مثل Octane).

queue:listen

  • برای هر Job فریم‌ورک را از نو boot می‌کند.
  • کندتر، ولی تغییرات کد را فوراً می‌بیند.
  • مناسب محیط توسعه.
php artisan queue:work redis --queue=high,default --tries=3 --timeout=60 \
    --sleep=3 --max-jobs=1000 --max-time=3600 --memory=256
php artisan queue:work --once            # فقط یک Job
php artisan queue:work --stop-when-empty # مناسب کانتینرهای موقت
php artisan queue:restart                # به همه workerها سیگنال ری‌استارت نرم می‌دهد

queue:restart یک timestamp در cache می‌نویسد؛ هر worker بعد از تمام کردن Job جاری آن را می‌بیند و با ظرافت خارج می‌شود و Supervisor آن را با کد جدید بالا می‌آورد. پس درایور cache باید بین سرورها مشترک باشد و این دستور باید جزو اسکریپت deploy باشد. گزینه‌های --max-jobs و --max-time هم با خروج دوره‌ای جلوی نشت حافظه را می‌گیرند.

Laravel Horizon

Horizon داشبورد و مدیر workerها برای صف‌های Redis است. به‌جای چند خط Supervisor، پیکربندی workerها (supervisorها، صف‌ها، تعداد پروسه، استراتژی auto-balancing) در کد و فایل config/horizon.php نگه‌داری می‌شود و داشبورد آن throughput، زمان اجرا، Jobهای ناموفق، tagها و متریک‌ها را نشان می‌دهد.

composer require laravel/horizon
php artisan horizon:install

php artisan horizon:terminate   # در deploy، به‌جای queue:restart

داشبورد Horizon در production فقط با Gate viewHorizon (در HorizonServiceProvider) باز می‌شود؛ فراموش کردن تعریف آن یعنی یا کسی دسترسی ندارد یا (در صورت پیکربندی اشتباه) همه دارند.

Events، Listeners و Broadcasting

Event پیاده‌سازی الگوی Observer / Pub-Sub درون برنامه است: کدی که اتفاقی را اعلام می‌کند (OrderPlaced) نمی‌داند چه کسانی به آن واکنش نشان می‌دهند (ارسال ایمیل، به‌روزرسانی موجودی، ثبت آمار). نتیجه، decoupling و رعایت Single Responsibility است: اضافه کردن واکنش جدید بدون دست زدن به کد سفارش.

تعریف و dispatch

<?php
// php artisan make:event OrderPlaced
class OrderPlaced
{
    use Dispatchable, InteractsWithSockets, SerializesModels;

    public function __construct(public Order $order) {}
}

// php artisan make:listener SendOrderConfirmation --event=OrderPlaced
class SendOrderConfirmation
{
    public function handle(OrderPlaced $event): void
    {
        Mail::to($event->order->user)->send(new OrderConfirmed($event->order));
    }
}

// اعلام رویداد
OrderPlaced::dispatch($order);
// یا: event(new OrderPlaced($order));

ثبت Listener: Event Discovery

در Laravel 11، Event Discovery به‌صورت پیش‌فرض فعال است: فریم‌ورک پوشه app/Listeners را اسکن می‌کند و هر متد handle (یا __invoke) را بر اساس type-hint پارامترش به رویداد مربوط وصل می‌کند. پوشه‌های دیگر را با ->withEvents(discover: [...]) در bootstrap/app.php اضافه کنید. ثبت دستی هم ممکن است:

<?php
// AppServiceProvider::boot()
Event::listen(OrderPlaced::class, SendOrderConfirmation::class);
Event::listen(function (OrderPlaced $event) { /* closure listener */ });

در Laravel ≤10 نگاشت رویداد به listener در آرایه $listen کلاس EventServiceProvider انجام می‌شد. در production با php artisan event:cache نتیجه اسکن کش می‌شود؛ event:list نگاشت فعلی را نشان می‌دهد.

Listener صف‌شده

<?php
use Illuminate\Contracts\Events\ShouldHandleEventsAfterCommit;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Queue\InteractsWithQueue;

class UpdateSalesReport implements ShouldQueue, ShouldHandleEventsAfterCommit
{
    use InteractsWithQueue;

    public string $queue = 'reports';
    public int $tries = 3;

    public function shouldQueue(OrderPlaced $event): bool
    {
        return $event->order->total > 0; // شرط صف شدن
    }

    public function handle(OrderPlaced $event): void { /* ... */ }

    public function failed(OrderPlaced $event, \Throwable $e): void { /* ... */ }
}
  • با ShouldQueue روی listener، فقط همان listener به صف می‌رود و بقیه همزمان اجرا می‌شوند.
  • ShouldHandleEventsAfterCommit روی listener، یا ShouldDispatchAfterCommit روی خود event، باعث می‌شود اجرا تا commit تراکنش عقب بیفتد.
  • اگر listener همزمان false برگرداند، انتشار رویداد به listenerهای بعدی متوقف می‌شود.

Event Subscriber

کلاسی که چند رویداد را در یک جا مدیریت می‌کند؛ مناسب وقتی منطق مرتبط (مثلاً همه رویدادهای ورود و خروج کاربر) را می‌خواهید کنار هم نگه دارید:

<?php
use Illuminate\Auth\Events\Login;
use Illuminate\Auth\Events\Logout;
use Illuminate\Events\Dispatcher;

class UserAuthSubscriber
{
    public function handleLogin(Login $event): void { /* ... */ }
    public function handleLogout(Logout $event): void { /* ... */ }

    public function subscribe(Dispatcher $events): array
    {
        return [
            Login::class => 'handleLogin',
            Logout::class => 'handleLogout',
        ];
    }
}

// AppServiceProvider::boot()
Event::subscribe(UserAuthSubscriber::class);

Event همه‌جا راه‌حل نیست: زنجیره‌های طولانی رویداد، جریان کنترل را پنهان و دیباگ را سخت می‌کنند. وقتی واکنش بخش جدانشدنی منطق اصلی است (مثلاً کم کردن موجودی در همان تراکنش سفارش)، فراخوانی مستقیم سرویس شفاف‌تر است. تفاوت با Model Observer در صفحه Eloquent آمده است.

Broadcasting (نمای کلی)

Broadcasting رویدادهای سمت سرور را از طریق WebSocket به مرورگر می‌رساند (اعلان لحظه‌ای، چت، داشبورد زنده). اجزا:

  • سرور WebSocket: Laravel Reverb (سرور first-party، با php artisan reverb:start)، یا سرویس‌های میزبانی‌شده مثل Pusher و Ably. در Laravel 11 دستور php artisan install:broadcasting پیکربندی و فایل routes/channels.php را می‌سازد.
  • رویداد: پیاده‌سازی ShouldBroadcast (از طریق صف ارسال می‌شود) یا ShouldBroadcastNow (همزمان).
  • کلاینت: کتابخانه JavaScript به نام Laravel Echo.

Notifications و Mail

Mailable فقط ایمیل است؛ Notification یک «پیام کوتاه درباره یک اتفاق» است که می‌تواند همزمان از چند کانال (mail، database، broadcast، SMS، Slack) به کاربر برسد. قاعده سرانگشتی: ایمیل‌های غنی و مستقل (فاکتور، خبرنامه) → Mailable؛ اطلاع‌رسانی به کاربر درباره رویدادی در سیستم → Notification.

Mailable

<?php
// php artisan make:mail OrderShipped --markdown=mail.orders.shipped
use Illuminate\Mail\Mailables\Attachment;
use Illuminate\Mail\Mailables\Content;
use Illuminate\Mail\Mailables\Envelope;

class OrderShipped extends Mailable implements ShouldQueue
{
    use Queueable, SerializesModels;

    public function __construct(public Order $order) {}

    public function envelope(): Envelope
    {
        return new Envelope(subject: 'سفارش شما ارسال شد');
    }

    public function content(): Content
    {
        return new Content(markdown: 'mail.orders.shipped'); // propertyهای public در view در دسترس‌اند
    }

    public function attachments(): array
    {
        return [Attachment::fromStorage("invoices/{$this->order->id}.pdf")];
    }
}

Mail::to($user)->cc($manager)->send(new OrderShipped($order));
Mail::to($user)->queue(new OrderShipped($order));
Mail::to($user)->later(now()->addMinutes(5), new OrderShipped($order));
  • درایورها (mailer): smtp، ses، postmark، mailgun، resend، sendmail، log و array برای توسعه و تست؛ mailer نوع failover بین چند سرویس جابه‌جا می‌شود.
  • Mailableی که ShouldQueue را پیاده کند، حتی با send() هم صف می‌شود.
  • برای پیش‌نمایش در مرورگر، کافی است Mailable را از یک route برگردانید.
  • تست: Mail::fake() سپس Mail::assertSent(OrderShipped::class, fn ($m) => $m->hasTo($user->email)) یا assertQueued.

Notification چندکاناله

<?php
// php artisan make:notification InvoicePaid
class InvoicePaid extends Notification implements ShouldQueue
{
    use Queueable;

    public function __construct(public Invoice $invoice) {}

    public function via(object $notifiable): array
    {
        return $notifiable->prefers_sms ? ['vonage', 'database'] : ['mail', 'database', 'broadcast'];
    }

    public function toMail(object $notifiable): MailMessage
    {
        return (new MailMessage)
            ->subject('فاکتور پرداخت شد')
            ->line("فاکتور شماره {$this->invoice->number} پرداخت شد.")
            ->action('مشاهده فاکتور', route('invoices.show', $this->invoice));
    }

    // برای کانال database و broadcast (اگر toDatabase تعریف نشود)
    public function toArray(object $notifiable): array
    {
        return ['invoice_id' => $this->invoice->id, 'amount' => $this->invoice->amount];
    }
}

Notification::send($admins, new InvoicePaid($invoice));         // گروهی
Notification::route('mail', 'finance@example.com')->notify(new InvoicePaid($invoice)); // on-demand
  • database: در جدول notifications ذخیره می‌شود (make:notifications-table؛ در نسخه‌های قدیمی notifications:table). سپس $user->unreadNotifications و ->markAsRead().
  • broadcast: از طریق Broadcasting روی کانال خصوصی کاربر ارسال می‌شود (اعلان زنده در UI).
  • SMS: کانال رسمی Vonage در پکیج جدا؛ برای سرویس‌های ایرانی (کاوه‌نگار و…) یک Custom Channel می‌نویسید: کلاسی با متد send($notifiable, Notification $notification) که در via() نام کلاسش را برمی‌گردانید.
  • کاربر هر کانال را با متدهایی مثل routeNotificationForMail() یا routeNotificationForVonage() روی مدل سفارشی می‌کند.

با ShouldQueue روی Notification، برای هر ترکیب notifiable و کانال یک Job جدا ساخته می‌شود؛ پس خرابی سرویس SMS جلوی ثبت database notification را نمی‌گیرد.

Atomic Lock

قفل توزیع‌شده روی store مشترک، تا از اجرای همزمان یک بخش حساس در چند پروسه یا سرور جلوگیری شود (پردازش دوباره یک پرداخت، جلوگیری از اجرای دوباره cron، race condition در موجودی).

<?php
use Illuminate\Contracts\Cache\LockTimeoutException;

$lock = Cache::lock("order:{$order->id}:pay", 10); // قفل حداکثر ۱۰ ثانیه (برای جلوگیری از قفل یتیم)

if ($lock->get()) {
    try {
        $this->processPayment($order);
    } finally {
        $lock->release();
    }
}

// یا: تا ۵ ثانیه برای گرفتن قفل صبر کن، وگرنه LockTimeoutException
try {
    Cache::lock('report:generate', 120)->block(5, function () {
        // قفل خودکار آزاد می‌شود
    });
} catch (LockTimeoutException $e) {
    // کس دیگری مشغول است
}

// آزاد کردن قفل در پروسه دیگر (مثلاً در Job)
$owner = $lock->owner();
Cache::restoreLock("order:{$order->id}:pay", $owner)->release();

Cache Stampede (Dog-piling)

وقتی یک کلید پربازدید و گران منقضی می‌شود، صدها درخواست همزمان cache miss می‌خورند و همه با هم کوئری سنگین را اجرا می‌کنند؛ دیتابیس زیر بار می‌رود و ممکن است کل سیستم از دسترس خارج شود.

t=0   کلید "dashboard:stats" منقضی شد
t=0+  درخواست ۱ ──► miss ──► کوئری ۳ ثانیه‌ای
      درخواست ۲ ──► miss ──► کوئری ۳ ثانیه‌ای
      ...
      درخواست ۵۰۰ ──► miss ──► کوئری ۳ ثانیه‌ای   ⇐ DB از کار می‌افتد

راه‌حل‌ها:

  1. قفل: فقط یک درخواست مقدار را بازسازی کند و بقیه کمی صبر کنند یا مقدار قدیمی را بگیرند.
  2. Stale-while-revalidate با Cache::flexible (از Laravel 11.23): تا یک مدت داده تازه است؛ در بازه دوم داده کهنه فوراً برگردانده می‌شود و بازسازی بعد از ارسال پاسخ در پس‌زمینه انجام می‌شود.
  3. Jitter در TTL تا کلیدهای مشابه همزمان منقضی نشوند.
  4. Pre-warming: یک Job زمان‌بندی‌شده قبل از انقضا مقدار را تازه کند (یا کلید بدون انقضا که فقط Job آن را بازنویسی می‌کند).
<?php
// ۵ ثانیه تازه، تا ۶۰ ثانیه مقدار کهنه سرو می‌شود و در پس‌زمینه بازسازی می‌گردد
$stats = Cache::flexible('dashboard:stats', [5, 60], fn () => Stats::compute());

// الگوی قفل دستی
$stats = Cache::get('dashboard:stats');
if ($stats === null) {
    $stats = Cache::lock('dashboard:stats:rebuild', 30)->block(10, function () {
        // ممکن است درخواست دیگری در این فاصله ساخته باشد
        return Cache::remember('dashboard:stats', 300 + random_int(0, 60), fn () => Stats::compute());
    });
}

اشتباهات رایج cache: cache کردن داده وابسته به کاربر با کلید عمومی (نشت اطلاعات بین کاربران)، cache کردن مدل‌های Eloquent سنگین به‌جای آرایه‌های سبک، فراموش کردن invalidation بعد از update، و استفاده از store file روی چند سرور.

Artisan Command سفارشی

<?php
// php artisan make:command SendInvoiceReminders
namespace App\Console\Commands;

use Illuminate\Console\Command;

class SendInvoiceReminders extends Command
{
    // {days=3} آرگومان با پیش‌فرض، {--dry-run} فلگ، {--queue=} گزینه با مقدار، {ids*} آرایه
    protected $signature = 'invoices:remind {days=3} {--dry-run} {--queue=default}';
    protected $description = 'Send reminders for invoices due in N days';

    public function handle(InvoiceRepository $invoices): int  // method injection
    {
        $due = $invoices->dueIn((int) $this->argument('days'));

        if ($due->isEmpty()) {
            $this->info('Nothing to do.');
            return self::SUCCESS;
        }

        if (! $this->option('dry-run') && ! $this->confirm("Send {$due->count()} reminders?", true)) {
            return self::FAILURE;
        }

        $this->withProgressBar($due, function ($invoice) {
            SendReminder::dispatch($invoice)->onQueue($this->option('queue'));
        });

        $this->newLine();
        $this->table(['ID', 'Due'], $due->map->only(['id', 'due_at'])->all());

        return self::SUCCESS;
    }
}

  • Closure command: Artisan::command('mail:test {email}', function (string $email) { ... })->purpose('...'); در routes/console.php.
  • اجرا از کد: Artisan::call('invoices:remind', ['days' => 7, '--dry-run' => true]) یا Artisan::queue(...).
  • پیاده‌سازی Isolatable گزینه --isolated را اضافه می‌کند تا فقط یک نمونه همزمان اجرا شود.
  • کد خروجی (SUCCESS=0، FAILURE=1) برای CI و Supervisor معنادار است.

Authorization در عمق: Gate و Policy

Authentication می‌پرسد «تو کی هستی؟» و Authorization می‌پرسد «آیا اجازه این کار را داری؟». Laravel دو ابزار دارد: Gate که یک closure برای یک توانایی (ability) است و Policy که کلاسی است که همه مجوزهای مربوط به یک مدل را گروه‌بندی می‌کند. پشت صحنه هر دو از طریق همان سرویس Gate ارزیابی می‌شوند.

Gate

  • closure در AppServiceProvider::boot.
  • برای کارهای غیروابسته به مدل: «دسترسی به پنل ادمین»، «مشاهده گزارش مالی».
  • سریع برای موارد ساده؛ اگر زیاد شود، شلوغ و پراکنده می‌شود.

Policy

  • کلاس با متدهای viewAny، view، create، update، delete، restore، forceDelete.
  • برای مجوزهای حول یک مدل یا resource.
  • منظم، قابل تست، auto-discovery بر اساس نام.

Gate

<?php
use Illuminate\Auth\Access\Response;
use Illuminate\Support\Facades\Gate;

// AppServiceProvider::boot()
Gate::define('view-financial-reports', fn (User $user) => $user->hasRole('finance'));

Gate::define('publish-post', function (User $user, Post $post) {
    return $user->id === $post->user_id
        ? Response::allow()
        : Response::deny('فقط نویسنده می‌تواند منتشر کند.');
});

// سوپرادمین: قبل از همه بررسی‌ها
Gate::before(function (User $user, string $ability) {
    if ($user->isSuperAdmin()) {
        return true;   // true یا false یعنی تصمیم نهایی؛ null یعنی «ادامه بده»
    }
});

// استفاده
Gate::allows('publish-post', $post);
Gate::denies('view-financial-reports');
Gate::forUser($otherUser)->allows('publish-post', $post);
Gate::authorize('publish-post', $post);              // در صورت عدم مجوز AuthorizationException ← 403
$response = Gate::inspect('publish-post', $post);    // $response->allowed(), ->message()

در before اگر برای کاربر عادی false برگردانید، همه مجوزهای او رد می‌شود. برای «ادامه بررسی معمول» باید null (هیچ چیز) برگردانید.

Policy

<?php
// php artisan make:policy PostPolicy --model=Post
class PostPolicy
{
    public function before(User $user, string $ability): ?bool
    {
        return $user->isAdmin() ? true : null;
    }

    public function view(?User $user, Post $post): bool   // ?User یعنی مهمان هم بررسی می‌شود
    {
        return $post->published || $user?->id === $post->user_id;
    }

    public function update(User $user, Post $post): Response
    {
        return $user->id === $post->user_id
            ? Response::allow()
            : Response::denyAsNotFound(); // 404 به‌جای 403 برای پنهان کردن وجود منبع
    }

    public function create(User $user): bool   // بدون نمونه مدل
    {
        return $user->hasVerifiedEmail();
    }
}

Auto-discovery: اگر مدل در App\Models\Post و Policy در App\Policies\PostPolicy باشد، ثبت لازم نیست. در غیر این صورت Gate::policy(Post::class, PostPolicy::class) در boot (در Laravel ≤10 آرایه $policies در AuthServiceProvider).

نقاط اعمال مجوز

احراز هویت API (Sanctum و Passport) و Rate Limiting

در Laravel 11 دستور php artisan install:api فایل routes/api.php را می‌سازد و Sanctum را نصب می‌کند (با --passport به‌جای آن Passport نصب می‌شود).

Sanctum: دو حالت کاملاً متفاوت

API Token (Personal Access Token)

  • برای اپ موبایل، کلاینت‌های third-party ساده، اسکریپت‌ها.
  • توکن در هدر Authorization: Bearer ....
  • در جدول personal_access_tokens به‌صورت hash SHA-256 ذخیره می‌شود؛ متن کامل فقط یک بار نمایش داده می‌شود.
  • پشتیبانی از abilities (شبیه scope) و انقضا.

SPA Authentication

  • برای SPA روی همان دامنه سطح بالا (مثلاً app.example.com و api.example.com).
  • بدون توکن؛ از session cookie معمولی Laravel و محافظت CSRF استفاده می‌کند.
  • امن‌تر از ذخیره توکن در localStorage (در برابر XSS، کوکی HttpOnly است).
  • نیازمند پیکربندی stateful domains و CORS با credentials.
<?php
// مدل User
use Laravel\Sanctum\HasApiTokens;
class User extends Authenticatable { use HasApiTokens, Notifiable; }

// صدور توکن (مثلاً endpoint لاگین موبایل)
Route::post('/tokens', function (Request $request) {
    $request->validate(['email' => 'required|email', 'password' => 'required', 'device_name' => 'required']);
    $user = User::where('email', $request->email)->first();

    if (! $user || ! Hash::check($request->password, $user->password)) {
        throw ValidationException::withMessages(['email' => ['اطلاعات ورود نادرست است.']]);
    }

    return ['token' => $user->createToken($request->device_name, ['orders:read'])->plainTextToken];
});

// محافظت از routeها
Route::middleware('auth:sanctum')->group(function () {
    Route::get('/orders', fn (Request $r) => $r->user()->orders);
    Route::post('/orders', [OrderController::class, 'store'])->middleware('abilities:orders:write');
});

// بررسی ability در کد
$request->user()->tokenCan('orders:write');

// ابطال
$request->user()->currentAccessToken()->delete();   // logout از همین دستگاه
$user->tokens()->delete();                           // logout از همه دستگاه‌ها

middlewareهای abilities (همه) و ability (حداقل یکی) در Laravel 11 باید در bootstrap/app.php با $middleware->alias([...]) به کلاس‌های CheckAbilities و CheckForAnyAbility نگاشت شوند. انقضای توکن با expiration در config/sanctum.php و پاک‌سازی با sanctum:prune-expired.

جریان SPA:

  1. در bootstrap/app.php: ->withMiddleware(fn ($m) => $m->statefulApi()) و تنظیم SANCTUM_STATEFUL_DOMAINS.
  2. SPA ابتدا GET /sanctum/csrf-cookie را صدا می‌زند تا کوکی XSRF-TOKEN را بگیرد.
  3. سپس POST /login (با withCredentials)؛ Laravel session می‌سازد.
  4. درخواست‌های بعدی با session cookie و هدر X-XSRF-TOKEN از auth:sanctum عبور می‌کنند.

Passport: چه زمانی؟

Passport یک OAuth2 Server کامل (بر پایه league/oauth2-server) است: client registration، authorization code با PKCE، client credentials برای ارتباط ماشین به ماشین، refresh token و scope. زمانی لازم است که برنامه‌های شخص ثالث بخواهند از طرف کاربران شما به داده‌هایشان دسترسی بگیرند («ورود با حساب ما» یا یک اکوسیستم API عمومی) یا قرارداد صریحاً OAuth2 بخواهد. برای اپ موبایل و SPA خودتان، Sanctum ساده‌تر و کافی است.

جمع‌بندی برای جواب تشریحی: SPA خودی ← Sanctum cookie؛ موبایل و توکن ساده ← Sanctum token؛ کلاینت‌های third-party و OAuth2 ← Passport. grant نوع password در OAuth جدید توصیه نمی‌شود.

Rate Limiting

limiterها با نام در AppServiceProvider::boot تعریف و با middleware throttle اعمال می‌شوند. شمارنده‌ها در cache پیش‌فرض نگه داشته می‌شوند (در production روی چند سرور، Redis؛ متد $middleware->throttleWithRedis() در bootstrap/app.php).

<?php
use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Support\Facades\RateLimiter;

RateLimiter::for('api', function (Request $request) {
    return $request->user()
        ? Limit::perMinute(120)->by($request->user()->id)
        : Limit::perMinute(30)->by($request->ip());

Pipeline، Macro و Collections

Pipeline: الگوی زنجیره پردازش

کلاس Illuminate\Pipeline\Pipeline یک شیء (passable) را از میان مجموعه‌ای از «pipe» عبور می‌دهد؛ هر pipe می‌تواند شیء را تغییر دهد، کار را متوقف کند یا به بعدی بسپارد ($next). این دقیقاً سازوکار Middleware است: HTTP Kernel درخواست را از طریق Pipeline از میان middlewareهای global به Router می‌فرستد و Router همین کار را برای middlewareهای route انجام می‌دهد.

Pipeline::send($request)->through([A, B, C])->then($destination)

  array_reduce(array_reverse([A,B,C]), carry, destination)  ⇒ پیازی از closureها:

  A.handle( req, fn ⇒ B.handle( req, fn ⇒ C.handle( req, fn ⇒ destination(req) ) ) )

  ┌─ A (before) ─┐
  │ ┌ B (before) ┐│
  │ │ ┌ C ─────┐ ││
  │ │ │ هسته   │ ││   ← Controller
  │ │ └────────┘ ││
  │ └ B (after) ─┘│
  └─ A (after) ──┘

متد then() آرایه pipeها را معکوس و با array_reduce به یک closure تو در تو تبدیل می‌کند؛ پس اولین pipe در آرایه، بیرونی‌ترین لایه است: اول «before» آن اجرا می‌شود و آخر از همه «after» آن.

<?php
use Illuminate\Support\Facades\Pipeline;

// هر pipe: کلاسی با متد handle($passable, Closure $next)
class ApplyCoupon
{
    public function handle(Order $order, \Closure $next)
    {
        if ($order->coupon) {
            $order->total -= $order->coupon->discountFor($order);
        }
        return $next($order);
    }
}

class EnsureStockAvailable
{
    public function handle(Order $order, \Closure $next)
    {
        throw_if(! $order->inStock(), OutOfStockException::class);
        return $next($order);
    }
}

$order = Pipeline::send($order)
    ->through([EnsureStockAvailable::class, ApplyCoupon::class, CalculateTax::class])
    ->then(fn (Order $order) => tap($order)->save());   // یا ->thenReturn()

pipeها از کانتینر resolve می‌شوند (DI دارند)؛ با via('process') نام متد را عوض کنید. کاربردهای رایج: فیلترهای جستجو روی query builder، فرایند checkout، پردازش چندمرحله‌ای فایل.

LazyCollection

LazyCollection بر پایه Generator است: آیتم‌ها یکی‌یکی و فقط هنگام نیاز تولید می‌شوند؛ پس پردازش فایل چند گیگابایتی یا میلیون‌ها رکورد با حافظه ثابت ممکن است. Model::cursor() و lazy() در Eloquent هم LazyCollection برمی‌گردانند (جزئیات در صفحه Eloquent).

<?php
use Illuminate\Support\LazyCollection;

LazyCollection::make(function () {
    $handle = fopen(storage_path('imports/customers.csv'), 'r');
    while (($line = fgetcsv($handle)) !== false) {
        yield $line;
    }
    fclose($handle);
})
->skip(1)                       // header
->map(fn ($row) => ['name' => $row[0], 'email' => $row[1]])
->filter(fn ($row) => filter_var($row['email'], FILTER_VALIDATE_EMAIL))
->chunk(1000)
->each(fn ($chunk) => DB::table('customers')->insert($chunk->all()));

تفاوت کلیدی: Collection معمولی همه داده را در حافظه دارد؛ LazyCollection جریانی است. ولی متدهایی مثل sortBy یا groupBy در LazyCollection هم ناچارند همه داده را جمع کنند. و همیشه یادتان باشد: فیلتر و جمع روی دیتابیس (where، sum در SQL) از فیلتر روی Collection بعد از get() بسیار کاراتر است.

سفارشی‌سازی Exception Handling و امکانات تست

Exception Handling به سبک Laravel 11

در Laravel 11 کلاس App\Exceptions\Handler حذف شده و همه چیز در ->withExceptions() فایل bootstrap/app.php انجام می‌شود. دو مفهوم جدا را تفکیک کنید: report یعنی ثبت و ارسال خطا (log، Sentry، Slack) و render یعنی تبدیل خطا به پاسخ HTTP.

<?php
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Http\Request;
use Psr\Log\LogLevel;
use Symfony\Component\HttpKernel\Exception\NotFoundHttpException;

->withExceptions(function (Exceptions $exceptions) {
    // report سفارشی؛ stop() یعنی logging پیش‌فرض هم انجام نشود
    $exceptions->report(function (PaymentFailedException $e) {
        Log::channel('payments')->critical($e->getMessage(), ['order' => $e->orderId]);
    })->stop();

    // render سفارشی
    $exceptions->render(function (NotFoundHttpException $e, Request $request) {
        if ($request->is('api/*')) {
            return response()->json(['message' => 'منبع یافت نشد.'], 404);
        }
        // برگرداندن null یعنی render پیش‌فرض
    });

    $exceptions->dontReport([InvalidCouponException::class]);
    $exceptions->level(PDOException::class, LogLevel::CRITICAL);
    $exceptions->context(fn () => ['tenant' => tenant()?->id]);   // context سراسری لاگ
    $exceptions->shouldRenderJsonWhen(fn (Request $r, Throwable $e) => $r->is('api/*') || $r->expectsJson());
})

خود Exception هم می‌تواند متدهای report() و render(Request $request) داشته باشد که فریم‌ورک خودکار صدا می‌زند؛ این برای خطاهای دامنه‌ای تمیزترین روش است:

<?php
class InsufficientBalanceException extends \DomainException

        return false; // خطای کسب‌وکار است؛ log نکن (true/void یعنی گزارش پیش‌فرض)

Octane، کارایی و استقرار، و جمع‌بندی امنیت

Laravel Octane و نشت state

Octane برنامه را روی یک application server دائمی (FrankenPHP، Swoole یا RoadRunner) اجرا می‌کند: فریم‌ورک یک بار boot می‌شود و در حافظه worker می‌ماند و همان نمونه Application به درخواست‌های متوالی پاسخ می‌دهد. bootstrap تکراری حذف می‌شود و throughput چند برابر می‌شود؛ ولی فرض «هر درخواست از صفر شروع می‌شود» دیگر درست نیست.

PHP-FPM

  • هر درخواست: boot کامل، اجرا، دور ریختن همه چیز.
  • state نشت نمی‌کند.
  • هزینه boot در هر درخواست.

Octane

  • یک boot، هزاران درخواست.
  • singletonها، propertyهای static و متغیرهای global بین درخواست‌ها می‌مانند.
  • نیازمند کد «stateless-aware».
<?php
// ❌ مشکل: singleton یک بار با Request درخواست اول ساخته می‌شود
$this->app->singleton(CartService::class, function ($app) {
    return new CartService($app['request']);   // تمام کاربران بعدی Request کاربر اول را می‌بینند!
});

// ✅ راه‌حل ۱: scoped (در هر درخواست از نو ساخته می‌شود)
$this->app->scoped(CartService::class, fn ($app) => new CartService($app['request']));

// ✅ راه‌حل ۲: resolver به‌جای خود شیء
$this->app->singleton(CartService::class, fn ($app) => new CartService(fn () => $app['request']));

// ✅ راه‌حل ۳: داده را به متد پاس بدهید
$cart->totalFor($request->user());

// ❌ نشت حافظه: آرایه static که مدام بزرگ می‌شود
class Metrics { public static array $events = []; }
  • در singletonها، Request، Application یا config repository را در constructor نگه ندارید؛ app()/request() را هنگام نیاز صدا بزنید.
  • Octane بعضی state‌های داخلی فریم‌ورک را بین درخواست‌ها reset می‌کند، ولی کد شما و پکیج‌های third-party مسئولیت خودشان را دارند.
  • با --max-requests workerها بعد از N درخواست بازیافت می‌شوند تا نشت حافظه مهار شود.
  • بعد از deploy: php artisan octane:reload؛ در توسعه octane:start --watch.
  • همین هشدارها برای queue:work هم صدق می‌کند؛ چون آن هم پروسه long-running است.

سوالات تشریحی

انواع binding در Service Container (bind، singleton، scoped، instance) را تعریف و با هم مقایسه کنید. تفاوت singleton و scoped در چه محیطی اهمیت پیدا می‌کند؟

تعریف: binding دستورالعمل کانتینر برای ساختن یک نوع است و تفاوت انواع آن در طول عمر نمونه است.

  • bind: هر make یک نمونه جدید (transient). برای اشیای سبک یا دارای state مستقل.
  • singleton: بار اول ساخته و تا پایان عمر Application همان نمونه برگردانده می‌شود. برای کلاینت‌های پرهزینه (اتصال Redis، SDK).
  • scoped: یک نمونه در هر چرخه درخواست یا Job؛ Octane و Queue Worker در ابتدای هر درخواست/Job این نمونه‌ها را flush می‌کنند.
  • instance: شیء از پیش ساخته‌شده را به‌عنوان singleton ثبت می‌کند؛ رایج در تست.
$this->app->bind(Exporter::class, CsvExporter::class);
$this->app->singleton(GeoIpClient::class, fn () => new GeoIpClient(config('services.geoip.key')));
$this->app->scoped(TenantContext::class);
$this->app->instance(Clock::class, new FrozenClock());

اهمیت تفاوت: در PHP-FPM هر درخواست پروسه را از صفر boot می‌کند؛ پس singleton و scoped عملاً یکسان‌اند. در محیط‌های long-running مثل Octane و queue:work، singleton بین درخواست‌ها یا Jobها باقی می‌ماند؛ اگر state وابسته به درخواست (کاربر جاری، tenant، Request) داشته باشد، به درخواست بعدی نشت می‌کند. قاعده: سرویس stateless یا state سراسری ← singleton؛ state وابسته به درخواست ← scoped.

کانتینر Laravel چگونه کلاسی را که هیچ bindingی برایش ثبت نشده resolve می‌کند؟ در چه شرایطی این کار با خطا مواجه می‌شود و راه‌حل چیست؟

سازوکار (Autowiring با Reflection): وقتی make(Foo::class) صدا زده شود و bindingی نباشد، کانتینر:

  1. با ReflectionClass چک می‌کند کلاس instantiable باشد؛
  2. پارامترهای constructor را می‌خواند؛
  3. برای هر پارامتر با type کلاس، به‌صورت بازگشتی همان فرایند را تکرار می‌کند؛ برای primitive از مقدار پیش‌فرض استفاده می‌کند؛
  4. شیء را با آرگومان‌های حل‌شده می‌سازد و resolving callbackها را اجرا می‌کند.

حالت‌های خطا (BindingResolutionException):

  • type-hint روی interface یا کلاس abstract بدون binding: «Target [X] is not instantiable».
  • پارامتر primitive بدون مقدار پیش‌فرض (مثل string $apiKey): «Unresolvable dependency».
  • وابستگی حلقوی (A به B و B به A).
// راه‌حل‌ها
$this->app->bind(PaymentGateway::class, ZarinpalGateway::class);            // interface
$this->app->when(SmsSender::class)->needs('$apiKey')->giveConfig('services.sms.key'); // primitive
$this->app->singleton(SmsSender::class, fn () => new SmsSender(config('services.sms.key')));

نکته: به همین دلیل اکثر کلاس‌های concrete هیچ binding نمی‌خواهند و binding فقط برای interfaceها، primitiveها، singleton‌ها و پیکربندی خاص ضروری است. Reflection هزینه دارد ولی در عمل ناچیز است.

تفاوت متدهای register و boot در Service Provider چیست و چرا Laravel این دو فاز را از هم جدا کرده است؟ مثالی از کد اشتباه بزنید.

register: فقط برای ثبت binding در کانتینر. Laravel اول register همه Providerها را اجرا می‌کند.

boot: بعد از register شدن همه Providerها اجرا می‌شود؛ در این زمان تمام سرویس‌ها در دسترس‌اند. ثبت Gate، Policy، RateLimiter، listener، macro، view composer و route اینجاست. از method injection هم پشتیبانی می‌کند.

چرا؟ ترتیب اجرای Providerها تضمین‌شده نیست. اگر در register از سرویسی استفاده کنید، ممکن است Provider آن هنوز ثبت نشده باشد یا سرویس زودهنگام با پیکربندی ناقص ساخته شود (مثلاً قبل از اینکه Provider دیگری آن را extend کند). جداسازی دو فاز تضمین می‌کند «نقشه ساخت» کامل باشد و بعد استفاده شروع شود.

// ❌ اشتباه
public function register(): void
{
    Gate::define('admin', fn ($u) => $u->is_admin);   // استفاده از سرویس Gate در فاز register
    View::share('settings', Setting::all());           // کوئری DB در register؛ برای هر artisan command هم اجرا می‌شود
}

// ✅ درست
public function register(): void
{
    $this->app->singleton(SettingsRepository::class);
}
public function boot(SettingsRepository $settings): void
{
    Gate::define('admin', fn ($u) => $u->is_admin);
    View::composer('layouts.app', fn ($view) => $view->with('settings', $settings->all()));
}

نکته تکمیلی: Providerی که فقط register دارد را می‌توان deferred کرد؛ Providerی که در boot کار جانبی دارد، نه.

Deferred Service Provider چیست، چگونه کار می‌کند و چه محدودیتی دارد؟

تعریف: Providerی که فقط زمانی load و register می‌شود که یکی از سرویس‌هایی که ارائه می‌کند واقعاً از کانتینر درخواست شود.

سازوکار: Provider اینترفیس DeferrableProvider را پیاده می‌کند و در متد provides() فهرست کلیدهای کانتینر را برمی‌گرداند. Laravel این نگاشت را در bootstrap/cache/services.php کش می‌کند. در هر درخواست، به‌جای اجرای register آن Provider، فقط می‌داند «اگر کسی X خواست، اول این Provider را register کن».

class PdfServiceProvider extends ServiceProvider implements DeferrableProvider
{
    public function register(): void
    {
        $this->app->singleton(PdfRenderer::class, fn () => new PdfRenderer(config('pdf')));
    }

    public function provides(): array
    {
        return [PdfRenderer::class];
    }
}

مزیت: کاهش هزینه boot در هر درخواست، مخصوصاً در برنامه‌های بزرگ با تعداد زیادی Provider پکیج.

محدودیت‌ها:

  • فقط برای Providerهایی که صرفاً binding ثبت می‌کنند. اگر در boot route، listener، macro یا Gate ثبت شود، چون Provider ممکن است هرگز load نشود، آن کارها انجام نمی‌شوند.
  • اگر provides() ناقص باشد، سرویس پیدا نمی‌شود یا با autowiring اشتباه ساخته می‌شود.
  • بعد از تغییر، کش services باید بازسازی شود (به‌طور خودکار هنگام تغییر فهرست Providerها، یا با optimize:clear).
Facade در Laravel به‌صورت داخلی چگونه کار می‌کند؟ آیا استفاده از Facade تست‌پذیری را کاهش می‌دهد؟ آن را با Dependency Injection مقایسه کنید.

سازوکار: Facade کلاسی است که از Illuminate\Support\Facades\Facade ارث می‌برد و فقط متد getFacadeAccessor() را تعریف می‌کند که کلید سرویس در کانتینر را برمی‌گرداند. فراخوانی Cache::get('k') چون متد static وجود ندارد به __callStatic می‌رسد؛ این متد با getFacadeRoot() شیء را از کانتینر می‌گیرد (و در $resolvedInstance کش می‌کند) و متد را روی شیء واقعی صدا می‌زند.

class Cache extends Facade

// Cache::get('k')  ≡  app('cache')->get('k')

سناریو: دو سرویس ReportExporter و BackupService هر دو به Filesystem نیاز دارند، ولی اولی باید روی دیسک local و دومی روی S3 بنویسد. بدون تغییر کد این کلاس‌ها چطور پیاده‌سازی می‌کنید؟

راه‌حل: Contextual Binding. کانتینر اجازه می‌دهد برای یک وابستگی واحد (Filesystem) بسته به کلاس مصرف‌کننده پیاده‌سازی متفاوتی تزریق شود. هر دو کلاس فقط به Contract وابسته‌اند و از جزئیات دیسک بی‌خبرند.

use Illuminate\Contracts\Filesystem\Filesystem;

class ReportExporter { public function __construct(private Filesystem $disk) {} }
class BackupService  { public function __construct(private Filesystem $disk) {} }

// AppServiceProvider::register()
$this->app->when(ReportExporter::class)
    ->needs(Filesystem::class)
    ->give(fn () => Storage::disk('local'));

$this->app->when(BackupService::class)
    ->needs(Filesystem::class)
    ->give(fn () => Storage::disk('s3'));

در نسخه‌های اخیر Laravel 11 می‌توان با contextual attribute همین را در خود constructor گفت: public function __construct(#[Storage('s3')] private Filesystem $disk) {}؛ ساده‌تر ولی تصمیم پیکربندی را به کلاس می‌برد.

چرا این روش؟

  • رعایت Dependency Inversion و Open/Closed: تغییر دیسک فقط در Provider.
  • در تست به‌راحتی Storage::fake() یا یک Filesystem mock داده می‌شود.
  • جایگزین‌های بدتر: Storage::disk('s3') hardcode داخل کلاس (coupling) یا ساختن دو interface مصنوعی.

همین الگو برای primitiveها هم کار می‌کند: needs('$bucket')->giveConfig('backup.bucket').

کد زیر گاهی ایمیل خوش‌آمد را با خطای ModelNotFoundException در صف شکست می‌دهد و گاهی برای کاربری ایمیل می‌فرستد که ثبت‌نامش rollback شده. علت چیست؟ بازنویسی کنید. 
DB::transaction(function () use ($data) {
    $user = User::create($data);
    SendWelcomeEmail::dispatch($user);
    $user->wallet()->create(['balance' => 0]);   // ممکن است exception بدهد
});

علت: Job بلافاصله وارد صف می‌شود، در حالی که تراکنش هنوز commit نشده است.

  • به‌خاطر SerializesModels، در payload فقط کلاس و id کاربر ذخیره می‌شود و worker هنگام اجرا آن را از DB می‌خواند. اگر worker سریع‌تر از commit باشد، به‌خاطر isolation تراکنش رکورد را نمی‌بیند ← ModelNotFoundException.
  • اگر ساختن wallet خطا دهد و تراکنش rollback شود، Job قبلاً در صف (مثلاً Redis، که بخشی از تراکنش DB نیست) قرار گرفته و برای داده‌ای ناموجود اجرا می‌شود.
DB::transaction(function () use ($data) {
    $user = User::create($data);
    $user->wallet()->create(['balance' => 0]);
    SendWelcomeEmail::dispatch($user)->afterCommit();   // فقط بعد از commit؛ با rollback دور ریخته می‌شود
});

class SendWelcomeEmail implements ShouldQueue
{
    use Queueable;
    public bool $deleteWhenMissingModels = true;        // لایه دفاعی دوم
    public function __construct(public User $user) {}
}

گزینه‌های دیگر: 'after_commit' => true در connection صف برای همه Jobها؛ برای رویدادها ShouldDispatchAfterCommit یا listener با ShouldHandleEventsAfterCommit؛ یا dispatch را بعد از بلوک transaction بنویسید. همین مشکل برای Mail و Notification صف‌شده هم وجود دارد.

رابطه tries، backoff، timeout و retry_after را در صف Laravel توضیح دهید. چرا ممکن است یک Job دو بار اجرا شود و چطور از آسیب آن جلوگیری می‌کنید؟
  • tries: حداکثر دفعات تلاش (پیش‌فرض worker یک). maxExceptions تعداد exception مجاز را جدا محدود می‌کند و retryUntil() به‌جای تعداد، مهلت زمانی می‌دهد.
  • backoff: فاصله بین تلاش‌ها؛ آرایه مثل [10, 60, 300] برای backoff افزایشی.
  • timeout: حداکثر زمان یک تلاش؛ worker بعد از آن پروسه را kill می‌کند (و تلاش شکست‌خورده حساب می‌شود).
  • retry_after: تنظیم connection؛ اگر Job بعد از این مدت acknowledge نشده باشد، صف فرض می‌کند worker مرده و Job را دوباره در دسترس می‌گذارد.

دلایل اجرای دوباره:

  1. timeout بزرگ‌تر یا مساوی retry_after: Job هنوز در حال اجراست که worker دوم آن را برمی‌دارد. قانون: timeout چند ثانیه کمتر از retry_after.
  2. crash یا kill شدن worker بعد از انجام کار ولی قبل از حذف Job از صف.
  3. retry بعد از خطایی که بعد از یک اثر جانبی رخ داده (ایمیل رفته، بعد DB خطا داده).
class ChargeSubscription implements ShouldQueue
{
    use Queueable;
    public int $tries = 4;
    public int $timeout = 50;          // retry_after = 90
    public array $backoff = [30, 120, 600];

    public function handle(PaymentGateway $gateway): void
    {
        if ($this->invoice->fresh()->isPaid()) {
            return;                      // idempotent: اجرای دوباره بی‌اثر است
        }
        $gateway->charge($this->invoice, idempotencyKey: "invoice-{$this->invoice->id}");
        $this->invoice->markPaid();
    }
}

محافظت: طراحی idempotent (بررسی وضعیت قبل از اثر، کلید یکتا در API پرداخت، updateOrCreate، unique index)، WithoutOverlapping برای منبع مشترک، و failed() برای مدیریت شکست نهایی.

تفاوت queue:work و queue:listen چیست؟ workerها را در production چگونه اجرا و بعد از هر deploy مدیریت می‌کنید؟

queue:work یک daemon طولانی‌مدت است: فریم‌ورک یک بار boot می‌شود و Jobها پشت سر هم در همان پروسه اجرا می‌شوند. سریع است ولی کد قدیمی در حافظه می‌ماند و state یا حافظه ممکن است نشت کند. queue:listen برای هر Job یک پروسه تازه با boot کامل می‌سازد؛ کند است ولی تغییرات کد را فوراً می‌بیند؛ مناسب توسعه.

در production:

  • یک process monitor (Supervisor، systemd، یا orchestrator کانتینر) workerها را زنده نگه می‌دارد و پس از خروج ری‌استارت می‌کند؛ numprocs تعداد workerهای موازی.
  • با --max-jobs و --max-time و --memory workerها دوره‌ای بازیافت می‌شوند.
  • صف‌های اولویت‌دار: --queue=high,default.
  • اگر Redis دارید، Horizon مدیریت workerها، balancing و داشبورد را فراهم می‌کند.
# Supervisor
command=php /var/www/app/artisan queue:work redis --tries=3 --timeout=60 --max-time=3600
numprocs=4
stopwaitsecs=3600

# در اسکریپت deploy
php artisan queue:restart       # یا php artisan horizon:terminate

چرا queue:restart؟ بدون آن workerها با کد قبلی ادامه می‌دهند و ممکن است Jobهای جدید را با کلاس‌های قدیمی (یا ناسازگار با schema جدید) اجرا کنند. این دستور یک سیگنال در cache ثبت می‌کند؛ هر worker پس از اتمام Job جاری به‌آرامی خارج می‌شود و Supervisor آن را با کد جدید بالا می‌آورد؛ پس هیچ Jobی وسط کار قطع نمی‌شود. پیش‌نیاز: cache مشترک و stopwaitsecs بزرگ‌تر از طولانی‌ترین Job.

Job Chaining و Job Batching را مقایسه کنید. برای import یک فایل CSV با ۲ میلیون ردیف که بعد از اتمام باید گزارش ارسال شود، کدام را و چگونه استفاده می‌کنید؟

Chain: اجرای ترتیبی؛ هر Job بعد از موفقیت قبلی. اگر یکی fail شود، باقی زنجیره اجرا نمی‌شوند. مناسب مراحلی که به خروجی مرحله قبل وابسته‌اند (دانلود ← پردازش ← انتشار).

Batch: اجرای موازی گروهی از Jobهای مستقل بین workerها، با پیگیری progress در جدول job_batches و callbackهای then، catch، finally. Jobها trait Batchable دارند.

    ->map(fn ($offset) => new ImportChunk($path, $offset, 5000));

    ->name("import:{$import->id}")
    ->allowFailures()

    ->catch(fn (Batch $b, Throwable $e) => Log::warning('chunk failed', ['batch' => $b->id]))

  • upsert روی کلید یکتا، Jobها را idempotent می‌کند.
  • UI می‌تواند با Bus::findBatch($id)->progress() درصد پیشرفت را نشان دهد.
  • اگر بعد از batch چند مرحله ترتیبی لازم باشد، batch را داخل یک chain قرار دهید.
تفاوت ShouldBeUnique با Job Middleware از نوع WithoutOverlapping چیست؟ برای هرکدام یک سناریوی مناسب بگویید.

ShouldBeUnique: در زمان dispatch عمل می‌کند. اگر Jobی با همان uniqueId() در صف یا در حال اجرا باشد، dispatch جدید نادیده گرفته می‌شود. قفل در cache تا پایان پردازش (یا $uniqueFor ثانیه) نگه داشته می‌شود. ShouldBeUniqueUntilProcessing قفل را هنگام شروع آزاد می‌کند.

WithoutOverlapping: در زمان اجرا عمل می‌کند. همه Jobها وارد صف می‌شوند، ولی دو Job با یک کلید همزمان اجرا نمی‌شوند؛ Job دوم release می‌شود تا بعداً اجرا شود (یا با dontRelease() حذف شود).

// سناریوی ۱: بازمحاسبه موجودی محصول بعد از هر تغییر؛ ۵۰ تغییر پشت سر هم ← یک بازمحاسبه کافی است
class RecalculateStock implements ShouldQueue, ShouldBeUnique
{
    use Queueable;
    public int $uniqueFor = 600;
    public function uniqueId(): string { return (string) $this->product->id; }
}

// سناریوی ۲: هر تراکنش کیف پول باید اعمال شود، ولی نه همزمان برای یک کاربر (race condition روی موجودی)
class ApplyWalletTransaction implements ShouldQueue
{
    use Queueable;
    public function middleware(): array
    {
        return [(new WithoutOverlapping("wallet:{$this->userId}"))->releaseAfter(5)->expireAfter(60)];
    }
}

  • هر دو به cache با پشتیبانی از atomic lock نیاز دارند و روی چند سرور باید cache مشترک باشد.
  • expireAfter برای جلوگیری از قفل یتیم در صورت crash ضروری است.
Cache Stampede چیست و در Laravel چه راه‌هایی برای جلوگیری از آن دارید؟

تعریف: وقتی کلید cache پربازدیدی که تولیدش گران است منقضی می‌شود، تعداد زیادی درخواست همزمان cache miss می‌خورند و همه با هم مقدار را از منبع (DB یا API) بازسازی می‌کنند. بار ناگهانی می‌تواند دیتابیس را از کار بیندازد و چون پاسخ‌ها کند می‌شوند، cache دیرتر پر می‌شود و مشکل تشدید می‌شود.

راه‌حل‌ها:

  1. Stale-while-revalidate با Cache::flexible (Laravel 11.23+): در بازه دوم مقدار کهنه فوراً سرو و بازسازی پس از ارسال پاسخ انجام می‌شود.
  2. Atomic lock: فقط برنده قفل بازسازی می‌کند.
  3. Jitter تصادفی در TTL تا کلیدها همزمان منقضی نشوند.
  4. Pre-warm با Job زمان‌بندی‌شده که قبل از انقضا مقدار را تازه می‌کند.
// ۱
$stats = Cache::flexible('dashboard:stats', [60, 300], fn () => Stats::heavyQuery());

// ۲
$stats = Cache::get('dashboard:stats') ?? Cache::lock('rebuild:stats', 30)->block(10, fn () =>
    Cache::remember('dashboard:stats', 600 + random_int(0, 120), fn () => Stats::heavyQuery())
);

// ۴ (routes/console.php)
Schedule::call(fn () => Cache::put('dashboard:stats', Stats::heavyQuery(), 900))->everyTenMinutes();

Trade-off: SWR و pre-warm داده کمی کهنه نشان می‌دهند ولی latency پایینی دارند؛ قفل داده تازه می‌دهد ولی درخواست‌های منتظر کندتر می‌شوند و LockTimeoutException باید مدیریت شود. همه این روش‌ها به cache مشترک (Redis) نیاز دارند.

برنامه شما روی سه سرور اجرا می‌شود و روی هر سه cron مربوط به schedule:run فعال است. گزارش روزانه سه بار ارسال می‌شود و گاهی دو اجرای یک command پرحجم با هم تداخل دارند. مشکل را تحلیل و رفع کنید.

تحلیل: scheduler روی هر سروری که schedule:run را اجرا کند، وظایف موعدرسیده را اجرا می‌کند؛ پس با سه سرور، هر وظیفه سه بار اجرا می‌شود. مشکل دوم مستقل است: command قبلی هنوز تمام نشده که اجرای بعدی (در دقیقه یا ساعت بعد) شروع می‌شود.

  • onOneServer: با atomic lock روی cache مشترک (Redis، database، memcached، dynamodb) کار می‌کند؛ با store file بی‌اثر است چون هر سرور cache خودش را دارد.
  • withoutOverlapping: قفل cache تا پایان اجرا؛ پیش‌فرض انقضای قفل ۲۴ ساعت است، پس اگر پروسه crash کند ممکن است وظیفه یک روز اجرا نشود؛ عدد مناسب بدهید.
  • runInBackground: وظایف طولانی بقیه را در صف همان دقیقه معطل نکنند.

جایگزین معماری: فقط روی یک سرور (یا یک کانتینر worker اختصاصی) cron را فعال کنید؛ ساده ولی single point of failure. یا وظیفه سنگین را به یک Job با ShouldBeUnique تبدیل و فقط dispatch آن را زمان‌بندی کنید تا پردازش بین workerها پخش شود.

Gate و Policy را تعریف و مقایسه کنید. نقش متد before چیست و در Laravel 11 مجوز را در کنترلر چگونه اعمال می‌کنید؟

Gate: یک closure با نام ability که کاربر (و آرگومان‌های اختیاری) را می‌گیرد و bool یا Response برمی‌گرداند؛ برای مجوزهای غیرمرتبط با مدل خاص (دسترسی به پنل، گزارش مالی).

Policy: کلاسی که مجوزهای مربوط به یک مدل را گروه‌بندی می‌کند (view، update، delete…). با قرارداد نام‌گذاری به‌طور خودکار کشف می‌شود و منظم‌تر و تست‌پذیرتر است.

before: قبل از هر بررسی اجرا می‌شود؛ true یعنی اجازه قطعی، false یعنی رد قطعی، null یعنی ادامه بررسی عادی. کاربرد کلاسیک: سوپرادمین. Gate::before سراسری و متد before در Policy مخصوص همان مدل است.

use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Support\Facades\RateLimiter;

public function boot(): void
{
    RateLimiter::for('api', function (Request $request) {
        return $request->user()
            ? Limit::perMinute(120)->by('user:'.$request->user()->id)
            : Limit::perMinute(30)->by('ip:'.$request->ip());
    });

    RateLimiter::for('login', function (Request $request) {
        $email = Str::lower((string) $request->input('email'));
        return [
            Limit::perMinute(5)->by($email.'|'.$request->ip()),
            Limit::perMinute(50)->by('login-ip:'.$request->ip()),  // جلوگیری از امتحان ایمیل‌های زیاد از یک IP
        ];
    });
}

کلاس Pipeline در Laravel چیست و چه ارتباطی با Middleware دارد؟ یک مثال کاربردی خارج از HTTP بزنید.

تعریف: Illuminate\Pipeline\Pipeline پیاده‌سازی الگوی Pipeline / Chain of Responsibility است: یک شیء (send) از میان مجموعه‌ای از مراحل (through) عبور می‌کند؛ هر مرحله امضای handle($passable, Closure $next) دارد و می‌تواند شیء را تغییر دهد، با exception متوقف کند یا با $next ادامه دهد. در انتها then($destination) اجرا می‌شود.

ارتباط با Middleware: HTTP Kernel دقیقاً همین را انجام می‌دهد: درخواست را با Pipeline از middlewareهای global به Router می‌فرستد و Router همین کار را با middlewareهای route تا رسیدن به controller تکرار می‌کند. پیاده‌سازی با array_reduce روی آرایه معکوس pipeها یک «پیاز» از closureها می‌سازد؛ برای همین کد قبل از $next از بیرون به داخل و کد بعد از آن از داخل به بیرون اجرا می‌شود (before/after middleware).

// فیلتر جستجوی محصولات؛ هر فیلتر یک کلاس کوچک و قابل تست
class FilterByCategory
{
    public function handle(Builder $query, Closure $next)
    {
        if (request()->filled('category')) {
            $query->where('category_id', request('category'));
        }
        return $next($query);
    }
}

    // ۲) قالب یکسان برای خطاهای HTTP در API
    $exceptions->render(function (HttpExceptionInterface $e, Request $r) {
        if ($r->is('api/*')) {
            return response()->json(['error' => [
                'message' => $e->getMessage() ?: Response::$statusTexts[$e->getStatusCode()],
                'status'  => $e->getStatusCode(),
            ]], $e->getStatusCode());
        }
    });

    // ۳) خطاهای کسب‌وکار log نشوند
    $exceptions->dontReport([DomainRuleException::class]);

    // ۴) کانال جدا برای پرداخت
    $exceptions->report(function (PaymentFailedException $e) {
        Log::channel('payments')->error($e->getMessage(), ['order_id' => $e->orderId]);
    })->stop();
})

// خطای دامنه با render اختصاصی
class DomainRuleException extends Exception
{
    public function render(Request $request): JsonResponse
    {
        return response()->json(['error' => ['message' => $this->getMessage(), 'status' => 422]], 422);
    }
}
  • ValidationException به‌طور پیش‌فرض برای API پاسخ 422 با کلید errors می‌دهد؛ اگر قالب متفاوتی می‌خواهید، آن را هم render کنید.
  • ModelNotFoundException قبل از render به NotFoundHttpException تبدیل می‌شود.
  • در production APP_DEBUG=false تا stack trace به کلاینت نرسد.

تفاوت با Laravel ≤10: کلاس App\Exceptions\Handler با متد register() و فراخوانی $this->reportable() و $this->renderable() و property $dontReport. منطق یکی است و فقط محل پیکربندی عوض شده است.

خلاصه برای مرور سریع

Container و Provider

  • bind هر بار جدید؛ singleton یک بار؛ scoped یک بار در هر درخواست/Job؛ instance شیء آماده.
  • Autowiring با Reflection؛ خطا برای interface بدون binding و primitive بدون default.
  • when()->needs()->give() و giveConfig()؛ tag/tagged؛ extend (decorator)؛ resolving.
  • App::call() برای method injection.
  • register = فقط binding؛ boot = استفاده از سرویس‌ها. Providerها در bootstrap/providers.php.
  • Deferred: DeferrableProvider + provides()؛ فقط برای binding.
  • Auto-discovery: extra.laravel.providers در composer.json.
  • پکیج: mergeConfigFrom (register)، publishes، loadRoutesFrom، loadViewsFrom، loadMigrationsFrom (boot).

Facade

  • getFacadeAccessor() ← کلید کانتینر؛ __callStatic ← getFacadeRoot() ← شیء واقعی.
  • Real-time: use Facades\App\Services\X;
  • تست: shouldReceive، spy، و fake() برای Queue/Bus/Event/Mail/Notification/Storage/Http.

Queue

  • Job: implements ShouldQueue + use Queueable (L11).
  • dispatch، dispatchSync، dispatchAfterResponse، ->afterCommit()، ->onQueue()، ->delay().
  • $tries، $maxExceptions، $backoff، $timeout، retryUntil()، failed()، release().
  • timeout < retry_after وگرنه اجرای دوباره.
  • $deleteWhenMissingModels برای مدل حذف‌شده.
  • ShouldBeUnique (dispatch) در برابر WithoutOverlapping (اجرا)؛ RateLimited، ThrottlesExceptions.
  • Bus::chain ترتیبی؛ Bus::batch موازی + Batchable + then/catch/finally.
  • queue:work (prod) در برابر queue:listen (dev)؛ queue:restart بعد از deploy.
  • queue:failed، queue:retry all، queue:forget، queue:flush، queue:prune-failed.
  • Horizon فقط Redis؛ horizon:terminate در deploy؛ Gate viewHorizon.

Events / Broadcast / Notification

  • Event discovery در app/Listeners (L11)؛ Event::listen، Event::subscribe؛ event:cache.
  • Listener صف‌شده: ShouldQueue؛ بعد از commit: ShouldHandleEventsAfterCommit / ShouldDispatchAfterCommit.
  • Broadcast: install:broadcasting، Reverb، ShouldBroadcast، Channel / PrivateChannel / PresenceChannel، routes/channels.php، Echo.
  • Notification: via()، toMail، toArray؛ $user->notify()، Notification::route().
  • Mailable: envelope()، content()، attachments()؛ Mail::to()->queue().

Cache و Schedule

  • remember، rememberForever، add (اتمیک)، pull، flexible (SWR).
  • Tags فقط redis/memcached/array.
  • Cache::lock($name, $sec)->get() / ->block($wait, fn) / release().
  • Stampede: flexible، lock، jitter، pre-warm.
  • Cron: * * * * * php artisan schedule:run؛ تعریف در routes/console.php.
  • withoutOverlapping (هم‌پوشانی)، onOneServer (چند سرور، cache مشترک)، runInBackground.
  • Command: $signature = 'x:y {arg} {--opt=}'، handle() با DI، Command::SUCCESS.

Auth و Rate Limit

  • Gate::define، Gate::before (null = ادامه)، Gate::authorize، Gate::inspect.
  • Policy: make:policy --model؛ auto-discovery؛ Response::denyAsNotFound().
  • L11: کنترلر پایه بدون AuthorizesRequests ← Gate::authorize()؛ route: ->can('update', 'post').
  • Sanctum token: createToken(name, abilities)، auth:sanctum، tokenCan.
  • Sanctum SPA: /sanctum/csrf-cookie، statefulApi()، stateful domains.
  • Passport: OAuth2 کامل برای third-party.
  • RateLimiter::for('api', fn ($r) => Limit::perMinute(60)->by(...)) + throttle:api ← 429.

ابزارها

  • Pipeline::send($x)->through([...])->then(fn)؛ همان سازوکار middleware.
  • X::macro('name', fn) روی Collection، Str، Request، Response، Builder.
  • LazyCollection = Generator، حافظه ثابت.
  • Http::timeout()->retry()->throw()، Http::pool، Http::fake، preventStrayRequests.
  • Storage::disk('s3')->put/get/url/temporaryUrl، storage:link، Storage::fake.
