Protocols

مدل‌های لایه‌ای شبکه، IP، TCP و UDP، DNS، تکامل HTTP از نسخه ۱ تا ۳، TLS، WebSocket، gRPC و پروتکل‌های پیام‌رسانی؛ همراه با سناریوی کامل «وقتی آدرسی را در مرورگر تایپ می‌کنید چه اتفاقی می‌افتد».

مدل OSI و TCP/IP

شبکه را به لایه‌ها تقسیم می‌کنیم تا هر لایه فقط یک مسئولیت داشته باشد و از طریق یک رابط مشخص به لایهٔ بالاتر سرویس بدهد. این جداسازی باعث می‌شود بتوان مثلاً Wi-Fi را با Ethernet عوض کرد بدون اینکه HTTP متوجه شود. به فرایند اضافه شدن هدر هر لایه به داده هنگام ارسال Encapsulation و به برداشتن آن‌ها در مقصد Decapsulation می‌گویند.

تفاوت کلیدی: OSI یک مدل مرجع و آموزشی با ۷ لایه است؛ TCP/IP مدل پیاده‌سازی‌شدهٔ واقعی اینترنت با ۴ لایه است که لایه‌های ۵ تا ۷ را در یک لایهٔ Application ادغام کرده است. Router در لایه ۳، Switch در لایه ۲ و Load Balancer بسته به نوع در لایه ۴ (L4 / TCP) یا لایه ۷ (L7 / HTTP) کار می‌کند.

تفاوت L4 و L7 Load Balancer سوال رایجی است: L4 فقط IP و پورت را می‌بیند و اتصال‌ها را توزیع می‌کند (سریع، بی‌خبر از محتوا)؛ L7 درخواست HTTP را می‌خواند و می‌تواند بر اساس path، header یا cookie مسیریابی کند، TLS را terminate کند و cache داشته باشد.

IP، آدرس‌دهی و NAT

IP (Internet Protocol) پروتکل لایهٔ شبکه است که بسته‌ها را از مبدأ به مقصد از میان چند شبکه مسیریابی می‌کند. IP best-effort و connectionless است: تضمینی برای رسیدن، ترتیب یا عدم تکرار بسته‌ها نمی‌دهد؛ این وظیفه به لایهٔ بالاتر (TCP) سپرده شده است. هر بسته یک فیلد TTL (در IPv6 با نام Hop Limit) دارد که در هر router یکی کم می‌شود تا بسته‌ها در حلقه برای همیشه نچرخند؛ ابزار traceroute از همین رفتار استفاده می‌کند.

IPv4

  • آدرس ۳۲ بیتی، حدود ۴٫۳ میلیارد آدرس
  • نمایش dotted-decimal: 192.168.1.10
  • کمبود آدرس ← وابستگی شدید به NAT
  • هدر با طول متغیر و checksum
  • fragmentation هم در مبدأ و هم در router ممکن است

IPv6

  • آدرس ۱۲۸ بیتی، فضای آدرس عملاً نامحدود
  • نمایش hex: 2001:db8::1 (صفرهای متوالی با :: خلاصه می‌شوند)
  • نیاز به NAT ندارد؛ هر دستگاه می‌تواند آدرس عمومی داشته باشد
  • هدر ثابت و ساده‌تر، بدون checksum
  • fragmentation فقط در مبدأ؛ SLAAC برای پیکربندی خودکار

CIDR

CIDR (Classless Inter-Domain Routing) با نماد /n می‌گوید چند بیت اول آدرس، بخش شبکه است. بقیهٔ بیت‌ها مربوط به host هستند. تعداد آدرس‌های یک بلوک 2^(32-n) است.

  • /32 = یک آدرس منفرد؛ /24 = ۲۵۶ آدرس (۲۵۴ قابل‌استفاده برای host، چون آدرس network و broadcast کنار می‌روند)؛ /16 = ۶۵۵۳۶ آدرس.
  • مثال: 192.168.1.0/24 یعنی 192.168.1.0 تا 192.168.1.255 با subnet mask 255.255.255.0.
  • 0.0.0.0/0 یعنی «همهٔ آدرس‌ها» (مثلاً در قوانین firewall یا default route).

NAT

NAT (Network Address Translation) در router، آدرس IP خصوصی (و معمولاً پورت مبدأ) بستهٔ خروجی را با IP عمومی خودش جایگزین می‌کند و این نگاشت را در جدولی نگه می‌دارد تا پاسخ را به دستگاه درست برگرداند. رایج‌ترین نوع آن PAT / NAT overload است که هزاران دستگاه را پشت یک IP عمومی قرار می‌دهد.

  • مزیت: صرفه‌جویی در آدرس IPv4 و پنهان ماندن ساختار شبکهٔ داخلی.
  • عیب: اتصال ورودی به دستگاه داخلی بدون port forwarding ممکن نیست؛ peer-to-peer را سخت می‌کند (به همین دلیل WebRTC از STUN/TURN استفاده می‌کند). NAT به‌خودی‌خود ابزار امنیتی نیست و جای firewall را نمی‌گیرد.

پورت و سوکت

IP فقط تا ماشین مقصد می‌رساند؛ پورت (عدد ۱۶ بیتی، ۰ تا ۶۵۵۳۵) مشخص می‌کند داده به کدام پروسه روی آن ماشین برسد. لایهٔ Transport با پورت‌ها کار می‌کند.

  • Well-known ports (0–1023): برای سرویس‌های استاندارد؛ bind کردن آن‌ها در لینوکس معمولاً دسترسی root (یا capability مناسب) می‌خواهد.
  • Registered (1024–49151): مثل 3306 (MySQL)، 5432 (PostgreSQL)، 6379 (Redis).
  • Ephemeral (پویا): پورت موقتی که سیستم‌عامل برای سمت client انتخاب می‌کند.

سوکت

Socket نقطهٔ پایانی ارتباط است: ترکیب IP:Port به‌علاوهٔ پروتکل. یک اتصال TCP به‌طور یکتا با 4-tuple (یا با احتساب پروتکل 5-tuple) شناسایی می‌شود:

(src IP, src port, dst IP, dst port [, protocol])
(10.0.0.5, 51734, 93.184.216.34, 443, TCP)

به همین دلیل یک سرور روی پورت 443 می‌تواند هم‌زمان میلیون‌ها اتصال داشته باشد: پورت مقصد یکسان است، اما ترکیب آدرس و پورت client‌ها فرق دارد. در سمت سرور، سوکت listening با accept() برای هر اتصال جدید یک سوکت جدید می‌سازد.

Server: socket() → bind(0.0.0.0:8080) → listen() → accept() ⟲ → read/write → close()
Client: socket() → connect(server:8080) ────────────────────────► read/write → close()

PHP-FPM و Nginx می‌توانند از طریق TCP socket (127.0.0.1:9000) یا Unix domain socket (/run/php/php8.3-fpm.sock) با هم حرف بزنند. Unix socket روی یک ماشین سربار کمتری دارد چون از پشتهٔ شبکه عبور نمی‌کند؛ TCP socket برای وقتی است که دو سرویس روی ماشین/کانتینر جدا هستند.

# اتصال‌ها بر اساس وضعیت (مثلاً تعداد TIME_WAIT)
ss -tan state time-wait | wc -l
# تست باز بودن پورت

TCP در عمق

TCP (Transmission Control Protocol) پروتکلی connection-oriented، reliable و ordered است که یک جریان بایت (byte stream) دوطرفه بین دو پروسه فراهم می‌کند. TCP مفهوم «پیام» ندارد؛ مرز پیام‌ها را پروتکل لایهٔ بالاتر (مثلاً HTTP با Content-Length) تعیین می‌کند.

  • چرا سه مرحله و نه دو؟ چون هر دو طرف باید ISN خود را بفرستند و تأییدش را بگیرند؛ SYN-ACK دو کار را در یک بسته انجام می‌دهد. با دو مرحله، سرور نمی‌داند client شمارهٔ او را دریافت کرده یا SYN قدیمیِ تکراری بوده است.

SYN flood: مهاجم SYN‌های زیادی می‌فرستد و ACK نهایی را نمی‌دهد تا صف اتصال‌های نیمه‌باز سرور پر شود. راه‌حل رایج SYN cookies است که سرور را از نگه‌داشتن state تا رسیدن ACK بی‌نیاز می‌کند.

TIME_WAIT

طرفی که اول اتصال را می‌بندد (active closer) به مدت 2 × MSL (Maximum Segment Lifetime؛ در لینوکس عملاً حدود ۶۰ ثانیه) در وضعیت TIME_WAIT می‌ماند. دو دلیل دارد:

  1. اگر ACK نهایی گم شود و طرف مقابل FIN را دوباره بفرستد، بتواند دوباره ACK کند.
  2. بسته‌های تأخیری اتصال قبلی با اتصال جدیدی که همان 4-tuple را دارد قاطی نشوند.

سناریوی کلاسیک: سرویسی که برای هر درخواست به یک API یا دیتابیس اتصال TCP جدید باز و بسته می‌کند، هزاران سوکت در TIME_WAIT جمع می‌کند و ممکن است ephemeral portها تمام شوند (خطای Cannot assign requested address). راه‌حل درست: connection reuse (keep-alive، connection pool، persistent connection) — نه دستکاری کورکورانهٔ پارامترهای kernel. CLOSE_WAIT زیاد هم معمولاً نشانهٔ باگ برنامه است: طرف مقابل بسته ولی برنامهٔ ما سوکت را close نکرده است.

سازوکارهای اطمینان (Reliability)

  • Sequence number: هر بایت شماره دارد؛ گیرنده داده را مرتب می‌کند و تکراری‌ها را حذف می‌کند.
  • ACK تجمعی: گیرنده اعلام می‌کند تا کدام بایت را پیوسته دریافت کرده است. SACK (Selective ACK) اجازه می‌دهد بلوک‌های دریافت‌شدهٔ ناپیوسته هم اعلام شوند.
  • Retransmission: با timeout (RTO که بر اساس RTT اندازه‌گیری‌شده تنظیم می‌شود) یا fast retransmit پس از سه duplicate ACK.
  • Checksum: تشخیص خرابی داده.

Flow control در برابر Congestion control

Flow Control — محافظت از گیرنده

  • گیرنده در هر ACK اندازهٔ receive window (rwnd) را اعلام می‌کند: «فعلاً فقط این‌قدر بافر خالی دارم».
  • فرستنده بیش از rwnd دادهٔ تأییدنشده در مسیر نمی‌گذارد.
  • rwnd = 0 یعنی صبر کن (zero window).
  • مسئله: گیرندهٔ کند نباید غرق شود.

Congestion Control — محافظت از شبکه

  • فرستنده یک congestion window (cwnd) داخلی دارد؛ نرخ ارسال = min(rwnd, cwnd).
  • Slow start: cwnd از مقدار کوچک شروع و در هر RTT تقریباً دو برابر می‌شود.
  • Congestion avoidance (AIMD): بعد از آستانه رشد خطی؛ با مشاهدهٔ packet loss کاهش ضربی.
  • الگوریتم‌ها: Reno، CUBIC (پیش‌فرض لینوکس)، BBR (مدل‌محور).

جملهٔ طلایی: Flow control از سرریز شدن گیرنده جلوگیری می‌کند (rwnd را گیرنده تعیین می‌کند)؛ Congestion control از سرریز شدن شبکه جلوگیری می‌کند (cwnd را فرستنده با حدس زدن ظرفیت شبکه تعیین می‌کند). Slow start دلیل این است که اتصال تازه نمی‌تواند از همان ابتدا با حداکثر سرعت بفرستد؛ یکی دیگر از دلایل ارزشمند بودن reuse اتصال.

Nagle و Delayed ACK

الگوریتم Nagle بسته‌های کوچک را تجمیع می‌کند تا سربار هدر کم شود؛ در ترکیب با delayed ACK گیرنده می‌تواند تأخیرهای محسوس ایجاد کند. برنامه‌های تعاملی و کم‌تأخیر (بازی، SSH، برخی درایورهای دیتابیس) گزینهٔ TCP_NODELAY را فعال می‌کنند.

چه زمانی کدام؟

  • TCP: وقتی صحت و کامل بودن داده حیاتی است: تراکنش مالی، API، انتقال فایل، ایمیل، کوئری دیتابیس.
  • UDP: وقتی تازگی داده از کامل بودن مهم‌تر است (فریم صوتی که دیر برسد بی‌ارزش است)، وقتی پیام‌ها کوچک و مستقل‌اند (DNS: یک سوال، یک جواب)، یا وقتی می‌خواهید پروتکل اطمینان اختصاصی خودتان را در فضای کاربر بسازید (QUIC).

DNS به‌طور پیش‌فرض از UDP استفاده می‌کند، اما برای پاسخ‌های بزرگ (truncate شده) و zone transfer به TCP سوییچ می‌کند. پس «DNS فقط UDP است» پاسخ کاملی نیست.

مثال بک‌اندی: ارسال metric به StatsD روی UDP انجام می‌شود تا اگر سرور metric در دسترس نبود، درخواست کاربر کند نشود (fire-and-forget). از دست رفتن چند metric قابل‌قبول است؛ کند شدن API نه.

DNS

DNS (Domain Name System) یک پایگاه‌دادهٔ توزیع‌شده، سلسله‌مراتبی و cache‌شونده است که نام‌های قابل‌خواندن (مثل api.example.com) را به رکوردهایی مثل آدرس IP ترجمه می‌کند. سلسله‌مراتب: Root (.) ← TLD (com) ← دامنهٔ دوم (example.com) ← زیردامنه‌ها.

  • Authoritative server: منبع اصلی رکوردهای یک zone؛ پاسخ او «authoritative» است و پاسخ resolver از cache «non-authoritative».

TTL و caching

TTL (به ثانیه) می‌گوید یک پاسخ چه مدت می‌تواند در cache بماند. TTL بالا یعنی بار کمتر و سرعت بیشتر، ولی تغییرات دیرتر منتشر می‌شوند؛ TTL پایین برعکس. پاسخ‌های منفی (NXDOMAIN) هم cache می‌شوند.

سناریوی مهاجرت سرور: چند روز قبل از جابه‌جایی، TTL رکورد را مثلاً از ۸۶۴۰۰ به ۳۰۰ کاهش دهید و صبر کنید تا TTL قدیمی منقضی شود؛ سپس IP را عوض کنید و بعد از پایدار شدن، TTL را دوباره بالا ببرید. «DNS propagation» در واقع منقضی شدن cacheها بر اساس TTL قبلی است، نه انتشار فعالانه.

dig api.example.com A +short
dig example.com MX
dig +trace example.com          # مسیر کامل از root
dig @8.8.8.8 example.com TXT     # پرسیدن از resolver مشخص

DNS سنتی رمزنگاری‌نشده است؛ DoH (DNS over HTTPS) و DoT (DNS over TLS) حریم خصوصی را بهتر می‌کنند و DNSSEC با امضای دیجیتال، صحت پاسخ را تضمین می‌کند (نه محرمانگی را). حملهٔ DNS cache poisoning هدف DNSSEC است.

تکامل HTTP: از 1.0 تا 3

HTTP پروتکل لایهٔ کاربرد، stateless و مبتنی بر request/response است. معنای (semantics) آن — متدها، status codeها، هدرها — در همهٔ نسخه‌ها یکسان است؛ آنچه تغییر کرده نحوهٔ انتقال پیام‌ها روی شبکه است.

HTTP/1.0

  • به‌طور پیش‌فرض برای هر درخواست یک اتصال TCP جدید باز و بعد بسته می‌شد ← هزینهٔ handshake و slow start برای هر تصویر و فایل CSS.
  • هدر Host اجباری نبود، پس virtual hosting (چند سایت روی یک IP) دشوار بود.

HTTP/1.1

  • Persistent connection (keep-alive) پیش‌فرض شد: چند درخواست پشت‌سرهم روی یک اتصال.
  • هدر Host اجباری شد ← name-based virtual hosting.
  • Chunked transfer encoding برای پاسخ‌هایی که طولشان از قبل معلوم نیست؛ ابزارهای cache مثل ETag، If-None-Match و Cache-Control؛ درخواست بازه با Range.
  • Pipelining تعریف شد (ارسال چند درخواست بدون انتظار)، اما پاسخ‌ها باید به ترتیب برگردند؛ عملاً مرورگرها آن را غیرفعال کردند.
  • مشکل اصلی: Head-of-Line (HOL) blocking در سطح application — روی هر اتصال در هر لحظه فقط یک درخواست/پاسخ؛ یک پاسخ کند بقیه را معطل می‌کند. مرورگرها برای دور زدنش حدود ۶ اتصال موازی به هر origin باز می‌کنند و توسعه‌دهنده‌ها به ترفندهایی مثل domain sharding، sprite و bundle کردن فایل‌ها روی آوردند.
  • هدرها متنی و تکراری‌اند (cookieها در هر درخواست دوباره فرستاده می‌شوند).

HTTP/2

  • Binary framing layer: پیام‌ها به frameهای دودویی (HEADERS، DATA، SETTINGS، …) شکسته می‌شوند؛ parse کردن آن کارآمدتر و کم‌خطاتر از متن است.
  • Multiplexing: روی یک اتصال TCP، چندین stream هم‌زمان؛ frameهای streamهای مختلف درهم ارسال می‌شوند. HOL blocking سطح HTTP حل شد و نیاز به ۶ اتصال و domain sharding از بین رفت.
  • HPACK: فشرده‌سازی هدرها با جدول static و dynamic و Huffman coding؛ هدرهای تکراری تقریباً رایگان می‌شوند. (فشرده‌سازی عمومی مثل gzip برای هدرها به دلیل حملهٔ CRIME کنار گذاشته شد.)
  • Stream prioritization و flow control در سطح stream.
  • Server Push: سرور می‌توانست منابع را قبل از درخواست بفرستد؛ ولی عملاً بهره‌وری کمی داشت (cache مرورگر را نادیده می‌گرفت) و Chrome آن را حذف کرد. جایگزین پیشنهادی: 103 Early Hints و <link rel="preload">.
  • در عمل مرورگرها HTTP/2 را فقط روی TLS پیاده کرده‌اند (مذاکره با ALPN).
  • مشکل باقی‌مانده: HOL blocking در سطح TCP. چون همه streamها روی یک اتصال TCP هستند، گم شدن یک بسته همهٔ streamها را تا retransmit متوقف می‌کند؛ در شبکه‌های پرخطا (موبایل) گاهی از HTTP/1.1 با چند اتصال هم بدتر است.

HTTP/3 و QUIC

  • HTTP/3 روی QUIC اجرا می‌شود و QUIC روی UDP. QUIC قابلیت‌های reliability، ترتیب، congestion control و رمزنگاری را خودش در فضای کاربر پیاده می‌کند.
  • Streamهای مستقل در لایهٔ transport: گم شدن بسته فقط همان stream را معطل می‌کند ← HOL blocking سطح TCP هم حذف شد.
  • TLS 1.3 درون QUIC ادغام شده و رمزنگاری اجباری است؛ handshake ترکیبی transport و رمزنگاری در 1-RTT و برای اتصال‌های تکراری 0-RTT.
  • Connection migration: اتصال با Connection ID شناسایی می‌شود نه 4-tuple؛ با عوض شدن شبکه (Wi-Fi ← 4G) اتصال قطع نمی‌شود.
  • فشرده‌سازی هدر با QPACK (نسخهٔ سازگار HPACK با تحویل بی‌ترتیب).
  • کشف: سرور با هدر Alt-Svc: h3=":443" یا رکورد DNS از نوع HTTPS اعلام می‌کند که HTTP/3 را پشتیبانی می‌کند؛ اگر UDP مسدود باشد، به HTTP/2 برمی‌گردد.

در بک‌اند معمولاً HTTP/2 یا HTTP/3 در لبه (Nginx، CDN، load balancer) terminate می‌شود و ارتباط داخلی تا PHP-FPM با FastCGI یا HTTP/1.1 است. پس فعال‌کردن HTTP/2 معمولاً کاری در سطح وب‌سرور است، نه Laravel.

TLS و HTTPS

TLS (Transport Layer Security) پروتکلی بین لایهٔ Transport و Application است که سه تضمین می‌دهد: محرمانگی (encryption)، یکپارچگی (integrity — داده در مسیر دست‌کاری نشده) و احراز هویت (authentication — سرور همانی است که ادعا می‌کند، و در mTLS، client هم). HTTPS یعنی HTTP روی TLS. SSL نام نسخه‌های قدیمی و ناامن آن است؛ امروز فقط TLS 1.2 و 1.3 باید فعال باشند.

رمزنگاری متقارن و نامتقارن

Symmetric (متقارن)

  • یک کلید مشترک برای رمز و رمزگشایی
  • بسیار سریع؛ مناسب حجم زیاد داده
  • مثال: AES-GCM، ChaCha20-Poly1305
  • مشکل: چطور کلید را امن به طرف مقابل برسانیم؟

Asymmetric (نامتقارن)

  • جفت کلید عمومی/خصوصی
  • کند؛ برای تبادل کلید و امضای دیجیتال
  • مثال: RSA، ECDSA، Ed25519؛ تبادل کلید: (EC)DHE
  • مشکل توزیع کلید را حل می‌کند

TLS ترکیبی (hybrid) است: در handshake با رمزنگاری نامتقارن، سرور احراز هویت می‌شود و یک کلید نشست مشترک توافق می‌شود؛ سپس همهٔ داده‌ها با رمزنگاری متقارن (سریع) و AEAD منتقل می‌شوند.

بهبودهای TLS 1.3 نسبت به 1.2

  • handshake کامل در 1-RTT (به‌جای 2-RTT) و امکان 0-RTT برای resumption.
  • حذف الگوریتم‌های قدیمی و ناامن: RSA key exchange، CBC، RC4، SHA-1، MD5، فشرده‌سازی و renegotiation.
  • Forward secrecy اجباری: فقط (EC)DHE موقت؛ اگر کلید خصوصی سرور بعداً لو برود، ترافیک ضبط‌شدهٔ قبلی قابل رمزگشایی نیست.
  • رمزنگاری بخش بیشتری از handshake (از جمله گواهی سرور).
  • فقط چند cipher suite امن AEAD.

دادهٔ 0-RTT در برابر replay attack محافظت ندارد؛ فقط برای درخواست‌های idempotent (مثل GET) مناسب است، نه POST پرداخت.

اگر پرسیدند «HTTPS چطور از حملهٔ Man-in-the-Middle جلوگیری می‌کند؟»: مهاجم می‌تواند ترافیک را رهگیری کند، اما نمی‌تواند گواهی معتبری برای دامنه ارائه دهد که توسط CA مورد اعتماد امضا شده باشد و کلید خصوصی‌اش را ندارد؛ پس CertificateVerify را نمی‌تواند بسازد. یکپارچگی AEAD هم جلوی تغییر داده را می‌گیرد. HSTS (Strict-Transport-Security) نیز مانع downgrade به HTTP (SSL stripping) می‌شود.

mTLS (mutual TLS): client هم گواهی ارائه می‌دهد. در ارتباط سرویس‌به‌سرویس (service mesh، اتصال به بانک یا درگاه پرداخت) کاربرد دارد.

WebSocket، SSE و Long Polling

HTTP کلاسیک فقط از client شروع می‌شود. برای اینکه سرور بتواند داده را به‌محض آماده شدن push کند، چند روش داریم.

WebSocket

WebSocket یک کانال full-duplex و پایدار روی یک اتصال TCP است که با یک درخواست HTTP/1.1 و مکانیزم Upgrade شروع می‌شود و بعد پروتکل از HTTP به frameهای WebSocket تغییر می‌کند.

  • آدرس‌ها: ws:// و نسخهٔ امن wss:// (روی TLS؛ در production همیشه wss).
  • frameهای متنی/باینری، ping/pong برای زنده نگه داشتن، frame بستن.
  • کاربرد: چت، بازی چندنفره، ویرایش هم‌زمان، داشبورد معاملاتی، نوتیفیکیشن دوطرفه.

WebSocket تحت Same-Origin Policy/CORS نیست؛ سرور باید خودش هدر Origin را بررسی کند و احراز هویت (توکن یا cookie) انجام دهد، وگرنه در معرض Cross-Site WebSocket Hijacking است. همچنین چون اتصال‌ها stateful و طولانی‌اند، load balancer باید از Upgrade پشتیبانی کند (در Nginx هدرهای Upgrade و Connection باید proxy شوند) و scale افقی به یک pub/sub مشترک (مثل Redis) نیاز دارد.

Server-Sent Events (SSE)

یک پاسخ HTTP معمولی با Content-Type: text/event-stream که باز می‌ماند و سرور رویدادهای متنی را پشت سرهم در آن می‌نویسد. یک‌طرفه (سرور ← client) است؛ در مرورگر با EventSource مصرف می‌شود، reconnect خودکار و Last-Event-ID دارد و از زیرساخت HTTP معمولی (auth، proxy، HTTP/2) استفاده می‌کند. برای نوتیفیکیشن، فید زنده و استریم خروجی LLM عالی است.

event: order.updated
id: 42
data: {"id":17,"status":"shipped"}

Polling و Long Polling

  • Short polling: client هر N ثانیه درخواست می‌دهد؛ ساده ولی پرهزینه و با تأخیر تا N ثانیه.
  • Long polling: سرور درخواست را باز نگه می‌دارد تا داده‌ای برسد (یا timeout)، پاسخ می‌دهد و client فوراً درخواست بعدی را می‌فرستد. سازگاری بالا، ولی سربار هدر و نگه‌داشتن worker برای هر client. در PHP-FPM سنتی، نگه داشتن درخواست باز یعنی اشغال یک worker — هزینهٔ سنگینی دارد.

gRPC و Protocol Buffers

gRPC یک فریم‌ورک RPC (Remote Procedure Call) است که روی HTTP/2 اجرا می‌شود و به‌طور پیش‌فرض از Protocol Buffers (protobuf) برای تعریف قرارداد و serialize کردن داده استفاده می‌کند. ایده: فراخوانی متد روی سرویس دیگر، مثل فراخوانی تابع محلی، با قرارداد قوی‌تایپ.

// user.proto
syntax = "proto3";
package user.v1;

service UserService {
  rpc GetUser (GetUserRequest) returns (User);                 // unary
  rpc ListUsers (ListUsersRequest) returns (stream User);      // server streaming
  rpc Chat (stream ChatMessage) returns (stream ChatMessage);  // bidirectional
}

message GetUserRequest { int64 id = 1; }
message User {
  int64  id    = 1;
  string name  = 2;
  string email = 3;
}
  • از فایل .proto با protoc کد client/server برای زبان‌های مختلف تولید می‌شود ← قرارداد واحد بین تیم‌ها.
  • protobuf باینری و فشرده است؛ نام فیلدها منتقل نمی‌شود، فقط شمارهٔ فیلد (tag). پس serialize/deserialize سریع‌تر و payload کوچک‌تر از JSON است.
  • سازگاری نسخه: شمارهٔ فیلدها را هرگز عوض نکنید یا دوباره استفاده نکنید؛ فیلد حذف‌شده را reserved کنید. افزودن فیلد جدید سازگار با نسخهٔ قبل است.
  • چهار نوع RPC: unary، server streaming، client streaming، bidirectional streaming (به لطف streamهای HTTP/2).
  • امکانات داخلی: deadline/timeout، cancellation، metadata (مثل هدر)، status codeهای مخصوص خودش (NOT_FOUND، UNAVAILABLE، …).

مزایا

  • کارایی بالا و تأخیر کم
  • قرارداد strongly-typed و تولید کد
  • streaming دوطرفه
  • عالی برای ارتباط داخلی microserviceها

معایب

  • مرورگر مستقیم پشتیبانی نمی‌کند (نیاز به gRPC-Web و proxy)
  • باینری؛ دیباگ با curl سخت‌تر (ابزارهایی مثل grpcurl لازم است)
  • cache کردن HTTP مثل REST ساده نیست
  • در PHP-FPM فقط client معمول است؛ سرور gRPC به runtime long-running (مثل RoadRunner) نیاز دارد

جمع‌بندی برای مقایسه: REST/JSON برای APIهای عمومی و مرورگر (ساده، خوانا، cache‌پذیر)؛ gRPC برای ارتباط داخلی سرویس‌به‌سرویس با حجم و کارایی بالا و قرارداد سخت‌گیرانه.

پروتکل‌های پیام‌رسانی: AMQP و MQTT

در معماری asynchronous، تولیدکننده (producer) پیام را به یک broker می‌دهد و مصرف‌کننده (consumer) هر وقت آماده بود آن را برمی‌دارد. این کار باعث decoupling، جذب بار ناگهانی (buffering) و تحمل خطا می‌شود.

AMQP 0-9-1 (RabbitMQ)

Producer ──publish(routing_key)──► Exchange ──binding──► Queue ──► Consumer (ack)
                                      │
                                      └─binding──► Queue ──► Consumer
  • Exchange پیام را بر اساس نوعش به queueها هدایت می‌کند: direct (تطابق دقیق routing key)، fanout (همهٔ queueهای متصل)، topic (الگو مثل order.*، order.#)، headers.
  • Acknowledgement: consumer بعد از پردازش موفق ack می‌دهد؛ اگر بدون ack قطع شود، پیام دوباره تحویل داده می‌شود ← تحویل at-least-once، پس consumer باید idempotent باشد.
  • صف و پیام durable/persistent برای ماندگاری پس از restart broker؛ prefetch (QoS) برای محدود کردن پیام‌های در حال پردازش هر consumer؛ Dead Letter Exchange برای پیام‌های رد‌شده یا منقضی.
  • روی TCP، پورت 5672 (و 5671 با TLS)؛ اتصال واحد با چند channel سبک.

MQTT

  • پروتکل pub/sub سبک برای IoT و شبکه‌های کم‌پهنای‌باند و ناپایدار؛ روی TCP (پورت 1883، با TLS 8883) و هدر حداقل ۲ بایت.
  • Topicهای سلسله‌مراتبی: home/kitchen/temp؛ wildcardها: + (یک سطح) و # (چند سطح).
  • QoS: 0 = at most once (fire-and-forget)، 1 = at least once (ممکن است تکراری شود)، 2 = exactly once (handshake چهارمرحله‌ای، پرهزینه‌تر).
  • Retained message (آخرین مقدار برای subscriber جدید)، Last Will (پیامی که broker در صورت قطع ناگهانی client منتشر می‌کند)، keep-alive.

وقتی URL را تایپ می‌کنید چه اتفاقی می‌افتد؟

این سوال کلاسیک مصاحبه و آزمون تشریحی است، چون همهٔ لایه‌ها را به هم وصل می‌کند. فرض کنید کاربر https://shop.example.com/products?page=2 را وارد می‌کند و بک‌اند Nginx + PHP-FPM + Laravel است.

  1. Parse کردن ورودی: مرورگر تشخیص می‌دهد ورودی URL است یا عبارت جستجو؛ scheme (https)، host، port پیش‌فرض (443)، path و query را جدا می‌کند. اگر دامنه در فهرست HSTS باشد، حتی با تایپ http:// مستقیم به https می‌رود.
  2. DNS resolution: cache مرورگر ← cache سیستم‌عامل و فایل hosts ← recursive resolver ← (در صورت نبود در cache) root ← TLD ← authoritative. نتیجه یک IP (A یا AAAA) است؛ ممکن است IP یک CDN یا load balancer باشد. مرورگر ممکن است رکورد HTTPS را هم بخواهد تا بداند HTTP/3 پشتیبانی می‌شود.
  3. رسیدن بسته‌ها به مقصد: سیستم‌عامل با جدول routing می‌فهمد مقصد خارج از شبکهٔ محلی است و بسته را به default gateway می‌فرستد (با ARP آدرس MAC gateway پیدا می‌شود). router خانگی NAT انجام می‌دهد و بسته‌ها از routerهای اینترنت عبور می‌کنند.
  4. اتصال TCP: three-way handshake با پورت 443 (یک RTT). (در HTTP/3 به‌جای آن handshake ترکیبی QUIC روی UDP.)
  5. TLS handshake: ClientHello با SNI و ALPN (پیشنهاد h2)؛ سرور گواهی را ارائه می‌کند؛ مرورگر زنجیره را تا root CA، تاریخ و SAN را بررسی می‌کند؛ کلید نشست با ECDHE ساخته می‌شود؛ پروتکل HTTP/2 انتخاب می‌شود.
  6. ارسال درخواست HTTP: GET /products?page=2 با هدرهای Host، User-Agent، Accept، Accept-Encoding، Cookie (session) و …
  7. لبهٔ زیرساخت: CDN/WAF ممکن است از cache پاسخ دهد یا درخواست را به load balancer بفرستد؛ LB (L7) TLS را terminate می‌کند و درخواست را با هدر X-Forwarded-For و X-Forwarded-Proto به یکی از سرورهای سالم می‌دهد.
  8. وب‌سرور: Nginx فایل‌های static را مستقیم سرو می‌کند؛ برای مسیرهای پویا با FastCGI درخواست را به PHP-FPM (Unix socket یا TCP 9000) می‌دهد.
  9. Laravel: public/index.php ← autoload کامپوزر ← bootstrap اپلیکیشن و service providerها ← HTTP Kernel ← global middleware (trust proxies، maintenance، trim strings) ← Router مسیر را پیدا می‌کند ← middlewareهای گروه/مسیر (session، CSRF، auth) ← Controller ← Eloquent کوئری به دیتابیس (اتصال TCP به MySQL و شاید Redis برای cache) ← View/JSON ← Response از middlewareها برمی‌گردد.
  10. پاسخ: HTTP/2 200 با Content-Type: text/html، Content-Encoding: br یا gzip، Cache-Control، Set-Cookie و بدنهٔ HTML.
  11. رندر در مرورگر: parse کردن HTML و ساخت DOM؛ کشف CSS/JS/تصاویر و درخواست موازی آن‌ها روی همان اتصال HTTP/2؛ CSSOM؛ اجرای JS؛ render tree ← layout ← paint ← composite.
  12. پس از آن: اتصال برای درخواست‌های بعدی باز می‌ماند (keep-alive)؛ session TLS برای resumption ذخیره می‌شود؛ منابع بر اساس هدرهای cache نگه داشته می‌شوند.

در پاسخ تشریحی، ترتیب لایه‌ها را رعایت کنید و هر مرحله را با پروتکل و لایه‌اش نام ببرید (DNS در Application، TCP در Transport، IP/routing در Network، ARP/Ethernet در Link). نشان دادن بخش سمت سرور (LB، وب‌سرور، PHP-FPM، lifecycle لاراول) شما را از یک پاسخ معمولی متمایز می‌کند.

سوالات تشریحی

مدل OSI و مدل TCP/IP را تعریف و مقایسه کنید. هر یک از پروتکل‌های HTTP، TLS، TCP، IP، Ethernet و ARP در کدام لایه قرار می‌گیرند؟

تعریف: هر دو مدل، ارتباط شبکه را به لایه‌هایی تقسیم می‌کنند که هر لایه مسئولیت مشخصی دارد و به لایهٔ بالاتر سرویس می‌دهد. OSI یک مدل مرجع مفهومی هفت‌لایه (Physical، Data Link، Network، Transport، Session، Presentation، Application) است؛ TCP/IP مدل عملی اینترنت با چهار لایه (Link، Internet، Transport، Application) است.

تفاوت‌ها:

  • TCP/IP لایه‌های Session، Presentation و Application را در یک لایهٔ Application ادغام کرده و Physical و Data Link را در لایهٔ Link.
  • OSI ابتدا طراحی و بعد پروتکل‌هایش (که موفق نشدند) ساخته شد؛ TCP/IP از دل پروتکل‌های واقعی بیرون آمد.
  • OSI برای آموزش و عیب‌یابی (اصطلاحاتی مثل L4/L7) هنوز رایج است.

جایگاه پروتکل‌ها:

  • HTTP: Application (L7).
  • TLS: بین Transport و Application؛ در OSI معمولاً به Presentation/Session نسبت داده می‌شود و در TCP/IP جزو Application حساب می‌شود.
  • TCP: Transport (L4).
  • IP: Network/Internet (L3).
  • Ethernet: Data Link (L2) و بخش فیزیکی (L1).
  • ARP: بین L2 و L3 (ترجمهٔ IP به MAC).

اهمیت عملی: این تقسیم‌بندی در انتخاب ابزار دیده می‌شود: Load Balancer لایه ۴ فقط IP/Port را می‌بیند، در حالی که لایه ۷ می‌تواند بر اساس URL و هدر مسیریابی کند و TLS را terminate کند.

Three-way handshake در TCP را شرح دهید. چرا سه مرحله لازم است و بستن اتصال چرا چهار مرحله دارد؟

برقراری اتصال:

  1. Client بستهٔ SYN با شمارهٔ ترتیب اولیه (ISN = x) می‌فرستد.
  2. Server با SYN-ACK پاسخ می‌دهد: ISN خودش (y) و ack = x+1.
  3. Client با ACK (ack = y+1) تأیید می‌کند. هر دو طرف ESTABLISHED می‌شوند.

چرا سه مرحله؟ ارتباط دوطرفه است و هر طرف باید ISN خود را اعلام کند و از دریافت آن مطمئن شود. این یعنی چهار پیام منطقی (SYN، ACK، SYN، ACK) که دو پیام وسطی در SYN-ACK ادغام می‌شوند. با دو مرحله، سرور نمی‌دانست client واقعاً ISN او را دریافت کرده یا SYN دریافتی یک بستهٔ قدیمی تکراری بوده است. در همین مرحله پارامترهایی مثل MSS و window scaling هم مذاکره می‌شود.

بستن چهارمرحله‌ای: TCP full-duplex است و هر جهت مستقل بسته می‌شود: A می‌فرستد FIN و B با ACK تأیید می‌کند؛ اما B ممکن است هنوز داده برای ارسال داشته باشد (half-close، وضعیت CLOSE_WAIT). وقتی تمام شد، B نیز FIN می‌فرستد و A با ACK پاسخ می‌دهد و وارد TIME_WAIT می‌شود.

پیامد عملی: handshake یک RTT (و با TLS بیشتر) هزینه دارد؛ بنابراین برای کارایی، اتصال‌ها را با keep-alive یا connection pool دوباره استفاده می‌کنیم. از نظر امنیتی، حالت نیمه‌باز می‌تواند هدف حملهٔ SYN flood باشد که با SYN cookies مقابله می‌شود.

یک سناریو: سرویس Laravel شما برای هر درخواست، به یک API خارجی درخواست HTTP می‌زند. در ساعات اوج، خطای «Cannot assign requested address» می‌بینید و ss هزاران اتصال در وضعیت TIME_WAIT نشان می‌دهد. علت چیست و چه می‌کنید؟

تشخیص: طرفی که اتصال TCP را اول می‌بندد به مدت 2×MSL (در لینوکس حدود ۶۰ ثانیه) در TIME_WAIT می‌ماند. چون سرویس ما برای هر فراخوانی یک اتصال جدید باز و بسته می‌کند، هر اتصال یک ephemeral port را برای مدتی قفل می‌کند. وقتی نرخ اتصال‌های جدید به یک مقصد (IP و پورت یکسان) از ظرفیت بازهٔ پورت‌ها تقسیم بر ۶۰ ثانیه بیشتر شود، پورت آزاد برای 4-tuple جدید پیدا نمی‌شود.

چرا TIME_WAIT وجود دارد؟ برای اینکه اگر ACK نهایی گم شد بتوان دوباره ACK کرد و بسته‌های تأخیری اتصال قدیمی با اتصال جدیدی که همان 4-tuple را دارد اشتباه نشوند. پس حذف آن راه‌حل نیست.

راه‌حل‌ها (به ترتیب اولویت):

  • استفادهٔ مجدد از اتصال: HTTP keep-alive و connection pooling. در PHP-FPM هر درخواست جدا است، اما در یک درخواست می‌توان از یک client مشترک برای چند فراخوانی استفاده کرد؛ در workerهای long-running (Octane، queue worker) client را نگه دارید.
  • کاهش تعداد فراخوانی‌ها: cache کردن پاسخ API در Redis، batch کردن درخواست‌ها، انتقال کار به queue.
  • استفاده از یک proxy محلی با اتصال پایدار به مقصد (مثلاً یک egress proxy یا sidecar) که اتصال‌ها را multiplex کند.
  • در صورت لزوم، تنظیمات kernel مانند گسترش ip_local_port_range یا فعال کردن tcp_tw_reuse برای اتصال‌های خروجی — به‌عنوان مسکن، نه درمان.

نکته: اگر به‌جای TIME_WAIT، تعداد زیادی CLOSE_WAIT دیدید، یعنی طرف مقابل بسته ولی برنامهٔ ما سوکت را close نکرده — نشانهٔ نشت منبع در کد است.

Flow control و Congestion control در TCP را تعریف کنید و تفاوت آن‌ها را بنویسید.

Flow control: سازوکاری برای جلوگیری از سرریز شدن گیرنده. گیرنده در هر ACK اندازهٔ فضای خالی بافرش را با receive window (rwnd) اعلام می‌کند و فرستنده بیش از این مقدار دادهٔ تأییدنشده در مسیر نمی‌گذارد. اگر rwnd صفر شود، فرستنده صبر می‌کند (با window probe).

Congestion control: سازوکاری برای جلوگیری از سرریز شدن شبکه (routerها و لینک‌های بین راه). فرستنده یک congestion window (cwnd) داخلی دارد که ظرفیت شبکه را تخمین می‌زند:

  • Slow start: شروع با cwnd کوچک و رشد نمایی (تقریباً دوبرابر در هر RTT) تا آستانه (ssthresh).
  • Congestion avoidance: رشد خطی (Additive Increase).
  • با تشخیص packet loss (timeout یا سه duplicate ACK) کاهش ضربی (Multiplicative Decrease) و fast retransmit/recovery.
  • الگوریتم‌های مدرن: CUBIC، BBR.

مقایسه:

  • تعیین‌کننده: rwnd را گیرنده اعلام می‌کند؛ cwnd را فرستنده حدس می‌زند.
  • هدف: محافظت از end host در برابر محافظت از شبکهٔ مشترک.
  • نرخ واقعی ارسال = min(rwnd, cwnd).

پیامد عملی: به دلیل slow start، یک اتصال تازه برای انتقال پاسخ‌های بزرگ کندتر است؛ این یکی از دلایل استفاده از keep-alive، CDN نزدیک به کاربر و HTTP/2 با یک اتصال گرم است.

TCP و UDP را مقایسه کنید. در چه شرایطی UDP انتخاب بهتری است؟ چرا HTTP/3 با وجود نیاز به اطمینان، روی UDP ساخته شده است؟

TCP: connection-oriented، reliable، ترتیب‌دار، byte stream، دارای flow و congestion control، هدر ۲۰+ بایت. UDP: connectionless، بدون تضمین تحویل و ترتیب، datagram با حفظ مرز پیام، هدر ۸ بایت، پشتیبانی از broadcast/multicast.

چه زمانی UDP؟

  • وقتی تازگی مهم‌تر از کامل بودن است: VoIP، ویدئوکنفرانس، بازی آنلاین — بستهٔ دیررسیده بی‌ارزش است و retransmit فقط تأخیر می‌افزاید.
  • پیام‌های کوچک و مستقل با یک رفت‌وبرگشت: DNS، DHCP، NTP.
  • ارسال fire-and-forget مثل metric به StatsD که نباید درخواست کاربر را کند کند.
  • ساختن پروتکل اطمینان سفارشی در فضای کاربر.

چرا HTTP/3 روی UDP؟

  • TCP در kernel سیستم‌عامل‌ها و middleboxها پیاده شده و تغییر آن عملاً ناممکن است (ossification). UDP یک بستر خنثی است که QUIC می‌تواند روی آن، در فضای کاربر، reliability، ترتیب و congestion control را به شیوهٔ بهتر پیاده کند.
  • QUIC ترتیب را به‌ازای هر stream حفظ می‌کند، پس گم شدن یک بسته فقط همان stream را معطل می‌کند — حذف HOL blocking سطح TCP که HTTP/2 از آن رنج می‌برد.
  • ادغام TLS 1.3 در handshake ← 1-RTT و 0-RTT.
  • Connection migration با Connection ID هنگام عوض شدن شبکه.

پس HTTP/3 «اطمینان را رها» نکرده؛ آن را از kernel به QUIC منتقل کرده است.

فرایند DNS resolution را از لحظه‌ای که مرورگر نام دامنه را دریافت می‌کند تا رسیدن به IP شرح دهید و نقش TTL را توضیح دهید.

تعریف: DNS پایگاه‌دادهٔ توزیع‌شده، سلسله‌مراتبی و cache‌شونده‌ای است که نام دامنه را به رکوردهایی مثل IP ترجمه می‌کند.

مراحل:

  1. cache مرورگر و سپس cache سیستم‌عامل و فایل hosts بررسی می‌شود.
  2. Stub resolver سیستم‌عامل یک recursive query به recursive resolver (ISP یا عمومی مثل 1.1.1.1) می‌فرستد.
  3. اگر resolver پاسخ را در cache داشت، برمی‌گرداند (non-authoritative).
  4. در غیر این صورت iterative عمل می‌کند: از Root server می‌پرسد ← ارجاع به سرورهای TLD (مثلاً .com) ← ارجاع به authoritative name server دامنه (از رکورد NS) ← دریافت رکورد A/AAAA (یا CNAME که باید دوباره دنبال شود).
  5. پاسخ به client برمی‌گردد و در هر لایه cache می‌شود.

TTL: عددی (ثانیه) که مالک رکورد تعیین می‌کند و می‌گوید پاسخ چه مدت می‌تواند در cache بماند.

  • TTL بالا: سرعت بیشتر و بار کمتر روی DNS، اما تغییر IP دیر به کاربران می‌رسد.
  • TTL پایین: انعطاف بیشتر برای failover و مهاجرت، اما کوئری بیشتر.
  • روش درست مهاجرت: ابتدا TTL را کاهش دهید، به اندازهٔ TTL قبلی صبر کنید، سپس IP را تغییر دهید.

نکته‌های تکمیلی: DNS به‌طور پیش‌فرض روی UDP/53 است و برای پاسخ‌های بزرگ به TCP می‌رود؛ پاسخ منفی (NXDOMAIN) هم cache می‌شود؛ DNSSEC صحت و DoH/DoT محرمانگی را اضافه می‌کنند.

رکوردهای A، AAAA، CNAME، MX، TXT و NS را تعریف کنید. برای راه‌اندازی ایمیل سازمانی یک دامنه چه رکوردهایی لازم است؟
  • A: نگاشت نام به آدرس IPv4.
  • AAAA: نگاشت نام به آدرس IPv6.
  • CNAME: نام مستعار؛ می‌گوید این نام در واقع نام دیگری است و resolver باید آن را دنبال کند (مثلاً www ← example.com یا زیردامنه ← آدرس CDN). روی apex دامنه نمی‌توان CNAME گذاشت و نامی که CNAME دارد رکورد دیگری نمی‌تواند داشته باشد.
  • MX: سرورهای دریافت ایمیل دامنه با عدد اولویت (کمتر = ترجیح بیشتر)؛ مقدارش باید یک نام میزبان باشد نه IP یا CNAME.
  • TXT: متن دلخواه؛ برای SPF، DKIM، DMARC و تأیید مالکیت دامنه (مثلاً برای Google یا صدور گواهی).
  • NS: name serverهای authoritative یک zone؛ در TLD، دامنه را به این سرورها delegate می‌کند.

راه‌اندازی ایمیل:

  • MX به سرور ایمیل (مثلاً example.com MX 10 mx1.provider.com) — برای دریافت.
  • SPF (TXT): v=spf1 include:provider.com -all — مشخص می‌کند چه سرورهایی مجازند از طرف دامنه ارسال کنند.
  • DKIM (TXT روی selector._domainkey.example.com): کلید عمومی برای اعتبارسنجی امضای ایمیل‌ها.
  • DMARC (TXT روی _dmarc.example.com): سیاست برخورد با ایمیل‌هایی که SPF/DKIM را پاس نمی‌کنند (p=none|quarantine|reject) و آدرس گزارش.
  • رکورد PTR (reverse DNS) برای IP سرور ارسال‌کننده، اگر خودتان سرور SMTP دارید.

بدون SPF/DKIM/DMARC ایمیل‌های اپلیکیشن (مثل بازیابی رمز) احتمالاً در spam می‌افتند.

تکامل HTTP را از نسخهٔ 1.0 تا 3 شرح دهید. هر نسخه چه مشکلی را حل کرد و چه مشکلی باقی گذاشت؟

HTTP/1.0: برای هر درخواست یک اتصال TCP جدید ← هزینهٔ handshake و slow start برای هر منبع؛ هدر Host اجباری نبود.

HTTP/1.1:

  • Persistent connection پیش‌فرض (keep-alive)، هدر Host اجباری (virtual hosting)، chunked encoding، cache validation (ETag)، Range.
  • مشکل: روی هر اتصال در هر لحظه یک درخواست (HOL blocking سطح application)؛ pipelining به دلیل ترتیب اجباری پاسخ‌ها عملاً استفاده نشد. مرورگرها ~۶ اتصال موازی باز می‌کردند؛ هدرهای متنی و تکراری.

HTTP/2:

  • Binary framing و multiplexing چند stream روی یک اتصال ← HOL سطح HTTP حل شد.
  • HPACK برای فشرده‌سازی هدرها؛ prioritization؛ flow control هر stream.
  • Server push که در عمل ناکارآمد بود و مرورگرها کنارش گذاشتند (جایگزین: 103 Early Hints و preload).
  • مشکل باقی‌مانده: HOL blocking سطح TCP — گم شدن یک بسته همهٔ streamها را متوقف می‌کند.

HTTP/3:

  • روی QUIC/UDP؛ streamهای مستقل در لایهٔ transport ← حذف HOL سطح TCP.
  • TLS 1.3 یکپارچه، handshake 1-RTT و 0-RTT؛ connection migration؛ QPACK.
  • چالش: UDP در برخی شبکه‌ها مسدود یا محدود است (fallback به HTTP/2)، مصرف CPU بیشتر به دلیل پیاده‌سازی در user space.

نکتهٔ کلیدی: semantics (متدها، status codeها، هدرها) در همهٔ نسخه‌ها یکسان است؛ بنابراین اپلیکیشن Laravel تغییری نمی‌کند و ارتقا در لایهٔ وب‌سرور/CDN انجام می‌شود.

Multiplexing در HTTP/2 چیست و چرا با وجود آن، Head-of-Line blocking همچنان در HTTP/2 وجود دارد؟

تعریف: در HTTP/2 هر درخواست/پاسخ یک stream با شناسهٔ یکتا است و پیام‌ها به frameهای دودویی کوچک شکسته می‌شوند. frameهای streamهای مختلف می‌توانند روی یک اتصال TCP درهم (interleave) ارسال شوند و گیرنده با شناسهٔ stream آن‌ها را دوباره کنار هم می‌گذارد. بنابراین یک پاسخ کند (مثلاً گزارش سنگین) دیگر جلوی پاسخ‌های سریع را نمی‌گیرد.

چرا HOL blocking باقی است؟ HTTP/2 مشکل را در لایهٔ application حل کرد، اما همهٔ streamها روی یک اتصال TCP هستند و TCP یک byte stream ترتیب‌دار واحد ارائه می‌دهد. اگر یک بستهٔ TCP گم شود، kernel تحویل همهٔ بایت‌های بعدی را به برنامه متوقف می‌کند تا آن بسته retransmit شود — حتی اگر بایت‌های بعدی متعلق به streamهای کاملاً دیگری باشند. TCP از مفهوم stream در HTTP/2 خبر ندارد.

پیامد: در شبکه‌های پرخطا (موبایل، Wi-Fi شلوغ) یک اتصال HTTP/2 ممکن است از چند اتصال HTTP/1.1 کندتر عمل کند، چون یک loss کل اتصال را معطل می‌کند و cwnd تنها اتصال هم کاهش می‌یابد.

راه‌حل: HTTP/3 روی QUIC که streamها را در خود لایهٔ transport می‌شناسد؛ گم شدن بسته فقط stream مربوط را معطل می‌کند.

TLS handshake را شرح دهید. چرا در TLS هم رمزنگاری نامتقارن و هم متقارن استفاده می‌شود؟ TLS 1.3 چه بهبودهایی دارد؟

هدف TLS: محرمانگی، یکپارچگی و احراز هویت سرور (و اختیاری client) روی یک کانال ناامن.

Handshake در TLS 1.3:

  1. ClientHello: نسخه‌ها و cipher suiteهای پشتیبانی‌شده، key_share (کلید عمومی موقت ECDHE)، SNI (نام دامنه) و ALPN (مثلاً h2).
  2. ServerHello: انتخاب cipher و key_share سرور. اکنون هر دو طرف با Diffie-Hellman یک secret مشترک دارند که هرگز روی شبکه نرفته است.
  3. سرور (رمزشده) Certificate، CertificateVerify (امضای transcript با کلید خصوصی) و Finished را می‌فرستد.
  4. Client زنجیرهٔ گواهی را تا یک root CA مورد اعتماد، تاریخ و تطابق دامنه با SAN بررسی می‌کند، Finished خود را می‌فرستد و داده‌های application شروع می‌شوند — مجموعاً 1-RTT.

چرا هر دو نوع رمزنگاری؟ رمزنگاری نامتقارن مشکل توزیع کلید و احراز هویت را حل می‌کند ولی کند است؛ رمزنگاری متقارن (AES-GCM، ChaCha20) بسیار سریع است ولی به کلید مشترک نیاز دارد. پس از نامتقارن برای توافق امن روی کلید و امضا، و از متقارن برای رمزنگاری حجم داده استفاده می‌شود (رمزنگاری ترکیبی).

بهبودهای TLS 1.3:

  • handshake کامل 1-RTT (در 1.2 دو RTT) و 0-RTT برای resumption (با ریسک replay، فقط برای درخواست‌های idempotent).
  • حذف الگوریتم‌های ضعیف: RSA key exchange، CBC، RC4، SHA-1، compression، renegotiation.
  • Forward secrecy اجباری با ECDHE موقت.
  • رمزنگاری بیشتر handshake (گواهی سرور دیگر plaintext نیست).
گواهی دیجیتال و زنجیرهٔ اعتماد (Certificate chain) را توضیح دهید. یک سناریو: سایت در مرورگر درست باز می‌شود اما curl و اپ موبایل خطای «unable to get local issuer certificate» می‌دهند. مشکل چیست؟

گواهی X.509: سندی که کلید عمومی سرور را به هویت آن (نام دامنه در SAN) گره می‌زند، دارای بازهٔ اعتبار است و توسط یک Certificate Authority امضا شده است.

زنجیرهٔ اعتماد:

  • Root CA: گواهی self-signed که از قبل در trust store سیستم‌عامل/مرورگر وجود دارد. کلید آن معمولاً offline نگه‌داری می‌شود.
  • Intermediate CA: توسط root امضا شده و گواهی‌های نهایی را امضا می‌کند (برای محدود کردن ریسک لو رفتن کلید root).
  • Leaf: گواهی سایت شما.

client از leaf شروع می‌کند، امضای هر گواهی را با کلید عمومی صادرکننده‌اش بررسی می‌کند تا به یک root مورد اعتماد برسد؛ همچنین تاریخ، دامنه، وضعیت ابطال و محدودیت‌ها را چک می‌کند.

تشخیص سناریو: سرور فقط گواهی leaf را ارسال می‌کند و intermediate را نمی‌فرستد. مرورگرها گاهی intermediate را از cache یا با دانلود خودکار (AIA fetching) پیدا می‌کنند، اما curl، OpenSSL و بسیاری از کتابخانه‌های موبایل این کار را نمی‌کنند و زنجیره را ناقص می‌بینند.

بررسی و رفع:

openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts
  • اگر فقط یک گواهی (depth 0) دیده شد، مشکل تأیید می‌شود.
  • در Nginx به‌جای cert.pem از fullchain.pem در ssl_certificate استفاده کنید (leaf + intermediate).
  • هرگز برای «رفع» مشکل، verify را در client خاموش نکنید (curl -k یا verify => false در Guzzle)؛ این کار MITM را ممکن می‌کند.
WebSocket، Server-Sent Events و Long Polling را مقایسه کنید. برای سیستم نوتیفیکیشن یک فروشگاه و برای یک چت گروهی کدام را انتخاب می‌کنید و چرا؟

Long Polling: client درخواست HTTP می‌فرستد و سرور تا رسیدن داده یا timeout پاسخ نمی‌دهد؛ سپس client بلافاصله درخواست بعدی را می‌فرستد. سازگاری بالا، اما سربار هدر برای هر پیام و نگه‌داشتن یک worker/اتصال برای هر کاربر (در PHP-FPM بسیار پرهزینه).

SSE: یک پاسخ HTTP با text/event-stream که باز می‌ماند؛ یک‌طرفه از سرور به client، فقط متن، با reconnect خودکار و Last-Event-ID؛ از زیرساخت HTTP عادی (auth، proxy، HTTP/2) استفاده می‌کند.

WebSocket: با درخواست HTTP و هدر Upgrade: websocket و پاسخ 101 Switching Protocols شروع می‌شود و سپس کانال full-duplex پایدار با frameهای کوچک متنی/باینری فراهم می‌کند. کمترین تأخیر و سربار، اما stateful است: نیاز به load balancer سازگار با Upgrade، بررسی Origin و احراز هویت سمت سرور، و pub/sub مشترک برای scale افقی.

انتخاب:

  • نوتیفیکیشن فروشگاه (تغییر وضعیت سفارش): جریان فقط سرور ← client است و فرکانس پایین؛ SSE ساده‌ترین و کافی است. اگر زیرساخت WebSocket از قبل وجود دارد (مثلاً Laravel Reverb + Echo)، استفاده از آن هم منطقی است.
  • چت گروهی: ارتباط دوطرفه، تأخیر پایین، typing indicator و presence ← WebSocket. پیام‌ها همچنان باید در دیتابیس ذخیره شوند و پس از reconnect، پیام‌های از دست رفته از API بازیابی شوند.
  • Long polling: فقط به‌عنوان fallback در محیط‌هایی که WebSocket/SSE مسدود است.
gRPC چیست و چه تفاوتی با REST دارد؟ در چه شرایطی gRPC را پیشنهاد می‌کنید؟

تعریف: gRPC یک فریم‌ورک RPC است که روی HTTP/2 اجرا می‌شود و قرارداد سرویس و پیام‌ها را با Protocol Buffers در فایل .proto تعریف می‌کند. از این فایل، کد client و server برای زبان‌های مختلف تولید می‌شود.

تفاوت با REST:

  • مدل: REST منبع‌محور (resource + متدهای HTTP)؛ gRPC عمل‌محور (فراخوانی متد مثل GetUser).
  • قالب داده: REST معمولاً JSON متنی و خوانا؛ gRPC باینری، فشرده و سریع (فقط شمارهٔ فیلد منتقل می‌شود).
  • قرارداد: در REST اختیاری (OpenAPI)؛ در gRPC اجباری و strongly-typed با تولید کد.
  • Streaming: gRPC چهار حالت unary، server/client streaming و bidirectional دارد.
  • مرورگر و cache: REST مستقیم در مرورگر کار می‌کند و با HTTP caching و CDN سازگار است؛ gRPC به gRPC-Web و proxy نیاز دارد و cache کردنش ساده نیست.
  • دیباگ: REST با curl؛ gRPC با ابزارهای خاص (grpcurl).

چه زمانی gRPC؟

  • ارتباط داخلی بین microserviceها با حجم بالا و حساسیت به تأخیر.
  • محیط چندزبانه که قرارداد مشترک و تولید کد ارزشمند است.
  • نیاز به streaming دوطرفه.

چه زمانی REST؟ API عمومی، مصرف‌کنندهٔ مرورگر یا شخص ثالث، نیاز به cache و سادگی. معمولاً ترکیب رایج است: REST در لبه، gRPC در داخل.

نکتهٔ سازگاری protobuf: شمارهٔ فیلدها را هرگز تغییر یا بازاستفاده نکنید و فیلدهای حذف‌شده را reserved کنید.

AMQP و MQTT را مقایسه کنید. مفهوم QoS در MQTT و Acknowledgement در AMQP چیست و چه پیامدی برای طراحی consumer دارد؟

AMQP (مثلاً RabbitMQ): پروتکل پیام‌رسانی سازمانی با مدل Exchange ← Binding ← Queue. producer به exchange منتشر می‌کند و exchange بر اساس نوع (direct، fanout، topic، headers) پیام را به queueها مسیریابی می‌کند. امکاناتی مثل durable queue، prefetch، dead-letter exchange و TTL دارد.

MQTT: پروتکل pub/sub بسیار سبک برای IoT و شبکه‌های ناپایدار؛ topicهای سلسله‌مراتبی با wildcard (+، #)، retained message، Last Will و هدر بسیار کوچک.

QoS در MQTT:

  • 0 — at most once: بدون تأیید؛ ممکن است گم شود.
  • 1 — at least once: با تأیید و ارسال مجدد؛ ممکن است تکراری شود.
  • 2 — exactly once: handshake چهارمرحله‌ای؛ پرهزینه‌ترین.

Ack در AMQP: consumer پس از پردازش موفق، ack می‌فرستد و broker پیام را حذف می‌کند. اگر consumer قبل از ack از کار بیفتد، پیام دوباره به consumer دیگری تحویل داده می‌شود؛ با nack/reject می‌توان پیام را به DLX فرستاد.

پیامد طراحی: در عمل تحویل at-least-once است، پس consumer باید idempotent باشد: مثلاً با ذخیرهٔ شناسهٔ پیام پردازش‌شده در جدولی با unique constraint، یا طراحی عملیات به شکلی که تکرارش اثر اضافه ندارد (upsert به‌جای insert). ack را بعد از commit تراکنش بدهید، نه قبل از آن؛ و prefetch را محدود کنید تا یک consumer تعداد زیادی پیام unacked نگه ندارد.

انتخاب: AMQP برای صف کار و یکپارچه‌سازی سرویس‌ها؛ MQTT برای هزاران دستگاه کم‌توان با اتصال ناپایدار.

وقتی کاربر آدرس https://shop.example.com را در مرورگر وارد می‌کند، تا نمایش صفحه چه اتفاقاتی می‌افتد؟ (با جزئیات سمت سرور برای یک اپلیکیشن Laravel)
  1. Parse و HSTS: مرورگر URL را تجزیه می‌کند (scheme، host، پورت پیش‌فرض 443، path)؛ اگر دامنه در فهرست HSTS باشد، اتصال حتماً https خواهد بود.
  2. DNS: cache مرورگر و OS ← recursive resolver ← root ← TLD ← authoritative؛ دریافت رکورد A/AAAA (احتمالاً IP یک CDN/LB) و cache بر اساس TTL.
  3. Routing: بسته‌ها با ARP به gateway می‌رسند، NAT روی router انجام می‌شود و از routerهای اینترنت عبور می‌کنند.
  4. TCP: three-way handshake با پورت 443 (یا QUIC در HTTP/3).
  5. TLS: ClientHello با SNI و ALPN؛ بررسی زنجیرهٔ گواهی؛ توافق کلید با ECDHE؛ انتخاب HTTP/2.
  6. درخواست HTTP: GET / با هدرهای Host، Accept، Accept-Encoding و Cookie.
  7. زیرساخت: CDN/WAF ← Load Balancer (terminate کردن TLS، افزودن X-Forwarded-For/Proto) ← Nginx.
  8. Nginx: اگر فایل static بود مستقیم سرو می‌کند؛ وگرنه با FastCGI به PHP-FPM می‌فرستد.
  9. Laravel: public/index.php ← autoloader ← ساخت Application و service providerها ← HTTP Kernel ← global middleware ← Router ← middlewareهای مسیر (session از Redis، CSRF، auth) ← Controller ← کوئری‌های Eloquent به MySQL ← Blade view ← Response که از pipeline middleware برمی‌گردد.
  10. پاسخ: 200 OK با HTML فشرده (gzip/br)، Set-Cookie و هدرهای cache.
  11. رندر: parse HTML ← DOM؛ دریافت CSS ← CSSOM؛ اجرای JS؛ render tree ← layout ← paint ← composite. منابع اضافی روی همان اتصال HTTP/2 multiplex می‌شوند.

نکات بهینه‌سازی که می‌توان اشاره کرد: CDN برای کاهش RTT، keep-alive و TLS resumption، HTTP/2 یا 3، cache کردن config و route در Laravel (php artisan optimize)، OPcache، و cache در Redis.

NAT چیست، چرا به وجود آمده و چه مشکلاتی ایجاد می‌کند؟ CIDR را با یک مثال توضیح دهید.

NAT: سازوکاری در router که آدرس (و معمولاً پورت) مبدأ بسته‌های خروجی از شبکهٔ خصوصی را با IP عمومی خودش جایگزین می‌کند و نگاشت را در جدول نگه می‌دارد تا پاسخ‌ها را به دستگاه درست برگرداند. رایج‌ترین شکل آن PAT است که تعداد زیادی دستگاه را پشت یک IP قرار می‌دهد.

چرا؟ کمبود آدرس‌های IPv4 (۳۲ بیت ≈ ۴٫۳ میلیارد). شبکه‌های داخلی از رنج‌های خصوصی RFC 1918 (10/8، 172.16/12، 192.168/16) استفاده می‌کنند که در اینترنت route نمی‌شوند.

مشکلات:

  • اتصال ورودی به دستگاه داخلی بدون port forwarding ممکن نیست ← peer-to-peer و VoIP سخت می‌شود (نیاز به STUN/TURN).
  • نقض اصل end-to-end؛ پروتکل‌هایی مثل FTP active که IP را درون payload می‌فرستند دچار مشکل می‌شوند.
  • جدول NAT state دارد؛ اتصال‌های بیکار طولانی ممکن است از جدول حذف شوند (به همین دلیل WebSocketها ping/keep-alive می‌فرستند).
  • چند کاربر پشت یک IP ← rate limiting بر اساس IP ممکن است کاربران بی‌گناه را محدود کند.
  • NAT جایگزین firewall نیست.

IPv6 با فضای آدرس ۱۲۸ بیتی نیاز به NAT را از بین می‌برد.

CIDR: نماد /n یعنی n بیت اول آدرس، بخش شبکه است. تعداد آدرس‌ها 2^(32-n). مثال: 10.0.1.0/24 شامل 10.0.1.0 تا 10.0.1.255 (۲۵۶ آدرس، ۲۵۴ قابل‌استفاده برای host). در طراحی VPC ابری مثلاً کل VPC را 10.0.0.0/16 و هر subnet را /24 تعریف می‌کنیم. CIDR جایگزین کلاس‌های قدیمی A/B/C شد تا تخصیص آدرس و تجمیع routeها کارآمدتر شود.

تفاوت FTP، FTPS و SFTP چیست؟ برای انتقال خودکار فایل‌های گزارش به سرور یک شریک تجاری کدام را پیشنهاد می‌کنید؟ SSH tunneling چه کاربردی دارد؟
  • FTP: پروتکل قدیمی با دو اتصال: کانال control (پورت 21) و کانال داده (در حالت active از سمت سرور، در passive روی پورت پویای سرور). همه‌چیز از جمله نام کاربری و رمز plaintext است. با NAT و firewall مشکل دارد.
  • FTPS: همان FTP به‌همراه TLS (explicit با دستور AUTH TLS یا implicit). رمزشده، اما هنوز دو کانال و پیچیدگی firewall دارد.
  • SFTP: پروتکلی کاملاً متفاوت که به‌عنوان زیرسیستم SSH روی یک اتصال (پورت 22) اجرا می‌شود. رمزنگاری، احراز هویت با کلید و عملیات کامل فایل (لیست، حذف، تغییر نام).

پیشنهاد: SFTP با احراز هویت کلید عمومی: یک پورت (ساده برای firewall و whitelist IP)، بدون رمز عبور در کد، و بررسی host key برای جلوگیری از MITM. در Laravel با دیسک sftp در config/filesystems.php (پکیج league/flysystem-sftp-v3) و یک job زمان‌بندی‌شده در scheduler انجام می‌شود؛ کلید خصوصی را در secret manager یا متغیر محیطی امن نگه دارید.

SSH tunneling: انتقال یک اتصال TCP دلخواه از درون کانال رمزشدهٔ SSH:

  • Local forwarding (ssh -L 3307:127.0.0.1:3306 user@server): دسترسی امن به دیتابیسی که فقط روی localhost سرور listen می‌کند، بدون باز کردن پورتش روی اینترنت.
  • Remote forwarding (-R): در دسترس قرار دادن یک سرویس محلی روی سرور راه دور.
  • Dynamic (-D): ساخت proxy از نوع SOCKS.
  • Bastion/jump host با ssh -J.
یک سناریو: کاربران گزارش می‌دهند API شما «گاهی» کند است یا خطا می‌دهد. با رویکرد لایه‌به‌لایهٔ شبکه، چگونه مشکل را عیب‌یابی می‌کنید؟

اصل: مشکل را به مراحل تجزیه کنید و از پایین به بالا یا با اندازه‌گیری زمان هر مرحله پیش بروید تا گلوگاه مشخص شود.

  1. اندازه‌گیری مراحل با curl: curl -w با time_namelookup، time_connect، time_appconnect، time_starttransfer. اگر DNS کند است ← resolver یا TTL خیلی پایین؛ اگر connect کند است ← شبکه، packet loss یا صف SYN پر؛ اگر TLS کند است ← نبود session resumption یا OCSP؛ اگر TTFB بالاست ← مشکل در اپلیکیشن.
  2. شبکه: mtr برای دیدن packet loss و تأخیر در مسیر؛ tcpdump برای مشاهدهٔ retransmission و RST.
  3. وضعیت اتصال‌ها روی سرور: ss -s و ss -tan: TIME_WAIT زیاد در اتصال‌های خروجی (نبود reuse)، CLOSE_WAIT زیاد (نشت سوکت)، backlog پر.
  4. TLS و گواهی: openssl s_client برای انقضا یا زنجیرهٔ ناقص (خطای «گاه‌به‌گاه» ممکن است مربوط به یک node پشت LB با گواهی متفاوت باشد).
  5. لایهٔ HTTP و زیرساخت: status codeها در لاگ LB و Nginx: 502 (PHP-FPM پاسخ نداد یا crash کرد)، 504 (timeout upstream)، 499 در Nginx (client قبل از پاسخ قطع کرد). بررسی health check و سالم بودن همهٔ nodeها.
  6. اپلیکیشن: اشباع pm.max_children در PHP-FPM (درخواست‌ها در صف می‌مانند)، کوئری کند (slow query log)، فراخوانی همزمان (blocking) API خارجی بدون timeout، lock در دیتابیس. ابزارهای APM، Laravel Telescope/Pulse و لاگ‌های ساختاریافته با request ID.

جمع‌بندی پاسخ: فرضیه بسازید، با داده (metric، لاگ، trace) تأیید کنید، تغییر کوچک اعمال کنید و دوباره اندازه بگیرید. «گاهی» بودن معمولاً به یک node خاص، یک وابستگی خارجی، یا اشباع منابع در ساعات اوج اشاره دارد.

خلاصه برای مرور سریع

لایه‌ها

  • OSI (۷): Physical، Data Link، Network، Transport، Session، Presentation، Application.
  • TCP/IP (۴): Link، Internet، Transport، Application.
  • Router = L3، Switch = L2، LB لایه ۴ (IP/Port) در برابر لایه ۷ (HTTP).
  • PDU: Bit ← Frame ← Packet ← Segment/Datagram ← Data.

IP

  • IPv4 = ۳۲ بیت؛ IPv6 = ۱۲۸ بیت، بدون نیاز به NAT.
  • خصوصی: 10/8، 172.16/12، 192.168/16؛ loopback 127.0.0.1 و ::1.
  • /24 = ۲۵۶ آدرس؛ تعداد = 2^(32-n).
  • NAT/PAT: صرفه‌جویی IPv4؛ مانع اتصال ورودی؛ firewall نیست.
  • IP: best-effort و connectionless؛ TTL ضد حلقه.

TCP

  • Handshake: SYN ← SYN-ACK ← ACK (۱ RTT).
  • Close: FIN/ACK در هر جهت (full-duplex ⇒ ۴ مرحله).
  • TIME_WAIT = active closer، 2×MSL؛ راه‌حل: reuse اتصال.
  • CLOSE_WAIT زیاد = برنامه سوکت را نمی‌بندد.
  • Flow control = rwnd (گیرنده)؛ Congestion = cwnd (فرستنده)، slow start، AIMD، CUBIC/BBR.
  • Reliability: seq، ACK، retransmit، checksum، SACK.

UDP

  • هدر ۸ بایت، بدون اتصال/ترتیب/تضمین؛ datagram.
  • DNS، VoIP، بازی، استریم زنده، QUIC، DHCP، StatsD.

پورت‌ها

  • 22 SSH/SFTP · 25/587/465 SMTP · 53 DNS · 80/443 HTTP(S) · 143/993 IMAP · 3306 MySQL · 5432 Postgres · 6379 Redis · 5672 AMQP · 1883 MQTT · 9000 PHP-FPM.
  • اتصال = 4-tuple (src IP، src port، dst IP، dst port).

DNS

  • Browser ← OS ← Recursive resolver ← Root ← TLD ← Authoritative.
  • A، AAAA، CNAME (نه در apex)، MX (اولویت)، TXT (SPF/DKIM/DMARC)، NS، PTR، CAA.
  • TTL را قبل از مهاجرت کم کنید؛ «propagation» = انقضای cache.
  • UDP/53، پاسخ بزرگ ← TCP.

HTTP

  • 1.0: اتصال جدید برای هر درخواست.
  • 1.1: keep-alive، Host اجباری، chunked؛ HOL سطح HTTP؛ ~۶ اتصال موازی.
  • 2: binary framing، multiplexing، HPACK، push (منسوخ ← 103 Early Hints)؛ HOL سطح TCP.
  • 3: QUIC روی UDP، streamهای مستقل، TLS 1.3 داخلی، 0/1-RTT، connection migration، QPACK.
  • Semantics در همهٔ نسخه‌ها یکسان است.

TLS

  • محرمانگی + یکپارچگی + احراز هویت.
  • Hybrid: نامتقارن (ECDHE، امضا) برای کلید؛ متقارن (AES-GCM) برای داده.
  • زنجیره: Root ← Intermediate ← Leaf؛ همیشه fullchain بفرستید.
  • SNI = نام دامنه در ClientHello؛ ALPN = انتخاب h2/h3.
  • 1.3: 1-RTT، 0-RTT (ریسک replay)، forward secrecy اجباری، حذف الگوریتم‌های قدیمی.
  • HSTS ضد SSL stripping؛ mTLS برای سرویس‌به‌سرویس.

Real-time

  • WebSocket: Upgrade ← 101، full-duplex، wss، بررسی Origin.
  • SSE: text/event-stream، یک‌طرفه، reconnect خودکار.
  • Long polling: fallback، پرهزینه در PHP-FPM.
  • Laravel: Broadcasting + Reverb + Echo.

سایر

  • gRPC: HTTP/2 + protobuf، ۴ نوع RPC، داخلی؛ شمارهٔ فیلد را تغییر ندهید.
  • AMQP: Exchange (direct/fanout/topic/headers) ← Queue، ack، DLX ⇒ consumer idempotent.
  • MQTT: سبک، IoT، QoS 0/1/2، retained، Last Will.
  • SMTP ارسال؛ IMAP همگام‌سازی؛ POP3 دانلود.
  • SFTP = روی SSH (نه FTP+TLS؛ آن FTPS است).
  • SSH: host key، کلید Ed25519، -L برای tunnel.

عیب‌یابی

  • Refused = پورت بسته (RST)؛ Timeout = drop/firewall؛ Name not known = DNS.
  • 502 = upstream خطا داد؛ 504 = upstream timeout.
  • dig، ss، nc، curl -v -w، openssl s_client، mtr، tcpdump.
