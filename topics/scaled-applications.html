Scaled Applications

چطور یک اپلیکیشن Laravel را از یک سرور به ده‌ها سرور برسانیم: Stateless بودن، Load Balancing، کش در همهٔ لایه‌ها و مقابله با Cache Stampede، صف‌ها و Jobهای Idempotent، Rate Limiting، مسیر مقیاس‌پذیری دیتابیس، Octane، مسائل همزمانی، تخمین ظرفیت و حذف SPOF.

مقیاس‌پذیری، کارایی و دسترس‌پذیری

این سه مفهوم اغلب با هم قاطی می‌شوند، در حالی که به سه سؤال متفاوت جواب می‌دهند:

Performance (کارایی)
سیستم برای یک درخواست چقدر سریع است؟ با Latency (مثلاً p50/p95/p99 زمان پاسخ) و مصرف منابع به ازای هر درخواست سنجیده می‌شود.
Scalability (مقیاس‌پذیری)
توانایی سیستم برای پاسخ‌گویی به بار بیشتر با افزودن منابع، به‌طوری که کارایی افت جدی نکند. معیارش Throughput (مثلاً RPS) در برابر منابع افزوده‌شده است. سیستم ایده‌آل تقریباً خطی مقیاس می‌گیرد: دو برابر سرور ≈ دو برابر ظرفیت.
Availability (دسترس‌پذیری)
درصد زمانی که سیستم در دسترس است و درست جواب می‌دهد؛ معمولاً با «تعداد ۹ها» بیان می‌شود (۹۹٫۹٪ و …). با Redundancy و حذف SPOF به دست می‌آید.
Reliability
سیستم در طول زمان درست کار کند (داده‌ها خراب نشوند، خطا پنهان نشود). سیستمی که در دسترس است ولی جواب غلط می‌دهد Available هست ولی Reliable نیست.
Elasticity
توانایی افزایش و کاهش خودکار منابع متناسب با بار (Autoscaling)؛ بُعد هزینه‌ای مقیاس‌پذیری.

جملهٔ کلیدی برای پاسخ تشریحی: «اگر سیستم برای یک کاربر کند است، مشکل Performance داریم؛ اگر برای یک کاربر سریع است ولی زیر بار زیاد کند می‌شود، مشکل Scalability داریم؛ اگر گاهی اصلاً جواب نمی‌دهد، مشکل Availability داریم.»

Vertical در برابر Horizontal Scaling

Vertical (Scale Up)

  • سرور قوی‌تر: CPU، RAM، دیسک NVMe بیشتر.
  • بدون تغییر کد؛ ساده و سریع.
  • سقف سخت‌افزاری دارد و هزینه غیرخطی رشد می‌کند.
  • همچنان SPOF است؛ ارتقا معمولاً Downtime دارد.
  • برای دیتابیس اصلی (Primary) اولین و معقول‌ترین قدم است.

Horizontal (Scale Out)

  • افزودن سرورهای بیشتر پشت Load Balancer.
  • عملاً بی‌سقف و Redundancy ذاتی (افزایش Availability).
  • پیش‌نیاز: اپلیکیشن Stateless و منابع مشترک (Redis، S3، DB).
  • پیچیدگی: هماهنگی، Consistency، شبکه، Deploy و Observability.
  • برای لایهٔ اپلیکیشن (PHP) و Workerها حالت طبیعی است.

در عمل ترکیبی کار می‌کنیم: لایهٔ App را Horizontal مقیاس می‌دهیم (چون PHP ذاتاً Shared-Nothing است) و دیتابیس را ابتدا Vertical و بعد با Read Replica و در نهایت Sharding.

Amdahl's Law یادآوری می‌کند که بخش سریالی سیستم (مثلاً یک Lock سراسری یا یک دیتابیس واحد) سقف مقیاس‌پذیری را تعیین می‌کند؛ هرچقدر هم سرور App اضافه کنید، گلوگاه مشترک جابه‌جا نمی‌شود.

Stateless بودن اپلیکیشن

Stateless یعنی هیچ نود اپلیکیشنی دادهٔ ماندگاری که درخواست بعدی به آن نیاز دارد در حافظه یا دیسک محلی خودش نگه ندارد. در نتیجه هر درخواست می‌تواند به هر نودی برود، نودها قابل‌جایگزینی‌اند (Cattle, not Pets) و می‌توان آن‌ها را بی‌دردسر اضافه، حذف یا Restart کرد.

پشت Load Balancer: Trusted Proxies

وقتی TLS روی Load Balancer خاتمه پیدا می‌کند، اپلیکیشن درخواست را HTTP و با IP خود LB می‌بیند. برای اینکه $request->ip()، url() و isSecure() درست کار کنند باید هدرهای X-Forwarded-* را فقط از Proxyهای مورد اعتماد بپذیریم:

// bootstrap/app.php
->withMiddleware(function (Middleware $middleware) {
    $middleware->trustProxies(at: ['10.0.0.0/8']);
})

Stateless بودن پیش‌نیاز Horizontal Scaling، Autoscaling، Rolling Deploy و Self-healing است. State حذف نمی‌شود؛ به Backing Serviceهای مشترک منتقل می‌شود که خودشان باید HA باشند (Redis Sentinel/Cluster، S3، DB با Replica).

JWT یا Session در Cookie (رمزنگاری‌شده) هم راه دیگری برای Stateless بودن سمت سرور است، ولی ابطال (Revocation) را سخت می‌کند و اندازهٔ هر درخواست را بالا می‌برد.

Load Balancing

Load Balancer ترافیک ورودی را بین چند سرور Backend توزیع می‌کند تا ظرفیت بالا برود، نود خراب از مدار خارج شود و بتوان بدون Downtime دیپلوی کرد.

الگوریتم‌های توزیع بار

Round Robin
نوبتی؛ ساده و مناسب وقتی سرورها هم‌توان و درخواست‌ها هم‌هزینه‌اند.
Weighted Round Robin
سرور قوی‌تر سهم بیشتری می‌گیرد؛ برای سخت‌افزار ناهمگن یا Canary (مثلاً ۵٪ ترافیک به نسخهٔ جدید).
Least Connections
به سروری که کمترین اتصال فعال دارد؛ برای درخواست‌هایی با زمان پاسخ متغیر (آپلود، گزارش، WebSocket) بهتر است.
Least Response Time
ترکیب اتصال فعال و Latency اندازه‌گیری‌شده.
IP Hash
هش IP کلاینت تعیین می‌کند به کدام سرور برود؛ نوعی Stickiness بدون Cookie. با NAT یا Proxy (کاربران زیاد پشت یک IP) توزیع نامتوازن می‌شود.
Consistent Hashing
با اضافه/حذف شدن سرور فقط بخش کوچکی از کلیدها جابه‌جا می‌شوند؛ برای Cache Clusterها و Sharding مهم است.
Power of Two Choices
دو سرور تصادفی انتخاب و کم‌بارترشان استفاده می‌شود؛ تقریباً به خوبیِ Least Connections با هزینهٔ کمتر.

Health Check

  • Active: LB به‌طور دوره‌ای Endpoint سلامت (مثلاً /up در Laravel 11+) را صدا می‌زند و نود ناسالم را خارج می‌کند.
  • Passive: LB خطاهای واقعی ترافیک را می‌شمارد (مثلاً max_fails در Nginx) و نود را موقتاً کنار می‌گذارد.
  • Liveness (پروسس زنده است؟) با Readiness (آمادهٔ گرفتن ترافیک است؟) فرق دارد. Readiness نباید به وابستگی‌ای چک شود که از کار افتادنش همهٔ نودها را هم‌زمان از مدار خارج کند (Cascading Failure).
upstream laravel_app {
    least_conn;
    server 10.0.0.11:80 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:80 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:80 backup;   # فقط وقتی بقیه از دسترس خارج‌اند
    keepalive 32;                 # استفادهٔ مجدد از اتصال‌ها به Backend
}

server {
    listen 443 ssl;
    server_name shop.example.com;

    location / {
        proxy_pass http://laravel_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
    }
}

Sticky Sessions؛ مزایا و معایب

مزایا

  • اپلیکیشن Stateful قدیمی بدون تغییر کد پشت LB کار می‌کند.
  • Cache محلی نود (In-process) بازدهی بیشتری دارد.
  • برای WebSocket یا پروتکل‌های چندمرحله‌ای گاهی لازم است.

معایب

  • توزیع بار نامتوازن (Hot Node).
  • با خرابی یا Scale-in یک نود، Session کاربرانش از بین می‌رود.
  • Autoscaling و Rolling Deploy را پیچیده می‌کند (Connection Draining لازم است).
  • مشکل اصلی (State محلی) را پنهان می‌کند، حل نمی‌کند.

پاسخ استاندارد: «Sticky Session راه‌حل موقت است؛ راه درست Stateless کردن App و انتقال Session به Redis است.» و یادتان باشد خود LB نباید SPOF باشد: جفت LB با Floating IP (keepalived/VRRP) یا LB مدیریت‌شدهٔ ابری، و در لایهٔ بالاتر DNS با چند رکورد یا GeoDNS.

کش در همهٔ لایه‌ها

سریع‌ترین درخواست درخواستی است که اصلاً به سرور شما نرسد. کش را باید از نزدیک‌ترین لایه به کاربر شروع کرد:

Browser cache ─► CDN edge ─► Reverse proxy ─► App cache (Redis/APCu) ─► DB buffer pool
   (0 ms)        (~10-30 ms)   (Nginx/Varnish)   (~1 ms network hop)      (InnoDB/shared_buffers)
 ◄──────────── نزدیک‌تر به کاربر = ارزان‌تر و سریع‌تر، ولی کنترل/Invalidation سخت‌تر ────────────►
لایهچه چیزیابزار / مکانیزمنکته
BrowserAsset، پاسخ‌های GETCache-Control، ETag، Last-ModifiedInvalidation عملاً ممکن نیست؛ از نام فایل نسخه‌دار (Hash) استفاده کنید.
CDNStatic، تصاویر، صفحات عمومیs-maxage، Purge APIفقط محتوای عمومی؛ مراقب Cache شدن پاسخ شخصی باشید.
Reverse Proxyصفحات کامل HTML، پاسخ APINginx fastcgi_cache/proxy_cache، VarnishMicro-caching (۱ تا ۵ ثانیه) در Spike معجزه می‌کند.
Applicationنتیجهٔ Query، محاسبات، FragmentRedis، Memcached، APCu (محلی)بیشترین کنترل؛ Laravel Cache.
FrameworkConfig، Route، View، Eventphp artisan optimize، OPcacheهر Deploy اجرا شود.
Databaseصفحات داده و Index در RAMInnoDB Buffer Pool، PostgreSQL shared_buffersQuery Cache در MySQL 8 حذف شده است.

هدرهای HTTP کش

# Asset با نام Hash‌دار (Vite build): یک سال، بدون Revalidate
Cache-Control: public, max-age=31536000, immutable

# صفحهٔ عمومی: مرورگر ۶۰ ثانیه، CDN ده دقیقه، تا ۳۰ ثانیه Stale مجاز
Cache-Control: public, max-age=60, s-maxage=600, stale-while-revalidate=30

# پاسخ شخصی (پروفایل، سبد خرید): هرگز در کش مشترک
Cache-Control: private, no-store

# Conditional Request: مرورگر با If-None-Match می‌پرسد، سرور 304 بدون Body می‌دهد
ETag: "a1b2c3"

no-cache یعنی «کش کن ولی قبل از استفاده Revalidate کن»؛ برای «اصلاً ذخیره نکن» باید از no-store استفاده کرد. این تفاوت سؤال کلاسیک است.

چه چیزی را کش کنیم؟

  • داده‌ای که زیاد خوانده و کم نوشته می‌شود (کاتالوگ محصول، تنظیمات، منو).
  • محاسبات گران (Aggregation، گزارش، رندر Markdown).
  • پاسخ APIهای خارجی کند یا محدود (با توجه به قوانین آن سرویس).
  • نه: داده‌ای که Staleness آن غیرقابل‌قبول است (موجودی حساب هنگام برداشت)، یا با Hit Ratio بسیار پایین.

معیار موفقیت کش Hit Ratio است. کشی با Hit Ratio پایین فقط یک Hop شبکه و یک نقطهٔ خرابی اضافه کرده است. آن را مانیتور کنید (INFO stats در Redis: keyspace_hits و keyspace_misses).

<?php
// Cache-Aside در Laravel
$product = Cache::remember(
    "product:{$id}:v1",
    now()->addMinutes(10),
    fn () => Product::with('images', 'category')->findOrFail($id)
);

// Invalidation پس از Commit (نه داخل تراکنش!)
DB::transaction(function () use ($product, $data) {
    $product->update($data);
    DB::afterCommit(fn () => Cache::forget("product:{$product->id}:v1"));
});

اگر کلید را داخل تراکنش و قبل از Commit حذف کنید، یک درخواست هم‌زمان ممکن است دادهٔ قدیمی را از DB بخواند و دوباره در کش بگذارد؛ نتیجه: کش Stale تا پایان TTL. همیشه بعد از Commit Invalidate کنید. همچنین در Cache-Aside کلید را حذف کنید، نه اینکه مقدار جدید را Set کنید؛ دو نوشتن هم‌زمان ممکن است با ترتیب برعکس به کش برسند.

استراتژی‌های Invalidation

  • TTL: ساده‌ترین؛ Staleness حداکثر به اندازهٔ TTL. برای جلوگیری از انقضای هم‌زمان، Jitter اضافه کنید (600 + random_int(0, 120)).
  • Explicit Delete: حذف کلید هنگام تغییر داده (Model Event، Observer، Event دامنه).
  • Versioned Keys: نسخه را در کلید بگذارید (products:v{$version})؛ با افزایش نسخه همهٔ کلیدهای قدیمی عملاً بی‌اثر می‌شوند و با TTL پاک می‌شوند.
  • Tags: گروه‌بندی کلیدها برای Flush دسته‌جمعی (در Laravel فقط با Driverهایی مثل Redis و Memcached؛ File و Database پشتیبانی نمی‌کنند).
  • Event-based: سرویس‌های دیگر با پیام (Pub/Sub یا CDC) از تغییر باخبر می‌شوند.
Cache::tags(['products', "category:{$catId}"])->put("product:{$id}", $product, 600);

// بعد از تغییر قیمت‌های یک دسته:
Cache::tags(["category:{$catId}"])->flush();

Cache Stampede (Thundering Herd / Dog-piling)

وقتی یک کلید داغ منقضی می‌شود، صدها درخواست هم‌زمان Miss می‌خورند و همه با هم Query گران را به DB می‌فرستند؛ DB زیر بار می‌رود، Queryها کندتر می‌شوند و درخواست‌های بیشتری Miss می‌خورند (حلقهٔ معیوب).

راه‌حل‌ها

  1. Mutex / Lock: فقط یک درخواست مقدار را بازسازی می‌کند؛ بقیه کمی صبر می‌کنند یا مقدار Stale می‌گیرند.
  2. Stale-While-Revalidate: بعد از انقضای نرم، مقدار قدیمی سرو می‌شود و بازسازی در پس‌زمینه انجام می‌شود (Cache::flexible در Laravel 11+).
  3. Probabilistic Early Expiration (XFetch): هر درخواست با احتمالی که با نزدیک شدن به انقضا بالا می‌رود، زودتر بازسازی می‌کند؛ پس بازسازی پخش می‌شود.
  4. Pre-warming / Refresh-ahead: یک Job زمان‌بندی‌شده کلیدهای داغ را قبل از انقضا بازسازی می‌کند.
  5. TTL Jitter: جلوگیری از انقضای دسته‌جمعی (Cache Avalanche).
<?php
// ۱) Lock: فقط یک پروسس بازسازی می‌کند
function feed(): array
{
    if (($cached = Cache::get('home:feed')) !== null) {
        return $cached;
    }

    // حداکثر ۵ ثانیه برای گرفتن Lock صبر کن؛ Lock خودش بعد از ۱۰ ثانیه آزاد می‌شود
    return Cache::lock('lock:home:feed', 10)->block(5, function () {
        // Double-check: شاید پروسس دیگری همین الان پر کرده باشد
        return Cache::get('home:feed') ?? tap(
            FeedBuilder::build(),
            fn ($feed) => Cache::put('home:feed', $feed, 600 + random_int(0, 60))
        );
    });
}

سایر مشکلات کلاسیک کش

Cache Penetration
درخواست برای کلیدهایی که در DB هم وجود ندارند (مثلاً ID تصادفی توسط مهاجم) همیشه Miss است. راه‌حل: کش کردن نتیجهٔ خالی با TTL کوتاه، Bloom Filter، اعتبارسنجی ورودی.
Cache Avalanche
انقضای هم‌زمان تعداد زیادی کلید یا از کار افتادن کل کش. راه‌حل: Jitter، کش HA، Circuit Breaker و Rate Limit روی مسیر DB.
Hot Key
یک کلید آن‌قدر پرخواننده است که یک نود Redis را اشباع می‌کند. راه‌حل: کش محلی In-process با TTL کوتاه (APCu)، Replica کردن کلید با پسوند تصادفی.

جملهٔ معروف Phil Karlton: «در علوم کامپیوتر فقط دو چیز سخت است: Cache Invalidation و نام‌گذاری.» در پاسخ تشریحی همیشه بگویید چه مقدار Staleness برای این داده قابل‌قبول است؛ این تصمیم، TTL و استراتژی را تعیین می‌کند.

CDN و Object Storage

CDN

CDN شبکه‌ای از سرورهای لبه (Edge / PoP) در نقاط مختلف جغرافیایی است که محتوا را نزدیک کاربر کش می‌کند. نتیجه: Latency کمتر، بار کمتر روی Origin، جذب Spike و حملات DDoS لایهٔ شبکه.

Pull CDN

  • در اولین درخواست، Edge محتوا را از Origin می‌گیرد و کش می‌کند.
  • راه‌اندازی ساده؛ فقط DNS یا URL را عوض می‌کنید.
  • اولین درخواست هر Edge کند است.

Push CDN

  • شما محتوا را صریحاً روی CDN آپلود می‌کنید.
  • کنترل کامل و مناسب فایل‌های بزرگ و کم‌تغییر.
  • مدیریت چرخهٔ عمر فایل‌ها بر عهدهٔ شماست.
  • Cache Busting: Vite نام فایل را با Hash تولید می‌کند (app-3f9a1c.js)؛ با هر تغییر URL عوض می‌شود و می‌توان max-age یک‌ساله داد.
  • Cache Key: مشخص کنید کدام Query String، Header یا Cookie در کلید باشند؛ Cookieهای غیرضروری Hit Ratio را صفر می‌کنند.
  • Origin Shield: یک لایهٔ کش میانی که Edgeها به جای Origin از آن می‌خوانند؛ تعداد درخواست‌ها به Origin را کم می‌کند.
  • Purge: با API یا Tag/Surrogate-Key برای حذف فوری محتوای تغییر‌یافته.

Object Storage

در معماری چندنودی، فایل‌های کاربر نباید روی دیسک محلی بمانند. Object Storage (S3، MinIO، Ceph) فضای تقریباً نامحدود، Durability بالا با Replication داخلی و دسترسی HTTP می‌دهد. برخلاف File System، ساختارش Flat (Bucket + Key) است و برای تغییر جزئی فایل یا قفل فایل مناسب نیست.

پردازش Async با صف

هر کاری که برای پاسخ دادن به کاربر لازم نیست باید از مسیر درخواست خارج شود: ارسال ایمیل و SMS، تولید PDF، پردازش تصویر، فراخوانی Webhook، همگام‌سازی با سرویس خارجی. صف سه مزیت اصلی دارد:

  • Latency کمتر برای کاربر (پاسخ ۲۰۲ یا پاسخ فوری).
  • Load Leveling: Spike ورودی در صف بافر می‌شود و Workerها با سرعت ثابت مصرف می‌کنند؛ DB و سرویس‌های پایین‌دستی منفجر نمی‌شوند.
  • Decoupling و Resilience: اگر سرویس SMS پنج دقیقه قطع باشد، Jobها با Retry بعداً اجرا می‌شوند و درخواست کاربر خطا نمی‌دهد.

یک Job قابل‌اعتماد در Laravel

<?php
namespace App\Jobs;

use App\Models\Order;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Queue\Middleware\WithoutOverlapping;
use Throwable;

class CapturePayment implements ShouldQueue
{
    use Queueable;

    public int $tries = 5;          // حداکثر تلاش
    public int $maxExceptions = 3;  // حداکثر Exception (جدا از Release دستی)
    public int $timeout = 30;       // ثانیه؛ باید از retry_after کمتر باشد

    // فقط ID را Serialize کنید، نه کل آبجکت سنگین را
    public function __construct(public int $orderId) {}

    // Exponential Backoff: 10s، 30s، 2m، 5m
    public function backoff(): array
    {
        return [10, 30, 120, 300];
    }

    public function middleware(): array
    {
        // دو Worker هم‌زمان روی یک سفارش کار نکنند
        return [(new WithoutOverlapping($this->orderId))->expireAfter(60)];
    }

    public function handle(PaymentGateway $gateway): void
    {
        $order = Order::findOrFail($this->orderId);

        if ($order->paid_at !== null) {
            return; // Idempotent: قبلاً انجام شده، دوباره پول کم نکن
        }

        // کلید Idempotency به Gateway: اگر Retry شد، دوبار Capture نمی‌شود
        $result = $gateway->capture($order->payment_ref, idempotencyKey: "order-{$order->id}");

        $order->update(['paid_at' => now(), 'gateway_tx' => $result->id]);
    }

    public function failed(?Throwable $e): void
    {
        // بعد از تمام شدن Retryها: اطلاع به تیم/کاربر، تغییر وضعیت سفارش
        report($e);
    }
}

// Dispatch فقط بعد از Commit تراکنش (وگرنه Worker رکوردی را که هنوز Commit نشده نمی‌بیند)
CapturePayment::dispatch($order->id)->onQueue('payments')->afterCommit();

مفاهیم کلیدی

At-least-once delivery
صف‌ها (از جمله Redis در Laravel) تضمین می‌کنند پیام حداقل یک‌بار پردازش شود، نه دقیقاً یک‌بار. اگر Worker وسط کار بمیرد یا Timeout شود، Job دوباره اجرا می‌شود؛ پس Job باید Idempotent باشد.
retry_after
در config/queue.php: اگر Job بعد از این مدت Ack نشده باشد، دوباره در دسترس Worker دیگر قرار می‌گیرد. باید از --timeout Worker چند ثانیه بیشتر باشد، وگرنه یک Job هم‌زمان دوبار اجرا می‌شود.
Backoff
فاصلهٔ بین تلاش‌ها؛ Exponential (با Jitter) تا سرویس در حال بهبود را زیر بار Retryها خفه نکنیم.
Failed Jobs / DLQ
Jobهایی که همهٔ تلاش‌هایشان شکست خورده در جدول failed_jobs ذخیره می‌شوند (معادل Dead-Letter Queue). با php artisan queue:failed دیده و با queue:retry دوباره اجرا می‌شوند.
Poison Message
پیامی که همیشه شکست می‌خورد (مثلاً دادهٔ خراب)؛ بدون سقف tries صف را برای همیشه مشغول می‌کند.
Unique Jobs
ShouldBeUnique جلوی قرار گرفتن Job تکراری با همان uniqueId در صف را می‌گیرد (نیازمند Lock روی کش مشترک).

Rate Limiting و Throttling

Rate Limiting تعداد درخواست‌های یک «کلید» (کاربر، IP، API Key، Tenant) را در بازهٔ زمانی محدود می‌کند. هدف: جلوگیری از سوءاستفاده و Brute-force، حفاظت از منابع مشترک در برابر یک کاربر پرمصرف (Noisy Neighbor)، تضمین عدالت و پیاده‌سازی پلن‌های تجاری. پاسخ استاندارد هنگام عبور از حد: 429 Too Many Requests با هدر Retry-After.

Rate Limiting در Laravel

<?php
// AppServiceProvider::boot()
use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;

RateLimiter::for('api', function (Request $request) {
    return $request->user()
        ? Limit::perMinute(120)->by($request->user()->id)
        : Limit::perMinute(30)->by($request->ip());
});

RateLimiter::for('login', fn (Request $request) => [
    Limit::perMinute(5)->by($request->input('email') . '|' . $request->ip()),
    Limit::perMinute(100)->by($request->ip()),   // چند محدودیت هم‌زمان
]);

// routes/api.php
Route::middleware(['auth:sanctum', 'throttle:api'])->group(function () { /* ... */ });

// محدودیت دستی برای یک عملیات خاص

Rate Limiter لاراول روی Cache Store پیش‌فرض کار می‌کند؛ در محیط چندنودی این Store باید مشترک (Redis) باشد، وگرنه هر نود شمارندهٔ خودش را دارد و حد واقعی N برابر می‌شود.

پیاده‌سازی Sliding Window Log با Redis

<?php
function allow(string $key, int $limit, int $windowSec): bool
{
    $now = microtime(true);
    $member = $now . ':' . bin2hex(random_bytes(4));

    // MULTI/EXEC: همهٔ دستورها اتمیک اجرا می‌شوند
    $res = Redis::transaction(function ($tx) use ($key, $now, $member, $windowSec) {
        $tx->zremrangebyscore($key, 0, $now - $windowSec); // حذف درخواست‌های قدیمی
        $tx->zadd($key, $now, $member);                    // ثبت درخواست فعلی
        $tx->zcard($key);                                  // شمارش داخل پنجره
        $tx->expire($key, $windowSec);
    });

    return $res[2] <= $limit;
}

الگوی INCR و بعد EXPIRE در دو فراخوانی جدا اتمیک نیست: اگر پروسس بین این دو بمیرد، کلید بدون TTL می‌ماند و کاربر برای همیشه بلاک می‌شود. از MULTI، اسکریپت Lua یا SET key 0 EX 60 NX قبل از INCR استفاده کنید. Rate Limit را هرچه زودتر اعمال کنید (Edge/Gateway/Nginx) تا درخواست اضافه حتی PHP را بوت نکند.

Throttling گاهی به معنای کند کردن (به‌جای رد کردن) درخواست‌هاست؛ و Rate Limit سمت خروجی هم مهم است: وقتی API شخص ثالث حد دارد، از Job Middleware RateLimited یا Redis::throttle() برای محدود کردن Workerها استفاده کنید.

مسیر مقیاس‌پذیری دیتابیس

دیتابیس تقریباً همیشه اولین گلوگاه یک اپلیکیشن Stateless است، چون State اینجا متمرکز شده است. ترتیب منطقی (از ارزان و کم‌ریسک به گران و پیچیده):

1. Query & index tuning      (EXPLAIN, N+1, slow query log)        ← ارزان‌ترین، بیشترین اثر
2. Connection management     (pooling: PgBouncer / ProxySQL)
3. Caching                   (Redis cache-aside, materialized results)
4. Vertical scaling          (more RAM for buffer pool, faster disks)
5. Read replicas             (read/write split, handle replication lag)
6. Partitioning              (one server, table split by range/list/hash)
7. Functional split          (separate DBs per domain / service)
8. Sharding                  (data split across servers by shard key)  ← گران‌ترین، برگشت‌ناپذیر

۱. بهینه‌سازی Query

  • حذف N+1 با Eager Loading (with()) و فعال کردن Model::preventLazyLoading() در محیط توسعه.
  • Index مناسب بر اساس EXPLAIN؛ Composite Index با ترتیب درست ستون‌ها.
  • انتخاب فقط ستون‌های لازم، Pagination با Cursor (cursorPaginate) به‌جای OFFSET بزرگ.
  • پردازش دسته‌ای با chunkById() یا lazyById() به‌جای بارگذاری همه در حافظه.

Replication معمولاً Asynchronous است و Replica چند میلی‌ثانیه تا چند ثانیه عقب است (Replication Lag). سناریوی خطرناک: کاربر پروفایلش را ویرایش می‌کند، Redirect می‌شود و صفحه از Replica خوانده می‌شود و دادهٔ قدیمی نشان می‌دهد. این همان نقض Read-Your-Writes است.

  • 'sticky' => true: اگر در همین درخواست نوشتنی انجام شده باشد، خواندن‌های بعدی همان درخواست از Write Connection انجام می‌شود. توجه: این فقط در محدودهٔ یک چرخهٔ درخواست است، نه درخواست بعدی کاربر.
  • برای درخواست‌های بعدی: خواندن صریح از Primary (User::useWritePdo()->find($id)) برای چند ثانیه پس از نوشتن (مثلاً با یک Flag در Session)، یا خواندن داده‌های حساس همیشه از Primary.
  • Jobهایی که بلافاصله پس از نوشتن Dispatch می‌شوند هم ممکن است از Replica دادهٔ قدیمی بخوانند.

۳. Partitioning در برابر Sharding

Partitioning

  • تقسیم یک جدول بزرگ به چند قسمت داخل همان سرور (Range بر اساس تاریخ، List، Hash).
  • برای اپلیکیشن شفاف است.
  • Partition Pruning و حذف داده‌های قدیمی با DROP PARTITION به‌جای DELETE سنگین.
  • ظرفیت نوشتن کل سرور را افزایش نمی‌دهد.

Sharding

  • تقسیم داده بین چند سرور مستقل بر اساس Shard Key (مثلاً tenant_id).
  • ظرفیت نوشتن و ذخیره‌سازی را افقی افزایش می‌دهد.
  • Join و تراکنش بین Shardها سخت یا ناممکن؛ Resharding دردناک؛ Hot Shard.
  • منطق Routing در App یا لایهٔ Proxy (مثل Vitess برای MySQL، Citus برای PostgreSQL).

انتخاب Shard Key مهم‌ترین تصمیم است: باید Cardinality بالا داشته باشد، بار را یکنواخت پخش کند و بیشتر Queryها فقط به یک Shard نیاز داشته باشند. tenant_id در SaaS معمولاً انتخاب خوبی است؛ created_at بد است چون همهٔ نوشتن‌ها به آخرین Shard می‌رود (Hot Shard).

۴. Connection Pooling

با Horizontal Scaling، تعداد اتصال‌ها چندبرابر می‌شود: تعداد سرور × pm.max_children (یا تعداد Workerهای Octane). مثلاً ۲۰ سرور × ۵۰ Worker = ۱۰۰۰ اتصال؛ PostgreSQL به ازای هر اتصال یک پروسس می‌سازد و این حجم را خوب تحمل نمی‌کند. راه‌حل: PgBouncer (حالت Transaction Pooling) یا ProxySQL برای MySQL. در حالت Transaction Pooling، Prepared Statementهای سمت سرور و تنظیمات سطح Session باید با احتیاط استفاده شوند.

Autoscaling لایهٔ App بدون فکر کردن به سقف اتصال دیتابیس، در اوج ترافیک خطای Too many connections می‌دهد. سقف Autoscaling را با ظرفیت DB هماهنگ کنید.

همزمانی، Race Condition و Idempotency

در سیستمی با چند نود و چند Worker، دو درخواست هم‌زمان روی یک داده کار کردن قاعده است، نه استثنا. Race Condition یعنی نتیجه به ترتیب زمانی غیرقابل‌پیش‌بینی اجرای عملیات بستگی دارد. رایج‌ترین شکلش Read-Modify-Write است:

stock = 1
Request A: SELECT stock → 1          Request B: SELECT stock → 1
Request A: 1 > 0 ✓ → UPDATE stock=0  Request B: 1 > 0 ✓ → UPDATE stock=0
Result: 2 orders, stock 0  ⇒ oversold (Lost Update)

راه‌حل‌ها (از ساده به پیچیده)

  1. عملیات اتمیک در دیتابیس: شرط و تغییر در یک Statement.
  2. Pessimistic Locking: SELECT … FOR UPDATE داخل تراکنش.
  3. Optimistic Locking: ستون version؛ اگر کسی وسط کار تغییرش داده، Update روی صفر سطر اثر می‌گذارد و دوباره تلاش می‌کنیم.
  4. Distributed Lock: Cache::lock() روی Redis برای عملیاتی که فقط در DB نیست (مثلاً فراخوانی API خارجی).
  5. Unique Constraint: آخرین خط دفاع؛ DB تکراری را رد می‌کند.
<?php
// ۱) اتمیک: شرط داخل WHERE
$affected = Product::whereKey($id)
    ->where('stock', '>', 0)
    ->decrement('stock');

if ($affected === 0) {
    throw new OutOfStockException();
}

// ۲) Pessimistic
DB::transaction(function () use ($id, $qty) {
    $product = Product::whereKey($id)->lockForUpdate()->firstOrFail();
    if ($product->stock < $qty) {
        throw new OutOfStockException();
    }
    $product->decrement('stock', $qty);
});

// ۳) Optimistic
$updated = Product::whereKey($p->id)
    ->where('version', $p->version)
    ->update(['stock' => $p->stock - 1, 'version' => $p->version + 1]);
// $updated === 0  ⇒ conflict ⇒ reload & retry یا خطای 409

// ۴) Distributed Lock با Redis
$lock = Cache::lock("wallet:{$userId}", 10);   // TTL جلوی Deadlock در صورت مرگ پروسس را می‌گیرد
if ($lock->get()) {
    try {
        // عملیات بحرانی
    } finally {
        $lock->release();   // فقط صاحب Lock می‌تواند آزادش کند
    }
}

Redis Lock با یک نود Redis و Failover آسنکرون تضمین قطعی نمی‌دهد (Lock ممکن است بعد از Failover گم شود و GC Pause طولانی ممکن است باعث شود Lock منقضی شده باشد ولی پروسس هنوز فکر کند صاحب آن است). برای درستی مطلق داده، به Constraint و تراکنش دیتابیس یا Fencing Token تکیه کنید و Lock را فقط برای کارایی/کاهش تکرار استفاده کنید.

Idempotency Key

عملیاتی Idempotent است که اجرای چندبارهٔ آن همان اثر اجرای یک‌باره را داشته باشد. GET، PUT و DELETE طبق تعریف HTTP Idempotent هستند؛ POST نیست. وقتی شبکه قطع می‌شود، کلاینت نمی‌داند درخواست پرداخت انجام شده یا نه و دوباره می‌فرستد؛ بدون Idempotency دوبار پول کم می‌شود.

Client ── POST /payments  Idempotency-Key: 7f3a… ──► API
           (timeout, retry with SAME key)
Client ── POST /payments  Idempotency-Key: 7f3a… ──► API: key seen → return stored response (no 2nd charge)
<?php
class EnsureIdempotency
{
    public function handle(Request $request, Closure $next): Response
    {
        $key = $request->header('Idempotency-Key');
        if (! $key) {
            return $next($request);
        }

        $cacheKey = "idem:{$request->user()->id}:{$key}";
        $fingerprint = hash('sha256', $request->getContent());

        if ($saved = Cache::get($cacheKey)) {
            if ($saved['fingerprint'] !== $fingerprint) {
                return response()->json(['message' => 'Key reused with different payload'], 422);
            }
            return response($saved['body'], $saved['status'])->header('Idempotent-Replayed', 'true');
        }

        $lock = Cache::lock("{$cacheKey}:lock", 30);
        if (! $lock->get()) {
            return response()->json(['message' => 'Request in progress'], 409);
        }

        try {
            $response = $next($request);
            if ($response->getStatusCode() < 500) {
                Cache::put($cacheKey, [
                    'fingerprint' => $fingerprint,
                    'status' => $response->getStatusCode(),
                    'body' => $response->getContent(),
                ], now()->addDay());
            }
            return $response;
        } finally {
            $lock->release();
        }
    }
}

برای عملیات مالی، ذخیرهٔ کلید در دیتابیس با Unique Index و در همان تراکنش عملیات اصلی، از کش امن‌تر است؛ چون کش ممکن است Evict شود. پاسخ‌های 5xx را ذخیره نکنید تا کلاینت بتواند دوباره تلاش کند.

Laravel Octane

در مدل کلاسیک PHP-FPM هر درخواست از صفر شروع می‌شود: Autoload، ساخت Container، ثبت Service Providerها، بارگذاری Config و Route؛ و در پایان همه چیز دور ریخته می‌شود (Shared-Nothing). این مدل امن و ساده است ولی سربار Bootstrap در هر درخواست دارد. Octane اپلیکیشن را یک‌بار بوت می‌کند و در حافظهٔ Workerهای طولانی‌مدت نگه می‌دارد؛ درخواست‌ها فقط Handle می‌شوند.

PHP-FPM:   request ─► [boot framework ─► handle ─► teardown]   (every request)

Octane:    worker start ─► [boot framework once]
                               │
           request 1 ─────────►├─ handle ─► reset request state
           request 2 ─────────►├─ handle ─► reset request state
           ...                 │
           after --max-requests ─► worker restarts (memory hygiene)

دام‌های Octane: State Leakage

چون Container و آبجکت‌ها بین درخواست‌ها زنده می‌مانند، هر State که به درخواست وابسته است ممکن است به درخواست کاربر بعدی نشت کند؛ این یک باگ امنیتی جدی است.

<?php
// ❌ اشتباه: Singleton که Request را در Constructor می‌گیرد
$this->app->singleton(TenantContext::class, function ($app) {
    return new TenantContext($app['request']->header('X-Tenant')); // Tenant اولین درخواست برای همیشه!
});

// ✅ درست: scoped — در هر درخواست (و هر Job) از نو ساخته می‌شود
$this->app->scoped(TenantContext::class, function ($app) {
    return new TenantContext($app['request']->header('X-Tenant'));
});

// ✅ یا Resolver تزریق کنید و در زمان استفاده Request را بگیرید
$this->app->singleton(Pricing::class, fn ($app) => new Pricing(fn () => $app['request']));

// ❌ Memory Leak: آرایهٔ Static که با هر درخواست بزرگ‌تر می‌شود
class Audit
{
    public static array $events = [];
    public static function log(string $e): void { static::$events[] = $e; } // هرگز خالی نمی‌شود
}

چک‌لیست Octane

  • به Singletonها Container، Request یا Config Repository را در Constructor تزریق نکنید؛ از scoped یا Closure Resolver استفاده کنید.
  • از Static Property و متغیر Global برای State درخواست استفاده نکنید.
  • --max-requests را برای محدود کردن اثر Memory Leak تنظیم کنید.
  • اتصال دیتابیس بین درخواست‌ها حفظ می‌شود؛ تعداد اتصال = تعداد Worker × تعداد سرور.
  • exit() و die() و هدرهای خام header() مشکل‌سازند؛ از Response لاراول استفاده کنید.
  • پکیج‌های Third-party را از نظر سازگاری با محیط Long-running بررسی کنید.
  • در حالت توسعه با --watch تغییر فایل‌ها را بارگذاری کنید؛ در Production بعد از Deploy حتماً octane:reload.

Octane Latency و Throughput را با حذف سربار Bootstrap بهبود می‌دهد، ولی Queryهای کند یا I/O را سریع نمی‌کند. اگر گلوگاه دیتابیس است، Octane مشکل را حل نمی‌کند. بهای آن: مدل ذهنی Stateful و ریسک نشت داده بین درخواست‌ها.

Autoscaling

Autoscaling یعنی تغییر خودکار تعداد نمونه‌ها متناسب با بار. سه نوع دارد:

  • Reactive: بر اساس متریک (CPU بالای ۶۰–۷۰٪، RPS به ازای هر نود، Latency p95). در Kubernetes: Horizontal Pod Autoscaler.
  • Scheduled: افزایش ظرفیت قبل از زمان‌های شلوغ قابل‌پیش‌بینی (کمپین، ساعت اداری).
  • Predictive: پیش‌بینی بر اساس الگوهای تاریخی.

برای Queue Workerها، CPU متریک مناسبی نیست؛ طول صف یا Wait Time معیار بهتری است. Horizon درون یک Supervisor تعداد پروسس‌ها را تنظیم می‌کند، ولی افزودن ماشین جدید کار Autoscaler زیرساخت است.

نکات عملی Autoscaling: (۱) Cooldown برای جلوگیری از نوسان (Flapping)، (۲) Scale-out سریع و Scale-in محتاطانه، (۳) Image آماده و Boot سریع (زمان Warm-up)، (۴) حداقل نمونه برای تحمل خرابی یک Zone، (۵) سقف هماهنگ با ظرفیت DB و سرویس‌های پایین‌دستی، (۶) Connection Draining هنگام حذف نود.

Back-pressure، Degradation و حذف SPOF

Back-pressure

Back-pressure سازوکاری است که در آن جزء پایین‌دستی وقتی ظرفیتش پر شده به بالادستی علامت می‌دهد «آهسته‌تر بفرست»، به‌جای اینکه درخواست‌ها را بی‌پایان در حافظه انباشته کند و در نهایت از کار بیفتد. بدون آن، صف‌های نامحدود فقط مشکل را عقب می‌اندازند و Latency را منفجر می‌کنند.

  • صف‌های محدود (Bounded): وقتی پر شد، درخواست جدید را رد کن (503 یا 429 با Retry-After).
  • Load Shedding: زیر فشار، درخواست‌های کم‌اهمیت (گزارش، Recommendation، ربات‌ها) را زودتر رد کن تا مسیرهای حیاتی (پرداخت، لاگین) سالم بمانند.
  • Timeout در همه جا: اتصال DB، HTTP Client (Http::timeout(3)->connectTimeout(1))، Job. فراخوانی بدون Timeout یعنی Workerهای قفل‌شده.
  • محدودیت هم‌زمانی: سقف pm.max_children، سقف Worker هر صف، Bulkhead (Pool جدا برای هر وابستگی).
  • Circuit Breaker: وقتی سرویسی پشت سر هم خطا می‌دهد، مدتی صدا زدنش را متوقف کن و سریع Fallback بده.

Graceful Degradation

به‌جای «همه یا هیچ»، سیستم در شرایط بحرانی با قابلیت کمتر ولی همچنان مفید کار کند:

  • سرو کردن دادهٔ Stale از کش وقتی DB در دسترس نیست.
  • خاموش کردن قابلیت‌های جانبی با Feature Flag (Laravel Pennant): پیشنهاد محصول، شمارندهٔ زنده، جست‌وجوی پیشرفته.
  • حالت Read-only هنگام مشکل Primary.
  • ارسال ایمیل و نوتیفیکیشن را به صف بسپار و بعداً انجام بده.
  • نسخهٔ سادهٔ صفحه (بدون شخصی‌سازی) که از CDN سرو می‌شود.

تخمین ظرفیت (Back-of-the-envelope)

هدف تخمین سرانگشتی دقت نیست؛ هدف فهمیدن مرتبهٔ بزرگی است تا تصمیم معماری درست گرفته شود: آیا یک سرور کافی است یا صد سرور؟ آیا داده در RAM جا می‌شود؟

اعداد کلیدی

  • یک روز = ۸۶٬۴۰۰ ثانیه ≈ 105 ثانیه (برای ساده‌سازی).
  • ۱ میلیون درخواست در روز ≈ ~12 RPS میانگین.
  • Peak معمولاً ۲ تا ۵ برابر میانگین در نظر گرفته می‌شود.
  • دسترسی RAM: نانوثانیه؛ Redis در شبکهٔ داخلی: زیر میلی‌ثانیه تا ~۱ms؛ Query ساده با Index: چند میلی‌ثانیه؛ رفت‌وبرگشت بین قاره‌ها: ~۱۰۰ms یا بیشتر.
  • قانون Pareto برای کش: معمولاً حدود ۲۰٪ داده ۸۰٪ خواندن‌ها را پوشش می‌دهد.

مثال کامل

فرض: ۱۰ میلیون DAU، هر کاربر ۲۰ درخواست خواندن و ۲ نوشتن در روز

QPS خواندن  = 10M × 20 / 86,400 ≈ 2,300 RPS   → Peak (×3) ≈ 7,000 RPS
QPS نوشتن   = 10M × 2  / 86,400 ≈ 230 RPS     → Peak ≈ 700 RPS
نسبت Read:Write ≈ 10:1  → کش و Read Replica بیشترین اثر را دارند

ذخیره‌سازی: هر نوشتن ~1 KB
  20M رکورد/روز × 1 KB = 20 GB/روز → ~7.3 TB/سال (بدون Index و Replica)
  با Index (~×1.5) و ۳ نسخه Replica → دهه‌ها TB در چند سال → Partitioning/Archiving لازم

کش: ۲۰٪ داده‌های خوانده‌شدهٔ روزانه
  اگر Working Set روزانه 20 GB باشد → حدود 4 GB RAM در Redis

پهنای باند خروجی: 7,000 RPS × 20 KB ≈ 140 MB/s ≈ 1.1 Gbps در Peak → CDN ضروری

تعداد سرور و قانون Little

Little's Law: L = λ × W؛ تعداد درخواست‌های هم‌زمان در سیستم = نرخ ورود × میانگین زمان پاسخ. این فرمول مستقیماً تعداد Worker لازم را می‌دهد:

Peak = 7,000 RPS ، میانگین زمان پاسخ = 100 ms
Concurrency = 7,000 × 0.1 = 700 درخواست هم‌زمان
→ حدود 700 Worker فعال PHP-FPM (به‌علاوهٔ حاشیهٔ اطمینان ~30٪ → ~900)
اگر هر سرور 60 Worker داشته باشد (محدود به RAM: 60 × ~50MB ≈ 3GB) → ~15 سرور
+ N+1 یا N+2 برای تحمل خرابی و Deploy → 17 سرور

اگر زمان پاسخ را با کش به 50 ms برسانیم → نصف Worker و نصف سرور.

در سؤال طراحی، تخمین را با فرض‌های صریح شروع کنید (DAU، درخواست به ازای کاربر، اندازهٔ رکورد، نسبت Read/Write)، اعداد را گرد کنید و در پایان نتیجهٔ معماری بگیرید: «نسبت ۱۰ به ۱ یعنی کش و Replica»، «۷ ترابایت در سال یعنی Partitioning و Archiving»، «۱ گیگابیت خروجی یعنی CDN».

تخمین را با Load Test (k6، JMeter، Locust) روی محیط شبیه Production تأیید کنید. Latency را با Percentile (p95/p99) بسنجید؛ میانگین، دم توزیع را پنهان می‌کند و کاربرانِ کند معمولاً همان پرارزش‌ترین‌ها (با دادهٔ بیشتر) هستند.

سوالات تشریحی

مفاهیم Scalability، Performance و Availability را تعریف کنید و تفاوت آن‌ها را با مثال توضیح دهید.

Performance: سرعت سیستم برای پاسخ به یک درخواست؛ با Latency (p50/p95/p99) و مصرف منابع به ازای هر درخواست سنجیده می‌شود.

Scalability: توانایی حفظ کارایی هنگام افزایش بار با افزودن منابع؛ معیار آن Throughput است و ایده‌آل، رشد تقریباً خطی ظرفیت با منابع است.

Availability: درصد زمانی که سیستم پاسخ درست می‌دهد (مثلاً 99.9٪ ≈ ۸٫۷۶ ساعت Downtime در سال)؛ با Redundancy و حذف SPOF به دست می‌آید.

  • صفحه‌ای که با یک کاربر ۴ ثانیه طول می‌کشد ← مشکل Performance (مثلاً N+1 Query).
  • صفحه‌ای که با ۱۰ کاربر ۱۰۰ms و با ۵۰۰۰ کاربر ۸ ثانیه است ← مشکل Scalability (گلوگاه DB یا Worker).
  • سایتی که با خرابی تنها سرور دیتابیس کاملاً قطع می‌شود ← مشکل Availability.

رابطه: این‌ها مستقل ولی به هم مرتبط‌اند. Horizontal Scaling معمولاً Availability را هم بالا می‌برد (Redundancy)، ولی ممکن است Latency را به‌خاطر Hopهای شبکه و Consistency کمی بدتر کند. بهبود Performance (کاهش زمان هر درخواست) طبق قانون Little ظرفیت را هم افزایش می‌دهد، چون Worker سریع‌تر آزاد می‌شود. در طراحی باید برای هر سه هدف عددی (SLO) تعریف کرد.

Vertical Scaling و Horizontal Scaling را مقایسه کنید. در چه شرایطی هر کدام را انتخاب می‌کنید؟

Vertical (Scale Up): افزایش منابع یک ماشین (CPU، RAM، دیسک). Horizontal (Scale Out): افزودن ماشین‌های بیشتر و توزیع بار بینشان.

  • Vertical: مراحل اولیهٔ محصول، اجزای Stateful که توزیعشان سخت است (دیتابیس Primary)، وقتی زمان کم است و هنوز به سقف نرسیده‌ایم.
  • Horizontal: لایهٔ App و Workerها (PHP ذاتاً Shared-Nothing است)، نیاز به HA، بار متغیر که Autoscaling می‌طلبد.

در عمل ترکیبی: App را افقی، DB را ابتدا عمودی و سپس با Read Replica و در نهایت Sharding افقی می‌کنیم. پیش از هر دو، بهینه‌سازی (Index، کش، حذف N+1) ارزان‌ترین «Scaling» است.

منظور از Stateless بودن اپلیکیشن چیست؟ برای اینکه یک اپلیکیشن Laravel را روی چند سرور پشت Load Balancer اجرا کنید، چه تغییراتی لازم است؟

تعریف: نود Stateless هیچ دادهٔ ماندگاری که درخواست بعدی به آن نیاز داشته باشد در حافظه یا دیسک محلی نگه نمی‌دارد؛ بنابراین هر درخواست می‌تواند به هر نودی برود و نودها قابل جایگزینی‌اند.

چرا: پیش‌نیاز Horizontal Scaling، Autoscaling، Rolling Deploy و تحمل خرابی است. بدون آن مجبور به Sticky Session هستیم.

تغییرات در Laravel:

  • Session: SESSION_DRIVER=redis (یا database).
  • Cache و Lock: CACHE_STORE=redis تا Rate Limiter، Cache::lock و ShouldBeUnique سراسری باشند.
  • فایل‌ها: FILESYSTEM_DISK=s3؛ هیچ آپلودی روی دیسک محلی.
  • Queue: Redis/SQS به‌جای sync؛ Workerها روی ماشین‌های جدا.
  • APP_KEY یکسان روی همهٔ نودها.
  • Scheduler: ->onOneServer() تا Taskها چندبار اجرا نشوند.
  • لاگ: stderr یا ارسال متمرکز (ELK، Loki).
  • Trusted Proxies: تنظیم trustProxies برای IP و HTTPS درست.
  • Build یکسان (Image واحد) و php artisan optimize در Deploy.

نکته: State حذف نمی‌شود، به Backing Serviceها منتقل می‌شود؛ پس Redis و DB خودشان باید HA باشند وگرنه SPOF جدید ساخته‌ایم.

تفاوت Load Balancer لایهٔ ۴ و لایهٔ ۷ چیست؟ الگوریتم‌های رایج توزیع بار و مزایا و معایب Sticky Session را توضیح دهید.

L4: در لایهٔ Transport کار می‌کند و فقط IP و Port را می‌بیند؛ اتصال TCP را بدون فهم محتوای آن هدایت می‌کند. بسیار سریع و کم‌سربار (AWS NLB، HAProxy در mode tcp).

L7: درخواست HTTP را Parse می‌کند؛ مسیریابی بر اساس Path، Host، Header و Cookie، TLS Termination، فشرده‌سازی، Rate Limit و WAF ممکن است (Nginx، ALB، Envoy). سربار بیشتر ولی انعطاف بسیار بیشتر.

الگوریتم‌ها:

  • Round Robin / Weighted: ساده؛ وزن برای سرورهای ناهمگن یا Canary.
  • Least Connections: مناسب درخواست‌های با مدت متغیر.
  • IP Hash / Consistent Hash: یک کلاینت یا کلید همیشه به یک سرور؛ برای کش‌های توزیع‌شده مفید، ولی پشت NAT نامتوازن.
  • Least Response Time / Power of Two Choices: تطبیقی‌تر.

Health Check: Active (فراخوانی /up) و Passive (شمارش خطا)؛ بدون آن LB ترافیک را به نود مرده می‌فرستد.

Sticky Session: مزیت: اپلیکیشن Stateful بدون تغییر کار می‌کند و کش محلی مؤثرتر است. معایب: توزیع نامتوازن، از دست رفتن Session با خرابی نود، دشواری Autoscaling و Deploy، و پنهان کردن مشکل اصلی. راه درست: Stateless کردن App و Session در Redis. همچنین خود LB نباید SPOF باشد (جفت LB با Floating IP یا سرویس مدیریت‌شده).

استراتژی‌های Cache-Aside، Read-Through، Write-Through و Write-Behind را تعریف و مقایسه کنید. هر کدام برای چه سناریویی مناسب است؟
  • Cache-Aside (Lazy Loading): اپلیکیشن ابتدا کش را می‌خواند؛ در Miss از DB خوانده و در کش ذخیره می‌کند؛ هنگام نوشتن DB را به‌روز و کلید را حذف می‌کند. رایج‌ترین الگو و همان Cache::remember. مزیت: فقط دادهٔ پرمصرف کش می‌شود و خرابی کش سیستم را از کار نمی‌اندازد. عیب: Miss اول کند، ریسک Stale و Stampede.
  • Read-Through: مثل Cache-Aside، ولی منطق بارگذاری از DB درون خود لایهٔ کش است و App فقط با کش صحبت می‌کند. کد تمیزتر، نیازمند کتابخانه یا سرویس با Loader.
  • Write-Through: هر نوشتن به‌صورت سنکرون هم در کش و هم در DB انجام می‌شود. کش همیشه تازه است؛ عیب: Latency نوشتن بیشتر و کش شدن داده‌هایی که شاید هرگز خوانده نشوند (معمولاً با TTL ترکیب می‌شود).
  • Write-Behind (Write-Back): نوشتن فقط در کش و انتقال Async و دسته‌ای به DB. سریع‌ترین نوشتن و کاهش بار DB؛ عیب: ریسک از دست رفتن داده در صورت خرابی کش و پیچیدگی ترتیب و Consistency.

سناریوها:

  • کاتالوگ محصول، پروفایل، تنظیمات ← Cache-Aside.
  • داده‌ای که بلافاصله پس از نوشتن زیاد خوانده می‌شود (مثلاً Leaderboard) ← Write-Through.
  • شمارندهٔ بازدید، لایک، آمار با تحمل از دست رفتن اندک ← Write-Behind (مثلاً INCR در Redis و Job دوره‌ای برای Flush به DB).

در هر حالت باید مشخص کرد چه میزان Staleness قابل‌قبول است و Invalidation پس از Commit تراکنش انجام شود.

Cache Stampede چیست و چه راهکارهایی برای جلوگیری از آن در Laravel وجود دارد؟

تعریف: وقتی یک کلید پرمصرف منقضی می‌شود، تعداد زیادی درخواست هم‌زمان Miss می‌خورند و همه با هم محاسبهٔ گران یا Query سنگین را به DB می‌فرستند (Thundering Herd). DB کند می‌شود، Queryها طولانی‌تر و درخواست‌های بیشتری Miss می‌خورند؛ ممکن است کل سیستم از کار بیفتد.

راهکارها:

  1. Lock (Mutex): فقط یک درخواست بازسازی می‌کند و بقیه صبر یا مقدار قدیمی دریافت می‌کنند.
  2. Stale-While-Revalidate: Cache::flexible('key', [300, 600], fn () => ...) در Laravel 11+؛ پس از Fresh Period مقدار قدیمی سرو و بازسازی پس از ارسال پاسخ انجام می‌شود.
  3. Probabilistic Early Expiration: بازسازی تصادفی زودتر از انقضا، متناسب با هزینهٔ محاسبه.
  4. Refresh-ahead: Job زمان‌بندی‌شده کلیدهای داغ را قبل از انقضا گرم می‌کند.
  5. TTL Jitter: جلوگیری از انقضای هم‌زمان کلیدهای متعدد (Avalanche).
return Cache::get('home:feed') ?? Cache::lock('lock:home:feed', 10)
    ->block(5, fn () => Cache::get('home:feed') ?? tap(
        FeedBuilder::build(),
        fn ($v) => Cache::put('home:feed', $v, 600 + random_int(0, 60))
    ));

نکات: Double-check بعد از گرفتن Lock ضروری است؛ TTL خود Lock باید از زمان محاسبه بیشتر باشد؛ Lock باید روی Store مشترک (Redis) باشد. Trade-off: Lock کمی Latency اضافه می‌کند و SWR داده را برای مدتی Stale نشان می‌دهد؛ انتخاب به میزان Staleness قابل‌تحمل بستگی دارد.

سایت فروشگاهی داریم که صفحهٔ محصول آن در کمپین‌ها چندین هزار درخواست در ثانیه دریافت می‌کند و دیتابیس زیر بار می‌رود. کش را در چه لایه‌هایی و چگونه طراحی می‌کنید؟

تحلیل: بار عمدتاً خواندنی است و صفحهٔ محصول برای همه یکسان است، به جز بخش‌های شخصی (سبد خرید، قیمت ویژه) و موجودی که سریع تغییر می‌کند.

Browser ─► CDN (assets + product HTML, s-maxage=60) ─► Nginx micro-cache (2s)
        ─► Laravel: Redis cache-aside (product data, 10m + jitter)
        ─► MySQL replicas (cache misses) ; Primary only for writes
Personal parts (cart, price for user) ─► small AJAX call, private, no-store
  • Browser و CDN: Assetهای Hash‌دار با max-age یک‌ساله و immutable. HTML عمومی محصول با s-maxage کوتاه و stale-while-revalidate؛ Purge با API هنگام تغییر قیمت.
  • جدا کردن بخش شخصی: صفحه برای همه یکسان سرو می‌شود و سبد خرید و موجودی لحظه‌ای با یک درخواست سبک جدا بارگذاری می‌شوند؛ این کار Hit Ratio را بالا نگه می‌دارد.
  • Reverse Proxy: Micro-cache یک تا دو ثانیه‌ای در Nginx؛ هزاران درخواست در ثانیه به چند درخواست در ثانیه به PHP تبدیل می‌شود.
  • Application: Cache-Aside در Redis برای دادهٔ محصول با TTL و Jitter؛ Invalidation با Model Event پس از Commit؛ محافظت از Stampede با Lock یا Cache::flexible.
  • Hot Key: برای محصول کمپین، کش In-process کوتاه‌مدت (APCu چند ثانیه‌ای) تا یک نود Redis اشباع نشود.
  • DB: Missها به Read Replica؛ نوشتن موجودی با UPDATE اتمیک روی Primary.
  • پیش‌گرم کردن کش قبل از شروع کمپین.

Trade-off: قیمت یا موجودی ممکن است چند ثانیه Stale باشد؛ بنابراین مرجع نهایی همیشه هنگام ثبت سفارش، دیتابیس است (اعتبارسنجی مجدد قیمت و موجودی در Checkout).

چرا از صف (Queue) استفاده می‌کنیم؟ یک Job قابل‌اعتماد در Laravel چه ویژگی‌هایی باید داشته باشد؟ مفاهیم Retry، Backoff، Idempotency و Failed Jobs را توضیح دهید.

چرا صف: (۱) کاهش Latency پاسخ با خارج کردن کارهای غیرضروری از مسیر درخواست؛ (۲) Load Leveling: صف Spike را جذب می‌کند و Workerها با نرخ قابل‌کنترل مصرف می‌کنند؛ (۳) Decoupling و Resilience: خرابی موقت سرویس خارجی با Retry جبران می‌شود؛ (۴) مقیاس مستقل Workerها.

ویژگی‌های Job خوب:

  • Idempotent: صف‌ها At-least-once هستند؛ Job ممکن است دوبار اجرا شود (Timeout، مرگ Worker، retry_after). پس قبل از اثر جانبی بررسی شود که قبلاً انجام نشده و از Idempotency Key در API خارجی و Unique Constraint استفاده شود.
  • Retry محدود: $tries و $maxExceptions تا Poison Message صف را قفل نکند.
  • Backoff نمایی: مثلاً [10, 30, 120, 300] تا سرویس آسیب‌دیده زیر Retry خفه نشود.
  • Timeout: $timeout کمتر از retry_after، وگرنه اجرای هم‌زمان تکراری رخ می‌دهد.
  • Payload کوچک: فقط ID؛ داده در handle تازه خوانده شود.
  • afterCommit: Dispatch بعد از Commit تا Worker رکوردی ببیند که وجود دارد.
  • Failed Jobs: پس از اتمام تلاش‌ها در failed_jobs (معادل DLQ) ذخیره می‌شود؛ متد failed() برای جبران یا اطلاع‌رسانی؛ queue:retry برای اجرای مجدد پس از رفع مشکل.
  • جداسازی صف‌ها: payments جدا از reports با Supervisor جدا در Horizon.

public int $timeout = 30;
public function backoff(): array { return [10, 30, 120, 300]; }

Horizon برای مانیتورینگ Wait Time، Throughput و Jobهای ناموفق و Auto-balancing Workerها استفاده می‌شود.

الگوریتم‌های Rate Limiting (Fixed Window، Sliding Window، Token Bucket و Leaky Bucket) را مقایسه کنید. برای یک API عمومی کدام را پیشنهاد می‌کنید و آن را کجا پیاده‌سازی می‌کنید؟
  • Fixed Window: یک شمارنده برای هر بازهٔ ثابت؛ ساده و O(1)، ولی در مرز پنجره تا ۲ برابر حد عبور می‌کند.
  • Sliding Window Log: ذخیرهٔ Timestamp همهٔ درخواست‌ها (مثلاً Sorted Set در Redis)؛ دقیق ولی حافظهٔ O(N).
  • Sliding Window Counter: ترکیب وزنی شمارندهٔ پنجرهٔ قبل و فعلی؛ تقریباً دقیق با حافظهٔ O(1).
  • Token Bucket: سطل با ظرفیت B و نرخ پر شدن r؛ Burst تا B مجاز و نرخ میانگین r. انعطاف‌پذیر و رایج‌ترین برای API.
  • Leaky Bucket: صف با ظرفیت محدود که با نرخ ثابت تخلیه می‌شود؛ خروجی کاملاً صاف (Traffic Shaping)، ولی Burst مشروع هم تأخیر می‌خورد.

پیشنهاد برای API عمومی: Token Bucket یا Sliding Window Counter، چون کلاینت‌ها رفتار انفجاری طبیعی دارند (باز شدن یک صفحه چند درخواست هم‌زمان می‌زند) و در عین حال نرخ میانگین کنترل می‌شود. Leaky Bucket برای محافظت از سرویسی که نرخ ثابت می‌خواهد (مثلاً ارسال به Gateway پیامک) مناسب است.

محل پیاده‌سازی (چندلایه):

  • Edge/Gateway/Nginx (limit_req): محدودیت درشت بر اساس IP؛ درخواست اضافه حتی به PHP نمی‌رسد.
  • اپلیکیشن: RateLimiter::for() و Middleware throttle با کلید کاربر، API Key یا Tenant و حد متفاوت برای هر پلن.
  • Store شمارنده باید مشترک و اتمیک باشد (Redis با Lua یا MULTI).

پاسخ 429 با هدرهای Retry-After و X-RateLimit-Remaining تا کلاینت بتواند Backoff کند. برای مسیرهای حساس (لاگین، OTP) محدودیت ترکیبی بر اساس IP و نام کاربری.

کد زیر برای ثبت سفارش در یک فروشگاه پرترافیک نوشته شده است. چه مشکلی دارد و چگونه اصلاحش می‌کنید؟ 
public function store(Request $request)
{
    $product = Product::find($request->product_id);
    if ($product->stock > 0) {
        $product->stock = $product->stock - 1;
        $product->save();
        Order::create(['product_id' => $product->id, 'user_id' => auth()->id()]);
        Mail::to(auth()->user())->send(new OrderPlaced());
    }
    return back();
}

مشکلات:

  • Race Condition (Lost Update): الگوی Read-Modify-Write؛ دو درخواست هم‌زمان هر دو stock = 1 می‌خوانند و هر دو سفارش ثبت می‌کنند ← Oversell.
  • نبود تراکنش: اگر Order::create شکست بخورد، موجودی کم شده ولی سفارشی وجود ندارد.
  • ارسال ایمیل سنکرون: Latency بالا و اگر SMTP کند باشد Workerهای FPM قفل می‌شوند.
  • Double Submit: کلیک دوباره یا Retry شبکه، سفارش تکراری می‌سازد.
  • find بدون OrFail و نبود Validation.
public function store(StoreOrderRequest $request)
{
    $order = DB::transaction(function () use ($request) {
        $affected = Product::whereKey($request->product_id)
            ->where('stock', '>', 0)
            ->decrement('stock');           // شرط و تغییر اتمیک

        if ($affected === 0) {
            throw new OutOfStockException();
        }

        return Order::create([
            'product_id' => $request->product_id,
            'user_id' => $request->user()->id,
            'idempotency_key' => $request->header('Idempotency-Key'), // Unique Index
        ]);
    });

    Mail::to($request->user())->queue(new OrderPlaced($order));
    return to_route('orders.show', $order);
}

جایگزین‌ها: lockForUpdate() داخل تراکنش اگر منطق چندمرحله‌ای است، یا Optimistic Locking با ستون version وقتی رقابت کم است. برای فروش فوق‌العاده (Flash Sale) می‌توان موجودی را در Redis با DECR اتمیک رزرو و سفارش را از طریق صف ثبت کرد تا DB زیر Lock Contention نرود.

Idempotency Key چیست و چرا برای APIهای پرداخت ضروری است؟ نحوهٔ پیاده‌سازی آن را شرح دهید.

تعریف: عملیاتی Idempotent است که اجرای چندباره‌اش همان اثر اجرای یک‌باره را داشته باشد. Idempotency Key شناسهٔ یکتایی (معمولاً UUID) است که کلاینت برای هر عملیات منطقی تولید و در هدر (مثلاً Idempotency-Key) ارسال می‌کند؛ Retryهای همان عملیات با همان کلید فرستاده می‌شوند.

چرا: در سیستم توزیع‌شده، Timeout به معنی شکست نیست؛ ممکن است سرور پرداخت را انجام داده ولی پاسخ در راه گم شده باشد. کلاینت (یا LB یا Queue) دوباره تلاش می‌کند و بدون کلید، کاربر دوبار پرداخت می‌کند. POST ذاتاً Idempotent نیست.

پیاده‌سازی:

  1. دریافت کلید و ساختن کلید ذخیره‌سازی در محدودهٔ کاربر (user_id + key).
  2. اگر نتیجه قبلاً ذخیره شده، همان پاسخ را برگردان (بدون اجرای مجدد). اگر Payload با دفعهٔ قبل فرق دارد ← 422.
  3. اگر درخواستی با همین کلید در حال اجراست (Lock گرفته شده) ← 409.
  4. اجرای عملیات و ذخیرهٔ پاسخ (برای پاسخ‌های غیر 5xx) با TTL مثلاً ۲۴ ساعت.

نکات طراحی:

  • برای عملیات مالی کلید را در DB با Unique Index و در همان تراکنش ثبت کنید؛ کش ممکن است Evict شود.
  • در فراخوانی Gateway بیرونی هم کلید را پاس دهید (بسیاری از Gatewayها پشتیبانی می‌کنند) تا Retry در Job هم امن باشد.
  • کلید جایگزین Validation نیست؛ Unique Constraint روی مفهوم کسب‌وکاری (مثلاً یک پرداخت به ازای هر سفارش) آخرین خط دفاع است.

این الگو در کنار صف‌های At-least-once، عملاً «Exactly-once effect» را می‌سازد.

CPU دیتابیس MySQL یک سیستم در ساعات اوج به ۹۵٪ می‌رسد و سایت کند می‌شود. قدم‌به‌قدم چه می‌کنید؟ مسیر مقیاس‌پذیری دیتابیس را توضیح دهید.

۱. اندازه‌گیری قبل از اقدام: Slow Query Log، performance_schema و Digestها برای پیدا کردن Queryهای پرهزینه (مجموع زمان، نه فقط کندترین)، و Laravel Telescope/Pulse یا APM برای یافتن N+1 و Endpoint مقصر.

۲. بهینه‌سازی Query (ارزان‌ترین و مؤثرترین): EXPLAIN و افزودن Composite/Covering Index، حذف N+1 با Eager Loading، حذف SELECT *، تبدیل OFFSET بزرگ به Cursor Pagination، انتقال گزارش‌های سنگین به Replica یا Job شبانه.

۳. مدیریت اتصال: بررسی تعداد اتصال‌ها؛ Pooling با ProxySQL.

۴. کش: Cache-Aside در Redis برای Queryهای پرتکرار با Hit Ratio بالا؛ محافظت از Stampede.

۵. Vertical Scaling: RAM بیشتر تا Working Set در Buffer Pool جا شود؛ دیسک سریع‌تر.

۶. Read Replica: اگر Read-heavy است، تنظیم read/write و sticky در Laravel؛ مدیریت Replication Lag و Read-Your-Writes.

۷. Partitioning: برای جداول عظیم زمانی (لاگ، سفارش‌ها) بر اساس Range تاریخ؛ آرشیو دادهٔ قدیمی.

۸. Functional Split و Sharding: جدا کردن دیتابیس دامنه‌ها، و در نهایت Sharding بر اساس کلیدی مثل tenant_id وقتی ظرفیت نوشتن یک سرور کافی نیست.

اصل کلیدی: از ارزان و برگشت‌پذیر به گران و برگشت‌ناپذیر. Sharding پیچیدگی دائمی (Join و تراکنش بین Shard، Resharding) می‌آورد و فقط وقتی توجیه دارد که بقیهٔ راه‌ها تمام شده باشند.

کوتاه‌مدت در بحران: فعال کردن Micro-cache، Rate Limit روی Endpointهای سنگین، و خاموش کردن قابلیت‌های غیرحیاتی با Feature Flag (Graceful Degradation).

Replication Lag چیست و چه مشکلی برای اپلیکیشن ایجاد می‌کند؟ گزینهٔ sticky در تنظیمات دیتابیس Laravel چه کاری انجام می‌دهد و آیا کافی است؟

تعریف: در Replication آسنکرون (پیش‌فرض MySQL)، Primary تراکنش را Commit و به کلاینت پاسخ می‌دهد و تغییرات بعداً (از طریق Binlog) روی Replica اعمال می‌شوند. فاصلهٔ زمانی بین Commit روی Primary و اعمال روی Replica را Replication Lag می‌گویند؛ معمولاً میلی‌ثانیه‌ها، ولی زیر بار نوشتن سنگین یا Query طولانی روی Replica می‌تواند به ثانیه‌ها یا دقیقه‌ها برسد.

مشکل: نقض Read-Your-Writes: کاربر آدرسش را تغییر می‌دهد، Redirect می‌شود و صفحهٔ بعد از Replica دادهٔ قدیمی نشان می‌دهد. یا Jobی که بلافاصله بعد از ایجاد رکورد اجرا می‌شود آن را روی Replica پیدا نمی‌کند (ModelNotFoundException).

sticky: با 'sticky' => true اگر در طول همان چرخهٔ درخواست عملیات نوشتنی روی Write Connection انجام شده باشد، خواندن‌های بعدی همان درخواست هم از Write Connection انجام می‌شوند.

کافی نیست، چون: درخواست بعدی کاربر (پس از Redirect) و Jobهای صف چرخهٔ جدیدی هستند و دوباره از Replica می‌خوانند.

راه‌حل‌های تکمیلی:

  • پس از نوشتن، یک Flag در Session (مثلاً تا ۵ ثانیه) و در آن مدت خواندن از Primary با useWritePdo().
  • خواندن داده‌های حساس (موجودی، وضعیت پرداخت) همیشه از Primary.
  • در Job، خواندن از Write Connection یا Dispatch با تأخیر کوتاه.
  • مانیتورینگ Lag و خارج کردن Replica عقب‌مانده از Pool خواندن.
  • Semi-synchronous Replication برای کاهش ریسک از دست رفتن داده هنگام Failover (به قیمت Latency نوشتن).
Laravel Octane چه تفاوتی با مدل PHP-FPM دارد؟ مزایا، معایب و دام‌های رایج آن را توضیح دهید. کد زیر تحت Octane چه مشکلی دارد؟ 
$this->app->singleton(CurrentLocale::class, function ($app) {
    return new CurrentLocale($app['request']->header('Accept-Language'));
});

تفاوت: PHP-FPM مدل Shared-Nothing دارد؛ هر درخواست فریم‌ورک را از صفر بوت و در پایان همه چیز را دور می‌ریزد. Octane اپلیکیشن را یک‌بار در Workerهای طولانی‌مدت (Swoole، RoadRunner یا FrankenPHP) بوت می‌کند و درخواست‌ها را روی همان نمونه Handle می‌کند.

مزایا: حذف سربار Bootstrap، Latency کمتر و Throughput بیشتر با سخت‌افزار یکسان؛ امکان اتصال‌های پایدار و در Swoole قابلیت‌هایی مثل Octane::concurrently.

معایب و دام‌ها:

  • State Leakage: Singleton و Static بین درخواست‌ها و کاربران مختلف باقی می‌مانند.
  • Memory Leak: آرایه‌های Static یا Listenerهایی که هر درخواست اضافه می‌شوند؛ با --max-requests کنترل می‌شود.
  • نیاز به octane:reload پس از Deploy؛ ناسازگاری بعضی پکیج‌ها؛ exit() و header() خام.
  • Queryهای کند یا I/O را سریع نمی‌کند؛ اگر گلوگاه DB است اثرش ناچیز است.

مشکل کد: Singleton فقط یک‌بار در هر Worker ساخته می‌شود؛ زبان اولین درخواست برای همهٔ درخواست‌های بعدی آن Worker استفاده می‌شود. در موارد مشابه (Tenant، کاربر جاری) این یک باگ امنیتی و نشت داده بین کاربران است.

$this->app->scoped(CurrentLocale::class, function ($app) {
    return new CurrentLocale($app['request']->header('Accept-Language'));
});

scoped در هر درخواست یا Job نمونهٔ جدید می‌سازد. قاعدهٔ کلی: Request، Container یا Config را در Constructor سرویس‌های Singleton تزریق نکنید؛ در زمان استفاده Resolve کنید.

برای یک شبکهٔ اجتماعی با ۱۰ میلیون کاربر فعال روزانه، QPS، فضای ذخیره‌سازی و تعداد سرور لازم را به‌صورت سرانگشتی تخمین بزنید و نتیجهٔ معماری بگیرید.

فرض‌ها (صریح بیان شوند): هر کاربر روزانه ۵۰ خواندن (Feed، پروفایل) و ۲ نوشتن (پست، کامنت)؛ هر پست ~۱KB متن (مدیا جدا در Object Storage)؛ Peak سه برابر میانگین؛ زمان پاسخ میانگین ۱۰۰ms.

Read QPS  = 10M × 50 / ~10^5 s ≈ 5,000 avg  → ~15,000 peak
Write QPS = 10M × 2  / ~10^5 s ≈ 200 avg    → ~600 peak
Read:Write ≈ 25:1

Storage/day  = 20M writes × 1 KB = 20 GB/day → ~7 TB/year (text only)
Media: if 10% of posts have a 500 KB image → 2M × 0.5 MB = 1 TB/day → Object Storage + CDN

Concurrency (Little's Law) = 15,000 × 0.1 s = 1,500 in-flight requests
App servers: ~60 workers each → ~25 servers + ~30% headroom + N+2 → ~35

نتیجه‌گیری معماری:

  • نسبت ۲۵ به ۱ ← سیستم Read-heavy؛ کش لایه‌ای (Feed در Redis، CDN برای مدیا) و Read Replica اولویت دارند.
  • ۷ ترابایت در سال متن ← Partitioning بر اساس زمان و آرشیو؛ در افق چندساله Sharding بر اساس user_id.
  • ۱ ترابایت مدیا در روز ← حتماً S3 و CDN با آپلود مستقیم Presigned.
  • ۶۰۰ نوشتن در ثانیه در Peak برای یک Primary خوب قابل‌تحمل است؛ ولی کارهای جانبی (Fan-out Feed، نوتیفیکیشن) باید به صف بروند.
  • Working Set کش: اگر ۲۰٪ داده‌های داغ روزانه کش شوند، چند گیگابایت RAM در Redis Cluster.

هدف این تخمین دقت نیست؛ مرتبهٔ بزرگی و گلوگاه‌ها را مشخص می‌کند و باید با Load Test تأیید شود.

Back-pressure و Graceful Degradation را تعریف کنید. در یک سیستم با وابستگی به سرویس‌های خارجی کند، چگونه از Cascading Failure جلوگیری می‌کنید؟

Back-pressure: سازوکاری که جزء پایین‌دستی هنگام پر شدن ظرفیت به بالادستی علامت «کندتر بفرست» یا «رد شد» می‌دهد، به‌جای انباشت بی‌پایان درخواست‌ها در حافظه. نمونه‌ها: صف محدود، پاسخ 429/503 با Retry-After، سقف هم‌زمانی.

Graceful Degradation: ارائهٔ سرویس با قابلیت کمتر به‌جای قطع کامل؛ مثل سرو دادهٔ Stale از کش، خاموش کردن Recommendation با Feature Flag یا حالت Read-only.

Cascading Failure چگونه رخ می‌دهد: سرویس پرداخت کند می‌شود (۳۰ ثانیه)، Workerهای PHP-FPM منتظر می‌مانند، همهٔ max_children اشغال می‌شوند و حتی صفحاتی که به پرداخت ربطی ندارند هم جواب نمی‌دهند.

راهکارها:

  • Timeout کوتاه و صریح: Http::connectTimeout(1)->timeout(3)؛ هیچ فراخوانی بدون Timeout.
  • Async کردن: فراخوانی‌های غیرضروری مسیر درخواست به صف بروند.
  • Retry محدود با Exponential Backoff و Jitter: Retry بی‌حساب، حملهٔ DDoS به سرویس بیمار است.
  • Circuit Breaker: پس از N خطا، مدتی مستقیماً Fallback بده و سرویس را صدا نزن؛ سپس با Half-open تست کن.
  • Bulkhead: صف و Worker جدا برای هر وابستگی تا کندی یکی همه را از کار نیندازد.
  • Load Shedding: در اوج فشار درخواست‌های کم‌اولویت زودتر رد شوند.
  • Fallback: دادهٔ کش‌شده، پاسخ پیش‌فرض یا پیام «بعداً تلاش کنید».

Trade-off: این الگوها پیچیدگی و گاهی دادهٔ کمتر تازه به همراه دارند، ولی Availability کل سیستم را حفظ می‌کنند. باید برای هر قابلیت مشخص کرد «حیاتی» است یا «قابل حذف موقت».

SPOF چیست؟ اگر LB با Availability ۹۹٫۹۹٪، اپلیکیشن ۹۹٫۹٪ و دیتابیس ۹۹٫۹٪ داشته باشیم، Availability کل چقدر است و چگونه آن را بهبود می‌دهید؟

تعریف: Single Point of Failure جزئی است که خرابی‌اش به تنهایی کل سیستم را از کار می‌اندازد (یک LB، یک دیتابیس، یک Redis، یک سرور Cron، حتی یک نفر که تنها دسترسی Deploy را دارد).

محاسبه: اجزای سری در هم ضرب می‌شوند:

0.9999 × 0.999 × 0.999 ≈ 0.9979  → ~99.79%
≈ 18.4 hours of downtime per year (vs 8.76 h for a single 99.9% component)

Availability کل از ضعیف‌ترین جزء هم کمتر است.

بهبود با Redundancy (اجزای موازی): A = 1 − (1 − A1)(1 − A2). دو نود App مستقل با ۹۹٫۹٪ ← 1 − 0.001² = 99.9999% (با فرض خرابی مستقل و Failover سریع).

  • App: حداقل دو نود در Zoneهای مختلف + Health Check در LB.
  • DB: Primary + Replica با Failover خودکار؛ RPO و RTO مشخص.
  • LB: جفت با Floating IP یا LB مدیریت‌شده.
  • Redis: Sentinel یا Cluster.
  • Cron: روی همهٔ نودها با onOneServer().
  • کاهش وابستگی‌های سری: کارهای غیرضروری را Async کنید تا خرابی‌شان مسیر اصلی را قطع نکند.
  • فرایند: Deploy خودکار و Rollback، Runbook، تست منظم Failover.

Trade-off: هر ۹ اضافه تقریباً هزینه و پیچیدگی را چند برابر می‌کند؛ هدف Availability باید از نیاز کسب‌وکار (SLA) و هزینهٔ Downtime به دست بیاید، نه «هرچه بیشتر بهتر».

خلاصه برای مرور سریع

مفاهیم پایه

  • Performance = سرعت یک درخواست (Latency)؛ Scalability = حفظ کارایی با بار بیشتر (Throughput)؛ Availability = درصد زمان در دسترس.
  • Vertical: ساده، سقف‌دار، SPOF. Horizontal: بی‌سقف، Redundant، نیازمند Stateless.
  • Stateless: Session/Cache/Lock ← Redis؛ فایل ← S3؛ لاگ ← stderr؛ Cron ← onOneServer()؛ APP_KEY یکسان؛ trustProxies.

Load Balancing

  • L4: IP/Port، سریع. L7: HTTP-aware، TLS Termination، مسیریابی Path/Header.
  • الگوریتم‌ها: Round Robin، Weighted، Least Connections، IP Hash، Consistent Hashing.
  • Health Check: Active (/up) و Passive؛ Liveness ≠ Readiness.
  • Sticky Session = راه موقت؛ توزیع نامتوازن و از دست رفتن Session.

کش

الگویک خط
Cache-AsideApp: Miss ← DB ← کش؛ نوشتن ← DB + حذف کلید (Cache::remember)
Read-Throughخود کش از DB بارگذاری می‌کند
Write-Throughنوشتن سنکرون در کش و DB

  • Invalidation: TTL + Jitter، حذف صریح بعد از Commit، Versioned Key، Tags (فقط Redis/Memcached).
  • Stampede: Lock (Cache::lock()->block() + Double-check)، SWR (Cache::flexible)، Early Recompute، Pre-warm.
  • Penetration ← کش نتیجهٔ خالی/Bloom Filter؛ Avalanche ← Jitter؛ Hot Key ← کش محلی.
  • HTTP: immutable برای Asset هش‌دار؛ s-maxage برای CDN؛ no-store برای شخصی؛ no-cache = Revalidate.

صف

  • چرا: Latency کمتر، Load Leveling، Decoupling، Retry.
  • At-least-once ← Job باید Idempotent باشد.
  • $tries، backoff() نمایی، $timeout < retry_after، afterCommit()، فقط ID در Payload، failed() + failed_jobs (DLQ).
  • Horizon: Supervisorها، balance=auto، متریک Wait Time؛ بعد از Deploy horizon:terminate.

Rate Limiting

  • Fixed Window (مشکل مرز ۲×)، Sliding Log (دقیق، حافظه زیاد)، Sliding Counter (تقریبی، O(1))، Token Bucket (Burst مجاز، رایج‌ترین)، Leaky Bucket (خروجی ثابت).
  • Laravel: RateLimiter::for() + throttle:name؛ Store مشترک و اتمیک؛ پاسخ 429 + Retry-After.

دیتابیس

  • مسیر: Query/Index ← Pooling ← کش ← Vertical ← Read Replica ← Partitioning ← Functional Split ← Sharding.
  • sticky => true فقط در همان درخواست؛ Read-Your-Writes در درخواست بعد = خواندن از Primary.
  • Shard Key: Cardinality بالا، توزیع یکنواخت، Query تک‌Shard (مثلاً tenant_id).
  • اتصال‌ها = سرورها × Workerها ← PgBouncer/ProxySQL.

همزمانی

  • Race Condition = Read-Modify-Write. راه‌حل: UPDATE اتمیک با شرط ← lockForUpdate ← Optimistic version ← Cache::lock ← Unique Constraint.
  • Idempotency Key: کلید یکتا از کلاینت، ذخیرهٔ پاسخ، 409 برای در حال اجرا، 422 برای Payload متفاوت، ذخیره در DB برای پول.

Octane

  • یک‌بار Boot، Workerهای ماندگار (Swoole / RoadRunner / FrankenPHP).
  • دام‌ها: Singleton با Request ← scoped؛ Static State؛ Memory Leak ← --max-requests؛ octane:reload بعد از Deploy.

  • Autoscaling: CPU/RPS برای Web، طول صف برای Worker؛ Cooldown؛ سقف هماهنگ با DB.
