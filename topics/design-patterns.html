Design Patterns

الگوهای طراحی GoF (Creational، Structural، Behavioral) و الگوهای معماری رایج در اپلیکیشن‌های PHP — هر کدام با هدف، مسئله، پیاده‌سازی PHP 8، مزایا و معایب و جایی که Laravel از آن استفاده می‌کند؛ به‌علاوهٔ بحث‌های مهم مثل Facade لاراول در برابر GoF، Repository، Service Locator و Active Record در برابر Data Mapper.

الگوی طراحی چیست

Design Pattern یک راه‌حل عمومی، اثبات‌شده و قابل استفادهٔ مجدد برای یک مسئلهٔ تکرارشونده در طراحی نرم‌افزار است. الگو کد آماده نیست؛ یک «قالب» یا «ایده» است که باید با شرایط مسئله تطبیق داده شود. کتاب Design Patterns: Elements of Reusable Object-Oriented Software (1994) از چهار نویسنده معروف به Gang of Four (GoF)، 23 الگو را در سه دسته معرفی کرد.

هر الگو چهار جزء اصلی دارد: نام (واژگان مشترک تیم)، مسئله (چه زمانی کاربرد دارد)، راه‌حل (ساختار کلاس‌ها و روابطشان) و پیامدها (trade-offها).

دستهدغدغهالگوهای GoF
Creationalچگونه object ساخته شود؛ جدا کردن کد استفاده‌کننده از جزئیات ساختSingleton، Factory Method، Abstract Factory، Builder، Prototype
Structuralچگونه کلاس‌ها و objectها ترکیب شوند تا ساختار بزرگ‌تر بسازندAdapter، Bridge، Composite، Decorator، Facade، Flyweight، Proxy
Behavioralتقسیم مسئولیت و نحوهٔ ارتباط بین objectهاChain of Responsibility، Command، Interpreter، Iterator، Mediator، Memento، Observer، State، Strategy، Template Method، Visitor

علاوه بر GoF، الگوهای معماری/Enterprise (از کتاب Martin Fowler، Patterns of Enterprise Application Architecture) مثل MVC، Repository، Service Layer، Active Record، Data Mapper، DTO و Unit of Work در توسعهٔ بک‌اند بسیار مهم‌اند.

اصول پایه‌ای که الگوها از آن‌ها پیروی می‌کنند

  • Program to an interface, not an implementation: وابستگی به abstraction.
  • Favor composition over inheritance: ترکیب objectها انعطاف بیشتری از ارث‌بری دارد (Strategy، Decorator).
  • Encapsulate what varies: بخشی که تغییر می‌کند را جدا کنید.
  • SOLID: به‌ویژه Open/Closed (افزودن رفتار بدون تغییر کد موجود) و Dependency Inversion.

الگو کِی کمک می‌کند و کِی over-engineering است؟

نشانه‌های استفادهٔ درست

  • مسئلهٔ واقعی و تکرارشونده وجود دارد (مثلاً سه درگاه پرداخت، نه یکی).
  • نقطهٔ تغییر مشخص است و انتظار می‌رود تغییر کند.
  • تست‌پذیری یا جایگزینی پیاده‌سازی نیاز واقعی است.
  • الگو ارتباط تیم را ساده می‌کند («این یک Decorator است»).

نشانه‌های over-engineering

  • interface با تنها یک پیاده‌سازی که هرگز دومی نخواهد داشت (بدون نیاز تست).
  • لایه‌های پوشاننده که فقط فراخوانی را پاس می‌دهند.
  • الگو برای «آینده‌ای فرضی» (نقض YAGNI).
  • پیچیدگی بیشتر از مسئله؛ فهم کد برای عضو جدید تیم سخت‌تر می‌شود.

جملهٔ طلایی: «الگو را برای حل مسئله به کار ببرید، نه برای اینکه از الگو استفاده کرده باشید.» در پاسخ تشریحی، همیشه برای هر الگو هم مزیت و هم هزینه (کلاس‌های بیشتر، indirection، پیچیدگی) را بنویسید.

Singleton

هدف: تضمین اینکه یک کلاس فقط یک instance داشته باشد و یک نقطهٔ دسترسی سراسری به آن فراهم شود.

مسئله: منابعی که باید یکتا باشند: اتصال دیتابیس، logger، تنظیمات، connection pool.

<?php
final class Config
{
    private static ?self $instance = null;
    private array $items = [];

    private function __construct() { $this->items = require 'config.php'; }  // جلوگیری از new
    private function __clone() {}                                            // جلوگیری از clone
    public function __wakeup(): never { throw new LogicException('Cannot unserialize singleton'); }

    public static function getInstance(): self
    {
        return self::$instance ??= new self();     // lazy initialization
    }

    public function get(string $key): mixed { return $this->items[$key] ?? null; }
}

Config::getInstance()->get('app.name');

چرا Singleton کلاسیک اغلب Anti-pattern است؟

  • Global state پنهان: هر جای کد می‌تواند Config::getInstance() را صدا بزند؛ وابستگی در امضای کلاس دیده نمی‌شود.
  • تست‌پذیری پایین: نمی‌توان به‌راحتی یک fake جایگزین کرد؛ state بین تست‌ها نشت می‌کند.
  • نقض SRP: کلاس هم منطق خودش را دارد و هم مدیریت چرخهٔ عمر خودش را.
  • coupling محکم به کلاس concrete.
  • در PHP-FPM «یکتایی» فقط در محدودهٔ یک درخواست است؛ در Octane بین درخواست‌ها می‌ماند و ممکن است دادهٔ کاربر قبلی نشت کند.

راه‌حل بهتر: Singleton در Container

به‌جای اینکه کلاس خودش یکتایی را تضمین کند، Service Container چرخهٔ عمر را مدیریت می‌کند. کلاس یک کلاس معمولی و قابل تست است و از طریق DI تزریق می‌شود:

<?php
// AppServiceProvider::register()
$this->app->singleton(GeoIpClient::class, fn ($app) => new GeoIpClient(
    apiKey: config('services.geoip.key'),
));

// scoped: یکتا در طول یک درخواست/job؛ در Octane و queue بین درخواست‌ها reset می‌شود
$this->app->scoped(TenantContext::class);

// bind: هر بار instance جدید
$this->app->bind(ReportBuilder::class);

final class LocationController
{
    public function __construct(private GeoIpClient $geo) {}   // وابستگی صریح؛ در تست قابل swap
}

تفاوت Singleton GoF با $app->singleton(): در دومی کلاس «نمی‌داند» singleton است؛ یکتایی یک تصمیم پیکربندی در composition root است نه بخشی از طراحی کلاس. پس constructor عمومی است، قابل تست است و در تست می‌توان با $this->app->instance() یا $this->mock() آن را جایگزین کرد. در Laravel، خود Application (container)، DatabaseManager و CacheManager به‌صورت singleton ثبت شده‌اند.

Factoryها: Simple Factory، Static Factory، Factory Method و Abstract Factory

هدف مشترک همهٔ factoryها: جدا کردن «تصمیم ساخت» از «استفاده» تا کد استفاده‌کننده به کلاس‌های concrete وابسته نباشد و منطق ساخت در یک جا متمرکز شود.

Simple Factory (یک idiom، نه الگوی GoF)

یک کلاس یا متد که بر اساس ورودی تصمیم می‌گیرد کدام کلاس را بسازد.

<?php
final class NotifierFactory
{
    public function __construct(private Container $container) {}

    public function make(string $channel): Notifier
    {
        return match ($channel) {
            'sms'   => $this->container->make(SmsNotifier::class),
            'email' => $this->container->make(EmailNotifier::class),
            'push'  => $this->container->make(PushNotifier::class),
            default => throw new InvalidArgumentException("Unknown channel: $channel"),
        };
    }
}

عیب: برای افزودن نوع جدید باید factory را ویرایش کرد (نقض جزئی Open/Closed). راه‌حل: یک registry (آرایهٔ نگاشت نام → کلاس) که قابل گسترش باشد؛ دقیقاً کاری که Manager لاراول با extend() انجام می‌دهد.

Static Factory / Named Constructor

<?php
final class Money
{
    private function __construct(public readonly int $minor, public readonly string $currency) {}

    public static function rial(int $amount): self { return new self($amount, 'IRR'); }
    public static function fromString(string $s): self { /* parse "100 USD" */ }
    public static function zero(string $currency): self { return new self(0, $currency); }
}
// Laravel: Carbon::now()، Carbon::parse()، Str::of()، Collection::make()، Response::json()

مزیت: نام گویا (fromString)، امکان چند «constructor» با معنای مختلف، اعتبارسنجی، cache یا برگرداندن زیرکلاس. عیب: متد static قابل mock نیست (برای Value Object مشکلی نیست).

Factory Method (GoF)

هدف: یک interface برای ساخت object تعریف می‌شود، اما زیرکلاس‌ها تصمیم می‌گیرند کدام کلاس ساخته شود. کلاس پایه الگوریتم کلی را دارد و ساخت محصول را به یک متد abstract (factory method) واگذار می‌کند.

<?php
interface Transport { public function deliver(Order $o): void; }

abstract class Logistics
{
    abstract protected function createTransport(): Transport;   // factory method

    public function planDelivery(Order $order): void            // منطق مشترک
    {
        $transport = $this->createTransport();
        $transport->deliver($order);
    }
}

final class RoadLogistics extends Logistics
{
    protected function createTransport(): Transport { return new Truck(); }
}

final class SeaLogistics extends Logistics
{
    protected function createTransport(): Transport { return new Ship(); }
}

در Laravel: متد newCollection() در مدل Eloquent یک factory method است؛ با override کردن آن در مدل، می‌توانید کالکشن سفارشی (UserCollection) برگردانید. newEloquentBuilder() هم به همین شکل یک Builder سفارشی برمی‌گرداند.

<?php
class User extends Model
{
    public function newCollection(array $models = []): UserCollection
    {
        return new UserCollection($models);   // همهٔ کوئری‌ها اکنون UserCollection برمی‌گردانند
    }
}

Abstract Factory (GoF)

هدف: یک interface برای ساخت خانواده‌ای از objectهای مرتبط بدون مشخص کردن کلاس concrete آن‌ها. تضمین می‌کند محصولات یک خانواده با هم سازگارند.

<?php
interface PaymentProviderFactory
{
    public function createGateway(): Gateway;
    public function createWebhookVerifier(): WebhookVerifier;
    public function createRefunder(): Refunder;
}

final class ZarinpalFactory implements PaymentProviderFactory
{
    public function createGateway(): Gateway { return new ZarinpalGateway(); }
    public function createWebhookVerifier(): WebhookVerifier { return new ZarinpalVerifier(); }
    public function createRefunder(): Refunder { return new ZarinpalRefunder(); }
}

final class StripeFactory implements PaymentProviderFactory { /* ... خانوادهٔ Stripe */ }

// کلاینت فقط به abstract factory وابسته است؛ امکان ترکیب ZarinpalGateway با StripeVerifier وجود ندارد
final class CheckoutService
{
    public function __construct(private PaymentProviderFactory $provider) {}
}

در Laravel: Illuminate\Database\Connectors\ConnectionFactory بر اساس driver (mysql، pgsql، sqlite، sqlsrv) connector و connection مناسب را می‌سازد و هر connection، grammar و post-processor سازگار با همان دیتابیس را دارد؛ یعنی یک خانوادهٔ سازگار از objectها.

Builder و Prototype

Builder

هدف: جدا کردن ساخت گام‌به‌گام یک object پیچیده از نمایش نهایی آن، تا با یک فرایند ساخت بتوان نمایش‌های مختلف ساخت.

مسئله: constructor با تعداد زیادی پارامتر اختیاری («telescoping constructor»)، یا objectی که ساختش چند مرحله و اعتبارسنجی دارد.

<?php
final class HttpRequestBuilder
{
    private string $method = 'GET';
    private array $headers = [];
    private ?string $body = null;
    private int $timeout = 30;

    public function __construct(private string $url) {}

    public function post(array $data): static
    {
        $this->method = 'POST';
        $this->body = json_encode($data, JSON_THROW_ON_ERROR);
        return $this->withHeader('Content-Type', 'application/json');
    }

    public function withHeader(string $k, string $v): static { $this->headers[$k] = $v; return $this; }
    public function timeout(int $s): static { $this->timeout = $s; return $this; }

    public function build(): HttpRequest           // محصول نهایی، معتبر و immutable
    {
        if ($this->method === 'POST' && $this->body === null) {
            throw new LogicException('POST requires body');
        }
        return new HttpRequest($this->method, $this->url, $this->headers, $this->body, $this->timeout);
    }
}

$request = (new HttpRequestBuilder('https://api.example.com/orders'))
    ->post(['id' => 1])->withHeader('X-Trace', 'abc')->timeout(5)->build();

در Laravel:

  • Query Builder: DB::table('users')->where('active', 1)->orderBy('name')->limit(10)->get()؛ هر متد بخشی از state کوئری را تنظیم می‌کند و get()/first() نقش build() + اجرا را دارد. خود SQL را Grammar مخصوص هر دیتابیس می‌سازد (همان فرایند، نمایش‌های مختلف).
  • کلاینت HTTP: Http::withToken($t)->timeout(5)->retry(3, 100)->post(...) (کلاس PendingRequest).
  • Schema Builder (Blueprint در migrationها)، MailMessage در notificationها، Model Factoryها.

مزایا

  • خوانایی بالا (fluent)، پارامترهای اختیاری بدون constructor بزرگ.
  • اعتبارسنجی متمرکز قبل از ساخت.
  • محصول نهایی می‌تواند immutable باشد.

معایب

  • کلاس اضافه و تکرار propertyها.
  • برای objectهای ساده over-engineering است (named arguments در PHP 8 خیلی از نیازها را برطرف می‌کند).

Prototype

هدف: ساخت object جدید با کپی کردن یک نمونهٔ موجود (prototype) به‌جای ساختن از صفر؛ وقتی ساخت پرهزینه است یا می‌خواهیم کپی‌هایی با تغییرات کوچک داشته باشیم. در PHP پیاده‌سازی بومی آن clone و __clone() است.

<?php
final class ReportTemplate
{
    public function __construct(
        public string $title,
        public array $columns,
        public Style $style,              // object تودرتو
    ) {}

    public function __clone(): void
    {
        $this->style = clone $this->style;   // deep copy؛ وگرنه همهٔ کپی‌ها یک Style مشترک دارند
    }
}

$base = new ReportTemplate('Sales', ['date', 'total'], new Style('blue'));
$monthly = clone $base;
$monthly->title = 'Monthly Sales';

در Laravel: $model->replicate() (کپی مدل بدون کلید اصلی و timestamps، برای ساخت رکورد مشابه)، $query->clone() برای استفاده از یک کوئری پایه در چند شاخه، و $date->copy() در Carbon.

<?php
$base = Order::where('tenant_id', $tenantId);
$paidCount    = $base->clone()->where('status', 'paid')->count();
$pendingCount = $base->clone()->where('status', 'pending')->count();
// بدون clone، شرط دوم به کوئری اول اضافه می‌شد (Builder قابل تغییر است)

Adapter، Bridge و Composite

Adapter

هدف: تبدیل interface یک کلاس به interface دیگری که کلاینت انتظار دارد؛ تا کلاس‌هایی که interface ناسازگار دارند با هم کار کنند. مثل مبدل برق.

مسئله: یک SDK شخص ثالث (مثلاً درگاه پیامک) API خودش را دارد و نمی‌خواهیم کل کد ما به آن وابسته شود.

<?php
interface SmsSender                         // Target: interface مورد انتظار دامنهٔ ما
{
    public function send(PhoneNumber $to, string $text): void;
}

final class KavenegarSmsAdapter implements SmsSender      // Adapter
{
    public function __construct(private KavenegarApi $api, private string $sender) {}  // Adaptee

    public function send(PhoneNumber $to, string $text): void
    {
        try {
            $this->api->Send($this->sender, $to->e164(), $text);   // ترجمهٔ فراخوانی
        } catch (\Kavenegar\Exceptions\ApiException $e) {
            throw new SmsFailed($e->getMessage(), previous: $e); // ترجمهٔ exception هم بخشی از adapter است
        }
    }
}

$this->app->bind(SmsSender::class, KavenegarSmsAdapter::class);  // تعویض provider = یک خط

در Laravel: لایهٔ Filesystem: Storage::disk('s3') و Storage::disk('local') هر دو یک API (put، get، url) دارند و Laravel روی adapterهای Flysystem (Local، S3، FTP) سوار است. Cache stores (RedisStore، FileStore، DatabaseStore، MemcachedStore) همگی contract Store را پیاده می‌کنند و API متفاوت Redis/Memcached را به یک interface ترجمه می‌کنند. Queue connectorها و Mail transportها هم همین‌طور.

Adapter در Hexagonal Architecture (Ports and Adapters) نقش کلیدی دارد: interface دامنه «port» است و پیاده‌سازی مخصوص هر سرویس خارجی «adapter». این باعث می‌شود تست دامنه با یک fake adapter و بدون شبکه انجام شود.

Bridge (به‌طور خلاصه)

هدف: جدا کردن abstraction از implementation تا هر دو مستقلاً تغییر کنند؛ با ترکیب به‌جای ارث‌بری، از «انفجار تعداد کلاس‌ها» جلوگیری می‌کند.

بدون Bridge (ارث‌بری):              با Bridge (ترکیب):
  Notification                        Notification ─────has-a────► Channel
  ├── UrgentSmsNotification           ├── UrgentNotification        ├── SmsChannel
  ├── UrgentEmailNotification         └── ReminderNotification      └── EmailChannel
  ├── ReminderSmsNotification
  └── ReminderEmailNotification       2 + 2 کلاس به‌جای 2 × 2

تفاوت با Adapter: Adapter بعد از طراحی برای سازگار کردن دو چیز موجود به کار می‌رود؛ Bridge از ابتدا برای جدا نگه داشتن دو بُعد تغییر طراحی می‌شود. در Laravel، Notificationها (چه پیامی) و Channelها (mail، database، broadcast، vonage) ایدهٔ مشابهی دارند.

Composite

هدف: ترکیب objectها در ساختار درختی و رفتار یکسان با «برگ» (یک object) و «گره مرکب» (گروهی از objectها) از طریق یک interface مشترک.

<?php
interface PriceComponent { public function price(): int; }

final class Product implements PriceComponent          // Leaf
{
    public function __construct(private int $price) {}
    public function price(): int { return $this->price; }
}

final class Bundle implements PriceComponent           // Composite
{
    /** @var list<PriceComponent> */
    private array $children = [];

    public function __construct(private int $discountPercent = 0) {}

    public function add(PriceComponent $c): static { $this->children[] = $c; return $this; }

    public function price(): int
    {
        $sum = array_sum(array_map(fn (PriceComponent $c) => $c->price(), $this->children));
        return intdiv($sum * (100 - $this->discountPercent), 100);
    }
}

$giftBox = (new Bundle(10))->add(new Product(500))->add((new Bundle())->add(new Product(200)));
echo $giftBox->price();   // کلاینت فرقی بین محصول تکی و بستهٔ تودرتو نمی‌گذارد

کاربرد: منو و دسته‌بندی‌های درختی، ساختار سازمانی، permissionهای گروهی، rule engineها (قانون مرکب AND/OR). در Laravel مثال برجسته‌ای در هسته نیست، اما ایدهٔ مشابه در Blade components تودرتو و گروه‌های middleware (یک نام که به مجموعه‌ای از middlewareها باز می‌شود) دیده می‌شود.

Decorator و Proxy

Decorator

هدف: افزودن رفتار جدید به یک object به‌صورت پویا با پیچیدن آن در objectی دیگر که همان interface را پیاده می‌کند؛ جایگزین انعطاف‌پذیر برای ارث‌بری. decoratorها قابل زنجیر شدن هستند.

مسئله: می‌خواهیم به یک repository، cache، logging یا metrics اضافه کنیم، بدون تغییر کد آن (Open/Closed) و بدون ساخت زیرکلاس برای هر ترکیب.

<?php
interface ProductRepository
{
    public function find(int $id): ?Product;
    public function save(Product $p): void;
}

final class EloquentProductRepository implements ProductRepository
{
    public function find(int $id): ?Product { return Product::find($id); }
    public function save(Product $p): void { $p->save(); }
}

final class CachingProductRepository implements ProductRepository       // Decorator
{
    public function __construct(
        private ProductRepository $inner,                                // همان interface
        private CacheRepository $cache,
        private int $ttl = 600,
    ) {}

    public function find(int $id): ?Product
    {
        return $this->cache->remember("product:$id", $this->ttl, fn () => $this->inner->find($id));
    }

    public function save(Product $p): void
    {
        $this->inner->save($p);
        $this->cache->forget("product:{$p->id}");                         // invalidation
    }
}

final class LoggingProductRepository implements ProductRepository { /* لاگ زمان اجرا، سپس delegate */ }

// ترکیب در Service Provider
$this->app->bind(ProductRepository::class, EloquentProductRepository::class);
$this->app->extend(ProductRepository::class, fn (ProductRepository $repo, $app) =>
    new CachingProductRepository($repo, $app->make(CacheRepository::class))

متد extend() در container لاراول دقیقاً برای decorate کردن یک سرویس resolve‌شده طراحی شده است.

در Laravel: Middleware از نظر مفهومی مثل decoratorهای تودرتو دور handler درخواست عمل می‌کند (هر لایه قبل و بعد از لایهٔ درونی کاری انجام می‌دهد)، هرچند پیاده‌سازی آن با Pipeline (Chain of Responsibility) است. Illuminate\Cache\Repository هم یک Store را می‌پیچد و رفتارهایی مثل remember، رویدادها و tagها را به آن اضافه می‌کند.

مزایا

  • Open/Closed و Single Responsibility (هر decorator یک دغدغه).
  • ترکیب پویا در زمان اجرا؛ ترتیب قابل تنظیم.
  • جلوگیری از انفجار زیرکلاس‌ها.

معایب

  • تعداد زیادی object کوچک؛ دیباگ stack عمیق.
  • باید همهٔ متدهای interface را delegate کرد (interface بزرگ = کد boilerplate).
  • ترتیب decoratorها مهم است و ممکن است باگ بسازد.

Proxy

هدف: فراهم کردن یک جانشین (placeholder) برای object دیگر تا دسترسی به آن را کنترل کند. proxy همان interface را دارد ولی هدفش «کنترل» است نه «افزودن رفتار».

  • Virtual Proxy (Lazy loading): ساخت object پرهزینه تا اولین استفاده عقب می‌افتد.
  • Protection Proxy: بررسی مجوز قبل از delegate.
  • Remote Proxy: نمایندهٔ محلی یک سرویس راه‌دور (مثل کلاینت gRPC).
  • Caching/Smart Proxy: شمارش ارجاع، کش، لاگ.
<?php
interface ReportGenerator { public function generate(): string; }

final class LazyReportProxy implements ReportGenerator
{
    private ?ReportGenerator $real = null;

    public function __construct(private Closure $factory) {}

    public function generate(): string
    {
        $this->real ??= ($this->factory)();     // ساخت فقط هنگام اولین نیاز
        return $this->real->generate();
    }
}

// PHP 8.4: lazy object بومی
$reflector = new ReflectionClass(HeavyService::class);
$service = $reflector->newLazyProxy(fn () => new HeavyService(/* ... */));

در Laravel: Deferred Service Providers (پیاده‌سازی DeferrableProvider) سرویس را فقط هنگام نیاز register می‌کنند؛ lazy loading رابطه‌ها در Eloquent ($post->comments فقط هنگام اولین دسترسی کوئری می‌زند)؛ و کلاس‌هایی با نام Proxy مثل HigherOrderCollectionProxy (برای $users->each->notify()). Facade هم از نظر رفتاری یک proxy استاتیک به سرویس داخل container است.

Decorator در برابر Proxy در برابر Adapter — هر سه یک object را «می‌پیچند»: Adapter interface را تغییر می‌دهد؛ Decorator همان interface را نگه می‌دارد و رفتار اضافه می‌کند (معمولاً قابل زنجیر، object درونی از بیرون تزریق می‌شود)؛ Proxy همان interface را نگه می‌دارد و دسترسی را کنترل می‌کند (اغلب خودش چرخهٔ عمر object واقعی را مدیریت می‌کند).

Facade در GoF

هدف: فراهم کردن یک interface ساده و یکپارچه برای یک زیرسیستم پیچیده با چندین کلاس. کلاینت به‌جای هماهنگ کردن ده کلاس، با یک object ساده کار می‌کند.

<?php
final class CheckoutFacade
{

مزایا و معایب Facadeهای Laravel

مزایا

  • کد کوتاه و خوانا، بدون نیاز به تزریق در هر کلاس.
  • برخلاف متد static واقعی، قابل تست: Cache::shouldReceive('get')->andReturn(1)، Mail::fake()، Queue::fake()، Event::fake()، چون Facade فقط instance پشت خود را عوض می‌کند (swap).

معایب

  • وابستگی پنهان: در constructor دیده نمی‌شود؛ کلاسی که ده Facade استفاده می‌کند، ظاهراً بی‌وابستگی است (scope creep).
  • coupling به فریم‌ورک در لایهٔ دامنه.
  • IDE و static analysis بدون ide-helper/Larastan متدها را نمی‌شناسند.

جایگزین‌ها: تزریق contract (Illuminate\Contracts\Cache\Repository) در constructor، یا Real-time Facade (use Facades\App\Services\Geo;) که هر کلاسی را به‌صورت facade قابل استفاده و قابل mock می‌کند.

سوال کلاسیک: «آیا Facade در لاراول همان Facade GoF است؟» پاسخ: خیر. نام مشترک است اما Laravel Facade در واقع یک static proxy / service locator است که فراخوانی static را به instance داخل container هدایت می‌کند؛ زیرسیستم را ساده نمی‌کند. با این حال، چون instance از container می‌آید، بر خلاف متد static واقعی قابل swap و mock است.

Strategy و الگوی Manager (Driver)

Strategy

هدف: تعریف خانواده‌ای از الگوریتم‌ها، کپسوله کردن هر کدام و قابل تعویض کردن آن‌ها؛ الگوریتم مستقل از کلاینتی که از آن استفاده می‌کند تغییر می‌کند.

مسئله: if/switch بزرگ روی نوع (درگاه پرداخت، روش محاسبهٔ هزینهٔ ارسال، نوع تخفیف) که با هر نوع جدید باید ویرایش شود.

<?php
interface PaymentGateway                                    // Strategy
{
    public function charge(Money $amount, string $callbackUrl): PaymentResult;
    public function verify(array $payload): VerifiedPayment;
}

final class ZarinpalGateway implements PaymentGateway { /* ... */ }    // Concrete strategies
final class IdPayGateway implements PaymentGateway { /* ... */ }
final class FakeGateway implements PaymentGateway { /* برای تست و local */ }

final class CheckoutService                                 // Context
{
    public function __construct(private PaymentGateway $gateway) {}

    public function pay(Order $order): PaymentResult
    {
        return $this->gateway->charge($order->total(), route('payment.callback', $order));
    }
}

// انتخاب strategy در composition root (بر اساس config)
$this->app->bind(PaymentGateway::class, fn ($app) => match (config('payment.default')) {
    'zarinpal' => $app->make(ZarinpalGateway::class),
    'idpay'    => $app->make(IdPayGateway::class),
    default    => $app->make(FakeGateway::class),
});

در PHP، strategyهای ساده را می‌توان با closure هم پیاده کرد (مثلاً callback مقایسه در usort یا sortBy(fn) در Collection).

مزایا

  • Open/Closed: strategy جدید بدون تغییر context.
  • حذف شرط‌های بزرگ؛ هر الگوریتم جدا و تست‌پذیر.
  • تعویض در زمان اجرا.

معایب

  • کلاینت (یا factory) باید بداند کدام strategy را انتخاب کند.
  • برای دو حالت ثابت و ساده، کلاس اضافه است.

تفاوت Strategy با State: ساختار تقریباً یکسان است. در Strategy، کلاینت الگوریتم را انتخاب می‌کند و strategyها معمولاً از هم خبر ندارند؛ در State، خود stateها تعیین می‌کنند state بعدی چیست و رفتار object با تغییر وضعیت درونی‌اش عوض می‌شود.

Manager Pattern در Laravel

Laravel برای زیرسیستم‌هایی که چند «driver» دارند از ترکیب Factory + Strategy + Registry استفاده می‌کند که به آن Manager می‌گویند: CacheManager، QueueManager، FilesystemManager، MailManager، AuthManager، SessionManager، LogManager. برخی از آن‌ها (مثل SessionManager) از کلاس پایهٔ Illuminate\Support\Manager ارث می‌برند.

<?php
use Illuminate\Support\Manager;

final class SmsManager extends Manager
{
    public function getDefaultDriver(): string
    {
        return $this->config->get('sms.default', 'kavenegar');
    }

    // Manager برای driver «kavenegar» به‌دنبال متد createKavenegarDriver می‌گردد
    protected function createKavenegarDriver(): SmsSender
    {
        return new KavenegarSmsAdapter(new KavenegarApi($this->config->get('sms.kavenegar.key')), '1000');
    }

    protected function createLogDriver(): SmsSender
    {
        return new LogSmsSender($this->container->make('log'));
    }
}

// استفاده: driver پیش‌فرض یا انتخابی؛ instance هر driver یک بار ساخته و نگه داشته می‌شود
app(SmsManager::class)->driver()->send($to, 'کد: 1234');
app(SmsManager::class)->driver('log')->send($to, 'test');

// افزودن driver سفارشی بدون تغییر کلاس (Open/Closed)
app(SmsManager::class)->extend('twilio', fn ($app) => new TwilioSmsAdapter(/* ... */));
  • Manager متدهای ناشناخته را با __call به driver پیش‌فرض forward می‌کند؛ برای همین Cache::get() مستقیماً روی store پیش‌فرض اجرا می‌شود و Cache::store('redis')->get() روی store مشخص.
  • یعنی: Factory (ساخت driver)، Strategy (driverها قابل تعویض با interface مشترک)، Adapter (هر driver یک سرویس خارجی را adapt می‌کند)، caching instanceها (هر driver یک بار ساخته می‌شود).

Observer (Events/Listeners و Model Observers)

هدف: تعریف یک وابستگی یک‌به‌چند بین objectها، طوری که وقتی یک object (subject) تغییر وضعیت می‌دهد، همهٔ وابستگان (observers) خودکار مطلع شوند؛ بدون اینکه subject آن‌ها را بشناسد (loose coupling).

<?php
// پیاده‌سازی کلاسیک با SPL
final class Order implements SplSubject
{
    private SplObjectStorage $observers;
    public function __construct() { $this->observers = new SplObjectStorage(); }

    public function attach(SplObserver $o): void { $this->observers->attach($o); }
    public function detach(SplObserver $o): void { $this->observers->detach($o); }
    public function notify(): void { foreach ($this->observers as $o) { $o->update($this); } }

    public function markPaid(): void { /* ... */ $this->notify(); }
}

رویدادهای مدل: retrieved، creating/created، updating/updated، saving/saved، deleting/deleted، restoring/restored و … . اگر متد creating/updating/saving/deleting مقدار false برگرداند، عملیات لغو می‌شود.

دام‌های Observer: (1) Mass update/delete مثل User::where(...)->update([...]) مستقیم SQL می‌زند و رویداد مدل را fire نمی‌کند. (2) منطق پنهان: کسی که $user->save() را می‌خواند نمی‌داند پنج کار دیگر اتفاق می‌افتد؛ منطق اصلی کسب‌وکار را در observer مخفی نکنید. (3) ارسال ایمیل یا dispatch job داخل تراکنش: اگر تراکنش rollback شود، ایمیل رفته است؛ از ShouldDispatchAfterCommit/afterCommit استفاده کنید. (4) ترتیب اجرای listenerها نباید مبنای منطق باشد.

مزایا

  • decoupling: افزودن واکنش جدید (SMS، آمار) بدون تغییر کد پرداخت.
  • امکان async با queue.
  • Open/Closed.

معایب

  • جریان کنترل غیرصریح؛ دیباگ و ردیابی سخت‌تر.
  • خطر زنجیرهٔ رویدادهای آبشاری و حلقه.
  • مدیریت خطا و ترتیب در listenerهای متعدد.

Command

هدف: کپسوله کردن یک درخواست/عملیات به‌صورت object؛ در نتیجه می‌توان آن را پارامتری کرد، در صف گذاشت، لاگ کرد، با تأخیر اجرا کرد، دوباره اجرا (retry) کرد یا undo کرد.

اجزا: Command (داده‌های لازم + متد execute/handle)، Invoker (کسی که اجرا را راه می‌اندازد، بدون دانستن جزئیات)، Receiver (کسی که کار واقعی را انجام می‌دهد).

<?php
interface Command { public function execute(): void; public function undo(): void; }

final class ChangePriceCommand implements Command
{
    private ?int $previous = null;
    public function __construct(private Product $product, private int $newPrice) {}

    public function execute(): void
    {
        $this->previous = $this->product->price;
        $this->product->update(['price' => $this->newPrice]);
    }

    public function undo(): void
    {
        $this->product->update(['price' => $this->previous]);
    }
}

final class CommandHistory           // Invoker با قابلیت undo
{
    private array $stack = [];
    public function run(Command $c): void { $c->execute(); $this->stack[] = $c; }
    public function undoLast(): void { array_pop($this->stack)?->undo(); }
}

در Laravel

  • Queued Jobs: یک job دقیقاً یک command object است: داده‌ها در constructor، منطق در handle()؛ serialize شده و در صف (Redis، SQS، database) ذخیره و بعداً توسط worker (invoker) اجرا می‌شود. قابلیت‌های retry ($tries، backoff)، تأخیر، chain (Bus::chain) و batch (Bus::batch) مستقیماً از object بودن درخواست می‌آیند.
  • Command Bus: Bus::dispatch()، dispatch_sync()؛ جدا کردن «درخواست انجام کار» از «انجام‌دهنده».
  • Artisan Commands: هر دستور CLI یک کلاس با signature و handle() است و Kernel (invoker) آن را بر اساس نام اجرا می‌کند؛ قابل زمان‌بندی در Scheduler.
<?php
final class GenerateMonthlyReport implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 3;
    public function __construct(public readonly int $tenantId, public readonly string $month) {}

    public function handle(ReportService $reports): void     // Receiver از container تزریق می‌شود
    {
        $reports->generate($this->tenantId, $this->month);
    }
}

GenerateMonthlyReport::dispatch($tenant->id, '2026-10')->onQueue('reports')->delay(now()->addMinutes(5));

Command را با CQRS اشتباه نگیرید: CQRS جدا کردن مدل نوشتن (command) از مدل خواندن (query) در سطح معماری است؛ اما Command pattern در CQRS برای نمایش درخواست‌های نوشتن به کار می‌رود. همچنین jobها باید ترجیحاً idempotent باشند، چون ممکن است بیش از یک بار اجرا شوند.

Chain of Responsibility و Pipeline

هدف (CoR): جلوگیری از coupling بین فرستندهٔ درخواست و گیرنده، با دادن فرصت به زنجیره‌ای از handlerها. هر handler تصمیم می‌گیرد درخواست را خودش پردازش کند و/یا به handler بعدی پاس دهد، یا زنجیره را قطع کند.

<?php
abstract class Handler
{
    private ?Handler $next = null;
    public function setNext(Handler $h): Handler { $this->next = $h; return $h; }

    public function handle(Ticket $t): ?string
    {
        return $this->next?->handle($t);     // پیش‌فرض: پاس به بعدی
    }
}

final class BotHandler extends Handler
{
    public function handle(Ticket $t): ?string
    {
        return $t->isFaq() ? 'answered by bot' : parent::handle($t);
    }
}
final class AgentHandler extends Handler { /* ... */ }
final class ManagerHandler extends Handler { /* ... */ }

$chain = new BotHandler();
$chain->setNext(new AgentHandler())->setNext(new ManagerHandler());
$chain->handle($ticket);

Pipeline در Laravel

Laravel نسخهٔ functional این الگو را با کلاس Illuminate\Pipeline\Pipeline پیاده کرده است: یک «passable» از میان مجموعه‌ای از «pipe»ها عبور می‌کند؛ هر pipe $next را دریافت می‌کند و می‌تواند قبل و بعد از آن کار کند یا اصلاً آن را صدا نزند (short-circuit). پیاده‌سازی داخلی با array_reduce روی pipeهای معکوس، closureهای تودرتو (پیاز) می‌سازد.

Request ──► [TrimStrings ──► [Authenticate ──► [VerifyCsrf ──► Controller]]]
                                                                     │
Response ◄── TrimStrings ◄──── Authenticate ◄──── VerifyCsrf ◄───────┘
(هر middleware می‌تواند قبل از $next درخواست و بعد از آن پاسخ را تغییر دهد،
 یا بدون صدا زدن $next مستقیماً پاسخ برگرداند: مثلاً 401)
<?php
// Middleware = یک pipe
final class EnsureUserIsSubscribed
{
    public function handle(Request $request, Closure $next): Response
    {
        if (! $request->user()?->subscribed()) {
            return redirect()->route('billing');      // قطع زنجیره
        }
        $response = $next($request);                  // ادامهٔ زنجیره
        $response->headers->set('X-Plan', $request->user()->plan);   // after-middleware
        return $response;
    }
}

// استفادهٔ مستقیم از Pipeline برای منطق دامنه: اعمال فیلترهای جست‌وجو
$products = app(Pipeline::class)
    ->send(Product::query())
    ->through([
        Filters\ByCategory::class,

        Filters\InStock::class,

    ->thenReturn()        // یا ->then(fn ($query) => $query->paginate())

            $query->where('price', '>=', $this->request->integer('min'));
        }
        return $next($query);
    }
}
  • به‌طور پیش‌فرض متد handle هر pipe صدا زده می‌شود؛ با ->via('apply') قابل تغییر است. pipe می‌تواند closure هم باشد.
  • در هستهٔ Laravel: HTTP Kernel درخواست را از middlewareهای global، گروه و route عبور می‌دهد؛ job middleware و pipelineهای Fortify (مراحل login) هم از همین کلاس استفاده می‌کنند.

مزایا

  • هر مرحله یک مسئولیت (SRP) و قابل استفادهٔ مجدد.
  • افزودن/حذف/جابه‌جایی مرحله بدون تغییر بقیه.
  • امکان short-circuit و کار قبل/بعد.

معایب

  • ترتیب مهم است و خطای ترتیب باگ امنیتی می‌سازد (auth قبل از کار حساس).
  • ممکن است درخواست بدون پردازش از انتهای زنجیره خارج شود.
  • دیباگ closureهای تودرتو سخت‌تر است.

Template Method، State، Iterator، Mediator، Null Object و Specification

Template Method

هدف: تعریف اسکلت یک الگوریتم در کلاس پایه و واگذاری برخی مراحل به زیرکلاس‌ها، بدون اینکه ساختار کلی الگوریتم تغییر کند. مبتنی بر ارث‌بری است (برخلاف Strategy که مبتنی بر ترکیب است). اصل «Hollywood»: Don't call us, we'll call you.

<?php
abstract class DataImporter
{
    final public function import(string $path): int          // template method (final)
    {
        $rows = $this->read($path);
        $count = 0;
        foreach ($rows as $row) {
            if (! $this->validate($row)) { continue; }
            $this->persist($this->transform($row));
            $count++;
        }
        $this->afterImport($count);                          // hook اختیاری
        return $count;
    }

    abstract protected function read(string $path): iterable;   // مراحل متغیر
    abstract protected function transform(array $row): array;
    abstract protected function persist(array $data): void;
    protected function validate(array $row): bool { return true; }   // پیش‌فرض قابل override
    protected function afterImport(int $count): void {}               // hook
}

final class CsvProductImporter extends DataImporter { /* read، transform، persist */ }

در Laravel: FormRequest (فریم‌ورک جریان اعتبارسنجی را اجرا می‌کند و شما authorize()، rules()، messages()، prepareForValidation() را پر می‌کنید)، Illuminate\Console\Command (شما handle() را می‌نویسید)، hookهای boot()/booted() مدل، و register()/boot() در Service Provider.

State

هدف: اجازه دادن به object که با تغییر وضعیت درونی، رفتارش را تغییر دهد؛ گویی کلاسش عوض شده است. جایگزین if ($this->status === ...)های پراکنده در همهٔ متدها.

<?php
interface OrderState
{
    public function pay(Order $o): void;
    public function ship(Order $o): void;
    public function cancel(Order $o): void;
}

abstract class BaseState implements OrderState            // رفتار پیش‌فرض: غیرمجاز
{
    public function pay(Order $o): void { throw new InvalidTransition(static::class . ' → pay'); }
    public function ship(Order $o): void { throw new InvalidTransition(static::class . ' → ship'); }
    public function cancel(Order $o): void { throw new InvalidTransition(static::class . ' → cancel'); }
}

final class PendingState extends BaseState
{
    public function pay(Order $o): void { $o->transitionTo(new PaidState()); }
    public function cancel(Order $o): void { $o->transitionTo(new CancelledState()); }
}

final class PaidState extends BaseState
{
    public function ship(Order $o): void { $o->transitionTo(new ShippedState()); }
    public function cancel(Order $o): void { /* refund */ $o->transitionTo(new CancelledState()); }
}

final class ShippedState extends BaseState {}
final class CancelledState extends BaseState {}

final class Order
{
    private OrderState $state;
    public function __construct() { $this->state = new PendingState(); }
    public function transitionTo(OrderState $s): void { $this->state = $s; }
    public function pay(): void { $this->state->pay($this); }        // delegate به state فعلی
    public function ship(): void { $this->state->ship($this); }
}

برای state machineهای ساده، یک enum با متد canTransitionTo() کافی و سبک‌تر است؛ State pattern کامل وقتی ارزش دارد که رفتار هر وضعیت پیچیده باشد. پکیج spatie/laravel-model-states این الگو را برای مدل‌های Eloquent پیاده می‌کند.

Iterator

هدف: پیمایش عناصر یک مجموعه بدون افشای ساختار درونی آن. در PHP به‌صورت بومی با Iterator، IteratorAggregate و generator پشتیبانی می‌شود. در Laravel: Collection (پیاده‌کنندهٔ IteratorAggregate)، LazyCollection (مبتنی بر generator)، cursor() و paginatorها.

Mediator (به‌طور خلاصه)

هدف: کاهش وابستگی‌های چندبه‌چند بین objectها با واداشتن آن‌ها به ارتباط فقط از طریق یک واسط مرکزی. به‌جای اینکه هر component همهٔ componentهای دیگر را بشناسد، فقط mediator را می‌شناسد. در Laravel، Event Dispatcher و Command Bus نقش mediator دارند: فرستنده و گیرنده یکدیگر را نمی‌شناسند. خطر: mediator ممکن است به یک God Object تبدیل شود.

Null Object

هدف: به‌جای برگرداندن null (و پخش شدن if ($x !== null) در همه‌جا)، یک object با رفتار خنثی برگردانیم که همان interface را دارد.

<?php
final class NullLogger implements LoggerInterface { use LoggerTrait; public function log($level, $message, array $context = []): void {} }

// Laravel: relation با withDefault — به‌جای null، یک مدل خالی/پیش‌فرض
public function author(): BelongsTo
{
    return $this->belongsTo(User::class)->withDefault(['name' => 'کاربر حذف‌شده']);
}
// حالا $post->author->name هرگز خطای «property on null» نمی‌دهد

نمونه‌های دیگر در Laravel: cache driver null (NullStore)، کانال لاگ null، و درایور broadcast null. مراقب باشید Null Object خطاهای واقعی را پنهان نکند (مثلاً نبودن کاربری که باید حتماً وجود داشته باشد).

Specification (به‌طور خلاصه)

هدف: کپسوله کردن یک قاعدهٔ کسب‌وکار به‌صورت object با متد isSatisfiedBy($candidate) که قابل ترکیب با and/or/not است.

<?php
interface Specification { public function isSatisfiedBy(Customer $c): bool; }

final class IsVip implements Specification { public function isSatisfiedBy(Customer $c): bool { return $c->totalSpent > 10_000_000; } }
final class AndSpec implements Specification
{
    public function __construct(private Specification $a, private Specification $b) {}
    public function isSatisfiedBy(Customer $c): bool { return $this->a->isSatisfiedBy($c) && $this->b->isSatisfiedBy($c); }
}
// معادل سمت دیتابیس در Laravel: local scopeها — Customer::vip()->active()->get()

MVC، Service Layer، Action Classes، DTO و Value Object

MVC

Model-View-Controller یک الگوی معماری برای جدا کردن دغدغه‌ها در اپلیکیشن‌های دارای رابط کاربری است:

  • Model: داده و منطق کسب‌وکار (در Laravel: Eloquent model + لایه‌های دامنه).
  • View: نمایش (Blade، یا JSON از طریق API Resource).
  • Controller: دریافت ورودی، هماهنگ کردن model و انتخاب view/پاسخ.
HTTP Request ──► Router ──► Middleware ──► Controller ──► Service / Model ──► DB
                                              │
                                              └──► View (Blade) / API Resource ──► HTTP Response

MVC به‌تنهایی نمی‌گوید منطق کسب‌وکار کجا برود و در اپ‌های بزرگ به Fat Controller یا Fat Model منجر می‌شود. برای همین لایه‌های Service، Action و Repository اضافه می‌شوند. قاعدهٔ رایج: Thin Controller؛ کنترلر فقط HTTP را به دامنه ترجمه کند.

Service Layer

لایه‌ای که use caseهای اپلیکیشن را هماهنگ می‌کند (تراکنش، فراخوانی چند model/repository، ارسال event). مستقل از HTTP است و از کنترلر، Artisan command و job قابل استفاده است.

<?php
final class OrderService
{
    public function __construct(
        private PaymentGateway $gateway,
        private InventoryService $inventory,
    ) {}

    public function place(PlaceOrderData $data, User $user): Order
    {
        return DB::transaction(function () use ($data, $user) {
            $this->inventory->reserve($data->items);
            $order = $user->orders()->create(['total' => $data->total()]);
            $order->items()->createMany($data->itemsArray());
            OrderPlaced::dispatch($order);     // listenerها بهتر است afterCommit باشند
            return $order;
        });
    }
}

خطر: «Service»ی که به مجموعهٔ بی‌ربطی از متدها تبدیل شود (UserService با 40 متد) — نقض SRP.

Action Classes

یک کلاس = یک عملیات (یک use case) با یک متد عمومی (handle، execute یا __invoke). ریزدانه‌تر از Service، نام‌گذاری گویا (CreateInvoice، CancelSubscription)، تست ساده.

<?php
final class CancelSubscription
{
    public function __construct(private BillingGateway $billing) {}

    public function __invoke(Subscription $sub, string $reason): void
    {
        $this->billing->cancel($sub->external_id);
        $sub->update(['status' => SubscriptionStatus::Cancelled, 'cancel_reason' => $reason]);
        SubscriptionCancelled::dispatch($sub);
    }
}

// Controller
public function destroy(Subscription $sub, CancelRequest $r, CancelSubscription $cancel)
{
    $cancel($sub, $r->validated('reason'));
    return to_route('billing');
}

نمونهٔ رسمی: Laravel Fortify/Jetstream که در app/Actions/Fortify کلاس‌هایی مثل CreateNewUser و UpdateUserPassword دارند.

final readonly class PlaceOrderData                       // DTO

Dependency Injection، IoC Container و Service Locator

Dependency Injection: object وابستگی‌هایش را خودش نمی‌سازد و دنبالشان نمی‌گردد؛ از بیرون دریافت می‌کند. این یکی از شکل‌های Inversion of Control (IoC) است و ابزار عملی اصل Dependency Inversion (وابستگی به abstraction) است.

  • Constructor injection: وابستگی‌های اجباری؛ رایج‌ترین و بهترین.
  • Method injection: وابستگی فقط برای یک متد (در Laravel، type-hint در متد کنترلر یا handle() job).
  • Setter/property injection: وابستگی اختیاری؛ خطر object نیمه‌کامل.
<?php
// ❌ بدون DI: coupling محکم، غیرقابل تست
final class InvoiceMailer
{
    public function send(Invoice $i): void
    {
        $mailer = new SmtpMailer('smtp.example.com', 587);   // ساخت درون کلاس
        $pdf = new DompdfRenderer();
        $mailer->send($i->customer->email, $pdf->render($i));
    }
}

// ✅ با DI: وابستگی‌ها صریح و قابل جایگزینی
final class InvoiceMailer
{
    public function __construct(private Mailer $mailer, private PdfRenderer $pdf) {}

    public function send(Invoice $i): void
    {
        $this->mailer->send($i->customer->email, $this->pdf->render($i));
    }
}

// Composition root: Service Provider
$this->app->bind(PdfRenderer::class, DompdfRenderer::class);
// Contextual binding: برای یک مصرف‌کنندهٔ خاص پیاده‌سازی متفاوت
$this->app->when(ReportExporter::class)->needs(PdfRenderer::class)->give(WkhtmlRenderer::class);

Service Container لاراول با auto-wiring (با Reflection، type-hintهای constructor را می‌خواند و بازگشتی resolve می‌کند) نیاز به پیکربندی را برای کلاس‌های concrete حذف می‌کند؛ فقط interfaceها و موارد خاص (پارامتر اسکالر، singleton) نیاز به binding دارند.

Service Locator

در Service Locator، کلاس وابستگی‌هایش را خودش از یک رجیستری مرکزی درخواست می‌کند:

<?php
final class InvoiceMailer
{
    public function send(Invoice $i): void
    {
        $mailer = app(Mailer::class);          // یا resolve()، App::make()، $this->container->get()
        $pdf = app(PdfRenderer::class);
        // ...
    }
}

Dependency Injection

  • وابستگی‌ها در امضای constructor صریحاند.
  • کلاس از container بی‌خبر است (قابل استفاده بیرون از فریم‌ورک).
  • تست: new InvoiceMailer($fakeMailer, $fakePdf).
  • constructor بزرگ = نشانهٔ هشدار نقض SRP (بازخورد طراحی).

Service Locator

  • وابستگی‌ها پنهاناند؛ باید بدنهٔ کد را خواند.
  • کلاس به container (یک global) وابسته است.
  • خطای «binding موجود نیست» در زمان اجرا، نه هنگام ساخت.
  • تست نیازمند پیکربندی container است.

چرا Service Locator را anti-pattern می‌دانند؟ چون وابستگی‌ها را پنهان می‌کند، قرارداد کلاس را مبهم می‌کند و کلاس را به یک global registry گره می‌زند. اما در Laravel استفاده از app() در مرزهای فریم‌ورک (Service Provider، factoryها، helperها، جایی که DI ممکن نیست مثل برخی closureها) قابل قبول است. Facadeها هم در واقع Service Locator با ظاهر static هستند. قاعده: در کد دامنه و سرویس‌ها از constructor injection استفاده کنید؛ locator را به composition root محدود کنید.

Repository، Active Record و Data Mapper

Active Record در برابر Data Mapper

Active Record (Eloquent)

  • هر object یک سطر جدول را نمایش می‌دهد و خودش می‌داند چطور ذخیره/بارگذاری شود: $user->save()، User::find(1).
  • داده + رفتار دامنه + منطق persistence در یک کلاس.
  • propertyها مستقیماً ستون‌های جدول‌اند (از طریق __get/__set).
  • توسعهٔ سریع، کد کم، ایده‌آل برای CRUD و دامنه‌های نزدیک به schema.

Data Mapper (Doctrine ORM)

  • Entityها POPO (کلاس ساده PHP) هستند و از دیتابیس بی‌خبراند.
  • یک لایهٔ جدا (EntityManager / Mapper) نگاشت object ↔ جدول را انجام می‌دهد: $em->persist($user); $em->flush();
  • معمولاً همراه Unit of Work (ردیابی تغییرات و نوشتن یکجا) و Identity Map.
  • مناسب دامنه‌های پیچیده (DDD) که مدل دامنه با schema فاصله دارد.
<?php
// Active Record
$user = User::find(1);
$user->email = 'a@b.com';
$user->save();                       // خود object SQL می‌زند

// Data Mapper (Doctrine)
$user = $entityManager->find(User::class, 1);
$user->changeEmail(new Email('a@b.com'));   // entity خالص، بدون دانش از DB
$entityManager->flush();             // Unit of Work تغییرات را تشخیص می‌دهد و UPDATE می‌زند
معیارActive RecordData Mapper
سادگی و سرعت توسعهبالاپایین‌تر (mapping، کلاس‌های بیشتر)
جداسازی دامنه از persistenceضعیف (نقض SRP)قوی
تست واحد بدون DBدشوارآسان (entity خالص)

Repository

هدف (Fowler/DDD): واسطی بین دامنه و لایهٔ داده که مانند یک مجموعهٔ درون‌حافظه‌ای از objectهای دامنه رفتار می‌کند؛ دامنه نمی‌داند داده از کجا می‌آید (SQL، API، cache).

<?php
interface OrderRepository
{
    public function findById(OrderId $id): ?Order;
    /** @return list<Order> */
    public function findUnpaidOlderThan(DateTimeImmutable $date): array;   // متدهای معنادار دامنه
    public function save(Order $order): void;
}

final class EloquentOrderRepository implements OrderRepository
{
    public function findById(OrderId $id): ?Order { return Order::find($id->value); }

    public function findUnpaidOlderThan(DateTimeImmutable $date): array
    {
        return Order::where('status', OrderStatus::Pending)
            ->where('created_at', '<', $date)
            ->get()->all();
    }

    public function save(Order $order): void { $order->save(); }
}

بحث Repository در Laravel

موافقان

  • متمرکز کردن کوئری‌های پیچیده و تکراری در یک جا با نام معنادار.
  • امکان decorator (cache) و جایگزینی منبع داده.
  • تست سرویس‌ها با fake repository بدون دیتابیس.
  • در معماری‌های DDD/Hexagonal، port رسمی لایهٔ persistence.

مخالفان

  • Eloquent خودش Active Record است؛ repository روی آن یک abstraction نشتی (leaky) است: معمولاً مدل‌های Eloquent (با lazy loading و save()) برگردانده می‌شوند، پس دامنه واقعاً از persistence جدا نشده.
  • «Generic repository» با متدهای all()، find()، create() فقط Eloquent را تکرار می‌کند و قدرت Query Builder (eager loading، scopes، pagination) را می‌گیرد.
  • تعویض دیتابیس/ORM در عمل تقریباً هیچ‌وقت رخ نمی‌دهد (YAGNI).
  • Laravel ابزارهای تست با دیتابیس واقعی (RefreshDatabase، SQLite in-memory، factories) را راحت کرده است.

پاسخ متعادل در آزمون: «Repository در Laravel اجباری نیست. برای CRUD ساده، Eloquent مستقیم در Action/Service کافی است و local scope و custom query builder کوئری‌ها را reusable می‌کنند. Repository وقتی ارزش دارد که: کوئری‌های پیچیدهٔ دامنه‌ای داریم، منبع داده متنوع است (API خارجی + DB)، به cache decorator نیاز داریم، یا معماری DDD با دامنهٔ مستقل از فریم‌ورک داریم. در این حالت repository باید متدهای دامنه‌ای (findUnpaidOlderThan) داشته باشد نه یک wrapper عمومی روی Eloquent.»

سوالات تشریحی

الگوی طراحی را تعریف کنید و سه دستهٔ الگوهای GoF را با مثال توضیح دهید. چه زمانی استفاده از الگو به over-engineering تبدیل می‌شود؟

تعریف: الگوی طراحی یک راه‌حل عمومی و اثبات‌شده برای یک مسئلهٔ تکرارشونده در طراحی نرم‌افزار است؛ کد آماده نیست، بلکه قالبی است که با زمینهٔ مسئله تطبیق داده می‌شود. هر الگو نام، مسئله، راه‌حل و پیامد (trade-off) دارد و مهم‌ترین فایده‌اش ایجاد واژگان مشترک در تیم است.

  • Creational — نحوهٔ ساخت objectها و جدا کردن کلاینت از کلاس concrete: Singleton، Factory Method، Abstract Factory، Builder (Query Builder)، Prototype (replicate()).
  • Structural — ترکیب کلاس‌ها و objectها: Adapter (Flysystem)، Decorator (caching repository)، Facade، Proxy، Composite، Bridge.
  • Behavioral — تقسیم مسئولیت و ارتباط objectها: Strategy (driverها)، Observer (events)، Command (jobs)، Chain of Responsibility (middleware)، Template Method، State، Iterator.

Over-engineering وقتی رخ می‌دهد که الگو برای مسئله‌ای فرضی یا آینده‌ای نامعلوم به کار رود (نقض YAGNI): interface برای کلاسی که هرگز پیاده‌سازی دوم ندارد، repositoryی که فقط متدهای Eloquent را تکرار می‌کند، factory برای ساخت یک object ساده، یا لایه‌هایی که فقط فراخوانی را پاس می‌دهند. هزینهٔ هر الگو، کلاس‌های بیشتر، indirection و سخت‌تر شدن فهم کد است.

معیار تصمیم: آیا نقطهٔ تغییر واقعی وجود دارد؟ آیا الگو تست‌پذیری یا خوانایی را بهتر می‌کند؟ ساده‌ترین راه‌حلی که کار می‌کند را بنویسید و وقتی تکرار یا درد واقعی ظاهر شد، refactor به سمت الگو کنید (refactoring to patterns).

الگوی Singleton را پیاده‌سازی کنید. چرا آن را anti-pattern می‌دانند؟ تفاوت آن با $app->singleton() و $app->scoped() در Laravel چیست؟

تعریف: Singleton تضمین می‌کند کلاس فقط یک instance داشته باشد و یک نقطهٔ دسترسی سراسری به آن بدهد.

<?php
final class Logger
{
    private static ?self $instance = null;
    private function __construct() {}
    private function __clone() {}
    public function __wakeup(): never { throw new LogicException(); }
    public static function instance(): self { return self::$instance ??= new self(); }
}

چرا anti-pattern:

  • Global state و وابستگی پنهان (Logger::instance() در هر جای کد).
  • تست‌پذیری ضعیف: جایگزینی با fake سخت است و state بین تست‌ها نشت می‌کند.
  • نقض SRP: کلاس هم کار خودش را می‌کند هم چرخهٔ عمرش را مدیریت می‌کند.
  • coupling به کلاس concrete (نقض Dependency Inversion).
  • در Octane/worker طولانی، state بین درخواست‌ها می‌ماند.

در Laravel: یکتایی به container سپرده می‌شود و کلاس یک کلاس عادی با constructor عمومی است:

<?php
$this->app->singleton(ExchangeRateClient::class, fn () => new ExchangeRateClient(config('rates.key')));
$this->app->scoped(CurrentTenant::class);     // یکتا در هر request/job
$this->app->bind(ReportBuilder::class);       // هر بار جدید
  • singleton: یک instance در طول عمر container (در FPM = یک درخواست؛ در Octane/queue worker = طول عمر پروسس).
  • scoped: مثل singleton ولی در شروع هر درخواست Octane یا هر job در queue worker reset می‌شود؛ برای stateهای وابسته به درخواست (tenant جاری، user context) مناسب است.

وابستگی از طریق constructor injection صریح است و در تست با $this->app->instance() یا $this->mock() جایگزین می‌شود.

Facade در GoF و Facade در Laravel را مقایسه کنید. وقتی Cache::get('key') صدا زده می‌شود، دقیقاً چه اتفاقی می‌افتد؟ چرا Facadeهای لاراول برخلاف متدهای static قابل تست‌اند؟

GoF Facade: یک interface ساده و سطح بالا برای یک زیرسیستم پیچیده متشکل از چند کلاس؛ مثلاً CheckoutFacade::placeOrder() که inventory، payment، shipping و mail را هماهنگ می‌کند. API جدید و ساده‌تری می‌سازد.

Laravel Facade: یک static proxy به یک سرویس در Service Container. زیرسیستمی را ساده نمی‌کند؛ همان API سرویس اصلی را با سینتکس static در اختیار می‌گذارد. از نظر الگو به Proxy + Service Locator نزدیک‌تر است.

جریان Cache::get('key'):

  1. کلاس Cache متد static get ندارد، پس Facade::__callStatic('get', ['key']) اجرا می‌شود.
  2. getFacadeRoot() با کلید getFacadeAccessor() (اینجا 'cache') instance را از container resolve می‌کند و در $resolvedInstance نگه می‌دارد.
  3. $instance->get('key') روی CacheManager اجرا می‌شود که آن هم با __call به store پیش‌فرض (Repository) forward می‌کند.
<?php
public static function __callStatic($method, $args)
{
    $instance = static::getFacadeRoot();
    if (! $instance) { throw new RuntimeException('A facade root has not been set.'); }
    return $instance->$method(...$args);
}

تست‌پذیری: چون فراخوانی در نهایت روی یک instance انجام می‌شود، می‌توان آن instance را عوض کرد: Cache::shouldReceive('get')->once()->andReturn('v') (یک Mockery mock را swap می‌کند)، یا Mail::fake()، Queue::fake()، Event::fake(). متد static واقعی به کلاس گره خورده و قابل جایگزینی نیست.

معایب: وابستگی پنهان (در constructor دیده نمی‌شود)، coupling به فریم‌ورک، نیاز به ide-helper برای IDE. در کد دامنه، تزریق contract (Illuminate\Contracts\Cache\Repository) صریح‌تر است.

یک فروشگاه سه درگاه پرداخت دارد و کاربر هنگام پرداخت درگاه را انتخاب می‌کند. با الگوی Strategy این سناریو را پیاده‌سازی کنید طوری که افزودن درگاه چهارم نیاز به تغییر کد موجود نداشته باشد.

ایده: هر درگاه یک strategy با interface مشترک است؛ یک resolver/registry بر اساس انتخاب کاربر strategy مناسب را از container می‌گیرد و سرویس checkout (context) فقط با interface کار می‌کند.

<?php
interface PaymentGateway
{
    public function key(): string;
    public function start(Order $order): RedirectUrl;
    public function verify(Order $order, array $callback): PaymentResult;
}

final class ZarinpalGateway implements PaymentGateway { public function key(): string { return 'zarinpal'; } /* ... */ }
final class IdPayGateway implements PaymentGateway { public function key(): string { return 'idpay'; } /* ... */ }
final class WalletGateway implements PaymentGateway { public function key(): string { return 'wallet'; } /* ... */ }

final class GatewayResolver
{
    /** @var array<string, PaymentGateway> */
    private array $gateways = [];

    /** @param iterable<PaymentGateway> $gateways */
    public function __construct(iterable $gateways)
    {
        foreach ($gateways as $g) { $this->gateways[$g->key()] = $g; }
    }

    public function resolve(string $key): PaymentGateway
    {
        return $this->gateways[$key] ?? throw new UnsupportedGateway($key);
    }

    /** @return list<string> */
    public function available(): array { return array_keys($this->gateways); }
}

// ServiceProvider: درگاه جدید = فقط یک کلاس + یک tag
$this->app->tag([ZarinpalGateway::class, IdPayGateway::class, WalletGateway::class], 'payment.gateways');
$this->app->singleton(GatewayResolver::class, fn ($app) => new GatewayResolver($app->tagged('payment.gateways')));

final class StartPayment
{
    public function __construct(private GatewayResolver $resolver) {}

    public function __invoke(Order $order, string $gatewayKey): RedirectUrl
    {
        return $this->resolver->resolve($gatewayKey)->start($order);   // بدون if/switch
    }
}
// validation: 'gateway' => ['required', Rule::in($resolver->available())]

چرا خوب است: Open/Closed (درگاه چهارم = یک کلاس جدید و افزودن به tag)، حذف شرط‌های پراکنده، تست هر درگاه به‌صورت مستقل، و امکان FakeGateway در محیط local و تست.

Trade-off: کلاس‌های بیشتر و یک لایهٔ indirection؛ اگر فقط یک درگاه دارید، این ساختار زودهنگام است. می‌توان به‌جای tag از Manager لاراول (extend('newGateway', ...)) هم استفاده کرد.

Simple Factory، Factory Method و Abstract Factory را تعریف و مقایسه کنید. برای هر کدام یک مثال در PHP یا Laravel بزنید.
  • Simple Factory (idiom، نه GoF): یک کلاس/متد که بر اساس پارامتر، یکی از چند کلاس را می‌سازد. ساده است ولی برای نوع جدید باید ویرایش شود.
  • Factory Method (GoF، مبتنی بر ارث‌بری): کلاس پایه الگوریتم را دارد و ساخت محصول را به یک متد (abstract یا قابل override) می‌سپارد؛ زیرکلاس تعیین می‌کند چه کلاسی ساخته شود.
  • Abstract Factory (GoF، مبتنی بر ترکیب): یک object factory با چند متد برای ساخت خانواده‌ای از محصولات مرتبط که باید با هم سازگار باشند.
<?php
// Simple Factory
final class ExporterFactory {
    public function make(string $type): Exporter {
        return match ($type) { 'csv' => new CsvExporter(), 'xlsx' => new XlsxExporter(),
            default => throw new InvalidArgumentException($type) };
    }
}

// Factory Method — مثال واقعی Laravel
class Order extends Model {
    public function newCollection(array $models = []): OrderCollection   // override
    { return new OrderCollection($models); }
}

// Abstract Factory
interface UiKitFactory { public function button(): Button; public function modal(): Modal; }
final class BootstrapKit implements UiKitFactory { /* BootstrapButton + BootstrapModal */ }
final class TailwindKit implements UiKitFactory { /* TailwindButton + TailwindModal */ }

یک Decorator برای افزودن cache به یک repository پیاده‌سازی کنید و آن را در container لاراول ثبت کنید. تفاوت Decorator، Proxy و Adapter چیست؟

Decorator objectی را می‌پیچد که همان interface را دارد و قبل/بعد از delegate کردن، رفتار اضافه می‌کند؛ بدون تغییر کلاس اصلی (Open/Closed).

<?php
interface CategoryRepository
{
    /** @return Collection<int, Category> */
    public function tree(): Collection;
    public function update(Category $c, array $data): void;
}

final class CachedCategoryRepository implements CategoryRepository
{
    public function __construct(
        private CategoryRepository $inner,
        private \Illuminate\Contracts\Cache\Repository $cache,
    ) {}

    public function tree(): Collection
    {
        return $this->cache->remember('categories:tree', now()->addHour(), fn () => $this->inner->tree());
    }

    public function update(Category $c, array $data): void
    {
        $this->inner->update($c, $data);
        $this->cache->forget('categories:tree');      // invalidation بعد از نوشتن
    }
}

// AppServiceProvider::register
$this->app->bind(CategoryRepository::class, EloquentCategoryRepository::class);
$this->app->extend(CategoryRepository::class,
    fn (CategoryRepository $repo, $app) => new CachedCategoryRepository($repo, $app['cache.store']));

مصرف‌کننده فقط CategoryRepository را type-hint می‌کند و نمی‌داند cache وجود دارد. با decorator دیگری (مثلاً logging یا metrics) می‌توان لایه‌ها را زنجیر کرد.

مقایسه:

  • Adapter: interface را تغییر می‌دهد تا کلاس ناسازگار (SDK خارجی) با interface مورد انتظار کار کند.
  • Decorator: interface را حفظ و رفتار اضافه می‌کند؛ object درونی از بیرون داده می‌شود و decoratorها قابل انباشته شدن‌اند.
  • Proxy: interface را حفظ و دسترسی را کنترل می‌کند (lazy loading، مجوز، remote)؛ اغلب خودش object واقعی را می‌سازد یا مدیریت می‌کند.

هزینه‌ها: باید همهٔ متدهای interface را delegate کرد، invalidation cache خودش منبع باگ است (دادهٔ کهنه)، و ترتیب decoratorها اهمیت دارد.

شرکت قصد دارد ارائه‌دهندهٔ پیامک را عوض کند و کد فعلی در ده‌ها جا مستقیماً SDK قدیمی را صدا می‌زند. با الگوی Adapter راه‌حلی ارائه دهید که این مشکل دیگر تکرار نشود.

مشکل: وابستگی مستقیم کد دامنه به API یک vendor (coupling محکم). تعویض vendor یعنی تغییر همهٔ نقاط فراخوانی و ریسک بالا.

راه‌حل: یک interface متعلق به دامنهٔ ما (Target/Port) تعریف می‌کنیم و برای هر vendor یک Adapter می‌نویسیم که فراخوانی‌ها، ساختار داده و exceptionها را ترجمه می‌کند. کد فقط به interface وابسته است.

<?php
interface SmsSender
{
    /** @throws SmsDeliveryFailed */
    public function send(string $mobile, string $message): string;   // برمی‌گرداند: message id
}

final class OldVendorAdapter implements SmsSender
{
    public function __construct(private \OldVendor\Client $client) {}

    public function send(string $mobile, string $message): string
    {
        $res = $this->client->sendMessage(['to' => $mobile, 'body' => $message]);
        if ($res['status'] !== 200) { throw new SmsDeliveryFailed($res['error']); }
        return (string) $res['id'];
    }
}

final class NewVendorAdapter implements SmsSender
{
    public function __construct(private \NewVendor\Api $api, private string $line) {}

    public function send(string $mobile, string $message): string
    {
        try {
            return $this->api->messages()->create($this->line, '+98' . ltrim($mobile, '0'), $message)->id;
        } catch (\NewVendor\ApiException $e) {
            throw new SmsDeliveryFailed($e->getMessage(), previous: $e);
        }
    }
}

// تعویض vendor = یک خط در provider (یا بر اساس config)
$this->app->bind(SmsSender::class, NewVendorAdapter::class);

مهاجرت: ابتدا OldVendorAdapter را بنویسید و همهٔ فراخوانی‌ها را به SmsSender تغییر دهید (refactor بدون تغییر رفتار)، سپس adapter جدید را اضافه و binding را عوض کنید. می‌توان با یک Decorator «failover» هر دو را ترکیب کرد.

مزایا: جدا شدن دامنه از vendor (Hexagonal: Port & Adapter)، تست با FakeSmsSender، ترجمهٔ exceptionها به exception دامنه. Laravel همین را برای Filesystem (Flysystem adapters)، Cache stores و Mail transports انجام داده است. می‌توان این قابلیت را به‌صورت یک notification channel سفارشی هم پیاده کرد.

الگوی Observer را تعریف کنید. Events/Listeners و Model Observers در Laravel چه تفاوتی دارند؟ دام‌های رایج استفاده از آن‌ها چیست؟

تعریف: Observer یک وابستگی یک‌به‌چند ایجاد می‌کند تا با تغییر وضعیت subject، همهٔ observerها خودکار مطلع شوند؛ subject فقط می‌داند «کسانی گوش می‌دهند»، نه اینکه چه کسانی (loose coupling، Open/Closed).

Events / Listeners

  • رویدادهای دامنه‌ای صریح: OrderPaid، UserRegistered.
  • Dispatcher مرکزی (Mediator) بین آن‌هاست.
  • listener می‌تواند ShouldQueue باشد (async).
  • سطح معنایی بالا: «چه اتفاقی در کسب‌وکار افتاد».

Model Observers

  • واکنش به چرخهٔ عمر persistence مدل: creating، updated، deleted.
  • یک کلاس که همهٔ hookهای یک مدل را گروه می‌کند.
  • مناسب دغدغه‌های فنی: تولید slug/uuid، پاک کردن cache، audit log.
<?php
final class OrderObserver
{
    public function updated(Order $order): void
    {
        if ($order->wasChanged('status') && $order->status === OrderStatus::Paid) {
            OrderPaid::dispatch($order);        // تبدیل رویداد فنی به رویداد دامنه
        }
    }
}

final class OrderPaid implements ShouldDispatchAfterCommit   // فقط پس از commit تراکنش
{
    use Dispatchable, SerializesModels;
    public function __construct(public readonly Order $order) {}
}

دام‌ها:

  • Mass update/delete (Order::where(...)->update()) مستقیم SQL است و رویداد مدل fire نمی‌شود.
  • تراکنش: listener یا job داخل تراکنشی که بعداً rollback می‌شود؛ با afterCommit یا ShouldDispatchAfterCommit حل می‌شود.
  • منطق پنهان: قوانین اصلی کسب‌وکار در observer دیده نمی‌شوند؛ دیباگ دشوار است.
  • حلقه: save() داخل saved رویداد را دوباره fire می‌کند (saveQuietly()).
  • listener همگام کند (ارسال ایمیل) زمان پاسخ را بالا می‌برد؛ از queue استفاده کنید.
Jobهای صف در Laravel چگونه الگوی Command را پیاده می‌کنند؟ یک job برای ارسال فاکتور بنویسید که در برابر اجرای تکراری امن باشد.

Command pattern: یک درخواست به‌صورت object کپسوله می‌شود (داده + عملیات)، در نتیجه می‌توان آن را ذخیره، صف، زمان‌بندی، retry یا لاگ کرد. اجزا: Command (job)، Invoker (queue worker / Bus) و Receiver (سرویسی که کار واقعی را انجام می‌دهد).

در Laravel، job داده‌هایش را در constructor می‌گیرد، serialize و در صف ذخیره می‌شود؛ worker بعداً آن را unserialize و handle() را با تزریق وابستگی‌ها اجرا می‌کند. چون job ممکن است به‌دلیل timeout یا خطا بیش از یک بار اجرا شود (تحویل at-least-once)، باید idempotent باشد.

<?php
final class SendInvoice implements ShouldQueue, ShouldBeUnique
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 5;
    public array $backoff = [10, 60, 300];         // تأخیر بین تلاش‌ها

    public function __construct(public readonly Invoice $invoice) {}   // فقط id مدل serialize می‌شود

    public function uniqueId(): string { return (string) $this->invoice->id; }

    public function handle(InvoiceMailer $mailer): void        // Receiver
    {
        $invoice = $this->invoice->fresh();
        if ($invoice->sent_at !== null) {
            return;                                 // idempotency: قبلاً ارسال شده
        }
        $mailer->send($invoice);
        $invoice->update(['sent_at' => now()]);
    }

    public function failed(Throwable $e): void
    {
        Log::error('Invoice sending failed', ['id' => $this->invoice->id, 'error' => $e->getMessage()]);
    }
}

SendInvoice::dispatch($invoice)->onQueue('mail')->afterCommit();

مزایای Command: جدا شدن «درخواست کار» از «اجرای آن» (async، مقیاس‌پذیری با افزودن worker)، retry و backoff، chain و batch (Bus::chain، Bus::batch)، و قابلیت تست با Queue::fake(). Artisan commandها نیز همین الگو هستند.

نکات: دادهٔ حجیم را در job نگذارید (فقط شناسه)؛ ShouldBeUnique از صف شدن تکراری جلوگیری می‌کند اما جای idempotency در handle را نمی‌گیرد.

الگوی Chain of Responsibility را توضیح دهید. کلاس Pipeline در Laravel چگونه کار می‌کند؟ با آن مجموعه‌ای از قوانین تخفیف را روی یک سبد خرید اعمال کنید.

تعریف: درخواست از زنجیره‌ای از handlerها عبور می‌کند؛ هر handler می‌تواند آن را پردازش کند، به بعدی بدهد، یا زنجیره را قطع کند. فرستنده نمی‌داند کدام handler کار را انجام می‌دهد.

Pipeline لاراول: send($passable)->through($pipes)->then($destination). در داخل، با array_reduce روی آرایهٔ معکوس pipeها یک closure تودرتو (پیاز) ساخته می‌شود که هر لایه $next را صدا می‌زند؛ بنابراین هر pipe می‌تواند قبل و بعد از $next کار کند. Middlewareهای HTTP دقیقاً همین‌طور اجرا می‌شوند.

<?php
final class CartContext
{
    public function __construct(public Cart $cart, public int $discount = 0, public array $applied = []) {}
}

final class VipDiscount
{
    public function handle(CartContext $ctx, Closure $next): CartContext
    {
        if ($ctx->cart->customer->isVip()) {
            $ctx->discount += intdiv($ctx->cart->subtotal() * 10, 100);
            $ctx->applied[] = 'vip';
        }
        return $next($ctx);
    }
}

final class CouponDiscount
{
    public function handle(CartContext $ctx, Closure $next): CartContext
    {
        if ($coupon = $ctx->cart->coupon) {
            if ($coupon->isExclusive()) {
                $ctx->discount = $coupon->amount;
                $ctx->applied = ['coupon'];
                return $ctx;                        // قطع زنجیره: قوانین بعدی اعمال نشوند
            }
            $ctx->discount += $coupon->amount;
        }
        return $next($ctx);
    }
}

final class MaxDiscountCap
{
    public function handle(CartContext $ctx, Closure $next): CartContext
    {
        $ctx->discount = min($ctx->discount, intdiv($ctx->cart->subtotal(), 2));   // سقف 50٪
        return $next($ctx);
    }
}

$result = app(Pipeline::class)
    ->send(new CartContext($cart))
    ->through([VipDiscount::class, CouponDiscount::class, MaxDiscountCap::class])
    ->thenReturn();

Builder: ساخت گام‌به‌گام یک object پیچیده را از نمایش نهایی آن جدا می‌کند؛ کلاینت با فراخوانی‌های fluent پیکربندی می‌کند و در پایان محصول ساخته می‌شود.

Query Builder: متدهای where، join، orderBy، limit فقط state داخلی (آرایه‌های wheres، joins، orders، bindings) را پر می‌کنند؛ SQL تا لحظهٔ get()/toSql() ساخته نمی‌شود. ساخت رشتهٔ SQL به Grammar مخصوص هر دیتابیس سپرده شده (MySqlGrammar، PostgresGrammar)؛ یعنی همان فرایند ساخت، نمایش‌های مختلف — تعریف کلاسیک Builder.

<?php
$q = DB::table('orders')

  • Telescoping constructor (new Query('orders', null, null, 'paid', 20, ...)): ناخوانا، مستعد خطا در ترتیب پارامترها.
  • Named arguments (PHP 8): برای objectهایی با پارامترهای اختیاری زیاد اما ساخت یک‌مرحله‌ای عالی است و نیاز به Builder را در DTOها و Value Objectها از بین می‌برد: new HttpOptions(timeout: 5, retries: 3).
  • Builder وقتی برتری دارد که ساخت چندمرحله‌ای یا شرطی است (when())، بخش‌ها قابل تکرارند (چند where)، اعتبارسنجی قبل از ساخت لازم است، یا یک فرایند باید نمایش‌های مختلف تولید کند.

نکته: Builder لاراول mutable است؛ برای استفادهٔ دوباره از یک کوئری پایه باید clone() کرد (Prototype)، وگرنه شرط‌ها روی هم انباشته می‌شوند.

هر دو برای متغیر کردن بخشی از یک الگوریتم هستند؛ تفاوت در مکانیزم است:

State pattern: رفتار هر وضعیت در یک کلاس جدا قرار می‌گیرد و object اصلی فراخوانی را به state فعلی delegate می‌کند؛ stateها خودشان انتقال بعدی را تعیین می‌کنند.

<?php
abstract class OrderState
{
    public function __construct(protected Order $order) {}
    public function pay(): void    { throw InvalidTransition::from($this, 'pay'); }
    public function ship(): void   { throw InvalidTransition::from($this, 'ship'); }
    public function cancel(): void { throw InvalidTransition::from($this, 'cancel'); }
    abstract public function name(): string;
}

final class Pending extends OrderState
{
    public function name(): string { return 'pending'; }
    public function pay(): void    { $this->order->setState(new Paid($this->order)); }
    public function cancel(): void { $this->order->setState(new Cancelled($this->order)); }
}

final class Paid extends OrderState
{
    public function name(): string { return 'paid'; }
    public function ship(): void   { $this->order->setState(new Shipped($this->order)); }
    public function cancel(): void { RefundPayment::dispatch($this->order); $this->order->setState(new Cancelled($this->order)); }
}
final class Shipped extends OrderState { public function name(): string { return 'shipped'; } }
final class Cancelled extends OrderState { public function name(): string { return 'cancelled'; } }

        if ($amount < 0) { throw new InvalidArgumentException('Negative money'); }
    }

    public static function of(int $amount, Currency $c): self { return new self($amount, $c); }

    public function add(self $o): self
    {
        $this->assertSameCurrency($o);
        return new self($this->amount + $o->amount, $this->currency);   // object جدید
    }

    public function percentage(int $p): self { return new self(intdiv($this->amount * $p, 100), $this->currency); }
    public function equals(self $o): bool { return $this->amount === $o->amount && $this->currency === $o->currency; }

    private function assertSameCurrency(self $o): void
    {
        if ($o->currency !== $this->currency) { throw new CurrencyMismatch(); }
    }
}

enum Currency: string { case IRR = 'IRR'; case USD = 'USD'; }

final class MoneyCast implements CastsAttributes
{
    public function get(Model $model, string $key, mixed $value, array $attributes): Money
    {
        return Money::of((int) $attributes['total_amount'], Currency::from($attributes['total_currency']));
    }

    public function set(Model $model, string $key, mixed $value, array $attributes): array
    {
        return ['total_amount' => $value->amount, 'total_currency' => $value->currency->value];
    }
}

Refactor: Strategy برای هر روش ارسال + Adapter برای API اسنپ + یک registry/factory + کنترلر لاغر.

<?php
interface ShippingMethod
{
    public function key(): string;
    public function cost(Order $order): Money;
}

final class PostShipping implements ShippingMethod
{
    public function key(): string { return 'post'; }
    public function cost(Order $o): Money { return Money::of(20000 + $o->weight * 1000, Currency::IRR); }
}

final class SnappShipping implements ShippingMethod
{
    public function __construct(private SnappClient $client) {}        // Adapter روی API خارجی
    public function key(): string { return 'snapp'; }
    public function cost(Order $o): Money { return $this->client->quote($o->address); }
}

final class ShippingCalculator
{
    /** @var array<string, ShippingMethod> */
    private array $methods;

    /** @param iterable<ShippingMethod> $methods */
    public function __construct(iterable $methods)
    {
        foreach ($methods as $m) { $this->methods[$m->key()] = $m; }
    }

    public function for(string $key): ShippingMethod
    {
        return $this->methods[$key] ?? throw new UnknownShippingMethod($key);
    }
}

// Provider
$this->app->tag([PostShipping::class, TipaxShipping::class, SnappShipping::class], 'shipping');
$this->app->bind(ShippingCalculator::class, fn ($app) => new ShippingCalculator($app->tagged('shipping')));

// Controller
public function cost(ShippingCostRequest $request, ShippingCalculator $calc): JsonResponse
{
    $order = Order::findOrFail($request->validated('order_id'));
    $cost = $calc->for($request->validated('method'))->cost($order);
    return response()->json(['amount' => $cost->amount]);
}

خلاصه برای مرور سریع

پایه

  • الگو = راه‌حل اثبات‌شده برای مسئلهٔ تکرارشونده؛ نام + مسئله + راه‌حل + پیامد.
  • GoF: Creational (ساخت)، Structural (ترکیب)، Behavioral (تعامل). Fowler/PoEAA: Repository، AR، DM، Service Layer، DTO.
  • اصول: program to interface، composition over inheritance، encapsulate what varies، SOLID.
  • Over-engineering: interface تک‌پیاده‌سازی، wrapper بی‌ارزش، YAGNI.

Creational

  • Singleton: یک instance؛ anti-pattern (global state، تست سخت). Laravel: singleton()، scoped() (reset در هر request/job در Octane/queue)، bind().
  • Simple Factory: match روی نوع. Static factory: Money::fromString()، Carbon::parse().
  • Factory Method: زیرکلاس محصول را تعیین می‌کند (ارث‌بری) — newCollection().
  • Abstract Factory: خانوادهٔ محصولات سازگار (ترکیب) — ConnectionFactory.
  • Builder: ساخت گام‌به‌گام — Query Builder (+ Grammar)، Http::، Blueprint.
  • Prototype: clone + __clone برای deep copy — replicate()، $query->clone().

Structural

  • Adapter: interface را تغییر می‌دهد — Flysystem، Cache Stores، SDK wrapperها.
  • Decorator: همان interface + رفتار اضافه، قابل زنجیر — $app->extend()، caching repo.
  • Proxy: همان interface + کنترل دسترسی/lazy — deferred providers، lazy relations، lazy objects در 8.4.
  • GoF Facade: API ساده برای زیرسیستم پیچیده. Laravel Facade: static proxy به container (__callStatic → getFacadeAccessor → resolve) — قابل mock با shouldReceive/fake؛ وابستگی پنهان.
  • Composite: درخت؛ برگ و گروه با یک interface. Bridge: جدا کردن دو بُعد (abstraction ↔ implementation).

Behavioral

  • Strategy: الگوریتم قابل تعویض با ترکیب؛ کلاینت انتخاب می‌کند — drivers، درگاه پرداخت.
  • State: ساختار مشابه Strategy، اما stateها انتقال را تعیین می‌کنند؛ جایگزین سبک: enum + canTransitionTo.
  • Template Method: اسکلت final در پایه + hook در زیرکلاس (ارث‌بری) — FormRequest، Command.
  • Observer: یک‌به‌چند — Events/Listeners (دامنه‌ای، قابل queue)، Model Observers (چرخهٔ عمر). دام: mass update بدون event، تراکنش → afterCommit.
  • Command: درخواست = object (صف، retry، undo) — Jobs، Bus، Artisan. Job باید idempotent باشد.
  • Chain of Responsibility: زنجیرهٔ handler با امکان قطع — Middleware، Pipeline::send()->through()->then() (array_reduce معکوس → پیاز).
  • Iterator: Collection، LazyCollection، generator. Mediator: Event Dispatcher، Bus.
  • Null Object: withDefault()، NullStore، NullLogger. Specification: قاعدهٔ قابل ترکیب ≈ scopeها.

معماری

  • MVC + thin controller؛ منطق در Service (هماهنگی use case) یا Action (یک کلاس = یک عملیات، Fortify).
  • DTO (انتقال داده) / VO (مقداری، immutable، invariant، equals) / Entity (ID). VO در Eloquent: custom cast.
  • DI: وابستگی صریح، constructor injection، auto-wiring، contextual binding (when()->needs()->give()). Service Locator (app()، Facade): وابستگی پنهان؛ فقط در composition root.
  • Active Record (Eloquent): object ذخیره‌کنندهٔ خود؛ سریع ولی درهم. Data Mapper (Doctrine): entity خالص + EntityManager + Unit of Work + Identity Map.
  • Repository: اختیاری در Laravel؛ فقط با متدهای دامنه‌ای؛ generic repository = anti-pattern؛ جایگزین: scope و custom builder.
  • Manager = Factory + Strategy + Registry (+ Adapter)؛ createXDriver()، extend()، driver()/store().

تمایزهای پرتکرار

  • Adapter (تغییر interface) ↔ Decorator (افزودن رفتار) ↔ Proxy (کنترل دسترسی).
  • Strategy (ترکیب، runtime) ↔ Template Method (ارث‌بری، compile-time).
  • Strategy (کلاینت انتخاب می‌کند) ↔ State (state خودش انتقال می‌دهد).
  • Factory Method (یک محصول، ارث‌بری) ↔ Abstract Factory (خانواده، ترکیب).
  • GoF Facade (ساده‌سازی زیرسیستم) ↔ Laravel Facade (static proxy / locator).
  • Singleton GoF (کلاس خودش) ↔ container singleton (پیکربندی بیرونی، قابل تست).
