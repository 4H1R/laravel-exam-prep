ACID در عمق

Transaction یک واحد منطقی کار است که شامل یک یا چند عملیات روی دیتابیس می‌شود و دیتابیس تضمین می‌کند که این مجموعه یا کامل اعمال شود یا اصلاً اعمال نشود. چهار ویژگی ACID قراردادی است که دیتابیس رابطه‌ای درباره‌ی تراکنش‌ها با ما می‌بندد. نکته‌ی مهم برای پاسخ تشریحی این است که فقط تعریف نکنید؛ بگویید هر ویژگی با چه مکانیزمی پیاده‌سازی می‌شود.

Write-Ahead Logging؛ قلب Durability

دیتابیس به‌جای اینکه با هر COMMIT صفحه‌های داده (data pages) را که به‌صورت تصادفی روی دیسک پخش‌اند بنویسد، ابتدا تغییر را به‌صورت ترتیبی (sequential) در لاگ می‌نویسد و آن را fsync می‌کند. صفحه‌های داده بعداً و به‌صورت دسته‌ای (checkpoint) flush می‌شوند. اگر سرور crash کند، هنگام راه‌اندازی، لاگ replay می‌شود (crash recovery). نوشتن ترتیبی بسیار سریع‌تر از نوشتن تصادفی است؛ به همین دلیل WAL هم Durability و هم کارایی را تأمین می‌کند.

تنظیمات مهم Durability در MySQL

  • innodb_flush_log_at_trx_commit = 1 (پیش‌فرض): در هر COMMIT لاگ نوشته و fsync می‌شود؛ ACID کامل.
  • = 2: در هر COMMIT به OS نوشته می‌شود ولی fsync حدوداً هر ثانیه؛ crash خود MySQL داده را از بین نمی‌برد ولی crash سیستم‌عامل/قطع برق ممکن است تا حدود یک ثانیه تراکنش را از بین ببرد.
  • = 0: سریع‌ترین و ناامن‌ترین؛ حتی crash خود MySQL هم ممکن است تراکنش‌های ثانیه‌ی آخر را از بین ببرد.
  • sync_binlog = 1: binlog هم در هر commit fsync شود؛ برای سازگاری binlog با داده (و درنتیجه replication و PITR) لازم است.

تله‌ی رایج سوال: «C» در ACID با «C» در CAP یکی نیست. در ACID، Consistency یعنی رعایت قیود و invariantهای داده؛ در CAP یعنی Linearizability، یعنی همه‌ی نودها در یک لحظه آخرین مقدار نوشته‌شده را ببینند.

Consistency تنها ویژگی ACID است که بخشی از آن بر عهده‌ی برنامه است. دیتابیس فقط قیودی را که تعریف کرده‌اید اعمال می‌کند؛ اگر قانون «مجموع موجودی حساب‌ها ثابت بماند» را در کد درست پیاده نکنید، دیتابیس نمی‌تواند آن را تضمین کند.

تراکنش در Laravel

<?php
use Illuminate\Support\Facades\DB;

// روش closure: در صورت Exception خودکار rollback، در غیر این صورت commit.
// پارامتر دوم: تعداد تلاش مجدد در صورت deadlock.
DB::transaction(function () use ($from, $to, $amount) {
    Account::whereKey($from)->decrement('balance', $amount);
    Account::whereKey($to)->increment('balance', $amount);
    Transfer::create(['from' => $from, 'to' => $to, 'amount' => $amount]);
}, attempts: 3);

// روش دستی
DB::beginTransaction();
try {
    // ...
    DB::commit();
} catch (\Throwable $e) {
    DB::rollBack();
    throw $e;
}

تراکنش‌های تودرتو در Laravel با SAVEPOINT پیاده می‌شوند؛ یعنی DB::transaction داخلی یک commit واقعی نیست و فقط بیرونی‌ترین تراکنش commit می‌کند. همچنین کارهای خارج از دیتابیس (ارسال ایمیل، صدا زدن API، dispatch کردن job) را داخل تراکنش قرار ندهید؛ rollback آن‌ها را برنمی‌گرداند. برای jobها از afterCommit یا DB::afterCommit() استفاده کنید.

تراکنش را کوتاه نگه دارید. تراکنش طولانی یعنی قفل طولانی، احتمال بیشتر deadlock، رشد undo log در InnoDB و جلوگیری از VACUUM در PostgreSQL.

سطوح ایزولاسیون و ناهنجاری‌ها

Isolation کامل (اجرای سریالی) گران است. استاندارد SQL چهار سطح تعریف می‌کند که هر کدام بین درستی و هم‌زمانی (concurrency) مصالحه می‌کنند. برای توضیح هر سطح، باید بدانید چه ناهنجاری (anomaly)‌ای را مجاز می‌داند.

ناهنجاری‌ها

Dirty Read
تراکنش A داده‌ای را می‌خواند که تراکنش B نوشته ولی هنوز commit نکرده؛ اگر B rollback کند، A داده‌ای را دیده که هرگز وجود نداشته است.
Non-Repeatable Read
A یک سطر را دو بار می‌خواند و بین این دو بار، B آن سطر را update و commit کرده؛ پس دو مقدار متفاوت دیده می‌شود.
Phantom Read
A یک شرط (range) را دو بار query می‌کند و بین این دو بار، B سطری را insert/delete کرده که با شرط مطابقت دارد؛ پس مجموعه‌ی نتایج تغییر می‌کند.
Lost Update
A و B هر دو مقداری را می‌خوانند، در برنامه تغییرش می‌دهند و می‌نویسند (read-modify-write)؛ نوشتن دوم، نوشتن اول را بی‌اثر می‌کند.
Write Skew
A و B هر دو یک شرط مشترک را می‌خوانند (مثلاً «حداقل دو پزشک کشیک هستند»)، و هر کدام بر اساس آن، سطر متفاوتی را تغییر می‌دهند؛ هیچ‌کدام تداخل مستقیم ندارند، اما نتیجه‌ی نهایی invariant را نقض می‌کند (هیچ پزشکی کشیک نمی‌ماند).

پیش‌فرض‌ها و تفاوت پیاده‌سازی

MySQL InnoDB

  • پیش‌فرض: REPEATABLE READ.
  • خواندن ساده (consistent nonlocking read) از snapshot خوانده می‌شود؛ snapshot در اولین خواندن تراکنش ساخته می‌شود (نه لزوماً در BEGIN).
  • UPDATE/DELETE و SELECT … FOR UPDATE «current read» هستند: آخرین نسخه‌ی commit‌شده را می‌خوانند و قفل می‌گیرند، نه snapshot.
  • برای جلوگیری از phantom در locking readها از gap lock و next-key lock استفاده می‌کند.
  • Serializable در InnoDB قفل‌محور است: SELECTهای ساده (وقتی autocommit خاموش است) ضمنی به FOR SHARE تبدیل می‌شوند.
  • Read Uncommitted واقعاً dirty read دارد.

PostgreSQL

  • پیش‌فرض: READ COMMITTED؛ هر statement snapshot تازه می‌گیرد.
  • Read Uncommitted مثل Read Committed رفتار می‌کند؛ dirty read هرگز رخ نمی‌دهد.
  • Repeatable Read همان Snapshot Isolation است؛ phantom هم رخ نمی‌دهد. اگر سطری که شما می‌خواهید update کنید را تراکنش دیگری بعد از snapshot شما تغییر داده باشد، خطای could not serialize access due to concurrent update می‌گیرید.
  • Serializable با SSI (Serializable Snapshot Isolation) پیاده شده: قفل خواندنی نمی‌گذارد، وابستگی‌های خطرناک را رصد می‌کند و یکی از تراکنش‌ها را با SQLSTATE 40001 abort می‌کند. برنامه باید retry کند.

مثال Write Skew

-- invariant: حداقل یک پزشک باید on_call باشد. الان Ali و Sara هر دو on_call هستند.
-- T1 (Ali)                                   -- T2 (Sara)
BEGIN;                                        BEGIN;
SELECT count(*) FROM doctors                  SELECT count(*) FROM doctors
 WHERE on_call AND shift_id = 7;  -- 2         WHERE on_call AND shift_id = 7;  -- 2
UPDATE doctors SET on_call = false            UPDATE doctors SET on_call = false
 WHERE name = 'Ali';                           WHERE name = 'Sara';
COMMIT;                                       COMMIT;
-- نتیجه: هیچ پزشکی on_call نیست! دو تراکنش سطرهای متفاوتی را نوشتند، پس
-- Snapshot Isolation تداخلی تشخیص نمی‌دهد.

راه‌حل‌ها: (۱) سطح SERIALIZABLE (در PostgreSQL یکی abort می‌شود)؛ (۲) قفل صریح روی سطرهایی که شرط را تشکیل می‌دهند: SELECT … FOR UPDATE؛ (۳) «materializing the conflict»: یک سطر مشترک (مثلاً سطر shifts) را قفل کنید تا تراکنش‌ها روی یک چیز مشترک تداخل پیدا کنند؛ (۴) در صورت امکان، تبدیل invariant به constraint.

تنظیم Isolation Level

-- MySQL: برای تراکنش بعدی
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- PostgreSQL: داخل تراکنش
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;

// Laravel: در config/database.php برای MySQL می‌توان سطح را با options/isolation_level تعیین کرد،
// یا به‌صورت موردی قبل از تراکنش:
DB::statement('SET TRANSACTION ISOLATION LEVEL SERIALIZABLE');

جمله‌ی کلیدی برای پاسخ: «بالاتر بردن سطح ایزولاسیون، ناهنجاری‌های کمتری را مجاز می‌کند اما هزینه‌اش هم‌زمانی کمتر، قفل یا abort بیشتر و نیاز به retry در برنامه است. انتخاب سطح باید بر اساس invariantهای کسب‌وکار باشد؛ برای بیشتر برنامه‌های وب Read Committed یا Repeatable Read کافی است و بخش‌های حساس (پول، موجودی) با قفل صریح یا عملیات atomic محافظت می‌شوند.»

بسیاری از تیم‌ها روی MySQL، Isolation را به READ COMMITTED تغییر می‌دهند تا gap lock و deadlock کمتر شود. این تصمیم درستی است فقط اگر بدانید non-repeatable read و phantom در منطق شما مشکل‌ساز نیستند. نکته‌ی تاریخی: در گذشته replication مبتنی بر statement با READ COMMITTED سازگار نبود؛ با binlog_format=ROW (پیش‌فرض MySQL 8) این محدودیت وجود ندارد.

MVCC

MVCC یعنی دیتابیس از هر سطر چند نسخه نگه می‌دارد تا خواننده‌ها نویسنده‌ها را بلاک نکنند و نویسنده‌ها خواننده‌ها را بلاک نکنند. هر تراکنش یک snapshot از داده‌های commit‌شده تا یک لحظه‌ی مشخص می‌بیند. نویسنده‌ها با هم همچنان با قفل سطری هماهنگ می‌شوند (دو تراکنش نمی‌توانند هم‌زمان یک سطر را update کنند).

MVCC در InnoDB

  • هر سطر در clustered index ستون‌های مخفی دارد: DB_TRX_ID (آخرین تراکنشی که آن را تغییر داده) و DB_ROLL_PTR (اشاره‌گر به رکورد undo که نسخه‌ی قبلی را می‌سازد).
  • نسخه‌ی جاری در جای خود (in-place) به‌روز می‌شود و نسخه‌های قدیمی از طریق زنجیره‌ی undo log بازسازی می‌شوند.
  • هر snapshot یک Read View است: فهرست تراکنش‌های فعال در لحظه‌ی ساخت. اگر DB_TRX_ID سطر برای این read view «نامرئی» باشد، InnoDB زنجیره‌ی undo را دنبال می‌کند تا به نسخه‌ی مرئی برسد.
  • Purge thread رکوردهای undo را که دیگر هیچ read viewای به آن‌ها نیاز ندارد پاک می‌کند. یک تراکنش باز طولانی، purge را متوقف می‌کند و history list length رشد می‌کند؛ نتیجه: کندی تدریجی کل سرور.

MVCC در PostgreSQL

  • هر UPDATE در عمل یک tuple جدید در heap می‌سازد و tuple قبلی را با xmax علامت می‌زند؛ هر tuple دارای xmin (تراکنش سازنده) و xmax (تراکنش حذف‌کننده) است.
  • tupleهای مرده (dead tuples) در جدول می‌مانند تا VACUUM (معمولاً autovacuum) فضایشان را قابل استفاده‌ی مجدد کند. اگر autovacuum عقب بماند: bloat جدول و ایندکس.
  • HOT update (Heap-Only Tuple): اگر هیچ ستون ایندکس‌شده‌ای تغییر نکند و در همان صفحه جا باشد، ایندکس‌ها به‌روزرسانی نمی‌شوند؛ دلیل دیگر برای اینکه ایندکس‌های غیرضروری نسازید.
  • شناسه‌ی تراکنش ۳۲ بیتی است؛ VACUUM باید tupleهای قدیمی را freeze کند تا از transaction ID wraparound جلوگیری شود.

سوال محتمل: «چرا در MVCC خواندن، نوشتن را بلاک نمی‌کند؟» پاسخ: چون خواننده نسخه‌ی snapshot خودش را می‌خواند و نیازی به قفل روی نسخه‌ی جاری ندارد؛ نویسنده نسخه‌ی جدید می‌سازد. فقط نوشتن-نوشتن روی یک سطر نیاز به قفل دارد. تبصره: SELECT … FOR UPDATE و FOR SHARE از MVCC عبور نمی‌کنند و قفل می‌گیرند.

قفل‌ها: Pessimistic و Optimistic

انواع قفل از نظر حالت

Shared (S) موجودExclusive (X) موجود
درخواست Sسازگار ✓منتظر ✗
درخواست Xمنتظر ✗منتظر ✗
  • Shared Lock (S): «من این را می‌خوانم و نباید تا پایان تراکنشم تغییر کند». چند تراکنش هم‌زمان می‌توانند S بگیرند. SQL: SELECT … FOR SHARE (در MySQL قدیمی‌تر LOCK IN SHARE MODE)؛ Laravel: sharedLock().
  • Exclusive Lock (X): «من این را تغییر می‌دهم». با هیچ قفل دیگری سازگار نیست. UPDATE/DELETE خودکار X می‌گیرند؛ صریح: SELECT … FOR UPDATE؛ Laravel: lockForUpdate().
  • Intention Locks (IS/IX): قفل در سطح جدول که اعلام می‌کند «قصد دارم روی سطرهایی قفل S/X بگیرم»؛ تا عملیاتی مثل LOCK TABLES … WRITE بتواند بدون بررسی تک‌تک سطرها تشخیص دهد تداخل هست یا نه.

دانه‌بندی (Granularity)

Row-level lock

  • هم‌زمانی بالا؛ فقط سطرهای درگیر قفل می‌شوند.
  • سربار مدیریت قفل بیشتر.
  • InnoDB و PostgreSQL برای DML از قفل سطری استفاده می‌کنند.

Table-level lock

  • ساده و کم‌سربار، ولی هم‌زمانی پایین.
  • MyISAM فقط قفل جدولی داشت.
  • DDLها (مثل ALTER TABLE) قفل metadata/جدولی می‌گیرند؛ مراقب migration روی جداول بزرگ باشید.

در InnoDB قفل‌ها روی رکوردهای ایندکس گرفته می‌شوند، نه روی «سطر» به‌صورت انتزاعی. اگر UPDATE … WHERE status = 'x' بزنید و روی status ایندکس نباشد، InnoDB کل clustered index را اسکن می‌کند و همه‌ی سطرهای اسکن‌شده (عملاً کل جدول) قفل می‌شوند. ایندکس مناسب روی شرط WHERE در UPDATE/DELETE فقط مسئله‌ی سرعت نیست؛ مسئله‌ی هم‌زمانی است.

Record، Gap و Next-Key Lock در InnoDB

Record Lock
قفل روی یک رکورد ایندکس.
Gap Lock
قفل روی فاصله‌ی بین دو رکورد ایندکس (یا قبل از اولین/بعد از آخرین)؛ هدفش جلوگیری از insert در آن بازه است. gap lockها با هم تداخل ندارند؛ فقط جلوی insert را می‌گیرند.
Next-Key Lock
ترکیب record lock روی یک رکورد + gap lock روی فاصله‌ی قبل از آن. قفل پیش‌فرض InnoDB برای جست‌وجو و اسکن ایندکس در REPEATABLE READ و ابزار جلوگیری از phantom.
Insert Intention Lock
نوعی gap lock که INSERT قبل از درج می‌گیرد؛ چند insert در یک gap اگر موقعیت متفاوت داشته باشند هم را بلاک نمی‌کنند، ولی با gap lock تراکنش دیگر تداخل دارند.
ایندکس روی age:   10        20        30
                  │         │         │
 (-∞,10]  (10,20]  (20,30]  (30,+∞)

T1: SELECT * FROM users WHERE age BETWEEN 15 AND 25 FOR UPDATE;   -- REPEATABLE READ
    ⇒ next-key lock روی (10,20] و (20,30]   ⇒ insert با age=12 یا 27 بلاک می‌شود
T2: INSERT INTO users(age) VALUES (27);   ⏳ منتظر می‌ماند (phantom ممکن نیست)

در READ COMMITTED: gap lock برای جست‌وجوها غیرفعال است ⇒ فقط record lock ⇒ insert آزاد
  • اگر جست‌وجو روی ایندکس یکتا با شرط تساوی و برای یک سطر موجود باشد (WHERE id = 5)، فقط record lock گرفته می‌شود، نه gap.
  • اگر سطر وجود نداشته باشد (WHERE id = 7 و 7 نیست)، gap lock گرفته می‌شود. این منشأ deadlockهای معروف الگوی «SELECT FOR UPDATE؛ اگر نبود INSERT» است.

Pessimistic Locking در Laravel

<?php
// رزرو آخرین صندلی‌ها: فقط یک تراکنش در هر لحظه می‌تواند این سطر را بخواند-و-تغییر دهد
DB::transaction(function () use ($eventId, $qty) {
    $event = Event::whereKey($eventId)->lockForUpdate()->firstOrFail(); // SELECT ... FOR UPDATE

    if ($event->remaining_seats < $qty) {
        throw new SoldOutException();
    }

    $event->decrement('remaining_seats', $qty);
    Booking::create(['event_id' => $eventId, 'qty' => $qty]);
});
// نکته: lockForUpdate بیرون از تراکنش عملاً بی‌اثر است؛ قفل با پایان statement (autocommit) آزاد می‌شود.

اگر منطق ساده است، از عملیات atomic استفاده کنید که اصلاً به قفل صریح نیاز ندارد:

<?php
// UPDATE events SET remaining_seats = remaining_seats - ? WHERE id = ? AND remaining_seats >= ?
$affected = Event::whereKey($eventId)
    ->where('remaining_seats', '>=', $qty)
    ->decrement('remaining_seats', $qty);

if ($affected === 0) {
    throw new SoldOutException();
}

Optimistic Locking با ستون version

فرض optimistic: «تداخل نادر است». قفلی نگه نمی‌داریم؛ هنگام نوشتن بررسی می‌کنیم که از زمان خواندن، کسی سطر را تغییر نداده باشد. اگر تغییر داده بود، خطای conflict برمی‌گردانیم یا دوباره تلاش می‌کنیم. مناسب برای ویرایش‌های طولانی که کاربر فرم را چند دقیقه باز نگه می‌دارد (نمی‌توان قفل دیتابیس را چند دقیقه نگه داشت).

// خواندن: version را هم به کلاینت بدهید (مثلاً hidden field یا ETag)
$doc = Document::findOrFail($id);   // version = 7

// نوشتن: UPDATE ... WHERE id = ? AND version = ?
$affected = Document::whereKey($id)

        'body'    => $request->input('body'),

Deadlock

Deadlock وضعیتی است که دو (یا چند) تراکنش هر کدام قفلی را نگه داشته‌اند که دیگری به آن نیاز دارد و هیچ‌کدام نمی‌توانند پیش بروند؛ یعنی یک چرخه در گراف انتظار (wait-for graph).

T1: UPDATE accounts SET … WHERE id = 1;   ── X lock روی 1 ✓
T2: UPDATE accounts SET … WHERE id = 2;   ── X lock روی 2 ✓
T1: UPDATE accounts SET … WHERE id = 2;   ── منتظر T2 ⏳
T2: UPDATE accounts SET … WHERE id = 1;   ── منتظر T1 ⏳   ⇒ چرخه ⇒ DEADLOCK

      ┌────── منتظر ──────┐
      ▼                   │
    [T1] ──── منتظر ────► [T2]

چهار شرط Coffman

Deadlock فقط وقتی رخ می‌دهد که هر چهار شرط برقرار باشد: Mutual Exclusion (منبع انحصاری)، Hold and Wait (نگه داشتن یکی و انتظار برای دیگری)، No Preemption (نمی‌توان قفل را به‌زور گرفت) و Circular Wait (انتظار چرخه‌ای). پیشگیری یعنی شکستن یکی از این‌ها؛ در عمل معمولاً Circular Wait را با ترتیب ثابت قفل‌گیری می‌شکنیم.

تشخیص

  • InnoDB: به‌صورت پیش‌فرض (innodb_deadlock_detect=ON) چرخه را فوراً تشخیص می‌دهد و یک تراکنش را به‌عنوان قربانی rollback می‌کند (تراکنشی که کوچک‌تر است؛ یعنی سطرهای کمتری را تغییر داده یا قفل کرده). خطا: ERROR 1213 (40001): Deadlock found when trying to get lock.
  • انتظار طولانی بدون چرخه: innodb_lock_wait_timeout (پیش‌فرض ۵۰ ثانیه) ⇒ ERROR 1205 Lock wait timeout exceeded.
  • دیدن آخرین deadlock: SHOW ENGINE INNODB STATUS (بخش LATEST DETECTED DEADLOCK)؛ برای ثبت همه در error log: innodb_print_all_deadlocks=ON.
  • PostgreSQL: پس از deadlock_timeout (پیش‌فرض ۱ ثانیه) انتظار، بررسی چرخه انجام می‌شود؛ خطا با SQLSTATE 40P01.

پیشگیری و کاهش

  1. ترتیب ثابت قفل‌گیری: همیشه منابع را به یک ترتیب قفل کنید (مثلاً بر اساس id صعودی). در انتقال پول، اول حساب با id کوچک‌تر.
  2. تراکنش کوتاه: هیچ I/O خارجی (HTTP، ایمیل) داخل تراکنش نباشد.
  3. ایندکس مناسب روی شرط‌های UPDATE/DELETE/FOR UPDATE تا سطرهای کمتری اسکن و قفل شوند.
  4. در صورت امکان READ COMMITTED در MySQL تا gap lockها حذف شوند.
  5. به‌جای الگوی «SELECT FOR UPDATE؛ اگر نبود INSERT» از INSERT … ON DUPLICATE KEY UPDATE (MySQL) یا INSERT … ON CONFLICT (PostgreSQL) یا upsert() در Laravel استفاده کنید.
  6. دسته‌های بزرگ UPDATE را به batchهای کوچک بشکنید.
  7. و مهم‌تر از همه: Deadlock را خطای عادی بدانید و retry کنید. در سیستم پرهم‌زمان، حذف کامل deadlock ممکن نیست.
<?php
// ترتیب ثابت + retry خودکار در deadlock
public function transfer(int $fromId, int $toId, int $amount): void
{
    DB::transaction(function () use ($fromId, $toId, $amount) {
        $ids = [$fromId, $toId];
        sort($ids); // همیشه اول id کوچک‌تر ⇒ چرخه شکل نمی‌گیرد

        $accounts = Account::whereIn('id', $ids)
            ->orderBy('id')
            ->lockForUpdate()
            ->get()
            ->keyBy('id');

        if ($accounts[$fromId]->balance < $amount) {
            throw new InsufficientFunds();
        }
        $accounts[$fromId]->decrement('balance', $amount);
        $accounts[$toId]->increment('balance', $amount);
    }, attempts: 3); // Laravel روی خطای deadlock کل closure را دوباره اجرا می‌کند
}

تفاوت Deadlock و Lock wait timeout: در deadlock چرخه وجود دارد و دیتابیس فوراً یکی را قربانی می‌کند؛ در lock wait timeout چرخه‌ای نیست، فقط یک تراکنش قفل را بیش از حد نگه داشته (مثلاً تراکنش طولانی یا فراموش‌شده). راه‌حل دومی پیدا کردن تراکنش نگه‌دارنده است (performance_schema.data_lock_waits در MySQL 8، pg_locks و pg_stat_activity در PostgreSQL).

ساختار داخلی ایندکس

B+Tree

ایندکس پیش‌فرض در InnoDB و PostgreSQL ساختار B+Tree است: درختی متوازن با فاکتور انشعاب (fan-out) بسیار بالا (صدها کلید در هر صفحه‌ی ۱۶KB در InnoDB یا ۸KB در PostgreSQL). ویژگی‌ها:

  • نودهای داخلی فقط کلید و اشاره‌گر دارند؛ داده/اشاره‌گر نهایی فقط در برگ‌ها است.
  • برگ‌ها به‌صورت لیست پیوندی مرتب به هم متصل‌اند ⇒ range scan و ORDER BY بسیار کارآمد.
  • متوازن است: هر جست‌وجو O(log n) با پایه‌ی بزرگ؛ یک جدول صدها میلیون سطری معمولاً عمق ۳ تا ۴ دارد، یعنی ۳ تا ۴ خواندن صفحه (که نودهای بالایی هم معمولاً در حافظه‌اند).
                    ┌───────────────┐
                    │   [30 | 60]   │            ← root
                    └──┬─────┬────┬─┘
          ┌────────────┘     │    └────────────┐
    ┌─────▼─────┐      ┌─────▼─────┐     ┌─────▼─────┐
    │ [10 | 20] │      │ [40 | 50] │     │ [70 | 80] │   ← internal
    └─┬───┬───┬─┘      └───────────┘     └───────────┘
      ▼   ▼   ▼
   ┌────┐┌────┐┌────┐    ┌────┐
   │1..9│⇄│10..│⇄│20..│ ⇄ │30..│ ⇄ …                    ← leaves (مرتب و پیوندی)
   └────┘└────┘└────┘    └────┘
   range scan: پیدا کردن اولین برگ ⇒ حرکت افقی روی لیست

انواع دیگر: Hash index (فقط تساوی؛ در InnoDB به‌صورت Adaptive Hash Index داخلی، در PostgreSQL صریحاً قابل ساخت)، GIN در PostgreSQL (برای JSONB، آرایه و full-text؛ ایندکس معکوس)، GiST/SP-GiST (داده‌های هندسی و بازه‌ای)، BRIN (جداول عظیم با داده‌ی مرتب طبیعی مثل زمان؛ بسیار کوچک)، و FULLTEXT و SPATIAL در MySQL.

Clustered و Secondary Index در InnoDB

Clustered Index (Primary Key)

  • خود جدول است: برگ‌ها کل سطر را نگه می‌دارند و داده به ترتیب PK ذخیره می‌شود.
  • هر جدول دقیقاً یکی دارد. اگر PK تعریف نکنید، اولین ایندکس UNIQUE NOT NULL و در غیر این صورت یک row id مخفی ۶ بایتی استفاده می‌شود.
  • جست‌وجو با PK: یک بار پیمایش درخت.

Secondary Index

  • برگ‌ها: مقدار ستون‌های ایندکس + مقدار PK (نه اشاره‌گر فیزیکی).
  • جست‌وجو: پیمایش secondary ⇒ گرفتن PK ⇒ پیمایش دوم در clustered index (bookmark lookup).
  • پس PK بزرگ (مثلاً UUID رشته‌ای ۳۶ کاراکتری) همه‌ی ایندکس‌های ثانویه را بزرگ می‌کند.

UUID v4 تصادفی به‌عنوان PK در InnoDB: چون clustered index به ترتیب PK مرتب است، insertهای تصادفی باعث page split، تکه‌تکه‌شدن، و پراکندگی نوشتن‌ها در کل buffer pool می‌شود. راه‌حل: PK عددی AUTO_INCREMENT/BIGINT، یا UUIDهای مرتب‌شونده بر اساس زمان (UUIDv7، ULID) و ذخیره به‌صورت BINARY(16) به‌جای CHAR(36). در PostgreSQL جدول heap است و مشکل کمتر است، ولی خود ایندکس B-Tree همچنان از کلیدهای تصادفی آسیب می‌بیند.

در PostgreSQL جداول clustered نیستند: داده در heap است و همه‌ی ایندکس‌ها (از جمله PK) به آدرس فیزیکی tuple (ctid) اشاره می‌کنند. Index Only Scan فقط وقتی واقعاً بدون رجوع به heap است که صفحه در visibility map همه‌ی tupleهایش visible علامت خورده باشد (یعنی VACUUM به‌روز باشد).

Composite Index و قانون Leftmost Prefix

ایندکس (a, b, c) ابتدا بر اساس a، سپس داخل هر a بر اساس b و سپس c مرتب است؛ مثل دفترچه‌ی تلفن که اول بر اساس نام خانوادگی و بعد نام مرتب است. پس فقط وقتی قابل استفاده است که شرط از چپ‌ترین ستون شروع شود.

قاعده‌ی طراحی composite index: ستون‌های تساوی اول، بعد ستونی که ORDER BY/GROUP BY روی آن است، و در آخر ستون range. مثلاً برای WHERE user_id = ? AND status = ? AND created_at > ? ORDER BY created_at ایندکس (user_id, status, created_at) مناسب است. ترتیب ستون‌ها در ایندکس مهم است، نه ترتیب در WHERE.

Covering Index

اگر همه‌ی ستون‌هایی که query لازم دارد (SELECT، WHERE، ORDER BY) در خود ایندکس باشند، دیتابیس اصلاً به جدول رجوع نمی‌کند. در EXPLAIN مربوط به MySQL با Using index و در PostgreSQL با Index Only Scan دیده می‌شود. در InnoDB چون PK داخل هر secondary index هست، ایندکس (status) برای SELECT id FROM t WHERE status = ? خودبه‌خود covering است. PostgreSQL (11+) با INCLUDE اجازه می‌دهد ستون‌های غیرکلیدی را در برگ‌ها نگه دارید.

-- MySQL
CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at);
-- این query کاملاً از ایندکس جواب داده می‌شود:
SELECT id, created_at FROM orders WHERE user_id = 7 AND status = 'paid' ORDER BY created_at DESC LIMIT 20;

-- PostgreSQL: ستون total فقط در برگ‌ها (بخشی از کلید نیست)
CREATE INDEX idx_orders_cover ON orders (user_id, created_at) INCLUDE (total);

Selectivity و Cardinality

  • Cardinality: تعداد مقادیر متمایز یک ستون (در MySQL در SHOW INDEX تخمینی است و با ANALYZE TABLE به‌روز می‌شود).
  • Selectivity = cardinality ÷ تعداد سطرها؛ بین ۰ و ۱. هرچه به ۱ نزدیک‌تر (مثل email)، ایندکس مفیدتر. ستون is_active با دو مقدار، selectivity پایینی دارد.
  • اگر شرط بخش بزرگی از جدول (مثلاً بیش از حدود ۲۰ تا ۳۰ درصد؛ عدد دقیق بستگی به cost model دارد) را برگرداند، optimizer معمولاً full scan را ترجیح می‌دهد، چون هزاران lookup تصادفی از یک اسکن ترتیبی گران‌تر است.
  • استثنا: ستون کم‌تنوع ولی با توزیع نامتوازن (مثلاً ۹۹٪ done و ۱٪ pending)؛ ایندکس برای جست‌وجوی pending عالی است. در PostgreSQL partial index (WHERE status = 'pending') بهترین گزینه است.

چه وقت ایندکس ضرر دارد؟

  • هر INSERT/UPDATE/DELETE باید همه‌ی ایندکس‌های مرتبط را به‌روز کند ⇒ write amplification. جداول write-heavy (لاگ، رویداد) را با ایندکس اشباع نکنید.
  • فضای دیسک و حافظه‌ی buffer pool مصرف می‌کند؛ ایندکس‌های بلااستفاده، داده‌ی مفید را از cache بیرون می‌کنند.
  • ایندکس‌های تکراری/زائد: با وجود (a, b) ایندکس جداگانه‌ی (a) معمولاً زائد است.
  • optimizer ممکن است ایندکس اشتباه انتخاب کند (آمار قدیمی)؛ ایندکس بیشتر = فضای تصمیم بزرگ‌تر.
  • ستون با selectivity بسیار پایین و توزیع یکنواخت.
  • جداول خیلی کوچک (چند صد سطر): full scan به همان سرعت است.

پیدا کردن ایندکس‌های بلااستفاده: در MySQL 8 view sys.schema_unused_indexes و در PostgreSQL pg_stat_user_indexes (ستون idx_scan = 0). در MySQL 8 می‌توانید قبل از حذف، ایندکس را INVISIBLE کنید تا بدون ریسک اثرش را بسنجید.

EXPLAIN و بهینه‌سازی Query

EXPLAIN برنامه‌ی اجرای (execution plan) که optimizer انتخاب کرده را نشان می‌دهد؛ EXPLAIN ANALYZE (MySQL 8.0.18+ و PostgreSQL) query را واقعاً اجرا می‌کند و زمان و تعداد سطر واقعی را کنار تخمین‌ها می‌گذارد. اختلاف زیاد بین rows تخمینی و واقعی معمولاً یعنی آمار قدیمی است.

۱. شرط Sargable بنویسید (تابع روی ستون نزنید)

CREATE INDEX idx_email_lower ON users ((LOWER(email)));

LIKE 'ali%' از ایندکس استفاده می‌کند (range)، ولی LIKE '%ali%' نه. برای جست‌وجوی متنی از FULLTEXT، pg_trgm در PostgreSQL یا موتور جست‌وجو استفاده کنید.

-- ✓ Keyset / Seek pagination: از آخرین id صفحه‌ی قبل ادامه بده

۴. فقط ستون‌های لازم را بخوانید

۶. OR روی ستون‌های مختلف

WHERE a = 1 OR b = 2 ممکن است به full scan برسد. optimizer گاهی index_merge می‌زند؛ در غیر این صورت به UNION ALL دو query ایندکس‌دار بازنویسی کنید (مراقب تکراری‌ها باشید).

۷. COUNT روی جداول بزرگ

در InnoDB و PostgreSQL، COUNT(*) به خاطر MVCC باید سطرها (یا کوچک‌ترین ایندکس) را بشمارد؛ عدد ذخیره‌شده‌ای ندارد. برای داشبورد از شمارنده‌ی جداگانه یا تخمین استفاده کنید.

روش کار سیستماتیک

  1. پیدا کردن queryهای کند: slow query log (long_query_time)، performance_schema/sys.statement_analysis، pg_stat_statements، Laravel Telescope/Pulse.
  2. اولویت با queryهایی که زمان کل (تکرار × میانگین) بیشتری دارند، نه لزوماً کندترین تکی.
  3. EXPLAIN/EXPLAIN ANALYZE ⇒ بررسی type، rows، Extra.
  4. ایندکس، بازنویسی query، کاهش داده‌ی خوانده‌شده، denormalization سنجیده، یا cache.
  5. اندازه‌گیری دوباره روی داده‌ی واقعی (نه دیتابیس تست کوچک).

در سوالات «این query کند است، چه می‌کنید؟» حتماً اشاره کنید: اول اندازه‌گیری (EXPLAIN ANALYZE، slow log)، بعد تغییر. پاسخ «یک ایندکس اضافه می‌کنم» بدون توضیح ترتیب ستون‌ها و تأثیر روی نوشتن، پاسخ کاملی نیست.

CTE و Window Function

CTE (Common Table Expression)

CTE یک نتیجه‌ی موقت نام‌دار است که با WITH تعریف می‌شود و فقط در همان query وجود دارد. فایده‌ی اصلی: خوانایی (شکستن query پیچیده به مراحل نام‌دار)، استفاده‌ی چندباره از یک زیرquery، و مهم‌تر از همه CTE بازگشتی (recursive) برای داده‌های درختی. MySQL از نسخه‌ی 8.0 از CTE و window function پشتیبانی می‌کند.

-- مشتریانی که در 30 روز گذشته بیش از میانگین خرید کرده‌اند
WITH recent AS (
    SELECT user_id, SUM(total) AS spent
    FROM orders
    WHERE created_at >= NOW() - INTERVAL 30 DAY
    GROUP BY user_id
),
avg_spent AS (
    SELECT AVG(spent) AS v FROM recent
)
SELECT r.user_id, r.spent
FROM recent r, avg_spent a
WHERE r.spent > a.v
ORDER BY r.spent DESC;

CTE بازگشتی: درخت دسته‌بندی

-- categories(id, parent_id, name): همه‌ی زیرشاخه‌های دسته‌ی 5 همراه با عمق
WITH RECURSIVE tree AS (
    SELECT id, parent_id, name, 0 AS depth
    FROM categories
    WHERE id = 5                      -- anchor member
    UNION ALL
    SELECT c.id, c.parent_id, c.name, t.depth + 1
    FROM categories c
    JOIN tree t ON c.parent_id = t.id -- recursive member
)
SELECT * FROM tree ORDER BY depth;

در CTE بازگشتی مراقب چرخه در داده باشید (مثلاً A والد B و B والد A). MySQL با cte_max_recursion_depth (پیش‌فرض 1000) جلوی حلقه‌ی بی‌پایان را می‌گیرد؛ در PostgreSQL می‌توانید از CYCLE (نسخه‌ی 14+) یا نگه‌داری مسیر استفاده کنید.

کارایی CTE: در PostgreSQL قبل از نسخه‌ی 12، CTE همیشه materialize می‌شد و مانع بهینه‌سازی بود (optimization fence). از نسخه‌ی 12 به بعد، CTE غیربازگشتی که یک بار استفاده شود inline می‌شود و می‌توانید با MATERIALIZED / NOT MATERIALIZED کنترلش کنید. MySQL هم CTE را بسته به شرایط merge یا materialize می‌کند. پس CTE ذاتاً کندتر از subquery نیست، ولی EXPLAIN را بررسی کنید.

Window Function

Window function روی یک «پنجره» از سطرهای مرتبط محاسبه انجام می‌دهد، بدون اینکه سطرها را مثل GROUP BY ادغام کند؛ هر سطر باقی می‌ماند و یک ستون محاسبه‌شده می‌گیرد. ساختار کلی:

function_name(...) OVER (
    PARTITION BY ...      -- گروه‌بندی پنجره (اختیاری)
    ORDER BY ...          -- ترتیب داخل پنجره
    ROWS BETWEEN ... AND ...  -- frame (اختیاری)
)

ROW_NUMBER()شماره‌ی یکتا برای هر سطر1, 2, 3, 4 (ترتیب ties نامعین مگر ORDER BY کامل)
RANK()رتبه با فاصله1, 2, 2, 4
DENSE_RANK()رتبه بدون فاصله1, 2, 2, 3
NTILE(n)تقسیم به n دسته (مثلاً چارک)—
LAG() / LEAD()مقدار سطر قبلی/بعدی (رشد ماه‌به‌ماه)—
FIRST_VALUE() / LAST_VALUE()اولین/آخرین مقدار پنجرهLAST_VALUE به frame حساس است
SUM()/AVG()/COUNT() OVERجمع تجمعی، میانگین متحرک، درصد از کل—

Top-N در هر گروه: ۳ سفارش آخر هر کاربر

WITH ranked AS (
    SELECT o.*,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC) AS rn
    FROM orders o
)
SELECT * FROM ranked WHERE rn <= 3;
-- نکته: window function را نمی‌توان مستقیم در WHERE استفاده کرد (بعد از WHERE محاسبه می‌شود)؛
-- به همین دلیل از CTE یا subquery استفاده می‌کنیم.

جمع تجمعی (Running Total) و میانگین متحرک

SELECT day,
       revenue,
       SUM(revenue) OVER (ORDER BY day
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(revenue) OVER (ORDER BY day
                          ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS moving_avg_7d,
       revenue - LAG(revenue) OVER (ORDER BY day)                         AS diff_prev_day,
       ROUND(100 * revenue / SUM(revenue) OVER (), 2)                     AS pct_of_total
FROM daily_revenue
ORDER BY day;

اگر ORDER BY داخل OVER بدهید و frame را مشخص نکنید، frame پیش‌فرض RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW است؛ یعنی سطرهای با مقدار ORDER BY برابر (peers) با هم جمع می‌شوند و running total برای روزهای تکراری «پرش» می‌کند. برای جمع تجمعی سطربه‌سطر صریحاً ROWS بنویسید.

رتبه‌بندی با RANK و DENSE_RANK

SELECT name, department_id, salary,
       RANK()       OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk,
       DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS dense_rnk
FROM employees;
-- salary: 900, 800, 800, 700  ⇒  rnk: 1,2,2,4   dense_rnk: 1,2,2,3

$ranked = DB::table('orders')
    ->select('*')
    ->selectRaw('ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn');

$latest3 = DB::query()->fromSub($ranked, 'r')->where('rn', '<=', 3)->get();

// یا پکیج‌هایی مثل staudenmeir/laravel-cte استفاده می‌شود.

تفاوت GROUP BY و Window Function: GROUP BY سطرها را به یک سطر در هر گروه تبدیل می‌کند؛ window function تعداد سطرها را حفظ می‌کند و فقط ستون محاسباتی اضافه می‌کند. پس برای «هر سفارش به‌همراه مجموع خرید آن کاربر» window function مناسب است: SUM(total) OVER (PARTITION BY user_id).

View، Materialized View، Procedure و Trigger

View

View یک query ذخیره‌شده با نام است؛ داده‌ای ذخیره نمی‌کند و هر بار که از آن select می‌کنید، query زیرین اجرا می‌شود. کاربردها: ساده‌سازی queryهای تکراری، لایه‌ی امنیتی (دادن دسترسی به view به‌جای جدول، مخفی کردن ستون‌های حساس)، و لایه‌ی سازگاری هنگام تغییر schema.

CREATE VIEW active_customers AS
SELECT id, name, email   -- ستون‌های حساس مثل national_id حذف شده
FROM users
WHERE status = 'active' AND deleted_at IS NULL;

GRANT SELECT ON shop.active_customers TO 'report_user'@'%';
  • View ساده (یک جدول، بدون aggregate/DISTINCT) معمولاً updatable است.
  • در MySQL الگوریتم MERGE (ادغام در query بیرونی، کارآمد) و TEMPTABLE (ساخت جدول موقت؛ با aggregate) وجود دارد.
  • View خودش سرعت را بالا نمی‌برد؛ فقط query را پنهان می‌کند. Viewهای تودرتو می‌توانند planهای بد بسازند.

Materialized View

Materialized View نتیجه‌ی query را فیزیکی ذخیره می‌کند؛ خواندن بسیار سریع است ولی داده تا refresh بعدی کهنه (stale) است. مناسب گزارش‌ها و داشبوردهایی که تأخیر چند دقیقه‌ای قابل قبول است.

-- PostgreSQL
CREATE MATERIALIZED VIEW daily_sales AS
SELECT date_trunc('day', created_at) AS day, SUM(total) AS revenue, COUNT(*) AS orders
FROM orders
GROUP BY 1;

CREATE UNIQUE INDEX ON daily_sales (day);           -- برای CONCURRENTLY لازم است
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales;  -- خواننده‌ها حین refresh بلاک نمی‌شوند

MySQL Materialized View ندارد. معادلش یک summary table است که با job زمان‌بندی‌شده (Laravel Scheduler، MySQL Event)، یا به‌صورت افزایشی با event/queue پس از هر تغییر، یا با trigger به‌روز می‌شود.

<?php
// routes/console.php — بازسازی summary table هر 10 دقیقه
Schedule::call(function () {
    DB::statement(<<<SQL
        INSERT INTO daily_sales (day, revenue, orders)
        SELECT DATE(created_at), SUM(total), COUNT(*)
        FROM orders WHERE created_at >= CURDATE() - INTERVAL 1 DAY
        GROUP BY DATE(created_at)
        ON DUPLICATE KEY UPDATE revenue = VALUES(revenue), orders = VALUES(orders)
    SQL);
})->everyTenMinutes()->withoutOverlapping();

Stored Procedure و Trigger: مصالحه‌ها

مزایا

  • اجرای منطق کنار داده ⇒ رفت‌وبرگشت شبکه‌ی کمتر برای عملیات چندمرحله‌ای حجیم.
  • Trigger تضمین می‌کند قاعده (مثلاً audit log) صرف‌نظر از اینکه کدام برنامه داده را تغییر داده اجرا شود.
  • کنترل دسترسی: کاربر فقط اجازه‌ی EXECUTE دارد، نه دسترسی مستقیم به جدول.

معایب

  • منطق کسب‌وکار پنهان و دوپاره (بخشی در PHP، بخشی در DB)؛ سخت‌تر برای خواندن و دیباگ.
  • نسخه‌بندی، code review، تست واحد و CI سخت‌تر.
  • مقیاس‌پذیری: دیتابیس گران‌ترین و سخت‌ترین لایه برای scale افقی است؛ CPU آن را صرف منطق برنامه نکنید.
  • وابستگی به vendor (زبان PL/pgSQL یا SQL/PSM در MySQL).
  • Trigger «جادوی پنهان» است: کندی INSERTها، اثرات زنجیره‌ای، و Eloquent Eventها از آن خبر ندارند.
-- نمونه‌ی trigger برای audit در MySQL
CREATE TRIGGER trg_price_audit
AFTER UPDATE ON products
FOR EACH ROW
BEGIN
    IF NEW.price <> OLD.price THEN
        INSERT INTO price_history (product_id, old_price, new_price, changed_at)
        VALUES (OLD.id, OLD.price, NEW.price, NOW());
    END IF;
END;

پاسخ متعادل: «در معماری‌های مدرن Laravel، منطق کسب‌وکار در لایه‌ی برنامه نگه داشته می‌شود (تست‌پذیر، نسخه‌بندی‌شده، scale افقی ساده). از Procedure/Trigger فقط در موارد محدود استفاده می‌کنم: audit و قیود یکپارچگی که باید مستقل از برنامه تضمین شوند، یا پردازش داده‌ی بسیار حجیم که انتقالش به برنامه گران است.» در Laravel معادل‌های برنامه‌ای: Model Observer/Event، Job، و constraintهای دیتابیس (FK، UNIQUE، CHECK).

انواع Partitioning

RANGE
بر اساس بازه (معمولاً تاریخ). عالی برای داده‌ی زمانی: archive یا حذف یک ماه کامل با DROP PARTITION در کسری از ثانیه به‌جای DELETE میلیون‌ها سطر.
LIST
بر اساس مجموعه‌ی مقادیر گسسته (مثلاً region یا country).
HASH / KEY

-- MySQL: پارتیشن‌بندی ماهانه‌ی جدول لاگ
CREATE TABLE access_logs (
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    created_at DATETIME NOT NULL,
    user_id    BIGINT UNSIGNED,
    path       VARCHAR(255),
    PRIMARY KEY (id, created_at)          -- ستون partition باید در همه‌ی کلیدهای یکتا باشد
)
PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2026_10 VALUES LESS THAN ('2026-11-01'),
    PARTITION p2026_11 VALUES LESS THAN ('2026-12-01'),
    PARTITION pmax     VALUES LESS THAN (MAXVALUE)
);

-- partition pruning: فقط p2026_11 خوانده می‌شود
EXPLAIN SELECT * FROM access_logs WHERE created_at >= '2026-11-05' AND created_at < '2026-11-06';

-- حذف داده‌ی قدیمی: آنی
ALTER TABLE access_logs DROP PARTITION p2026_10;
-- PostgreSQL: declarative partitioning
CREATE TABLE events (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    created_at timestamptz NOT NULL,
    payload    jsonb

Partitioning جایگزین ایندکس خوب نیست.

چالش‌های Sharding

  • Cross-shard query/JOIN: باید scatter-gather در برنامه انجام شود؛ گزارش‌گیری را به data warehouse منتقل کنید.
  • تراکنش توزیع‌شده: 2PC یا Saga؛ بهتر است مدل داده طوری باشد که تراکنش‌ها داخل یک shard بمانند.
  • ID یکتای سراسری: auto-increment هر shard تکراری می‌شود ⇒ UUIDv7، ULID، Snowflake ID.
  • Resharding و جابه‌جایی داده بدون downtime.
  • Hot shard: یک tenant/کاربر خیلی بزرگ (celebrity problem).
  • ابزارها: Vitess (MySQL)، Citus (PostgreSQL)، یا دیتابیس‌های توزیع‌شده‌ی بومی.

Sharding آخرین گزینه است. مسیر معمول: بهینه‌سازی query و ایندکس ⇒ cache ⇒ read replica ⇒ scale عمودی ⇒ partitioning و archive ⇒ functional split ⇒ sharding. در پاسخ تشریحی این ترتیب و دلیل هزینه‌ی بالای sharding (از دست رفتن JOIN، تراکنش، و پیچیدگی عملیاتی) را ذکر کنید.

Replication و Read Replica

Replication یعنی نگه‌داری کپی داده روی چند سرور. اهداف: (۱) Scale خواندن با read replica؛ (۲) High Availability (replica آماده‌ی جایگزینی primary)؛ (۳) فاصله‌ی جغرافیایی کمتر تا کاربر؛ (۴) اجرای گزارش‌های سنگین و backup روی replica بدون فشار به primary.

  • PostgreSQL: Streaming Replication فیزیکی (ارسال WAL به standby)؛ standby یک کپی بایت‌به‌بایت کل cluster است. Logical Replication (publication/subscription) برای replicate کردن جداول انتخابی، بین نسخه‌های مختلف یا برای upgrade کم‌downtime.

Replication Lag و Read-Your-Writes

در replication غیرهمگام، replica از primary عقب است. سناریوی کلاسیک: کاربر پروفایلش را ویرایش می‌کند (نوشتن روی primary)، redirect می‌شود و صفحه‌ی پروفایل از replica خوانده می‌شود ⇒ مقدار قدیمی را می‌بیند و فکر می‌کند ذخیره نشده. این نقض تضمین Read-Your-Writes است.

علل lag: نوشتن‌های سنگین/تراکنش بزرگ روی primary، applier تک‌thread، replica ضعیف‌تر یا زیر بار گزارش، شبکه، و queryهای طولانی روی replica.

راه‌حل‌ها

  1. Sticky در محدوده‌ی request: پس از نوشتن، بقیه‌ی خواندن‌های همان request از primary (گزینه‌ی sticky در Laravel).
  2. Sticky مبتنی بر زمان در session: تا N ثانیه پس از نوشتن (بیشتر از lag معمول)، خواندن‌های آن کاربر از primary؛ مثلاً با یک flag در session/cookie.
  3. Position/GTID tracking: پس از نوشتن، GTID یا LSN را نگه دارید و فقط از replicaای بخوانید که به آن رسیده باشد (WAIT_FOR_EXECUTED_GTID_SET در MySQL؛ مقایسه‌ی pg_last_wal_replay_lsn() در PostgreSQL).
  4. خواندن‌های حساس همیشه از primary (مثلاً موجودی کیف پول، وضعیت پرداخت).
  5. به‌روزرسانی خوش‌بینانه‌ی UI با داده‌ای که کلاینت خودش فرستاده.

تضمین دیگر: Monotonic Reads؛ کاربر نباید با رفرش صفحه، داده‌ی «عقب‌تر» از قبل ببیند (چون این بار به replica با lag بیشتر رفته). راه‌حل: هر کاربر را همیشه به یک replica ثابت (مثلاً با hash شناسه‌ی کاربر) بفرستید.

HA، Failover، CAP/PACELC و Connection Pooling

High Availability و Failover

HA یعنی سیستم با از کار افتادن یک جزء همچنان سرویس بدهد. در دیتابیس، یعنی primary جایگزین داشته باشد و جابه‌جایی (failover) سریع و امن انجام شود. دو معیار کلیدی:

RPO (Recovery Point Objective)
حداکثر داده‌ای که از دست دادنش قابل قبول است (بر حسب زمان). async ⇒ RPO چند ثانیه؛ sync/semi-sync ⇒ نزدیک صفر.
RTO (Recovery Time Objective)

  • Split-brain: اگر primary قدیمی فقط از شبکه جدا شده باشد (نه خاموش) و دوباره بالا بیاید، دو primary هم‌زمان نوشتن می‌پذیرند ⇒ داده‌ی متناقض. راه‌حل: quorum (تصمیم با اکثریت، تعداد نود فرد)، و fencing (STONITH، خاموش کردن یا read-only کردن اجباری primary قدیمی).
  • در failover با replication غیرهمگام، تراکنش‌هایی که به replica نرسیده‌اند از دست می‌روند؛ RPO را صریحاً بپذیرید یا semi-sync بگذارید.
  • برنامه باید با قطعی کوتاه کنار بیاید: retry برای خطای اتصال، timeout معقول، و idempotency در عملیات.
  • failover را تمرین کنید؛ failover که هرگز تست نشده، در لحظه‌ی بحران کار نمی‌کند.

CAP Theorem

در یک سیستم داده‌ی توزیع‌شده، هنگام وقوع Partition شبکه (قطع ارتباط بین نودها)، نمی‌توان هم‌زمان هر دوی این‌ها را داشت:

  • Consistency (C): هر خواندن، آخرین نوشتن را می‌بیند (linearizability).
  • Availability (A): هر درخواست به نود سالم، پاسخ (غیرخطا) می‌گیرد.

چون partition در شبکه‌ی واقعی اجتناب‌ناپذیر است، «انتخاب ۲ از ۳» گمراه‌کننده است؛ انتخاب واقعی این است که هنگام partition، سیستم CP باشد (درخواست‌هایی را که نمی‌تواند سازگار پاسخ دهد رد کند) یا AP (پاسخ بدهد، شاید با داده‌ی کهنه، و بعداً همگرا شود).

PACELC

توسعه‌ی CAP توسط Daniel Abadi: if Partition ⇒ A or C; Else ⇒ Latency or Consistency. یعنی حتی وقتی شبکه سالم است، replication همگام (consistency بیشتر) هزینه‌ی latency دارد. این برای اکثر روزهای عمر سیستم (که partition ندارد) مهم‌تر از CAP است.

Connection Pooling

ساختن اتصال دیتابیس گران است (TCP handshake، TLS، احراز هویت، تخصیص حافظه). همچنین هر اتصال روی سرور منبع مصرف می‌کند: MySQL برای هر اتصال یک thread، و PostgreSQL برای هر اتصال یک process کامل می‌سازد؛ به همین دلیل PostgreSQL به تعداد اتصال زیاد حساس‌تر است.

  • PHP-FPM: مدل share-nothing؛ هر worker در هر request اتصال جدید باز می‌کند (مگر با PDO::ATTR_PERSISTENT که اتصال را در همان process نگه می‌دارد). حداکثر اتصال ≈ تعداد سرورهای app × pm.max_children (+ queue workerها)؛ این عدد به‌راحتی از max_connections دیتابیس بیشتر می‌شود.
  • Laravel Octane و queue workerها اتصال را بین requestها/jobها نگه می‌دارند (مثل pool کوچک per-worker)؛ مراقب اتصال‌های مرده (MySQL server has gone away) و تنظیم timeout باشید.
  • Pooler خارجی: PgBouncer برای PostgreSQL، ProxySQL برای MySQL (که read/write split و query routing هم دارد). هزاران اتصال کلاینت روی ده‌ها اتصال واقعی multiplex می‌شوند.

Point-in-Time Recovery (PITR)

PITR یعنی بازگرداندن دیتابیس به هر لحظه‌ی دلخواه؛ مثلاً یک ثانیه قبل از اجرای اشتباه DELETE FROM orders بدون WHERE. اصل کار: آخرین backup کامل + replay لاگ تغییرات تا لحظه‌ی مورد نظر.

  full backup (یکشنبه 02:00)         حادثه: چهارشنبه 14:32:10
        │                                     │
        ▼                                     ▼
  ──────■─────────────────────────────────────✗──────────► زمان
        └──── binlog / WAL archive ──────────►┘
  restore = full backup  +  replay لاگ‌ها تا 14:32:09 (stop-datetime / recovery_target_time)
  • MySQL: restore بکاپ کامل، سپس mysqlbinlog --start-position=… --stop-datetime="2026-11-04 14:32:09" binlog.* | mysql. binlogها باید فعال باشند، نگه داشته شوند (binlog_expire_logs_seconds) و ترجیحاً به جای دیگری کپی شوند.
  • PostgreSQL: archive_mode=on و archive_command (یا ابزاری مثل pgBackRest) فایل‌های WAL را آرشیو می‌کند؛ هنگام restore، base backup + restore_command + recovery_target_time.

اصول یک استراتژی خوب

  1. قانون 3-2-1: سه نسخه، روی دو نوع رسانه، یک نسخه خارج از محل (offsite / region دیگر). در برابر ransomware، یک نسخه‌ی immutable یا جدا از شبکه.
  2. Backup تست‌نشده، backup نیست: restore دوره‌ای و خودکار در محیط جدا و اندازه‌گیری زمان آن (RTO واقعی).
  3. Replication جایگزین backup نیست: خطای انسانی و داده‌ی خراب هم replicate می‌شود. (replica با تأخیر عمدی، مثل SOURCE_DELAY در MySQL، می‌تواند لایه‌ی محافظ اضافی باشد.)
  4. ترکیب: full هفتگی + incremental/differential روزانه (XtraBackup، pgBackRest) + آرشیو پیوسته‌ی binlog/WAL.
  5. رمزنگاری backup، کنترل دسترسی، و پایش موفقیت/شکست jobها.
  6. backup را از replica بگیرید تا بار primary کم شود (با در نظر گرفتن lag).
  7. RPO/RTO را با کسب‌وکار توافق کنید و استراتژی را از آن استخراج کنید، نه برعکس.

سوال سناریویی رایج: «کسی ساعت ۱۴:۳۲ تمام سفارش‌ها را حذف کرد. چه می‌کنید؟» پاسخ: (۱) جلوگیری از آسیب بیشتر (متوقف کردن نوشتن یا شناسایی منبع)؛ (۲) پیدا کردن دقیق موقعیت حادثه در binlog/WAL؛ (۳) restore آخرین full backup روی سرور جداگانه؛ (۴) replay لاگ‌ها تا درست قبل از حادثه؛ (۵) استخراج جدول/سطرهای از دست رفته و بازگرداندن آن‌ها به production (یا جایگزینی کامل، بسته به شرایط)؛ (۶) post-mortem و جلوگیری (دسترسی‌ها، sql_safe_updates، review).

  • تصویر لحظه‌ای کل داده در فواصل زمانی (fork + نوشتن فایل).
  • فایل فشرده، restart سریع، مناسب backup.
  • از دست رفتن داده از آخرین snapshot تا crash.
  • fork روی داده‌ی بزرگ ممکن است مکث و مصرف حافظه‌ی اضافه ایجاد کند.

AOF (Append Only File)

  • هر فرمان نوشتنی به فایل اضافه می‌شود؛ appendfsync: always (امن و کند)، everysec (پیش‌فرض؛ حداکثر حدود ۱ ثانیه از دست رفتن)، no.
  • durability بهتر، فایل بزرگ‌تر (با rewrite فشرده می‌شود).
  • در عمل اغلب RDB و AOF با هم استفاده می‌شوند.

Redis به‌عنوان cache باید maxmemory و maxmemory-policy مناسب (مثلاً allkeys-lru) داشته باشد؛ اما برای صف و lock، policyای که کلیدها را حذف کند خطرناک است (job گم می‌شود). برای همین معمولاً Redis cache و Redis queue را جدا می‌کنند. همچنین replication در Redis غیرهمگام است؛ پس داده‌ی مالی حساس را فقط در Redis نگه ندارید.

سوالات تشریحی

ویژگی‌های ACID را تعریف کنید و توضیح دهید دیتابیس هر کدام را با چه مکانیزمی تضمین می‌کند.

تعریف: ACID مجموعه‌ی تضمین‌هایی است که یک دیتابیس تراکنشی درباره‌ی هر Transaction (واحد منطقی کار) می‌دهد.

  • Atomicity: همه‌ی عملیات تراکنش یا با هم اعمال می‌شوند یا هیچ‌کدام. مکانیزم: undo log در InnoDB که نسخه‌ی قبلی را نگه می‌دارد و در rollback اعمال می‌شود؛ در PostgreSQL نسخه‌های ساخته‌شده توسط تراکنش abort شده هرگز visible نمی‌شوند.
  • Consistency: تراکنش دیتابیس را از یک حالت معتبر به حالت معتبر دیگر می‌برد. مکانیزم: constraintها (PK، FK، UNIQUE، CHECK، NOT NULL) و بخشی هم منطق صحیح برنامه؛ تنها ویژگی‌ای است که مسئولیتش مشترک است.
  • Isolation: تراکنش‌های هم‌زمان اثر ناخواسته روی هم نگذارند. مکانیزم: MVCC برای خواندن، قفل‌های سطری (و در InnoDB gap/next-key lock) برای نوشتن، و در PostgreSQL Serializable، الگوریتم SSI. میزان آن با Isolation Level تنظیم می‌شود.
  • Durability: پس از COMMIT، تغییرات با crash از بین نمی‌رود. مکانیزم: Write-Ahead Logging (redo log در InnoDB، WAL در PostgreSQL): تغییر ابتدا به‌صورت ترتیبی در لاگ نوشته و fsync می‌شود و پس از crash، لاگ replay می‌شود. در MySQL تنظیم innodb_flush_log_at_trx_commit=1 و sync_binlog=1 برای durability کامل لازم است.

نکته‌ی تکمیلی: Consistency در ACID با Consistency در CAP (linearizability) متفاوت است. همچنین durability روی یک نود، در برابر از دست رفتن خود دیسک یا سرور محافظت نمی‌کند؛ برای آن replication و backup لازم است.

مصالحه: کاهش durability (مثلاً flush هر ثانیه) throughput نوشتن را بالا می‌برد ولی خطر از دست رفتن تراکنش‌های آخرین ثانیه را می‌پذیرد؛ برای داده‌ی مالی قابل قبول نیست.

سطوح ایزولاسیون تراکنش را نام ببرید و با ذکر ناهنجاری‌هایی که هر سطح مجاز می‌داند مقایسه کنید. پیش‌فرض MySQL و PostgreSQL چیست؟

تعریف: Isolation Level تعیین می‌کند یک تراکنش تا چه حد اثر تراکنش‌های هم‌زمان را می‌بیند؛ مصالحه‌ای بین درستی و هم‌زمانی.

  • Read Uncommitted: حتی داده‌ی commit‌نشده دیده می‌شود ⇒ Dirty Read. تقریباً هرگز استفاده نمی‌شود.
  • Read Committed: فقط داده‌ی commit‌شده؛ ولی هر statement snapshot تازه دارد ⇒ Non-Repeatable Read و Phantom ممکن است.
  • Repeatable Read: کل تراکنش یک snapshot می‌بیند ⇒ خواندن مجدد یک سطر همان نتیجه را می‌دهد. در استاندارد phantom مجاز است؛ در PostgreSQL (Snapshot Isolation) phantom رخ نمی‌دهد و در InnoDB برای خواندن snapshot رخ نمی‌دهد و برای locking read با next-key lock جلوگیری می‌شود.
  • Serializable: نتیجه معادل یک اجرای سریالی است؛ همه‌ی ناهنجاری‌ها از جمله Write Skew حذف می‌شوند.

پیش‌فرض‌ها: MySQL InnoDB ⇒ REPEATABLE READ؛ PostgreSQL ⇒ READ COMMITTED.

تفاوت پیاده‌سازی: Serializable در InnoDB قفل‌محور است (SELECTها shared lock می‌گیرند) و در PostgreSQL مبتنی بر SSI است که قفل خواندن نمی‌گذارد و در صورت تشخیص تداخل، تراکنش را با خطای 40001 abort می‌کند؛ پس برنامه باید retry داشته باشد. در RR مربوط به MySQL، lost update در الگوی «SELECT ساده سپس UPDATE با مقدار محاسبه‌شده در برنامه» ممکن است، در حالی که PostgreSQL در RR آن را با خطا تشخیص می‌دهد.

جمع‌بندی: سطح بالاتر ⇒ ناهنجاری کمتر، ولی قفل/abort بیشتر و throughput کمتر. معمولاً سطح پیش‌فرض + قفل صریح یا عملیات atomic در نقاط حساس انتخاب عملی است.

Write Skew چیست؟ چرا Snapshot Isolation (مثلاً Repeatable Read در PostgreSQL) جلوی آن را نمی‌گیرد و چه راه‌حل‌هایی دارد؟

تعریف: Write Skew ناهنجاری‌ای است که در آن دو تراکنش هم‌زمان یک شرط مشترک را می‌خوانند، هر کدام بر اساس نتیجه‌ی آن تصمیم می‌گیرد و سطرهای متفاوتی را تغییر می‌دهد؛ هر تراکنش به‌تنهایی درست است، اما ترکیب آن‌ها یک invariant را نقض می‌کند.

مثال: قانون «حداقل یک پزشک در هر شیفت on-call باشد». Ali و Sara هر دو on-call هستند. هر دو هم‌زمان درخواست مرخصی می‌دهند؛ هر تراکنش می‌شمارد «۲ نفر on-call هستند، پس من می‌توانم بروم» و سطر خودش را update می‌کند. نتیجه: صفر پزشک.

چرا Snapshot Isolation جلویش را نمی‌گیرد: SI فقط تداخل نوشتن-نوشتن روی یک سطر را تشخیص می‌دهد (first-committer-wins). اینجا هر تراکنش سطر متفاوتی نوشته و هر دو از snapshot خودشان خوانده‌اند؛ تداخل از نوع خواندن-نوشتن است که SI ردیابی نمی‌کند. سایر مثال‌ها: رزرو دو جلسه در یک اتاق و زمان، انتخاب username تکراری بدون UNIQUE، خرج کردن هم‌زمان از دو حساب مرتبط با سقف مشترک.

راه‌حل‌ها:

  • Serializable: در PostgreSQL، SSI وابستگی خطرناک را تشخیص داده و یکی را abort می‌کند (با retry در برنامه).
  • قفل صریح روی سطرهای شرط: SELECT … FROM doctors WHERE shift_id = 7 AND on_call FOR UPDATE؛ تراکنش دوم منتظر می‌ماند و پس از آن، تعداد به‌روز را می‌بیند (در InnoDB current read).
  • Materializing conflicts: اگر سطری برای قفل وجود ندارد (مثلاً رزرو بازه‌ی خالی)، یک سطر مشترک بسازید/قفل کنید (مثلاً سطر rooms یا shifts).
  • Constraint در صورت امکان: UNIQUE، یا در PostgreSQL exclusion constraint برای بازه‌های زمانی هم‌پوشان.

نکته: این مثال نشان می‌دهد «Repeatable Read» به معنای «امن برای همه‌ی invariantها» نیست.

MVCC چیست و چه مشکلی را حل می‌کند؟ پیاده‌سازی آن در InnoDB و PostgreSQL را مقایسه کنید و توضیح دهید چرا تراکنش‌های طولانی برای هر دو مضرند.

تعریف: Multi-Version Concurrency Control روشی است که دیتابیس از هر سطر چند نسخه نگه می‌دارد تا هر تراکنش یک snapshot سازگار از داده‌های commit‌شده ببیند.

مشکلی که حل می‌کند: در کنترل هم‌زمانی صرفاً قفل‌محور، خواننده‌ها باید برای نویسنده‌ها صبر کنند و برعکس. در MVCC خواندن، نوشتن را بلاک نمی‌کند و نوشتن، خواندن را؛ فقط دو نوشتن روی یک سطر با قفل هماهنگ می‌شوند. نتیجه: هم‌زمانی بسیار بالاتر برای بارهای وب که عمدتاً خواندنی‌اند.

InnoDB: نسخه‌ی جاری در جای خود در clustered index به‌روز می‌شود؛ سطر ستون‌های مخفی DB_TRX_ID و DB_ROLL_PTR دارد و نسخه‌های قبلی از زنجیره‌ی undo log بازسازی می‌شوند. هر snapshot یک read view است. purge thread undoهای غیرلازم را پاک می‌کند.

PostgreSQL: هر UPDATE یک tuple جدید در heap می‌سازد؛ tupleها xmin/xmax دارند و visibility با مقایسه‌ی آن‌ها با snapshot تعیین می‌شود. tupleهای مرده با VACUUM پاک می‌شوند.

چرا تراکنش طولانی مضر است: تا وقتی تراکنشی با snapshot قدیمی باز است، دیتابیس نمی‌تواند نسخه‌هایی را که ممکن است آن تراکنش ببیند پاک کند. در InnoDB undo و history list length رشد می‌کند و خواندن‌ها برای پیمایش زنجیره‌ی طولانی undo کند می‌شوند؛ در PostgreSQL VACUUM نمی‌تواند dead tupleها را پاک کند و جدول bloat می‌شود. علاوه بر این، قفل‌های گرفته‌شده هم تا پایان تراکنش می‌مانند. پس: تراکنش کوتاه، بدون I/O خارجی، و پایش تراکنش‌های باز (information_schema.innodb_trx، pg_stat_activity با وضعیت idle in transaction).

Optimistic Locking و Pessimistic Locking را تعریف و مقایسه کنید. در Laravel هر کدام را چگونه پیاده‌سازی می‌کنید و در چه شرایطی کدام را انتخاب می‌کنید؟

Pessimistic Locking: فرض می‌کند تداخل محتمل است؛ پیش از تغییر، سطر را قفل انحصاری می‌کند تا تراکنش‌های دیگر تا پایان تراکنش منتظر بمانند. SQL: SELECT … FOR UPDATE؛ Laravel: lockForUpdate() (و sharedLock() برای قفل اشتراکی) که حتماً داخل تراکنش باید باشد.

Optimistic Locking: فرض می‌کند تداخل نادر است؛ قفلی نگه نمی‌دارد و هنگام نوشتن بررسی می‌کند داده از زمان خواندن تغییر نکرده باشد، معمولاً با ستون version (یا updated_at): UPDATE … SET …, version = version + 1 WHERE id = ? AND version = ?. اگر affected rows صفر بود ⇒ conflict ⇒ خطای 409 یا retry.

<?php
// Pessimistic
DB::transaction(function () use ($id) {
    $w = Wallet::whereKey($id)->lockForUpdate()->firstOrFail();
    $w->balance -= 100;
    $w->save();
});

// Optimistic
$ok = Wallet::whereKey($id)->where('version', $version)
    ->update(['balance' => $new, 'version' => DB::raw('version + 1')]);
if (! $ok) { abort(409); }

معیار انتخاب:

  • میزان تداخل: تداخل بالا (موجودی کالای پرفروش در حراج) ⇒ pessimistic (یا بهتر، UPDATE atomic)، چون optimistic به retry storm می‌رسد. تداخل پایین (ویرایش پروفایل) ⇒ optimistic.
  • طول عملیات: اگر بین خواندن و نوشتن تعامل کاربر هست (فرم چنددقیقه‌ای) فقط optimistic ممکن است؛ قفل دیتابیس را نمی‌توان بین دو HTTP request نگه داشت. در API می‌توان version را با ETag/If-Match منتقل کرد.
  • Deadlock: pessimistic ممکن است deadlock بسازد؛ optimistic نه.
  • هزینه‌ی کار هدررفته: در optimistic کار انجام‌شده هنگام conflict دور ریخته می‌شود.

نکته: اگر منطق فقط کاهش/افزایش یک عدد است، ساده‌ترین و مقیاس‌پذیرترین راه، UPDATE atomic شرطی است: UPDATE … SET stock = stock - 1 WHERE id = ? AND stock > 0.

کد زیر برای ثبت سفارش نوشته شده و گاهی موجودی منفی می‌شود یا بیش از موجودی فروخته می‌شود. مشکل چیست و چگونه اصلاحش می‌کنید؟ 
<?php
public function order(int $productId, int $qty)
{
    $product = Product::find($productId);
    if ($product->stock >= $qty) {
        $product->stock = $product->stock - $qty;
        $product->save();
        Order::create(['product_id' => $productId, 'qty' => $qty]);
    }
}

مشکل: Race Condition از نوع Lost Update (check-then-act). دو request هم‌زمان هر دو stock = 1 را می‌خوانند، هر دو شرط را برقرار می‌بینند، هر دو stock = 0 را ذخیره می‌کنند و دو سفارش ثبت می‌شود (oversell). چون مقدار جدید در PHP محاسبه شده و به‌صورت مقدار مطلق نوشته می‌شود، نوشتن دوم نوشتن اول را بی‌اثر می‌کند. مشکل دوم: به‌روزرسانی موجودی و ساخت سفارش در یک تراکنش نیستند؛ اگر Order::create شکست بخورد، موجودی کم شده ولی سفارشی نیست. همچنین find برای محصول ناموجود null برمی‌گرداند.

اصلاح ۱: UPDATE atomic شرطی (بهترین برای این مورد):

<?php
DB::transaction(function () use ($productId, $qty) {
    $affected = Product::whereKey($productId)
        ->where('stock', '>=', $qty)
        ->decrement('stock', $qty);   // یک statement؛ دیتابیس row lock می‌گیرد

    if ($affected === 0) {
        throw new OutOfStockException();
    }
    Order::create(['product_id' => $productId, 'qty' => $qty]);
});

اصلاح ۲: قفل pessimistic وقتی منطق پیچیده‌تر است (چند شرط، قیمت، تخفیف):

<?php
DB::transaction(function () use ($productId, $qty) {
    $p = Product::whereKey($productId)->lockForUpdate()->firstOrFail();
    if ($p->stock < $qty) throw new OutOfStockException();
    $p->decrement('stock', $qty);
    Order::create([...]);
}, attempts: 3);

لایه‌ی دفاعی اضافه: constraint در دیتابیس: ستون UNSIGNED در MySQL یا CHECK (stock >= 0) (در MySQL 8.0.16+ اعمال می‌شود) تا حتی باگ برنامه هم نتواند موجودی منفی بسازد. برای حراج‌های بسیار پرترافیک، می‌توان موجودی را در Redis با DECRBY atomic یا Lua script رزرو کرد و سپس به‌صورت async در دیتابیس ثبت نمود. همچنین برای جلوگیری از ثبت دوباره با double-click، idempotency key روی request.

Deadlock در دیتابیس چگونه رخ می‌دهد؟ InnoDB و PostgreSQL چگونه آن را تشخیص می‌دهند و شما به‌عنوان توسعه‌دهنده چه راهکارهایی برای پیشگیری و مدیریت آن دارید؟

تعریف: Deadlock وضعیتی است که دو یا چند تراکنش هر یک قفلی را نگه داشته‌اند و منتظر قفلی هستند که دیگری نگه داشته؛ یعنی چرخه در wait-for graph. هیچ‌کدام بدون مداخله پیش نمی‌روند.

مثال کلاسیک: انتقال پول هم‌زمان A⇒B و B⇒A. تراکنش اول سطر A را قفل می‌کند، دومی سطر B را؛ سپس اولی منتظر B و دومی منتظر A می‌ماند. منبع رایج دیگر در InnoDB: gap lock‌ها در الگوی «SELECT … FOR UPDATE روی سطر ناموجود و سپس INSERT» توسط دو تراکنش هم‌زمان؛ gap lockها با هم سازگارند، ولی insert intention هر کدام با gap lock دیگری تداخل دارد.

تشخیص:

  • InnoDB: تشخیص فوری چرخه (innodb_deadlock_detect) و rollback تراکنش «کوچک‌تر» با خطای 1213. جزئیات در SHOW ENGINE INNODB STATUS و با innodb_print_all_deadlocks در error log. انتظار بدون چرخه به innodb_lock_wait_timeout (خطای 1205) می‌رسد.
  • PostgreSQL: پس از deadlock_timeout (پیش‌فرض ۱ ثانیه) گراف بررسی و یک تراکنش با 40P01 abort می‌شود.

پیشگیری:

  1. ترتیب ثابت قفل‌گیری (مثلاً مرتب‌سازی idها) تا Circular Wait رخ ندهد.
  2. تراکنش کوتاه، بدون فراخوانی شبکه/API داخل آن.
  3. ایندکس روی ستون‌های شرط UPDATE/DELETE/FOR UPDATE تا سطرهای کمتری قفل شود.
  4. استفاده از upsert (ON DUPLICATE KEY / ON CONFLICT) به‌جای الگوی select-then-insert.
  5. در صورت قابل قبول بودن، READ COMMITTED در MySQL برای حذف gap lockها.
  6. شکستن batchهای بزرگ به دسته‌های کوچک.

مدیریت: deadlock در سیستم پرهم‌زمان اجتناب‌ناپذیر است؛ باید آن را retry کرد. در Laravel: DB::transaction($callback, attempts: 3) که روی خطای deadlock کل closure را دوباره اجرا می‌کند؛ پس کد داخل closure باید عوارض جانبی خارجی نداشته باشد. در کنار آن، پایش و لاگ deadlockها برای پیدا کردن الگوی تکراری.

Gap Lock و Next-Key Lock در InnoDB چه هستند، چه مشکلی را حل می‌کنند و چه هزینه‌ای دارند؟

تعریف: قفل‌های InnoDB روی رکوردهای ایندکس گرفته می‌شوند.

  • Record Lock: قفل روی یک رکورد ایندکس.
  • Gap Lock: قفل روی فاصله‌ی بین رکوردهای ایندکس؛ مانع درج سطر جدید در آن بازه می‌شود (gap lockها با هم تداخل ندارند).
  • Next-Key Lock: record lock + gap lock قبل از آن رکورد؛ قفل پیش‌فرض InnoDB برای اسکن ایندکس در REPEATABLE READ.

چه مشکلی را حل می‌کند: Phantom در locking readها. اگر تراکنشی SELECT * FROM orders WHERE amount BETWEEN 100 AND 200 FOR UPDATE بزند، فقط قفل کردن سطرهای موجود کافی نیست؛ تراکنش دیگری می‌تواند سطر جدیدی با amount = 150 درج کند و اجرای دوم همان query نتیجه‌ی متفاوت بدهد. next-key lock بازه را قفل می‌کند تا insert منتظر بماند. این برای درستی replication مبتنی بر statement در گذشته هم مهم بود.

ایندکس: 100   180   250
T1: … WHERE amount BETWEEN 100 AND 200 FOR UPDATE
    قفل: رکوردهای 100 و 180 و gapها تا 250
T2: INSERT amount=150 ⏳   INSERT amount=300 ✓

هزینه‌ها:

  • هم‌زمانی کمتر: insertهای بی‌ربط در بازه هم منتظر می‌مانند.
  • Deadlock: الگوی رایج «SELECT … WHERE id = 7 FOR UPDATE (سطر وجود ندارد ⇒ gap lock) سپس INSERT» توسط دو تراکنش، deadlock می‌سازد.
  • بدون ایندکس مناسب، اسکن کامل یعنی قفل شدن تقریباً کل جدول و gapهایش.

کنترل: با ایندکس یکتا و شرط تساوی روی سطر موجود فقط record lock گرفته می‌شود. در سطح READ COMMITTED gap lock برای جست‌وجوها غیرفعال است (به‌جز بررسی FK و duplicate key)؛ بسیاری از سیستم‌های پرنوشتن به همین دلیل RC را انتخاب می‌کنند و phantom را در صورت لزوم با طراحی دیگر (UNIQUE constraint، upsert) کنترل می‌کنند.

تفاوت Clustered Index و Secondary Index را در InnoDB توضیح دهید. چرا استفاده از UUID نسخه‌ی ۴ به‌عنوان Primary Key در جداول بزرگ InnoDB توصیه نمی‌شود؟

Clustered Index: در InnoDB جدول خودش یک B+Tree مرتب بر اساس Primary Key است؛ برگ‌های این درخت کل سطر را نگه می‌دارند. هر جدول دقیقاً یک clustered index دارد (اگر PK نباشد، اولین UNIQUE NOT NULL یا یک row id مخفی). جست‌وجو با PK یک پیمایش درخت است و range scan روی PK داده‌های فیزیکی مجاور را می‌خواند.

Secondary Index: B+Tree جداگانه‌ای که برگ‌هایش مقدار ستون‌های ایندکس + مقدار PK را دارند. جست‌وجو دو مرحله دارد: پیدا کردن PK در secondary، سپس پیمایش clustered index برای سطر کامل (مگر اینکه ایندکس covering باشد).

idx_email: 'a@x' → PK 42  ──►  PRIMARY: 42 → [کل سطر]

مشکلات UUIDv4 به‌عنوان PK:

  1. درج تصادفی: چون جدول به ترتیب PK ذخیره می‌شود، هر insert در جای تصادفی درخت انجام می‌شود ⇒ page split مکرر، صفحه‌های نیمه‌پر (fragmentation)، و نیاز به نگه‌داشتن تقریباً کل ایندکس در buffer pool. با AUTO_INCREMENT همه‌ی insertها به انتهای درخت می‌روند.
  2. اندازه: CHAR(36) (۳۶ بایت یا بیشتر بسته به charset) در برابر BIGINT ۸ بایتی؛ و چون PK در همه‌ی secondary indexها تکرار می‌شود، کل ایندکس‌ها بزرگ‌تر و cache کم‌اثرتر می‌شود.
  3. مقایسه‌ی کندتر رشته‌ها و collation.

راه‌حل‌ها: PK عددی داخلی (BIGINT AUTO_INCREMENT) و یک ستون UUID جداگانه با UNIQUE index برای شناسه‌ی عمومی در API؛ یا UUIDهای زمان‌مرتب (UUIDv7، ULID) که تقریباً ترتیبی درج می‌شوند، ذخیره‌شده به‌صورت BINARY(16). UUID مزایای خودش را دارد: تولید در کلاینت/سرویس بدون رفت‌وبرگشت، عدم افشای تعداد رکوردها، و ادغام ساده‌ی داده بین shardها.

مقایسه با PostgreSQL: جداول PostgreSQL heap هستند و clustered نیستند؛ پس جابه‌جایی سطرها رخ نمی‌دهد، اما خود ایندکس B-Tree روی UUID تصادفی همچنان پراکندگی و cache miss بیشتری دارد.

Composite Index و قانون Leftmost Prefix را توضیح دهید. برای query زیر چه ایندکسی طراحی می‌کنید و چرا؟ SELECT id, total FROM orders WHERE user_id = ? AND status = ? AND created_at >= ? ORDER BY created_at DESC LIMIT 20

تعریف: Composite Index ایندکسی روی چند ستون است که مقادیر را به‌صورت لغت‌نامه‌ای (lexicographic) مرتب می‌کند: ابتدا ستون اول، در صورت برابری ستون دوم و الی آخر.

Leftmost Prefix: ایندکس (a, b, c) فقط برای شرط‌هایی قابل استفاده برای seek است که از چپ‌ترین ستون‌ها شروع شوند: (a)، (a,b)، (a,b,c). شرط فقط روی b یا c نمی‌تواند از آن استفاده کند (مثل اینکه دفترچه‌ی تلفن مرتب‌شده بر اساس نام خانوادگی را با نام کوچک جست‌وجو کنید). همچنین پس از اولین شرط range، ستون‌های بعدی برای seek استفاده نمی‌شوند (فقط برای فیلتر، از طریق Index Condition Pushdown). ترتیب ستون‌ها در WHERE مهم نیست؛ ترتیب در تعریف ایندکس مهم است.

طراحی برای query داده‌شده:

CREATE INDEX idx_orders_user_status_created
    ON orders (user_id, status, created_at);
  • user_id و status شرط تساوی دارند ⇒ اول می‌آیند؛ با هم بازه‌ی کوچکی از ایندکس را مشخص می‌کنند.
  • created_at هم شرط range و هم ORDER BY است ⇒ آخر؛ داخل هر (user_id, status) مقادیر created_at مرتب‌اند، پس هم range seek انجام می‌شود، هم filesort حذف می‌شود (پیمایش معکوس برای DESC) و LIMIT 20 بعد از ۲۰ سطر متوقف می‌شود.
  • ستون‌های id (PK داخل secondary در InnoDB) و total: اگر total را هم به انتهای ایندکس اضافه کنیم (user_id, status, created_at, total)، ایندکس covering می‌شود و رجوع به جدول حذف می‌گردد (Using index). این را بر اساس اهمیت query و هزینه‌ی نوشتن تصمیم می‌گیریم.

چرا ترتیب دیگر بد است: (created_at, user_id, status) ⇒ range روی ستون اول، پس user_id و status فقط فیلترند و تعداد زیادی رکورد اسکن می‌شود. (status, user_id, created_at) هم برای این query درست کار می‌کند (هر دو تساوی‌اند)، اما user_id در اول ایندکس، queryهای دیگر مثل «همه‌ی سفارش‌های کاربر» را هم پوشش می‌دهد؛ پس ترتیب بین ستون‌های تساوی را بر اساس queryهای دیگر و استفاده‌ی مجدد انتخاب می‌کنیم.

تأیید: با EXPLAIN بررسی می‌کنیم: type = range، key = ایندکس جدید، rows کم، و نبود Using filesort.

یک صفحه‌ی گزارش در production کند شده است. خروجی EXPLAIN برای query اصلی type: ALL، rows: 4,800,000 و Extra: Using where; Using temporary; Using filesort را نشان می‌دهد. این خروجی را تفسیر کنید و مراحل بهینه‌سازی را شرح دهید.

تفسیر:

  • type: ALL ⇒ full table scan؛ هیچ ایندکسی برای شرط استفاده نشده (key = NULL).
  • rows: 4.8M ⇒ تخمین تعداد سطرهای بررسی‌شده؛ تقریباً کل جدول.
  • Using where ⇒ فیلتر پس از خواندن سطر در لایه‌ی سرور.
  • Using temporary ⇒ جدول موقت برای GROUP BY/DISTINCT.
  • Using filesort ⇒ مرتب‌سازی جداگانه چون ترتیب مناسبی از ایندکس در دسترس نیست.

مراحل:

  1. اندازه‌گیری دقیق: EXPLAIN ANALYZE برای زمان و سطرهای واقعی؛ بررسی اینکه query در slow log/pg_stat_statements چه سهمی از زمان کل دارد.
  2. بررسی sargability: آیا روی ستون تابع زده شده (DATE(created_at) = …)، تبدیل نوع ضمنی، LIKE '%…' یا OR بین ستون‌های مختلف وجود دارد؟ بازنویسی به شکل range: created_at >= ? AND created_at < ?.
  3. ایندکس composite مطابق الگو: ستون‌های تساوی، سپس ستون GROUP BY/ORDER BY، سپس range؛ در صورت امکان covering تا Using index بگیریم. اگر GROUP BY روی ستون‌هایی باشد که به ترتیب ایندکس‌اند، temporary و filesort می‌توانند حذف شوند.
  4. کاهش داده: فقط ستون‌های لازم به‌جای SELECT *؛ محدود کردن بازه‌ی زمانی پیش‌فرض گزارش؛ keyset pagination به‌جای OFFSET بزرگ.
  5. به‌روز کردن آمار (ANALYZE TABLE) اگر rows تخمینی با واقعی فاصله‌ی زیاد دارد.
  6. اگر گزارش aggregate سنگین روی داده‌ی تاریخی است: summary table / materialized view که به‌صورت دوره‌ای یا افزایشی به‌روز شود، یا cache نتیجه با TTL.
  7. انتقال گزارش‌ها به read replica یا data warehouse تا روی primary اثر نگذارد.
  8. در جداول زمانی بسیار بزرگ: partitioning بر اساس تاریخ برای partition pruning.
  9. اندازه‌گیری مجدد و بررسی اثر ایندکس جدید روی نوشتن‌ها.

نکته: فقط ایندکس اضافه کردن کافی نیست اگر شرط بخش بزرگی از جدول را برگرداند؛ آنجا optimizer همچنان full scan را ترجیح می‌دهد و راه‌حل واقعی pre-aggregation است.

Window Function چیست و چه تفاوتی با GROUP BY دارد؟ یک query بنویسید که سه محصول پرفروش هر دسته را برگرداند و تفاوت ROW_NUMBER، RANK و DENSE_RANK را توضیح دهید.

تعریف: Window Function روی مجموعه‌ای از سطرهای مرتبط با سطر جاری («پنجره»، تعریف‌شده با OVER (PARTITION BY … ORDER BY … frame)) محاسبه انجام می‌دهد. برخلاف GROUP BY که هر گروه را به یک سطر تبدیل می‌کند، window function تعداد سطرها را حفظ می‌کند و فقط یک ستون محاسبه‌شده اضافه می‌کند. پس می‌توان هم‌زمان جزئیات سطر و مقدار تجمعی گروه را داشت.

WITH sales AS (
    SELECT p.category_id, p.id AS product_id, p.name, SUM(oi.qty) AS sold
    FROM products p
    JOIN order_items oi ON oi.product_id = p.id
    GROUP BY p.category_id, p.id, p.name
),
ranked AS (
    SELECT s.*,
           DENSE_RANK() OVER (PARTITION BY category_id ORDER BY sold DESC) AS rnk
    FROM sales s
)
SELECT category_id, product_id, name, sold, rnk
FROM ranked
WHERE rnk <= 3
ORDER BY category_id, rnk;

از CTE استفاده کردیم چون window function پس از WHERE و GROUP BY محاسبه می‌شود و نمی‌توان مستقیم در WHERE روی آن فیلتر کرد.

تفاوت توابع رتبه‌بندی برای فروش‌های 90، 80، 80، 70:

  • ROW_NUMBER() ⇒ 1، 2، 3، 4؛ همیشه یکتا؛ ترتیب ties نامعین مگر ORDER BY کامل (مثلاً اضافه کردن product_id). مناسب «دقیقاً ۳ سطر» یا deduplicate.
  • RANK() ⇒ 1، 2، 2، 4؛ ties رتبه‌ی برابر و سپس فاصله. مثل رتبه‌بندی مسابقات.
  • DENSE_RANK() ⇒ 1، 2، 2، 3؛ بدون فاصله. «سه سطح فروش برتر» ممکن است بیش از ۳ محصول برگرداند.

سایر کاربردها: جمع تجمعی SUM(x) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)، میانگین متحرک، مقایسه با دوره‌ی قبل با LAG()، درصد از کل با SUM(x) OVER (). در MySQL از نسخه‌ی 8.0 پشتیبانی می‌شود.

نکته‌ی کارایی: window function نیاز به مرتب‌سازی داخل partition دارد؛ ایندکس مناسب روی (partition_col, order_col) یا pre-aggregation برای داده‌ی بزرگ کمک می‌کند.

Partitioning و Sharding را مقایسه کنید. جدول لاگ رویدادهای یک سیستم روزانه ۲۰ میلیون سطر رشد می‌کند و فقط داده‌ی ۹۰ روز اخیر لازم است؛ چه راهکاری پیشنهاد می‌کنید؟

Partitioning: تقسیم یک جدول به چند partition روی همان سرور؛ برای برنامه شفاف است (SQL تغییر نمی‌کند). انواع: RANGE (تاریخ)، LIST (مقادیر گسسته مثل region)، HASH/KEY (توزیع یکنواخت). مزایا: partition pruning (خواندن فقط partitionهای مرتبط)، حذف آنی داده‌ی قدیمی با DROP PARTITION، ایندکس‌های کوچک‌تر در هر partition و نگه‌داری ساده‌تر.

Sharding: تقسیم داده بین چند سرور دیتابیس مستقل بر اساس shard key. هدف: scale نوشتن و حجم داده فراتر از یک سرور. هزینه‌ها: از دست رفتن JOIN و تراکنش بین shardها، نیاز به routing در برنامه یا لایه‌ی میانی (Vitess، Citus)، ID یکتای سراسری، resharding و پیچیدگی عملیاتی.

سناریو: ۲۰M سطر در روز ≈ ۲۳۰ insert در ثانیه به‌طور میانگین که برای یک سرور خوب قابل تحمل است؛ ۹۰ روز ≈ ۱.۸ میلیارد سطر. مشکل اصلی حجم و حذف داده‌ی قدیمی است، نه توان نوشتن. پس sharding لازم نیست:

  • RANGE partitioning روزانه روی created_at (حدود ۹۰ partition)؛ یک job روزانه (Laravel Scheduler) partition فردا را می‌سازد و partition قدیمی‌تر از ۹۰ روز را DROP می‌کند (یا قبلش به object storage/آرشیو export می‌کند). DELETE روزانه‌ی ۲۰M سطر، undo/WAL عظیم، lag در replication و bloat می‌سازد؛ DROP PARTITION تقریباً آنی است.
  • PK باید شامل created_at باشد (محدودیت MySQL)؛ مثلاً (id, created_at). ایندکس‌ها را حداقلی نگه داریم چون جدول write-heavy است.
  • queryها همیشه شرط زمانی داشته باشند تا pruning فعال شود.
  • insertها را batch کنیم (یا از طریق queue)، و گزارش‌ها را روی replica یا summary table اجرا کنیم.
  • اگر نیاز تحلیلی سنگین است، بررسی ذخیره‌ساز مناسب‌تر (ستونی مثل ClickHouse، یا TimescaleDB روی PostgreSQL).

Sharding را زمانی در نظر می‌گیریم که توان نوشتن یا حجم داده‌ی فعال از ظرفیت بزرگ‌ترین سرور معقول فراتر برود.

در یک برنامه‌ی Laravel با primary و دو read replica، کاربران گزارش می‌دهند بعد از ویرایش پروفایل، تغییرات را نمی‌بینند و پس از چند رفرش ظاهر می‌شود. علت را توضیح دهید و راه‌حل‌ها را بیان کنید.

علت: Replication Lag و نقض Read-Your-Writes. replication در MySQL و PostgreSQL به‌صورت پیش‌فرض asynchronous است؛ primary پس از commit محلی به کلاینت پاسخ می‌دهد و تغییرات کمی بعد (میلی‌ثانیه‌ها تا ثانیه‌ها، و زیر بار سنگین بیشتر) روی replicaها اعمال می‌شود. جریان: POST /profile روی primary نوشته می‌شود ⇒ redirect ⇒ GET /profile یک request جدید است و Laravel آن را از replica می‌خواند ⇒ داده‌ی قدیمی. «چند رفرش» هم ممکن است بین دو replica با lag متفاوت جابه‌جا شود و حتی داده‌ی عقب‌تر نشان دهد (نقض Monotonic Reads).

چرا sticky کافی نیست: 'sticky' => true فقط در همان request پس از نوشتن، خواندن‌ها را به write connection می‌برد؛ request بعد از redirect دوباره از replica می‌خواند.

راه‌حل‌ها:

  1. Sticky زمانی در session: پس از هر نوشتن، یک timestamp در session (یا cookie) ذخیره و تا N ثانیه (بیشتر از lag معمول) خواندن‌های آن کاربر را از primary انجام دهیم. پیاده‌سازی با middleware که در صورت وجود flag، از onWriteConnection()/useWritePdo() یا connection جداگانه‌ی primary استفاده کند.
  2. خواندن‌های حساس از primary: پروفایل خود کاربر، کیف پول، وضعیت سفارش: User::onWriteConnection()->find($id). خواندن‌های عمومی (لیست محصولات) از replica.
  3. ردیابی GTID/LSN: پس از نوشتن، GTID را در session نگه داریم و فقط از replicaای بخوانیم که به آن رسیده (WAIT_FOR_EXECUTED_GTID_SET با timeout)؛ دقیق‌ترین ولی پیچیده‌تر.
  4. بازگرداندن داده‌ی نوشته‌شده در پاسخ POST یا به‌روزرسانی UI از داده‌ی کلاینت، تا اصلاً نیازی به خواندن بلافاصله نباشد.
  5. Monotonic reads: هر کاربر به یک replica ثابت هدایت شود.
  6. کاهش خود lag: پایش Seconds_Behind_Source/replay_lag، replica هم‌توان primary، applier موازی، تقسیم تراکنش‌های حجیم، و خارج کردن replica با lag بالا از pool توسط proxy (مثلاً ProxySQL با max_replication_lag).

جمع‌بندی: read replica معامله‌ای بین scale خواندن و eventual consistency است و باید آگاهانه مسیرهای نیازمند consistency قوی را مشخص کرد.

قضیه‌ی CAP را توضیح دهید و بگویید چرا عبارت «دو از سه» گمراه‌کننده است. PACELC چه چیزی به CAP اضافه می‌کند؟

CAP: در یک سیستم داده‌ی توزیع‌شده (replicated)، هنگام وقوع Network Partition (عدم امکان ارتباط بین بخشی از نودها) نمی‌توان هم‌زمان این دو را تضمین کرد:

  • Consistency: هر خواندن آخرین نوشتن تأییدشده را برمی‌گرداند (linearizability؛ متفاوت با C در ACID).
  • Availability: هر درخواست به یک نود سالم، پاسخ غیرخطا دریافت می‌کند.

چرا «دو از سه» گمراه‌کننده است: P یک انتخاب نیست؛ partition در شبکه‌های واقعی رخ می‌دهد (خرابی سوئیچ، GC طولانی، قطعی بین دیتاسنترها). پس سیستم توزیع‌شده باید تحمل partition داشته باشد و سوال واقعی این است: هنگام partition، C یا A؟

  • CP: سمت اقلیت درخواست‌ها را رد می‌کند تا داده‌ی ناسازگار برنگرداند (etcd، ZooKeeper، سیستم‌های مبتنی بر Raft/Paxos). مناسب: lock توزیع‌شده، تنظیمات، پرداخت.
  • AP: همه‌ی نودها پاسخ می‌دهند، شاید با داده‌ی کهنه، و پس از رفع partition همگرا می‌شوند (Cassandra، DynamoDB در حالت پیش‌فرض). مناسب: سبد خرید، شمارنده‌ی like، feed.

همچنین انتخاب‌ها طیفی‌اند و می‌توانند per-operation باشند؛ مثلاً در Cassandra با consistency level QUORUM یا ONE.

PACELC: CAP فقط درباره‌ی زمان partition است، در حالی که سیستم بیشتر وقت سالم است. PACELC می‌گوید: if P ⇒ A or C; Else ⇒ L or C. یعنی در حالت عادی هم بین Latency و Consistency مصالحه هست: replication همگام (منتظر تأیید replica) consistency را بالا می‌برد ولی latency هر نوشتن را زیاد می‌کند؛ خواندن از replica محلی سریع است ولی ممکن است کهنه باشد. مثال‌ها: Cassandra/DynamoDB ⇒ PA/EL؛ HBase و سیستم‌های اجماعی ⇒ PC/EC.

کاربرد عملی در یک سیستم Laravel: MySQL با replicaهای async: خواندن از primary تقریباً سازگار است، خواندن از replica ⇒ انتخاب «EL». در failover با async، ممکن است تراکنش‌هایی از دست بروند؛ semi-sync این ریسک را با افزایش latency (EC) کاهش می‌دهد.

برای دیتابیس ۵۰۰ گیگابایتی یک فروشگاه اینترنتی با الزام RPO کمتر از ۵ دقیقه و RTO کمتر از ۲ ساعت، استراتژی Backup طراحی کنید. Logical و Physical backup و PITR را در پاسخ توضیح دهید.

تعاریف: RPO حداکثر داده‌ی قابل قبول برای از دست رفتن (بر حسب زمان)؛ RTO حداکثر زمان بازگشت سرویس.

Logical backup (mysqldump، mydumper، pg_dump): خروجی SQL/داده؛ قابل حمل بین نسخه‌ها و انتخاب جدول، اما restore آن کند است چون همه‌ی ایندکس‌ها بازسازی می‌شوند؛ برای ۵۰۰GB احتمالاً بیش از RTO دو ساعته طول می‌کشد. Physical backup (Percona XtraBackup، pg_basebackup/pgBackRest، snapshot دیسک): کپی فایل‌های داده؛ backup و restore سریع، incremental، ولی وابسته به نسخه و پلتفرم. PITR: restore یک backup کامل + replay لاگ تغییرات (binlog در MySQL، WAL در PostgreSQL) تا لحظه‌ی دلخواه.

طراحی:

  1. Physical full backup هفتگی + incremental روزانه، گرفته‌شده از یک replica تا بار primary کم شود.
  2. آرشیو پیوسته‌ی binlog/WAL به object storage (مثلاً هر دقیقه یا با streaming) ⇒ RPO چند ثانیه تا حداکثر چند دقیقه. در MySQL: sync_binlog=1، GTID و نگه‌داری binlog به مدت کافی؛ در PostgreSQL: archive_mode و archive_command یا pgBackRest.
  3. Logical dump روزانه‌ی جداول حیاتی (مثلاً سفارش‌ها، کاربران) برای بازیابی انتخابی سریع یک جدول.
  4. قانون 3-2-1: نسخه در همان دیتاسنتر برای restore سریع، نسخه در region دیگر، و یک نسخه‌ی immutable (object lock) در برابر ransomware و حذف عمدی. رمزنگاری و کنترل دسترسی.
  5. HA جدا از backup: replica با failover خودکار برای خرابی سخت‌افزار (RTO دقیقه‌ای). backup برای خطای انسانی/داده‌ی خراب است که replication آن را هم کپی می‌کند. یک delayed replica (مثلاً با تأخیر یک ساعته) می‌تواند بازیابی از DELETE اشتباه را بسیار سریع‌تر کند.
  6. تست restore خودکار هفتگی روی سرور جدا، اندازه‌گیری زمان واقعی و مقایسه با RTO؛ و runbook مستند.
  7. پایش: هشدار در صورت شکست backup یا توقف آرشیو لاگ.

سناریوی بازیابی: DELETE اشتباه ساعت ۱۴:۳۲ ⇒ restore physical backup روی سرور جدا ⇒ replay binlog/WAL تا ۱۴:۳۱:۵۹ ⇒ استخراج سطرهای حذف‌شده و بازگرداندن به production یا جایگزینی کامل. زمان: کپی physical ۵۰۰GB با شبکه‌ی سریع + replay لاگ‌ها در محدوده‌ی RTO قابل انجام است، که با logical dump تقریباً ناممکن بود.

کد زیر چه مشکلاتی دارد؟ آن را از نظر تراکنش، قفل و سازگاری داده تحلیل و اصلاح کنید. 
<?php
DB::transaction(function () use ($order) {
    $order = Order::lockForUpdate()->find($order->id);
    $response = Http::timeout(30)->post('https://psp.example/charge', [
        'amount' => $order->total,
    ]);
    $order->update(['status' => 'paid', 'ref' => $response['ref']]);
    SendInvoiceEmail::dispatch($order);
    Mail::to($order->user)->send(new OrderPaid($order));
});

مشکلات:

  1. فراخوانی HTTP داخل تراکنش با قفل: سطر سفارش تا ۳۰ ثانیه قفل می‌ماند؛ تراکنش طولانی ⇒ انتظار سایر requestها، lock wait timeout، اشغال اتصال دیتابیس، و در MVCC جلوگیری از purge/vacuum. زیر بار، connection pool تمام می‌شود.
  2. ناسازگاری بین سیستم‌ها: rollback دیتابیس، شارژ انجام‌شده در درگاه پرداخت را برنمی‌گرداند. اگر بعد از charge، update یا dispatch خطا دهد، پول کسر شده ولی سفارش paid نیست.
  3. Retry خطرناک: اگر با attempts یا retry دستی دوباره اجرا شود، کاربر دو بار شارژ می‌شود؛ درخواست پرداخت idempotency key ندارد.
  4. Dispatch قبل از commit: job ممکن است قبل از commit اجرا شود و سفارش را با وضعیت قدیمی ببیند، یا اگر تراکنش rollback شود، ایمیل فاکتور برای سفارش پرداخت‌نشده ارسال شود.
  5. ارسال ایمیل هم‌زمان داخل تراکنش: کند و غیرقابل rollback؛ ایمیل ممکن است ارسال شود و تراکنش بعداً شکست بخورد.
  6. بررسی نشدن وضعیت فعلی سفارش (شاید قبلاً paid شده) و نتیجه‌ی پاسخ HTTP.

اصلاح (الگوی چندمرحله‌ای با تراکنش‌های کوتاه):

<?php
// 1) تراکنش کوتاه: انتقال به وضعیت میانی (فقط اگر pending است)
$claimed = Order::whereKey($id)->where('status', 'pending')
    ->update(['status' => 'processing']);
if (! $claimed) { return; } // قبلاً در حال پردازش یا پرداخت‌شده

// 2) فراخوانی خارجی بیرون از تراکنش، با idempotency key پایدار
$response = Http::timeout(10)
    ->withHeaders(['Idempotency-Key' => "order-{$id}"])
    ->post('https://psp.example/charge', ['amount' => $order->total])
    ->throw();

// 3) تراکنش کوتاه دوم + jobهایی که فقط پس از commit dispatch شوند
DB::transaction(function () use ($id, $response) {
    Order::whereKey($id)->update(['status' => 'paid', 'ref' => $response['ref']]);
    SendInvoiceEmail::dispatch($id)->afterCommit();
    SendOrderPaidMail::dispatch($id)->afterCommit();
});

برای حالت‌هایی که فرایند وسط کار قطع شود (سفارش در processing بماند)، یک job دوره‌ای reconciliation وضعیت را از درگاه استعلام می‌کند. در معماری‌های پیچیده‌تر از الگوی Transactional Outbox استفاده می‌شود تا ثبت تغییر و انتشار رویداد اتمیک باشند.

خلاصه برای مرور سریع

ACID و تراکنش

  • A ⇐ undo log | C ⇐ constraint + منطق برنامه | I ⇐ MVCC + قفل | D ⇐ WAL/redo + fsync.
  • innodb_flush_log_at_trx_commit=1 و sync_binlog=1 ⇒ durability کامل.
  • C در ACID ≠ C در CAP (linearizability).
  • تراکنش کوتاه؛ بدون HTTP/ایمیل داخلش؛ job با afterCommit؛ تودرتو = SAVEPOINT؛ DB::transaction($fn, attempts: 3) ⇒ retry در deadlock.

MVCC

  • خواندن نوشتن را بلاک نمی‌کند و برعکس؛ فقط write-write قفل دارد.
  • InnoDB: نسخه‌ی قدیمی در undo، purge؛ PG: tuple جدید در heap (xmin/xmax)، VACUUM، bloat، HOT update.
  • تراکنش طولانی ⇒ history list بلند (InnoDB) / bloat (PG).

قفل‌ها و Deadlock

  • S با S سازگار؛ X با هیچ‌چیز. lockForUpdate() = FOR UPDATE، sharedLock() = FOR SHARE؛ فقط داخل تراکنش.
  • InnoDB قفل را روی رکورد ایندکس می‌گیرد ⇒ UPDATE بدون ایندکس = قفل همه‌ی سطرهای اسکن‌شده.
  • Gap lock = جلوی insert در بازه؛ Next-key = record + gap (پیش‌فرض RR)؛ در RC غیرفعال.
  • Lost update ⇒ UPDATE atomic شرطی | FOR UPDATE | version column.
  • Optimistic: تداخل کم، عملیات طولانی/فرم، بدون deadlock. Pessimistic: تداخل زیاد، تراکنش کوتاه.
  • SKIP LOCKED ⇒ صف کار روی DB؛ NOWAIT ⇒ خطای فوری.
  • Deadlock = چرخه‌ی انتظار. InnoDB: فوری، خطای 1213، قربانی کوچک‌تر. PG: پس از deadlock_timeout، 40P01.
  • پیشگیری: ترتیب ثابت قفل، تراکنش کوتاه، ایندکس، upsert، RC، batch کوچک؛ و همیشه retry.

ایندکس

  • B+Tree: داده فقط در برگ، برگ‌ها پیوندی و مرتب ⇒ range و ORDER BY سریع؛ عمق ۳–۴.
  • InnoDB: clustered = جدول بر اساس PK؛ secondary = ستون‌ها + PK ⇒ lookup دوم.
  • UUIDv4 PK ⇒ page split، ایندکس بزرگ ⇒ BIGINT یا UUIDv7/ULID در BINARY(16).
  • Composite: leftmost prefix؛ تساوی ⇒ ORDER BY ⇒ range؛ بعد از range بقیه seek نمی‌شوند.
  • Covering ⇒ Using index / Index Only Scan؛ PG: INCLUDE.
  • Selectivity پایین ⇒ ایندکس بی‌اثر (مگر توزیع نامتوازن ⇒ partial index در PG).
  • ضرر ایندکس: کندی نوشتن، فضا، cache؛ ایندکس زائد را حذف کنید (invisible index در MySQL 8).

EXPLAIN

  • type: const > eq_ref > ref > range > index > ALL.
  • Extra: Using index عالی | Using index condition خوب | Using filesort/Using temporary روی داده‌ی بزرگ بد.
  • EXPLAIN ANALYZE = اجرای واقعی؛ PG: EXPLAIN (ANALYZE, BUFFERS).
  • Anti-patternها: تابع روی ستون، تبدیل نوع ضمنی، LIKE '%x'، OFFSET بزرگ (⇒ keyset/cursorPaginate)، SELECT *، N+1 (⇒ with())، OR بین ستون‌ها.

SQL پیشرفته

  • CTE: خوانایی + WITH RECURSIVE برای درخت؛ PG12+ inline می‌شود.
  • Window: سطرها حفظ می‌شوند. ROW_NUMBER 1234 | RANK 1224 | DENSE_RANK 1223.
  • Top-N per group ⇒ ROW_NUMBER در CTE + WHERE rn <= N.
  • Running total ⇒ ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (پیش‌فرض RANGE با ties پرش دارد).
  • View = query ذخیره‌شده (امنیت، سادگی)؛ Materialized View = نتیجه‌ی ذخیره‌شده، stale تا refresh (فقط PG؛ MySQL ⇒ summary table).
  • Procedure/Trigger: نزدیک داده و مستقل از برنامه، ولی منطق پنهان، تست و scale سخت ⇒ فقط audit و integrity.

Scale و توزیع

  • Partitioning = یک سرور (RANGE/LIST/HASH)، pruning، DROP PARTITION آنی؛ کلید partition در همه‌ی UNIQUEها؛ بدون FK در MySQL.
  • Sharding = چند سرور؛ shard key با cardinality بالا و توزیع یکنواخت؛ hash / range / consistent hashing / directory؛ هزینه: JOIN، تراکنش، ID سراسری، resharding، hot shard.
  • مسیر scale: query/index ⇒ cache ⇒ replica ⇒ vertical ⇒ partition/archive ⇒ functional split ⇒ shard.
  • Replication: MySQL binlog (ROW) + GTID؛ PG streaming WAL + logical. Async (پیش‌فرض) / semi-sync / sync.
  • Replica ⇒ scale خواندن، نه نوشتن؛ lag ⇒ read-your-writes: sticky (فقط همان request)، session flag زمانی، GTID/LSN، خواندن حساس از primary (onWriteConnection()).
  • HA: failover خودکار (Orchestrator، Patroni، InnoDB Cluster)، quorum + fencing ضد split-brain؛ RPO/RTO.
  • CAP: هنگام partition ⇒ C یا A. PACELC: در غیر این صورت ⇒ Latency یا Consistency. Cassandra PA/EL، etcd/HBase PC/EC.
  • Pooling: PG process-per-connection ⇒ PgBouncer (transaction mode، مراقب ویژگی‌های session)؛ MySQL ⇒ ProxySQL؛ اتصال‌ها ≈ سرورها × pm.max_children.

Backup

  • Logical (mysqldump --single-transaction، pg_dump): قابل حمل، restore کند. Physical (XtraBackup، pg_basebackup): سریع، وابسته به نسخه.
  • PITR = full backup + replay binlog/WAL تا لحظه‌ی قبل از حادثه.
  • 3-2-1، immutable copy، رمزنگاری، تست restore؛ replication ≠ backup؛ delayed replica.
