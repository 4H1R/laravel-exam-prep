CI/CD

یکپارچه‌سازی و تحویل مداوم: از تعریف دقیق CI، Continuous Delivery و Continuous Deployment تا طراحی Pipeline کامل برای Laravel در GitHub Actions و GitLab CI، مدیریت Secretها، استراتژی‌های Deployment، استقرار بدون Downtime، Migrationهای امن، Rollback و متریک‌های DORA.

CI، Continuous Delivery و Continuous Deployment

سه اصطلاحی که اغلب با هم قاطی می‌شوند، در واقع سه پله‌ی پشت‌سرهم از اتوماسیون‌اند. هرکدام روی پله‌ی قبلی ساخته می‌شود.

Continuous Integration (CI)

CI یک روش کار است (نه فقط یک ابزار): همه‌ی اعضای تیم تغییرات کوچک خود را مکرراً (دست‌کم روزی یک بار) در شاخه‌ی اصلی مشترک (mainline) ادغام می‌کنند و هر ادغام به‌صورت خودکار build و تست می‌شود. هدف این است که مشکلات یکپارچه‌سازی (conflict، شکستن قرارداد بین ماژول‌ها، تست‌های شکسته) در چند دقیقه کشف شوند، نه در هفته‌ی آخر قبل از release.

  • کد در یک مخزن مشترک با شاخه‌ی اصلی همیشه «سبز».
  • build و تست خودکار روی هر push و هر Pull Request.
  • اگر build شکست، اولویت تیم درست کردن فوری آن است («stop the line»).

Continuous Delivery (CD)

Continuous Delivery یعنی هر تغییری که از Pipeline عبور می‌کند، همیشه در وضعیت قابل‌انتشار (releasable) است و انتشار آن روی Production با یک تصمیم انسانی و یک کلیک انجام می‌شود. همه‌ی مراحل (build، تست، استقرار روی staging، تست‌های پذیرش) خودکارند؛ فقط «دکمه‌ی آخر» دستی است و آن هم یک تصمیم کسب‌وکاری است، نه یک کار فنی پرخطا.

Continuous Deployment

Continuous Deployment یک قدم جلوتر است: هر تغییری که همه‌ی مراحل Pipeline را با موفقیت پشت سر بگذارد، بدون دخالت انسان روی Production مستقر می‌شود. پیش‌نیاز آن، تست خودکار بسیار قابل‌اعتماد، Monitoring قوی، Rollback خودکار یا سریع و معمولاً Feature Flag است.

  commit ──► build ──► unit/integration tests ──► staging ──► acceptance ──► [ production ]
  └─────────── Continuous Integration ───────┘
  └──────────────────────── Continuous Delivery ──────────────────────┘  (دکمه‌ی دستی)
  └──────────────────────── Continuous Deployment ────────────────────────────────────┘  (خودکار)

تفاوت کلیدی Delivery و Deployment فقط در یک چیز است: آیا رفتن به Production نیاز به تأیید انسانی دارد یا نه. در هر دو، کد همیشه قابل‌انتشار است. جمله‌ی طلایی: «Continuous Delivery یعنی می‌توانی هر لحظه منتشر کنی؛ Continuous Deployment یعنی واقعاً هر بار منتشر می‌کنی.»

داشتن یک سرور Jenkins یا یک فایل .github/workflows به معنی «انجام CI» نیست. اگر برنچ‌ها هفته‌ها جدا بمانند و دیر merge شوند، فقط «build خودکار روی برنچ» دارید، نه Continuous Integration.

Pipeline
زنجیره‌ی خودکار مراحل (stage/job) که از commit تا انتشار اجرا می‌شود؛ معمولاً به‌صورت «Pipeline as Code» در مخزن نگهداری می‌شود.
Artifact
خروجی قابل‌استقرار build (فایل zip، Docker image، پکیج) که یک‌بار ساخته و بین محیط‌ها جابه‌جا می‌شود.
Mainline / Trunk
شاخه‌ی اصلی مشترک (main) که باید همیشه سالم و قابل‌انتشار باشد.
Release
در دسترس قرار دادن یک قابلیت برای کاربر؛ می‌تواند از Deployment (قرار دادن کد روی سرور) جدا باشد.

چرا CI/CD؟ حلقه‌ی بازخورد و Batchهای کوچک

منطق اصلی CI/CD از دو ایده می‌آید: کوتاه کردن حلقه‌ی بازخورد (feedback loop) و کوچک کردن اندازه‌ی هر تغییر (batch size).

حلقه‌ی بازخورد کوتاه

هزینه‌ی رفع یک باگ با فاصله‌ی زمانی بین ایجاد و کشف آن رابطه‌ی مستقیم دارد. اگر توسعه‌دهنده ۱۰ دقیقه بعد از push بفهمد تستی شکسته، هنوز context ذهنی را دارد و در چند دقیقه درستش می‌کند. اگر سه هفته بعد در QA یا Production کشف شود، باید ابتدا بفهمد کدام تغییر از میان ده‌ها تغییر مقصر است.

Batch کوچک = ریسک کم

  • Blast radius کوچک‌تر: یک deploy با ۳ commit اگر خراب شود، دامنه‌ی جست‌وجو محدود است؛ یک release ماهانه با ۲۰۰ commit این‌طور نیست.
  • Rollback آسان‌تر: برگرداندن یک تغییر کوچک ساده و کم‌عارضه است.
  • Merge conflict کمتر: برنچ‌های کوتاه‌عمر با main فاصله‌ی زیادی پیدا نمی‌کنند.
  • Code review بهتر: PR با ۱۵۰ خط واقعاً review می‌شود؛ PR با ۳۰۰۰ خط فقط «Approve» می‌گیرد.
  • ارزش زودتر به کاربر می‌رسد و بازخورد کسب‌وکاری هم سریع‌تر برمی‌گردد.

مزایای دیگر

فنی

  • تکرارپذیری: deploy یک اسکریپت است، نه یک «مراسم» دستی.
  • کاهش خطای انسانی (فراموش کردن migrate یا cache:clear).
  • کیفیت یکنواخت: lint، static analysis و تست برای همه اجباری است.
  • ثبت تاریخچه: هر deploy قابل ردیابی تا commit و PR است.

سازمانی

  • کاهش ترس از deploy؛ deploy به یک رویداد عادی تبدیل می‌شود.
  • Lead time کمتر از ایده تا Production.
  • شفافیت: همه وضعیت build و محیط‌ها را می‌بینند.
  • امکان اندازه‌گیری (متریک‌های DORA).

اگر پرسیدند «چرا deploy مکرر ریسک را کم می‌کند در حالی که تعداد deployها بیشتر شده؟» پاسخ: ریسک هر deploy متناسب با اندازه‌ی تغییر است نه تعداد deployها. تغییرات کوچک، تشخیص و Rollback سریع و تمرین مداوم فرایند، احتمال و اثر شکست را کاهش می‌دهند. «If it hurts, do it more often.»

Pint

Pint یک wrapper روی PHP-CS-Fixer با preset پیش‌فرض Laravel است. در CI با --test اجرا می‌شود تا فقط گزارش دهد و فایلی را تغییر ندهد (در صورت مغایرت exit code غیرصفر برمی‌گرداند).

vendor/bin/pint --test        # در CI: فقط بررسی
vendor/bin/pint --dirty       # در لوکال: فقط فایل‌های تغییرکرده را اصلاح کن

PHPStan و Larastan

PHPStan کد را بدون اجرا تحلیل می‌کند. Larastan افزونه‌ای است که «جادو»ی Laravel (Facadeها، propertyهای Eloquent، relationها، Builder) را برای PHPStan قابل‌فهم می‌کند. سطح سخت‌گیری با level (۰ تا ۹/max) تعیین می‌شود. در پروژه‌ی قدیمی با baseline خطاهای فعلی را ثبت می‌کنند تا فقط خطای جدید جلوی merge را بگیرد.

# phpstan.neon
includes:
    - vendor/larastan/larastan/extension.neon
parameters:
    paths:
        - app/
    level: 6
vendor/bin/phpstan analyse --memory-limit=1G
vendor/bin/phpstan analyse --generate-baseline   # ثبت خطاهای موجود در phpstan-baseline.neon

تست با پایگاه‌داده‌ی واقعی

SQLite in-memory سریع است، اما رفتارش با MySQL/PostgreSQL فرق دارد (نوع داده‌ها، foreign key، JSON، collation، قفل‌ها). برای اطمینان، دست‌کم یک job باید با همان موتوری که در Production دارید اجرا شود؛ در CI این کار با service container انجام می‌شود.

سریع‌ترین بررسی‌ها (Pint، PHPStan) را می‌توان به‌صورت job موازی کنار تست‌ها اجرا کرد. هر job که به خروجی دیگری نیاز ندارد نباید منتظر آن بماند؛ فقط مرحله‌ی build/deploy باید به همه‌ی بررسی‌ها وابسته (needs) باشد.

اصل «Build once, deploy many»: artifact (مثلاً Docker image با tag برابر SHA کامیت) فقط یک بار ساخته می‌شود و همان artifact روی staging و سپس production مستقر می‌شود. تفاوت محیط‌ها فقط در پیکربندی (env vars/secrets) است. ساختن دوباره برای هر محیط یعنی چیزی که تست شده با چیزی که منتشر می‌شود الزاماً یکی نیست.

Workflow کامل GitHub Actions برای Laravel

در GitHub Actions، هر workflow یک فایل YAML در .github/workflows/ است که با یک یا چند event (push، pull_request، workflow_dispatch، schedule) فعال می‌شود. workflow شامل چند job است که به‌طور پیش‌فرض موازی و هرکدام روی یک runner تازه اجرا می‌شوند؛ هر job شامل چند step است که یا دستور shell (run) هستند یا یک action آماده (uses).

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

# اگر روی همان برنچ push جدیدی آمد، اجرای قبلی لغو شود
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read          # اصل حداقل دسترسی برای GITHUB_TOKEN

jobs:
  quality:
    name: Pint & PHPStan
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.3'
          coverage: none
          tools: composer:v2
      - name: Get Composer cache directory
        id: composer-cache
        run: echo "dir=$(composer config cache-files-dir)" >> "$GITHUB_OUTPUT"
      - uses: actions/cache@v4
        with:
          path: ${{ steps.composer-cache.outputs.dir }}
          key: composer-${{ runner.os }}-${{ hashFiles('composer.lock') }}
          restore-keys: composer-${{ runner.os }}-
      - run: composer install --no-interaction --prefer-dist --no-progress
      - run: vendor/bin/pint --test
      - run: vendor/bin/phpstan analyse --memory-limit=1G --no-progress

  tests:
    name: Tests (PHP ${{ matrix.php }})
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        php: ['8.3', '8.4']

    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: password
          MYSQL_DATABASE: testing
        ports:
          - 3306:3306
        options: >-
          --health-cmd="mysqladmin ping"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

    env:
      APP_ENV: testing
      DB_CONNECTION: mysql
      DB_HOST: 127.0.0.1
      DB_PORT: 3306
      DB_DATABASE: testing
      DB_USERNAME: root
      DB_PASSWORD: password

    steps:
      - uses: actions/checkout@v4

      - uses: shivammathur/setup-php@v2
        with:
          php-version: ${{ matrix.php }}
          extensions: mbstring, pdo_mysql, bcmath, intl, redis
          coverage: none

      - name: Get Composer cache directory
        id: composer-cache
        run: echo "dir=$(composer config cache-files-dir)" >> "$GITHUB_OUTPUT"

      - uses: actions/cache@v4
        with:
          path: ${{ steps.composer-cache.outputs.dir }}
          key: composer-${{ runner.os }}-php${{ matrix.php }}-${{ hashFiles('composer.lock') }}
          restore-keys: composer-${{ runner.os }}-php${{ matrix.php }}-

      - run: composer install --no-interaction --prefer-dist --no-progress

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci && npm run build      # برای تست‌هایی که manifest ویت را لازم دارند

      - name: Prepare environment
        run: |
          cp .env.example .env
          php artisan key:generate

      - run: php artisan migrate --force
      - run: php artisan test

      - name: Security audit
        run: composer audit

  build-image:
    needs: [quality, tests]
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy-staging:
    needs: build-image
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: ./scripts/deploy.sh staging ${{ github.sha }}
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://example.com
    steps:
      - run: ./scripts/deploy.sh production ${{ github.sha }}
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}

نکات این workflow

  • Matrix: job تست برای هر نسخه‌ی PHP یک‌بار جداگانه و موازی اجرا می‌شود. fail-fast: false باعث می‌شود شکست یک نسخه بقیه را لغو نکند تا تصویر کامل را ببینید.
  • Service container: MySQL کنار job بالا می‌آید. چون job مستقیماً روی runner (نه داخل container) اجرا می‌شود، با 127.0.0.1 و پورت map شده به آن وصل می‌شویم. گزینه‌های --health-cmd باعث می‌شوند stepها تا سالم شدن MySQL منتظر بمانند.
  • Cache: کلید cache به hashFiles('composer.lock') وابسته است؛ با تغییر lock file کلید عوض می‌شود و restore-keys نزدیک‌ترین cache قبلی را بازیابی می‌کند. ما پوشه‌ی cache خود Composer (دانلودها) را cache می‌کنیم؛ composer install همچنان اجرا می‌شود و صحت نصب را تضمین می‌کند.
  • متغیرهای env در سطح job بر مقادیر .env اولویت دارند، چون Laravel متغیرهای محیطی موجود را با مقدار فایل .env بازنویسی نمی‌کند.
  • concurrency اجرای قدیمی روی همان برنچ را لغو می‌کند و در دقیقه‌های runner صرفه‌جویی می‌شود.
  • environment: production اجازه می‌دهد قوانین حفاظتی (reviewer اجباری، محدودیت برنچ) و secretهای مخصوص آن محیط اعمال شوند.
  • tag تصویر = github.sha: تغییرناپذیر و قابل ردیابی تا کامیت؛ همان tag روی staging و production می‌رود.

اکشن‌های شخص ثالث را دست‌کم با major version (@v4) و در محیط‌های حساس با commit SHA کامل pin کنید؛ tag یک action ممکن است جابه‌جا شود و کد مخرب در Pipeline شما اجرا کند. همچنین مراقب رویداد pull_request_target باشید: در context مخزن اصلی و با دسترسی به secretها اجرا می‌شود و checkout کردن کد PR از fork در آن یک آسیب‌پذیری شناخته‌شده است.

اجزای اصلی را بتوانید نام ببرید: Workflow → Event (on) → Job → Step → Action/Run، به‌علاوه‌ی Runner (ماشین اجراکننده)، needs (وابستگی و ترتیب jobها)، matrix، services، secrets و environment.

معادل در GitLab CI

در GitLab، Pipeline در فایل .gitlab-ci.yml در ریشه‌ی مخزن تعریف می‌شود. مفاهیم معادل‌اند ولی نام‌ها فرق دارند: stages ترتیب اجرا را تعیین می‌کنند، jobهای یک stage موازی اجرا می‌شوند و هر job روی یک GitLab Runner (معمولاً با executor داکر) داخل image مشخص‌شده اجرا می‌شود.

# .gitlab-ci.yml
stages: [quality, test, build, deploy]

default:
  image: registry.example.com/ci/php:8.3   # image آماده با extensionها و Composer

variables:
  COMPOSER_CACHE_DIR: "$CI_PROJECT_DIR/.composer-cache"

.composer: &composer
  cache:
    key:
      files: [composer.lock]
    paths: [.composer-cache/]
  before_script:
    - composer install --no-interaction --prefer-dist --no-progress

pint:
  stage: quality
  <<: *composer
  script:
    - vendor/bin/pint --test

phpstan:
  stage: quality
  <<: *composer
  script:
    - vendor/bin/phpstan analyse --memory-limit=1G --no-progress

tests:
  stage: test
  <<: *composer
  parallel:
    matrix:
      - PHP_VERSION: ["8.3", "8.4"]
  image: registry.example.com/ci/php:$PHP_VERSION
  services:
    - name: mysql:8.0
      alias: mysql
  variables:
    MYSQL_DATABASE: testing
    MYSQL_ROOT_PASSWORD: password
    DB_CONNECTION: mysql
    DB_HOST: mysql          # در GitLab سرویس با alias در دسترس است، نه 127.0.0.1
    DB_DATABASE: testing
    DB_USERNAME: root
    DB_PASSWORD: password
  script:
    - cp .env.example .env
    - php artisan key:generate
    - php artisan migrate --force
    - php artisan test --log-junit report.xml
  artifacts:
    when: always
    reports:
      junit: report.xml

build-image:
  stage: build
  image: docker:27
  services: [docker:27-dind]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"

deploy-staging:
  stage: deploy
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  environment:
    name: staging
  script:
    - ./scripts/deploy.sh staging "$CI_COMMIT_SHA"

deploy-production:
  stage: deploy
  needs: [deploy-staging]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

Runner، Artifact و Cache

Runner

Runner ماشین یا عاملی است که jobها را اجرا می‌کند.

Hosted / Shared

  • توسط GitHub/GitLab مدیریت می‌شود؛ هر job روی ماشین تمیز و یک‌بارمصرف.
  • بدون نگهداری، ولی هزینه بر اساس دقیقه و دسترسی محدود به شبکه‌ی داخلی.

Self-hosted

  • روی زیرساخت خودتان؛ دسترسی به شبکه‌ی داخلی، سخت‌افزار دلخواه، cache محلی.
  • مسئولیت به‌روزرسانی، امنیت و ایزوله‌سازی با شماست. هرگز برای مخزن عمومی با PR از fork استفاده نکنید.

این دو هر دو «ذخیره‌ی فایل بین اجراها» به نظر می‌رسند، اما هدف و ضمانتشان کاملاً متفاوت است:

Secretها، Environment Protection و Branch Protection

مدیریت Secret

  • هرگز رمز، API key یا فایل .env واقعی را در مخزن commit نکنید؛ فقط .env.example بدون مقدار حساس.
  • Secretها را در بخش امن پلتفرم (GitHub Secrets، GitLab CI/CD Variables با گزینه‌ی Masked و Protected) یا یک Secret Manager بیرونی (Vault، AWS Secrets Manager) نگه دارید.
  • Secretها فقط از طریق env var به stepهایی که لازم دارند داده شوند، نه سراسری.
  • پلتفرم مقادیر secret را در لاگ ماسک می‌کند، اما اگر مقدار تبدیل شود (base64، بخشی از آن) ماسک کار نمی‌کند؛ پس هرگز آن را echo نکنید.
  • به‌جای کلیدهای بلندمدت ابری، از OIDC استفاده کنید: runner یک توکن کوتاه‌مدت از ارائه‌دهنده‌ی ابری می‌گیرد (در GitHub با permissions: id-token: write).
  • Secretها به‌طور پیش‌فرض به workflowهایی که از PR یک fork اجرا می‌شوند داده نمی‌شوند؛ این رفتار را دور نزنید.
  • Least privilege: کلید deploy فقط به همان سرور/محیط دسترسی داشته باشد و GITHUB_TOKEN با permissions محدود شود.
  • Secret scanning (مثل GitHub secret scanning یا gitleaks) را در pipeline و pre-commit فعال کنید.

اگر secretی نشت کرد (در commit یا لاگ)، حذف commit کافی نیست؛ تاریخچه‌ی git، forkها و cacheها ممکن است آن را نگه داشته باشند. اولین اقدام Revoke/Rotate فوری است، سپس پاک‌سازی تاریخچه و بررسی لاگ‌های دسترسی.

Environment Protection

در GitHub، یک Environment (مثلاً production) می‌تواند secretهای مخصوص خود و قوانین حفاظتی داشته باشد:

  • Required reviewers: job تا تأیید افراد مشخص متوقف می‌ماند (پیاده‌سازی Continuous Delivery).
  • Wait timer: تأخیر اجباری قبل از اجرا.
  • Deployment branches/tags: فقط از main یا tagهای v* اجازه‌ی deploy باشد.

در GitLab معادل آن Protected Environments و Protected Variables است؛ متغیر protected فقط در pipelineهای برنچ/tag محافظت‌شده در دسترس است، پس یک برنچ دلخواه نمی‌تواند secret تولید را بخواند.

Branch Protection و Required Checks

  • جلوگیری از push مستقیم به main؛ تغییر فقط از طریق PR/MR.
  • Required status checks: PR فقط وقتی merge می‌شود که jobهای مشخص (tests، phpstan، pint) سبز باشند.
  • برنچ PR باید با main به‌روز باشد (یا استفاده از merge queue تا ترکیب نهایی تست شود).
  • حداقل تعداد Approval، و رد شدن Approval با push جدید.
  • CODEOWNERS: review اجباری صاحبان بخش‌های حساس (مثلاً migrationها یا پیکربندی CI).
  • منع force-push و حذف برنچ اصلی؛ امضای commit در صورت نیاز.

Branch protection کنترل پیشگیرانه روی ورود کد است؛ Environment protection کنترل روی خروج کد به محیط‌ها. ترکیب این دو تضمین می‌کند هیچ کدی بدون review و تست سبز به main نمی‌رسد و هیچ deployی بدون مجوز به Production نمی‌رود.

محیط‌ها و Promotion

یک زنجیره‌ی معمول: local → CI → dev → staging → production. گاهی محیط‌های موقت Preview/Review App برای هر PR ساخته و بعد از merge حذف می‌شوند.

Promotion

Promotion یعنی همان artifact پس از موفقیت در یک محیط، به محیط بعدی «ترفیع» داده شود. چیزی که بین محیط‌ها فرق می‌کند فقط پیکربندی است (اصل سوم Twelve-Factor App: config در محیط، نه در کد).

  build ──► image:3f9c2ab
                 │
                 ├──► staging     (.env staging: DB_HOST=stg-db, APP_DEBUG=false)
                 │       │  smoke tests ✓  +  approval ✓
                 └──────►└──► production  (.env prod: DB_HOST=prod-db)
  • Parity: هرچه staging به production شبیه‌تر باشد، «روی staging کار می‌کرد» کمتر رخ می‌دهد. Docker به یکسان‌سازی runtime کمک زیادی می‌کند.
  • داده: کپی داده‌ی Production در staging باید ناشناس‌سازی (anonymize) شود.
  • Smoke test بعد از هر deploy: چند درخواست حیاتی (health check، login، صفحه‌ی اصلی) به‌صورت خودکار.
  • در Laravel، APP_ENV و APP_DEBUG=false در staging و production حتماً تنظیم شوند؛ APP_DEBUG=true در محیط عمومی جزئیات حساس را افشا می‌کند.

staging را با همان فرایند و اسکریپتی deploy کنید که production را؛ بدین ترتیب خود فرایند deploy هم ده‌ها بار قبل از Production تست می‌شود.

استراتژی‌های Deployment

Recreate

همه‌ی نمونه‌های نسخه‌ی قدیم متوقف و سپس نسخه‌ی جدید راه‌اندازی می‌شود. ساده‌ترین روش است و هیچ‌وقت دو نسخه هم‌زمان اجرا نمی‌شوند، اما Downtime دارد. برای ابزار داخلی یا وقتی دو نسخه نمی‌توانند هم‌زمان کار کنند مناسب است.

Rolling Update

نمونه‌ها یکی‌یکی (یا دسته‌دسته) با نسخه‌ی جدید جایگزین می‌شوند و Load Balancer فقط به نمونه‌های سالم ترافیک می‌دهد. پیش‌فرض Kubernetes Deployment است (maxSurge/maxUnavailable). بدون Downtime و بدون نیاز به ظرفیت دوبرابر، اما در طول rollout دو نسخه هم‌زمان سرویس می‌دهند و rollback هم یک rolling دیگر است.

Blue-Green

دو محیط کامل و یکسان: Blue (فعلی، زنده) و Green (نسخه‌ی جدید). نسخه‌ی جدید روی Green مستقر و تست می‌شود و سپس Router/Load Balancer یک‌باره ترافیک را به Green می‌برد. Rollback = برگرداندن سوییچ به Blue (چند ثانیه).

             ┌──► Blue  (v1)  ◄── ترافیک فعلی
  Router ────┤
             └──► Green (v2)  ◄── تست، سپس سوییچ

هزینه‌ی آن ظرفیت دوبرابر و چالش پایگاه‌داده‌ی مشترک است: هر دو نسخه به یک دیتابیس وصل‌اند، پس schema باید با هر دو سازگار باشد.

Canary Release

نسخه‌ی جدید ابتدا برای درصد کوچکی از ترافیک (مثلاً ۱٪ ← ۵٪ ← ۲۵٪ ← ۱۰۰٪) فعال می‌شود و در هر مرحله متریک‌ها (نرخ خطا، latency، متریک کسب‌وکاری) با نسخه‌ی قدیم مقایسه می‌شوند. اگر بدتر بود، به‌صورت خودکار یا دستی برمی‌گردد. ریسک را به کمترین تعداد کاربر محدود می‌کند، اما به routing وزن‌دار (Ingress، service mesh) و Monitoring دقیق نیاز دارد.

Feature Flags (Feature Toggles)

کد جدید deploy می‌شود ولی پشت یک شرط خاموش است و در زمان اجرا (بدون deploy مجدد) برای همه، گروهی از کاربران یا درصدی روشن می‌شود. بدین ترتیب Deployment از Release جدا می‌شود. در Laravel، پکیج رسمی Laravel Pennant این کار را انجام می‌دهد:

<?php
use Laravel\Pennant\Feature;
use Illuminate\Support\Lottery;

// AppServiceProvider::boot()
Feature::define('new-checkout', fn (User $user) => match (true) {
    $user->isInternal() => true,
    default => Lottery::odds(1, 20),   // حدود ۵٪ کاربران

// در کد
if (Feature::active('new-checkout')) {
    return $this->newCheckout($cart);

return $this->legacyCheckout($cart);

Pennant نتیجه‌ی ارزیابی را برای هر scope (مثلاً کاربر) ذخیره می‌کند تا هر کاربر تجربه‌ی ثابتی داشته باشد.

استقرار بدون Downtime در Laravel

روش کلاسیک روی سرورهای VM (که Deployer و Envoyer هم از آن استفاده می‌کنند) release directory + symlink است. هر release در پوشه‌ی جداگانه آماده می‌شود و در انتها یک symlink به‌صورت اتمیک به آن اشاره می‌کند. وب‌سرور همیشه از current سرو می‌کند.

/var/www/app
├── current  ──►  releases/20261107103000      (symlink)
├── releases
│   ├── 20261105091500
│   ├── 20261106140000
│   └── 20261107103000
│       ├── storage  ──►  ../../shared/storage
│       └── .env     ──►  ../../shared/.env
└── shared
    ├── storage/          (لاگ‌ها، فایل‌های آپلود، sessionهای فایلی)
    └── .env

مراحل

  1. ساخت پوشه‌ی جدید در releases/ و قرار دادن کد (git clone یا انتقال artifact ساخته‌شده در CI).
  2. نصب وابستگی‌ها: composer install --no-dev --optimize-autoloader --no-interaction (asset فرانت ترجیحاً در CI build شده است).
  3. لینک کردن منابع مشترک: storage و .env از shared/.
  4. php artisan migrate --force — گزینه‌ی --force لازم است چون Laravel در محیط production برای اجرای migration تأیید تعاملی می‌خواهد.
  5. php artisan optimize — cache کردن config، route، view و event برای کارایی.
  6. سوییچ اتمیک symlink current به release جدید.
  7. Reload کردن PHP-FPM (نه restart) تا OPcache کد جدید را بارگذاری کند.
  8. php artisan queue:restart (یا horizon:terminate) تا workerها با کد جدید بالا بیایند.
  9. حذف releaseهای قدیمی (مثلاً نگه داشتن ۵ تای آخر برای rollback).
#!/usr/bin/env bash
set -euo pipefail

APP=/var/www/app
RELEASE=$APP/releases/$(date +%Y%m%d%H%M%S)

mkdir -p "$RELEASE"
tar -xzf /tmp/build.tar.gz -C "$RELEASE"          # artifact ساخته‌شده در CI

cd "$RELEASE"
composer install --no-dev --optimize-autoloader --no-interaction --prefer-dist

rm -rf storage
ln -s "$APP/shared/storage" storage
ln -s "$APP/shared/.env" .env

php artisan migrate --force
php artisan optimize

# سوییچ اتمیک: ابتدا لینک موقت، سپس rename (rename در یک filesystem اتمیک است)
ln -sfn "$RELEASE" "$APP/current_tmp"
mv -Tf "$APP/current_tmp" "$APP/current"

sudo systemctl reload php8.3-fpm
php artisan queue:restart

# نگه داشتن ۵ release آخر
ls -1dt "$APP"/releases/* | tail -n +6 | xargs -r rm -rf

چرا این جزئیات مهم‌اند؟

  • ln -sfn به‌تنهایی اتمیک نیست (ابتدا لینک قبلی را حذف و سپس لینک جدید می‌سازد)؛ ترکیب لینک موقت + mv -T که از rename() استفاده می‌کند اتمیک است.
  • OPcache و realpath cache: با opcache.validate_timestamps=0 در Production، PHP تغییر فایل‌ها را نمی‌بیند؛ reload کردن FPM لازم است. در Nginx هم با fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name; مسیر واقعی (بعد از resolve شدن symlink) به PHP داده می‌شود.
  • queue:restart: workerها فرایندهای بلندمدت‌اند و کد قدیمی را در حافظه دارند. این دستور یک سیگنال در cache ثبت می‌کند؛ هر worker بعد از اتمام job فعلی خارج می‌شود و Supervisor/systemd آن را با کد جدید بالا می‌آورد. پس driver cache باید بین سرورها مشترک باشد (مثلاً Redis).
  • config:cache: بعد از cache شدن config، فایل .env دیگر خوانده نمی‌شود و env() بیرون از فایل‌های config/ مقدار null برمی‌گرداند؛ پس در کد همیشه از config() استفاده کنید.
  • ترتیب migrate و switch: migration قبل از سوییچ اجرا می‌شود، پس برای چند ثانیه کد قدیم روی schema جدید کار می‌کند. migration باید backward-compatible باشد (بخش بعد).

ابزارها

Deployer
ابزار PHP متن‌باز با recipe آماده برای Laravel (recipe/laravel.php)؛ ساختار releases/shared/current، dep deploy و dep rollback را پیاده می‌کند.
Envoyer
سرویس تجاری رسمی Laravel برای zero-downtime deployment با همین الگو، به‌همراه health check و rollback از طریق داشبورد.

task runner لاراول با سینتکس شبیه Blade برای اجرای دستورات روی سرورها از طریق SSH؛ خودش ساختار release را تحمیل نمی‌کند.
Forge / Cloud / Vapor
سرویس‌های رسمی provisioning و میزبانی که deploy را خودکار می‌کنند.

Maintenance Mode در برابر Zero-Downtime

php artisan down برنامه را در حالت نگهداری (پاسخ 503) قرار می‌دهد؛ گزینه‌ی --secret اجازه‌ی دسترسی توسعه‌دهنده را با یک توکن می‌دهد و --render یک view از پیش رندرشده نمایش می‌دهد. این روش برای تغییرات بزرگ و ناسازگار قابل قبول است، اما هدف استقرار zero-downtime این است که به آن نیازی نباشد. در محیط چندسروری، driver حالت نگهداری را می‌توان روی cache تنظیم کرد تا روی همه‌ی سرورها اعمال شود.

در دنیای container، معادل همین الگو rolling update در Kubernetes یا ECS است: image جدید ساخته می‌شود، podهای جدید پس از گذراندن readiness probe ترافیک می‌گیرند و podهای قدیمی با SIGTERM به‌آرامی خاموش می‌شوند. migration معمولاً به‌صورت یک Job جداگانه (نه در entrypoint هر container) اجرا می‌شود.

اگر پرسیدند «چرا بعد از deploy کد قدیمی هنوز اجرا می‌شود؟» سه مظنون اصلی: OPcache (FPM reload نشده)، queue workerها (queue:restart اجرا نشده) و cacheهای Laravel (config/route cache از release قبلی یا نیاز به اجرای مجدد optimize).

Migrationهای امن و Rollback

در هر استقرار بدون Downtime، دوره‌ای وجود دارد که کد نسخه‌ی قدیم و جدید هم‌زمان با یک دیتابیس کار می‌کنند (rolling، blue-green، canary یا حتی چند ثانیه بین migrate و switch). پس هر تغییر schema باید با هر دو نسخه‌ی کد سازگار باشد.

الگوی Expand / Contract (Parallel Change)

هر تغییر ناسازگار به چند deploy کوچک و سازگار شکسته می‌شود. مثال: تغییر نام ستون name به full_name.

  1. Expand: ستون جدید full_name را nullable اضافه کن. کد را طوری deploy کن که در هر دو ستون بنویسد ولی هنوز از name بخواند.
  2. Migrate data: داده‌های قدیمی را به‌صورت دسته‌ای (chunk) در ستون جدید کپی کن (با job یا command، نه یک UPDATE عظیم که جدول را قفل کند).
  3. Switch reads: کد را deploy کن که از full_name بخواند (و همچنان در هر دو بنویسد).
  4. Contract: بعد از اطمینان، نوشتن در name را حذف کن و در deploy بعدی ستون name را drop کن.
<?php
// مرحله‌ی Expand — سازگار با کد قدیم
return new class extends Migration {
    public function up(): void
    {
        Schema::table('users', function (Blueprint $table) {
            $table->string('full_name')->nullable()->after('name');
        });
    }
};

// Backfill دسته‌ای (در یک command یا job جداگانه)
User::query()
    ->whereNull('full_name')
    ->chunkById(1000, function ($users) {
        foreach ($users as $user) {
            $user->updateQuietly(['full_name' => $user->name]);
        }
    });

Eloquent وقتی ستونی را که در مدل وجود ندارد نمی‌خواند مشکلی ندارد، اما اگر ستونی که کد قدیم هنوز در INSERT استفاده می‌کند drop شود، کد قدیم در همان چند ثانیه‌ی deploy خطا می‌دهد. ترتیب همیشه: اول کد، بعد schema برای حذف‌ها؛ اول schema، بعد کد برای افزودن‌ها.

استراتژی‌های Rollback

  • Rollback کد: در الگوی symlink، برگرداندن current به release قبلی (dep rollback)؛ در container، deploy مجدد tag قبلی image (kubectl rollout undo). چون artifactها تغییرناپذیرند، این کار سریع و قابل اعتماد است.
  • Roll forward: به‌جای برگشت، یک اصلاح سریع (hotfix) از همان pipeline منتشر می‌شود. وقتی pipeline سریع است و تغییرات کوچک‌اند، اغلب گزینه‌ی ترجیحی است.
  • Feature flag kill switch: سریع‌ترین «rollback»؛ قابلیت معیوب بدون deploy خاموش می‌شود.
  • Rollback دیتابیس: متد down() و migrate:rollback در Production خطرناک است، چون ممکن است داده‌ی نوشته‌شده بعد از deploy از بین برود (مثلاً drop ستون جدید). با Expand/Contract، کد قدیم روی schema جدید هم کار می‌کند و نیازی به rollback دیتابیس نیست.
  • قبل از migrationهای پرخطر backup بگیرید و بازیابی آن را تمرین کرده باشید.

جمله‌ی کلیدی برای پاسخ: «کد را می‌توان برگرداند، داده را نه. بنابراین migrationها را طوری طراحی می‌کنیم که هیچ‌وقت لازم نباشد برگردند: افزایشی، سازگار با نسخه‌ی قبلی، و حذف‌ها با تأخیر در deploy بعدی.»

Versioning، Tag و Release

Semantic Versioning (SemVer)

قالب MAJOR.MINOR.PATCH:

  • MAJOR: تغییر ناسازگار با نسخه‌ی قبلی (breaking change) در API عمومی.
  • MINOR: قابلیت جدید سازگار با قبل.
  • PATCH: رفع باگ سازگار با قبل.
  • پیش‌انتشار: 2.0.0-rc.1، 2.0.0-beta.2. نسخه‌ی 0.x یعنی API هنوز پایدار نیست.

محدودیت‌های Composer مستقیماً روی SemVer بنا شده‌اند: ^11.0 یعنی >=11.0 <12.0 و ~11.2 یعنی >=11.2 <12.0. همین دلیل اهمیت رعایت SemVer در پکیج‌هاست.

Tag و Release

git tag -a v1.4.0 -m "Release 1.4.0"     # annotated tag (نویسنده، تاریخ، پیام)
git push origin v1.4.0                    # می‌تواند pipeline انتشار را trigger کند
  • از annotated tag برای release استفاده کنید؛ tag نباید بعد از انتشار جابه‌جا شود.
  • Pipeline می‌تواند با push یک tag به شکل v* فعال شود و image را با tag نسخه منتشر کند.
  • برای اپلیکیشن‌های وب داخلی (نه کتابخانه)، بسیاری از تیم‌ها به‌جای SemVer از SHA کامیت یا CalVer (تاریخ‌محور) استفاده می‌کنند؛ مهم یکتایی و قابل ردیابی بودن است.

Changelog و Conventional Commits

با قرارداد Conventional Commits (feat:، fix:، chore:، و BREAKING CHANGE: یا feat!:) می‌توان نسخه‌ی بعدی و changelog را خودکار تولید کرد (ابزارهایی مثل release-please یا semantic-release): fix ← PATCH، feat ← MINOR، breaking ← MAJOR. فایل CHANGELOG.md برای انسان نوشته می‌شود (قالب «Keep a Changelog»: Added / Changed / Fixed / Removed / Security) و نباید فقط dump لاگ git باشد.

feat(orders): add bulk export to CSV
fix(auth): prevent session fixation on login
feat(api)!: remove deprecated v1 endpoints

BREAKING CHANGE: /api/v1/* endpoints are removed, use /api/v2.

متریک‌های DORA و Trunk-Based Development

چهار متریک DORA

پژوهش DORA (DevOps Research and Assessment) چهار متریک را معرفی کرد که با هم سرعت (throughput) و پایداری (stability) تحویل نرم‌افزار را می‌سنجند. یافته‌ی مهم این پژوهش: تیم‌های برتر در هر دو بُعد هم‌زمان بهترند؛ سرعت و پایداری با هم در تضاد نیستند.

متریک‌ها برای بهبود فرایند تیم‌اند، نه ارزیابی افراد. اگر هدف شوند (Goodhart's Law)، تیم‌ها آن‌ها را بازی می‌دهند؛ مثلاً deployهای خالی برای بالا بردن frequency.

Trunk-Based Development

همه‌ی توسعه‌دهندگان مستقیماً روی trunk (main) یا روی برنچ‌های بسیار کوتاه‌عمر (چند ساعت تا یکی دو روز) کار می‌کنند و دست‌کم روزانه merge می‌کنند. این در واقع شرط لازم برای CI به معنای واقعی است.

  • کار ناتمام پشت Feature Flag merge می‌شود.
  • تغییرات بزرگ با Branch by Abstraction انجام می‌شوند: ابتدا یک interface روی پیاده‌سازی قدیم، سپس پیاده‌سازی جدید پشت همان interface، و در نهایت سوییچ و حذف قدیمی.
  • release از روی trunk (یا یک release branch کوتاه که فقط hotfix می‌گیرد).

Trunk-Based

  • برنچ‌های کوتاه، merge روزانه
  • conflict کم، بازخورد سریع
  • نیازمند تست خودکار قوی و Feature Flag
  • مناسب SaaS و Continuous Delivery

GitFlow

  • برنچ‌های develop، feature/*، release/*، hotfix/*
  • برنچ‌های طولانی، merge دیر و پرتعارض
  • مناسب نرم‌افزار نسخه‌دار با چند نسخه‌ی پشتیبانی‌شده
  • با CI/CD سریع در تضاد است

رابطه‌ی Trunk-Based با CI: «Integration» یعنی ادغام در trunk مشترک. اگر کد روزها در feature branch بماند، هر چقدر هم روی آن build خودکار اجرا شود، با کد بقیه یکپارچه نشده است. پس Trunk-Based Development شیوه‌ی عملی اجرای CI است.

Anti-patternهای Pipeline و GitOps

Anti-patternهای رایج

  • Flaky tests: تست‌هایی که بدون تغییر کد گاهی رد و گاهی قبول می‌شوند. اعتماد به pipeline را از بین می‌برند و تیم عادت می‌کند «دوباره اجرا کن». علت‌های رایج در Laravel: وابستگی به زمان واقعی (به‌جای $this->travelTo() یا Carbon::setTestNow())، وابستگی به ترتیب اجرای تست‌ها و داده‌ی باقی‌مانده (به‌جای RefreshDatabase)، فراخوانی سرویس خارجی واقعی (به‌جای Http::fake())، داده‌ی تصادفی بدون seed، و race condition در تست‌های موازی. درمان: قرنطینه‌ی موقت و رفع ریشه‌ای، نه نادیده گرفتن.
  • Pipeline کند: اگر بازخورد بیش از حدود ۱۰ دقیقه طول بکشد، توسعه‌دهنده سراغ کار دیگری می‌رود و context switch گران می‌شود. راه‌حل: cache، اجرای موازی jobها، تست موازی (php artisan test --parallel)، اجرای تست‌های کند/E2E در مرحله‌ی جدا.
  • مراحل دستی: «بعد از deploy یادت باشد cache را پاک کنی» یعنی دیر یا زود فراموش می‌شود. هر کار تکراری باید در اسکریپت باشد.
  • build جداگانه برای هر محیط: نقض «build once, deploy many».
  • نادیده گرفتن شکست: continue-on-error: true روی تست‌ها، || true در اسکریپت، یا merge با build قرمز.
  • Secret در مخزن یا لاگ.
  • Pipeline خارج از کد: پیکربندی کلیک‌شده در UI که نسخه‌بندی و review نمی‌شود؛ به‌جایش Pipeline as Code.
  • وابستگی شناور: composer update در CI به‌جای composer install از روی lock، یا image پایه با tag latest؛ build غیرقابل‌تکرار می‌شود.
  • Staging متفاوت با Production: SQLite در staging و MySQL در production، یا نسخه‌ی متفاوت PHP.

GitOps

GitOps مدلی برای Continuous Deployment (به‌ویژه در Kubernetes) است که در آن Git تنها منبع حقیقت (single source of truth) برای وضعیت مطلوب زیرساخت و برنامه است. وضعیت به‌صورت declarative (مانیفست‌های Kubernetes، Helm chart، Kustomize) در یک مخزن نگهداری می‌شود و یک agent داخل کلاستر (مثل Argo CD یا Flux) به‌طور مداوم وضعیت واقعی را با Git مقایسه و همگام (reconcile) می‌کند.

  CI: test ─► build image:sha ─► PR در مخزن config (image tag = sha)
                                              │ merge
                                              ▼
  Kubernetes cluster ◄── pull & reconcile ── Argo CD / Flux  (مقایسه‌ی مداوم Git با کلاستر)

Push-based (CI/CD کلاسیک)

  • Pipeline با credential کلاستر دستور deploy را می‌فرستد.
  • CI باید به Production دسترسی داشته باشد.
  • تغییر دستی روی کلاستر (drift) تشخیص داده نمی‌شود.

Pull-based (GitOps)

  • agent داخل کلاستر تغییرات را از Git می‌کشد.
  • credential کلاستر بیرون از آن نیست.
  • drift تشخیص و اصلاح می‌شود؛ تاریخچه و audit در Git؛ rollback = git revert.

سوالات تشریحی

Continuous Integration، Continuous Delivery و Continuous Deployment را تعریف و با هم مقایسه کنید.

Continuous Integration: روشی که در آن توسعه‌دهندگان تغییرات کوچک خود را مکرراً (حداقل روزانه) در شاخه‌ی اصلی مشترک ادغام می‌کنند و هر ادغام به‌صورت خودکار build و تست می‌شود. هدف: کشف سریع خطاهای یکپارچه‌سازی و نگه داشتن main در وضعیت سالم.

Continuous Delivery: ادامه‌ی CI؛ هر تغییری که از Pipeline عبور کند، artifact قابل‌انتشار تولید می‌کند و به‌طور خودکار تا محیط staging مستقر و تست می‌شود. انتشار در Production با یک تأیید دستی (یک کلیک) انجام می‌شود.

Continuous Deployment: حذف همان تأیید دستی؛ هر تغییر سبز به‌طور خودکار به Production می‌رود.

  • تفاوت اصلی Delivery و Deployment: وجود یا عدم وجود گیت انسانی قبل از Production. در هر دو، کد همیشه قابل‌انتشار است.
  • پیش‌نیازهای Continuous Deployment: تست خودکار بسیار قابل اعتماد، Monitoring و Alerting، rollback سریع، Feature Flag برای جدا کردن release از deploy و migrationهای backward-compatible.
  • انتخاب: سازمان‌های دارای الزامات قانونی یا نیاز به هماهنگی کسب‌وکاری معمولاً Continuous Delivery را انتخاب می‌کنند؛ تیم‌های SaaS بالغ به Continuous Deployment می‌رسند.

جمع‌بندی: CI دغدغه‌ی کیفیت ادغام است، Delivery دغدغه‌ی آمادگی دائمی برای انتشار، و Deployment دغدغه‌ی اتوماسیون کامل انتشار.

چرا تغییرات کوچک و deploy مکرر ریسک را کاهش می‌دهد؟ آیا deploy بیشتر به معنای خرابی بیشتر نیست؟

پاسخ کوتاه: ریسک هر deploy به اندازه‌ی تغییر (batch size) وابسته است، نه به تعداد deployها.

  • Blast radius کوچک: deploy با چند commit فقط چند نقطه‌ی احتمالی خرابی دارد؛ release ماهانه با صدها تغییر، ترکیب‌های پیش‌بینی‌نشده‌ی زیادی دارد.
  • تشخیص سریع: اگر بعد از یک deploy کوچک نرخ خطا بالا رفت، مقصر تقریباً مشخص است؛ MTTR پایین می‌آید.
  • Rollback ساده: برگرداندن یک تغییر کوچک اثر جانبی کمی دارد.
  • حلقه‌ی بازخورد کوتاه: توسعه‌دهنده وقتی هنوز context را دارد از مشکل مطلع می‌شود.
  • تمرین فرایند: وقتی deploy روزانه انجام شود، خودکار، قابل اعتماد و کم‌استرس می‌شود؛ deployهای نادر دستی و پراشتباه می‌مانند.
  • Review بهتر: PRهای کوچک واقعاً بررسی می‌شوند.

پژوهش DORA هم نشان می‌دهد تیم‌هایی که بیشتر deploy می‌کنند، Change Failure Rate پایین‌تر و زمان بازیابی کوتاه‌تری دارند؛ یعنی سرعت و پایداری مکمل‌اند. شرط آن اتوماسیون، تست خودکار و Monitoring است؛ deploy مکرر دستی و بدون تست واقعاً خطرناک است.

یک Pipeline کامل برای یک پروژه‌ی Laravel طراحی کنید. چه مراحلی دارد و ترتیب آن‌ها بر چه اساسی است؟

ترتیب مراحل بر اساس اصل fail fast است: بررسی‌های سریع و ارزان اول، کارهای کند و پرهزینه بعد، و هر مرحله فقط وقتی اجرا شود که پیش‌نیازش سبز باشد.

  1. Checkout کد.
  2. نصب وابستگی‌ها با cache: composer install --prefer-dist --no-interaction از روی composer.lock (هرگز update) و npm ci؛ cache با کلید hash فایل lock.
  3. Code style: vendor/bin/pint --test.
  4. Static analysis: PHPStan با Larastan (با baseline برای پروژه‌ی قدیمی).
  5. تست‌ها: php artisan test با سرویس MySQL هم‌نسخه‌ی Production، به‌صورت matrix روی نسخه‌های PHP پشتیبانی‌شده؛ گزارش JUnit و coverage به‌عنوان artifact.
  6. امنیت: composer audit، npm audit، secret scanning و اسکن image.
  7. Build artifact: Docker image (یا آرشیو release شامل public/build) با tag برابر SHA کامیت، push به registry. فقط روی main.
  8. Deploy staging خودکار + smoke test.
  9. Deploy production با همان artifact، پس از approval (Continuous Delivery) یا خودکار.

نکات طراحی: مراحل 3 تا 6 به هم وابسته نیستند و موازی اجرا می‌شوند؛ build فقط به همه‌ی آن‌ها needs دارد. با concurrency اجراهای قدیمی لغو می‌شوند. secretها فقط در jobهای deploy و در scope محیط مربوط تعریف می‌شوند. هدف زمانی کل بازخورد PR زیر حدود ۱۰ دقیقه است.

تفاوت Artifact و Cache در CI را توضیح دهید و برای هرکدام در یک پروژه‌ی Laravel مثال بزنید.

Artifact خروجی یک job است که برای استفاده در jobهای بعدی همان pipeline یا برای نگهداری و دانلود ذخیره می‌شود و وجودش تضمین‌شده است. Cache داده‌ای است که برای تسریع اجراهای بعدی نگه داشته می‌شود و ممکن است وجود نداشته باشد (best effort).

  • مثال Artifact: خروجی npm run build (پوشه‌ی public/build) که job بسته‌بندی release به آن نیاز دارد؛ گزارش JUnit تست‌ها؛ گزارش coverage؛ فایل tar نهایی release.
  • مثال Cache: پوشه‌ی cache دانلودهای Composer با کلید hashFiles('composer.lock')، cache npm، cache لایه‌های Docker (type=gha).

Secretها را در Pipeline چگونه مدیریت می‌کنید؟ اگر یک API key در لاگ CI یا تاریخچه‌ی git نشت کند چه اقدامی انجام می‌دهید؟

اصول مدیریت secret:

  • هیچ secretی در مخزن نباشد؛ فقط .env.example. فایل .env در .gitignore.
  • نگهداری در مخزن امن پلتفرم (GitHub Secrets/Environment Secrets، GitLab Masked & Protected Variables) یا Secret Manager (Vault).
  • Scope محدود: secret تولید فقط در environment production که قوانین حفاظتی دارد؛ در دسترس PRهای fork نباشد.
  • Least privilege: کلید deploy فقط برای یک سرور/محیط؛ permissions حداقلی برای GITHUB_TOKEN.
  • ترجیح credential کوتاه‌مدت با OIDC به کلید بلندمدت.
  • عدم چاپ secret در لاگ (ماسک کردن خودکار با تبدیل مقدار دور زده می‌شود).
  • Secret scanning در CI و pre-commit hook.

واکنش به نشت (به ترتیب):

  1. Revoke و rotate فوری کلید؛ این مهم‌ترین قدم است، چون باید فرض کنیم کلید دیده شده است.
  2. به‌روزرسانی مقدار جدید در Secret store و deploy مجدد سرویس‌های وابسته.
  3. بررسی لاگ‌های دسترسی سرویس مربوطه برای استفاده‌ی غیرمجاز در بازه‌ی نشت.
  4. پاک کردن لاگ CI و در صورت نیاز بازنویسی تاریخچه‌ی git (مثلاً با git filter-repo)؛ اما این جایگزین rotate نیست، چون clone و forkها ممکن است آن را داشته باشند.
  5. Postmortem: چرا رخ داد و چه کنترلی (scanning، ماسک، review) جلوی تکرارش را می‌گیرد.
یک workflow در GitHub Actions با push روی هر برنچ، composer update اجرا می‌کند، secret را echo می‌کند، تست‌ها را با continue-on-error اجرا می‌کند و با git pull روی سرور deploy می‌کند. این workflow چه مشکلاتی دارد و چگونه اصلاحش می‌کنید؟

workflow مورد بحث:

on: [push]
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: composer update
      - run: echo "Using key ${{ secrets.PROD_API_KEY }}"
      - run: php artisan test
        continue-on-error: true
      - run: ssh deploy@prod "cd /var/www && git pull && php artisan migrate"

مشکلات و اصلاح:

  1. composer update به‌جای composer install: نسخه‌های جدیدتر از lock نصب می‌شوند؛ build غیرقابل‌تکرار و کد تست‌شده با کد Production متفاوت است. اصلاح: composer install --no-interaction --prefer-dist و cache با hash فایل lock.
  2. چاپ secret در لاگ: حتی با ماسک، الگوی خطرناکی است. secret فقط به‌صورت env به step لازم داده شود.
  3. continue-on-error: true روی تست‌ها: تست قرمز جلوی deploy را نمی‌گیرد؛ عملاً تست بی‌اثر است. باید حذف شود.
  4. deploy روی هر push به هر برنچ: هر feature branch مستقیماً Production را تغییر می‌دهد. deploy باید job جداگانه با needs، شرط if: github.ref == 'refs/heads/main' و environment: production با approval باشد.
  5. php artisan migrate بدون --force در production منتظر تأیید تعاملی می‌ماند و در عمل اجرا نمی‌شود.
  6. deploy با git pull در پوشه‌ی زنده: Downtime و حالت نیمه‌به‌روز؛ composer install، optimize، reload FPM و queue:restart ندارد؛ rollback ندارد. اصلاح: release directory + symlink (Deployer) یا image تغییرناپذیر.
  7. نبود مراحل کیفیت: Pint، PHPStan، سرویس دیتابیس برای تست، composer audit، و همچنین .env و key:generate برای تست.
  8. بدون permissions و concurrency: توکن با دسترسی پیش‌فرض و احتمال دو deploy هم‌زمان.

نسخه‌ی اصلاح‌شده دو job دارد: test روی push و pull_request، و deploy با needs: test، شرط برنچ main، environment: production و اسکریپت deploy اتمیک.

استراتژی‌های Rolling، Blue-Green و Canary را مقایسه کنید. هرکدام در چه شرایطی مناسب‌تر است؟

Rolling: نمونه‌ها به‌تدریج با نسخه‌ی جدید جایگزین می‌شوند و Load Balancer فقط به نمونه‌های سالم (readiness) ترافیک می‌دهد. نیاز به ظرفیت اضافه‌ی کمی دارد و پیش‌فرض Kubernetes است. عیب: در طول rollout دو نسخه هم‌زمان سرویس می‌دهند و rollback هم تدریجی است.

Blue-Green: دو محیط کامل؛ نسخه‌ی جدید روی محیط غیرفعال مستقر و تست می‌شود، سپس ترافیک یک‌باره سوییچ می‌شود. Rollback در چند ثانیه با برگرداندن سوییچ. عیب: هزینه‌ی زیرساخت دوبرابر (حداقل موقتاً)، و دیتابیس مشترک باید با هر دو نسخه سازگار باشد؛ sessionها و jobهای در حال اجرا هم باید مدیریت شوند.

Canary: نسخه‌ی جدید به درصد کمی از ترافیک داده و با مقایسه‌ی متریک‌ها (نرخ خطا، p95 latency، متریک کسب‌وکاری) مرحله‌به‌مرحله افزایش می‌یابد. کمترین تعداد کاربر در معرض ریسک قرار می‌گیرد. عیب: نیازمند routing وزن‌دار، Monitoring دقیق با تفکیک نسخه، و پیچیدگی عملیاتی.

مراحل یک Deployment بدون Downtime برای اپلیکیشن Laravel روی سرور را توضیح دهید. هر مرحله چرا لازم است؟

الگوی استاندارد (Deployer/Envoyer): پوشه‌های releases/، shared/ و symlink current.

  1. ساخت release جدید در پوشه‌ی جدا؛ release فعلی دست‌نخورده سرویس می‌دهد.
  2. composer install --no-dev --optimize-autoloader: بدون پکیج‌های توسعه و با classmap بهینه.
  3. لینک storage و .env از shared تا آپلودها، لاگ‌ها و پیکربندی بین releaseها حفظ شوند.
  4. php artisan migrate --force؛ --force چون production تأیید تعاملی می‌خواهد. migration باید با کد قدیم سازگار باشد، چون تا سوییچ، کد قدیم روی schema جدید اجرا می‌شود.
  5. php artisan optimize: cache کردن config، route، view و event.
  6. سوییچ اتمیک symlink (لینک موقت + mv -T) تا هیچ درخواستی به نیمه‌ی راه نخورد.
  7. reload PHP-FPM: با opcache.validate_timestamps=0 فایل‌های جدید دیده نمی‌شوند؛ reload به‌صورت graceful درخواست‌های جاری را قطع نمی‌کند. در Nginx از $realpath_root استفاده شود.
  8. php artisan queue:restart: workerها کد قدیم را در حافظه دارند؛ پس از اتمام job جاری خارج و توسط Supervisor با کد جدید راه‌اندازی می‌شوند.
  9. health check / smoke test و پاک کردن releaseهای قدیمی (نگه داشتن چند عدد برای rollback).

Rollback: برگرداندن symlink به release قبلی + reload FPM + queue:restart؛ چون migrationها backward-compatible هستند، نیاز به rollback دیتابیس نیست.

یک سناریو: باید ستون name جدول users (با ۲۰ میلیون رکورد) را به full_name تغییر نام دهید، بدون Downtime و در حالی که rolling deploy دارید. چه می‌کنید؟

مشکل: renameColumn در یک migration، کد نسخه‌ی قدیم را که هنوز روی برخی سرورها اجرا می‌شود فوراً می‌شکند؛ روی جدول بزرگ هم ممکن است قفل طولانی ایجاد کند.

راه‌حل: الگوی Expand/Contract در چند deploy:

  1. Deploy 1 (Expand): migration افزودن ستون nullable full_name. کد جدید در هر دو ستون می‌نویسد (مثلاً در یک model event یا accessor/mutator) و هنوز از name می‌خواند. این deploy با کد قدیم کاملاً سازگار است.
  2. Backfill: یک artisan command یا job که با chunkById و دسته‌های کوچک (مثلاً ۱۰۰۰ تایی)، با فاصله و قابلیت ادامه، full_name را از name پر کند؛ نه یک UPDATE سنگین که جدول را قفل و replication را عقب بیندازد.
  3. Deploy 2: خواندن از full_name؛ همچنان نوشتن در هر دو (تا اگر rollback شد، نسخه‌ی قبلی داده‌ی درست داشته باشد).
  4. Deploy 3: توقف نوشتن در name؛ در صورت نیاز تبدیل full_name به NOT NULL.
  5. Deploy 4 (Contract): drop ستون name، پس از اطمینان از اینکه هیچ کد، گزارش یا سرویس دیگری از آن استفاده نمی‌کند.

نکات تکمیلی: روی جدول بزرگ، رفتار DDL موتور (Online DDL در MySQL 8 یا ابزارهایی مثل gh-ost/pt-online-schema-change) را بررسی کنید؛ backup بگیرید؛ replication lag را مانیتور کنید. هزینه‌ی این روش، چند deploy و کمی کد موقت است، در عوض در هر لحظه rollback کد امن است و هیچ‌وقت نیاز به rollback دیتابیس پیدا نمی‌شود.

بلافاصله بعد از یک deploy، نرخ خطای 500 در Production بالا رفته است. به‌عنوان مسئول deploy قدم‌به‌قدم چه می‌کنید؟

اولویت: کاهش اثر روی کاربر (mitigate)، نه پیدا کردن ریشه.

  1. تأیید و ارتباط: با داشبورد (نرخ خطا، latency) و error tracker (Sentry) تأیید کنید که شروع مشکل با زمان deploy منطبق است. در کانال incident اعلام کنید و deployهای دیگر را متوقف کنید.
  2. Mitigation سریع:
    • اگر تغییر پشت Feature Flag است: خاموش کردن flag (سریع‌ترین).
    • در غیر این صورت rollback به artifact قبلی: dep rollback/سوییچ symlink + reload FPM + queue:restart، یا kubectl rollout undo، یا برگرداندن سوییچ blue-green، یا توقف canary.
    • اگر migration ناسازگار اجرا شده، rollback کد کافی نیست؛ اینجاست که اهمیت migrationهای backward-compatible معلوم می‌شود.
  3. تأیید بازیابی: بررسی متریک‌ها تا بازگشت به حالت عادی.
  4. تحلیل: روی release معیوب در staging یا با لاگ‌ها و stack traceها ریشه را پیدا کنید (کلید config جدید که در production تنظیم نشده، cache کهنه، وابستگی، کوئری کند و…).
  5. Roll forward: اصلاح با تست رگرسیون جدید از مسیر عادی pipeline (نه hotfix دستی روی سرور).
  6. Postmortem بدون سرزنش: چرا تست‌ها یا canary آن را نگرفتند؟ اقدامات اصلاحی مثل تست جدید، smoke test بعد از deploy، rollback خودکار بر اساس نرخ خطا.

این سناریو مستقیماً روی دو متریک DORA اثر دارد: Change Failure Rate و Time to Restore.

Feature Flag چیست و چگونه «Deployment» را از «Release» جدا می‌کند؟ مزایا و معایب آن را بنویسید.

تعریف: Feature Flag یک شرط در کد است که مسیر اجرای یک قابلیت را در زمان اجرا و بدون deploy مجدد کنترل می‌کند. مقدار آن از پیکربندی، دیتابیس یا سرویس مدیریت flag خوانده می‌شود و می‌تواند به کاربر، گروه یا درصدی از ترافیک وابسته باشد.

جدایی Deploy و Release: Deploy یعنی قرار دادن کد روی سرور (رویداد فنی)؛ Release یعنی فعال کردن قابلیت برای کاربر (تصمیم کسب‌وکاری). با flag، کد ناتمام یا جدید خاموش deploy می‌شود و بعداً برای کارمندان، سپس ۵٪ کاربران و در نهایت همه روشن می‌شود.

if (Feature::active('new-checkout')) {   // Laravel Pennant
    return $this->newCheckout($cart);
}

مزایا:

  • امکان Trunk-Based Development: کد ناتمام بدون شکستن main merge می‌شود.
  • Kill switch: rollback آنی قابلیت معیوب.
  • انتشار تدریجی، تست در Production برای کاربران داخلی، A/B testing.

معایب:

  • بدهی فنی: flagهای قدیمی که پاک نمی‌شوند کد را پیچیده می‌کنند.
  • ترکیب‌های زیاد flagها، تست را دشوار می‌کند (هر دو مسیر باید تست شوند).
  • flag روی تغییرات schema کمکی نمی‌کند؛ migration همچنان باید سازگار باشد.

بهترین روش: هر flag مالک و تاریخ انقضا داشته باشد و پس از انتشار کامل حذف شود.

متریک‌های DORA را نام ببرید و توضیح دهید هرکدام چه چیزی را می‌سنجد و چگونه می‌توان آن را بهبود داد.

DORA چهار متریک برای سنجش عملکرد تحویل نرم‌افزار معرفی کرده است؛ دو تا سرعت و دو تا پایداری:

  1. Deployment Frequency: هر چند وقت یک‌بار با موفقیت در Production deploy می‌کنیم. بهبود: batch کوچک، اتوماسیون کامل deploy، حذف approvalهای غیرضروری.
  2. Lead Time for Changes: زمان از commit تا اجرا در Production. بهبود: pipeline سریع (cache، موازی‌سازی)، PRهای کوچک و review سریع، Trunk-Based Development.
  3. Change Failure Rate: درصد deployهایی که به خرابی، hotfix یا rollback منجر می‌شوند. بهبود: تست خودکار بهتر، static analysis، staging شبیه production، canary، migrationهای امن.
  4. Time to Restore Service: مدت زمان بازگرداندن سرویس پس از خرابی. بهبود: Monitoring و Alerting خوب (کاهش MTTD)، rollback یک‌کلیکی، Feature Flag، runbook.

نکته‌ی کلیدی: این چهار با هم معنا دارند. بالا بردن frequency با بالا رفتن failure rate پیشرفت نیست. پژوهش DORA نشان داده تیم‌های برتر در هر چهار متریک هم‌زمان بهترند. متریک‌ها برای بهبود فرایند تیم استفاده شوند، نه رتبه‌بندی افراد، وگرنه بازی داده می‌شوند.

Trunk-Based Development را با GitFlow مقایسه کنید. چرا گفته می‌شود Trunk-Based پیش‌نیاز CI واقعی است؟

Trunk-Based Development: همه روی یک شاخه‌ی اصلی کار می‌کنند و برنچ‌ها بسیار کوتاه‌عمرند (ساعت‌ها تا یکی دو روز). کار ناتمام پشت Feature Flag و تغییرات بزرگ با Branch by Abstraction انجام می‌شود.

GitFlow: مدل چندشاخه‌ای با main، develop، feature/*، release/* و hotfix/*. feature branchها ممکن است هفته‌ها زنده بمانند و release از طریق برنچ release آماده می‌شود.

چرا پیش‌نیاز CI است: «Integration» یعنی ادغام کد با کد بقیه‌ی تیم در شاخه‌ی مشترک. اجرای تست روی یک feature branch جدا، فقط آن برنچ را تست می‌کند، نه ترکیبش با کار بقیه. هرچه برنچ طولانی‌تر بماند، یکپارچه‌سازی دیرتر و دردناک‌تر است. پس بدون merge مکرر به trunk، فقط «build خودکار» داریم، نه Continuous Integration.

تیم شما با «Flaky test» مواجه است و توسعه‌دهندگان عادت کرده‌اند pipeline را دوباره اجرا کنند. علت‌های احتمالی در Laravel و راه‌حل شما چیست؟

تعریف: تست flaky بدون تغییر کد، گاهی قبول و گاهی رد می‌شود. خطر اصلی‌اش از بین رفتن اعتماد به pipeline است: وقتی قرمز شدن «عادی» شود، شکست‌های واقعی هم نادیده گرفته می‌شوند.

علت‌های رایج:

  • زمان: وابستگی به now()، تغییر روز یا timezone. راه‌حل: $this->travelTo(...) یا Carbon::setTestNow().
  • وضعیت مشترک و ترتیب: داده‌ی باقی‌مانده از تست دیگر. راه‌حل: trait RefreshDatabase، عدم استفاده از state استاتیک.
  • سرویس خارجی: فراخوانی واقعی API. راه‌حل: Http::fake()، Queue::fake()، Mail::fake()، Http::preventStrayRequests().
  • داده‌ی تصادفی: factory که گاهی مقدار مرزی یا تکراری unique تولید می‌کند.
  • ترتیب نتایج: فرض ترتیب در کوئری بدون orderBy.
  • Race condition: در تست‌های موازی یا async، یا انتظار با sleep.

فرایند:

  1. شناسایی با گزارش تاریخچه‌ی تست‌ها (کدام تست با کد یکسان نتیجه‌ی متفاوت دارد).
  2. قرنطینه‌ی موقت (خارج کردن از required checks) با ثبت تیکت و مالک؛ نه حذف بی‌صدا.
  3. بازتولید با اجرای مکرر یا ترتیب تصادفی، و رفع ریشه.
  4. سیاست تیمی: retry خودکار راه‌حل نیست و فقط مشکل را پنهان می‌کند.
اصل «Build once, deploy many» را توضیح دهید. Promotion بین محیط‌ها چگونه باید انجام شود و تفاوت محیط‌ها کجا تعریف می‌شود؟

تعریف: artifact قابل‌استقرار (مثلاً Docker image یا آرشیو release) فقط یک بار در CI ساخته و با شناسه‌ی تغییرناپذیر (SHA کامیت یا نسخه) در registry ذخیره می‌شود. همان artifact ابتدا روی staging و پس از موفقیت روی production مستقر می‌شود.

چرا:

  • چیزی که تست شده دقیقاً همان چیزی است که منتشر می‌شود؛ build مجدد ممکن است وابستگی، image پایه یا ابزار build متفاوتی بگیرد.
  • rollback سریع: artifact قبلی آماده است.
  • ردیابی: از روی نسخه‌ی در حال اجرا، commit و PR مشخص است.

تفاوت محیط‌ها: فقط در پیکربندی، که طبق اصل Twelve-Factor در محیط اجرا تزریق می‌شود (env vars، secretها، فایل .env مشترک در سرور، ConfigMap/Secret در Kubernetes)، نه در کد یا image. بنابراین image نباید .env داشته باشد و config:cache باید در محیط مقصد (زمان deploy یا start) اجرا شود.

Promotion: deploy خودکار به staging ← smoke/acceptance test ← approval (در Continuous Delivery) ← deploy همان tag به production. هرگز «build برای production» جداگانه نداشته باشید.

GitOps چیست و چه تفاوتی با Pipelineهای push-based معمول دارد؟

تعریف: GitOps رویکردی است که در آن وضعیت مطلوب سیستم (مانیفست‌های Kubernetes، Helm/Kustomize، نسخه‌ی imageها) به‌صورت declarative در Git نگهداری می‌شود و یک agent داخل کلاستر (Argo CD، Flux) به‌طور مداوم وضعیت واقعی را با Git مقایسه و reconcile می‌کند.

جریان کار: CI کد را تست و image را با tag SHA می‌سازد، سپس tag جدید را در مخزن پیکربندی commit یا PR می‌کند. با merge، agent تغییر را می‌کشد و اعمال می‌کند.

تفاوت با push-based:

  • در push-based، CI با credential کلاستر مستقیماً kubectl apply یا SSH اجرا می‌کند؛ CI به Production دسترسی دارد و سطح حمله بزرگ‌تر است. در GitOps credential داخل کلاستر می‌ماند.
  • Drift detection: تغییر دستی روی کلاستر شناسایی و به وضعیت Git برگردانده می‌شود.
  • Audit و rollback: هر تغییر یک commit با نویسنده و review است؛ rollback = git revert.

معایب: بیشتر مناسب Kubernetes و زیرساخت declarative است؛ مدیریت secret در Git نیازمند ابزار جداگانه (Sealed Secrets، External Secrets) است؛ و migrationهای دیتابیس و کارهای ترتیبی نیاز به طراحی دقیق (hook یا Job) دارند.

بعد از deploy، تغییر یک مقدار در فایل .env سرور اثری ندارد و در جایی از کد env('PAYMENT_KEY') مقدار null برمی‌گرداند. علت چیست و درست آن چیست؟

علت: در فرایند deploy دستور php artisan optimize (یا config:cache) اجرا شده است. این دستور همه‌ی فایل‌های config/ را ارزیابی و نتیجه را در یک فایل PHP در bootstrap/cache ذخیره می‌کند. از آن پس Laravel فایل .env را بارگذاری نمی‌کند؛ بنابراین:

  • هر فراخوانی env() بیرون از فایل‌های config مقدار null (یا default) برمی‌گرداند (مگر آنکه آن متغیر واقعاً در environment فرایند تعریف شده باشد).
  • تغییر .env تا زمان cache مجدد config اثری ندارد.

راه درست:

<?php
// config/services.php
'payment' => [
    'key' => env('PAYMENT_KEY'),
],

// در کد برنامه
$key = config('services.payment.key');
  • env() فقط داخل فایل‌های config/؛ در بقیه‌ی کد همیشه config().
  • پس از تغییر پیکربندی، php artisan config:cache (یا deploy مجدد) و reload PHP-FPM و queue:restart، چون workerها هم config قدیمی را در حافظه دارند.
  • Larastan می‌تواند فراخوانی env() بیرون از config را گزارش کند و در CI جلوی آن را بگیرد.

خلاصه برای مرور سریع

تعاریف

  • CI: merge مکرر (روزانه) به main + build و تست خودکار هر تغییر.
  • Continuous Delivery: همیشه قابل‌انتشار؛ Production با تأیید دستی.
  • Continuous Deployment: هر تغییر سبز خودکار به Production.
  • Deploy ≠ Release: Feature Flag این دو را جدا می‌کند.

مراحل Pipeline (fail fast)

  • checkout ← install (cache) ← Pint ← PHPStan/Larastan ← tests + MySQL ← audit ← build image ← staging ← prod.
  • composer install نه update؛ npm ci نه npm install.
  • pint --test، phpstan analyse، php artisan test، composer audit.
  • Build once, deploy many؛ tag image = SHA.

GitHub Actions

  • Workflow ← on ← jobs ← steps (uses/run)؛ runner.
  • needs، strategy.matrix، services (localhost + port)، concurrency، permissions، environment.
  • cache key = OS + PHP + hashFiles('composer.lock').

GitLab CI

  • stages، rules، parallel.matrix، services با alias، when: manual، Protected/Masked variables.

Artifact vs Cache

  • Artifact = خروجی، تضمینی، بین jobها. نبودش ← شکست.
  • Cache = سرعت، best effort. نبودش ← کندی.

امنیت

  • Secret در store پلتفرم، scope محدود، OIDC، بدون echo.
  • نشت ← اول rotate، بعد پاک‌سازی.
  • Branch protection + required checks + CODEOWNERS؛ Environment protection + reviewers.
  • pin کردن actionها؛ مراقب pull_request_target.

استراتژی‌ها

  • Recreate: downtime، ساده.
  • Rolling: تدریجی، دو نسخه هم‌زمان، ارزان.
  • Blue-Green: سوییچ آنی، rollback آنی، هزینه ×۲.
  • Canary: درصد کم + مقایسه‌ی متریک؛ پیچیده.
  • Feature Flag (Pennant): kill switch؛ بدهی فنی.

Zero-downtime Laravel

  • releases/ + shared/ (storage، .env) + symlink current.
  • composer --no-dev -o ← migrate --force ← optimize ← switch اتمیک ← reload FPM ← queue:restart.
  • $realpath_root در Nginx؛ validate_timestamps=0 ⇒ reload لازم.
  • بعد از config:cache: env() فقط در config/.
  • Deployer (dep rollback)، Envoyer، Envoy.

Migration امن

  • Expand ← backfill (chunkById) ← switch reads ← Contract.
  • افزودن: اول schema بعد کد. حذف: اول کد بعد schema.
  • کد را می‌شود برگرداند، داده را نه ⇒ roll forward، بدون migrate:rollback در prod.

Release

  • SemVer: MAJOR (breaking)، MINOR (feature)، PATCH (fix).
  • Annotated tag، Conventional Commits، CHANGELOG.

DORA

  • سرعت: Deployment Frequency، Lead Time for Changes.
  • پایداری: Change Failure Rate، Time to Restore.

Anti-pattern

  • Flaky test، pipeline کند (>۱۰ دقیقه)، مرحله‌ی دستی، build per env، continue-on-error، secret در repo، latest.
  • Trunk-Based = شرط CI واقعی؛ GitFlow = برنچ‌های بلند.
  • GitOps: Git = منبع حقیقت؛ pull + reconcile (Argo CD/Flux)؛ drift detection.
