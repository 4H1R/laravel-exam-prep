System Design (Microservices)

روش ساختاریافته برای پاسخ به سوال‌های طراحی سیستم، مقایسه‌ی صادقانه‌ی Monolith و Microservices، ارتباط همزمان و ناهمزمان، Saga و Outbox، CQRS، الگوهای Resilience، Observability و امنیت بین سرویس‌ها؛ همراه با چهار طراحی نمونه با دیاگرام.

روش حل سوال طراحی

سوال System Design جواب «درست» واحد ندارد؛ ارزیاب دنبال روش فکر کردن است: اینکه نیازمندی‌ها را روشن کنید، با عدد تصمیم بگیرید، trade-offها را نام ببرید و گلوگاه‌ها را خودتان پیدا کنید. در پاسخ کتبی هم دقیقاً همین ترتیب را رعایت کنید تا جواب ساختار داشته باشد.

                                                        │

  1. شفاف‌سازی نیازمندی‌ها: سیستم دقیقاً چه کاری می‌کند و چه کاری نمی‌کند (scope). فرض‌هایتان را صریح بنویسید.
  2. تخمین ظرفیت (back-of-the-envelope): کاربر فعال روزانه (DAU)، QPS خواندن و نوشتن، نسبت read/write، حجم ذخیره‌سازی و پهنای باند.
  3. طراحی API: endpointهای اصلی، ورودی/خروجی، status code، صفحه‌بندی، idempotency.
  4. مدل داده: موجودیت‌ها، کلیدها، الگوی دسترسی (access pattern) و انتخاب پایگاه داده بر اساس همان الگو.
  5. طراحی سطح بالا: جعبه‌ها و فلش‌ها: کلاینت، LB، سرویس‌ها، cache، DB، صف.
  6. Deep dive: دو یا سه بخش حساس را عمیق کنید (تولید ID، cache، sharding، ترتیب پیام‌ها…).
  7. گلوگاه‌ها و trade-offها: SPOF، hot key، سازگاری داده، هزینه، و اینکه با ۱۰ برابر بار چه چیزی اول می‌شکند.

در پاسخ تشریحی، حتی اگر سوال فقط گفته «طراحی کنید»، با یک پاراگراف فرض‌ها و نیازمندی‌ها شروع کنید و یک تخمین عددی بیاورید. نوشتن «این سیستم read-heavy است پس…» نشان می‌دهد تصمیم‌ها مبتنی بر داده است، نه سلیقه.

هر انتخابی را با «چون…» همراه کنید و یک جایگزین را رد کنید: «Kafka را انتخاب کردم چون نیاز به replay داریم؛ RabbitMQ برای این مورد retention ندارد.» همین جمله‌ها نمره‌ی trade-off را می‌گیرند.

Monolith تا Microservices

Monolith
کل برنامه یک واحد deploy است، معمولاً با یک پایگاه داده‌ی مشترک. فراخوانی بین بخش‌ها یک function call درون‌پردازه‌ای است.
Modular Monolith
همچنان یک واحد deploy، اما کد به ماژول‌هایی با مرز صریح تقسیم شده: هر ماژول API عمومی (interface/event) دارد و جدول‌ها و کلاس‌های داخلی ماژول دیگر را مستقیم لمس نمی‌کند.
Microservices
مجموعه‌ای از سرویس‌های کوچک که مستقل deploy می‌شوند، هر کدام مالک داده‌ی خودشان‌اند، حول یک قابلیت کسب‌وکار (business capability) شکل گرفته‌اند و از طریق شبکه (HTTP/gRPC/پیام) با هم حرف می‌زنند.
Distributed Monolith
ضدالگو: سرویس‌ها جدا شده‌اند اما با هم deploy می‌شوند، دیتابیس مشترک دارند یا زنجیره‌ی فراخوانی همزمان طولانی دارند؛ یعنی همه‌ی هزینه‌های توزیع‌شدگی بدون هیچ‌کدام از مزایایش.

چه زمانی Microservices منطقی است؟

نشانه‌های مناسب بودن

  • چندین تیم مستقل که روی یک کدبیس به هم برخورد می‌کنند (Conway's Law).
  • بخش‌هایی با نیاز scaling بسیار متفاوت (مثلاً پردازش ویدیو در برابر پنل ادمین).
  • نیاز به deploy مستقل با چرخه‌ی انتشار متفاوت.
  • دامنه‌ی کسب‌وکار شناخته‌شده و مرزهای پایدار.
  • زیرساخت بالغ: CI/CD، container orchestration، monitoring و tracing.

نشانه‌های نامناسب بودن

  • تیم کوچک (مثلاً کمتر از ۱۰ نفر) یا استارتاپ در مرحله‌ی کشف محصول.
  • دامنه هنوز مبهم است؛ مرز اشتباه در microservices خیلی گران‌تر از monolith اصلاح می‌شود.
  • نیاز شدید به تراکنش‌های بین‌موجودیتی (مثلاً هسته‌ی حسابداری).
  • نبود مهارت DevOps و observability.
  • انگیزه فقط «مد روز» یا «رزومه» است.

Microservices مشکل سازمانی و مقیاس تیم را حل می‌کند، نه لزوماً مشکل performance. یک monolith خوب با cache، replica و horizontal scaling می‌تواند ترافیک بسیار بالایی را تحمل کند. اولین مایکروسرویس‌ها معمولاً latency را بیشتر می‌کنند.

Modular Monolith در Laravel

هر ماژول (مثلاً Modules/Billing) ServiceProvider، route، migration و مدل‌های خودش را دارد و فقط از طریق یک contract عمومی یا event با بقیه حرف می‌زند. این مرزها را می‌توان با تست معماری اجبار کرد تا بعداً جدا کردن یک ماژول به سرویس مستقل ساده باشد.

<?php
// Modules/Billing/Contracts/BillingService.php  — تنها راه ورود به ماژول
namespace Modules\Billing\Contracts;

interface BillingService
{
    public function chargeOrder(int $orderId, int $amountInRials): PaymentResult;
}

// Modules/Orders/... فقط به interface وابسته است، نه به مدل‌ها یا جدول‌های Billing
final class PlaceOrder
{
    public function __construct(private BillingService $billing) {}
}

// tests/Arch/ModulesTest.php  (Pest architecture test)
arch('orders must not touch billing internals')
    ->expect('Modules\Orders')
    ->not->toUse('Modules\Billing\Models');

مرزبندی سرویس‌ها و DDD

سخت‌ترین تصمیم در معماری میکروسرویس، محل مرزها است. مرز اشتباه یعنی سرویس‌هایی که برای هر کاری باید با هم حرف بزنند (chatty) و با هم تغییر کنند. ابزار اصلی برای پیدا کردن مرز درست، Domain-Driven Design است.

Bounded Context
محدوده‌ای که در آن یک مدل دامنه و یک زبان مشترک معنای یکتا دارند. معمولاً بهترین کاندیدا برای یک سرویس (یا یک ماژول).
Ubiquitous Language
واژگان مشترک بین متخصص کسب‌وکار و توسعه‌دهنده درون یک context.
Aggregate
خوشه‌ای از موجودیت‌ها با یک ریشه (aggregate root) که مرز سازگاری تراکنشی است؛ تغییرات درون یک aggregate اتمیک‌اند، بین aggregateها eventual.
Context Map
نقشه‌ی رابطه‌ی contextها: Customer/Supplier، Conformist، Anti-Corruption Layer، Shared Kernel، Published Language.
Domain Event
رخدادی معنادار برای کسب‌وکار که در گذشته اتفاق افتاده؛ با فعل گذشته نام‌گذاری می‌شود: OrderPlaced، PaymentFailed.

تلاش برای ساختن یک مدل Product «جامع» که همه استفاده کنند همان چیزی است که monolithها را درهم‌تنیده می‌کند. هر context نسخه‌ی خودش را دارد و فقط product_id مشترک است.

معیارهای یک مرز خوب

  • High cohesion, low coupling: چیزهایی که با هم تغییر می‌کنند کنار هم باشند.
  • حول business capability (Ordering، Payment) نه لایه‌ی فنی (سرویس «Database» یا «Validation») و نه موجودیت تکی (entity service مثل «CustomerService» که فقط CRUD است).
  • یک use case رایج نباید به فراخوانی همزمان ۵ سرویس نیاز داشته باشد.
  • هر سرویس توسط یک تیم قابل مالکیت باشد.

Database per Service

هر سرویس مالک انحصاری داده‌ی خودش است و سرویس دیگر فقط از طریق API یا event به آن دسترسی دارد. این یعنی می‌تواند schema را بدون هماهنگی تغییر دهد، نوع DB مناسب خودش را انتخاب کند (MySQL برای سفارش، Elasticsearch برای جستجو، Redis برای session) و مستقل scale شود.

  [Order Svc]        [Payment Svc]       [Catalog Svc]
       │                   │                   │
   (MySQL)            (PostgreSQL)      (Elasticsearch)
       ✗ ─── دسترسی مستقیم به DB سرویس دیگر ممنوع ─── ✗

هزینه‌ها و راه‌حل‌ها:

  • JOIN بین سرویس‌ها ممکن نیست → API Composition (یک لایه چند API را صدا می‌زند و نتیجه را ترکیب می‌کند) یا CQRS read model (سرویسی که با گوش دادن به eventها یک view denormalized می‌سازد).
  • تراکنش بین سرویس‌ها ممکن نیست → Saga.
  • داده‌ی تکراری (مثلاً نام مشتری در سرویس سفارش) → قابل قبول، به شرط مشخص بودن مالک اصلی و همگام‌سازی با event.

Shared Database بین سرویس‌ها رایج‌ترین دلیل distributed monolith است: یک تغییر schema همه را می‌شکند و هیچ سرویسی واقعاً مستقل deploy نمی‌شود. حداقل گام: schema جدا برای هر سرویس روی یک سرور مشترک، با کاربر DB جدا.

ارتباط همزمان و ناهمزمان

Synchronous (REST، gRPC)

  • فراخواننده منتظر پاسخ می‌ماند؛ مدل ساده‌ی request/response.
  • مناسب برای query و عملیاتی که کاربر همان لحظه نتیجه را لازم دارد.
  • Temporal coupling: اگر سرویس مقصد down باشد، فراخواننده هم شکست می‌خورد.
  • latency زنجیره جمع می‌شود و availability ضرب می‌شود.

Asynchronous (Queue، Pub/Sub، Stream)

  • فرستنده پیام را به broker می‌دهد و ادامه می‌دهد.
  • decoupling زمانی؛ جذب اوج بار (buffering)؛ fan-out آسان به چند مصرف‌کننده.
  • پیچیدگی: eventual consistency، ترتیب پیام، پیام تکراری، debug سخت‌تر.
  • مناسب برای side-effectها، کارهای طولانی و یکپارچه‌سازی بین contextها.

Command، Event، Query

  • Command (ChargePayment): درخواست انجام کار، یک گیرنده‌ی مشخص، ممکن است رد شود.
  • Event (PaymentCharged): اعلام یک واقعیت گذشته، فرستنده گیرنده‌ها را نمی‌شناسد، قابل رد شدن نیست.
  • Query: درخواست داده بدون side-effect؛ معمولاً همزمان.

دو شیوه‌ی محتوای event: Event Notification (فقط ID؛ گیرنده برای جزئیات API را صدا می‌زند → coupling دوباره) و Event-Carried State Transfer (داده‌ی لازم داخل event؛ گیرنده مستقل می‌ماند اما payload بزرگ‌تر و نسخه‌بندی schema مهم‌تر می‌شود).

قاعده‌ی عملی: Query همزمان، Command و side-effect ناهمزمان. هر جا کاربر منتظر نتیجه‌ی فوری نیست (ایمیل، گزارش، به‌روزرسانی search index) از صف استفاده کنید تا خرابی سرویس مقصد مستقیماً به کاربر نرسد.

RabbitMQ در برابر Kafka

هر دو «message broker» نامیده می‌شوند اما مدل ذهنی متفاوتی دارند: RabbitMQ یک صف هوشمند است که پیام را مسیریابی و پس از تحویل حذف می‌کند؛ Kafka یک لاگ توزیع‌شده‌ی ماندگار است که پیام را برای مدت مشخصی نگه می‌دارد و مصرف‌کننده‌ها خودشان جای خواندنشان را (offset) نگه می‌دارند.

Service Discovery

در محیط پویا (autoscaling، container) آدرس IP نمونه‌ها مدام تغییر می‌کند؛ پس سرویس‌ها باید یکدیگر را با نام پیدا کنند.

Client-side discovery

  • کلاینت از Service Registry (Consul، Eureka، etcd) لیست نمونه‌های سالم را می‌گیرد و خودش load balance می‌کند.
  • مزیت: یک hop کمتر، الگوریتم LB هوشمند.
  • عیب: منطق discovery باید در هر زبان/کلاینت پیاده شود.

Server-side discovery

  • کلاینت به یک آدرس ثابت (LB یا DNS) درخواست می‌دهد و LB نمونه را انتخاب می‌کند.
  • در Kubernetes: Service با نام DNS مثل orders.shop.svc.cluster.local.
  • مزیت: کلاینت ساده. عیب: یک hop و جزء زیرساختی بیشتر.

ثبت نمونه‌ها یا self-registration است (سرویس خودش را ثبت و heartbeat می‌فرستد) یا third-party registration (پلتفرم، مثل Kubernetes، این کار را انجام می‌دهد). Health check تضمین می‌کند ترافیک فقط به نمونه‌ی سالم برود.

تراکنش توزیع‌شده، Saga و Outbox

صورت مسئله

ثبت سفارش یعنی: ایجاد سفارش (Order DB)، کسر وجه (Payment DB) و رزرو موجودی (Inventory DB). در monolith یک DB::transaction کافی بود؛ اما با database-per-service، تراکنش ACID واحدی بین این سه وجود ندارد.

چرا 2PC معمولاً راه‌حل نیست؟

Two-Phase Commit یک coordinator دارد: فاز Prepare (همه رأی می‌دهند و قفل‌ها را نگه می‌دارند) و فاز Commit/Abort. مشکلات:

  • Blocking: اگر coordinator بعد از prepare از کار بیفتد، شرکت‌کننده‌ها با قفل‌های باز منتظر می‌مانند.
  • کاهش availability: همه‌ی شرکت‌کننده‌ها باید همزمان در دسترس باشند.
  • latency و نگه داشتن قفل در طول رفت‌وبرگشت شبکه.
  • بسیاری از تکنولوژی‌ها (Kafka به‌عنوان شرکت‌کننده‌ی XA، اکثر NoSQLها، APIهای HTTP خارجی) از آن پشتیبانی نمی‌کنند.

Saga

Saga دنباله‌ای از تراکنش‌های محلی است؛ هر مرحله تراکنش محلی خودش را commit و یک event/پیام منتشر می‌کند تا مرحله‌ی بعد آغاز شود. اگر مرحله‌ای شکست بخورد، تراکنش‌های جبرانی (compensating transactions) مراحل قبلی را به‌صورت معنایی خنثی می‌کنند (مثلاً «بازپرداخت»، نه rollback فیزیکی).

  • Compensatable: مراحلی که جبران دارند (رزرو موجودی ↔ آزادسازی).
  • Pivot: نقطه‌ی بی‌بازگشت؛ اگر موفق شود saga باید تا انتها برود (مثلاً capture پرداخت).
  • Retriable: مراحل بعد از pivot که باید آن‌قدر retry شوند تا موفق شوند (ارسال ایمیل تأیید).

نبود Isolation در Saga

Saga اتمیک است (به کمک جبران) اما Isolation ندارد: نتایج میانی برای دیگران قابل مشاهده‌اند. راهکارها:

  • Semantic lock: وضعیت PENDING روی سفارش تا کاربر/سرویس دیگر آن را نهایی فرض نکند.
  • Commutative updates: عملیاتی که ترتیبشان مهم نیست (افزایش/کاهش به‌جای set).
  • Reread value / version: قبل از به‌روزرسانی بررسی شود داده تغییر نکرده.
  • ترتیب مراحل: مراحلی که احتمال شکستشان بالاتر است را زودتر و قبل از pivot انجام دهید.

مسئله‌ی Dual Write و الگوی Transactional Outbox

کد زیر به‌ظاهر درست است اما دو سیستم (DB و broker) را بدون تراکنش مشترک می‌نویسد:

<?php
DB::transaction(function () use ($order) {
    $order->save();
});
$broker->publish('OrderCreated', $order->toArray()); // اگر اینجا crash شود؟ event گم می‌شود
// اگر publish داخل transaction باشد و commit شکست بخورد؟ event برای سفارشی که وجود ندارد!

Outbox: event را در همان تراکنش محلی در جدول outbox درج می‌کنیم. یک فرایند جدا (relay) رکوردهای outbox را خوانده و به broker می‌فرستد و علامت ارسال می‌زند. پس «تغییر داده» و «ثبت event» با هم atomic هستند.

CREATE TABLE outbox (
  id             BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  message_id     CHAR(36)     NOT NULL UNIQUE,   -- UUID برای dedupe در مصرف‌کننده
  aggregate_type VARCHAR(50)  NOT NULL,
  aggregate_id   VARCHAR(50)  NOT NULL,          -- به‌عنوان partition key
  type           VARCHAR(100) NOT NULL,
  payload        JSON         NOT NULL,
  created_at     TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  published_at   TIMESTAMP    NULL,
  INDEX idx_unpublished (published_at, id)
);
<?php
DB::transaction(function () use ($data) {
    $order = Order::create($data + ['status' => 'PENDING']);

    DB::table('outbox')->insert([
        'message_id'     => (string) Str::uuid(),
        'aggregate_type' => 'order',
        'aggregate_id'   => (string) $order->id,
        'type'           => 'OrderCreated',
        'payload'        => json_encode(['order_id' => $order->id, 'total' => $order->total]),
    ]);
});

// Relay (مثلاً یک command زمان‌بندی‌شده یا worker دائمی)
DB::table('outbox')->whereNull('published_at')->orderBy('id')->limit(100)
    ->lockForUpdate()->get()   // داخل transaction؛ یا SKIP LOCKED برای چند relay
    ->each(function ($row) use ($broker) {
        $broker->publish($row->type, $row->payload, key: $row->aggregate_id, id: $row->message_id);
        DB::table('outbox')->where('id', $row->id)->update(['published_at' => now()]);
    });
  • Polling publisher: ساده؛ بار polling روی DB و کمی تأخیر.
  • Transaction log tailing (CDC): ابزاری مثل Debezium binlog در MySQL یا WAL در PostgreSQL را می‌خواند و رکوردهای outbox را به Kafka می‌فرستد؛ تأخیر کم و بدون polling، اما زیرساخت بیشتر.
  • اگر relay بعد از publish و قبل از update کرش کند، پیام دوباره ارسال می‌شود؛ پس Outbox یعنی at-least-once و مصرف‌کننده باید idempotent باشد (الگوی Inbox: جدول processed_messages با کلید یکتای message_id).

زوج طلایی: Saga برای سازگاری بین سرویس‌ها + Outbox برای اینکه هر مرحله‌ی saga به‌صورت اتمیک «داده را تغییر دهد و پیام را منتشر کند» + Idempotent consumer برای تحمل پیام تکراری.

Idempotency و Eventual Consistency

تضمین‌های تحویل پیام

تضمینمعناچطور حاصل می‌شودریسک
At-most-onceصفر یا یک بارack قبل از پردازش؛ بدون retryاز دست رفتن پیام
At-least-onceیک بار یا بیشترack بعد از پردازش؛ retry در خطاپیام تکراری
Exactly-onceدقیقاً یک باردر حالت کلی end-to-end ممکن نیست؛ «effectively once» = at-least-once + پردازش idempotent—

چرا exactly-once delivery افسانه است؟ consumer پیام را پردازش می‌کند (مثلاً ایمیل می‌فرستد یا DB را به‌روز می‌کند) و قبل از ack کرش می‌کند. broker راهی ندارد بفهمد پردازش انجام شده یا نه؛ پس یا دوباره می‌فرستد (تکرار) یا نمی‌فرستد (احتمال گم شدن). Kafka قابلیت exactly-once را با idempotent producer و transaction ارائه می‌دهد، اما این تضمین فقط برای جریان «خواندن از Kafka → پردازش → نوشتن در Kafka» است؛ به‌محض اینکه side-effect بیرونی (DB دیگر، API پرداخت، ایمیل) وارد شود، باز هم به idempotency در سطح برنامه نیاز داریم.

Idempotent Consumer

<?php
public function handle(array $message): void
{
    DB::transaction(function () use ($message) {
        // کلید یکتا روی message_id؛ درج تکراری رد می‌شود
        $inserted = DB::table('processed_messages')->insertOrIgnore([
            'message_id'   => $message['id'],
            'processed_at' => now(),
        ]);

        if ($inserted === 0) {
            return; // قبلاً پردازش شده — بی‌صدا ack کن
        }

        Reservation::create([
            'order_id' => $message['order_id'],
            'sku'      => $message['sku'],
            'qty'      => $message['qty'],
        ]);
    });
}

نکته‌ی کلیدی: ثبت message_id و اثر کسب‌وکار در یک تراکنش انجام می‌شوند؛ اگر جدا باشند دوباره همان مشکل dual write پیش می‌آید. راه‌های دیگر idempotency: unique constraint طبیعی (یک رزرو به‌ازای هر order_id)، عملیات ذاتاً idempotent (SET status = 'PAID' به‌جای balance = balance - x) و شرط نسخه (WHERE version = ?).

Idempotency-Key در API

برای درخواست‌های غیر idempotent مثل POST /payments، کلاینت یک کلید یکتا در header Idempotency-Key می‌فرستد. سرور پاسخ اولین درخواست را با آن کلید ذخیره می‌کند و برای retryهای بعدی همان پاسخ را برمی‌گرداند، بدون اجرای دوباره. باید وضعیت «در حال پردازش» را هم مدیریت کرد (قفل روی کلید) تا دو درخواست همزمان با یک کلید هر دو اجرا نشوند، و کلید را به hash بدنه‌ی درخواست گره زد تا استفاده‌ی مجدد با بدنه‌ی متفاوت رد شود.

Eventual Consistency

در سیستم توزیع‌شده با پیام‌رسانی ناهمزمان، replicaها و read modelها پس از مدتی (معمولاً میلی‌ثانیه تا چند ثانیه) به حالت سازگار می‌رسند، به شرط اینکه نوشتن جدیدی نیاید. این انتخاب آگاهانه‌ای است: availability و latency بهتر در ازای کهنگی موقت داده.

  • در UX: وضعیت میانی را نشان دهید («سفارش شما در حال پردازش است») به‌جای وانمود به قطعیت.
  • Read-your-writes: پس از نوشتن، خواندن کاربر از منبع اصلی (primary یا سرویس مالک) انجام شود یا پاسخ نوشتن، داده‌ی جدید را برگرداند.
  • ترتیب پیام‌ها: eventها ممکن است خارج از ترتیب برسند؛ با partition key (Kafka) ترتیب را برای یک موجودیت حفظ کنید یا با شماره‌ی نسخه/timestamp در consumer، event قدیمی‌تر را نادیده بگیرید.
  • Reconciliation: یک job دوره‌ای که اختلاف داده‌ها بین سرویس‌ها را پیدا و اصلاح می‌کند؛ شبکه‌ی ایمنی در برابر باگ‌ها.

جمله‌ی کلیدی برای پاسخ: «در عمل هدف exactly-once processing است نه exactly-once delivery؛ یعنی تحویل at-least-once به‌همراه dedupe بر اساس message id یا idempotency key در همان تراکنشی که اثر کسب‌وکار ثبت می‌شود.»

CQRS و Event Sourcing

CQRS

Command Query Responsibility Segregation یعنی مدل نوشتن (commands، با قوانین دامنه و validation) از مدل خواندن (queries، بهینه برای نمایش) جدا شود. این جداسازی می‌تواند در سطح کد باشد (کلاس‌های جدا روی همان DB) یا در سطح ذخیره‌سازی (write DB نرمال‌شده + read store دی‌نرمال مثل Elasticsearch یا جدول‌های summary).

  • هر طرف مستقل scale و بهینه می‌شود (معمولاً خواندن خیلی بیشتر است).
  • queryهای پیچیده‌ی گزارش‌گیری روی DB تراکنشی فشار نمی‌آورند.
  • مدل نوشتن ساده و متمرکز بر قوانین دامنه می‌ماند.
  • راه‌حل طبیعی برای «JOIN بین سرویس‌ها» در microservices.

هزینه‌ها

  • eventual consistency بین نوشتن و خواندن (کاربر ممکن است بلافاصله تغییرش را نبیند).
  • زیرساخت و کد بیشتر: projector، rebuild، مانیتورینگ تأخیر.
  • برای CRUD ساده، پیچیدگی بی‌دلیل است.

Event Sourcing

به‌جای ذخیره‌ی وضعیت فعلی، دنباله‌ی همه‌ی رویدادهایی که وضعیت را ساخته‌اند به‌صورت append-only ذخیره می‌شود؛ وضعیت فعلی با replay کردن رویدادها (fold) به دست می‌آید. مثل دفتر کل حسابداری: موجودی ذخیره نمی‌شود، تراکنش‌ها ذخیره می‌شوند.

event_store (stream_id = account-42)
 v1  AccountOpened    {owner: "Ali"}
 v2  MoneyDeposited   {amount: 500}
 v3  MoneyWithdrawn   {amount: 120}
 v4  MoneyDeposited   {amount: 50}
                         ⇒ وضعیت فعلی: balance = 430
<?php
final class BankAccount
{
    private int $balance = 0;
    private int $version = 0;
    private array $pending = [];

    public static function fromHistory(iterable $events): self
    {
        $account = new self();
        foreach ($events as $event) {
            $account->apply($event);
        }
        return $account;
    }

    public function withdraw(int $amount): void
    {
        if ($amount > $this->balance) {
            throw new InsufficientFunds();          // قانون دامنه روی وضعیت فعلی
        }
        $this->record(new MoneyWithdrawn($amount));
    }

    private function record(object $event): void
    {
        $this->apply($event);
        $this->pending[] = $event;                  // ذخیره با شرط expected version
    }

    private function apply(object $event): void
    {
        match (true) {
            $event instanceof MoneyDeposited => $this->balance += $event->amount,
            $event instanceof MoneyWithdrawn => $this->balance -= $event->amount,
            default => null,
        };
        $this->version++;
    }
}
  • Optimistic concurrency: هنگام append، نسخه‌ی مورد انتظار چک می‌شود (unique روی stream_id, version).
  • Snapshot: برای streamهای طولانی، هر N رویداد یک snapshot ذخیره می‌شود تا replay از آن نقطه شروع شود.
  • Projection: read modelها از روی eventها ساخته می‌شوند و هر زمان می‌توان آن‌ها را از صفر بازسازی کرد.

چه زمانی ارزش دارد

  • نیاز ذاتی به audit trail کامل و غیرقابل تغییر (مالی، ledger، حقوقی).
  • queryهای زمانی: «وضعیت در تاریخ X چه بود؟»
  • دامنه‌ی پیچیده که خود رویدادها برای کسب‌وکار معنادارند.
  • نیاز به ساخت read modelهای جدید از تاریخچه‌ی گذشته.

چرا اغلب ارزش ندارد

  • Schema evolution سخت: eventهای قدیمی برای همیشه می‌مانند؛ نیاز به versioning و upcasting.
  • query روی وضعیت فعلی بدون projection ممکن نیست.
  • حذف داده‌ی شخصی (GDPR) در لاگ تغییرناپذیر؛ راهکار crypto-shredding.
  • منحنی یادگیری تیم و ابزار کمتر.

CQRS و Event Sourcing مستقل از هم‌اند. Event Sourcing تقریباً همیشه به CQRS نیاز دارد (برای query)، ولی CQRS بدون Event Sourcing بسیار رایج و کم‌هزینه‌تر است. هیچ‌کدام را برای کل سیستم اعمال نکنید؛ فقط برای bounded contextی که واقعاً لازم دارد.

الگوهای Resilience

در سیستم توزیع‌شده، خرابی استثنا نیست، قاعده است: شبکه قطع می‌شود، سرویس کند می‌شود، GC مکث می‌کند. خطرناک‌ترین حالت سرویس کند است نه سرویس مرده: درخواست‌ها منتظر می‌مانند، worker و connectionها پر می‌شوند و خرابی آبشاروار (cascading failure) به سرویس‌های بالادست سرایت می‌کند.

Payment کند (۳۰ ثانیه) ─► Order: همه‌ی PHP-FPM workerها منتظر ─► Gateway: صف و timeout
                                            ─► حتی endpointهایی که به Payment ربطی ندارند down می‌شوند

۱. Timeout

  • هر فراخوانی شبکه باید timeout داشته باشد؛ پیش‌فرض بسیاری از کلاینت‌ها بی‌نهایت یا خیلی طولانی است.
  • دو نوع: connect timeout (کوتاه، مثلاً ۱ ثانیه) و read/request timeout (بر اساس p99 سرویس مقصد).
  • Deadline propagation: اگر کل درخواست کاربر ۲ ثانیه بودجه دارد، فراخوانی‌های پایین‌دستی باید از بودجه‌ی باقی‌مانده استفاده کنند.

۲. Retry با Exponential Backoff و Jitter

  • فقط خطاهای گذرا (timeout، 503، 429، قطع اتصال) retry شوند؛ 400 و 422 هرگز.
  • فقط عملیات idempotent یا عملیات دارای idempotency key.
  • فاصله‌ها نمایی رشد کنند و jitter (تصادفی) داشته باشند تا همه‌ی کلاینت‌ها همزمان برنگردند (thundering herd).
  • retry فقط در یک لایه: اگر هر ۳ لایه ۳ بار retry کنند، سرویس انتهایی ۲۷ برابر بار می‌گیرد (retry storm). از retry budget (مثلاً حداکثر ۱۰٪ درخواست‌ها) استفاده کنید.
Full jitter:   sleep = random(0, min(cap, base × 2^attempt))
base = 100ms, cap = 5s  ⇒  attempt 1: 0–200ms، attempt 2: 0–400ms، attempt 3: 0–800ms …
<?php
use Illuminate\Http\Client\ConnectionException;
use Illuminate\Http\Client\RequestException;
use Illuminate\Support\Facades\Http;

$response = Http::baseUrl(config('services.inventory.url'))
    ->connectTimeout(1)          // ثانیه
    ->timeout(2)
    ->withHeaders(['Idempotency-Key' => $order->uuid])
    ->retry(
        3,
        fn (int $attempt) => random_int(0, min(2000, 100 * (2 ** $attempt))), // ms با jitter
        fn (Throwable $e) => $e instanceof ConnectionException
            || ($e instanceof RequestException && in_array($e->response->status(), [429, 502, 503, 504])),
        throw: false,
    )
    ->post('/reservations', $payload);

۳. Circuit Breaker

مثل فیوز برق: وقتی نرخ خطای یک وابستگی از آستانه گذشت، مدار باز می‌شود و فراخوانی‌ها بلافاصله با خطا یا fallback برمی‌گردند، بدون اینکه منتظر timeout بمانند؛ هم فراخواننده از هدر رفتن منابع نجات پیدا می‌کند و هم سرویس بیمار فرصت بهبود دارد.

         خطاها از آستانه گذشت
 ┌────────┐ ──────────────────► ┌────────┐
 │ CLOSED │                     │  OPEN  │  همه‌ی درخواست‌ها فوراً رد/fallback
 └────────┘ ◄──┐                └───┬────┘
      ▲        │ موفق                │ پس از cooldown (مثلاً ۳۰ ثانیه)
      │        │                    ▼
      │     ┌──┴────────┐ شکست  ┌───────────┐
      └─────│ موفقیت‌ها  │◄──────│ HALF-OPEN │  تعداد محدودی درخواست آزمایشی
            └───────────┘ ─────►└───────────┘ ──شکست──► OPEN
<?php
final class CircuitBreaker
{
    public function __construct(
        private string $service,
        private int $threshold = 5,
        private int $cooldown = 30,
    ) {}

    public function call(callable $action, callable $fallback): mixed
    {
        if (Cache::has("cb:{$this->service}:open")) {
            return $fallback();                       // OPEN: سریع شکست بخور
        }

        try {
            $result = $action();
            Cache::forget("cb:{$this->service}:failures");
            return $result;
        } catch (Throwable $e) {
            $failures = Cache::increment("cb:{$this->service}:failures");
            if ($failures >= $this->threshold) {
                // پس از انقضای کلید، درخواست بعدی نقش آزمایش half-open را دارد
                Cache::put("cb:{$this->service}:open", true, $this->cooldown);
                Cache::forget("cb:{$this->service}:failures");
            }
            return $fallback();
        }
    }
}

برای jobهای صف، Laravel middleware ThrottlesExceptions را دارد که پس از تعداد مشخصی exception، اجرای job را برای مدتی به تعویق می‌اندازد؛ رفتاری شبیه circuit breaker در سطح job.

۴. Bulkhead

مثل دیواره‌های ضدآب کشتی: منابع (thread pool، connection pool، worker، صف) برای هر وابستگی یا نوع کار جدا شوند تا خرابی یکی همه را غرق نکند. مثال: صف payments با workerهای اختصاصی جدا از صف emails؛ یا pool جدا برای فراخوانی سرویس گزارش‌گیری کند.

۵. Fallback و Graceful Degradation

  • داده‌ی cache‌شده‌ی کهنه (stale) به‌جای خطا: «پیشنهادهای محبوب» به‌جای «پیشنهاد شخصی‌سازی‌شده».
  • مقدار پیش‌فرض یا غیرفعال کردن قابلیت غیرحیاتی.
  • قبول درخواست و پردازش بعدی (صف) به‌جای رد کردن.

۶. Load Shedding و Rate Limiting

وقتی بار از ظرفیت بیشتر است، بهتر است بخشی از درخواست‌ها سریع با 503/429 رد شوند (ترجیحاً کم‌اهمیت‌ترها) تا اینکه همه کند شوند و سیستم کامل از دسترس خارج شود.

ترکیب استاندارد هر فراخوانی بیرونی: Timeout (همیشه) ← Retry محدود با backoff و jitter (فقط خطای گذرا و عملیات idempotent) ← Circuit Breaker (جلوگیری از فشار روی سرویس بیمار) ← Fallback (تجربه‌ی کاربری قابل قبول) و Bulkhead (محدود کردن شعاع آسیب).

Observability در سیستم توزیع‌شده

Monitoring می‌گوید چه چیزی خراب است (برای خرابی‌های شناخته‌شده)؛ Observability توانایی پاسخ به سوال‌های پیش‌بینی‌نشده درباره‌ی چرایی رفتار سیستم از روی خروجی‌هایش است. در microservices که یک درخواست از ده سرویس عبور می‌کند، بدون آن debug تقریباً غیرممکن است.

Correlation ID

شناسه‌ای یکتا که در لبه (gateway) برای هر درخواست ساخته یا از header ورودی خوانده می‌شود، در همه‌ی لاگ‌ها ثبت و به همه‌ی فراخوانی‌های HTTP و پیام‌های صف منتقل می‌شود؛ با یک جستجو همه‌ی لاگ‌های یک درخواست در همه‌ی سرویس‌ها پیدا می‌شود.

<?php
// app/Http/Middleware/CorrelationId.php
use Illuminate\Support\Facades\Context;

public function handle(Request $request, Closure $next): Response
{
    $id = $request->header('X-Correlation-ID') ?: (string) Str::uuid();

    // Context (Laravel 11+): به metadata لاگ‌ها اضافه و به jobهای dispatch‌شده منتقل می‌شود
    Context::add('correlation_id', $id);

    $response = $next($request);
    $response->headers->set('X-Correlation-ID', $id);
    return $response;
}

// هنگام صدا زدن سرویس دیگر
Http::withHeaders(['X-Correlation-ID' => Context::get('correlation_id')])
    ->get($url);

Distributed Tracing

  • Trace: کل سفر یک درخواست؛ Span: یک عملیات (فراخوانی HTTP، query، publish) با زمان شروع، مدت و parent.
  • انتشار context با استاندارد W3C Trace Context، header traceparent: 00-<trace-id>-<parent-span-id>-<flags>.
  • OpenTelemetry استاندارد بی‌طرف برای تولید و ارسال trace، metric و log است؛ backend قابل تعویض است.
  • Sampling: head-based (تصمیم در ابتدای درخواست، مثلاً ۱٪، ارزان) در برابر tail-based (تصمیم بعد از پایان؛ می‌تواند همه‌ی traceهای خطادار یا کند را نگه دارد اما گران‌تر).

متریک‌های کلیدی

  • RED برای سرویس‌ها: Rate (درخواست در ثانیه)، Errors (نرخ خطا)، Duration (توزیع latency، p50/p95/p99).
  • USE برای منابع: Utilization، Saturation، Errors.
  • متریک‌های صف: طول صف، سن قدیمی‌ترین پیام، consumer lag در Kafka.
  • SLI/SLO: شاخص (مثلاً درصد درخواست‌های زیر ۳۰۰ms) و هدف (۹۹٪ در ۳۰ روز)؛ هشدار بر اساس مصرف error budget.

استقرار و امنیت بین سرویس‌ها

Container و Kubernetes

Container برنامه و وابستگی‌هایش را در یک image تغییرناپذیر بسته‌بندی می‌کند تا در همه‌ی محیط‌ها یکسان اجرا شود. با ده‌ها سرویس و صدها container، به orchestrator نیاز است که زمان‌بندی، self-healing، scaling و rollout را انجام دهد؛ استاندارد عملی Kubernetes است.

Service Mesh

لایه‌ی زیرساختی که ارتباط سرویس‌به‌سرویس را از کد برنامه بیرون می‌کشد؛ معمولاً با یک sidecar proxy (مثل Envoy) کنار هر pod. نمونه‌ها: Istio، Linkerd.

┌──────── Pod A ────────┐            ┌──────── Pod B ────────┐
│ [order app] ◄► [proxy]│ ══ mTLS ══►│[proxy] ◄► [payment app]│
└───────────────────────┘            └───────────────────────┘
            ▲  control plane: سیاست‌ها، گواهی‌ها، routing  ▲
  • قابلیت‌ها: mTLS خودکار، retry/timeout/circuit breaking، traffic splitting برای canary، متریک و trace یکسان بدون تغییر کد.
  • هزینه: پیچیدگی عملیاتی، مصرف منابع و latency اضافه برای هر hop. برای چند سرویس معدود معمولاً زیادی است.

امنیت بین سرویس‌ها (Zero Trust)

فرض «شبکه‌ی داخلی امن است» غلط است؛ اگر یک سرویس نفوذ شود، مهاجم نباید بتواند آزادانه بقیه را صدا بزند. دو سوال جدا داریم: کدام سرویس صدا می‌زند (هویت سرویس) و از طرف کدام کاربر (هویت کاربر).

mTLS
TLS دوطرفه: هم سرور و هم کلاینت گواهی ارائه می‌کنند؛ ترافیک رمز می‌شود و هویت سرویس فراخواننده احراز می‌شود. مدیریت و چرخش گواهی‌ها سخت است؛ service mesh آن را خودکار می‌کند.
JWT Propagation
Gateway توکن کاربر را اعتبارسنجی می‌کند و آن را (یا یک توکن داخلی کوتاه‌عمر) به سرویس‌های پایین‌دست می‌فرستد. هر سرویس دوباره امضا را بررسی می‌کند (با کلید عمومی از JWKS) و فقط به claimها اعتماد می‌کند، نه به headerهای ساده مثل X-User-Id.
Token Exchange
تبدیل توکن بیرونی به توکن داخلی با audience و scope محدود به سرویس مقصد تا توکن دزدیده‌شده همه‌جا کار نکند.
Service Account / Client Credentials
برای فراخوانی‌هایی که از طرف کاربر نیستند (jobهای پس‌زمینه)، سرویس با OAuth2 client credentials توکن خودش را می‌گیرد.
  • اصل least privilege: هر سرویس فقط به endpointهای لازم دسترسی دارد (authorization policy در mesh یا NetworkPolicy در Kubernetes).
  • Secretها در vault یا Secret manager، نه در image یا repository؛ با چرخش دوره‌ای.
  • توکن‌های کوتاه‌عمر؛ authorization در سطح دامنه (مالکیت منبع) در خود سرویس، نه فقط در gateway.

پاسخ نمونه: «mTLS هویت و رمزنگاری در سطح سرویس را تأمین می‌کند و JWT هویت و مجوزهای کاربر را در زنجیره‌ی فراخوانی منتقل می‌کند؛ این دو مکمل‌اند نه جایگزین.»

Deep dives

  • 301 یا 302؟ 301 (دائمی) توسط مرورگر cache می‌شود: بار کمتر اما آمار کلیک از دست می‌رود و تغییر مقصد ممکن نیست. 302/307 برای آمار و کنترل.
  • Cache: توزیع کلیک‌ها power-law است؛ cache کردن بخش کوچکی از لینک‌های داغ اکثر ترافیک را پوشش می‌دهد. cache-aside با TTL؛ نتیجه‌ی «یافت نشد» را هم کوتاه‌مدت cache کنید (در برابر حمله با کدهای تصادفی) یا از Bloom filter استفاده کنید.
  • آمار: ثبت کلیک هرگز در مسیر redirect همزمان نباشد؛ event به Kafka و پردازش batch.
  • Sharding: بر اساس hash کد؛ چون همه‌ی lookupها با کد است، هر درخواست فقط به یک shard می‌رود.
  • سوءاستفاده: rate limit روی ساخت لینک، بررسی URL در لیست‌های بدافزار.

-- KEYS[1]=bucket key  ARGV: rate(token/s), capacity, now(ms), requested
local rate      = tonumber(ARGV[1])
local capacity  = tonumber(ARGV[2])
local now       = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local data   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts     = tonumber(data[2]) or now

tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)
local allowed = 0
if tokens >= requested then
  tokens = tokens - requested
  allowed = 1
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000))
return allowed
  • Fail-open یا fail-closed؟ اگر Redis در دسترس نباشد، معمولاً fail-open (اجازه‌ی عبور) تا خرابی limiter کل API را نخواباند؛ برای endpointهای حساس (login، OTP) fail-closed.
  • در Laravel، RateLimiter::for('api', fn (Request $r) => Limit::perMinute(60)->by($r->user()?->id ?: $r->ip())) و middleware throttle:api همین کار را با cache store مشترک (Redis) انجام می‌دهد.
  • چندمنطقه‌ای: شمارش محلی در هر region با همگام‌سازی تقریبی؛ دقت کامل سراسری به latency بین‌منطقه‌ای می‌ارزد.

<?php
final class OrderSaga
{
    public function onStockReserved(StockReserved $e): void
    {
        DB::transaction(function () use ($e) {
            $saga = SagaState::lockForUpdate()->findOrFail($e->orderId);
            if ($saga->state !== 'STARTED') {
                return;                                   // پیام تکراری یا خارج از ترتیب
            }
            $saga->update(['state' => 'STOCK_RESERVED']);
            Outbox::push('payment.commands', new AuthorizePayment(
                orderId: $e->orderId,
                amount: $saga->amount,
                idempotencyKey: "pay-{$e->orderId}",      // retry امن در Payment
            ));
        });
    }

    public function onPaymentFailed(PaymentFailed $e): void
    {
        DB::transaction(function () use ($e) {
            $saga = SagaState::lockForUpdate()->findOrFail($e->orderId);
            $saga->update(['state' => 'RELEASING_STOCK']);
            Outbox::push('inventory.commands', new ReleaseStock($e->orderId));
        });
    }
}
  • هر انتقال state و ارسال command در یک تراکنش محلی + outbox؛ هر handler با بررسی state فعلی idempotent است.
  • Timeout: اگر پاسخ Payment در زمان مشخص نیامد، saga به مسیر جبران می‌رود (با یک scheduled job که sagaهای معطل را پیدا می‌کند).
  • کاربر بلافاصله 202 Accepted و شناسه‌ی سفارش می‌گیرد و وضعیت را با polling یا WebSocket دنبال می‌کند.
  • رزرو موجودی با انقضا تا اگر saga گیر کرد، موجودی برای همیشه قفل نماند.

در سوال طراحی سفارش، سه نکته را حتماً بنویسید: چرا تراکنش توزیع‌شده (2PC) را انتخاب نکردید، جدول مراحل و جبران‌ها، و اینکه پیام‌ها با Outbox منتشر و با idempotency مصرف می‌شوند.

سوالات تشریحی

معماری Monolith و Microservices را تعریف و مقایسه کنید. در چه شرایطی مهاجرت به Microservices را پیشنهاد می‌کنید؟

تعریف: Monolith برنامه‌ای است که به‌صورت یک واحد build و deploy می‌شود و معمولاً یک پایگاه داده‌ی مشترک دارد. Microservices سبکی است که سیستم را به سرویس‌های کوچک، مستقل‌الاستقرار و حول قابلیت‌های کسب‌وکار تقسیم می‌کند؛ هر سرویس مالک داده‌ی خودش است و از طریق شبکه ارتباط برقرار می‌کند.

مقایسه:

  • سادگی: monolith در توسعه، تست، debug و deploy ساده‌تر است؛ microservices پیچیدگی شبکه، سازگاری داده و عملیات را اضافه می‌کند.
  • تراکنش: monolith از ACID محلی بهره می‌برد؛ microservices به Saga و eventual consistency نیاز دارد.
  • مقیاس‌پذیری: microservices امکان scale مستقل هر بخش را می‌دهد؛ monolith کل برنامه را scale می‌کند (که اغلب کافی است).
  • تیم: microservices استقلال تیم‌ها و deploy مستقل را ممکن می‌کند (Conway's Law).
  • Fault isolation: در microservices خرابی محدود می‌ماند، به شرط timeout، circuit breaker و bulkhead.

چه زمانی مهاجرت: وقتی چند تیم روی یک کدبیس به هم برخورد می‌کنند و چرخه‌ی انتشار کند شده، بخش‌هایی نیاز scaling یا فناوری بسیار متفاوت دارند، دامنه و مرزها پایدار شده‌اند و زیرساخت CI/CD، container orchestration و observability آماده است. برای تیم کوچک یا محصول در مرحله‌ی کشف، modular monolith انتخاب بهتری است.

روش: مهاجرت تدریجی با Strangler Fig، نه بازنویسی کامل؛ اول ماژولی با مرز روشن و ارزش بالا جدا شود. باید از distributed monolith (سرویس‌های جدا با DB مشترک یا deploy هماهنگ) پرهیز کرد چون هزینه‌های هر دو دنیا را دارد بدون مزایایشان.

یک monolith قدیمی Laravel داریم که توسعه‌اش کند شده است. چطور آن را بدون توقف سرویس به معماری سرویس‌گرا منتقل می‌کنید؟

رویکرد: مهاجرت تدریجی با الگوی Strangler Fig؛ بازنویسی یکباره ریسک بالا، توقف ارائه‌ی قابلیت جدید و احتمال شکست زیادی دارد.

  1. Modularize first: داخل همان monolith مرز ماژول‌ها (bounded contextها) را مشخص کنید؛ وابستگی‌های مستقیم بین ماژول‌ها را به interface و event تبدیل کنید و با تست معماری اجبار کنید. اغلب همین قدم بیشترین سود را دارد.
  2. Facade: یک reverse proxy یا API Gateway جلوی monolith قرار دهید تا امکان هدایت مسیر به مسیر وجود داشته باشد.
  3. انتخاب اولین سرویس: بخشی با وابستگی کم، مرز روشن و ارزش بالا (مثلاً Notification یا Search)، نه هسته‌ی پرریسک.
  4. انتقال داده: سرویس جدید DB خودش را دارد؛ در دوره‌ی گذار داده با event یا CDC همگام می‌شود تا مالکیت کامل منتقل شود. یک Anti-Corruption Layer مانع نشت مدل قدیمی می‌شود.
  5. هدایت ترافیک تدریجی: با feature flag یا canary درصدی از ترافیک به سرویس جدید؛ مقایسه‌ی نتایج (shadow traffic) و امکان rollback فوری در proxy.
  6. حذف کد قدیمی پس از پایداری و تکرار برای ماژول بعدی.
Client ─► Gateway ─┬─ /notifications ─► [Notification Svc] ─ own DB
                   └─ همه‌ی مسیرهای دیگر ─► [Legacy Monolith]

پیش‌نیازها: CI/CD مستقل، correlation id و tracing، تست قرارداد (contract test) بین monolith و سرویس جدید. ریسک‌ها: دوره‌ی طولانی دوگانگی داده و منطق، و وسوسه‌ی دسترسی سرویس جدید به DB قدیمی که باید از آن پرهیز شود.

الگوی Database per Service چیست و چرا توصیه می‌شود؟ گزارشی که به داده‌ی سفارش و مشتری از دو سرویس مختلف نیاز دارد را چطور پیاده می‌کنید؟

تعریف: هر سرویس مالک انحصاری داده‌ی خودش است و هیچ سرویس دیگری مستقیم به DB آن دسترسی ندارد؛ دسترسی فقط از طریق API یا event منتشرشده.

چرا:

  • Loose coupling: تغییر schema بدون هماهنگی با تیم‌های دیگر؛ deploy مستقل واقعی.
  • Polyglot persistence: انتخاب DB مناسب هر سرویس (رابطه‌ای برای سفارش، Elasticsearch برای جستجو).
  • scale و fault isolation مستقل؛ کوئری سنگین یک سرویس DB دیگری را کند نمی‌کند.

هزینه‌ها: JOIN و تراکنش بین سرویس‌ها ممکن نیست؛ داده‌ی تکراری و eventual consistency.

راه‌حل گزارش:

  • API Composition: یک لایه (BFF یا سرویس گزارش) از Order لیست سفارش‌ها و از Customer اطلاعات مشتری‌ها را (batch با لیست IDها، نه N+1 فراخوانی) می‌گیرد و در حافظه ترکیب می‌کند. ساده است اما برای داده‌ی حجیم، فیلتر و مرتب‌سازی روی فیلدهای دو طرف ناکارآمد است.
  • CQRS read model: سرویس گزارش با subscribe به OrderPlaced و CustomerUpdated یک جدول denormalized (یا data warehouse) می‌سازد که کوئری روی آن سریع است؛ هزینه، eventual consistency و نگهداری projector است.
  • برای تحلیل‌های سنگین: CDC از DBهای سرویس‌ها به یک data warehouse.

جمع‌بندی: برای صفحه‌ی جزئیات با داده‌ی کم API Composition؛ برای گزارش‌گیری با فیلتر و حجم بالا، read model.

ارتباط همزمان (Synchronous) و ناهمزمان (Asynchronous) بین سرویس‌ها را مقایسه کنید. در فرایند ثبت سفارش، کدام بخش‌ها را همزمان و کدام را ناهمزمان طراحی می‌کنید؟

همزمان (REST/gRPC): فراخواننده تا رسیدن پاسخ منتظر می‌ماند. ساده و قابل فهم است و پاسخ فوری می‌دهد، اما temporal coupling ایجاد می‌کند: اگر مقصد کند یا down باشد، فراخواننده هم آسیب می‌بیند. در زنجیره، latency جمع و availability ضرب می‌شود (پنج سرویس 99.9٪ ⇒ حدود 99.5٪).

ناهمزمان (صف، pub/sub، stream): فرستنده پیام را به broker می‌دهد و ادامه می‌دهد. decoupling زمانی، جذب اوج بار، fan-out به چند مصرف‌کننده و مقاومت در برابر خرابی موقت مقصد؛ در عوض eventual consistency، پیام تکراری یا خارج از ترتیب، و debug سخت‌تر.

در ثبت سفارش:

  • همزمان: اعتبارسنجی ورودی، خواندن قیمت فعلی (یا استفاده از snapshot قیمت در سبد) و ذخیره‌ی سفارش با وضعیت PENDING در سرویس Order؛ پاسخ 202 Accepted با شناسه‌ی سفارش.
  • ناهمزمان: رزرو موجودی، پرداخت (در قالب saga با پیام)، ارسال ایمیل/SMS، به‌روزرسانی search index و analytics، صدور فاکتور.
  • اگر کسب‌وکار نیاز دارد کاربر بلافاصله نتیجه‌ی پرداخت را ببیند، redirect به درگاه همزمان است اما تأیید نهایی (callback/webhook) ناهمزمان و idempotent پردازش می‌شود.

قاعده: query و آنچه کاربر همان لحظه لازم دارد همزمان (با timeout و circuit breaker)؛ side-effectها و هماهنگی بین contextها ناهمزمان (با outbox و consumer idempotent).

RabbitMQ و Kafka را مقایسه کنید. برای (الف) صف ارسال ایمیل و (ب) جریان رویدادهای سفارش که چند تیم مصرف می‌کنند، کدام را انتخاب می‌کنید و چرا؟

RabbitMQ: message broker مبتنی بر AMQP با مدل exchange، binding و queue. پیام به consumer push می‌شود و پس از ack حذف می‌شود. routing انعطاف‌پذیر (direct، topic، fanout، headers)، DLX، TTL و priority داخلی دارد. مناسب task queue و توزیع کار بین workerهای رقیب.

Kafka: لاگ توزیع‌شده‌ی append-only و ماندگار. topic به partition تقسیم می‌شود؛ ترتیب فقط درون partition تضمین است؛ consumerها pull می‌کنند و هر consumer group offset مستقل دارد؛ پیام‌ها تا پایان retention باقی می‌مانند و قابل replay‌اند. throughput بسیار بالا به لطف I/O ترتیبی و batching.

(الف) ایمیل: RabbitMQ (یا حتی صف Laravel روی Redis/SQS). هر پیام یک کار مستقل است، باید یک‌بار انجام و حذف شود، retry و DLQ داخلی می‌خواهیم و replay معنا ندارد.

(ب) رویدادهای سفارش: Kafka. چند مصرف‌کننده‌ی مستقل (Inventory، Analytics، Fraud) هرکدام با سرعت خودشان می‌خوانند؛ مصرف‌کننده‌ی جدید می‌تواند از تاریخچه شروع کند؛ با order_id به‌عنوان key، ترتیب رویدادهای هر سفارش حفظ می‌شود.

در هر دو حالت تحویل عملاً at-least-once است و مصرف‌کننده باید idempotent باشد.

الگوی Saga را تعریف کنید و دو روش Choreography و Orchestration را با مثال ثبت سفارش مقایسه کنید. چرا از 2PC استفاده نمی‌کنیم؟

تعریف: Saga دنباله‌ای از تراکنش‌های محلی در سرویس‌های مختلف است؛ هر مرحله تراکنش خودش را commit و پیامی برای شروع مرحله‌ی بعد منتشر می‌کند. در صورت شکست، تراکنش‌های جبرانی اثر مراحل قبلی را به‌صورت معنایی خنثی می‌کنند (آزادسازی موجودی، بازپرداخت).

چرا نه 2PC: 2PC در زمان prepare قفل نگه می‌دارد و blocking است؛ با خرابی coordinator شرکت‌کننده‌ها معطل می‌مانند؛ availability را به کمترین شرکت‌کننده گره می‌زند و بسیاری از brokerها، NoSQLها و APIهای خارجی (درگاه بانک) از آن پشتیبانی نمی‌کنند.

Choreography: هماهنگ‌کننده‌ی مرکزی نیست؛ هر سرویس به event واکنش نشان می‌دهد: Order ⇒ OrderCreated ⇒ Payment ⇒ PaymentCompleted ⇒ Inventory ⇒ StockReserved ⇒ Order تأیید. در شکست، StockFailed باعث refund در Payment و لغو در Order می‌شود. مزیت: ساده برای جریان کوتاه، coupling کم. عیب: جریان در کد چند سرویس پخش است، فهم و تغییرش سخت و خطر وابستگی چرخه‌ای.

Orchestration: یک orchestrator (state machine ماندگار) به ترتیب command می‌فرستد (ReserveStock، AuthorizePayment) و بر اساس پاسخ‌ها مرحله‌ی بعد یا جبران را اجرا می‌کند. مزیت: کل فرایند در یک جا، مدیریت timeout و شاخه‌ها آسان، تست‌پذیر. عیب: جزء اضافه و خطر تمرکز منطق دامنه در orchestrator.

نکات تکمیلی: Saga isolation ندارد ⇒ از semantic lock (وضعیت PENDING) استفاده می‌کنیم؛ هر مرحله با Outbox منتشر و با idempotency مصرف می‌شود؛ مراحل پرریسک قبل از pivot (capture پرداخت) قرار می‌گیرند. برای سفارش با ۴ مرحله و timeout پرداخت، orchestration را ترجیح می‌دهم.

کد زیر در سرویس Order چه مشکلاتی دارد؟ آن را بازطراحی کنید. 
<?php
public function store(Request $request)
{
    return DB::transaction(function () use ($request) {
        $order = Order::create($request->all());
        $res = Http::post('http://payment/charge', ['order' => $order->id, 'amount' => $order->total]);
        $order->update(['status' => $res->json('status')]);
        Kafka::publish('orders', ['event' => 'OrderCreated', 'id' => $order->id]);
        return $order;
    });
}

مشکلات:

  • فراخوانی شبکه داخل تراکنش DB: تراکنش و قفل‌ها در تمام مدت پاسخ Payment باز می‌مانند؛ کندی Payment به قفل و تمام شدن connectionهای DB منجر می‌شود.
  • بدون timeout و retry کنترل‌شده: سرویس کند همه‌ی workerهای PHP-FPM را اشغال می‌کند (cascading failure).
  • Dual write: اگر publish موفق شود اما commit شکست بخورد، event برای سفارشی که وجود ندارد منتشر شده؛ اگر پس از commit پروسه کرش کند (در نسخه‌ی خارج از تراکنش)، event گم می‌شود.
  • ناسازگاری با پرداخت: اگر charge انجام شود و بعد تراکنش rollback شود، پول کسر شده ولی سفارشی نیست. در retry کلاینت هم احتمال پرداخت دوباره است چون idempotency key ندارد.
  • $request->all(): mass assignment؛ باید داده‌ی validate‌شده استفاده شود. خطای پاسخ Payment هم بررسی نمی‌شود.

<?php
public function store(StoreOrderRequest $request)
{
    $order = DB::transaction(function () use ($request) {
        $order = Order::create($request->validated() + ['status' => 'PENDING']);
        Outbox::record('OrderCreated', ['order_id' => $order->id, 'total' => $order->total]);
        return $order;
    });

    return response()->json(['id' => $order->id, 'status' => 'PENDING'], 202);
}
// پرداخت در saga با فرمان AuthorizePayment و Idempotency-Key = "pay-{order_id}"
// relay رکوردهای outbox را به Kafka می‌فرستد؛ consumerها idempotent هستند.

اگر فراخوانی همزمان واقعاً لازم باشد، خارج از تراکنش، با timeout، retry محدود، circuit breaker و idempotency key انجام شود.

چرا گفته می‌شود «exactly-once delivery» در سیستم‌های توزیع‌شده افسانه است؟ چطور یک consumer طراحی می‌کنید که پیام تکراری اثر دوباره نگذارد؟

سه تضمین: at-most-once (ممکن است گم شود)، at-least-once (ممکن است تکرار شود)، exactly-once.

چرا exactly-once ممکن نیست: consumer پیام را پردازش می‌کند و قبل از ارسال ack کرش می‌کند یا ack در شبکه گم می‌شود. broker نمی‌تواند تشخیص دهد پردازش انجام شده یا نه؛ پس یا دوباره می‌فرستد (تکرار) یا نمی‌فرستد (گم شدن). همین مسئله برای retry در HTTP هم وجود دارد. Kafka تضمین exactly-once را با idempotent producer و transaction ارائه می‌دهد، اما فقط درون خود Kafka (read-process-write)؛ side-effect بیرونی مثل DB یا API پرداخت را پوشش نمی‌دهد.

راه‌حل عملی: at-least-once + پردازش idempotent = effectively-once.

  • هر پیام یک message_id یکتا دارد (از outbox).
  • Inbox/processed_messages: در همان تراکنشی که اثر کسب‌وکار ثبت می‌شود، message_id با unique constraint درج می‌شود؛ اگر تکراری بود، پیام نادیده گرفته و ack می‌شود.
  • Natural idempotency: unique روی کلید کسب‌وکار (یک رزرو برای هر order_id)؛ عملیات مطلق (status = PAID) به‌جای نسبی (balance -= x)؛ شرط نسخه.
  • برای API خارجی، Idempotency-Key ارسال شود تا طرف مقابل هم dedupe کند.
<?php
DB::transaction(function () use ($msg) {
    if (DB::table('processed_messages')->insertOrIgnore(['message_id' => $msg['id']]) === 0) {
        return; // تکراری
    }
    Payment::markPaid($msg['order_id']);
});

اشتباه رایج: چک کردن «آیا قبلاً پردازش شده؟» با SELECT و سپس پردازش در دو مرحله‌ی جدا؛ در همزمانی دو consumer هر دو عبور می‌کنند. اتمیک بودن با unique constraint یا قفل تضمین می‌شود.

CQRS و Event Sourcing را تعریف کنید، تفاوت و رابطه‌ی آن‌ها را توضیح دهید و بگویید در چه شرایطی استفاده از آن‌ها ارزش هزینه‌اش را دارد.

CQRS: جداسازی مدل نوشتن (command، قوانین دامنه) از مدل خواندن (query، داده‌ی بهینه برای نمایش). می‌تواند فقط در سطح کد باشد یا با ذخیره‌سازی جدا: write DB نرمال و read store دی‌نرمال که از طریق event به‌روز می‌شود.

Event Sourcing: به‌جای ذخیره‌ی وضعیت فعلی، تمام رویدادهای تغییر وضعیت به‌صورت append-only ذخیره و وضعیت با replay ساخته می‌شود؛ با snapshot برای کارایی و optimistic concurrency روی شماره‌ی نسخه‌ی stream.

رابطه: مستقل‌اند. Event Sourcing تقریباً همیشه CQRS لازم دارد، چون query روی دنباله‌ی رویدادها عملی نیست و باید projection ساخت. اما CQRS بدون Event Sourcing رایج است.

مزایا: CQRS: scale و بهینه‌سازی مستقل خواندن و نوشتن، حل مسئله‌ی query بین سرویس‌ها. ES: audit trail کامل، query زمانی («وضعیت در تاریخ X»)، ساخت read model جدید از تاریخچه، debug با replay.

هزینه‌ها: eventual consistency بین نوشتن و خواندن؛ زیرساخت projector؛ در ES، تکامل schema رویدادها (versioning و upcasting)، حذف داده‌ی شخصی در لاگ تغییرناپذیر و منحنی یادگیری.

چه زمانی ارزش دارد:

  • CQRS: نسبت خواندن به نوشتن بسیار بالا با الگوهای خواندن متفاوت، داشبورد و جستجو، گزارش‌گیری بین چند سرویس.
  • ES: دامنه‌های مالی و ledger، کیف پول، سیستم‌هایی با الزام ممیزی قانونی، دامنه‌ی پیچیده‌ای که رویدادها برای کسب‌وکار معنادارند.
  • نه برای CRUD ساده یا کل سیستم؛ فقط برای bounded context خاصی که نیاز دارد.
سرویس Payment گاهی ۳۰ ثانیه طول می‌کشد تا پاسخ دهد و در این زمان کل سایت (حتی صفحاتی که به پرداخت ربط ندارند) از دسترس خارج می‌شود. علت چیست و چطور سیستم را مقاوم می‌کنید؟

علت: cascading failure ناشی از منابع مشترک. هر درخواست به Payment یک worker PHP-FPM (و شاید connection DB) را تا ۳۰ ثانیه اشغال می‌کند. با چند ده درخواست در ثانیه، همه‌ی workerها منتظر Payment می‌مانند و درخواست‌های بی‌ربط هم worker آزاد پیدا نمی‌کنند. retryهای بی‌حساب کلاینت‌ها هم بار Payment را بیشتر می‌کنند.

راه‌حل لایه‌لایه:

  • Timeout: connect timeout حدود ۱ ثانیه و request timeout بر اساس p99 سالم (مثلاً ۳ ثانیه)؛ هیچ فراخوانی بدون timeout.
  • Retry محدود فقط برای خطای گذرا، با exponential backoff + jitter و Idempotency-Key تا پرداخت تکراری رخ ندهد؛ retry فقط در یک لایه.
  • Circuit breaker: وقتی نرخ خطا یا timeout از آستانه گذشت، مدار باز می‌شود و درخواست‌ها فوراً fallback می‌گیرند؛ پس از cooldown در حالت half-open آزمایش می‌شود.
  • Bulkhead: محدود کردن تعداد فراخوانی همزمان به Payment یا جدا کردن pool/worker برای مسیر پرداخت تا بقیه‌ی سایت سالم بماند.
  • Async کردن: سفارش با وضعیت PENDING_PAYMENT ثبت و پرداخت از طریق صف/saga پیگیری شود؛ کاربر با polling یا WebSocket نتیجه را می‌بیند.
  • Fallback و degradation: پیام «پرداخت در حال بررسی است» یا غیرفعال کردن موقت روش پرداخت مشکل‌دار.
  • Observability: متریک latency p99 و نرخ خطای Payment، هشدار روی باز شدن circuit و trace برای یافتن ریشه (مثلاً کندی درگاه بانک).

نتیجه: سرویس کند از سرویس مرده خطرناک‌تر است؛ هدف این است که خرابی یک وابستگی، سریع و محدود شکست بخورد (fail fast) و شعاع آسیبش مهار شود.

چرا retry باید همراه با exponential backoff و jitter باشد؟ «retry storm» چیست و چطور از آن جلوگیری می‌کنید؟

Retry برای عبور از خطاهای گذرا (قطع لحظه‌ای شبکه، 503، 429) ضروری است، اما retry بی‌محابا خودش عامل خرابی می‌شود.

  • Exponential backoff: فاصله‌ی تلاش‌ها نمایی بیشتر می‌شود (۱۰۰، ۲۰۰، ۴۰۰ میلی‌ثانیه…) تا به سرویس تحت فشار فرصت بهبود داده شود، با یک سقف (cap).
  • Jitter: بدون تصادفی‌سازی، هزاران کلاینتی که همزمان خطا گرفته‌اند همزمان هم retry می‌کنند (thundering herd) و موج‌های بار هماهنگ می‌سازند. Full jitter: sleep = random(0, min(cap, base × 2^n)).

Retry storm: وقتی چند لایه هرکدام مستقل retry کنند، بار ضرب می‌شود: Gateway ۳ بار × Order ۳ بار × Inventory ۳ بار ⇒ تا ۲۷ درخواست برای هر درخواست کاربر به سرویسی که همین الان زیر بار مانده؛ بازیابی را غیرممکن می‌کند.

پیشگیری:

  • retry فقط در یک لایه (معمولاً نزدیک‌ترین به وابستگی یا در mesh).
  • Retry budget: حداکثر درصد مشخصی از درخواست‌ها می‌توانند retry باشند.
  • Circuit breaker که در خرابی پایدار retry را متوقف می‌کند.
  • retry فقط خطاهای گذرا و عملیات idempotent؛ احترام به header Retry-After.
  • تعداد تلاش محدود و deadline کلی درخواست.
<?php
Http::timeout(2)->retry(3, fn (int $n) => random_int(0, min(2000, 100 * 2 ** $n)))
    ->get($url);

در صف‌های Laravel همین ایده با public function backoff(): array { return [10, 60, 300]; } و $tries پیاده می‌شود و پیام‌های ناموفق نهایی به failed jobs (معادل DLQ) می‌روند.

API Gateway و الگوی BFF را تعریف کنید، وظایف و ریسک‌های Gateway را بنویسید و توضیح دهید Service Discovery چه مسئله‌ای را حل می‌کند.

API Gateway: نقطه‌ی ورود واحد کلاینت‌های بیرونی به مجموعه‌ی سرویس‌ها. وظایف: routing و versioning، احراز هویت (اعتبارسنجی JWT)، rate limiting، TLS termination، CORS، request aggregation، protocol translation (REST ↔ gRPC)، ساخت correlation id و لاگ/متریک مرکزی. مزیت: کلاینت از ساختار داخلی جدا می‌شود و دغدغه‌های مشترک یکبار پیاده می‌شوند.

ریسک‌ها: SPOF و گلوگاه (نیاز به چند instance و autoscaling)، hop و latency اضافه، و خطر تبدیل شدن به محل منطق کسب‌وکار؛ gateway باید «نازک» بماند.

BFF: برای هر نوع کلاینت (وب، موبایل، پارتنر) یک backend اختصاصی که داده را از سرویس‌ها جمع و دقیقاً مطابق نیاز همان UI شکل می‌دهد؛ معمولاً تیم frontend مالک آن است. مزیت: payload بهینه برای موبایل، تغییر UI بدون تغییر سرویس‌های هسته. عیب: تکرار کد بین BFFها. در عمل: Gateway برای دغدغه‌های مشترک + BFFها پشت آن.

Service Discovery: در محیط پویا (container، autoscaling) IP نمونه‌ها دائماً تغییر می‌کند؛ discovery امکان یافتن نمونه‌های سالم با نام سرویس را می‌دهد.

  • Client-side: کلاینت از registry (Consul، Eureka) لیست می‌گیرد و خودش load balance می‌کند.
  • Server-side: کلاینت به LB یا DNS ثابت می‌زند؛ در Kubernetes شیء Service با DNS داخلی و kube-proxy این کار را انجام می‌دهد.
  • ثبت با self-registration و heartbeat یا توسط پلتفرم، همراه با health check.
کاربران گزارش می‌دهند endpoint ثبت سفارش گاهی ۵ ثانیه طول می‌کشد. این درخواست از ۶ سرویس عبور می‌کند. چطور علت را پیدا می‌کنید و چه زیرساخت Observability‌ای پیشنهاد می‌دهید؟

ابزار اصلی: Distributed Tracing. هر درخواست یک trace id در لبه می‌گیرد و هر عملیات (HTTP، query، publish) یک span با زمان شروع و مدت و parent است. context با header استاندارد traceparent (W3C Trace Context) بین سرویس‌ها و در metadata پیام‌ها منتقل می‌شود. با OpenTelemetry instrument می‌کنیم و در Jaeger/Tempo نمودار waterfall می‌بینیم که دقیقاً کدام span زمان را مصرف کرده است.

مراحل عیب‌یابی:

  1. در متریک‌ها (RED: rate، errors، duration) ببینیم مشکل در p99 است یا همه‌ی درخواست‌ها، از چه زمانی، و آیا با deploy یا اوج ترافیک هم‌زمان است.
  2. traceهای کند را فیلتر کنیم (tail-based sampling کمک می‌کند traceهای کند حتماً نگه داشته شوند).
  3. span مقصر را پیدا کنیم: query بدون index، فراخوانی سریالی که می‌توانست موازی باشد، retry پنهان، انتظار برای connection pool، lock DB یا سرویس خارجی.
  4. با correlation id لاگ‌های structured همه‌ی سرویس‌ها را برای همان درخواست جستجو کنیم تا جزئیات خطا یا retry معلوم شود.

زیرساخت پیشنهادی:

  • Logs: JSON ساختاریافته با correlation_id، service، version؛ تجمیع در ELK یا Loki. در Laravel با middleware و Context::add() که به لاگ‌ها و jobها منتقل می‌شود.
  • Metrics: Prometheus/Grafana؛ histogram برای latency و percentileها؛ طول صف و consumer lag.
  • Traces: OpenTelemetry SDK + collector.
  • SLO و alert بر اساس error budget، نه آستانه‌های دلخواه.

نکته: میانگین latency مشکل tail را پنهان می‌کند؛ با ۶ سرویس، احتمال اینکه یک درخواست به tail یکی از آن‌ها بخورد زیاد است.

امنیت ارتباط بین میکروسرویس‌ها را چطور تأمین می‌کنید؟ نقش mTLS و JWT را توضیح دهید.

اصل: Zero Trust؛ شبکه‌ی داخلی امن فرض نمی‌شود. اگر یک سرویس نفوذ شود، نباید بتواند آزادانه سرویس‌های دیگر را صدا بزند یا ترافیک را شنود کند. دو هویت مجزا داریم: هویت سرویس فراخواننده و هویت کاربر نهایی.

  • mTLS: TLS دوطرفه که در آن هر دو طرف گواهی ارائه می‌کنند؛ ترافیک رمز و هویت سرویس احراز می‌شود. چالش: صدور و چرخش گواهی‌ها؛ service mesh (Istio، Linkerd) این را خودکار و policyهای «چه سرویسی اجازه‌ی صدا زدن چه سرویسی را دارد» را اعمال می‌کند.
  • JWT propagation: gateway توکن کاربر را اعتبارسنجی و به پایین‌دست منتقل می‌کند. هر سرویس امضا، exp و aud را خودش با کلید عمومی (JWKS) بررسی می‌کند و به headerهای ساده‌ای مثل X-User-Id که قابل جعل‌اند اعتماد نمی‌کند.
  • Token exchange / توکن داخلی: تبدیل توکن بیرونی به توکن کوتاه‌عمر با audience و scope محدود به سرویس مقصد تا نشت یک توکن همه‌جا کارایی نداشته باشد.
  • Client credentials: برای فراخوانی‌های سیستمی (job پس‌زمینه) که از طرف کاربر نیست.

تکمیلی: authorization در سطح منبع (مالکیت سفارش) درون سرویس، نه فقط در gateway؛ NetworkPolicy برای محدود کردن مسیرهای شبکه؛ مدیریت secret در vault با چرخش؛ least privilege برای کاربر DB هر سرویس؛ لاگ ممیزی.

جمع‌بندی: mTLS می‌گوید «چه کسی (کدام سرویس) با من حرف می‌زند و کانال امن است»؛ JWT می‌گوید «این درخواست از طرف کدام کاربر و با چه مجوزی است». مکمل‌اند.

یک سرویس کوتاه‌کننده‌ی لینک (URL Shortener) با ۱۰۰ میلیون لینک جدید در ماه طراحی کنید.

نیازمندی‌ها: ساخت لینک کوتاه، redirect سریع، alias دلخواه و انقضا، آمار کلیک. غیرعملکردی: redirect با p99 کم، availability بالا، کدهای غیرقابل حدس.

تخمین: 100M/ماه ⇒ حدود ۴۰ نوشتن در ثانیه؛ با نسبت خواندن ۱۰۰ به ۱، حدود ۴۰۰۰ redirect در ثانیه (اوج حدود ۱۰ هزار). ۵ سال ⇒ ۶ میلیارد رکورد × ۵۰۰ بایت ≈ ۳TB. Base62 با ۷ کاراکتر ≈ ۳.۵ تریلیون کد؛ کافی.

API: POST /api/v1/links ⇒ 201 با کد؛ GET /{code} ⇒ 302 با header Location.

تولید کد: range allocation: هر instance بازه‌ای از IDها را از یک allocator (یا sequence در DB) رزرو می‌کند و محلی مصرف می‌کند؛ ID با permutation برگشت‌پذیر درهم و به Base62 تبدیل می‌شود. بدون collision و بدون گلوگاه مرکزی. جایگزین: hash با بررسی collision.

Deep dives:

  • Cache: سیستم به‌شدت read-heavy و توزیع کلیک power-law است ⇒ cache-aside در Redis با LRU؛ negative caching یا Bloom filter برای کدهای ناموجود.
  • 301 در برابر 302: 301 بار را کم می‌کند (cache مرورگر) اما آمار و امکان تغییر مقصد از دست می‌رود؛ برای آمار 302.
  • آمار ناهمزمان: ثبت کلیک در مسیر redirect همزمان نیست؛ event به Kafka و تجمیع batch در OLAP.
  • داده: الگوی دسترسی key-value ⇒ sharding با hash کد؛ unique روی code؛ انقضا با job پاک‌سازی.
  • امنیت: rate limit ساخت لینک، بررسی URLهای مخرب.
News Feed یک شبکه‌ی اجتماعی را طراحی کنید. رویکرد fan-out on write و fan-out on read را مقایسه کنید و مشکل کاربران پرطرفدار (celebrity) را چطور حل می‌کنید؟

نیازمندی: کاربر پست منتشر می‌کند و دنبال‌کنندگان در feed خود پست‌ها را (معمولاً به ترتیب زمان یا رتبه) با صفحه‌بندی می‌بینند. سیستم به‌شدت read-heavy است و latency خواندن feed باید کم باشد.

Fan-out on write (push)

  • هنگام انتشار، ID پست در feed cache همه‌ی دنبال‌کنندگان (مثلاً Redis list/sorted set) درج می‌شود.
  • خواندن بسیار سریع (feed از قبل آماده).
  • نوشتن گران برای کاربر با میلیون‌ها دنبال‌کننده؛ هدر رفتن کار برای کاربران غیرفعال.

Fan-out on read (pull)

  • هنگام خواندن، پست‌های اخیر همه‌ی دنبال‌شونده‌ها جمع و merge می‌شود.
  • نوشتن ارزان؛ بدون کار اضافه برای غیرفعال‌ها.
  • خواندن کند و پرهزینه برای کسی که هزاران نفر را دنبال می‌کند.

رویکرد ترکیبی (hybrid): برای کاربران عادی fan-out on write از طریق صف (Post Service ⇒ event PostCreated ⇒ Fan-out workers ⇒ feed cache هر دنبال‌کننده). برای celebrityها (دنبال‌کننده بیش از یک آستانه) fan-out انجام نمی‌شود؛ هنگام خواندن feed، پست‌های اخیر celebrityهایی که کاربر دنبال می‌کند جداگانه خوانده (و چون پرخواننده‌اند در cache هستند) و با feed آماده merge می‌شود.

Post ─► Post Svc ─► DB + outbox ─► Kafka(PostCreated) ─► Fan-out Workers ─► Redis feed:{user} (ZSET, آخرین ۵۰۰)
Read ─► Feed Svc ─► Redis feed:{user} ∪ posts of followed celebrities ─► hydrate (Post/User cache) ─► rank ─► cursor pagination
  • feed فقط ID نگه می‌دارد؛ محتوا با batch از cache پست‌ها hydrate می‌شود.
  • صفحه‌بندی cursor-based (نه offset) چون feed مدام تغییر می‌کند.
  • feed cache فقط برای کاربران فعال؛ برای کاربر برگشتی، ساخت مجدد با pull.
  • Eventual consistency قابل قبول است: چند ثانیه تأخیر در رسیدن پست مشکلی ندارد.
Eventual Consistency را تعریف کنید. کاربری بلافاصله پس از ثبت سفارش، آن را در لیست سفارش‌هایش نمی‌بیند (لیست از read model ساخته می‌شود). این مشکل را چطور مدیریت می‌کنید؟

تعریف: Eventual consistency تضمینی است که اگر نوشتن جدیدی انجام نشود، همه‌ی replicaها و نماهای داده پس از مدتی به یک مقدار همگرا می‌شوند؛ در بازه‌ی میانی، خواندن ممکن است داده‌ی کهنه برگرداند. این انتخابی آگاهانه برای availability، latency و decoupling بهتر است (CAP/PACELC) و نتیجه‌ی طبیعی پیام‌رسانی ناهمزمان، read replica و CQRS است.

علت مشکل: سفارش در write DB ثبت شده اما event هنوز به projector نرسیده یا پردازش نشده است؛ کاربر نوشتن خودش را نمی‌بیند (نقض read-your-writes).

راه‌حل‌ها:

  • بازگرداندن داده در پاسخ نوشتن: فرانت سفارش جدید را از پاسخ POST به‌صورت optimistic به لیست اضافه کند.
  • خواندن از منبع اصلی برای مدت کوتاه: پس از نوشتن، تا چند ثانیه درخواست‌های همان کاربر از write model/primary خوانده شوند (مشابه گزینه‌ی sticky در اتصال read/write لاراول برای replica).
  • Version/token: پاسخ نوشتن یک شماره‌ی نسخه یا offset برمی‌گرداند و read model فقط وقتی پاسخ می‌دهد که به آن نسخه رسیده باشد (یا کلاینت کمی صبر کند).
  • UX صادقانه: نمایش وضعیت «در حال پردازش» و به‌روزرسانی با WebSocket یا polling.
  • کاهش تأخیر: پایش consumer lag، CDC به‌جای polling outbox، مقیاس دادن projectorها.

نکته: همه‌ی داده‌ها نباید eventual باشند؛ برای موجودی حساب یا جلوگیری از فروش بیش از موجودی، تصمیم در سرویس مالک با سازگاری قوی (تراکنش محلی، قفل یا شرط نسخه) گرفته می‌شود و فقط نماها eventual هستند.

خلاصه برای مرور سریع

چارچوب پاسخ

  • Requirements (functional + non-functional) ← Estimation (QPS، storage) ← API ← Data model ← High-level ← Deep dives ← Bottlenecks/trade-offs.
  • QPS ≈ DAU × req/day ÷ 10^5؛ اوج ≈ ۲ تا ۳ برابر. ۷ کاراکتر Base62 ≈ ۳.۵ تریلیون.
  • هر تصمیم: «چون…» + یک جایگزین ردشده.

معماری

  • Microservices = deploy مستقل + مالکیت داده + حول business capability. حل مسئله‌ی سازمانی، نه لزوماً performance.
  • شروع با Modular Monolith؛ مهاجرت با Strangler Fig + Anti-Corruption Layer.
  • ضدالگو: Distributed Monolith (DB مشترک، deploy هماهنگ، زنجیره‌ی همزمان طولانی).
  • مرز = Bounded Context (DDD)؛ Aggregate = مرز تراکنش؛ Database per Service؛ JOIN ⇒ API Composition یا CQRS read model.

داده و سازگاری

  • 2PC: blocking، coordinator SPOF، availability کم ⇒ معمولاً نه.
  • Saga = تراکنش‌های محلی + جبران. Choreography (event، ساده، پراکنده) / Orchestration (state machine مرکزی، پیچیده‌ها). Compensatable ← Pivot ← Retriable. بدون isolation ⇒ semantic lock (PENDING).
  • Outbox: تغییر داده + رکورد event در یک تراکنش؛ relay با polling یا CDC (Debezium، binlog/WAL) ⇒ at-least-once.
  • Inbox / idempotent consumer: message_id یکتا در همان تراکنش اثر کسب‌وکار.
  • Exactly-once delivery افسانه است ⇒ at-least-once + dedupe = effectively-once. Kafka EOS فقط درون Kafka.
  • Idempotency-Key در POST؛ ذخیره‌ی پاسخ اول؛ قفل روی کلید؛ مقایسه‌ی hash بدنه.
  • Eventual consistency: UX وضعیت میانی، read-your-writes، ترتیب با partition key یا version، reconciliation job.
  • CQRS: جدا کردن خواندن/نوشتن. Event Sourcing: ذخیره‌ی رویدادها، replay، snapshot، projection؛ هزینه: schema evolution، GDPR. فقط برای context خاص.

Resilience

  • سرویس کند از سرویس مرده خطرناک‌تر است ⇒ cascading failure.
  • Timeout همیشه (connect کوتاه، read بر اساس p99)، deadline propagation.
  • Retry: فقط خطای گذرا + idempotent؛ random(0, min(cap, base·2^n))؛ یک لایه؛ retry budget.
  • Circuit Breaker: Closed ⇒ Open (fail fast) ⇒ Half-Open (آزمایش) ⇒ Closed.
  • Bulkhead: pool/صف/worker جدا. Fallback: cache کهنه، پیش‌فرض. Load shedding: 429/503 سریع.
  • Laravel: Http::timeout()->connectTimeout()->retry()، job با $tries و backoff()، middleware ThrottlesExceptions.

Observability، استقرار، امنیت

  • Logs (structured JSON + correlation id) / Metrics (RED، USE، percentile) / Traces (OpenTelemetry، traceparent، span).
  • Laravel Context::add('correlation_id', …) ⇒ لاگ‌ها و jobها؛ ارسال در header فراخوانی‌ها.
  • K8s: Pod، Deployment، Service، Ingress، ConfigMap/Secret، HPA؛ readiness (وابستگی‌ها) در برابر liveness (فقط خود پروسه).
  • Rolling / Blue-Green / Canary؛ migration سازگار با عقب (expand/contract).
  • Service mesh: sidecar (Envoy)، mTLS خودکار، retry، traffic split؛ هزینه‌ی عملیاتی.
  • Zero trust: mTLS = هویت سرویس + رمزنگاری؛ JWT = هویت کاربر، اعتبارسنجی در هر سرویس (JWKS)، توکن کوتاه‌عمر، token exchange.

طراحی‌های نمونه در یک خط

  • URL Shortener: read-heavy ⇒ Redis + CDN؛ range allocation + Base62؛ 302 برای آمار؛ کلیک‌ها ناهمزمان به Kafka؛ shard با hash کد.
  • Rate Limiter: در gateway؛ token bucket با Lua اتمیک در Redis؛ 429 + Retry-After؛ fail-open به‌جز endpointهای حساس.
  • Notification: API + dedupe + preferences ⇒ صف جدا برای هر کانال/اولویت ⇒ workerها ⇒ providerها با failover؛ retry + DLQ؛ rate limit کاربر.
  • Order Saga: PENDING + 202 ⇒ Reserve ⇒ Authorize ⇒ Confirm/Capture (pivot) ⇒ Ship؛ جبران: release/void؛ outbox + idempotency + timeout.
  • News Feed: hybrid fan-out؛ push برای عادی، pull برای celebrity؛ ZSET از IDها؛ cursor pagination.
