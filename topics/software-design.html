Software Design (OOP · SOLID · Clean Code)

اصول طراحی نرم‌افزار شیءگرا از پایه تا معماری: چهار ستون OOP، اصول SOLID با مثال «نقض ← اصلاح» در PHP و Laravel، Coupling و Cohesion، تزریق وابستگی، Clean Code، Code Smellها و Refactoring، و نگاهی به معماری لایه‌ای، Hexagonal و واژگان DDD.

چهار ستون OOP

برنامه‌نویسی شیءگرا (Object-Oriented Programming) یعنی مدل‌کردن سیستم به‌صورت مجموعه‌ای از شیء‌ها که هر کدام داده (state) و رفتار (behavior) مربوط به خودش را یک‌جا نگه می‌دارد و با بقیه فقط از طریق پیام (فراخوانی متد) ارتباط دارد. چهار مفهوم اصلی که تقریباً همیشه در آزمون پرسیده می‌شود: Encapsulation، Abstraction، Inheritance و Polymorphism.

۱) Encapsulation (کپسوله‌سازی)

یعنی پنهان‌کردن وضعیت داخلی شیء و در اختیار گذاشتن فقط یک رابط کنترل‌شده برای تغییر آن، تا شیء همیشه در یک وضعیت معتبر (invariant) باقی بماند. ابزارهایش در PHP: سطح دسترسی private/protected، readonly (PHP 8.1)، کلاس‌های readonly (PHP 8.2) و متدهایی که قواعد کسب‌وکار را اعمال می‌کنند. کپسوله‌سازی «getter و setter برای همه فیلدها» نیست؛ setter بی‌قید و شرط عملاً همان فیلد public است.

<?php
// نادرست: بدون کپسوله‌سازی: هر کسی می‌تواند موجودی را منفی کند
class BankAccount
{
    public float $balance = 0;
}
$acc = new BankAccount();
$acc->balance = -500; // invariant شکسته شد

// درست: با کپسوله‌سازی: قاعده «موجودی منفی نمی‌شود» داخل خود شیء است
final class Account
{
    private int $balanceInCents = 0;

    public function deposit(int $amount): void
    {
        if ($amount <= 0) {
            throw new InvalidArgumentException('Amount must be positive.');
        }
        $this->balanceInCents += $amount;
    }

    public function withdraw(int $amount): void
    {
        if ($amount > $this->balanceInCents) {
            throw new InsufficientFunds();
        }
        $this->balanceInCents -= $amount;
    }

    public function balance(): int
    {
        return $this->balanceInCents;
    }
}

در PHP 8.4 با asymmetric visibility می‌توان نوشت public private(set) int $balance؛ یعنی خواندن آزاد و نوشتن فقط از داخل کلاس. Property hooks هم در 8.4 اضافه شده‌اند. اگر پروژه روی 8.3 است، همان private + متد عمومی کافی است.

۲) Abstraction (انتزاع)

یعنی نمایش فقط ویژگی‌های ضروری یک مفهوم و پنهان‌کردن جزئیات پیاده‌سازی؛ مصرف‌کننده می‌داند «چه کاری» انجام می‌شود، نه «چطور». در PHP معمولاً با interface یا abstract class بیان می‌شود.

<?php
interface PaymentGateway
{
    public function charge(Money $amount, string $token): PaymentResult;
}

// کد سفارش فقط با مفهوم «درگاه پرداخت» کار می‌کند،
// نه با جزئیات HTTP و امضای درخواست درگاه خاص.
final class CheckoutService
{
    public function __construct(private PaymentGateway $gateway) {}

    public function pay(Order $order, string $token): PaymentResult
    {
        return $this->gateway->charge($order->total(), $token);
    }
}

۳) Inheritance (وراثت)

رابطه is-a: کلاس فرزند رفتار و وضعیت کلاس والد را به ارث می‌برد و می‌تواند آن را گسترش دهد یا override کند. PHP فقط single inheritance برای کلاس دارد (یک extends)، ولی یک کلاس می‌تواند چند interface را implement کند و چند trait استفاده کند.

<?php
abstract class Notification
{
    public function __construct(protected string $recipient) {}

    abstract protected function body(): string;

    public function render(): string
    {
        return "To: {$this->recipient}\n" . $this->body();
    }
}

final class WelcomeNotification extends Notification
{
    #[\Override] // PHP 8.3: اگر متد والد وجود نداشته باشد، خطا می‌دهد
    protected function body(): string
    {
        return 'Welcome aboard!';
    }
}

وراثت قوی‌ترین نوع coupling است: فرزند به جزئیات پیاده‌سازی والد وابسته می‌شود و تغییر والد ممکن است بی‌صدا فرزندان را بشکند (Fragile Base Class problem). وراثت را فقط برای رابطه واقعی is-a که قرارداد والد را کامل رعایت می‌کند (LSP) به کار ببرید؛ برای «استفاده مجدد از کد» معمولاً composition بهتر است.

۴) Polymorphism (چندریختی)

یعنی یک رابط، چند پیاده‌سازی: کد فراخواننده با نوع انتزاعی کار می‌کند و رفتار واقعی در زمان اجرا بر اساس نوع واقعی شیء انتخاب می‌شود (dynamic dispatch یا subtype polymorphism). PHP «method overloading» به سبک Java (چند متد هم‌نام با پارامترهای مختلف) ندارد؛ چیزی که در PHP به آن overloading می‌گویند متدهای جادویی __call و __get است.

<?php
interface Shape { public function area(): float; }

final class Circle implements Shape {
    public function __construct(private float $r) {}
    public function area(): float { return M_PI * $this->r ** 2; }
}

final class Rect implements Shape {
    public function __construct(private float $w, private float $h) {}
    public function area(): float { return $this->w * $this->h; }
}

/** @param Shape[] $shapes */
function totalArea(array $shapes): float
{
    // هیچ if/switch روی نوع وجود ندارد؛ هر شیء خودش می‌داند مساحتش چیست
    return array_sum(array_map(fn (Shape $s) => $s->area(), $shapes));
}

نمونه‌های Laravel: هر driver کش (redis، file، database) قرارداد Illuminate\Contracts\Cache\Store را پیاده می‌کند؛ کانال‌های Notification (mail، database، broadcast) و disk‌های Filesystem هم همین الگو را دارند. کد شما فقط با Cache::get() کار می‌کند و driver از کانفیگ عوض می‌شود.

اگر در کد زنجیره‌ای از if ($x instanceof A) … elseif ($x instanceof B) یا switch ($type) می‌بینید که در چند جا تکرار شده، این نشانه «جایگزین‌کردن شرط با polymorphism» (Replace Conditional with Polymorphism) است و هم‌زمان OCP را هم نقض می‌کند.

کی کدام را انتخاب کنیم؟

  • Interface: وقتی می‌خواهید چند پیاده‌سازی مستقل و قابل‌جایگزین داشته باشید و کد مصرف‌کننده فقط به قرارداد وابسته باشد (DIP، تست با mock). پیش‌فرض خوب برای مرز بین لایه‌ها.
  • Abstract class: وقتی پیاده‌سازی‌ها واقعاً از یک خانواده‌اند و الگوریتم یا state مشترک دارند؛ مثلاً Template Method که اسکلت الگوریتم در والد و گام‌های متغیر در فرزند است. معمولاً abstract class خودش یک interface را implement می‌کند.
  • Trait: برای استفاده مجدد از قطعه‌کد کوچک و افقی بین کلاس‌های بی‌ربط، مثل HasFactory، SoftDeletes، Notifiable در Laravel. trait نوع (type) نیست و جایگزین interface نمی‌شود؛ الگوی رایج: interface برای قرارداد + trait برای پیاده‌سازی پیش‌فرض.
<?php
interface HasSlug
{
    public function slug(): string;
}

trait GeneratesSlug
{
    // trait می‌تواند متد abstract بخواهد تا به کلاس میزبان وابسته شود
    abstract protected function slugSource(): string;

    public function slug(): string
    {
        return \Illuminate\Support\Str::slug($this->slugSource());
    }
}

final class Article implements HasSlug
{
    use GeneratesSlug;

    public function __construct(private string $title) {}

    protected function slugSource(): string
    {
        return $this->title;
    }
}

حل تداخل trait‌ها

<?php
trait Loggable  { public function report(): string { return 'log'; } }
trait Auditable { public function report(): string { return 'audit'; } }

class Invoice
{
    use Loggable, Auditable {
        Auditable::report insteadof Loggable; // کدام نسخه برنده شود
        Loggable::report as logReport;        // نسخه دیگر با نام مستعار
    }
}

اشتباه رایج: پرکردن trait با منطق کسب‌وکار سنگین و وابستگی پنهان به propertyهای کلاس میزبان (مثلاً $this->user که در trait تعریف نشده). این کار coupling پنهان می‌سازد، تست را سخت می‌کند و یک «God Class» تکه‌تکه شده تحویل می‌دهد. اگر trait به سرویس خارجی نیاز دارد، احتمالاً باید یک کلاس جدا باشد که از طریق composition تزریق شود.

در پاسخ تشریحی حتماً بگویید trait یک مکانیزم کپی کد توسط کامپایلر است، نه وراثت؛ $obj instanceof SomeTrait همیشه false است و نمی‌توانید روی trait type hint بزنید. برای بررسی استفاده از trait باید از class_uses() استفاده کرد.

Composition به‌جای Inheritance

اصل «Favor composition over inheritance» (از کتاب GoF) می‌گوید برای استفاده مجدد از رفتار، به‌جای ارث‌بری، شیء را از اشیای کوچک‌تر بسازید (رابطه has-a) و کار را به آنها واگذار (delegate) کنید.

چرا وراثت برای reuse مشکل‌ساز است؟

  • Coupling شدید و ایستا: رابطه در زمان کامپایل ثابت است و در runtime قابل تعویض نیست.
  • Fragile base class: تغییر در والد ممکن است رفتار همه فرزندان را عوض کند.
  • انفجار ترکیبی کلاس‌ها: برای ترکیب ویژگی‌ها (مثلاً «گزارش PDF ایمیلی زمان‌بندی‌شده») باید سلسله‌مراتب عمیق یا کلاس‌های ترکیبی زیاد بسازید.
  • ارث‌بری چیزهای ناخواسته: فرزند همه متدهای public والد را می‌گیرد، حتی اگر برایش معنا نداشته باشد (نقض LSP/ISP).

با composition هر بُعد تغییر (فرمت، روش ارسال) یک interface و چند پیاده‌سازی کوچک دارد؛ ترکیب‌ها در runtime یا در Service Container ساخته می‌شوند و تست هر جزء جداگانه ساده است. این همان ایده‌ای است که پشت الگوهای Strategy، Decorator و Bridge وجود دارد.

کی وراثت هنوز درست است؟

  • رابطه واقعی is-a که فرزند همه قرارداد والد را رعایت می‌کند (LSP).
  • چارچوب (framework) نقطه توسعه را به شکل کلاس پایه ارائه داده: Model، FormRequest، Job، Command در Laravel. اینجا وراثت «قرارداد چارچوب» است.
  • Template Method با سلسله‌مراتب کم‌عمق (یک یا دو سطح).

قاعده سرانگشتی: کلاس‌های خود را به‌طور پیش‌فرض final تعریف کنید. اگر بعداً نیاز واقعی به وراثت پیدا شد، آگاهانه final را بردارید. این کار جلوی سلسله‌مراتب‌های تصادفی را می‌گیرد و شما را به سمت composition هدایت می‌کند.

«has-a در برابر is-a» و «انعطاف در runtime در برابر رابطه ایستای compile-time» دو کلیدواژه‌ای هستند که پاسخ این سوال را کامل می‌کنند. یک مثال Decorator (مثلاً CachedUserRepository که یک UserRepository دیگر را wrap می‌کند) هم نشان می‌دهد composition چطور رفتار را بدون تغییر کلاس اصلی اضافه می‌کند.

SOLID — S: Single Responsibility

SOLID پنج اصل طراحی شیءگراست که Robert C. Martin (Uncle Bob) جمع‌بندی کرد و هدف مشترکشان ساختن کدی است که تغییرپذیر، قابل‌فهم و قابل‌تست باشد. اولین اصل:

Single Responsibility Principle: «یک کلاس (ماژول) باید فقط یک دلیل برای تغییر داشته باشد.» در بیان دقیق‌تر خود Martin: «یک ماژول باید فقط در برابر یک actor (یک گروه ذی‌نفع) پاسخ‌گو باشد.»

SRP به معنای «هر کلاس فقط یک متد» یا «فقط یک کار کوچک» نیست؛ معیار، منبع تغییر است. اگر تیم مالی فرمول مالیات را عوض کند و تیم مارکتینگ قالب ایمیل را، و هر دو تغییر به یک کلاس برسد، آن کلاس دو مسئولیت دارد.

// نادرست: کنترلر چاق: اعتبارسنجی، منطق کسب‌وکار، پرداخت، ایمیل و پاسخ HTTP یک‌جا
class OrderController extends Controller
{
    public function store(Request $request)
    {
        $data = $request->validate([
            'items'   => 'required|array',
            'coupon'  => 'nullable|string',
        ]);

        $total = 0;
        foreach ($data['items'] as $item) {
            $total += Product::find($item['id'])->price * $item['qty'];
        }
        if ($data['coupon'] ?? null) {
            $total *= 0.9;
        }

        $order = Order::create(['user_id' => auth()->id(), 'total' => $total]);
        Http::post('https://gateway.example/pay', ['amount' => $total]);
        Mail::to($request->user())->send(new OrderPlaced($order));

        return response()->json($order, 201);
    }
}

SRP در Laravel

  • Form Request: اعتبارسنجی و authorization ورودی را از کنترلر جدا می‌کند.
  • API Resource: تبدیل مدل به JSON (لایه نمایش) را جدا می‌کند.
  • Event/Listener و Job: اثرات جانبی مثل ارسال ایمیل از جریان اصلی جدا می‌شود.
  • Policy: قواعد دسترسی در یک کلاس مخصوص.
  • Middleware: هر دغدغه مشترک HTTP (احراز هویت، throttle، CORS) یک کلاس.

افراط در SRP هم بد است: شکستن هر کلاس به ده کلاس یک‌خطی، فهم جریان را سخت می‌کند و cohesion را پایین می‌آورد. هدف، کنار هم نگه‌داشتن چیزهایی است که با هم تغییر می‌کنند و جدا کردن چیزهایی که به دلایل متفاوت تغییر می‌کنند.

نشانه‌های نقض SRP برای نوشتن در امتحان: نام کلاس با «And» یا «Manager/Helper/Util» کلی؛ import تعداد زیادی کلاس از لایه‌های مختلف (HTTP، DB، Mail)؛ تست‌کردن یک متد نیازمند mock کردن نیمی از سیستم؛ تغییرات بی‌ربط مکرر روی یک فایل در git log.

SOLID — O: Open/Closed

Open/Closed Principle (Bertrand Meyer): «اجزای نرم‌افزار باید برای گسترش باز و برای تغییر بسته باشند.» یعنی بتوان رفتار جدید اضافه کرد بدون اینکه کد موجود و تست‌شده را ویرایش کرد.

ابزار اصلی OCP، abstraction + polymorphism است: نقطه متغیر را پشت یک interface می‌بریم و رفتار جدید را با یک کلاس جدید اضافه می‌کنیم.

    {
        return match ($order->shipping_method) {
            'post'    => 20_000 + $order->weight * 1_000,
            'courier' => 50_000,
            'tipax'   => 35_000 + $order->weight * 500,
            default   => throw new UnexpectedValueException(),
        };
    }
}
<?php
// درست: هر روش ارسال یک Strategy؛ روش جدید = کلاس جدید + ثبت در container
interface ShippingMethod
{
    public function supports(string $code): bool;
    public function cost(Order $order): int;
}

final class PostShipping implements ShippingMethod
{
    public function supports(string $code): bool { return $code === 'post'; }
    public function cost(Order $order): int { return 20_000 + $order->weight * 1_000; }

final class ShippingCost

    public function __construct(private iterable $methods) {}

                return $method->cost($order);
            }

        throw new UnsupportedShippingMethod($order->shipping_method);
    }

OCP در Laravel

  • Middleware pipeline: رفتار جدید روی درخواست با افزودن middleware، بدون تغییر هسته.
  • Custom drivers: Cache::extend()، Storage::extend()، Auth::extend() و custom notification channel اجازه می‌دهند driver جدید اضافه کنید بدون دست‌زدن به framework.
  • Events/Listeners: واکنش جدید به رویداد = Listener جدید.
  • Macroable: Collection::macro()، Str::macro() برای افزودن متد به کلاس‌های framework.
  • Custom validation rule با پیاده‌سازی ValidationRule.

OCP یعنی «هرگز کد را عوض نکن» نیست. باگ را باید در همان‌جا درست کرد. همچنین لازم نیست از روز اول برای همه چیز نقطه توسعه بسازید (YAGNI)؛ وقتی دومین یا سومین گونه از یک رفتار ظاهر شد (Rule of Three)، آن نقطه را abstract کنید.

ارتباط اصول را بگویید: OCP «هدف» است و DIP و LSP «ابزار» رسیدن به آن. بدون وابستگی به abstraction (DIP) نمی‌توان پیاده‌سازی جدید را plug کرد، و اگر پیاده‌سازی جدید قرارداد را نشکند (LSP) کد موجود بدون تغییر درست کار می‌کند.

SOLID — L: Liskov Substitution

Liskov Substitution Principle (Barbara Liskov، 1987): «اگر S زیرنوع T باشد، باید بتوان هر جا که T استفاده شده، شیئی از S گذاشت بدون اینکه درستی برنامه تغییر کند.» به زبان ساده: فرزند باید قرارداد رفتاری والد را رعایت کند، نه فقط امضای متدها را.

قواعد قرارداد (Design by Contract)

  • Precondition‌ها را در فرزند سخت‌تر نکنید (فرزند نباید ورودی‌ای را که والد قبول می‌کرد رد کند).
  • Postcondition‌ها را ضعیف‌تر نکنید (فرزند باید حداقل همان تضمین‌های خروجی والد را بدهد).
  • Invariant‌های والد حفظ شوند.
  • Exception جدید و غیرمنتظره پرتاب نشود (مثلاً NotImplementedException در متدی که والد قول اجرایش را داده).
  • از نظر نوع‌ها: پارامترها می‌توانند contravariant (عام‌تر) و نوع بازگشتی covariant (خاص‌تر) باشند؛ PHP از 7.4 این را پشتیبانی می‌کند.

مثال کلاسیک: مستطیل و مربع

<?php
class Rectangle
{
    public function __construct(protected int $w, protected int $h) {}
    public function setWidth(int $w): void  { $this->w = $w; }
    public function setHeight(int $h): void { $this->h = $h; }
    public function area(): int { return $this->w * $this->h; }
}

class Square extends Rectangle
{
    public function setWidth(int $w): void  { $this->w = $this->h = $w; }
    public function setHeight(int $h): void { $this->w = $this->h = $h; }
}

function resize(Rectangle $r): void
{
    $r->setWidth(5);
    $r->setHeight(4);
    assert($r->area() === 20); // برای Square شکست می‌خورد: 16
}

از نظر ریاضی مربع «یک» مستطیل است، ولی از نظر رفتار این کلاس‌ها (عرض و ارتفاع مستقل قابل تغییرند) مربع جایگزین معتبر نیست. راه‌حل: سلسله‌مراتب را حذف کنید و هر دو را پیاده‌سازی یک Shape با value object تغییرناپذیر بسازید (withWidth() شیء جدید برمی‌گرداند).

نقض رایج در کد واقعی

هر کدی که FileStorage می‌گیرد و delete() را صدا می‌زند، با این پیاده‌سازی می‌شکند. اصلاح معمولاً با ISP است: interface را به WritableStorage و DeletableStorage بشکنید تا ArchiveStorage فقط قراردادی را بپذیرد که واقعاً رعایت می‌کند.

LSP در Laravel

کل ایده driverها بر LSP تکیه دارد: وقتی CACHE_STORE را از file به redis عوض می‌کنید، کد شما نباید بفهمد. هر driver که Illuminate\Contracts\Cache\Store را پیاده می‌کند باید همان معنای get/put/forget را حفظ کند. Fakeها در تست (Mail::fake()، Queue::fake()، Storage::fake()) هم جایگزین‌های LSP-سازگار هستند.

نشانه‌های نقض LSP: بررسی نوع در کد مصرف‌کننده (if ($storage instanceof ArchiveStorage))، متدهای override‌شده‌ای که خالی هستند یا exception «پشتیبانی نمی‌شود» می‌دهند، و تست‌هایی که برای والد پاس می‌شوند ولی برای فرزند نه. در پاسخ، «قرارداد رفتاری، نه فقط امضا» را حتماً بنویسید.

SOLID — I: Interface Segregation

Interface Segregation Principle: «هیچ کلاینتی نباید مجبور شود به متدهایی وابسته باشد که از آنها استفاده نمی‌کند.» به‌جای یک interface چاق (fat interface)، چند interface کوچک و نقش‌محور (role interface) بسازید.

چرا مهم است؟

  • تغییر در متدی که کلاینت استفاده نمی‌کند، نباید آن کلاینت را تحت‌تأثیر قرار دهد (کاهش coupling).
  • پیاده‌سازی‌ها مجبور به متدهای خالی یا exception نمی‌شوند (کمک به LSP).
  • تست‌ها ساده‌تر: test double کوچک‌تر.

ISP در Laravel

پوشه Illuminate\Contracts پر از interfaceهای کوچک و تک‌منظوره است: Arrayable (فقط toArray())، Jsonable، Htmlable، Responsable (فقط toResponse())، Renderable. Interfaceهای نشانگر (marker) مثل ShouldQueue، ShouldBeUnique و ShouldBroadcast هم نمونه‌های افراطی ISP هستند: یک کلاس با implement کردن آنها فقط یک «نقش» را اعلام می‌کند.

ISP از دید کلاینت تعریف می‌شود، نه پیاده‌ساز. سوال درست این است: «این مصرف‌کننده دقیقاً به چه متدهایی نیاز دارد؟» نه «این کلاس چه کارهایی بلد است؟»

تفاوت ISP و SRP: SRP درباره دلیل تغییر یک کلاس است (سمت پیاده‌سازی)، ISP درباره اندازه و تمرکز قرارداد از دید مصرف‌کننده است. یک کلاس می‌تواند چند interface کوچک را implement کند و همچنان SRP را رعایت کند اگر همه آنها یک مسئولیت منسجم باشند.

SOLID — D: Dependency Inversion

Dependency Inversion Principle: (۱) ماژول‌های سطح بالا (سیاست/منطق کسب‌وکار) نباید به ماژول‌های سطح پایین (جزئیات: DB، HTTP، فایل) وابسته باشند؛ هر دو باید به abstraction وابسته باشند. (۲) abstraction نباید به جزئیات وابسته باشد؛ جزئیات باید به abstraction وابسته باشند.

«Inversion» یعنی جهت وابستگی در کد، برخلاف جهت جریان کنترل می‌شود: منطق سفارش، درگاه پرداخت را صدا می‌زند، ولی در کد، این کلاس درگاه است که به interface تعریف‌شده توسط لایه سفارش وابسته است. نکته ظریف: مالکیت interface با ماژول سطح بالاست.

Without DIP:
  OrderService ─────────────► ZarinpalClient   (direct dependency on details)

With DIP:
  OrderService ─────► PaymentGateway (interface, owned by the domain layer)
                             ▲
                             │ implements
                      ZarinpalGateway / FakeGateway (infrastructure)

DIP در Laravel

  • Contracts: Illuminate\Contracts\Mail\Mailer، Cache\Repository، Queue\Queue و … ؛ کد شما می‌تواند به جای کلاس concrete به این قراردادها type hint بزند.
  • Service Container با bind/singleton/scoped مشخص می‌کند کدام پیاده‌سازی به کدام abstraction وصل شود؛ Service Provider محل این «سیم‌کشی» است.
  • Contextual binding: $this->app->when(A::class)->needs(Storage::class)->give(S3Storage::class) برای اینکه مصرف‌کننده‌های مختلف پیاده‌سازی متفاوت بگیرند.

DIP با DI یکی نیست. DIP یک اصل طراحی درباره جهت وابستگی‌هاست؛ DI یک تکنیک برای تحویل وابستگی از بیرون است. می‌توان DI انجام داد ولی DIP را نقض کرد (تزریق کلاس concrete از لایه پایین)، و IoC Container صرفاً ابزاری است که DI را خودکار می‌کند.

همه چیز را interface نکنید. DIP برای مرزهای ناپایدار یا خارجی (درگاه پرداخت، SMS، سرویس‌های third-party، ذخیره‌سازی) بیشترین ارزش را دارد. برای کلاس‌های پایدار داخلی (مثل یک value object یا PriceCalculator ساده) interface اضافه فقط indirection بی‌فایده است.

DRY، KISS، YAGNI و اصول دیگر

DRY
Don't Repeat Yourself (کتاب Pragmatic Programmer): «هر تکه دانش باید یک نمایش واحد، بی‌ابهام و معتبر در سیستم داشته باشد.»
KISS
Keep It Simple, Stupid: ساده‌ترین راه‌حلی که مسئله را درست حل می‌کند را انتخاب کنید؛ پیچیدگی باید توجیه داشته باشد.
YAGNI
You Aren't Gonna Need It (از Extreme Programming): قابلیتی را که امروز لازم نیست، امروز نسازید.
Law of Demeter
«فقط با دوستان نزدیکت حرف بزن»: متد فقط با خودش، پارامترهایش، اشیایی که می‌سازد و فیلدهای مستقیمش کار کند.
Tell, Don't Ask
به شیء بگویید چه کند، به‌جای اینکه وضعیتش را بپرسید و بیرون از آن تصمیم بگیرید.
SoC
Separation of Concerns: هر بخش سیستم یک دغدغه مشخص را مدیریت کند (نمایش، منطق، دسترسی به داده).

DRY — درباره دانش، نه متن

DRY یعنی یک قاعده کسب‌وکار فقط یک جا تعریف شود؛ نه اینکه هر دو خط کد مشابه باید یکی شوند. دو تکه کد که امروز شبیه‌اند ولی به دلایل متفاوت تغییر می‌کنند (مثلاً اعتبارسنجی ثبت‌نام کاربر و ثبت فروشنده) اگر به‌زور یکی شوند، یک abstraction غلط با flagهای boolean متعدد می‌سازند. به تکرار تصادفی (incidental duplication) دست نزنید.

<?php
// نادرست: قاعده «سفارش قابل لغو است؟» در کنترلر، Blade و Job تکرار شده
if ($order->status === 'pending' && $order->created_at->gt(now()->subDay())) { /* ... */ }

// درست: دانش یک جا
final class Order extends Model
{
    public function isCancellable(): bool
    {
        return $this->status === OrderStatus::Pending
            && $this->created_at->gt(now()->subDay());
    }
}

عبارت «duplication is far cheaper than the wrong abstraction» (Sandi Metz) را به یاد داشته باشید. تکرار را تا دیدن الگوی واقعی تحمل کنید (Rule of Three)، بعد abstract کنید. اصل مقابل DRY افراطی را گاهی WET یا AHA (Avoid Hasty Abstractions) می‌نامند.

KISS و YAGNI

  • KISS: یک کوئری Eloquent ساده بهتر از Repository + Specification + Criteria برای یک CRUD ساده است. کد خوانا برای نفر بعدی مهم‌تر از کد «زیرکانه» است.
  • YAGNI: «شاید روزی چند دیتابیس پشتیبانی کنیم» دلیل کافی برای لایه انتزاع امروز نیست. هزینه‌های ساختن زودهنگام: زمان ساخت، پیچیدگی نگه‌داری، و اغلب حدس اشتباه درباره نیاز آینده.
  • YAGNI شامل کیفیت نمی‌شود: تست، مدیریت خطا و کد تمیز «قابلیت آینده» نیستند.

Law of Demeter (اصل کمترین دانش)

<?php
// نادرست: train wreck: کنترلر ساختار داخلی سه شیء را می‌داند
$city = $order->getCustomer()->getAddress()->getCity()->getName();

// درست: از شیء نزدیک بخواهید
$city = $order->shippingCityName();

هدف کاهش coupling است: اگر ساختار Address عوض شود، فقط Order باید تغییر کند. نکته: fluent interface‌ها (Query Builder، Collection) که هر بار همان نوع شیء را برمی‌گردانند، نقض Demeter نیستند؛ User::where(...)->orderBy(...)->get() مشکلی ندارد.

Tell, Don't Ask

<?php
// نادرست: Ask: منطق بیرون از شیء
if ($wallet->getBalance() >= $price) {
    $wallet->setBalance($wallet->getBalance() - $price);
}

// درست: Tell: شیء خودش قاعده را اجرا می‌کند
$wallet->pay($price); // اگر موجودی کافی نبود، InsufficientFunds پرتاب می‌شود

این اصل مستقیماً به encapsulation کمک می‌کند و جلوی Anemic Domain Model (مدل‌هایی که فقط getter/setter دارند و همه منطق در سرویس‌هاست) را می‌گیرد.

Separation of Concerns

در Laravel: Route (نگاشت URL)، Middleware (دغدغه‌های مشترک)، Form Request (اعتبارسنجی)، Controller (هماهنگی HTTP)، Action/Service (use case)، Model (داده و قواعد دامنه)، Resource/Blade (نمایش). SoC اصل کلی‌تری است که SRP در سطح کلاس و معماری لایه‌ای در سطح سیستم از آن پیروی می‌کنند.

سوال رایج: «تعارض DRY و KISS/YAGNI را توضیح دهید.» پاسخ: DRY افراطی abstractionهای زودهنگام و پیچیده می‌سازد (نقض KISS و YAGNI). راه تعادل: DRY را برای دانش و قواعد کسب‌وکار سخت‌گیرانه اجرا کنید، ولی شباهت ظاهری کد را تا تکرار سوم تحمل کنید.

Coupling و Cohesion

دو معیار بنیادی کیفیت طراحی که تقریباً همه اصول دیگر (SOLID، Demeter، SoC) در خدمت آنها هستند. هدف: Low Coupling, High Cohesion.

Coupling (وابستگی بین ماژول‌ها)

  • میزان وابستگی یک ماژول به ماژول‌های دیگر.
  • Coupling بالا: تغییر در A باعث تغییر در B، C و D می‌شود (shotgun surgery)، تست جداگانه سخت است.
  • کاهش با: interface، DI، event، Demeter، DTO در مرزها.

Cohesion (انسجام درون ماژول)

  • میزان ارتباط و هم‌هدفی اجزای داخل یک ماژول.
  • Cohesion بالا: متدها روی داده‌های مشترک و برای یک هدف کار می‌کنند.
  • Cohesion پایین: کلاس‌های Utils/Helper که مجموعه‌ای از توابع بی‌ربط‌اند.

Coincidental (تصادفی، کلاس Utils) ← Logical (دسته‌بندی منطقی مثل «همه ورودی‌ها») ← Temporal (کارهایی که هم‌زمان اجرا می‌شوند، مثل bootstrap) ← Procedural ← Communicational (روی داده مشترک) ← Sequential (خروجی یکی ورودی دیگری) ← Functional (همه اجزا برای یک وظیفه واحد) که بهترین است.

پاس‌دادن Illuminate\Http\Request به لایه سرویس یک stamp coupling رایج است: سرویس به HTTP گره می‌خورد و از Artisan command یا Job قابل استفاده نیست. داده‌های اعتبارسنجی‌شده یا یک DTO را پاس دهید.

اگر پرسیدند «چرا low coupling و high cohesion مهم‌اند؟»: (۱) تغییرپذیری، تغییر محلی می‌ماند؛ (۲) تست‌پذیری، اجزا جدا تست می‌شوند؛ (۳) قابلیت استفاده مجدد؛ (۴) فهم‌پذیری، برای فهمیدن یک ماژول لازم نیست کل سیستم را بخوانید؛ (۵) کار موازی تیم‌ها. این دو معمولاً با هم حرکت می‌کنند: افزایش cohesion معمولاً coupling را کم می‌کند.

DI، IoC و Service Locator

IoC
Inversion of Control: اصل کلی که در آن کنترل جریان یا ساخت اشیا از کد شما به یک چارچوب/کانتینر منتقل می‌شود («Don't call us, we'll call you»). Framework، Event، Template Method و DI همه شکل‌هایی از IoC هستند.
DI
Dependency Injection: شکل خاصی از IoC؛ شیء وابستگی‌هایش را نمی‌سازد و پیدا نمی‌کند، بلکه از بیرون دریافت می‌کند.
IoC Container
ابزاری که گراف وابستگی‌ها را می‌سازد و DI را خودکار می‌کند؛ در Laravel همان Service Container است.
Service Locator
شیء خودش از یک رجیستری سراسری وابستگی‌اش را درخواست می‌کند (app(Foo::class) داخل متد).

انواع DI

  • Constructor injection (پیش‌فرض و بهترین): وابستگی‌های اجباری در سازنده؛ شیء هرگز در وضعیت ناقص ساخته نمی‌شود و وابستگی‌ها صریح و قابل دیدن‌اند.
  • Method injection: وابستگی فقط برای یک متد لازم است؛ Laravel در متدهای کنترلر، handle() در Job و Command، و Listenerها این را خودکار انجام می‌دهد.
  • Setter injection: برای وابستگی‌های اختیاری؛ خطر وضعیت ناقص و mutable بودن.

Facadeها کجای ماجرا هستند؟

Facade (Cache::get()) یک static proxy به شیئی در container است؛ از نظر طراحی به Service Locator نزدیک است (وابستگی در امضا دیده نمی‌شود)، ولی Laravel با Cache::shouldReceive() و Mail::fake() تست‌پذیری‌اش را حفظ کرده. در کد دامنه و کتابخانه‌های قابل استفاده مجدد، تزریق Contract (مثل Illuminate\Contracts\Cache\Repository) صریح‌تر است؛ در کنترلر و کد چسب (glue)، Facade قابل‌قبول و رایج است.

«Constructor over-injection» (سازنده‌ای با ۸ وابستگی) مشکل DI نیست؛ علامت نقض SRP است. راه‌حل، پنهان‌کردن وابستگی‌ها با app() نیست، بلکه شکستن کلاس است.

جمع‌بندی برای پاسخ: IoC اصل است، DI الگو/تکنیک پیاده‌سازی آن، Container ابزار خودکارسازی DI، و DIP اصل طراحی درباره اینکه به چه چیزی (abstraction) وابسته شویم. Service Locator هم IoC است ولی Mark Seemann آن را anti-pattern می‌داند چون وابستگی‌ها را پنهان می‌کند.

Clean Code

کد تمیز کدی است که خواندن، فهمیدن و تغییر دادنش برای نفر بعدی (یا خود شما شش ماه بعد) ساده باشد. کد بسیار بیشتر از نوشته‌شدن، خوانده می‌شود.

نام‌گذاری

  • نیت را آشکار کند: $elapsedDays نه $d؛ activeSubscribers() نه getList2().
  • کلاس‌ها اسم (InvoiceGenerator)، متدها فعل (generate())، boolean به شکل سوال (isPaid، hasAccess، canRefund).
  • از encoding و پیشوندهای بی‌معنا پرهیز کنید ($strName، IUserInterface)؛ اختصار فقط وقتی همه آن را می‌شناسند (id، url).
  • یک واژه برای یک مفهوم: اگر جایی fetch و جایی retrieve و جایی get برای یک عمل دارید، یکی کنید (Ubiquitous Language).

توابع کوچک، یک کار، یک سطح انتزاع

  • تابع باید یک کار انجام دهد و همه خطوطش در یک سطح انتزاع باشند (منطق سطح بالا و جزئیات regex در یک تابع قاطی نشوند).
  • آرگومان‌ها: هر چه کمتر بهتر؛ بیش از ۳ آرگومان نشانه نیاز به یک Parameter Object/DTO است. Flag argument (render(true)) یعنی تابع دو کار می‌کند؛ آن را دو تابع کنید. PHP 8 named arguments خوانایی فراخوانی را بهتر می‌کند ولی جایگزین طراحی خوب نیست.
  • Command-Query Separation: تابع یا وضعیت را تغییر دهد (command) یا چیزی برگرداند (query)، نه هر دو.
  • بدون اثر جانبی پنهان: تابعی به نام checkPassword() نباید session را هم initialize کند.

Early return و Guard clause

<?php
// نادرست: Arrow code (تو در تو)
public function refund(Order $order): void
{
    if ($order->isPaid()) {
        if (! $order->isRefunded()) {
            if ($order->paid_at->gt(now()->subDays(14))) {
                $this->gateway->refund($order);
            } else {
                throw new RefundWindowExpired();
            }
        }
    }
}

// درست: Guard clauses: شرایط استثنا اول، مسیر اصلی صاف
private const REFUND_WINDOW_DAYS = 14;

public function refund(Order $order): void
{
    if (! $order->isPaid() || $order->isRefunded()) {
        return;
    }
    if ($order->paid_at->lt(now()->subDays(self::REFUND_WINDOW_DAYS))) {
        throw new RefundWindowExpired();
    }

    $this->gateway->refund($order);
}

Magic number و Magic string

عدد یا رشته بی‌نام (14، 'pending'، 3) را با ثابت نام‌دار، Enum (PHP 8.1) یا کانفیگ جایگزین کنید. Enum‌های backed در Laravel مستقیماً در cast مدل و validation (Rule::enum()) استفاده می‌شوند.

<?php
enum OrderStatus: string
{
    case Pending = 'pending';
    case Paid = 'paid';
    case Cancelled = 'cancelled';

    public function isFinal(): bool
    {
        return $this === self::Cancelled;
    }
}

// Model
protected function casts(): array
{
    return ['status' => OrderStatus::class];
}

کامنت‌ها

  • کامنت جبران کد نامفهوم نیست؛ اول کد را با نام بهتر یا استخراج تابع گویا کنید.
  • کامنت خوب «چرا» را توضیح می‌دهد (تصمیم کسب‌وکار، محدودیت API خارجی، workaround یک باگ)، نه «چه» را.
  • کامنت‌های بد: تکرار کد، کد کامنت‌شده (git آن را نگه می‌دارد)، کامنت‌های قدیمی و گمراه‌کننده.
  • PHPDoc برای چیزی که type system بیان نمی‌کند ارزش دارد: @param array<int, OrderItem>، @throws.

مدیریت خطا و Exception

  • Exception به‌جای کد خطا یا false/null مبهم؛ exception‌های دامنه‌ای با نام گویا (InsufficientFunds) بسازید.
  • Fail fast: ورودی نامعتبر را زود رد کنید (در سازنده value object یا Form Request).
  • exception را نبلعید: catch (\Exception $e) {} خالی باگ‌ها را پنهان می‌کند. یا مدیریت کنید، یا با context بیشتر دوباره پرتاب کنید (throw new PaymentFailed('...', previous: $e)).
  • فقط چیزی را catch کنید که می‌توانید درباره‌اش کاری انجام دهید؛ بقیه به handler سراسری Laravel (bootstrap/app.php → withExceptions()) برسد.
  • null برنگردانید اگر می‌توانید مجموعه خالی یا Null Object برگردانید؛ null هم پاس ندهید.

«چه چیزی کد را تمیز می‌کند؟» را با این ساختار پاسخ دهید: نام‌گذاری گویا ← توابع کوچک تک‌مسئولیتی با آرگومان کم ← نبود اثر جانبی پنهان ← early return به‌جای تودرتویی ← ثابت/enum به‌جای عدد جادویی ← مدیریت خطای صریح ← تست. و اشاره کنید که Boy Scout Rule («کد را تمیزتر از آنچه تحویل گرفتی تحویل بده») راه عملی حفظ کیفیت است.

مثال: Primitive Obsession ← Value Object

<?php
// نادرست: هر جا موبایل استفاده شده باید دوباره validate و normalize شود
function sendOtp(string $mobile): void { /* ... */ }

// درست: Value Object: معتبر بودن در لحظه ساخت تضمین می‌شود
final readonly class Mobile
{
    public string $value;

    public function __construct(string $raw)
    {
        $normalized = preg_replace('/^(\+98|0098|0)/', '0', trim($raw));
        if (! preg_match('/^09\d{9}$/', $normalized)) {
            throw new InvalidArgumentException("Invalid mobile: {$raw}");
        }
        $this->value = $normalized;
    }

    public function equals(self $other): bool
    {
        return $this->value === $other->value;
    }
}

function sendOtp(Mobile $mobile): void { /* دیگر نیازی به بررسی نیست */ }

<?php
// نادرست: سرویس دائم داده‌های Cart را بیرون می‌کشد

{

روند امن Refactoring

  1. اول تست بنویسید که رفتار فعلی را قفل کند (در کد legacy: characterization test).
  2. گام‌های کوچک بردارید و بعد از هر گام تست‌ها را اجرا کنید.
  3. refactoring و تغییر رفتار (feature/bugfix) را در یک commit قاطی نکنید.
  4. از ابزارها کمک بگیرید: refactor خودکار IDE، تحلیل ایستا (PHPStan/Larastan، Psalm)، و Rector برای تبدیل‌های خودکار.

تفاوت Shotgun Surgery و Divergent Change سوال محبوبی است: در shotgun surgery یک تغییر به چند کلاس پخش می‌شود (cohesion پایین در سطح سیستم، دانش پراکنده)؛ در divergent change یک کلاس به‌خاطر چند نوع تغییر ویرایش می‌شود (نقض SRP).

معماری لایه‌ای، Hexagonal و DDD

معماری لایه‌ای (Layered / N-tier)

┌─ Presentation ──── Controller, FormRequest, Resource, Blade
│        ▼
├─ Application ───── Action / Service / Use Case, DTO
│        ▼
├─ Domain ────────── Model, Value Object, Business Rules, Events
│        ▼
└─ Infrastructure ── Eloquent, Queue, Mail, HTTP Client, Gateway

Rule: each layer depends only on the layer below it.

مزیت: سادگی و تفکیک دغدغه‌ها. ایراد کلاسیک: لایه دامنه به زیرساخت (دیتابیس) وابسته است، پس منطق کسب‌وکار بدون دیتابیس قابل تست نیست. Clean/Hexagonal دقیقاً این وابستگی را با DIP برعکس می‌کنند.

Service class و Action class در Laravel

Service class

  • گروهی از عملیات مرتبط حول یک مفهوم: SubscriptionService با subscribe()، cancel()، renew().
  • خطر: به مرور تبدیل به God Class می‌شود.

Action class

  • یک کلاس = یک use case با یک متد عمومی (handle/execute/__invoke): CancelSubscription.
  • SRP عالی، قابل استفاده مجدد از Controller، Job، Command و Listener.
  • خطر: تعداد زیاد فایل؛ بیش‌ازحد برای CRUD ساده.
<?php
final class CancelSubscription
{
    public function __construct(private PaymentGateway $gateway) {}

    public function handle(Subscription $subscription, CancelReason $reason): void
    {
        if ($subscription->isCancelled()) {
            throw new SubscriptionAlreadyCancelled();
        }

        DB::transaction(function () use ($subscription, $reason) {
            $subscription->cancel($reason); // قاعده دامنه داخل مدل
            $this->gateway->stopRecurring($subscription->gateway_id);
        });

        SubscriptionCancelled::dispatch($subscription);
    }
}

// قابل استفاده از Controller، Artisan command یا Job
app(CancelSubscription::class)->handle($sub, CancelReason::UserRequest);

فراخوانی سرویس خارجی (HTTP) داخل DB::transaction ریسک دارد: اگر درگاه موفق شود و commit شکست بخورد، دو سیستم ناسازگار می‌شوند؛ تراکنش هم مدت زیادی باز می‌ماند. در سیستم واقعی معمولاً اثر خارجی را بعد از commit (مثلاً با DB::afterCommit() یا یک Job با afterCommit) یا با الگوی Outbox انجام می‌دهند.

Hexagonal (Ports & Adapters) و Clean Architecture

          Driving adapters                      Driven adapters
   (HTTP Controller, CLI, Queue)          (Eloquent Repo, SMS, Payment API)
              │                                      ▲
              ▼                                      │ implements
        ┌───────────── Port (in) ─────────── Port (out) ────┐
        │                  APPLICATION CORE                  │
        │        Use Cases  +  Domain Model (framework-free)    │
        └────────────────────────────────────────────────────┘
   Dependency Rule: all source-code dependencies point inward.
  • Port: interfaceی که هسته تعریف می‌کند؛ ورودی (use case) یا خروجی (PaymentGateway، OrderRepository).
  • Adapter: پیاده‌سازی port با فناوری مشخص (Controller، EloquentOrderRepository، ZarinpalGateway).
  • Clean Architecture (Uncle Bob) همین ایده با دایره‌های هم‌مرکز Entities ← Use Cases ← Interface Adapters ← Frameworks است؛ Onion هم مشابه است.
  • مزیت: هسته بدون دیتابیس و framework قابل تست است و فناوری بیرونی قابل تعویض. هزینه: کد و mapping بیشتر (مدل دامنه جدا از مدل Eloquent). برای CRUD ساده over-engineering است؛ برای دامنه پیچیده و طول عمر بالا ارزشمند.

واژگان پایه DDD

Entity
شیئی با هویت (identity) پایدار که در طول زمان تغییر می‌کند؛ دو Entity با id یکسان، یکی‌اند حتی اگر ویژگی‌هایشان فرق کند (User، Order).
Value Object
شیء بدون هویت که با مقدارش تعریف می‌شود، تغییرناپذیر (immutable) است و برابری‌اش بر اساس مقدار است (Money، Email، DateRange).
Aggregate
خوشه‌ای از Entity و Value Object که به‌عنوان یک واحد سازگاری رفتار می‌کند؛ فقط از طریق Aggregate Root تغییر می‌کند (Order ریشه و OrderLine‌ها عضو). مرز تراکنش معمولاً یک aggregate است.
Repository
انتزاعی شبیه کالکشن برای بارگذاری و ذخیره aggregateها، که جزئیات persistence را پنهان می‌کند.
Domain Service
منطق دامنه‌ای که طبیعتاً به هیچ Entity تعلق ندارد (مثل انتقال وجه بین دو حساب).
Domain Event
رخدادی معنادار در دامنه به زمان گذشته (OrderPlaced).
Ubiquitous Language
زبان مشترک تیم فنی و کسب‌وکار که در کد هم دقیقاً همان استفاده می‌شود.
Bounded Context
مرزی که در آن یک مدل و زبان مشخص معتبر است («مشتری» در فروش با «مشتری» در پشتیبانی متفاوت است).

تفاوت Entity و Value Object را با معیار برابری توضیح دهید: Entity با identity مقایسه می‌شود و mutable است؛ Value Object با مقادیر مقایسه می‌شود و immutable است (تغییر = ساخت شیء جدید). در Laravel، value object را می‌توان با custom cast (پیاده‌سازی CastsAttributes) به ستون‌های مدل وصل کرد.

سوالات تشریحی

Abstraction و Encapsulation را تعریف کنید و تفاوت آنها را با مثال توضیح دهید.

Abstraction: نمایش ویژگی‌ها و رفتارهای ضروری یک مفهوم و پنهان‌کردن جزئیات پیاده‌سازی از مصرف‌کننده؛ پاسخ به «چه کاری انجام می‌شود». ابزار: interface و abstract class.

Encapsulation: بسته‌بندی داده و رفتار در یک واحد و محدود کردن دسترسی مستقیم به وضعیت داخلی تا invariantها حفظ شوند؛ پاسخ به «چه کسی و چطور داده را تغییر می‌دهد». ابزار: private، protected، readonly و متدهای کنترل‌شده.

  • Abstraction در سطح طراحی است (چه رابطی ارائه شود)، Encapsulation در سطح پیاده‌سازی (داده چطور محافظت شود).
  • مثال: PaymentGateway::charge() انتزاع است؛ مصرف‌کننده نمی‌داند پشت آن زرین‌پال است یا Stripe. داخل کلاس ZarinpalGateway، کلید API و کلاینت HTTP به‌صورت private نگه‌داری می‌شوند؛ این کپسوله‌سازی است.
  • مثال دیگر: کلاس Account با فیلد private $balance که فقط از طریق withdraw() تغییر می‌کند و قاعده «منفی نشدن» را اجرا می‌کند.

رابطه: این دو مکمل‌اند؛ انتزاع رابط ساده را تعریف می‌کند و کپسوله‌سازی تضمین می‌کند کسی از رابط عبور نکند و به داده دست نزند. کپسوله‌سازی به معنای getter/setter برای همه فیلدها نیست؛ setter بی‌قیدوشرط عملاً کپسوله‌سازی را از بین می‌برد.

تفاوت interface، abstract class و trait در PHP چیست؟ در چه شرایطی هر کدام را انتخاب می‌کنید؟
  • Interface: فقط قرارداد (امضای متدهای public و ثابت‌ها)، بدون state. یک کلاس می‌تواند چند interface را implement کند. نوع (type) می‌سازد و برای type hint و instanceof قابل استفاده است.
  • Abstract class: قرارداد + پیاده‌سازی مشترک و state، سازنده دارد، نمونه‌سازی مستقیم ندارد. فقط یک والد (single inheritance). رابطه is-a.
  • Trait: مکانیزم horizontal reuse؛ کامپایلر کدش را داخل کلاس کپی می‌کند. نوع نمی‌سازد (instanceof روی trait معنا ندارد)، می‌تواند property و متد abstract داشته باشد و تداخل نام‌ها با insteadof/as حل می‌شود.

انتخاب:

  • مرز بین ماژول‌ها، چند پیاده‌سازی قابل‌جایگزین، تست با mock ← interface (DIP).
  • خانواده‌ای از کلاس‌ها با الگوریتم مشترک (Template Method) یا state مشترک ← abstract class (که معمولاً خودش interface را implement می‌کند).
  • قطعه رفتار کوچک و تکراری در کلاس‌های بی‌ربط ← trait؛ مثل SoftDeletes و Notifiable در Laravel.

الگوی رایج: interface برای قرارداد + trait برای پیاده‌سازی پیش‌فرض. اشتباه رایج: استفاده از trait برای منطق کسب‌وکار سنگین با وابستگی پنهان به propertyهای کلاس میزبان که coupling پنهان و تست سخت ایجاد می‌کند.

چرا گفته می‌شود «Composition را به Inheritance ترجیح دهید»؟ با یک مثال توضیح دهید و بگویید کجا وراثت هنوز انتخاب درستی است.

تعریف: Composition یعنی ساختن رفتار از ترکیب اشیای کوچک‌تر (رابطه has-a) و واگذاری کار به آنها؛ Inheritance یعنی دریافت رفتار از کلاس والد (رابطه is-a).

مشکلات وراثت برای reuse:

  • Coupling شدید به جزئیات والد و مشکل Fragile Base Class.
  • رابطه ایستا و در runtime غیرقابل تغییر.
  • انفجار کلاس‌ها برای ترکیب ویژگی‌ها: PdfReport، EmailedPdfReport، EmailedCsvReport…
  • ارث‌بردن متدهای نامربوط (Refused Bequest، نقض LSP).

مثال: به‌جای سلسله‌مراتب گزارش، یک ReportJob که Formatter (Pdf/Csv) و Delivery (Email/S3) را از سازنده می‌گیرد. هر بُعد مستقل تغییر می‌کند و هر ترکیب در container ساخته می‌شود. الگوهای Strategy و Decorator (مثلاً CachedUserRepository که repository دیگری را wrap می‌کند) نمونه‌های این اصل‌اند.

کجا وراثت درست است: رابطه واقعی is-a که قرارداد والد را کامل رعایت می‌کند؛ نقاط توسعه framework (Model، FormRequest، Command)؛ Template Method کم‌عمق. توصیه عملی: کلاس‌ها را پیش‌فرض final کنید.

اصل Single Responsibility را تعریف کنید. آیا معنی آن «هر کلاس فقط یک کار» است؟ نقض آن در یک کنترلر Laravel و اصلاحش را شرح دهید.

تعریف: یک ماژول باید فقط یک دلیل برای تغییر داشته باشد؛ یا به تعبیر دقیق‌تر Robert Martin، فقط در برابر یک actor (گروه ذی‌نفع) مسئول باشد.

سوءبرداشت: SRP به معنای «یک متد در هر کلاس» یا «یک کار ریز» نیست. معیار، منبع تغییر است. کلاس Invoice می‌تواند چند متد مرتبط داشته باشد؛ ولی اگر محاسبه مالیات (تیم مالی) و قالب PDF (تیم طراحی) هر دو در آن باشد، دو مسئولیت دارد.

نقض رایج: متد store کنترلری که اعتبارسنجی، محاسبه قیمت، ذخیره در DB، فراخوانی درگاه و ارسال ایمیل را با هم انجام می‌دهد.

اصلاح در Laravel:

  • اعتبارسنجی و authorization ← FormRequest
  • قواعد قیمت ← PriceCalculator یا متد مدل
  • use case ← Action مثل PlaceOrder
  • ایمیل ← Event + Listener صف‌شده
  • شکل خروجی ← API Resource

کنترلر فقط درخواست HTTP را به use case وصل می‌کند. مزایا: تست‌پذیری، استفاده مجدد Action از Command یا Job، تغییرات محلی. هشدار: افراط در SRP به کلاس‌های ریز بی‌شمار و cohesion پایین می‌رسد؛ چیزهایی که با هم تغییر می‌کنند باید کنار هم بمانند.

کد زیر کدام اصل SOLID را نقض می‌کند؟ آن را بازطراحی کنید. match ($type) { 'pdf' => ..., 'csv' => ..., 'excel' => ... } در متد export() که با هر فرمت جدید باید ویرایش شود.

اصل نقض‌شده: Open/Closed Principle؛ کلاس برای افزودن رفتار جدید (فرمت جدید) باید تغییر کند، نه گسترش. معمولاً SRP هم نقض شده چون منطق همه فرمت‌ها در یک کلاس است، و اگر همین switch در جاهای دیگر (مثلاً تعیین Content-Type) تکرار شده باشد، Shotgun Surgery هم داریم.

بازطراحی با Strategy + DIP:

<?php
interface Exporter
{
    public function format(): string;          // 'pdf' | 'csv' | ...
    public function export(Collection $rows): string;
    public function mimeType(): string;
}

final class CsvExporter implements Exporter { /* ... */ }
final class PdfExporter implements Exporter { /* ... */ }

final class ExportService
{
    /** @param iterable<Exporter> $exporters */
    public function __construct(private iterable $exporters) {}

    public function export(string $format, Collection $rows): string
    {
        foreach ($this->exporters as $exporter) {
            if ($exporter->format() === $format) {
                return $exporter->export($rows);
            }
        }
        throw new UnsupportedFormat($format);
    }
}

// ServiceProvider
$this->app->tag([CsvExporter::class, PdfExporter::class], 'exporters');
$this->app->when(ExportService::class)->needs('$exporters')->giveTagged('exporters');

نتیجه: فرمت Excel = یک کلاس جدید + ثبت tag، بدون دست‌زدن به ExportService. هر exporter جدا تست می‌شود. نکته YAGNI: اگر فقط یک یا دو فرمت دارید و تغییر نمی‌کنند، همان match قابل‌قبول است؛ abstraction را وقتی بسازید که نقطه تغییر واقعاً ظاهر شده.

اصل Liskov Substitution را توضیح دهید. چرا مثال Square و Rectangle نقض این اصل است؟ نشانه‌های نقض LSP در کد چیست؟

تعریف: اگر S زیرنوع T است، باید بتوان هر شیء T را با شیء S جایگزین کرد بدون اینکه درستی برنامه تغییر کند. زیرنوع باید قرارداد رفتاری والد را رعایت کند، نه فقط امضای متدها را.

قواعد: precondition سخت‌تر نشود؛ postcondition ضعیف‌تر نشود؛ invariantها حفظ شوند؛ exception غیرمنتظره جدید پرتاب نشود؛ پارامترها contravariant و نوع بازگشتی covariant باشند.

Square/Rectangle: قرارداد ضمنی Rectangle این است که setWidth فقط عرض را عوض می‌کند. Square برای حفظ invariant خودش (ضلع‌های برابر) هر دو را عوض می‌کند، پس کدی که setWidth(5); setHeight(4); انجام می‌دهد و انتظار مساحت ۲۰ دارد، با Square عدد ۱۶ می‌گیرد. رابطه is-a ریاضی، رابطه is-a رفتاری نیست. راه‌حل: حذف وراثت و استفاده از interface مشترک Shape با value objectهای immutable.

نشانه‌ها:

  • instanceof برای رفتار خاص زیرنوع در کد مصرف‌کننده
  • متد override‌شده خالی یا throw new LogicException('Not supported')
  • تست‌های والد که برای فرزند شکست می‌خورند

اهمیت: LSP پیش‌نیاز OCP است؛ driverهای Laravel (cache، queue، filesystem) و fakeهای تست فقط چون LSP را رعایت می‌کنند قابل‌تعویض‌اند.

Interface Segregation را تعریف کنید و تفاوتش را با SRP بگویید. چه مثال‌هایی از ISP در Laravel وجود دارد؟

تعریف: هیچ کلاینتی نباید مجبور به وابستگی به متدهایی باشد که استفاده نمی‌کند. به‌جای interface «چاق»، interfaceهای کوچک نقش‌محور بسازید.

چرا:

  • تغییر یک متد بی‌ربط، کلاینت‌هایی را که از آن استفاده نمی‌کنند متأثر نمی‌کند.
  • پیاده‌سازی‌ها مجبور به متد خالی یا exception نمی‌شوند (کمک به LSP).
  • test doubleها کوچک و ساده می‌شوند.

مثال: UserRepository با ۱۰ متد (find، save، export، syncLdap…) را به FindsUsers، SavesUsers، ExportsUsers بشکنیم؛ سرویس گزارش فقط ExportsUsers را دریافت کند.

تفاوت با SRP: SRP درباره دلایل تغییر یک کلاس (دید پیاده‌ساز) است؛ ISP درباره اندازه قرارداد از دید مصرف‌کننده است. یک کلاس منسجم می‌تواند چند interface کوچک را implement کند.

Laravel: Arrayable، Jsonable، Htmlable، Responsable هر کدام یک متد دارند؛ interfaceهای نشانگر مثل ShouldQueue، ShouldBeUnique و ShouldBroadcast فقط یک نقش را اعلام می‌کنند؛ و Contracts به قراردادهای کوچک مثل Cache\Store و Cache\Repository تفکیک شده‌اند.

Dependency Inversion Principle، Dependency Injection و Inversion of Control را تعریف و با هم مقایسه کنید.
  • DIP (اصل طراحی): ماژول سطح بالا به ماژول سطح پایین وابسته نباشد؛ هر دو به abstraction وابسته باشند و abstraction متعلق به لایه سطح بالا باشد. موضوعش «به چه چیزی وابسته شویم» است.
  • IoC (اصل کلی): کنترل جریان یا ساخت اشیا از کد شما به framework منتقل می‌شود («Don't call us, we'll call you»). Event، Template Method و DI همه IoC هستند.
  • DI (تکنیک): شیء وابستگی‌اش را نمی‌سازد، از بیرون دریافت می‌کند؛ از طریق constructor (ترجیحی)، method یا setter. موضوعش «چطور وابستگی به دست برسد» است.
  • IoC Container (ابزار): Service Container لاراول که با Reflection سازنده‌ها را می‌خواند و گراف وابستگی را خودکار می‌سازد (auto-wiring).
<?php
interface SmsSender { public function send(string $to, string $msg): void; }

final class OtpService {
    public function __construct(private SmsSender $sms) {} // DI + DIP
}

$this->app->bind(SmsSender::class, KavenegarSmsSender::class); // Container

نکته کلیدی: این‌ها مستقل‌اند. می‌توان DI انجام داد و DIP را نقض کرد (تزریق KavenegarClient concrete)؛ و می‌توان DIP داشت بدون container (سیم‌کشی دستی در composition root). مزیت مشترک: loose coupling، تعویض پیاده‌سازی، و تست با fake ($this->app->instance(SmsSender::class, new FakeSms)).

چرا Service Locator را یک anti-pattern می‌دانند؟ آیا Facadeهای Laravel هم Service Locator هستند؟

Service Locator: کلاس وابستگی‌هایش را در زمان اجرا از یک رجیستری سراسری درخواست می‌کند (app(Foo::class) داخل متد) به‌جای اینکه آنها را دریافت کند.

مشکلات:

  • وابستگی پنهان: امضای کلاس دروغ می‌گوید؛ برای فهمیدن نیازهایش باید کل بدنه را خواند.
  • Coupling به container: کلاس بدون framework قابل استفاده نیست.
  • خطای دیرهنگام: binding اشتباه فقط وقتی همان مسیر کد اجرا شود دیده می‌شود.
  • تست سخت‌تر: باید container را پیکربندی کنید به‌جای پاس‌دادن ساده fake به سازنده.
  • مخفی‌شدن نشانه نقض SRP (سازنده‌ای که اگر صریح بود ۹ وابستگی نشان می‌داد).

Facadeها: از نظر ساختار، Facade یک static proxy روی container است و به Service Locator شبیه است: وابستگی در امضا دیده نمی‌شود. اما Laravel مشکل تست را با Mail::fake()، Queue::fake() و Cache::shouldReceive() حل کرده است. جمع‌بندی منصفانه:

  • در کنترلر، route و کد چسب: Facade راحت و قابل‌قبول است.
  • در کد دامنه، Actionهای مهم و پکیج‌های قابل استفاده مجدد: constructor injection با Contract (Illuminate\Contracts\Mail\Mailer) صریح‌تر و مستقل‌تر است.
Coupling و Cohesion را تعریف کنید. چرا هدف «Low Coupling, High Cohesion» است؟ برای هر کدام یک مثال بد و خوب بزنید.

Coupling: میزان وابستگی یک ماژول به ماژول‌های دیگر؛ هرچه بیشتر، تغییر در یکی بیشتر به دیگری سرایت می‌کند. انواع از بد به خوب: content، common/global، control (flag)، stamp (پاس دادن کل ساختار)، data، message.

Cohesion: میزان ارتباط و هم‌هدفی اجزای درون یک ماژول. بدترین: coincidental (کلاس Utils)؛ بهترین: functional (همه اجزا برای یک وظیفه).

چرا: تغییرات محلی می‌مانند، تست جداگانه ممکن است، استفاده مجدد و فهم ساده‌تر است، و تیم‌ها موازی کار می‌کنند.

DRY، KISS و YAGNI را توضیح دهید. آیا ممکن است این اصول با هم در تعارض باشند؟ چگونه تعادل برقرار می‌کنید؟
  • DRY: هر تکه دانش (قاعده کسب‌وکار) یک نمایش واحد و معتبر در سیستم داشته باشد. درباره دانش است، نه شباهت متنی کد.
  • KISS: ساده‌ترین راه‌حل درست را انتخاب کنید؛ پیچیدگی باید توجیه داشته باشد.
  • YAGNI: قابلیت یا انعطافی را که امروز نیاز نیست، نسازید؛ هزینه ساخت و نگه‌داری قطعی است ولی نیاز آینده حدسی.

تعارض: DRY افراطی دو کد را که فقط ظاهراً شبیه‌اند ولی به دلایل متفاوت تغییر می‌کنند، در یک abstraction ادغام می‌کند. نتیجه: تابعی با چند پارامتر boolean و شاخه‌های if که هم KISS را نقض می‌کند و هم coupling بین دو ویژگی بی‌ربط ایجاد می‌کند. همچنین ساختن لایه‌های عام برای «جلوگیری از تکرار در آینده» نقض YAGNI است.

تعادل:

  • DRY را برای قواعد کسب‌وکار سخت‌گیرانه اجرا کنید (مثل Order::isCancellable() به‌جای تکرار شرط در کنترلر، Blade و Job).
  • برای شباهت تصادفی (incidental duplication) Rule of Three: تا سومین تکرار صبر کنید.
  • به یاد داشته باشید: «تکرار ارزان‌تر از abstraction اشتباه است» (Sandi Metz).
  • YAGNI شامل کیفیت نمی‌شود؛ تست و مدیریت خطا «قابلیت آینده» نیستند.
Law of Demeter و Tell, Don't Ask را با مثال توضیح دهید. آیا زنجیره Query Builder در Laravel نقض Law of Demeter است؟

Law of Demeter (اصل کمترین دانش): متد یک شیء فقط باید با خودش، پارامترهایش، اشیایی که خودش ساخته و اجزای مستقیمش صحبت کند؛ نه با «غریبه‌ها»ی برگشتی از آنها.

<?php
// نقض: کنترلر ساختار سه شیء را می‌داند
$order->getCustomer()->getAddress()->getCity()->getName();
// اصلاح (Hide Delegate)
$order->shippingCityName();

Tell, Don't Ask: به‌جای پرسیدن وضعیت و تصمیم‌گیری بیرون از شیء، به شیء دستور دهید و بگذارید خودش قواعد را اجرا کند.

<?php
// Ask
if ($wallet->balance() >= $price) { $wallet->setBalance($wallet->balance() - $price); }
// Tell
$wallet->pay($price); // InsufficientFunds در صورت کمبود

هدف هر دو: کاهش coupling و تقویت encapsulation؛ وقتی ساختار Address عوض شود فقط Order تغییر می‌کند، و منطق کیف پول در یک جا می‌ماند (جلوگیری از Anemic Domain Model).

Query Builder: خیر. User::where(...)->orderBy(...)->limit(10)->get() یک fluent interface است که هر متد همان شیء builder را برمی‌گرداند؛ شما به ساختار داخلی اشیای مختلف سرک نمی‌کشید. Demeter درباره عبور از چند شیء متفاوت است، نه تعداد نقطه‌ها.

کد زیر چه مشکلاتی از نظر Clean Code دارد؟ آن را بازنویسی کنید. function proc($u, $f = false) { if ($u) { if ($u->s == 2) { if ($f) { mail(...); } return $u->p * 0.09; } } return null; }

مشکلات:

  • نام‌گذاری مبهم: proc، $u، $f، s، p نیت را بیان نمی‌کنند.
  • Magic numbers: 2 (کدام وضعیت؟) و 0.09 (نرخ مالیات؟).
  • Flag argument: $f یعنی تابع دو کار می‌کند.
  • اثر جانبی پنهان و نقض CQS: تابعی که مقدار محاسبه می‌کند، ایمیل هم می‌فرستد.
  • Arrow code: سه سطح if تودرتو.
  • برگرداندن null مبهم و نبود type hint.
<?php
final class TaxCalculator
{
    private const VAT_RATE = 0.10; // از config یا جدول نرخ‌ها خوانده شود

    public function vatFor(User $user): int
    {
        if ($user->status !== UserStatus::Active) {
            throw new InactiveUser($user->id);
        }

        return (int) round($user->plan_price * self::VAT_RATE);
    }
}

// ارسال ایمیل جدا: رویداد یا فراخوانی صریح در use case
$vat = $taxCalculator->vatFor($user);
VatCalculated::dispatch($user, $vat);

اصول به‌کاررفته: نام‌های گویا، type hint کامل، Enum به‌جای عدد جادویی، ثابت نام‌دار، guard clause، حذف flag با جداکردن دو مسئولیت، و exception صریح به‌جای null. همچنین مبالغ پولی را بهتر است به‌صورت integer (ریال/سنت) یا value object Money نگه داشت تا خطای ممیز شناور رخ ندهد.

Code smell چیست؟ چهار smell از میان Long Method، God Class، Feature Envy، Primitive Obsession و Shotgun Surgery را توضیح داده و روش refactoring هر کدام را بگویید.

تعریف: code smell نشانه‌ای سطحی در کد است که احتمالاً به مشکل عمیق‌تر طراحی اشاره دارد؛ باگ نیست ولی تغییر و فهم کد را سخت می‌کند. Refactoring تغییر ساختار داخلی بدون تغییر رفتار بیرونی است، در گام‌های کوچک و با پشتوانه تست.

  • Long Method: متدی که چند کار و چند سطح انتزاع دارد. ← Extract Method با نام گویا، Decompose Conditional، guard clause.
  • God Class: کلاسی که بخش بزرگی از سیستم را می‌داند و انجام می‌دهد (UserService دوهزار خطی). ← Extract Class، تفکیک به Actionها، انتقال قواعد به مدل یا value object.
  • Feature Envy: متدی که بیشتر با داده‌های کلاس دیگر کار می‌کند (سرویسی که $cart->items را پیمایش و جمع می‌زند). ← Move Method به کلاس صاحب داده ($cart->subtotal()).
  • Primitive Obsession: مفاهیم دامنه با string و int (ایمیل، موبایل، مبلغ) که اعتبارسنجی‌شان همه‌جا تکرار می‌شود. ← Replace Primitive with Value Object (Mobile، Money) یا Enum.
  • Shotgun Surgery: یک تغییر منطقی (مثلاً افزودن وضعیت سفارش) نیازمند ویرایش ده فایل. ← Move Method/Field و تجمیع دانش در یک جا (Enum با متدهای رفتاری، polymorphism).

روند امن: اول تست (یا characterization test برای legacy)، سپس گام‌های کوچک با اجرای تست بعد از هر گام، جداکردن commit refactoring از تغییر رفتار، و کمک گرفتن از PHPStan/Larastan و Rector.

یک سناریو: کلاس OrderService در پروژه شما ۲۵۰۰ خط و ۱۵ وابستگی در سازنده دارد و هر تغییر کوچک باعث باگ در جای دیگری می‌شود. چگونه آن را بازطراحی می‌کنید؟

تشخیص: این یک God Class است؛ نقض SRP (دلایل متعدد تغییر)، cohesion پایین، coupling بالا (۱۵ وابستگی = constructor over-injection) و احتمالاً Divergent Change.

گام‌ها:

  1. شبکه ایمنی: قبل از هر تغییری، تست‌های feature/characterization برای رفتارهای حیاتی (ثبت سفارش، لغو، بازپرداخت) بنویسید.
  2. نقشه مسئولیت‌ها: متدها را بر اساس use case و وابستگی‌هایی که استفاده می‌کنند گروه‌بندی کنید؛ گروه‌ها معمولاً مرز طبیعی کلاس‌های جدیدند.
  3. استخراج Actionها: PlaceOrder، CancelOrder، RefundOrder؛ هر کدام فقط ۲-۳ وابستگی لازمش را می‌گیرد.
  4. انتقال قواعد به دامنه: منطقی مثل isCancellable() یا محاسبه جمع به مدل یا value object (رفع Feature Envy و Anemic Model).
  5. جداسازی اثرات جانبی: ایمیل، پیامک، به‌روزرسانی انبار با Event/Listener صف‌شده.
  6. مرزهای خارجی پشت interface: درگاه پرداخت و سرویس‌های third-party (DIP) تا قابل fake باشند.
  7. مهاجرت تدریجی (Strangler): متدهای قدیمی موقتاً به Actionهای جدید delegate کنند تا فراخواننده‌ها مرحله‌به‌مرحله منتقل شوند؛ سپس حذف.

نتیجه مورد انتظار: کلاس‌های کوچک با تست واحد ساده، تغییرات محلی، و امکان استفاده مجدد use caseها از Controller، Command و Job. هشدار: بازنویسی یک‌باره (big-bang rewrite) ریسک بالایی دارد؛ refactoring تدریجی با تست ارجح است.

معماری Hexagonal (Ports & Adapters) چیست و چه تفاوتی با معماری لایه‌ای سنتی دارد؟ در چه پروژه‌ای ارزش هزینه‌اش را دارد؟

تعریف: معماری‌ای (Alistair Cockburn) که هسته اپلیکیشن (use caseها و مدل دامنه) را در مرکز و مستقل از فناوری نگه می‌دارد. هسته از طریق Portها (interfaceهایی که خودش تعریف می‌کند) با بیرون ارتباط دارد و Adapterها این portها را با فناوری مشخص پیاده می‌کنند.

  • Driving adapters (ورودی): HTTP Controller، Artisan Command، Queue consumer.
  • Driven adapters (خروجی): EloquentOrderRepository، ZarinpalGateway، SMS.
  • Dependency Rule: وابستگی‌های کد همیشه به سمت مرکز.

تفاوت با لایه‌ای: در معماری لایه‌ای سنتی، لایه دامنه به لایه دسترسی داده وابسته است (بالا ← پایین)، پس منطق کسب‌وکار به دیتابیس گره خورده. Hexagonal با DIP این وابستگی را برعکس می‌کند: زیرساخت به interface تعریف‌شده در هسته وابسته است. همچنین «بالا و پایین» ندارد؛ همه فناوری‌ها (UI، DB، صف) به یک اندازه «بیرون» هستند.

مزایا: تست هسته بدون DB و framework، تعویض فناوری، تمرکز بر دامنه، تأخیر در تصمیم‌های فنی.

هزینه: کد بیشتر، mapping بین مدل دامنه و مدل persistence (در Laravel یعنی کنار گذاشتن بخشی از راحتی Active Record)، و منحنی یادگیری.

کی ارزش دارد: دامنه پیچیده با قواعد زیاد، عمر طولانی محصول، چند کانال ورودی، یا وابستگی به سرویس‌های خارجی متغیر. برای CRUD ساده یا MVP، Laravel استاندارد + Action classها کافی و عملی‌تر است.

Entity، Value Object و Aggregate را در DDD تعریف کنید و برای هر کدام مثالی در یک فروشگاه اینترنتی بزنید.
  • Entity: شیئی با هویت پایدار که در طول زمان تغییر می‌کند؛ برابری بر اساس identity. مثال: Customer و Order؛ اگر آدرس مشتری عوض شود، همان مشتری است.
  • Value Object: شیء بدون هویت که با مقدارش تعریف می‌شود، immutable است و برابری‌اش بر اساس مقدار است؛ اعتبارسنجی در سازنده. مثال: Money(150000, 'IRR')، Address، Email. تغییر = ساخت شیء جدید.
  • Aggregate: خوشه‌ای از Entity و Value Object که مرز سازگاری (consistency boundary) را تعریف می‌کند و فقط از طریق Aggregate Root تغییر می‌کند. مثال: Order (ریشه) با OrderLine‌ها؛ افزودن قلم فقط با $order->addLine() که قاعده «حداکثر ۱۰ قلم» و جمع کل را حفظ می‌کند.
<?php
final readonly class Money
{
    public function __construct(public int $amount, public string $currency)
    {
        if ($amount < 0) throw new InvalidArgumentException();
    }

    public function add(Money $other): self
    {
        if ($other->currency !== $this->currency) throw new CurrencyMismatch();
        return new self($this->amount + $other->amount, $this->currency);
    }
}

قواعد Aggregate: بیرون از aggregate فقط به ریشه ارجاع دهید؛ بین aggregateها با id ارجاع دهید نه شیء؛ معمولاً هر تراکنش یک aggregate را تغییر می‌دهد و هماهنگی بین aggregateها با Domain Event انجام می‌شود. در Laravel، value object را می‌توان با custom cast به ستون مدل Eloquent وصل کرد.

خلاصه برای مرور سریع

OOP

  • Encapsulation: پنهان‌کردن state، حفظ invariant (private، readonly).
  • Abstraction: نمایش «چه» نه «چطور» (interface).
  • Inheritance: is-a، قوی‌ترین coupling، Fragile Base Class.
  • Polymorphism: یک رابط، چند پیاده‌سازی؛ جایگزین switch روی نوع.
  • Interface = قرارداد؛ Abstract = قرارداد + کد مشترک (is-a)؛ Trait = کپی کد، نوع نمی‌سازد.
  • Composition (has-a) > Inheritance برای reuse؛ کلاس‌ها را پیش‌فرض final کنید.

اصول دیگر

  • DRY: یک نمایش برای هر دانش؛ Rule of Three؛ تکرار < abstraction اشتباه.
  • KISS: ساده‌ترین راه درست. YAGNI: چیزی که الان لازم نیست نساز.
  • Demeter: با غریبه حرف نزن؛ fluent builder نقض نیست.
  • Tell Don't Ask: $wallet->pay() نه get/set بیرونی.
  • SoC: Route / Middleware / Request / Controller / Action / Model / Resource.
  • Low coupling + High cohesion؛ Utils = cohesion تصادفی؛ پاس دادن Request به سرویس = stamp coupling.

DI / IoC

  • IoC = اصل؛ DI = تکنیک؛ Container = ابزار؛ DIP = جهت وابستگی.
  • Constructor injection برای وابستگی اجباری؛ method injection در controller/job.
  • bind (هر بار جدید)، singleton (یکی برای عمر app)، scoped (یکی در هر request/job)، when()->needs()->give().
  • Service Locator: وابستگی پنهان، خطای دیرهنگام؛ Facade = static proxy ولی با fake() قابل تست.
  • ۱۰ وابستگی در سازنده = بوی نقض SRP.

Clean Code

  • نام نیت‌نما؛ کلاس = اسم، متد = فعل، bool = is/has/can.
  • تابع کوچک، یک کار، یک سطح انتزاع، ≤ ۳ آرگومان، بدون flag.
  • CQS؛ بدون اثر جانبی پنهان؛ guard clause / early return.
  • ثابت نام‌دار و Enum به‌جای magic number/string.
  • کامنت «چرا» نه «چه»؛ کد کامنت‌شده را حذف کن.
  • Exception دامنه‌ای، fail fast، catch خالی ممنوع، previous: برای زنجیره.

Smell ← Refactoring

  • Long Method ← Extract Method
  • God Class ← Extract Class / Actions
  • Feature Envy ← Move Method
  • Primitive Obsession ← Value Object / Enum
  • Shotgun Surgery ← تجمیع دانش (Move)
  • Divergent Change ← Extract Class
  • Switch روی نوع ← Polymorphism
  • Long Param List / Data Clumps ← Parameter Object / DTO
  • Message Chain ← Hide Delegate
  • Refused Bequest ← Delegation به‌جای وراثت
  • اول تست، گام کوچک، commit جدا.

معماری و DDD

  • Layered: هر لایه به پایینی؛ دامنه به DB گره می‌خورد.
  • Hexagonal/Clean: هسته در مرکز، Port = interface هسته، Adapter = پیاده‌سازی؛ وابستگی‌ها به داخل.
  • Service = گروه عملیات؛ Action = یک use case.
  • Entity = هویت + mutable؛ Value Object = مقدار + immutable؛ Aggregate = مرز سازگاری با Root.
  • Bounded Context، Ubiquitous Language، Domain Event، Repository.
