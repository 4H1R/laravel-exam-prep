Container در برابر ماشین مجازی

Container یک فرایند (یا گروهی از فرایندها) ایزوله روی سیستم‌عامل میزبان است که کرنل میزبان را به اشتراک می‌گذارد اما فایل‌سیستم، شبکه، فهرست فرایندها و منابع محدودشده‌ی خودش را می‌بیند. ماشین مجازی (VM) یک کامپیوتر کامل شبیه‌سازی‌شده با کرنل و سیستم‌عامل مستقل است که روی Hypervisor اجرا می‌شود.

ایزوله‌سازی با Namespace و محدودیت با cgroup

Container جادو نیست؛ ترکیبی از قابلیت‌های کرنل Linux است:

Namespaces
«چه چیزی را می‌بیند». هر container نمای جداگانه‌ای از منابع دارد: pid (فرایندها؛ اولین فرایند PID 1 است)، net (کارت شبکه، IP و پورت‌ها)، mnt (فایل‌سیستم)، uts (hostname)، ipc، user (نگاشت UIDها) و cgroup.
cgroups
«چقدر می‌تواند مصرف کند». محدود کردن و اندازه‌گیری CPU، حافظه، I/O و تعداد فرایندها (مثلاً --memory=512m --cpus=1.5). اگر container از سقف حافظه عبور کند، OOM killer آن را می‌کشد (exit code 137).
Union / Overlay FS
فایل‌سیستم لایه‌ای (درایور overlay2): لایه‌های فقط‌خواندنی image به‌علاوه‌ی یک لایه‌ی قابل‌نوشتن مخصوص هر container.
Capabilities و seccomp
محدود کردن دسترسی‌های root و system callها برای کاهش سطح حمله.
ویژگیContainerVM
کرنلمشترک با میزبانکرنل مستقل برای هر VM
زمان راه‌اندازیمیلی‌ثانیه تا ثانیه (شروع یک فرایند)ده‌ها ثانیه تا دقیقه (boot سیستم‌عامل)
اندازهمگابایتگیگابایت
سربارنزدیک به صفرسربار Hypervisor و Guest OS
ایزوله‌سازیدر سطح فرایند؛ ضعیف‌تر (کرنل مشترک)در سطح سخت‌افزار مجازی؛ قوی‌تر
سیستم‌عامل مهمانهمان خانواده‌ی کرنل میزبان (container لینوکسی نیازمند کرنل لینوکس)هر سیستم‌عاملی
تراکمصدها container روی یک میزبانتعداد محدود VM

جمله‌ی کلیدی: «Container مجازی‌سازی در سطح سیستم‌عامل است، VM مجازی‌سازی در سطح سخت‌افزار.» Container سبک‌تر و سریع‌تر است، چون کرنل را به اشتراک می‌گذارد؛ اما به همین دلیل ایزوله‌سازی امنیتی آن ضعیف‌تر است. در عمل این دو رقیب نیستند: معمولاً containerها داخل VMهای ابری اجرا می‌شوند.

Docker Desktop روی Windows و macOS در واقع یک VM سبک لینوکسی (یا WSL2 در Windows) اجرا می‌کند و containerهای لینوکسی داخل آن اجرا می‌شوند؛ به همین دلیل bind mount روی این سیستم‌ها کندتر از Linux است.

Image، Container، Registry و معماری Docker

Image
قالب فقط‌خواندنی و تغییرناپذیر شامل فایل‌سیستم لایه‌ای و metadata (دستور پیش‌فرض، متغیرها، پورت‌ها). مثل «کلاس» در برنامه‌نویسی شیءگرا.
Container
نمونه‌ی در حال اجرای یک image: لایه‌های image + یک لایه‌ی نازک قابل‌نوشتن + فرایند ایزوله. مثل «شیء». از یک image می‌توان ده‌ها container ساخت. با حذف container، لایه‌ی قابل‌نوشتنش هم حذف می‌شود.
Registry
سرویس ذخیره و توزیع imageها: Docker Hub، GitHub Container Registry (ghcr.io)، GitLab Registry، AWS ECR یا Harbor خصوصی. یک registry شامل repositoryها و هر repository شامل tagهاست.
Dockerfile
دستورالعمل متنی ساخت image.
Tag و Digest
Tag برچسب قابل‌تغییر انسانی (php:8.3-fpm-alpine)؛ Digest هش محتوایی تغییرناپذیر (php@sha256:…).

معماری

  docker CLI ──(REST API)──► dockerd (Docker Engine) ──► containerd ──► runc ──► container
                                    │
                                    └──── pull / push ────► Registry

Docker CLI فقط کلاینت است؛ کار اصلی را daemon (dockerd) انجام می‌دهد که مدیریت چرخه‌ی عمر container را به containerd و ساخت فرایند ایزوله را به runc می‌سپارد. قالب image و runtime توسط استاندارد OCI (Open Container Initiative) تعریف شده‌اند؛ به همین دلیل imageهای ساخته‌شده با Docker در Kubernetes، Podman و سایر runtimeها قابل اجرا هستند.

دسترسی به سوکت daemon (/var/run/docker.sock) یا عضویت در گروه docker عملاً معادل دسترسی root روی میزبان است. mount کردن این سوکت داخل یک container (مثلاً برای CI) یک ریسک امنیتی جدی است.

لایه‌ها و Cache ساخت

هر دستور RUN، COPY و ADD در Dockerfile یک لایه‌ی جدید می‌سازد (دستورهایی مثل ENV، CMD و EXPOSE فقط metadata تغییر می‌دهند). لایه‌ها بین imageها به اشتراک گذاشته می‌شوند: ده image که روی php:8.3-fpm-alpine ساخته شده‌اند، لایه‌های پایه را یک بار روی دیسک نگه می‌دارند و یک بار دانلود می‌کنند.

قانون Cache

هنگام build، Docker برای هر دستور بررسی می‌کند آیا لایه‌ای با همان دستور و همان ورودی قبلاً ساخته شده است. برای COPY/ADD، ورودی شامل checksum محتوای فایل‌ها است. به محض اینکه یک لایه cache miss شود، همه‌ی لایه‌های بعدی دوباره ساخته می‌شوند.

ترتیب بد

FROM php:8.3-fpm-alpine
WORKDIR /var/www/html
COPY . .
# هر تغییر در هر فایل ⇒ نصب مجدد همه‌ی وابستگی‌ها
RUN composer install --no-dev

ترتیب خوب

FROM php:8.3-fpm-alpine
WORKDIR /var/www/html
COPY composer.json composer.lock ./
# فقط وقتی lock عوض شود دوباره اجرا می‌شود
RUN composer install --no-dev --no-scripts
COPY . .
  • از کم‌تغییرترین به پرتغییرترین: image پایه ← بسته‌های سیستمی ← extensionها ← فایل‌های وابستگی (composer.lock، package-lock.json) ← نصب وابستگی ← کد برنامه.
  • ترکیب دستورات مرتبط در یک RUN و پاک‌سازی در همان لایه: حذف فایل در لایه‌ی بعدی حجم image را کم نمی‌کند، چون فایل در لایه‌ی قبلی باقی است.
  • apt-get update و apt-get install را در یک RUN بنویسید؛ وگرنه لایه‌ی cache‌شده‌ی update قدیمی می‌ماند و نصب بعدی با فهرست کهنه اجرا می‌شود.
  • BuildKit cache mount (RUN --mount=type=cache,target=...) دانلودهای Composer/npm را بین buildها نگه می‌دارد بدون اینکه وارد لایه‌ی image شوند.
  • در CI که ماشین تازه است، cache محلی وجود ندارد؛ از cache خارجی (--cache-from، type=gha یا type=registry) استفاده کنید.
docker history myapp:1.4.0          # لایه‌ها و حجم هرکدام
docker build --no-cache -t myapp .   # build بدون استفاده از cache

سوال کلاسیک: «چرا COPY composer.json composer.lock را جدا و قبل از COPY . . می‌نویسیم؟» چون کد برنامه مدام عوض می‌شود ولی وابستگی‌ها به‌ندرت؛ با این ترتیب لایه‌ی سنگین composer install تا وقتی lock تغییر نکرده از cache استفاده می‌شود و build از چند دقیقه به چند ثانیه می‌رسد.

COPY در برابر ADD

ADD علاوه بر کپی، اگر مبدأ یک آرشیو tar محلی باشد آن را خودکار استخراج می‌کند و می‌تواند از URL دانلود کند. این رفتارهای ضمنی غافلگیرکننده‌اند (مثلاً فایل .tar.gz که قرار بود همان‌طور کپی شود، باز می‌شود) و دانلود با ADD معمولاً بدون بررسی checksum است. توصیه‌ی رسمی: همیشه COPY، مگر اینکه دقیقاً قابلیت استخراج خودکار را بخواهید. برای دانلود، RUN curl + بررسی checksum در همان لایه شفاف‌تر است.

ENV در برابر ARG

ARG PHP_VERSION=8.3                 # ARG قبل از FROM فقط برای خود FROM قابل استفاده است
FROM php:${PHP_VERSION}-fpm-alpine

ARG APP_VERSION=dev                 # باید بعد از FROM دوباره اعلام شود تا در stage در دسترس باشد
LABEL org.opencontainers.image.version=$APP_VERSION

ENV APP_ENV=production \
    COMPOSER_ALLOW_SUPERUSER=1      # در container اجراشده هم وجود دارد
docker build --build-arg PHP_VERSION=8.4 --build-arg APP_VERSION=1.4.0 -t myapp:1.4.0 .

هیچ‌کدام برای secret مناسب نیستند: ENV در image باقی می‌ماند (docker inspect) و مقدار ARG در docker history دیده می‌شود. برای secretهای زمان build (مثلاً توکن مخزن خصوصی Composer) از BuildKit secret استفاده کنید که فقط در طول همان RUN mount می‌شود و در هیچ لایه‌ای ذخیره نمی‌شود:

RUN --mount=type=secret,id=composer_auth,target=/root/.composer/auth.json \
    composer install --no-dev --prefer-dist
docker build --secret id=composer_auth,src=./auth.json -t myapp .

HEALTHCHECK

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost/up || exit 1

exit code صفر یعنی سالم و ۱ یعنی ناسالم. Docker خودش container ناسالم را restart نمی‌کند (در حالت standalone)، اما Compose با depends_on: condition: service_healthy و Swarm از آن استفاده می‌کنند. Kubernetes دستور HEALTHCHECK را نادیده می‌گیرد و probeهای خودش را دارد.

PHP-FPM پروتکل FastCGI صحبت می‌کند، نه HTTP؛ پس health check مستقیم با curl روی پورت 9000 کار نمی‌کند. معمولاً health check روی container Nginx (مسیر /up لاراول) تعریف می‌شود، یا با فعال کردن ping.path در pool FPM و ابزاری مثل cgi-fcgi.

VOLUME

VOLUME /var/lib/mysql اعلام می‌کند آن مسیر داده‌ی ماندگار است؛ اگر هنگام run چیزی به آن mount نشود، Docker یک volume بی‌نام (anonymous) می‌سازد. تغییراتی که در مراحل بعدی build روی آن مسیر انجام شود دور ریخته می‌شود. برای imageهای برنامه معمولاً نیازی به VOLUME نیست؛ mount را در Compose یا هنگام run تعریف کنید.

CMD، ENTRYPOINT، Exec form و PID 1

Exec form در برابر Shell form

Exec form (توصیه‌شده)

CMD ["php-fpm"]
ENTRYPOINT ["php", "artisan"]
  • آرایه‌ی JSON؛ فرایند مستقیماً اجرا می‌شود و PID 1 است.
  • سیگنال‌ها (SIGTERM) مستقیم به برنامه می‌رسند.
  • بدون پردازش shell: $VAR باز نمی‌شود.

Shell form

CMD php-fpm
# معادل: ["/bin/sh", "-c", "php-fpm"]
  • از طریق /bin/sh -c اجرا می‌شود؛ shell PID 1 است.
  • sh سیگنال SIGTERM را به فرزند منتقل نمی‌کند ⇒ خاموش شدن غیر graceful.
  • امکان استفاده از متغیر و pipe.

CMD و ENTRYPOINT با هم

ENTRYPOINT برنامه‌ی ثابت و CMD آرگومان‌های پیش‌فرض آن است. آرگومان‌های docker run جایگزین CMD می‌شوند، نه ENTRYPOINT.

الگوی entrypoint script

برای کارهای آماده‌سازی در زمان start (مثل cache کردن config با env واقعی) یک اسکریپت entrypoint می‌نویسیم که در انتها با exec فرایند اصلی را جایگزین خودش کند تا آن فرایند PID 1 شود:

#!/bin/sh
# docker/entrypoint.sh
set -e

php artisan config:cache
php artisan event:cache

exec "$@"     # بدون exec، shell به‌عنوان PID 1 باقی می‌ماند و سیگنال‌ها گم می‌شوند
COPY docker/entrypoint.sh /usr/local/bin/entrypoint
ENTRYPOINT ["entrypoint"]
CMD ["php-fpm"]

PID 1 و سیگنال‌ها

  • docker stop ابتدا SIGTERM (یا STOPSIGNAL تعریف‌شده) می‌فرستد و پس از مهلت (پیش‌فرض ۱۰ ثانیه) SIGKILL. docker kill به‌طور پیش‌فرض فوراً SIGKILL می‌فرستد.
  • کرنل برای PID 1 رفتار پیش‌فرض سیگنال‌ها را اعمال نمی‌کند؛ اگر برنامه handler نداشته باشد، SIGTERM نادیده گرفته می‌شود و container پس از ۱۰ ثانیه kill می‌شود.
  • PID 1 مسئول جمع‌آوری فرایندهای zombie است. اگر برنامه این کار را نمی‌کند، از docker run --init (tini) یا init: true در Compose استفاده کنید.
  • php artisan queue:work با extension pcntl به SIGTERM واکنش graceful نشان می‌دهد: job جاری را تمام و سپس خارج می‌شود. مهلت توقف (stop_grace_period) باید از طولانی‌ترین job بیشتر باشد.

اگر container هنگام docker stop دقیقاً ۱۰ ثانیه طول می‌کشد تا متوقف شود، تقریباً همیشه علتش این است که فرایند اصلی SIGTERM را دریافت یا پردازش نمی‌کند (shell form، اسکریپت بدون exec، یا نبود handler). راه‌حل: exec form، exec "$@" و در صورت نیاز --init.

Dockerfile چندمرحله‌ای Production برای Laravel

Multi-stage build چند FROM در یک Dockerfile دارد. هر stage می‌تواند ابزارهای سنگین build (Composer، Node، کامپایلرها) داشته باشد و image نهایی فقط خروجی آن‌ها را با COPY --from برمی‌دارد. نتیجه: image کوچک‌تر، سطح حمله‌ی کمتر و جدا شدن محیط build از runtime.

  ┌────────────┐    ┌────────────────────┐    ┌──────────────────┐
  │ base       │──► │ vendor (+composer) │──► │                  │
  │ php-fpm +  │    └────────────────────┘    │  runtime         │──► app image (php-fpm)
  │ extensions │──────────────────────────────►│  (non-root,      │
  └────────────┘    ┌────────────────────┐    │   opcache)       │──► web image (nginx + public)
                    │ assets (node/vite) │──► │                  │
                    └────────────────────┘    └──────────────────┘
# syntax=docker/dockerfile:1

############################
# 1) base: PHP-FPM + extensions
############################
FROM php:8.3-fpm-alpine AS base

RUN apk add --no-cache icu-libs libzip fcgi \
 && apk add --no-cache --virtual .build-deps $PHPIZE_DEPS icu-dev libzip-dev \
 && docker-php-ext-install -j"$(nproc)" pdo_mysql intl zip bcmath pcntl opcache \
 && pecl install redis \
 && docker-php-ext-enable redis \
 && apk del .build-deps

WORKDIR /var/www/html

############################
# 2) vendor: Composer dependencies
############################
FROM base AS vendor
COPY --from=composer:2 /usr/bin/composer /usr/bin/composer
ENV COMPOSER_CACHE_DIR=/tmp/composer-cache

COPY composer.json composer.lock ./
RUN --mount=type=cache,target=/tmp/composer-cache \
    composer install --no-dev --no-scripts --no-autoloader --prefer-dist --no-interaction

COPY . .
RUN composer dump-autoload --optimize --classmap-authoritative --no-dev

############################
# 3) assets: Vite build
############################
FROM node:22-alpine AS assets
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY vite.config.js ./
COPY resources ./resources
COPY public ./public
RUN npm run build

############################
# 4) runtime: final PHP-FPM image
############################
FROM base AS runtime

COPY docker/php/opcache.ini /usr/local/etc/php/conf.d/zz-opcache.ini
COPY docker/php/php.ini     /usr/local/etc/php/conf.d/zz-app.ini

COPY --from=vendor --chown=www-data:www-data /var/www/html /var/www/html
COPY --from=assets --chown=www-data:www-data /app/public/build /var/www/html/public/build

COPY docker/entrypoint.sh /usr/local/bin/entrypoint
RUN chmod +x /usr/local/bin/entrypoint \
 && php artisan route:cache \
 && php artisan view:cache \
 && chown -R www-data:www-data storage bootstrap/cache

USER www-data
EXPOSE 9000
ENTRYPOINT ["entrypoint"]
CMD ["php-fpm"]

############################
# 5) web: Nginx serving static files, proxying PHP to app
############################
FROM nginx:1.27-alpine AS web
COPY docker/nginx/default.conf /etc/nginx/conf.d/default.conf
COPY --from=runtime /var/www/html/public /var/www/html/public
; docker/php/opcache.ini
opcache.enable=1
opcache.memory_consumption=256
opcache.interned_strings_buffer=16
opcache.max_accelerated_files=20000
opcache.validate_timestamps=0   ; کد داخل image تغییر نمی‌کند ⇒ بررسی timestamp لازم نیست

چرا این طراحی؟

  • stage پایه‌ی مشترک: Composer روی همان PHP و extensionهای runtime اجرا می‌شود، پس بررسی platform requirements (ext-intl، نسخه‌ی PHP) واقعی است. (استفاده از image composer به‌عنوان stage مستقل رایج است، اما PHP آن ممکن است با runtime فرق کند.)
  • build-deps موقت: کامپایلرها ($PHPIZE_DEPS) در همان لایه نصب و حذف می‌شوند؛ فقط کتابخانه‌های runtime (icu-libs، libzip) می‌مانند.
  • ترتیب لایه‌ها: ابتدا lock fileها، سپس نصب وابستگی و در آخر کد؛ برای npm هم همین الگو.
  • --no-dev و --classmap-authoritative: بدون PHPUnit و ابزارهای توسعه، و autoload سریع‌تر بدون جست‌وجوی فایل‌سیستم.
  • Node فقط در stage build: image نهایی Node و node_modules ندارد.
  • کاربر غیر root: USER www-data؛ فقط storage و bootstrap/cache قابل‌نوشتن‌اند.
  • config:cache در زمان start (در entrypoint)، نه build؛ چون متغیرهای محیطی و secretهای واقعی فقط در runtime وجود دارند و نباید وارد image شوند. route:cache و view:cache به env وابسته نیستند و در build امن‌اند.
  • image جداگانه‌ی web: Nginx به فایل‌های استاتیک public/ نیاز دارد؛ با COPY --from=runtime دقیقاً همان نسخه‌ی assetها را دارد.
docker build --target runtime -t registry.example.com/shop/app:3f9c2ab .
docker build --target web     -t registry.example.com/shop/web:3f9c2ab .

با --target می‌توان یک stage مشخص را ساخت؛ مثلاً یک stage dev با Xdebug و وابستگی‌های dev روی همان base، تا dev و prod از یک Dockerfile و یک پایه بیایند.

اجرای php artisan migrate در entrypoint هر container، وقتی چند replica هم‌زمان بالا می‌آیند، باعث race condition و قفل روی جدول migrations می‌شود. migration را به‌صورت یک مرحله‌ی جدا در pipeline یا یک Job/سرویس یک‌باره اجرا کنید.

بهترین روش‌های امنیت و حجم

  • Pin کردن نسخه: php:8.3-fpm-alpine3.20 به‌جای php:latest؛ برای تکرارپذیری کامل، pin با digest (@sha256:...) و به‌روزرسانی کنترل‌شده (مثلاً با Renovate/Dependabot).
  • اجرا با کاربر غیر root (USER). اگر مهاجم از برنامه نفوذ کند، root داخل container خطر فرار به میزبان را بیشتر می‌کند.
  • هیچ secretی در لایه‌ها: نه در ENV، نه ARG، نه فایل کپی‌شده (حتی اگر در لایه‌ی بعد پاک شود). از BuildKit secret و تزریق runtime استفاده کنید.
  • Multi-stage تا ابزار build وارد image نهایی نشود.
  • حداقل بسته: apk add --no-cache، apt-get install --no-install-recommends و پاک کردن /var/lib/apt/lists/* در همان لایه.
  • اسکن آسیب‌پذیری image در CI: Trivy، Docker Scout، Grype؛ build را روی CVE بحرانی fail کنید.
  • Rebuild دوره‌ای تا وصله‌های امنیتی image پایه اعمال شوند.
  • محدودیت‌های runtime: --read-only (با tmpfs برای مسیرهای لازم)، --cap-drop ALL، --security-opt no-new-privileges، محدودیت --memory/--cpus؛ هرگز --privileged بدون دلیل.
  • Image رسمی یا verified از منبع مطمئن؛ امضای image (مثلاً cosign) در محیط‌های حساس.

«چرا RUN rm secret.txt بعد از COPY secret.txt امن نیست؟» چون image مجموعه‌ای از لایه‌هاست و لایه‌ی COPY همچنان فایل را دارد؛ با docker save و باز کردن لایه‌ها، فایل قابل بازیابی است. حذف در لایه‌ی بعد فقط آن را «پنهان» می‌کند.

Exit codeهای مهم برای دیباگ

  • 0: پایان عادی (برای سرویس یعنی فرایند به background رفته یا کارش تمام شده).
  • 1: خطای برنامه؛ docker logs را ببینید.
  • 126 / 127: دستور قابل اجرا نیست / پیدا نشد (مثلاً نبود bash در Alpine، یا فایل با line ending ویندوزی CRLF).
  • 137: = 128 + 9 (SIGKILL): kill شده؛ اغلب OOM (OOMKilled: true در inspect) یا پایان مهلت stop.
  • 143: = 128 + 15 (SIGTERM): با SIGTERM خاتمه یافته.

ذخیره‌سازی: Volume، Bind Mount و tmpfs

لایه‌ی قابل‌نوشتن container موقت است: با حذف container از بین می‌رود و برای نوشتن سنگین هم کند است (copy-on-write). داده‌ی ماندگار باید بیرون از آن نگه داشته شود.

نوعمحل دادهمدیریتکاربرد
Named Volumeناحیه‌ی مدیریت‌شده توسط Docker (روی Linux معمولاً /var/lib/docker/volumes/)Docker (docker volume ...)؛ مستقل از چرخه‌ی عمر containerداده‌ی دیتابیس، Redis، فایل‌های آپلود در Production
Bind Mountمسیر دلخواه روی میزبانشما؛ وابسته به ساختار پوشه‌ی میزبانکد منبع در توسعه (hot reload)، فایل پیکربندی
tmpfsRAM میزبانبا توقف container پاک می‌شودفایل‌های موقت حساس یا پرسرعت؛ همراه با --read-only

docker run --read-only --tmpfs /tmp myapp                            # tmpfs
docker volume ls

docker volume rm mysql-data
  • --mount صریح‌تر از -v است؛ اگر مسیر میزبان در bind mount وجود نداشته باشد، -v آن را به‌صورت پوشه می‌سازد ولی --mount خطا می‌دهد.
  • اگر یک named volume خالی روی مسیری از image که محتوا دارد mount شود، Docker محتوای image را در volume کپی می‌کند؛ bind mount این کار را نمی‌کند و محتوای image را می‌پوشاند (مثلاً bind mount پروژه، پوشه‌ی vendor داخل image را مخفی می‌کند).
  • مالکیت و permission: در bind mount، UID فایل‌ها همان UID میزبان است؛ مشکل رایج «Permission denied» روی storage/ در Laravel از اینجاست.
  • Backup volume: با یک container موقت: docker run --rm -v mysql-data:/data -v "$(pwd)":/backup alpine tar czf /backup/db.tgz -C /data . (برای دیتابیس، dump منطقی مثل mysqldump امن‌تر از کپی فایل‌های در حال استفاده است).

در Production کد برنامه داخل image است (تغییرناپذیر)، نه bind mount. Volume فقط برای state (دیتابیس، آپلود). در محیط چندسروری حتی آپلودها بهتر است روی object storage (S3) بروند تا containerها stateless بمانند.

دو اشتباه بسیار رایج

  • localhost داخل container یعنی خود همان container، نه میزبان و نه container دیگر. اگر Laravel داخل container با DB_HOST=127.0.0.1 تنظیم شده باشد، به MySQL در container دیگر وصل نمی‌شود. باید از نام سرویس (DB_HOST=mysql) استفاده کرد. برای دسترسی به سرویسی روی خود میزبان، در Docker Desktop نام host.docker.internal وجود دارد (روی Linux با --add-host=host.docker.internal:host-gateway).
  • Publish کردن پورت لازم نیست برای ارتباط container به container در یک شبکه؛ آن‌ها مستقیم روی پورت داخلی (مثلاً 3306) با هم حرف می‌زنند. -p فقط برای دسترسی از بیرون میزبان است.

Port publishing

  Internet ──► Host:8080 ──(NAT)──► nginx container:80 ──► app container:9000 (FastCGI, داخلی)
                                              │
                                              └──► mysql:3306  (بدون publish؛ فقط در شبکه‌ی داخلی)

-p 3306:3306 پورت را روی همه‌ی interfaceهای میزبان باز می‌کند و Docker با قواعد iptables خودش ممکن است فایروال‌هایی مثل UFW را دور بزند. دیتابیس را publish نکنید؛ اگر لازم است، فقط روی loopback: -p 127.0.0.1:3306:3306.

تفاوت EXPOSE و -p: EXPOSE فقط metadata/مستندسازی است و پورتی را روی میزبان باز نمی‌کند؛ -p (یا ports: در Compose) پورت میزبان را به پورت container نگاشت می‌کند. -P همه‌ی پورت‌های EXPOSE‌شده را به پورت‌های تصادفی میزبان publish می‌کند.

Docker Compose: استک کامل Laravel

Docker Compose ابزاری برای تعریف و اجرای برنامه‌های چند container به‌صورت declarative در یک فایل YAML (compose.yaml) است. Compose به‌طور خودکار یک شبکه‌ی user-defined برای پروژه می‌سازد، پس سرویس‌ها با نام سرویس یکدیگر را پیدا می‌کنند. دستور فعلی docker compose (نسخه‌ی ۲، plugin داخلی) است و کلید version: در بالای فایل منسوخ شده است.

# compose.yaml
x-app: &app
  image: registry.example.com/shop/app:${APP_TAG:-dev}
  build:
    context: .
    target: runtime
  env_file: .env
  restart: unless-stopped
  depends_on:
    mysql:
      condition: service_healthy
    redis:
      condition: service_healthy

services:
  app:                                  # PHP-FPM
    <<: *app
    depends_on:
      migrate:
        condition: service_completed_successfully
    volumes:
      - storage:/var/www/html/storage/app

  migrate:                              # اجرای یک‌باره‌ی migration
    <<: *app
    command: ["php", "artisan", "migrate", "--force"]
    restart: "no"

  queue:                                # worker صف — همان image، فرایند متفاوت
    <<: *app
    command: ["php", "artisan", "queue:work", "redis", "--tries=3", "--max-time=3600"]
    stop_grace_period: 60s
    depends_on:
      migrate:
        condition: service_completed_successfully

  scheduler:                            # زمان‌بند لاراول
    <<: *app
    command: ["php", "artisan", "schedule:work"]
    depends_on:
      migrate:
        condition: service_completed_successfully

  nginx:
    image: registry.example.com/shop/web:${APP_TAG:-dev}
    build:
      context: .
      target: web
    ports:
      - "8080:80"
    depends_on:
      - app
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost/up"]
      interval: 30s
      timeout: 3s
      retries: 3

  mysql:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: ${DB_DATABASE}
      MYSQL_USER: ${DB_USERNAME}
      MYSQL_PASSWORD: ${DB_PASSWORD}
      MYSQL_ROOT_PASSWORD: ${DB_ROOT_PASSWORD}
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s

  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

volumes:
  mysql-data:
  redis-data:
  storage:
# docker/nginx/default.conf
server {
    listen 80;
    root /var/www/html/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass app:9000;            # نام سرویس Compose
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }

    location ~ /\.(?!well-known).* {
        deny all;
    }
}

نکات کلیدی

  • depends_on ساده فقط ترتیب start را تعیین می‌کند، نه آماده بودن. MySQL ممکن است چند ثانیه بعد از start هنوز اتصال نپذیرد. با condition: service_healthy و تعریف healthcheck، Compose صبر می‌کند تا سرویس واقعاً سالم شود. service_completed_successfully برای jobهای یک‌باره مثل migrate.
  • یک image، چند نقش: app، queue، scheduler و migrate همه از یک image با command متفاوت‌اند؛ پس نسخه‌ی کد در همه یکسان است.
  • YAML anchor و extension field (x-app) برای جلوگیری از تکرار پیکربندی.
  • دو نوع env: فایل .env کنار compose.yaml به‌طور خودکار برای جایگزینی متغیرها در خود فایل Compose (${DB_DATABASE}) خوانده می‌شود؛ env_file: متغیرها را به داخل container می‌فرستد؛ environment: مقدار صریح برای container. این دو مفهوم متفاوت‌اند.
  • در ارتباط داخلی، سرویس‌ها روی پورت داخلی با هم حرف می‌زنند؛ فقط Nginx پورت publish کرده است.
  • LOG_CHANNEL=stderr: لاگ‌های Laravel به خروجی استاندارد می‌روند و با docker compose logs یا collector مرکزی جمع می‌شوند.

اصل «one concern per container»: به‌جای اجرای PHP-FPM، Nginx، cron و queue worker در یک container با supervisord، هرکدام container جداگانه دارند. دلایل:

  • مقیاس‌پذیری مستقل: می‌توان ۵ worker صف و ۲ app داشت (docker compose up -d --scale queue=5).
  • چرخه‌ی عمر و سلامت مستقل: crash شدن worker باعث restart وب نمی‌شود؛ Docker فقط وضعیت PID 1 را می‌بیند.
  • لاگ تفکیک‌شده و محدودیت منابع جداگانه.
  • Scheduler فقط یک نمونه: اگر cron داخل هر replica برنامه باشد، با scale شدن، taskها چند بار اجرا می‌شوند. (برای اطمینان در چندسروری، onOneServer() با cache مشترک هم وجود دارد.)

این اصل قطعی نیست: «یک نگرانی در هر container»؛ PHP-FPM خودش چند فرایند worker دارد و این مشکلی نیست. بعضی imageها هم عمداً Nginx و FPM را با هم دارند (مثلاً برای سادگی در PaaS).

Logها، Dev در برابر Prod و Laravel Sail

لاگ به stdout/stderr

طبق اصل Twelve-Factor، برنامه لاگ را به‌صورت جریان رویداد به stdout/stderr می‌نویسد و مسئولیت جمع‌آوری، چرخش (rotation) و ارسال با محیط اجراست. Docker خروجی PID 1 را با logging driver (پیش‌فرض json-file) ذخیره می‌کند و docker logs آن را نشان می‌دهد. نوشتن لاگ در فایل داخل container یعنی: پر شدن لایه‌ی قابل‌نوشتن، از دست رفتن با حذف container و ندیدن آن در ابزارهای مرکزی.

  • Laravel: LOG_CHANNEL=stderr (کانال آماده در config/logging.php).
  • image رسمی PHP-FPM لاگ‌های خطای FPM و خروجی workerها را به stderr هدایت می‌کند؛ image رسمی Nginx هم access.log و error.log را به stdout/stderr لینک کرده است.
  • برای driver json-file چرخش را تنظیم کنید (max-size، max-file) وگرنه دیسک میزبان پر می‌شود.

Registry و استراتژی Tag

نام کامل یک image: [registry/][namespace/]repository[:tag][@digest]، مثلاً ghcr.io/acme/shop-app:1.4.2. اگر registry ذکر نشود Docker Hub فرض می‌شود و اگر tag ذکر نشود latest.

چرا به :latest تکیه نکنیم؟

  • latest فقط یک tag معمولی و قابل‌تغییر است؛ به معنای «جدیدترین» نیست، فقط پیش‌فرض است. هر push بدون tag آن را جابه‌جا می‌کند.
  • تکرارناپذیری: امروز و فردا docker pull app:latest ممکن است دو image متفاوت بدهد؛ دو سرور در یک کلاستر ممکن است نسخه‌های متفاوت اجرا کنند.
  • Rollback ناممکن: «نسخه‌ی قبلی latest» مشخص نیست.
  • ردیابی: از روی latest نمی‌توان فهمید کدام commit در حال اجراست.
  • Kubernetes برای tag latest به‌طور پیش‌فرض imagePullPolicy: Always در نظر می‌گیرد و رفتار cache متفاوتی دارد.

مقدمه‌ی Orchestration: Kubernetes و Swarm

Compose روی یک میزبان کار می‌کند. وقتی چند سرور، توزیع بار، self-healing، rolling update، مقیاس‌دهی خودکار و service discovery بین میزبان‌ها لازم باشد، به Orchestrator نیاز داریم. در Kubernetes وضعیت مطلوب را به‌صورت declarative تعریف می‌کنید و control loopها مداوم وضعیت واقعی را به سمت آن می‌برند.

اشیای اصلی Kubernetes

Pod
کوچک‌ترین واحد قابل استقرار؛ یک یا چند container که namespace شبکه (یک IP) و volumeها را به اشتراک می‌گذارند و روی یک node زمان‌بندی می‌شوند. Podها موقت‌اند و IP آن‌ها ثابت نیست.
ReplicaSet
تضمین می‌کند تعداد مشخصی Pod همیشه در حال اجرا باشد.
Deployment
مدیریت declarative برنامه‌های stateless: تعداد replica، image، استراتژی rolling update و rollback (kubectl rollout undo)؛ ReplicaSetها را می‌سازد.
Service
نقطه‌ی دسترسی پایدار (IP مجازی و نام DNS) و توزیع بار روی Podهایی که با selector انتخاب می‌شوند. انواع: ClusterIP (داخلی، پیش‌فرض)، NodePort، LoadBalancer.
Ingress
قواعد مسیریابی HTTP/HTTPS لایه‌ی ۷ (host و path، TLS) از بیرون به Serviceها؛ نیازمند یک Ingress Controller (مثل ingress-nginx).
ConfigMap
پیکربندی غیرحساس به‌صورت env یا فایل.
Secret
داده‌ی حساس؛ به‌طور پیش‌فرض فقط base64 است (نه رمزنگاری)؛ برای امنیت واقعی encryption at rest و RBAC یا ابزارهای خارجی لازم است.
Probes
livenessProbe (اگر رد شود container restart می‌شود)، readinessProbe (اگر رد شود از Service خارج می‌شود)، startupProbe (برای شروع کند).
دیگر
StatefulSet (هویت و ذخیره‌سازی پایدار، مثل دیتابیس)، Job/CronJob (migration، scheduler)، HorizontalPodAutoscaler، Namespace.

سوالات تشریحی

Container و ماشین مجازی را تعریف و مقایسه کنید. Container از چه قابلیت‌هایی در کرنل Linux برای ایزوله‌سازی استفاده می‌کند؟

تعریف: VM شبیه‌سازی کامل یک کامپیوتر روی Hypervisor است که سیستم‌عامل و کرنل مستقل خودش را دارد. Container یک یا چند فرایند ایزوله روی سیستم‌عامل میزبان است که کرنل میزبان را به اشتراک می‌گذارد و فایل‌سیستم، شبکه و فضای فرایند جداگانه می‌بیند.

سازوکار ایزوله‌سازی:

  • Namespaces (چه می‌بیند): pid، net، mnt، uts، ipc، user، cgroup.
  • cgroups (چقدر مصرف می‌کند): سقف CPU، حافظه، I/O.
  • Union filesystem (overlay2): لایه‌های فقط‌خواندنی image + لایه‌ی قابل‌نوشتن.
  • Capabilities و seccomp: محدودسازی دسترسی‌ها و system callها.

مقایسه:

  • سرعت و سبکی: container در حد ثانیه یا کمتر بالا می‌آید و مگابایتی است؛ VM نیاز به boot و گیگابایت‌ها حجم دارد.
  • تراکم: روی یک میزبان صدها container در برابر تعداد محدود VM.
  • ایزوله‌سازی: VM قوی‌تر است؛ آسیب‌پذیری کرنل در container می‌تواند به فرار به میزبان منجر شود.
  • سیستم‌عامل: container لینوکسی نیازمند کرنل لینوکس است (روی Mac/Windows با یک VM لینوکسی اجرا می‌شود)؛ VM هر سیستم‌عاملی را اجرا می‌کند.

جمع‌بندی: container مجازی‌سازی سطح سیستم‌عامل و VM مجازی‌سازی سطح سخت‌افزار است؛ در عمل مکمل‌اند و containerها معمولاً داخل VMهای ابری اجرا می‌شوند.

تفاوت Image، Container و Registry را توضیح دهید. لایه‌های image چه هستند و چه مزیتی دارند؟
  • Image: قالب فقط‌خواندنی و تغییرناپذیر شامل فایل‌سیستم لایه‌ای و metadata (CMD، ENV، پورت‌ها). مثل کلاس.
  • Container: نمونه‌ی در حال اجرای image؛ لایه‌های image + یک لایه‌ی قابل‌نوشتن + فرایند ایزوله. مثل شیء. با حذف container، تغییرات لایه‌ی قابل‌نوشتن از بین می‌رود.
  • Registry: سرویس ذخیره و توزیع image (Docker Hub، GHCR، ECR، Harbor) شامل repositoryها و tagها.

لایه‌ها: هر دستور RUN/COPY/ADD یک لایه می‌سازد که تفاوت فایل‌سیستم نسبت به لایه‌ی قبل است و با هش محتوایش شناخته می‌شود.

  • اشتراک: imageهایی با پایه‌ی مشترک، لایه‌های مشترک را یک بار ذخیره و دانلود می‌کنند.
  • Cache ساخت: لایه‌ای که ورودی‌اش تغییر نکرده دوباره ساخته نمی‌شود.
  • Copy-on-write: containerها لایه‌های image را به اشتراک می‌گذارند و فقط تغییرات خود را در لایه‌ی بالایی می‌نویسند؛ ساخت container تقریباً آنی است.

پیامد مهم: فایل حذف‌شده در لایه‌ی بعدی همچنان در لایه‌ی قبلی موجود است؛ پس secret یا فایل حجیم را نباید حتی موقتاً در لایه‌ای قرار داد.

چرا ترتیب دستورات در Dockerfile روی سرعت build اثر دارد؟ با یک مثال Laravel توضیح دهید.

سازوکار: Docker برای هر دستور بررسی می‌کند آیا لایه‌ای با همان دستور و همان ورودی (برای COPY، checksum فایل‌ها) در cache وجود دارد. اولین cache miss، همه‌ی لایه‌های بعدی را invalid می‌کند. پس دستورات با تغییر کم باید بالا و دستورات پرتغییر پایین باشند.

مثال بد:

COPY . .
RUN composer install --no-dev

با تغییر یک خط در یک Controller، checksum لایه‌ی COPY . . عوض و composer install هر بار از صفر اجرا می‌شود (چند دقیقه).

مثال خوب:

COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --no-autoloader
COPY . .
RUN composer dump-autoload --optimize --no-dev

تا وقتی lock تغییر نکرده، لایه‌ی سنگین نصب از cache می‌آید؛ تغییر کد فقط دو لایه‌ی آخر (سریع) را می‌سازد. --no-scripts و --no-autoloader لازم‌اند چون هنوز کد برنامه (و فایل artisan) کپی نشده است.

نکات تکمیلی: همین الگو برای package-lock.json و npm ci؛ .dockerignore تا فایل‌های بی‌ربط (مثل storage/logs) cache را invalid نکنند؛ BuildKit cache mount برای دانلودها؛ و در CI استفاده از cache خارجی (--cache-from) چون runner تازه است.

تفاوت CMD و ENTRYPOINT چیست؟ exec form و shell form چه فرقی دارند و چرا exec form توصیه می‌شود؟

CMD: دستور یا آرگومان‌های پیش‌فرض؛ اگر به docker run image ... آرگومان بدهیم، CMD جایگزین می‌شود.

ENTRYPOINT: برنامه‌ی ثابت container؛ آرگومان‌های run به انتهای آن اضافه می‌شوند و فقط با --entrypoint override می‌شود.

ترکیب: ENTRYPOINT برنامه و CMD آرگومان پیش‌فرض:

ENTRYPOINT ["php", "artisan"]
CMD ["list"]
# docker run app            → php artisan list
# docker run app queue:work → php artisan queue:work

Exec form (["php-fpm"]): برنامه مستقیماً با exec اجرا می‌شود و PID 1 است، پس SIGTERM حاصل از docker stop مستقیماً به آن می‌رسد و می‌تواند graceful خاموش شود.

Shell form (CMD php-fpm): به /bin/sh -c "php-fpm" تبدیل می‌شود؛ shell PID 1 است و سیگنال را به فرزند منتقل نمی‌کند. نتیجه: پس از مهلت ۱۰ ثانیه، Docker با SIGKILL فرایند را می‌کشد؛ برای queue worker یعنی قطع job در میانه‌ی کار. مزیت shell form فقط جایگزینی متغیرها و pipe است.

بهترین روش: exec form؛ اگر اسکریپت entrypoint لازم است، در انتهای آن exec "$@" تا فرایند اصلی جای shell را بگیرد؛ و در صورت نیاز به reaping فرایندهای zombie، --init.

تفاوت COPY و ADD، و همچنین ENV و ARG را بیان کنید. Secret مورد نیاز در زمان build (مثلاً توکن مخزن خصوصی Composer) را چگونه به build می‌دهید؟

COPY در برابر ADD: هر دو فایل را از build context به image کپی می‌کنند. ADD دو رفتار اضافه دارد: استخراج خودکار آرشیو tar محلی و دانلود از URL. این رفتارهای ضمنی غافلگیرکننده‌اند و دانلود با ADD شفافیت و کنترل checksum کمتری دارد؛ بنابراین COPY پیش‌فرض است و ADD فقط برای استخراج عمدی tar.

ENV در برابر ARG:

  • ARG: فقط در زمان build (--build-arg)؛ در container اجراشده وجود ندارد. ARG قبل از FROM فقط برای خود FROM است و باید در هر stage دوباره اعلام شود.
  • ENV: هم در build و هم در runtime؛ در metadata image ماندگار است و با docker run -e قابل override.

Secret در build: نه ENV (در docker inspect دیده می‌شود)، نه ARG (در docker history دیده می‌شود)، نه COPY فایل (در لایه می‌ماند حتی اگر بعداً پاک شود). روش درست BuildKit secret mount است:

RUN --mount=type=secret,id=composer_auth,target=/root/.composer/auth.json \
    composer install --no-dev --prefer-dist
docker build --secret id=composer_auth,src=./auth.json .

فایل فقط در طول همان RUN در دسترس است و در هیچ لایه‌ای ذخیره نمی‌شود. secretهای runtime (رمز دیتابیس، APP_KEY) هم هرگز در image نیستند و در زمان اجرا از env/secret manager تزریق می‌شوند.

Multi-stage build چیست و چه مزایایی دارد؟ ساختار stageهای یک image production برای Laravel را شرح دهید.

تعریف: Dockerfile با چند FROM که هرکدام یک stage است؛ stage نهایی فقط خروجی‌های لازم را با COPY --from=stage از stageهای قبل برمی‌دارد و ابزارهای build در image نهایی باقی نمی‌مانند.

مزایا: image کوچک‌تر (pull و deploy سریع‌تر)، سطح حمله‌ی کمتر (بدون Composer، Node، کامپایلر)، جدا شدن محیط build از runtime، یک Dockerfile برای dev و prod با --target، و build موازی stageهای مستقل توسط BuildKit.

ساختار برای Laravel:

  1. base: php:8.3-fpm-alpine + extensionها (pdo_mysql، intl، zip، bcmath، pcntl، opcache، redis)؛ build-deps در همان لایه نصب و حذف.
  2. vendor: از base + باینری Composer؛ ابتدا composer.json/lock و composer install --no-dev --no-scripts --no-autoloader، سپس کپی کد و dump-autoload --optimize --classmap-authoritative.
  3. assets: node:22-alpine؛ npm ci و npm run build و خروجی public/build.
  4. runtime: از base؛ کپی کد و vendor و assetها با --chown، تنظیمات OPcache با validate_timestamps=0، route:cache/view:cache، USER www-data، CMD ["php-fpm"]. config:cache در entrypoint، چون env در runtime است.
  5. web (اختیاری): nginx:alpine + COPY --from=runtime پوشه‌ی public.

نکته: اجرای Composer روی همان stage پایه‌ی PHP تضمین می‌کند platform requirements با runtime یکسان بررسی شوند.

این Dockerfile چه مشکلاتی دارد؟ FROM php:latest ← COPY . /app ← ENV DB_PASSWORD=Secret123 ← RUN apt-get update ← RUN apt-get install -y git unzip libzip-dev ← RUN composer install ← CMD php artisan serve --host=0.0.0.0
  1. php:latest: نسخه‌ی شناور؛ build امروز و ماه بعد ممکن است PHP متفاوتی داشته باشد. اصلاح: php:8.3-fpm-alpine (یا pin با digest).
  2. COPY . /app قبل از نصب وابستگی: هر تغییر کد cache نصب را باطل می‌کند. همچنین بدون .dockerignore، .env و .git و vendor محلی وارد image می‌شوند. اصلاح: اول lock fileها، سپس install، سپس کد؛ و .dockerignore.
  3. ENV DB_PASSWORD: secret در metadata image؛ هر کسی با دسترسی به image آن را می‌بیند. اصلاح: تزریق در runtime.
  4. apt-get update و install در دو RUN جدا: لایه‌ی update کش می‌شود و بعداً با فهرست کهنه نصب انجام می‌شود؛ cache apt هم پاک نشده است. اصلاح: یک RUN با --no-install-recommends و rm -rf /var/lib/apt/lists/*.
  5. نصب libzip-dev بدون docker-php-ext-install zip: extension نصب نمی‌شود و ابزار dev در image می‌ماند.
  6. composer install: Composer در image php وجود ندارد؛ وابستگی‌های dev هم نصب می‌شوند. اصلاح: COPY --from=composer:2 و --no-dev --optimize-autoloader، ترجیحاً در stage جدا.
  7. php artisan serve: سرور توسعه‌ی تک‌فرایندی است و برای Production مناسب نیست. اصلاح: PHP-FPM + Nginx (یا یک application server مثل Octane/FrankenPHP).
  8. Shell form CMD: سیگنال‌ها به برنامه نمی‌رسند. اصلاح: exec form.
  9. اجرا با root، بدون WORKDIR، بدون OPcache و بدون multi-stage.
Named Volume، Bind Mount و tmpfs را مقایسه کنید. داده‌ی MySQL و کد برنامه را در توسعه و Production با کدام نگه می‌دارید؟

مسئله: لایه‌ی قابل‌نوشتن container با حذف آن از بین می‌رود و برای نوشتن سنگین کند است؛ داده‌ی ماندگار باید بیرون از آن باشد.

  • Named Volume: فضای ذخیره‌سازی مدیریت‌شده توسط Docker، مستقل از چرخه‌ی عمر container و ساختار پوشه‌ی میزبان؛ قابل backup و قابل استفاده با volume driverها. volume خالی هنگام mount محتوای اولیه‌ی image را می‌گیرد.
  • Bind Mount: نگاشت مستقیم یک مسیر میزبان؛ تغییرات دوطرفه و آنی؛ وابسته به میزبان و مستعد مشکلات permission (UID)؛ محتوای image در آن مسیر را می‌پوشاند.
  • tmpfs: در RAM؛ با توقف container پاک می‌شود؛ برای فایل موقت حساس یا پرسرعت و همراه با --read-only.

یک سناریو: اپلیکیشن Laravel داخل container با خطای SQLSTATE[HY000] [2002] Connection refused به MySQL که در container دیگری است وصل نمی‌شود. در .env مقدار DB_HOST=127.0.0.1 است. علت و راه‌حل؟

علت اصلی: هر container namespace شبکه‌ی خودش را دارد؛ 127.0.0.1 داخل container app یعنی خود container app، که MySQL در آن اجرا نمی‌شود.

راه‌حل:

  • هر دو container در یک شبکه‌ی user-defined باشند (Compose خودکار این کار را می‌کند) و از نام سرویس استفاده شود: DB_HOST=mysql. DNS داخلی Docker نام را به IP container ترجمه می‌کند.
  • پورت داخلی (3306) استفاده شود، نه پورت publish‌شده روی میزبان.
  • اگر containerها با docker run روی شبکه‌ی bridge پیش‌فرض‌اند، آنجا DNS بر اساس نام وجود ندارد؛ شبکه بسازید: docker network create app-net و هر دو را با --network app-net اجرا کنید.

علت‌های احتمالی دیگر با همین خطا:

  • MySQL هنوز آماده نیست: container بالا آمده اما در حال initialize است. اصلاح: healthcheck با mysqladmin ping و depends_on: condition: service_healthy، و retry در برنامه.
  • config کش‌شده: config:cache در build با مقادیر قدیمی؛ تغییر env اثر ندارد. اصلاح: cache در start.
  • متغیر env container با .env متفاوت است (متغیر محیطی واقعی بر .env اولویت دارد).

دیباگ: docker compose exec app getent hosts mysql، docker network inspect، docker compose logs mysql و docker compose exec app php artisan db:show.

آیا depends_on در Docker Compose تضمین می‌کند سرویس وابسته آماده‌ی پذیرش اتصال باشد؟ چگونه ترتیب راه‌اندازی صحیح را تضمین می‌کنید؟

پاسخ: خیر. depends_on در شکل ساده (فهرست نام‌ها) فقط ترتیب start را تعیین می‌کند: container MySQL قبل از app شروع می‌شود، اما ممکن است MySQL هنوز در حال initialize باشد و اتصال را رد کند.

راه‌حل در Compose:

services:
  mysql:
    image: mysql:8.4
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 10
      start_period: 30s
  migrate:
    image: shop-app
    command: ["php", "artisan", "migrate", "--force"]
    depends_on:
      mysql: { condition: service_healthy }
  app:
    image: shop-app
    depends_on:
      migrate: { condition: service_completed_successfully }
  • service_started (پیش‌فرض)، service_healthy (منتظر healthcheck سالم)، service_completed_successfully (منتظر پایان موفق یک job یک‌باره).

نکته‌ی مهم‌تر: این ترتیب فقط در زمان راه‌اندازی است. اگر دیتابیس بعداً restart شود، Compose app را متوقف نمی‌کند. پس برنامه باید خودش در برابر قطعی موقت مقاوم باشد (retry، reconnect، health check که وابستگی‌ها را گزارش دهد). در Kubernetes اصلاً مفهوم depends_on وجود ندارد و همین مقاومت و readiness probe جایگزین آن‌اند.

چرا PID 1 در container اهمیت دارد؟ چگونه از خاموش شدن graceful یک queue worker لاراول هنگام deploy اطمینان حاصل می‌کنید؟

PID 1 اولین فرایند namespace فرایندهای container است و دو ویژگی خاص دارد:

  • کرنل رفتار پیش‌فرض سیگنال‌ها را روی PID 1 اعمال نمی‌کند؛ اگر handler برای SIGTERM نداشته باشد، سیگنال نادیده گرفته می‌شود.
  • مسئول reap کردن فرایندهای zombie (فرزندان یتیم) است.
  • container تا وقتی زنده است که PID 1 زنده باشد.

جریان توقف: docker stop (یا توقف Pod در Kubernetes) SIGTERM می‌فرستد و پس از مهلت (پیش‌فرض ۱۰ ثانیه در Docker، ۳۰ ثانیه در Kubernetes) SIGKILL.

برای queue worker:

  1. exec form: command: ["php", "artisan", "queue:work", ...] تا خود PHP فرایند PID 1 باشد و SIGTERM را دریافت کند؛ اگر entrypoint script دارید، exec "$@".
  2. extension pcntl نصب باشد؛ queue:work با آن SIGTERM را می‌گیرد، job جاری را تمام می‌کند و خارج می‌شود.
  3. مهلت کافی: stop_grace_period در Compose یا terminationGracePeriodSeconds در Kubernetes بیشتر از طولانی‌ترین job (و هماهنگ با --timeout worker).
  4. Idempotent بودن jobها و تنظیم retry_after، چون در بدترین حالت (SIGKILL، OOM) job دوباره اجرا می‌شود.
  5. در صورت نیاز init: true (tini) برای reaping.

در مدل container معمولاً به queue:restart نیازی نیست، چون deploy خودش containerهای قدیمی را با SIGTERM متوقف و containerهای جدید را با image جدید اجرا می‌کند.

چرا توصیه می‌شود هر container فقط یک فرایند/نقش داشته باشد؟ در یک استک Laravel چه containerهایی تعریف می‌کنید؟

اصل: «یک نگرانی در هر container». Docker سلامت و چرخه‌ی عمر container را بر اساس PID 1 می‌سنجد؛ اگر چند سرویس با supervisord در یک container باشند، crash یکی ممکن است دیده نشود.

دلایل:

  • مقیاس‌پذیری مستقل: ۵ worker صف در برابر ۲ وب.
  • جداسازی خرابی و منابع: مصرف حافظه‌ی زیاد worker روی وب اثر نمی‌گذارد؛ limitهای جدا.
  • لاگ و Monitoring تفکیک‌شده.
  • deploy و restart مستقل.
  • جلوگیری از اجرای تکراری scheduler وقتی وب scale می‌شود.

استک Laravel:

  • app: PHP-FPM (image برنامه).
  • nginx: وب‌سرور و فایل‌های استاتیک، fastcgi_pass app:9000.
  • queue: همان image با php artisan queue:work (یا horizon)، قابل scale.
  • scheduler: همان image با php artisan schedule:work، دقیقاً یک نمونه.
  • migrate: job یک‌باره با migrate --force.
  • mysql و redis با named volume و healthcheck.

نکته: استفاده از یک image برای app، queue و scheduler تضمین می‌کند همه یک نسخه‌ی کد را اجرا می‌کنند. این اصل مطلق نیست؛ FPM خودش چند فرایند worker دارد و ترکیب Nginx+FPM در یک image برای بعضی PaaSها رایج است.

استراتژی tag گذاری imageها را برای یک تیم توضیح دهید. چرا استفاده از :latest در Production توصیه نمی‌شود؟

مشکلات latest:

  • فقط یک tag پیش‌فرض و متحرک است، نه لزوماً جدیدترین نسخه.
  • تکرارناپذیری: دو pull در دو زمان ممکن است image متفاوت بدهد؛ نودهای مختلف کلاستر ممکن است نسخه‌های متفاوت اجرا کنند.
  • Rollback نامشخص و ردیابی نسخه‌ی در حال اجرا تا commit ناممکن.
  • caching و pull policy غیرقابل پیش‌بینی (در Kubernetes برای latest پیش‌فرض Always است).

استراتژی پیشنهادی:

  • SHA کامیت روی هر build از main: app:3f9c2ab؛ تغییرناپذیر، پایه‌ی deploy و «build once, deploy many».
  • SemVer روی releaseها: app:1.4.2 و در صورت نیاز tagهای متحرک 1.4 و 1 برای مصرف‌کنندگان.
  • Digest (@sha256:...) برای قطعیت کامل در مانیفست‌های production/GitOps.
  • tagهای برنچ (main، pr-123) فقط برای محیط‌های موقت.
  • فعال کردن tag immutability در registry و سیاست cleanup برای imageهای قدیمی.
  • LABELهای OCI (source، revision، version) برای ردیابی.

همین اصل برای imageهای پایه هم برقرار است: FROM php:8.3-fpm-alpine به‌جای FROM php، با به‌روزرسانی کنترل‌شده.

بهترین روش‌های امنیتی برای ساخت و اجرای imageهای Docker در Production را بنویسید.

زمان ساخت:

  • image پایه‌ی رسمی و حداقلی با نسخه‌ی pin‌شده؛ rebuild دوره‌ای برای وصله‌ها.
  • Multi-stage: ابزار build، کامپایلر و Node در image نهایی نباشند.
  • بدون secret در لایه‌ها: نه ENV، نه ARG، نه COPY؛ BuildKit secret برای build و تزریق runtime برای اجرا.
  • .dockerignore برای .env، .git و فایل‌های محلی.
  • اسکن آسیب‌پذیری (Trivy، Docker Scout، Grype) در CI و fail روی CVE بحرانی؛ composer audit برای وابستگی‌ها.
  • حداقل بسته‌ها و پاک‌سازی cache در همان لایه.
  • امضای image و استفاده از registry خصوصی با دسترسی محدود.

زمان اجرا:

  • کاربر غیر root (USER www-data)؛ فقط مسیرهای لازم قابل‌نوشتن.
  • --read-only + tmpfs، --cap-drop ALL، no-new-privileges؛ هرگز --privileged.
  • عدم mount کردن docker.sock (معادل root میزبان).
  • محدودیت منابع (memory، cpu، pids) برای جلوگیری از DoS روی میزبان.
  • شبکه: فقط پورت‌های لازم publish شوند؛ دیتابیس فقط در شبکه‌ی داخلی.
  • به‌روز نگه داشتن Docker Engine و کرنل میزبان؛ در Kubernetes: Pod Security، NetworkPolicy، RBAC و Secretهای رمزنگاری‌شده.

اصل کلی: Defense in depth و least privilege؛ container مرز امنیتی کامل نیست، چون کرنل مشترک است.

تفاوت image توسعه و Production چیست؟ Laravel Sail چیست و آیا برای Production مناسب است؟

Image توسعه برای سرعت چرخه‌ی کدنویسی و دیباگ طراحی می‌شود: کد با bind mount، وابستگی‌های dev، Xdebug، OPcache با بررسی timestamp، APP_DEBUG=true، Node برای Vite dev server.

Image Production برای امنیت، کارایی و تکرارپذیری: کد داخل image، composer install --no-dev -o، assetهای build‌شده، OPcache با validate_timestamps=0، بدون ابزار توسعه، کاربر غیر root، و secretها در runtime.

بهترین روش: یک Dockerfile با stageهای مشترک base و هدف‌های dev و runtime (--target)، تا نسخه‌ی PHP و extensionها یکسان باشد (dev/prod parity) و «روی سیستم من کار می‌کرد» رخ ندهد.

Laravel Sail: رابط خط فرمان سبک روی Docker Compose برای محیط توسعه‌ی محلی؛ با php artisan sail:install فایل Compose با سرویس‌های انتخابی (MySQL/PostgreSQL، Redis، Mailpit، Meilisearch…) می‌سازد و دستورات sail artisan، sail composer، sail test را درون container اجرا می‌کند. مزیتش راه‌اندازی سریع و یکسان برای همه‌ی تیم بدون نصب PHP روی سیستم است.

برای Production مناسب نیست: کد را mount می‌کند، وابستگی‌های dev دارد، برای امنیت و کارایی بهینه نشده و جای image تغییرناپذیر production را نمی‌گیرد. برای Production باید image اختصاصی multi-stage ساخت.

اشیای اصلی Kubernetes (Pod، Deployment، Service، Ingress، ConfigMap، Secret) را توضیح دهید. چه زمانی Docker Compose کافی است و چه زمانی به Kubernetes نیاز داریم؟
  • Pod: کوچک‌ترین واحد استقرار؛ یک یا چند container با IP و volume مشترک. موقت است و IP ثابتی ندارد.
  • Deployment: تعریف declarative برنامه‌ی stateless: image، تعداد replica، rolling update و rollback؛ با ReplicaSet تعداد Podها را تضمین می‌کند (self-healing).
  • Service: نام DNS و IP مجازی پایدار با توزیع بار روی Podهای منتخب با label. ClusterIP (داخلی)، NodePort، LoadBalancer.
  • Ingress: مسیریابی HTTP/HTTPS (host/path، TLS) از بیرون به Serviceها؛ نیازمند Ingress Controller.
  • ConfigMap: پیکربندی غیرحساس به‌صورت env یا فایل.
  • Secret: داده‌ی حساس؛ به‌طور پیش‌فرض فقط base64 (نه رمزنگاری) است، پس encryption at rest و RBAC لازم است.
  • به‌علاوه‌ی probeها: readiness (ورود به Service)، liveness (restart).

Compose کافی است وقتی: توسعه‌ی محلی، CI، یا یک سرور تکی با ترافیک متوسط داریم و downtime کوتاه در deploy یا خرابی میزبان قابل قبول است.

Kubernetes لازم است وقتی: چند سرور و high availability، rolling update بدون downtime، autoscaling، self-healing خودکار، service discovery بین نودها، تعداد زیاد سرویس (microservices) و تیم عملیاتی برای مدیریت پیچیدگی آن داریم.

میانه: Docker Swarm (همان فرمت Compose روی کلاستر، ساده‌تر ولی اکوسیستم کوچک‌تر) یا سرویس‌های مدیریت‌شده (ECS، Cloud Run). انتخاب Kubernetes بدون نیاز واقعی، هزینه‌ی عملیاتی بالایی دارد.

یک container بلافاصله پس از اجرا متوقف می‌شود یا مدام restart می‌شود. مراحل عیب‌یابی شما چیست؟

۱. وضعیت و exit code:

docker ps -a
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' app
docker logs --tail 200 app

۲. تفسیر exit code:

  • 0: فرایند اصلی کارش تمام شده یا به background رفته (مثلاً دستوری که daemon می‌شود). container فقط تا وقتی زنده است که PID 1 زنده باشد؛ فرایند باید در foreground اجرا شود.
  • 1: خطای برنامه؛ لاگ را ببینید (مثلاً APP_KEY تنظیم نشده، خطای PHP، اتصال دیتابیس).
  • 126/127: فایل اجرایی پیدا نشد یا مجوز اجرا ندارد: نبود bash در Alpine، chmod +x فراموش‌شده، یا line ending ویندوزی (CRLF) در اسکریپت entrypoint.
  • 137: SIGKILL؛ اگر OOMKilled=true است، حافظه کم است (افزایش limit یا کاهش pm.max_children در FPM).

۳. بررسی محیط: docker inspect برای env، mountها و command نهایی؛ اجرای تعاملی با override: docker run --rm -it --entrypoint sh image و اجرای دستی دستور.

۴. وابستگی‌ها: آیا دیتابیس آماده است؟ healthcheck و depends_on: service_healthy؛ آیا permission پوشه‌ی storage برای کاربر غیر root درست است؟

۵. حلقه‌ی restart: restart: always خطا را پنهان می‌کند؛ موقتاً حذفش کنید یا از docker events استفاده کنید. در Kubernetes معادلش CrashLoopBackOff است: kubectl describe pod و kubectl logs --previous.

خلاصه برای مرور سریع

مفاهیم

  • Container = فرایند ایزوله با کرنل مشترک؛ VM = کرنل مستقل روی Hypervisor.
  • Namespaces (دیدن) + cgroups (مصرف) + overlay FS (لایه‌ها).
  • Image (کلاس، read-only) ← Container (شیء + لایه‌ی writable) ← Registry (repository:tag).
  • CLI ← dockerd ← containerd ← runc؛ استاندارد OCI.

لایه و Cache

  • RUN/COPY/ADD ⇒ لایه. اولین miss ⇒ همه‌ی بعدی‌ها rebuild.
  • ترتیب: base ← apk/apt ← ext ← lock files ← install ← کد.
  • پاک‌سازی در همان RUN؛ حذف در لایه‌ی بعد حجم را کم نمی‌کند.
  • RUN --mount=type=cache و --mount=type=secret.

دستورات

  • COPY > ADD (ADD: URL + extract tar).
  • ARG = build-time؛ ENV = build + runtime؛ هیچ‌کدام برای secret.
  • EXPOSE = مستند؛ -p = publish.
