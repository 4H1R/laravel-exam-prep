Code Optimization

بهینه‌سازی کد بک‌اند PHP/Laravel از «اول اندازه بگیر» تا پروفایلینگ، حل مسئله N+1، کار با داده‌های حجیم، کش، OPcache و JIT، تنظیم PHP-FPM، پیچیدگی الگوریتمی، صف‌ها، Octane، بهینه‌سازی لایه HTTP و تست بار.

اول اندازه‌گیری، بعد بهینه‌سازی

بهینه‌سازی (Optimization) یعنی کاهش مصرف یک منبع مشخص (زمان پاسخ، CPU، حافظه، تعداد کوئری، پهنای باند) برای یک سناریوی مشخص، بدون شکستن رفتار درست برنامه. کلمه‌ی کلیدی «مشخص» است: تا وقتی ندانیم چه چیزی کند است و چقدر، هر تغییری حدس است.

جمله‌ی معروف Donald Knuth این است: «Premature optimization is the root of all evil». ادامه‌ی کمتر نقل‌شده‌اش مهم‌تر است: در حدود ۹۷٪ موارد بازدهی‌های کوچک را باید نادیده گرفت، اما نباید فرصت آن ۳٪ بحرانی را از دست داد. یعنی پیام این نیست که «به کارایی فکر نکن»؛ پیام این است که بدون داده بهینه نکن و تمرکزت را روی گلوگاه واقعی بگذار.

چرخه‌ی درست بهینه‌سازی

  1. تعریف هدف قابل اندازه‌گیری: مثلاً «p95 زمان پاسخ endpoint لیست سفارش‌ها زیر ۳۰۰ms با ۲۰۰ کاربر هم‌زمان». هدف مبهم مثل «سریع‌تر شود» پایان ندارد.
  2. Baseline: وضعیت فعلی را در محیطی شبیه production اندازه بگیر (داده‌ی واقعی‌نما، OPcache روشن، debug خاموش).
  3. Profile: با ابزار مناسب پیدا کن زمان دقیقاً کجا صرف می‌شود.
  4. یک تغییر در هر بار: فقط گلوگاه اصلی را اصلاح کن.
  5. اندازه‌گیری مجدد و مقایسه: اگر بهبود معنادار نبود، تغییر را برگردان.
  6. جلوگیری از بازگشت (regression): مانیتورینگ، تست کارایی یا assertion روی تعداد کوئری.

قانون Amdahl به زبان ساده

اگر بخشی از درخواست فقط ۵٪ زمان کل را می‌گیرد، حتی اگر آن را بی‌نهایت سریع کنی، کل درخواست حداکثر ۵٪ سریع‌تر می‌شود. پس اول سراغ بخشی برو که سهم بزرگی از زمان دارد. در اپلیکیشن‌های وب معمولی، این بخش تقریباً همیشه I/O است: دیتابیس، فراخوانی APIهای خارجی، فایل و شبکه؛ نه حلقه‌های PHP.

خوانایی در برابر کارایی

  • کد خوانا ارزان‌تر نگهداری می‌شود، باگ کمتری دارد و بهینه‌سازی بعدی‌اش هم آسان‌تر است.
  • بهینه‌سازی‌های «میکرو» (مثل ++$i به جای $i++ یا single quote به جای double quote) در PHP مدرن تقریباً اثری ندارند و ارزش قربانی کردن خوانایی را ندارند.
  • بهینه‌سازی‌های معماری و الگوریتمی (حذف N+1، کش، صف، ایندکس، O(n²) به O(n)) معمولاً هم اثر بزرگ دارند و هم اگر درست نوشته شوند خوانایی را خراب نمی‌کنند.
  • اگر بهینه‌سازی کد را پیچیده کرد، دلیلش را در کامنت بنویس و با benchmark مستند کن.

در پاسخ تشریحی به سوال «Premature optimization چیست؟» حتماً سه چیز را بگو: ۱) تعریف (بهینه‌سازی قبل از داشتن داده درباره‌ی گلوگاه)، ۲) هزینه‌اش (پیچیدگی، باگ، اتلاف زمان روی بخش کم‌اثر)، ۳) اینکه طراحی درست از ابتدا (مثل انتخاب ساختار داده‌ی مناسب، ایندکس، جلوگیری از N+1) premature optimization حساب نمی‌شود.

ابزارهای پروفایلینگ

در خروجی دو عدد مهم است: Inclusive time (زمان تابع به همراه توابعی که صدا زده) و Self/Exclusive time (زمان خود تابع). تابعی با self time بالا گلوگاه CPU است؛ تابعی با inclusive بالا اما self کم، فقط مسیر رسیدن به گلوگاه است.

Xdebug حتی وقتی پروفایل نمی‌گیرد هم سربار دارد. روشن بودن آن روی سرور production یا موقع تست بار، نتایج را کاملاً بی‌اعتبار می‌کند. همیشه قبل از benchmark چک کنید: php -m | grep -i xdebug.

تفاوت Telescope و Blackfire را بدانید: Telescope «چه اتفاقی افتاد» (کدام کوئری‌ها، jobها، exceptionها) را ثبت می‌کند؛ Blackfire و Xdebug «زمان دقیقاً در کدام تابع صرف شد» را با call graph نشان می‌دهند. برای مسائل دیتابیسی Telescope/Debugbar کافی است، برای گلوگاه CPU پروفایلر لازم است.

تشخیص نوع گلوگاه: CPU، I/O، حافظه، دیتابیس

قبل از هر اقدامی باید بفهمیم منبع محدودکننده کدام است، چون راه‌حل‌ها کاملاً متفاوت‌اند. اضافه کردن CPU به سیستمی که منتظر دیتابیس است هیچ اثری ندارد.

فرمول ساده‌ی زمان یک درخواست

زمان پاسخ ≈ زمان صف (انتظار برای worker آزاد)
          + bootstrap فریمورک
          + Σ (round-trip هر کوئری + زمان اجرای آن)
          + Σ فراخوانی‌های HTTP خارجی
          + محاسبات PHP و رندر view
          + انتقال در شبکه به کاربر

این فرمول نشان می‌دهد چرا N+1 خطرناک است: حتی اگر هر کوئری ۱ میلی‌ثانیه طول بکشد، ۵۰۰ کوئری یعنی حداقل نیم ثانیه فقط round-trip. همچنین نشان می‌دهد چرا وقتی همه‌ی workerهای PHP-FPM مشغول‌اند، «زمان صف» ناگهان زمان پاسخ را چند برابر می‌کند.

Latency را با درصدک (percentile) گزارش کنید نه میانگین. میانگین ۱۵۰ms ممکن است p99 برابر ۴ ثانیه را پنهان کند؛ یعنی از هر ۱۰۰ کاربر یکی تجربه‌ی بسیار بدی دارد.

مسئله N+1 و Eager Loading

N+1 یعنی یک کوئری برای گرفتن لیست اصلی (۱) و سپس یک کوئری جداگانه برای رابطه‌ی هر آیتم (N). در Eloquent این مشکل به‌خاطر Lazy Loading پیش می‌آید: دسترسی به $post->author اگر رابطه از قبل load نشده باشد، همان لحظه یک کوئری اجرا می‌کند.

قبل: N+1

<?php
// Controller
$posts = Post::latest()->take(50)->get();          // 1 کوئری

// Blade
@foreach ($posts as $post)
    {{ $post->author->name }}                      // 50 کوئری
    {{ $post->comments->count() }}                 // 50 کوئری دیگر
@endforeach
// جمع: 101 کوئری
select * from posts order by created_at desc limit 50;
select * from users where id = 7 limit 1;
select * from users where id = 3 limit 1;
select * from comments where post_id = 101;
-- ... تکرار برای هر پست

بعد: Eager Loading

<?php
$posts = Post::query()
    ->select(['id', 'title', 'user_id', 'created_at'])
    ->with('author:id,name')      // فقط ستون‌های لازم از users (کلید id لازم است)
    ->withCount('comments')        // شمارش در دیتابیس، بدون load کامنت‌ها
    ->latest()
    ->take(50)
    ->get();
// جمع: 2 کوئری (posts با subquery شمارش + users)

// در Blade:
// {{ $post->author->name }}  و  {{ $post->comments_count }}
select id, title, user_id, created_at,
       (select count(*) from comments where posts.id = comments.post_id) as comments_count
from posts order by created_at desc limit 50;
select id, name from users where id in (7, 3, 12, ...);

تفاوت $user->posts()->count() و $user->posts->count(): اولی یک کوئری COUNT(*) می‌زند؛ دومی همه‌ی پست‌ها را load و hydrate می‌کند و بعد در PHP می‌شمارد. اگر داخل حلقه باشد، هر دو N+1 هستند و راه‌حل درست withCount است.

N+1 فقط در view رخ نمی‌دهد: در API Resourceها، accessorها، Policyها (مثلاً چک مالکیت با رابطه) و jobها هم رایج است. برای تست، می‌توان تعداد کوئری را assert کرد: با DB::enableQueryLog() و شمارش DB::getQueryLog() در یک تست Feature.

کار را به دیتابیس بسپار

دیتابیس برای فیلتر، مرتب‌سازی، تجمیع و join بهینه شده و از ایندکس استفاده می‌کند. آوردن داده به PHP و فیلتر با Collection هم حافظه می‌خورد و هم کندتر است.

ایندکس از دید توسعه‌دهنده‌ی اپلیکیشن

  • ستون‌هایی که در WHERE، JOIN، ORDER BY و foreign key استفاده می‌شوند کاندید ایندکس‌اند. در migration: $table->index(['status', 'created_at'])؛ foreignId()->constrained() روی MySQL/InnoDB ایندکس هم می‌سازد.
  • ترتیب ستون‌ها در ایندکس ترکیبی مهم است (قاعده‌ی leftmost prefix): ایندکس (status, created_at) برای WHERE status = ? ORDER BY created_at عالی است، اما برای فیلتر فقط روی created_at به کار نمی‌آید.
  • اعمال تابع روی ستون ایندکس‌دار معمولاً ایندکس را بی‌اثر می‌کند: WHERE DATE(created_at) = ? را به بازه تبدیل کنید: whereBetween('created_at', [$start, $end]).
  • LIKE '%term%' با wildcard در ابتدا از B-Tree index استفاده نمی‌کند؛ برای جستجوی متنی از full-text index یا Laravel Scout و موتور جستجو استفاده کنید.
  • ایندکس هزینه‌ی نوشتن و فضای دیسک دارد؛ برای ستون‌هایی با تنوع کم (مثل boolean تنها) معمولاً مفید نیست.
  • همیشه با EXPLAIN تأیید کنید: ستون type=ALL یعنی full table scan؛ rows تعداد تخمینی ردیف‌های بررسی‌شده است.

صفحه‌بندی

paginate() علاوه بر داده یک کوئری COUNT هم می‌زند؛ simplePaginate() این کوئری را ندارد. روی جدول‌های بزرگ، OFFSET بزرگ (صفحه‌ی ۱۰۰۰۰) کند است چون دیتابیس باید همه‌ی ردیف‌های قبلی را رد کند؛ cursorPaginate() با شرط where id > ? این مشکل را ندارد ولی پرش به صفحه‌ی دلخواه را پشتیبانی نمی‌کند.

«کار را تا جای ممکن در دیتابیس انجام بده» یک اصل کلی است، اما مطلق نیست: منطق کسب‌وکار پیچیده در SQL خام سخت تست می‌شود و دیتابیس معمولاً سخت‌تر از سرورهای اپلیکیشن scale می‌شود. فیلتر، تجمیع و join را به دیتابیس بسپارید؛ محاسبات سنگین غیرپایگاه‌داده‌ای را در اپلیکیشن یا صف انجام دهید.

داده‌های حجیم: chunk، lazy، cursor و عملیات دسته‌ای

وقتی باید صدها هزار رکورد را پردازش کنیم، Model::all() همه‌ی ردیف‌ها را هم‌زمان به مدل Eloquent تبدیل و در حافظه نگه می‌دارد و به‌راحتی از memory_limit عبور می‌کند. Laravel چند روش پردازش تدریجی دارد:

متدنحوه‌ی کارحافظهنکته‌ی مهم
chunk(1000, fn)کوئری‌های پشت‌سرهم با LIMIT/OFFSETحداکثر یک chunkاگر حین پردازش ستونی را که در WHERE یا ORDER است تغییر دهید، رکوردها جا می‌افتند؛ OFFSET در صفحات انتهایی کند است.
chunkById(1000, fn)کوئری با where id > lastId order by id limit 1000حداکثر یک chunkبرای وقتی که حین پردازش رکوردها را update می‌کنید امن است و روی جدول بزرگ سریع است (keyset).
lazy() / lazyById()همان chunk در پشت صحنه، اما خروجی یک LazyCollection تختحداکثر یک chunkAPI راحت‌تر (->each، ->filter) بدون callback تو در تو.
cursor()فقط یک کوئری؛ با generator هر بار یک مدل hydrate می‌شودیک مدل Eloquent در هر لحظه، اما…درایور PDO به‌طور پیش‌فرض کل نتیجه‌ی خام را بافر می‌کند، پس روی داده‌ی خیلی بزرگ باز هم حافظه تمام می‌شود؛ eager loading هم پشتیبانی نمی‌شود.
 
<?php
// ارسال ایمیل به کاربرانی که هنوز اطلاع‌رسانی نشده‌اند و همزمان update می‌کنیم
User::where('notified', false)
    ->chunkById(500, function ($users) {
        foreach ($users as $user) {
            SendNoticeJob::dispatch($user->id);
        }
        User::whereIn('id', $users->pluck('id'))->update(['notified' => true]);
    });

// خروجی CSV از جدول بزرگ با LazyCollection
return response()->streamDownload(function () {
    $out = fopen('php://output', 'w');
    fputcsv($out, ['id', 'email', 'created_at']);
    User::select(['id', 'email', 'created_at'])
        ->lazyById(2000)
        ->each(fn ($u) => fputcsv($out, [$u->id, $u->email, $u->created_at]));
    fclose($out);
}, 'users.csv');

اشتباه کلاسیک: User::where('notified', false)->chunk(...) و داخل callback ستون notified را true کنید. در کوئری بعدی OFFSET جلو رفته اما مجموعه‌ی نتیجه کوچک شده، پس تقریباً نیمی از رکوردها پردازش نمی‌شوند. راه‌حل: chunkById.

درج و به‌روزرسانی دسته‌ای (Bulk)

<?php
// بد: 10,000 بار INSERT و 10,000 بار fire شدن event مدل
foreach ($rows as $row) {
    Product::create($row);
}

// خوب: INSERT چند ردیفی، در دسته‌های ۱۰۰۰تایی
$now = now();
foreach (array_chunk($rows, 1000) as $batch) {
    $batch = array_map(fn ($r) => $r + ['created_at' => $now, 'updated_at' => $now], $batch);
    Product::insert($batch);
}

// Upsert: درج یا به‌روزرسانی بر اساس کلید یکتا (در یک کوئری)
Product::upsert(
    $rows,
    uniqueBy: ['sku'],
    update: ['price', 'stock', 'updated_at']
);

// چند تغییر وابسته به هم: داخل تراکنش
DB::transaction(function () use ($order) {
    $order->update(['status' => 'paid']);
    Stock::whereIn('product_id', $order->items->pluck('product_id'))->decrement('qty');
});
  • insert() و upsert() و update() روی Query Builder، model eventها (creating، saved، observerها) را اجرا نمی‌کنند و timestamps را خودکار پر نمی‌کنند (upsert روی مدل، timestamps را در صورت فعال بودن اضافه می‌کند). اگر منطق مهمی در observer دارید، این را در نظر بگیرید.
  • در MySQL، upsert به ایندکس PRIMARY یا UNIQUE متکی است و پارامتر uniqueBy عملاً بر اساس همان ایندکس‌ها کار می‌کند.
  • تعداد placeholderها در یک کوئری محدودیت دارد؛ به همین خاطر دسته‌بندی (مثلاً ۵۰۰ تا ۱۰۰۰ ردیف) لازم است.
  • هزاران INSERT جدا در یک تراکنش هم بسیار سریع‌تر از هزاران تراکنش auto-commit است، چون هر commit یک flush به دیسک دارد.

کش (Caching) و دستورات optimize لاراول

Cache یعنی نگهداری نتیجه‌ی یک عملیات پرهزینه در محلی سریع‌تر تا درخواست‌های بعدی دوباره آن را محاسبه نکنند. کش قوی‌ترین ابزار کارایی است، اما «یکی از دو مسئله‌ی سخت علوم کامپیوتر» یعنی invalidation را با خود می‌آورد.

لایه‌های کش

مرورگر (Cache-Control) ─► CDN ─► Reverse proxy (Nginx) ─► اپلیکیشن (Redis/Memcached)
                                                               └─► OPcache (bytecode)
                                                               └─► Query/Buffer cache دیتابیس

کش داده در اپلیکیشن

<?php
use Illuminate\Support\Facades\Cache;

// Cache-aside: اگر بود بخوان، نبود محاسبه کن و ذخیره کن
$stats = Cache::remember('dashboard:stats', now()->addMinutes(10), function () {
    return [
        'users'   => User::count(),
        'revenue' => Order::where('status', 'paid')->sum('amount'),
    ];
});

// invalidation بعد از تغییر داده
Cache::forget("product:{$product->id}");

// Stale-while-revalidate: تا 5 دقیقه تازه، تا 15 دقیقه مقدار قدیمی برگردان و در پس‌زمینه تازه کن
$top = Cache::flexible('products:top', [300, 900], fn () => Product::topSelling()->get());

// Memoization در طول یک درخواست (بدون ذخیره در Redis)
function currentTenantSettings(): array
{
    return once(fn () => Setting::forTenant(tenant())->pluck('value', 'key')->all());
}

مشکلات رایج کش

Cache stampede
وقتی یک کلید پرطرفدار منقضی می‌شود و صدها درخواست هم‌زمان آن را دوباره محاسبه می‌کنند. راه‌حل: lock (Cache::lock)، stale-while-revalidate، TTL تصادفی (jitter)، یا گرم کردن کش با job زمان‌بندی‌شده.
Stale data
نمایش داده‌ی قدیمی. باید TTL را با میزان تحمل کسب‌وکار تنظیم کرد و پس از نوشتن، کلید را پاک یا به‌روز کرد.
Cache key collision
کلیدی که به همه‌ی پارامترهای مؤثر (کاربر، زبان، صفحه، فیلتر) وابسته نیست و داده‌ی یک کاربر را به دیگری نشان می‌دهد.
Cache tags
گروه‌بندی کلیدها برای پاک‌سازی دسته‌جمعی؛ فقط روی driverهایی مثل Redis و Memcached (نه file/database).

کش HTTP

  • Cache-Control: public, max-age=3600 اجازه می‌دهد مرورگر و CDN پاسخ را نگه دارند؛ private فقط مرورگر؛ no-store هیچ‌جا.
  • ETag و Last-Modified: درخواست شرطی با If-None-Match؛ اگر تغییری نبود سرور 304 Not Modified بدون body برمی‌گرداند.
  • در Laravel: middleware آماده‌ی cache.headers.
<?php
Route::middleware('cache.headers:public;max_age=600;etag')->group(function () {
    Route::get('/api/categories', [CategoryController::class, 'index']);
});

دستورچه می‌کندنکته

سوال رایج: «چرا بعد از config:cache مقدار env() در کنترلر null است؟» پاسخ: چون با وجود فایل کش، Laravel دیگر فایل .env را بارگذاری نمی‌کند؛ مقدارها فقط در زمان ساخت کش و فقط داخل فایل‌های config خوانده شده‌اند. راه‌حل: تعریف مقدار در یک فایل config و استفاده از config().

Composer Autoloader، OPcache، Preloading و JIT

Autoloader بهینه

به‌صورت پیش‌فرض autoloader مبتنی بر PSR-4 برای پیدا کردن هر کلاس، نام فضای نام را به مسیر تبدیل می‌کند و وجود فایل را روی دیسک بررسی می‌کند. در production می‌توان یک classmap کامل ساخت.

composer install --no-dev --optimize-autoloader --classmap-authoritative --no-interaction
# یا بعداً:
composer dump-autoload -o        # --optimize: ساخت classmap از PSR-4/PSR-0
composer dump-autoload -a        # --classmap-authoritative: فقط classmap، بدون جستجوی فایل‌سیستم
  • --optimize-autoloader (-o): برای کلاس‌های موجود در classmap مستقیم فایل پیدا می‌شود؛ اگر کلاسی در classmap نبود، همچنان به جستجوی PSR-4 برمی‌گردد.
  • --classmap-authoritative (-a): اگر کلاس در classmap نبود، دیگر جستجو نمی‌کند و فرض می‌کند وجود ندارد. سریع‌تر است، اما کلاس‌هایی که بعد از build ساخته می‌شوند (کد تولیدشده در runtime) پیدا نمی‌شوند.
  • --no-dev: پکیج‌های توسعه (Debugbar، Telescope در صورت dev بودن، PHPUnit) نصب نمی‌شوند.

OPcache

PHP در هر اجرا فایل‌ها را parse و به opcode (bytecode) کامپایل می‌کند. OPcache این opcodeها را در shared memory نگه می‌دارد تا فرایندهای PHP-FPM دیگر کامپایل تکراری نکنند. برای هر اپلیکیشن production الزامی است و معمولاً بیشترین اثر را با کمترین هزینه دارد.

; /etc/php/8.3/fpm/conf.d/10-opcache.ini  (نمونه‌ی production)
opcache.enable = 1
opcache.enable_cli = 0
opcache.memory_consumption = 256          ; مگابایت
opcache.interned_strings_buffer = 16      ; مگابایت، برای رشته‌های تکراری
opcache.max_accelerated_files = 20000     ; بیشتر از تعداد فایل‌های PHP پروژه + vendor
opcache.validate_timestamps = 0           ; تغییر فایل را چک نکن (بعد از deploy باید FPM را reload کرد)
opcache.save_comments = 1                 ; برای annotation/attribute خوانی برخی کتابخانه‌ها لازم است

با validate_timestamps=0 بعد از هر deploy کد جدید اجرا نمی‌شود مگر OPcache پاک شود؛ معمولاً با sudo systemctl reload php8.3-fpm. در deployهای مبتنی بر symlink هم reload لازم است (و در Nginx از $realpath_root استفاده کنید). اجرای opcache_reset() از CLI روی کش FPM اثری ندارد، چون CLI حافظه‌ی مشترک جدای خودش را دارد.

برای بررسی وضعیت: opcache_get_status() (درصد پر شدن حافظه، hit rate، تعداد کلیدها). اگر حافظه یا max_accelerated_files پر شود، OPcache ممکن است ری‌استارت شود و ناگهان CPU بالا برود.

Preloading (از PHP 7.4)

با opcache.preload یک اسکریپت هنگام شروع سرور FPM اجرا می‌شود و کلاس‌ها و توابع مشخص‌شده را یک‌بار load و link می‌کند تا برای همه‌ی درخواست‌ها از قبل در حافظه باشند.

opcache.preload = /var/www/app/preload.php
opcache.preload_user = www-data
  • مزیت: حذف هزینه‌ی autoload و link برای کلاس‌های پرتکرار فریمورک. بهبود معمولاً چند درصد است، نه چند برابر.
  • عیب: هر تغییر در فایل‌های preload‌شده نیاز به restart کامل FPM دارد؛ مدیریت لیست فایل‌ها هم دشوار است. باید قبل و بعد اندازه گرفت.

JIT (از PHP 8.0)

JIT (Just-In-Time compiler) بخشی از opcodeها را در زمان اجرا به کد ماشین native تبدیل می‌کند. JIT بخشی از OPcache است و به یک بافر حافظه نیاز دارد.

opcache.jit_buffer_size = 64M
opcache.jit = tracing     ; حالت‌های رایج: tracing یا function؛ disable برای خاموش کردن

JIT کجا کمک می‌کند

  • کدهای CPU-bound: محاسبات ریاضی، پردازش تصویر به‌صورت خالص PHP، الگوریتم‌های سنگین، حلقه‌های داغ طولانی.
  • اسکریپت‌های CLI و workerهای طولانی‌مدت محاسباتی.

JIT کجا تقریباً بی‌اثر است

  • اپلیکیشن وب معمولی Laravel که بیشتر زمانش منتظر دیتابیس، Redis، شبکه و فایل است (I/O-bound).
  • وقتی گلوگاه N+1 یا کوئری کند است.
  • مصرف حافظه‌ی بیشتر و دیباگ سخت‌تر را هم باید در نظر داشت.

تفاوت OPcache و JIT را دقیق بنویسید: OPcache کامپایل source به opcode را حذف می‌کند (همیشه مفید)؛ JIT اجرای opcode توسط ماشین مجازی Zend را با کد ماشین جایگزین می‌کند (فقط برای کد CPU-bound مفید). JIT بدون OPcache کار نمی‌کند.

تنظیم PHP-FPM Process Manager

PHP-FPM یک pool از فرایندهای worker نگه می‌دارد. هر worker در هر لحظه فقط یک درخواست را پردازش می‌کند. پس حداکثر درخواست هم‌زمانی که PHP پردازش می‌کند برابر pm.max_children است؛ بقیه در صف (backlog سوکت) منتظر می‌مانند و این همان «زمان صف» است.

حالت pmرفتارمناسب برای
staticهمیشه دقیقاً pm.max_children فرایند فعال استسرور اختصاصی با ترافیک بالا و قابل پیش‌بینی؛ بدون هزینه‌ی fork در لحظه‌ی پیک
dynamicبین min_spare_servers و max_spare_servers فرایند بیکار نگه می‌دارد و تا max_children بالا می‌رودحالت پیش‌فرض و متعادل برای بیشتر سرورها
ondemandفرایند فقط هنگام درخواست ساخته می‌شود و پس از process_idle_timeout از بین می‌رودسرورهای کم‌ترافیک یا چند سایت روی یک سرور با حافظه‌ی محدود؛ اولین درخواست‌ها هزینه‌ی fork دارند

محاسبه‌ی pm.max_children

pm.max_children ≈ (RAM کل − RAM لازم برای OS، دیتابیس، Redis، Nginx و…) ÷ میانگین RSS یک worker PHP

مثال: سرور 8GB، حدود 2GB برای سیستم‌عامل و سرویس‌های دیگر، هر worker حدود 60MB
       (8192 − 2048) ÷ 60 ≈ 102  ← با حاشیه‌ی اطمینان حدود 90
# میانگین حافظه‌ی (RSS) فرایندهای php-fpm به مگابایت
ps --no-headers -o rss -C php-fpm8.3 | awk '{ sum += $1; n++ } END { if (n) printf "%.1f MB\n", sum/n/1024 }'
; /etc/php/8.3/fpm/pool.d/www.conf
pm = dynamic
pm.max_children = 90
pm.start_servers = 20
pm.min_spare_servers = 10
pm.max_spare_servers = 30
pm.max_requests = 500              ; بازیافت worker برای مهار نشت حافظه
request_terminate_timeout = 60s    ; کشتن درخواست‌های گیرکرده
request_slowlog_timeout = 5s       ; ثبت stack trace درخواست‌های کند
slowlog = /var/log/php8.3-fpm-slow.log
pm.status_path = /fpm-status       ; فقط از داخل شبکه/localhost در دسترس باشد
  • اگر در لاگ FPM پیام server reached pm.max_children setting دیدید، یعنی درخواست‌ها در صف مانده‌اند. اما قبل از افزایش، مطمئن شوید RAM کافی است؛ وگرنه سرور swap می‌کند یا OOM killer فرایندها را می‌کشد و وضعیت بدتر می‌شود.
  • اگر workerها کند هستند چون منتظر دیتابیس‌اند، افزایش max_children فقط فشار بیشتری به دیتابیس می‌آورد. اول علت کندی را رفع کنید.
  • برای workloadهای CPU-bound، تعداد worker خیلی بیشتر از تعداد هسته‌ها فقط context switch اضافه می‌کند. برای workloadهای I/O-bound (حالت معمول وب) تعداد worker می‌تواند چند برابر هسته‌ها باشد.
  • صفحه‌ی status (/fpm-status) مقادیر active processes، idle processes، listen queue و max children reached را نشان می‌دهد و برای مانیتورینگ عالی است.

در پاسخ به «pm.max_children را چگونه تعیین می‌کنید؟» فرمول حافظه را بنویسید، روش اندازه‌گیری RSS را بگویید، به حاشیه‌ی اطمینان و سرویس‌های دیگر روی همان سرور اشاره کنید و در نهایت بگویید با تست بار و صفحه‌ی status اعتبارسنجی می‌کنید. اشاره به pm.max_requests برای مهار memory leak امتیاز اضافه دارد.

پیچیدگی الگوریتمی در کد واقعی

پیچیدگی زمانی (Big-O) نشان می‌دهد زمان اجرا با رشد ورودی چگونه رشد می‌کند. کدی که روی ۱۰۰ رکورد تست شده و O(n²) است، روی ۱۰۰ هزار رکورد ده میلیارد عملیات دارد. بیشتر مشکلات واقعی از حلقه‌ی پنهان می‌آیند: تابعی که داخل حلقه صدا زده می‌شود و خودش یک حلقه است.

in_array داخل حلقه → isset روی آرایه‌ی flip‌شده

<?php
// O(n × m): in_array هر بار کل آرایه را خطی می‌گردد
$result = [];
foreach ($orders as $order) {                       // n
    if (in_array($order['user_id'], $blockedIds)) { // m
        $result[] = $order;
    }
}

// O(n + m): ساخت یک hash map یک‌بار، سپس جستجوی O(1)
$blocked = array_flip($blockedIds);                 // کلیدها = شناسه‌ها
$result = [];
foreach ($orders as $order) {
    if (isset($blocked[$order['user_id']])) {
        $result[] = $order;
    }
}

آرایه‌های PHP در واقع hash table هستند؛ دسترسی با کلید (isset، array_key_exists) به‌طور میانگین O(1) است اما جستجوی مقدار (in_array، array_search) O(n) است. با ۱۰ هزار سفارش و ۵ هزار شناسه، تفاوت بین ۵۰ میلیون مقایسه و ۱۵ هزار عملیات است.

isset برای کلیدی که مقدارش null است false برمی‌گرداند؛ اگر null معنادار است از array_key_exists استفاده کنید. همچنین in_array بدون پارامتر سوم (strict: true) مقایسه‌ی loose انجام می‌دهد که می‌تواند باگ ایجاد کند.

ساختن رشته‌ها

  • عملگر .= در PHP برای الحاق پشت‌سرهم کارایی خوبی دارد و implode() روی آرایه هم انتخاب خوانایی است؛ تفاوت این دو معمولاً قابل‌اندازه‌گیری نیست.
  • مشکل واقعی ساختن یک رشته‌ی خیلی بزرگ (مثلاً CSV صدمگابایتی) در حافظه است. راه درست، stream کردن خروجی است: fputcsv روی php://output با response()->streamDownload()، یا نوشتن تدریجی در فایل.
  • برای قالب‌بندی‌های پیچیده sprintf خواناتر است؛ برای HTML از Blade استفاده کنید، نه الحاق دستی.

سوال‌های «این کد چه مشکلی دارد؟» معمولاً یک in_array، firstWhere یا کوئری داخل foreach دارند. پاسخ کامل: ۱) پیچیدگی فعلی (O(n×m) یا N کوئری)، ۲) راه‌حل (hash map با array_flip/keyBy یا whereIn)، ۳) پیچیدگی جدید، ۴) هزینه‌ی حافظه‌ی اضافه برای ساخت map.

مدیریت حافظه: Generator، LazyCollection و آرایه‌های بزرگ

PHP حافظه را با reference counting و یک garbage collector برای ارجاع‌های چرخه‌ای مدیریت می‌کند. در مدل FPM، بعد از هر درخواست کل حافظه آزاد می‌شود؛ به همین دلیل مشکلات حافظه بیشتر در jobها، دستورات Artisan، importهای بزرگ و پروسه‌های طولانی‌مدت (queue worker، Octane) دیده می‌شوند.

Generator

Generator با yield مقادیر را یکی‌یکی تولید می‌کند، بدون اینکه کل مجموعه در حافظه ساخته شود. مصرف حافظه O(1) نسبت به تعداد آیتم‌هاست.

<?php
// بد: کل فایل 2GB در حافظه
$lines = file('/data/huge.csv');

// خوب: خواندن خط‌به‌خط با Generator
function readCsv(string $path): \Generator
{
    $handle = fopen($path, 'r');
    try {
        while (($row = fgetcsv($handle)) !== false) {
            yield $row;
        }
    } finally {
        fclose($handle);
    }
}

foreach (readCsv('/data/huge.csv') as $row) {
    // پردازش یک ردیف
}

LazyCollection

<?php
use Illuminate\Support\LazyCollection;

LazyCollection::make(function () {
    $handle = fopen(storage_path('import/products.csv'), 'r');
    while (($row = fgetcsv($handle)) !== false) {
        yield $row;
    }
    fclose($handle);
})
->skip(1)                                   // header
->map(fn ($r) => ['sku' => $r[0], 'price' => (int) $r[1]])
->chunk(1000)
->each(fn ($chunk) => Product::upsert($chunk->all(), ['sku'], ['price']));

در این مثال در هر لحظه حداکثر ۱۰۰۰ ردیف در حافظه است، حتی اگر فایل ده میلیون ردیف داشته باشد. ترکیب stream خواندن + chunk + bulk upsert الگوی استاندارد import است.

نکات دیگر

  • unset($bigArray) ارجاع را حذف می‌کند و اگر ارجاع دیگری نباشد حافظه قابل استفاده‌ی مجدد می‌شود؛ در حلقه‌های طولانی برای متغیرهای حجیم موقت مفید است.
  • آرایه‌های PHP سربار قابل‌توجهی برای هر عنصر دارند (هش‌تیبل)؛ یک میلیون عنصر عدد صحیح ده‌ها مگابایت حافظه می‌گیرد. مدل‌های Eloquent بسیار سنگین‌تر از آرایه‌ی خام‌اند؛ برای گزارش‌گیری حجیم، toBase() یا Query Builder (DB::table) سبک‌تر است.
  • PHP برای آرایه‌ها copy-on-write دارد: پاس دادن آرایه به تابع کپی نمی‌کند مگر آن را تغییر دهید. استفاده از reference (&) برای «صرفه‌جویی حافظه» معمولاً لازم نیست و کد را گیج‌کننده می‌کند.
  • در queue workerها، کش‌های static، singletonها و Query Log فعال باعث رشد تدریجی حافظه می‌شوند. گزینه‌های --memory، --max-jobs و --max-time در queue:work worker را قبل از مشکل بازیافت می‌کنند.
  • اندازه‌گیری: memory_get_usage() و memory_get_peak_usage(true).

بالا بردن memory_limit به -1 یا چند گیگابایت «راه‌حل» نیست؛ فقط مشکل را به OOM killer سیستم‌عامل منتقل می‌کند. راه‌حل، پردازش جریانی است.

انتقال کار کند به صف و Laravel Octane

Queue: کاربر نباید منتظر کار پس‌زمینه بماند

هر کاری که برای ساختن پاسخ HTTP لازم نیست (ارسال ایمیل و SMS، تولید PDF، فراخوانی webhook، پردازش تصویر، همگام‌سازی با سرویس خارجی) باید به صف منتقل شود. زمان پاسخ از چند ثانیه به چند ده میلی‌ثانیه می‌رسد و workerهای FPM هم زودتر آزاد می‌شوند.

<?php
// قبل: کاربر منتظر SMTP و تولید PDF می‌ماند
public function store(StoreOrderRequest $request)
{
    $order = Order::create($request->validated());
    $pdf = InvoicePdf::generate($order);               // 1.5s
    Mail::to($order->user)->send(new OrderPlaced($order, $pdf)); // 1s
    return new OrderResource($order);
}

// بعد: پاسخ فوری، کار سنگین در worker
public function store(StoreOrderRequest $request)
{
    $order = Order::create($request->validated());
    ProcessPlacedOrder::dispatch($order)->afterCommit();
    return new OrderResource($order);
}
  • afterCommit() تضمین می‌کند job فقط بعد از commit شدن تراکنش dispatch شود؛ وگرنه ممکن است worker رکوردی را بخواند که هنوز commit نشده.
  • Jobها باید idempotent باشند چون ممکن است دوباره اجرا شوند (retry). $tries، $backoff و $timeout را تنظیم کنید.
  • به job فقط شناسه یا مدل (که با SerializesModels فقط شناسه‌اش ذخیره می‌شود) پاس دهید، نه داده‌ی حجیم.
  • برای فراخوانی چند API خارجی مستقل در همان درخواست، Http::pool() آن‌ها را هم‌زمان اجرا می‌کند؛ زمان کل ≈ کندترین درخواست، نه مجموع.
  • در Laravel می‌توان کار کوچک را بعد از ارسال پاسخ اجرا کرد (مثل dispatch(...)->afterResponse())، ولی این کار همچنان worker FPM را اشغال نگه می‌دارد و retry ندارد؛ برای کار جدی صف واقعی بهتر است.

Laravel Octane

در مدل سنتی PHP-FPM، برای هر درخواست کل فریمورک bootstrap می‌شود: autoload، ساخت container، ثبت service providerها، خواندن config. Octane اپلیکیشن را یک‌بار boot می‌کند و در حافظه نگه می‌دارد و درخواست‌ها را با همان نمونه سرو می‌کند. سرورهای پشتیبانی‌شده: FrankenPHP، Swoole، Open Swoole و RoadRunner.

مزایا

  • حذف هزینه‌ی bootstrap در هر درخواست؛ throughput بسیار بالاتر برای endpointهای سبک.
  • امکاناتی مثل concurrent tasks و Octane cache (در Swoole).
  • تعداد کمتر سرور برای همان ترافیک.

ریسک‌ها

  • نشت state بین درخواست‌ها: singletonهایی که Request، کاربر یا config را در خودشان نگه می‌دارند، متغیرهای static، آرایه‌هایی که مدام بزرگ می‌شوند.
  • نشت حافظه در طول زمان؛ گزینه‌ی --max-requests worker را بازیافت می‌کند.
  • بعد از deploy باید workerها reload شوند (octane:reload).
  • اگر گلوگاه دیتابیس است، Octane آن را حل نمی‌کند.
<?php
// خطرناک در Octane: Request درون singleton گیر می‌کند و در درخواست بعدی هم همان می‌ماند
$this->app->singleton(ReportService::class, function ($app) {
    return new ReportService($app['request']);
});

// امن: Request را در زمان استفاده resolve کنید یا به متد پاس دهید
$this->app->singleton(ReportService::class, fn ($app) => new ReportService(
    fn () => $app['request']
));

Octane سرعت «PHP» را بالا نمی‌برد؛ هزینه‌ی bootstrap را حذف می‌کند. بنابراین بیشترین اثر را روی درخواست‌های سبک و پرتعداد دارد. اگر یک endpoint یک ثانیه منتظر کوئری است، با Octane هم تقریباً یک ثانیه طول می‌کشد.

بهینه‌سازی لایه HTTP و کارایی ادراک‌شده

فشرده‌سازی

پاسخ‌های متنی (HTML، JSON، CSS، JS، SVG) با gzip یا Brotli معمولاً ۷۰ تا ۹۰ درصد کوچک‌تر می‌شوند. Brotli معمولاً نسبت فشرده‌سازی بهتری دارد اما در Nginx به ماژول جداگانه (ngx_brotli) نیاز دارد. تصاویر JPEG/PNG/WebP و فایل‌های zip را دوباره فشرده نکنید؛ فقط CPU هدر می‌رود.

gzip on;
gzip_comp_level 5;
gzip_min_length 1024;
gzip_types text/plain text/css application/json application/javascript
           application/xml image/svg+xml;
gzip_vary on;

# دارایی‌های ساخته‌شده توسط Vite نام hash‌دار دارند و می‌توان آن‌ها را برای همیشه کش کرد
location /build/ {
    expires 1y;
    add_header Cache-Control "public, immutable";

}

HTTP/2 و HTTP/3

  • HTTP/2: multiplexing (چند درخواست هم‌زمان روی یک اتصال TCP)، فشرده‌سازی header (HPACK) و پروتکل باینری. مشکل head-of-line blocking در سطح HTTP را حل می‌کند و نیاز به ترفندهایی مثل domain sharding را از بین می‌برد. عملاً روی HTTPS استفاده می‌شود.
  • HTTP/3: روی QUIC (مبتنی بر UDP)؛ head-of-line blocking در سطح TCP را هم ندارد و روی شبکه‌های موبایل با packet loss بهتر عمل می‌کند.

CDN

CDN فایل‌های ثابت (و در صورت تنظیم، پاسخ‌های قابل کش) را در سرورهای لبه نزدیک کاربر نگه می‌دارد: latency کمتر، بار کمتر روی origin و مقاومت بیشتر در برابر پیک ترافیک. نام فایل‌های hash‌دار (cache busting) اجازه می‌دهد TTL طولانی بدون نگرانی از نسخه‌ی قدیمی تنظیم شود.

Vite و دارایی‌های فرانت

  • npm run build فایل‌ها را minify، tree-shake و با نام hash‌دار در public/build می‌سازد؛ دایرکتیو @vite در Blade از روی manifest، تگ‌های درست را تولید می‌کند.
  • code splitting با import() دینامیک باعث می‌شود کاربر فقط JS صفحه‌ی فعلی را دانلود کند.
  • در production هرگز dev server را اجرا نکنید و فایل public/hot نباید روی سرور باشد.

کارایی ادراک‌شده (Perceived performance)

  • آنچه کاربر حس می‌کند مهم است: TTFB (زمان تا اولین بایت، مسئولیت مستقیم بک‌اند)، و Core Web Vitals مثل LCP (بزرگ‌ترین محتوای قابل‌مشاهده)، INP (پاسخ‌گویی به تعامل) و CLS (جابه‌جایی چیدمان).
  • ترفندها: skeleton/placeholder، lazy loading تصاویر (loading="lazy")، تعیین ابعاد تصویر، فرمت‌های WebP/AVIF، صفحه‌بندی یا infinite scroll به جای لیست کامل، پاسخ ۲۰۲ و نمایش وضعیت برای کارهای طولانی.
  • کاهش حجم payload در API: فقط فیلدهای لازم در API Resource، صفحه‌بندی، فشرده‌سازی.

اشتباهات رایج Benchmark

  • محیط غیرواقعی: APP_DEBUG=true، Xdebug روشن، OPcache خاموش، config کش نشده، یا دیتابیس با ۱۰۰ ردیف به جای ۱۰ میلیون.
  • تولید بار از همان سرور: ابزار تست با اپلیکیشن سر CPU رقابت می‌کند؛ مولد بار را روی ماشین جدا اجرا کنید.
  • نبود warm-up: اولین درخواست‌ها OPcache و کش‌ها را پر می‌کنند؛ آن‌ها را از نتایج کنار بگذارید یا جداگانه گزارش دهید.
  • فقط میانگین: p95/p99 و نرخ خطا را گزارش کنید. RPS بالا با ۲۰٪ خطای 502 موفقیت نیست.
  • کش همیشه داغ: اگر همه‌ی درخواست‌ها یک URL را می‌زنند، فقط کارایی کش را سنجیده‌اید. داده و پارامترهای متنوع استفاده کنید.
  • Microbenchmark گمراه‌کننده: اندازه‌گیری ۱۰ میلیون بار یک عملیات بی‌اهمیت در حلقه با microtime چیزی درباره‌ی اپلیکیشن واقعی نمی‌گوید؛ از hrtime(true) و تکرار چندباره استفاده کنید و نتیجه را در بستر واقعی بسنجید.
  • تست روی production بدون هماهنگی: می‌تواند سرویس را برای کاربران واقعی از کار بیندازد یا داده‌ی جعلی بسازد. staging هم‌اندازه بهترین گزینه است.
  • نادیده گرفتن وابستگی‌ها: rate limit سرویس‌های خارجی، محدودیت اتصال دیتابیس (max_connections)، ظرفیت Redis.

اگر پرسیدند «چطور ثابت می‌کنید بهینه‌سازی شما مؤثر بوده؟»: baseline قبل از تغییر، همان سناریوی تست بار با همان داده و محیط، مقایسه‌ی p95/p99، throughput و نرخ خطا، و تکرار چندباره برای حذف نویز. همچنین بعد از deploy، مانیتورینگ production را با بازه‌ی قبل مقایسه کنید.

مفهوم «Premature Optimization» را توضیح دهید. چرا گفته می‌شود باید ابتدا اندازه‌گیری کرد؟ رویکرد شما برای بهینه‌سازی یک سیستم کند چیست؟

تعریف: Premature optimization یعنی صرف وقت و پیچیده کردن کد برای بهبود کارایی بخشی که هنوز با داده ثابت نشده گلوگاه است. جمله‌ی Knuth می‌گوید در حدود ۹۷٪ موارد بازدهی‌های کوچک ارزش ندارند، ولی آن ۳٪ بحرانی را نباید از دست داد.

چرا اول اندازه‌گیری:

  • شهود توسعه‌دهنده درباره‌ی محل کندی معمولاً اشتباه است؛ در وب اغلب زمان در I/O (دیتابیس، شبکه) صرف می‌شود نه حلقه‌های PHP.
  • طبق قانون Amdahl، بهبود بخشی که ۵٪ زمان را می‌گیرد حداکثر ۵٪ اثر دارد.
  • بدون baseline نمی‌توان ثابت کرد تغییر مفید بوده یا حتی کارایی را بدتر نکرده.

رویکرد: ۱) هدف قابل اندازه‌گیری (مثلاً p95 زیر ۳۰۰ms)؛ ۲) baseline در محیط شبیه production؛ ۳) پیدا کردن گلوگاه با APM، Telescope/Debugbar برای کوئری‌ها، slow query log و Blackfire/Xdebug برای CPU؛ ۴) اصلاح بزرگ‌ترین گلوگاه با یک تغییر در هر بار؛ ۵) اندازه‌گیری مجدد؛ ۶) جلوگیری از regression با مانیتورینگ و تست.

نکته‌ی تکمیلی: طراحی درست از ابتدا (ایندکس مناسب، جلوگیری از N+1، استفاده از صف برای کار کند) premature optimization نیست؛ این‌ها مهندسی خوب است. آنچه باید از آن پرهیز کرد میکروبهینه‌سازی‌های بی‌اثر به قیمت خوانایی است.

مسئله‌ی N+1 در ORMها چیست؟ با یک مثال در Laravel توضیح دهید، تعداد کوئری‌ها را قبل و بعد از اصلاح بنویسید و بگویید چگونه از تکرار آن جلوگیری می‌کنید.

تعریف: وقتی یک کوئری لیست N رکورد را می‌گیرد و سپس برای رابطه‌ی هر رکورد یک کوئری جداگانه اجرا می‌شود، مجموعاً N+1 کوئری داریم. علت در Eloquent، lazy loading رابطه‌ها هنگام دسترسی به property است.

<?php
// N+1: برای 100 سفارش، 1 + 100 کوئری
$orders = Order::latest()->take(100)->get();
foreach ($orders as $o) {
    echo $o->customer->name;
}

// اصلاح: 2 کوئری (orders + customers با where in)
$orders = Order::with('customer:id,name')->latest()->take(100)->get();

اگر روی هر سفارش تعداد آیتم‌ها هم نمایش داده شود، به جای $o->items->count() از withCount('items') استفاده می‌کنیم تا شمارش در یک subquery انجام شود و آیتم‌ها load نشوند.

چرا مهم است: هر کوئری هزینه‌ی round-trip شبکه دارد؛ ۵۰۰ کوئری یک‌میلی‌ثانیه‌ای یعنی نیم ثانیه فقط انتظار، به‌علاوه‌ی بار روی دیتابیس که با هم‌زمانی کاربران چند برابر می‌شود.

پیشگیری:

  • Model::preventLazyLoading(! app()->isProduction()) تا در توسعه هر lazy load خطا بدهد.
  • Debugbar/Telescope برای دیدن تعداد کوئری و کوئری‌های تکراری.
  • تست Feature که تعداد کوئری endpoint را assert می‌کند.
  • دقت در API Resourceها و accessorها؛ استفاده از whenLoaded() در Resource.

نکته: eager loading بی‌رویه (load رابطه‌هایی که استفاده نمی‌شوند) هم هزینه است؛ فقط رابطه‌ها و ستون‌های لازم را load کنید.

متدهای chunk، chunkById، lazy و cursor در Eloquent را از نظر نحوه‌ی کار و مصرف حافظه مقایسه کنید. هر کدام را در چه شرایطی انتخاب می‌کنید؟

هدف مشترک: پردازش تعداد زیادی رکورد بدون اینکه همه هم‌زمان در حافظه باشند (برخلاف get()/all()).

  • chunk(n): کوئری‌های متوالی با LIMIT/OFFSET؛ در هر لحظه یک دسته در حافظه است. مشکل: اگر حین پردازش ستون شرط را تغییر دهید رکوردها جا می‌افتند، و OFFSET بزرگ روی جدول بزرگ کند است.
  • chunkById(n): keyset pagination با where id > last order by id؛ هم سریع است و هم وقتی رکوردها را حین پردازش update می‌کنید امن است. انتخاب پیش‌فرض من برای jobهای دسته‌ای.
  • lazy() / lazyById(): همان chunk در پشت صحنه اما خروجی LazyCollection تخت؛ کد خواناتر با each، map، filter. مناسب export و pipelineهای پردازش.
  • cursor(): فقط یک کوئری اجرا می‌کند و با generator هر بار یک مدل می‌سازد؛ کمترین مدل Eloquent هم‌زمان در حافظه. اما PDO به‌طور پیش‌فرض کل نتیجه‌ی خام را بافر می‌کند، پس روی داده‌ی خیلی بزرگ باز هم حافظه کم می‌آید؛ و eager loading ندارد (خطر N+1).
<?php
Invoice::where('status', 'pending')->chunkById(500, function ($invoices) {
    foreach ($invoices as $invoice) {
        $invoice->update(['status' => 'processing']);
    }
});

جمع‌بندی: برای update در حین پردازش ← chunkById؛ برای export/pipeline ← lazyById؛ برای مجموعه‌ی متوسط بدون رابطه و یک کوئری ← cursor. در همه‌ی موارد ستون‌ها را محدود کنید و برای کارهای خیلی بزرگ هر دسته را به یک job در صف بسپارید.

کد زیر چه مشکلات کارایی دارد؟ نسخه‌ی بهینه را بنویسید و پیچیدگی قبل و بعد را تحلیل کنید. foreach ($orders as $o) { if (in_array($o->user_id, $vipIds)) { $o->product = Product::find($o->product_id); } }

مشکلات:

  • in_array جستجوی خطی است؛ داخل حلقه پیچیدگی O(n × m) می‌شود (n سفارش، m شناسه‌ی VIP).
  • Product::find داخل حلقه یعنی یک کوئری برای هر سفارش VIP (الگوی N+1)؛ محصولات تکراری هم چند بار خوانده می‌شوند.
  • in_array بدون strict مقایسه‌ی loose دارد.
<?php
$vip = array_flip($vipIds);                       // O(m) – hash map
$vipOrders = $orders->filter(fn ($o) => isset($vip[$o->user_id]));   // O(n)

$products = Product::whereIn('id', $vipOrders->pluck('product_id')->unique())
    ->get(['id', 'name', 'price'])
    ->keyBy('id');                                // 1 کوئری

foreach ($vipOrders as $o) {
    $o->setRelation('product', $products->get($o->product_id)); // O(1)
}

تحلیل: قبل: O(n × m) مقایسه + تا n کوئری. بعد: O(n + m) عملیات در حافظه + ۱ کوئری. هزینه‌ی اضافه، حافظه‌ی hash map است که معمولاً ناچیز است.

بهتر از آن: اگر $orders از دیتابیس می‌آید و رابطه‌ی product تعریف شده، کل منطق را در کوئری انجام دهید: Order::whereIn('user_id', $vipIds)->with('product:id,name,price')->get() تا فیلتر هم با ایندکس دیتابیس انجام شود.

OPcache چیست و چه تنظیماتی برای production پیشنهاد می‌کنید؟ تنظیم validate_timestamps=0 چه پیامدی برای فرایند deploy دارد؟

تعریف: PHP در حالت عادی در هر درخواست فایل‌ها را parse و به opcode کامپایل می‌کند. OPcache opcodeهای کامپایل‌شده را در shared memory نگه می‌دارد تا همه‌ی workerهای FPM بدون کامپایل مجدد از آن استفاده کنند. بهبود معمولاً چشمگیر و تقریباً بدون هزینه است.

تنظیمات کلیدی:

  • opcache.enable=1
  • opcache.memory_consumption (مثلاً 256MB) به اندازه‌ای که کل کد پروژه و vendor جا شود.
  • opcache.max_accelerated_files بیشتر از تعداد فایل‌های PHP (مثلاً 20000).
  • opcache.interned_strings_buffer (مثلاً 16) برای رشته‌های تکراری.
  • opcache.validate_timestamps=0 تا در هر درخواست mtime فایل‌ها چک نشود.

پیامد validate_timestamps=0: OPcache دیگر تغییر فایل‌ها را تشخیص نمی‌دهد؛ بعد از deploy کد قدیمی اجرا می‌شود، یا بدتر، ترکیبی از فایل‌های قدیمی و جدید. بنابراین در اسکریپت deploy باید بعد از جایگزینی کد، PHP-FPM را reload کرد (systemctl reload php8.3-fpm) یا از ابزاری برای پاک کردن کش FPM استفاده کرد. فراخوانی opcache_reset() از CLI کافی نیست چون CLI حافظه‌ی جدا دارد.

مانیتورینگ: با opcache_get_status() درصد پر شدن حافظه و hit rate را بررسی کنید؛ پر شدن حافظه یا تعداد کلیدها باعث ری‌استارت OPcache و افت ناگهانی کارایی می‌شود.

JIT در PHP 8 چیست و چه تفاوتی با OPcache دارد؟ آیا فعال کردن JIT یک اپلیکیشن Laravel معمولی را سریع‌تر می‌کند؟ چرا؟

تعریف: JIT (Just-In-Time) بخشی از OPcache است که opcodeهای پرتکرار را در زمان اجرا به کد ماشین native تبدیل می‌کند تا به جای تفسیر توسط Zend VM مستقیماً روی CPU اجرا شوند. با opcache.jit_buffer_size (غیرصفر) و opcache.jit (مثلاً tracing) فعال می‌شود.

تفاوت با OPcache:

  • OPcache مرحله‌ی کامپایل source به opcode را حذف می‌کند؛ برای همه‌ی اپلیکیشن‌ها مفید است.
  • JIT مرحله‌ی اجرای opcode را سریع‌تر می‌کند؛ فقط وقتی مفید است که زمان قابل‌توجهی صرف اجرای خود کد PHP شود.
  • JIT بدون OPcache وجود ندارد.

برای Laravel معمولی: اثر معمولاً ناچیز است، چون چنین اپلیکیشنی I/O-bound است: بیشتر زمان درخواست صرف انتظار برای MySQL، Redis، APIهای خارجی و فایل می‌شود. JIT زمان انتظار را کم نمی‌کند. علاوه بر این حافظه‌ی بیشتری مصرف می‌کند و در برخی موارد دیباگ را سخت‌تر می‌کند.

کجا مفید است: کدهای CPU-bound مثل محاسبات عددی، پردازش تصویر یا داده به‌صورت خالص PHP، الگوریتم‌های سنگین در CLI یا workerها.

نتیجه‌گیری: فعال کردن JIT را با benchmark روی workload واقعی تصمیم می‌گیرم؛ برای اپ وب معمولی اولویت با حذف N+1، کش و صف است.

یک سرور ۸ گیگابایتی دارید که Nginx، PHP-FPM و Redis روی آن اجرا می‌شوند. pm.max_children را چگونه محاسبه می‌کنید؟ تفاوت حالت‌های static، dynamic و ondemand چیست؟

اصل: هر worker FPM در هر لحظه یک درخواست پردازش می‌کند و حافظه‌ی خودش را دارد؛ پس سقف worker را حافظه تعیین می‌کند.

محاسبه:

  1. میانگین RSS هر worker را زیر بار واقعی اندازه می‌گیرم: ps -o rss -C php-fpm8.3 و میانگین با awk؛ فرض کنیم ۷۰MB.
  2. حافظه‌ی رزرو برای OS، Nginx، Redis و بافر: مثلاً ۲.۵GB.
  3. (8192 − 2560) ÷ 70 ≈ 80؛ با حاشیه‌ی اطمینان حدود ۷۰.

سپس با تست بار و صفحه‌ی pm.status_path (listen queue، max children reached) و free -m اعتبارسنجی می‌کنم.

حالت‌ها:

  • static: همیشه max_children فرایند؛ بدون هزینه‌ی fork هنگام پیک؛ برای سرور اختصاصی پرترافیک.
  • dynamic: تعداد بین min/max spare تنظیم می‌شود؛ تعادل حافظه و پاسخ‌گویی؛ پیش‌فرض.
  • ondemand: فرایند فقط هنگام نیاز ساخته و پس از idle timeout حذف می‌شود؛ صرفه‌جویی حافظه برای سایت‌های کم‌ترافیک، با تأخیر اولیه.

هشدار: اگر workerها کندند چون منتظر دیتابیس‌اند، افزایش max_children مشکل را حل نمی‌کند و حتی دیتابیس را بیشتر تحت فشار می‌گذارد. pm.max_requests را هم برای بازیافت workerها و مهار memory leak تنظیم می‌کنم.

استراتژی‌های کش در یک اپلیکیشن Laravel را توضیح دهید. Cache stampede چیست و چگونه از آن جلوگیری می‌کنید؟

لایه‌ها:

  • کش HTTP: هدرهای Cache-Control، ETag و پاسخ 304؛ CDN برای فایل‌های ثابت و پاسخ‌های عمومی.
  • کش داده در اپ: Cache::remember روی Redis برای نتایج کوئری‌های سنگین و محاسبات (الگوی cache-aside).
  • Memoization درون درخواست: helper once() یا property در سرویس.
  • کش فریمورک: config:cache، route:cache، view:cache، event:cache یا php artisan optimize در deploy.
  • کش opcode: OPcache.

Invalidation: TTL متناسب با تحمل داده‌ی قدیمی، پاک کردن کلید در observer یا بعد از نوشتن، کلیدهای نسخه‌دار، cache tags روی Redis.

Cache stampede: وقتی کلید پرمصرفی منقضی می‌شود و تعداد زیادی درخواست هم‌زمان cache miss می‌گیرند و همه با هم کوئری سنگین را اجرا می‌کنند؛ دیتابیس زیر بار می‌رود.

راه‌حل‌ها:

  • Lock: فقط یک درخواست با Cache::lock('key') بازسازی کند و بقیه مقدار قدیمی یا انتظار کوتاه.
  • Stale-while-revalidate: Cache::flexible() مقدار قدیمی را برمی‌گرداند و در پس‌زمینه تازه می‌کند.
  • Jitter: TTL تصادفی تا همه‌ی کلیدها هم‌زمان منقضی نشوند.
  • گرم کردن پیش‌دستانه: job زمان‌بندی‌شده که قبل از انقضا کش را می‌سازد.

ریسک‌ها: داده‌ی کهنه، کلیدی که به کاربر/زبان وابسته نیست و نشت داده بین کاربران، و پنهان شدن کوئری کند پشت کش تا روز انقضا.

سناریو: endpoint ثبت سفارش به‌طور میانگین ۴ ثانیه طول می‌کشد. پروفایل نشان می‌دهد ۳ ثانیه صرف تولید فاکتور PDF و ارسال ایمیل می‌شود. چه می‌کنید و چه نکاتی را رعایت می‌کنید؟

تحلیل: تولید PDF و ارسال ایمیل برای ساختن پاسخ HTTP لازم نیستند؛ کاربر فقط باید بداند سفارش ثبت شد. پس این کارها را به صف (Queue) منتقل می‌کنم.

<?php
$order = DB::transaction(fn () => Order::createFromCart($cart));
GenerateInvoiceAndNotify::dispatch($order)->afterCommit();
return response()->json(new OrderResource($order), 201);

نکات:

  • afterCommit تا worker رکورد commit‌نشده را نخواند.
  • Job idempotent باشد (مثلاً اگر فاکتور ساخته شده دوباره نسازد)، چون retry ممکن است.
  • $tries، $backoff و $timeout مناسب؛ مدیریت failed jobs و هشدار.
  • اجرای worker با Supervisor یا systemd، و queue:restart در deploy.
  • اگر کاربر باید فاکتور را ببیند، وضعیت «در حال آماده‌سازی» و اطلاع‌رسانی بعدی (یا polling/WebSocket).
  • صف‌های جدا با اولویت (مثلاً emails و default) تا کار سنگین کارهای فوری را معطل نکند.

نتیجه: زمان پاسخ به حدود ۱ ثانیه (یا کمتر) می‌رسد و workerهای FPM سریع‌تر آزاد می‌شوند و ظرفیت هم‌زمانی بالا می‌رود. سپس همان ۱ ثانیه‌ی باقی‌مانده را هم پروفایل می‌کنم (کوئری‌ها، N+1، فراخوانی‌های خارجی هم‌زمان با Http::pool).

Trade-off: پیچیدگی عملیاتی بیشتر (مانیتورینگ صف، workerها) و eventual consistency.

دستورات config:cache، route:cache، view:cache، event:cache و optimize در Laravel چه می‌کنند؟ چه مشکلاتی ممکن است ایجاد کنند؟

هدف کلی: حذف کارهای تکراری bootstrap در هر درخواست با ساختن فایل‌های PHP آماده در bootstrap/cache در زمان deploy.

  • config:cache: همه‌ی فایل‌های config را در یک آرایه‌ی واحد ادغام می‌کند؛ دیگر نیاز به خواندن ده‌ها فایل و .env نیست.
  • route:cache: routeها را از پیش ثبت و serialize می‌کند؛ برای اپ‌های با route زیاد اثر محسوسی دارد.
  • view:cache: همه‌ی Blade templateها را از قبل کامپایل می‌کند.
  • event:cache: نگاشت eventها به listenerها را کش می‌کند تا discovery در هر درخواست انجام نشود.
  • optimize: همه‌ی موارد بالا را یکجا اجرا می‌کند؛ optimize:clear برعکس.

مشکلات رایج:

  • بعد از config:cache، فراخوانی env() خارج از فایل‌های config مقدار null می‌دهد. باید همیشه از config() استفاده کرد.
  • تغییر .env یا config روی سرور بدون اجرای مجدد کش اعمال نمی‌شود.
  • اجرای این دستورات در محیط local باعث گیجی هنگام توسعه می‌شود.
  • کش باید در هر deploy با کد جدید دوباره ساخته شود؛ کش قدیمی می‌تواند به کلاس یا routeای اشاره کند که دیگر وجود ندارد.

این دستورات در کنار composer install --no-dev -o و OPcache بخشی از چک‌لیست استاندارد deploy هستند.

یک job شبانه باید یک فایل CSV با ۵ میلیون ردیف را import کند و با خطای Allowed memory size exhausted متوقف می‌شود. علت را تحلیل کنید و راه‌حل بدهید.

علت‌های محتمل:

  • خواندن کل فایل با file() یا file_get_contents و ساخت آرایه‌ی ۵ میلیون عنصری.
  • ساختن مدل Eloquent برای هر ردیف و نگه داشتن همه در یک Collection.
  • Query log فعال یا eventهایی که اشیاء را نگه می‌دارند.
  • درج تک‌تک که علاوه بر کندی، اشیاء زیادی می‌سازد.

<?php
LazyCollection::make(function () use ($path) {
    $h = fopen($path, 'r');
    fgetcsv($h); // header
    while (($row = fgetcsv($h)) !== false) {
        yield ['sku' => $row[0], 'price' => (int) $row[1], 'stock' => (int) $row[2]];
    }
    fclose($h);
})
->chunk(1000)
->each(function ($chunk) {
    Product::upsert($chunk->all(), ['sku'], ['price', 'stock']);
});
  • حافظه در هر لحظه فقط یک دسته‌ی ۱۰۰۰تایی است: O(chunk) به جای O(n).
  • upsert دسته‌ای به جای ۵ میلیون کوئری، تعداد کوئری را به حدود ۵۰۰۰ می‌رساند.
  • DB::disableQueryLog() در اسکریپت‌های طولانی.
  • برای مقیاس بیشتر: شکستن فایل و dispatch هر بخش به یک job (یا Bus::batch) برای پردازش موازی و قابلیت ادامه از نقطه‌ی خطا.

چیزی که راه‌حل نیست: افزایش memory_limit به ۴GB؛ مشکل را با رشد داده دوباره ظاهر می‌کند و سرور را در معرض OOM killer قرار می‌دهد. توجه: upsert model eventها را اجرا نمی‌کند؛ اگر منطقی در observer هست باید جداگانه مدیریت شود.

Laravel Octane چگونه کارایی را افزایش می‌دهد؟ چه ریسک‌هایی دارد و در چه شرایطی استفاده از آن را توصیه نمی‌کنید؟

مکانیزم: در PHP-FPM، هر درخواست از صفر شروع می‌شود: autoload، ساخت service container، ثبت و boot کردن service providerها، بارگذاری config و routeها. Octane اپلیکیشن را یک‌بار boot می‌کند و در workerهای طولانی‌مدت (FrankenPHP، Swoole، RoadRunner) نگه می‌دارد؛ هر درخواست فقط از یک نمونه‌ی آماده استفاده می‌کند. نتیجه کاهش latency و افزایش throughput برای درخواست‌های سبک است.

ریسک‌ها:

  • نشت state: singletonی که Request یا کاربر جاری را در constructor گرفته، در درخواست‌های بعدی هم همان را دارد؛ ممکن است داده‌ی یک کاربر به کاربر دیگر نشان داده شود.
  • متغیرهای static و آرایه‌های رشدکننده که باعث memory leak می‌شوند؛ نیاز به --max-requests.
  • پکیج‌های third-party که برای مدل «هر درخواست از صفر» نوشته شده‌اند.
  • نیاز به reload workerها در deploy و تغییر در شیوه‌ی دیباگ و مانیتورینگ.

چه وقت توصیه نمی‌کنم:

  • وقتی گلوگاه دیتابیس یا API خارجی است؛ Octane فقط هزینه‌ی bootstrap را حذف می‌کند.
  • کدبیس قدیمی با state سراسری زیاد و بدون پوشش تست.
  • ترافیک کم که FPM به‌راحتی جوابگوست و پیچیدگی اضافه توجیه ندارد.

قبل از مهاجرت، با تست بار مقایسه می‌کنم و کد را برای state در singletonها بررسی می‌کنم.

تفاوت exists() و count() و همچنین تفاوت $user->posts()->count() و $user->posts->count() را توضیح دهید. چرا انجام تجمیع در دیتابیس بهتر است؟

exists در برابر count:

  • exists() کوئری select exists(...) می‌سازد؛ دیتابیس با پیدا کردن اولین ردیف متوقف می‌شود.
  • count() باید همه‌ی ردیف‌های منطبق را بشمارد.
  • برای سوال «آیا وجود دارد؟» همیشه exists() درست‌تر و سریع‌تر است.

رابطه با پرانتز و بدون پرانتز:

  • $user->posts() یک Query Builder برمی‌گرداند؛ ->count() یک SELECT COUNT(*) اجرا می‌کند.
  • $user->posts رابطه را load می‌کند (همه‌ی ستون‌ها و همه‌ی ردیف‌ها، hydrate به مدل) و سپس count() روی Collection در PHP اجرا می‌شود.
  • اگر رابطه از قبل eager load شده، دومی کوئری جدید نمی‌زند؛ در غیر این صورت اولی بسیار سبک‌تر است.
  • در لیست کاربران، هر دو داخل حلقه N+1 هستند؛ راه‌حل User::withCount('posts') و استفاده از $user->posts_count.

چرا تجمیع در دیتابیس: دیتابیس داده را محلی دارد و با ایندکس فیلتر و تجمیع می‌کند؛ فقط یک عدد از شبکه منتقل می‌شود. در PHP باید همه‌ی ردیف‌ها منتقل، به آرایه یا مدل تبدیل و در حافظه نگه داشته شوند: هم کندتر، هم پرمصرف‌تر و با رشد داده غیرقابل‌مقیاس.

<?php
$users = User::withCount('posts')
    ->withSum('orders as total_spent', 'amount')
    ->withExists('subscription as is_subscribed')
    ->paginate(20);
برای تست بار یک API چه ابزارها و چه روشی استفاده می‌کنید؟ اشتباهات رایجی که نتایج benchmark را بی‌اعتبار می‌کنند کدام‌اند؟

ابزارها:

  • ab: ساده و همه‌جا موجود؛ برای تست سریع یک URL؛ تک‌نخی و محدود.
  • wrk: چندنخی، تولید بار بسیار بالا، توزیع latency؛ سناریوهای پیچیده با Lua.
  • k6: سناریو با JavaScript، stageهای ramp-up، thresholdها (مثلاً p(95)<300) و ادغام با CI؛ انتخاب اصلی من.

روش: هدف مشخص (RPS و p95 مورد انتظار)، محیط staging هم‌اندازه‌ی production با داده‌ی واقعی‌نما، سناریوی واقعی (ترکیب endpointها، think time، توکن‌های متفاوت)، ramp-up تدریجی، مانیتورینگ هم‌زمان سرور (CPU، RAM، FPM status، کوئری‌های کند) و گزارش p50/p95/p99، throughput و نرخ خطا.

اشتباهات رایج:

  • Xdebug روشن، APP_DEBUG=true، OPcache خاموش یا کش‌های config/route ساخته نشده.
  • اجرای مولد بار روی همان سرور اپلیکیشن.
  • دیتابیس خیلی کوچک که همه‌چیز در حافظه جا می‌شود.
  • زدن یک URL ثابت که فقط کش را تست می‌کند.
  • نبود warm-up و گزارش فقط میانگین.
  • نادیده گرفتن نرخ خطا (RPS بالا با پاسخ‌های 502).
  • تغییر چند متغیر هم‌زمان بین دو اجرا و اجرای تنها یک‌بار (نویز).
Composer با گزینه‌های --optimize-autoloader و --classmap-authoritative چه تفاوتی ایجاد می‌کند؟ چه ریسکی در گزینه‌ی دوم وجود دارد؟

پیش‌زمینه: autoloader پیش‌فرض PSR-4 برای هر کلاس جدید، namespace را به مسیر فایل تبدیل و با file_exists روی دیسک چک می‌کند؛ برای هزاران کلاس هزینه‌ی قابل‌توجهی دارد (حتی با stat cache).

  • --optimize-autoloader (-o): با اسکن پوشه‌های PSR-4/PSR-0 یک classmap کامل (نام کلاس ← مسیر فایل) می‌سازد. کلاس‌های موجود مستقیم پیدا می‌شوند؛ اگر کلاسی در map نبود، به روش PSR-4 برمی‌گردد.
  • --classmap-authoritative (-a): classmap را تنها منبع حقیقت می‌داند؛ اگر کلاس در map نبود، بلافاصله «وجود ندارد» فرض می‌شود و هیچ جستجوی فایل‌سیستمی انجام نمی‌شود. حتی برای کلاس‌های ناموجود (مثلاً class_existsهای پیاپی پکیج‌ها) سریع‌تر است. -a به‌طور ضمنی -o را هم شامل می‌شود.

ریسک گزینه‌ی دوم: کلاس‌هایی که بعد از ساخت classmap روی دیسک ایجاد می‌شوند (کد تولیدشده در runtime، فایل‌های proxy یا کلاس اضافه‌شده بدون اجرای مجدد dump-autoload) هرگز load نمی‌شوند و خطای Class not found می‌گیریم. به همین دلیل فقط در production و در build تمیز استفاده می‌شود و در development نه.

composer install --no-dev --prefer-dist --no-interaction --optimize-autoloader --classmap-authoritative

نکته: اثر این گزینه‌ها همراه با OPcache بیشتر می‌شود؛ --no-dev هم پکیج‌های توسعه را حذف می‌کند که هم امنیت و هم حجم را بهتر می‌کند.

بین خوانایی کد و کارایی چگونه تعادل برقرار می‌کنید؟ یک مثال بیاورید که بهینه‌سازی ارزش پیچیده کردن کد را داشته باشد و یک مثال که نداشته باشد.

اصل: پیش‌فرض با خوانایی است، چون بیشتر هزینه‌ی نرم‌افزار در نگهداری است و کد خوانا باگ کمتری دارد. پیچیدگی را فقط وقتی می‌پذیرم که اندازه‌گیری نشان دهد آن بخش گلوگاه است و بهبود از نظر کسب‌وکار معنادار است.

بهینه‌سازی ارزشمند: گزارشی که با Collection روی ۲ میلیون سفارش جمع می‌زد و ۴۰ ثانیه طول می‌کشید، با یک کوئری GROUP BY و ایندکس مناسب به ۲۰۰ms رسید. کد کمی SQL-محورتر شد اما اثر ۲۰۰ برابری دارد؛ با کامنت و تست پوشش می‌دهم.

بهینه‌سازی بی‌ارزش: تبدیل یک collect($items)->map()->filter() روی ۲۰ آیتم به حلقه‌ی دستی با reference، یا جایگزینی double quote با single quote. اثری قابل‌اندازه‌گیری روی زمان درخواست ندارد ولی خوانایی را کم می‌کند.

راهکارها برای داشتن هر دو:

  • کپسوله کردن بخش بهینه‌شده در یک متد یا کلاس با نام گویا (مثلاً OrderReport::dailyRevenue()).
  • کامنت درباره‌ی «چرا» به همراه عدد benchmark.
  • تست برای حفظ رفتار و تست کارایی یا assertion تعداد کوئری برای جلوگیری از regression.
  • ترجیح بهینه‌سازی‌های معماری (کش، صف، ایندکس) که در لایه‌ی جدا اعمال می‌شوند و منطق اصلی را پیچیده نمی‌کنند.

خلاصه برای مرور سریع

اصول

  • هدف قابل اندازه‌گیری → baseline → profile → یک تغییر → اندازه‌گیری مجدد.
  • Amdahl: فقط بخش پرسهم ارزش بهینه‌سازی دارد.
  • وب معمولاً I/O-bound است؛ اول دیتابیس و شبکه.
  • p95/p99 گزارش کن، نه میانگین.

ابزارها

  • Xdebug profile (فقط dev) → cachegrind؛ Blackfire (کم‌سربار، مقایسه).
  • Telescope / Debugbar / Clockwork → کوئری‌ها، تعداد، تکرار.
  • slow query log + EXPLAIN؛ DB::listen.

دیتابیس از سمت اپ

  • N+1 → with()، withCount()، preventLazyLoading.
  • فقط ستون لازم: select، pluck، with('rel:id,name').
  • exists() نه count() > 0؛ sum() در SQL نه Collection.
  • کوئری در حلقه → whereIn + keyBy.
  • ایندکس ترکیبی: leftmost prefix؛ تابع روی ستون = بدون ایندکس.
  • OFFSET بزرگ کند → cursorPaginate/chunkById.

داده‌ی حجیم

  • chunk: offset؛ با تغییر ستون شرط رکورد جا می‌افتد.
  • chunkById: keyset؛ امن برای update.
  • lazy: LazyCollection روی chunk.
  • cursor: یک کوئری، یک مدل؛ بافر PDO، بدون eager load.
  • Bulk: insert، upsert، update با whereIn؛ بدون model event.

کش

  • Cache::remember، flexible (SWR)، once()، lock ضد stampede.
  • HTTP: Cache-Control، ETag → 304؛ cache.headers.
  • php artisan optimize = config + event + route + view cache.
  • بعد از config:cache: env() بیرون config = null.

Runtime

  • Composer: --no-dev -o -a؛ -a = بدون fallback فایل‌سیستم.
  • OPcache: source→opcode در shared memory؛ validate_timestamps=0 → reload FPM در deploy.
  • Preload: load کلاس‌ها هنگام start؛ تغییر = restart.
  • JIT: opcode→کد ماشین؛ فقط CPU-bound.

PHP-FPM

  • هر worker = یک درخواست هم‌زمان.
  • max_children ≈ RAM آزاد ÷ RSS هر worker.
  • static (پرترافیک)، dynamic (پیش‌فرض)، ondemand (کم‌ترافیک).
  • pm.max_requests ضد leak؛ slowlog؛ status page.

کد و حافظه

  • in_array در حلقه O(n·m) → array_flip + isset O(n+m).
  • firstWhere در حلقه → keyBy + get.
  • array_merge در حلقه O(n²) → array_merge(...$parts).
  • Generator / LazyCollection / stream → حافظه‌ی ثابت.
  • memory_limit بالا راه‌حل نیست.

معماری و HTTP

  • کار کند → Queue (afterCommit، idempotent، retry).
  • Http::pool برای فراخوانی هم‌زمان.
  • Octane: حذف bootstrap؛ خطر state leak؛ --max-requests.
  • gzip/brotli، HTTP/2 multiplexing، CDN، Vite با hash → immutable.
  • TTFB مسئولیت بک‌اند؛ LCP، INP، CLS.

تست بار

  • ab (ساده)، wrk (پربار)، k6 (سناریو + threshold + CI).
  • Load / Stress / Soak / Spike.
  • پرهیز: Xdebug، debug mode، مولد بار روی همان سرور، کش داغ، بدون warm-up، فقط میانگین.
