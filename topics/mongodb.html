MongoDB

پایگاه داده‌ی سندمحور (Document-oriented) با مدل BSON: از CRUD و عملگرهای کوئری و ایندکس‌ها تا Aggregation Pipeline، طراحی Schema (embedding در برابر referencing و الگوها)، Replica Set، Sharding، تراکنش‌ها و استفاده از MongoDB در Laravel.

مدل سندی و BSON

MongoDB یک پایگاه داده‌ی NoSQL از نوع Document Store است. به‌جای سطر و ستون، داده‌ها در قالب سند (Document) ذخیره می‌شوند؛ هر سند ساختاری شبیه JSON دارد: مجموعه‌ای از جفت‌های کلید/مقدار که مقدارها می‌توانند خودشان شیء تودرتو (Embedded Document) یا آرایه باشند.

{
  "_id": { "$oid": "6724a1f0c3b2a91e4f0d1a22" },
  "name": "Ali Rezaei",
  "email": "ali@example.com",
  "roles": ["admin", "editor"],
  "address": { "city": "Tehran", "zip": "1234567890" },
  "createdAt": { "$date": "2026-11-01T08:30:00Z" },
  "loginCount": 42
}

BSON چیست؟

MongoDB اسناد را روی دیسک و در شبکه به شکل BSON (Binary JSON) نگه می‌دارد. BSON یک فرمت باینری است که:

  • نوع‌های بیشتری از JSON دارد: ObjectId، Date، Int32، Int64 (Long)، Double، Decimal128، Binary، Timestamp، Regex و…
  • قابل پیمایش سریع است، چون طول هر فیلد و سند در خودش ذخیره شده و برای رسیدن به یک فیلد لازم نیست کل متن parse شود.
  • در عوض ممکن است کمی حجیم‌تر از JSON متنی معادل باشد (به خاطر نگه‌داشتن طول‌ها و نام فیلدها در هر سند).

تفاوت JSON و BSON سوال محبوبی است: JSON فرمت متنی و خوانا برای انسان با نوع‌های محدود (string, number, bool, null, array, object) است؛ BSON باینری، نوع‌دار (Date، ObjectId، Decimal128، Int64)، مناسب پیمایش سریع و ذخیره‌سازی است. در MongoDB شما با JSON-مانند کار می‌کنید، ولی ذخیره‌سازی BSON است.

ویژگی‌های کلیدی مدل سندی

  • Schema انعطاف‌پذیر (Flexible Schema): اسناد یک Collection لازم نیست ساختار یکسان داشته باشند. این به معنی «بدون Schema» نیست؛ Schema به لایه‌ی برنامه منتقل می‌شود و می‌توان با $jsonSchema اعتبارسنجی هم گذاشت.
  • Data locality: داده‌هایی که با هم خوانده می‌شوند، در یک سند کنار هم ذخیره می‌شوند؛ بنابراین بسیاری از JOINها حذف می‌شوند.
  • نگاشت طبیعی به اشیای برنامه: یک سند تقریباً همان شیء/آرایه‌ی PHP یا JSON در API است، پس impedance mismatch کمتر است.
  • اتمیک بودن در سطح یک سند: هر عملیات نوشتن روی یک سند (حتی با فیلدهای تودرتو) اتمیک است.

«Schemaless» اصطلاح گمراه‌کننده‌ای است. در عمل همیشه یک Schema ضمنی وجود دارد که کد شما به آن وابسته است. اگر آن را مدیریت نکنید (Validation، نسخه‌بندی Schema)، با گذشت زمان داده‌های ناسازگار خواهید داشت.

اعتبارسنجی Schema

db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["email", "createdAt"],
      properties: {
        email:     { bsonType: "string", pattern: "^.+@.+$" },
        age:       { bsonType: "int", minimum: 0 },
        createdAt: { bsonType: "date" }
      }
    }
  },
  validationLevel: "strict",   // یا "moderate"
  validationAction: "error"    // یا "warn"
});

چه زمانی MongoDB؟

انتخاب بین MongoDB و یک RDBMS (مثل MySQL/PostgreSQL) باید بر اساس الگوی دسترسی به داده (Access Pattern)، نیاز به یکپارچگی و مقیاس باشد، نه مُد روز.

MongoDB مناسب است وقتی…

  • داده ذاتاً سلسله‌مراتبی/تودرتو است (کاتالوگ محصول با ویژگی‌های متفاوت، CMS، پروفایل کاربر).
  • Schema سریع تغییر می‌کند یا اسناد ساختار متنوع دارند.
  • نیاز به مقیاس افقی (Sharding) داخلی و حجم نوشتن بالا دارید (لاگ، رویداد، IoT).
  • بیشتر خواندن‌ها «یک موجودیت با تمام جزئیاتش» است و JOIN پیچیده کم است.
  • داده‌های Time-series یا event store با الگوی append.

RDBMS انتخاب بهتری است وقتی…

  • روابط زیاد و پیچیده بین موجودیت‌ها و کوئری‌های ad-hoc با JOINهای متعدد دارید.
  • یکپارچگی قوی بین چند موجودیت (حسابداری، بانکی، موجودی انبار) حیاتی است و تراکنش چندجدولی امری روزمره است.
  • گزارش‌گیری تحلیلی و SQL استاندارد برای تیم/ابزارهای BI مهم است.
  • Schema پایدار و به‌خوبی شناخته‌شده است.
  • به Foreign Key و Constraintهای سمت دیتابیس نیاز دارید.

فیلد _id و ObjectId

  • هر سند باید فیلد _id داشته باشد که در Collection یکتاست و روی آن به‌طور خودکار یک unique index وجود دارد.
  • اگر شما مقداری ندهید، driver یک ObjectId می‌سازد.
  • _id می‌تواند هر نوعی جز آرایه باشد (عدد، رشته، سند) و بعد از درج قابل تغییر نیست.

ObjectId یک مقدار ۱۲ بایتی است:

| 4 bytes timestamp | 5 bytes random (per process) | 3 bytes counter |
   ثانیه از Unix epoch     یکتا برای ماشین/پروسس        شمارنده‌ی افزایشی
  • بدون هماهنگی مرکزی در سمت client ساخته می‌شود؛ پس برای سیستم توزیع‌شده مناسب است.
  • تقریباً بر اساس زمان مرتب است؛ مرتب‌سازی بر اساس _id تقریباً همان مرتب‌سازی بر اساس زمان ایجاد است.
  • زمان ایجاد را می‌توان از آن استخراج کرد: ObjectId("...").getTimestamp().

چون ObjectId «یکنواخت افزایشی (monotonically increasing)» است، استفاده‌ی مستقیم از آن به‌عنوان ranged shard key باعث می‌شود همه‌ی درج‌ها به یک shard (آخرین chunk) بروند: hot shard. راه‌حل: hashed shard key یا کلید ترکیبی.

ObjectId را رمز امنیتی فرض نکنید؛ قابل حدس‌تر از UUID تصادفی است. اگر شناسه را در URL عمومی نشان می‌دهید و نمی‌خواهید شمارش/حدس‌زدن ممکن باشد، کنترل دسترسی بگذارید یا شناسه‌ی عمومی جداگانه داشته باشید.

Create

use shop

db.users.insertOne({ name: "Sara", email: "sara@example.com", age: 29, tags: ["vip"] })

db.users.insertMany([
  { name: "Reza", email: "reza@example.com", age: 35 },

Read: find، فیلتر و projection

// همه‌ی کاربرانی که سنشان بین 18 و 30 است، فقط name و email، مرتب و صفحه‌بندی‌شده
db.users.find(
  { age: { $gte: 18, $lte: 30 } },          // filter
  { name: 1, email: 1, _id: 0 }             // projection
).sort({ age: -1 }).skip(20).limit(10)

db.users.findOne({ email: "sara@example.com" })

// فیلد تودرتو با dot notation (حتماً داخل کوتیشن)
db.users.find({ "address.city": "Tehran" })

db.users.countDocuments({ age: { $gt: 30 } })

در projection نمی‌توانید include و exclude را با هم ترکیب کنید (جز _id: 0). یعنی { name: 1, age: 0 } خطا می‌دهد.

صفحه‌بندی با skip بزرگ کند است، چون سرور باید همه‌ی اسناد قبلی را رد کند. برای صفحه‌های عمیق از Range/Keyset pagination استفاده کنید: find({ _id: { $gt: lastSeenId } }).sort({ _id: 1 }).limit(10).

Upsert

Upsert یعنی «اگر سندی با این فیلتر بود به‌روز کن، وگرنه درج کن». برای شمارنده‌ها، تنظیمات کاربر یا همگام‌سازی داده‌ی خارجی بسیار کاربردی است.

db.pageViews.updateOne(
  { page: "/home", day: "2026-11-07" },
  {
    $inc: { views: 1 },
    $setOnInsert: { createdAt: new Date() }
  },
  { upsert: true }
)

// گرفتن نتیجه‌ی بعد از تغییر به‌صورت اتمیک
db.counters.findOneAndUpdate(
  { _id: "invoice" },
  { $inc: { seq: 1 } },
  { upsert: true, returnDocument: "after" }
)

Upsert تحت هم‌زمانی بالا ممکن است دو سند تکراری بسازد (دو درخواست هم‌زمان هر دو «پیدا نشد» می‌بینند). راه‌حل استاندارد: یک unique index روی فیلدهای فیلتر؛ در این صورت یکی از دو درج با duplicate key شکست می‌خورد و می‌توان آن را retry کرد.

Delete

db.sessions.deleteOne({ _id: "abc" })
db.logs.deleteMany({ createdAt: { $lt: ISODate("2026-01-01") } })
db.logs.deleteMany({})          // همه‌ی اسناد (ایندکس‌ها می‌مانند)
db.logs.drop()                  // کل collection همراه ایندکس‌ها

حذف حجم بزرگ با deleteMany فشار زیادی (oplog، replication lag) ایجاد می‌کند. برای داده‌های منقضی‌شونده از TTL index استفاده کنید، یا حذف را دسته‌ای (batch) انجام دهید.

کوئری روی آرایه‌ها و $elemMatch

کوئری { tags: "php" } یعنی «آرایه‌ی tags شامل php باشد». نکته‌ی ظریف وقتی است که چند شرط روی عناصر آرایه‌ای از اسناد می‌گذارید:

// سند نمونه:
// { _id: 1, results: [ { product: "A", score: 3 }, { product: "B", score: 9 } ] }

// ❌ هر شرط می‌تواند با عنصر متفاوتی برآورده شود → سند 1 برمی‌گردد!
db.surveys.find({ "results.product": "A", "results.score": { $gt: 8 } })

// ✅ هر دو شرط باید روی «همان یک عنصر» برقرار باشند → سند 1 برنمی‌گردد
db.surveys.find({ results: { $elemMatch: { product: "A", score: { $gt: 8 } } } })

تفاوت dot notation و $elemMatch روی آرایه‌ی اسناد از سوالات کلاسیک است. dot notation شرط‌ها را روی کل آرایه می‌سنجد (هر شرط با هر عنصری)، ولی $elemMatch تضمین می‌کند که یک عنصر واحد همه‌ی شرط‌ها را داشته باشد.

$exists و null

db.users.find({ phone: null })              // phone برابر null است یا اصلاً وجود ندارد
db.users.find({ phone: { $exists: false } }) // فقط وقتی فیلد وجود ندارد
db.users.find({ phone: { $type: "null" } })  // فقط وقتی مقدار صریحاً null است

$regex و کارایی

db.users.find({ email: { $regex: "^ali" } })        // prefix، می‌تواند از ایندکس استفاده کند
db.users.find({ name: { $regex: "rez", $options: "i" } }) // کامل اسکن ایندکس/collection

فقط regex prefix و case-sensitive (با ^) به‌طور مؤثر از ایندکس استفاده می‌کند. regex بدون anchor یا با i عملاً همه‌ی کلیدها را می‌خواند. برای جست‌وجوی متنی از text index یا Atlas Search / موتور جست‌وجوی جدا (Elasticsearch) استفاده کنید. همچنین ورودی کاربر را قبل از قرار دادن در regex escape کنید (خطر ReDoS و تزریق الگو).

NoSQL Injection

اگر ورودی کاربر مستقیماً در فیلتر قرار بگیرد، کاربر می‌تواند به جای رشته یک شیء بفرستد، مثلاً password[$ne]=x که در PHP به آرایه‌ی ['$ne' => 'x'] تبدیل می‌شود و شرط را دور می‌زند.

<?php
// ❌ خطرناک
$user = $collection->findOne(['email' => $_POST['email'], 'password' => $_POST['password']]);

// ✅ نوع را اجبار کنید و رمز را هرگز مستقیم مقایسه نکنید
$email = (string) $request->input('email');
$user  = $collection->findOne(['email' => $email]);
if (! $user || ! password_verify((string) $request->input('password'), $user['password'])) {
    abort(401);
}

ایندکس‌ها و explain

ایندکس در MongoDB یک ساختار B-tree است که مقادیر یک یا چند فیلد را به‌صورت مرتب به همراه اشاره‌گر به سند نگه می‌دارد. بدون ایندکس، کوئری یک COLLSCAN (اسکن کل Collection) است.

هزینه‌ی ایندکس: هر insert/update/delete باید همه‌ی ایندکس‌های مرتبط را به‌روز کند؛ ایندکس فضای دیسک و RAM می‌گیرد. بهترین حالت این است که «working set» (داده‌ها و ایندکس‌های پرکاربرد) در RAM جا شود.

انواع ایندکس

// Single field
db.users.createIndex({ email: 1 }, { unique: true })

// Compound
db.orders.createIndex({ userId: 1, status: 1, createdAt: -1 })

// Multikey: روی فیلد آرایه، خودکار multikey می‌شود (یک کلید برای هر عنصر)
db.products.createIndex({ tags: 1 })

// Text (حداکثر یک text index برای هر collection)
db.articles.createIndex({ title: "text", body: "text" }, { weights: { title: 5 } })
db.articles.find({ $text: { $search: "laravel queue" } }, { score: { $meta: "textScore" } })
           .sort({ score: { $meta: "textScore" } })

// TTL: حذف خودکار اسناد بعد از زمان مشخص (فیلد باید از نوع Date باشد)
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })

// Partial: فقط اسنادی که شرط را دارند ایندکس می‌شوند
db.orders.createIndex(
  { createdAt: -1 },
  { partialFilterExpression: { status: "pending" } }
)

// Unique + Partial: ایمیل یکتا فقط بین کاربران حذف‌نشده
db.users.createIndex(
  { email: 1 },
  { unique: true, partialFilterExpression: { deletedAt: { $exists: false } } }
)

// Hashed (بیشتر برای shard key)
db.events.createIndex({ deviceId: "hashed" })
Single field
ایندکس روی یک فیلد؛ جهت (1 یا -1) برای sort تک‌فیلدی اهمیتی ندارد چون در هر دو جهت قابل پیمایش است.
Compound
ایندکس چندفیلدی؛ ترتیب فیلدها حیاتی است و از قاعده‌ی prefix پیروی می‌کند.
Multikey
ایندکس روی آرایه؛ در یک compound index حداکثر یکی از فیلدها در هر سند می‌تواند آرایه باشد.
Text
جست‌وجوی کلمه‌ای با stemming و stop word؛ یکی برای هر collection.
TTL
یک thread پس‌زمینه تقریباً هر ۶۰ ثانیه اسناد منقضی را حذف می‌کند؛ پس حذف دقیقاً سر ثانیه نیست.
Unique
تضمین یکتایی؛ اسنادی که فیلد را ندارند مقدار null حساب می‌شوند (دو سند بدون فیلد = تکراری)، مگر partial/sparse باشد.
Partial
فقط زیرمجموعه‌ای از اسناد را ایندکس می‌کند؛ کوچک‌تر و ارزان‌تر. کوئری باید شرط فیلتر را شامل شود تا از آن استفاده شود.
Sparse
فقط اسنادی که فیلد را دارند؛ partial انعطاف بیشتری دارد و توصیه‌ی فعلی است.
Wildcard
ایندکس روی فیلدهای دلخواه/ناشناخته ({ "attrs.$**": 1 }) برای Schemaهای خیلی متغیر.

قاعده‌ی Prefix در ایندکس ترکیبی

ایندکس { a: 1, b: 1, c: 1 } برای کوئری‌هایی روی a، a,b و a,b,c قابل استفاده است، ولی برای کوئری فقط روی b یا c (بدون a) کارایی ندارد.

قاعده‌ی ESR (Equality → Sort → Range)

برای چیدن فیلدها در ایندکس ترکیبی: ابتدا فیلدهایی که با برابری فیلتر می‌شوند، سپس فیلدهای مرتب‌سازی، و در آخر فیلدهای بازه‌ای ($gt، $lt، $in بزرگ، regex).

// کوئری:
db.orders.find({ userId: 42, total: { $gte: 100 } }).sort({ createdAt: -1 })

// ✅ طبق ESR: Equality (userId) → Sort (createdAt) → Range (total)
db.orders.createIndex({ userId: 1, createdAt: -1, total: 1 })

// ❌ اگر Range قبل از Sort بیاید: { userId: 1, total: 1, createdAt: -1 }
//    خروجی بازه دیگر بر اساس createdAt مرتب نیست → SORT در حافظه (in-memory sort)

دلیل ESR: فیلدهای برابری دامنه را به یک بخش پیوسته از ایندکس محدود می‌کنند؛ در آن بخش، فیلد بعدی (sort) از قبل مرتب است و MongoDB لازم نیست در حافظه sort کند؛ فیلد بازه‌ای در انتها فقط کلیدها را فیلتر می‌کند بدون آنکه ترتیب را بشکند. اگر Range قبل از Sort باشد، ترتیب sort در خروجی از دست می‌رود.

Covered Query

db.users.createIndex({ email: 1, name: 1 })
db.users.find({ email: "sara@example.com" }, { name: 1, _id: 0 })   // covered

مثال واقعی: گزارش فروش ماهانه به تفکیک دسته‌بندی

سند سفارش:

{
  "_id": 1001,
  "userId": 42,
  "status": "paid",
  "createdAt": { "$date": "2026-10-12T10:00:00Z" },
  "items": [
    { "sku": "A12", "category": "laptop", "price": 1200, "qty": 1 },
    { "sku": "M03", "category": "mouse",  "price": 25,   "qty": 2 }
  ]
}
db.orders.aggregate([
  // 1) هر چه زودتر فیلتر کن تا از ایندکس استفاده شود و داده‌ی کمتری جریان یابد
  { $match: {
      status: "paid",
      createdAt: { $gte: ISODate("2026-10-01"), $lt: ISODate("2026-11-01") }
  }},
  // 2) هر آیتم سفارش یک سند جدا
  { $unwind: "$items" },
  // 3) جمع فروش و تعداد به تفکیک دسته
  { $group: {
      _id: "$items.category",
      revenue:  { $sum: { $multiply: ["$items.price", "$items.qty"] } },
      unitsSold:{ $sum: "$items.qty" },
      orders:   { $addToSet: "$_id" }
  }},
  // 4) شکل خروجی
  { $project: {
      _id: 0,
      category: "$_id",
      revenue: 1,
      unitsSold: 1,
      orderCount: { $size: "$orders" }
  }},
  { $sort: { revenue: -1 } },
  { $limit: 5 }
])

$lookup (Join)

// ساده: localField/foreignField
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $lookup: {
      from: "users",
      localField: "userId",
      foreignField: "_id",
      as: "user"
  }},
  { $unwind: "$user" },                         // آرایه‌ی تک‌عضوی را به شیء تبدیل کن
  { $project: { total: 1, "user.name": 1, "user.email": 1 } }
])

// با pipeline: فقط ۳ سفارش آخر هر کاربر
db.users.aggregate([
  { $lookup: {
      from: "orders",
      let: { uid: "$_id" },
      pipeline: [
        { $match: { $expr: { $eq: ["$userId", "$$uid"] } } },
        { $sort: { createdAt: -1 } },
        { $limit: 3 }
      ],
      as: "recentOrders"
  }}
])

$lookup برای هر سند ورودی روی collection دیگر کوئری می‌زند؛ حتماً روی foreignField ایندکس بگذارید. اگر در مسیر اصلی برنامه مدام $lookup می‌زنید، احتمالاً Schema را برای الگوی دسترسی‌تان درست طراحی نکرده‌اید (embedding یا extended reference را بررسی کنید).

$facet: صفحه‌بندی + شمارش + فیلترهای جانبی در یک درخواست

db.products.aggregate([
  { $match: { category: "laptop", price: { $lte: 2000 } } },
  { $facet: {
      items:   [ { $sort: { price: 1 } }, { $skip: 0 }, { $limit: 20 },
                 { $project: { title: 1, price: 1 } } ],
      total:   [ { $count: "count" } ],
      byBrand: [ { $group: { _id: "$brand", n: { $sum: 1 } } }, { $sort: { n: -1 } } ],
      priceRanges: [ { $bucket: { groupBy: "$price", boundaries: [0, 500, 1000, 1500, 2001] } } ]
  }}
])

نکات بهینه‌سازی pipeline: (۱) $match و $sort را در ابتدای pipeline بگذارید تا از ایندکس استفاده کنند؛ بعد از $group یا $unwind ایندکس دیگر کاربردی ندارد. (۲) با $project فیلدهای غیرلازم را زود حذف کنید. (۳) هر stage محدودیت حافظه‌ی ۱۰۰ مگابایت دارد و برای عبور از آن باید از allowDiskUse استفاده شود (در نسخه‌های جدید رفتار پیش‌فرض اجازه‌ی استفاده از دیسک است). (۴) سند خروجی هر stage هم تابع محدودیت ۱۶MB است.

طراحی Schema: Embed یا Reference

مهم‌ترین تصمیم در MongoDB این است که داده‌ی مرتبط را داخل سند جاسازی (Embed) کنیم یا در collection جدا نگه داریم و با شناسه ارجاع (Reference) بدهیم.

Embedding

  • یک بار خواندن = همه‌ی داده (بدون join).
  • به‌روزرسانی اتمیک کل موجودیت در یک سند.
  • مناسب رابطه‌ی «شامل بودن» (contains) و داده‌ای که همیشه با والد خوانده می‌شود.
  • عیب: تکرار داده، رشد سند، محدودیت ۱۶MB، سختی کوئری مستقل روی زیرداده.

Referencing

  • بدون تکرار؛ به‌روزرسانی در یک نقطه.
  • مناسب داده‌ی بزرگ، بی‌حد، پرتغییر یا مشترک بین چند والد.
  • مناسب رابطه‌ی M:N.
  • عیب: نیاز به کوئری دوم یا $lookup، و نبود اتمیک بودن بین دو سند بدون تراکنش.

سوالات راهنما برای تصمیم

  1. آیا زیرداده همیشه با والد خوانده می‌شود؟ → Embed.
  2. آیا زیرداده مستقلاً کوئری یا به‌روز می‌شود؟ → Reference.
  3. تعداد زیرداده‌ها محدود و کوچک است یا بی‌حد (unbounded)؟
  4. نسبت خواندن به نوشتن چقدر است؟ داده‌ی تکراری چقدر تغییر می‌کند؟
  5. چرخه‌ی حیات زیرداده به والد وابسته است؟ (حذف والد = حذف فرزند)

کاردینالیتی: one-to-few، one-to-many، one-to-squillions

رابطهمثالراه‌حل معمول
One-to-Few (چند تا ده‌ها)آدرس‌های کاربر، شماره تلفن‌هاEmbed آرایه‌ی اسناد در والد
One-to-Many (صدها تا چند هزار)قطعات یک محصول، محصولات یک دستهآرایه‌ای از referenceها در والد (partIds: [...]) یا ref در فرزند
One-to-Squillions (میلیون‌ها، بی‌حد)لاگ‌های یک سرور، پیام‌های یک چتReference به والد در فرزند (hostId در هر log) + ایندکس
Many-to-Manyدانشجو/درس، محصول/تگآرایه‌ی ref در یک یا هر دو طرف، یا collection واسط
 
// One-to-Few: embed
{ _id: 1, name: "Sara", addresses: [
    { type: "home", city: "Tehran", street: "..." },
    { type: "work", city: "Tehran", street: "..." } ] }

// One-to-Many: آرایه‌ی ref در والد
{ _id: "P-100", name: "Laptop X", partIds: [ "PT-1", "PT-2", "PT-3" ] }

// One-to-Squillions: ref در فرزند
{ _id: ObjectId("..."), hostId: "srv-17", level: "error", msg: "...", at: ISODate("...") }
db.logs.createIndex({ hostId: 1, at: -1 })

Anti-pattern: Unbounded Array — جاسازی آرایه‌ای که بی‌حد رشد می‌کند (مثلاً همه‌ی کامنت‌های یک پست پربازدید یا همه‌ی سفارش‌های کاربر در سند کاربر). پیامدها: نزدیک شدن به سقف ۱۶MB، به‌روزرسانی و انتقال سند بزرگ در هر تغییر، ایندکس multikey حجیم و کندی. راه‌حل: Reference در فرزند، یا الگوی Subset/Bucket.

محدودیت اندازه‌ی سند

  • حداکثر اندازه‌ی یک سند BSON ۱۶ مگابایت است.
  • حداکثر عمق تودرتویی ۱۰۰ سطح است.
  • برای فایل‌های بزرگ‌تر از GridFS استفاده می‌شود (فایل را به chunkهای کوچک در دو collection fs.files و fs.chunks تقسیم می‌کند)، هرچند در عمل معمولاً ذخیره‌ی فایل در Object Storage (مثل S3) و نگه‌داشتن آدرس آن بهتر است.

هدف محدودیت ۱۶MB جلوگیری از اسناد بیش از حد بزرگ است که RAM و پهنای باند را مصرف می‌کنند. اگر به این سقف نزدیک می‌شوید، تقریباً همیشه نشانه‌ی اشکال در طراحی Schema است، نه دلیلی برای GridFS.

رابطه‌ی دوطرفه و denormalization

در MongoDB تکرار داده (denormalization) پذیرفته است، به شرطی که: داده‌ی تکراری به‌ندرت تغییر کند، خواندن خیلی بیشتر از نوشتن باشد، و استراتژی به‌روزرسانی نسخه‌های تکراری را مشخص کرده باشید (همزمان، با job پس‌زمینه، یا پذیرش ناسازگاری موقت).

الگوهای طراحی Schema

Bucket Pattern

به جای یک سند برای هر رویداد، رویدادهای یک بازه (مثلاً یک ساعت) را در یک سند گروه‌بندی می‌کنیم. تعداد اسناد و حجم ایندکس کم می‌شود و آماره‌های پیش‌محاسبه‌شده را هم می‌توان کنارش نگه داشت. کاربرد: IoT، متریک‌ها، time-series.

{
  sensorId: "S-12",
  start: ISODate("2026-11-07T10:00:00Z"),
  end:   ISODate("2026-11-07T10:59:59Z"),
  count: 60,
  sum:   1314.5,
  readings: [ { t: ISODate("2026-11-07T10:00:00Z"), v: 21.9 }, /* ... */ ]
}

// افزودن خوانش جدید به bucket جاری (با سقف 200 آیتم)
db.readings.updateOne(
  { sensorId: "S-12", count: { $lt: 200 }, start: ISODate("2026-11-07T10:00:00Z") },
  { $push: { readings: { t: new Date(), v: 22.1 } }, $inc: { count: 1, sum: 22.1 } },
  { upsert: true }
)

MongoDB از نسخه‌ی 5.0 Time Series Collection بومی دارد که bucket کردن را به‌صورت داخلی انجام می‌دهد: db.createCollection("metrics", { timeseries: { timeField: "ts", metaField: "sensor", granularity: "minutes" } }).

Computed Pattern

محاسبات پرتکرار (جمع، میانگین، شمارش) را هنگام نوشتن انجام بده و نتیجه را ذخیره کن، تا خواندن‌ها ارزان شوند. مثال: نگه‌داشتن ratingAvg و ratingCount در سند محصول به جای aggregate روی همه‌ی نظرها در هر بار نمایش.

db.products.updateOne(
  { _id: "P-100" },
  { $inc: { ratingCount: 1, ratingSum: 4 } }
)
// ratingAvg = ratingSum / ratingCount در زمان خواندن یا با یک $set جداگانه

Subset Pattern

وقتی سند بزرگ است ولی فقط بخش کوچکی از آن معمولاً نمایش داده می‌شود: زیرمجموعه‌ی پرکاربرد را embed کن و بقیه را در collection جدا نگه دار. مثال: ۱۰ نظر آخر محصول داخل سند محصول، همه‌ی نظرها در reviews.

// products
{ _id: "P-100", title: "Laptop X", recentReviews: [ /* 10 تای آخر */ ], reviewCount: 1832 }
// reviews
{ _id: ObjectId("..."), productId: "P-100", userId: 42, rating: 5, text: "..." }

Extended Reference Pattern

به جای فقط ذخیره‌ی شناسه، فیلدهای پرکاربرد سند مرجع را هم کپی کن تا join حذف شود. مثال: در سفارش، علاوه بر customerId، نام و آدرس ارسال را هم نگه دار. مزیت اضافه: آدرس سفارش باید همان «آدرس در زمان سفارش» بماند، حتی اگر کاربر بعداً آدرسش را عوض کند (snapshot).

{
  _id: 1001,
  customer: { _id: 42, name: "Sara Ahmadi", phone: "0912..." },   // extended reference
  shippingAddress: { city: "Tehran", street: "..." },             // snapshot
  items: [ { sku: "A12", title: "Laptop X", price: 1200, qty: 1 } ]
}

الگوهای دیگر که خوب است بشناسید

Outlier
اکثر اسناد کوچک‌اند ولی چند سند استثنایی (مثلاً کتاب پرفروش با میلیون‌ها خریدار) بزرگ می‌شوند؛ برای آن‌ها flag hasOverflow و سندهای سرریز جدا.
Attribute
ویژگی‌های متغیر را به آرایه‌ی [{k, v}] تبدیل کن تا با یک ایندکس { "attrs.k": 1, "attrs.v": 1 } قابل جست‌وجو باشند.
Schema Versioning
فیلد schemaVersion در سند؛ برنامه هر دو نسخه را می‌فهمد و مهاجرت تدریجی انجام می‌شود.
Polymorphic
اسناد با شکل‌های متفاوت ولی هدف مشترک در یک collection (مثلاً انواع محصول) با فیلد type.
Tree
نمایش سلسله‌مراتب با parent reference، child references، ancestors array یا materialized path.

                       (replicate oplog)      (replicate oplog)
            ◄─────── heartbeat هر ۲ ثانیه بین اعضا ───────►
  • Primary: تنها عضوی که نوشتن را می‌پذیرد. همه‌ی تغییرات را در oplog ثبت می‌کند.
  • Secondary: oplog را از primary (یا عضو دیگر) کپی و به‌صورت ناهمگام (async) اعمال می‌کند.
  • Arbiter: فقط در رأی‌گیری شرکت می‌کند و داده ندارد (توصیه می‌شود تا جای ممکن به جای arbiter از secondary داده‌دار استفاده شود).
  • عضوهای خاص: hidden (برای backup/گزارش)، delayed (با تأخیر عمدی برای بازیابی از خطای انسانی)، priority: 0 (هرگز primary نمی‌شود).
  • تعداد اعضا: حداکثر ۵۰ عضو که حداکثر ۷ تای آن‌ها رأی دارند. تعداد اعضای رأی‌دهنده را فرد بگیرید (معمولاً ۳ یا ۵).

Election (انتخاب Primary)

  1. اعضا با heartbeat وضعیت هم را چک می‌کنند.
  2. اگر primary بیش از electionTimeoutMillis (پیش‌فرض ۱۰ ثانیه) در دسترس نباشد، یک secondary واجد شرایط کاندید می‌شود.
  3. برای برنده شدن، کاندید باید رأی اکثریت (majority) اعضای رأی‌دهنده را بگیرد؛ عضوی که oplog به‌روزتر و priority بالاتر دارد شانس بیشتری دارد.
  4. در طول انتخابات (معمولاً چند ثانیه) نوشتن ممکن نیست؛ driverها با retryable writes این را تا حدی پنهان می‌کنند.

چرا اکثریت؟ برای جلوگیری از split-brain. در partition شبکه، فقط بخشی که اکثریت را دارد می‌تواند primary داشته باشد. با ۳ عضو، از دست رفتن ۱ عضو قابل تحمل است؛ با ۵ عضو، ۲ عضو. به همین دلیل replica set دو عضوی (بدون arbiter) تحمل خطا ندارد.

Rollback: اگر primary قدیمی نوشته‌هایی را پذیرفته باشد که هنوز به اکثریت نرسیده و سپس از کار بیفتد، بعد از برگشت آن نوشته‌ها rollback می‌شوند. با w: "majority" نوشته‌ای که تأیید شده rollback نمی‌شود.

Read Preference

مشخص می‌کند خواندن از کدام عضو انجام شود:

  • primary (پیش‌فرض): همیشه از primary؛ به‌روزترین داده.
  • primaryPreferred: primary، و اگر نبود secondary.
  • secondary / secondaryPreferred: کاهش بار primary؛ ولی داده ممکن است stale باشد (replication lag).
  • nearest: کمترین latency شبکه (مناسب استقرار چندمنطقه‌ای).

خواندن از secondary برای «مقیاس دادن خواندن» راه‌حل اصلی نیست، چون همه‌ی اعضا همان بار نوشتن را هم دارند. کاربرد درستش: گزارش‌گیری سنگین روی عضو hidden/analytics، یا کاهش latency در مناطق جغرافیایی دور، در جایی که داده‌ی کمی قدیمی قابل قبول است.

Causal Consistency: با session سببی (causally consistent session) به همراه readConcern: "majority" و writeConcern: "majority"، تضمین می‌شود کاربر نوشته‌ی خودش را بخواند (read-your-own-writes) حتی اگر از secondary بخواند.

Sharding

Sharding روش MongoDB برای مقیاس افقی است: داده‌ی یک collection بر اساس shard key بین چند shard تقسیم می‌شود. هر shard خودش یک replica set است.

          App + Driver
               │
        ┌──────┴──────┐
        │   mongos    │  ◄── router: کوئری را به shardهای درست هدایت می‌کند
        └──────┬──────┘
               │      ┌─────────────────────────┐
               ├─────►│ Config Servers (RS)     │ ◄── metadata: کدام chunk کجاست
               │      └─────────────────────────┘
      ┌────────┼─────────┐
      ▼        ▼         ▼
   Shard A   Shard B   Shard C        (هر کدام یک Replica Set)
   chunks    chunks    chunks
   [min,k1)  [k1,k2)   [k2,max)
  • mongos: روتر بی‌حالت؛ برنامه به آن وصل می‌شود.
  • Config servers: replica setی که متادیتای cluster و نگاشت chunk به shard را نگه می‌دارد.
  • Chunk: بازه‌ای پیوسته از مقادیر shard key. Balancer در پس‌زمینه chunkها را بین shardها جابه‌جا می‌کند تا توزیع داده متعادل بماند.

Ranged در برابر Hashed

Ranged Sharding

  • chunkها بازه‌های پیوسته از مقدار کلید هستند.
  • کوئری بازه‌ای روی shard key targeted است (فقط به shardهای لازم می‌رود).
  • خطر: کلید یکنواخت افزایشی (زمان، ObjectId، auto-increment) → همه‌ی insertها به آخرین chunk → hot shard.

Hashed Sharding

  • hash مقدار کلید مبنای توزیع است.
  • توزیع یکنواخت نوشتن حتی با کلید افزایشی.
  • عیب: کوئری بازه‌ای روی کلید به همه‌ی shardها پخش می‌شود (scatter-gather).

انتخاب Shard Key (مهم‌ترین تصمیم)

ویژگی‌های کلید خوب:

  1. Cardinality بالا: تعداد مقادیر متمایز زیاد باشد؛ کلیدی مثل country با ۲۰۰ مقدار حداکثر ۲۰۰ chunk قابل تقسیم دارد و chunkهای غیرقابل تقسیم (jumbo) ایجاد می‌کند.
  2. Frequency پایین: یک مقدار خاص (مثلاً یک مشتری بسیار بزرگ) بخش عمده‌ی داده را نداشته باشد.
  3. تغییر غیریکنواخت (non-monotonic): تا نوشتن‌ها پخش شوند.
  4. هم‌خوانی با کوئری‌ها: اکثر کوئری‌های پرتکرار شامل shard key باشند تا targeted باشند نه broadcast.
sh.enableSharding("shop")
sh.shardCollection("shop.orders", { customerId: 1, createdAt: 1 })   // ranged، ترکیبی
sh.shardCollection("shop.events", { deviceId: "hashed" })            // hashed
sh.status()

مثال پاسخ: برای collection سفارش‌ها در یک SaaS چندمستأجره، کلید { tenantId: 1, _id: 1 } انتخاب خوبی است: کوئری‌ها تقریباً همیشه tenantId دارند (targeted)، و جزء دوم cardinality را بالا می‌برد تا داده‌ی یک tenant بزرگ هم قابل تقسیم باشد. کلید { createdAt: 1 } انتخاب بدی است (hot shard).

تغییر shard key در گذشته تقریباً غیرممکن بود؛ نسخه‌های جدید امکان refineCollectionShardKey (افزودن پسوند به کلید، از 4.4) و resharding آنلاین (از 5.0) را دارند، ولی همچنان عملیات سنگینی است. پس از ابتدا درست انتخاب کنید.

قبل از sharding مطمئن شوید واقعاً لازم است: ایندکس‌گذاری درست، طراحی Schema، و مقیاس عمودی معمولاً تا حجم‌های بزرگ کافی‌اند. Sharding پیچیدگی عملیاتی (mongos، config server، balancer، backup) اضافه می‌کند.

تراکنش‌ها و CAP

اتمیک بودن تک‌سندی

هر عملیات نوشتن روی یک سند اتمیک است، حتی اگر چند فیلد و آرایه‌ی تودرتو را تغییر دهد. با طراحی مناسب (embedding) بسیاری از نیازهای تراکنشی بدون تراکنش چندسندی حل می‌شوند.

// کم کردن موجودی فقط اگر کافی باشد — اتمیک و بدون race condition
db.products.updateOne(
  { _id: "P-100", stock: { $gte: 2 } },
  { $inc: { stock: -2 } }
)
// اگر modifiedCount == 0 بود یعنی موجودی کافی نبوده

تراکنش‌های چندسندی (Multi-document Transactions)

  • از نسخه‌ی 4.0 روی replica set و از 4.2 روی sharded cluster.
  • ویژگی‌های ACID با isolation از نوع snapshot.
  • نیاز به replica set دارد (روی standalone کار نمی‌کند؛ برای توسعه‌ی محلی هم یک replica set تک‌عضوی بسازید).
  • محدودیت زمانی پیش‌فرض اجرای تراکنش ۶۰ ثانیه است؛ تراکنش طولانی lock و فشار حافظه ایجاد می‌کند.
  • در تعارض نوشتن (write conflict) خطای موقت TransientTransactionError برمی‌گردد و باید retry شود؛ API withTransaction این retry را انجام می‌دهد.
const session = db.getMongo().startSession();
session.withTransaction(() => {
  const accounts = session.getDatabase("bank").accounts;
  accounts.updateOne({ _id: "A", balance: { $gte: 100 } }, { $inc: { balance: -100 } });
  accounts.updateOne({ _id: "B" }, { $inc: { balance: 100 } });
}, { readConcern: { level: "snapshot" }, writeConcern: { w: "majority" } });
session.endSession();

دیدگاه درست برای پاسخ: تراکنش چندسندی در MongoDB وجود دارد ولی ابزار اصلی نیست. هزینه‌ی کارایی بیشتری نسبت به نوشتن تک‌سندی دارد. اگر طراحی شما در اکثر عملیات به تراکنش چندسندی نیاز دارد، یا Schema را بازبینی کنید یا شاید RDBMS انتخاب مناسب‌تری باشد.

CAP و MongoDB

قضیه‌ی CAP می‌گوید در یک سیستم توزیع‌شده، هنگام Partition شبکه، باید بین Consistency (همه یک داده‌ی یکسان و آخرین را ببینند) و Availability (هر درخواست پاسخ بگیرد) یکی را انتخاب کرد.

  • MongoDB در پیکربندی پیش‌فرض (نوشتن فقط روی primary، خواندن از primary) معمولاً CP در نظر گرفته می‌شود: هنگام partition، بخشی که اکثریت ندارد primary ندارد و نوشتن را رد می‌کند.
  • با تنظیم read preference به secondary و read concern local، به سمت دسترس‌پذیری بیشتر و سازگاری ضعیف‌تر (eventual) می‌رود. یعنی MongoDB tunable consistency دارد.
  • مدل PACELC دقیق‌تر است: حتی بدون partition (Else) بین Latency و Consistency trade-off داریم؛ مثلاً w: 1 در برابر w: "majority".

تعادل معمولw: "majority"، خواندن از primary با local
حداکثر سرعت/دسترس‌پذیریw: 1، readPreference: nearest، readConcern: local

سوالات تشریحی

MongoDB را تعریف کنید و مدل سندی آن را با مدل رابطه‌ای مقایسه کنید.

تعریف: MongoDB یک پایگاه داده‌ی NoSQL سندمحور است که داده را در قالب اسناد BSON (JSON باینری نوع‌دار) درون Collectionها ذخیره می‌کند. هر سند می‌تواند شیء تودرتو و آرایه داشته باشد و اسناد یک Collection لازم نیست Schema یکسان داشته باشند.

مقایسه با مدل رابطه‌ای:

  • ساختار: RDBMS جدول/سطر/ستون با Schema سخت دارد؛ MongoDB Collection/Document با Schema انعطاف‌پذیر (و اعتبارسنجی اختیاری $jsonSchema).
  • روابط: در RDBMS با نرمال‌سازی و FK و JOIN؛ در MongoDB با embedding (داده‌ی مرتبط داخل سند) یا referencing و $lookup.
  • رویکرد طراحی: RDBMS «اول داده، بعد کوئری»؛ MongoDB «اول الگوی دسترسی، بعد Schema».
  • تراکنش: RDBMS تراکنش چندجدولی را ارزان و بومی دارد؛ در MongoDB نوشتن تک‌سندی اتمیک است و تراکنش چندسندی (از 4.0) هزینه‌ی بیشتری دارد.
  • مقیاس: MongoDB Sharding بومی برای مقیاس افقی دارد.

جمع‌بندی: مدل سندی برای داده‌ی سلسله‌مراتبی، Schema متغیر و حجم بالای خواندن/نوشتن موجودیت‌های مستقل مناسب است؛ مدل رابطه‌ای برای روابط پیچیده، یکپارچگی قوی بین موجودیت‌ها و گزارش‌گیری ad-hoc.

در چه شرایطی استفاده از MongoDB را توصیه نمی‌کنید؟ با مثال توضیح دهید.
  • سیستم‌های مالی و حسابداری: انتقال وجه، دفتر کل و موجودی انبار به تراکنش‌های متعدد چندموجودیتی و Constraintهای سخت نیاز دارند. RDBMS این را بومی، ارزان و با ابزارهای بالغ فراهم می‌کند.
  • روابط پیچیده‌ی M:N با کوئری‌های ad-hoc: مثلاً ERP یا سیستم آموزشی با گزارش‌های متنوع که JOINهای زیادی لازم دارند. $lookup پرتکرار نشانه‌ی انتخاب اشتباه است.
  • نیاز به گزارش‌گیری BI با SQL: ابزارها و تیم‌های تحلیل معمولاً SQL می‌خواهند.
  • Schema پایدار و کاملاً رابطه‌ای: انعطاف Schema مزیتی ندارد و فقط Constraintهای دیتابیس (FK، CHECK) را از دست می‌دهید.
  • حجم کوچک و تیم آشنا با SQL: پیچیدگی عملیاتی (replica set، طراحی بر اساس کوئری) توجیه ندارد.

نکته: «NoSQL سریع‌تر است» به‌تنهایی دلیل نیست. سرعت از طراحی درست بر اساس الگوی دسترسی و ایندکس می‌آید. در بسیاری از سیستم‌ها ترکیب این دو (Polyglot Persistence) بهترین پاسخ است: داده‌ی تراکنشی در PostgreSQL/MySQL و لاگ/رویداد/کاتالوگ متغیر در MongoDB.

Embedding و Referencing را مقایسه کنید. معیارهای انتخاب بین این دو چیست؟

Embedding: داده‌ی مرتبط داخل سند والد قرار می‌گیرد (مثلاً آدرس‌ها داخل کاربر). Referencing: داده در collection جدا و با شناسه به هم مرتبط می‌شوند (مثلاً userId در سفارش).

معیارها:

  • الگوی خواندن: اگر همیشه با هم خوانده می‌شوند → embed. اگر زیرداده مستقلاً کوئری می‌شود → reference.
  • کاردینالیتی: one-to-few → embed؛ one-to-many → آرایه‌ی ref؛ one-to-squillions → ref در فرزند.
  • رشد: آرایه‌ی بی‌حد (unbounded) را embed نکنید (سقف ۱۶MB و کندی).
  • نرخ تغییر داده‌ی تکراری: اگر داده‌ی کپی‌شده زیاد عوض می‌شود، reference تا به‌روزرسانی در چند جا لازم نشود.
  • اتمیک بودن: embed به‌روزرسانی اتمیک بدون تراکنش می‌دهد.
  • چرخه‌ی حیات: اگر فرزند بدون والد معنا ندارد (آیتم‌های سفارش)، embed طبیعی است.
// سفارش: آیتم‌ها embed (همیشه با سفارش خوانده می‌شوند، محدودند، snapshot قیمت)
{ _id: 1, customerId: 42, items: [ { sku: "A1", price: 10, qty: 2 } ] }
// کاربر ↔ سفارش‌ها: reference (بی‌حد و مستقل)

حالت میانی: الگوهای Extended Reference و Subset، یعنی کپی کردن بخش پرکاربرد و ارجاع به بقیه.

ObjectId چیست، از چه بخش‌هایی تشکیل شده و چه مزایا و محدودیت‌هایی دارد؟

تعریف: نوع پیش‌فرض _id در MongoDB؛ یک مقدار ۱۲ بایتی که driver در سمت client می‌سازد.

  • ۴ بایت: timestamp (ثانیه از Unix epoch)
  • ۵ بایت: مقدار تصادفی یکتا برای هر ماشین/پروسس
  • ۳ بایت: شمارنده‌ی افزایشی

مزایا:

  • تولید بدون هماهنگی مرکزی → مناسب سیستم توزیع‌شده و درج سریع (برخلاف auto-increment که نیاز به یک نقطه‌ی مرکزی دارد).
  • تقریباً مرتب بر اساس زمان؛ sort بر اساس _id ≈ ترتیب ایجاد، و زمان ایجاد قابل استخراج است.
  • فشرده‌تر از UUID رشته‌ای (۱۲ بایت در برابر ۳۶ کاراکتر).

محدودیت‌ها:

  • یکنواخت افزایشی → به‌عنوان ranged shard key باعث hot shard می‌شود.
  • دقت زمانی در حد ثانیه و ترتیب بین پروسس‌های مختلف در همان ثانیه تضمین نمی‌شود.
  • تا حدی قابل حدس است؛ نباید جای توکن امنیتی استفاده شود.
قاعده‌ی ESR در طراحی ایندکس ترکیبی چیست؟ برای کوئری زیر ایندکس مناسب طراحی کنید: find({status: "paid", total: {$gt: 100}}).sort({createdAt: -1})

تعریف: ESR مخفف Equality → Sort → Range است؛ ترتیب پیشنهادی فیلدها در ایندکس ترکیبی.

  • Equality اول: شرط برابری ایندکس را به یک بازه‌ی پیوسته محدود می‌کند.
  • Sort دوم: در آن بازه، کلیدها از قبل بر اساس فیلد sort مرتب‌اند؛ پس sort در حافظه حذف می‌شود.
  • Range آخر: شرط بازه‌ای کلیدها را فیلتر می‌کند بدون اینکه ترتیب را بشکند.

پاسخ:

db.orders.createIndex({ status: 1, createdAt: -1, total: 1 })

اگر { status: 1, total: 1, createdAt: -1 } بسازیم، اسناد با total بالاتر از ۱۰۰ در چند زیر‌بازه‌ی جدا پخش‌اند و خروجی بر اساس createdAt مرتب نیست؛ در explain یک stage SORT (در حافظه) می‌بینیم که با داده‌ی بزرگ کند است و محدودیت حافظه دارد.

Trade-off: در ترتیب ESR ممکن است کلیدهای بیشتری بررسی شوند (range فیلتر نهایی است)، ولی معمولاً حذف sort در حافظه و امکان استفاده‌ی مؤثر از limit این را جبران می‌کند. همیشه با explain("executionStats") تأیید کنید.

سناریو: یک صفحه‌ی لیست سفارش‌ها در production ناگهان کند شده است. مراحل عیب‌یابی شما در MongoDB چیست؟
  1. شناسایی کوئری: لاگ کوئری‌های کند (slow query log، پیش‌فرض بالای ۱۰۰ms) یا Profiler (db.setProfilingLevel(1, {slowms: 100})) و db.currentOp() برای کوئری‌های در حال اجرا. در Laravel هم می‌توان کوئری‌ها را لاگ کرد.
  2. تحلیل با explain: .explain("executionStats") و بررسی:
    • وجود COLLSCAN به جای IXSCAN؛
    • نسبت totalDocsExamined به nReturned؛
    • وجود stage SORT در حافظه.
  3. رفع: ساخت/اصلاح ایندکس ترکیبی طبق ESR؛ حذف regex بدون anchor؛ جایگزینی skip بزرگ با keyset pagination؛ projection برای کاهش حجم؛ بررسی رشد ناگهانی اسناد (آرایه‌ی بی‌حد).
  4. بررسی منابع: آیا working set در RAM جا می‌شود؟ (cache eviction، page fault)؛ replication lag؛ تعداد اتصالات؛ ایندکسی که اخیراً حذف شده یا build در حال انجام.
  5. بررسی تغییرات اخیر: deploy جدید که شکل کوئری را عوض کرده (فیلد جدید در فیلتر، sort متفاوت)، یا رشد داده که plan cache را تغییر داده.
  6. تأیید: بعد از اصلاح دوباره explain و مانیتور latency (p95/p99).

نکته: ساخت ایندکس روی collection بزرگ در production بار ایجاد می‌کند؛ در زمان کم‌ترافیک یا به‌صورت rolling روی اعضای replica set انجام شود.

Aggregation Pipeline چیست؟ یک pipeline بنویسید که ۱۰ مشتری برتر از نظر مجموع خرید در ۳۰ روز گذشته را همراه با نام آن‌ها برگرداند.

تعریف: چارچوب پردازش داده در MongoDB که اسناد را از دنباله‌ای از stageها عبور می‌دهد؛ هر stage خروجی قبلی را تبدیل می‌کند (فیلتر، گروه‌بندی، join، تغییر شکل). معادل ترکیب WHERE/GROUP BY/JOIN/ORDER BY در SQL است و روی سرور اجرا می‌شود.

const since = new Date(Date.now() - 30 * 24 * 3600 * 1000);
db.orders.aggregate([
  { $match: { status: "paid", createdAt: { $gte: since } } },   // از ایندکس استفاده می‌کند
  { $group: { _id: "$customerId", spent: { $sum: "$total" }, orders: { $sum: 1 } } },
  { $sort: { spent: -1 } },
  { $limit: 10 },                                                // قبل از lookup!
  { $lookup: { from: "customers", localField: "_id", foreignField: "_id", as: "c" } },
  { $unwind: "$c" },
  { $project: { _id: 0, customerId: "$_id", name: "$c.name", spent: 1, orders: 1 } }
])

نکات طراحی:

  • $match در ابتدا تا از ایندکس { status: 1, createdAt: 1 } استفاده و حجم داده کم شود.
  • $limit قبل از $lookup، تا join فقط برای ۱۰ سند انجام شود، نه برای همه‌ی مشتریان.
  • اگر این گزارش پرتکرار است، الگوی Computed یا materialized view با $merge در یک job زمان‌بندی‌شده بهتر از اجرای هر بار است.
Replica Set را توضیح دهید. فرایند election چگونه است و چرا تعداد اعضا را فرد می‌گیرند؟

تعریف: گروهی از نمونه‌های mongod با داده‌ی یکسان؛ یک primary که همه‌ی نوشتن‌ها را می‌پذیرد و چند secondary که با کپی و اعمال oplog هم‌گام می‌شوند. هدف: High Availability، افزونگی داده و امکان خواندن از secondary یا backup بدون فشار به primary.

Election:

  • اعضا هر ۲ ثانیه heartbeat می‌فرستند.
  • اگر primary برای مدت electionTimeoutMillis (پیش‌فرض ۱۰ ثانیه) پاسخ ندهد، یک secondary واجد شرایط خود را کاندید می‌کند.
  • کاندیدی که رأی اکثریت اعضای رأی‌دهنده را بگیرد primary می‌شود؛ oplog به‌روزتر و priority بالاتر مؤثرند.
  • در این فاصله نوشتن ممکن نیست؛ retryable writes در driver کمک می‌کند.

چرا فرد؟ شرط اکثریت از split-brain جلوگیری می‌کند. با ۳ عضو اکثریت ۲ است و از کار افتادن ۱ عضو قابل تحمل است؛ با ۴ عضو اکثریت ۳ است و باز فقط ۱ عضو قابل تحمل است. پس عضو چهارم تحمل خطا را بالا نمی‌برد و فقط هزینه دارد. اگر بخش اقلیت partition شود، primary آن بخش خودش step down می‌کند.

نکته: اگر عضو زوج لازم است (مثلاً به دلیل دیتاسنتر)، یکی را votes: 0 می‌کنند یا (با احتیاط) arbiter اضافه می‌کنند.

Write Concern و Read Concern را تعریف کنید. چرا w: "majority" مهم است؟

Write Concern: سطح تأییدی که driver قبل از اعلام موفقیت نوشتن انتظار دارد: w: 0 (بدون تأیید)، w: 1 (فقط primary)، w: "majority" (اکثریت اعضا)، به همراه j: true (ثبت در journal) و wtimeout.

Read Concern: سطح سازگاری/پایداری داده‌ی خوانده‌شده: local (آخرین داده‌ی همان عضو، شاید rollback شود)، majority (فقط داده‌ی تأییدشده توسط اکثریت)، linearizable (قوی‌ترین، فقط primary)، snapshot (برای تراکنش)، available.

چرا majority؟ با w: 1 اگر primary بعد از تأیید نوشتن و قبل از replicate شدن از کار بیفتد، secondary جدید آن نوشته را ندارد و وقتی primary قدیمی برگردد آن نوشته rollback می‌شود؛ یعنی کاربر «موفق» دیده ولی داده از دست رفته. با w: "majority" نوشته روی اکثریت است و هر primary جدید حتماً آن را دارد.

Trade-off: majority تأخیر نوشتن را به اندازه‌ی رفت‌وبرگشت تا secondaryها بالا می‌برد. برای داده‌ی حیاتی (پرداخت) majority، برای داده‌ی کم‌اهمیت پرحجم (لاگ کلیک) شاید w: 1 کافی باشد. در نسخه‌های جدید (از 5.0) majority پیش‌فرض ضمنی اغلب پیکربندی‌هاست.

سناریو: کاربر پروفایلش را ویرایش می‌کند، ولی بلافاصله بعد از redirect، اطلاعات قدیمی را می‌بیند. تنظیمات: readPreference=secondaryPreferred. علت و راه‌حل چیست؟

علت: نوشتن روی primary انجام شده، ولی خواندن بعدی از یک secondary انجام می‌شود که هنوز oplog را اعمال نکرده است (replication lag). این نقض تضمین read-your-own-writes است؛ مدل eventual consistency.

راه‌حل‌ها:

  • خواندن از primary برای داده‌هایی که کاربر خودش تغییر داده است (ساده‌ترین؛ read preference پیش‌فرض primary است و فقط برای کوئری‌های گزارشی secondary انتخاب شود).
  • Causally consistent session با readConcern: "majority" و writeConcern: "majority"؛ driver تضمین می‌کند خواندن بعدی در همان session حداقل نوشته‌ی قبلی را ببیند.
  • بعد از ویرایش، داده‌ی جدید را مستقیماً از نتیجه‌ی findOneAndUpdate با returnDocument: "after" نمایش دهید.
  • اگر cache (مثلاً Redis) دارید، آن را در زمان نوشتن invalidate کنید؛ گاهی مقصر اصلی cache است نه replication.

نکته: خواندن از secondary برای افزایش ظرفیت خواندن راه‌حل اصلی نیست، چون secondaryها همان بار نوشتن را هم دارند؛ برای مقیاس، ایندکس، cache یا sharding مناسب‌ترند.

معیارهای انتخاب Shard Key را توضیح دهید. چرا createdAt یا ObjectId انتخاب بدی برای ranged shard key است؟

Shard key فیلد(هایی) است که تعیین می‌کند هر سند در کدام chunk و در نتیجه کدام shard قرار بگیرد.

معیارها:

  • Cardinality بالا: تعداد مقادیر متمایز زیاد تا داده قابل تقسیم به chunkهای زیاد باشد.
  • Frequency پایین: هیچ مقداری بخش عمده‌ی داده را نداشته باشد (وگرنه jumbo chunk).
  • عدم یکنواختی افزایشی: تا نوشتن‌ها پخش شوند.
  • پشتیبانی از کوئری‌ها: کوئری‌های پرتکرار شامل shard key باشند تا mongos آن‌ها را فقط به shard مربوطه بفرستد (targeted)، نه به همه (scatter-gather).

مشکل createdAt/ObjectId: مقادیر همیشه افزایشی‌اند، پس هر سند جدید در بازه‌ی [آخرین مقدار, maxKey) قرار می‌گیرد، یعنی آخرین chunk روی یک shard. همه‌ی نوشتن‌ها به همان shard می‌رود (hot shard) و balancer مدام باید chunk جابه‌جا کند؛ مقیاس افقی نوشتن عملاً از بین می‌رود.

راه‌حل‌ها: hashed shard key ({ _id: "hashed" }) برای پخش یکنواخت (به قیمت scatter شدن کوئری‌های بازه‌ای)، یا کلید ترکیبی مثل { customerId: 1, createdAt: 1 } که هم پخش‌کننده است و هم کوئری «سفارش‌های یک مشتری در بازه‌ی زمانی» را targeted نگه می‌دارد.

کد زیر برای ذخیره‌ی کامنت‌های یک پست استفاده شده است. چه مشکلی دارد و چگونه اصلاحش می‌کنید؟ 
// هر کامنت جدید:
db.posts.updateOne(
  { _id: postId },
  { $push: { comments: { userId, userName, text, at: new Date() } } }
)
// نمایش پست: db.posts.findOne({ _id: postId })

مشکلات:

  • Unbounded array: پست پربازدید ممکن است ده‌ها هزار کامنت داشته باشد؛ سند به سقف ۱۶MB نزدیک و در نهایت نوشتن رد می‌شود.
  • هر بار خواندن پست، همه‌ی کامنت‌ها منتقل می‌شوند، در حالی که معمولاً ۱۰ تای اول نمایش داده می‌شود. مصرف RAM و شبکه بالا می‌رود.
  • هر $push روی سند بزرگ هزینه‌ی نوشتن و replication بیشتری دارد؛ نوشتن‌های هم‌زمان روی یک سند داغ با هم رقابت می‌کنند.
  • userName کپی شده؛ اگر کاربر نامش را عوض کند، کامنت‌های قدیمی ناهماهنگ‌اند (اگر عمدی نیست باید استراتژی به‌روزرسانی داشت).

اصلاح: collection جدای comments با reference به پست (one-to-squillions) و ایندکس، به‌علاوه‌ی الگوی Subset برای نمایش سریع:

db.comments.insertOne({ postId, userId, userName, text, at: new Date() })
db.comments.createIndex({ postId: 1, at: -1 })
db.posts.updateOne({ _id: postId }, {
  $push: { recentComments: { $each: [ { userId, userName, text, at: new Date() } ], $slice: -5 } },
  $inc:  { commentCount: 1 }       // Computed pattern
})
تراکنش‌های چندسندی در MongoDB چگونه کار می‌کنند و چه زمانی باید از آن‌ها استفاده کرد؟

تعریف: از نسخه‌ی 4.0 (replica set) و 4.2 (sharded cluster)، MongoDB تراکنش ACID روی چند سند و چند collection را پشتیبانی می‌کند. تراکنش در یک session اجرا می‌شود، isolation از نوع snapshot دارد و تا commit تغییرات برای دیگران قابل مشاهده نیست.

نکات فنی:

  • نیازمند replica set است (حتی تک‌عضوی برای توسعه).
  • محدودیت زمانی پیش‌فرض ۶۰ ثانیه؛ باید کوتاه باشد.
  • در write conflict خطای TransientTransactionError می‌آید؛ از withTransaction استفاده کنید که retry را خودکار انجام می‌دهد. منطق داخل تراکنش باید idempotent یا قابل تکرار باشد.
  • هزینه‌ی کارایی بیشتر از عملیات تک‌سندی دارد (lock، نگه‌داری snapshot، هماهنگی در sharded).

چه زمانی؟ وقتی یک عملیات تجاری واقعاً باید چند سند مستقل را هم‌زمان تغییر دهد و نمی‌توان با embedding آن را تک‌سندی کرد؛ مثل انتقال وجه بین دو حساب، یا ثبت سفارش و کم کردن موجودی در collection دیگر.

چه زمانی نه؟ وقتی با طراحی Schema می‌شود نیاز را حذف کرد. مثلاً به‌روزرسانی سفارش و آیتم‌هایش (embed) یا کاهش موجودی با شرط (updateOne({stock: {$gte: n}}, {$inc: {stock: -n}})) اتمیک است و تراکنش لازم ندارد. اگر بیشتر عملیات‌ها تراکنش چندسندی می‌خواهند، RDBMS احتمالاً مناسب‌تر است.

سناریو: برای ذخیره‌ی کدهای OTP که بعد از ۲ دقیقه منقضی می‌شوند و جلوگیری از ثبت دوباره‌ی یک سفارش (idempotency key) چه ایندکس‌هایی طراحی می‌کنید؟

OTP با TTL index:

db.otps.createIndex({ createdAt: 1 }, { expireAfterSeconds: 120 })
db.otps.createIndex({ phone: 1 })
db.otps.insertOne({ phone: "0912...", codeHash: "...", createdAt: new Date(), attempts: 0 })
  • TTL index روی فیلد Date؛ thread پس‌زمینه تقریباً هر ۶۰ ثانیه اسناد منقضی را حذف می‌کند. پس ممکن است سند تا حدود یک دقیقه بیشتر بماند؛ برای امنیت، در کد هم شرط createdAt > now - 120s را چک کنید.
  • یک روش دیگر: فیلد expireAt با expireAfterSeconds: 0 تا زمان انقضا برای هر سند جداگانه تنظیم شود.
  • کد را hash شده ذخیره کنید و تعداد تلاش را محدود کنید.

Idempotency key با unique index:

db.orders.createIndex({ idempotencyKey: 1 }, { unique: true })
  • کلاینت برای هر تلاش ثبت سفارش یک کلید یکتا می‌فرستد؛ درخواست تکراری (retry شبکه، دابل کلیک) با خطای E11000 duplicate key روبه‌رو می‌شود و ما سفارش موجود را برمی‌گردانیم.
  • این در برابر race condition امن است، چون یکتایی در سطح دیتابیس تضمین می‌شود، نه با «اول find بعد insert» در برنامه.
  • اگر می‌خواهید کلیدها بعد از مدتی پاک شوند، collection جدای idempotency با TTL بسازید.
کوئری زیر قرار است محصولاتی را برگرداند که «در انبار تهران موجودی بیش از ۱۰ دارند»، ولی نتایج اشتباه است. مشکل چیست؟ 
// سند: { name: "X", stock: [ { city: "Tehran", qty: 2 }, { city: "Tabriz", qty: 50 } ] }
db.products.find({ "stock.city": "Tehran", "stock.qty": { $gt: 10 } })

مشکل: وقتی روی آرایه‌ای از اسناد با dot notation چند شرط می‌گذاریم، MongoDB هر شرط را مستقل روی کل آرایه می‌سنجد: کافی است یک عنصر city=Tehran داشته باشد و عنصری دیگر qty>10. پس محصول X (تهران ۲، تبریز ۵۰) به‌اشتباه برمی‌گردد.

اصلاح: با $elemMatch تضمین می‌کنیم هر دو شرط روی یک عنصر برقرار باشند:

db.products.find({ stock: { $elemMatch: { city: "Tehran", qty: { $gt: 10 } } } })
db.products.createIndex({ "stock.city": 1, "stock.qty": 1 })   // multikey compound

نکته‌ی تکمیلی: برای برگرداندن فقط عنصر مطابق در خروجی می‌توان از projection { "stock.$": 1 } یا $filter در aggregation استفاده کرد. و $elemMatch برای شرط تکی لازم نیست؛ { "stock.city": "Tehran" } کافی است.

الگوهای Bucket، Computed و Extended Reference را با یک مثال برای هر کدام توضیح دهید.
  • Bucket: گروه‌بندی چند رویداد کوچک در یک سند بر اساس بازه‌ی زمانی یا تعداد. مثال: خوانش‌های دمای هر سنسور در هر ساعت در یک سند با آرایه‌ی readings و فیلدهای count و sum. مزیت: اسناد و کلیدهای ایندکس بسیار کمتر، و آمار پیش‌محاسبه. (Time Series Collection در 5.0+ همین را بومی انجام می‌دهد.)
  • Computed: محاسبه‌ی مقادیر پرتکرار در زمان نوشتن به جای زمان خواندن. مثال: ratingCount و ratingSum در سند محصول که با هر نظر جدید $inc می‌شوند؛ صفحه‌ی محصول بدون aggregate روی هزاران نظر میانگین را نشان می‌دهد. مناسب وقتی read ≫ write.
  • Extended Reference: علاوه بر شناسه، فیلدهای پرکاربرد سند مرجع هم کپی می‌شوند. مثال: سفارش شامل customer: {_id, name, phone} و آدرس ارسال است؛ نمایش سفارش بدون $lookup انجام می‌شود و آدرس، snapshot زمان سفارش باقی می‌ماند.

Trade-off مشترک: همه‌ی این الگوها خواندن را ارزان و نوشتن را کمی پیچیده‌تر می‌کنند و ممکن است داده‌ی تکراری یا تقریبی (eventually consistent) ایجاد کنند. پس فقط فیلدهای کم‌تغییر را کپی کنید و استراتژی همگام‌سازی (به‌روزرسانی دسته‌ای، job پس‌زمینه، Change Streams) را مشخص کنید.

MongoDB را از منظر قضیه‌ی CAP تحلیل کنید.

CAP: در یک سیستم توزیع‌شده، هنگام partition شبکه نمی‌توان هم‌زمان Consistency (همه آخرین داده را ببینند) و Availability (همه‌ی درخواست‌ها پاسخ موفق بگیرند) را داشت؛ تحمل partition در سیستم توزیع‌شده اجباری است، پس انتخاب بین C و A است.

MongoDB:

  • با پیکربندی پیش‌فرض (single primary، خواندن از primary، w: "majority") رفتار CP دارد: در partition، بخش اقلیت primary ندارد و نوشتن را رد می‌کند؛ در زمان election هم نوشتن موقتاً ممکن نیست.
  • سازگاری قابل تنظیم (tunable) است: با readPreference: secondary/nearest و readConcern: local خواندن در دسترس‌تر ولی ممکن است stale باشد (رفتار نزدیک به AP برای خواندن).
  • از دید PACELC: در حالت عادی هم بین latency و consistency انتخاب داریم؛ w: 1 سریع‌تر ولی در failover ممکن است داده rollback شود.

جمع‌بندی: برچسب CP یا AP برای کل محصول ساده‌سازی است؛ پاسخ دقیق این است که MongoDB به‌طور پیش‌فرض consistency را ترجیح می‌دهد و با write/read concern و read preference برای هر عملیات قابل تنظیم است.

چگونه در یک پروژه‌ی Laravel از MongoDB استفاده می‌کنید؟ نحوه‌ی تعریف مدل و یک رابطه‌ی embed را توضیح دهید.
  1. نصب افزونه‌ی PHP mongodb و پکیج رسمی composer require mongodb/laravel-mongodb.
  2. تعریف connection با 'driver' => 'mongodb'، dsn و database در config/database.php.
  3. مدل‌ها از MongoDB\Laravel\Eloquent\Model ارث می‌برند.
<?php
use MongoDB\Laravel\Eloquent\Model;

class Order extends Model
{
    protected $connection = 'mongodb';
    protected $table = 'orders';
    protected $fillable = ['customer_id', 'status', 'total'];

    public function items()
    {
        return $this->embedsMany(OrderItem::class);   // آرایه‌ی items داخل سند سفارش
    }
}

$order = Order::create(['customer_id' => 42, 'status' => 'pending', 'total' => 0]);
$order->items()->create(['sku' => 'A12', 'price' => 1200, 'qty' => 1]);
$paid = Order::where('status', 'paid')->where('total', '>', 100)->get();

نکات: Query Builder و Eloquent آشنا کار می‌کنند و به MQL ترجمه می‌شوند؛ برای aggregation پیچیده از Model::raw() استفاده می‌شود؛ روابط hasMany/belongsTo با reference و embedsOne/embedsMany با embedding پیاده می‌شوند؛ تراکنش با DB::connection('mongodb')->transaction() و نیازمند replica set است؛ ایندکس‌ها را در migration تعریف کنید. Validation دیتابیسی ندارید، پس FormRequest و در صورت نیاز $jsonSchema لازم است.

خلاصه برای مرور سریع

مبانی

  • Document store؛ ذخیره به‌صورت BSON (باینری، نوع‌دار: ObjectId، Date، Decimal128، Int64).
  • Database → Collection → Document → Field. ساخت تنبل با اولین insert.
  • _id اجباری، یکتا، ایندکس خودکار، تغییرناپذیر.
  • ObjectId = ۴ بایت زمان + ۵ بایت تصادفی + ۳ بایت شمارنده؛ تقریباً مرتب زمانی.
  • حداکثر اندازه‌ی سند ۱۶MB، عمق ۱۰۰؛ فایل بزرگ: GridFS یا S3.
  • نوشتن روی یک سند همیشه اتمیک است.

CRUD

  • insertOne/insertMany (ordered: false)
  • find(filter, projection).sort().skip().limit()
  • updateOne/updateMany با $set $unset $inc $push $addToSet $pull
  • upsert: true + $setOnInsert؛ هم‌زمانی → unique index.
  • replaceOne = جایگزینی کامل؛ findOneAndUpdate + returnDocument: "after".
  • $ / $[] / $[x] + arrayFilters برای عناصر آرایه.
  • $push + $each + $slice = آرایه‌ی با سقف.

کوئری

  • چند شرط = AND ضمنی؛ $or صریح.
  • آرایه‌ی اسناد با چند شرط روی یک عنصر → $elemMatch.
  • {f: null} = null یا ناموجود؛ $exists: false = فقط ناموجود.
  • regex فقط با ^ و بدون i از ایندکس بهره می‌برد.
  • صفحه‌بندی عمیق: keyset (_id > last) نه skip.
  • NoSQL injection: نوع ورودی را به string اجبار کنید.

ایندکس

  • انواع: single، compound، multikey، text (یکی)، TTL، unique، partial، sparse، hashed، wildcard.
  • قاعده‌ی prefix در compound.
  • ESR: Equality → Sort → Range.
  • Covered query: همه‌ی فیلدها در ایندکس، _id: 0.
  • explain: COLLSCAN بد، IXSCAN خوب، SORT در حافظه = هشدار؛ keys/docs examined ≈ nReturned.
  • TTL حدوداً هر ۶۰ ثانیه حذف می‌کند.

Aggregation

  • $match و $sort اول (ایندکس)؛ $project زود.
  • $group + $sum/$avg/$push/$addToSet.
  • $unwind آرایه را پخش می‌کند.
  • $lookup = LEFT JOIN؛ ایندکس روی foreignField؛ $limit قبلش.
  • $facet = چند pipeline روی یک ورودی (داده + شمارش + فیلترها).
  • حافظه‌ی هر stage ۱۰۰MB → allowDiskUse.
  • $merge/$out برای materialized view.

Schema

  • «آنچه با هم خوانده می‌شود، با هم ذخیره شود».
  • One-to-few → embed؛ one-to-many → آرایه‌ی ref؛ one-to-squillions → ref در فرزند.
  • Anti-pattern: آرایه‌ی بی‌حد، $lookup زیاد، collection‌های بیش از حد.
  • الگوها: Bucket، Computed، Subset، Extended Reference، Outlier، Attribute، Schema Versioning.

Replica Set

  • 1 primary + secondaryها؛ همگام‌سازی async با oplog.
  • Election با اکثریت؛ timeout پیش‌فرض ۱۰s؛ اعضای فرد (۳ یا ۵)؛ حداکثر ۷ رأی‌دهنده.
  • Write concern: 0، 1، majority، j: true.
  • Read concern: local، available، majority، linearizable، snapshot.
  • Read pref: primary (پیش‌فرض)، primaryPreferred، secondary، secondaryPreferred، nearest.
  • secondary = خطر داده‌ی stale؛ causal session برای read-your-writes.

Sharding

  • mongos (router) + config servers + shards (هر کدام RS).
  • Chunk = بازه‌ی shard key؛ balancer توزیع را متعادل می‌کند.
  • Ranged: کوئری بازه‌ای targeted، خطر hot shard. Hashed: پخش یکنواخت، بازه scatter-gather.
  • کلید خوب: cardinality بالا، frequency پایین، غیرافزایشی، در کوئری‌ها حاضر.

تراکنش و CAP

  • چندسندی: 4.0 (RS)، 4.2 (sharded)؛ snapshot؛ ۶۰ ثانیه؛ withTransaction + retry.
  • اول با طراحی Schema نیاز به تراکنش را حذف کنید.
  • CAP: پیش‌فرض CP؛ tunable با read/write concern.

Laravel

  • ext-mongodb + mongodb/laravel-mongodb.
  • 'driver' => 'mongodb'، مدل از MongoDB\Laravel\Eloquent\Model.
  • embedsMany/embedsOne، hasMany/belongsTo، push/pull، raw() برای aggregate.
  • Polyglot: تراکنشی در SQL، لاگ/کاتالوگ در Mongo.
