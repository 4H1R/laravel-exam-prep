Laravel — Architecture & Basics

معماری Laravel از چرخه عمر درخواست تا Service Container، و ابزارهای روزمره مثل Routing، Middleware، Controller، Validation، Blade، Session، احراز هویت و Migration؛ با تمرکز بر نسخه‌های ۱۱ و ۱۲ و تفاوت‌هایشان با نسخه‌های قدیمی‌تر.

Laravel و الگوی MVC

Laravel یک فریم‌ورک full-stack و متن‌باز PHP است که روی اجزای Symfony (مثل HttpFoundation، Console و Routing) و Composer ساخته شده است. هسته آن یک Service Container است و تقریباً همه اجزا (Router، Cache، Queue، Mail و…) به صورت سرویس‌هایی در این container ثبت می‌شوند. فلسفه Laravel «Convention over Configuration» و «Developer Experience» است: پیش‌فرض‌های معقول، API خوانا و ابزارهای آماده برای کارهای تکراری.

اما Laravel فقط MVC نیست. کنار این سه لایه، لایه‌های دیگری هم دارد که در طراحی خوب استفاده می‌شوند: Route (نگاشت URL به کد)، Middleware (فیلترهای HTTP)، Form Request (اعتبارسنجی و مجوز)، Policy (منطق دسترسی)، Job/Event/Listener (کار غیرهمزمان و decoupling)، API Resource (لایه تبدیل خروجی) و کلاس‌های Service/Action دلخواه برای منطق تجاری.

                                              │                 ▼
                                              │             Model (Eloquent) ──► DB

سوال کلاسیک: «منطق تجاری را کجا می‌نویسید؟» پاسخ خوب: نه در View و ترجیحاً نه در Controller. Controller باید Thin باشد: ورودی را از Form Request بگیرد، یک Service/Action را صدا بزند و پاسخ برگرداند. منطق مرتبط با یک موجودیت (scope، accessor، relation) در Model و منطق چندمرحله‌ای یا بین‌موجودیتی در Service/Action قرار می‌گیرد. هدف: تست‌پذیری و استفاده مجدد (مثلاً از همان Action در Controller، Command و Job).

ویژگی‌های کلیدی که باید بتوانید نام ببرید

  • Service Container و Dependency Injection خودکار با Reflection.
  • Eloquent ORM مبتنی بر Active Record (جزئیات در صفحه Eloquent).
  • Routing گویا، Route Model Binding، Middleware.
  • Blade به عنوان موتور قالب کامپایل‌شونده.
  • Artisan CLI، Migration، Seeder، Factory.
  • زیرسیستم‌های آماده: Queue، Event، Cache، Mail، Notification، Scheduler، Broadcasting (جزئیات در صفحه Laravel Deeper).
  • امنیت پیش‌فرض: CSRF، escape خروجی، hash رمز عبور، رمزنگاری cookie، محافظت از mass assignment.
  • تست‌پذیری: PHPUnit/Pest، HTTP tests، Fakeها.

نسخه‌ها: Laravel از نسخه ۹ به بعد هر سال یک نسخه major منتشر می‌کند (۱۱ در ۲۰۲۴ با PHP ≥ 8.2، ۱۲ در ۲۰۲۵). Laravel 12 عمدتاً یک «maintenance release» بود و ساختار اسکلت ۱۱ را حفظ کرد؛ تغییر اصلی‌اش starter kitهای جدید بود. بنابراین هرچه در این صفحه برای «Laravel 11+» گفته می‌شود برای ۱۲ هم صادق است.

چرخه عمر درخواست (Request Lifecycle)

فهم دقیق این مسیر هم برای debugging و هم برای پاسخ به سوالات تشریحی ضروری است. مراحل در Laravel 11+ به این ترتیب است:

  1. Web server (Nginx/Apache) همه درخواست‌ها را به public/index.php می‌فرستد (front controller).
  2. public/index.php: ثابت LARAVEL_START را تعریف می‌کند، اگر برنامه در maintenance mode باشد فایل storage/framework/maintenance.php را اجرا می‌کند، Composer autoloader را بار می‌کند و bootstrap/app.php را require می‌کند.
  3. bootstrap/app.php: یک نمونه از Illuminate\Foundation\Application (که خودش Service Container است) می‌سازد و routing، middleware و exception handling را پیکربندی می‌کند.
  4. $app->handleRequest(Request::capture()): درخواست از superglobalها به شیء Illuminate\Http\Request تبدیل می‌شود و HTTP Kernel از container resolve می‌شود.
  5. Bootstrapping کرنل: کرنل لیستی از bootstrapperها را اجرا می‌کند: بارگذاری .env (LoadEnvironmentVariables)، بارگذاری config (LoadConfiguration)، تنظیم error handling (HandleExceptions)، ثبت facadeها (RegisterFacades)، register کردن همه providerها (RegisterProviders) و سپس boot کردن آن‌ها (BootProviders).
  6. Global middleware: درخواست از طریق کلاس Pipeline از middlewareهای سراسری عبور می‌کند (مثل TrimStrings، ConvertEmptyStringsToNull، ValidatePostSize، PreventRequestsDuringMaintenance، HandleCors، TrustProxies).
  7. Router: route مطابق با متد و URI پیدا می‌شود (یا 404/405).
  8. Route middleware: middlewareهای گروه (مثلاً web: cookie encryption، session، CSRF، SubstituteBindings) و middlewareهای خود route اجرا می‌شوند. Route Model Binding در SubstituteBindings انجام می‌شود.
  9. Controller/Closure: container کلاس controller را می‌سازد و وابستگی‌های constructor و متد را تزریق می‌کند؛ Form Requestها در همین نقطه validate می‌شوند.
  10. تبدیل به Response: مقدار برگشتی به Response تبدیل می‌شود (رشته → HTML، آرایه/مدل/Collection → JsonResponse، View → رندر).
  11. مسیر برگشت: Response به ترتیب معکوس از middlewareها عبور می‌کند (بخش «after» هر middleware).
  12. ارسال: $response->send() هدرها و بدنه را می‌فرستد.
  13. Terminate: $kernel->terminate() متد terminate() middlewareهای terminable و callbackهای app()->terminating() را اجرا می‌کند. زیر PHP-FPM پاسخ قبل از این مرحله به کاربر flush شده است.

کد واقعی index.php در Laravel 11

<?php
use Illuminate\Foundation\Application;
use Illuminate\Http\Request;

define('LARAVEL_START', microtime(true));

// Determine if the application is in maintenance mode...
if (file_exists($maintenance = __DIR__.'/../storage/framework/maintenance.php')) {
    require $maintenance;
}

require __DIR__.'/../vendor/autoload.php';

/** @var Application $app */
$app = require_once __DIR__.'/../bootstrap/app.php';

$app->handleRequest(Request::capture());

در Laravel 10 و قبل

<?php
$app = require_once __DIR__.'/../bootstrap/app.php';

$kernel = $app->make(Illuminate\Contracts\Http\Kernel::class);

$response = $kernel->handle(
    $request = Illuminate\Http\Request::capture()
)->send();

$kernel->terminate($request, $response);

دو نکته که ممتحن دنبالش است: (۱) همه providerها ابتدا register و بعد همه boot می‌شوند؛ پس در boot می‌توان مطمئن بود سرویس‌های سایر providerها ثبت شده‌اند. (۲) Middlewareها یک پیاز (onion) می‌سازند: کد قبل از $next($request) در مسیر رفت و کد بعد از آن در مسیر برگشت اجرا می‌شود.

در اجرای عادی PHP-FPM، این چرخه برای هر درخواست از صفر تکرار می‌شود (share-nothing). به همین دلیل cache کردن config و route در production اهمیت دارد. در Octane برنامه یک‌بار boot شده و در حافظه می‌ماند (جزئیات در صفحه Laravel Deeper). درخواست‌های Console هم مسیری مشابه با Console Kernel دارند (artisan → $app->handleCommand()).

Container، Provider و Facade (مقدماتی)

این سه مفهوم ستون فقرات Laravel هستند. در این صفحه تعریف و کاربرد روزمره آن‌ها را می‌بینیم؛ جزئیات (singleton/scoped، contextual binding، deferred provider، درون‌کاوی facade) در صفحه Laravel Deeper آمده است.

Service Container

Service Container (یا IoC Container) ابزاری برای مدیریت وابستگی‌ها و تزریق آن‌ها (Dependency Injection) است. شما «دستور ساخت» یک سرویس را ثبت می‌کنید (binding) و هر جا آن سرویس لازم شد، container آن را می‌سازد. نکته قدرتمند auto-resolution است: اگر کلاسی به interface وابسته نباشد، container بدون هیچ ثبتی و با استفاده از Reflection وابستگی‌های constructor را تشخیص داده و به صورت بازگشتی می‌سازد.

<?php
// Auto-resolution: هیچ bindingی لازم نیست
class ReportController extends Controller
{
    public function __construct(private ReportService $reports) {}   // ساخته و تزریق می‌شود
}

// binding interface به پیاده‌سازی (در AppServiceProvider::register)
$this->app->bind(PaymentGateway::class, StripeGateway::class);
$this->app->singleton(CurrencyConverter::class, fn ($app) => new CurrencyConverter(
    config('services.fx.key')
));

// resolve دستی (ترجیحاً کم استفاده شود)
$gateway = app(PaymentGateway::class);
$gateway = app()->make(PaymentGateway::class);
$gateway = resolve(PaymentGateway::class);

Service Provider

Service Provider محل مرکزی bootstrap کردن برنامه و پکیج‌هاست: ثبت bindingها در container، ثبت event listenerها، middleware، routeها، view composerها و… هر provider دو متد اصلی دارد:

register()

  • فقط ثبت binding در container.
  • نباید از سرویس‌های دیگر استفاده کند؛ چون ممکن است هنوز ثبت نشده باشند.

boot()

  • بعد از register شدن همه providerها اجرا می‌شود.
  • جای مناسب برای Gate::define، RateLimiter::for، Model::preventLazyLoading، View::composer، Route::model، و… .
  • امکان type-hint وابستگی‌ها در امضای متد.
<?php
namespace App\Providers;

use Illuminate\Support\Facades\Gate;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->bind(PaymentGateway::class, StripeGateway::class);
    }

    public function boot(): void
    {
        Gate::define('access-admin', fn (User $user) => $user->is_admin);
    }
}

// bootstrap/providers.php  (Laravel 11+)
return [
    App\Providers\AppServiceProvider::class,
];

دستور php artisan make:provider BillingServiceProvider در Laravel 11 provider را خودکار به bootstrap/providers.php اضافه می‌کند. providerهای پکیج‌ها از طریق package auto-discovery (بخش extra.laravel در composer.json پکیج) ثبت می‌شوند.

Facade

Facade یک «رابط static» برای سرویس‌های داخل container است. Cache::get('key') در ظاهر static است، اما در واقع:

  1. کلاس Illuminate\Support\Facades\Cache متد get ندارد؛ پس متد جادویی __callStatic کلاس پایه Facade فراخوانی می‌شود.
  2. getFacadeAccessor() کلید سرویس را برمی‌گرداند (برای Cache رشته 'cache').
  3. Facade نمونه واقعی را از container resolve می‌کند (و آن را cache می‌کند).
  4. متد get روی همان شیء واقعی (CacheManager) صدا زده می‌شود.
<?php
// سه روش معادل برای استفاده از یک سرویس:
Cache::put('k', 'v', 60);                  // Facade
cache()->put('k', 'v', 60);                // helper
public function __construct(private \Illuminate\Contracts\Cache\Repository $cache) {} // DI

«آیا Facade همان static method است و تست‌پذیری را از بین می‌برد؟» خیر. Facade فقط یک proxy به شیء داخل container است؛ بنابراین می‌توان آن را در تست جایگزین کرد: Cache::shouldReceive('get')->andReturn(...) یا Mail::fake()، Queue::fake(). عیب واقعی Facade این است که وابستگی‌ها پنهان می‌شوند (در constructor دیده نمی‌شوند) و کلاس ممکن است بی‌صدا بیش از حد بزرگ شود.

پیکربندی، .env و محیط‌ها

Laravel پیکربندی را در دو لایه نگه می‌دارد:

  • .env: مقادیر وابسته به محیط و محرمانه (رمز دیتابیس، کلیدهای API، APP_KEY). این فایل نباید commit شود؛ .env.example به عنوان الگو commit می‌شود.
  • config/*.php: آرایه‌های PHP که ساختار پیکربندی را تعریف می‌کنند و مقادیرشان را با env('KEY', default) از محیط می‌خوانند.
<?php
// config/services.php
return [
    'payment' => [
        'key'     => env('PAYMENT_KEY'),
        'timeout' => (int) env('PAYMENT_TIMEOUT', 10),
    ],
];

// در کد برنامه — همیشه config() نه env()
$key = config('services.payment.key');
$timeout = config('services.payment.timeout', 5);   // مقدار پیش‌فرض
config(['app.locale' => 'fa']);                      // تنظیم در runtime (فقط برای همان درخواست)

چرا env() فقط در فایل‌های config؟

در production دستور php artisan config:cache همه فایل‌های config را یک‌بار اجرا کرده و نتیجه را در یک فایل PHP (bootstrap/cache/config.php) ذخیره می‌کند. وقتی config cache شده باشد، Laravel دیگر فایل .env را بارگذاری نمی‌کند؛ در نتیجه هر env() که خارج از فایل‌های config صدا زده شود null (یا مقدار پیش‌فرض) برمی‌گرداند — مگر اینکه متغیر به صورت واقعی در محیط سیستم‌عامل/سرور تعریف شده باشد. این باگ فقط در production ظاهر می‌شود و پیدا کردنش سخت است.

اشتباه رایج: if (env('APP_ENV') === 'production') در یک Controller یا Service. صحیح: app()->environment('production') یا App::isProduction() یا config('app.env').

Config caching و تغییرات .env

  • php artisan config:cache: ساخت cache؛ سرعت بارگذاری را بالا می‌برد چون به جای ده‌ها فایل، یک فایل خوانده می‌شود و .env parse نمی‌شود.
  • php artisan config:clear: حذف cache. اگر بعد از تغییر .env در production تغییری دیده نمی‌شود، علتش cache بودن config است؛ باید دوباره config:cache اجرا شود.
  • در محیط توسعه config را cache نکنید.

محیط‌ها و Debug mode

APP_ENV
نام محیط (local، testing، staging، production). با app()->environment(['local','staging']) بررسی می‌شود. هنگام اجرای تست، فایل .env.testing (در صورت وجود) و متغیرهای phpunit.xml استفاده می‌شوند.
APP_DEBUG

Route Model Binding و Rate Limiting

Route Model Binding یعنی Laravel به جای اینکه شناسه خام را به شما بدهد، خودش مدل متناظر را از دیتابیس واکشی کرده و تزریق می‌کند؛ اگر پیدا نشود، به طور خودکار 404 برمی‌گرداند. این کار در middleware SubstituteBindings (عضو گروه‌های web و api) انجام می‌شود.

Implicit binding

شرط: نام پارامتر route با نام متغیر type-hint شده یکسان باشد.

<?php
Route::get('/posts/{post}', function (Post $post) {   // {post} ⇔ $post
    return $post;          // معادل Post::findOrFail($id)
});

// کلید سفارشی در خود route
Route::get('/posts/{post:slug}', fn (Post $post) => $post);

// کلید سفارشی برای همه routeها — در مدل
class Post extends Model
{
    public function getRouteKeyName(): string
    {
        return 'slug';
    }
}

// شامل رکوردهای soft-deleted
Route::get('/users/{user}', ...)->withTrashed();

// رفتار سفارشی به جای 404
Route::get('/locations/{location:slug}', [LocationController::class, 'show'])
    ->missing(fn (Request $request) => redirect()->route('locations.index'));

Scoped binding

در routeهای تودرتو، معمولاً می‌خواهیم مدل فرزند حتماً متعلق به والد باشد (جلوگیری از دسترسی به post کاربر دیگر از طریق URL). وقتی برای فرزند کلید سفارشی تعیین شود، Laravel خودکار از رابطه والد استفاده می‌کند؛ در غیر این صورت scopeBindings() را صدا بزنید:

<?php
// $user->posts()->where('slug', ...)->firstOrFail()  — خودکار scoped
Route::get('/users/{user}/posts/{post:slug}', fn (User $user, Post $post) => $post);

Route::get('/users/{user}/posts/{post}', fn (User $user, Post $post) => $post)
    ->scopeBindings();   // Laravel رابطه posts را روی User حدس می‌زند

Explicit binding و منطق سفارشی

<?php
// AppServiceProvider::boot()
Route::model('member', User::class);    // پارامتر {member} → User

Route::bind('user', function (string $value) {
    return User::where('username', $value)->where('active', true)->firstOrFail();
});

// یا override در خود مدل
public function resolveRouteBinding($value, $field = null)
{
    return $this->where($field ?? 'id', $value)->where('tenant_id', tenant()->id)->firstOrFail();
}

Enumهای backed هم قابل bind هستند: Route::get('/categories/{category}', fn (Category $category) => ...) که Category یک enum با مقدار string است؛ مقدار نامعتبر به 404 می‌انجامد.

تفاوت‌ها به زبان امتحانی: Implicit = بر اساس قرارداد نام و type-hint، بدون پیکربندی. Explicit = نگاشت صریح پارامتر به مدل یا منطق resolve دلخواه با Route::model/Route::bind. Custom key = جستجو با ستونی غیر از کلید اصلی ({post:slug} یا getRouteKeyName). Scoped = محدود کردن فرزند به والد برای امنیت.

Route Model Binding جایگزین authorization نیست. اینکه {post} وجود دارد به این معنا نیست که کاربر فعلی مجاز به ویرایش آن است؛ باید Policy (can:update,post) هم اعمال شود.

Rate Limiting (مقدماتی)

محدودکننده‌ها با نام تعریف و با middleware throttle به route متصل می‌شوند. وقتی سقف رد شود، پاسخ 429 Too Many Requests با هدرهای Retry-After و X-RateLimit-* برمی‌گردد.

<?php
use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Support\Facades\RateLimiter;

// AppServiceProvider::boot()
RateLimiter::for('api', function (Request $request) {
    return Limit::perMinute(60)->by($request->user()?->id ?: $request->ip());
});

RateLimiter::for('login', fn (Request $request) => [
    Limit::perMinute(5)->by($request->input('email').'|'.$request->ip()),
]);

Route::middleware('throttle:api')->group(function () { /* ... */ });
Route::post('/login', ...)->middleware('throttle:login');
Route::get('/quick', ...)->middleware('throttle:10,1');   // ۱۰ درخواست در ۱ دقیقه

شمارنده‌ها در cache نگه داشته می‌شوند؛ پس در چند سرور باید cache مشترک (Redis) باشد. جزئیات بیشتر در صفحه Laravel Deeper.

Middleware

Middleware یک لایه فیلتر روی درخواست HTTP است که قبل و/یا بعد از رسیدن درخواست به controller اجرا می‌شود؛ پیاده‌سازی الگوی Chain of Responsibility / Pipeline. کاربردها: احراز هویت، CSRF، CORS، تنظیم locale، لاگ، افزودن header، محدودیت نرخ.

php artisan make:middleware EnsureUserHasRole   # app/Http/Middleware/EnsureUserHasRole.php

Before، After و پارامتر

<?php
namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class EnsureUserHasRole
{
    // پارامترها بعد از $next می‌آیند:  ->middleware('role:editor,admin')
    public function handle(Request $request, Closure $next, string ...$roles): Response
    {
        // ---- BEFORE: قبل از controller
        if (! $request->user() || ! in_array($request->user()->role, $roles, true)) {
            abort(403);               // short-circuit: $next صدا زده نمی‌شود
        }

        $response = $next($request);  // عبور به لایه بعدی

        // ---- AFTER: بعد از controller، روی پاسخ
        $response->headers->set('X-Checked-Role', 'yes');

        return $response;
    }
}

Terminable middleware

اگر middleware متد terminate($request, $response) داشته باشد، بعد از ارسال پاسخ اجرا می‌شود؛ مناسب کارهای سبکی مثل ثبت آمار که نباید کاربر را منتظر بگذارد (کارهای سنگین را به Queue بسپارید).

<?php
class LogRequestDuration
{
    public function handle(Request $request, Closure $next): Response
    {
        return $next($request);
    }

    public function terminate(Request $request, Response $response): void
    {
        Log::info('duration', ['ms' => (microtime(true) - LARAVEL_START) * 1000]);
    }
}
// Laravel برای terminate یک نمونه جدید از container می‌سازد؛ برای استفاده از
// همان نمونه handle، آن را در AppServiceProvider::register به صورت singleton ثبت کنید.

درخواست وب (فرم)

  • Redirect 302 به صفحه قبل.
  • خطاها در session flash می‌شوند و در view با متغیر $errors (MessageBag) و @error در دسترس‌اند.

  • اگر $request->expectsJson() درست باشد (هدر Accept: application/json یا درخواست AJAX).
  • پاسخ 422 با بدنه JSON شامل message و errors.

CSRF، Session و Flash data

CSRF چیست؟

Cross-Site Request Forgery حمله‌ای است که در آن سایت مخرب، مرورگر کاربرِ لاگین‌شده را وادار می‌کند درخواستی (مثلاً POST انتقال وجه) به سایت ما بفرستد؛ مرورگر cookie session را خودکار ضمیمه می‌کند و سرور درخواست را معتبر تلقی می‌کند.

محافظت Laravel: برای هر session یک توکن تصادفی تولید و در session ذخیره می‌شود. middleware ValidateCsrfToken (در گروه web) برای همه درخواست‌های تغییردهنده وضعیت (POST، PUT، PATCH، DELETE) بررسی می‌کند که توکن ارسالی با توکن session یکسان باشد. منابع توکن به ترتیب:

  1. فیلد _token در فرم (@csrf).
  2. هدر X-CSRF-TOKEN (مثلاً از <meta name="csrf-token" content="{{ csrf_token() }}">).
  3. هدر X-XSRF-TOKEN: Laravel cookie رمزشده XSRF-TOKEN را در هر پاسخ می‌فرستد و کتابخانه‌هایی مثل Axios آن را خودکار در این هدر برمی‌گردانند.

سایت مهاجم به دلیل Same-Origin Policy نمی‌تواند توکن را بخواند، پس نمی‌تواند درخواست معتبر بسازد. عدم تطابق توکن ⇒ TokenMismatchException ⇒ پاسخ 419 Page Expired.

<?php
// استثنا کردن URIها (مثلاً webhookهای سرویس خارجی که توکن ندارند)
->withMiddleware(function (Middleware $middleware) {
    $middleware->validateCsrfTokens(except: [
        'stripe/*',
        'payment/callback',
    ]);
})
// Laravel ≤ 10: آرایه $except در App\Http\Middleware\VerifyCsrfToken

چرا routeهای api.php نیاز به CSRF ندارند؟ چون stateless هستند و با توکن در هدر Authorization احراز هویت می‌شوند، نه cookie. مرورگر هدر Authorization را خودکار به درخواست‌های cross-site اضافه نمی‌کند، پس CSRF موضوعیت ندارد. اما اگر SPA با Sanctum cookie-based احراز هویت کند، CSRF دوباره لازم است (endpoint /sanctum/csrf-cookie).

یک لایه دفاعی دیگر: cookie session در Laravel به صورت پیش‌فرض SameSite=lax و HttpOnly است (در config/session.php). همچنین درخواست‌های GET نباید هرگز وضعیت را تغییر دهند؛ چون CSRF روی آن‌ها بررسی نمی‌شود.

Migration، Seeder و Factory

Migration

Migration نسخه‌بندی (version control) ساختار دیتابیس است: تغییرات schema به صورت کد PHP نوشته، در git ثبت و در همه محیط‌ها به ترتیب یکسان اجرا می‌شوند. Laravel اجراشده‌ها را در جدول migrations با شماره batch ثبت می‌کند.

php artisan make:migration create_posts_table          # Laravel از نام، جدول را حدس می‌زند
php artisan make:migration add_status_to_posts_table --table=posts
php artisan make:model Post -mfs                        # مدل + migration + factory + seeder
<?php
use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration      // کلاس anonymous — جلوگیری از تداخل نام
{
    public function up(): void
    {
        Schema::create('posts', function (Blueprint $table) {
            $table->id();                                            // BIGINT UNSIGNED AI PK
            $table->foreignId('user_id')->constrained()->cascadeOnDelete();
            $table->string('title');
            $table->string('slug')->unique();
            $table->text('body')->nullable();
            $table->enum('status', ['draft', 'published'])->default('draft');
            $table->unsignedInteger('views')->default(0);
            $table->json('meta')->nullable();
            $table->timestamp('published_at')->nullable()->index();
            $table->timestamps();                                    // created_at, updated_at
            $table->softDeletes();                                   // deleted_at
            $table->index(['user_id', 'status']);                    // ایندکس ترکیبی
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('posts');
    }
};

// تغییر جدول موجود
Schema::table('posts', function (Blueprint $table) {
    $table->string('subtitle')->nullable()->after('title');
    $table->string('title', 500)->change();      // Laravel 11: بدون doctrine/dbal؛
                                                 // همه modifierهای قبلی را دوباره ذکر کنید
    $table->renameColumn('body', 'content');
    $table->dropColumn('views');
});

Zero-downtime: تغییرات مخرب (حذف/تغییر نام ستون) را در چند مرحله انجام دهید: ستون جدید اضافه کنید → کد را طوری deploy کنید که هر دو را پشتیبانی کند → داده را منتقل کنید → ستون قدیمی را در deploy بعدی حذف کنید. روی جداول بزرگ، افزودن ایندکس ممکن است جدول را قفل کند.

Factory

Factory داده جعلی ولی واقع‌گرایانه برای مدل‌ها تولید می‌کند (با کتابخانه Faker از طریق fake())؛ کاربرد اصلی در تست و seeding محیط توسعه.

<?php
// database/factories/PostFactory.php
class PostFactory extends Factory
{
    public function definition(): array
    {
        return [
            'user_id' => User::factory(),          // ساخت خودکار والد
            'title'   => fake()->sentence(),
            'slug'    => fake()->unique()->slug(),
            'body'    => fake()->paragraphs(3, true),
            'status'  => 'draft',
        ];
    }

    public function published(): static           // state
    {
        return $this->state(fn () => ['status' => 'published', 'published_at' => now()]);
    }
}

Post::factory()->count(10)->published()->create();  // ذخیره در DB
Post::factory()->make();                              // بدون ذخیره
User::factory()->has(Post::factory()->count(3))->create();

(states پیشرفته، relationship در factory و sequence در صفحه Eloquent.)

مدیریت خطا (Exception Handling)

همه exceptionها توسط handler مرکزی گرفته می‌شوند که دو کار انجام می‌دهد: report (ثبت در لاگ یا ارسال به سرویس‌هایی مثل Sentry) و render (تبدیل به پاسخ HTTP). در Laravel 11 این کار در bootstrap/app.php پیکربندی می‌شود:

<?php
->withExceptions(function (Exceptions $exceptions) {
    // گزارش سفارشی
    $exceptions->report(function (PaymentFailedException $e) {
        Log::channel('payments')->error($e->getMessage());
    });

    // پاسخ سفارشی — مثلاً JSON یکدست برای API
    $exceptions->render(function (NotFoundHttpException $e, Request $request) {
        if ($request->is('api/*')) {
            return response()->json(['message' => 'Resource not found.'], 404);
        }
    });

    $exceptions->dontReport([InvalidCouponException::class]);
})
<?php
abort(404);  abort(403, 'Unauthorized action.');
abort_if(! $user->isAdmin(), 403);
abort_unless($post->isPublished(), 404);
report($e);                  // گزارش بدون توقف اجرای برنامه
throw ValidationException::withMessages(['email' => 'این ایمیل مسدود است.']);

// exception با report/render داخلی
class OrderLimitExceeded extends Exception
{
    public function render(Request $request) { return response()->json(['message' => $this->getMessage()], 422); }
}
  • صفحات خطای سفارشی: فایل resources/views/errors/404.blade.php (یا 500، 419، 503) خودکار استفاده می‌شود؛ 4xx.blade.php و 5xx.blade.php به عنوان fallback.
  • exceptionهای HTTP مثل ModelNotFoundException به 404، AuthorizationException به 403، ValidationException به 422/redirect و AuthenticationException به 401/redirect تبدیل می‌شوند و به صورت پیش‌فرض report نمی‌شوند.
  • در Laravel ≤ 10 همه این‌ها در app/Exceptions/Handler.php با متدهای register()، reportable()، renderable() و آرایه $dontReport انجام می‌شد.

سوالات تشریحی

چرخه عمر یک درخواست HTTP در Laravel را از لحظه ورود به سرور تا ارسال پاسخ به کاربر به ترتیب شرح دهید.

خلاصه: همه درخواست‌ها از یک front controller واحد (public/index.php) وارد می‌شوند، از container و kernel می‌گذرند، در یک pipeline از middlewareها به controller می‌رسند و پاسخ از همان مسیر برمی‌گردد.

  1. index.php: بررسی maintenance mode، بارگذاری Composer autoloader، require کردن bootstrap/app.php.
  2. bootstrap/app.php: ساخت Application که همان Service Container است و پیکربندی routing/middleware/exceptions.
  3. $app->handleRequest(Request::capture()) ⇒ HTTP Kernel resolve می‌شود.
  4. Bootstrap کرنل: بارگذاری .env و config، تنظیم exception handler، ثبت facadeها، اجرای register() همه providerها و سپس boot() همه.
  5. Global middleware (TrimStrings، TrustProxies، …) از طریق Pipeline.
  6. Router route مطابق را پیدا می‌کند؛ سپس middlewareهای گروه (web: session، CSRF، SubstituteBindings) و route اجرا می‌شوند.
  7. Controller: با DI ساخته می‌شود؛ Form Request validate می‌شود؛ مقدار برگشتی به Response تبدیل می‌شود.
  8. پاسخ از middlewareها به ترتیب معکوس عبور می‌کند (منطق «after»)، send() می‌شود، و در نهایت terminate() برای terminable middlewareها اجرا می‌شود.
index.php → app.php (Container) → Kernel::handle → bootstrap(providers register→boot)
→ global MW → Router → group/route MW → Controller → Response → MW (reverse) → send → terminate

نکات تکمیلی: در Laravel ≤ 10 به جای handleRequest، کرنل صریحاً در index.php ساخته و handle/terminate فراخوانی می‌شد. در PHP-FPM این چرخه برای هر درخواست تکرار می‌شود؛ به همین دلیل config:cache و route:cache در production اهمیت دارند و Octane با نگه‌داشتن برنامه در حافظه این سربار را حذف می‌کند.

الگوی MVC در Laravel چگونه پیاده شده است؟ چرا «Fat Controller» یک ضدالگو است و منطق تجاری را کجا قرار می‌دهید؟

تعریف: در Laravel Model = کلاس‌های Eloquent (داده و قواعد آن)، View = Blade یا خروجی JSON، Controller = هماهنگ‌کننده بین ورودی HTTP و منطق برنامه. Router هم نقش نگاشت URL به controller را دارد.

مشکل Fat Controller: وقتی validation، کوئری، محاسبات، ارسال ایمیل و فراخوانی API همه در یک متد controller باشند:

  • منطق قابل استفاده مجدد نیست (مثلاً از Artisan command یا Job).
  • تست فقط از طریق HTTP ممکن است.
  • نقض Single Responsibility؛ کلاس‌های هزار خطی.

تقسیم مسئولیت پیشنهادی:

  • Form Request: validation و authorization ورودی.
  • Service / Action class: منطق تجاری (مثلاً PlaceOrderAction).
  • Model: relationها، scopeها، cast و منطق کوچک مربوط به خود موجودیت.
  • Event/Job: کارهای جانبی یا کند (ایمیل، webhook).
  • API Resource: شکل خروجی.
<?php
public function store(StoreOrderRequest $request, PlaceOrderAction $placeOrder)
{
    $order = $placeOrder->execute($request->user(), $request->validated());
    return OrderResource::make($order)->response()->setStatusCode(201);
}

Trade-off: برای CRUD ساده، لایه Service اضافه فقط پیچیدگی می‌آورد؛ اصل این است که controller نازک بماند، نه اینکه برای هر چیزی کلاس بسازیم.

تفاوت env() و config() چیست؟ چرا توصیه می‌شود env() فقط در فایل‌های config استفاده شود؟

تعریف: env('KEY') مقدار یک متغیر محیطی (بارگذاری‌شده از .env یا محیط سیستم) را می‌خواند. config('file.key') مقداری را از آرایه‌های پیکربندی config/*.php می‌خواند که داخل container نگه داشته می‌شوند.

چرا env فقط در config:

  • دستور php artisan config:cache همه فایل‌های config را اجرا و نتیجه نهایی را در bootstrap/cache/config.php ذخیره می‌کند.
  • وقتی cache وجود دارد، فایل .env دیگر بارگذاری نمی‌شود.
  • در نتیجه env() در controller یا service در production مقدار null برمی‌گرداند — باگی که در محیط local (بدون cache) دیده نمی‌شود.
<?php
// ✗ اشتباه
$key = env('STRIPE_KEY');

// ✓ صحیح — config/services.php
'stripe' => ['key' => env('STRIPE_KEY')],
// در کد:
$key = config('services.stripe.key');

مزایای جانبی config(): مقدار پیش‌فرض متمرکز، type casting در یک جا، امکان تغییر در تست (config(['services.stripe.key' => 'test']))، و مستندسازی همه تنظیمات در یک مکان. برای تشخیص محیط هم app()->environment('production') به جای env('APP_ENV').

نکته deploy: پس از تغییر .env روی سرور، باید config:cache دوباره اجرا شود؛ وگرنه تغییرات دیده نمی‌شوند.

ساختار Laravel 11 در مقایسه با Laravel 10 چه تغییراتی کرده است؟ در یک پروژه Laravel 11 یک middleware سراسری و یک alias را کجا ثبت می‌کنید؟

ایده اصلی: Laravel 11 اسکلت را slim کرد؛ کلاس‌های پایه در فریم‌ورک ماندند و پیکربندی به API روان Application::configure() در bootstrap/app.php منتقل شد.

  • حذف از اسکلت: app/Http/Kernel.php، app/Console/Kernel.php، app/Exceptions/Handler.php، اکثر middlewareهای داخل app/Http/Middleware و همه providerها به جز AppServiceProvider.
  • جایگزین‌ها: withRouting()، withMiddleware()، withExceptions()؛ Schedule در routes/console.php؛ providerها در bootstrap/providers.php.
  • اختیاری شدن: routes/api.php با install:api و channels.php با install:broadcasting.
  • پیش‌فرض‌ها: SQLite و driverهای database برای session/cache/queue، route سلامت /up، متد casts() در مدل، حداقل PHP 8.2.
<?php
// bootstrap/app.php
->withMiddleware(function (Middleware $middleware) {
    $middleware->append(\App\Http\Middleware\AddRequestId::class);       // global
    $middleware->alias(['role' => \App\Http\Middleware\EnsureUserHasRole::class]);
    $middleware->web(append: [\App\Http\Middleware\SetLocale::class]); // گروه web
})

معادل در Laravel 10: افزودن کلاس به آرایه $middleware و $middlewareAliases در app/Http/Kernel.php. پروژه‌های ارتقایافته از 10 لازم نیست ساختار را تغییر دهند؛ Laravel 11 از ساختار قدیمی هم پشتیبانی می‌کند.

Route Model Binding را توضیح دهید. انواع implicit و explicit، کلید سفارشی و scoped binding چه تفاوتی دارند؟

تعریف: مکانیزمی که پارامتر route را به‌طور خودکار به نمونه مدل تبدیل می‌کند؛ اگر رکورد یافت نشود ModelNotFoundException و در نتیجه 404 رخ می‌دهد. توسط middleware SubstituteBindings انجام می‌شود.

  • Implicit: نام پارامتر route = نام متغیر type-hint شده. /posts/{post} + Post $post.
  • Custom key: جستجو با ستون دیگر: {post:slug} برای یک route یا getRouteKeyName() برای همه.
  • Scoped: در routeهای تودرتو فرزند از طریق رابطه والد جستجو می‌شود: /users/{user}/posts/{post:slug} ⇒ $user->posts()->where('slug', …). با کلید پیش‌فرض باید ->scopeBindings() زد.
  • Explicit: تعریف صریح در boot(): Route::model('member', User::class) یا منطق کامل با Route::bind.
<?php
Route::bind('order', fn (string $value) =>
    Order::where('code', $value)->where('tenant_id', tenant()->id)->firstOrFail()
);

Route::get('/users/{user}/posts/{post}', fn (User $user, Post $post) => $post)
    ->scopeBindings()
    ->withTrashed()
    ->missing(fn () => redirect('/'));

مزایا: حذف کد تکراری findOrFail، 404 خودکار، کنترلر تمیزتر. نکات: binding ≠ authorization (هنوز Policy لازم است)؛ scoped binding جلوی دسترسی به منبع والد دیگر را می‌گیرد؛ explicit برای multi-tenant یا جستجوی ترکیبی مفید است.

Middleware چیست؟ تفاوت before middleware، after middleware و terminable middleware را با مثال بیان کنید.

تعریف: Middleware لایه‌ای است که درخواست HTTP قبل از رسیدن به controller و پاسخ قبل از رسیدن به کاربر از آن عبور می‌کند. Laravel آن‌ها را با کلاس Pipeline به صورت لایه‌های تودرتو (onion) اجرا می‌کند؛ هر لایه می‌تواند درخواست را رد کند (short-circuit) یا با $next($request) به لایه بعد بدهد.

  • Before: کد قبل از $next — مثلاً بررسی نقش، تنظیم locale.
  • After: کد بعد از $next روی $response — مثلاً افزودن header امنیتی.
  • Terminable: متد terminate() بعد از ارسال پاسخ — مثلاً ثبت متریک.
<?php
class SecurityHeaders
{
    public function handle(Request $request, Closure $next): Response
    {
        if ($request->is('admin/*') && ! $request->user()?->is_admin) {
            abort(403);                                    // before
        }
        $response = $next($request);
        $response->headers->set('X-Frame-Options', 'DENY'); // after
        return $response;
    }

    public function terminate(Request $request, Response $response): void
    {
        Metrics::record($request->path(), $response->getStatusCode());
    }
}

پارامتر: ->middleware('role:editor') ⇒ آرگومان بعد از $next. ثبت: global / group / route alias در bootstrap/app.php. نکته: برای terminate، container نمونه جدید می‌سازد مگر middleware به صورت singleton ثبت شده باشد. کار سنگین را به جای terminate در Queue بگذارید.

Form Request چیست و چه مزیتی نسبت به $request->validate() درون controller دارد؟ نقش متدهای authorize، rules، messages و prepareForValidation را بیان کنید.

تعریف: کلاسی که از FormRequest ارث‌بری می‌کند و منطق authorization، validation و نرمال‌سازی ورودی یک درخواست را کپسوله می‌کند. وقتی در متد controller type-hint شود، container قبل از اجرای متد آن را resolve و validate می‌کند.

  • authorize(): اگر false برگرداند ⇒ 403؛ معمولاً $this->user()->can(...).
  • rules(): آرایه قواعد؛ می‌تواند به $this->route('post') برای ignore در unique دسترسی داشته باشد.
  • messages() / attributes(): پیام و نام فارسی فیلدها.
  • prepareForValidation(): تغییر ورودی قبل از validate (با $this->merge)، مثلاً ساخت slug یا حذف فاصله از شماره موبایل.
  • after() / passedValidation(): قواعد چندفیلدی و پس‌پردازش.
<?php
class UpdateUserRequest extends FormRequest
{
    public function authorize(): bool { return $this->user()->can('update', $this->route('user')); }

    protected function prepareForValidation(): void
    {
        $this->merge(['mobile' => preg_replace('/\D/', '', (string) $this->mobile)]);
    }

    public function rules(): array
    {
        return [
            'email'  => ['required', 'email', Rule::unique('users')->ignore($this->route('user'))],
            'mobile' => ['required', 'digits:11'],
        ];
    }
}

مقایسه: validate() برای موارد ساده و یک‌باره کافی است. Form Request: controller نازک‌تر، قابل استفاده مجدد بین store/update، تست‌پذیر جداگانه، ترکیب authorization با validation. همیشه از $request->validated() یا safe() برای داده استفاده کنید نه all().

یک اپلیکیشن موبایل به endpoint ثبت سفارش درخواست می‌فرستد و در صورت خطای validation به جای JSON، یک redirect با کد 302 و HTML دریافت می‌کند. علت چیست و چطور رفع می‌کنید؟

علت: وقتی ValidationException رخ می‌دهد، Laravel نوع پاسخ را با $request->expectsJson() تعیین می‌کند. این متد فقط وقتی true است که درخواست AJAX باشد (X-Requested-With) یا هدر Accept شامل application/json باشد. کلاینت موبایل این هدر را نمی‌فرستد، پس Laravel آن را درخواست وب فرض کرده و redirect back با خطاهای flash شده در session برمی‌گرداند.

حمله CSRF را تعریف کنید و توضیح دهید Laravel چگونه از آن جلوگیری می‌کند. خطای 419 چه زمانی رخ می‌دهد و چرا routeهای API به CSRF نیاز ندارند؟

تعریف: در Cross-Site Request Forgery سایت مهاجم مرورگر قربانیِ لاگین‌شده را وادار به ارسال درخواست تغییردهنده وضعیت به سایت ما می‌کند. چون مرورگر cookieها را خودکار ضمیمه می‌کند، سرور بدون مکانیزم اضافه نمی‌تواند درخواست جعلی را از واقعی تشخیص دهد.

مکانیزم Laravel (Synchronizer Token):

  • یک توکن تصادفی برای هر session تولید و در session ذخیره می‌شود.
  • فرم‌ها آن را با @csrf در فیلد _token ارسال می‌کنند؛ درخواست‌های JS از هدر X-CSRF-TOKEN یا X-XSRF-TOKEN (cookie رمزشده XSRF-TOKEN) استفاده می‌کنند.
  • middleware ValidateCsrfToken در گروه web برای POST/PUT/PATCH/DELETE تطابق را با مقایسه امن (hash_equals) بررسی می‌کند.
  • مهاجم به دلیل Same-Origin Policy قادر به خواندن توکن نیست.

خطای 419 (Page Expired): توکن ارسال نشده، نادرست است، یا session منقضی شده (مثلاً فرمی که ساعت‌ها باز مانده، تغییر APP_KEY، یا session driver ناپایدار در چند سرور).

<?php
// استثنا برای webhook خارجی
$middleware->validateCsrfTokens(except: ['webhooks/stripe']);
// امنیت webhook را با بررسی امضای HMAC جایگزین کنید.

API: routeهای api stateless هستند و با هدر Authorization: Bearer احراز هویت می‌شوند که مرورگر خودکار ارسال نمی‌کند؛ پس CSRF معنا ندارد. استثنا: SPA با Sanctum cookie-based که چون به cookie متکی است، باید ابتدا /sanctum/csrf-cookie را بگیرد. لایه‌های دفاعی مکمل: SameSite=lax cookie و عدم تغییر وضعیت با GET.

Service Container و Service Provider را تعریف کنید. چرا در متد register() نباید از سرویس‌های دیگر استفاده کرد؟

Service Container: ابزار مدیریت وابستگی و پیاده‌سازی Inversion of Control. «چگونگی ساخت» سرویس‌ها را نگه می‌دارد و هنگام نیاز آن‌ها را می‌سازد و تزریق می‌کند. با Reflection وابستگی‌های constructor کلاس‌های concrete را خودکار resolve می‌کند؛ برای interfaceها نیاز به binding دارد.

Service Provider: نقطه مرکزی bootstrap برنامه و پکیج‌ها؛ کلاسی با دو متد:

  • register(): فقط ثبت binding (bind، singleton).
  • boot(): پس از register شدن همه providerها؛ ثبت Gate، event، route، view composer، rate limiter و…
<?php
public function register(): void
{
    $this->app->singleton(SmsSender::class, fn ($app) =>
        new KavenegarSmsSender(config('services.sms.key'))
    );
}

public function boot(): void
{
    RateLimiter::for('sms', fn (Request $r) => Limit::perMinute(3)->by($r->ip()));
}

چرا نه در register: ترتیب اجرای register()ها تضمین‌شده نیست. اگر در register یک provider سرویسی را resolve کنید که provider دیگری هنوز ثبت نکرده، یا binding ناقص می‌گیرید یا خطا. علاوه بر این، resolve زودهنگام سرویس‌ها مزیت lazy loading را از بین می‌برد و در deferred providerها رفتار غیرمنتظره ایجاد می‌کند. قاعده: «register = ثبت دستورالعمل، boot = استفاده».

مزیت کلی: loose coupling (کد به interface وابسته است)، جایگزینی آسان پیاده‌سازی (مثلاً درگاه پرداخت) و mock کردن در تست با $this->app->instance(...).

Facade در Laravel چیست و چگونه فراخوانی Cache::get('key') به یک شیء واقعی می‌رسد؟ آیا Facadeها تست‌پذیری را کاهش می‌دهند؟

تعریف: Facade یک کلاس با رابط static است که به عنوان proxy به یک سرویس ثبت‌شده در Service Container عمل می‌کند. نام الگو از Facade pattern گرفته شده ولی عملاً شبیه Static Proxy / Service Locator است.

مسیر resolve:

  1. کلاس Cache متد static به نام get ندارد ⇒ PHP متد جادویی __callStatic('get', ['key']) را روی کلاس پایه Facade صدا می‌زند.
  2. getFacadeRoot() با کلید برگشتی از getFacadeAccessor() ('cache') نمونه را از container می‌گیرد (و در آرایه static کش می‌کند).
  3. $instance->get('key') روی CacheManager واقعی اجرا می‌شود.
<?php
class Cache extends Facade
{
    protected static function getFacadeAccessor(): string
    {
        return 'cache';
    }
}

تست‌پذیری: برخلاف static واقعی، Facade قابل جایگزینی است: Cache::shouldReceive('get')->once()->andReturn('v') (Mockery) یا fakeها: Mail::fake()، Queue::fake()، Storage::fake()، Http::fake(). پس تست‌پذیری کم نمی‌شود.

معایب واقعی: وابستگی‌ها در امضای کلاس پنهان می‌شوند (scope creep)، IDE بدون helper نمی‌تواند autocomplete کامل بدهد، و کد به Laravel گره می‌خورد. جمع‌بندی: در controller و کد کاربردی Facade قابل قبول است؛ در کلاس‌های domain/پکیج، تزریق Contract در constructor شفاف‌تر است.

Session و Flash data در Laravel چگونه کار می‌کنند؟ الگوی Post/Redirect/Get را توضیح دهید و بگویید پس از login و logout چه عملیاتی روی session لازم است.

Session: مکانیزمی برای نگهداری حالت کاربر بین درخواست‌های بی‌حالت HTTP. شناسه session در cookie رمزشده و داده در driver (file، database، redis، cookie…) نگهداری می‌شود. middleware StartSession در گروه web آن را راه‌اندازی می‌کند؛ پس routeهای api session ندارند.

Flash data: داده‌ای که فقط تا درخواست بعدی زنده است؛ مثلاً پیام «ذخیره شد» یا خطاهای validation و old() input.

PRG: پس از پردازش موفق فرم POST، به جای رندر مستقیم view، به یک صفحه GET redirect می‌کنیم. اگر کاربر صفحه را refresh کند، فقط GET تکرار می‌شود نه ثبت دوباره سفارش.

Resource Controller و Resource Route را توضیح دهید. چه تفاوتی بین Route::resource و Route::apiResource وجود دارد و برای عملیاتی مثل «انتشار مقاله» که در CRUD نمی‌گنجد چه می‌کنید؟

Migration چیست و چرا از آن استفاده می‌کنیم؟ تفاوت migrate:rollback، migrate:refresh و migrate:fresh را بگویید. چگونه یک ستون را روی جدولی با میلیون‌ها رکورد در production تغییر نام می‌دهید؟

تعریف: Migration کنترل نسخه schema دیتابیس به صورت کد است؛ تغییرات تکرارپذیر، قابل بازبینی در code review و یکسان در همه محیط‌ها اجرا می‌شوند. Laravel سابقه اجرا را در جدول migrations با شماره batch نگه می‌دارد.

  • migrate:rollback: اجرای down() آخرین batch (یا --step=n).
  • migrate:refresh: rollback همه با down() و سپس migrate مجدد.
  • migrate:fresh: drop مستقیم همه جداول بدون اجرای down و سپس migrate؛ سریع‌تر و مستقل از درستی downها. هر دو مورد اخیر فقط برای توسعه/تست.

تغییر نام امن در production (expand/contract):

  1. Migration ۱: افزودن ستون جدید nullable.
  2. Deploy کدی که در هر دو ستون می‌نویسد و از قدیمی می‌خواند.
  3. انتقال داده به صورت batch (با chunkById در یک command یا job) تا قفل طولانی ایجاد نشود.
  4. Deploy کدی که فقط از ستون جدید استفاده می‌کند.
  5. Migration ۲: حذف ستون قدیمی.
<?php
Schema::table('users', fn (Blueprint $t) => $t->string('mobile')->nullable()->after('phone'));
// ... بعداً
Schema::table('users', fn (Blueprint $t) => $t->dropColumn('phone'));

چرا نه renameColumn مستقیم: در لحظه deploy، نسخه قدیمی کد (روی سرورهای دیگر یا workerهای صف) هنوز نام قبلی را استفاده می‌کند و خطا می‌دهد؛ روی جداول بزرگ هم ALTER ممکن است جدول را قفل کند. قوانین طلایی: migration اجراشده را ویرایش نکنید؛ در production از --force فقط با migrate استفاده کنید؛ down() را بنویسید ولی به آن برای بازگشت داده تکیه نکنید (backup).

پس از deploy روی سرور production: (۱) تغییر یک مقدار در .env اعمال نمی‌شود، (۲) یک route جدید 404 می‌دهد، (۳) صفحه خطا جزئیات stack trace و متغیرها را نشان می‌دهد. علت هر کدام و فرایند صحیح deploy را شرح دهید.

تشخیص:

  1. .env: config cache شده (bootstrap/cache/config.php)؛ وقتی cache وجود دارد .env خوانده نمی‌شود. باید php artisan config:cache دوباره اجرا شود. اگر جایی از کد env() مستقیم استفاده شده، آن را به config() تغییر دهید.
  2. route جدید: routeها cache شده‌اند و فایل جدید routes/*.php خوانده نمی‌شود ⇒ route:cache مجدد. (احتمالات دیگر: ترتیب route و تداخل با {param}، یا OPcache با validate_timestamps=0 که نیاز به reload PHP-FPM دارد.)
  3. stack trace: APP_DEBUG=true در production — نشت اطلاعات حساس. باید false و APP_ENV=production باشد.

چگونه در Laravel 11 همه خطاهای یک API را به فرمت JSON یکسان تبدیل می‌کنید و خطاهای مهم را در کانال جداگانه لاگ می‌کنید؟

مفهوم: exception handler دو مسئولیت دارد: report (ثبت/ارسال به سرویس مانیتورینگ) و render (تبدیل به پاسخ HTTP). در Laravel 11 هر دو در withExceptions() فایل bootstrap/app.php تنظیم می‌شوند (معادل app/Exceptions/Handler.php در نسخه‌های قبل).

<?php
->withExceptions(function (Exceptions $exceptions) {
    // همه خطاهای مسیر api/* به صورت JSON
    $exceptions->shouldRenderJsonWhen(fn (Request $r, Throwable $e) => $r->is('api/*'));

    // پیام سفارشی برای 404
    $exceptions->render(function (NotFoundHttpException $e, Request $r) {
        if ($r->is('api/*')) {
            return response()->json(['message' => 'Not found', 'code' => 'NOT_FOUND'], 404);
        }
    });

    // گزارش خطای پرداخت در کانال مجزا و توقف گزارش پیش‌فرض
    $exceptions->report(function (PaymentGatewayException $e) {
        Log::channel('payments')->critical($e->getMessage(), ['order' => $e->orderId]);
    })->stop();

    $exceptions->dontReport([CouponExpiredException::class]);
})

    'driver' => 'daily',
    'path'   => storage_path('logs/payments.log'),
    'level'  => 'warning',

],

نکات:

  • با APP_DEBUG=false، پیام خطاهای 500 به «Server Error» عمومی تبدیل می‌شود تا جزئیات نشت نکند.
  • exceptionهای validation، authentication، authorization و 404 به صورت پیش‌فرض report نمی‌شوند.
  • می‌توان متدهای report() و render() را مستقیماً روی کلاس exception سفارشی تعریف کرد.
  • از report($e) برای ثبت خطا بدون توقف جریان (مثلاً fallback به درگاه دوم) استفاده کنید.
  • context مفید (user id، request id) با Log::withContext یا Context facade اضافه شود.
ابزارهای Telescope، Pulse و Horizon و همچنین Sanctum و Passport را مقایسه کنید. هر کدام در چه شرایطی انتخاب می‌شوند؟

مشاهده‌پذیری و صف:

  • Telescope: دستیار دیباگ؛ هر درخواست، کوئری، exception، job، mail، cache hit و… را با جزئیات ثبت می‌کند. سربار و حجم داده بالا ⇒ عمدتاً محیط local/staging؛ در production فقط با فیلتر و محدودیت دسترسی.
  • Pulse: مانیتورینگ تجمیعی production با سربار کم: endpointها و کوئری‌های کند، jobهای کند، کاربران پرمصرف، exceptionهای پرتکرار، CPU/حافظه سرورها.
  • Horizon: فقط برای صف Redis: داشبورد throughput، زمان انتظار، jobهای شکست‌خورده و retry، و تعریف کد-محور supervisorها و auto-balancing workerها در config/horizon.php.

احراز هویت API:

  • Sanctum: سبک؛ دو حالت: (۱) personal access token با abilities برای موبایل/API ساده، ذخیره hash توکن در جدول personal_access_tokens؛ (۲) SPA authentication روی همان دامنه با cookie session و CSRF. برای اکثر برنامه‌ها کافی است.
  • Passport: سرور کامل OAuth2 (authorization code + PKCE، client credentials، refresh token، scopes). وقتی برنامه‌های third-party باید از طرف کاربران شما به API دسترسی بگیرند یا نقش Identity Provider دارید.
