PHP

PHP از درون تا بیرون: چرخهٔ اجرای درخواست با PHP-FPM و OPcache، سیستم نوع و مقایسه‌ها، قابلیت‌های مدرن PHP 8.x (enum، readonly، match، property hooks و …)، OOP و traits، closure و generator، exception، Composer و PSRها، امنیت و مدیریت حافظه — با سوالات تشریحی و پاسخ نمونه.

PHP چگونه اجرا می‌شود

PHP یک زبان تفسیری با کامپایل به bytecode است. هستهٔ آن Zend Engine است که کد منبع را مرحله به مرحله پردازش می‌کند:

source.php ──► Lexer (tokens) ──► Parser (AST) ──► Compiler (opcodes) ──► Zend VM (execute)
                                                          ▲
                                         OPcache: opcodeها را در shared memory نگه می‌دارد
                                         تا در درخواست بعدی دوباره کامپایل نشوند
  • Opcode: دستورالعمل‌های سطح پایین ماشین مجازی Zend (مثل ASSIGN، DO_FCALL، ECHO).
  • OPcache: بدون آن، هر درخواست همهٔ فایل‌ها را از نو parse و compile می‌کند. OPcache خروجی کامپایل را در حافظهٔ مشترک بین پروسس‌های FPM نگه می‌دارد. در production معمولاً opcache.validate_timestamps=0 می‌گذارند تا حتی mtime فایل‌ها چک نشود؛ در این حالت بعد از deploy باید FPM را reload یا OPcache را reset کرد.
  • Preloading (PHP 7.4): با opcache.preload می‌توان در شروع سرور فایل‌هایی را یک بار بارگذاری کرد تا کلاس‌ها و توابعشان برای همهٔ درخواست‌ها از قبل حاضر باشند.
  • JIT (PHP 8.0): opcodeها را به کد ماشین native تبدیل می‌کند. برای کارهای CPU-bound (محاسبات، پردازش تصویر) سود زیادی دارد، اما در اپ‌های وب معمولی که بیشتر وقتشان صرف I/O (دیتابیس، شبکه) می‌شود، بهبود کمی ایجاد می‌کند.

چرخهٔ درخواست با PHP-FPM

Browser ──► Nginx ──(FastCGI / unix socket)──► PHP-FPM master
                                                   ├── worker 1  (یک درخواست در هر لحظه)
                                                   ├── worker 2
                                                   └── worker N  (pm.max_children)

هر worker برای هر درخواست:
  RINIT ──► اجرای public/index.php ──► ساخت پاسخ ──► RSHUTDOWN (آزادسازی همه‌چیز)
یک بار در عمر پروسس: MINIT (بارگذاری extensionها) ... MSHUTDOWN
  • PHP-FPM (FastCGI Process Manager) یک master process و یک pool از worker processها دارد. حالت‌های pm: static (تعداد ثابت)، dynamic (بین min و max)، ondemand (فقط هنگام نیاز).
  • هر worker در هر لحظه فقط یک درخواست را سرویس می‌دهد؛ پس حداکثر همروندی برابر pm.max_children است. اگر همه مشغول باشند، درخواست‌ها در صف می‌مانند (و نهایتاً 502/504).
  • pm.max_requests: worker بعد از N درخواست بازتولید می‌شود؛ راهی برای مهار memory leak در extensionها.

معماری Shared-Nothing

در مدل کلاسیک، هیچ state ای بین دو درخواست باقی نمی‌ماند: متغیرها، objectها، اتصال‌ها (به جز persistent connectionها) و … در پایان درخواست دور ریخته می‌شوند. هر درخواست Laravel از صفر bootstrap می‌شود (ساخت container، ثبت providerها، بارگذاری config).

مزایا

  • سادگی ذهنی: نشت حافظه یا state خراب یک درخواست، درخواست بعدی را آلوده نمی‌کند.
  • مقیاس‌پذیری افقی آسان: هر سرور مستقل است (session و cache باید بیرونی باشند، مثل Redis).
  • یک خطای fatal فقط همان درخواست را از بین می‌برد.

معایب

  • هزینهٔ bootstrap در هر درخواست (برای همین config:cache و route:cache مهم‌اند).
  • نبود connection pooling بومی و نبود state درون‌حافظه‌ای.
  • مدل blocking: هر worker هنگام انتظار برای I/O بیکار می‌ماند.

Laravel Octane (روی Swoole، RoadRunner یا FrankenPHP) این مدل را می‌شکند: اپلیکیشن یک بار boot می‌شود و در حافظه می‌ماند و درخواست‌ها پشت سر هم روی همان instance پردازش می‌شوند. سرعت بالاتر می‌رود اما باید مراقب state نشت‌کننده باشیم: propertyهای static، singletonهایی که به request وابسته‌اند، آرایه‌هایی که مدام بزرگ می‌شوند.

اگر پرسیدند «چرا در PHP سنتی memory leak کمتر مشکل‌ساز است؟» پاسخ: به‌خاطر shared-nothing؛ در پایان هر درخواست کل حافظهٔ درخواست آزاد می‌شود. اما در پروسس‌های طولانی‌مدت (queue worker، Octane، دستورهای daemon) leak واقعاً جمع می‌شود؛ برای همین queue:work گزینه‌های --max-jobs، --max-time و --memory دارد.

اجرای CLI (php artisan ...) از FPM استفاده نمی‌کند؛ یک پروسس مستقل است و php.ini مخصوص CLI می‌تواند متفاوت باشد (مثلاً memory_limit یا فعال بودن OPcache که در CLI به‌طور پیش‌فرض خاموش است).

PHP یک زبان dynamically typed و weakly typed است (هرچند با type declarationها و strict_types می‌توان آن را سخت‌گیرتر کرد). انواع داده:

دستهانواعتوضیح

Compoundarray، object، callable، iterablearray در واقع یک ordered hash map است؛ هم لیست است هم دیکشنری.

Type Juggling (تبدیل ضمنی نوع)

PHP بر اساس context نوع را تبدیل می‌کند: "5" + 3 برابر 8 است، "abc" . 1 برابر "abc1". در شرط‌ها مقادیر falsy عبارت‌اند از: false، 0، 0.0، ""، "0"، []، null. نکتهٔ معروف: "0" falsy است اما "0.0" و " " truthy هستند.

== در برابر ===

  • == (loose): ابتدا type juggling انجام می‌دهد، بعد مقایسه می‌کند.
  • === (strict): نوع و مقدار باید هر دو یکسان باشند؛ هیچ تبدیلی انجام نمی‌شود.

تغییر مهم PHP 8: مقایسهٔ رشته با عدد

از PHP 8.0 (RFC «Saner string to number comparisons»): اگر رشته numeric باشد، مقایسه عددی انجام می‌شود؛ در غیر این صورت عدد به رشته تبدیل و مقایسهٔ رشته‌ای انجام می‌شود. قبلاً رشته به عدد تبدیل می‌شد و "abc" به 0 می‌رسید.

عملگر Spaceship و مقایسهٔ آرایه‌ها

$a <=> $b (از PHP 7.0) مقدار -1، 0 یا 1 برمی‌گرداند و برای callback مرتب‌سازی ایده‌آل است:

<?php
usort($users, fn($a, $b) => [$a->age, $a->name] <=> [$b->age, $b->name]); // مرتب‌سازی چندکلیدی

[1, 2] == [2 => 1];        // false
['a' => 1, 'b' => 2] == ['b' => 2, 'a' => 1];   // true  (کلید/مقدار برابر)
['a' => 1, 'b' => 2] === ['b' => 2, 'a' => 1];  // false (ترتیب و نوع هم مهم است)
  • ?? (null coalescing): اگر سمت چپ وجود نداشته باشد یا null باشد، سمت راست را برمی‌گرداند و notice نمی‌دهد. ??= از PHP 7.4.
  • ?: (Elvis): اگر سمت چپ falsy باشد سمت راست را برمی‌گرداند؛ پس 0 ?: 5 برابر 5 ولی 0 ?? 5 برابر 0 است.

Type Declaration و strict_types

PHP به‌تدریج یک سیستم نوع قوی پیدا کرده است. type declaration روی پارامتر، مقدار برگشتی و property (از PHP 7.4، typed properties) قابل استفاده است و در زمان اجرا بررسی می‌شود (نقض آن TypeError می‌دهد).

    }
}

  • فراخواننده اجرای خود را ادامه می‌دهد.

  • تابع اصلاً برنمی‌گردد (throw، exit، حلقهٔ بی‌نهایت).
  • به static analyzer می‌گوید کد بعد از فراخوانی unreachable است (مثل abort() در Laravel).

declare(strict_types=1)

در حالت پیش‌فرض (coercive mode)، PHP مقادیر scalar را در صورت امکان به نوع اعلام‌شده تبدیل می‌کند: ارسال "5" به پارامتر int قبول و به 5 تبدیل می‌شود. با declare(strict_types=1); این تبدیل ممنوع می‌شود و TypeError پرتاب می‌شود.

<?php
declare(strict_types=1);   // باید اولین statement فایل باشد

function add(int $a, int $b): int { return $a + $b; }

add(1, 2);       // 3
add("1", 2);     // TypeError
add(1.5, 2);     // TypeError
function half(float $x): float { return $x / 2; }
half(5);         // 2.5 — تنها استثنا: int به float (widening) مجاز است
  • Per-file است و روی فراخوانی‌هایی که از داخل آن فایل انجام می‌شود اثر دارد، نه روی تعریف تابع. یعنی تصمیم با caller است. اگر تابع در فایل strict تعریف شده ولی از فایل غیر strict صدا زده شود، coercion انجام می‌شود.
  • برای return type، حالت فایلی که تابع در آن تعریف شده ملاک است.
  • روی فراخوانی توابع داخلی PHP (مثل strlen(123)) هم از فایل strict اثر دارد.
  • روی عملگرها ("5" + 3) و شرط‌ها (if ("abc")) اثری ندارد؛ فقط مرز تابع/property را کنترل می‌کند.
  • روی مقداردهی به typed property از داخل همان فایل هم اثر دارد.

جملهٔ کلیدی برای پاسخ: «strict_types یک تنظیم per-file است که حالت caller را تعیین می‌کند؛ coercion اسکالرها را غیرفعال می‌کند به‌جز widening از int به float، و روی عملگرها اثری ندارد.»

Named Arguments (8.0)

آرگومان‌ها را با نام پارامتر پاس می‌دهیم؛ ترتیب مهم نیست و می‌توان پارامترهای اختیاری میانی را رد کرد.

<?php

str_pad(string: 'x', length: 10, pad_type: STR_PAD_LEFT);

Constructor Property Promotion (8.0)

<?php
// قبل
class Point {
    private int $x;
    public function __construct(int $x) { $this->x = $x; }

// بعد
final class OrderService
{

هر پارامتر constructor که visibility modifier داشته باشد، هم‌زمان property تعریف و مقداردهی می‌کند. در Laravel برای تزریق وابستگی در کنترلر و سرویس بسیار رایج است.

Attributes (8.0)

metadata ساخت‌یافته و قابل خواندن با Reflection، جایگزین docblock annotationها:

<?php
#[Attribute(Attribute::TARGET_METHOD)]
final class Route
{
    public function __construct(public string $method, public string $path) {}
}

class UserController
{
    #[Route('GET', '/users')]
    public function index() {}
}

$ref = new ReflectionMethod(UserController::class, 'index');
foreach ($ref->getAttributes(Route::class) as $attr) {
    $route = $attr->newInstance();   // instance فقط هنگام newInstance ساخته می‌شود
    echo $route->path;               // /users
}

attributeهای داخلی مهم: #[\SensitiveParameter] (8.2، پنهان کردن مقدار در stack trace)، #[\AllowDynamicProperties] (8.2)، #[\Override] (8.3)، #[\Deprecated] (8.4). Laravel هم attributeهایی مثل #[ObservedBy] برای مدل‌ها دارد.

سایر قابلیت‌های 8.0

  • throw به‌عنوان expression: $user = $repo->find($id) ?? throw new NotFound();
  • catch بدون متغیر: catch (JsonException) { ... }
  • توابع رشته‌ای str_contains، str_starts_with، str_ends_with.
  • ::class روی object: $obj::class.
  • اینترفیس Stringable که کلاس‌های دارای __toString خودکار پیاده می‌کنند.
  • بسیاری از warningهای توابع داخلی به TypeError/ValueError تبدیل شدند.

Fibers (8.1) — مفهوم

Fiber یک واحد اجرای سبک با stack مستقل است که می‌تواند وسط اجرا suspend و بعداً resume شود. این همروندی همکارانه (cooperative) است، نه موازی‌سازی: در هر لحظه فقط یک fiber اجرا می‌شود و threadی ساخته نمی‌شود.

<?php
$fiber = new Fiber(function (string $x): string {
    $y = Fiber::suspend($x . ' suspended');   // کنترل به caller برمی‌گردد
    return "resumed with $y";
});
echo $fiber->start('job');     // job suspended
$fiber->resume('data');
echo $fiber->getReturn();      // resumed with data

کاربرد اصلی آن در کتابخانه‌های async (مثل event loop در Revolt و AMPHP v3) است تا کد async بدون callback و Promise، به شکل همگام نوشته شود. توسعه‌دهندهٔ اپلیکیشن معمولاً مستقیم با Fiber کار نمی‌کند.

readonly و Enum

Readonly Properties (8.1)

  • فقط یک بار و فقط از داخل scope کلاس مقداردهی می‌شود؛ پس از آن هر تغییری Error می‌دهد.
  • باید typed باشد و مقدار پیش‌فرض نمی‌گیرد (مقداردهی در constructor).
  • readonly بودن سطحی (shallow) است: اگر property یک object باشد، خود object همچنان قابل تغییر است.
<?php
final class Money
{
    public function __construct(
        public readonly int $amount,
        public readonly string $currency,
    ) {}

    public function add(Money $other): static
    {
        if ($other->currency !== $this->currency) {
            throw new InvalidArgumentException('Currency mismatch');
        }
        return new static($this->amount + $other->amount, $this->currency); // wither: object جدید
    }
}

$m = new Money(100, 'USD');
$m->amount = 200;   // Error: Cannot modify readonly property Money::$amount

Readonly Classes (8.2)

readonly class Dto { ... } همهٔ propertyها را readonly می‌کند و ساخت dynamic property را ممنوع می‌کند. همهٔ propertyها باید typed باشند. ایده‌آل برای DTO و Value Object.

از PHP 8.3 می‌توان propertyهای readonly را داخل __clone() دوباره مقداردهی کرد؛ این کار پیاده‌سازی deep clone برای objectهای immutable را ممکن می‌کند.

Enumها (8.1)

enum یک نوع با مجموعهٔ بسته و محدود از مقادیر ممکن است. هر case یک instance یکتا (singleton) از enum است، پس با === مقایسه می‌شود.

<?php
// Pure enum: فقط case، بدون مقدار اسکالر
enum Suit { case Hearts; case Spades; }

// Backed enum: هر case یک مقدار int یا string دارد (برای ذخیره در DB/JSON)
enum OrderStatus: string implements HasLabel
{
    case Pending   = 'pending';

    }

  • enum می‌تواند interface پیاده کند، متد (عادی و static) و ثابت داشته باشد و trait (بدون property) استفاده کند.
  • enum state ندارد: property تعریف نمی‌شود (جز name و value که readonly هستند)، با new ساخته نمی‌شود و قابل ارث‌بری نیست.

OOP، Late Static Binding و Traits

Visibility

  • public: از همه‌جا. protected: از خود کلاس و کلاس‌های فرزند/والد. private: فقط از همان کلاسی که تعریف شده.
  • visibility در PHP class-based است، نه object-based: یک متد می‌تواند به propertyهای private object دیگری از همان کلاس دسترسی داشته باشد (برای متدهایی مثل equals() مفید است).

self در برابر static (Late Static Binding)

  • self:: به کلاسی که کد در آن نوشته شده اشاره می‌کند (در compile-time تعیین می‌شود).
  • static:: به کلاسی که در زمان اجرا صدا زده شده اشاره می‌کند (Late Static Binding، از PHP 5.3).
  • parent:: به کلاس والد.
<?php
class Model
{
    public static function create(): static
    {
        return new static();        // اگر new self() بود، همیشه Model برمی‌گشت
    }

    public static function table(): string
    {
        return static::$table;      // property کلاس فرزند خوانده می‌شود
    }
    protected static string $table = 'models';
}

class User extends Model
{
    protected static string $table = 'users';
}

get_class(User::create());   // User
User::table();               // users  (با self::$table نتیجه models می‌شد)

Eloquent به‌شدت از LSB استفاده می‌کند: User::query() و User::create() در کلاس پایهٔ Model تعریف شده‌اند اما با new static یک instance از User می‌سازند.

Static

اعضای static متعلق به کلاس‌اند نه instance. در PHP-FPM، propertyهای static فقط در طول یک درخواست زنده‌اند، اما در Octane و queue worker بین درخواست‌ها/jobها باقی می‌مانند و منبع رایج باگ هستند. متدهای static قابل mock نیستند و وابستگی پنهان می‌سازند؛ برای منطق دامنه بهتر است از instance و DI استفاده شود.

Traits

trait مکانیزم استفادهٔ مجدد افقی از کد است: کد trait در زمان compile عملاً در کلاس «کپی» می‌شود. trait نوع (type) نیست؛ نمی‌توان instanceof SomeTrait نوشت یا آن را type-hint کرد.

<?php
trait Loggable
{
    protected static int $count = 0;         // هر کلاسِ استفاده‌کننده، نسخهٔ مستقل خودش را دارد

    abstract protected function logPrefix(): string;   // کلاس استفاده‌کننده موظف به پیاده‌سازی

    public function log(string $m): void
    {
        static::$count++;
        echo $this->logPrefix() . $m;
    }

    public static function make(): static { return new static(); }   // متد static در trait
}

trait Hello { public function greet() { return 'Hello'; } }
trait Hi    { public function greet() { return 'Hi'; } }

class Greeter
{
    use Hello, Hi {
        Hello::greet insteadof Hi;    // حل تعارض: نسخهٔ Hello برنده است
        Hi::greet as greetHi;         // نسخهٔ Hi با نام مستعار در دسترس می‌ماند
        greet as protected;           // تغییر visibility
    }
}
  • اولویت: متد خود کلاس > متد trait > متد ارث‌برده از والد.
  • trait می‌تواند property، متد abstract، متد static، property static و (از 8.2) ثابت داشته باشد.
  • اگر trait و کلاس property هم‌نام داشته باشند، فقط وقتی مجاز است که کاملاً سازگار باشند (visibility، نوع و مقدار اولیه یکسان).
  • در Laravel: HasFactory، SoftDeletes، Notifiable، Dispatchable. Eloquent متدهای boot{TraitName} و initialize{TraitName} را خودکار صدا می‌زند.

استفادهٔ افراطی از trait باعث coupling پنهان می‌شود (trait به propertyهای کلاس میزبان وابسته است)، تست مستقل آن دشوار است و کلاس را به «God Object» تبدیل می‌کند. اگر رفتار مستقل است، composition (تزریق یک سرویس) معمولاً بهتر است.

<?php

{

    public function __set(string $key, mixed $value): void { $this->items[$key] = $value; }

    {
        if (str_starts_with($method, 'get')) {

        throw new BadMethodCallException("Method $method does not exist");

Clone: کپی سطحی در برابر کپی عمیق

clone $obj یک shallow copy می‌سازد: propertyهای اسکالر و آرایه کپی می‌شوند، اما propertyهایی که object هستند فقط handleشان کپی می‌شود و هر دو کپی به همان object درونی اشاره می‌کنند.

<?php
class Order
{
    public array $items = [];
    public function __construct(public Address $address) {}

    public function __clone(): void
    {
        $this->address = clone $this->address;   // deep copy برای object تودرتو
        // آرایه‌ها خودشان by value کپی می‌شوند، مگر اینکه حاوی object باشند:
        $this->items = array_map(fn($i) => clone $i, $this->items);
    }
}

$a = new Order(new Address('Tehran'));
$b = clone $a;
$b->address->city = 'Shiraz';
echo $a->address->city;   // بدون __clone: Shiraz   |   با __clone: Tehran

در Laravel، $query->clone() برای Query Builder و $model->replicate() برای ساخت کپی مدل بدون کلید اصلی استفاده می‌شوند؛ Carbon نیز copy() دارد و نسخهٔ CarbonImmutable مشکل تغییر ناخواستهٔ تاریخ را حل می‌کند.

معنای انتقال: Object، Array و Reference

  • Array و اسکالرها by value منتقل می‌شوند، اما با Copy-on-Write: کپی واقعی فقط زمانی انجام می‌شود که یکی از دو طرف تغییر کند. پس پاس دادن یک آرایهٔ بزرگ به تابع به‌خودی‌خود گران نیست.
  • Objectها by handle منتقل می‌شوند: متغیر، شناسهٔ object را نگه می‌دارد. با پاس دادن object به تابع، کپی handle پاس می‌شود؛ تغییر propertyها در تابع بیرون دیده می‌شود، ولی جایگزین کردن متغیر داخل تابع روی بیرون اثر ندارد. این دقیقاً «pass by reference» نیست.
  • Reference (&) دو نام برای یک zval می‌سازد؛ جایگزین کردن یکی، دیگری را هم عوض می‌کند.

مقایسهٔ Objectها

  • $a == $b: هر دو از یک کلاس باشند و همهٔ propertyها (به‌صورت loose و بازگشتی) برابر باشند.
  • $a === $b: هر دو به همان instance اشاره کنند.
  • برای Value Object بهتر است متد equals() صریح نوشته شود. در Eloquent، $a->is($b) کلید، جدول و connection را مقایسه می‌کند.

Closure و Arrow Function

Closure یک تابع بی‌نام است که به‌صورت object از کلاس Closure نمایش داده می‌شود و می‌تواند متغیرهای scope بیرونی را capture کند. در PHP، capture صریح است (با use).

<?php

Binding: bind، bindTo، call

closureی که داخل متد کلاس تعریف شود، $this را خودکار bind می‌کند. با static function یا static fn این کار انجام نمی‌شود (کمی حافظه صرفه‌جویی و جلوگیری از نگه داشتن ناخواستهٔ object). می‌توان closure را به object و scope دیگری متصل کرد:

<?php
class Counter { private int $count = 42; }

$peek = function () { return $this->count; };

$bound = Closure::bind($peek, new Counter, Counter::class);  // newThis + newScope
echo $bound();                                                 // 42 (دسترسی به private!)

echo $peek->call(new Counter);       // 42 — bind موقت و اجرای فوری (7.0)
$b2 = $peek->bindTo(new Counter, Counter::class);

Laravel از همین مکانیزم در Macroable استفاده می‌کند: Collection::macro('toUpper', function () { return $this->map(...); })؛ closure هنگام اجرا به instance کالکشن bind می‌شود تا $this در آن کار کند.

در پروسس‌های طولانی (Octane، queue worker)، closureهایی که $this یا objectهای بزرگ را capture می‌کنند و در یک لیست static ذخیره می‌شوند، باعث memory leak می‌شوند. همچنین closureها به‌طور بومی serializable نیستند؛ Laravel برای queue کردن closure از laravel/serializable-closure استفاده می‌کند.

Generator، Iterator و اینترفیس‌های SPL

Generator تابعی است که به‌جای return یک مجموعهٔ کامل، با yield مقادیر را یکی‌یکی و تنبل (lazy) تولید می‌کند. صدا زدن آن بدنه را اجرا نمی‌کند؛ یک object از کلاس Generator (که Iterator را پیاده می‌کند) برمی‌گرداند. اجرا هر بار تا yield بعدی پیش می‌رود و state توابع (متغیرهای محلی) حفظ می‌شود.

<?php
// بدون generator: کل فایل در حافظه — برای فایل 2GB با memory_limit خطا می‌دهد
$lines = file('huge.csv');

// با generator: در هر لحظه فقط یک خط در حافظه
function readCsv(string $path): Generator
{
    $h = fopen($path, 'r');
    try {
        while (($row = fgetcsv($h)) !== false) {
            yield $row;                  // اجرا اینجا متوقف و مقدار تحویل داده می‌شود
        }
    } finally {
        fclose($h);                      // حتی اگر مصرف‌کننده زودتر break کند
    }
}

foreach (readCsv('huge.csv') as $i => $row) {
    // پردازش ...
}

function kv(): Generator {
    yield 'a' => 1;                      // کلید سفارشی
    yield from ['b' => 2, 'c' => 3];     // delegation به iterable یا generator دیگر
    return 'done';                       // با getReturn() خوانده می‌شود
}
  • مزیت حافظه: مصرف حافظه O(1) نسبت به تعداد آیتم‌ها به‌جای O(n).
  • Pipeline تنبل: می‌توان generatorها را زنجیر کرد و فقط به اندازهٔ نیاز محاسبه کرد (حتی دنبالهٔ بی‌نهایت).
  • متد send() مقداری را به داخل generator می‌فرستد (به‌عنوان نتیجهٔ عبارت yield) — پایهٔ coroutineهای قدیمی.
  • محدودیت: generator یک‌بارمصرف است و پس از شروع پیمایش قابل rewind نیست؛ count() هم ندارد.

در Laravel: User::cursor() با یک کوئری و generator رکوردها را یکی‌یکی hydrate می‌کند (حافظهٔ PHP کم، اما driver ممکن است نتایج را buffer کند)؛ lazy() و chunk() با چند کوئری صفحه‌بندی‌شده کار می‌کنند. LazyCollection روی generator ساخته شده است. پاسخ خوب در سوال «چطور یک میلیون رکورد را export کنیم؟» باید به این‌ها اشاره کند.

Iterator، IteratorAggregate، ArrayAccess و Countable

<?php
final class Cart implements IteratorAggregate, Countable, ArrayAccess
{
    private array $items = [];

    public function getIterator(): Iterator           // IteratorAggregate: ساده‌تر از Iterator کامل
    {
        return new ArrayIterator($this->items);       // یا: yield from $this->items;
    }

    public function count(): int { return count($this->items); }      // count($cart)

    public function offsetExists(mixed $k): bool { return isset($this->items[$k]); }
    public function offsetGet(mixed $k): mixed { return $this->items[$k] ?? null; }
    public function offsetSet(mixed $k, mixed $v): void
    {
        $k === null ? $this->items[] = $v : $this->items[$k] = $v;    // $cart[] = $item
    }
    public function offsetUnset(mixed $k): void { unset($this->items[$k]); }
}

$cart = new Cart();
$cart[] = 'book';
foreach ($cart as $item) { /* ... */ }
echo count($cart);   // 1
  • Iterator: پنج متد current، key، next، rewind، valid را خودتان پیاده می‌کنید.
  • IteratorAggregate: فقط getIterator() که یک Traversable برمی‌گرداند (معمولاً یک generator). Illuminate\Support\Collection همین را پیاده می‌کند، به‌علاوهٔ ArrayAccess، Countable و JsonSerializable.
  • Traversable اینترفیس پایه است و فقط از طریق Iterator یا IteratorAggregate پیاده‌سازی می‌شود. نوع iterable یعنی array|Traversable.

Namespace، Composer، Autoloading و PSRها

Namespace

namespace از تداخل نام کلاس‌ها، توابع و ثابت‌ها جلوگیری می‌کند و ساختار منطقی کد را نشان می‌دهد. use فقط یک alias در زمان compile می‌سازد و چیزی را بارگذاری نمی‌کند.

<?php
namespace App\Services\Payment;

use App\Models\Order;
use Illuminate\Support\Facades\Log as Logger;      // alias
use function App\Support\money_format;             // import تابع
use const App\Support\MAX_RETRY;                   // import ثابت

$x = strlen('a');   // ابتدا App\Services\Payment\strlen جست‌وجو و سپس به تابع global برمی‌گردد
$y = \strlen('a');  // مستقیم global (کمی سریع‌تر؛ OPcache برخی توابع را inline می‌کند)
$c = new \DateTime(); // کلاس‌ها fallback به global ندارند؛ بدون \ یا use خطا می‌دهد

fallback به global فقط برای توابع و ثابت‌ها است، نه کلاس‌ها. new DateTime() داخل یک namespace بدون use DateTime یا \DateTime، کلاس App\...\DateTime را جست‌وجو می‌کند و خطا می‌دهد.

map / filter / reduce

<?php
$orders = [['id' => 1, 'total' => 500, 'paid' => true], ['id' => 2, 'total' => 300, 'paid' => false]];

$totals = array_map(fn($o) => $o['total'], $orders);              // callback اول، آرایه دوم
$paid   = array_filter($orders, fn($o) => $o['paid']);            // آرایه اول، callback دوم!

array_filter($arr, fn($v, $k) => ..., ARRAY_FILTER_USE_BOTH);
array_map(null, [1, 2], ['a', 'b']);                   // zip: [[1,'a'], [2,'b']]
array_column($orders, 'total', 'id');                  // [1 => 500, 2 => 300]

array_filter کلیدها را حفظ می‌کند؛ نتیجهٔ فیلتر [0 => a, 2 => c] است و json_encode آن را به object تبدیل می‌کند ({"0":"a","2":"c"}) نه آرایه. برای لیست، array_values() بزنید (در Laravel: ->filter()->values()). array_map با یک آرایه کلیدها را حفظ می‌کند.

Cookie

  • داده در مرورگر ذخیره می‌شود و با هر درخواست ارسال می‌شود (حدود 4KB).
  • قابل خواندن و دست‌کاری توسط کاربر؛ نباید دادهٔ حساس رمزنشده در آن باشد.
  • Laravel همهٔ کوکی‌ها را با middleware EncryptCookies رمز و امضا می‌کند.

  • داده در سرور (فایل، Redis، DB) و فقط یک session ID در کوکی است.
  • در PHP بومی: session_start() و $_SESSION.
  • Laravel مکانیزم session مستقل خودش را دارد و از $_SESSION استفاده نمی‌کند.

$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,   // از 8.0 پیش‌فرض است
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,                    // prepare واقعی سمت سرور
]);

// ❌ آسیب‌پذیر: $_GET['email'] = "' OR 1=1 --"
$pdo->query("SELECT * FROM users WHERE email = '{$_GET['email']}'");

// ✅ prepared statement: داده جدا از ساختار کوئری ارسال می‌شود
$stmt = $pdo->prepare('SELECT * FROM users WHERE email = :email AND status = :status');
$stmt->execute(['email' => $email, 'status' => 'active']);
$user = $stmt->fetch();

// placeholder برای نام جدول/ستون کار نمی‌کند → whitelist
$col = in_array($_GET['sort'], ['name', 'created_at'], true) ? $_GET['sort'] : 'id';

prepared statement یعنی ساختار کوئری و داده جداگانه به دیتابیس می‌رسند؛ پس داده هرگز به‌عنوان SQL تفسیر نمی‌شود. Eloquent و Query Builder به‌طور پیش‌فرض binding دارند، اما whereRaw، DB::raw، orderByRaw و نام ستونی که از ورودی کاربر می‌آید (مثل orderBy($request->sort)) همچنان نقطهٔ خطرند.

مدیریت حافظه، Garbage Collection و Static Analysis

Reference Counting

هر مقدار در PHP داخل یک ساختار zval نگه داشته می‌شود. برای انواع پیچیده (string، array، object) یک refcount وجود دارد که تعداد متغیرهای اشاره‌کننده را می‌شمارد. وقتی refcount به صفر برسد، حافظه بلافاصله آزاد می‌شود (و __destruct صدا زده می‌شود). copy-on-write هم بر همین اساس کار می‌کند: کپی فقط وقتی انجام می‌شود که مقداری با refcount بزرگ‌تر از 1 تغییر کند.

چرخه‌ها (Cycles) و Cycle Collector

<?php
$a = new stdClass;
$b = new stdClass;
$a->b = $b;
$b->a = $a;      // چرخه
unset($a, $b);   // refcount هر کدام 1 می‌ماند → با شمارش مرجع آزاد نمی‌شوند

gc_collect_cycles();   // اجرای دستی cycle collector؛ تعداد آزادشده را برمی‌گرداند
  • PHP یک cycle collector دارد که «rootهای مشکوک» را در یک buffer جمع می‌کند و وقتی buffer پر شد، الگوریتم mark-and-sweep را روی آن‌ها اجرا می‌کند تا چرخه‌های بی‌استفاده را پیدا و آزاد کند.
  • WeakReference (7.4) و WeakMap (8.0) اجازه می‌دهند به object اشاره کنیم بدون اینکه refcount آن را بالا ببریم؛ مناسب برای cache مرتبط با objectها بدون جلوگیری از آزاد شدن آن‌ها.
  • ابزارها: memory_get_usage()، memory_get_peak_usage()، و profilerهایی مثل Xdebug و Blackfire.

نشت حافظه در کد Laravel بیشتر در پروسس‌های طولانی دیده می‌شود: Query Log فعال (DB::enableQueryLog())، آرایه‌های static که پر می‌شوند، listenerهایی که در هر job دوباره ثبت می‌شوند، یا بارگذاری میلیون‌ها مدل با get() به‌جای chunk/lazy/cursor.

Static Analysis

ابزارهای static analysis کد را بدون اجرا بررسی می‌کنند و باگ‌هایی را پیدا می‌کنند که در زبان dynamic تا زمان اجرا مخفی می‌مانند: صدا زدن متد روی null، نوع نادرست آرگومان، کد unreachable، propertyهای تعریف‌نشده.

  • PHPStan: سطح‌بندی (level) از 0 به بالا؛ هرچه سطح بالاتر، سخت‌گیرتر. قابلیت baseline برای پذیرش خطاهای فعلی پروژهٔ legacy و جلوگیری از خطای جدید. Larastan افزونهٔ PHPStan برای فهم magic لاراول (Facade، Eloquent، relationها).
  • Psalm: مشابه PHPStan، با قابلیت taint analysis برای ردیابی دادهٔ ورودی کاربر تا sinkهای خطرناک (SQL، HTML).
  • هر دو generics را از طریق docblock پشتیبانی می‌کنند:
<?php
/**
 * @template T of Model
 * @param class-string<T> $class
 * @return Collection<int, T>
 */
function loadAll(string $class): Collection { /* ... */ }

/** @param array{id: int, name: string, tags?: list<string>} $payload  — array shape */
function store(array $payload): void { /* ... */ }
  • ابزارهای مکمل: Rector (refactor و ارتقای خودکار نسخهٔ PHP/Laravel)، PHP-CS-Fixer و Laravel Pint (code style)، PHPUnit/Pest (تست). در CI معمولاً: Pint → PHPStan → تست‌ها.

چرا static analysis در PHP مهم است؟ چون خطای نوع در PHP تا زمان اجرای همان مسیر کد بروز نمی‌کند؛ static analyzer مانند یک «کامپایلر» عمل می‌کند و این خطاها را قبل از production می‌گیرد. type declarationهای بومی + docblockهای generic + سطح بالای PHPStan تقریباً تجربهٔ یک زبان statically typed را می‌دهند.

سوالات تشریحی

چرخهٔ اجرای یک درخواست PHP را با PHP-FPM و OPcache توضیح دهید. معماری shared-nothing چیست و چه مزایا و معایبی دارد؟

جریان درخواست: وب‌سرور (Nginx) درخواست را از طریق پروتکل FastCGI به PHP-FPM می‌دهد. FPM یک master process و یک pool از workerها دارد؛ یک worker آزاد درخواست را می‌گیرد و public/index.php را اجرا می‌کند. Zend Engine کد را tokenize، parse (AST) و به opcode کامپایل می‌کند و ماشین مجازی Zend opcodeها را اجرا می‌کند. در پایان، همهٔ حافظهٔ درخواست آزاد می‌شود و worker منتظر درخواست بعدی می‌ماند.

OPcache opcodeهای کامپایل‌شده را در shared memory نگه می‌دارد تا مرحلهٔ parse/compile در درخواست‌های بعدی حذف شود. در production با validate_timestamps=0 حتی بررسی تغییر فایل هم انجام نمی‌شود (پس از deploy باید FPM را reload کرد). JIT (8.0) یک گام جلوتر opcode را به کد ماشین تبدیل می‌کند و برای کارهای CPU-bound مفید است.

Shared-nothing: هیچ state ای از یک درخواست به درخواست بعد منتقل نمی‌شود.

  • مزایا: ایزوله بودن خطاها و leakها، سادگی، مقیاس‌پذیری افقی آسان.
  • معایب: هزینهٔ bootstrap فریم‌ورک در هر درخواست، نبود connection pool و cache درون‌حافظه‌ای، و همروندی محدود به pm.max_children چون هر worker blocking است.

مقایسه: Laravel Octane اپ را یک بار boot و در حافظه نگه می‌دارد؛ latency کمتر است ولی باید مراقب state مشترک (static، singletonهای وابسته به request) بود. راهکارهای بهینه‌سازی FPM: OPcache، config:cache/route:cache، composer dump-autoload -o.

خروجی کد زیر در PHP 8 چیست؟ تفاوت == و === را با اشاره به تغییر PHP 8 توضیح دهید. var_dump(0 == "a", "1" == "01", "10" == "1e1", 100 == "1e2", null == false, "abc" == 0, in_array("x", [0]));

خروجی: false, true, true, true, true, false, false

  • === نوع و مقدار را بدون هیچ تبدیلی مقایسه می‌کند. == ابتدا type juggling انجام می‌دهد.
  • قبل از PHP 8 در مقایسهٔ عدد با رشته، رشته به عدد تبدیل می‌شد و "a" به 0 می‌رسید؛ پس 0 == "a" برابر true بود و in_array("x", [0]) هم true می‌شد.
  • از PHP 8: اگر رشته numeric باشد، مقایسهٔ عددی؛ وگرنه عدد به رشته تبدیل و مقایسهٔ رشته‌ای انجام می‌شود. پس 0 == "a" یعنی "0" == "a" که false است.
  • "1" == "01" و "10" == "1e1": هر دو طرف رشتهٔ numeric هستند، پس به‌صورت عدد مقایسه می‌شوند (1 = 1، 10 = 10).
  • null == false: هر دو به bool تبدیل می‌شوند.

نتیجهٔ عملی: همیشه از === و پارامتر strict: true در in_array/array_search استفاده کنید. برای مقایسهٔ hash و token از hash_equals() استفاده کنید، چون علاوه بر strict بودن، در برابر timing attack مقاوم است. در کد بحرانی، match هم که strict است جایگزین مناسبی برای switch است.

declare(strict_types=1) دقیقاً چه کاری انجام می‌دهد و محدودهٔ اثر آن چیست؟ خروجی را توضیح دهید: فایل A (strict) تابع f(int $x) را تعریف کرده و فایل B (بدون strict) f("5") را صدا می‌زند.

تعریف: این directive حالت coercive پیش‌فرض را برای تبدیل اسکالرها در مرز تابع غیرفعال می‌کند؛ اگر نوع آرگومان دقیقاً با type declaration سازگار نباشد، TypeError پرتاب می‌شود. تنها استثنا widening از int به float است.

محدودهٔ اثر:

  • per-file است و باید اولین statement فایل باشد.
  • برای آرگومان‌ها، حالت فایل فراخواننده (caller) ملاک است، نه فایلی که تابع در آن تعریف شده.
  • برای return type، حالت فایلی که تابع در آن تعریف شده ملاک است.
  • روی عملگرها و شرط‌ها ("5" + 1، if ("0")) اثری ندارد.

پاسخ سناریو: چون فراخوانی در فایل B (غیر strict) انجام شده، "5" به 5 تبدیل می‌شود و خطایی رخ نمی‌دهد. اگر همین فراخوانی در فایل A بود، TypeError می‌گرفتیم.

<?php // B.php (no strict_types)
f("5");    // OK → $x = 5
f("abc");  // TypeError حتی در حالت coercive (رشتهٔ غیرعددی قابل تبدیل نیست)
f(5.5);    // در حالت coercive: float با بخش اعشاری به int، از 8.1 هشدار deprecation می‌دهد

چرا استفاده کنیم: جلوگیری از تبدیل‌های بی‌صدا که باگ را پنهان می‌کنند (مثل "1.9" که در حالت coercive به پارامتر int داده شود). هزینه: باید ورودی‌های خارجی (request، CSV) را صریحاً cast کرد؛ Laravel با FormRequest و castهای مدل این کار را ساده می‌کند.

انواع union، intersection، DNF، mixed، void، never و static را تعریف کنید و برای هر کدام یک کاربرد مثال بزنید.
  • Union A|B (8.0): مقدار یکی از چند نوع است. مثال: function find(int|string $id) برای پذیرش id عددی یا UUID.
  • Intersection A&B (8.1): مقدار باید همهٔ انواع را داشته باشد؛ فقط برای کلاس/interface. مثال: Countable&Iterator یا در تست: UserRepository&MockObject.
  • DNF (8.2): union از intersectionها، مثل (Countable&Iterator)|null.
  • mixed (8.0): هر نوعی شامل null؛ با نبود type فرق دارد چون صریحاً می‌گوید «هر چیزی عمداً مجاز است».
  • void (7.1): تابع برمی‌گردد ولی مقداری ندارد؛ مثل setter یا event handler.
  • never (8.1): تابع هرگز برنمی‌گردد (همیشه throw یا exit). مثل abort() و redirectAndExit()؛ static analyzer کد بعد از آن را unreachable می‌داند و type narrowing دقیق‌تری می‌دهد.
  • static (return، 8.0): کلاسی که متد روی آن صدا زده شده؛ برای fluent API و named constructorها در سلسله‌مراتب ارث‌بری.
<?php
abstract class Builder {
    public function limit(int $n): static { $this->limit = $n; return $this; }
}
class UserBuilder extends Builder { public function active(): static { return $this; } }
(new UserBuilder)->limit(5)->active();   // با return type «self» تحلیلگر active() را نمی‌شناخت

function denyUnless(bool $ok): void { if (!$ok) { fail(); } }
function fail(): never { throw new AuthorizationException(); }

نکته: void و never فقط برای return type هستند؛ mixed با ? یا union ترکیب نمی‌شود چون خودش null را شامل است.

match و switch را مقایسه کنید. کد زیر را با match بازنویسی کنید و توضیح دهید چه باگ پنهانی داشت. 
<?php
switch ($code) {          // $code = "0" از ورودی
    case 0:  $msg = 'OK'; break;
    case 1:  $msg = 'Warning';
    case 2:  $msg = 'Error'; break;
}

مشکلات: (1) switch مقایسهٔ loose دارد؛ "0" == 0 true است و ورودی رشته‌ای بی‌صدا match می‌شود (در PHP 7 حتی "abc" هم با case 0 برابر بود). (2) case 1 فاقد break است و به case 2 fall-through می‌کند؛ پس برای 1 پیام Error می‌شود. (3) برای مقدار ناشناخته $msg تعریف نمی‌شود.

<?php
$msg = match ((int) $code) {
    0       => 'OK',
    1       => 'Warning',
    2       => 'Error',
    default => throw new UnexpectedValueException("Unknown code $code"),
};

مقایسه:

  • match یک expression است و مقدار برمی‌گرداند؛ switch statement است.
  • match با === مقایسه می‌کند؛ پس cast صریح لازم است.
  • fall-through ندارد؛ چند مقدار با کاما در یک شاخه قرار می‌گیرند.
  • اگر هیچ شاخه‌ای match نشود و default نباشد، UnhandledMatchError می‌دهد (fail-fast).
  • محدودیت: هر شاخه فقط یک expression است؛ برای منطق چندخطی باید تابع صدا زد یا همچنان از switch/if استفاده کرد.
Enumها در PHP 8.1 را توضیح دهید. تفاوت pure و backed enum چیست؟ یک enum برای وضعیت سفارش با منطق انتقال وضعیت پیاده‌سازی کنید و مزیت آن را نسبت به class constants بگویید.

تعریف: enum نوعی با مجموعهٔ بسته و از پیش تعیین‌شده از مقادیر است؛ هر case یک object یکتا (singleton) است. Pure enum فقط نام case دارد؛ backed enum برای هر case یک مقدار int یا string دارد که برای ذخیره در دیتابیس یا JSON استفاده می‌شود و متدهای from() (با ValueError) و tryFrom() (با null) دارد.

<?php
enum OrderStatus: string
{
    case Pending = 'pending';
    case Paid = 'paid';
    case Shipped = 'shipped';
    case Cancelled = 'cancelled';

    /** @return list<self> */
    public function allowedNext(): array
    {
        return match ($this) {
            self::Pending => [self::Paid, self::Cancelled],
            self::Paid    => [self::Shipped, self::Cancelled],
            self::Shipped, self::Cancelled => [],
        };
    }

    public function canTransitionTo(self $to): bool
    {
        return in_array($to, $this->allowedNext(), true);
    }
}

// Laravel: protected $casts = ['status' => OrderStatus::class];
if (! $order->status->canTransitionTo(OrderStatus::Shipped)) {
    throw new DomainException('Invalid transition');
}

مزیت نسبت به ثابت‌ها:

  • Type safety: امضای ship(OrderStatus $s) فقط مقادیر معتبر را می‌پذیرد؛ با ثابت، هر string قابل ارسال است.
  • رفتار (label، رنگ، قوانین انتقال) کنار داده قرار می‌گیرد.
  • match بدون default روی enum، اگر case جدیدی اضافه شود و پوشش داده نشود، خطای زمان اجرا (و هشدار static analyzer) می‌دهد.
  • cases() برای validation و فرم.

محدودیت: enum state و property ندارد، قابل ارث‌بری نیست و با new ساخته نمی‌شود؛ اما می‌تواند interface پیاده کند و ثابت و متد static داشته باشد.

readonly property و readonly class چیست؟ چگونه با آن‌ها یک Value Object immutable بسازیم؟ محدودیت‌ها و تفاوت با asymmetric visibility در PHP 8.4 را بیان کنید.

تعریف: property با modifier readonly (8.1) فقط یک بار و فقط از داخل scope کلاس مقداردهی می‌شود؛ هر تلاش بعدی Error می‌دهد. readonly class (8.2) همهٔ propertyها را readonly و dynamic property را ممنوع می‌کند.

<?php
final readonly class Email
{
    public string $value;

    public function __construct(string $value)
    {
        $value = strtolower(trim($value));
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException("Invalid email: $value");
        }
        $this->value = $value;
    }

    public function equals(self $other): bool { return $this->value === $other->value; }
}

final readonly class Money
{
    public function __construct(public int $amount, public string $currency) {}
    public function withAmount(int $amount): static { return new static($amount, $this->currency); }
}

محدودیت‌ها:

  • باید typed باشد و مقدار پیش‌فرض در تعریف نمی‌گیرد.
  • immutability سطحی است؛ اگر property یک object قابل تغییر (مثل DateTime) باشد، درونش تغییر می‌کند. باید از DateTimeImmutable یا VOهای readonly استفاده کرد.
  • تغییر به‌روش «wither» (ساخت object جدید) انجام می‌شود. در 8.3 مقداردهی دوباره در __clone مجاز شد که الگوی clone-and-modify را ممکن می‌کند.

تفاوت با public private(set) (8.4): readonly یعنی «یک بار برای همیشه»؛ asymmetric visibility یعنی «بیرون فقط بخواند، اما خود کلاس هر چند بار خواست بنویسد». اولی برای Value Object و DTO و دومی برای Entity با state کنترل‌شده (مثل Order::$status که فقط از طریق متد pay() عوض می‌شود) مناسب است.

تفاوت self، static و parent چیست؟ Late Static Binding را توضیح دهید و خروجی کد زیر را بنویسید. 
<?php
class A {
    public static function name() { return 'A'; }
    public static function viaSelf() { return self::name(); }
    public static function viaStatic() { return static::name(); }
    public static function make() { return new static(); }
}
class B extends A {
    public static function name() { return 'B'; }
}
echo B::viaSelf(), B::viaStatic(), get_class(B::make());

خروجی: ABB

  • self:: در زمان کامپایل به کلاسی که کد در آن نوشته شده (A) resolve می‌شود؛ پس B::viaSelf() همچنان A::name() را صدا می‌زند.
  • static:: از Late Static Binding استفاده می‌کند: در زمان اجرا به کلاسی که فراخوانی از آن آغاز شده («called class»، اینجا B) resolve می‌شود.
  • new static() instance از کلاس فراخواننده می‌سازد، پس B.
  • parent:: متد/ثابت کلاس والد را صدا می‌زند (مثلاً parent::__construct()) و «called class» را هم حفظ می‌کند.

کاربرد: Active Record در Eloquent: User::create([...]) و User::query() در Model تعریف شده‌اند ولی با new static و static:: مدل درست (User) را می‌سازند. همچنین return type static برای fluent API.

نکته: اگر کلاس final باشد، self و static عملاً یکسان‌اند. استفاده از new static در کلاس غیر final یعنی فرض کرده‌ایم constructor فرزندان سازگار است؛ برای اطمینان می‌توان constructor را final کرد یا در interface تعریف کرد.

Abstract class، interface و trait را مقایسه کنید. در چه شرایطی از هر کدام استفاده می‌کنید؟
  • Interface: یک قرارداد (چه کاری انجام می‌شود) بدون پیاده‌سازی. یک کلاس چند interface پیاده می‌کند. ابزار اصلی Dependency Inversion و polymorphism است: کد به PaymentGateway وابسته است نه به StripeGateway. در Laravel، Contracts و binding در container.
  • Abstract class: پیاده‌سازی مشترک ناقص برای خانواده‌ای از کلاس‌ها با رابطهٔ is-a. می‌تواند state، constructor و متد concrete داشته باشد. فقط یک والد مجاز است. مناسب Template Method (مثل Illuminate\Console\Command).
  • Trait: استفادهٔ مجدد افقی از کد بین کلاس‌های بی‌ربط؛ کد در کلاس کپی می‌شود. نوع نیست و قابل type-hint نیست. مناسب قابلیت‌های cross-cutting کوچک (SoftDeletes، Notifiable).
<?php
interface Exporter { public function export(iterable $rows): string; }

abstract class FileExporter implements Exporter          // اسکلت مشترک
{
    public function export(iterable $rows): string
    {
        $out = $this->header();
        foreach ($rows as $r) { $out .= $this->row($r); }
        return $out;
    }
    abstract protected function header(): string;
    abstract protected function row(array $r): string;
}

trait Timestamps { public function touch(): void { $this->updatedAt = new DateTimeImmutable(); } }

final class CsvExporter extends FileExporter { /* header() و row() */ }

قاعدهٔ انتخاب: اول interface (برای قرارداد و تست‌پذیری)؛ اگر چند پیاده‌سازی کد مشترک زیادی دارند، یک abstract class که interface را پیاده کند؛ trait فقط برای رفتار کوچک و مستقل که ارث‌بری برایش معنایی ندارد. در اغلب موارد composition (تزریق یک سرویس) از ارث‌بری و trait بهتر است، چون وابستگی را صریح و قابل جایگزینی می‌کند.

اگر دو trait متد هم‌نام داشته باشند چه اتفاقی می‌افتد؟ راه‌های حل تعارض و قابلیت‌های trait (abstract، static، property) را با کد نشان دهید.

اگر کلاس از دو trait با متد هم‌نام استفاده کند و تعارض را حل نکند، Fatal error می‌گیریم. برای حل:

  • insteadof: انتخاب یکی از دو پیاده‌سازی.
  • as: ساخت alias برای دیگری و/یا تغییر visibility.
  • یا تعریف همان متد در خود کلاس (متد کلاس بر trait اولویت دارد).
<?php
trait FileLogger  { public function log(string $m) { /* file */ } }
trait SlackLogger { public function log(string $m) { /* slack */ } }

trait Counts
{
    private static int $instances = 0;               // هر کلاس استفاده‌کننده نسخهٔ جدای خود را دارد
    abstract public function id(): int;              // الزام کلاس میزبان
    public static function created(): int { return self::$instances; }
    public function __construct() { self::$instances++; }
}

class Reporter
{
    use FileLogger, SlackLogger, Counts {
        FileLogger::log insteadof SlackLogger;
        SlackLogger::log as protected notifySlack;
    }
    public function id(): int { return 1; }

    public function report(string $m): void
    {
        $this->log($m);          // FileLogger
        $this->notifySlack($m);  // SlackLogger
    }
}

ترتیب اولویت: متد کلاس > متد trait > متد ارث‌برده از والد. propertyهای هم‌نام بین trait و کلاس فقط در صورت سازگاری کامل مجازند. از PHP 8.2 trait می‌تواند ثابت داشته باشد.

نقد: trait وابستگی ضمنی به میزبان ایجاد می‌کند؛ متد abstract این وابستگی را دست‌کم صریح می‌کند. در Laravel، Eloquent متدهای bootSoftDeletes و initializeSoftDeletes را برای راه‌اندازی خودکار trait صدا می‌زند.

Magic methodهای __get، __call، __callStatic و __invoke را توضیح دهید. Laravel چگونه از آن‌ها استفاده می‌کند و معایبشان چیست؟
  • __get($name) / __set: هنگام دسترسی به property ناموجود یا غیرقابل دسترس. در Eloquent، $user->email از آرایهٔ داخلی $attributes خوانده می‌شود و accessorها، castها و relationها (lazy loading) از همین مسیر اعمال می‌شوند.
  • __isset: بدون آن isset($user->email) و ?? روی attributeهای magic همیشه false/پیش‌فرض می‌دادند.
  • __call: متد instance ناموجود. مدل Eloquent متدهای ناشناخته را به Eloquent Builder forward می‌کند ($user->newQuery()->where())؛ همچنین Macroable.
  • __callStatic: متد static ناموجود. User::where(...) یک instance می‌سازد و فراخوانی را به __call می‌دهد؛ Facadeها هم instance واقعی را از container resolve می‌کنند و متد را روی آن صدا می‌زنند.
  • __invoke: object را callable می‌کند؛ Single Action Controller، invokable rule و listener.
<?php
abstract class Facade
{
    public static function __callStatic(string $method, array $args): mixed
    {
        $instance = app(static::accessor());     // resolve از container
        return $instance->$method(...$args);
    }
    abstract protected static function accessor(): string;
}

معایب: کندتر از دسترسی مستقیم؛ نامرئی برای IDE و static analysis (نیاز به @property/@method، ide-helper یا Larastan)؛ خطای تایپی ($user->emial) به‌جای خطای واضح، null برمی‌گرداند؛ دیباگ دشوارتر. توصیه: در کد دامنهٔ خودتان کم و آگاهانه استفاده کنید و در __call برای متد ناشناخته BadMethodCallException پرتاب کنید.

کد زیر چه مشکلی دارد؟ تفاوت shallow copy و deep copy را توضیح دهید و کد را اصلاح کنید. 
<?php
class Invoice {
    public function __construct(public DateTime $dueDate, public array $lines = []) {}
}
$template = new Invoice(new DateTime('2026-01-01'));
$copy = clone $template;
$copy->dueDate->modify('+30 days');
echo $template->dueDate->format('Y-m-d');   // ؟

مشکل: خروجی 2026-01-31 است، یعنی template هم تغییر کرد. clone یک shallow copy است: اسکالرها و آرایه‌ها کپی می‌شوند، اما propertyهایی که object هستند فقط handle کپی می‌کنند و هر دو object به همان DateTime اشاره می‌کنند.

Deep copy یعنی objectهای تودرتو هم کپی شوند. این کار در متد __clone انجام می‌شود که روی object جدید و پس از کپی سطحی صدا زده می‌شود:

<?php
class Invoice {
    public function __construct(public DateTime $dueDate, public array $lines = []) {}

    public function __clone(): void
    {
        $this->dueDate = clone $this->dueDate;
        $this->lines = array_map(fn(Line $l) => clone $l, $this->lines);   // آرایهٔ object
    }
}

// راه‌حل بهتر: immutability
class Invoice2 {
    public function __construct(public readonly DateTimeImmutable $dueDate) {}
}
$due = $invoice->dueDate->modify('+30 days');   // object جدید؛ اصلی دست نمی‌خورد

جمع‌بندی: برای objectهای قابل تغییر تودرتو، __clone را پیاده کنید؛ اما راه‌حل ریشه‌ای استفاده از objectهای immutable (DateTimeImmutable، CarbonImmutable، Value Objectهای readonly) است که اصلاً نیاز به deep copy را از بین می‌برد. مراقب ارجاع‌های حلقوی در deep copy دستی هم باشید.

«در PHP objectها by reference پاس داده می‌شوند» — این جمله را نقد کنید. خروجی کد زیر را توضیح دهید. 
<?php
function a(array $x) { $x[] = 4; }
function b(stdClass $o) { $o->v = 2; }
function c(stdClass $o) { $o = new stdClass(); $o->v = 3; }
function d(array &$x) { $x[] = 4; }

$arr = [1, 2, 3]; $obj = new stdClass(); $obj->v = 1;
a($arr); b($obj); c($obj); d($arr);
echo count($arr), $obj->v;

خروجی: 42 (آرایه 4 عضو، v برابر 2).

  • جملهٔ صورت سوال دقیق نیست. objectها «by handle» (یا pass-by-sharing) منتقل می‌شوند: متغیر یک شناسه به object را نگه می‌دارد و هنگام پاس دادن، کپی همین شناسه by value پاس می‌شود.
  • b: از طریق handle، state همان object تغییر کرد، پس بیرون دیده می‌شود.
  • c: متغیر محلی $o به object جدید اشاره داده شد؛ متغیر بیرونی همچنان object قبلی را نگه می‌دارد. اگر واقعاً by reference بود، بیرون هم عوض می‌شد.
  • a: آرایه by value (با copy-on-write) پاس شد؛ تغییر روی کپی بود.
  • d: با & آرایه واقعاً by reference پاس شد.

پیامد طراحی: چون objectها قابل تغییر از راه دورند، تابعی که object می‌گیرد می‌تواند side effect پنهان داشته باشد؛ دلیل دیگری برای Value Objectهای immutable. reference (&) را فقط در موارد خاص استفاده کنید؛ copy-on-write را می‌شکند و دنبال کردن جریان داده را سخت می‌کند (مثلاً دام foreach ($a as &$v) بدون unset($v)).

<?php

$f1 = function () use ($x) { return $x; };
$f2 = function () use (&$x) { return $x; };
$f3 = fn() => $x;

خروجی: 1210

  • $f1: use ($x) مقدار را در لحظهٔ تعریف کپی می‌کند → 1.
  • $f2: use (&$x) reference می‌گیرد → مقدار فعلی 2.
  • $f3: arrow function هم متغیرها را by value و در لحظهٔ تعریف capture می‌کند (خودکار) → 1.
  • $total: arrow function نمی‌تواند متغیر بیرونی را تغییر دهد؛ += روی کپی محلی انجام می‌شود → 0.

مقایسه: closure معمولی capture صریح با use دارد و می‌تواند by reference بگیرد و چند statement داشته باشد. arrow function (7.4) کوتاه است، کل scope را خودکار by value می‌گیرد و فقط یک expression دارد؛ مناسب callbackهای map/filter. هر دو در context کلاس $this را خودکار bind می‌کنند مگر با static تعریف شوند.

راه درست جمع زدن: array_sum یا array_reduce($nums, fn($c, $n) => $c + $n, 0)؛ یعنی به‌جای side effect، مقدار را برگردانید.

Generator چیست و چه مزیتی در مصرف حافظه دارد؟ یک تابع برای خواندن و فیلتر کردن یک فایل لاگ چندگیگابایتی پیاده‌سازی کنید و معادل آن در Laravel را نام ببرید.

تعریف: تابعی که yield دارد، هنگام صدا زدن اجرا نمی‌شود و یک object Generator (پیاده‌کنندهٔ Iterator) برمی‌گرداند. هر بار که مصرف‌کننده مقدار بعدی را می‌خواهد، اجرا تا yield بعدی جلو می‌رود و سپس با حفظ state متوقف می‌شود. یعنی ارزیابی lazy است.

مزیت حافظه: به‌جای ساخت آرایهٔ کامل (O(n) حافظه)، در هر لحظه فقط یک آیتم در حافظه است (O(1)). پردازش جریانی، pipelineهای تنبل و حتی دنباله‌های بی‌نهایت ممکن می‌شوند.

<?php
function lines(string $path): Generator
{
    $h = fopen($path, 'rb') ?: throw new RuntimeException("Cannot open $path");
    try {
        while (($line = fgets($h)) !== false) {
            yield rtrim($line, "\n");
        }
    } finally {
        fclose($h);                       // اجرا می‌شود حتی اگر مصرف‌کننده break کند
    }
}

function filterLevel(iterable $lines, string $level): Generator
{
    foreach ($lines as $n => $line) {
        if (str_contains($line, ".$level:")) {
            yield $n + 1 => $line;        // شمارهٔ خط به‌عنوان کلید
        }
    }
}

foreach (filterLevel(lines('/var/log/app.log'), 'ERROR') as $no => $line) {
    echo "$no: $line\n";
}

محدودیت‌ها: یک‌بارمصرف است (پس از شروع rewind نمی‌شود)، count() ندارد و دسترسی تصادفی ممکن نیست.

در Laravel: LazyCollection::make(fn() => yield ...) و File::lines()؛ برای دیتابیس Model::cursor() (یک کوئری، hydrate تک‌به‌تک) و lazy()/lazyById() (کوئری‌های صفحه‌ای پشت یک LazyCollection) و chunk().

سلسله‌مراتب Throwable در PHP را توضیح دهید. تفاوت Error و Exception چیست؟ خروجی کد زیر چیست؟ 
<?php
function f() {
    try {
        echo intdiv(1, 0);
    } catch (Exception $e) {
        return 'exception';
    } finally {
        echo 'cleanup ';
    }
    return 'end';
}
try { echo f(); } catch (Throwable $t) { echo get_class($t); }

خروجی: cleanup DivisionByZeroError

intdiv(1, 0) یک DivisionByZeroError پرتاب می‌کند که زیرکلاس Error است نه Exception؛ پس catch (Exception) آن را نمی‌گیرد. finally قبل از انتشار خطا به بیرون اجرا می‌شود و در بیرون catch (Throwable) آن را می‌گیرد.

  • Throwable: interface ریشه؛ فقط از طریق Error یا Exception پیاده می‌شود.
  • Error: خطاهای داخلی موتور که معمولاً نشانهٔ باگ هستند: TypeError، ArgumentCountError، ValueError، DivisionByZeroError، UnhandledMatchError، صدا زدن متد روی null. از PHP 7 قابل catch شدند (قبلاً fatal بودند).
  • Exception: شرایط استثنایی قابل انتظار که برنامه باید مدیریت کند. شاخه‌های SPL: LogicException (خطای منطق کد، مثل InvalidArgumentException) و RuntimeException (خطای محیط زمان اجرا).

قواعد: exceptionهای سفارشی را از Exception/زیرکلاس‌های SPL ارث ببرید، نه Error؛ Throwable را فقط در مرزها (handler سراسری، worker) catch کنید؛ از previous برای chaining استفاده کنید؛ و در finally هرگز return نگذارید چون exception را می‌بلعد.

Composer و استاندارد PSR-4 را توضیح دهید. autoloading چگونه کار می‌کند و برای production چه بهینه‌سازی‌هایی لازم است؟

Composer مدیر وابستگی PHP است: وابستگی‌ها را طبق constraintهای composer.json resolve می‌کند، نسخه‌های دقیق را در composer.lock ثبت می‌کند، در vendor/ نصب می‌کند و یک autoloader (vendor/autoload.php) تولید می‌کند.

Autoloading: با spl_autoload_register تابعی ثبت می‌شود که وقتی کلاسی برای اولین بار استفاده می‌شود و هنوز تعریف نشده، نام کامل کلاس را می‌گیرد و فایلش را require می‌کند؛ پس فقط کلاس‌های مورد استفاده بارگذاری می‌شوند و نیازی به require دستی نیست.

PSR-4: یک namespace prefix به یک پوشهٔ پایه نگاشت می‌شود و بقیهٔ نام کلاس به زیرپوشه‌ها و نام فایل:

"autoload": { "psr-4": { "App\\": "app/" } }
App\Domain\Billing\Invoice  →  app/Domain/Billing/Invoice.php

هر فایل یک کلاس، نام فایل دقیقاً برابر نام کلاس (حساس به حروف روی لینوکس — منبع رایج خطای «class not found» که فقط روی سرور رخ می‌دهد).

بهینه‌سازی production:

  • composer install --no-dev --optimize-autoloader: ساخت classmap کامل و حذف پکیج‌های dev.
  • --classmap-authoritative: فقط از classmap، بدون جست‌وجوی فایل‌سیستم.
  • OPcache روشن و commit کردن composer.lock تا همهٔ محیط‌ها نسخهٔ یکسان داشته باشند.

install در برابر update: install lock را نصب می‌کند (قطعی و قابل تکرار)؛ update lock را تغییر می‌دهد و باید آگاهانه و همراه با تست اجرا شود.

PSR-7، PSR-11 و PSR-15 را تعریف کنید. چرا استانداردهای PSR مهم‌اند و Laravel تا چه حد از آن‌ها پیروی می‌کند؟
  • PSR-7 (HTTP Message): interfaceهایی مثل RequestInterface، ServerRequestInterface، ResponseInterface، StreamInterface و UriInterface. ویژگی کلیدی immutability است: $r2 = $r->withHeader('X', 'y') object جدید برمی‌گرداند. Laravel از Symfony HttpFoundation (قابل تغییر) استفاده می‌کند، ولی با نصب PSR-7 bridge می‌توان در کنترلر ServerRequestInterface را type-hint کرد.
  • PSR-11 (Container): ContainerInterface با get(string $id) و has(string $id). Container لاراول آن را پیاده می‌کند؛ کتابخانه‌ها می‌توانند بدون وابستگی به Laravel از container استفاده کنند.
  • PSR-15 (Server Request Handlers): RequestHandlerInterface::handle() و MiddlewareInterface::process($request, $handler). middleware لاراول از الگوی مشابه ولی امضای اختصاصی handle(Request $request, Closure $next) استفاده می‌کند و PSR-15 نیست.
<?php
final class TimingMiddleware implements MiddlewareInterface    // PSR-15
{
    public function process(ServerRequestInterface $req, RequestHandlerInterface $handler): ResponseInterface
    {
        $start = hrtime(true);
        $res = $handler->handle($req);
        return $res->withHeader('X-Time', (string) (hrtime(true) - $start));   // immutable
    }
}

اهمیت: interoperability و کاهش vendor lock-in؛ کتابخانه به interface استاندارد وابسته می‌شود (Dependency Inversion) و با هر پیاده‌سازی کار می‌کند. Laravel از PSR-3 (Log)، PSR-4، PSR-11، PSR-16 (Cache) کامل پیروی می‌کند، برای PSR-7 پل دارد و در کدنویسی Pint با preset لاراول (مبتنی بر PSR-12) استفاده می‌شود.

  4. Session fixation: پس از login، session ID عوض نمی‌شود.
  5. XSS: name بدون escape چاپ می‌شود.

print_r($d + [5 => 'y', 'city' => 'Tehran']);

خروجی:

  • isset($d['name']) → false، چون مقدار null است. array_key_exists → true، چون کلید وجود دارد. empty($d['age']) → true، چون 0 falsy است.
  • array_merge → ['name' => null, 'age' => 30, 0 => 'x', 1 => 'y']: کلیدهای رشته‌ای را سمت راست بازنویسی می‌کند، کلیدهای عددی از نو شماره‌گذاری و الحاق می‌شوند.
  • + → ['name' => null, 'age' => 0, 5 => 'x', 'city' => 'Tehran']: union کلیدها؛ اگر کلید در سمت چپ باشد، سمت چپ برنده است و کلیدهای عددی حفظ می‌شوند.

کاربرد:

  • isset/??: بررسی سریع «وجود و غیر null بودن»، حتی برای کلیدهای تودرتو بدون warning.
  • array_key_exists: وقتی null معنادار است؛ مثلاً در PATCH باید بین «فیلد ارسال نشده» و «فیلد عمداً null شده» فرق گذاشت (در Laravel: $request->has() در برابر filled()).
  • empty: بررسی «خالی بودن» در معنای falsy؛ مراقب "0" و 0 باشید.
  • $options + $defaults برای اعمال مقادیر پیش‌فرض؛ array_merge برای الحاق لیست‌ها یا override تنظیمات.

خلاصه برای مرور سریع

اجرا

  • Source → tokens → AST → opcodes → Zend VM. OPcache = کش opcode در shared memory. JIT (8.0) = کد ماشین، مفید برای CPU-bound.
  • FPM: master + workerها؛ هر worker یک درخواست؛ همروندی = pm.max_children.
  • Shared-nothing: state بین درخواست‌ها نمی‌ماند. Octane = اپ ماندگار در حافظه؛ مراقب static و singleton.

نوع و مقایسه

  • PHP 8: 0 == "a" false؛ رشتهٔ غیرعددی → عدد به رشته تبدیل می‌شود.
  • falsy: false 0 0.0 "" "0" [] null.
  • ?? = isset/null؛ ?: = falsy؛ <=> = -1/0/1.
  • strict_types: per-file، caller تعیین می‌کند، فقط int→float مجاز، روی عملگرها بی‌اثر.

OOP

  • self = کلاس تعریف؛ static = کلاس فراخوانی (LSB)؛ Eloquent: new static.
  • Interface = قرارداد؛ Abstract = پیاده‌سازی مشترک + state؛ Trait = کپی کد افقی، نوع نیست.
  • Trait conflict: insteadof + as؛ اولویت: class > trait > parent.
  • Magic: __get/__set/__isset (Eloquent attributes)، __call/__callStatic (Builder، Facade)، __invoke (action).
  • clone سطحی است؛ deep copy در __clone؛ بهتر: immutable.
  • Object = by handle؛ array = by value + COW؛ & = reference. == object: هم‌کلاس و propertyهای برابر؛ ===: همان instance.
  • foreach (&$v) → حتماً unset($v).

Closure و Generator

  • use ($x) کپی در لحظهٔ تعریف؛ use (&$x) reference؛ fn خودکار by value و تک‌expression.
  • Closure::bind/bindTo/call تغییر $this و scope (Macroable).
  • Generator: lazy، حافظهٔ O(1)، یک‌بارمصرف؛ yield from، send، getReturn. Laravel: cursor، lazy، LazyCollection.
  • IteratorAggregate + Countable + ArrayAccess = شیء شبه‌آرایه (Collection).

خطا

  • Throwable → Error (باگ: TypeError، ValueError، DivisionByZeroError) | Exception (Logic / Runtime).
  • catch (Exception) خطای Error را نمی‌گیرد. finally همیشه اجرا؛ return در finally = بلعیدن exception.

Composer و PSR

  • PSR-4: prefix → پوشه. install از lock؛ update lock را عوض می‌کند. Prod: --no-dev -o.
  • ^1.2 = <2.0؛ ~1.2.3 = <1.3.0.
  • PSR-1/12/PER: style؛ 3: Logger؛ 4: Autoload؛ 6/16: Cache؛ 7: HTTP message (immutable)؛ 11: Container؛ 14: Events؛ 15: Middleware؛ 17/18: HTTP factory/client.
  • Laravel middleware ≠ PSR-15؛ Request ≠ PSR-7 (Symfony).

آرایه و رشته

  • array_map(cb, arr) ولی array_filter(arr, cb)؛ filter کلید را حفظ می‌کند → array_values.
  • isset null را false می‌داند؛ array_key_exists نه.
  • array_merge: عددی renumber، رشته‌ای راست برنده؛ +: چپ برنده.
  • sort توابع in-place و stable (8.0)؛ a = حفظ کلید، k = بر اساس کلید، u = callback.
  • فارسی: mb_* و regex با /u؛ strpos(...) !== false.

امنیت

  • password_hash/verify/needs_rehash؛ نه md5/sha. random_bytes، hash_equals.
  • XSS: htmlspecialchars(ENT_QUOTES) هنگام خروجی؛ Blade {{ }}.
  • SQLi: prepared statement؛ نام ستون/جدول → whitelist؛ مراقب whereRaw/orderBy($input).
  • Cookie: Secure، HttpOnly، SameSite. پس از login: session_regenerate_id(true).
