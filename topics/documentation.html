چرا و برای چه کسی

مستندات (Documentation) هر نوشته‌ای است که دانش لازم برای استفاده، توسعه، نگهداری یا اجرای یک سیستم را به انسان منتقل می‌کند؛ دانشی که از خود کد قابل استخراج نیست یا استخراجش پرهزینه است. کد به ما می‌گوید سیستم چه کاری و چگونه انجام می‌دهد؛ مستندات معمولاً باید بگوید چرا، برای چه کسی، چطور از آن استفاده کنیم و چه گزینه‌هایی کنار گذاشته شد.

هزینه‌ی نبودن مستندات

  • Onboarding کند: عضو جدید هفته‌ها وقت و وقت همکاران را صرف «پرسیدن» می‌کند.
  • Bus factor پایین: دانش فقط در ذهن یک یا دو نفر است و با رفتن آن‌ها از دست می‌رود.
  • تصمیم‌های تکراری: تیم دوباره درباره‌ی موضوعی بحث می‌کند که قبلاً تصمیمش گرفته شده، چون دلیل تصمیم ثبت نشده است.
  • حوادث طولانی‌تر: بدون runbook، زمان بازیابی (MTTR) بالا می‌رود.
  • یکپارچه‌سازی پرخطا: مصرف‌کنندگان API رفتار را حدس می‌زنند و باگ‌های یکپارچه‌سازی زیاد می‌شود.

مستندات بد از نبودنش بدتر است

مستند قدیمی و نادرست (doc rot) اعتماد را از بین می‌برد: وقتی کسی دو بار با README اشتباه به بن‌بست برسد، دیگر هیچ مستندی را نمی‌خواند. بنابراین هدف «زیاد نوشتن» نیست؛ هدف مستند کم، دقیق، قابل یافتن و به‌روز است که مالک دارد و همراه کد تغییر می‌کند.

در پاسخ به «چرا مستندسازی مهم است؟» فقط نگویید «برای فهم کد». مخاطب‌محور جواب دهید: مستندسازی ابزاری برای انتقال دانش است که هزینه‌ی onboarding، bus factor، زمان رفع حادثه و خطاهای یکپارچه‌سازی را کاهش می‌دهد؛ و هر مستند باید برای یک مخاطب و یک نیاز مشخص نوشته شود.

Comment در کد: چرا، نه چه

قاعده‌ی اصلی: کد «چه» و «چگونه» را بیان می‌کند؛ comment باید «چرا» را بگوید. commentی که فقط کد را به زبان انسانی تکرار می‌کند ارزشی اضافه نمی‌کند، با تغییر کد کهنه می‌شود و به نویز تبدیل می‌شود.

comment بد (تکرار «چه»)

// increment i by one
$i++;

// get the user by id
$user = User::find($id);

// loop over orders
foreach ($orders as $order) { /* ... */ }

comment خوب (توضیح «چرا»)

// Gateway may process a timed-out request anyway,
// so we reuse the idempotency key on retry to avoid
// charging the customer twice. See ADR-0007.
$charge = $gateway->charge($order, key: $order->payment_key);

// Intentionally not eager loading: this job processes
// one order at a time and memory is the constraint.

چه زمانی comment لازم است؟

  • دلیل یک تصمیم غیربدیهی: «چرا از این الگوریتم/کتابخانه استفاده شد» یا «چرا این راه‌حل ساده‌تر کار نمی‌کند».
  • محدودیت‌ها و workaroundها: باگ یک کتابخانه‌ی بیرونی، محدودیت API شریک، رفتار عجیب یک مرورگر؛ همراه با لینک issue.
  • قواعد کسب‌وکار که از کد بدیهی نیستند: «طبق قانون مالیات، گرد کردن باید در سطح هر ردیف انجام شود».
  • هشدار: «ترتیب این دو فراخوانی مهم است چون…»، «این متد در یک تراکنش اجرا می‌شود».
  • Regex یا الگوریتم پیچیده: توضیح هدف و یک نمونه‌ی ورودی/خروجی.
  • API عمومی (کلاس‌ها و متدهایی که دیگران مصرف می‌کنند) از طریق docblock.

commentهایی که نباید بنویسید

  • کد comment‌شده (commented-out code): Git تاریخچه را دارد؛ آن را حذف کنید.
  • تاریخچه‌ی تغییرات بالای فایل («۱۴۰۲/۰۳/۱۰ علی: افزودن فیلد»): کار Git است.
  • commentهای اجباری بی‌محتوا روی هر getter و setter.
  • commentی که بیانگر کد بد است: اگر برای توضیح یک تکه کد comment طولانی لازم است، اول بپرسید آیا با نام‌گذاری بهتر یا extract method قابل حذف است.

TODO و FIXME

// TODO(PAY-412): remove fallback after all merchants migrate to API v2 (planned Q1).
// FIXME: race condition when two workers process the same refund; tracked in PAY-398.

TODO بدون شناسه‌ی issue و مالک، عملاً «هرگز» انجام نمی‌شود. برخی تیم‌ها با یک قاعده‌ی lint، TODO بدون شماره‌ی ticket را رد می‌کنند.

آزمون سریع: «اگر این comment را حذف کنم، خواننده‌ی بعدی چیزی از دست می‌دهد که از کد قابل فهم نیست؟» اگر جواب منفی است، comment زائد است.

کد خودمستند در برابر comment

Self-documenting code کدی است که با نام‌گذاری دقیق، توابع کوچک، typeهای صریح و ساختار روشن، هدف خود را بدون comment بیان می‌کند. این اولین خط دفاع است؛ comment مکمل آن است، نه جایگزینش.

قبل

// check if user can get discount
if ($u->created_at < now()->subYear()
    && $u->orders()->count() > 10
    && ! $u->is_blocked) {
    $p = $p * 0.9; // 10% off
}

بعد

if ($customer->isEligibleForLoyaltyDiscount()) {
    $price = $price->applyDiscount(
        LoyaltyDiscount::PERCENT
    );
}

// in Customer model
public function isEligibleForLoyaltyDiscount(): bool
{
    return $this->isMemberForAtLeast(years: 1)
        && $this->completedOrdersCount() > 10
        && ! $this->is_blocked;
}

ابزارهای خودمستندسازی در PHP مدرن

  • نام‌گذاری: متغیر و متد با نام دامنه ($invoice نه $data؛ markAsPaid() نه update()).
  • Type declarations: typeهای native برای پارامتر، خروجی و property، به‌همراه declare(strict_types=1).
  • Enum به‌جای رشته و عدد جادویی: OrderStatus::Paid به‌جای 'p' یا 2.
  • Value Object: Money، Email؛ قواعد را در خود نوع کپسوله می‌کند.
  • Named arguments: retry(times: 3, sleepMilliseconds: 200) به‌جای retry(3, 200).
  • readonly و constructor property promotion برای اعلام صریح تغییرناپذیری.
  • تست‌ها به‌عنوان مستندات اجرایی: نام تست مثل it_rejects_coupon_after_expiry_date قاعده‌ی کسب‌وکار را مستند می‌کند و برخلاف comment، اگر کهنه شود fail می‌شود.

محدودیت‌های کد خودمستند

کد هرچقدر هم تمیز باشد، نمی‌تواند این‌ها را بگوید:

  • چرا این رویکرد انتخاب شد و گزینه‌های دیگر چرا رد شدند.
  • تصویر کلان: معماری، جریان داده بین سرویس‌ها، وابستگی‌های بیرونی.
  • نحوه‌ی استفاده برای کسی که به کد دسترسی ندارد (مصرف‌کننده‌ی API).
  • دانش عملیاتی: نحوه‌ی deploy، پیکربندی، واکنش به حادثه.

جمع‌بندی برای پاسخ تشریحی: «کد خودمستند و comment رقیب نیستند. با نام‌گذاری، type، enum و توابع کوچک، نیاز به commentهای "چه" را حذف می‌کنیم؛ comment را برای "چرا"، محدودیت‌ها و هشدارها نگه می‌داریم؛ و دانش سطح بالاتر (معماری، تصمیم‌ها، عملیات) را در مستندات جداگانه مثل README، ADR و runbook ثبت می‌کنیم.» جمله‌ی «کد خوب نیازی به مستندات ندارد» یک ساده‌سازی نادرست است.

PHPDoc و Docblock

PHPDoc قالب استاندارد (de facto) برای comment ساخت‌یافته در PHP است که با /** ... */ شروع می‌شود. پیش‌نویس‌های PSR-5 و PSR-19 آن را توصیف می‌کنند ولی هیچ‌کدام به‌طور رسمی پذیرفته نشده‌اند؛ با این حال IDEها (PhpStorm)، ابزارهای static analysis (PHPStan، Psalm) و تولیدکننده‌های مستندات (phpDocumentor) آن را می‌فهمند.

وقتی type native کافی است، docblock تکراری ننویسید

زائد

/**
 * Get the user name.
 *
 * @param int $id
 * @return string
 */
public function name(int $id): string

مفید

/**
 * @param list<int> $ids
 * @return Collection<int, User>
 *
 * @throws ModelNotFoundException
 *         if any id does not exist.
 */
public function findMany(array $ids): Collection

از PHP 7 و به‌خصوص PHP 8 به بعد، typeهای native (union، nullable، mixed، never، intersection، DNF) بخش بزرگی از نقش docblock را گرفته‌اند. docblock امروز بیشتر برای چیزهایی است که سیستم type خود PHP نمی‌تواند بیان کند.

تگ‌های پرکاربرد

تگکاربرد

@throwsexceptionهایی که فراخواننده باید مدیریت کند (PHP، checked exception ندارد)
@vartype یک property یا متغیر محلی وقتی static analysis نمی‌تواند استنتاج کند

Eloquent و docblock

/**
 * @property int $id
 * @property string $email
 * @property OrderStatus $status
 * @property-read \Illuminate\Database\Eloquent\Collection<int, Order> $orders
 */
class Customer extends Model
{
    /** @return HasMany<Order, $this> */
    public function orders(): HasMany
    {
        return $this->hasMany(Order::class);
    }
}

attributeهای Eloquent جادویی‌اند و IDE و PHPStan بدون @property آن‌ها را نمی‌شناسند. ابزارهایی مثل barryvdh/laravel-ide-helper این docblockها را از روی schema تولید می‌کنند و Larastan (افزونه‌ی PHPStan برای Laravel) بخش زیادی را خودکار استنتاج می‌کند.

docblock نادرست از نبودنش بدتر است: اگر @return User بنویسید ولی متد null هم برگرداند، IDE و همکاران گمراه می‌شوند. اجرای PHPStan در CI (در سطح مناسب) باعث می‌شود docblockها با کد واقعی تطبیق داده شوند و «مستند اجرایی» شوند.

از PHP 8.4، attribute #[\Deprecated] برای توابع، متدها و ثابت‌های کلاس اضافه شده که برخلاف تگ @deprecated، هنگام فراخوانی در runtime هشدار deprecation تولید می‌کند. تگ docblock همچنان برای ابزارها و نسخه‌های قدیمی‌تر رایج است.

مستندات API: OpenAPI و Scribe

برای API، مستندات بخشی از قرارداد (contract) بین تولیدکننده و مصرف‌کننده است. OpenAPI Specification (نام قبلی: Swagger Specification) استانداردی مستقل از زبان برای توصیف REST/HTTP API در قالب YAML یا JSON است. «Swagger» امروز بیشتر به مجموعه ابزارها (Swagger UI، Swagger Editor، Codegen) اشاره دارد. نسخه‌ی 3.1 با JSON Schema هم‌راستا شده است.

یک API doc خوب چه چیزهایی دارد؟

  • احراز هویت (نوع توکن، header، نحوه‌ی گرفتن توکن) و مجوزها.
  • هر endpoint: متد، مسیر، پارامترهای path/query/body با type، الزامی/اختیاری بودن و قیدها.
  • نمونه‌ی واقعی درخواست و پاسخ (موفق و خطا).
  • قالب خطا و کدهای وضعیت (مثلاً ۴۲۲ برای validation با ساختار errors در Laravel).
  • pagination، فیلتر، مرتب‌سازی، rate limit، idempotency.
  • نسخه‌بندی و سیاست deprecation؛ changelog API.

Design-first در برابر Code-first

Design-first (Spec-first)

  • اول فایل OpenAPI نوشته و با مصرف‌کنندگان review می‌شود، بعد پیاده‌سازی.
  • فرانت و بک می‌توانند موازی کار کنند (mock server از روی spec).
  • طراحی API آگاهانه‌تر و سازگارتر.
  • خطر واگرایی spec و کد؛ نیاز به contract test یا validation پاسخ‌ها در تست.

Code-first

  • مستند از روی کد (route، FormRequest، Resource، annotation/attribute) تولید می‌شود.
  • همگامی بهتر با پیاده‌سازی؛ سربار کمتر.
  • طراحی API ممکن است تحت تأثیر جزئیات پیاده‌سازی قرار گیرد.
  • کیفیت مستند به کیفیت annotationها و استنتاج ابزار بستگی دارد.

ابزارهای Laravel

  • Scribe (knuckleswtf/scribe): از routeها، قوانین validation در FormRequest و docblock یا PHP attributeها مستند می‌سازد؛ خروجی آن صفحه‌ی HTML، مجموعه‌ی Postman و فایل OpenAPI است. می‌تواند با فراخوانی واقعی endpoint (در محیط امن) نمونه‌ی پاسخ تولید کند.
  • Scramble (dedoc/scramble): بدون annotation و با تحلیل static کد (FormRequest، API Resource، type خروجی) OpenAPI تولید می‌کند.
  • L5-Swagger: Swagger UI را با zircote/swagger-php ترکیب می‌کند؛ spec با annotation یا attributeهای OpenApi\Attributes روی کد نوشته می‌شود.

Architecture Decision Record

ADR سندی کوتاه است که یک تصمیم مهم معماری را همراه با زمینه، گزینه‌ها و پیامدهایش ثبت می‌کند. «مهم» یعنی تصمیمی که برگرداندنش پرهزینه است یا روی ساختار، ویژگی‌های کیفی (کارایی، امنیت، مقیاس‌پذیری)، وابستگی‌ها یا شیوه‌ی کار تیم اثر دارد. قالب کلاسیک آن را Michael Nygard معرفی کرد.

چرا ADR؟

  • پاسخ به سؤال همیشگی «چرا این کار را این‌طور کردیم؟» بعد از رفتن افراد.
  • جلوگیری از بحث‌های تکراری و تغییرات ناآگاهانه («Chesterton's fence»: قبل از برداشتن حصار بدانید چرا گذاشته شده).
  • onboarding: خواندن ADRها تاریخچه‌ی فکری سیستم را نشان می‌دهد.
  • تصمیم‌گیری بهتر: نوشتن گزینه‌ها و پیامدها، تفکر را شفاف و قابل review می‌کند.

ویژگی‌ها

  • کوتاه (معمولاً یک تا دو صفحه)، یک تصمیم در هر ADR.
  • شماره‌گذاری ترتیبی و نگهداری در repo: docs/adr/0007-use-idempotency-keys-for-payments.md.
  • وضعیت: Proposed، Accepted، Deprecated، Superseded by ADR-00XX.
  • تغییرناپذیر پس از پذیرش: اگر تصمیم عوض شد، ADR جدید می‌نویسید که ADR قبلی را supersede می‌کند؛ ADR قدیمی را بازنویسی نمی‌کنید، چون تاریخچه‌ی تصمیم ارزشمند است.
  • review از طریق PR مثل کد.

نمونه‌ی ADR

# ADR-0007: استفاده از Idempotency Key برای درخواست‌های پرداخت

- وضعیت: Accepted
- تاریخ: 2026-09-14
- تصمیم‌گیرندگان: تیم Payments (علی ر.، سارا م.)، معمار فنی
- مرتبط: PAY-318 ، ADR-0003 (پردازش پرداخت در queue)

## زمینه (Context)
درگاه پرداخت در ساعات اوج گاهی بعد از ۳۰ ثانیه timeout می‌دهد، در حالی که
تراکنش را پردازش کرده است. Job پرداخت ما در صورت timeout تا ۳ بار retry می‌شود.
در ماه گذشته ۴۲ مورد شارژ دوباره‌ی مشتری گزارش شد. درگاه از header
Idempotency-Key پشتیبانی می‌کند و کلید را ۲۴ ساعت نگه می‌دارد.

## گزینه‌های بررسی‌شده
1. حذف retry خودکار و بررسی دستی موارد timeout
   - ساده، ولی بار پشتیبانی زیاد و تجربه‌ی بد کاربر
2. پرسیدن وضعیت تراکنش از درگاه قبل از هر retry
   - API وضعیت درگاه با تأخیر به‌روز می‌شود؛ race condition باقی می‌ماند
3. ارسال Idempotency-Key ثابت به ازای هر تلاش پرداخت (انتخاب‌شده)

## تصمیم (Decision)
برای هر PaymentAttempt یک UUID تولید و در جدول payment_attempts ذخیره می‌کنیم
و در همه‌ی retryهای همان تلاش، همین مقدار را به‌عنوان Idempotency-Key می‌فرستیم.
بازه‌ی retry باید کمتر از ۲۴ ساعت باشد.

## پیامدها (Consequences)
مثبت:
- شارژ تکراری ناشی از retry حذف می‌شود.
- retry امن می‌شود و می‌توانیم backoff طولانی‌تری داشته باشیم.
منفی / ریسک:
- وابستگی به رفتار درگاه؛ در صورت تغییر درگاه باید پشتیبانی idempotency بررسی شود.
- نیاز به migration جدید و نگهداری کلید.
پیگیری:
- افزودن متریک "duplicate charge prevented" و هشدار.
- به‌روزرسانی runbook «پرداخت ناموفق».

بخش‌های ضروری ADR را حفظ کنید: عنوان (تصمیم به‌صورت جمله)، وضعیت، زمینه، تصمیم، پیامدها و در قالب‌های کامل‌تر مثل MADR: گزینه‌های بررسی‌شده با مزایا و معایب. نکته‌ای که ممتحن دوست دارد بشنود: پیامدهای منفی را هم باید صادقانه نوشت؛ هر تصمیم معماری یک trade-off است.

چه چیزی ADR لازم دارد؟ انتخاب دیتابیس یا message broker، الگوی ارتباط بین سرویس‌ها (sync در برابر async)، استراتژی احراز هویت، تصمیم monolith در برابر microservice، قرارداد نسخه‌بندی API، کتابخانه‌ی اصلی‌ای که جایگزینی‌اش سخت است. نام‌گذاری یک متغیر یا انتخاب بین دو helper ساده ADR لازم ندارد.

CHANGELOG و Release Notes

CHANGELOG فایلی است که فهرست مرتب و زمان‌دار تغییرات قابل توجه هر نسخه را برای انسان‌ها نگه می‌دارد. قرارداد Keep a Changelog رایج‌ترین قالب آن است و معمولاً همراه با Semantic Versioning به کار می‌رود.

اصول Keep a Changelog

  • CHANGELOG برای انسان‌ها نوشته می‌شود، نه ماشین؛ پس dump کردن git log نیست. commitهایی مثل «fix typo» یا «refactor test» برای کاربر معنا ندارند.
  • هر نسخه یک بخش دارد؛ جدیدترین نسخه بالا.
  • تاریخ انتشار به قالب ISO 8601: YYYY-MM-DD.
  • یک بخش [Unreleased] در بالای فایل برای تغییراتی که هنوز منتشر نشده‌اند.
  • تغییرات بر اساس نوع گروه‌بندی می‌شوند: Added، Changed، Deprecated، Removed، Fixed، Security.
  • نسخه‌ها به diff یا release مربوط لینک می‌شوند.

نکته‌ی مهم Deprecated: قبل از حذف یک قابلیت (MAJOR)، در یک نسخه‌ی MINOR آن را deprecated اعلام کنید تا مصرف‌کنندگان فرصت مهاجرت داشته باشند. این همان سیاستی است که در PHPDoc با @deprecated و در API با header یا مستند deprecation دنبال می‌شود.

خودکارسازی

  • اگر تیم از Conventional Commits استفاده کند، ابزارهایی مثل release-please یا semantic-release می‌توانند پیش‌نویس CHANGELOG و نسخه‌ی بعدی را خودکار بسازند؛ ولی بهتر است یک انسان متن نهایی را برای خوانایی ویرایش کند.
  • روش دیگر: هر PR یک قطعه‌ی کوچک changelog (changelog fragment) اضافه می‌کند و هنگام release این قطعه‌ها ادغام می‌شوند؛ از conflict روی یک فایل مشترک جلوگیری می‌کند.
  • چک CI: PRهایی که کد را تغییر داده‌اند ولی CHANGELOG یا fragment ندارند (با امکان برچسب «skip-changelog» برای تغییرات داخلی).

Release notes با CHANGELOG فرق ظریفی دارد: release notes معمولاً برای کاربر نهایی یا مشتری و با لحن محصولی نوشته می‌شود (برجسته‌سازی قابلیت‌ها، راهنمای مهاجرت)، در حالی که CHANGELOG فهرست کامل و فنی تغییرات قابل توجه برای توسعه‌دهندگان و مصرف‌کنندگان API است.

Runbook و Onboarding

Runbook

Runbook دستورالعمل گام‌به‌گام برای انجام یک عملیات یا واکنش به یک وضعیت مشخص در production است؛ برای کسی نوشته می‌شود که ممکن است نیمه‌شب، تحت فشار و بدون آشنایی عمیق با آن سرویس، با هشدار روبه‌رو شود. هدف آن کاهش MTTR (میانگین زمان بازیابی) و وابستگی به افراد خاص است.

# Runbook: صف payments عقب افتاده است (QueueBacklogHigh)

## هشدار
QueueBacklogHigh: بیش از ۵۰۰ job در صف "payments" به مدت ۱۰ دقیقه.

## اثر بر کاربر
پرداخت‌ها ثبت می‌شوند ولی رسید و فعال‌سازی اشتراک با تأخیر انجام می‌شود.
شدت: SEV-2 اگر بیش از ۳۰ دقیقه طول بکشد.

## تشخیص
1. داشبورد Horizon: /horizon ← وضعیت supervisor "payments" را ببینید.
2. آیا workerها در حال اجرا هستند؟
       kubectl get pods -l app=billing-worker
3. نرخ failed jobs:
       php artisan queue:failed | head
4. وضعیت درگاه پرداخت: status.gateway.example

## اقدام‌ها
- workerها متوقف‌اند ← restart:
      kubectl rollout restart deployment/billing-worker
- درگاه کند است ← افزایش timeout لازم نیست؛ jobها با backoff retry می‌شوند.
  فقط پایش کنید و در کانال #incidents اطلاع دهید.
- jobها با خطای یکسان fail می‌شوند ← آخرین deploy را بررسی و در صورت لزوم rollback:
      ./deploy rollback billing

## ارجاع (Escalation)
اگر ظرف ۳۰ دقیقه حل نشد: on-call تیم Payments (PagerDuty) و سپس مدیر فنی.

## پس از حادثه
ثبت در incident log؛ در صورت نیاز postmortem بدون سرزنش (blameless).
  • هر هشدار (alert) باید به runbook خود لینک داشته باشد.
  • دستورات کپی‌پذیر و دقیق؛ از «سرویس را بررسی کنید» بدون گفتن «چطور» پرهیز کنید.
  • بعد از هر حادثه، runbook را به‌روز کنید؛ اگر قدمی اشتباه یا ناقص بود، همان‌جا اصلاح شود.
  • گام‌های تکراری و قابل اعتماد runbook کاندیدای خودکارسازی‌اند (runbook automation).

Postmortem

پس از هر حادثه‌ی جدی، سند postmortem با رویکرد blameless نوشته می‌شود: خلاصه، timeline، اثر، علت ریشه‌ای (root cause) و عوامل مؤثر، چه چیزی خوب کار کرد، چه چیزی بد بود، و action itemهای دارای مالک و موعد. هدف یادگیری سیستمی است، نه پیدا کردن مقصر.

هدف: عضو جدید در کمترین زمان «اولین تغییر واقعی» خود را به production برساند.

  • روز اول: دسترسی‌ها (repo، CI، staging، ابزار مانیتورینگ)، راه‌اندازی محیط محلی (لینک به README)، ابزارها و قراردادهای تیم.
  • نقشه‌ی سیستم: نمودار C4 سطح ۱ و ۲، فهرست سرویس‌ها و مالکانشان، واژه‌نامه‌ی دامنه (مثلاً تفاوت «Order» و «Invoice» در کسب‌وکار ما).
  • روش کار: workflow گیت، فرایند PR و review، Definition of Done، نحوه‌ی deploy و on-call.
  • مسیر یادگیری: چند «good first issue»، ADRهای کلیدی برای خواندن، یک همراه (buddy).
  • از عضو جدید بخواهید هر جا گیر کرد مستند را اصلاح کند؛ او بهترین تست‌کننده‌ی onboarding است.

تفاوت runbook با مستند معماری: runbook عمل‌محور (how-to در Diátaxis) است و برای لحظه‌ی بحران طراحی می‌شود: کوتاه، گام‌به‌گام، با دستورات دقیق و مسیر escalation. مستند معماری فهم‌محور (explanation) است.

مستندسازی env و پیکربندی

یکی از رایج‌ترین علل خرابی deploy و «روی سیستم من کار می‌کرد»، متغیر محیطی مستندنشده است. پیکربندی باید کامل، با مقدار نمونه‌ی امن، با توضیح و قابل اعتبارسنجی مستند شود.

.env.example به‌عنوان مستند زنده

# ---------------------------------------------------------------
# Payment gateway
# ---------------------------------------------------------------
# Base URL of the gateway API. Use the sandbox URL outside production.
PAYMENT_GATEWAY_URL=https://sandbox.gateway.example/api

# Secret API key (required). Get it from the team vault: payments/gateway.
PAYMENT_GATEWAY_KEY=

# Request timeout in seconds. Keep below the queue job timeout (60s).
PAYMENT_GATEWAY_TIMEOUT=30

# Disk used for generated invoice PDFs: "local" or "s3".
INVOICE_PDF_DISK=s3
  • هر متغیر جدید در همان PR به .env.example اضافه شود (قابل بررسی در review یا CI).
  • هیچ secret واقعی در .env.example نباشد؛ فقط محل دریافت آن (vault یا secret manager).
  • برای هر متغیر: معنا، الزامی/اختیاری، مقدار پیش‌فرض، مقادیر مجاز و واحد (ثانیه؟ میلی‌ثانیه؟).

در Laravel: config به‌عنوان لایه‌ی مستند

// config/payments.php
return [
    /*
    |--------------------------------------------------------------------------
    | Gateway timeout
    |--------------------------------------------------------------------------
    | Seconds to wait for the gateway. Must be lower than the queue job
    | timeout, otherwise the worker kills the job before we can retry.
    */
    'timeout' => (int) env('PAYMENT_GATEWAY_TIMEOUT', 30),

    'key' => env('PAYMENT_GATEWAY_KEY'),
];
  • env() فقط در فایل‌های config/ فراخوانی شود و در بقیه‌ی کد از config('payments.timeout') استفاده شود؛ چون بعد از php artisan config:cache، فایل .env دیگر بارگذاری نمی‌شود و env() خارج از config مقدار null برمی‌گرداند.
  • commentهای بالای هر کلید در config همان سبکی است که خود Laravel در فایل‌های config پیش‌فرض استفاده می‌کند.

اعتبارسنجی پیکربندی در زمان boot

مستندی که اجرا می‌شود بهتر از مستندی است که فقط خوانده می‌شود: اگر یک متغیر الزامی نیست، برنامه زود و با پیام واضح شکست بخورد (fail fast).

// app/Providers/AppServiceProvider.php
public function boot(): void
{
    if ($this->app->environment('production') && blank(config('payments.key'))) {
        throw new \RuntimeException(
            'PAYMENT_GATEWAY_KEY is not set. See docs/configuration.md#payment-gateway'
        );
    }
}

Docs-as-code و همگام‌سازی

Docs-as-code یعنی با مستندات همان رفتاری را داشته باشیم که با کد داریم: در قالب متنی ساده (Markdown، AsciiDoc، OpenAPI YAML)، در همان repo کنار کد، تحت version control، با review در Pull Request، و با ساخت، تست و انتشار خودکار در CI.

مزایا

  • مستند و کد در یک PR تغییر می‌کنند؛ reviewer هر دو را می‌بیند.
  • تاریخچه، blame و revert برای مستندات.
  • مستند هر نسخه همراه همان نسخه‌ی کد (branch/tag).
  • ابزارهای خودکار: lint، بررسی لینک، تولید سایت.
  • توسعه‌دهندگان در محیط آشنای خود (IDE، Git) می‌نویسند.

چالش‌ها

  • برای افراد غیرفنی (محصول، پشتیبانی) سخت‌تر است.
  • جستجوی بین چند repo نیازمند یک پورتال مرکزی (مثلاً سایت مستندات یا developer portal).
  • بدون فرهنگ و قاعده، همچنان کهنه می‌شود؛ ابزار به‌تنهایی کافی نیست.

راه‌های همگام نگه داشتن مستندات با کد

  1. Definition of Done: «مستندات مرتبط به‌روز شده» بخشی از تعریف اتمام هر task باشد.
  2. قالب PR با checklist: «آیا env جدید، endpoint جدید، تغییر رفتار یا تصمیم معماری دارد؟ مستند/ADR/CHANGELOG به‌روز شد؟»
  3. تولید reference از کد: OpenAPI از Scribe/Scramble، مستند کلاس‌ها از PHPDoc؛ هر چیزی که تولیدشدنی است دستی نوشته نشود.
  4. چک‌های CI:
    • تولید spec و fail شدن build در صورت تفاوت با نسخه‌ی commit‌شده.
    • lint مستندات (markdownlint)، بررسی لینک‌های شکسته، و style linter مثل Vale برای اصطلاحات و سبک.
    • lint فایل OpenAPI (Spectral) و تشخیص تغییرات breaking.
    • بررسی اینکه کلیدهای .env.example با متغیرهای استفاده‌شده در config/ هم‌خوان باشند.
  5. مستندات اجرایی: تست‌ها (به‌خصوص feature testهای خوانا)، اعتبارسنجی پاسخ API با spec در تست، doctest برای نمونه‌کدها، اعتبارسنجی config در boot.
  6. مالکیت: CODEOWNERS برای docs/؛ مستند بی‌صاحب کهنه می‌شود.
  7. بازبینی دوره‌ای: تاریخ «آخرین بازبینی» در صفحات و مرور فصلی؛ حذف صفحات منسوخ.
  8. نزدیکی به کد: هرچه مستند به کد نزدیک‌تر باشد (docblock، README پوشه‌ی ماژول)، احتمال به‌روز ماندنش بیشتر است.
# .github/workflows/docs.yml (نمونه)
name: docs
on: [pull_request]
jobs:
  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with: { php-version: '8.3' }
      - run: composer install --no-interaction --prefer-dist
      - name: Regenerate API docs and fail if they changed
        run: |
          php artisan scribe:generate --no-interaction
          git diff --exit-code -- docs/api/ || (echo "API docs are outdated. Run scribe:generate." && exit 1)
      - name: Lint markdown
        run: npx markdownlint-cli2 "docs/**/*.md" "README.md"

مسیر خروجی Scribe و نام فایل‌ها به پیکربندی config/scribe.php بستگی دارد؛ در CI همان مسیری را بررسی کنید که پروژه‌ی شما واقعاً تولید می‌کند.

سؤال کلاسیک: «چطور مطمئن می‌شوید مستندات کهنه نمی‌شوند؟» پاسخ قوی سه لایه دارد: فرایند (DoD، قالب PR، review، مالک)، ابزار (تولید از کد، چک CI، lint و بررسی لینک) و طراحی (مستند نزدیک کد، مستند اجرایی مثل تست و اعتبارسنجی config، و حذف مستندات غیرضروری تا سطح نگهداری کم شود).

سبک نوشتن فنی

نوشتن فنی خوب یعنی خواننده با کمترین تلاش به آنچه نیاز دارد برسد. چند اصل کلیدی:

اصول

  1. مخاطب و هدف را مشخص کنید: قبل از نوشتن بپرسید «چه کسی می‌خواند و بعد از خواندن باید چه کاری بتواند بکند؟»
  2. مهم‌ترین چیز اول (inverted pyramid): نتیجه یا دستور اصلی در ابتدا، جزئیات بعد.
  3. قابل مرور (scannable): عنوان‌های گویا، فهرست، جدول، پاراگراف کوتاه. خواننده‌ی فنی می‌خواند تا پیدا کند، نه برای لذت.
  4. جمله‌ی کوتاه و فعل معلوم: «Job را dispatch کنید» به‌جای «لازم است که dispatch شدن Job انجام گیرد».
  5. دقت و مشخص بودن: «timeout را روی ۳۰ ثانیه بگذارید» به‌جای «timeout را مقدار مناسبی بگذارید».
  6. اصطلاحات یکسان: اگر یک‌جا «مشتری» گفتید، جای دیگر «کاربر» نگویید (مگر واقعاً متفاوت باشند). واژه‌نامه‌ی دامنه کمک می‌کند (Ubiquitous Language).
  7. مثال واقعی و قابل اجرا: نمونه‌کد کامل و تست‌شده، با خروجی مورد انتظار.
  8. پیش‌فرض نگیرید: از «فقط»، «به‌سادگی»، «بدیهی است» پرهیز کنید؛ برای خواننده‌ای که گیر کرده تحقیرآمیز است.
  9. پیش‌نیازها و فرض‌ها را صریح بگویید (نسخه‌ی PHP، دسترسی لازم).
  10. هشدارها را برجسته کنید: عملیات مخرب یا غیرقابل بازگشت (مثلاً migrate:fresh) با هشدار واضح.

ضعیف

برای راه‌اندازی، کارهای لازم را انجام دهید و دیتابیس را تنظیم کنید. سپس به‌سادگی برنامه را اجرا کنید. اگر مشکلی بود ممکن است به خاطر تنظیمات باشد.

بهتر

  1. فایل env را بسازید: cp .env.example .env
  2. مقدار DB_PASSWORD را از vault (billing/local) بردارید.
  3. اجرا کنید: php artisan migrate --seed

اگر خطای SQLSTATE[HY000] [2002] دیدید، MySQL بالا نیست: docker compose up -d mysql

نمونه‌کد در مستندات

  • کامل و قابل کپی (importها و namespace در صورت نیاز).
  • کوتاه و متمرکز بر نکته‌ی اصلی؛ کد نامربوط حذف شود.
  • نسخه‌ی مرتبط (PHP/Laravel) مشخص باشد.
  • در صورت امکان در CI اجرا یا تست شود تا با تغییر API نشکند.

مستندات به زبان فارسی و انگلیسی

در تیم‌های فارسی‌زبان، اصطلاحات فنی را به انگلیسی نگه دارید (queue، migration، middleware) تا با کد و منابع بیرونی یکسان بماند، ولی توضیح را روان بنویسید. در مستندات چندزبانه، یک زبان «منبع حقیقت» باشد تا ترجمه‌ها از هم عقب نمانند. شناسه‌ها، نام متغیرها و پیام‌های خطا را ترجمه نکنید.

«قانون دو دقیقه»: اگر یک همکار سؤالی پرسید که جوابش در مستندات نبود، بعد از جواب دادن، همان جواب را (در دو دقیقه) به مستند مرتبط اضافه کنید. سؤال‌های تکراری در چت، بهترین نقشه‌ی کمبودهای مستندات‌اند.

سوالات تشریحی

چرا مستندسازی نرم‌افزار مهم است؟ مخاطبان اصلی مستندات یک سرویس بک‌اند را نام ببرید و برای هر کدام نوع مستند مناسب را پیشنهاد کنید.

تعریف و اهمیت: مستندات ابزار انتقال دانشی است که از خود کد قابل استخراج نیست یا استخراجش پرهزینه است: «چرا»، «چطور استفاده کنم»، «تصویر کلان» و «چطور اجرا و نگهداری کنم». اثرات مستقیم آن:

  • کاهش زمان onboarding و وابستگی به افراد (bus factor).
  • جلوگیری از تصمیم‌گیری و بحث تکراری.
  • کاهش MTTR در حوادث.
  • کاهش خطای یکپارچه‌سازی برای مصرف‌کنندگان API.

مخاطبان و مستند مناسب:

  • توسعه‌دهنده‌ی جدید: README با quick start، راهنمای onboarding، CONTRIBUTING.
  • توسعه‌دهنده‌ی فعلی/آینده: comment «چرا»، PHPDoc برای API عمومی کلاس‌ها، ADR، پیام commit و PR.
  • مصرف‌کننده‌ی API: OpenAPI و مستند تعاملی (Scribe، Swagger UI)، CHANGELOG و سیاست deprecation.
  • عملیات/on-call: runbook، مستند deploy، جدول پیکربندی env.
  • معمار و مدیر: نمودارهای C4 و مستند معماری.

نکته‌ی مهم: مستند کهنه از نبودنش بدتر است، چون اعتماد را از بین می‌برد. پس هدف، مستند کم، دقیق، به‌روز و دارای مالک است که همراه کد تغییر کند (docs-as-code).

جمله‌ی «comment باید چرا را بگوید، نه چه را» را توضیح دهید و با مثال PHP نشان دهید چه commentهایی مفید و چه commentهایی مضرند.

توضیح: کد خودش دقیق‌ترین توصیف از «چه» و «چگونه» است. commentی که همان را تکرار کند اطلاعات جدیدی نمی‌دهد و چون کامپایلر آن را بررسی نمی‌کند، با تغییر کد کهنه و گمراه‌کننده می‌شود. ارزش comment در اطلاعاتی است که از کد قابل استنتاج نیست: دلیل، قید، هشدار و زمینه‌ی کسب‌وکار.

// Bad: repeats the code
// set status to paid
$order->status = OrderStatus::Paid;

// Good: explains why
// Mark as paid before dispatching the job: the receipt job reads
// the status and would otherwise send a "pending" email (PAY-221).
$order->status = OrderStatus::Paid;
$order->save();
SendReceipt::dispatch($order);

commentهای مفید:

  • دلیل تصمیم غیربدیهی و گزینه‌های ردشده.
  • workaround برای باگ کتابخانه یا محدودیت سرویس بیرونی، با لینک issue.
  • قاعده‌ی کسب‌وکار یا الزام قانونی.
  • هشدار درباره‌ی ترتیب، همزمانی یا اثر جانبی.
  • docblock برای API عمومی و typeهای پیشرفته.

commentهای مضر: تکرار کد، کد comment‌شده (Git تاریخچه را دارد)، تاریخچه‌ی تغییرات در فایل، TODO بدون ticket و مالک، و commentهای نادرست و کهنه.

قاعده‌ی تکمیلی: اگر برای توضیح یک قطعه به comment طولانی نیاز دارید، اول با نام‌گذاری بهتر، extract method، enum یا value object کد را خودمستند کنید.

«کد خوب نیازی به مستندات ندارد.» این جمله را نقد کنید. کد خودمستند چیست و محدودیت‌هایش کدام است؟

کد خودمستند کدی است که با نام‌گذاری دامنه‌محور، توابع کوچک با یک مسئولیت، typeهای صریح، enum به‌جای مقادیر جادویی، value object و named arguments، هدف خود را بدون comment بیان می‌کند.

// instead of: if ($u->t == 2 && $u->c > 10)
if ($customer->isEligibleForLoyaltyDiscount()) { /* ... */ }

بخش درست جمله: کد خوب نیاز به commentهای «چه» را از بین می‌برد و باید اولین اولویت باشد. تست‌های خوانا هم نوعی مستند اجرایی‌اند که برخلاف comment، اگر کهنه شوند fail می‌شوند.

بخش نادرست: کد، هرچقدر هم تمیز، نمی‌تواند این‌ها را منتقل کند:

  • چرا این طراحی انتخاب شد و چه گزینه‌هایی رد شدند (ADR).
  • تصویر کلان: ارتباط سرویس‌ها، جریان داده، وابستگی‌های بیرونی (C4).
  • قرارداد برای کسی که کد را نمی‌بیند: مصرف‌کننده‌ی API (OpenAPI).
  • دانش عملیاتی: راه‌اندازی، پیکربندی، deploy، واکنش به حادثه (README، runbook).
  • قیود بیرونی: قانون، توافق با شریک، رفتار عجیب سرویس ثالث.

جمع‌بندی: کد خودمستند و مستندات مکمل‌اند؛ کد تمیز سطح نیاز به مستند را پایین می‌آورد ولی آن را صفر نمی‌کند. رویکرد درست: «چه» در کد، «چرا»ی محلی در comment، و دانش سطح سیستم در مستندات جداگانه.

PHPDoc در PHP مدرن (با وجود type declarationهای native) چه کاربردی دارد؟ چه زمانی docblock زائد است؟ مثال بزنید.

تعریف: PHPDoc قالب de facto برای commentهای ساخت‌یافته (/** */) با تگ‌هایی مثل @param، @return، @throws است که IDE، PHPStan/Psalm و تولیدکننده‌های مستندات آن را می‌فهمند.

زائد: وقتی فقط type native را تکرار می‌کند:

/** @param int $id  @return string */
public function name(int $id): string

کاربردهای ارزشمند امروز:

  • typeهای دقیق‌تر از سیستم type PHP: list<int>، array<string, Money>، array shape (array{id: int, name: string})، non-empty-string، positive-int.
  • Generics: @template T، Collection<int, User>، class-string<T>.
  • @throws: اعلام exceptionهایی که فراخواننده باید مدیریت کند.
  • اعضای جادویی: @property و @method برای attributeهای Eloquent یا __call.
  • @deprecated با جایگزین و نسخه‌ی حذف؛ @internal برای اعلام اینکه جزء API عمومی نیست.
  • توضیح رفتاری برای API عمومی کتابخانه: شرایط مرزی، اثرات جانبی، مثال.
/**
 * @param  list<int>  $ids
 * @return Collection<int, Invoice>
 * @throws ModelNotFoundException if any id is missing
 */
public function findOrFailMany(array $ids): Collection

نکته: با اجرای PHPStan/Larastan در CI، docblockها با کد واقعی تطبیق داده می‌شوند و نادرستی آن‌ها خطا می‌دهد؛ یعنی docblock از «comment» به «مستند اجرایی» تبدیل می‌شود.

  • مستند تعاملی تولید کرد (Swagger UI، Redoc) که امکان «try it» دارد؛

در یک پروژه‌ی Laravel چطور مستندات API را تولید و همگام نگه می‌دارید؟ نحوه‌ی کار Scribe را توضیح دهید.

Scribe (knuckleswtf/scribe) یک ابزار code-first است که با اجرای php artisan scribe:generate:

  • routeها را از router Laravel می‌خواند؛
  • پارامترهای بدنه را از قوانین validation در FormRequest استخراج می‌کند؛
  • توضیحات، گروه‌ها و مثال‌ها را از docblock (@group، @urlParam، @bodyParam، @response، @authenticated) یا PHP attributeها برمی‌دارد؛
  • در صورت پیکربندی، با فراخوانی endpointها در محیط امن، پاسخ نمونه تولید می‌کند؛
  • خروجی: صفحه‌ی HTML، مجموعه‌ی Postman و فایل OpenAPI.
/**
 * Create an invoice
 *
 * @group Invoices
 * @authenticated
 * @response 201 {"data": {"id": 1043, "status": "draft"}}
 * @response 422 {"message": "The amount field is required.", "errors": {"amount": ["The amount field is required."]}}
 */
public function store(StoreInvoiceRequest $request): JsonResponse

همگام‌سازی:

  1. اجرای scribe:generate در CI و git diff --exit-code روی خروجی؛ اگر کسی endpoint را تغییر داده و مستند را بازتولید نکرده، build fail می‌شود.
  2. lint فایل OpenAPI تولیدشده و بررسی breaking change نسبت به نسخه‌ی منتشرشده.
  3. استفاده‌ی سازگار از FormRequest و API Resource تا استنتاج ابزار دقیق باشد.
  4. checklist PR: «endpoint جدید یا تغییر قرارداد؟ docblock و CHANGELOG به‌روز شد؟»
  5. feature test برای ساختار پاسخ (assertJsonStructure) تا قرارداد واقعی هم تست شود.

جایگزین‌ها: Scramble (استنتاج کامل از کد بدون annotation) و L5-Swagger (با annotation/attributeهای swagger-php). انتخاب بین آن‌ها به میزان کنترل مورد نیاز بر متن مستند و سربار annotation بستگی دارد.

مدل C4 را توضیح دهید. هر سطح چه چیزی را نشان می‌دهد و برای چه مخاطبی است؟ یک نمودار Container برای یک فروشگاه اینترنتی مبتنی بر Laravel توصیف کنید.

تعریف: C4 (از Simon Brown) روشی برای توصیف معماری نرم‌افزار در چهار سطح بزرگ‌نمایی است تا هر نمودار فقط یک سطح انتزاع داشته باشد:

  1. System Context: سیستم به‌صورت یک جعبه، کاربران و سیستم‌های بیرونی. مخاطب: همه، حتی غیرفنی‌ها.
  2. Container: واحدهای جداگانه قابل اجرا/استقرار (اپلیکیشن، دیتابیس، صف، storage) و ارتباطشان. مخاطب: توسعه‌دهندگان و عملیات. (Container به معنی Docker نیست.)
  3. Component: اجزای اصلی داخل یک container و مسئولیتشان. مخاطب: توسعه‌دهندگان آن container.
  4. Code: کلاس‌ها؛ معمولاً از IDE تولید و به‌ندرت دستی نگه‌داری می‌شود.

نمودار Container فروشگاه:

[Customer] ─HTTPS─► [Storefront: Laravel + Inertia/Vue]
[Admin]    ─HTTPS─► [Admin Panel: Laravel/Filament]
     both ─► [MySQL: orders, products, customers]  (SQL)
     both ─► [Redis: cache, sessions, queue]
[Queue Worker: Laravel Horizon] ◄─ Redis
     ├─► [Payment Gateway] (external, HTTPS)
     ├─► [Email Provider]  (external, SMTP/API)
     └─► [S3: invoices, product images]

هر جعبه: نام، فناوری و یک جمله مسئولیت؛ هر فلش: جهت، «چه چیزی» و پروتکل. نمودار باید عنوان، سطح و legend داشته باشد.

تعریف: Architecture Decision Record سند کوتاهی است که یک تصمیم مهم معماری را همراه با زمینه، گزینه‌ها و پیامدها ثبت می‌کند. در repo (مثلاً docs/adr/) با شماره‌ی ترتیبی نگه داشته می‌شود، از طریق PR review می‌شود و پس از پذیرش تغییرناپذیر است؛ تصمیم جدید با ADR جدیدی که قبلی را supersede می‌کند ثبت می‌شود.

ساختار: عنوان، وضعیت (Proposed/Accepted/Deprecated/Superseded)، تاریخ و تصمیم‌گیرندگان، زمینه، گزینه‌ها، تصمیم، پیامدها (مثبت و منفی).

# ADR-0012: استفاده از Redis به‌عنوان queue driver

وضعیت: Accepted — 2026-10-05

## زمینه
صف فعلی database driver است. با رشد سفارش‌ها به ~۲۰۰ job در ثانیه در اوج،
polling جدول jobs باعث lock contention و کند شدن کوئری‌های اصلی MySQL شده است.
Redis قبلاً برای cache در زیرساخت موجود است.

## گزینه‌ها
1. ادامه با database driver + بهینه‌سازی index  — ساده، ولی بار روی DB اصلی می‌ماند
2. Redis + Laravel Horizon                       — سریع، داشبورد و متریک، زیرساخت آشنا
3. RabbitMQ / SQS                                 — قابلیت‌های پیشرفته، ولی سربار عملیاتی/هزینه‌ی جدید

## تصمیم
Redis با Horizon برای همه‌ی صف‌ها؛ instance جدای Redis برای queue (جدا از cache)
با persistence فعال (AOF).

## پیامدها
+ حذف بار polling از MySQL، throughput بالاتر، پایش با Horizon
- در صورت از دست رفتن Redis بدون persistence مناسب، jobهای در صف از دست می‌روند
- نیاز به پایش حافظه‌ی Redis و runbook جدید «Redis queue full»
- jobها دیگر با تراکنش DB اتمیک نیستند ← استفاده از afterCommit برای dispatch

چرا ارزشمند است: پاسخ به «چرا» برای اعضای آینده، جلوگیری از بحث تکراری، و شفاف‌سازی trade-offها. پیامدهای منفی باید صادقانه نوشته شوند؛ ADR بدون معایب احتمالاً تحلیل کاملی نبوده است.

تعریف: CHANGELOG فهرست زمان‌دار و مرتب تغییرات قابل توجه هر نسخه است که برای انسان‌ها (توسعه‌دهندگان، مصرف‌کنندگان API، مشتریان) نوشته می‌شود تا بدانند چه چیزی عوض شده و آیا باید کاری انجام دهند.

ساختار Keep a Changelog:

  • جدیدترین نسخه در بالا؛ بخش [Unreleased] برای تغییرات منتشرنشده.
  • هر نسخه با شماره‌ی SemVer و تاریخ ISO: ## [2.4.0] - 2026-10-28.
  • گروه‌بندی: Added، Changed، Deprecated، Removed، Fixed، Security.
  • لینک هر نسخه به diff یا release.

چرا git log کافی نیست:

  • مخاطب متفاوت: commitها برای توسعه‌دهندگان همان پروژه‌اند و پر از جزئیات داخلی («fix test»، «refactor») هستند.
  • دانه‌بندی: یک تغییر قابل توجه ممکن است ده commit باشد.
  • دسته‌بندی و اولویت: Security و Removed باید برجسته باشند تا کاربر واکنش نشان دهد.

تعریف: Diátaxis چارچوبی برای سازمان‌دهی مستندات فنی است که بر اساس دو محور، چهار نوع مستند با نیازهای متفاوت تعریف می‌کند: محور عمل در برابر شناخت و محور یادگیری (study) در برابر کار (work).

  • Tutorial (عمل + یادگیری): درس گام‌به‌گام برای تازه‌کار با نتیجه‌ی تضمین‌شده. مثال: «اولین feature در کدبیس ما از migration تا تست».
  • How-to guide (عمل + کار): دستورالعمل رسیدن به یک هدف مشخص برای کاربری که پیش‌زمینه دارد. مثال: «افزودن یک درگاه پرداخت جدید»، runbookها.
  • Reference (شناخت + کار): توصیف دقیق و کامل؛ برای جستجو، نه خواندن پیوسته. مثال: OpenAPI، جدول env، PHPDoc.
  • Explanation (شناخت + یادگیری): زمینه، دلیل و trade-off. مثال: مستند معماری، ADR، «چرا event-driven».

چرا مخلوط نکنیم: هر نوع برای یک «حالت ذهنی» متفاوت طراحی شده است:

  • tutorialی که وسط کار وارد بحث نظری می‌شود، تمرکز یادگیرنده را می‌شکند؛
  • how-toای که همه‌ی گزینه‌ها را فهرست می‌کند، کاربر عجول را کند می‌کند؛
  • referenceی که پر از آموزش است، پیدا کردن یک پارامتر را سخت می‌کند؛
  • explanationی که گام‌های عملی دارد، نه آموزش خوبی است و نه دستورالعمل خوب.

به‌جای مخلوط کردن، انواع را به هم لینک کنید. در عمل: reference را تا حد امکان از کد تولید کنید، how-toها و runbookها را کوتاه و عملی نگه دارید، و explanation را در مستند معماری و ADRها بنویسید.

  • تولید reference از کد (Scribe/Scramble برای API، PHPDoc) و fail شدن CI اگر خروجی تولیدشده با نسخه‌ی commit‌شده فرق کند.
  • lint مستندات، بررسی لینک شکسته، Vale برای سبک و اصطلاحات.
  • بررسی هم‌خوانی .env.example با کلیدهای استفاده‌شده.

۳. طراحی مستند

  • کاهش حجم: فقط چیزهایی که ارزش دارند؛ مستند کمتر یعنی نگهداری کمتر.
  • مستند نزدیک کد: docblock، README ماژول.
  • مستند اجرایی: feature testهای خوانا، اعتبارسنجی پاسخ API با spec، اعتبارسنجی config در boot.
  • quick start در قالب اسکریپت (composer setup) که در CI اجرا می‌شود.

سنجش: تعداد سؤال‌های تکراری در چت، زمان onboarding، و گزارش‌های «مستند غلط بود».

Runbook چیست و چه بخش‌هایی دارد؟ تفاوت آن با postmortem و مستند معماری را بگویید.

تعریف: runbook دستورالعمل گام‌به‌گام برای انجام یک عملیات یا واکنش به یک هشدار/وضعیت مشخص در production است. برای مهندس on-call نوشته می‌شود که ممکن است تحت فشار و بدون آشنایی عمیق با سرویس کار کند. هدف: کاهش MTTR و وابستگی به افراد خاص.

بخش‌ها:

  1. نام هشدار/وضعیت و شرط فعال شدن آن.
  2. اثر بر کاربر و سطح شدت.
  3. گام‌های تشخیص با دستورات دقیق و کپی‌پذیر (داشبورد، log، php artisan queue:failed).
  4. اقدام‌های اصلاحی برای هر علت محتمل (restart worker، rollback، غیرفعال کردن feature flag).
  5. مسیر escalation و زمان‌بندی آن.
  6. اقدامات پس از حادثه و لینک‌های مرتبط.

کد و مستند زیر چه مشکلاتی دارند؟ پیشنهاد اصلاح بدهید. // get price بالای متدی که env('TAX_RATE') را در یک Service فراخوانی می‌کند و TAX_RATE در .env.example نیست. 
// get price
public function price(Product $p)
{
    return $p->price * (1 + env('TAX_RATE'));
}

مشکلات:

  1. comment بی‌ارزش: «get price» همان نام متد است؛ چیزی درباره‌ی اینکه قیمت با مالیات است، واحد مبلغ چیست یا گرد کردن چطور انجام می‌شود نمی‌گوید.
  2. env() خارج از config: بعد از php artisan config:cache در production، .env بارگذاری نمی‌شود و env('TAX_RATE') مقدار null برمی‌گرداند؛ نتیجه: قیمت بدون مالیات، بی‌صدا.
  3. متغیر مستندنشده: TAX_RATE در .env.example نیست؛ کسی نمی‌داند باید 0.09 باشد یا 9.
  4. نبود type و نام مبهم: $p و نبود return type.
  5. (فنی) محاسبه‌ی پولی با float خطای گرد کردن دارد؛ بهتر است با واحد خرد (integer) یا کتابخانه‌ی Money کار شود.

اصلاح:

// config/pricing.php
// VAT rate as a decimal fraction (0.09 = 9%). Required in all environments.
'tax_rate' => (float) env('TAX_RATE', 0.09),

// PriceCalculator
/**
 * Gross price in minor units (cents). Tax is rounded per item
 * as required by the tax authority (see ADR-0015).
 */
public function grossPrice(Product $product): int
{
    $rate = config('pricing.tax_rate');

    return (int) round($product->price_cents * (1 + $rate));
}

و افزودن به .env.example با comment توضیح واحد، و در صورت نیاز اعتبارسنجی مقدار در boot. تست واحد هم قاعده‌ی گرد کردن را مستند و تضمین می‌کند.

اصول نوشتن فنی خوب را برای یک مستند داخلی (مثلاً راهنمای deploy) توضیح دهید. یک متن ضعیف را با نسخه‌ی بهبودیافته مقایسه کنید.

اصول:

  • مخاطب‌محوری: چه کسی می‌خواند و بعد از خواندن باید چه کاری بتواند انجام دهد؟ پیش‌نیازها و دسترسی‌ها صریح.
  • مهم‌ترین چیز اول: نتیجه یا دستور اصلی ابتدا، جزئیات و پس‌زمینه بعد.
  • قابل مرور: عنوان گویا، گام‌های شماره‌دار، جدول، پاراگراف کوتاه.
  • دقیق و مشخص: مقدار، مسیر و دستور دقیق؛ نه «تنظیم مناسب».
  • جمله‌ی کوتاه، فعل معلوم و امری برای گام‌ها.
  • اصطلاحات یکسان در کل مستند و هم‌خوان با کد.
  • هشدار برجسته برای عملیات مخرب و برگشت‌ناپذیر.
  • عیب‌یابی: خطاهای رایج با پیام دقیق و راه‌حل.
  • پرهیز از «فقط»، «به‌سادگی» و پیش‌فرض‌های ناگفته.

ضعیف: «برای deploy، تغییرات را push کنید و بعد از اینکه همه‌چیز اوکی شد، migrationها را بزنید. اگر مشکلی بود rollback کنید.»

بهتر:

  1. PR را در main merge کنید؛ pipeline به‌طور خودکار روی staging deploy می‌کند.
  2. روی staging تست دود را اجرا کنید: ./scripts/smoke.sh staging (باید «OK» چاپ کند).
  3. tag بزنید: git tag -a v2.4.0 -m "Release 2.4.0" && git push origin v2.4.0؛ این کار deploy production را آغاز می‌کند.
  4. migrationها به‌صورت خودکار با php artisan migrate --force در pipeline اجرا می‌شوند.

هشدار: migrationهای مخرب (حذف ستون) باید در دو مرحله و دو release انجام شوند؛ rollback کد، ستون حذف‌شده را برنمی‌گرداند.

Rollback: ./deploy rollback billing؛ اگر migration اجرا شده، ابتدا با on-call هماهنگ کنید.

نسخه‌ی دوم ترتیب، دستور دقیق، نتیجه‌ی مورد انتظار، هشدار و مسیر بازگشت را دارد.

خلاصه برای مرور سریع

اصول کلی

  • مستند = انتقال دانشی که در کد نیست: چرا، چطور استفاده، تصویر کلان، عملیات.
  • مخاطب‌محور: یک مستند، یک مخاطب، یک نیاز.
  • مستند کهنه بدتر از نبودنش است (doc rot) ← کم، دقیق، به‌روز، دارای مالک.
  • اثرها: onboarding سریع‌تر، bus factor بالاتر، MTTR کمتر، تصمیم تکراری کمتر.

Comment و کد

  • کد = چه/چگونه؛ comment = چرا، قید، هشدار، قاعده‌ی کسب‌وکار.
  • ممنوع: تکرار کد، کد comment‌شده، تاریخچه در فایل، TODO بدون ticket.
  • خودمستندسازی: نام‌گذاری دامنه، توابع کوچک، type، enum، value object، named args، تست خوانا.
  • کد خودمستند ≠ بی‌نیازی از مستند (معماری، دلیل، API، عملیات).

PHPDoc

  • تکرار type native زائد است.
  • ارزشمند: list<T>، array shape، @template، @throws، @property، @deprecated، @internal.
  • PHPStan/Larastan در CI ← docblock اجرایی؛ ide-helper برای Eloquent.

README

  • هدف، پیش‌نیاز، راه‌اندازی، تست، env، معماری، deploy، عیب‌یابی، مالک، مشارکت.
  • دستورات تست‌شده؛ عضو جدید تست‌کننده‌ی README.
  • همراه‌ها: CONTRIBUTING، CHANGELOG، SECURITY، CODEOWNERS، .env.example.

API

  • OpenAPI = قرارداد قابل پردازش با ماشین (UI، SDK، mock، validation، diff).
  • شامل: auth، پارامترها، نمونه‌ها، قالب خطا (۴۲۲)، pagination، rate limit، نسخه.
  • Design-first: طراحی بهتر، کار موازی؛ Code-first: همگامی.
  • Laravel: Scribe (FormRequest + docblock/attribute)، Scramble (استنتاج)، L5-Swagger.
  • CI: تولید + git diff --exit-code، Spectral، breaking-change check.

معماری و تصمیم

  • C4: Context ← Container ← Component ← Code؛ container ≠ Docker.
  • نمودار: عنوان، legend، فلش برچسب‌دار با پروتکل، یک سطح انتزاع.
  • Diagrams as code: Mermaid، PlantUML، Structurizr.
  • ADR: عنوان، وضعیت، زمینه، گزینه‌ها، تصمیم، پیامدها (+ و −)؛ تغییرناپذیر، supersede.

Release و عملیات

  • Keep a Changelog: Unreleased بالا، تاریخ ISO، Added/Changed/Deprecated/Removed/Fixed/Security.
  • CHANGELOG ≠ git log؛ برای انسان.
  • Deprecated در MINOR ← Removed در MAJOR.
  • Runbook: هشدار، اثر، تشخیص، اقدام، escalation؛ لینک از alert.
  • Postmortem: blameless، timeline، root cause، action item با مالک.
  • .env.example کامل بدون secret؛ env() فقط در config/؛ fail fast در boot.
