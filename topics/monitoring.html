Monitoring، Observability و سه ستون

Monitoring در برابر Observability

Monitoring یعنی جمع‌آوری، تجمیع و نمایش داده‌های از پیش تعریف‌شده درباره‌ی سیستم و هشدار دادن وقتی این داده‌ها از آستانه‌ی مشخصی عبور می‌کنند. Monitoring به سوال‌هایی پاسخ می‌دهد که از قبل می‌دانستیم باید بپرسیم («آیا نرخ خطا بالای ۱٪ است؟»، «آیا دیسک پر شده؟»). این همان «known unknowns» است.

Observability (مشاهده‌پذیری) ویژگی خود سیستم است: میزان توانایی ما برای فهمیدن وضعیت درونی سیستم از روی خروجی‌هایش، از جمله برای سوال‌هایی که از قبل پیش‌بینی نکرده بودیم («چرا فقط کاربران اندرویدی در ایران که سبد خرید بالای ۱۰ قلم دارند کندی دارند؟»). این همان «unknown unknowns» است و به داده‌ی غنی، با جزئیات و با cardinality بالا (شناسه‌ی کاربر، نسخه، endpoint) و امکان پرس‌وجوی آزاد نیاز دارد.

Monitoring

  • «آیا سیستم سالم است؟»
  • داشبورد و هشدار روی متریک‌های از پیش انتخاب‌شده
  • مناسب خرابی‌های شناخته‌شده
  • یک فعالیت / ابزار

Observability

  • «چرا سیستم این رفتار را دارد؟»
  • کاوش آزاد در داده‌ی غنی و مرتبط (log + metric + trace)
  • مناسب سیستم‌های توزیع‌شده و خرابی‌های جدید
  • یک ویژگی سیستم (باید instrument شده باشد)

جمله‌ی کلیدی: «Monitoring به شما می‌گوید چه چیزی خراب است؛ Observability کمک می‌کند بفهمید چرا.» Monitoring زیرمجموعه‌ای از Observability است، نه رقیب آن.

Correlation ID / Request ID

یک شناسه‌ی یکتا که در ابتدای هر درخواست تولید (یا از header ورودی مثل X-Request-Id خوانده) می‌شود، به همه‌ی لاگ‌های آن درخواست اضافه می‌شود، در header پاسخ برگردانده می‌شود و به سرویس‌های پایین‌دستی و jobهای صف منتقل می‌شود. با یک جست‌وجو می‌توان کل داستان یک درخواست را در چند سرویس دید. در سیستم‌های دارای tracing، trace_id همین نقش را دارد.

چه چیزهایی را نباید لاگ کرد

  • Secretها: رمز عبور، توکن‌های دسترسی، API key، header Authorization، کوکی session، APP_KEY.
  • اطلاعات پرداخت: شماره‌ی کامل کارت، CVV2 (الزامات PCI DSS).
  • PII (اطلاعات شناسایی شخصی) بیش از حد لازم: کد ملی، شماره‌ی تلفن، آدرس، ایمیل کامل؛ در صورت نیاز ماسک یا hash شود.
  • بدنه‌ی کامل درخواست/پاسخ به‌صورت پیش‌فرض.
  • داده‌ی پزشکی و حساس قانونی.

لاگ‌ها معمولاً دسترسی گسترده‌تر و نگهداری طولانی‌تری از دیتابیس دارند و در چند سیستم کپی می‌شوند؛ هر داده‌ی حساس در لاگ، سطح نشت را چند برابر می‌کند. «Log injection» هم وجود دارد: ورودی کاربر با کاراکتر newline می‌تواند رکورد جعلی بسازد؛ لاگ ساختاریافته (JSON) این خطر را کاهش می‌دهد.

بهترین روش‌ها

  • فیلدهای استاندارد ثابت: timestamp (ISO 8601 با timezone/UTC)، level، message، service، env، version، request_id/trace_id.
  • پیام ثابت + داده در context: "Payment failed" با order_id در فیلد جدا، نه "Payment failed for order 1234"؛ تا بتوان بر اساس پیام گروه‌بندی کرد.
  • سطح مناسب: خطاهای قابل‌انتظار کاربر (validation) را error لاگ نکنید؛ نویز ایجاد می‌کند.
  • در container، لاگ به stdout/stderr؛ روی سرور، rotation (مثلاً کانال daily یا logrotate).
  • سیاست retention و sampling برای لاگ‌های پرحجم (مثلاً debug یا health check).

سیستم لاگ Laravel روی کتابخانه‌ی Monolog ساخته شده و در config/logging.php با مفهوم channel پیکربندی می‌شود. هر channel یک driver (مقصد و نحوه‌ی نوشتن) دارد. کانال پیش‌فرض با LOG_CHANNEL تعیین می‌شود.

Context facade (Laravel 11+) و Request ID

در Laravel 11، Illuminate\Support\Facades\Context اضافه شد: داده‌ای که در Context قرار می‌گیرد به‌صورت metadata به همه‌ی لاگ‌ها اضافه می‌شود و مهم‌تر از آن، به jobهای صف که در همان درخواست dispatch می‌شوند منتقل می‌شود؛ پس request ID در لاگ‌های worker هم دیده می‌شود.

<?php
namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Context;
use Illuminate\Support\Str;
use Symfony\Component\HttpFoundation\Response;

class AssignRequestId
{
    public function handle(Request $request, Closure $next): Response
    {
        $requestId = $request->header('X-Request-Id') ?: (string) Str::uuid();

        Context::add('request_id', $requestId);
        Context::add('url', $request->path());

        $response = $next($request);
        $response->headers->set('X-Request-Id', $requestId);

        return $response;
    }
}

// bootstrap/app.php
->withMiddleware(function (Middleware $middleware) {
    $middleware->append(\App\Http\Middleware\AssignRequestId::class);
})

گزارش Exceptionها

در Laravel 11+ پیکربندی exceptionها در bootstrap/app.php و متد withExceptions انجام می‌شود: می‌توان گزارش برخی exceptionها را متوقف (dontReport)، context سراسری اضافه کرد (context) یا گزارش را به سرویس بیرونی فرستاد. فراخوانی report($e) یک exception را بدون قطع جریان برنامه گزارش می‌کند.

<?php
->withExceptions(function (Exceptions $exceptions) {
    $exceptions->dontReport([
        \App\Exceptions\CartEmptyException::class,
    ]);
    $exceptions->context(fn () => [
        'app_version' => config('app.version'),
    ]);
})

تفاوت‌ها: Log::withContext() context را به channel جاری در طول همین درخواست اضافه می‌کند؛ Log::shareContext() روی همه‌ی channelها؛ Context::add() علاوه بر لاگ‌ها، به jobهای صف هم منتقل می‌شود. پاسخ استاندارد برای «پیاده‌سازی correlation ID در Laravel»: middleware + Context + header پاسخ + انتقال header به درخواست‌های HTTP خروجی.

Cardinality labelها در Loki (و Prometheus) حیاتی است: label باید مقادیر محدود داشته باشد (app، env، level). گذاشتن user_id یا request_id به‌عنوان label، میلیون‌ها stream می‌سازد و سیستم را از کار می‌اندازد. این داده‌ها در محتوای لاگ (JSON) بمانند.

انواع متریک و Percentileها

یک metric مقدار عددی است که در طول زمان نمونه‌برداری می‌شود (time series) و با نام + labelها شناخته می‌شود؛ مثلاً http_requests_total{method="POST", route="/orders", status="500"}. هر ترکیب یکتای labelها یک time series جداگانه است.

یک histogram به نام http_request_duration_seconds در عمل چند series تولید می‌کند: ..._bucket{le="0.1"}، ..._bucket{le="0.5"}، … ، ..._bucket{le="+Inf"}، ..._sum و ..._count. bucketها تجمعیاند: le="0.5" یعنی تعداد درخواست‌های کمتر یا مساوی ۰٫۵ ثانیه.

چرا Percentile و نه میانگین؟

Percentile (صدک) pN مقداری است که N درصد مشاهدات کمتر یا مساوی آن هستند. p50 (میانه) تجربه‌ی «کاربر معمولی»، p95 و p99 تجربه‌ی «دم توزیع» (tail latency) را نشان می‌دهند.

مثال عددی: ۱۰۰ درخواست؛ ۹۵ تا در ۵۰ میلی‌ثانیه و ۵ تا در ۳۰۰۰ میلی‌ثانیه پاسخ داده شده‌اند.

  • میانگین = (۹۵×۵۰ + ۵×۳۰۰۰) ÷ ۱۰۰ = (۴۷۵۰ + ۱۵۰۰۰) ÷ ۱۰۰ = ۱۹۷٫۵ ms — عددی که هیچ کاربری تجربه نکرده است.
  • p50 = ۵۰ ms و p95 = ۵۰ ms (مرز)، اما p99 = ۳۰۰۰ ms: ۵٪ کاربران ۳ ثانیه منتظر مانده‌اند.
  • میانگین با چند مقدار بسیار بزرگ یا بسیار کوچک منحرف می‌شود و توزیع را پنهان می‌کند.
  • tail latency مهم است: در یک صفحه که ۱۰ درخواست backend می‌زند، احتمال اینکه دست‌کم یکی از p99 کندتر باشد حدود ۱ − ۰٫۹۹ به توان ۱۰ ≈ ۱۰٪ است؛ پس p99 سرویس به تجربه‌ی معمول کاربر تبدیل می‌شود.
  • کاربران پرمصرف (با داده‌ی بیشتر، سبد بزرگ‌تر) اغلب همان‌هایی هستند که در دم توزیع قرار می‌گیرند.

میانگین گرفتن از percentileها غلط است: میانگین p99 سه سرور، p99 کل سیستم نیست. باید bucketهای histogram را جمع کرد و سپس percentile را از مجموع محاسبه کرد. همچنین percentile درخواست‌های ناموفق سریع (مثلاً 500 فوری) می‌تواند latency را به‌طور کاذب خوب نشان دهد؛ latency موفق و ناموفق را جدا ببینید.

Pull در برابر Push

Pull (Prometheus)

  • Prometheus تعیین می‌کند چه چیزی و کی خوانده شود؛ کنترل مرکزی بار.
  • متریک خودکار up: اگر scrape شکست بخورد، می‌فهمیم target در دسترس نیست.
  • service discovery (Kubernetes، Consul، فایل).
  • چالش: targetهای پشت NAT/فایروال و jobهای کوتاه‌عمر.

Push (StatsD، OTLP، InfluxDB)

  • برنامه متریک را به collector می‌فرستد.
  • مناسب jobهای کوتاه‌عمر، serverless و شبکه‌های محدود.
  • تشخیص «مرده» سخت‌تر است (نبود داده ≠ خطا).
  • Prometheus برای batch jobها Pushgateway دارد.

چالش PHP: مدل اجرای PHP-FPM «share-nothing» است؛ هر درخواست حافظه‌ی مستقل دارد و فرایندها با هم حافظه‌ی مشترکی ندارند. پس یک counter در حافظه‌ی PHP بعد از درخواست از بین می‌رود. کتابخانه‌های Prometheus برای PHP (مثل promphp/prometheus_client_php) شمارنده‌ها را در یک storage مشترک مثل Redis یا APCu نگه می‌دارند و یک route /metrics آن‌ها را render می‌کند. برای متریک‌های زیرساختی از exporterها استفاده می‌شود: php-fpm_exporter (از status page FPM)، nginx-prometheus-exporter، mysqld_exporter، redis_exporter، node_exporter.

RED، USE و چهار سیگنال طلایی

این سه چارچوب پاسخ می‌دهند به: «چه چیزی را مانیتور کنیم؟» تا در انبوه متریک‌ها گم نشویم.

Four Golden Signals (Google SRE)

  1. Latency: زمان پاسخ؛ با تفکیک درخواست‌های موفق و ناموفق.
  2. Traffic: میزان تقاضا (درخواست در ثانیه، تراکنش، session).
  3. Errors: نرخ درخواست‌های ناموفق؛ صریح (5xx)، ضمنی (200 با محتوای غلط) یا بر اساس سیاست (کندتر از ۱ ثانیه = خطا).
  4. Saturation: میزان «پر بودن» سرویس؛ منبعی که اول تمام می‌شود (حافظه، CPU، طول صف، workerهای آزاد FPM، اتصالات دیتابیس). اغلب پیش‌بینی‌کننده‌ی مشکل آینده است.

RED (برای سرویس‌ها — Tom Wilkie)

  • Rate: تعداد درخواست در ثانیه.
  • Errors: تعداد/نرخ درخواست‌های ناموفق.
  • Duration: توزیع زمان پاسخ (percentileها).

RED دید مصرف‌کننده‌ی سرویس را می‌دهد و برای هر سرویس درخواست‌محور (API، وب، microservice) یکسان است؛ پس داشبوردهای استاندارد و قابل مقایسه می‌سازد.

USE (برای منابع — Brendan Gregg)

  • Utilization: درصد زمانی که منبع مشغول است (مثلاً CPU ۸۰٪).
  • Saturation: کار اضافه‌ای که منبع نمی‌تواند فوراً انجام دهد و در صف می‌ماند (run queue/load، swap، صف I/O).
  • Errors: خطاهای منبع (خطای دیسک، packet drop، خطای ECC).

USE برای منابع سخت‌افزاری و زیرساختی (CPU، حافظه، دیسک، شبکه، و حتی منابع نرم‌افزاری مثل connection pool) است و برای یافتن گلوگاه عملکرد به‌کار می‌رود.

نمونه برای یک اپلیکیشن Laravel

  • وب/API: RPS، نرخ 5xx و 4xx، p50/p95/p99 به تفکیک route.
  • PHP-FPM: active processes در برابر pm.max_children، listen queue (saturation)، تعداد دفعات رسیدن به max children.
  • صف: طول صف (backlog)، wait time (زمان انتظار job قبل از شروع)، throughput، نرخ jobهای failed، runtime هر job.
  • دیتابیس: QPS، کوئری‌های کند، اتصالات فعال در برابر max_connections، replication lag، deadlockها.
  • Cache/Redis: hit ratio، حافظه، evictionها.
  • کسب‌وکار: سفارش در دقیقه، نرخ موفقیت پرداخت؛ گاهی اولین نشانه‌ی خرابی همین‌هاست.

SLI، SLO، SLA و Error Budget

SLI
Service Level Indicator: یک معیار کمّی از کیفیت سرویس از دید کاربر، معمولاً به شکل نسبت «رویدادهای خوب ÷ کل رویدادها». مثال: درصد درخواست‌های موفق (غیر 5xx)، درصد درخواست‌هایی که زیر ۳۰۰ms پاسخ داده شده‌اند.
SLO
Service Level Objective: هدف داخلی برای یک SLI در یک بازه‌ی زمانی. مثال: «۹۹٫۹٪ درخواست‌های API در هر بازه‌ی ۳۰ روزه موفق باشند» یا «۹۵٪ درخواست‌ها زیر ۳۰۰ms».
SLA
Service Level Agreement: قرارداد با مشتری که شامل تعهد سطح سرویس و پیامد نقض آن (جریمه، اعتبار، بازپرداخت) است. معمولاً از SLO داخلی ضعیف‌تر است تا حاشیه‌ی امن وجود داشته باشد.
Error Budget
مقدار «خرابی مجاز» = ۱ − SLO. بودجه‌ای که تیم می‌تواند صرف ریسک (deploy، آزمایش، نگهداری) کند.
  SLI (اندازه‌گیری)  ──►  SLO (هدف داخلی: 99.9%)  ──►  SLA (قرارداد با مشتری: 99.5% + جریمه)
                                │
                                └─► Error Budget = 0.1%  ──►  سیاست: اگر تمام شد، تمرکز روی پایداری

نسخه‌ی مبتنی بر درخواست: اگر سرویس ماهانه ۱۰ میلیون درخواست دارد و SLO برابر ۹۹٫۹٪ است، error budget = ۱۰٬۰۰۰٬۰۰۰ × ۰٫۰۰۱ = ۱۰٬۰۰۰ درخواست ناموفق در ماه. اگر یک deploy معیوب در ۲۰ دقیقه ۶٬۰۰۰ درخواست را خراب کند، ۶۰٪ بودجه‌ی ماه مصرف شده است.

Error Budget Policy

  • بودجه باقی است: تیم آزاد است سریع deploy کند، آزمایش کند و ریسک بپذیرد.
  • بودجه تمام شده: توقف یا کند کردن انتشار قابلیت‌های جدید (به‌جز اصلاحات)، تمرکز بر پایداری، تست و رفع بدهی فنی تا بودجه بازیابی شود.
  • این سیاست تنش همیشگی بین «سرعت توسعه» و «پایداری» را با یک عدد مورد توافق حل می‌کند.

Burn rate

Burn rate سرعت مصرف بودجه نسبت به حالت یکنواخت است. burn rate = ۱ یعنی بودجه دقیقاً در پایان بازه‌ی SLO تمام می‌شود. با SLO ۹۹٫۹٪، اگر نرخ خطا ۱٫۴۴٪ باشد، burn rate = ۱۴٫۴ است؛ در این سرعت در یک ساعت ۲٪ بودجه‌ی ۳۰ روزه (۱۴٫۴ × ۱ ÷ ۷۲۰) مصرف می‌شود و کل بودجه در حدود ۵۰ ساعت تمام می‌شود. هشدارهای مبتنی بر burn rate (مثلاً «burn rate بالای ۱۴٫۴ در ۱ ساعت و ۵ دقیقه‌ی اخیر» ⇒ page) از هشدار ساده روی نرخ خطا دقیق‌ترند.

چرا SLO هیچ‌وقت ۱۰۰٪ نیست؟ (۱) ۱۰۰٪ دست‌یافتنی نیست و هزینه‌ی هر «نُه» اضافه تقریباً تصاعدی است؛ (۲) کاربر بین ۹۹٫۹۹٪ و ۱۰۰٪ تفاوتی حس نمی‌کند، چون شبکه‌ی موبایل و ISP خودش کمتر قابل‌اعتماد است؛ (۳) SLO صددرصد یعنی error budget صفر، یعنی هیچ deploy و تغییری مجاز نیست.

SLI خوب از دید کاربر اندازه‌گیری می‌شود (در Load Balancer یا نزدیک کاربر)، نه از دید سرور («CPU زیر ۸۰٪» SLI نیست). تعداد SLOها کم و معنادار باشد: معمولاً دسترس‌پذیری و latency برای مسیرهای حیاتی کاربر (login، checkout).

Alerting اصولی و On-call

هدف alert این است که یک انسان را در زمان مناسب برای اقدامی که فقط انسان می‌تواند انجام دهد مطلع کند. هر alert که نیاز به اقدام ندارد، هزینه است.

اصول

  • Symptom-based، نه cause-based: روی چیزی که کاربر حس می‌کند هشدار دهید (نرخ خطا، latency، مصرف error budget)، نه روی هر علت احتمالی (CPU ۹۰٪). CPU بالا با پاسخ‌دهی سالم مشکل نیست؛ و خرابی ممکن است علتی داشته باشد که هرگز برایش alert تعریف نکرده‌اید. علت‌ها برای دیباگ در داشبوردند.
  • Actionable: هر alert باید پاسخ روشنی برای «حالا چه کنم؟» داشته باشد و به یک runbook لینک شود.
  • Severity: فقط مشکلات فوری و اثرگذار بر کاربر ⇒ page (بیدار کردن on-call)؛ مشکلات غیرفوری (دیسک تا ۳ روز دیگر پر می‌شود، گواهی TLS دو هفته‌ی دیگر منقضی می‌شود) ⇒ ticket یا پیام کاری.
  • مدت پایداری (for): برای جلوگیری از flapping و هشدار روی spikeهای لحظه‌ای.
  • Grouping و deduplication: قطعی دیتابیس نباید ۲۰۰ alert جدا برای هر سرویس بسازد (Alertmanager: grouping، inhibition، silence).
  • بازبینی منظم: alertهایی که بدون اقدام بسته می‌شوند را حذف یا اصلاح کنید.
  • Alert روی نبود داده هم لازم است (up == 0، absent())؛ سکوت Monitoring نشانه‌ی سلامت نیست.

Alert fatigue

وقتی alertها زیاد، پرنویز یا غیرقابل اقدام باشند، تیم به آن‌ها عادت می‌کند، mute می‌کند یا دیر پاسخ می‌دهد و در نهایت alert واقعی هم نادیده گرفته می‌شود. نشانه‌ها: alertهایی که خودبه‌خود resolve می‌شوند، alertهای تکراری برای یک رخداد، page در نیمه‌شب برای چیزی که می‌توانست تا صبح صبر کند.

On-call و Runbook

  • On-call rotation با برنامه‌ی منصفانه، escalation policy (اگر نفر اول در X دقیقه ack نکرد ⇒ نفر دوم) و ابزارهایی مثل PagerDuty/Opsgenie/Grafana OnCall.
  • Runbook: سند کوتاه برای هر alert: معنی alert، اثر روی کاربر، داشبوردها و کوئری‌های لازم، قدم‌های تشخیص و mitigation، و چه زمانی escalate کنیم.
  • کارهای تکراری runbook کاندید خودکارسازی‌اند.

سه سوال برای ارزیابی هر alert: (۱) آیا کاربر اثر را حس می‌کند یا به‌زودی حس خواهد کرد؟ (۲) آیا اقدام فوری انسانی لازم است؟ (۳) آیا دستورالعمل اقدام (runbook) وجود دارد؟ اگر پاسخ هر کدام «نه» است، آن alert نباید page باشد.

Health Check، Uptime و Synthetic Monitoring

Health check endpoint

endpointی که وضعیت سلامت نمونه‌ی برنامه را برای Load Balancer، orchestrator یا سیستم Monitoring گزارش می‌دهد. در Laravel 11+ به‌طور پیش‌فرض در bootstrap/app.php مسیر /up تعریف شده است:

<?php
// bootstrap/app.php
return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    // ...

این route اگر برنامه بدون exception boot شود پاسخ 200 و در غیر این صورت 500 برمی‌گرداند. هنگام درخواست به آن، رویداد Illuminate\Foundation\Events\DiagnosingHealth dispatch می‌شود؛ با listener روی این رویداد می‌توان بررسی‌های بیشتری (مثل اتصال دیتابیس یا cache) اضافه کرد که اگر exception بدهند، health check شکست می‌خورد.

<?php
use Illuminate\Foundation\Events\DiagnosingHealth;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Event;

// AppServiceProvider::boot()
Event::listen(DiagnosingHealth::class, function () {
    DB::connection()->getPdo();      // در صورت قطعی دیتابیس exception ⇒ 500
});

Liveness در برابر Readiness

Liveness — «زنده‌ام؟»

  • آیا فرایند گیر کرده (deadlock، hang) و باید restart شود؟
  • سطحی؛ فقط وضعیت خود برنامه.
  • نباید وابستگی‌های بیرونی را چک کند: اگر DB قطع شود و liveness شکست بخورد، همه‌ی podها هم‌زمان restart می‌شوند و مشکل بدتر می‌شود.

Readiness — «آماده‌ی ترافیکم؟»

  • آیا این نمونه می‌تواند درخواست را درست پاسخ دهد؟
  • می‌تواند وابستگی‌های حیاتی را بررسی کند.
  • شکست ⇒ فقط از Load Balancer/Service خارج می‌شود، restart نمی‌شود.
  • در زمان startup و shutdown مهم است (zero-downtime deploy).

Health check «عمیق» که برای هر درخواست چند کوئری سنگین یا فراخوانی سرویس بیرونی انجام دهد، خودش بار ایجاد می‌کند و می‌تواند باعث cascading failure شود. بررسی‌ها سبک، با timeout کوتاه و در صورت نیاز با cache چندثانیه‌ای باشند. endpointهای health نباید اطلاعات حساس (نسخه‌ها، رشته‌ی اتصال) را افشا کنند.

Uptime و Synthetic Monitoring

  • Uptime check (black-box): سرویسی بیرونی از چند منطقه‌ی جغرافیایی هر دقیقه آدرس عمومی (مثلاً /up) را درخواست می‌کند و کد وضعیت، زمان پاسخ و اعتبار گواهی TLS را بررسی می‌کند. مشکلاتی را می‌گیرد که Monitoring داخلی نمی‌بیند: DNS، CDN، فایروال، گواهی منقضی، قطعی کل دیتاسنتر.
  • Synthetic monitoring: اجرای خودکار سناریوهای واقعی کاربر (login، جست‌وجو، افزودن به سبد، شروع پرداخت) به‌صورت دوره‌ای با اسکریپت یا مرورگر headless. حتی وقتی ترافیک واقعی کم است (نیمه‌شب) مشکل را کشف می‌کند.
  • RUM (Real User Monitoring): مکمل synthetic؛ اندازه‌گیری تجربه‌ی واقعی کاربران در مرورگر (Core Web Vitals، خطاهای JS).
  • Heartbeat / dead man's switch: برای cron و scheduler: job در پایان موفق یک URL را ping می‌کند؛ اگر ping نرسد، alert. Laravel برای taskهای زمان‌بندی‌شده متدهای pingBefore/thenPing و pingOnSuccess دارد.

APM، Distributed Tracing و Error Tracking

APM

Application Performance Monitoring ابزارهایی هستند که با instrumentation خودکار در سطح برنامه، زمان هر درخواست را به اجزایش (کوئری‌های دیتابیس، فراخوانی HTTP بیرونی، cache، رندر view) می‌شکنند، تراکنش‌های کند را نشان می‌دهند و مشکلاتی مثل N+1 query را آشکار می‌کنند. نمونه‌ها: New Relic، Datadog APM، Elastic APM، Sentry Performance، و راه‌حل‌های متن‌باز مبتنی بر OpenTelemetry.

Distributed Tracing

Trace
کل مسیر یک درخواست در سیستم؛ درختی از spanها با یک trace_id مشترک.
Span
یک واحد کار با نام، زمان شروع و پایان، span_id، parent_span_id، attributeها (مثل http.route، db.statement)، eventها و status.
Context propagation
انتقال trace_id و span_id والد از یک سرویس به سرویس بعدی (در header HTTP، metadata پیام صف) تا spanها به یک trace متصل شوند.
Sampling
نگهداری فقط بخشی از traceها برای کنترل هزینه. Head-based: تصمیم در ابتدای درخواست (مثلاً ۱۰٪)؛ ساده ولی ممکن است traceهای خطادار را از دست بدهد. Tail-based: تصمیم بعد از اتمام trace (مثلاً نگهداری همه‌ی traceهای خطادار یا کند)؛ دقیق‌تر ولی نیازمند buffer در collector.

OpenTelemetry

OpenTelemetry (OTel) یک استاندارد و مجموعه ابزار vendor-neutral (پروژه‌ی CNCF) برای تولید و ارسال traces، metrics و logs است. اجزا: API و SDK برای زبان‌ها (از جمله PHP)، کتابخانه‌های auto-instrumentation، پروتکل OTLP و Collector که داده را دریافت، پردازش (sampling، فیلتر، حذف PII) و به backendهای مختلف (Jaeger، Grafana Tempo، Zipkin، Datadog، …) صادر می‌کند. مزیت اصلی: یک بار instrument می‌کنید و backend را بدون تغییر کد عوض می‌کنید؛ vendor lock-in حذف می‌شود.

Error Tracking (Sentry)

ابزارهای error tracking مثل Sentry exceptionها را با جزئیات کامل جمع‌آوری می‌کنند و فراتر از لاگ ساده‌اند:

  • Grouping: هزاران رخداد یک خطا در یک issue با شمارنده (نه هزاران خط لاگ).
  • Stack trace کامل با کد اطراف، متغیرها و breadcrumbs (رویدادهای قبل از خطا: کوئری‌ها، لاگ‌ها، درخواست‌های HTTP).
  • Context: کاربر، مرورگر، URL، tagها و محیط.
  • Release tracking: کدام release خطا را معرفی کرد، «regression» پس از resolve، و اتصال به commit.
  • Alert روی خطای جدید یا افزایش ناگهانی نرخ یک خطا.

Telescope، Pulse و Horizon

اکوسیستم Laravel سه ابزار رسمی با هدف‌های متفاوت دارد که اغلب با هم اشتباه گرفته می‌شوند.

Laravel Telescope — دستیار دیباگ

Telescope جزئیات تک‌تک رویدادها را ثبت و در یک داشبورد نمایش می‌دهد: درخواست‌ها، exceptionها، لاگ‌ها، کوئری‌های دیتابیس (با زمان و تشخیص کوئری‌های تکراری)، jobهای صف، ایمیل‌ها، notificationها، cache، eventها، Redis، scheduled taskها و درخواست‌های HTTP خروجی. ابزاری عالی برای توسعه‌ی محلی و staging است.

  • به‌دلیل نوشتن حجم زیاد داده در دیتابیس برای هر درخواست، سربار دارد؛ در Production فقط با احتیاط: فیلتر (فقط exceptionها و رویدادهای مهم)، pruning منظم (telescope:prune) و محدود کردن دسترسی با gate.
  • معمولاً به‌صورت --dev نصب و فقط در محیط local ثبت می‌شود.

Laravel Pulse — نمای کلی Production

Pulse داشبوردی سبک و طراحی‌شده برای Production است که داده را تجمیع‌شده (نه تک‌رویداد) نشان می‌دهد تا گلوگاه‌ها و روندها دیده شوند:

  • درخواست‌ها، کوئری‌ها، jobها و درخواست‌های HTTP خروجی کند (با آستانه‌ی قابل تنظیم)؛
  • exceptionهای پرتکرار؛
  • کاربران پرمصرف (Application Usage)؛
  • throughput صف‌ها؛ وضعیت cache (hit/miss)؛
  • منابع سرورها (CPU، حافظه، دیسک) با اجرای دستور php artisan pulse:check روی هر سرور.

برای کاهش سربار از sampling و در ترافیک بالا از ingest از طریق Redis (و دستور pulse:work) پشتیبانی می‌کند؛ داده‌ها در دیتابیس ذخیره می‌شوند و کارت‌های سفارشی قابل اضافه شدن‌اند.

Laravel Horizon — داشبورد و مدیریت صف Redis

Horizon برای صف‌های مبتنی بر Redis است و دو نقش دارد:

  • پیکربندی workerها به‌صورت کد در config/horizon.php: supervisorها، صف‌ها، تعداد فرایند و balancing خودکار (auto/simple) بین صف‌ها؛ اجرای همه با یک فرایند php artisan horizon.
  • Monitoring صف: throughput، runtime، wait time هر صف، jobهای در حال اجرا، تکمیل‌شده و failed (با امکان retry)، tagها، و هشدار (notification) وقتی wait time از آستانه‌ی تعیین‌شده (waits) بیشتر شود.
  • برای نمودارهای metrics، دستور horizon:snapshot باید به‌صورت زمان‌بندی‌شده (مثلاً هر ۵ دقیقه) اجرا شود. پس از deploy با horizon:terminate فرایندها با کد جدید راه‌اندازی می‌شوند.

مدیریت Incident، Postmortem و MTTD/MTTR

Incident رخدادی برنامه‌ریزی‌نشده است که سرویس را مختل کرده یا کیفیتش را کاهش داده است (یا تهدید می‌کند که خواهد کرد). مدیریت incident فرایندی ساخت‌یافته برای بازگرداندن سریع سرویس و یادگیری از آن است.

چرخه‌ی Incident

  رخداد ─► تشخیص (Detect) ─► تأیید/Ack ─► Triage (شدت) ─► Mitigate (توقف خونریزی) ─► Resolve ─► Postmortem ─► Action items
           └── MTTD ──┘└─ MTTA ─┘                 └──────────── MTTR ────────────┘
  • Severity: سطوحی مثل SEV1 (قطعی کامل یا از دست رفتن داده، همه‌ی کاربران) تا SEV3/SEV4 (اثر جزئی، دور زدنی). شدت تعیین می‌کند چه کسانی و با چه سرعتی درگیر شوند.
  • نقش‌ها: Incident Commander (هماهنگی و تصمیم‌گیری، نه لزوماً رفع فنی)، مسئول ارتباطات (به‌روزرسانی status page و ذی‌نفعان)، و کارشناسان فنی (Operations).
  • اولویت mitigation بر root cause: ابتدا rollback، خاموش کردن feature flag، failover یا افزایش ظرفیت؛ تحلیل ریشه بعداً.
  • ثبت timeline در کانال incident در لحظه.
  • ارتباط با کاربران (status page) به‌موقع و صادقانه.

Blameless Postmortem

سندی که پس از incident نوشته می‌شود تا بفهمیم سیستم و فرایند چگونه اجازه‌ی وقوع آن را دادند و چه تغییری از تکرارش جلوگیری می‌کند. «بدون سرزنش» یعنی فرض می‌کنیم افراد با اطلاعات و ابزاری که داشتند تصمیم معقولی گرفتند؛ اگر یک انسان توانسته با یک دستور Production را خراب کند، مشکل در نبود محافظ است. سرزنش باعث پنهان‌کاری و از دست رفتن اطلاعات می‌شود.

ساختار

  1. خلاصه و اثر (مدت، درصد کاربران متأثر، درخواست‌های ناموفق، مصرف error budget، اثر مالی).
  2. Timeline دقیق با زمان: شروع، تشخیص، اقدامات، بازیابی.
  3. علت ریشه‌ای و عوامل مشارکت‌کننده (معمولاً بیش از یک عامل؛ تکنیک «5 Whys»).
  4. تشخیص: چطور فهمیدیم؟ آیا alert زودتر می‌توانست بفهمد؟
  5. آنچه خوب پیش رفت و آنچه بد پیش رفت.
  6. Action itemها با مالک و مهلت (پیشگیری، تشخیص سریع‌تر، mitigation سریع‌تر) و پیگیری تا اتمام.

متریک‌های زمانی

MTTD
Mean Time To Detect: میانگین زمان از شروع مشکل تا تشخیص آن. با Monitoring و alerting بهتر کاهش می‌یابد. اگر کاربران زودتر از alert شما متوجه می‌شوند، MTTD مشکل دارد.
MTTA
Mean Time To Acknowledge: از alert تا پذیرش توسط on-call.
MTTR
Mean Time To Recover/Restore (گاهی Repair یا Resolve): میانگین زمان از شروع (یا تشخیص) خرابی تا بازگشت سرویس. با rollback سریع، feature flag، runbook و اتوماسیون کاهش می‌یابد. تعریف دقیق باید در تیم مشخص شود، چون این مخفف معانی مختلفی دارد.
MTBF
Mean Time Between Failures: میانگین فاصله بین خرابی‌ها؛ معیار قابلیت اطمینان.

در سیستم‌های پیچیده، جلوگیری از همه‌ی خرابی‌ها ممکن نیست؛ پس کاهش MTTD و MTTR اغلب بازده بیشتری از تلاش برای بالا بردن MTBF دارد. این همان نگاه DORA است که «Time to Restore» را یکی از چهار متریک کلیدی می‌داند.

سوالات تشریحی

Monitoring و Observability را تعریف و مقایسه کنید.

Monitoring: جمع‌آوری و نمایش مجموعه‌ای از متریک‌ها و بررسی‌های از پیش تعریف‌شده و هشدار در صورت عبور از آستانه‌ها. به سوال‌هایی پاسخ می‌دهد که از قبل می‌دانستیم باید بپرسیم (known unknowns): «نرخ خطا بالای ۱٪ است؟»، «دیسک پر است؟».

Observability: ویژگی سیستم است: اینکه چقدر می‌توان از روی خروجی‌های آن (logs، metrics، traces و events) وضعیت درونی‌اش را فهمید، حتی برای سوال‌هایی که پیش‌بینی نکرده بودیم (unknown unknowns). نیازمند داده‌ی غنی با context و cardinality بالا (user_id، نسخه، endpoint)، همبستگی بین سیگنال‌ها (trace_id در لاگ) و امکان کوئری آزاد است.

  • Monitoring می‌گوید چه چیزی خراب است؛ Observability کمک می‌کند بفهمیم چرا.
  • Monitoring برای خرابی‌های شناخته‌شده و تکراری کافی است؛ در سیستم‌های توزیع‌شده و microservice که حالت‌های خرابی جدید و ترکیبی دارند، Observability ضروری است.
  • Monitoring یک فعالیت/ابزار است؛ Observability با instrumentation در طراحی سیستم ایجاد می‌شود.

رابطه: رقیب نیستند؛ Monitoring بخشی از Observability است. مثال: alert روی افزایش p99 (monitoring)، سپس بررسی traceهای کند و لاگ‌های مرتبط برای یافتن اینکه فقط درخواست‌های یک مشتری بزرگ با یک کوئری خاص کند شده‌اند (observability).

سه ستون Observability (Logs، Metrics، Traces) را توضیح دهید. هرکدام برای چه نوع سوالی مناسب است و چگونه با هم استفاده می‌شوند؟
  • Logs: رکوردهای زمان‌دار و با جزئیات از رویدادهای گسسته. مناسب «دقیقاً چه اتفاقی برای این درخواست/کاربر افتاد؟». قوت: جزئیات و context. ضعف: حجم و هزینه‌ی بالا و دشواری روندیابی.
  • Metrics: مقادیر عددی تجمیع‌شده در زمان با labelهای محدود. مناسب «روند چیست؟ آیا الان غیرعادی است؟» و پایه‌ی داشبورد و alert. قوت: ارزان، سریع، فشرده. ضعف: جزئیات تک‌رویداد ندارد و cardinality محدود است.
  • Traces: مسیر end-to-end یک درخواست به‌صورت درختی از spanها در سرویس‌ها و اجزا. مناسب «زمان این درخواست کجا صرف شد؟ کدام وابستگی کند است؟». ضعف: نیاز به instrumentation و context propagation؛ معمولاً sampling.
  • Events (مکمل): deploy، تغییر config، feature flag؛ برای پاسخ به «چه چیزی تغییر کرد؟».

جریان ترکیبی در عیب‌یابی:

  1. alert روی metric (نرخ 5xx بالا رفته) و annotation deploy روی نمودار.
  2. تفکیک metric بر اساس route و instance برای محدود کردن دامنه.
  3. رفتن به traceهای نمونه‌ی خطادار/کند برای یافتن span مقصر.
  4. جست‌وجوی logها با همان trace_id برای دیدن پیام خطا و context.

کلید این جریان همبستگی است: یک شناسه‌ی مشترک (trace_id/request_id) و labelهای یکسان (service، env، version) در هر سه.

Structured logging چیست و چه مزیتی بر لاگ متنی دارد؟ چه اطلاعاتی را نباید در لاگ نوشت؟

تعریف: ثبت لاگ به‌صورت رکوردهای با فیلدهای مشخص و قابل پردازش ماشینی (معمولاً JSON)، به‌جای رشته‌ی متنی آزاد.

{"level":"error","message":"Payment failed","order_id":1234,"user_id":88,
 "gateway":"zarinpal","request_id":"6f1c...","service":"shop-api"}

مزایا:

  • جست‌وجو و فیلتر دقیق روی فیلدها (order_id=1234، gateway=zarinpal AND level=error) بدون regex شکننده.
  • تجمیع و ساخت متریک از لاگ (تعداد خطا به تفکیک gateway).
  • همبستگی با request_id/trace_id بین سرویس‌ها و jobها.
  • پیام ثابت + context متغیر ⇒ گروه‌بندی آسان.
  • مقاوم‌تر در برابر log injection.

نباید لاگ شود:

  • رمز عبور، توکن، API key، header Authorization، کوکی session، کلیدهای رمزنگاری.
  • شماره‌ی کامل کارت و CVV2.
  • PII غیرضروری (کد ملی، تلفن، آدرس، ایمیل کامل)؛ در صورت نیاز ماسک یا hash.
  • بدنه‌ی کامل درخواست/پاسخ و bindings کوئری‌ها به‌صورت پیش‌فرض.

دلیل: لاگ‌ها دسترسی گسترده‌تر، کپی‌های متعدد و نگهداری طولانی‌تری از دیتابیس دارند؛ نشت از لاگ یکی از رایج‌ترین مسیرهای افشای داده و نقض الزامات قانونی (مثل GDPR یا PCI DSS) است.

چگونه در یک اپلیکیشن Laravel که jobهای صف و فراخوانی به سرویس‌های دیگر دارد، Correlation ID پیاده‌سازی می‌کنید؟

هدف: همه‌ی لاگ‌های مربوط به یک درخواست کاربر، در وب، jobهای صف و سرویس‌های پایین‌دستی، با یک شناسه‌ی مشترک قابل یافتن باشند.

  1. Middleware سراسری: شناسه را از header ورودی X-Request-Id (اگر Load Balancer یا سرویس بالادستی فرستاده) بخوان یا UUID جدید بساز.
  2. افزودن به Context: Context::add('request_id', $id) (Laravel 11+). داده‌ی Context به‌صورت metadata به همه‌ی لاگ‌ها اضافه و به‌طور خودکار به jobهای dispatch‌شده منتقل می‌شود؛ پس لاگ‌های worker هم همان شناسه را دارند. (در نسخه‌های قدیمی‌تر: Log::withContext و انتقال دستی در payload job.)
  3. بازگرداندن در پاسخ: $response->headers->set('X-Request-Id', $id) تا پشتیبانی بتواند از کاربر بگیرد.
  4. انتقال به سرویس‌های دیگر: افزودن header در درخواست‌های خروجی: Http::withHeaders(['X-Request-Id' => Context::get('request_id')]) (یا یک macro/middleware برای HTTP client).
  5. لاگ ساختاریافته (JSON) تا فیلد request_id در سیستم مرکزی قابل فیلتر باشد.
<?php
public function handle(Request $request, Closure $next): Response
{
    $id = $request->header('X-Request-Id') ?: (string) Str::uuid();
    Context::add('request_id', $id);

    $response = $next($request);
    $response->headers->set('X-Request-Id', $id);
    return $response;
}

تکامل: با OpenTelemetry، header استاندارد traceparent (W3C Trace Context) به‌طور خودکار propagate می‌شود و trace_id همین نقش را بازی می‌کند، با این مزیت که spanها و زمان‌بندی هم ثبت می‌شوند. باید به header ورودی از منابع غیرقابل اعتماد با احتیاط نگاه کرد (اعتبارسنجی قالب و طول).

انواع متریک Counter، Gauge، Histogram و Summary را با مثال توضیح دهید. چرا برای latency معمولاً Histogram را بر Summary ترجیح می‌دهند؟
  • Counter: فقط افزایشی (با restart صفر می‌شود). مثال: http_requests_total، jobs_failed_total. مقدار خامش معنای کمی دارد؛ با rate() یا increase() استفاده می‌شود.
  • Gauge: مقدار لحظه‌ای که بالا و پایین می‌رود. مثال: طول صف، حافظه‌ی مصرفی، اتصالات فعال دیتابیس، تعداد workerهای مشغول FPM.
  • Histogram: شمارش مشاهدات در bucketهای از پیش تعریف‌شده‌ی تجمعی (_bucket{le="0.5"}) به‌علاوه‌ی _sum و _count. percentile در سمت سرور با histogram_quantile() محاسبه می‌شود.
  • Summary: quantileها (مثلاً 0.5، 0.9، 0.99) را در خود کلاینت روی یک پنجره‌ی زمانی محاسبه می‌کند، به‌علاوه‌ی sum و count.

چرا Histogram برای latency:

  • قابلیت تجمیع: bucketهای چند instance قابل جمع‌اند و می‌توان p95 کل سرویس را محاسبه کرد؛ quantileهای Summary قابل تجمیع نیستند (میانگین p99 سه سرور، p99 کل نیست).
  • انعطاف در کوئری: هر percentile و هر بازه را بعداً می‌توان محاسبه کرد؛ در Summary quantileها از قبل ثابت‌اند.
  • محاسبه‌ی درصد درخواست‌های زیر آستانه (برای SLI) مستقیماً از bucket ممکن است.
  • سربار کمتر در کلاینت.

هزینه‌ی Histogram: دقت percentile به انتخاب bucketها بستگی دارد (درون‌یابی خطی داخل bucket) و هر bucket یک series جداگانه است؛ پس bucketها باید متناسب با SLO انتخاب شوند (مثلاً یک مرز دقیقاً روی ۳۰۰ms اگر SLO آن است). Summary وقتی مناسب است که فقط یک instance داریم و quantile دقیق می‌خواهیم.

چرا برای سنجش latency از percentileها (p50، p95، p99) استفاده می‌کنیم و نه میانگین؟ با یک مثال عددی توضیح دهید.

تعریف: pN مقداری است که N درصد مشاهدات کمتر یا مساوی آن هستند. p50 (میانه) تجربه‌ی معمول، p95/p99 تجربه‌ی بدترین درصدهای کاربران (tail latency) را نشان می‌دهند.

مثال: از ۱۰۰ درخواست، ۹۵ تا در ۵۰ms و ۵ تا در ۳۰۰۰ms پاسخ گرفته‌اند.

  • میانگین = (۹۵×۵۰ + ۵×۳۰۰۰)/۱۰۰ = ۱۹۷٫۵ms؛ نه نماینده‌ی ۹۵٪ کاربران (۵۰ms) و نه آن ۵٪ (۳ ثانیه). عددی است که هیچ‌کس تجربه نکرده.
  • p50 = ۵۰ms، p99 = ۳۰۰۰ms: به‌وضوح نشان می‌دهد گروهی از کاربران تجربه‌ی بسیار بدی دارند.

چرا tail مهم است:

  • توزیع latency معمولاً نامتقارن و دُم‌بلند است؛ میانگین آن را پنهان می‌کند و با چند مقدار پرت جابه‌جا می‌شود.
  • Fan-out: اگر یک صفحه ۱۰ فراخوانی موازی داشته باشد، احتمال اینکه دست‌کم یکی از p99 کندتر باشد حدود ۱ − ۰٫۹۹ به توان ۱۰ ≈ ۱۰٪ است؛ p99 هر جزء به تجربه‌ی رایج کاربر تبدیل می‌شود.
  • کاربران با بیشترین داده و تعامل (اغلب ارزشمندترین مشتریان) معمولاً در دم توزیع‌اند.

نکات عملی: percentileها را نمی‌توان میانگین گرفت؛ باید از histogram تجمیع‌شده محاسبه شوند. latency درخواست‌های موفق و ناموفق را جدا ببینید (خطاهای سریع، p99 را کاذب خوب نشان می‌دهند). SLO latency را به شکل «۹۵٪ درخواست‌ها زیر ۳۰۰ms» تعریف کنید.

SLI، SLO و SLA را تعریف کنید. Error budget چیست؟ برای یک سرویس با SLO دسترس‌پذیری ۹۹٫۹٪ در ۳۰ روز، بودجه‌ی خطا را محاسبه و نحوه‌ی استفاده از آن را توضیح دهید.
  • SLI: معیار کمّی کیفیت سرویس از دید کاربر؛ معمولاً نسبت رویدادهای خوب به کل. مثال: درصد درخواست‌های غیر 5xx؛ درصد درخواست‌های زیر ۳۰۰ms.
  • SLO: هدف داخلی برای SLI در یک بازه. مثال: «۹۹٫۹٪ درخواست‌ها در هر ۳۰ روز موفق».
  • SLA: قرارداد با مشتری با پیامد مالی/حقوقی در صورت نقض؛ معمولاً سست‌تر از SLO (مثلاً SLA ۹۹٫۵٪ وقتی SLO ۹۹٫۹٪ است) تا قبل از نقض قرارداد هشدار بگیریم.
  • Error budget: ۱ − SLO؛ مقدار خرابی مجاز.

محاسبه: ۳۰ روز × ۲۴ ساعت × ۶۰ دقیقه = ۴۳٬۲۰۰ دقیقه. ۰٫۱٪ از آن = ۴۳٫۲ دقیقه downtime مجاز در ماه. به‌صورت مبتنی بر درخواست: با ۱۰ میلیون درخواست در ماه، ۱۰٬۰۰۰ درخواست ناموفق مجاز است.

استفاده:

  • تصمیم‌گیری داده‌محور بین سرعت و پایداری: تا وقتی بودجه باقی است، تیم می‌تواند سریع deploy کند و ریسک بپذیرد؛ وقتی تمام شد، طبق error budget policy انتشار قابلیت جدید متوقف و تمرکز روی پایداری می‌شود.
  • Alerting بر اساس burn rate: مثلاً اگر در ۱ ساعت بیش از ۲٪ بودجه‌ی ماه مصرف شود (burn rate ۱۴٫۴)، page.
  • اولویت‌بندی کار: incidentی که ۶۰٪ بودجه را مصرف کرده، action itemهایش اولویت دارند.

چرا ۱۰۰٪ نه؟ دست‌نیافتنی، با هزینه‌ی تصاعدی، فراتر از قابلیت اطمینان شبکه‌ی خود کاربر، و به معنای منع هر تغییر.

روش‌های RED و USE و چهار سیگنال طلایی را توضیح دهید و تفاوت کاربرد آن‌ها را بنویسید.

Four Golden Signals (کتاب SRE گوگل):

  • Latency (با تفکیک موفق/ناموفق)، Traffic (تقاضا)، Errors (صریح، ضمنی، سیاستی) و Saturation (پر بودن منبع محدودکننده؛ پیش‌بینی‌کننده‌ی مشکل).

RED (برای سرویس‌ها): Rate (درخواست بر ثانیه)، Errors (درخواست‌های ناموفق)، Duration (توزیع زمان پاسخ). دید مصرف‌کننده‌ی سرویس؛ برای هر API و microservice یکسان، پس داشبورد استاندارد می‌سازد.

USE (برای منابع): برای هر منبع (CPU، حافظه، دیسک، شبکه، connection pool): Utilization (درصد مشغولی)، Saturation (کار در صف/انتظار) و Errors. برای یافتن گلوگاه‌های زیرساختی.

رابطه: RED تقریباً همان Golden Signals بدون Saturation است. در عمل: alert روی RED/Golden Signals (symptom)، دیباگ با USE (cause). مثال Laravel: افزایش p99 در RED ← در USE دیده می‌شود FPM به max_children رسیده (saturation) و CPU دیتابیس ۱۰۰٪ است.

تیم on-call شما هر شب ده‌ها alert دریافت می‌کند که بیشترشان نیاز به اقدام ندارند. مشکل چیست و سیستم alerting را چگونه بازطراحی می‌کنید؟

مشکل: Alert fatigue. وقتی alertها پرنویز و غیرقابل اقدام‌اند، افراد به آن‌ها بی‌توجه می‌شوند، mute می‌کنند یا دیر پاسخ می‌دهند و alert واقعی گم می‌شود؛ به‌علاوه‌ی فرسودگی تیم.

بازطراحی:

  1. ممیزی: فهرست alertهای چند هفته‌ی اخیر؛ کدام‌ها منجر به اقدام شدند؟ alertهای بدون اقدام حذف، تجمیع یا به ticket تبدیل شوند.
  2. Symptom-based: page فقط برای اثر روی کاربر: نرخ خطا، latency، burn rate error budget. alertهای علت‌محور (CPU ۹۰٪، یک pod restart شد) به داشبورد یا ticket منتقل شوند.
  3. Severity و routing: page فقط برای فوری و اثرگذار؛ ticket برای کارهای قابل انتظار تا ساعت کاری (دیسک ۳ روز دیگر پر می‌شود).
  4. کاهش flapping: بازه‌ی for: مناسب، hysteresis، و بازه‌ی محاسبه‌ی معقول.
  5. Grouping/inhibition: در Alertmanager، alertهای مرتبط با یک رخداد در یک اعلان؛ اگر دیتابیس down است، alertهای وابسته سرکوب شوند.
  6. Runbook برای هر alert باقی‌مانده و لینک آن در annotation.
  7. خودکارسازی واکنش‌های تکراری (restart، پاک‌سازی دیسک، autoscaling) به‌جای page.
  8. بازبینی دوره‌ای و متریک‌هایی مثل تعداد page در هر شیفت.

معیار: هر page باید فوری، اثرگذار بر کاربر، نیازمند قضاوت انسانی و دارای runbook باشد.

مدل pull در Prometheus را با مدل push مقایسه کنید. جمع‌آوری متریک‌های برنامه‌ای از یک اپلیکیشن PHP-FPM چه چالشی دارد و چگونه حل می‌شود؟

Pull (Prometheus): Prometheus در فواصل منظم endpoint /metrics هر target را scrape می‌کند.

  • مزایا: کنترل مرکزی نرخ و بار؛ متریک up خودکار برای تشخیص target در دسترس نبودن؛ service discovery؛ آسانی دیباگ (باز کردن /metrics در مرورگر)؛ برنامه به سیستم Monitoring وابسته نیست.
  • معایب: targetهای پشت NAT/فایروال؛ jobهای کوتاه‌عمر ممکن است قبل از scrape تمام شوند (راه‌حل: Pushgateway).

Push (StatsD، OTLP، InfluxDB): برنامه داده را به collector می‌فرستد. مناسب serverless و jobهای کوتاه؛ اما تشخیص «سرویس مرده» از «سرویس بدون داده» سخت‌تر و کنترل بار با فرستنده‌هاست.

چالش PHP-FPM: مدل اجرای PHP share-nothing است: هر درخواست در یک worker با حافظه‌ی مستقل اجرا می‌شود و پس از پایان درخواست state پاک می‌شود. پس نمی‌توان مثل Go/Java یک counter درون‌حافظه‌ای در طول عمر فرایند نگه داشت و در /metrics نمایش داد.

راه‌حل‌ها:

  • کتابخانه‌ای مثل promphp/prometheus_client_php با storage مشترک (Redis یا APCu)؛ هر درخواست counter را در Redis افزایش می‌دهد و یک route /metrics (محافظت‌شده) آن‌ها را render می‌کند.
  • ارسال push به StatsD یا OpenTelemetry Collector (UDP/OTLP) که تجمیع می‌کند و برای Prometheus expose می‌کند.
  • Exporterها برای متریک‌های زیرساختی: php-fpm_exporter (status page FPM: active/idle processes، listen queue، max children reached)، nginx، mysqld، redis و node_exporter.
  • متریک‌های صف از Horizon یا یک command زمان‌بندی‌شده که gaugeها (طول صف) را به‌روز می‌کند.
Distributed tracing چیست؟ مفاهیم trace، span و context propagation را توضیح دهید و نقش OpenTelemetry را بیان کنید.

تعریف: روشی برای ثبت مسیر کامل یک درخواست در میان سرویس‌ها و اجزای یک سیستم توزیع‌شده، به‌همراه زمان‌بندی هر بخش، تا بتوان فهمید latency و خطا دقیقاً در کجا رخ داده است.

  • Trace: کل سفر یک درخواست؛ درختی از spanها با یک trace_id مشترک.
  • Span: یک واحد کار (درخواست HTTP، کوئری دیتابیس، فراخوانی سرویس دیگر، پردازش job) با نام، زمان شروع/پایان، span_id، parent_span_id، attributeها و status.
  • Context propagation: انتقال trace_id و span والد از سرویسی به سرویس دیگر، معمولاً با header استاندارد W3C traceparent (00-<trace-id>-<parent-span-id>-<flags>) در HTTP و metadata در پیام‌های صف. بدون propagation، هر سرویس trace جداگانه‌ای دارد و تصویر end-to-end از بین می‌رود.
  • Sampling: head-based (تصمیم در ابتدا، ساده) یا tail-based (پس از پایان، نگهداری همه‌ی traceهای خطادار/کند).

OpenTelemetry: استاندارد باز و vendor-neutral (CNCF) شامل API/SDK برای زبان‌ها (از جمله PHP)، auto-instrumentation برای فریم‌ورک‌ها و کتابخانه‌ها، پروتکل OTLP و Collector برای پردازش (batch، sampling، حذف PII) و ارسال به backendهای مختلف (Jaeger، Tempo، Zipkin، سرویس‌های تجاری). مزیت: یک بار instrument، تغییر backend بدون تغییر کد و یکپارچگی traces، metrics و logs.

کاربرد: یافتن سرویس یا کوئری کند در یک زنجیره، کشف N+1 و فراخوانی‌های سریالی که می‌توانستند موازی باشند، درک وابستگی‌ها (service map) و اتصال لاگ‌ها به درخواست با trace_id.

یک سناریو: بعد از deploy دیروز، کاربران از کندی صفحه‌ی checkout شکایت دارند؛ میانگین latency تغییر چندانی نکرده ولی p99 از ۴۰۰ms به ۳ ثانیه رسیده است. چگونه بررسی می‌کنید؟

۱. تأیید و محدود کردن دامنه: نمودار p99 را با annotation deploy مقایسه کنید؛ آیا شروع افزایش دقیقاً با deploy منطبق است؟ تفکیک بر اساس route، instance، نوع کاربر و موفق/ناموفق. ثابت ماندن میانگین یعنی مشکل در درصد کوچکی از درخواست‌هاست (tail).

۲. Mitigation در صورت شدت: اگر اثر جدی است و همبستگی با deploy قوی است، rollback یا خاموش کردن feature flag مرتبط، سپس تحلیل.

۳. Traceها: traceهای نمونه از درخواست‌های بالای ۲ ثانیه‌ی checkout را باز کنید؛ کدام span زمان را گرفته؟ (کوئری دیتابیس، فراخوانی درگاه پرداخت، lock، cache miss).

۴. فرضیه‌های رایج و نحوه‌ی بررسی:

  • N+1 یا کوئری بدون index که فقط برای سبدهای بزرگ کند است ⇒ Pulse (slow queries)، slow query log، EXPLAIN.
  • Saturation: FPM به max_children رسیده و درخواست‌ها در صف می‌مانند ⇒ متریک‌های php-fpm_exporter (listen queue)؛ اتصالات دیتابیس نزدیک max_connections.
  • وابستگی بیرونی کند یا timeout بلند ⇒ spanهای HTTP خروجی؛ آیا timeout و retry درست تنظیم شده؟
  • Cache: کلید cache در کد جدید عوض شده (cache stampede) یا cache پاک شده ⇒ hit ratio.
  • Lock contention در دیتابیس (SELECT … FOR UPDATE جدید) ⇒ lock waits.

۵. لاگ‌ها و خطاها: با trace_id traceهای کند، لاگ‌ها و Sentry (timeoutها، retryها) را بررسی کنید.

۶. رفع و پیشگیری: اصلاح (index، eager loading، timeout)، تست بار روی سناریو، افزودن SLO/alert روی p99 checkout (نه میانگین) و postmortem. درس کلیدی: میانگین این مشکل را پنهان کرد.

Laravel Telescope، Pulse و Horizon را مقایسه کنید. کدام را در Production استفاده می‌کنید و چرا؟

Telescope: دستیار دیباگ که تک‌تک رویدادها را با جزئیات کامل ثبت می‌کند: درخواست‌ها، کوئری‌ها، exceptionها، لاگ‌ها، jobها، ایمیل‌ها، cache، eventها، HTTP خروجی. عالی برای توسعه و staging. در Production به‌دلیل سربار نوشتن حجم زیاد داده و حساسیت اطلاعات، یا استفاده نمی‌شود یا با فیلتر شدید، pruning و gate دسترسی.

Pulse: داشبورد سبک و تجمیعی طراحی‌شده برای Production: کندترین درخواست‌ها، کوئری‌ها، jobها و درخواست‌های خروجی، exceptionهای پرتکرار، کاربران پرمصرف، throughput صف، cache و منابع سرورها (با pulse:check). با sampling و ingest از طریق Redis سربار را کنترل می‌کند.

Horizon: مخصوص صف‌های Redis: پیکربندی workerها به‌صورت کد (supervisorها، balancing، تعداد فرایند)، داشبورد throughput، runtime، wait time، jobهای failed با retry، tagها و notification وقتی wait time از آستانه بیشتر شود. نیاز به horizon:snapshot زمان‌بندی‌شده برای نمودارها.

Health check endpoint چیست؟ تفاوت liveness و readiness را توضیح دهید و بگویید route /up در Laravel چگونه کار می‌کند.

تعریف: endpointی که orchestrator، Load Balancer یا سیستم Monitoring به‌طور دوره‌ای فراخوانی می‌کند تا بفهمد یک نمونه‌ی برنامه سالم است و می‌تواند ترافیک بگیرد.

  • Liveness: «آیا فرایند زنده است و گیر نکرده؟» شکست ⇒ restart. باید سطحی باشد و وابستگی‌های بیرونی را چک نکند؛ وگرنه قطعی دیتابیس باعث restart هم‌زمان همه‌ی نمونه‌ها و بدتر شدن وضع می‌شود.
  • Readiness: «آیا آماده‌ی سرویس‌دهی است؟» شکست ⇒ خروج از Load Balancer بدون restart. می‌تواند وابستگی‌های حیاتی را بررسی کند. در startup (warmup) و هنگام shutdown در deploy بدون downtime اهمیت دارد.
  • Startup probe (Kubernetes): برای برنامه‌هایی با شروع کند تا liveness زودهنگام آن‌ها را نکشد.

Laravel /up: از Laravel 11 در bootstrap/app.php با withRouting(health: '/up') تعریف می‌شود. اگر برنامه بدون exception boot شود 200 و در غیر این صورت 500 برمی‌گرداند. رویداد DiagnosingHealth را dispatch می‌کند؛ با listener می‌توان بررسی‌هایی مثل اتصال دیتابیس اضافه کرد (exception ⇒ 500).

بهترین روش‌ها: سبک و سریع با timeout کوتاه؛ عدم افشای اطلاعات حساس؛ عدم ثبت لاگ برای هر فراخوانی health check (نویز)؛ و استفاده از uptime check بیرونی روی همین endpoint برای کشف مشکلات DNS، TLS و شبکه که Monitoring داخلی نمی‌بیند.

Blameless postmortem چیست و چه بخش‌هایی دارد؟ MTTD و MTTR را تعریف کنید و راه‌های کاهش هرکدام را بنویسید.

Blameless postmortem: سندی که پس از هر incident مهم نوشته می‌شود تا بفهمیم چه شد، چرا شد و چه تغییری از تکرارش جلوگیری می‌کند، بدون مقصر دانستن افراد. فرض این است که افراد با اطلاعات موجود تصمیم معقولی گرفتند و خطای انسانی نشانه‌ی ضعف در سیستم و محافظ‌هاست. سرزنش باعث پنهان‌کاری و از دست رفتن اطلاعات می‌شود.

بخش‌ها:

  1. خلاصه و اثر (مدت، کاربران متأثر، error budget مصرف‌شده).
  2. Timeline دقیق: شروع، تشخیص، اقدامات، بازیابی.
  3. علت ریشه‌ای و عوامل مشارکت‌کننده (5 Whys).
  4. نحوه‌ی تشخیص و اینکه آیا می‌توانست زودتر باشد.
  5. آنچه خوب و آنچه بد پیش رفت؛ کجا شانس آوردیم.
  6. Action itemها با مالک و مهلت، و پیگیری.

MTTD (Mean Time To Detect): میانگین زمان از شروع مشکل تا تشخیص آن. کاهش با: alertهای symptom-based و burn-rate، uptime/synthetic check، error tracking با alert روی خطای جدید، annotation deploy.

MTTR (Mean Time To Recover/Restore): میانگین زمان تا بازگشت سرویس. کاهش با: rollback سریع و خودکار، feature flag (kill switch)، runbook، داشبوردها و traceهای آماده، تمرین incident (game day)، نقش‌های مشخص (Incident Commander) و deployهای کوچک که علت را واضح می‌کنند.

در سیستم‌های پیچیده جلوگیری از همه‌ی خرابی‌ها ممکن نیست؛ کاهش MTTD و MTTR اغلب بازده بیشتری دارد و MTTR یکی از متریک‌های DORA است.

یک سناریو: CPU سرور MySQL به‌طور مداوم بالای ۹۰٪ است و پاسخ‌دهی برنامه کند شده. چه ابزارها و مراحلی برای یافتن کوئری‌های مشکل‌دار به‌کار می‌برید؟

۱. تصویر لحظه‌ای: SHOW FULL PROCESSLIST برای کوئری‌های در حال اجرا، مدت و وضعیت (Sending data، Locked)؛ آیا کوئری خاصی بارها تکرار شده؟

۲. Slow query log: فعال کردن (در صورت نبود) با slow_query_log=1 و long_query_time مناسب (مثلاً ۰٫۵ ثانیه، یا موقتاً کمتر)، سپس تحلیل با pt-query-digest یا mysqldumpslow برای رتبه‌بندی بر اساس مجموع زمان (نه فقط کندترین تک‌کوئری).

۳. Performance Schema / sys schema: آمار تجمیعی digest کوئری‌ها، کوئری‌هایی با full table scan، تعداد ردیف‌های بررسی‌شده در برابر برگشتی.

۴. تحلیل کوئری: EXPLAIN / EXPLAIN ANALYZE: نوع دسترسی (ALL = full scan)، index استفاده‌شده، rows، Using filesort/Using temporary.

۵. ردیابی تا کد Laravel: Pulse (slow queries با محل فراخوانی)، APM/tracing، DB::listen برای لاگ کوئری‌های کند با request_id، و در dev Model::preventLazyLoading() برای کشف N+1.

۶. متریک‌های همبسته: QPS (آیا ترافیک بالا رفته یا کوئری‌ها گران‌تر شده‌اند؟)، annotation deploy، اتصالات فعال، hit ratio بافر InnoDB، lock waits.

۷. اصلاح: index مناسب (ترکیبی با ترتیب درست)، eager loading، انتخاب ستون‌های لازم، صفحه‌بندی cursor به‌جای OFFSET بزرگ، cache نتایج پرتکرار، انتقال گزارش‌های سنگین به replica خواندنی. سپس alert روی متریک‌های دیتابیس و بررسی منظم slow log.

ELK و Loki را برای تجمیع لاگ مقایسه کنید. مفهوم cardinality چیست و چرا در Prometheus و Loki اهمیت دارد؟

ELK/EFK: Elasticsearch (ذخیره و full-text index)، Logstash یا Fluentd/Fluent Bit (جمع‌آوری و پردازش)، Kibana (UI). جست‌وجوی آزاد و سریع روی هر فیلد، تحلیل پیچیده و کاربرد امنیتی (SIEM)؛ اما پرمصرف از نظر RAM و دیسک و نگهداری سنگین‌تر.

Loki: فقط labelها (مثل app، env، level) را index می‌کند و محتوای لاگ را فشرده در chunkها (اغلب روی object storage) نگه می‌دارد؛ کوئری با LogQL ابتدا streamها را با label انتخاب و سپس محتوا را فیلتر/parse می‌کند. بسیار ارزان‌تر و سبک‌تر، با یکپارچگی طبیعی با Grafana و Prometheus؛ اما جست‌وجوی آزاد روی حجم بزرگ کندتر است.

Cardinality: تعداد ترکیب‌های یکتای مقادیر labelها. در Prometheus هر ترکیب یکتا یک time series جداگانه و در Loki یک stream جداگانه است. مثال: label status با ۱۰ مقدار × route با ۵۰ مقدار × ۲۰ instance = ۱۰٬۰۰۰ series؛ قابل مدیریت. اما افزودن user_id با یک میلیون مقدار ⇒ میلیاردها series.

پیامد cardinality بالا: مصرف شدید حافظه، کندی کوئری‌ها، هزینه‌ی بالا و حتی از کار افتادن Prometheus/Loki.

قاعده: label فقط برای ابعاد با مقادیر محدود و معنادار برای تجمیع (service، env، route نرمال‌شده مثل /orders/{id} نه URL خام، status class). شناسه‌های یکتا (user_id، order_id، request_id) در محتوای لاگ یا attributeهای trace قرار گیرند، نه label متریک.

خلاصه برای مرور سریع

مفاهیم پایه

  • Monitoring = «چه چیزی» خراب است (known unknowns).
  • Observability = «چرا» (unknown unknowns)؛ ویژگی سیستم.
  • Logs (جزئیات رویداد)، Metrics (عدد تجمیعی، روند، alert)، Traces (مسیر درخواست)، Events (deploy/config).
  • همبستگی با trace_id / request_id.

Logging

  • JSON، پیام ثابت + context، timestamp ISO، service/env/version.
  • سطوح: emergency، alert، critical، error، warning، notice، info، debug.
  • نه: رمز، توکن، Authorization، کارت/CVV، PII اضافی.
  • Laravel: channels (single، daily، stack، stderr، slack)، level = حداقل.
  • Log::withContext / shareContext / Context::add (→ jobها).
  • container ⇒ LOG_CHANNEL=stderr.
  • ELK = full-text index، سنگین؛ Loki = فقط label، ارزان.

Metrics

  • Counter (فقط بالا، با rate)، Gauge (بالا/پایین)، Histogram (bucket، قابل تجمیع)، Summary (quantile سمت کلاینت، غیرقابل تجمیع).
  • Cardinality: label با مقادیر محدود؛ user_id label نیست.
  • Percentile > میانگین؛ percentileها را میانگین نگیرید.
  • ۹۵×۵۰ + ۵×۳۰۰۰ ⇒ avg ۱۹۷٫۵، p99 ۳۰۰۰.

Prometheus

  • Pull از /metrics؛ up؛ Pushgateway برای batch.
  • rate(x_total[5m])، sum by (route)، histogram_quantile(0.95, sum by (le) (rate(..._bucket[5m]))).
  • Alertmanager: group، inhibit، silence، route.
  • PHP-FPM share-nothing ⇒ Redis/APCu storage یا exporter.
  • node_exporter، mysqld_exporter، php-fpm_exporter.

چارچوب‌ها

  • Golden: Latency، Traffic، Errors، Saturation.
  • RED (سرویس): Rate، Errors، Duration.
  • USE (منبع): Utilization، Saturation، Errors.

SLO

  • SLI = اندازه‌گیری؛ SLO = هدف داخلی؛ SLA = قرارداد + جریمه.
  • Error budget = ۱ − SLO.
  • ۹۹٫۹٪ / ۳۰ روز = ۴۳٫۲ دقیقه؛ ۹۹٫۹۹٪ = ۴٫۳۲ دقیقه؛ ۹۹٪ = ۷٫۲ ساعت.
  • بودجه تمام ⇒ توقف feature، تمرکز بر پایداری.
  • Burn rate ۱۴٫۴ ⇒ ۲٪ بودجه در ۱ ساعت.

Alerting

  • Symptom-based، actionable، runbook، severity (page/ticket)، for:، grouping.
  • Alert fatigue ⇒ ممیزی و حذف.
  • Alert روی نبود داده (absent، up == 0).

Health

  • Laravel /up (withRouting(health:))، رویداد DiagnosingHealth.
  • Liveness سطحی ⇒ restart؛ Readiness ⇒ خروج از LB.
  • Uptime بیرونی، Synthetic (سناریو)، RUM، heartbeat برای cron (pingOnSuccess).

Tracing و خطا

  • Trace = درخت span؛ propagation با traceparent.
  • Sampling: head vs tail.
  • OpenTelemetry: SDK + OTLP + Collector؛ vendor-neutral.
  • Sentry: grouping، stack trace، breadcrumbs، release tracking.

ابزار Laravel

  • Telescope: دیباگ، تک‌رویداد، dev.
  • Pulse: prod، تجمیعی، slow queries/requests/jobs، pulse:check.
  • Horizon: صف Redis، wait time، failed jobs، horizon:snapshot.

زیرساخت و DB

  • CPU (iowait، steal، load)، Memory (MemAvailable، swap، OOM)، Disk (فضا، inode، I/O)، Network.
  • slow_query_log + long_query_time ⇒ pt-query-digest ⇒ EXPLAIN.
  • DB::listen، DB::whenQueryingForLongerThan، preventLazyLoading.

Incident

  • Detect ← Ack ← Triage ← Mitigate ← Resolve ← Postmortem.
  • Incident Commander؛ mitigation قبل از root cause.
  • Blameless: timeline، impact، root cause، action items با مالک.
  • MTTD، MTTA، MTTR، MTBF.
