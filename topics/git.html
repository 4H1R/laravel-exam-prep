Git

مدل داخلی Git (اشیا، index، HEAD و refها)، merge و rebase، بازنویسی و بازگردانی تاریخچه، کار با remote، tag و SemVer، workflowهای تیمی، Pull Request، Conventional Commits و ابزارهای بازیابی مثل reflog و bisect؛ با تمرکز بر اینکه هر دستور «دقیقاً چه چیزی را جابه‌جا می‌کند».

مدل داخلی Git

Git یک سیستم کنترل نسخه‌ی توزیع‌شده (Distributed VCS) است: هر clone یک کپی کامل از کل تاریخچه دارد و بیشتر عملیات (commit، log، diff، branch) کاملاً محلی و بدون شبکه انجام می‌شوند. برخلاف سیستم‌های متمرکز مثل SVN، سرور مرکزی (مثلاً GitHub یا GitLab) فقط یک «قرارداد تیمی» است، نه یک نیاز فنی.

Snapshot، نه diff

Git در هر commit یک snapshot از کل پروژه ذخیره می‌کند، نه فهرست تغییرات نسبت به نسخه‌ی قبل. فایل‌هایی که تغییر نکرده‌اند دوباره ذخیره نمی‌شوند؛ commit جدید فقط به همان شیء قبلی اشاره می‌کند. diffی که در git log -p می‌بینید در لحظه محاسبه می‌شود. (در packfileها برای فشرده‌سازی از delta استفاده می‌شود، اما این جزئیات ذخیره‌سازی است، نه مدل مفهومی.)

اشیای Git (Object Database)

پوشه‌ی .git/objects یک پایگاه داده‌ی content-addressable است: کلید هر شیء، hash محتوای آن است. اگر محتوا یک بیت تغییر کند، hash هم تغییر می‌کند؛ بنابراین تاریخچه عملاً تغییرناپذیر (immutable) است و «ویرایش» یک commit یعنی ساختن commit جدید با hash جدید.

blob
محتوای خام یک فایل (بدون نام و مجوز). دو فایل با محتوای یکسان فقط یک blob دارند.
tree
معادل یک پوشه: فهرستی از نام‌ها، modeها و اشاره‌گر به blobها و treeهای دیگر.
commit
اشاره به یک tree ریشه + اشاره به commit(های) والد + author، committer، تاریخ و پیام. commit معمولی یک والد، merge commit دو (یا بیشتر) والد و commit اول هیچ والدی ندارد.
tag (annotated)
شیئی که به یک commit اشاره می‌کند و نام، پیام، tagger و در صورت نیاز امضا دارد.
SHA
شناسه‌ی هر شیء؛ به‌طور پیش‌فرض SHA-1 با ۴۰ کاراکتر hex (Git از قالب SHA-256 هم به‌صورت اختیاری پشتیبانی می‌کند). معمولاً ۷ تا ۱۲ کاراکتر اول برای ارجاع کافی است.

   │                │     └── blob  User.php

Refها و HEAD

  • ref یک نام خوانا برای یک hash است. branchها در refs/heads/، remote-tracking branchها در refs/remotes/origin/ و tagها در refs/tags/ قرار دارند.
  • branch فقط یک اشاره‌گر متحرک به یک commit است (یک فایل کوچک حاوی یک hash). ساختن branch تقریباً هزینه‌ای ندارد؛ به همین دلیل branchهای کوتاه‌عمر در Git رایج‌اند.
  • HEAD اشاره‌گر به «جایی که الان هستید» است. معمولاً HEAD به یک branch اشاره می‌کند (ref: refs/heads/main) و با هر commit، همان branch جلو می‌رود.
  • Detached HEAD: وقتی HEAD مستقیماً به یک commit (نه یک branch) اشاره کند؛ مثلاً بعد از git switch --detach v1.2.0 یا git checkout <sha>. commitهایی که در این حالت می‌سازید به هیچ branchی وصل نیستند و اگر قبل از رفتن branch نسازید، فقط از طریق reflog قابل بازیابی‌اند.
git cat-file -t a1b2c3      # نوع شیء: commit
git cat-file -p a1b2c3      # محتوای commit: tree، parent، author، پیام
git rev-parse HEAD          # hash کامل commit فعلی
cat .git/HEAD               # ref: refs/heads/main
git log --oneline --graph --all --decorate

جمله‌ی کلیدی برای پاسخ تشریحی: «در Git هر commit یک snapshot تغییرناپذیر است که با hash محتوایش شناخته می‌شود؛ branch و tag فقط اشاره‌گر به commitها هستند و HEAD نشان می‌دهد الان روی کدام اشاره‌گر هستیم.» تقریباً همه‌ی دستورات Git (reset، rebase، merge، checkout) را می‌شود با این جمله توضیح داد: یا commit جدید می‌سازند، یا اشاره‌گرها را جابه‌جا می‌کنند، یا index و working tree را با یک commit هماهنگ می‌کنند.

فایل‌هایی که روی دیسک می‌بینید و ویرایش می‌کنید.
Index (Staging Area)
«پیش‌نویس commit بعدی». در واقع یک فایل باینری (.git/index) است که snapshot مورد نظر برای commit بعدی را نگه می‌دارد.
Repository
پایگاه داده‌ی اشیا و refها؛ commitها اینجا دائمی می‌شوند.

چرا staging area وجود دارد؟

staging به شما اجازه می‌دهد از میان تغییرات working tree فقط بخشی را انتخاب کنید و commitهای اتمیک بسازید؛ مثلاً رفع یک باگ و یک refactor را که هم‌زمان انجام داده‌اید، در دو commit جدا ثبت کنید. با git add -p حتی می‌شود بخش‌هایی (hunk) از یک فایل را stage کرد.

git status -sb                 # وضعیت کوتاه + branch
git add -p app/Services/OrderService.php   # stage انتخابی hunkها
git diff                       # working tree در برابر index (تغییرات unstaged)
git diff --staged              # index در برابر HEAD (آنچه commit می‌شود)
git commit -m "fix(order): prevent double charge on retry"
git commit --amend --no-edit   # افزودن تغییرات stage‌شده به آخرین commit (hash عوض می‌شود)
git log --oneline -n 10
git show HEAD --stat

git diff بدون آرگومان تغییرات stage‌شده را نشان نمی‌دهد. اگر فایلی را add کرده‌اید و diff خالی است، از git diff --staged (معادل --cached) استفاده کنید.

.gitignore

فایل .gitignore به Git می‌گوید فایل‌های untracked را نادیده بگیرد. نکات مهم:

  • .gitignore روی فایل‌هایی که از قبل track شده‌اند اثری ندارد. برای خارج کردن آن‌ها: git rm --cached .env و سپس commit (فایل روی دیسک می‌ماند).
  • الگوها: /vendor فقط در ریشه، logs/ فقط پوشه، *.log همه‌جا، **/cache در هر عمق، و ! برای استثنا (مثلاً !.gitkeep). اگر پوشه‌ی والد ignore شده باشد، با ! نمی‌توان فایلی درون آن را برگرداند.
  • سه سطح: .gitignore در repo (مشترک تیم)، .git/info/exclude (فقط همین clone) و فایل global با core.excludesFile (برای فایل‌های IDE و سیستم‌عامل مثل .idea/ و .DS_Store).
  • برای فهمیدن اینکه چرا یک فایل ignore شده: git check-ignore -v path/to/file.

Branch و Merge

از Git 2.23 دستور git switch برای تعویض branch و git restore برای بازگرداندن فایل‌ها معرفی شدند تا وظایف چندگانه‌ی checkout تفکیک شود. checkout هنوز کار می‌کند.

git switch -c feature/invoice-pdf      # ساخت و رفتن به branch جدید
git switch main
git branch -vv                          # branchها + upstream + ahead/behind
git branch -d feature/invoice-pdf       # حذف امن (فقط اگر merge شده باشد)
git branch -D experiment                # حذف اجباری

Fast-forward merge

اگر branch مقصد (مثلاً main) از زمان جدا شدن feature هیچ commit جدیدی نگرفته باشد، Git فقط اشاره‌گر main را جلو می‌برد؛ هیچ commit جدیدی ساخته نمی‌شود و تاریخچه خطی می‌ماند.

قبل:    A ── B ── C   (main)
                   └── D ── E   (feature)

بعد از git merge feature  (fast-forward):
        A ── B ── C ── D ── E   (main, feature)

Three-way merge

اگر هر دو branch commit جدید داشته باشند، Git سه snapshot را مقایسه می‌کند: merge base (نزدیک‌ترین جد مشترک)، نوک branch فعلی و نوک branch دیگر. نتیجه یک merge commit با دو والد است.

        A ── B ── C ── F ────── M   (main)
                   \           /
                    D ── E ───┘     (feature)

merge base = C ؛ M دو والد دارد: F (والد اول) و E (والد دوم)

منطق three-way برای هر بخش از فایل: اگر فقط یک طرف نسبت به base تغییر داده باشد، تغییر همان طرف برداشته می‌شود؛ اگر هر دو طرف یک ناحیه را به شکل متفاوت تغییر داده باشند، conflict رخ می‌دهد. استراتژی پیش‌فرض merge در نسخه‌های جدید Git، ort است.

گزینه‌های مهم merge

دستورنتیجهکاربرد
git merge featureاگر ممکن باشد fast-forward، وگرنه merge commitپیش‌فرض
git merge --no-ff featureهمیشه merge commit، حتی اگر ff ممکن باشدحفظ مرز feature در تاریخچه (رایج در Git Flow)
git merge --ff-only featureفقط ff؛ در غیر این صورت خطااطمینان از تاریخچه‌ی خطی
git merge --squash featureهمه‌ی تغییرات در index قرار می‌گیرند؛ باید خودتان commit کنید و هیچ ارتباط والدی با feature ثبت نمی‌شودیک commit تمیز به ازای هر feature

بعد از --squash، Git نمی‌داند که feature «merge شده است». بنابراین git branch -d feature خطا می‌دهد و اگر روی همان branch ادامه دهید و دوباره merge کنید، ممکن است conflictهای تکراری ببینید. بعد از squash-merge، branch را حذف کنید و برای کار بعدی branch تازه بسازید.

تفاوت ff و three-way را همیشه با «آیا commit جدید ساخته می‌شود؟» و «تعداد والدها» توضیح دهید: ff فقط اشاره‌گر را جابه‌جا می‌کند؛ three-way یک commit با دو والد می‌سازد که بر پایه‌ی merge base محاسبه شده است.

Conflict و حل آن

Conflict زمانی رخ می‌دهد که Git نتواند به‌صورت خودکار تصمیم بگیرد؛ معمولاً وقتی دو طرف خطوط یکسانی را نسبت به merge base به شکل متفاوت تغییر داده‌اند، یا یک طرف فایلی را حذف و طرف دیگر آن را ویرایش کرده است. conflict یک خطا نیست؛ Git از شما تصمیم‌گیری انسانی می‌خواهد.

<?php
class PriceCalculator
{
    public function total(Order $order): int
    {
<<<<<<< HEAD
        return $order->subtotal() + $this->tax($order);
||||||| base
        return $order->subtotal();
=======
        return $order->subtotal() - $order->discount();
>>>>>>> feature/discount
    }
}

بخش میانی (|||||||) فقط وقتی نمایش داده می‌شود که merge.conflictStyle روی diff3 یا zdiff3 تنظیم شده باشد و بسیار مفید است، چون نشان می‌دهد هر طرف چه چیزی را عوض کرده است. پاسخ درست در این مثال احتمالاً ترکیب هر دو است: subtotal() - discount() + tax()؛ یعنی حل conflict نیازمند فهم منطق کسب‌وکار است، نه انتخاب مکانیکی یک طرف.

مراحل حل conflict

  1. git status را ببینید تا فایل‌های unmerged را بشناسید.
  2. هر فایل را باز کنید، منطق هر دو طرف را بفهمید و نسخه‌ی نهایی را بنویسید (markerها را حذف کنید).
  3. تست‌ها و lint را اجرا کنید؛ کدی که کامپایل یا اجرا نشود ممکن است از نظر Git «حل‌شده» باشد.
  4. git add <file> برای علامت‌گذاری به‌عنوان resolved.
  5. در merge: git commit؛ در rebase: git rebase --continue؛ در cherry-pick: git cherry-pick --continue.
  6. در صورت سردرگمی: git merge --abort یا git rebase --abort.
git config --global merge.conflictStyle zdiff3
git checkout --ours   composer.lock    # نسخه‌ی branch فعلی
git checkout --theirs composer.lock    # نسخه‌ی branch دیگر
git mergetool                           # ابزار گرافیکی
git config --global rerere.enabled true # به خاطر سپردن حل conflictهای تکراری

در rebase معنای ours/theirs برعکس به نظر می‌رسد: چون rebase commitهای شما را روی branch مقصد replay می‌کند، --ours یعنی branch پایه (مثلاً main) و --theirs یعنی commit شما که در حال اعمال است.

برای composer.lock یا package-lock.json، به‌جای ویرایش دستی، یکی از دو نسخه را بردارید و دوباره composer update <package> (یا composer install) اجرا کنید تا lock file سازگار تولید شود. ویرایش دستی hash محتوا (content-hash) را خراب می‌کند.

پیشگیری از conflict

  • branchهای کوتاه‌عمر و PRهای کوچک؛ هرچه branch بیشتر عمر کند، فاصله و احتمال conflict بیشتر است.
  • به‌روز کردن مرتب branch با main (rebase یا merge).
  • formatter مشترک (مثلاً Laravel Pint) تا تغییرات سلیقه‌ای فاصله‌گذاری conflict نسازند.
  • تقسیم فایل‌های بزرگ و پرتغییر (God class، فایل route عظیم).
  • هماهنگی تیمی برای تغییرات گسترده (rename سراسری، جابه‌جایی پوشه‌ها).

Rebase در برابر Merge

Rebase یعنی «commitهای branch من را بردار و یکی‌یکی روی یک پایه‌ی جدید دوباره اعمال کن». چون والد هر commit عوض می‌شود، commitهای جدید با hash جدید ساخته می‌شوند؛ یعنی rebase تاریخچه را بازنویسی می‌کند. commitهای قدیمی حذف نمی‌شوند؛ فقط دیگر branchی به آن‌ها اشاره نمی‌کند (و تا مدتی در reflog باقی می‌مانند).

قبل:     A ── B ── C ── F        (main)
                    └── D ── E    (feature)

git switch feature && git rebase main

بعد:     A ── B ── C ── F                (main)
                         └── D' ── E'    (feature)   ← D' و E' hash جدید دارند

Merge

  • تاریخچه‌ی واقعی را حفظ می‌کند (چه کسی، چه زمانی، از کجا).
  • غیرمخرب است؛ هیچ commit موجودی تغییر نمی‌کند.
  • برای branchهای مشترک امن است.
  • تاریخچه ممکن است با merge commitهای زیاد شلوغ و غیرخطی شود.
  • conflictها یک‌جا و یک‌بار حل می‌شوند.

Rebase

  • تاریخچه‌ی خطی و خوانا؛ git log و git bisect ساده‌تر.
  • تاریخچه بازنویسی می‌شود (hash جدید).
  • روی branch مشترک خطرناک است.
  • ممکن است مجبور شوید یک conflict را برای چند commit پشت سر هم حل کنید.
  • اطلاعات «این کار موازی انجام شده بود» از بین می‌رود.

قانون طلایی rebase

هرگز commitهایی را که push شده‌اند و دیگران ممکن است روی آن‌ها کار کرده باشند rebase نکنید. اگر main یا یک branch مشترک را rebase کنید، همکاران شما commitهای قدیمی (با hash قدیمی) را دارند و commitهای شما با hash جدید آمده‌اند؛ Git این‌ها را commitهای متفاوتی می‌بیند، در pull بعدی تاریخچه دوبرابر می‌شود و conflictهای گیج‌کننده رخ می‌دهد. rebase برای تمیز کردن کار محلی/شخصی قبل از اشتراک‌گذاری است.

الگوهای رایج

# به‌روز کردن branch شخصی با آخرین main
git fetch origin
git rebase origin/main
# بعد از rebase یک branch که قبلاً push شده (فقط branch شخصی!):
git push --force-with-lease

# pull بدون ساختن merge commitهای بی‌معنی
git pull --rebase
git config --global pull.rebase true

# جابه‌جایی پایه‌ی یک branch: commitهای feature که روی old-base بودند را روی main بگذار
git rebase --onto main old-base feature

کدام را انتخاب کنیم؟

  • Rebase برای همگام‌سازی branch شخصی با main و تمیز کردن commitها قبل از PR.
  • Merge برای وارد کردن یک feature تمام‌شده به main (یا squash-merge در PR)، و هر جا که branch مشترک است.
  • بسیاری از تیم‌ها ترکیبی کار می‌کنند: «rebase محلی، merge در PR».

git pull به‌صورت پیش‌فرض fetch + merge است. اگر شما و همکارتان هم‌زمان روی یک branch commit کنید، pull معمولی یک merge commit بی‌معنی مثل «Merge branch 'main' of origin» می‌سازد. pull --rebase commitهای محلی شما را روی آخرین نسخه‌ی remote قرار می‌دهد. این مورد قانون طلایی را نقض نمی‌کند، چون فقط commitهای push‌نشده‌ی خودتان بازنویسی می‌شوند.

Interactive Rebase و Cherry-pick

git rebase -i ابزار اصلی «ویرایش تاریخچه‌ی محلی» است: تغییر ترتیب commitها، ادغام (squash)، ویرایش پیام، تقسیم یا حذف commit. هدف این است که قبل از PR، تاریخچه یک داستان منطقی و قابل review بگوید، نه سابقه‌ی آزمون و خطای شما.

git rebase -i HEAD~4
# یا: همه‌ی commitهای branch نسبت به main
git rebase -i origin/main
pick   3f1a2b1 feat(invoice): add PDF generation service
fixup  8c9d0e2 fix typo
squash 1a2b3c4 feat(invoice): add download endpoint
reword 7e6f5d4 wip
drop   4d5e6f7 debug dump
# p, pick   = commit را نگه دار
# r, reword = نگه دار ولی پیام را ویرایش کن
# e, edit   = توقف برای ویرایش (مثلاً تقسیم commit)
# s, squash = با commit قبلی ادغام کن و پیام‌ها را ترکیب کن
# f, fixup  = مثل squash ولی پیام این commit دور ریخته می‌شود
# d, drop   = حذف commit

fixup و autosquash

اگر در review مشخص شد یک commit قبلی ایراد دارد، به‌جای commit «fix review comments» می‌توانید یک fixup commit هدفمند بسازید و Git خودش در rebase آن را سر جایش قرار دهد:

git commit --fixup=3f1a2b1
git rebase -i --autosquash origin/main

Squash: مزایا و معایب

  • مزیت: تاریخچه‌ی main تمیز، یک commit به ازای هر feature/PR، revert ساده‌ی کل feature.
  • عیب: جزئیات مفید از بین می‌رود؛ اگر یک PR بزرگ squash شود، git bisect فقط به یک commit بزرگ می‌رسد و نمی‌تواند دقیق‌تر شود.
  • قاعده‌ی خوب: commitهای «wip»، «fix typo» و «address review» را squash کنید، اما commitهای منطقی و مستقل (مثلاً «migration»، «refactor»، «feature») را جدا نگه دارید.

Cherry-pick

git cherry-pick <sha> تغییرات (diff) یک commit مشخص را روی branch فعلی اعمال می‌کند و یک commit جدید با hash جدید می‌سازد. کاربرد اصلی: بردن یک hotfix از main به یک release branch قدیمی (backport)، یا نجات یک commit از branchی که قرار نیست merge شود.

git switch release/2.4
git cherry-pick -x a1b2c3d     # -x: افزودن "(cherry picked from commit ...)" به پیام
git cherry-pick A^..C          # بازه‌ای از commitها (شامل A)
git cherry-pick --continue | --abort

cherry-pick زیاد نشانه‌ی بوی بد در workflow است: یک تغییر با دو hash متفاوت در دو branch وجود دارد و merge بعدی ممکن است conflict یا تغییر تکراری ایجاد کند. اگر یک commit به چند branch نیاز دارد، معمولاً بهتر است آن را روی پایه‌ی مشترک بسازید و merge کنید.

reset، revert، restore و stash

کلید فهم این دستورات این است که هر کدام روی کدام ناحیه اثر می‌گذارد: اشاره‌گر branch/HEAD، index یا working tree.

git reset: جابه‌جا کردن branch

git reset <commit> branch فعلی (و HEAD) را به commit دیگری منتقل می‌کند. سه حالت آن فقط در این تفاوت دارند که index و working tree را هم به‌روز می‌کنند یا نه:

حالتBranch/HEADIndexWorking Treeکاربرد نمونه
--softجابه‌جادست‌نخوردهدست‌نخوردهادغام چند commit آخر در یک commit: تغییرات stage‌شده می‌مانند
--mixed (پیش‌فرض)جابه‌جاreset می‌شوددست‌نخوردهبرگرداندن commit و unstage کردن تغییرات برای commit مجدد

git reset --soft HEAD~3      # سه commit آخر را "باز کن"، همه stage‌شده بمانند
git commit -m "feat(cart): add coupon support"
git reset HEAD~1             # آخرین commit را بردار، تغییرات در working tree بمانند
git reset --hard origin/main # branch محلی را دقیقاً مثل remote کن (تغییرات محلی از بین می‌رود)

git reset --hard تغییرات commit‌نشده را برای همیشه حذف می‌کند (reflog فقط commitها را نگه می‌دارد، نه تغییرات working tree). commitهایی که با reset «گم» شده‌اند از طریق git reflog قابل بازیابی‌اند.

git revert: خنثی‌سازی امن

git revert <sha> یک commit جدید می‌سازد که دقیقاً عکس تغییرات commit هدف است. تاریخچه بازنویسی نمی‌شود، بنابراین روی branchهای مشترک و push‌شده (مثل main) روش صحیح است.

git revert a1b2c3d
git revert --no-commit A..C && git commit -m "revert: roll back coupon feature"
git revert -m 1 <merge-sha>   # revert یک merge commit: والد اول به‌عنوان mainline

نکته‌ی ظریف: اگر یک merge را revert کنید و بعداً بخواهید همان branch (پس از اصلاح) را دوباره merge کنید، Git فکر می‌کند آن commitها قبلاً merge شده‌اند و تغییرات قبلی را نمی‌آورد. راه‌حل معمول «revert کردن آن revert» قبل از merge مجدد است.

git restore --source=HEAD~2 config/app.php # آوردن نسخه‌ی فایل از یک commit دیگر

git stash

stash تغییرات commit‌نشده (working tree و index) را در یک پشته ذخیره و working tree را تمیز می‌کند؛ مثلاً وقتی وسط کار هستید و باید فوراً روی hotfix کار کنید.

git stash push -m "wip: coupon validation"   # ذخیره (فایل‌های untracked شامل نمی‌شوند)
git stash -u                                   # شامل فایل‌های untracked
git stash list                                 # stash@{0}, stash@{1}, ...
git stash show -p stash@{1}
git stash pop                                  # اعمال و حذف از پشته (اگر conflict نشود)
git stash apply stash@{1}                      # اعمال بدون حذف
git stash drop stash@{1}
git stash branch feature/coupon stash@{0}      # ساخت branch از روی stash

stash برای ذخیره‌ی طولانی‌مدت مناسب نیست؛ stashها نام branch ندارند، فراموش می‌شوند و push نمی‌شوند. برای کار نیمه‌تمام طولانی، یک commit «wip» روی branch خودتان بسازید و بعداً با reset --soft یا interactive rebase تمیزش کنید. جایگزین دیگر git worktree add ../hotfix main است که یک working tree دوم در کنار اولی می‌سازد.

Remote: fetch، pull، push

remote یک نام مستعار برای URL یک repository دیگر است (معمولاً origin). Git برای هر branch راه دور یک remote-tracking branch مثل origin/main نگه می‌دارد که «آخرین چیزی است که از remote دیده‌ایم» و فقط با fetch به‌روز می‌شود.

  Remote (GitHub)                    Local

  │ main ── F    │ ─────────────► │ origin/main ── F   │
  └──────────────┘                │ main        ── C   │ ← هنوز عقب است

دستورچه کاری می‌کند
git fetchcommitها و refهای جدید را دانلود و origin/* را به‌روز می‌کند. هیچ تغییری در branchهای محلی یا working tree نمی‌دهد؛ همیشه امن است.
git pullfetch + ادغام upstream در branch فعلی (merge به‌صورت پیش‌فرض، یا rebase با --rebase/pull.rebase).
git pushcommitهای محلی را به remote می‌فرستد. فقط اگر fast-forward باشد پذیرفته می‌شود؛ وگرنه rejected (non-fast-forward).
git push -u origin feature/xpush و تنظیم upstream تا بعداً git push/git pull بدون آرگومان کار کند.

force push و force-with-lease

بعد از rebase یا amend، تاریخچه‌ی محلی با remote واگرا شده و push معمولی رد می‌شود. git push --force بی‌قیدوشرط تاریخچه‌ی remote را بازنویسی می‌کند و اگر همکار شما در این فاصله commitی push کرده باشد، کار او پاک می‌شود.

--force-with-lease فقط زمانی بازنویسی می‌کند که branch روی remote هنوز همان جایی باشد که origin/feature محلی شما نشان می‌دهد؛ یعنی «فقط اگر از آخرین fetch من کسی چیزی push نکرده باشد». اگر کسی push کرده باشد، push رد می‌شود.

git push --force-with-lease
git push --force-with-lease --force-if-includes   # محافظت بیشتر وقتی fetch خودکار پس‌زمینه دارید

محدودیت --force-with-lease: اگر بعد از push همکار، شما (یا IDE شما به‌صورت خودکار) git fetch کرده باشید، origin/feature به‌روز شده و lease پاس می‌شود؛ در حالی که commit او را هرگز در branch محلی خود نیاورده‌اید. گزینه‌ی --force-if-includes بررسی می‌کند که نوک remote واقعاً در تاریخچه‌ی محلی شما وجود داشته باشد.

در پاسخ به «fetch و pull چه تفاوتی دارند؟» حتماً بگویید: fetch فقط اطلاعات را می‌آورد و remote-tracking branchها را به‌روز می‌کند (امن، قابل بررسی با git log main..origin/main)؛ pull علاوه بر آن، تغییرات را در branch فعلی ادغام می‌کند و ممکن است merge commit یا conflict ایجاد کند. روی main و branchهای محافظت‌شده، force push باید در تنظیمات سرور (branch protection) ممنوع باشد.

Tag و SemVer

tag یک اشاره‌گر ثابت به یک commit است (برخلاف branch جلو نمی‌رود) و معمولاً برای علامت‌گذاری releaseها استفاده می‌شود.

Lightweight tag

  • فقط یک ref به commit، بدون شیء جداگانه.
  • git tag v1.4.0-tmp
  • مناسب علامت‌گذاری شخصی و موقت.

Annotated tag

  • شیء کامل: نام tagger، تاریخ، پیام، امکان امضای GPG/SSH.
  • git tag -a v1.4.0 -m "Release 1.4.0"
  • روش توصیه‌شده برای releaseها؛ git describe به‌طور پیش‌فرض فقط این نوع را در نظر می‌گیرد.
git tag -a v2.3.0 -m "Release 2.3.0"
git tag -s v2.3.0 -m "Signed release"     # امضا‌شده
git push origin v2.3.0                     # tagها با push معمولی ارسال نمی‌شوند
git push --follow-tags                     # ارسال annotated tagهای مرتبط با commitهای push‌شده
git tag -l "v2.*"
git describe --tags                        # مثلاً v2.3.0-5-g1a2b3c4 (۵ commit بعد از tag)
git push origin --delete v2.3.0-rc1

tag منتشرشده را جابه‌جا نکنید. Composer و سایر package managerها نسخه را از tag می‌خوانند و کسی که v2.3.0 را قبلاً نصب کرده، کد متفاوتی از کسی دارد که بعداً نصب می‌کند. اگر release اشتباه بود، نسخه‌ی patch جدید (v2.3.1) منتشر کنید.

Semantic Versioning

در SemVer، نسخه به شکل MAJOR.MINOR.PATCH است و معنای هر جزء یک قرارداد با مصرف‌کننده‌ی API عمومی است:

جزءکِی افزایش می‌یابدمثال
MAJORتغییر ناسازگار با نسخه‌ی قبل (breaking change)حذف یک متد public، تغییر signature، تغییر قالب پاسخ API
MINORقابلیت جدید سازگار با قبلافزودن endpoint یا پارامتر اختیاری
PATCHرفع باگ سازگار با قبلاصلاح محاسبه‌ی اشتباه
  • با افزایش MINOR، PATCH صفر می‌شود؛ با افزایش MAJOR هر دو صفر می‌شوند: 1.9.4 → 2.0.0.
  • Pre-release: 2.0.0-alpha.1، 2.0.0-rc.2؛ اولویت آن‌ها از نسخه‌ی نهایی 2.0.0 کمتر است.
  • Build metadata بعد از + (مثل 1.0.0+20261106) در مقایسه‌ی اولویت نادیده گرفته می‌شود.
  • نسخه‌های 0.y.z برای توسعه‌ی اولیه‌اند و API پایدار تلقی نمی‌شود.

ارتباط با Composer

قیدمعادل

SemVer فقط وقتی معنا دارد که «API عمومی» را تعریف کرده باشید (برای یک library: کلاس‌ها و متدهای public؛ برای یک REST API: قرارداد endpointها). اپلیکیشن‌های نهایی که مصرف‌کننده‌ی بیرونی ندارند گاهی از CalVer (مثل 2026.11.0) یا شماره‌ی build استفاده می‌کنند.

Workflowهای تیمی

Branching strategy قراردادی است که تیم برای ساخت branch، ادغام و release دنبال می‌کند. انتخاب آن به فرکانس deploy، تعداد نسخه‌های هم‌زمانی که پشتیبانی می‌کنید، بلوغ CI/تست و اندازه‌ی تیم بستگی دارد.

Git Flow

            \              / \         /

              \          /

                \  /     \
develop  ────●───●───●────●───●──────────────────
              \     /

  • دو branch دائمی: main (کد production) و develop (ادغام featureها).
  • branchهای کمکی: feature/*، release/*، hotfix/*.
  • مناسب: نرم‌افزار با releaseهای زمان‌بندی‌شده و نسخه‌دار (اپ موبایل، محصول on-premise، library) یا پشتیبانی هم‌زمان از چند نسخه.
  • معایب: پیچیدگی، branchهای طولانی‌مدت، merge hell، فاصله‌ی زیاد بین نوشتن کد و رسیدن به production؛ برای deploy پیوسته سنگین است.

GitHub Flow

  • یک branch اصلی (main) که همیشه قابل deploy است.
  • برای هر تغییر: branch کوتاه‌عمر ← commit ← Pull Request ← review و CI ← merge ← deploy.
  • مناسب: وب‌اپلیکیشن و SaaS با deploy مداوم و یک نسخه در production.
  • معایب: بدون CI و تست خودکار قوی خطرناک است؛ مدیریت چند نسخه‌ی هم‌زمان را پوشش نمی‌دهد.

Trunk-based Development

  • همه مستقیماً روی trunk (main) یا با branchهایی بسیار کوتاه‌عمر (حداکثر یکی دو روز) کار می‌کنند و چند بار در روز ادغام می‌کنند.
  • کار ناتمام پشت feature flag پنهان می‌شود؛ یعنی deploy از release جدا می‌شود.
  • نیازمند: CI سریع و قابل اعتماد، پوشش تست خوب، فرهنگ تغییرات کوچک، و گاهی release branch برای نسخه‌ها.
  • مزایا: کمترین conflict، بازخورد سریع، پایه‌ی Continuous Integration واقعی.
  • معایب: مدیریت feature flagها (بدهی فنی flagهای قدیمی) و نیاز به نظم و بلوغ تیمی.

GitLab Flow گونه‌ای میانه است: GitHub Flow به‌علاوه‌ی branchهای محیطی (مثل staging و production) یا release branchها، که تغییرات از بالادست به پایین‌دست ادغام می‌شوند.

Pull Request و Code Review

Pull Request (در GitLab: Merge Request) درخواست ادغام یک branch در branch دیگر است که بستری برای review، بحث، اجرای CI و ثبت تصمیم‌ها فراهم می‌کند. PR بخشی از Git نیست؛ قابلیت پلتفرم‌هایی مثل GitHub و GitLab است.

یک PR خوب

  • کوچک و متمرکز: یک هدف. PRهای چندصد خطی به‌خوبی review نمی‌شوند (reviewer خسته فقط approve می‌کند).
  • توضیح کامل: چه چیزی، چرا، چگونه تست شده، لینک issue، اسکرین‌شات برای UI، نکات deploy (migration، متغیر env جدید، queue).
  • self-review قبل از درخواست review: خواندن diff خود، حذف dump و کد مرده.
  • CI سبز: تست، static analysis (PHPStan/Larastan)، style (Pint) قبل از درگیر کردن انسان.
  • Draft PR برای گرفتن بازخورد زودهنگام روی رویکرد.

  1. درستی: آیا نیازمندی را برآورده می‌کند؟ edge caseها، null، خطا و همزمانی (race condition).
  2. طراحی: مسئولیت‌ها در جای درست هستند؟ coupling، تکرار، abstraction بی‌مورد.
  3. امنیت: authorization، validation، SQL injection، mass assignment، نشت اطلاعات در log.
  4. کارایی: N+1 query، index دیتابیس، کارهای سنگین در request به‌جای queue.
  5. تست: تست‌ها رفتار را می‌سنجند یا فقط coverage را بالا می‌برند؟
  6. خوانایی و نگهداری: نام‌گذاری، پیچیدگی، مستندات لازم.

فرهنگ review

  • نقد کد، نه شخص؛ سؤال بپرسید («اینجا اگر سفارش null باشد چه می‌شود؟») به‌جای حکم.
  • شدت کامنت را مشخص کنید: nit: برای سلیقه‌ای، «blocking» برای مشکلات جدی.
  • چیزهایی که ابزار می‌تواند بگیرد (style، فرمت) را به ابزار بسپارید.
  • review سریع (مثلاً ظرف یک روز کاری)؛ PR معطل‌مانده باعث context switch و conflict می‌شود.
  • تعریف و تحسین کد خوب هم بخشی از review است.

محافظت از branch و روش‌های merge

  • Branch protection: منع push مستقیم و force push به main، الزام CI سبز، حداقل یک approve، به‌روز بودن branch، و CODEOWNERS برای الزام review از مالکان یک بخش.
  • گزینه‌های merge در GitHub: Merge commit (حفظ همه‌ی commitها + merge commit)، Squash and merge (یک commit)، Rebase and merge (commitها خطی، بدون merge commit).

اهداف code review فقط «پیدا کردن باگ» نیست: انتقال دانش (کاهش bus factor)، یکپارچگی سبک و معماری، آموزش اعضای جدید و ثبت تصمیم‌ها. در پاسخ تشریحی هر دو جنبه‌ی فنی و انسانی را بگویید.

Commit Message و Conventional Commits

پیام commit برای «خواننده‌ی آینده» نوشته می‌شود: کسی که شش ماه بعد با git blame به یک خط عجیب می‌رسد و می‌خواهد بداند چرا این‌طور نوشته شده. diff می‌گوید چه تغییر کرد؛ پیام باید بگوید چرا.

قواعد کلاسیک

  • خط اول (subject) کوتاه، حدود ۵۰ کاراکتر و حداکثر ۷۲؛ بدون نقطه در انتها.
  • وجه امری در انگلیسی: «Add»، «Fix»؛ نه «Added» یا «Fixes». (جمله باید با «If applied, this commit will …» جور باشد.)
  • یک خط خالی بین subject و body.
  • body با شکست خط حدود ۷۲ کاراکتر: انگیزه، رویکرد، پیامدها و گزینه‌های ردشده.
  • یک commit = یک تغییر منطقی (atomic). کد هر commit باید build و تست را پاس کند تا bisect قابل اعتماد باشد.

Conventional Commits

یک قرارداد ساخت‌یافته برای پیام commit که توسط ماشین قابل پردازش است:

<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
fix(payment): prevent double charge when gateway times out

The gateway may process a request even if it responds with a timeout.
We now send an idempotency key derived from the order id, so a retry
returns the original charge instead of creating a new one.

Closes #318
feat(api)!: return amounts as integer minor units

BREAKING CHANGE: `amount` in /api/v2/orders is now an integer in cents
instead of a decimal string. Clients must divide by 100.
typeمعنیاثر در SemVer
featقابلیت جدیدMINOR
fixرفع باگPATCH
! یا footer BREAKING CHANGE:تغییر ناسازگارMAJOR
docs، style، refactor، perf، test، build، ci، chore، revertانواع رایج دیگر (در spec اجباری نیستند؛ از قرارداد Angular آمده‌اند)به‌طور پیش‌فرض بدون release (به جز perf در برخی پیکربندی‌ها)

مزایا: تولید خودکار CHANGELOG، تعیین خودکار نسخه‌ی بعدی (ابزارهایی مثل semantic-release یا release-please)، فیلتر کردن تاریخچه (git log --grep "^feat") و قابل فهم‌تر شدن تاریخچه. اجرای قرارداد معمولاً با یک commit-msg hook (مثلاً commitlint) و بررسی در CI انجام می‌شود.

پیام‌هایی مثل «fix»، «update»، «changes» یا «wip» در تاریخچه‌ی نهایی main بی‌ارزش‌اند. اگر روی branch شخصی این‌ها را دارید، قبل از merge با interactive rebase یا squash آن‌ها را به پیام معنادار تبدیل کنید.

بازیابی: reflog و bisect

reflog: تاریخچه‌ی جابه‌جایی اشاره‌گرها

reflog یک log محلی است که هر بار HEAD یا یک branch جابه‌جا شود (commit، reset، rebase، checkout، merge، amend) یک ورودی ثبت می‌کند. چون commitها در Git واقعاً حذف نمی‌شوند (تا زمان garbage collection)، reflog «شبکه‌ی ایمنی» تقریباً هر اشتباهی است.

git reflog
# 4e5f6a7 HEAD@{0}: reset: moving to HEAD~3
# 9a8b7c6 HEAD@{1}: commit: feat(cart): add coupon support
# ...
git reset --hard HEAD@{1}             # برگشتن به قبل از reset اشتباه
git branch rescue 9a8b7c6             # یا ساختن branch روی commit گمشده
git reflog show feature/cart          # reflog یک branch خاص
git reset --hard ORIG_HEAD            # بعد از rebase/merge/reset: وضعیت قبلی
  • reflog محلی است؛ push نمی‌شود و در clone جدید وجود ندارد.
  • ورودی‌ها پس از مدتی منقضی می‌شوند (به‌طور پیش‌فرض ۹۰ روز برای ورودی‌های قابل دسترس و ۳۰ روز برای ورودی‌های unreachable)، سپس git gc می‌تواند commitهای بی‌مرجع را حذف کند.
  • تغییرات هرگز commit/stage‌نشده در reflog نیستند؛ reset --hard روی آن‌ها قابل بازگشت نیست.

قبل از عملیات پرریسک (rebase بزرگ، filter-repo) یک branch پشتیبان بسازید: git branch backup/before-rebase. ساده‌تر از جستجو در reflog است.

bisect: جستجوی دودویی باگ

git bisect با جستجوی دودویی روی تاریخچه، اولین commitی را پیدا می‌کند که باگ را وارد کرده است. اگر بین نسخه‌ی سالم و خراب ۱۰۰۰ commit فاصله باشد، حدود ۱۰ مرحله (log₂ 1000) کافی است.

git bisect start
git bisect bad                 # نسخه‌ی فعلی خراب است
git bisect good v2.2.0         # این نسخه سالم بود
# Git یک commit میانی را checkout می‌کند؛ تست کنید و اعلام کنید:
git bisect good    # یا: git bisect bad   یا: git bisect skip (اگر قابل تست نیست)
# ... تا اینکه: "a1b2c3d is the first bad commit"
git bisect reset               # برگشت به وضعیت اولیه

# خودکارسازی کامل: اسکریپتی که برای سالم exit 0 و برای خراب exit غیرصفر برمی‌گرداند
git bisect start HEAD v2.2.0
git bisect run php artisan test --filter=CouponDiscountTest

bisect وقتی بهترین کارایی را دارد که هر commit قابل build و تست باشد و commitها کوچک و اتمیک باشند. این یکی از دلایل فنی قوی برای commitهای تمیز و Conventional است. exit code ۱۲۵ در bisect run به معنی skip است.

ابزارهای کمکی دیگر

  • git blame -w -C file: چه کسی و در کدام commit هر خط را نوشته (با نادیده گرفتن whitespace و تشخیص جابه‌جایی کد). برای نادیده گرفتن commitهای format سراسری: blame.ignoreRevsFile با فایل .git-blame-ignore-revs.
  • git log -S "calculateTax" --oneline (pickaxe): commitهایی که تعداد رخداد یک رشته را تغییر داده‌اند.
  • git log -L :total:app/Services/PriceCalculator.php: تاریخچه‌ی یک تابع.
  • git fsck --lost-found: پیدا کردن اشیای dangling (مثلاً stash حذف‌شده).

Hookها، Monorepo و Submodule

Git Hooks

Hook اسکریپتی است که Git در نقاط مشخصی از چرخه اجرا می‌کند. اگر hookهای «pre-» با کد غیرصفر خارج شوند، عملیات متوقف می‌شود.

#!/bin/sh
# .githooks/pre-commit — فقط فایل‌های PHP stage‌شده را بررسی می‌کند
FILES=$(git diff --cached --name-only --diff-filter=ACM -- '*.php')
[ -z "$FILES" ] && exit 0

for f in $FILES; do
  php -l "$f" > /dev/null || exit 1
done

./vendor/bin/pint --test $FILES || {
  echo "Code style issues found. Run: ./vendor/bin/pint"
  exit 1
}
# hookهای داخل .git/hooks version control نمی‌شوند؛ برای اشتراک در تیم:
git config core.hooksPath .githooks
chmod +x .githooks/pre-commit
  • ابزارهای مدیریت hook: CaptainHook و GrumPHP در اکوسیستم PHP (نصب با Composer)، Husky و lint-staged در اکوسیستم JS، و pre-commit framework (پایتون).
  • hookها باید سریع باشند؛ pre-commit چنددقیقه‌ای باعث می‌شود توسعه‌دهندگان آن را دور بزنند.

hookهای سمت کلاینت با git commit --no-verify قابل دور زدن‌اند و اختیاری‌اند؛ پس جایگزین CI نیستند. hook بازخورد سریع محلی می‌دهد، CI و branch protection تضمین می‌کنند.

Monorepo در برابر Polyrepo

Monorepo (یک repo برای چند پروژه)

  • تغییرات اتمیک بین چند سرویس/پکیج در یک PR.
  • اشتراک کد و ابزار ساده‌تر، یک نسخه‌ی واحد از وابستگی‌ها.
  • نیاز به ابزار برای build و تست انتخابی (فقط بخش‌های تغییرکرده).
  • repo بزرگ: clone کند؛ راه‌حل‌ها: git sparse-checkout، partial clone (--filter=blob:none).
  • مجوزهای ریزدانه دشوارتر است.

Polyrepo (repo جدا برای هر سرویس)

  • مالکیت و مجوز روشن، CI مستقل و ساده.
  • نسخه‌دهی و release مستقل.
  • تغییرات بین‌سرویسی نیازمند چند PR هماهنگ.
  • خطر واگرایی ابزار و نسخه‌ی وابستگی‌ها.

Submodule و Subtree

Submodule یک repo دیگر را در یک مسیر از repo شما قرار می‌دهد، اما فقط یک commit مشخص از آن را ثبت می‌کند (نه branch). اطلاعات آن در فایل .gitmodules است.

git submodule add https://github.com/acme/shared-contracts.git contracts
git clone --recurse-submodules <url>
git submodule update --init --recursive   # بعد از clone معمولی
cd contracts && git pull origin main && cd .. && git add contracts && git commit -m "chore: bump contracts"
  • مشکلات رایج: فراموش کردن update بعد از pull (کد قدیمی)، detached HEAD داخل submodule، و commit کردن اشاره‌گری که push نشده است.
  • Subtree: کد repo دیگر را مستقیماً در تاریخچه‌ی شما ادغام می‌کند؛ کاربران repo ابزار اضافه‌ای لازم ندارند، اما ارسال تغییرات به repo مبدأ پیچیده‌تر است.
  • در PHP، برای اشتراک کد بین پروژه‌ها معمولاً یک پکیج Composer (حتی private از طریق repository از نوع vcs یا path) بهتر از submodule است، چون نسخه‌دهی SemVer و مدیریت وابستگی را به‌طور طبیعی دارد.

سوالات تشریحی

ساختار داخلی Git را توضیح دهید. blob، tree، commit و ref چه هستند و branch در واقع چیست؟

تعریف: Git یک پایگاه داده‌ی content-addressable است: هر شیء با hash محتوایش (پیش‌فرض SHA-1) ذخیره و شناسایی می‌شود. چهار نوع شیء اصلی دارد:

  • blob: محتوای یک فایل، بدون نام.
  • tree: یک پوشه؛ نام فایل‌ها و اشاره به blobها و treeهای فرزند.
  • commit: اشاره به tree ریشه (یعنی یک snapshot کامل)، اشاره به والد(ها)، author/committer و پیام.
  • annotated tag: شیئی با نام و پیام که به یک commit اشاره می‌کند.

Ref یک نام خوانا برای یک hash است. branch فقط یک ref متحرک است، یعنی فایلی کوچک در refs/heads/ که hash آخرین commit را نگه می‌دارد و با هر commit جدید جلو می‌رود. HEAD نشان می‌دهد الان روی کدام branch (یا در حالت detached، کدام commit) هستیم.

پیامدها:

  • چون hash به محتوا و والد وابسته است، تاریخچه immutable است؛ amend و rebase commit جدید می‌سازند.
  • ساختن branch تقریباً رایگان است، پس branchهای کوتاه‌عمر برای هر feature عملی‌اند.
  • فایل‌های بدون تغییر بین commitها به اشتراک گذاشته می‌شوند؛ snapshot بودن به معنی هدر رفتن فضا نیست.
  • یکپارچگی تضمین می‌شود: دستکاری هر بایت در تاریخچه hash همه‌ی commitهای بعدی را تغییر می‌دهد.
تفاوت fast-forward merge و three-way merge را با رسم شکل توضیح دهید. گزینه‌ی --no-ff چه زمانی مفید است؟

Fast-forward: وقتی branch مقصد از زمان جدا شدن هیچ commit جدیدی نداشته باشد، یعنی نوک مقصد جد مستقیم نوک feature باشد، Git فقط اشاره‌گر مقصد را جلو می‌برد. هیچ commit جدیدی ساخته نمی‌شود و تاریخچه خطی است.

A ─ B ─ C (main)               A ─ B ─ C ─ D ─ E (main)
         └ D ─ E (feature)   ⇒

Three-way: وقتی هر دو branch commit جدید دارند، Git سه نسخه را مقایسه می‌کند: merge base (جد مشترک)، نوک branch فعلی و نوک branch دیگر. تغییراتی که فقط در یک طرف هستند خودکار اعمال می‌شوند و تغییرات متضاد در یک ناحیه conflict ایجاد می‌کنند. نتیجه یک merge commit با دو والد است.

A ─ B ─ C ─ F ─── M (main)
         └ D ─ E ─┘  (feature)

--no-ff حتی وقتی ff ممکن است merge commit می‌سازد. مزایا:

  • مرز هر feature در تاریخچه دیده می‌شود (git log --first-parent فقط merge commitهای main را نشان می‌دهد).
  • revert کل feature با یک دستور: git revert -m 1 <merge>.

عیب آن تاریخچه‌ی شلوغ‌تر است. تیم‌هایی که تاریخچه‌ی خطی می‌خواهند از --ff-only یا squash-merge استفاده می‌کنند.

Rebase و Merge را مقایسه کنید. «قانون طلایی rebase» چیست و چرا نقض آن مشکل‌ساز است؟

Merge دو تاریخچه را با یک merge commit به هم وصل می‌کند و هیچ commit موجودی را تغییر نمی‌دهد. Rebase commitهای branch را روی پایه‌ی جدید دوباره اعمال می‌کند؛ چون والد عوض می‌شود، commitهای جدید با hash جدید ساخته می‌شوند.

قانون طلایی: commitهایی را که push شده و دیگران ممکن است بر پایه‌ی آن‌ها کار کرده باشند rebase نکنید.

چرا؟ همکاران شما commitهای قدیمی (D، E) را دارند و شما commitهای جدید (D′، E′) را force-push کرده‌اید. از دید Git این‌ها commitهای متفاوتی‌اند؛ در pull بعدی همکار، تغییرات تکراری، merge commit عجیب و conflictهای گیج‌کننده رخ می‌دهد و اگر force-push بی‌احتیاط باشد، ممکن است commitهای دیگران روی remote پاک شود.

جمع‌بندی عملی: rebase برای همگام‌سازی و تمیز کردن branch شخصی قبل از PR (و pull --rebase برای commitهای push‌نشده)؛ merge (یا squash-merge در PR) برای ادغام در main و branchهای مشترک. اگر rebase روی branch شخصی push‌شده لازم شد، از --force-with-lease استفاده کنید.

سه حالت git reset (soft، mixed، hard) را توضیح دهید و تفاوت reset با revert را بیان کنید. روی main کدام را استفاده می‌کنید؟

reset اشاره‌گر branch فعلی (و HEAD) را به commit دیگری منتقل می‌کند. تفاوت حالت‌ها در اثر روی index و working tree است:

  • --soft: فقط branch جابه‌جا می‌شود؛ تغییرات commitهای حذف‌شده stage‌شده می‌مانند. کاربرد: ادغام چند commit آخر در یکی (reset --soft HEAD~3 و commit مجدد).
  • --mixed (پیش‌فرض): index هم reset می‌شود؛ تغییرات در working tree می‌مانند اما unstaged. کاربرد: بازچینی commitها.
  • --hard: index و working tree هم با commit هدف یکی می‌شوند؛ تغییرات commit‌نشده برای همیشه از دست می‌روند.

revert یک commit جدید می‌سازد که اثر commit هدف را خنثی می‌کند؛ تاریخچه بازنویسی نمی‌شود.

روی main (و هر branch push‌شده و مشترک) همیشه git revert؛ هم امن است و هم مشخص می‌کند که چه چیزی، چرا و توسط چه کسی برگشته است. reset برای کار محلی push‌نشده است. برای revert یک merge commit از -m 1 استفاده می‌شود.

تفاوت git fetch و git pull چیست؟ pull --rebase چه مزیتی دارد؟

fetch commitها و refهای جدید را از remote دانلود و فقط remote-tracking branchها (مثل origin/main) را به‌روز می‌کند. branchهای محلی و working tree دست‌نخورده می‌مانند؛ بنابراین همیشه امن است و می‌توان قبل از ادغام تغییرات را بررسی کرد:

git fetch
git log --oneline main..origin/main   # چه چیزی آمده؟
git diff main...origin/main

pull = fetch + ادغام upstream در branch فعلی (به‌طور پیش‌فرض merge). ممکن است conflict یا merge commit ایجاد کند.

pull --rebase: به‌جای merge، commitهای محلی push‌نشده‌ی شما را روی نسخه‌ی جدید remote قرار می‌دهد. مزایا:

  • از merge commitهای بی‌معنی «Merge branch 'main' of origin» جلوگیری می‌کند.
  • تاریخچه خطی می‌ماند.
  • قانون طلایی را نقض نمی‌کند، چون فقط commitهای push‌نشده بازنویسی می‌شوند.

با git config --global pull.rebase true پیش‌فرض می‌شود. در محیط CI یا هنگام کار روی branch ناآشنا، fetch و بررسی قبل از ادغام انتخاب محتاطانه‌تری است.

یک سناریو: بعد از rebase روی branch feature می‌خواهید push کنید و رد می‌شود. همکارتان هم روی همین branch کار می‌کند. چه می‌کنید؟ تفاوت --force و --force-with-lease را بگویید.

علت رد شدن: rebase commitها را با hash جدید بازنویسی کرده و تاریخچه‌ی محلی دیگر ادامه‌ی (fast-forward) تاریخچه‌ی remote نیست.

اقدام:

  1. اول با همکار هماهنگ کنید؛ در اصل، branch مشترک نباید rebase شود (قانون طلایی). اگر هماهنگی ممکن نیست، به‌جای rebase از git merge origin/main استفاده کنید.
  2. git fetch و بررسی اینکه همکار چیزی push کرده یا نه: git log HEAD..origin/feature.
  3. اگر commit جدیدی دارد، آن را روی branch rebase‌شده بیاورید (rebase دوباره روی origin/feature یا cherry-pick).
  4. سپس git push --force-with-lease و اطلاع به همکار تا branch محلی خود را با git fetch و git reset --hard origin/feature (اگر تغییر محلی ندارد) یا git pull --rebase هماهنگ کند.

تفاوت‌ها:

  • --force: remote را بی‌قیدوشرط بازنویسی می‌کند؛ commitهای همکار که از آخرین fetch شما push شده‌اند پاک می‌شوند.
  • --force-with-lease: فقط اگر ref روی remote هنوز برابر origin/feature محلی شما باشد بازنویسی می‌کند؛ اگر کسی در این فاصله push کرده باشد، رد می‌شود.
  • ضعف lease: اگر بعد از push همکار fetch کرده باشید (حتی خودکار در IDE)، lease پاس می‌شود. --force-if-includes این را هم بررسی می‌کند.

روی main و release branchها force push باید با branch protection کاملاً ممنوع باشد.

چند commit «wip» و «fix typo» در branch خود دارید و می‌خواهید قبل از PR تاریخچه را تمیز کنید. چه روش‌هایی دارید؟ squash کردن چه مزایا و معایبی دارد؟

روش‌ها:

  • Interactive rebase: git rebase -i origin/main و استفاده از squash (ادغام و ترکیب پیام‌ها)، fixup (ادغام و دور ریختن پیام)، reword، drop و تغییر ترتیب خطوط.
  • fixup هدفمند: git commit --fixup=<sha> و بعد git rebase -i --autosquash origin/main.
  • reset --soft: git reset --soft origin/main و یک commit جدید؛ ساده‌ترین روش برای تبدیل همه به یک commit.
  • Squash and merge در PR: پلتفرم هنگام merge همه را یک commit می‌کند.

اگر branch قبلاً push شده، بعد از بازنویسی git push --force-with-lease لازم است (فقط برای branch شخصی).

مزایای squash: تاریخچه‌ی main خوانا (یک commit به ازای هر تغییر منطقی)، revert آسان کل feature، حذف نویز آزمون و خطا، و حفظ قابلیت build بودن هر commit (به نفع bisect).

معایب: اگر PR بزرگ باشد، جزئیات مراحل منطقی از بین می‌رود و bisect و blame فقط به یک commit بزرگ می‌رسند؛ commitهای مستقل (مثلاً refactor جدا از feature) در هم ادغام می‌شوند.

رویکرد متعادل: نویز را squash کنید، ولی گام‌های منطقی مستقل را به‌صورت commitهای جدا با پیام معنادار نگه دارید.

یک سناریو: به‌طور تصادفی git reset --hard HEAD~3 اجرا کرده‌اید و سه commit مهم «گم» شده است. چطور آن‌ها را بازیابی می‌کنید؟ چه چیزهایی قابل بازیابی نیستند؟

نکته‌ی کلیدی: reset commitها را حذف نمی‌کند، فقط اشاره‌گر branch را عقب می‌برد. commitها هنوز در object database هستند و reflog ثبت کرده که HEAD قبلاً کجا بوده است.

git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~3
# 9f8e7d6 HEAD@{1}: commit: feat: add coupon validation
git reset --hard 9f8e7d6     # یا HEAD@{1}
# روش محتاطانه‌تر: git branch rescue 9f8e7d6
# بلافاصله بعد از reset/rebase/merge: git reset --hard ORIG_HEAD

چه چیزهایی قابل بازیابی نیستند یا محدودیت دارند:

  • تغییرات commit‌نشده در working tree که با --hard پاک شده‌اند، در reflog نیستند. (اگر فقط stage شده بودند، blob آن‌ها ممکن است با git fsck --lost-found پیدا شود.)
  • reflog محلی است؛ در clone دیگر یا روی سرور وجود ندارد.
  • ورودی‌ها منقضی می‌شوند (پیش‌فرض‌ها ۹۰ و ۳۰ روز) و پس از آن git gc اشیای بی‌مرجع را حذف می‌کند.

پیشگیری: قبل از عملیات پرخطر یک branch پشتیبان بسازید، به‌جای --hard از --keep یا stash استفاده کنید، و commitها را زودبه‌زود روی branch شخصی push کنید.

یک باگ در production دیده شده که در نسخه‌ی v2.2.0 وجود نداشت و بین آن و HEAD حدود ۵۰۰ commit فاصله است. با Git چطور commit معیوب را پیدا می‌کنید؟

ابزار: git bisect که با جستجوی دودویی اولین commit معیوب را پیدا می‌کند. برای ۵۰۰ commit حدود ۹ مرحله (log₂ 500) کافی است.

  1. یک تست خودکار بنویسید که باگ را بازتولید کند (و در نسخه‌ی سالم پاس شود). این تست بعداً regression test هم خواهد بود.
  2. اجرای bisect:
git bisect start HEAD v2.2.0       # bad سپس good
git bisect run ./vendor/bin/phpunit --filter=InvoiceRoundingTest
# خروجی: "3c4d5e6 is the first bad commit"
git show 3c4d5e6
git bisect reset
  • bisect run برای exit code ۰ آن commit را good و برای ۱ تا ۱۲۷ (به جز ۱۲۵) bad در نظر می‌گیرد؛ ۱۲۵ یعنی skip (مثلاً commit قابل build نیست).
  • اگر تست خودکار ممکن نیست، دستی تست کنید و git bisect good/bad بزنید.
  • اگر schema دیتابیس بین commitها تغییر کرده، اسکریپت باید migration مناسب را اجرا کند (مثلاً RefreshDatabase در تست).

شرط کارایی: commitهای کوچک و اتمیک که هر کدام build و تست را پاس می‌کنند. با squash-merge commitهای بزرگ، bisect فقط PR مقصر را پیدا می‌کند. مکمل‌ها: git log -S برای جستجوی تغییر یک رشته و git blame برای خطوط مشکوک.

Git Flow، GitHub Flow و Trunk-based Development را مقایسه کنید. برای یک تیم ۶ نفره که یک SaaS مبتنی بر Laravel را چند بار در هفته deploy می‌کند، کدام را پیشنهاد می‌دهید و چرا؟
  • Git Flow: branchهای دائمی main و develop به‌علاوه‌ی feature/*، release/* و hotfix/*. مناسب releaseهای دوره‌ای و پشتیبانی چند نسخه‌ی هم‌زمان. عیب: پیچیدگی، branchهای طولانی، conflict زیاد، فاصله‌ی زیاد تا production.
  • GitHub Flow: فقط main که همیشه deployable است؛ branch کوتاه، PR، review و CI، merge و deploy. ساده و مناسب deploy پیوسته، اما بدون CI قوی ریسکی است و چندنسخه‌ای را پوشش نمی‌دهد.
  • Trunk-based: ادغام چندباره در روز در trunk با branchهای چندساعته و feature flag برای کار ناتمام. کمترین conflict و سریع‌ترین بازخورد، ولی نیازمند CI سریع، تست خودکار قوی و نظم تیمی.

پیشنهاد برای این تیم: GitHub Flow (با حرکت تدریجی به سمت trunk-based):

  • یک نسخه در production وجود دارد، پس release branch و develop سربار بی‌فایده‌اند.
  • PRهای کوچک با branch protection: CI شامل Pest/PHPUnit، Larastan و Pint، و حداقل یک approve.
  • squash-merge با پیام Conventional تا CHANGELOG و نسخه خودکار تولید شود.
  • feature flag (مثلاً Laravel Pennant) برای featureهای بزرگ تا branchها طولانی نشوند.
  • deploy خودکار از main به staging و deploy کنترل‌شده به production؛ hotfix هم یک PR عادی است.

اگر بعداً محصول on-premise با چند نسخه‌ی تحت پشتیبانی اضافه شود، می‌توان release branchها را اضافه کرد.

یک Pull Request خوب چه ویژگی‌هایی دارد و در code review به چه مواردی توجه می‌کنید؟ هدف code review فقط پیدا کردن باگ است؟

PR خوب:

  • کوچک و تک‌هدفه (معمولاً چند صد خط یا کمتر)؛ refactor و feature در PRهای جدا.
  • توضیح «چه و چرا»، لینک issue، نحوه‌ی تست، نکات deploy (migration، env جدید، worker).
  • self-review، CI سبز، commitهای تمیز.

چک‌لیست review:

  1. درستی: برآورده شدن نیازمندی، edge caseها، مدیریت خطا، تراکنش و race condition.
  2. امنیت: authorization (Policy/Gate)، validation، mass assignment، SQL injection، داده‌ی حساس در log.
  3. کارایی: N+1 (eager loading)، index، کار سنگین در queue.
  4. طراحی: جای درست منطق، coupling، سازگاری با معماری موجود.
  5. تست: پوشش رفتارهای مهم و حالت‌های خطا.
  6. خوانایی: نام‌گذاری، پیچیدگی، مستندات.

اهداف فراتر از باگ: اشتراک دانش و کاهش bus factor، یکپارچگی معماری و سبک، آموزش، و ثبت تصمیم‌ها در تاریخچه‌ی PR.

فرهنگ: نقد کد نه شخص، سؤال به‌جای حکم، تفکیک nit: از موارد blocking، review سریع، و سپردن style به ابزارهای خودکار.

Conventional Commits چیست؟ ساختار آن را با مثال بنویسید و ارتباطش را با Semantic Versioning توضیح دهید.

تعریف: یک قرارداد سبک برای پیام commit که ساختار مشخص و قابل پردازش با ماشین دارد:

<type>(<scope>)[!]: <description>

<body: چرا و چگونه>

<footer: BREAKING CHANGE: ... / Closes #123>
feat(auth): add two-factor authentication via TOTP
fix(cart): round tax per line instead of per order
refactor(order)!: rename status "paid" to "settled"

BREAKING CHANGE: API consumers must handle the new status value.

ارتباط با SemVer:

  • fix ← افزایش PATCH
  • feat ← افزایش MINOR
  • ! بعد از type/scope یا footer BREAKING CHANGE: ← افزایش MAJOR
  • typeهای دیگر (docs، refactor، test، ci، chore و…) معمولاً release ایجاد نمی‌کنند.

مزایا: تولید خودکار CHANGELOG و نسخه (semantic-release، release-please)، تاریخچه‌ی قابل جستجو، و وادار کردن توسعه‌دهنده به فکر کردن درباره‌ی ماهیت تغییر (آیا breaking است؟).

اجرا: hook commit-msg با commitlint و بررسی در CI؛ در صورت squash-merge، کافی است عنوان PR از قرارداد پیروی کند.

محدودیت: قرارداد فقط قالب را تضمین می‌کند؛ کیفیت محتوا (توضیح «چرا») همچنان به نویسنده بستگی دارد.

کد/دستورات زیر چه مشکلی دارند؟ git add .env && git commit -m "update" && git push origin main --force

این دستور زنجیره‌ای چند مشکل جدی دارد:

  1. commit کردن .env: این فایل secretها (کلید APP_KEY، رمز دیتابیس، کلید APIها) را دارد. باید در .gitignore باشد و فقط .env.example بدون مقدار commit شود. اگر push شد، باید فرض کرد لو رفته است: همه‌ی کلیدها را rotate کنید، فایل را با git rm --cached .env خارج کنید و در صورت نیاز تاریخچه را با git filter-repo پاک‌سازی کنید (که خودش نیازمند هماهنگی تیم است).
  2. پیام «update»: بی‌معنی است؛ نه نوع تغییر را می‌گوید نه دلیل آن را. باید مثلاً chore(config): add mail queue settings با توضیح باشد.
  3. push مستقیم به main: review و CI را دور می‌زند؛ باید از طریق PR انجام شود.
  4. --force روی main: تاریخچه‌ی مشترک را بازنویسی می‌کند و ممکن است commitهای دیگران را پاک کند. در صورت نیاز واقعی به force روی branch شخصی، --force-with-lease استفاده شود؛ روی main هرگز.

پیشگیری سیستمی: branch protection روی main (منع push مستقیم و force push)، secret scanning در pre-commit (مثل gitleaks) و در پلتفرم/CI، و .gitignore استاندارد Laravel.

Conflict در Git چه زمانی رخ می‌دهد و مراحل حل آن چیست؟ برای کاهش conflict در تیم چه پیشنهادهایی دارید؟

تعریف: conflict وقتی رخ می‌دهد که Git در three-way merge (یا rebase/cherry-pick) نتواند خودکار تصمیم بگیرد: هر دو طرف یک ناحیه از فایل را نسبت به merge base به شکل متفاوت تغییر داده‌اند، یا یک طرف فایل را حذف و طرف دیگر ویرایش کرده است.

مراحل حل:

  1. git status برای فهرست فایل‌های unmerged.
  2. بررسی markerها (<<<<<<<، =======، >>>>>>>)؛ با merge.conflictStyle=zdiff3 نسخه‌ی base هم دیده می‌شود.
  3. فهم منطق هر دو تغییر و نوشتن نسخه‌ی ترکیبی صحیح؛ اغلب جواب درست ترکیب هر دو است، نه انتخاب یکی.
  4. اجرای تست‌ها، سپس git add و git commit یا git rebase --continue.
  5. در صورت نیاز --abort. برای lock fileها، یک نسخه را بردارید و با Composer دوباره تولید کنید.

کاهش conflict:

  • branchهای کوتاه‌عمر و PRهای کوچک؛ ادغام مکرر (پایه‌ی trunk-based).
  • همگام‌سازی منظم branch با main.
  • formatter مشترک (Pint) و تنظیمات editor یکسان (.editorconfig) تا تغییرات فاصله‌گذاری conflict نسازند.
  • شکستن فایل‌های بزرگ و پرتغییر؛ ارتباط تیمی برای refactorهای گسترده.
  • rerere برای تکرار خودکار حل conflictهای قبلی.
Git hookها چه هستند؟ یک pre-commit hook برای پروژه‌ی PHP چه کارهایی باید انجام دهد و چرا hook جایگزین CI نیست؟

تعریف: hookها اسکریپت‌هایی هستند که Git در رویدادهای مشخص (مثل pre-commit، commit-msg، pre-push و در سرور pre-receive) اجرا می‌کند. اگر hookهای «pre» کد خروج غیرصفر برگردانند، عملیات لغو می‌شود.

pre-commit مناسب برای PHP (فقط روی فایل‌های stage‌شده و سریع):

  • php -l برای خطای syntax.
  • بررسی style با pint --test (یا اصلاح خودکار).
  • اسکن secret (gitleaks) و جلوگیری از commit فایل‌های .env.
  • جلوگیری از dd()/dump() فراموش‌شده.
  • کارهای کندتر مثل تست کامل و PHPStan بهتر است در pre-push یا CI باشند.

اشتراک‌گذاری: .git/hooks version control نمی‌شود؛ با git config core.hooksPath .githooks یا ابزارهایی مثل CaptainHook/GrumPHP (از طریق Composer) hookها در repo نگه‌داری و نصب می‌شوند.

چرا جایگزین CI نیست:

  • با --no-verify قابل دور زدن‌اند و ممکن است روی سیستم یک نفر نصب نشده باشند.
  • به محیط محلی وابسته‌اند (نسخه‌ی PHP، extensionها).
  • CI در محیط یکسان و کنترل‌شده اجرا می‌شود و همراه با branch protection اجبار ایجاد می‌کند.

پس hook برای بازخورد سریع است و CI برای تضمین.

git stash چیست و چه زمانی از آن استفاده می‌کنید؟ چه جایگزین‌هایی برای آن وجود دارد؟

تعریف: stash تغییرات commit‌نشده (working tree و index) را در یک پشته‌ی محلی ذخیره و working tree را به وضعیت HEAD برمی‌گرداند. stash در واقع commitهای ویژه‌ای است که در refs/stash نگه‌داری می‌شوند.

کاربردها:

  • وسط کار هستید و باید فوراً branch را عوض کنید (hotfix).
  • قبل از pull یا rebase که working tree تمیز می‌خواهد.
  • انتقال تغییرات به branch دیگر (stash، switch، pop).
git stash push -u -m "wip: invoice totals"
git switch hotfix/login
# ...
git switch feature/invoice
git stash pop

نکات: فایل‌های untracked به‌طور پیش‌فرض stash نمی‌شوند (-u لازم است)؛ pop در صورت conflict stash را حذف نمی‌کند؛ stash push نمی‌شود و نام branch ندارد، پس به‌راحتی فراموش می‌شود.

جایگزین‌ها:

  • WIP commit روی branch شخصی و بعداً reset --soft HEAD~1 یا squash؛ قابل push و پشتیبان‌گیری.
  • git worktree: git worktree add ../app-hotfix main؛ working tree دوم بدون دست زدن به کار فعلی. برای کار موازی بهترین گزینه است.

خلاصه برای مرور سریع

مدل

  • commit = snapshot تغییرناپذیر + والد(ها)؛ شناسه = hash محتوا.
  • اشیا: blob (فایل)، tree (پوشه)، commit، annotated tag.
  • branch = اشاره‌گر متحرک؛ tag = اشاره‌گر ثابت؛ HEAD = جای فعلی.
  • Detached HEAD = HEAD مستقیم روی commit؛ commitها را با branch نجات دهید.
  • سه ناحیه: working tree ← (add) ← index ← (commit) ← repo.
  • diff = unstaged؛ diff --staged = آنچه commit می‌شود.

ادغام

  • ff: فقط جلو بردن اشاره‌گر، بدون commit جدید.
  • three-way: base + دو نوک ← merge commit با دو والد.
  • --no-ff مرز feature را حفظ می‌کند؛ --squash یک commit بدون ارتباط والدی.
  • rebase = replay با hash جدید؛ تاریخچه‌ی خطی.
  • قانون طلایی: commitهای push‌شده‌ی مشترک را rebase نکنید.
  • rebase محلی، merge/squash در PR.
  • conflict: فهم هر دو طرف، تست، add، continue؛ zdiff3 و rerere مفیدند.
  • در rebase، ours = پایه و theirs = commit شما.

بازگردانی

  • reset --soft: فقط branch؛ --mixed: + index؛ --hard: + working tree.
  • revert: commit معکوس، امن برای main؛ merge: -m 1.
  • restore file: دور ریختن تغییر؛ restore --staged: unstage.
  • stash -u، pop در برابر apply؛ جایگزین: WIP commit یا worktree.
  • cherry-pick -x: کپی یک commit با hash جدید (backport).
  • rebase -i: pick، reword، edit، squash، fixup، drop؛ --fixup + --autosquash.

Remote

  • fetch: فقط origin/* را به‌روز می‌کند (امن).
  • pull = fetch + merge؛ pull --rebase بدون merge commit بی‌معنی.
  • push فقط ff پذیرفته می‌شود؛ بعد از rebase: --force-with-lease (+ --force-if-includes).
  • tagها جدا push می‌شوند: git push origin v1.2.0 یا --follow-tags.

نسخه و پیام

  • SemVer: MAJOR (ناسازگار)، MINOR (قابلیت سازگار)، PATCH (رفع باگ).
  • Composer: ^2.3 = <3.0؛ ~2.3.1 = <2.4.0؛ ^0.4 = <0.5.
  • Annotated tag برای release؛ tag منتشرشده را جابه‌جا نکنید.
  • Conventional: type(scope)!: desc؛ feat→MINOR، fix→PATCH، BREAKING→MAJOR.
  • subject حدود ۵۰ کاراکتر، امری، body = «چرا».

Workflow و تیم

  • Git Flow: main + develop + feature/release/hotfix؛ برای release دوره‌ای و چندنسخه‌ای.
  • GitHub Flow: main همیشه deployable + PR؛ برای SaaS.
  • Trunk-based: ادغام روزانه + feature flag + CI قوی.
  • PR کوچک، توضیح چه/چرا/تست/deploy، CI سبز، branch protection، CODEOWNERS.
  • review: درستی، امنیت، کارایی، طراحی، تست، خوانایی + اشتراک دانش.

بازیابی و ابزار

  • reflog: تاریخچه‌ی محلی HEAD؛ نجات بعد از reset/rebase؛ ORIG_HEAD.
  • تغییرات commit‌نشده با reset --hard قابل بازیابی نیستند.
  • bisect: جستجوی دودویی؛ bisect run؛ ۱۲۵ = skip.
  • blame، log -S، log -L برای ردیابی.
  • .gitignore روی فایل track‌شده اثر ندارد ← rm --cached.
  • secret لو رفته ← اول rotate، بعد پاک‌سازی.
  • hook = بازخورد سریع (قابل دور زدن)؛ CI = تضمین. core.hooksPath برای اشتراک.
  • submodule = اشاره به یک commit مشخص؛ در PHP پکیج Composer معمولاً بهتر است.
