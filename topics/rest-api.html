REST API

اصول معماری REST، طراحی منابع و URI، متدها و status codeها، خطا با Problem Details، صفحه‌بندی، نسخه‌بندی، احراز هویت (OAuth 2.0، JWT، Sanctum)، caching، idempotency و پیاده‌سازی کامل در Laravel.

REST، قیدها و مدل Richardson

REST (Representational State Transfer) یک سبک معماری است که Roy Fielding در رسالهٔ دکترای خود (سال ۲۰۰۰) تعریف کرد؛ نه پروتکل است و نه استاندارد. در REST همه‌چیز حول منبع (Resource) می‌چرخد: هر منبع با یک URI شناسایی می‌شود و client با نمایش (representation) آن منبع (مثلاً JSON) کار می‌کند و با متدهای استاندارد HTTP وضعیتش را منتقل یا تغییر می‌دهد. یک API فقط وقتی واقعاً RESTful است که این شش قید را رعایت کند:

چهار جزء Uniform Interface

  1. Identification of resources: هر منبع URI یکتا دارد (/users/42).
  2. Manipulation through representations: client با نمایشی که دریافت کرده (JSON) و متادیتای کافی، می‌تواند منبع را تغییر دهد.
  3. Self-descriptive messages: هر پیام با متد، status code و هدرهایی مثل Content-Type و Cache-Control خودش را توصیف می‌کند.
  4. HATEOAS (Hypermedia as the Engine of Application State): پاسخ‌ها شامل لینک به اقدامات و منابع مرتبط‌اند تا client مسیر را از پاسخ کشف کند.

«Stateless» یعنی state نشست client روی سرور نگه داشته نمی‌شود، نه اینکه سرور هیچ داده‌ای ندارد. Resource state (داده‌های دیتابیس) کاملاً مجاز است. پس API با session cookie سمت سرور به‌طور دقیق stateless نیست، در حالی که API با Bearer token که هر درخواست را مستقل احراز می‌کند stateless است.

اشتباه رایج: «هر API که JSON روی HTTP برمی‌گرداند REST است». API با مسیرهایی مثل POST /getUser و POST /deleteUser در واقع RPC روی HTTP است، نه REST.

مدل بلوغ Richardson

Leonard Richardson مدلی چهارسطحی برای سنجش میزان RESTful بودن یک API ارائه کرد:

Level 3 ─ Hypermedia Controls (HATEOAS)      ← "Glory of REST"
Level 2 ─ HTTP Verbs + Status Codes          ← اغلب APIهای «REST» امروزی
Level 1 ─ Resources (URIهای جدا برای هر منبع)
Level 0 ─ The Swamp of POX (یک endpoint، همه‌چیز POST)
سطحویژگیمثال

از دید Fielding، بدون HATEOAS یک API واقعاً REST نیست؛ اما در صنعت، Level 2 استاندارد عملی است و Level 3 فقط در برخی APIهای عمومی دیده می‌شود.

طراحی منابع و URI

قواعد اصلی

  • اسم، نه فعل: URI منبع را نام می‌برد؛ عمل را متد HTTP بیان می‌کند. GET /orders نه GET /getOrders.
  • جمع برای collection: /users و /users/42 (یکدستی مهم‌تر از قاعدهٔ دستوری است).
  • حروف کوچک و kebab-case: /order-items؛ بدون پسوند فایل (.json) و بدون اسلش پایانی.
  • شناسهٔ پایدار: ترجیحاً شناسه‌ای که تغییر نمی‌کند (ID، UUID یا ULID). UUID/ULID حدس‌زدن شناسه‌ها را دشوار می‌کند (ولی جایگزین authorization نیست).
  • Nesting حداکثر یک سطح برای بیان مالکیت: /users/42/orders. به‌جای /users/42/orders/7/items/3 از /order-items/3 یا /orders/7/items استفاده کنید.
  • Query string برای فیلتر، مرتب‌سازی، صفحه‌بندی و جستجو، نه برای شناسایی منبع: /orders?status=paid&sort=-created_at&page[size]=20.
  • اقدامات غیر CRUD: یا به‌عنوان زیرمنبع مدل کنید (POST /orders/7/cancellation)، یا اگر واقعاً فعل است، به شکل زیرمسیر کنترل‌شده (POST /orders/7/cancel). مهم یکدستی در کل API است.

متدهای HTTP، Safe و Idempotent

Safe
متدی که قرار نیست وضعیت منبع را روی سرور تغییر دهد (فقط خواندن). لاگ یا شمارندهٔ بازدید نقض محسوب نمی‌شود چون client آن را درخواست نکرده است.
Idempotent
تکرار یک درخواست یکسان N بار، همان اثر نهایی روی وضعیت سرور را دارد که اجرای یک‌باره (پاسخ ممکن است متفاوت باشد؛ مثلاً DELETE دوم 404 می‌دهد). این ویژگی برای retry امن پس از timeout حیاتی است.
Cacheable
پاسخ آن به‌طور پیش‌فرض می‌تواند cache شود.

PUT در برابر PATCH در برابر POST

PUT

  • client نمایش کامل منبع را می‌فرستد؛ فیلدهای نفرستاده‌شده باید به پیش‌فرض برگردند یا حذف شوند.
  • URI را client تعیین می‌کند: PUT /users/42/avatar.
  • Idempotent: ارسال دوبارهٔ همان بدنه همان نتیجه را می‌دهد.

PATCH

  • فقط تغییرات را می‌فرستد: {"name":"Ali"}.
  • قالب‌های استاندارد: JSON Merge Patch (RFC 7396، application/merge-patch+json) و JSON Patch (RFC 6902، آرایه‌ای از عملیات).
  • لزوماً idempotent نیست: {"op":"add","path":"/tags/-"} یا «موجودی را ۵ تا افزایش بده» با تکرار اثر انباشته دارد.
  • POST وقتی سرور شناسه را تعیین می‌کند (POST /orders ← 201 + Location: /orders/981) یا برای عملیات‌هایی که در قالب CRUD نمی‌گنجند. POST idempotent نیست: دو بار ارسال یعنی دو سفارش — مگر با Idempotency-Key.
PUT /users/42 HTTP/1.1
Content-Type: application/json

{"name": "Ali Rezaei", "email": "ali@example.com", "phone": null}

PATCH /users/42 HTTP/1.1
Content-Type: application/merge-patch+json

{"phone": "+989121234567"}

نمونه سوال: «آیا DELETE idempotent است وقتی بار دوم 404 برمی‌گرداند؟» بله؛ idempotency دربارهٔ اثر روی وضعیت سرور است نه یکسان بودن پاسخ. بعد از اولین DELETE منبع وجود ندارد و بعد از دهمین هم وجود ندارد.

هرگز عمل تغییردهنده را با GET پیاده نکنید (GET /users/42/delete). crawlerها، prefetch مرورگر و cacheها GET را بی‌خطر فرض می‌کنند و ممکن است آن را خودکار اجرا کنند؛ همچنین در برابر CSRF آسیب‌پذیر است.

401 در برابر 403: 401 یعنی «نمی‌دانم کی هستی» (احراز هویت ناموفق یا نبود توکن، مشکل authentication)؛ 403 یعنی «می‌دانم کی هستی اما اجازه نداری» (مشکل authorization). 400 در برابر 422: 400 برای درخواست بدشکل (JSON خراب)، 422 برای داده‌ای که از نظر قالب درست است ولی قوانین کسب‌وکار یا validation را نقض می‌کند. 409 در برابر 422: 409 وقتی دادهٔ درخواست به‌تنهایی معتبر است ولی با وضعیت فعلی منبع تعارض دارد.

ضدالگو: برگرداندن 200 OK با بدنهٔ {"success": false, "error": "..."}. این کار monitoring، cache، retry و ابزارهای client را گمراه می‌کند. خطاهای 4xx یعنی «client باید درخواست را اصلاح کند» (retry بی‌فایده است)، 5xx یعنی «مشکل از سرور است» (retry با backoff ممکن است کمک کند).

قالب خطا و Validation

همهٔ خطاهای API باید قالب یکسان و قابل‌پردازش توسط ماشین داشته باشند. استاندارد RFC 9457 — Problem Details for HTTP APIs (جایگزین RFC 7807) این قالب را تعریف می‌کند و Content-Type آن application/problem+json است.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Your request is not valid.",
  "status": 422,
  "detail": "Two fields failed validation.",
  "instance": "/orders",
  "errors": {
    "email": ["The email field must be a valid email address."],
    "items.0.quantity": ["The quantity must be at least 1."]
  },
  "trace_id": "01JC8X2M5Q7K..."
}
type
URI شناسهٔ نوع خطا (ترجیحاً به مستندات اشاره کند)؛ پیش‌فرض about:blank. client بر اساس این فیلد تصمیم می‌گیرد، نه متن پیام.
title
خلاصهٔ انسانی و ثابت برای آن نوع خطا.
status
همان status code (برای راحتی).
detail
توضیح خاص همین رخداد.
instance
URI مربوط به این رخداد خاص.
extension members
فیلدهای اضافه مثل errors یا trace_id مجازند.

اصول Validation

  • همه‌چیز را در سرور validate کنید؛ validation سمت client فقط برای تجربهٔ کاربری است.
  • همهٔ خطاها را یک‌جا برگردانید (نه فقط اولی) و آن‌ها را به فیلد مربوط نگاشت کنید.
  • از allow-list استفاده کنید: فقط فیلدهای validate‌شده را بپذیرید ($request->validated()) تا از Mass Assignment جلوگیری شود.
  • در خطاهای 500 جزئیات داخلی (stack trace، کوئری SQL) را افشا نکنید؛ APP_DEBUG=false در production. به‌جای آن یک trace_id بدهید که در لاگ قابل جستجو باشد.
  • کد خطای پایدار و مستند (مثلاً type یا یک فیلد code مثل insufficient_balance) بدهید تا client به متن پیام وابسته نشود.

قالب پیش‌فرض خطای validation در Laravel {"message": "...", "errors": {"field": ["..."]}} با status 422 است. این قالب Problem Details نیست ولی ساختار یکدستی دارد؛ می‌توان در bootstrap/app.php با withExceptions آن را به RFC 9457 تبدیل کرد (نمونه در بخش پیاده‌سازی).

صفحه‌بندی، فیلتر و مرتب‌سازی

هیچ endpoint فهرستی نباید کل جدول را برگرداند؛ صفحه‌بندی برای کارایی، حافظه و حفاظت از سرور ضروری است و باید سقف per_page داشته باشد.

Offset / Page-based

  • ?page=3&per_page=20 ← LIMIT 20 OFFSET 40
  • پرش مستقیم به صفحهٔ دلخواه و نمایش تعداد کل صفحات
  • در offsetهای بزرگ کند است: دیتابیس باید همهٔ ردیف‌های قبلی را بخواند و دور بریزد
  • با درج/حذف هم‌زمان، آیتم‌ها تکراری یا جاافتاده می‌شوند
  • COUNT(*) روی جدول بزرگ هزینه دارد
  • مناسب: پنل ادمین، داده‌های کوچک‌تا‌متوسط

Cursor / Keyset-based

  • ?cursor=eyJpZCI6MTAwfQ ← WHERE id < 100 ORDER BY id DESC LIMIT 20
  • کارایی ثابت در هر عمق (با ایندکس روی ستون مرتب‌سازی)
  • پایدار در برابر درج‌های هم‌زمان
  • پرش به صفحهٔ N و تعداد کل ممکن نیست
  • ستون مرتب‌سازی باید یکتا یا ترکیبی یکتا باشد (created_at, id)
  • مناسب: infinite scroll، فید، همگام‌سازی، داده‌های بزرگ
{
  "data": [ { "id": 120, "title": "..." } ],
  "links": { "next": "https://api.example.com/v1/posts?cursor=eyJpZCI6MTAwfQ", "prev": null },
  "meta":  { "per_page": 20, "next_cursor": "eyJpZCI6MTAwfQ" }
}
<?php
// Laravel: offset
$posts = Post::query()->latest()->paginate(perPage: min($request->integer('per_page', 15), 100));
// بدون COUNT(*) — فقط next/prev
$posts = Post::query()->latest()->simplePaginate(20);
// Cursor (keyset) — ORDER BY باید روی ستون‌های یکتا/ایندکس‌دار باشد
$posts = Post::query()->orderByDesc('id')->cursorPaginate(20);

return PostResource::collection($posts); // links و meta را خودکار اضافه می‌کند

فیلتر، مرتب‌سازی، sparse fieldsets و include

  • فیلتر: ?status=paid&created_after=2026-01-01 یا سبک JSON:API ?filter[status]=paid.
  • مرتب‌سازی: ?sort=-created_at,name (منفی = نزولی).
  • Sparse fieldsets: ?fields[users]=id,name برای کاهش حجم پاسخ.
  • Include روابط: ?include=author,comments ← در Laravel با eager loading (with()) برای جلوگیری از N+1.
  • جستجو: ?q=laptop.

امنیت: هرگز مقدار sort یا نام فیلد را مستقیم در کوئری قرار ندهید (مثلاً orderBy($request->sort) یا orderByRaw). نام ستون‌ها را با allow-list بررسی کنید؛ وگرنه کاربر می‌تواند بر اساس ستون‌های حساس مرتب کند یا در حالت raw به SQL injection برسد. پکیج spatie/laravel-query-builder همین allow-list را پیاده می‌کند.

نسخه‌بندی API

وقتی API مصرف‌کنندهٔ خارجی یا اپ موبایل دارد (که کاربران دیر به‌روزرسانی می‌کنند)، تغییرات breaking نباید clientهای فعلی را خراب کنند.

Non-breaking (بدون نسخهٔ جدید)

  • افزودن endpoint جدید
  • افزودن فیلد اختیاری به پاسخ
  • افزودن پارامتر اختیاری به درخواست
  • افزودن مقدار جدید به enum (اگر clientها tolerant باشند)

Breaking (نیاز به نسخهٔ جدید)

OAuth 2.0

OAuth 2.0 فریم‌ورکی برای تفویض دسترسی (delegated authorization) است: کاربر (Resource Owner) به یک اپلیکیشن (Client) اجازه می‌دهد بدون دادن رمز عبورش، با یک access token محدود (scope) به منابعش روی Resource Server دسترسی داشته باشد. توکن را Authorization Server صادر می‌کند.

Authorization Code + PKCE (برای اپ‌های کاربرمحور: SPA، موبایل، وب)

1. Client یک code_verifier تصادفی می‌سازد و code_challenge = BASE64URL(SHA256(verifier))
2. Browser ──► AuthServer /authorize?response_type=code&client_id=..&redirect_uri=..
                 &scope=orders:read&state=xyz&code_challenge=..&code_challenge_method=S256
3. کاربر login می‌کند و رضایت می‌دهد
4. AuthServer ──► redirect_uri?code=AUTH_CODE&state=xyz   (client مقدار state را چک می‌کند ← ضد CSRF)
5. Client ──► AuthServer /token  (code + code_verifier [+ client_secret برای confidential client])
6. AuthServer بررسی می‌کند SHA256(verifier) == challenge  ──► access_token (+ refresh_token)
7. Client ──► Resource Server با Authorization: Bearer access_token
  • چرا «code» و نه مستقیم توکن؟ توکن هرگز در URL و تاریخچهٔ مرورگر قرار نمی‌گیرد؛ تبادل code با توکن از کانال پشتی انجام می‌شود.
  • PKCE جلوی authorization code interception را می‌گیرد: حتی اگر مهاجم code را بدزدد، code_verifier را ندارد. برای public clientها (که نمی‌توانند secret نگه دارند) ضروری است و در OAuth 2.1 برای همهٔ clientها توصیه/الزام شده است.
  • Implicit flow (توکن مستقیم در fragment URL) و Password grant (ROPC) منسوخ و ناامن تلقی می‌شوند.

دام‌های JWT:

  • Payload فقط base64url-encode شده، رمزنگاری نشده؛ هر کسی می‌تواند آن را بخواند. اطلاعات حساس نگذارید (برای رمزنگاری JWE لازم است).

  • بررسی نکردن exp، aud و iss.
  • لغو (revocation) سخت است: JWT تا انقضا معتبر می‌ماند؛ راه‌حل: عمر کوتاه + refresh token، یا denylist بر اساس jti (که بخشی از مزیت stateless را از بین می‌برد).
  • ذخیره در localStorage در برابر XSS آسیب‌پذیر است؛ برای SPA مرورگری cookie با HttpOnly امن‌تر است (ولی CSRF باید مدیریت شود).
  • secret ضعیف برای HS256 با brute-force شکسته می‌شود.
  • JWTهای حجیم سربار هر درخواست را بالا می‌برند.

Idempotency Key، HATEOAS و Content Negotiation

Idempotency key برای POST

سناریو: اپ موبایل POST /payments می‌فرستد، سرور پرداخت را انجام می‌دهد اما پاسخ به دلیل قطعی شبکه نمی‌رسد. client نمی‌داند پرداخت انجام شده یا نه؛ اگر retry کند ممکن است دو بار پول کسر شود. راه‌حل: client یک کلید یکتا (UUID) برای هر عمل منطقی تولید می‌کند و در هدر Idempotency-Key می‌فرستد (الگویی که Stripe رایج کرد و پیش‌نویس IETF برای استانداردسازی آن وجود دارد).

  1. سرور کلید را (در محدودهٔ کاربر/client) بررسی می‌کند.
  2. اگر کلید جدید است: آن را با وضعیت «در حال پردازش» به‌صورت اتمیک ثبت می‌کند (unique constraint یا Cache::lock/add)، عملیات را انجام می‌دهد و پاسخ (status + body) را کنار کلید ذخیره می‌کند.
  3. اگر کلید تکراری با همان بدنه است: پاسخ ذخیره‌شده را بدون اجرای مجدد برمی‌گرداند.
  4. اگر کلید در حال پردازش است: 409 Conflict. اگر کلید تکراری با بدنهٔ متفاوت است: 422 (سوءاستفاده یا باگ client).
  5. کلیدها پس از مدتی (مثلاً ۲۴ ساعت) منقضی می‌شوند.
<?php
final class EnsureIdempotency
{
    public function handle(Request $request, Closure $next): Response
    {
        $key = $request->header('Idempotency-Key');
        if (! $key || ! $request->isMethod('POST')) {
            return $next($request);
        }

        $cacheKey  = "idem:{$request->user()->id}:{$key}";
        $signature = hash('sha256', $request->getContent());

        if ($saved = Cache::get($cacheKey)) {
            abort_if($saved['sig'] !== $signature, 422, 'Idempotency-Key reused with a different payload.');
            return response($saved['body'], $saved['status'], $saved['headers'] + ['Idempotent-Replayed' => 'true']);
        }

        $lock = Cache::lock("{$cacheKey}:lock", 30);
        abort_unless($lock->get(), 409, 'A request with this Idempotency-Key is in progress.');

        try {
            $response = $next($request);
            if ($response->getStatusCode() < 500) { // خطای سرور را ذخیره نکن تا retry ممکن باشد
                Cache::put($cacheKey, [
                    'sig'     => $signature,
                    'status'  => $response->getStatusCode(),
                    'body'    => $response->getContent(),
                    'headers' => ['Content-Type' => $response->headers->get('Content-Type')],
                ], now()->addDay());
            }
            return $response;
        } finally {
            $lock->release();
        }
    }
}

در عملیات مالی، علاوه بر idempotency key، یک unique constraint در دیتابیس (مثلاً روی (user_id, idempotency_key) یا شناسهٔ تراکنش درگاه) لایهٔ دفاعی نهایی است، چون cache ممکن است پاک شود.

Content Negotiation

  • client با Accept: application/json قالب پاسخ مورد نظر و با Content-Type قالب بدنهٔ ارسالی را اعلام می‌کند. همچنین Accept-Language و Accept-Encoding (gzip، br).
  • سرور اگر قالب درخواستی را نداشت 406 Not Acceptable و اگر بدنهٔ ارسالی را نمی‌فهمید 415 Unsupported Media Type برمی‌گرداند.
  • وقتی پاسخ به هدری بستگی دارد، باید Vary: Accept (یا Vary: Accept-Language) تنظیم شود تا cacheها نسخه‌ها را قاطی نکنند.

در Laravel اگر client هدر Accept: application/json نفرستد، خطای validation یا احراز هویت ممکن است به‌جای JSON به redirect (302) تبدیل شود. در Laravel 11+ برای مسیرهای API می‌توان در bootstrap/app.php با $exceptions->shouldRenderJsonWhen(fn ($request) => $request->is('api/*')) رندر JSON را اجباری کرد.

CORS و مستندسازی با OpenAPI

CORS

Same-Origin Policy مرورگر اجازه نمی‌دهد JavaScript صفحه‌ای از https://app.example.com پاسخ درخواستی به origin دیگر (مثلاً https://api.example.com) را بخواند. CORS (Cross-Origin Resource Sharing) سازوکاری است که سرور با هدرها اعلام کند کدام originها مجازند.

OPTIONS /v1/orders HTTP/1.1                       ← preflight (چون متد PUT/DELETE یا هدر Authorization یا Content-Type: application/json دارد)
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 600
Vary: Origin
  • CORS را مرورگر اعمال می‌کند؛ curl، Postman و سرورها آن را نادیده می‌گیرند. پس CORS ابزار امنیتی سمت سرور نیست و جای احراز هویت را نمی‌گیرد.
  • Access-Control-Allow-Origin: * با Allow-Credentials: true مجاز نیست؛ برای ارسال cookie باید origin دقیق برگردانده شود.
  • در Laravel تنظیمات در config/cors.php است (با php artisan config:publish cors) و middleware HandleCors به‌طور پیش‌فرض فعال است.

Controller

<?php
namespace App\Http\Controllers\Api\V1;

use App\Actions\PlaceOrder;
use App\Http\Controllers\Controller;
use App\Http\Requests\{StoreOrderRequest, UpdateOrderRequest};
use App\Http\Resources\OrderResource;
use App\Models\Order;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Gate;

class OrderController extends Controller
{
    public function index(Request $request)
    {
        $orders = $request->user()->orders()          // scope به کاربر جاری ← ضد BOLA
            ->with('items')
            ->when($request->query('status'), fn ($q, $s) => $q->where('status', $s))
            ->latest('id')
            ->cursorPaginate(min($request->integer('per_page', 20), 100));

        return OrderResource::collection($orders);
    }

    public function store(StoreOrderRequest $request, PlaceOrder $placeOrder)
    {
        $order = $placeOrder->handle($request->user(), $request->validated());

        return (new OrderResource($order->load('items')))
            ->response()
            ->setStatusCode(201)
            ->header('Location', route('orders.show', $order));
    }

    public function show(Order $order)
    {
        Gate::authorize('view', $order);
        return new OrderResource($order->load('items'));
    }

    public function update(UpdateOrderRequest $request, Order $order)
    {
        $order->update($request->validated());
        return new OrderResource($order);
    }

    public function destroy(Order $order)
    {
        Gate::authorize('delete', $order);
        $order->delete();
        return response()->noContent(); // 204
    }
}

سوالات تشریحی

REST را تعریف کنید و قیدهای معماری آن را نام ببرید. قید Stateless چه مزایا و هزینه‌هایی دارد؟

تعریف: REST یک سبک معماری برای سیستم‌های توزیع‌شده است (Roy Fielding، ۲۰۰۰) که در آن هر چیز یک منبع با URI یکتاست و client با نمایشهای آن منبع از طریق یک رابط یکنواخت (متدهای HTTP) کار می‌کند. REST پروتکل یا استاندارد نیست.

قیدها:

  • Client–Server: جداسازی UI از داده و منطق.
  • Stateless: هر درخواست خودکفاست.
  • Cacheable: پاسخ‌ها قابلیت cache خود را اعلام می‌کنند.
  • Uniform Interface: شناسایی منابع، تغییر از طریق representation، پیام‌های خودتوصیف، HATEOAS.
  • Layered System: امکان وجود proxy، CDN و gateway بدون اطلاع client.
  • Code on Demand: اختیاری.

Stateless یعنی سرور state نشست client را بین درخواست‌ها نگه نمی‌دارد و هر درخواست (مثلاً با Bearer token) همهٔ اطلاعات لازم را دارد. دادهٔ منابع در دیتابیس مجاز است.

مزایا: scale افقی ساده (هر سرور پشت load balancer می‌تواند هر درخواست را پاسخ دهد، بدون sticky session)، تحمل خطا (از کار افتادن یک سرور نشستی را از بین نمی‌برد)، سادگی و قابلیت cache بهتر.

هزینه‌ها: هر درخواست بزرگ‌تر است (توکن و context تکرار می‌شود)، احراز هویت در هر درخواست تکرار می‌شود (lookup توکن یا verify امضای JWT)، و جریان‌های چندمرحله‌ای (wizard) باید state را در client یا به شکل منبع در سرور (مثلاً /carts/{id}) نگه دارند.

مدل بلوغ Richardson را شرح دهید. API موجود شما در کدام سطح است اگر همهٔ عملیات را با POST /api/users/action انجام دهد؟

تعریف: مدلی چهارسطحی برای سنجش میزان پایبندی API به اصول REST:

  • Level 0 — Swamp of POX: یک endpoint و معمولاً فقط POST؛ HTTP صرفاً تونل انتقال است (مثل SOAP یا XML-RPC).
  • Level 1 — Resources: منابع URI جداگانه دارند (/users/42)، اما متدها و status codeها درست استفاده نمی‌شوند.
  • Level 2 — HTTP Verbs: استفادهٔ درست از GET/POST/PUT/PATCH/DELETE با رعایت safe/idempotent، و status codeهای معنادار (201، 404، 409). اکثر APIهای «RESTful» در صنعت این‌جا هستند.
  • Level 3 — Hypermedia Controls: پاسخ‌ها شامل لینک‌هایی به اقدامات ممکن‌اند (HATEOAS)؛ client جریان را از پاسخ کشف می‌کند.

تحلیل مثال: POST /api/users/action با بدنه‌ای مثل {"action":"delete","id":5} منبع را تا حدی (users) جدا کرده ولی عمل را در بدنه رمز کرده است؛ این بین سطح 0 و 1 است و در واقع RPC روی HTTP محسوب می‌شود.

پیامدها: cache کار نمی‌کند (همه POST)، retry امن ممکن نیست (چون idempotent بودن قابل‌تشخیص نیست)، monitoring بر اساس status code بی‌معنی می‌شود و مستندسازی سخت است.

بهبود به Level 2: GET /users، GET /users/5، POST /users ← 201، PATCH /users/5، DELETE /users/5 ← 204، و خطاها با 404/422/409.

مفاهیم Safe و Idempotent را تعریف کنید و متدهای HTTP را از این نظر دسته‌بندی کنید. چرا این ویژگی‌ها در عمل مهم‌اند؟

Safe: متدی که client با آن درخواست تغییر وضعیت سرور را نمی‌دهد (فقط خواندن): GET، HEAD، OPTIONS.

Idempotent: اجرای N بارهٔ یک درخواست یکسان، همان اثر نهایی روی وضعیت سرور را دارد که اجرای یک‌باره. پاسخ می‌تواند متفاوت باشد.

  • Safe و idempotent: GET، HEAD، OPTIONS.
  • Idempotent ولی نه safe: PUT (جایگزینی با همان مقدار)، DELETE (بار دوم منبع همچنان حذف‌شده است، حتی اگر 404 برگردد).
  • هیچ‌کدام: POST (دو بار ارسال = دو منبع) و PATCH در حالت کلی (مثل «افزایش موجودی به اندازهٔ ۵»).

اهمیت عملی:

  • Retry امن: وقتی timeout رخ می‌دهد، client نمی‌داند درخواست اجرا شده یا نه. درخواست idempotent را می‌توان بی‌خطر تکرار کرد؛ HTTP clientها، proxyها و load balancerها هم فقط درخواست‌های idempotent را خودکار retry می‌کنند.
  • Caching و prefetch: مرورگر، crawler و CDN فرض می‌کنند GET بی‌خطر است؛ اگر GET تغییری ایجاد کند (مثلاً /delete?id=5)، crawler ممکن است داده‌ها را پاک کند.
  • امنیت: عملیات تغییردهنده با GET در برابر CSRF آسیب‌پذیرتر است (یک تگ تصویر کافی است).

راه‌حل برای POST: هدر Idempotency-Key که سرور با ذخیرهٔ نتیجهٔ اولین اجرا، POST را عملاً idempotent می‌کند.

تفاوت PUT، PATCH و POST را با مثال توضیح دهید. برای به‌روزرسانی فقط شمارهٔ تلفن کاربر کدام را انتخاب می‌کنید؟
  • POST: ایجاد منبع جدید زیر یک collection که سرور شناسه‌اش را تعیین می‌کند (POST /users ← 201 Created + Location: /users/42) یا اجرای پردازشی که در CRUD نمی‌گنجد. idempotent نیست.
  • PUT: ارسال نمایش کامل منبع برای جایگزینی در URI مشخص (یا ایجادش در آن URI اگر client شناسه را تعیین می‌کند). فیلدهای ارسال‌نشده باید به مقدار پیش‌فرض/null برگردند. idempotent است.
  • PATCH: ارسال تغییرات جزئی. قالب‌های استاندارد: JSON Merge Patch (RFC 7396) که شیء جزئی می‌فرستد و null یعنی حذف فیلد، و JSON Patch (RFC 6902) که فهرست عملیات (add، replace، remove) می‌فرستد. لزوماً idempotent نیست.
PUT /users/42      {"name":"Ali","email":"ali@x.com","phone":"0912..."}   ← همهٔ فیلدها
PATCH /users/42    {"phone":"0912..."}                                    ← فقط تغییر

انتخاب: برای تغییر فقط تلفن، PATCH مناسب است: payload کوچک‌تر، و مهم‌تر از آن، خطر lost update کمتر — با PUT، client باید کل منبع را بفرستد و اگر نسخهٔ قدیمی را خوانده باشد، تغییرات هم‌زمان دیگران در سایر فیلدها را بازنویسی می‌کند.

نکتهٔ پیاده‌سازی در Laravel: در PATCH از قوانین sometimes استفاده کنید تا فقط فیلدهای ارسال‌شده validate شوند، و برای جلوگیری از تعارض هم‌زمان از ETag و If-Match (پاسخ 412) استفاده کنید.

تفاوت status codeهای 400، 401، 403، 404، 409 و 422 را توضیح دهید و برای هر کدام یک مثال در یک API فروشگاهی بزنید.
  • 400 Bad Request: درخواست از نظر نحوی بدشکل است و سرور نمی‌تواند آن را تفسیر کند. مثال: بدنهٔ JSON نیمه‌کاره، یا ?page=abc.
  • 401 Unauthorized: در واقع یعنی unauthenticated: توکن ارسال نشده، نامعتبر یا منقضی است. پاسخ باید هدر WWW-Authenticate داشته باشد. مثال: درخواست GET /me بدون Bearer token.
  • 403 Forbidden: کاربر شناخته شده ولی اجازهٔ این عمل را ندارد. مثال: کاربر عادی DELETE /products/5 را می‌زند که فقط ادمین مجاز است.
  • 404 Not Found: منبع وجود ندارد. مثال: GET /orders/999999. گاهی برای منابع متعلق به دیگران هم به‌جای 403 از 404 استفاده می‌شود تا وجود منبع افشا نشود.
  • 409 Conflict: درخواست معتبر است اما با وضعیت فعلی منبع تعارض دارد. مثال: لغو سفارشی که قبلاً ارسال شده، یا ثبت‌نام با ایمیلی که قبلاً وجود دارد (برخی تیم‌ها برای ایمیل تکراری 422 را ترجیح می‌دهند؛ مهم یکدستی است).
  • 422 Unprocessable Content: نحو درست است ولی داده‌ها قوانین validation را نقض می‌کنند. مثال: quantity: -2 یا ایمیل نامعتبر. پیش‌فرض Laravel برای خطای validation.

چرا دقت مهم است؟ client بر اساس status تصمیم می‌گیرد: در 401 کاربر را به login یا refresh توکن می‌برد؛ در 403 پیام عدم دسترسی نشان می‌دهد؛ در 422 خطاها را کنار فیلدهای فرم نمایش می‌دهد؛ در 409 داده را دوباره می‌خواند. همهٔ 4xxها یعنی retry بدون تغییر درخواست بی‌فایده است، برخلاف 503 یا 429.

یک قالب استاندارد و یکدست برای پاسخ خطا در API طراحی کنید. RFC 9457 (Problem Details) چه فیلدهایی دارد و چرا استفاده از آن مفید است؟

اصل: همهٔ خطاها — validation، احراز هویت، not found، خطای سرور — باید یک ساختار ماشین‌خوان یکسان داشته باشند تا client یک‌بار parser بنویسد.

RFC 9457 (جانشین RFC 7807) قالب application/problem+json را تعریف می‌کند:

  • type: URI که نوع خطا را شناسایی می‌کند (ترجیحاً به مستندات اشاره کند)؛ پیش‌فرض about:blank.
  • title: خلاصهٔ انسانی ثابت برای آن نوع.
  • status: status code HTTP.
  • detail: توضیح مخصوص همین رخداد.
  • instance: URI این رخداد خاص.
  • فیلدهای اضافه (extension) مثل errors برای خطاهای فیلدها یا trace_id.
{
  "type": "https://api.shop.ir/problems/insufficient-stock",
  "title": "Insufficient stock",
  "status": 409,
  "detail": "Only 2 items of product 15 are available.",
  "instance": "/v1/orders",
  "product_id": 15,
  "available": 2,
  "trace_id": "01JC8X2M5Q"
}

مزایا: استاندارد است و ابزارها و کتابخانه‌ها آن را می‌شناسند؛ type پایدار به client اجازه می‌دهد بدون وابستگی به متن پیام (که ممکن است ترجمه یا تغییر کند) منطق بنویسد؛ قابل توسعه است.

نکات امنیتی: در خطاهای 5xx هرگز stack trace، کوئری یا مسیر فایل برنگردانید (APP_DEBUG=false)؛ به‌جایش trace_id بدهید که در لاگ‌ها قابل جستجو باشد. در Laravel این قالب با withExceptions و render در bootstrap/app.php پیاده می‌شود.

صفحه‌بندی offset-based و cursor-based را مقایسه کنید. برای فید یک اپ اجتماعی با میلیون‌ها پست کدام را انتخاب می‌کنید و چرا؟

Offset-based: ?page=500&per_page=20 ← LIMIT 20 OFFSET 9980.

  • مزایا: ساده، امکان پرش به صفحهٔ دلخواه و نمایش تعداد کل صفحات.
  • معایب: دیتابیس باید همهٔ ردیف‌های قبل از offset را اسکن و دور بریزد ← در صفحات عمیق بسیار کند؛ COUNT(*) روی جدول بزرگ گران است؛ با درج پست جدید در حین مرور، آیتم‌ها جابه‌جا شده و تکراری یا جاافتاده دیده می‌شوند.

Cursor/Keyset-based: client یک cursor مبهم (معمولاً base64 از مقدار ستون مرتب‌سازی آخرین آیتم) می‌فرستد ← WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20.

  • مزایا: با ایندکس مناسب، کارایی ثابت در هر عمق؛ پایدار در برابر درج‌های هم‌زمان.
  • معایب: پرش به صفحهٔ N و شمارش کل ممکن نیست؛ ترتیب باید بر ستون(های) یکتا و ایندکس‌دار باشد؛ مرتب‌سازی دلخواه کاربر پیچیده‌تر می‌شود.

انتخاب برای فید: Cursor-based. فید به‌صورت infinite scroll مصرف می‌شود (نیازی به «صفحهٔ ۵۰۰» نیست)، داده دائماً در حال درج است و حجم جدول زیاد است. ترتیب را با ستون ترکیبی (created_at, id) و ایندکس ترکیبی متناظر تعریف می‌کنیم تا ردیف‌های با زمان یکسان گم نشوند.

Post::query()->orderByDesc('created_at')->orderByDesc('id')->cursorPaginate(20);

در همهٔ حالات، per_page باید سقف داشته باشد (مثلاً ۱۰۰) تا client نتواند با per_page=1000000 سرور را از کار بیندازد.

روش‌های نسخه‌بندی API را با مزایا و معایب مقایسه کنید. چه تغییری breaking محسوب می‌شود و چگونه یک نسخه را بازنشسته می‌کنید؟

روش‌ها:

  • URI path (/v1/orders): رایج‌ترین؛ واضح، قابل‌تست در مرورگر، routing و cache ساده. ایراد نظری: نسخه بخشی از هویت منبع نیست.
  • Query parameter (?version=2): ساده ولی به‌راحتی فراموش یا حذف می‌شود.
  • Custom header (Api-Version: 2 یا تاریخ‌محور): URI تمیز؛ ولی کمتر قابل‌مشاهده و cache باید Vary داشته باشد.
  • Media type (Accept: application/vnd.shop.v2+json): نزدیک‌ترین به فلسفهٔ REST (نسخه‌بندی representation)، اما پیچیده‌تر برای مصرف‌کننده.

Breaking: حذف یا تغییر نام فیلد، تغییر نوع (عدد به رشته) یا معنای فیلد، اجباری کردن پارامتر، تغییر قالب خطا، تغییر URL یا رفتار احراز هویت. Non-breaking: افزودن endpoint، فیلد اختیاری در پاسخ یا پارامتر اختیاری (به شرط اینکه clientها فیلدهای ناشناخته را نادیده بگیرند — اصل tolerant reader).

بازنشستگی:

  1. اعلام عمومی و مستند مهاجرت؛ انتشار نسخهٔ جدید به‌موازات قدیمی.
  2. افزودن هدرهای Deprecation و Sunset (تاریخ خاموشی) به پاسخ‌های نسخهٔ قدیمی و لینک مستندات.
  3. پایش ترافیک نسخهٔ قدیمی به تفکیک client و تماس با مصرف‌کنندگان فعال.
  4. پس از تاریخ sunset، پاسخ 410 Gone با توضیح.

در Laravel: گروه‌های route با prefix('v1') و controller/Resource/Form Request جدا برای هر نسخه؛ لایهٔ دامنه (Actionها و مدل‌ها) مشترک می‌ماند.

OAuth 2.0 چیست؟ جریان Authorization Code با PKCE را شرح دهید و بگویید PKCE دقیقاً چه حمله‌ای را خنثی می‌کند. Client Credentials در چه شرایطی استفاده می‌شود؟

تعریف: OAuth 2.0 فریم‌ورکی برای تفویض دسترسی است: کاربر (Resource Owner) به یک Client اجازه می‌دهد بدون افشای رمز عبورش، با یک access token محدود به scope مشخص، به منابعش روی Resource Server دسترسی داشته باشد. توکن را Authorization Server صادر می‌کند. OAuth خودش پروتکل احراز هویت نیست؛ OpenID Connect با افزودن id_token این لایه را اضافه می‌کند.

Authorization Code + PKCE:

  1. client یک code_verifier تصادفی می‌سازد و code_challenge = BASE64URL(SHA256(verifier)) را حساب می‌کند.
  2. کاربر به /authorize هدایت می‌شود با client_id، redirect_uri، scope، state و code_challenge.
  3. کاربر login و رضایت می‌دهد؛ Authorization Server با یک code کوتاه‌عمر و یک‌بارمصرف به redirect_uri برمی‌گرداند. client مقدار state را بررسی می‌کند (ضد CSRF).
  4. client در کانال پشتی، code را همراه code_verifier به /token می‌فرستد.
  5. سرور بررسی می‌کند هش verifier با challenge برابر باشد و access token (و refresh token) صادر می‌کند.

حملهٔ خنثی‌شده: Authorization code interception — در اپ موبایل یا SPA، اپ مخرب ممکن است با ثبت همان custom URL scheme یا از طریق لاگ‌ها، code را رهگیری کند. بدون PKCE و در public clientها که secret ندارند، مهاجم می‌توانست code را با توکن عوض کند؛ با PKCE بدون داشتن code_verifier (که هرگز از دستگاه خارج نشده) تبادل شکست می‌خورد.

Client Credentials: ارتباط ماشین به ماشین بدون حضور کاربر؛ سرویس با client_id و client_secret مستقیماً توکن می‌گیرد. مثال: سرویس گزارش‌گیری که شبانه API سرویس فاکتور را صدا می‌زند.

منسوخ‌ها: Implicit flow و Password grant به دلیل افشای توکن و دریافت مستقیم رمز کاربر توصیه نمی‌شوند. در Laravel، Passport این grantها را پیاده‌سازی می‌کند.

ساختار JWT را توضیح دهید. مهم‌ترین اشتباهات امنیتی در استفاده از JWT چیست و مشکل لغو (revocation) توکن را چگونه حل می‌کنید؟

ساختار: سه بخش base64url که با نقطه جدا شده‌اند: header.payload.signature.

  • Header: الگوریتم (alg: HS256، RS256، ES256) و نوع.
  • Payload: claimها: iss، sub، aud، exp، iat، nbf، jti و claimهای سفارشی مثل scope.
  • Signature: امضای header.payload با secret (HMAC) یا کلید خصوصی (RSA/ECDSA). امضا یکپارچگی و اصالت را تضمین می‌کند، نه محرمانگی.

اشتباهات رایج:

  • قرار دادن اطلاعات حساس در payload با این تصور که رمز شده است؛ payload فقط encode شده و قابل خواندن است.
  • پذیرفتن alg: none یا algorithm confusion (استفاده از کلید عمومی RS256 به‌عنوان secret HS256). الگوریتم مورد انتظار را در سرور ثابت کنید.
  • بررسی نکردن exp، aud، iss.
  • secret ضعیف در HS256 (قابل brute-force آفلاین).
  • عمر طولانی access token (روزها یا ماه‌ها).
  • ذخیره در localStorage که با هر XSS قابل سرقت است.

مسئلهٔ revocation: JWT self-contained است و سرور بدون lookup آن را معتبر می‌داند؛ پس logout یا مسدود کردن کاربر فوراً اثر نمی‌کند. راه‌حل‌ها:

  • access token کوتاه‌عمر (۵–۱۵ دقیقه) + refresh token stateful با rotation که در سرور قابل لغو است.
  • Denylist بر اساس jti در Redis تا زمان انقضا (بخشی از مزیت stateless از دست می‌رود).
  • Token version در رکورد کاربر و claim متناظر؛ افزایش نسخه همهٔ توکن‌های قبلی را باطل می‌کند.

نکته: اگر یک اپلیکیشن monolith دارید، توکن opaque (مثل Sanctum) که در دیتابیس lookup می‌شود، ساده‌تر و قابل لغو فوری است؛ JWT در سیستم‌های توزیع‌شده که سرویس‌ها می‌خواهند بدون تماس با Authorization Server توکن را verify کنند ارزش دارد.

Laravel Sanctum و Passport را مقایسه کنید. برای (الف) SPA و اپ موبایل خود شرکت و (ب) پلتفرمی که می‌خواهد به اپ‌های شخص ثالث اجازهٔ دسترسی به دادهٔ کاربران بدهد، کدام را انتخاب می‌کنید؟

Sanctum: پکیج سبک احراز هویت API با دو قابلیت:

  • API tokens: توکن‌های opaque که هش آن‌ها در جدول personal_access_tokens ذخیره می‌شود، با abilities (شبیه scope) و انقضا؛ با $user->createToken() صادر و با auth:sanctum بررسی می‌شوند. لغو فوری با حذف رکورد.
  • SPA authentication: برای SPA first-party روی همان دامنهٔ اصلی (مثلاً app.shop.ir و api.shop.ir)، از session cookie و محافظت CSRF (دریافت /sanctum/csrf-cookie) استفاده می‌کند؛ هیچ توکنی در JS ذخیره نمی‌شود ← مقاوم در برابر سرقت توکن با XSS.

Passport: پیاده‌سازی کامل OAuth 2.0 Authorization Server: ثبت client، صفحهٔ رضایت، grantهای authorization code + PKCE، client credentials، refresh token و device؛ access tokenها به‌صورت JWT امضاشده.

انتخاب:

  • (الف) Sanctum: SPA با cookie-based authentication و اپ موبایل با API token (ترجیحاً با انقضا و ذخیره در Keychain/Keystore). نیازی به پیچیدگی OAuth نیست چون clientها متعلق به خود شما هستند.
  • (ب) Passport: اپ‌های شخص ثالث نباید رمز کاربران را ببینند؛ کاربر باید از طریق صفحهٔ رضایت با scopeهای مشخص دسترسی بدهد و بتواند آن را لغو کند — دقیقاً سناریوی OAuth 2.0 با Authorization Code + PKCE. برای ارتباط سرور به سرور شرکا هم client credentials.

نکته: اگر به SSO سازمانی نیاز دارید، ممکن است یک Identity Provider خارجی (Keycloak، Auth0 و …) با OpenID Connect انتخاب بهتری از ساختن Authorization Server باشد.

یک سناریو: کاربران اپ موبایل گزارش می‌دهند گاهی برای یک خرید دو بار پول از حسابشان کسر شده است. علت محتمل چیست و چه راه‌حلی در سطح API پیاده می‌کنید؟

علت محتمل: POST /payments یا POST /orders idempotent نیست. درخواست به سرور رسیده و پردازش شده، اما پاسخ به دلیل timeout یا قطعی شبکهٔ موبایل به client نرسیده است؛ client (یا کاربر با زدن دوبارهٔ دکمه، یا کتابخانهٔ HTTP با retry خودکار) همان درخواست را دوباره فرستاده و سرور آن را عملیات جدیدی تلقی کرده است.

راه‌حل: Idempotency Key

  1. client برای هر قصد خرید یک UUID تولید و در هدر Idempotency-Key می‌فرستد و در retryها همان کلید را تکرار می‌کند.
  2. سرور (در middleware) کلید را در محدودهٔ کاربر بررسی می‌کند: اگر جدید است، به‌صورت اتمیک (unique constraint یا lock در Redis) آن را رزرو، عملیات را اجرا و پاسخ (status و body) را همراه هش بدنهٔ درخواست ذخیره می‌کند.
  3. درخواست تکراری با همان کلید و بدنه: همان پاسخ ذخیره‌شده بدون اجرای مجدد برگردانده می‌شود.
  4. درخواست هم‌زمان با کلیدی که در حال پردازش است: 409؛ کلید یکسان با بدنهٔ متفاوت: 422.
  5. کلیدها پس از مثلاً ۲۴ ساعت منقضی می‌شوند؛ خطاهای 5xx ذخیره نمی‌شوند تا retry ممکن باشد.

لایه‌های تکمیلی:

  • Unique constraint در دیتابیس روی شناسهٔ تراکنش/کلید به‌عنوان دفاع نهایی.
  • اجرای عملیات در تراکنش دیتابیس و در صورت نیاز lockForUpdate روی سفارش.
  • ارسال کلید idempotency به درگاه پرداخت (اگر پشتیبانی کند) و تطبیق با callback درگاه.
  • در UI غیرفعال کردن دکمه پس از کلیک — مفید ولی کافی نیست.

این الگو یک POST ناامن را برای retry عملاً idempotent می‌کند — همان کاری که Stripe و بسیاری از APIهای پرداخت انجام می‌دهند.

Caching در REST API را توضیح دهید: نقش Cache-Control، ETag و Last-Modified چیست؟ تفاوت no-cache و no-store و نحوهٔ جلوگیری از lost update با If-Match را بنویسید.

دو مکانیزم اصلی:

  • Expiration (تازگی): Cache-Control: max-age=60 یعنی تا ۶۰ ثانیه بدون تماس با سرور از cache استفاده کن. s-maxage برای CDN، public/private برای مشخص کردن cache مشترک یا فقط مرورگر.
  • Validation (اعتبارسنجی): پس از stale شدن، client با درخواست شرطی می‌پرسد «تغییر کرده؟». سرور در پاسخ اول ETag: "v7" (شناسهٔ نسخه) یا Last-Modified می‌فرستد؛ client بعداً If-None-Match: "v7" یا If-Modified-Since می‌فرستد و اگر تغییری نباشد، 304 Not Modified بدون بدنه دریافت می‌کند.

no-cache در برابر no-store: no-cache یعنی ذخیره مجاز است اما قبل از هر استفاده باید با سرور revalidate شود (معمولاً با ETag)؛ no-store یعنی هیچ‌جا ذخیره نشود — برای اطلاعات حساس مثل موجودی حساب یا توکن. پاسخ‌های شخصی باید حداقل private باشند تا CDN آن‌ها را به کاربر دیگر ندهد.

ETag در برابر Last-Modified: Last-Modified دقت ثانیه دارد و به ساعت سرور وابسته است؛ ETag دقیق‌تر است و می‌تواند هش محتوا یا نسخهٔ رکورد باشد.

Optimistic concurrency:

GET /products/15        → 200, ETag: "v7"
PUT /products/15
If-Match: "v7"          → 200 (اگر هنوز v7 است) یا 412 Precondition Failed

دو ادمین هم‌زمان محصول را ویرایش می‌کنند؛ اولی موفق می‌شود و نسخه به v8 می‌رسد؛ دومی با If-Match: "v7" پاسخ 412 می‌گیرد و باید دادهٔ تازه را بخواند — بدون این مکانیزم تغییرات اولی بی‌صدا بازنویسی می‌شد (lost update).

در Laravel: middleware cache.headers (مثلاً public;max_age=60;etag)، یا محاسبهٔ دستی ETag از updated_at/ستون version و بررسی $request->getETags().

CORS چیست و چرا وجود دارد؟ یک سناریو: frontend روی https://app.shop.ir هنگام فراخوانی https://api.shop.ir خطای CORS می‌گیرد اما همان درخواست در Postman کار می‌کند. توضیح دهید و رفع کنید.

تعریف: مرورگر با Same-Origin Policy اجازه نمی‌دهد اسکریپت یک origin (ترکیب scheme + host + port) پاسخ درخواست به origin دیگر را بخواند. CORS مکانیزمی است که سرور با هدرهای Access-Control-Allow-* صراحتاً اجازهٔ دسترسی originهای مشخص را اعلام کند. هدف: جلوگیری از اینکه سایت مخرب با استفاده از cookieهای کاربر، داده‌های او را از سایت دیگری بخواند.

چرا Postman کار می‌کند؟ CORS را فقط مرورگر اعمال می‌کند. Postman و curl مرورگر نیستند و این سیاست را ندارند. پس CORS ابزار امنیتی سمت سرور برای جلوگیری از دسترسی نیست.

علل محتمل:

  • origin frontend در allowed_origins سرور نیست.
  • درخواست به دلیل هدر Authorization، Content-Type: application/json یا متد PUT/DELETE، preflight (OPTIONS) می‌فرستد و سرور به OPTIONS پاسخ درست نمی‌دهد (مثلاً middleware احراز هویت، OPTIONS را 401 می‌کند یا route آن وجود ندارد).
  • ارسال cookie (credentials: 'include') در حالی که سرور Allow-Origin: * برمی‌گرداند یا Allow-Credentials: true نمی‌دهد.
  • خطای 500 در سرور که پاسخش هدرهای CORS ندارد و مرورگر آن را به‌عنوان خطای CORS نشان می‌دهد.

رفع در Laravel: در config/cors.php: 'paths' => ['api/*', 'sanctum/csrf-cookie']، 'allowed_origins' => ['https://app.shop.ir']، و در صورت استفاده از cookie، 'supports_credentials' => true. middleware HandleCors به‌طور پیش‌فرض در پشتهٔ global است و preflight را پاسخ می‌دهد. برای عیب‌یابی، تب Network مرورگر را برای درخواست OPTIONS و هدرهای پاسخ بررسی کنید.

هشدار: «رفع» با * برای همه‌چیز، به‌خصوص همراه credentials، ناامن است؛ از allow-list دقیق استفاده کنید.

کد زیر چه مشکلاتی دارد؟ آن را بازنویسی کنید. public function update(Request $r, $id) { $o = Order::find($id); $o->update($r->all()); return response()->json(['success' => true, 'data' => $o], 200); }

مشکلات:

  1. Mass assignment: $r->all() هر فیلدی را می‌پذیرد؛ مهاجم می‌تواند status، total یا user_id را تغییر دهد (اگر $fillable/$guarded درست نباشد).
  2. بدون validation: داده‌های نامعتبر مستقیم به دیتابیس می‌روند.
  3. BOLA/IDOR: هیچ بررسی مالکیت یا مجوزی وجود ندارد؛ هر کاربر می‌تواند سفارش دیگران را با تغییر $id ویرایش کند.
  4. Null pointer: اگر سفارش وجود نداشته باشد، find مقدار null برمی‌گرداند و فراخوانی update روی null خطای 500 می‌دهد، به‌جای 404.
  5. افشای داده: برگرداندن مستقیم مدل همهٔ ستون‌ها (شاید فیلدهای داخلی) را لو می‌دهد و قرارداد خروجی را به schema دیتابیس گره می‌زند.
  6. قالب پاسخ: wrapper success: true با status ثابت 200 الگوی ضعیفی است؛ موفقیت/شکست را status code بیان می‌کند.

بازنویسی:

<?php
// routes/api.php: Route::apiResource('orders', OrderController::class)->middleware('auth:sanctum');

class UpdateOrderRequest extends FormRequest
{
    public function authorize(): bool
    {
        return $this->user()->can('update', $this->route('order'));
    }

    public function rules(): array
    {
        return [
            'shipping_address_id' => ['sometimes', 'integer',
                Rule::exists('addresses', 'id')->where('user_id', $this->user()->id)],
            'note' => ['sometimes', 'nullable', 'string', 'max:500'],
        ];
    }
}

public function update(UpdateOrderRequest $request, Order $order): OrderResource
{
    $order->update($request->validated());   // فقط فیلدهای مجاز
    return new OrderResource($order);         // 200 با قالب کنترل‌شده
}

Route model binding برای سفارش ناموجود خودکار 404، Policy در authorize() برای عدم مالکیت 403 و Form Request برای داده نامعتبر 422 برمی‌گرداند. اگر سفارش در وضعیت غیرقابل‌ویرایش است (مثلاً ارسال‌شده)، Policy یا منطق دامنه باید 409 بدهد.

Rate limiting چیست و چرا لازم است؟ الگوریتم‌های رایج را مقایسه کنید و نحوهٔ پیاده‌سازی و اطلاع‌رسانی آن به client را در Laravel توضیح دهید.

تعریف: محدود کردن تعداد درخواست‌های یک شناسه (کاربر، API key، IP یا ترکیب آن‌ها) در یک بازهٔ زمانی.

چرا؟ جلوگیری از brute-force روی login و OTP، کاهش اثر DoS و scraping، تقسیم عادلانهٔ منابع بین مشتریان، کنترل هزینه (مثلاً APIهای پولی پشت سرویس) و پیاده‌سازی پلن‌های تجاری (Free: ۶۰/دقیقه، Pro: ۱۰۰۰/دقیقه).

الگوریتم‌ها:

  • Fixed window: شمارنده در هر دقیقهٔ تقویمی؛ ساده ولی در مرز پنجره‌ها تا دو برابر سقف اجازه می‌دهد.
  • Sliding window: پنجرهٔ متحرک؛ دقیق‌تر با هزینهٔ حافظه/محاسبهٔ بیشتر.
  • Token bucket: سطلی با ظرفیت B که با نرخ R پر می‌شود؛ اجازهٔ burst کوتاه با میانگین کنترل‌شده — رایج در API gatewayها.
  • Leaky bucket: خروجی با نرخ ثابت؛ هموارسازی ترافیک.

اطلاع‌رسانی: پاسخ 429 Too Many Requests با هدر Retry-After و معمولاً X-RateLimit-Limit و X-RateLimit-Remaining. client باید با exponential backoff و jitter پاسخ دهد.

Laravel:

RateLimiter::for('api', fn (Request $r) => $r->user()
    ? Limit::perMinute($r->user()->isPro() ? 1000 : 60)->by($r->user()->id)
    : Limit::perMinute(20)->by($r->ip()));

Route::middleware(['auth:sanctum', 'throttle:api'])->group(/* ... */);

middleware throttle هدرها و پاسخ 429 را خودکار تولید می‌کند. در محیط چندسروری، cache store باید مشترک باشد (Redis). نکته: محدودیت فقط بر اساس IP برای کاربرانی که پشت NAT مشترک (شبکهٔ شرکت یا اپراتور موبایل) هستند، مشکل‌ساز است؛ بهتر است برای کاربران احراز شده بر اساس user ID محدود کنید.

REST، GraphQL و gRPC را مقایسه کنید. برای یک اپ موبایل با صفحاتی که داده‌های متنوعی از چند منبع نیاز دارند، کدام را پیشنهاد می‌دهید؟

REST: منبع‌محور با متدهای HTTP، معمولاً JSON. مزایا: سادگی، HTTP caching و CDN، ابزارهای فراوان، status codeهای معنادار. معایب: over-fetching (فیلدهای اضافه) و under-fetching (چند round-trip برای جمع کردن داده‌های مرتبط).

GraphQL: یک endpoint با schema تایپ‌دار؛ client دقیقاً فیلدها و روابط لازم را در یک کوئری می‌خواهد. مزایا: حل over/under-fetching، تکامل schema بدون نسخه‌بندی، introspection. معایب: HTTP caching دشوار (POST به یک URL)، خطر N+1 در resolverها (نیاز به DataLoader/batching)، کوئری‌های پرهزینه (نیاز به محدودیت عمق و پیچیدگی)، authorization در سطح فیلد، و معمولاً 200 حتی برای خطا.

gRPC: RPC روی HTTP/2 با protobuf باینری و قرارداد سخت؛ کارایی بالا و streaming. معایب: پشتیبانی محدود مرورگر، دیباگ سخت‌تر، نبود HTTP cache. مناسب ارتباط داخلی سرویس‌ها.

پیشنهاد برای اپ موبایل: دو گزینهٔ معقول:

  • GraphQL اگر صفحات متنوع و نیازهای داده‌ای سریعاً تغییر می‌کنند و چند client (iOS، Android، وب) با نیازهای متفاوت وجود دارد؛ کاهش round-trip روی شبکهٔ موبایل ارزشمند است.
  • یا REST با الگوی BFF (Backend for Frontend): endpointهای مخصوص صفحه که داده‌های تجمیعی برمی‌گردانند، به‌همراه ?include= و sparse fieldsets؛ سادگی و cache‌پذیری REST حفظ می‌شود.

ارتباط بین سرویس‌های داخلی پشت آن می‌تواند gRPC باشد. انتخاب نهایی به مهارت تیم، نیاز به cache و پیچیدگی قابل‌پذیرش بستگی دارد.

یک endpoint برای ثبت سفارش طراحی کنید: URI، متد، بدنهٔ درخواست، پاسخ‌های موفق و خطا، و اجزای پیاده‌سازی آن در Laravel را مشخص کنید. اگر پردازش سفارش طولانی باشد چه تغییری می‌دهید؟

قرارداد:

POST /api/v1/orders
Authorization: Bearer ...
Idempotency-Key: 6f1c2e0a-...
Content-Type: application/json
Accept: application/json

{"shipping_address_id": 12, "items": [{"product_id": 15, "quantity": 2}]}
  • 201 Created + Location: /api/v1/orders/981 + بدنهٔ OrderResource.
  • 401 بدون توکن؛ 403 اگر کاربر مجاز به خرید نیست (مثلاً حساب مسدود).
  • 422 برای خطای validation (Problem Details با errors).
  • 409 برای موجودی ناکافی یا کلید idempotency در حال پردازش.
  • 429 عبور از rate limit؛ 415 اگر Content-Type JSON نیست.

اجزای Laravel:

  • Route: Route::apiResource('orders', OrderController::class) در گروه prefix('v1') با middlewareهای auth:sanctum، throttle:api و middleware سفارشی idempotency.
  • StoreOrderRequest: قوانین validation و authorize() با Policy.
  • یک Action/Service (PlaceOrder) که در DB::transaction موجودی را با lockForUpdate بررسی و کم می‌کند، سفارش و آیتم‌ها را می‌سازد و event OrderPlaced را dispatch می‌کند (ارسال ایمیل و ... در listenerهای queue‌شده).
  • OrderResource برای خروجی؛ رندر یکدست خطاها در bootstrap/app.php.
  • تست Feature با postJson و assertCreated، assertUnprocessable.

پردازش طولانی (مثلاً هماهنگی با انبار یا تأیید تقلب): مدل asynchronous با 202 Accepted:

HTTP/1.1 202 Accepted
Location: /api/v1/orders/981
{"id": 981, "status": "processing"}

سفارش با وضعیت processing ثبت و یک Job در صف قرار می‌گیرد. client با polling روی GET /orders/981 (همراه Retry-After)، یا از طریق WebSocket/SSE یا webhook از نتیجه مطلع می‌شود. این کار timeout در لایه‌های proxy را حذف می‌کند و API را در برابر بار ناگهانی مقاوم‌تر می‌کند.

خلاصه برای مرور سریع

REST

  • سبک معماری (Fielding)، نه پروتکل.
  • ۶ قید: Client-Server، Stateless، Cacheable، Uniform Interface، Layered، Code on Demand (اختیاری).
  • Uniform Interface: URI منبع، representation، self-descriptive، HATEOAS.
  • Stateless = بدون session state در سرور ⇒ scale افقی.
  • Richardson: 0 (POX) ← 1 (Resources) ← 2 (Verbs) ← 3 (Hypermedia).

URI

  • اسم جمع، kebab-case، بدون فعل و پسوند.
  • Nesting یک سطح؛ فیلتر/sort/page در query.
  • ?filter[status]=paid&sort=-created_at&fields[users]=id,name&include=author

متدها

متدSafeIdem.

  • PUT = جایگزینی کامل؛ PATCH = جزئی (Merge Patch / JSON Patch)؛ POST = ایجاد، سرور ID می‌دهد.

Status

  • 200 OK · 201 Created + Location · 202 Accepted (async) · 204 No Content.
  • 301/308 دائمی · 302/307 موقت (307/308 متد را حفظ می‌کنند) · 304 Not Modified.
  • 400 بدشکل · 401 احراز نشده · 403 مجوز ندارد · 404 · 405 + Allow · 409 تعارض وضعیت · 412 If-Match شکست · 415 Content-Type · 422 validation · 429 + Retry-After.
  • 500 باگ · 502 upstream بد · 503 در دسترس نیست · 504 upstream timeout.

خطا

  • RFC 9457 · application/problem+json · type، title، status، detail، instance + extensions.
  • بدون stack trace؛ trace_id بدهید.

صفحه‌بندی

  • Offset: پرش به صفحه، کند در عمق، ناپایدار.
  • Cursor: ثابت و پایدار، بدون پرش؛ ORDER BY یکتا + ایندکس.
  • Laravel: paginate، simplePaginate، cursorPaginate؛ سقف per_page.

نسخه‌بندی

  • URI (رایج) · Query · Header · Media type (RESTfulترین).
  • Breaking: حذف/تغییر نام/نوع فیلد، اجباری کردن پارامتر.
  • بازنشستگی: Deprecation، Sunset، 410 Gone.

Auth

  • 401 = authentication، 403 = authorization.
  • OAuth 2.0 = delegated authorization؛ OIDC = احراز هویت.
  • Auth Code + PKCE (کاربرمحور)، Client Credentials (M2M)؛ Implicit و Password منسوخ.
  • PKCE ضد code interception؛ state ضد CSRF.
  • JWT = header.payload.signature؛ امضا شده نه رمز شده؛ alg را ثابت کنید؛ exp/aud/iss؛ لغو سخت ⇒ عمر کوتاه + refresh rotation.
  • Sanctum: token opaque + SPA cookie؛ Passport: OAuth2 server کامل.
  • BOLA/IDOR: همیشه مالکیت شیء را چک کنید (Policy).

عملیاتی

  • Rate limit: fixed/sliding window، token/leaky bucket؛ 429 + Retry-After؛ Redis مشترک.
  • Cache-Control: max-age، s-maxage، private/public، no-cache (revalidate)، no-store (هرگز).
  • ETag + If-None-Match ⇒ 304؛ If-Match ⇒ 412 (ضد lost update).
  • Idempotency-Key برای POST: ذخیرهٔ اتمیک پاسخ، 409 در حال پردازش، 422 بدنهٔ متفاوت.
  • Content negotiation: Accept/Content-Type، 406/415، Vary.
  • CORS را مرورگر اعمال می‌کند؛ preflight OPTIONS؛ * با credentials ممنوع.
  • OpenAPI 3.x: قرارداد ماشین‌خوان؛ design-first در برابر code-first.
